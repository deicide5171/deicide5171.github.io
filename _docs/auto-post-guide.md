# 데일리 기술 포스트 자동 생성 가이드 (v6 — 빌더 학습 모드)

이 문서는 자동 생성되는 기술 블로그 포스트의 **공식 스펙**이다.
자동화 에이전트(클라우드 루틴)는 이 파일이 저장소에 존재하면 아래 규칙을 최우선으로 따른다.
형식·규칙을 바꾸고 싶으면 이 파일만 수정하면 된다.

## 개요

### 이 파이프라인의 목적 (2026-09-28 전면 변경)

**목적이 "검색 트래픽 확보"에서 "저자 본인의 학습"으로 바뀌었다.**
저자는 생성된 글을 직접 읽고 공부한 뒤 네이버에 올린다. 따라서 양보다 밀도가 중요하고,
얕은 입문 나열식 글("~가 뭔가요" 수준의 사전적 설명)은 더 이상 만들지 않는다.

### 관통 개념: AI 시대의 빌더(Builder)

모든 글은 하나의 목표를 향한다 —
**"사용자의 요구사항만 들어도 머릿속에서 전체 프로젝트의 구성과 프로세스가 떠오르는 상태"**.

그래서 개별 기술을 소개하는 데서 끝내지 말고, 언제나 **전체 시스템 그림 안에서의 위치**를 함께 그린다.
글 하나를 읽고 나면 "아, 이건 이런 요구사항이 왔을 때, 이 자리에, 이런 이유로 넣는 것이구나"가
남아야 한다. 이것이 이 파이프라인의 유일한 품질 기준이다.

### 운영 방식

- **하루 3편** 생성 → 저자가 그날 네이버에 3건 올린다 (깃헙 블로그에는 자동 게시).
- 각 편은 두 가지 형식으로 생성한다.
  1. 깃헙 블로그용 마크다운 → `_posts/YYYY-MM-DD-<slug>-post.md`
  2. 네이버 블로그용 HTML → `_naver/YYYY-MM-DD-<slug>.html`
- **날짜 기준: 한국시간(KST)** — `TZ=Asia/Seoul date +%F` 를 파일명·브랜치·"오늘" 판정에 모두 사용한다.
  저자가 한국에 있으므로 모든 날짜·시각 계산과 보고는 KST 기준으로 한다.
  (실행 시각 01:30 UTC = KST 10:30 = 머신 로컬 Kolkata 07:00 — 셋 다 같은 날짜라 안전하다.
  만약 실행 시각을 저녁으로 옮기면 KST가 먼저 날짜를 넘기므로, 그때는 이 기준을 다시 점검할 것.)
- **전달 방식**: 하루 1개 브랜치 `auto-post/YYYY-MM-DD` + master 대상 PR 1개, 생성 직후 자동 merge.
- `_naver/`, `_docs/` 폴더는 Jekyll 빌드에서 제외된다(블로그에 노출 안 됨).
- 2026-09-28에 네이버 대기열(미게시 290편)은 폐기했다. 그 글들은 깃헙 블로그에만 남아 있으며
  네이버에는 올리지 않는다. 네이버에는 이제 **새로 만드는 빌더 관점 글만** 하루 3건 올라간다.

## 필러 구성 (하루 3편)

| 슬롯 | 필러 | categories 값 | 내용 |
|---|---|---|---|
| 1 | **AI** | `ai` | AI 시대 빌더에게 필요한 최신·핵심 주제 |
| 2 | **GIS** | `gis` | 공간 기술 최신·핵심 주제 |
| 3 | **시스템 설계 ↔ 개발 전략** (하루씩 교대) | `system-design` / `dev-strategy` | 홀수일 `system-design`, 짝수일 `dev-strategy` |

- `dev-strategy`는 2026-09-28에 신설한 카테고리다: 기술 선택과 아키텍처 의사결정, 트레이드오프 판단,
  프로젝트 구성·진행 프로세스, 팀·협업 구조, 마이그레이션·리팩터링 전략 등
  **"무엇을 어떻게 지을 것인가"의 판단 영역**을 다룬다.
- 기존 카테고리(`infra`, `database`, `frontend`, `backend`, `it-trend`, `web-dev`, `dev-insight`)는
  과거 글 전용이며, 새 글에는 위 4개(`ai`, `gis`, `system-design`, `dev-strategy`)만 쓴다.
  단, 내용상 인프라·DB·프론트·백엔드 지식이 필요하면 위 4개 카테고리 글 안에서 자유롭게 다룬다.

### 주제 선정 기준 — "요즘 핫하고, 빌더에게 중요한 것"만

1. **WebSearch로 최신성 확인 필수.** 생성 시점 기준 최근 1~3개월의 릴리스·발표·업계 논쟁을 검색해
   그중 빌더의 판단에 실제로 영향을 주는 것을 고른다. 유행어만 좇지 말고 "이게 내 설계 판단을 바꾸는가"를 묻는다.
2. **얕은 입문글 금지.** "~가 뭔가요", "~ 설치하기" 같은 사전적·절차적 글은 만들지 않는다.
   이미 그런 글이 693편 있고, 목적이 학습으로 바뀌었다.
3. **기존 693편 전수 대조.** 아래 "중복 절대 금지" 게이트를 그대로 적용한다.
   같은 기술을 다루더라도 반드시 빌더 관점의 새 각도여야 한다.

### 빌더 관점 — 모든 글에 반드시 들어가는 4요소

주제가 무엇이든 아래 네 가지가 본문에 녹아 있어야 한다. 하나라도 빠지면 미완성으로 보고 보강한다.

1. **어떤 요구사항에서 출발하는가** — 사용자·기획자의 말(예: "지도에서 반경 안 매장을 보여주세요")로
   시작해, 그 말이 어떤 기술 문제로 번역되는지 보여준다.
2. **전체 시스템에서의 위치** — 이 기술의 앞단과 뒷단에 무엇이 오는가. 데이터가 어디서 들어와
   어디로 나가는가. 가능하면 SVG 구조도로 그린다.
3. **선택의 트레이드오프** — 대안은 무엇이고 왜 이것을 고르는가. 언제 쓰면 안 되는가.
   비교 표를 적극 활용한다.
4. **실제 프로젝트 진행 순서** — 이걸 쓰기로 했다면 무엇부터 손대고, 어디서 막히고, 무엇을 먼저 검증하는가.

## 중복 절대 금지 — 필수 감사 (예외 없음, merge 전 반드시 통과)

**배경**: 과거 두 차례(2026-08-20, 2026-08-21~22) 대량 배치 중 세션이 rate limit로 끊겼다가 재개되는 과정에서, 이미 존재하는 글과 주제가 사실상 동일한 글이 생성·merge된 사고가 있었다(사후에 PR로 발견·수정). "주의해서 피한다"는 지시만으로는 재발을 막지 못한다는 것이 증명됐으므로, 아래 절차를 **기계적으로, 예외 없이** 수행한다. 특히 여러 세션에 걸친 이어쓰기(resume)나 대량 선작성 배치에서 더 취약하니 그럴수록 더 엄격히 지킨다.

1. **글을 만들기 직전**: 반드시 `git pull origin master`로 최신 상태를 받은 뒤 `_posts/` 전체에서 title과 slug를 추출해 스크래치 파일(예: `/tmp/.../existing-titles.txt`)로 만든다. 로컬 캐시나 기억에 의존하지 말고 매번 origin/master 기준으로 새로 만든다.
2. **한 편을 완성할 때마다**: 그 글의 title/slug를 즉시 그 목록에 추가한다 (같은 세션에서 방금 만든 글과의 중복도 방지).
3. **PR을 merge하기 직전, 반드시 최종 감사를 1회 수행한다** (이번 실행에서 새로 만든 글 전체 대상):
   - 각 새 글의 slug를 kebab-case 토큰으로 분리(날짜·`-post` 제거, 불용어 제거)
   - **같은 categories 값**을 가진 기존 글(오늘 새로 만든 것 포함 전체)과 토큰 집합을 비교해 자카드 유사도를 계산
   - 공통 토큰 2개 이상, 또는 유사도 0.35 이상인 쌍이 하나라도 나오면: 두 글의 excerpt를 직접 읽고 실제로 같은 핵심 주제·같은 결론을 다루는지 판단한다
   - **실제 중복(같은 앵글, 같은 핵심 개념 재탕)으로 판단되면 그 자리에서 새 글을 다른 세부 주제로 즉시 교체(재작성)한다.** 판단이 애매하면 안전한 쪽(교체)을 택한다. "이미 만들어버렸으니 그냥 둔다"는 선택지가 아니다.
   - 감사를 생략하고 merge하지 않는다. rate limit이 임박해도 이 단계는 건너뛰지 않는다 — 시간이 부족하면 감사를 마친 편까지만 push·PR·merge하고, 감사 못 한 편은 다음 실행이 이어받도록 남겨둔다(생성했지만 감사 전이면 merge 대상에서 제외).
4. **여러 날짜를 한 번에 처리하는 선작성 배치**에서는 이 감사를 **날짜별로 그 날짜의 PR을 merge하기 직전마다** 수행한다 — 마지막에 몰아서 한 번만 하지 않는다.
5. 이 감사는 사람이 나중에 검수하라고 미루는 절차가 아니라, **에이전트 자신이 merge 권한을 쓰기 전에 스스로 통과해야 하는 게이트**다.

## 중복 방지 & 이어쓰기 (배치 재개)

1. `TODAY=$(TZ=Asia/Seoul date +%F)`
2. `git fetch origin` 후 `refs/heads/auto-post/${TODAY}` 존재 확인
   - 있으면: 해당 브랜치를 checkout하고 **이어쓰기 모드** — `_posts/${TODAY}-*.md`들의 `categories`를 세어 부족한 슬롯만 생성
   - 없으면: master에서 새 브랜치 생성
3. 하루 3편(ai 1, gis 1, system-design 또는 dev-strategy 1)이 다 있으면 "오늘 배치 완료됨"만 보고하고 종료

## 형식 1: 깃헙 블로그용 마크다운

경로: `_posts/YYYY-MM-DD-<slug>-post.md` (slug는 짧은 영어 kebab-case)

```markdown
---
layout: single
title: "한국어 제목"
date: YYYY-MM-DD HH:MM:00 +0530
categories: ai            # 필러 값 하나
tags: ["소문자", "핵심", "키워드", "3~6개"]
toc: true
toc_sticky: true
excerpt: "글 요약 한 문장"
---
```

- `date`의 시각 (하루 3편): ai 12:50 / gis 12:45 / system-design 또는 dev-strategy 12:40
- 본문 구조: 도입(왜 지금, 2~3문단) → 핵심 개념(## 섹션 2~4개, 표·비교 활용) → 코드/설정 예제 1~2개(언어 명시) → 실무 포인트/주의사항 → 마무리 요약(3줄 불릿) → 참고 자료(공식 문서 위주)
- **분량: 한국어 2,000~3,500자 (코드블록 제외 본문 기준) — 하한선 2,000자는 예외 없는 필수 조건**
  (학습용으로 목적이 바뀌었으므로 기존 1,500자에서 상향했다.)
  - 입문·개념·트러블슈팅 글도 예외가 아니다. "초보자용이라 짧게"는 허용되지 않는다.
    (2026-08-31~09-20 배치에서 300편 전부 평균 888자로 미달한 사고가 있었다. 검색 노출에서 얇은 콘텐츠는
    불리하므로 분량 미달은 이 파이프라인의 목적 자체를 훼손한다.)
  - **한 편을 커밋하기 전에 반드시 자체 측정할 것**: frontmatter를 제외한 본문에서 코드블록을 제거하고
    공백을 뺀 글자수가 2,000자 이상인지 확인한다. 미달이면 커밋하지 말고 내용을 보강한다
    (배경 설명, 비교 표, 실무 사례, 함정 사례, 대안 비교 등을 추가).
  - 입문 글에서 분량을 채우는 정석: 왜 이 개념이 필요해졌는지의 맥락 → 잘못된 접근과 그 결과 →
    올바른 접근 → 코드 예제 → 흔한 실수 3가지 이상 → 다음에 배울 것 안내
- **이미지(SVG 다이어그램)**: GIS 글은 **필수 1개 이상 — 누락 시 그 글은 미완성으로 간주하고 커밋하지 않는다**
  (과거 배치에서 GIS 글의 40~70%만 이미지를 포함한 이력이 있으니, GIS 글은 커밋 직전 SVG 존재를 확인할 것).
  다른 필러도 개념도·구조도가 유용하면 포함.
  에이전트가 직접 그린 SVG를 `assets/images/posts/YYYY-MM-DD-<slug>-<n>.svg`에 저장한다.
  - SVG 루트에 **반드시 `viewBox="0 0 800 450" width="800" height="450"`를 모두 명시** (width/height가 없으면 브라우저가 300px로 작게 렌더링함)
  - MD 삽입은 마크다운 `![]()` 문법 대신 **HTML 태그로 본문 폭을 꽉 채운다**:
    `<img src="/assets/images/posts/파일명.svg" alt="설명" style="width:100%;">`
  - 네이버 HTML에서도 `<img src="https://deicide5171.github.io/assets/images/posts/파일명.svg" style="width:100%;">`
  - 내용 예: 아키텍처 구조도, 좌표계·타일 피라미드 개념도, 데이터 흐름도. 간결한 도형+한글 라벨 위주.
    **외부 이미지 핫링크는 저작권 문제로 금지.**

## 형식 2: 네이버 블로그용 HTML

경로: `_naver/YYYY-MM-DD-<slug>.html` — 같은 주제를 네이버 독자용(~습니다체)으로 다시 쓴 문서. 마크다운 문법 금지.

**파일명의 날짜 = 생성일이자 업로드 예정일.** 하루 3편을 만들어 그날 바로 올리므로 둘이 같다.

**⚠️ 본문에 날짜를 넣지 않는다**: 사용자는 생성일과 무관하게 원하는 시점에 네이버에 올리므로,
본문의 메타 줄에 생성 날짜가 박혀 있으면 실제 게시일과 어긋나 혼란을 준다.
- 메타 줄은 **카테고리만** 표기한다: `<p style="font-size:14px; color:#999;">GIS</p>`
- `2026. 9. 6. · GIS` 처럼 날짜를 앞에 붙이지 말 것. (파일명의 날짜는 정리·추적용이므로 그대로 유지한다.)

**폴더 규칙**:
- `_naver/` 루트 = **네이버 미게시 대기함** — 새 파일은 반드시 여기에 생성
- `_naver/posted/` = **게시 완료 보관함** — 사용자가 네이버에 올린 뒤 옮기는 곳. **자동화는 이 폴더에 쓰기 금지(읽기만 허용)**
- 스타일 참고용 최신 파일은 `_naver/` 루트에서 찾고, 루트가 비어 있으면 `_naver/posted/`의 최신 파일을 참고

- 완전한 HTML 문서: `<!DOCTYPE html>` + `<html lang="ko">` + `<meta charset="utf-8">` + `<title>`
- `<body style="background-color:#ffffff; padding:20px;">`
- 본문 요소는 **전부 인라인 스타일만** (`<style>` 블록·class·script 금지 — 네이버 에디터엔 인라인만 살아남음)
- 맨 위 HTML 주석으로 게시 방법 안내 (브라우저로 열기 → 전체선택·복사 → 네이버 글쓰기에 붙여넣기 → 제목은 제목칸, 해시태그는 태그칸으로)
- 구성: 제목 줄(26px bold) → 날짜·카테고리 메타(회색 14px) → 요약 박스(배경 #f0f7f4 + border-left 4px #03c75a) → 소제목(21px + border-left 5px #03c75a) → 문단(16px, line-height 1.8, 3~4문장, 핵심 `<b>`) → 코드 `<pre>`(배경 #f4f4f4, monospace, `<`·`>` 이스케이프) → 표(border-collapse + 셀 border) → 여백 `<p>&nbsp;</p>` → 주의 박스(배경 #fff7f0 + 주황 border-left) → 해시태그 줄(#03c75a)
- 외부 이미지·리소스 금지. 기존 `_naver/` 최신 파일과 스타일 일관성 유지.

## git 작업 규칙 (배치)

1. 브랜치: `auto-post/${TODAY}` (위 이어쓰기 규칙대로 checkout/생성)
2. **편 단위로 커밋·push**: 한 필러의 MD+HTML(+SVG 이미지) 파일들을 완성할 때마다
   `git add <해당 글의 파일들> && git commit -m "post: <제목> (auto)" && git push -u origin auto-post/${TODAY}`
   — 중간에 중단돼도 완성분은 남는다
3. 모든 작업 후 **open 상태**의 master 대상 PR 확인: 없으면 생성(제목 `daily posts: ${TODAY} (N편)`).
   같은 날 이전 PR이 이미 merge된 뒤의 추가 생성분이라면 새 PR을 만든다.
3.5. **merge 전 필수 게이트**: 위 "중복 절대 금지" 섹션의 최종 감사를 이번 PR에 포함된 모든 글에 대해 수행하고, 중복으로 판단된 글은 교체까지 마친다. 이 단계를 통과하기 전에는 다음 단계(merge)로 넘어가지 않는다.
4. **PR 자동 merge**: 위 게이트를 통과한 뒤에만 GitHub MCP 도구나 GitHub API로 즉시 merge한다(merge commit 방식).
   merge하면 GitHub Pages가 자동으로 게시한다. merge 실패 시 PR을 열어둔 채 실패 사유를 보고한다.
   merge 후 원격 브랜치 삭제는 토큰 권한상 불가하므로 그대로 남겨둔다(무해 — 다음 실행의 이어쓰기 판단에도 지장 없음).
5. rate limit·오류로 중단 시: 마지막 완성 편까지 push를 확인하고, **완성분만이라도 PR·merge까지 마친 뒤** 생성 편수/남은 필러를 보고
6. **금지**: master 직접 커밋/push(게시는 반드시 PR merge 경유), 기존 파일 수정·삭제, force push, `_config.yml` 변경
7. 완료 보고 후 가능하면 PushNotification으로 "N편 생성·게시 완료 + 링크" 알림
