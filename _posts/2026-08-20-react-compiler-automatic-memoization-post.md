리스트 아이템 하나에 콜백을 내려주려다 `useCallback`을 붙이고, 그 콜백이 의존하는 값에 `useMemo`를 붙이고, 다시 그 값을 계산하는 함수에 `useCallback`을 붙이는 흐름은 React 컴포넌트를 짜본 사람이라면 낯설지 않다. 문제는 이 패턴이 반복될수록 정작 컴포넌트가 하는 일보다 "무엇을 언제 다시 계산할지"를 설명하는 코드가 더 길어진다는 점이다. 의존성 배열 하나를 빠뜨리면 stale closure 버그가 생기고, 반대로 과도하게 메모이제이션을 걸면 오히려 비교 비용이 늘어 성능에 도움이 안 되는 경우도 흔했다.

React 팀은 이 부담을 언어·런타임이 아니라 **빌드 타임 컴파일러**로 옮기는 방향을 택했다. React Compiler는 컴포넌트와 훅의 소스 코드를 정적으로 분석해, 개발자가 손으로 붙이던 `useMemo`/`useCallback`/`React.memo`를 컴파일 결과물에 자동으로 삽입한다. 즉 코드는 최적화 이전의 단순한 형태로 남겨두고, 최적화는 빌드 단계에서 기계적으로 처리하겠다는 접근이다.

## 핵심 개념 1: 정적 분석으로 메모이제이션을 자동 삽입하는 원리

React Compiler는 컴포넌트 함수와 커스텀 훅의 본문을 분석해, 어떤 값이 어떤 입력(prop, state, 다른 변수)에 의존하는지 의존성 그래프를 구성한다. 이 그래프를 바탕으로 렌더링마다 다시 계산할 필요가 없는 값과 함수를 찾아내고, 해당 값을 캐시에 저장했다가 입력이 바뀌지 않았으면 재사용하도록 코드를 변환한다. 결과물은 사람이 `useMemo`를 촘촘히 박아 넣은 코드와 개념적으로 비슷하지만, 실제로는 컴파일러 전용의 저수준 캐싱 메커니즘(메모 슬롯)을 사용한다. 개발자 입장에서 중요한 점은, 컴파일러가 잘못 판단해도 최악의 경우 "메모이제이션을 덜 적용하는" 방향으로만 안전하게 실패하도록 설계되어 있다는 것이다.

## 핵심 개념 2: 왜 Rules of React 준수가 전제조건인가

이 자동화가 성립하려면 컴포넌트와 훅이 **순수 함수**처럼 동작해야 한다. 같은 입력에는 항상 같은 출력을 내고, 렌더링 도중에 외부 상태를 직접 변경하지 않으며, 훅 호출 순서가 조건문에 따라 바뀌지 않아야 한다. React 팀이 오래전부터 문서화해 온 이른바 Rules of React — 컴포넌트를 순수하게 유지하기, 훅을 최상위에서만 호출하기 같은 규칙 — 를 어기면 컴파일러가 의존성을 잘못 추론해 화면이 갱신되지 않거나 오래된 값을 그대로 보여주는 문제가 생길 수 있다. 다시 말해 React Compiler는 새로운 규칙을 추가하는 것이 아니라, 원래부터 지켜야 했던 규칙을 지켰을 때만 안전하게 작동하는 도구다. 이 때문에 팀 차원에서는 ESLint의 React 관련 규칙(`eslint-plugin-react-hooks`)을 엄격하게 적용해 두는 것이 컴파일러 도입의 실질적인 선행 조건이 된다.

## 핵심 개념 3: 수동 메모이제이션과의 비교

| 구분 | 수동 메모이제이션 | React Compiler |
|---|---|---|
| 적용 방식 | 개발자가 직접 `useMemo`/`useCallback`/`memo` 삽입 | 빌드 타임에 컴파일러가 자동 삽입 |
| 실수 가능성 | 의존성 배열 누락·과다 적용 등 사람 실수 발생 | 정적 분석 기준으로 일관되게 처리 |
| 가독성 | 최적화 코드가 비즈니스 로직과 뒤섞임 | 소스 코드는 최적화 이전 형태 유지 |
| 전제 조건 | 별도 규칙 없음(단, 잘못 쓰면 버그) | 컴포넌트·훅이 Rules of React를 준수해야 함 |
| 세밀한 제어 | 특정 값만 골라 수동으로 최적화 가능 | 컴파일러 판단에 맡기되, 필요시 옵트아웃 가능 |

표에서 보듯 두 방식이 완전히 대체 관계는 아니다. 컴파일러가 처리하기 어려운 경계 상황이나, 특정 최적화를 명시적으로 강제하고 싶은 구간에서는 여전히 수동 메모이제이션이나 `"use no memo"` 같은 옵트아웃 지시어를 함께 쓰는 편이 현실적이다.

## 예제

컴파일 이전 소스 코드는 다음과 같이 최적화를 신경 쓰지 않은 단순한 형태로 작성한다.

```jsx
// 컴파일 전 — 개발자가 작성하는 원본 코드
function ProductList({ items, onSelect }) {
  const sorted = items.slice().sort((a, b) => a.price - b.price);
  const handleClick = (id) => onSelect(id);

  return (
    <ul>
      {sorted.map((item) => (
        <li key={item.id} onClick={() => handleClick(item.id)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}
```

React Compiler를 거치면 개념적으로 아래와 같이 값과 콜백이 자동으로 캐시된다(실제 산출물은 컴파일러 내부 표현을 사용하며, 아래는 그 의도를 사람이 읽을 수 있게 옮긴 것이다).

```jsx
// 컴파일 후 — 컴파일러가 자동으로 메모이제이션을 적용한 형태(개념적 표현)
function ProductList({ items, onSelect }) {
  const sorted = useMemo(
    () => items.slice().sort((a, b) => a.price - b.price),
    [items]
  );
  const handleClick = useCallback((id) => onSelect(id), [onSelect]);

  return (
    <ul>
      {sorted.map((item) => (
        <li key={item.id} onClick={() => handleClick(item.id)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}
```

개발자는 첫 번째 형태만 작성하고 유지보수하면 되고, 두 번째 형태에 해당하는 최적화는 빌드 파이프라인이 대신 책임진다.

## 실무 포인트

- **점진적 도입을 전제로 설계되어 있다**: 컴파일러는 파일·디렉터리 단위로 켜고 끌 수 있어, 레거시 코드 전체를 한 번에 순수 함수 규칙에 맞추지 않아도 일부 영역부터 적용해 볼 수 있다.
- **ESLint 규칙을 먼저 정비한다**: `eslint-plugin-react-hooks`의 규칙을 위반하는 코드가 많다면, 컴파일러 도입보다 그 위반 사항을 먼저 해소하는 작업이 선행되어야 실제 이득을 볼 수 있다.
- **외부 라이브러리·비순수 훅을 감싸는 코드는 별도로 점검한다**: 서드파티 훅이 내부에서 규칙을 어기고 있으면 컴파일러가 잘못된 최적화를 적용할 여지가 있으므로, 도입 초기에는 해당 구간을 옵트아웃하거나 별도로 검증하는 편이 안전하다.
- **기존 수동 메모이제이션 코드를 무조건 걷어내지 않는다**: 컴파일러가 대부분을 대체하더라도, 특정 값의 참조 안정성을 명시적으로 보장해야 하는 구간에서는 수동 메모이제이션을 유지하는 편이 나을 수 있다.
- **성능 수치는 프로젝트마다 검증한다**: 리렌더링 감소 폭이나 번들 크기 변화는 컴포넌트 구조와 상태 설계에 따라 달라지므로, 도입 전후를 실제로 프로파일링해 비교하는 과정이 필요하다.

## 3줄 요약

- React Compiler는 컴포넌트·훅을 정적 분석해 `useMemo`/`useCallback`을 빌드 타임에 자동으로 삽입하는 도구다.
- 이 자동화는 컴포넌트가 Rules of React(순수성, 훅 호출 규칙)를 지킬 때만 안전하게 동작하므로, 도입 전 ESLint 규칙 정비가 사실상 선행 조건이다.
- 기존 수동 메모이제이션을 전면 대체하기보다, 컴파일러가 커버하기 어려운 구간에서는 여전히 수동 개입이나 옵트아웃이 필요하다.
