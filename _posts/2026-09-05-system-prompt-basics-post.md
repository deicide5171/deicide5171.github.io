## 같은 프롬프트인데 왜 역할을 나누나

LLM API로 챗봇을 만들면 메시지에 `role`을 지정한다. `system`, `user`, `assistant` 세 가지가 있는데, 초보자는 그냥 `user`에 다 넣어도 동작하니 굳이 나눌 필요를 못 느낀다. 하지만 **시스템 프롬프트(system)**는 "AI가 어떻게 행동해야 하는지"를 정하는 특별한 자리로, 일반 대화(user)와 역할이 분명히 다르다.

## 세 가지 역할

| role | 누가 말하는가 | 용도 |
|---|---|---|
| system | 개발자(설정) | AI의 성격·규칙·제약을 지정 |
| user | 사용자 | 실제 질문·요청 |
| assistant | AI | AI의 이전 답변(대화 맥락 유지용) |

## 시스템 프롬프트로 무엇을 하나

```python
messages = [
    {
        "role": "system",
        "content": "너는 친절한 고객센터 상담원이야. 항상 존댓말을 쓰고, "
                   "회사 정책상 환불은 7일 이내만 가능하다고 안내해. "
                   "모르는 것은 지어내지 말고 상담사 연결을 안내해."
    },
    {"role": "user", "content": "환불하고 싶어요"},
]
```

시스템 프롬프트에 역할·말투·규칙·제약을 적어두면, 그 뒤 모든 대화에 이 설정이 일관되게 적용된다. 사용자가 "규칙을 무시하라"고 해도 시스템 프롬프트의 지시가 우선되도록 설계하는 것이 일반적이다.

## user에 다 넣는 것과 뭐가 다른가

```text
[나쁜 방법] 매 요청의 user에 규칙을 반복해서 붙임
  - 대화가 길어지면 규칙이 묻히거나 잊힘
  - 사용자가 규칙 부분을 조작하기 쉬움

[좋은 방법] 규칙은 system에, 실제 요청만 user에
  - 설정과 대화가 분리되어 일관성 유지
  - 규칙이 대화 내용과 섞이지 않음
```

## 실무 포인트

- **시스템 프롬프트는 명확하고 구체적일수록 좋다.** "친절하게 답해"보다 "존댓말을 쓰고, 답변은 3문장 이내로, 모르면 모른다고 답해"처럼 구체적인 규칙이 원하는 동작을 안정적으로 만든다.
- **시스템 프롬프트만으로 100% 통제되지는 않는다.** 사용자가 교묘하게 유도하면 규칙을 벗어나는 응답이 나올 수 있다(프롬프트 인젝션). 민감한 작업에는 시스템 프롬프트 외에 출력 검증 같은 추가 안전장치가 필요하다.
- **너무 긴 시스템 프롬프트는 비용과 지연을 늘린다.** 매 요청마다 함께 전송되므로 토큰을 소모한다. 꼭 필요한 규칙만 간결하게 담고, 반복 호출이 많으면 프롬프트 캐싱을 검토하는 것이 좋다.

## 마무리 요약

- system·user·assistant 역할 중 시스템 프롬프트는 AI의 성격·규칙·제약을 지정하는 특별한 자리다.
- 규칙은 system에, 실제 요청은 user에 넣어야 설정과 대화가 분리되어 일관성이 유지된다.
- 시스템 프롬프트는 구체적으로 쓰되, 그것만으로 완벽히 통제되지 않으므로 민감한 작업엔 추가 안전장치가 필요하다.
