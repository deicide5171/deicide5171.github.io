## 왜 지금 샤딩 키 설계를 다시 봐야 하는가

수직 확장(더 좋은 서버로 교체)이나 읽기 복제본 추가로도 쓰기 처리량 한계에 부딪히면, 결국 데이터를 여러 물리적 노드로 쪼개는 샤딩을 고려하게 된다. 문제는 샤딩을 "테이블을 여러 DB로 나누는 것" 정도로 단순하게 접근했다가, 샤딩 키를 잘못 골라서 특정 샤드에만 트래픽이 몰리는 핫스팟이나, 거의 모든 쿼리가 여러 샤드를 조인해야 하는 크로스 샤드 쿼리 지옥에 빠지는 경우가 흔하다는 것이다. 샤딩은 한번 적용하면 되돌리기가 매우 어려운 결정이므로, 키 설계 단계에서 트래픽 패턴을 충분히 검토해야 한다.

이 글은 두 가지 대표적인 샤딩 방식인 해시 샤딩과 레인지 샤딩의 구조적 차이, 그리고 서비스가 성장하면서 샤드 수를 늘려야 하는 리샤딩 상황에서 각 방식이 어떤 대가를 치르는지를 정리한다.

## 핵심 개념 1 — 해시 샤딩과 레인지 샤딩의 구조 차이

해시 샤딩은 샤딩 키(예: user_id)에 해시 함수를 적용한 뒤 그 결과를 샤드 개수로 나눈 나머지로 샤드를 결정한다. 키 분포가 균등하기만 하면 데이터가 샤드 전체에 고르게 퍼지므로 핫스팟이 거의 생기지 않는다는 것이 장점이다. 반면 레인지 샤딩은 키의 범위(예: user_id 1~100만은 샤드 A, 100만~200만은 샤드 B)로 샤드를 나눈다. 범위 기반 조회(예: 특정 기간의 주문 조회)가 단일 샤드 안에서 끝나는 경우가 많아 범위 스캔 성능이 좋다는 장점이 있지만, 최근 가입자나 최신 데이터에 트래픽이 몰리는 서비스라면 마지막 샤드에만 부하가 집중되는 핫스팟 문제가 생기기 쉽다.

| 항목 | 해시 샤딩 | 레인지 샤딩 |
|---|---|---|
| 데이터 분포 | 균등 (핫스팟 적음) | 불균등해지기 쉬움 |
| 범위 조회 성능 | 나쁨 (여러 샤드 스캔) | 좋음 (단일 샤드로 국한) |
| 리샤딩 시 이동량 | 대부분 재배치 필요 | 특정 범위만 분할 가능 |
| 적합한 사례 | 단건 조회 위주(사용자 프로필) | 시계열·범위 조회 위주(로그, 주문 이력) |

## 핵심 개념 2 — 크로스 샤드 쿼리를 피하는 키 선택

샤딩 키 설계에서 가장 중요한 원칙은 "가장 빈번한 쿼리 패턴이 단일 샤드 안에서 끝나도록" 키를 고르는 것이다. 예를 들어 커머스 서비스에서 주문 조회가 대부분 "특정 사용자의 주문 목록"이라면 user_id를 샤딩 키로 써야 한다. 반대로 order_id를 샤딩 키로 쓰면 주문 단건 조회는 빨라지지만, 사용자별 주문 목록 조회가 모든 샤드를 뒤져야 하는 크로스 샤드 쿼리가 되어 애플리케이션 레이어에서 결과를 병합(scatter-gather)해야 하는 부담이 생긴다.

## 예제 — 일관된 해싱(Consistent Hashing)으로 리샤딩 비용 줄이기

```python
import hashlib

class ConsistentHashRing:
    def __init__(self, nodes, virtual_nodes=150):
        self.ring = {}
        self.sorted_keys = []
        for node in nodes:
            for i in range(virtual_nodes):
                key = self._hash(f"{node}-{i}")
                self.ring[key] = node
        self.sorted_keys = sorted(self.ring.keys())

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_node(self, key):
        h = self._hash(key)
        for ring_key in self.sorted_keys:
            if h <= ring_key:
                return self.ring[ring_key]
        return self.ring[self.sorted_keys[0]]
```

단순 `hash(key) % N` 방식은 샤드 수(N)가 바뀌는 순간 거의 모든 키의 소속 샤드가 바뀐다. 일관된 해싱을 쓰면 샤드를 추가·제거할 때 재배치가 필요한 키의 비율을 전체의 극히 일부로 줄일 수 있다.

## 실무 포인트

- **샤딩 키는 애플리케이션의 실제 쿼리 로그를 분석한 뒤 정하라.** 이론적으로 균등해 보이는 키라도 실제 트래픽 패턴에서는 특정 값에 쏠릴 수 있다.
- **테넌트 기반 서비스라면 테넌트 ID를 샤딩 키로 고려하되, 대형 테넌트가 하나의 샤드를 독점하지 않도록 서브 샤딩이나 전용 샤드 분리를 함께 설계하라.**
- **리샤딩 계획을 처음부터 문서화해두라.** 샤드 수를 2배로 늘릴 때 데이터 이동을 어떻게 수행할지(더블 라이트, 백그라운드 마이그레이션, 트래픽 전환 순서)를 미리 정하지 않으면 실제 리샤딩 시점에 다운타임이 커진다.

## 마무리 요약

- 해시 샤딩은 균등 분산에, 레인지 샤딩은 범위 조회 성능에 강점이 있으며 서비스의 주요 쿼리 패턴에 따라 선택이 갈린다.
- 샤딩 키 설계의 핵심은 가장 빈번한 쿼리가 크로스 샤드 스캐터-개더 없이 단일 샤드에서 끝나도록 만드는 것이다.
- 일관된 해싱과 사전에 문서화된 리샤딩 전략은 샤드 수를 늘려야 하는 순간의 이동 비용과 다운타임을 크게 줄여준다.
