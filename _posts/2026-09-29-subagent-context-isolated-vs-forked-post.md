## "리서치는 서브에이전트한테 시키고, 결과만 받아오세요"

에이전트 오케스트레이터를 짜다 보면 자연스럽게 이런 요구가 생긴다. 메인 에이전트가 사용자와 긴 대화를 이어가는 도중, 무거운 조사나 코드 수정 같은 하위 작업을 별도 에이전트에 위임하고 싶어진다. 이유는 단순하다 — 조사 과정에서 나오는 수십 번의 검색 결과와 시행착오를 메인 에이전트의 컨텍스트 창에 그대로 쌓으면, 정작 사용자와의 대화 맥락이 컨텍스트 뒤로 밀려나거나 비용이 감당 안 되게 불어난다.

그런데 "위임한다"는 말은 구체적으로 무엇을 의미하는가? 서브에이전트가 부모의 대화 이력을 전부 알아야 하는가, 아니면 작업 지시 한 줄만 알면 되는가? 이 질문에 대한 답이 서브에이전트의 정확도, 토큰 비용, 응답 지연을 모두 동시에 결정한다. 2026년 9월 LangChain이 deepagents에 정식으로 넣은 **컨텍스트 모드**(isolated / fork)는 이 질문을 프레임워크 차원의 명시적 선택지로 만들었다는 점에서 살펴볼 가치가 있다.

## 두 가지 모드, 완전히 다른 실패 양상

**Isolated(기본값)**는 서브에이전트가 부모로부터 작업 설명 하나만 받고, 부모 대화가 어떻게 흘러왔는지는 전혀 모르는 상태로 시작한다. 깨끗한 상태에서 시작하니 부모의 잡음(다른 주제의 대화, 이전 실패 시도)에 오염되지 않는다. 대신 프롬프트 캐시가 처음부터 다시 쌓이므로(cold start) 매번 시스템 프롬프트 전체를 새로 계산해야 한다.

**Fork**는 서브에이전트가 부모의 전체 대화 이력과 정확히 동일한 시스템 프롬프트 접두사를 그대로 물려받는다. 부모가 이미 진단을 끝낸 작업을 이어받아 실행만 하는 워커에 적합하다. 핵심은 접두사가 완전히 같기 때문에 **부모의 프롬프트 캐시를 그대로 재사용**할 수 있다는 것이다 — 캐시 읽기 비용이 신규 생성 대비 크게 낮으므로, fork는 정확도뿐 아니라 순수하게 비용 문제이기도 하다.

| 기준 | Isolated | Fork |
|---|---|---|
| 물려받는 것 | task 설명 한 줄 | 전체 대화 이력 + 시스템 프롬프트 |
| 프롬프트 캐시 | 새로 시작 (cold) | 부모 것 재사용 (warm) |
| 맥락 오염 위험 | 낮음 | 있음 (무관한 이전 시도까지 봄) |
| 적합한 작업 | 독립적 조사, 병렬 리서치 | 부모가 진단한 작업을 이어받아 실행 |
| 실패 시 영향 범위 | 부모 상태에 영향 없음 | 부모 로컬 상태를 덮어쓸 위험 있음 |

## 진행 순서 — 기본값에서 시작해 필요한 곳만 fork로 바꾼다

**1단계**: 모든 서브에이전트를 isolated로 두고 시작한다. 대부분의 "이 조사 좀 해줘" 류 위임은 격리로 충분하고, 오염 위험도 없다.

**2단계**: 프롬프트 캐시 히트율과 토큰 비용을 관찰한다. 같은 시스템 프롬프트를 서브에이전트가 매번 콜드로 다시 계산하는 게 비용 로그에서 보이기 시작하면, 그 서브에이전트가 진짜로 부모의 맥락을 이어받아야 하는 워커인지 다시 판단한다.

**3단계**: "부모가 이미 결정을 내렸고, 서브에이전트는 그 결정을 그대로 실행만 한다"는 조건을 만족하는 작업만 fork로 바꾼다. 예를 들어 메인 에이전트가 버그를 진단하고 원인을 특정한 뒤, 실제 코드 수정만 워커에게 넘기는 경우가 전형적이다.

```python
from deepagents import create_deep_agent
from deepagents.middleware.subagents import SubAgent

fix_worker = SubAgent(
    name="apply-fix",
    description="부모가 진단한 버그를 실제로 수정한다",
    mode="fork",  # 부모의 진단 맥락을 그대로 물려받음
)

researcher = SubAgent(
    name="background-research",
    description="독립적인 배경 조사를 수행한다",
    mode="isolated",  # 기본값, 명시하지 않아도 됨
)
```

**4단계**: 여러 fork 서브에이전트를 병렬로 띄우는 경우를 별도로 검증한다. 각 fork가 부모의 상태 일부(예: 준비 단계 플래그)를 결과에 함께 담아 돌려주면, 두 fork가 동시에 같은 부모 상태를 덮어써 `InvalidUpdateError` 같은 충돌이 발생할 수 있다. 실제로 LangChain은 이 문제를 겪은 뒤 준비·응답·대화 오프로딩 관련 필드를 `OmitFromOutput`으로 표시해, fork가 준비된 맥락은 물려받되 부모의 로컬 상태를 결과로 덮어쓰지는 못하도록 고쳤다. 자체 멀티에이전트 프레임워크를 짤 때도 "fork 결과가 부모 상태의 어느 부분까지 되돌려 쓸 수 있는가"를 명시적으로 결정해야 한다.

## 실무 포인트

**fork를 남용하면 격리의 장점이 사라진다.** 부모 대화에 다른 사용자 요청이나 실패한 시도가 섞여 있다면, fork된 서브에이전트는 그 잡음까지 그대로 물려받아 엉뚱한 판단을 내릴 수 있다. fork는 "이어받을 맥락이 실제로 필요한가"를 먼저 확인한 뒤에 쓴다.

**캐시 재사용은 접두사가 바이트 단위로 같을 때만 성립한다.** fork 서브에이전트가 부모와 조금이라도 다른 프롬프트 조립 미들웨어를 쓰면 캐시가 깨지고 fork의 이점이 사라진다. 부모와 자식이 같은 프롬프트 생성 경로를 공유하도록 구성해야 한다.

**격리 수준은 보안 경계와는 별개다.** isolated 모드는 컨텍스트 엔지니어링 관점의 격리이지, 권한이나 도구 접근 범위를 제한하는 것은 아니다. 서브에이전트에게 어떤 도구를 줄지는 컨텍스트 모드와 별도로 다시 설계해야 한다.

## 정리

- 서브에이전트 위임은 "누가 무엇을 기억하는가"를 정하는 컨텍스트 설계 문제이며, 기본값은 격리(isolated)로 두는 것이 안전하다.
- fork는 정확도 문제가 아니라 프롬프트 캐시 재사용을 통한 **비용·지연 최적화 수단**이라는 점을 기억하고, 부모의 결정을 그대로 이어받아 실행하는 작업에만 쓴다.
- 병렬 fork를 쓸 때는 서브에이전트 결과가 부모의 로컬 상태를 덮어쓸 수 있는지를 반드시 점검한다.
