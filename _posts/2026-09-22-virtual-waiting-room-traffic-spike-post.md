## 왜 서버를 더 늘려도 콘서트 예매 사이트는 뻗는가

콘서트 티켓 예매나 인기 강의 수강신청처럼 "정확히 오전 10시부터 선착순"인 이벤트는 시스템 관점에서 매우 독특한 트래픽 패턴을 만든다. 평소 트래픽 대비 수백 배에 달하는 요청이 단 몇 초 안에 동시에 쏟아지고, 그마저도 대부분 같은 몇 개의 API(좌석 조회, 결제 페이지 진입)에 집중된다. 이때 흔히 나오는 대응은 "서버를 더 늘리면 되지 않나"라는 생각이지만, 실제로는 서버를 아무리 늘려도 한계에 부딪히는 경우가 많다.

이유는 서버 자체의 처리 능력보다, DB 커넥션·캐시·외부 결제 게이트웨이처럼 뒷단에 있는 공유 자원의 한계가 먼저 드러나기 때문이다. 웹 서버는 수평 확장이 비교적 쉽지만, 하나의 재고 값을 두고 경쟁하는 DB나 초당 호출 횟수 제한이 있는 외부 API는 서버를 늘린다고 함께 확장되지 않는다. 결국 시스템을 지키는 더 근본적인 방법은 "요청을 다 받아서 처리하려는 시도" 자체를 포기하고, 요청이 시스템에 들어오는 속도 자체를 제어하는 것이다.

## 잘못된 접근: 요청을 다 받고 서버 안에서 큐잉하기

트래픽이 몰릴 때 애플리케이션 서버 안에서 세마포어나 큐로 동시 처리 수를 제한하는 방법을 먼저 떠올리기 쉽다.

```java
// 애플리케이션 서버 안에서 동시 처리 수만 제한하는 방식
Semaphore ticketingSemaphore = new Semaphore(100);

public ResponseEntity<?> reserveSeat(SeatRequest request) {
    if (!ticketingSemaphore.tryAcquire()) {
        return ResponseEntity.status(503).build();
    }
    try {
        return doReserve(request);
    } finally {
        ticketingSemaphore.release();
    }
}
```

이 방식의 문제는 **요청이 이미 네트워크를 타고 서버까지 도달한 뒤에야 걸러진다**는 점이다. 서버까지 오는 과정에서 로드밸런서, 네트워크 대역폭, 커넥션 수용량이 먼저 한계에 부딪히고, 서버 프로세스 자체도 수많은 연결을 붙잡고 대기시키느라 메모리와 스레드를 소모한다. 몰린 트래픽을 서버가 "일단 받아준다"는 전제 자체가 무너지기 쉽다.

## 올바른 접근: 진입 자체를 앞단에서 통제하는 가상 대기열

가상 대기열(Virtual Waiting Room)은 사용자가 실제 서비스(좌석 조회, 결제)에 접근하기 전, CDN이나 별도의 경량 게이트웨이 레벨에서 대기 순번표를 발급하고 정해진 속도로만 실제 서비스로 흘려보내는 구조다.

```javascript
// 대기열 진입 시 발급되는 토큰 예시 흐름
const enterWaitingRoom = async (userId) => {
  const response = await fetch('/waiting-room/enter', {
    method: 'POST',
    body: JSON.stringify({ userId, eventId: 'concert-2026' }),
  });
  const { queueToken, estimatedWaitSeconds } = await response.json();
  // 이 시점에는 아직 실제 예매 서버에 요청이 전혀 도달하지 않는다
  return queueToken;
};
```

대기열 서버는 Redis의 정렬 집합(Sorted Set) 같은 자료구조로 순번을 관리하며, 실제 예매 서버가 안전하게 처리할 수 있는 속도(초당 N명)로만 순번이 지난 사용자에게 실제 서비스 접근 토큰을 발급한다. 이 구조의 핵심은 **대기열 자체는 실제 예매 로직과 완전히 분리된 훨씬 가벼운 시스템**이라는 점이다. 순번 발급과 대기 상태 조회만 처리하면 되므로, 본 서비스보다 훨씬 적은 자원으로 수십만 명의 동시 대기를 감당할 수 있다.

## 대기열 없는 시스템 vs 대기열 적용 시스템

| 항목 | 대기열 없음 | 가상 대기열 적용 |
|---|---|---|
| 트래픽 몰림 시 | 모든 요청이 즉시 본 서버로 몰림 | 대기열이 흡수하고 본 서버는 일정 속도만 받음 |
| DB·결제 게이트웨이 부하 | 순간 최대치에 그대로 노출 | 유입 속도가 제어되어 안정적인 부하 유지 |
| 사용자 경험 | 타임아웃, 무한 로딩, 에러 페이지 | "대기 순번 3,204번, 예상 대기 2분" 같은 명확한 안내 |
| 실패 시 재시도 패턴 | 새로고침 폭탄(더 큰 트래픽 유발) | 대기열 안에서 자연스럽게 순서 유지 |

특히 사용자 경험 측면의 차이가 크다. 아무 안내 없이 화면이 멈추면 사용자는 반사적으로 새로고침을 반복하고, 이는 트래픽을 더 키우는 악순환을 만든다. 명확한 대기 순번과 예상 시간을 보여주는 것만으로도 이 악순환을 크게 줄일 수 있다.

## 실무 포인트

- **대기열 통과 후 발급되는 토큰에는 반드시 유효시간을 둬라.** 순번이 지나 실제 서비스 접근 권한을 얻었는데도 사용자가 한참 뒤에 들어오면, 그 자리를 계속 비워두는 셈이 되어 처리량 관리가 무너진다.
- **대기열 우회 가능성을 차단하라.** 대기열 없이 API를 직접 호출하는 방식으로 우회할 수 있다면 대기열 자체가 무의미해진다. 실제 API 서버 쪽에서도 유효한 대기열 토큰이 있는지 검증하는 계층을 반드시 함께 둬야 한다.
- **본 서비스로 흘려보내는 속도는 실측으로 정하라.** 감으로 정한 처리 속도는 실제 부하 테스트로 검증된 안전 마진과 다를 수 있다. 이벤트 시작 전 반드시 실제 규모의 부하 테스트로 안전한 유입 속도를 확인해야 한다.

## 마무리 요약

- 트래픽이 순간적으로 몰리는 서비스는 서버 증설만으로 해결되지 않는다. DB·외부 API 같은 공유 자원의 한계가 먼저 드러나기 때문이다.
- 요청을 서버 안에서 큐잉하는 방식은 이미 서버까지 도달한 뒤에야 걸러지므로, 앞단 자체가 먼저 무너질 수 있다.
- 가상 대기열은 진입 자체를 앞단의 경량 시스템에서 통제해, 본 서비스에는 안전하게 처리 가능한 속도로만 트래픽을 흘려보내는 실전 해법이다.
