## 왜 지금 저지연 GC를 다시 봐야 하는가

G1GC는 오랫동안 JVM의 기본 컬렉터로서 처리량과 지연시간의 균형을 잘 맞춰왔지만, 힙 크기가 수십 GB를 넘어가는 대형 서비스에서는 근본적인 한계에 부딪힌다. G1도 영역(region) 단위로 점진적으로 수거하지만, 특정 단계(Mixed GC의 Evacuation Pause 등)에서는 여전히 애플리케이션 스레드를 완전히 멈추는 Stop-The-World 정지가 발생하며, 이 정지 시간은 힙이 커질수록 함께 늘어나는 경향이 있다. 밀리초 단위의 p99 지연시간 SLA를 지켜야 하는 서비스에서는 이 정지 시간 자체가 문제가 된다. ZGC와 Shenandoah는 "힙 크기와 무관하게 정지 시간을 일정하게(대개 한 자릿수 밀리초 이내) 유지한다"는 목표로 설계된 저지연 컬렉터로, 이를 달성하기 위해 기존 GC와는 다른 근본적인 메커니즘을 쓴다.

## 핵심 개념 1 — 대부분의 GC 작업을 애플리케이션 스레드와 동시에 수행한다

기존 컬렉터가 정지 시간을 줄이기 어려웠던 이유는, 객체를 옮기는(compaction) 작업이나 참조를 다시 연결하는 작업을 애플리케이션 스레드가 멈춰 있는 동안에만 안전하게 할 수 있다고 가정했기 때문이다. ZGC와 Shenandoah는 이 가정 자체를 깨고, 객체 이동과 참조 갱신 대부분을 애플리케이션 스레드가 계속 실행되는 동안 동시에(concurrently) 수행한다. 정지가 필요한 구간은 GC 사이클 시작·종료 시점의 매우 짧은 동기화 지점 정도로 최소화되며, 이 덕분에 힙이 아무리 커져도 정지 시간이 거의 늘어나지 않는다.

## 핵심 개념 2 — 컬러 포인터와 로드 배리어로 "이동 중인 객체" 문제를 푼다

애플리케이션 스레드가 계속 실행되는 도중에 GC 스레드가 객체를 다른 메모리 위치로 옮기면, 이미 그 객체를 가리키고 있던 포인터들이 순간적으로 낡은 주소를 가리키는 문제가 생긴다. ZGC는 이 문제를 컬러 포인터(colored pointer)라는 기법으로 해결한다 — 64비트 포인터의 사용하지 않는 상위 비트 몇 개에 그 객체의 GC 상태(예: "이 참조는 재배치됐을 수 있다")를 메타데이터로 인코딩해둔다. 객체를 참조로 읽을 때마다(로드 배리어, load barrier) 이 메타데이터를 확인해, 만약 이미 이동된 객체라면 그 자리에서 즉시 새 주소로 포인터를 고쳐 쓴다. Shenandoah는 컬러 포인터 대신 Brooks Pointer라는, 각 객체 헤더에 forwarding pointer를 추가로 두는 방식으로 유사한 문제를 해결한다. 두 방식 모두 "객체가 이동 중이어도 애플리케이션 코드가 항상 올바른 최신 위치를 참조하게 만든다"는 목표는 같지만 구현 메커니즘이 다르다.

| 항목 | G1GC | ZGC | Shenandoah |
|---|---|---|---|
| 목표 | 처리량과 지연시간 균형 | 힙 크기 무관 초저지연 | 힙 크기 무관 저지연 |
| 이동 중 참조 처리 | STW 구간에서만 안전하게 처리 | 컬러 포인터 + 로드 배리어 | Brooks Pointer(forwarding) |
| 최대 힙 크기 확장성 | 수십 GB에서 정지 시간 증가 | 테라바이트급까지 정지 시간 거의 무관 | 테라바이트급까지 지원 |
| 성숙도(JDK 배포 상태) | 오랜 기본값, 매우 안정적 | JDK 15+ 프로덕션 지원 | OpenJDK 배포판별 지원 차이 존재 |

## 예제 — ZGC 활성화와 기본 로그 확인

```bash
# JDK 17+ 기준 ZGC 활성화
java -XX:+UseZGC -Xmx32g -Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=50m \
     -jar application.jar

# 로그에서 확인할 핵심 지표
# GC(N) Pause Mark Start, Pause Mark End, Pause Relocate Start 등
# 각 Pause 항목의 시간이 힙 크기와 무관하게 일정한 수준(수 ms 이내)을 유지하는지 확인
```

## 실무 포인트

- **애플리케이션의 실제 지연시간 요구사항을 먼저 계량화하라.** p99 지연시간이 이미 GC와 무관한 다른 요인(네트워크, DB 쿼리)에 좌우되고 있다면 저지연 GC 도입 효과가 기대만큼 크지 않을 수 있으므로, 먼저 GC가 실제 병목인지 프로파일링으로 확인해야 한다.
- **처리량(throughput) 저하 가능성을 감안하라.** 저지연 GC는 동시 수행을 위해 로드 배리어 같은 추가 오버헤드를 CPU 사이클에 계속 부담시키므로, 일부 워크로드에서는 G1 대비 전체 처리량이 다소 낮게 나올 수 있다.
- **JDK 버전과 배포판별 지원 상태를 확인하라.** ZGC와 Shenandoah 모두 초기 버전에서 여러 세대에 걸쳐 개선돼 왔으므로, 사용 중인 JDK 배포판(OpenJDK, Temurin 등)에서의 성숙도와 기본 활성화 여부를 반드시 확인해야 한다.

## 마무리 요약

- ZGC와 Shenandoah는 객체 이동과 참조 갱신 대부분을 애플리케이션 스레드와 동시에 수행해, 힙 크기가 커져도 정지 시간이 거의 늘어나지 않도록 설계됐다.
- 컬러 포인터(ZGC)와 Brooks Pointer(Shenandoah)는 "이동 중인 객체를 가리키는 낡은 포인터" 문제를 서로 다른 메커니즘으로 해결한다.
- 저지연이라는 이점은 로드 배리어 오버헤드로 인한 처리량 저하와 트레이드오프 관계이므로, GC가 실제 병목인지 먼저 검증한 뒤 도입해야 한다.
