## 왜 지금 해상도 경쟁을 봐야 하나

항공·위성 영상 시장에서 해상도 경쟁이 다시 화제다. 2026년 8월 기준으로 Vexcel 같은 항공영상 전문 업체가 전국 단위를 7.5cm급 초고해상도로 촬영하는 프로그램을 확대하고 있는 것으로 알려졌다. 기존에 흔히 쓰이던 15~30cm급 항공영상과 비교하면 픽셀당 커버 면적이 4배 이상 줄어드는 셈이라, 개별 차량, 도로 표지, 소규모 구조물까지 식별 가능한 수준으로 정밀도가 올라간다.

이런 흐름이 나오는 배경은 단순하다. 카메라 센서와 항공기 GNSS/IMU 장비가 저렴해지고, 클라우드 스토리지·컴퓨팅 비용이 계속 내려가면서 "더 자주, 더 세밀하게" 찍는 것이 예전보다 경제적으로 말이 되기 시작했기 때문이다. 위성 쪽에서도 상업 위성 업체들이 서브미터급, 일부는 30cm 이하 해상도를 상용 서비스로 제공하는 사례가 늘고 있다.

문제는 이런 고해상도 원본 데이터가 실제 GIS 실무에 들어오는 순간 저장 용량, 타일링 파이프라인, 처리 비용 전반에 파급 효과를 낸다는 점이다. 이 글에서는 해상도가 올라갈 때 실무 파이프라인의 어느 지점이 압박을 받는지, 그리고 어떻게 대응하는 것이 합리적인지를 정리한다.

## 해상도별 데이터 규모 비교

같은 면적을 촬영해도 해상도가 두 배 세밀해지면 픽셀 수는 대략 네 배로 늘어난다. 대략적인 감을 잡기 위한 비교는 다음과 같다.

| 해상도(GSD) | 1㎢당 대략 픽셀 수 | 전형적 활용처 |
|---|---|---|
| 30cm | 약 1,100만 픽셀 | 도시 계획, 일반 지도 서비스 |
| 15cm | 약 4,400만 픽셀 | 정밀 지적, 시설물 관리 |
| 7.5cm | 약 1억 7,800만 픽셀 | 개별 자산 식별, 균열·손상 탐지 |

숫자로 보면 30cm에서 7.5cm로 가는 것은 단순히 "조금 더 선명해지는" 수준이 아니라, 같은 지역을 저장하는 데 필요한 원본 데이터량이 한 자릿수 이상 늘어나는 변화다. 압축과 피라미드(오버뷰) 구조를 잘 설계하지 않으면 스토리지 비용과 타일 서빙 지연이 그대로 실무 문제로 튄다.

## 파이프라인에 미치는 영향

- **저장**: 무압축 원본을 그대로 두면 전국 단위 커버리지에서 페타바이트급 스토리지가 필요해질 수 있다. Cloud Optimized GeoTIFF(COG)와 같은 클라우드 친화적 포맷, 그리고 JPEG2000·타일 기반 압축을 병행하는 것이 사실상 표준으로 자리 잡고 있다.
- **타일링**: 웹 지도에서 고해상도 영상을 서빙하려면 줌 레벨별 오버뷰(피라미드)를 미리 만들어 둬야 한다. 원본 해상도가 올라갈수록 최상위 줌 레벨 타일 생성에 드는 CPU·I/O 비용도 함께 늘어난다.
- **처리 비용**: 정사보정(orthorectification), 모자이킹, 변화 탐지 같은 연산은 픽셀 수에 비례해 무거워진다. 전국 단위 재처리 작업이라면 클라우드 배치 처리나 분산 처리 프레임워크 없이는 현실적인 시간 안에 끝내기 어렵다.
- **활용 사례**: 반대로 얻는 것도 크다. 균열·손상 자동 탐지, 개별 수목·표지판 인벤토리, 소규모 불법 시설물 탐지처럼 기존 저해상도로는 어려웠던 세밀한 분석이 가능해진다.

## 예제: GDAL로 COG 변환과 오버뷰 생성

대용량 원본 영상을 클라우드에서 효율적으로 서빙하려면 COG 변환과 오버뷰 생성이 기본 단계다.

```bash
# 1) 일반 GeoTIFF를 Cloud Optimized GeoTIFF로 변환
gdal_translate input_ortho.tif output_cog.tif \
  -of COG \
  -co COMPRESS=JPEG \
  -co QUALITY=85 \
  -co BLOCKSIZE=512 \
  -co OVERVIEWS=IGNORE_EXISTING

# 2) 오버뷰(피라미드) 레벨 확인
gdalinfo output_cog.tif | grep -A 5 "Overviews"
```

타일 서버 쪽에서 처리 비용을 가늠할 때는 픽셀 수 기준 대략적인 견적을 먼저 뽑아보는 것이 유용하다.

```python
# 해상도(GSD)에 따른 대략적인 픽셀 수 추정
def estimate_pixels(area_km2: float, gsd_cm: float) -> float:
    gsd_m = gsd_cm / 100
    pixels_per_km2 = 1_000_000 / (gsd_m ** 2)
    return area_km2 * pixels_per_km2

# 예: 서울시 면적(약 605km2)을 7.5cm로 촬영할 경우
print(estimate_pixels(605, 7.5))  # 약 1.07 x 10^11 픽셀
```

## 실무 포인트

- 전국 단위로 고해상도 원본을 한꺼번에 도입하기보다, 실제 활용처(정밀 분석이 필요한 지역)를 먼저 선정해 단계적으로 확대하는 편이 비용 대비 효과가 좋다.
- COG, MBTiles, 클라우드 네이티브 래스터 포맷을 미리 검토해 두면 나중에 대용량 영상이 들어왔을 때 파이프라인을 뒤집지 않아도 된다.
- 해상도가 올라갈수록 좌표계·정사보정 오차가 상대적으로 더 크게 드러날 수 있으므로, GNSS/IMU 보정 품질과 검증 절차를 함께 점검하는 것이 좋다.
- 라이선스·개인정보 이슈(차량 번호판, 개인 주택 마당 등 식별 가능 수준)도 해상도가 올라가면서 함께 커지는 문제이니, 도입 전에 활용 정책을 정리해 두는 것이 안전하다.

## 3줄 요약

- 7.5cm급 초고해상도 항공영상 프로그램이 확대되는 흐름은 GIS 파이프라인의 저장·타일링·처리 비용 전반에 파급 효과를 준다.
- 해상도가 두 배 세밀해지면 픽셀 수는 대략 네 배로 늘어나므로, COG 같은 클라우드 친화적 포맷과 오버뷰 전략이 사실상 필수가 된다.
- 정밀 분석이 필요한 영역부터 단계적으로 고해상도 데이터를 도입하고, 좌표 정확도·라이선스 이슈를 함께 점검하는 것이 현실적인 접근이다.
