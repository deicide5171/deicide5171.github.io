## 왜 같은 입력인데 매번 다른 답이 나오나

LLM API를 처음 붙이고 나서 당황스러운 경험 중 하나는, 완전히 동일한 프롬프트를 여러 번 보냈는데도 응답이 조금씩, 때로는 크게 달라진다는 점이다. 전통적인 소프트웨어에서는 "같은 입력에는 같은 출력"이 당연한 전제였지만, LLM은 다음 단어를 확률 분포에서 **샘플링**하는 방식으로 텍스트를 생성하기 때문에 이 전제가 그대로 성립하지 않는다.

이 비결정성은 프로토타입 단계에서는 크게 문제되지 않지만, 테스트 자동화나 회귀 검증을 시작하는 순간 골칫거리가 된다. "어제는 통과했던 테스트가 오늘은 실패한다"는 상황이 반복되면, 개발자는 테스트 자체를 신뢰하지 못하게 되고 결국 LLM이 관련된 부분의 테스트를 아예 건너뛰는 나쁜 습관으로 이어진다.

## temperature: 확률 분포를 얼마나 날카롭게 만들지 정하는 값

`temperature`는 모델이 다음 토큰을 고를 때 확률 분포의 "뾰족한 정도"를 조절하는 파라미터다. 값이 0에 가까울수록 항상 가장 확률이 높은 토큰을 선택하는 쪽으로 수렴하고, 값이 높을수록 확률이 낮은 토큰도 선택될 여지가 커진다.

```python
# temperature가 낮을수록 매번 비슷한 답이 나올 확률이 높아진다
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    temperature=0,
    messages=[{"role": "user", "content": "이 함수의 시간복잡도를 분석해줘: ..."}],
)
```

여기서 흔히 오해하는 부분이 있다. **`temperature=0`을 설정해도 100% 완전히 동일한 출력이 보장되지는 않는다.** GPU 병렬 연산의 부동소수점 계산 순서, 배치 처리 방식의 미세한 차이 등으로 인해 극히 드물게 결과가 달라질 수 있다. `temperature=0`은 "거의 항상 동일한 결과"를 만들 뿐, 수학적으로 완전한 결정론을 보장하는 스위치는 아니라는 점을 알고 있어야 한다.

## seed: 무작위성 자체를 고정하기

일부 API는 `temperature`와 별개로 `seed` 파라미터를 제공한다. 내부적으로 샘플링에 쓰이는 난수 생성기의 시작값을 고정해, 같은 seed와 같은 요청 조건이라면 결과가 훨씬 더 안정적으로 재현되게 한다.

```python
response = client.chat.completions.create(
    model="gpt-4o",
    temperature=0.7,
    seed=42,
    messages=[{"role": "user", "content": "짧은 사용자 후기 예시를 하나 생성해줘."}],
)
```

`seed`를 쓰면 temperature를 반드시 0으로 낮추지 않아도, 즉 어느 정도의 창의성을 유지하면서도 재현 가능한 결과를 얻을 수 있다는 점이 중요하다. 다만 seed를 지원하더라도 모델 버전이 서버 쪽에서 업데이트되면 같은 seed·같은 프롬프트라도 결과가 달라질 수 있으므로, API 응답에 함께 포함되는 `system_fingerprint`(또는 이에 대응하는 값)를 확인해 실제로 같은 모델 스냅샷에서 생성된 결과인지 검증하는 습관이 필요하다.

## 용도별 temperature·seed 조합 가이드

| 용도 | 권장 temperature | seed 사용 | 이유 |
|---|---|---|---|
| 코드 생성, 데이터 추출, 분류 | 0 ~ 0.2 | 선택적 | 정답이 명확한 작업은 일관성이 우선 |
| 자동화 테스트·회귀 검증 | 0 | 반드시 사용 | 실패 원인이 모델의 무작위성인지 코드 버그인지 구분해야 함 |
| 창작·마케팅 카피 | 0.7 ~ 1.0 | 필요시(A/B 테스트 재현용) | 다양성 자체가 목적이므로 낮은 temperature가 오히려 손해 |
| 브레인스토밍, 아이디어 발산 | 0.8 ~ 1.2 | 사용 안 함 | 매번 다른 아이디어가 나오는 것이 의도된 동작 |

## 실무 포인트

- **완전한 결정론이 필요하다면 애플리케이션 레벨에서 캐싱을 고려하라.** temperature와 seed를 아무리 낮춰도 API 자체가 100% 결정론을 보장하지 않으므로, 정말 항상 같은 결과가 필요한 경우(예: 데모, 회귀 테스트의 골든 파일)라면 첫 호출 결과를 캐싱해 재사용하는 편이 안전하다.
- **테스트 코드에서는 정확히 일치가 아니라 구조적 검증을 우선하라.** LLM 응답 테스트는 문자열이 완전히 같은지보다, JSON 스키마를 만족하는지, 특정 키워드가 포함되는지 같은 느슨한 기준으로 작성하는 것이 비결정성과 공존하는 현실적인 전략이다.
- **모델 제공사마다 seed 지원 여부와 보장 수준이 다르다.** 새 모델이나 새 API 버전으로 전환할 때 seed 관련 동작이 문서에 명시된 대로인지 반드시 재확인해야 한다.

## 마무리 요약

- LLM은 확률적 샘플링으로 텍스트를 생성하기 때문에 같은 입력에도 매번 다른 출력이 나올 수 있으며, 이는 결함이 아니라 구조적 특성이다.
- temperature는 확률 분포의 날카로움을, seed는 샘플링에 쓰이는 난수의 시작값을 조절해 재현성을 높이지만 둘 다 완전한 결정론까지는 보장하지 않는다.
- 회귀 테스트에는 temperature 0과 seed 고정을 함께 쓰되, 완전 일치보다는 구조적 검증 기준으로 테스트를 설계하는 것이 현실적이다.
