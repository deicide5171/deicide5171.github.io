## 왜 지금 Request Hedging을 다시 봐야 하는가

수백 대의 서버로 분산 처리되는 시스템에서 평균 응답시간(p50)은 충분히 빠른데, p99나 p999처럼 꼬리 구간의 지연시간만 유독 길게 튀는 현상을 자주 마주친다. 이런 개별 서버의 순간적인 느려짐은 GC 일시정지, 디스크 I/O 경합, 네트워크 큐 지연처럼 예측하기 어려운 원인에서 비롯되며, 서버 한 대만 봐서는 원인을 특정하기도 어렵다. 문제는 이런 꼬리 지연이 서비스 체인이 길어질수록 증폭된다는 점이다 — 하나의 사용자 요청이 내부적으로 100개의 병렬 하위 요청을 만든다면, 그중 단 하나만 p99 구간에 걸려도 전체 응답은 그 가장 느린 하나를 기다려야 한다. Request Hedging은 재시도(retry)와는 다른 접근으로 이 문제를 완화한다 — 실패를 기다렸다가 재시도하는 대신, 응답이 일정 시간 안에 오지 않으면 아직 실패하지 않았어도 같은 요청을 다른 서버에 추가로 보내고, 둘 중 먼저 도착한 응답을 채택하는 것이다.

## 핵심 개념 1 — 재시도(Retry)와 헤징(Hedging)의 근본적 차이

재시도는 "요청이 실패했다"는 것을 확인한 뒤에야 다시 시도하는 사후 대응이다. 반면 헤징은 요청이 아직 실패하지 않았더라도, 정해둔 지연 임계값(hedging delay)을 넘어서면 원래 요청을 취소하지 않은 채 동일한 요청을 다른 인스턴스로 하나 더 보낸다. 두 요청 중 어느 것이든 먼저 응답이 도착하면 그 결과를 쓰고 나머지 하나는 취소한다. 이 방식의 이점은 명확하다 — 느린 서버가 최종적으로 응답에 실패할 때까지 기다리지 않고, "느려지고 있다"는 신호만으로 선제적으로 대응해 전체 응답시간을 단축한다. 다만 이는 공짜가 아니다. 헤징된 요청만큼 백엔드에 추가 부하가 걸리므로, 무분별하게 모든 요청에 헤징을 적용하면 오히려 시스템 전체 부하를 늘려 상황을 악화시킬 수 있다.

## 핵심 개념 2 — 언제 얼마나 헤징할지 결정하는 임계값 설계

헤징의 실무 핵심은 "얼마나 기다린 뒤에 추가 요청을 보낼 것인가"라는 임계값 설계에 있다. 가장 흔히 쓰는 기준은 해당 요청 타입의 최근 응답시간 분포에서 특정 백분위수(예: p95)를 임계값으로 삼는 것이다. 이렇게 하면 정의상 전체 요청의 5%만 헤징 대상이 되므로, 추가 부하를 예측 가능한 범위로 통제할 수 있다. 이 임계값을 고정값이 아니라 최근 트래픽의 실측 분포로 계속 갱신하는 적응형 방식(adaptive hedging)을 쓰면, 트래픽 패턴이 시간대별로 달라져도 헤징 비율이 일정하게 유지된다. 또한 헤징은 멱등성(idempotent)이 보장된 읽기 요청에만 적용하는 것이 원칙이다 — 결제 승인처럼 부작용이 있는 쓰기 요청을 헤징하면 같은 요청이 두 번 처리될 위험이 생기므로, 그런 요청에는 멱등성 키를 반드시 함께 결합해야 한다.

| 항목 | Retry(재시도) | Hedging(헤징) |
|---|---|---|
| 발동 시점 | 요청이 실패로 확정된 후 | 응답이 임계값(예: p95)보다 늦어지는 시점 |
| 목적 | 실패 복구 | 꼬리 지연시간(p99 등) 단축 |
| 원래 요청 | 실패 확정, 폐기 | 취소하지 않고 병행 유지 |
| 추가 부하 | 실패율에 비례 | 정한 백분위 비율만큼 고정적으로 발생 |
| 적용 대상 | 멱등 요청 권장 | 반드시 멱등 요청에만 적용 |

## 코드 예제 — gRPC 클라이언트에서 헤징 설정

```yaml
# gRPC 서비스 설정(service config)에서 헤징 정책 정의
{
  "methodConfig": [{
    "name": [{ "service": "search.SearchService" }],
    "hedgingPolicy": {
      "maxAttempts": 3,
      "hedgingDelay": "0.1s",
      "nonFatalStatusCodes": ["UNAVAILABLE"]
    }
  }]
}
```

```java
// 애플리케이션 레벨에서 직접 구현하는 단순화된 헤징 예시
CompletableFuture<Response> primary = callServer(serverA, request);
CompletableFuture<Response> hedged = primary
    .completeOnTimeout(null, 100, TimeUnit.MILLISECONDS)
    .thenCompose(result -> result != null
        ? CompletableFuture.completedFuture(result)
        : callServer(serverB, request)); // 100ms 안에 응답 없으면 다른 서버에도 요청

Response response = CompletableFuture.anyOf(primary, hedged).join();
```

## 실무 포인트

- **헤징 비율을 반드시 모니터링하라.** 헤징된 요청 비율이 설정한 백분위수(예: 5%)보다 훨씬 높게 나온다면, 이는 백엔드 전체가 느려지고 있다는 신호이지 헤징으로 해결할 문제가 아니다. 이런 경우 헤징이 오히려 이미 느려진 시스템에 부하를 더해 상황을 악화시킬 수 있으므로, 헤징 자체에 상한(circuit breaker와 유사하게 헤징 비율이 너무 높아지면 헤징을 잠시 끄는 것)을 두는 것이 안전하다.
- **캐시가 있는 계층에서는 헤징 효과가 배가된다.** 첫 번째 요청이 캐시 미스로 느려지는 동안 두 번째 헤징 요청이 다른 노드의 캐시 히트로 빠르게 응답하는 경우가 실제로 흔히 관찰된다.
- **모든 요청에 헤징을 걸지 말고, 실제로 꼬리 지연시간이 사용자 경험에 크게 영향을 주는 핵심 경로(검색, 결제 조회 등)에만 선택적으로 적용하라.** 시스템 전체에 무차별 적용하면 관리해야 할 추가 부하와 복잡도만 늘어난다.

## 마무리 요약

- Request Hedging은 실패를 확인한 뒤 재시도하는 대신, 응답이 임계값보다 늦어지는 시점에 선제적으로 같은 요청을 다른 서버에 추가로 보내 더 빠른 응답을 채택하는 전략이다.
- 헤징 임계값은 보통 최근 응답시간의 특정 백분위수(p95 등)로 설정해 추가 부하를 예측 가능한 범위로 통제하며, 멱등한 읽기 요청에만 적용하는 것이 원칙이다.
- 헤징 비율을 모니터링해 백엔드 전체가 느려지는 신호와 구분하고, 실제 사용자 경험에 영향이 큰 핵심 경로에만 선택적으로 적용해야 부작용 없이 효과를 볼 수 있다.
