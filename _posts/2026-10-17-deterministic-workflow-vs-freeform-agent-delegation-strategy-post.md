## 어떤 요구에서 출발하는가

"견적서 검토 프로세스를 에이전트로 자동화해주세요 — 서류를 받으면 항목을 확인하고, 이상하면 담당자에게 확인 요청을 보내고, 문제없으면 승인 처리까지 해주세요." 이런 요청이 들어오면 설계자가 가장 먼저 답해야 할 질문은 "어떤 에이전트 프레임워크를 쓸까"가 아니다. **이 작업의 다음 단계를 실행 전에 코드로 적어둘 수 있는가, 아니면 서류 내용을 보기 전까지는 다음에 뭘 할지 알 수 없는가**다. 이 질문에 잘못 답하면 두 방향으로 실패한다. 모든 경우의 수를 미리 그래프로 그리려다 기능 하나 추가할 때마다 그래프 전체를 다시 그려야 하는 유지보수 지옥에 빠지거나, 반대로 반복적이고 예측 가능한 작업에까지 완전한 자율성을 줘서 실행할 때마다 다른 경로를 타고 실패를 재현할 수 없는 상태에 빠진다.

업무 자동화를 에이전트로 넘기는 일이 일상이 된 지금, 이 경계를 어디에 그을지는 매 프로젝트 초반에 반드시 내려야 하는 아키텍처 결정이 됐다.

## 전체 시스템에서의 위치 — 오케스트레이션 레이어는 어디에 앉는가

오케스트레이션 레이어는 요청을 받는 API 서버와 실제 LLM 호출 사이에 놓인다. 결정론적 워크플로우를 선택하면 이 레이어는 상태를 가진 그래프나 스크립트가 되어, 어떤 단계 다음에 어떤 단계가 오는지를 코드가 통제하고 LLM은 각 노드 내부의 국소적 판단(이 서류가 이상한지, 이 문장이 승인 조건을 만족하는지)만 맡는다. 자유형 에이전트를 선택하면 이 레이어 자체가 LLM이 되어, 다음에 어떤 도구를 부를지와 언제 작업을 끝낼지까지 스스로 판단한다. 두 구조 모두 체크포인트 저장소(실패 시 재개 지점)와 도구 호출 계층을 공유하지만, "다음에 무엇을 할지 누가 결정하는가"가 완전히 다르다.

## 선택의 트레이드오프

| 기준 | 결정론적 워크플로우 | 자유형 에이전트 위임 |
|---|---|---|
| 재현성·감사 | 같은 입력이면 같은 경로, 추적 쉬움 | 실행마다 경로가 달라질 수 있음 |
| 실패 복구 | 단계 단위 체크포인트로 부분 재개 | 전체 트랜스크립트를 되짚어야 함 |
| 변화 대응 | 새 분기마다 그래프 수정 필요 | 프롬프트 수정만으로 대응 가능 |
| 적합한 작업 | 분기와 순서가 이미 명확한 반복 업무 | 다음 단계가 입력을 보기 전엔 불분명한 탐색 |
| 실패 원인 | 설계 누락(처리 못한 분기) | 에이전트 간 정합성 붕괴 |

이 선택이 추상적인 취향 문제가 아니라는 근거가 있다. 프로덕션에 올라간 1,600건 이상의 멀티에이전트 실행 트레이스를 분석한 조사에서 실패율이 41%~86.7%에 달했고, 그 원인의 대부분이 모델의 추론 능력 부족이 아니라 **시스템 설계와 에이전트 간 정합성 문제**로 나타났다. 즉 "자유도를 주면 더 똑똑하게 풀 것"이라는 직관과 달리, 분할선이 이미 명확한 작업일수록 그 분할을 코드로 고정하는 편이 실패를 줄인다. 반대로 서류 내용에 따라 다음 담당자가 완전히 달라지는 것처럼 범위 자체가 실행 중에 드러나는 작업이라면, 그래프로 미리 못박는 순간 처리 못 하는 사례가 쌓이기 시작한다.

업계 전반의 수렴 지점은 결국 하이브리드다. 뼈대는 결정론적 코드로 짜고, 판단이 꼭 필요한 지점에서만 LLM을 부른다. 2026년 들어 LangGraph의 PostgresSaver 체크포인터처럼 주요 오케스트레이션 프레임워크들이 공통적으로 "내구성 있는 실행(durable execution)"을 핵심 기능으로 끌어올린 것도 같은 흐름이다 — 자유도는 노드 내부에만 주고, 실행 상태 자체는 언제든 복구 가능한 결정론적 저장소에 둔다는 뜻이다.

## 코드로 보는 하이브리드 경계

```python
# 결정론적 뼈대: 분기는 코드가 결정
def review_quote(document):
    state = checkpoint.load_or_init(document.id)

    if state.stage == "extract":
        fields = extract_fields(document)          # 결정론적 파싱
        state.stage = "classify"
        checkpoint.save(state)

    if state.stage == "classify":
        # 판단이 꼭 필요한 지점에서만 LLM 호출 (bounded decision point)
        verdict = llm_classify(fields, schema=ANOMALY_SCHEMA)
        state.stage = "approve" if not verdict.anomaly else "escalate"
        checkpoint.save(state)

    if state.stage == "escalate":
        notify_reviewer(fields, verdict.reason)
        return "pending_human"

    if state.stage == "approve":
        approve_quote(document.id)
        return "approved"
```

전체 흐름(추출 → 분류 → 승인/에스컬레이션)은 코드가 결정하지만, "이 항목이 이상한가"라는 판단 하나만 스키마가 강제된 LLM 호출로 좁혀 넣었다. 이 범위를 넘어 LLM이 다음 단계 자체를 고르게 하면 하이브리드가 아니라 자유형으로 되돌아간다.

## 실무에서 걸리는 두 가지 안티패턴

첫 번째는 탐색적 작업을 억지로 결정론적 그래프에 끼워맞추는 경우다. 신규 요청 유형이 생길 때마다 그래프에 분기를 추가해야 하고, 결국 그래프가 if문 트리와 다를 바 없어지며 유지보수 비용이 자유형 에이전트보다 커진다. 두 번째는 반대로 반복적이고 예측 가능한 업무에 완전한 자율성을 준 경우다. 똑같은 유형의 서류인데도 에이전트가 매번 다른 순서로 도구를 호출하고, 실패가 나도 어느 단계에서 틀렸는지 트랜스크립트를 처음부터 읽어야 한다. 판단 체크리스트는 세 가지로 좁힐 수 있다. 다음 단계를 실행 전에 적을 수 있는가, 틀렸을 때 되돌리는 비용이 큰가(크다면 결정론 + 사람 개입 지점이 필요), 분기 자체가 자주 바뀌는가(자주 바뀐다면 자유형이 유지보수에 유리).

## 실제 프로젝트 진행 순서

1. 작업을 단계 다이어그램으로 먼저 그려본다. 다음 단계를 적다가 막히는 지점이 나오면 그 지점만 자유형 위임 후보로 표시한다.
2. 각 단계(노드)의 입출력 스키마를 정의해 단계 간 경계를 명확히 한다.
3. 실패 복구 비용이 큰 단계부터 체크포인트 저장을 붙인다.
4. 자유도가 꼭 필요한 지점만 식별해 그 노드에 한해 LLM 판단을 넣는 하이브리드로 전환한다.
5. 운영 중 쌓이는 실패 트레이스를 재현 가능한 리그레션 테스트 셋으로 전환해, 다음 설계 변경의 기준으로 삼는다.

## 마무리

- 자동화 설계의 첫 질문은 모델 선택이 아니라 "다음 단계를 실행 전에 적을 수 있는가"다.
- 실제 실패율 데이터는 자유도를 늘릴수록 좋아진다는 직관과 반대로, 분할선이 명확한 작업은 코드로 고정하는 편이 안전하다는 것을 보여준다.
- 뼈대는 결정론적 코드, 판단은 범위가 좁혀진 LLM 호출이라는 하이브리드가 2026년 주요 프레임워크들이 수렴한 지점이다.
