## 왜 지금 이 문제가 불거지는가

"우리 API를 이제 사람 개발자가 아니라 AI 에이전트가 직접 호출하게 해주세요." 몇 달 전까지 이런 요구사항은 "API 키 발급하고 기존 레이트 리밋 그대로 적용하면 끝"으로 처리됐다. 분당 100회, 시간당 1000회 같은 숫자는 사람이 호출하는 트래픽 패턴을 전제로 튜닝된 것이었고, 그 전제는 꽤 오래 잘 작동했다.

문제는 에이전트가 사람과 전혀 다른 속도와 패턴으로 API를 두드린다는 데 있다. 에이전트는 작업 하나를 끝내려고 같은 엔드포인트를 몇 초 안에 수십 번 호출할 수 있고, 재시도 루프에 빠지면 분당 요청 수 임계값을 넘기지 않으면서도 리소스를 계속 소모한다. 2026년 업계에서 반복적으로 지적되는 사례가 바로 이것이다 — "분당 N회"라는 전통적 제한은 에이전트가 끊임없이 돌리는 재시도 루프 앞에서 사실상 무력화된다. 요청 하나하나는 제한 안에 있지만, 전체 소비 자원은 통제 불능으로 치솟는다.

## 요구사항을 기술 문제로 번역하기

"에이전트가 우리 API를 쓰게 해주세요"라는 말은 실제로 세 가지 질문을 숨기고 있다. 첫째, 무엇을 세야 하는가 — 요청 횟수인가, 아니면 그 요청이 실제로 소비하는 컴퓨팅·토큰·비용인가. 둘째, 누구 단위로 제한해야 하는가 — 호출하는 애플리케이션 전체인가, 그 애플리케이션이 띄운 개별 에이전트 인스턴스인가, 그 에이전트 뒤에 있는 최종 사용자인가. 셋째, 한도를 넘었을 때 무엇을 해야 하는가 — 그냥 차단할 것인가, 재시도 예산을 따로 둘 것인가, 서킷 브레이커로 완전히 끊을 것인가.

기존 레이트 리밋 설계는 이 셋 중 첫 번째 질문에 "요청 횟수"라고 단정하고 시작했다. 에이전트 트래픽에서는 이 단정 자체가 틀린 전제가 된다. 같은 "요청 1건"이라도 짧은 분류 작업과 긴 문서 요약이 소비하는 자원은 수십 배 차이 날 수 있기 때문이다.

## 전체 시스템에서의 위치

레이트 리밋은 API 게이트웨이 한 지점의 설정값이 아니라, 요청이 들어와 자원을 소비하고 응답이 나가기까지 전체 경로에 걸친 제어 장치다.

<img src="/assets/images/posts/2026-10-01-agent-traffic-api-rate-limiting-redesign-1.svg" alt="에이전트 요청이 게이트웨이의 계층적 한도 검사(조직-에이전트-최종사용자)를 거치고, 비용 계측기가 실제 자원 소비를 기록하며, 초과 시 재시도 예산과 서킷 브레이커로 이어지는 구조도" style="width:100%;">

요청은 게이트웨이에서 먼저 조직 단위, 에이전트 식별자 단위, 최종 사용자 단위로 겹겹이 쌓인 한도를 통과해야 한다. 요청이 실제로 처리되는 동안 **비용 계측기**가 토큰 수·컴퓨팅 시간·외부 API 호출 비용을 실시간으로 기록하고, 이 값이 사전에 설정한 비용 한도에 가까워지면 다음 요청부터 조절이 들어간다. 재시도가 반복되는 호출에는 별도의 **재시도 예산**을 적용해, 같은 작업이 실패를 반복하며 소모할 수 있는 자원 총량에 상한을 둔다. 이 상한을 넘기면 서킷 브레이커가 해당 에이전트의 호출을 일정 시간 완전히 차단한다.

## 선택의 트레이드오프

| 기준 | 요청 수 기반 (기존) | 비용·토큰 기반 (에이전트 대응) |
|---|---|---|
| 측정 단위 | 분당/시간당 요청 횟수 | 토큰 수, 컴퓨팅 시간, 실제 비용 |
| 재시도 루프 방어 | 못 막음 — 요청 수만 안 넘으면 통과 | 재시도 예산으로 누적 소비를 직접 제한 |
| 구현 복잡도 | 낮음 — 카운터 하나로 충분 | 높음 — 요청별 자원 소비 계측 필요 |
| 사람 트래픽에 적용 | 적합 — 패턴이 예측 가능 | 과한 설계 — 계측 비용만 늘어남 |
| 적합한 경우 | 사람이 직접 호출하는 공개 API | 에이전트·자동화 클라이언트가 섞인 API |

함정은 두 방식 중 하나만 택하는 것이다. 실무에서는 사람 사용자에게는 기존 요청 수 기반 제한을 유지하고, API 키나 OAuth 클라이언트 단위로 "이 호출 주체가 에이전트인가"를 식별해 그 경로에만 비용 기반 계층을 추가로 얹는 조합이 가장 잘 작동한다. 모든 트래픽에 비용 계측을 욱여넣으면 계측 자체가 지연과 운영 부담을 키운다.

## 실제 프로젝트 진행 순서

1. **호출 주체를 식별하는 체계부터 만든다.** API 키나 OAuth 클라이언트 등록 단계에서 "이 클라이언트는 에이전트다"라는 표식을 남겨야, 이후 제한 정책을 사람 트래픽과 분리해 적용할 수 있다.
2. **요청당 자원 소비를 계측한다.** 토큰 수나 처리 시간을 응답에 메타데이터로 남기는 작업을 가장 먼저 끝낸다. 이 계측 없이는 비용 기반 한도 자체를 설계할 수 없다.
3. **계층적 한도 구조를 설계한다.** 조직 전체 한도, 에이전트 식별자별 한도, 그 뒤의 최종 사용자별 한도를 각각 어떤 값으로 둘지 트래픽 패턴을 관찰하며 정한다.
4. **재시도 예산과 서킷 브레이커를 먼저 좁은 범위에 적용한다.** 전체 API가 아니라 에이전트 트래픽이 집중되는 엔드포인트 한두 곳에 먼저 붙여 실제 효과를 검증한다.
5. **임계값을 고정하지 말고 피크·한산 시간대에 따라 조절 가능하게 만든다.** 여유 있는 시간대에는 완화하고, 수요가 몰릴 때는 자동으로 조이는 적응형 조절을 마지막 단계로 넣는다.

## 마무리

- 에이전트는 사람과 다른 속도·패턴으로 API를 호출하므로, 요청 횟수만 세는 기존 레이트 리밋은 재시도 루프 앞에서 무력화된다.
- 토큰·컴퓨팅·비용을 직접 계측해 조직-에이전트-사용자 단위로 계층화한 한도와, 재시도 예산·서킷 브레이커 조합이 에이전트 트래픽에 필요한 대응이다.
- 모든 트래픽에 비용 기반 계측을 욱여넣기보다, 에이전트로 식별된 경로에만 추가 계층을 얹는 조합이 구현 부담 대비 효과가 크다.
