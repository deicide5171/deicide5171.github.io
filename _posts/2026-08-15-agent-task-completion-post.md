## 왜 지금 "완료율"인가

지난 몇 년간 LLM을 평가하는 방식은 대체로 "이 답변이 자연스러운가", "사람이 쓴 것과 비슷한가"에 초점이 맞춰져 있었다. 챗봇 시대에는 합리적인 기준이었다. 사용자가 모델과 나누는 것은 결국 대화였기 때문이다.

하지만 에이전트 시대에는 이 기준이 무의미해진다. 최근에는 소비자용 에이전트가 매장에 전화를 걸어 재고를 확인하고 실제로 주문까지 완료하는 사례처럼, 에이전트가 실제 세계의 작업을 끝까지 수행하는 방향으로 무게중심이 옮겨가고 있다. 이런 에이전트에게 "말투가 자연스러운가"는 부차적인 질문이다. 진짜 질문은 하나다 — **일이 실제로 끝났는가.**

동시에 모델 쪽에서도 변화가 있다. 컨텍스트 윈도우가 100만 토큰 수준으로 늘어나면서 에이전트가 긴 작업 이력, 여러 도구 호출 결과, 방대한 문서를 한 번에 들고 있을 수 있게 됐다. 능력이 늘어난 만큼, 그 능력을 "끝까지 해냈는가"로 측정하는 평가 체계가 뒤따라야 하는 시점이다.

## 대화 평가 vs 완료 평가

두 평가 패러다임은 측정 대상 자체가 다르다.

| 항목 | 대화 중심 평가 | 완료 중심 평가 |
|---|---|---|
| 측정 대상 | 응답의 유창함·관련성 | 작업의 최종 상태 |
| 채점 방식 | 사람 또는 LLM이 텍스트를 비교 | 실행 결과(파일, DB, 외부 시스템 상태)를 검증 |
| 실패 감지 | 답변이 이상하면 감지 | 답변은 그럴듯한데 작업은 실패해도 감지 가능 |
| 대표 사례 | 챗봇 QA, 요약 품질 평가 | 코딩 에이전트의 테스트 통과 여부, 예약·구매 완료 여부 |

완료 중심 평가의 핵심은 "그럴듯함"과 "성공"을 분리한다는 점이다. 에이전트가 자신감 있게 "완료했습니다"라고 말해도, 실제로 파일이 저장되지 않았거나 API 호출이 실패했다면 그 결과물은 실패로 채점되어야 한다.

## 완료 중심 평가를 설계할 때 체크할 것

1. **검증 가능한 종료 상태를 정의한다** — "적절히 답했는가"가 아니라 "DB에 레코드가 생겼는가", "테스트가 통과했는가"처럼 코드로 확인 가능한 조건을 채점 기준으로 삼는다.
2. **중간 과정이 아니라 최종 상태를 본다** — 에이전트가 도구를 몇 번 호출했는지보다, 그 결과로 세계 상태가 원하는 대로 바뀌었는지가 중요하다.
3. **실패를 구분한다** — 작업을 아예 시도하지 않은 실패와, 시도했지만 부작용을 남기고 실패한 경우(예: 파일을 절반만 쓰고 중단)는 위험도가 다르다.
4. **재현 가능한 환경을 준비한다** — 실제 매장에 전화를 걸거나 실제 결제를 하는 시나리오는 평가 때마다 격리된 샌드박스로 재현해야 안전하고 반복 가능하다.

## 최소 예제: 완료 여부를 코드로 채점하기

아래는 "특정 파일에 원하는 내용이 실제로 기록됐는가"를 기준으로 채점하는 간단한 평가 스크립트다.

```python
# eval_task_completion.py
from pathlib import Path

def grade(task_dir: Path) -> dict:
    output = task_dir / "result.json"
    if not output.exists():
        return {"completed": False, "reason": "출력 파일 없음"}

    import json
    data = json.loads(output.read_text())
    if data.get("status") != "success":
        return {"completed": False, "reason": f"status={data.get('status')}"}

    return {"completed": True, "reason": "ok"}
```

에이전트의 최종 응답 텍스트는 채점 기준에서 아예 제외했다. 오직 실행 결과로 남은 산출물만 확인한다.

## 실무 포인트

- 사내에서 에이전트를 도입할 때도 "답변 만족도" 설문 대신, 실제 업무 시스템(티켓 상태, 배포 성공 여부 등)을 기준으로 성공률을 집계하는 편이 훨씬 신뢰도 높은 지표가 된다.
- EU AI Act의 투명성 의무처럼 규제도 "AI가 무엇을 했는지"를 추적 가능하게 만드는 방향으로 움직이고 있다. 완료 중심 평가 체계는 이런 감사 요구에도 자연스럽게 대응할 수 있다.
- 완료율만 좇다 보면 에이전트가 부작용을 감수하고서라도 "일단 완료 처리"하는 리스크가 생길 수 있다. 완료 여부와 별개로 "되돌리기 어려운 부작용을 남겼는가"도 항상 함께 채점해야 한다.

## 3줄 요약

- AI 에이전트 평가는 "대화가 자연스러운가"에서 "작업이 실제로 끝났는가"로 무게중심이 옮겨가고 있다.
- 완료 중심 평가는 응답 텍스트가 아니라 실행 후 남은 상태(파일, DB, 외부 시스템)를 검증한다.
- 완료율 지표를 도입할 때는 부작용 여부도 함께 채점해야 안전하다.
