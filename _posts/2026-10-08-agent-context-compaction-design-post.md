## 왜 지금 이 판단이 불거지는가

"에이전트가 하루 종일 한 작업을 붙잡고 있어도 중간에 맥락을 잃지 않게 해주세요." 이 요구는 모델의 컨텍스트 윈도우가 아무리 커져도(100만 토큰급 모델이 나와도) 사라지지 않는다. 긴 리팩터링, 반복되는 테스트-수정 루프, 수십 번의 도구 호출이 쌓이는 에이전틱 코딩 세션에서는 결국 어느 시점에 컨텍스트가 한계에 닿는다. 문제는 "윈도우를 늘리면 해결되는가"가 아니라 "한계에 닿았을 때 무엇을 버리고 무엇을 남길 것인가"다. 이건 용량의 문제가 아니라 설계의 문제다.

2026년 들어 주요 코딩 에이전트들이 이 문제에 각자 답을 내놓았다. Claude Code는 세션이 한계치 근처(보통 사용 가능 토큰의 95% 수준)에 닿으면 자동으로 대화 이력을 LLM으로 다시 써서 압축하는 auto-compact를 기본으로 켜 둔다. OpenAI의 Codex CLI도 설정된 토큰 한도를 넘으면 자동으로, 또는 `/compact` 명령으로 수동으로 이력을 요약하고 원본 턴을 버린다. 두 구현 모두 "꽉 차면 요약해서 줄인다"는 같은 전략을 쓰지만, 정확히 언제·무엇을 압축하느냐를 둘러싼 설계 논쟁이 뜨겁다 — 임계값에 도달한 뒤 압축하면 이미 품질이 떨어진 다음이라는 비판과, 압축 자체를 모델이 스스로 판단해야 한다는 반론이 동시에 나온다. 자신의 에이전트 파이프라인에 긴 세션을 태우기로 한 순간, 이 선택은 피할 수 없는 설계 결정이 된다.

## 요구사항을 기술 문제로 번역하기

"세션이 끊기지 않게 해주세요"는 실제로는 "컨텍스트 윈도우가 한계에 가까워질 때, 어떤 정보를 어떤 형태로 보존할 것인가"라는 질문으로 번역된다. 여기서 두 가지 독립적인 결정이 숨어 있다. 첫째는 **타이밍** — 언제 압축을 트리거할 것인가. 토큰 사용량이 고정 임계값(예: 95%)을 넘는 순간 기계적으로 트리거할 수도 있고, 작업의 의미 단위(한 하위 작업이 끝나는 시점 등)를 모델이 스스로 판단해 트리거할 수도 있다. 둘째는 **방법** — 압축을 어떻게 수행할 것인가. 과거 대화를 LLM에게 다시 읽혀 "완료된 작업·현재 상태·남은 작업" 형태로 요약하게 할 수도 있고, 요약 없이 불필요한 토큰(장황한 설명, 중복된 도구 출력)만 결정적으로 삭제할 수도 있다. 이 두 축의 조합이 실제 압축 전략을 결정한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-08-agent-context-compaction-design-1.svg" alt="에이전트 세션의 턴들이 누적되며 컨텍스트 윈도우를 채우고, 압축 트리거가 작동하면 압축 전략 계층(요약·검증 삭제·관측 마스킹·서브에이전트 격리 중 선택)을 거쳐 압축된 컨텍스트가 다시 모델 입력으로 돌아가는 순환 구조도" style="width:100%;">

압축 계층은 에이전트 루프 안에서 "모델 호출"과 "다음 턴의 입력" 사이에 끼어드는 전처리 단계다. 앞단에는 누적되는 대화 턴, 도구 호출 결과, 파일 읽기 출력이 계속 쌓이는 컨텍스트 버퍼가 있다. 이 버퍼가 설정된 한도에 가까워지면 압축 계층이 개입해, 쌓인 이력을 더 작은 표현으로 바꾼다. 뒷단에는 압축된 컨텍스트를 받아 다음 모델 호출의 입력으로 쓰는 에이전트 루프가 있고, 이 루프는 압축 결과가 "사용자 의도·이미 내린 결정·파일 상태·남은 작업"을 제대로 보존했는지에 전적으로 의존한다. 압축이 망가지면 에이전트는 이미 끝낸 작업을 반복하거나, 사용자가 중간에 바꾼 요구사항을 잊어버린다 — 겉으로는 "세션이 안 끊겼는데 왜 이상하게 행동하지"로 보이는 버그의 상당수가 바로 이 계층에서 발생한다.

## 선택의 트레이드오프

| 전략 | 트리거 방식 | 정보 손실 | 비용/지연 | 적합한 상황 |
|---|---|---|---|---|
| 임계값 기반 LLM 요약 | 토큰 사용량이 고정 % 도달 | 중간(요약이 환각 가능) | 요약 생성 비용 추가 | 범용 코딩 에이전트, 가장 널리 쓰임 |
| Verbatim/토큰 삭제 | 임계값 또는 수동 | 낮음(남은 텍스트는 원문 그대로) | 낮음(LLM 호출 없음) | 중복·장황한 출력이 많은 세션 |
| Observation Masking | 오래된 도구 출력 시점 | 낮음(최신 상태만 유지) | 매우 낮음(단순 치환) | 반복적인 파일 읽기·테스트 실행이 많은 세션 |
| 시맨틱 타이밍(모델 자율 판단) | 작업 단위 완료 시점 모델 판단 | 낮음(품질 저하 전에 압축) | 추가 판단 비용 | 긴 멀티스텝 작업, 품질 민감 |
| 서브에이전트 격리 | 하위 작업마다 새 컨텍스트 | 거의 없음(격리로 회피) | 조정 오버헤드 | 독립적으로 나뉘는 하위 작업이 많은 경우 |

실무에서 가장 흔한 선택은 임계값 기반 LLM 요약이지만, 이것만 쓰면 "이미 품질이 떨어진 뒤에 압축한다"는 근본적 한계가 남는다. 반대로 서브에이전트 격리는 정보 손실이 거의 없지만 하위 작업 간 조정 비용이 커서, 작업이 서로 독립적이지 않은 경우(예: 한 파일을 여러 단계에 걸쳐 계속 수정)에는 오히려 맥락이 쪼개져 불리하다. 둘 중 하나만 고르기보다, 반복되는 도구 출력에는 observation masking을, 전체 흐름 요약에는 LLM 요약을 함께 쓰는 계층적 조합이 실무에서는 더 흔하다.

## 실제 프로젝트 진행 순서

1. **압축이 실제로 필요한지부터 확인한다.** 세션이 애초에 짧게 끝나는 워크플로라면 압축 설계에 들이는 비용 자체가 과투자다. 평균 세션 길이와 턴당 토큰 증가율을 먼저 측정한다.
2. **무엇을 "반드시 보존해야 하는 정보"로 정의할지 명시적으로 적는다.** 사용자의 원래 요구사항, 지금까지 내린 설계 결정, 수정한 파일 목록과 그 이유, 아직 끝나지 않은 작업 — 이 네 가지를 압축 결과의 필수 필드로 못박아 두지 않으면 요약이 매번 다른 것을 빠뜨린다.
3. **가장 비용이 낮은 전략부터 적용한다.** LLM 요약을 먼저 넣기보다, 오래된 도구 출력을 마스킹하거나 중복 텍스트를 결정적으로 제거하는 것부터 시작해 얼마나 버틸 수 있는지 본다.
4. **임계값과 트리거 시점을 실제 실패 사례로 조정한다.** 압축 직후 에이전트가 이전 결정을 잊는 사례를 수집해, 트리거 시점을 앞당기거나 보존 필드를 늘린다.
5. **압축 품질을 별도로 평가한다.** 압축 전후로 같은 질문("지금까지 뭘 했지?")을 던져 답이 일치하는지 자동으로 검증하는 회귀 테스트를 만든다. 압축은 눈에 보이지 않는 실패를 만들기 때문에 수동 QA만으로는 놓치기 쉽다.

## 코드 예시 — 보존 필드를 강제하는 압축 프롬프트 구조

```python
COMPACTION_PROMPT = """
아래는 지금까지의 대화 이력이다. 다음 형식으로만 요약하라:

[사용자 요구사항]
- 원래 요청한 내용을 그대로 유지

[확정된 설계 결정]
- 이미 내린 결정과 그 이유 (번복하지 말 것)

[수정된 파일과 상태]
- 파일 경로: 무엇을 왜 바꿨는지

[남은 작업]
- 아직 끝나지 않은 단계만 나열

이 네 섹션 외의 내용은 포함하지 말 것.
"""

def should_compact(token_count, max_tokens, threshold=0.95):
    return token_count >= max_tokens * threshold
```

## 실무 포인트

**압축 품질을 측정하지 않으면 회귀를 알아챌 방법이 없다.** 요약이 매끄럽게 생성되는 것과 실제로 중요한 정보를 보존하는 것은 다른 문제다. 압축 직후 질의응답 테스트를 CI처럼 자동화해야 한다.

**모든 것을 LLM 요약에 맡기지 않는다.** 도구 호출 결과처럼 구조가 뻔한 데이터는 요약보다 결정적 마스킹이 더 안전하고 저렴하다. 압축을 단일 전략이 아니라 계층으로 설계해야 하는 이유다.

**압축 시점을 사용자에게 투명하게 알린다.** 압축이 일어난 세션에서 에이전트가 이전 맥락을 일부 놓치는 건 구조적으로 피할 수 없다. 이걸 숨기기보다, 압축이 일어났다는 신호를 남겨 사용자가 중요한 결정을 다시 확인하도록 유도하는 편이 낫다.

## 마무리

- 컨텍스트 윈도우는 아무리 커져도 긴 에이전틱 세션에서는 결국 한계에 닿으며, 핵심 질문은 "늘릴 것인가"가 아니라 "한계에 닿았을 때 무엇을 보존할 것인가"다.
- 임계값 기반 LLM 요약, verbatim 삭제, observation masking, 시맨틱 타이밍, 서브에이전트 격리는 각각 정보 손실·비용·적합한 상황이 다르며, 실무에서는 이들을 계층적으로 조합하는 경우가 많다.
- 보존해야 할 필드를 명시적으로 정의하고, 압축 품질을 자동으로 검증하는 테스트를 갖추지 않으면 압축은 눈에 보이지 않는 실패를 만드는 계층이 된다.
