## 왜 지금 프리픽스 캐싱을 다시 봐야 하는가

에이전트 서비스가 늘면서 하나의 요청 안에 긴 시스템 프롬프트, 도구 설명, few-shot 예제가 함께 딸려 들어가는 패턴이 표준이 됐다. 문제는 사용자마다 실제로 다른 부분은 마지막 몇 줄뿐인데, 서빙 엔진이 요청마다 전체 시퀀스의 KV 캐시를 처음부터 다시 계산한다면 GPU 연산의 대부분이 완전히 똑같은 값을 반복해서 만드는 데 쓰인다는 점이다. Anthropic·OpenAI가 제공하는 프롬프트 캐싱 API는 이 문제를 사용자가 명시적으로 캐시 경계를 지정하는 방식으로 풀지만, 자체 서빙 스택을 운영하는 팀이라면 애초에 어떤 요청이 어떤 접두사를 공유하는지 엔진이 스스로 찾아내 재사용하게 만드는 편이 훨씬 유연하다. SGLang의 RadixAttention은 바로 이 자동 탐지·재사용을 KV 캐시 관리 계층에서 구현한 설계다.

## 핵심 개념 1 — 라딕스 트리로 KV 캐시를 색인하기

RadixAttention의 핵심은 지금까지 처리한 모든 시퀀스의 KV 캐시를 하나의 라딕스 트리(압축 트라이)에 저장해둔다는 것이다. 트리의 각 경로는 토큰 시퀀스를, 각 노드는 그 지점까지의 KV 캐시 블록을 가리킨다. 새 요청이 들어오면 엔진은 요청의 토큰 시퀀스를 트리 루트부터 따라 내려가며 이미 캐시된 최장 공통 접두사를 찾는다. 시스템 프롬프트와 few-shot 예제가 100% 일치한다면 그 구간 전체의 KV 캐시 연산을 건너뛰고, 실제로 새로운 부분(사용자 질문)에 대해서만 prefill을 수행한다. 여러 사용자의 요청이 같은 시스템 프롬프트를 공유하는 멀티테넌트 API 서버, 같은 few-shot 템플릿을 반복 사용하는 에이전트 워크플로, 트리 탐색형 추론(tree-of-thought)처럼 하나의 프리픽스에서 여러 분기가 뻗어나가는 워크로드에서 특히 효과가 크다.

## 핵심 개념 2 — 캐시 축출과 참조 카운팅

GPU 메모리는 유한하므로 트리는 무한정 커질 수 없다. RadixAttention은 각 노드에 참조 카운트를 유지해 현재 활성 요청이 물고 있는 노드는 절대 축출하지 않고, 가장 오래전에 접근한 리프 노드부터 LRU 방식으로 제거한다. 여기에 더해 SGLang은 캐시 인지 스케줄러를 함께 둬서, 들어오는 요청들을 무작위 순서가 아니라 공유 접두사가 많은 요청끼리 묶어 배치하도록 큐 순서 자체를 조정한다. 이렇게 하면 캐시 적중률이 스케줄링 단계에서부터 최적화된다.

| 방식 | 캐시 경계 지정 | 적용 범위 | 적중 판단 시점 |
|---|---|---|---|
| API 프롬프트 캐싱(Anthropic 등) | 사용자가 명시적으로 표시 | 해당 API 호출 전체 | 요청 수신 즉시 |
| 단순 KV 캐시 재사용 | 완전히 동일한 요청만 | 정확히 같은 시퀀스 | 문자열 완전 일치 |
| RadixAttention | 자동 탐지, 표시 불필요 | 임의 요청 간 공유 접두사 | 트리 탐색으로 최장 일치 계산 |

## 코드 예제 — SGLang 서버에서 공유 접두사 활용

```python
import sglang as sgl

@sgl.function
def multi_turn_qa(s, system_prompt, question):
    s += sgl.system(system_prompt)   # 여러 요청이 동일하면 자동으로 캐시 재사용
    s += sgl.user(question)
    s += sgl.assistant(sgl.gen("answer", max_tokens=256))

# 같은 system_prompt로 여러 질문을 배치 실행하면
# RadixAttention이 시스템 프롬프트 구간의 prefill을 한 번만 계산한다
states = multi_turn_qa.run_batch(
    [{"system_prompt": SHARED_PROMPT, "question": q} for q in questions],
)
```

명시적인 캐시 API를 호출하지 않아도, 배치 안에서 동일한 접두사를 가진 요청들은 엔진 내부에서 자동으로 트리 노드를 공유한다.

## 실무 포인트

- **접두사가 정확히 일치해야 캐시가 재사용된다.** 시스템 프롬프트에 요청마다 타임스탬프나 요청 ID를 끼워 넣으면 그 지점부터 트리 경로가 갈라져 캐시 이득이 사라진다. 가변 정보는 프롬프트 뒷부분에 배치해야 한다.
- **캐시 적중률은 트래픽 패턴에 크게 좌우된다.** 사용자마다 완전히 다른 시스템 프롬프트를 쓰는 서비스라면 라딕스 트리가 커봤자 적중이 거의 없어 이득이 작다. 공통 템플릿을 쓰는 멀티테넌트·에이전트 워크로드에서 효과가 극대화된다.
- **GPU 메모리와 처리량 사이에 트레이드오프가 있다.** 캐시를 위해 확보하는 메모리가 커질수록 동시에 처리할 수 있는 배치 크기는 줄어들 수 있으므로, 캐시 풀 크기와 배치 크기를 함께 튜닝해야 한다.

## 마무리 요약

- RadixAttention은 서로 다른 요청이 공유하는 접두사의 KV 캐시를 라딕스 트리로 색인해, 사용자가 캐시 경계를 명시하지 않아도 자동으로 재사용한다.
- 참조 카운팅 기반 LRU 축출과 캐시 인지 스케줄링이 결합되어, 활성 요청의 캐시를 보존하면서도 적중률이 높은 순서로 배치를 구성한다.
- 프롬프트 뒷부분에 가변 정보를 배치하고 공통 템플릿을 쓰는 워크로드일수록 이 최적화의 이득이 크다.
