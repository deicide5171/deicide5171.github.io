## 왜 지금 Vision API를 직접 다뤄야 하나

"사진을 올리면 자동으로 분류해주세요", "영수증 사진에서 금액만 뽑아주세요" 같은 요구사항은 더 이상 특수한 요청이 아니다. 몇 년 전이라면 별도의 이미지 인식 모델을 학습시키거나 OCR 엔진을 붙여야 했을 일이, 이제는 Claude나 GPT 계열의 멀티모달 API에 이미지를 첨부하고 자연어로 질문만 던지면 끝나는 경우가 많다. 문제는 "일단 되는" 프로토타입과 "실제 서비스에 넣을 수 있는" 구현 사이의 간극이 생각보다 크다는 점이다.

Vision API는 텍스트 전용 API와 호출 방식이 미묘하게 다르고, 이미지라는 매체 특성상 텍스트에는 없던 제약(인코딩 방식, 파일 크기 상한, 이미지당 토큰 비용)이 따라온다. 이 글에서는 개념 설명보다, 처음 Vision API를 붙일 때 실제로 걸려 넘어지는 지점들을 코드와 함께 짚는다.

## 첫 호출: 이미지를 요청에 넣는 두 가지 방법

Vision API에 이미지를 전달하는 방법은 크게 두 가지다. 하나는 이미지를 base64로 인코딩해 요청 본문에 직접 담는 방식이고, 다른 하나는 이미지가 이미 인터넷에 공개된 URL을 전달하는 방식이다.

```python
import base64

with open("receipt.jpg", "rb") as f:
    image_data = base64.b64encode(f.read()).decode("utf-8")

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {
                "type": "image",
                "source": {
                    "type": "base64",
                    "media_type": "image/jpeg",
                    "data": image_data,
                },
            },
            {"type": "text", "text": "이 영수증에서 총 결제 금액만 숫자로 답해줘."},
        ],
    }],
)
```

처음 이 코드를 작성할 때 가장 흔히 저지르는 실수는 `media_type`을 실제 파일 형식과 다르게 적는 것이다. PNG 파일을 `image/jpeg`로 잘못 명시하면 API가 400 에러를 던지거나, 최악의 경우 조용히 잘못된 결과를 내놓는다. 파일 확장자만 보고 판단하지 말고, 실제 이미지 포맷을 확인하는 라이브러리(Python의 `imghdr`나 `Pillow`)로 검증한 뒤 `media_type`을 채우는 습관이 필요하다.

## 흔한 에러 1: 이미지 크기 초과

대부분의 Vision API는 이미지 하나당 크기 상한(보통 몇 MB 수준)과 함께, 너무 큰 이미지는 자동으로 리사이즈해 처리한다는 안내를 두고 있다. 문제는 이 리사이즈 과정에서 원본 해상도가 필요한 세밀한 텍스트(예: 작은 글씨의 영수증 항목)가 뭉개질 수 있다는 점이다.

```python
from PIL import Image

def resize_if_needed(path, max_dimension=1568):
    img = Image.open(path)
    if max(img.size) > max_dimension:
        ratio = max_dimension / max(img.size)
        new_size = tuple(int(x * ratio) for x in img.size)
        img = img.resize(new_size, Image.LANCZOS)
    return img
```

업로드 전에 클라이언트나 서버에서 미리 적정 해상도로 리사이즈해 보내면, API 쪽의 자동 리사이즈에 결과물 품질을 맡기지 않고 직접 통제할 수 있다. 특히 표나 작은 글자가 포함된 문서 이미지라면 원본 대비 화질 저하가 답변 정확도에 바로 영향을 준다.

## 흔한 에러 2: 이미지 토큰 비용을 텍스트처럼 생각하기

이미지 하나가 소비하는 토큰 수는 해상도에 비례해서 계산되며, 생각보다 크다. 대략적으로 1000×1000픽셀 이미지 한 장이 수백에서 천 단위 토큰을 소비할 수 있다. 여러 장의 이미지를 배치로 처리하는 파이프라인을 설계할 때 이 비용을 텍스트 프롬프트처럼 가볍게 취급하면, 트래픽이 늘었을 때 API 비용이 예상보다 훨씬 빠르게 불어난다.

| 처리 방식 | 이미지당 대략적 비용 감각 | 비고 |
|---|---|---|
| 원본 고해상도 그대로 전송 | 높음 | 세부 정보는 살지만 비용 부담 큼 |
| 사전 리사이즈 후 전송 | 중간 | 용도에 맞는 최소 해상도로 조정 |
| 관심 영역만 크롭해 전송 | 낮음 | 영수증 금액란처럼 특정 영역만 필요할 때 효과적 |

## 흔한 에러 3: 한 번에 너무 많은 이미지를 밀어넣기

여러 장의 사진을 동시에 비교 분석시키고 싶어서 요청 하나에 이미지 10장, 20장을 한꺼번에 담는 경우가 있다. API 자체는 여러 장을 허용하지만, 이미지 수가 늘어날수록 모델이 각 이미지에 집중하는 능력이 흐려지고 응답 지연도 함께 늘어난다. 정말 여러 장을 동시에 봐야 하는 작업(예: 같은 제품의 여러 각도 사진 비교)이 아니라면, 이미지 단위로 요청을 쪼개고 결과를 애플리케이션 레벨에서 합치는 편이 안정적이다.

## 실무 포인트

- **재시도 로직에 이미지 재인코딩 비용을 고려하라.** 텍스트 요청과 달리 이미지 요청은 재시도할 때마다 base64 인코딩·네트워크 전송 비용이 함께 반복된다. 실패 원인이 일시적 네트워크 문제인지, 이미지 형식 문제인지 구분해 후자는 재시도 대신 즉시 에러로 처리해야 한다.
- **민감한 이미지(신분증, 결제 정보)는 프롬프트 로깅에서 제외하라.** 디버깅을 위해 요청·응답을 로깅할 때 이미지 데이터를 그대로 남기면 개인정보가 로그 시스템에 쌓인다. 이미지 자체는 로깅하지 않고 메타데이터(크기, 처리 결과 요약)만 남기는 편이 안전하다.
- **모델별 지원 포맷 차이를 확인하라.** JPEG, PNG는 대부분 지원하지만 WebP, GIF, HEIC 지원 여부는 API·모델 버전마다 다르다. 사용자가 업로드한 원본 포맷을 그대로 보내지 말고, 서버에서 지원 포맷으로 변환하는 단계를 항상 거치는 것이 안전하다.

## 마무리 요약

- Vision API는 텍스트 API와 달리 인코딩 방식, 이미지 크기, 토큰 비용이라는 별도의 제약을 가지므로 프로토타입 단계에서부터 이를 고려해야 한다.
- media_type 불일치, 과도한 원본 해상도, 다중 이미지 과다 전송이 실전에서 가장 흔히 겪는 세 가지 실패 지점이다.
- 이미지는 로깅·재시도·비용 계산 모두에서 텍스트와 다르게 다뤄야 하는 별도의 리소스로 취급해야 안정적인 서비스가 된다.
