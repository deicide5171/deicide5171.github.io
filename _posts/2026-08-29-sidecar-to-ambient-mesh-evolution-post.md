서비스 메시가 처음 등장했을 때 내세운 약속은 단순했다. 애플리케이션 코드는 건드리지 않고, 파드마다 프록시 컨테이너(사이드카)를 하나씩 붙여 mTLS·재시도·서킷브레이커 같은 통신 관심사를 인프라 레이어로 옮긴다는 것이었다. Istio와 Envoy가 이 모델을 표준처럼 만들었고, 실제로 많은 조직이 이 방식으로 MSA 통신을 표준화했다.

문제는 규모가 커지면서 드러났다. 파드 하나마다 별도의 Envoy 프로세스가 뜨면서 CPU·메모리 오버헤드가 서비스 개수에 비례해 누적됐고, 사이드카 주입은 파드 생명주기(초기화 순서, 재시작, 리소스 쿼터)에 관여하는 복잡한 의존성이 됐다. 메시를 켜는 것과 안 켜는 것 사이에 "일부만 메시에 넣는다"는 선택지가 사실상 없었던 것도 문제였다. 이런 배경에서 Istio는 사이드카 없이 동작하는 **앰비언트 메시(Ambient Mesh)** 아키텍처를 내놓았고, 이 글에서는 사이드카 모델이 왜 한계에 부딪혔는지, 앰비언트 메시가 이를 어떻게 레이어 분리로 해결하는지를 정리한다.

## 핵심 개념 1: 사이드카 모델의 구조와 비용

전통적인 Istio 사이드카 모델에서는 파드마다 애플리케이션 컨테이너 옆에 Envoy 프록시 컨테이너가 주입된다. 파드 안의 모든 트래픽은 iptables 규칙으로 이 Envoy를 거치도록 강제되고, mTLS 종료·L7 라우팅·재시도·관측성 지표 수집이 전부 이 프록시 안에서 이뤄진다. 애플리케이션은 자신이 메시 안에 있다는 것을 몰라도 된다는 것이 장점이었다.

대가는 리소스다. 서비스가 수백 개, 파드가 수천 개인 클러스터에서는 사이드카 프록시 자체의 CPU·메모리 합산이 무시할 수 없는 수준이 되고, 파드 하나가 뜰 때마다 사이드카가 먼저 준비돼야 트래픽을 받을 수 있다는 초기화 순서 문제(및 그 반대인 종료 순서 문제)도 운영 부담으로 쌓인다. 또한 L4 수준의 mTLS만 필요한 서비스도 L7 라우팅 기능까지 포함한 무거운 프록시를 통째로 짊어져야 했다.

## 핵심 개념 2: 앰비언트 메시 — ztunnel과 waypoint로 계층을 나눈다

앰비언트 메시의 핵심 아이디어는 "모든 트래픽에 L7 기능이 필요한 것은 아니다"라는 관찰에서 출발한다. 그래서 기능을 두 레이어로 분리한다.

- **ztunnel(zero-trust tunnel)**: 노드마다 하나씩 떠 있는 경량 프록시로, 파드마다 뜨는 것이 아니라 노드를 공유한다. mTLS 암호화, 신원 인증(SPIFFE), L4 라우팅만 처리하는 최소 기능만 갖춰 오버헤드가 훨씬 작다.
- **waypoint 프록시**: L7 기능(HTTP 라우팅, 재시도, 서킷브레이커, 세밀한 트래픽 정책)이 실제로 필요한 서비스에 대해서만 선택적으로 배치되는 별도 프록시. 네임스페이스나 서비스 단위로 켜고 끌 수 있다.

이 구조 덕분에 대부분의 서비스는 ztunnel의 L4 보안만으로 메시에 참여하고, 정교한 트래픽 제어가 필요한 일부 서비스만 waypoint를 추가로 배치한다. 애플리케이션 파드에는 더 이상 사이드카 컨테이너가 주입되지 않으므로 파드 리소스·생명주기가 애플리케이션 자체와 분리된다.

## 핵심 개념 3: 도입 단위와 트레이드오프

앰비언트 메시가 주는 가장 실질적인 이득은 **점진적 도입**이 가능해졌다는 것이다. 사이드카 모델에서는 네임스페이스 단위로 "메시에 넣을지 말지"만 선택할 수 있었지만, 앰비언트에서는 L4 보안(ztunnel)까지만 켤지, L7 정책(waypoint)까지 필요한지를 서비스별로 다르게 가져갈 수 있다. 트래픽이 많고 리소스에 민감한 백엔드 서비스는 ztunnel만으로 mTLS를 확보하고, 카나리 배포나 세밀한 라우팅이 필요한 프론트 API 게이트웨이 앞단만 waypoint를 붙이는 식의 혼합 운영이 표준적인 패턴이 됐다.

다만 트레이드오프도 있다. 아키텍처가 레이어로 나뉘면서 트래픽 경로를 추적할 때 확인해야 할 컴포넌트가 하나(사이드카)에서 둘(ztunnel + waypoint)로 늘어나 장애 지점 분석이 더 복잡해질 수 있다. 또한 앰비언트는 비교적 최근 아키텍처라 사이드카 모델만큼 오랜 기간 검증된 엣지 케이스 대응 사례가 아직 상대적으로 적고, 조직 내 관측성·디버깅 도구도 새 구조에 맞게 다시 손봐야 하는 경우가 많다.

| 구분 | 사이드카 모델 | 앰비언트 메시 |
|---|---|---|
| 프록시 배치 단위 | 파드마다 1개 | 노드당 ztunnel + 선택적 waypoint |
| 리소스 오버헤드 | 파드 수에 비례 | 노드 수 + 실제 필요 서비스 수 |
| 파드 생명주기 결합 | 강함(초기화 순서 이슈) | 없음(애플리케이션과 분리) |
| L7 기능 적용 단위 | 메시 전체 일괄 | 서비스별 선택적(waypoint) |
| 장애 추적 경로 | 단일 컴포넌트 | ztunnel + waypoint 이원화 |

## 예제: 네임스페이스별 앰비언트 모드 활성화

```yaml
# 네임스페이스를 앰비언트 메시(L4)에 편입 — 사이드카 주입 없이 ztunnel만 적용
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    istio.io/dataplane-mode: ambient   # 사이드카 대신 ztunnel 경유

---
# L7 기능이 필요한 서비스에만 waypoint 프록시를 별도로 배치
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway
metadata:
  name: waypoint
  namespace: payments
  labels:
    istio.io/waypoint-for: service
spec:
  gatewayClassName: istio-waypoint
  listeners:
    - name: mesh
      port: 15008
      protocol: HBONE
```

`payments` 네임스페이스 전체는 사이드카 없이 ztunnel의 mTLS·L4 라우팅만 적용받고, 세밀한 HTTP 라우팅 정책이 필요한 서비스에만 waypoint 게이트웨이를 별도로 붙이는 구성이다.

## 실무 포인트

- **전면 전환보다 병행 운영으로 시작한다**: 기존 사이드카 메시가 이미 안정 운영 중이라면 신규 네임스페이스나 리소스 민감 서비스부터 앰비언트로 옮기고, 검증된 워크로드는 급하게 전환하지 않는 것이 안전하다.
- **관측성 스택 재점검이 필수다**: 사이드카 기반 지표·트레이싱 대시보드는 프록시가 파드 안에 있다는 전제로 만들어진 경우가 많다. ztunnel·waypoint 각각의 지표를 새로 수집·시각화하도록 손봐야 한다.
- **L7 기능이 필요한 서비스 목록을 먼저 정리한다**: waypoint를 무분별하게 모든 서비스에 붙이면 앰비언트 도입의 이점(대부분 서비스는 경량 ztunnel만)이 사라진다. 실제로 세밀한 트래픽 정책이 필요한 서비스만 골라내는 작업이 선행돼야 한다.

## 3줄 요약

- 사이드카 모델은 파드마다 프록시를 붙여 통신 관심사를 인프라로 옮겼지만, 서비스 수가 늘수록 리소스 오버헤드와 파드 생명주기 결합이 운영 부담이 됐다.
- 앰비언트 메시는 기능을 노드 공유 ztunnel(L4 보안)과 선택적 waypoint(L7 정책)로 분리해, 대부분 서비스는 경량 레이어만으로 메시에 참여하게 한다.
- 레이어 분리는 점진적·서비스별 도입을 가능하게 하지만, 장애 추적 경로가 늘고 관측성 도구도 새 구조에 맞게 다시 구축해야 하는 트레이드오프가 따른다.
