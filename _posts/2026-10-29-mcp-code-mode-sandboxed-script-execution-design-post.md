## 왜 지금 이 문제가 불거지는가

"이 스프레드시트 500행을 하나씩 검토해서 CRM에 반영해주세요"라는 요구를 에이전트에게 맡기면, 보통 모델은 행 하나마다 도구 호출 턴을 하나씩 만든다. 도구를 부르고, 결과를 컨텍스트에 받고, 다음 행으로 넘어가는 과정을 500번 반복한다. 턴마다 전체 도구 스키마가 컨텍스트에 다시 얹히고, 중간 결과도 전부 모델이 들고 있어야 하니 토큰 비용과 지연이 행 수에 비례해서 불어난다. MCP 서버를 여러 개 붙인 팀이라면 이 문제를 먼저 "도구가 너무 많아서 느리다"는 증상으로 겪지만, 사실은 도구 개수가 아니라 **도구를 호출하는 방식 자체**가 원인인 경우가 많다.

Cloudflare의 Kenton Varda와 Sunil Pai가 2025년 9월 26일 공개한 "Code Mode: the better way to use MCP"는 이 문제를 다른 축에서 풀었다. 모델이 매 단계 JSON 도구 호출 턴을 주고받는 대신, 모델에게 도구를 TypeScript 함수처럼 보여주고 전체 로직을 담은 스크립트 하나를 작성하게 한 뒤, 그 스크립트를 샌드박스에서 실행해 최종 결과만 모델 컨텍스트로 돌려주는 방식이다. 이 접근은 더 이상 실험이 아니다. Cloudflare는 2026년 3월 26일 MCP Portal에 Code Mode를 정식 기능으로 올렸고, Anthropic도 비슷한 시기에 자체 엔지니어링 블로그에서 "code execution with MCP" 패턴을 공개했다. 도구를 10개 넘게 묶어 쓰는 팀이라면 이제 직접 호출과 코드 모드 중 어느 쪽으로 설계할지 판단해야 하는 시점이 됐다.

## 두 실행 모델의 구조 차이

직접 도구 호출 모델에서는 모델이 추론 → 도구 호출(JSON) → 결과 수신 → 다음 추론이라는 루프를 작업이 끝날 때까지 반복한다. 모든 중간 결과가 모델의 컨텍스트 윈도우를 통과하고, 모든 도구 스키마가 시스템 프롬프트에 상주한다. Code Mode에서는 이 루프가 모델 바깥으로 옮겨간다. 모델은 도구 스키마를 타입 선언 파일(.d.ts)로 받아 필요할 때만 읽고, 반복·조건·중간 가공 로직을 담은 스크립트 하나를 작성한다. 이 스크립트가 샌드박스 안에서 실행되면서 도구 함수들을 프로그램처럼 호출하고, 모델에게는 스크립트 실행이 끝난 뒤의 최종 결과만 전달된다.

이 구조에서 가장 중요한 변화는 **중간 결과가 모델 컨텍스트를 거치지 않는다**는 점이다. 500행을 순회하며 CRM에 쓰는 작업이라면, 직접 호출 모델은 500번의 왕복과 500번의 컨텍스트 적재를 만들지만, Code Mode는 for 루프 하나와 최종 요약 한 번으로 끝난다. Cloudflare의 후속 글 "give agents an entire API in 1,000 tokens"가 강조하는 것도 이 지점이다 — 도구 스키마 전체를 프롬프트에 올리는 대신, 필요한 함수 시그니처만 온디맨드로 파일에서 읽게 하면 초기 컨텍스트 비용 자체가 크게 줄어든다.

## 아키텍처 비교: 직접 호출 vs Code Mode

<img src="/assets/images/posts/2026-10-29-mcp-code-mode-sandboxed-script-execution-design-1.svg" alt="MCP 직접 도구 호출과 Code Mode 아키텍처 비교" style="width:100%;">

| 기준 | 직접 도구 호출 | Code Mode |
|---|---|---|
| 반복 작업 비용 | 호출 횟수만큼 왕복·컨텍스트 적재 | 샌드박스 내부 루프, 왕복 1회 |
| 도구 스키마 노출 | 전체를 시스템 프롬프트에 상주 | 필요 시 타입 파일로 온디맨드 로드 |
| 실행 신뢰 경계 | MCP 서버가 각 호출을 개별 검증 | 모델이 작성한 코드를 실행 — 진짜 샌드박스 필수 |
| 자격증명 위치 | 서버가 보유, 호출 단위로 사용 | 샌드박스 밖 HTTP 브릿지로 분리 이동 |
| 디버깅 단위 | 호출 1건 단위로 원인 추적 쉬움 | 스크립트 전체 실행 실패 시 원인 추적 비용 증가 |
| 적합한 경우 | 단발성 호출(티켓 1건 생성 등) | 대량 루프·조건 분기·중간 가공이 필요한 작업 |

주의할 점은 Code Mode가 "항상 더 싸다"는 주장이 아직 확정된 사실이 아니라는 것이다. 여러 벤치마크가 65~98%의 토큰 절감을 보고했지만, 2026년 6월 한 내부 스파이크 테스트에서는 토큰 사용량은 뒤섞인 결과를, 턴 수는 오히려 순증가하는 결과를 보였다. 작업의 성격(반복이 많은가, 아니면 애매한 판단이 많은가)에 따라 결과가 갈린다는 뜻이다.

## 실행 신뢰 경계를 다시 그려야 하는 이유

직접 호출 모델에서는 모델이 "무엇을 호출할지"만 결정하고, 실제 실행은 MCP 서버가 검증된 함수 안에서 수행한다. Code Mode에서는 모델이 작성한 임의의 코드가 그대로 실행되므로, 이 코드를 신뢰할 수 없는 입력으로 다뤄야 한다. 인프로세스 실행은 위험하다 — 파일시스템이나 네트워크에 직접 접근 가능한 런타임에서 모델이 생성한 코드를 그대로 돌리면 프롬프트 인젝션이 곧바로 임의 코드 실행으로 이어진다. 그래서 Firecracker나 gVisor 같은 microVM, Cloudflare Workers의 isolate, Deno의 권한 격리 같은 실제 샌드박스가 전제 조건이다.

자격증명 처리도 함께 바뀐다. 직접 호출 모델에서는 MCP 서버가 다운스트림 API의 자격증명을 갖고 있다가 호출마다 사용하면 됐다. Code Mode에서는 샌드박스 내부에 자격증명을 넣을 수 없다 — 모델이 생성한 코드가 그 값을 읽어낼 수 있기 때문이다. 그래서 자격증명은 샌드박스 바깥의 별도 HTTP 브릿지로 옮기고, 스크립트는 "이 작업을 해달라"는 요청만 브릿지에 보내며, 다운스트림 인증은 브릿지가 전담하는 구조로 재설계해야 한다.

## 도입 순서와 막히는 지점

```typescript
// 샌드박스 안에서 모델이 작성·실행하는 스크립트 예시
import { crm, sheet } from "./tools"; // 온디맨드로 읽은 도구 타입

const rows = await sheet.read("Q4-leads");
for (const row of rows) {
  if (row.status === "미검토") {
    await crm.upsertContact({ email: row.email, stage: "검토중" });
  }
}
// 중간 500번의 호출 결과는 샌드박스 안에만 머물고,
// 모델 컨텍스트에는 이 스크립트의 최종 요약만 돌아온다.
```

기존 MCP 서버를 통째로 버릴 필요는 없다. 먼저 도구 스키마를 TypeScript 타입 선언으로 변환하는 레이어를 추가하는 것으로 시작한다. 그다음 샌드박스 런타임을 고른다 — 자체 Firecracker microVM을 운영할지, Cloudflare Workers/Durable Objects 같은 관리형 격리를 쓸지는 콜드스타트 지연과 운영 부담 사이의 트레이드오프다. 세 번째로 자격증명을 샌드박스 밖 브릿지로 분리한다. 마지막으로, 전체 작업을 한 번에 전환하지 말고 반복·루프가 많은 배치 작업부터 먼저 옮겨 토큰과 턴 수를 실측해야 한다. 가장 자주 막히는 지점은 두 가지다. 모델이 생성한 코드에 버그가 있을 때 "코드를 고쳐서 재실행"하는 디버깅 루프가 새로 생긴다는 점, 그리고 스크립트 안에서 브릿지를 거치는 외부 호출마다 레이턴시가 쌓여 "루프가 적은 작업"에서는 오히려 손해를 본다는 점이다.

## 정리

- Code Mode는 도구 개수 문제가 아니라 **도구 호출 모델 자체**를 직접 호출에서 코드 생성·샌드박스 실행으로 바꾸는 설계다.
- 토큰 절감 효과는 작업 성격에 따라 갈리므로, 전체 전환 전에 반복이 많은 워크로드부터 실측해야 한다.
- 모델이 작성한 코드를 실행하는 순간 진짜 샌드박스와 자격증명 분리가 전제 조건이 된다 — 단발성 호출에는 여전히 직접 호출이 더 단순하고 저렴하다.
