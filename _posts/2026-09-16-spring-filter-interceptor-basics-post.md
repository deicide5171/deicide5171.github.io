## 요청 처리 전후에 공통 작업을 넣고 싶다

인증 확인, 로깅, 요청 검증처럼 모든(또는 여러) 요청에 공통으로 적용할 작업이 있다. 이런 걸 컨트롤러마다 넣지 않고 **요청 흐름의 한 지점에서 가로채** 처리한다. 스프링에는 이런 지점이 둘 있다: **필터(Filter)**와 **인터셉터(Interceptor)**.

## 필터 vs 인터셉터

| 구분 | 필터 | 인터셉터 |
|---|---|---|
| 소속 | 서블릿(스프링 밖) | 스프링 MVC |
| 실행 시점 | 스프링 진입 전/후 | 컨트롤러 전/후 |
| 접근 정보 | 요청·응답(낮은 수준) | 핸들러 정보 등 |
| 예 | 인코딩·CORS·보안 | 인증·로깅·권한 |

## 요청 흐름

```text
요청 -> [필터] -> 스프링 DispatcherServlet -> [인터셉터]
     -> 컨트롤러 -> [인터셉터] -> [필터] -> 응답

필터가 더 바깥, 인터셉터가 더 안쪽(컨트롤러에 가까움)
```

## 실무 포인트

- **스프링 정보가 필요하면 인터셉터.** 어떤 컨트롤러/핸들러가 실행될지 같은 스프링 MVC 정보에 접근하려면 인터셉터를 쓴다. 로그인 여부 확인, 특정 컨트롤러에만 권한 체크 등이 여기에 맞다.
- **더 넓은 범위엔 필터.** 문자 인코딩, CORS, 전체 요청 로깅처럼 스프링 이전 단계에서 모든 요청에 적용할 것은 필터가 적합하다. 보안 프레임워크(Spring Security)도 필터 기반이다.
- **하나만 골라 명확히.** 같은 작업을 필터·인터셉터 양쪽에 중복으로 넣지 말고, 성격에 맞는 한쪽에 둔다. 실행 순서와 책임이 헷갈리지 않게 한다.

## 마무리 요약

- 필터와 인터셉터는 요청을 컨트롤러 전후에 가로채 공통 작업을 처리하는 지점이다.
- 필터는 스프링 바깥(서블릿) 넓은 범위, 인터셉터는 스프링 MVC 안 컨트롤러 근처에서 동작한다.
- 스프링 정보가 필요하면 인터셉터, 인코딩·CORS·보안 등 넓은 범위엔 필터를 쓴다.
