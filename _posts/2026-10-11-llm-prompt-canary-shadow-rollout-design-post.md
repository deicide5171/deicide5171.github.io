## 왜 지금 이 판단이 불거지는가

"시스템 프롬프트에 지시사항 한 줄 추가했을 뿐인데, 배포하고 나니 특정 카테고리 질문에서 답변 품질이 눈에 띄게 떨어졌어요. 그런데 에러 로그에는 아무것도 안 잡혀요." LLM 기반 기능을 운영하는 팀이 흔히 겪는 상황이다. 일반 코드 배포라면 예외가 터지거나 HTTP 상태 코드가 바뀌어 모니터링에 바로 잡히지만, 프롬프트나 모델을 바꾼 뒤 품질이 떨어지는 건 "틀린 응답"이 아니라 "그럴듯하지만 미묘하게 나빠진 응답"이라 기존 배포 모니터링으로는 잡히지 않는다. 변경 자체는 한 줄이라도, 그 한 줄이 실제 사용자 트래픽 전체에 어떤 영향을 주는지는 내보내 보기 전까지 알 수 없다는 점에서, LLM 변경은 코드 배포보다 오히려 더 신중한 점진적 노출 설계가 필요하다.

## 요구사항을 기술 문제로 번역하기

"점진적으로 내보내고 이상하면 되돌리게 해주세요"는 일반 소프트웨어 배포에서는 피처 플래그와 카나리 배포로 이미 해결된 문제처럼 보인다. 하지만 LLM 변경에 그대로 적용하면 두 가지가 어긋난다. 첫째, 일반 카나리는 "에러율이 올라갔는가"처럼 이진적이고 즉시 계측 가능한 신호로 판정하지만, LLM 응답은 틀렸다는 게 명확하지 않고 품질 저하가 서서히 드러난다. 둘째, 같은 입력이라도 모델이 비결정적으로 다른 출력을 낼 수 있어, "버전 A와 B의 출력이 다르다"는 사실만으로는 어느 쪽이 더 나쁜지 판단할 수 없다. 그래서 실제 작업은 "트래픽을 나눠서 내보내 주세요"가 아니라, **사용자에게 노출하기 전에 출력 차이를 안전하게 관찰하는 단계(섀도우)와, 노출하되 피해 범위를 제한하는 단계(카나리)를 분리하고, 각 단계에서 무엇을 "이상함"으로 정의할지 미리 합의하는 문제**로 번역된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-11-llm-prompt-canary-shadow-rollout-design-1.svg" alt="요청 라우터가 실제 사용자에게는 기존 버전만 응답하고 후보 버전은 섀도우로 동일 입력을 미러링해 오프라인 비교하다가, 검증을 통과하면 소규모 카나리 트래픽부터 단계적으로 후보 버전 비중을 늘리고 자동 롤백 트리거가 상시 감시하는 구조도" style="width:100%;">

이 구조에서 라우팅 계층은 **기존에 운영 중인 LLM 게이트웨이(모델 호출을 중개하는 레이어)의 한 단계 더 앞**에 위치한다. 앞단에는 사용자 요청을 받는 애플리케이션이 있고, 뒷단에는 실제 모델·프롬프트 조합을 호출하는 추론 레이어가 있다. 이 사이에 "지금 이 요청을 어느 버전으로 보낼지" 결정하는 라우팅 로직과, 버전별 출력을 비교·채점하는 평가 레이어가 끼어든다. 섀도우 단계에서는 후보 버전의 응답이 실제 사용자에게 전달되지 않고 로그로만 쌓이며, 카나리 단계부터 비로소 일부 트래픽이 실제로 후보 버전의 응답을 받는다. 이 레이어가 없으면 모든 프롬프트·모델 변경은 "전체 트래픽에 한 번에 내보내고 반응을 지켜본다"는, 되돌리기 어려운 전부-아니면-전무 방식으로 흐른다.

## 선택의 트레이드오프

| 방식 | 사용자 노출 위험 | 신호의 현실성 | 적합한 변경 범위 |
|---|---|---|---|
| 섀도우(미러링, 로그만) | 없음 | 낮음(실제 사용자 반응 없음) | 모델 업그레이드, 대규모 프롬프트 재구성 |
| 소규모 카나리(0.1~1%) | 낮음(제한된 사용자) | 중간(실제 반응 일부 포착) | 중간 규모 프롬프트 수정 |
| 단계적 확대(5→20→50→100%) | 단계별로 통제됨 | 높음(트래픽 늘수록 신뢰도 상승) | 섀도우·카나리를 통과한 모든 변경 |
| 즉시 전체 배포 | 가장 높음 | 즉시 전체 신호 확보 | 긴급 수정이나 명백히 작은 오타 수정 정도 |

섀도우는 사용자에게 전혀 노출되지 않아 가장 안전하지만, 벤치마크로는 못 보는 문제를 실제 반응으로 확인하지는 못한다. 소규모 카나리는 실제 신호를 얻되 피해 범위를 좁히는 절충안이지만, 같은 세션 안에서 버전이 바뀌면 사용자가 일관성 없는 경험을 겪으므로 세션 단위로 버전을 고정하는 장치가 필요하다. 대부분의 프로덕션 LLM 시스템은 이 넷을 조합한다. 모델 업그레이드나 시스템 프롬프트 전면 재작성처럼 변경 폭이 큰 경우는 섀도우부터 시작하고, 지시문 한두 줄 추가 같은 작은 변경은 바로 소규모 카나리로 들어가는 식으로 변경 규모에 따라 시작 단계를 다르게 잡는 것이 실무적이다.

## 실제 프로젝트 진행 순서

1. **롤백 트리거를 카나리 시작 전에 미리 정의한다.** "작업 완료율이 몇 퍼센트 이상 떨어지면 자동 롤백"처럼, 카나리가 진행 중일 때 판단을 내리는 것이 아니라 시작 전에 숫자로 합의해둔다.
2. **변경 규모가 크면 섀도우부터, 작으면 소규모 카나리부터 시작한다.** 모델 교체나 프롬프트 전면 개편은 24~72시간 섀도우로 실제 트래픽 분포에서의 출력 차이를 먼저 관찰한다.
3. **세션 단위로 버전을 고정하는 장치를 넣는다.** 같은 사용자가 요청마다 다른 버전에 걸리면 일관성 문제가 생기고, 원인 추적도 어려워진다.
4. **카나리 비중을 단계적으로 늘리되 각 단계마다 관찰 기간을 둔다.** 1% → 5% → 20% → 50% → 100%처럼 단계를 밟고, 각 단계 사이에 충분한 관찰 시간(예: 24시간)을 확보한다.
5. **롤백은 피처 플래그로 즉시 되돌릴 수 있게 설계한다.** 재배포 없이 플래그 하나로 이전 버전으로 돌아갈 수 있어야 사고 대응 시간이 짧아진다.

## 코드 예시 — 세션 고정 라우팅과 롤백 트리거

```python
def route_version(session_id: str, canary_percent: int) -> str:
    bucket = hash(session_id) % 100
    return "candidate" if bucket < canary_percent else "control"

def should_rollback(metrics: dict, baseline: dict) -> bool:
    task_success_drop = baseline["success_rate"] - metrics["success_rate"]
    return task_success_drop > 0.03  # 3%p 이상 하락 시 자동 롤백
```

## 실무 포인트

**에러율만으로 판단하지 않는다.** LLM 변경의 실패는 예외가 아니라 품질 저하로 나타나므로, 작업 완료율이나 사용자 재질문율 같은 과업 중심 지표를 별도로 정의해야 한다.

**섀도우 결과를 100% 신뢰하지 않는다.** 실제 사용자에게 노출되지 않은 섀도우 트래픽에는 실사용자의 피드백 루프(재질문, 중단)가 빠져 있어, 작은 카나리로 한 번 더 검증하는 단계를 생략하면 안 된다.

**단계마다 관찰 기간을 압축하고 싶은 유혹을 경계한다.** 트래픽이 적은 시간대에 급하게 단계를 올리면 실제 피크 시간대 사용 패턴에서 발생하는 문제를 놓칠 수 있다.

## 마무리

- "점진적으로 내보내고 이상하면 되돌려 주세요"는 사용자 노출 전 관찰(섀도우)과 노출 후 피해 제한(카나리)을 분리하고, 각 단계의 "이상함"을 과업 중심 지표로 미리 정의하는 문제로 번역된다.
- 일반 코드 카나리와 달리 LLM 변경은 에러가 아니라 품질 저하로 실패하므로, 작업 완료율 같은 별도 신호가 필요하다.
- 변경 규모가 크면 섀도우부터, 작으면 소규모 카나리부터 시작해 단계별 관찰 기간을 두고 확대하는 순서가 안전하다.
