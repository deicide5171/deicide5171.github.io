## 왜 지금 이 판단이 불거지는가

"우리 지도 앱에 OSM 데이터랑 파트너사가 준 매장 리스트, 우리가 직접 수집한 POI를 다 합쳐서 중복 없이 보여주세요." 이 요구를 받으면 바로 떠오르는 방법은 좌표 거리와 이름 유사도로 매칭하는 것이다. 하지만 실제로 해보면 금방 막힌다. 같은 스타벅스 매장이 OSM에는 건물 중심점으로, 파트너 피드에는 출입구 좌표로, 우리 수집 데이터에는 GPS 오차가 낀 지점으로 찍혀 있어 수십 미터씩 어긋난다. 이름 표기도 "스타벅스 강남점", "Starbucks Gangnam", "스타벅스(강남역점)"처럼 제각각이다. 매칭 규칙을 아무리 정교하게 짜도 릴리스마다(건물이 리모델링되거나 매장이 이전하면) 다시 깨지고, 그때마다 매칭 로직을 재검증해야 한다.

Overture Maps Foundation(리눅스 재단 산하)은 이 문제를 각 데이터 사용자가 매번 풀지 않도록, 전 세계 건물·장소·도로·행정구역에 릴리스 간 안정적으로 유지되는 전역 ID를 붙이는 GERS(Global Entity Reference System)를 공식 데이터 모델의 일부로 운영한다. 2026년 들어 Overture Maps Foundation은 회원사 50곳을 넘겼고, OGC(Open Geospatial Consortium)가 올해 초부터 GERS를 국제 표준으로 검토하기 시작했다는 보도도 나왔다. 공간 데이터를 하나의 신뢰할 수 있는 키로 묶는 문제가 개별 회사의 매칭 경쟁에서 공유 인프라 표준 경쟁으로 넘어가는 중이라는 뜻이다. 자체 매칭 로직에 계속 투자할지, 이 공유 ID 체계에 올라탈지를 판단해야 하는 시점이 됐다.

## 요구사항을 기술 문제로 번역하기

"데이터를 합쳐주세요"는 실제로는 **엔티티 해상도(entity resolution)** 문제, 더 정확히는 **컨플레이션(conflation)** 문제로 번역된다. 서로 다른 소스에서 온 두 레코드가 "같은 실세계 객체를 가리키는가"를 판정하고, 그렇다면 하나의 식별자로 묶어야 한다. GERS는 이 판정을 Overture가 릴리스마다 직접 수행해 결과를 ID 형태로 미리 제공한다. 건물·장소·행정구역처럼 여러 입력 소스를 병합하는 테마는 피처 단위 컨플레이션으로 ID 안정성을 유지하고, 그렇지 않은 테마는 결정적 해시로 입력 데이터셋(OSM 등)과의 일관된 매칭을 보장한다. 결국 "매칭해주세요"라는 요구가 "우리 데이터의 조인 키를 자체 PK 대신 GERS ID로 바꾸고, 릴리스마다 바뀌는 변경 내역(changelog)을 소비하는 파이프라인을 짜주세요"라는 구체적인 엔지니어링 작업으로 바뀐다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-08-overture-maps-gers-entity-reference-id-1.svg" alt="OSM, 파트너 피드, 자체 수집 데이터가 Overture의 GERS 컨플레이션 레이어를 거쳐 전역 레지스트리와 변경 내역을 생성하고, 이 GERS ID를 조인 키로 삼아 자체 공간 데이터베이스가 여러 소스를 중복 없이 통합한 뒤 검색·지도 렌더링·추천 시스템으로 이어지는 구조도" style="width:100%;">

GERS는 원시 다중 소스 데이터와 자체 공간 데이터베이스 사이의 데이터 정합 계층이다. 앞단에는 OpenStreetMap, 상업 파트너 피드, 자체 현장 수집 데이터처럼 서로 독립적으로 생성되는 공간 데이터 소스들이 있다. Overture는 이들을 릴리스마다(약 월 단위) 받아 피처 단위 컨플레이션 또는 결정적 해시로 매칭하고, 그 결과를 GERS 레지스트리(전체 엔티티의 ID·버전·최초 등장 릴리스를 담은 단일 소스)와 변경 내역(changelog)으로 공개한다. 뒷단에서는 이 GERS ID를 자체 데이터베이스의 조인 키로 채택해, 서로 다른 소스에서 온 레코드를 하나의 엔티티로 묶고 검색 랭킹·추천 시스템·지도 렌더링에서 중복 없는 통합 뷰를 제공한다. GERS를 빼면 이 통합은 각 팀이 자체적으로 매칭 로직을 짜고 유지보수해야 하는, 반복적이고 깨지기 쉬운 작업으로 남는다.

## 선택의 트레이드오프

| 접근 | 초기 구축 비용 | 릴리스 간 안정성 | 커버리지 | 적합한 상황 |
|---|---|---|---|---|
| 자체 규칙 기반 매칭 (좌표+이름 유사도) | 낮음(빠르게 시작 가능) | 낮음(릴리스마다 재검증 필요) | 자체 데이터 범위로 한정 | 소규모, 지역 한정 서비스 |
| 자체 ML 기반 엔티티 해상도 | 높음(학습 데이터·모델 운영 필요) | 중간(재학습 비용 발생) | 학습 데이터 범위 내 | 도메인 특화 매칭 규칙이 중요한 경우 |
| Overture GERS ID 채택 | 중간(파이프라인 전환 비용) | 높음(Overture가 유지보수) | 전 세계, Overture 테마 범위 | 글로벌 서비스, 다중 소스 통합이 핵심인 경우 |
| 상용 MDM/컨플레이션 서비스 | 높음(라이선스 비용) | 높음(벤더 SLA) | 벤더 커버리지에 의존 | 예산이 충분하고 벤더 종속을 감수할 수 있는 경우 |

GERS를 채택한다고 매칭 문제가 완전히 사라지는 건 아니다. Overture의 커버리지 밖에 있는 소규모·지역 특화 엔티티(예: 아직 지도화되지 않은 골목 상권)는 여전히 자체 매칭이 필요하고, GERS ID 자체도 "안정적이도록 설계됐다"는 것이지 절대적으로 불변하지는 않는다 — 건물이 실제로 분할·합병되면 ID도 함께 바뀐다. 따라서 GERS는 매칭 로직을 완전히 대체한다기보다, 전 세계 커버리지가 필요한 핵심 엔티티(건물, 대형 장소, 행정구역)에 대해 매칭 비용을 외부화하고, 자체 로직은 GERS가 못 덮는 롱테일에 집중하는 분업 구조로 가져가는 게 현실적이다.

## 실제 프로젝트 진행 순서

1. **어떤 Overture 테마가 필요한지부터 좁힌다.** Buildings, Places, Transportation, Divisions 중 실제로 다중 소스 통합이 필요한 테마만 고른다. 전부 도입하면 파이프라인이 불필요하게 무거워진다.
2. **GERS 레지스트리와 변경 내역을 먼저 받아 구조를 파악한다.** 레지스트리의 스키마(ID, 버전, 최초 등장 릴리스)와 changelog의 이벤트 타입(생성·병합·분할·소멸)을 읽고, 자체 스키마에 `gers_id` 컬럼을 추가할지 결정한다.
3. **자체 데이터와 GERS 엔티티를 1회성으로 매칭(온보딩)한다.** 기존에 자체 PK로 관리하던 레코드들을 GERS ID와 연결하는 초기 매핑 테이블을 만든다. 이 단계에서 매칭률이 낮은 영역(롱테일)을 파악해 둔다.
4. **changelog 소비 파이프라인을 설계한다.** 릴리스마다 병합·분할된 엔티티를 자동으로 반영하지 않으면, 시간이 지날수록 자체 매핑 테이블이 실제 Overture 데이터와 어긋난다.
5. **GERS가 못 덮는 영역의 폴백 전략을 별도로 설계한다.** 커버리지 밖 엔티티는 기존의 자체 매칭 로직을 그대로 유지하거나, 신규 엔티티로 등록하고 다음 릴리스에 Overture 쪽에도 기여하는 경로를 검토한다.
6. **두 릴리스에 걸쳐 ID 안정성을 직접 검증한다.** 샘플 엔티티 집합을 두고 이전 릴리스와 다음 릴리스의 ID가 실제로 유지되는지 확인한 뒤에 프로덕션 조인 키로 전환한다.

## 코드 예시 — DuckDB로 자체 POI와 Overture Places를 GERS ID로 조인하기

```sql
INSTALL spatial; LOAD spatial;
INSTALL httpfs; LOAD httpfs;

CREATE TABLE overture_places AS
SELECT id AS gers_id, names.primary AS name, geometry
FROM read_parquet('s3://overturemaps-us-west-2/release/2026-07-22.0/theme=places/*/*.parquet');

-- 자체 POI 테이블에 매핑 단계에서 확보한 gers_id가 있다고 가정
SELECT
  my_poi.poi_id,
  my_poi.internal_name,
  overture_places.name AS gers_name,
  overture_places.gers_id
FROM my_poi
JOIN overture_places
  ON my_poi.gers_id = overture_places.gers_id;
```

## 실무 포인트

**GERS ID를 자체 PK 대신 쓰지 말고, 함께 보관한다.** 외부 표준에 전적으로 의존하면 Overture의 스키마 변경이나 커버리지 축소에 자체 시스템이 그대로 노출된다. `gers_id`는 조인·중복 제거용 보조 키로 두고, 자체 PK는 그대로 유지하는 편이 안전하다.

**changelog를 소비하지 않으면 매핑이 서서히 썩는다.** 초기 온보딩 때 매칭해 둔 ID가 영원히 유효하다고 가정하면 안 된다. 병합·분할 이벤트를 주기적으로 반영하는 배치 잡을 반드시 운영 파이프라인에 포함해야 한다.

**커버리지 격차를 사전에 측정해 기대치를 관리한다.** 글로벌 대도시 중심 데이터는 Overture 커버리지가 좋지만, 특정 국가·지역의 세부 상권은 비어 있을 수 있다. 도입 전에 자체 서비스 지역의 매칭률을 샘플링해보고, 낮으면 GERS 도입의 우선순위를 재검토해야 한다.

## 마무리

- 여러 소스의 공간 데이터를 합치는 문제는 좌표 거리 비교가 아니라 엔티티 해상도(컨플레이션) 문제이며, Overture Maps의 GERS는 이 작업을 릴리스마다 전역 레지스트리와 변경 내역 형태로 외부화해 제공한다.
- GERS ID는 원시 다중 소스 데이터와 자체 공간 데이터베이스 사이의 데이터 정합 계층에 위치하며, 자체 매칭 로직을 완전히 대체하기보다 커버리지가 좋은 핵심 엔티티의 매칭 비용을 외부화하는 역할을 한다.
- 도입 시에는 필요한 테마만 좁혀서 시작하고, changelog 소비 파이프라인과 커버리지 밖 폴백 전략을 함께 설계해야 시간이 지나도 매핑이 깨지지 않는다.
