## 왜 도메인을 IP로 바꿔야 하나

컴퓨터는 서로를 IP 주소(예: `93.184.216.34`)로 찾는다. 하지만 사람이 숫자를 외우기는 어려우니 `example.com` 같은 도메인 이름을 쓴다. **DNS(Domain Name System)**는 이 도메인 이름을 실제 IP 주소로 변환해주는 "인터넷의 전화번호부"다.

## 도메인이 IP로 바뀌는 과정

```text
1. 브라우저 캐시 확인 (최근에 찾은 적 있나?)
2. OS·로컬 캐시 확인
3. 없으면 DNS 리졸버(보통 통신사·공용 DNS)에 질의
4. 리졸버가 루트 -> TLD(.com) -> 권한 서버 순으로 물어봄
5. 최종 IP 주소를 받아 브라우저에 전달
6. 브라우저가 그 IP로 실제 연결

이 모든 과정이 보통 수십 밀리초 안에 끝난다.
```

## 자주 나오는 DNS 레코드 종류

| 레코드 | 의미 |
|---|---|
| A | 도메인 → IPv4 주소 |
| AAAA | 도메인 → IPv6 주소 |
| CNAME | 도메인 → 다른 도메인(별칭) |
| MX | 메일 서버 지정 |
| TXT | 텍스트 정보(도메인 소유 확인, SPF 등) |

## TTL과 캐싱

DNS 응답에는 **TTL(Time To Live)**이 붙어, 그 시간 동안 결과를 캐시한다. 매번 전체 과정을 거치면 느리기 때문에, 한 번 조회한 결과를 여기저기 캐시해 재사용한다.

```text
TTL = 3600 (1시간) -> 1시간 동안은 캐시된 IP를 그대로 씀

이래서 도메인의 IP를 바꿔도 즉시 반영되지 않는다.
전 세계 캐시가 TTL만큼 지나 갱신될 때까지 옛 IP로 접속하는 사용자가 있다.
```

## 실무 포인트

- **서버 IP를 바꾸기 전에 TTL을 미리 낮춰라.** IP 변경(서버 이전 등)을 계획한다면, 며칠 전에 TTL을 짧게(예: 300초) 줄여두면 변경 시 캐시가 빨리 갱신되어 전파 지연을 줄일 수 있다.
- **"DNS 전파(propagation)"는 즉시 되지 않는다.** 도메인 설정을 바꿔도 전 세계 캐시가 갱신되기까지 TTL만큼 시간이 걸린다. "왜 아직 옛 사이트가 보이지"는 대부분 캐시가 아직 안 지난 것이다.
- **CNAME은 다른 도메인을 가리키므로 최상위(루트) 도메인에는 제약이 있다.** `example.com` 자체에는 보통 CNAME을 못 붙이고 A 레코드를 써야 하는데, 이 제약 때문에 클라우드 서비스들은 별칭(ALIAS/ANAME) 같은 대안 레코드를 제공하기도 한다.

## 마무리 요약

- DNS는 사람이 쓰는 도메인 이름을 컴퓨터가 쓰는 IP 주소로 바꿔주는 인터넷의 전화번호부다.
- 캐시 → 리졸버 → 루트/TLD/권한 서버를 거쳐 IP를 찾으며, 대부분 수십 밀리초 안에 끝난다.
- TTL 때문에 DNS 변경은 즉시 반영되지 않으므로, IP 변경 전 TTL을 미리 낮춰두는 것이 좋다.
