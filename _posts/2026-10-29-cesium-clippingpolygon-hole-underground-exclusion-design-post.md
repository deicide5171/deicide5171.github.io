## 왜 지금 이 설계가 필요한가

"지하 주차장이랑 배관 라인은 지도에서 안 보이게 하고, 이 구역은 사유지라서 3D 모델 자체를 통째로 가려주세요." 3D 도시 모델을 서비스하는 팀이라면 한 번쯤 받는 요구다. 얼핏 보면 레이어를 하나 꺼두면 될 것 같지만, 실제로는 하나의 3D Tiles 타일셋 안에 섞여 있는 건물·지하 구조물·제외 구역을 선택적으로 숨겨야 하는 문제다. 더 까다로운 건 "이 구역은 가리되, 그 안의 한 블록은 다시 보여주세요" 같은 요구다 — 제외 구역 안에 다시 예외 구역이 뚫리는 구조다.

CesiumJS는 2024년 5월(1.117)부터 `ClippingPolygon`과 `ClippingPolygonCollection`으로 3D Tiles·지형의 특정 영역을 가리는 기능을 제공해왔다. 오목한 다각형과 역전(inverse) 영역까지 지원했지만, 한 폴리곤 "안에 구멍을 뚫어 그 부분만 다시 보이게" 하는 것은 할 수 없었다. 2026년 9월 2일 공개된 Cesium 1.145는 이 지점을 두 가지로 보완했다. 벡터 타일 렌더링 기법을 가져온 품질 알고리즘 개선으로 줌 거리에 따른 클리핑 경계 품질을 높였고, `ClippingPolygon`에 **구멍(hole) 지원**을 추가했다 — 공식 데모는 스웨덴 국경 GeoJSON에 구멍을 뚫어 그 안쪽만 다시 보이게 하는 예시로 이 기능을 소개했다. 지하·제외 구역을 다루는 팀에게는 "클라이언트에서 즉시 반영할지, 타일 생성 단계에서 막을지"를 다시 판단해야 하는 계기다.

## 세 가지 제외 구역 구현 방식

<img src="/assets/images/posts/2026-10-29-cesium-clippingpolygon-hole-underground-exclusion-design-1.svg" alt="클라이언트 클리핑, 타일셋 베이크, 서버 필터링 세 경로 비교" style="width:100%;">

제외 구역을 만드는 방법은 데이터가 흐르는 파이프라인의 어느 지점에서 끊느냐에 따라 세 갈래로 나뉜다. 첫째는 **클라이언트 런타임 클리핑**이다. 3D Tiles 전체를 그대로 브라우저까지 내려보내고, CesiumJS 뷰어가 `ClippingPolygonCollection`으로 특정 영역을 렌더링 단계에서 가린다. 둘째는 **타일셋 생성 시점 베이크**다. 3D Tiles를 만드는 전처리 파이프라인(예: cesium-native 기반 타일러)에서 애초에 제외 구역의 지오메트리를 타일에 포함시키지 않는다. 셋째는 **서버 단 타일 필터링**이다. 타일 서버가 요청을 받을 때마다 사용자 권한이나 요청 범위에 따라 내려줄 타일 자체를 거르는 방식이다.

| 기준 | 클라이언트 클리핑 | 타일셋 베이크 | 서버 필터링 |
|---|---|---|---|
| 정책 변경 반영 속도 | 즉시(코드만 수정) | 타일 재생성 필요 | 서버 설정만 변경 |
| 런타임 GPU 비용 | 클리핑 평면 연산 추가 | 없음(애초에 지오메트리 없음) | 없음 |
| 데이터 노출 | 전체 데이터가 이미 클라이언트에 도착 | 민감 지오메트리 자체가 전달 안 됨 | 민감 지오메트리 자체가 전달 안 됨 |
| 구멍(제외 안의 예외) | 1.145부터 지원 | 전처리 로직으로 직접 구현 | 요청 단위 로직으로 직접 구현 |
| 진짜 단면(solid 절단면) | 미지원 — 절단면이 비어 보임 | 모델링 단계에서 캡 메쉬 추가 필요 | 해당 없음 |
| 적합한 경우 | 정책이 자주 바뀌는 초기 단계 | 제외 구역이 안정화된 운영 단계 | 사용자별 접근 권한이 다른 경우 |

여기서 반드시 짚어야 할 것은 클라이언트 클리핑이 **데이터 노출 문제를 전혀 해결하지 못한다**는 점이다. 브라우저 네트워크 탭을 열어보면 가려진 지하 배관이나 사유지 모델의 지오메트리가 이미 다운로드돼 있다. 군사시설 좌표처럼 진짜 민감한 정보라면 클라이언트 클리핑만으로는 부족하고, 타일을 만들기 전에 서버·전처리 단계에서 애초에 제외해야 한다. 반대로 "보기 싫은 지하 배관을 안 보이게" 같은 UX 목적이라면 클라이언트 클리핑으로 충분하고, 정책이 자주 바뀌는 초기 단계에는 오히려 이쪽이 유리하다.

또 하나 짚을 한계는 Cesium 커뮤니티 포럼에 여전히 남아 있는 미해결 요청이다 — "건물을 수직으로 잘라서 단면도처럼 내부가 보이게 해달라"는 요청에 대해 `ClippingPolygon`은 절단면을 **비우기만** 할 뿐, 잘린 단면에 꽉 찬 캡(solid cap)을 채워주지 않는다. 진짜 건축 단면도 같은 표현이 필요하다면 클리핑이 아니라 모델링 단계에서 단면 메쉬를 따로 준비해야 한다.

## 적용 코드와 진행 순서

```javascript
// CesiumJS 1.145 — 구멍이 있는 ClippingPolygon
const outer = Cesium.Cartesian3.fromDegreesArray([
  127.10, 37.50, 127.12, 37.50, 127.12, 37.52, 127.10, 37.52,
]);
const hole = Cesium.Cartesian3.fromDegreesArray([
  127.108, 37.508, 127.112, 37.508, 127.112, 37.512, 127.108, 37.512,
]);

const clippingPolygon = new Cesium.ClippingPolygon({
  positions: outer,
  holes: [new Cesium.ClippingPolygon({ positions: hole })],
});

tileset.clippingPolygons = new Cesium.ClippingPolygonCollection({
  polygons: [clippingPolygon],
  unionClippingRegions: false, // 지정 영역 바깥을 가린다
});
```

도입 순서는 데이터 민감도에 따라 갈라야 한다. UX 목적의 제외 구역(지하 배관, 임시 공사 구간)은 먼저 클라이언트 `ClippingPolygon`으로 프로토타입을 만들어 기획팀과 범위를 빠르게 조율한다. 범위가 안정되면 그제서야 타일 생성 파이프라인에 베이크해 런타임 GPU 비용을 없앤다. 반면 접근 자체를 막아야 하는 사유지·보안 구역은 처음부터 서버단에서 타일 전달을 거르는 설계로 가야 한다 — 클라이언트 클리핑을 "임시 보안 조치"로 쓰면 안 된다. 가장 먼저 막히는 지점은 구멍이 여러 개 겹치는 복합 제외 구역에서 1.145의 새 품질 알고리즘이 줌 레벨별로 경계가 들쭉날쭉해지는 경우이므로, 실제 운영 전에 목표 줌 레벨 구간에서 반드시 육안 검증을 거쳐야 한다.

## 정리

- ClippingPolygon의 구멍 지원(1.145, 2026-09-02)은 "제외 구역 안의 예외 구역"을 코드만으로 표현할 수 있게 한 실질적 진전이다.
- 클라이언트 클리핑은 데이터를 숨기지 못한다 — 진짜 민감한 지오메트리는 타일 생성·서버 단계에서 애초에 제외해야 한다.
- 정책이 자주 바뀌는 초기에는 클라이언트 클리핑으로 빠르게 검증하고, 범위가 안정되면 타일셋 베이크로 옮겨 런타임 비용을 없애는 순서가 안전하다.
