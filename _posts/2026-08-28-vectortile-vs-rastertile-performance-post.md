웹 지도에서 "타일(tile)"이라는 단위는 같지만, 그 타일 안에 무엇이 들어있는지는 두 갈래로 갈린다. 하나는 서버가 미리 렌더링해둔 PNG/JPEG 이미지를 그대로 내려주는 **래스터 타일**이고, 다른 하나는 도로·건물·라벨의 실제 좌표와 속성을 담은 압축 바이너리(주로 MVT, Mapbox Vector Tile 포맷)를 내려줘 **클라이언트가 그 자리에서 그리는** **벡터 타일**이다. 둘 다 같은 줌 레벨/타일 좌표(z/x/y) 체계를 쓰지만, "그림을 받아서 붙이는가"와 "좌표를 받아서 그리는가"라는 근본적인 차이가 성능·용량·표현력 전반에 걸쳐 서로 다른 트레이드오프를 만든다.

이 글에서는 두 방식이 각각 어디서 강하고 어디서 약한지, 그리고 실무에서 어떤 상황에 어느 쪽을 고르는지를 정리한다.

## 핵심 개념 1: 무엇을 미리 계산하고, 무엇을 그 자리에서 계산하는가

래스터 타일은 서버(또는 빌드 파이프라인)가 스타일까지 반영해 완성된 이미지를 미리 만들어둔다. 클라이언트는 그 이미지를 다운로드해서 화면에 그대로 붙이기만 하면 되므로 클라이언트 쪽 렌더링 부담이 거의 없다. 대신 스타일(배경색, 라벨 언어, 도로 강조 색상 등)을 바꾸려면 타일 자체를 처음부터 다시 렌더링해서 재배포해야 한다.

벡터 타일은 반대로 "무엇이 어디 있는가"라는 원본 지리 데이터만 압축해서 내려주고, 실제 그리기(도로에 색 입히기, 라벨 배치하기, 건물 채우기)는 클라이언트의 스타일 명세(style spec)를 기준으로 브라우저의 WebGL이 그 자리에서 수행한다. 그 결과 같은 타일 데이터를 두고도 스타일 JSON 파일 하나만 바꾸면 다크모드, 다국어 라벨, 도로 강조 색상 전환을 서버 재배포 없이 즉시 적용할 수 있다.

## 핵심 개념 2: 네트워크 전송량과 확대·축소 시의 체감 성능

같은 지역을 나타내는 벡터 타일은 좌표와 속성만 담고 있어 대체로 같은 래스터 타일 이미지보다 파일 크기가 작다. 특히 저해상도 디스플레이와 고해상도(Retina) 디스플레이를 모두 지원하려면 래스터는 해상도별로 별도 타일 세트를 만들어야 하지만, 벡터 타일은 좌표 데이터이므로 화면 해상도와 무관하게 같은 타일을 다시 사용해 스케일만 다르게 그리면 된다.

확대·축소 시의 체감도 다르다. 래스터 타일은 줌 레벨이 바뀌면 그 레벨에 맞는 새 이미지를 다시 받아야 하고, 받기 전까지는 이전 레벨 이미지를 확대해 흐릿하게 보여주는 것이 일반적이다. 벡터 타일은 이미 받아둔 좌표 데이터를 GPU가 실시간으로 재투영해 그리므로, 확대·축소 애니메이션이 매끄럽게 이어지고 라벨이 겹치지 않도록 재배치하는 것도 클라이언트에서 즉시 처리된다.

| 기준 | 래스터 타일 | 벡터 타일 |
|---|---|---|
| 타일 내용물 | 완성된 이미지(PNG/JPEG) | 좌표+속성 데이터(MVT) |
| 스타일 변경 | 타일 재생성·재배포 필요 | 클라이언트 스타일 JSON만 교체 |
| 고해상도 대응 | 해상도별 별도 타일 필요 | 동일 데이터로 대응 가능 |
| 확대·축소 체감 | 새 이미지 로딩 전 흐릿함 | GPU 재투영으로 매끄러움 |
| 클라이언트 부담 | 낮음(단순 이미지 표시) | 높음(GPU 렌더링 필요) |
| 회전·3D 틸트 | 어려움(2D 이미지 한계) | 자연스러움(좌표 재계산) |

## 핵심 개념 3: 클라이언트 성능과 저사양 기기라는 반대급부

벡터 타일이 유연성과 회전·3D 표현력에서 앞서지만 공짜는 아니다. 클라이언트가 매 프레임 스타일 규칙을 적용해 도형을 그려야 하므로 CPU/GPU 부담이 래스터보다 크고, 복잡한 스타일(많은 레이어, 정교한 필터 조건)을 저사양 모바일 기기에서 돌리면 프레임 드랍이 생길 수 있다. 반대로 래스터 타일은 클라이언트가 그냥 이미지를 붙이기만 하면 되므로 아무리 오래된 기기에서도 렌더링 성능이 예측 가능하다. 위성영상처럼 애초에 좌표 기반 재구성이 의미 없는 연속 톤 이미지(항공사진, 위성 원본 영상)는 벡터화 자체가 불가능하므로 래스터가 유일한 선택지이기도 하다.

## 예제: MapLibre GL JS로 벡터 타일 스타일 전환

```javascript
import maplibregl from "maplibre-gl";

const map = new maplibregl.Map({
  container: "map",
  style: "/styles/light.json", // 벡터 타일 소스 + 스타일 규칙
  center: [127.0, 37.5],
  zoom: 11,
});

// 다크모드 전환: 같은 벡터 타일 데이터를 재요청하지 않고 스타일만 교체
function toggleDarkMode(isDark) {
  map.setStyle(isDark ? "/styles/dark.json" : "/styles/light.json");
}
```

```json
{
  "sources": {
    "base": { "type": "vector", "tiles": ["https://tiles.example.com/{z}/{x}/{y}.pbf"] }
  },
  "layers": [
    { "id": "roads", "type": "line", "source": "base", "source-layer": "road",
      "paint": { "line-color": "#666", "line-width": ["interpolate", ["linear"], ["zoom"], 10, 1, 16, 4] } }
  ]
}
```

같은 타일 소스(`base`)를 두고 `paint` 속성만 바꾼 스타일 JSON을 여러 개 준비해두면, 서버에 새 요청을 보내지 않고도 클라이언트에서 즉시 스타일을 전환할 수 있다. 래스터 타일이었다면 이 전환마다 완전히 다른 타일 세트 전체를 새로 받아야 했을 것이다.

## 실무 포인트

- **저사양 기기가 주요 타깃이면 벡터 타일의 레이어 수를 제한할 것**: 스타일에 레이어가 많고 조건부 필터가 복잡할수록 저사양 모바일에서 프레임 드랍이 발생하기 쉽다. 줌 레벨별로 표시하는 레이어를 줄이는 것이 일반적인 대응이다.
- **위성·항공 이미지는 벡터화 대상이 아니다**: 연속 톤 래스터 원본은 애초에 벡터로 표현할 개체가 없으므로, 이 경우는 래스터 타일(또는 COG)이 유일하게 맞는 선택이며 벡터타일 도입 논의 자체가 적용되지 않는다.
- **하이브리드 구성도 흔하다**: 배경 지도(도로, 건물)는 벡터 타일로 유연하게, 그 위에 얹는 위성영상이나 열지도 같은 래스터 레이어는 그대로 이미지 타일로 겹쳐 쓰는 구성이 실무에서 자주 쓰인다.

## 3줄 요약

- 래스터 타일은 완성된 이미지를 미리 만들어 전송해 클라이언트 부담이 낮지만 스타일 변경 시 재생성·재배포가 필요하다.
- 벡터 타일은 좌표 데이터만 전송해 클라이언트가 그 자리에서 그리므로 스타일 전환·다국어·고해상도 대응이 유연하지만 GPU 렌더링 부담이 크다.
- 위성·항공 원본처럼 벡터화가 불가능한 연속 톤 이미지는 래스터가 유일한 선택지이며, 배경은 벡터·오버레이는 래스터인 하이브리드 구성도 실무에서 흔하다.
