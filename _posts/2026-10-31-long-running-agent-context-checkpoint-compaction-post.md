## 왜 지금 이 문제가 불거지는가

"이 리팩터링 작업, 에이전트한테 몇 시간 동안 맡겨주세요. 중간에 끊겨도 처음부터 다시 하지 않게 해주세요." 에이전트가 짧은 단일 턴 작업을 넘어 수십 분~수 시간짜리 작업을 맡게 되면서 흔해진 요구다. 문제는 컨텍스트 윈도우가 아무리 넓어져도 결국 한계에 부딪힌다는 점이다. 가장 널리 쓰이는 해법은 윈도우가 꽉 차기 전에 지금까지의 대화·도구 호출 기록을 요약해 공간을 비우는 압축(compaction)인데, 이 방식에는 조용한 함정이 있다. 요약은 윈도우 안에만 존재했던 세부 정보를 돌이킬 수 없이 버린다. 중간 단계에서만 유효했던 파일 경로, 특정 도구 호출의 정확한 인자, 사용자가 지나가며 던진 제약 조건 같은 것들이 요약 문장 한 줄로 뭉개지면 복구할 방법이 없다.

이 문제가 단순한 성능 저하가 아니라 신뢰성 문제라는 점을 보여주는 연구 결과도 있다. 2026년 3월 공개된 한 연구(arXiv:2603.29231)는 짧은 작업에서 76.3%였던 평균 성공률이 매우 긴 작업에서는 52.1%까지 떨어졌고, 더 중요하게는 **메모리 스캐폴드를 그냥 끼워 넣는 것만으로는 장기 작업 신뢰성이 개선되지 않았으며 오히려 모델 10개 중 6개에서 성능을 악화시켰다**고 보고했다. 메모리를 추가하는 것 자체가 목적이 아니라, 무엇을 언제 어디에 남길지를 설계하는 것이 핵심이라는 뜻이다. 이전 글에서 다룬 Temporal·Restate 같은 워크플로 엔진 선택은 "죽었을 때 LLM 호출을 다시 재생해도 되는가"라는 질문에 답했다면, 이 글은 그 엔진이 무엇이든 공통으로 맞닥뜨리는 더 안쪽 질문 — "컨텍스트 자체를 어떻게 구조화해야 압축이 정보를 잃지 않는가"를 다룬다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-31-long-running-agent-context-checkpoint-compaction-1.svg" alt="현재 작업 중인 working memory 컨텍스트 윈도우가 한계에 가까워지면 압축을 실행하기 전에 구조화된 상태를 먼저 durable store에 체크포인트로 기록하고, 그 다음 압축을 수행하며, 재개 시에는 체크포인트에서 상태를 읽어 검증한 뒤 새 윈도우를 시드하는 흐름과, working memory·hot checkpoint·cold 장기 메모리 저장소로 나뉜 계층 구조도" style="width:100%;">

장기 실행 에이전트의 상태는 세 계층으로 나눠 생각하는 것이 안전하다. 현재 스레드 안에서만 유효한 **워킹 메모리**(컨텍스트 윈도우 그 자체), 압축 직전에 구조화된 형태로 durable store에 써 두는 **핫 체크포인트**(진행 상황, 남은 작업, 생성된 아티팩트), 그리고 스레드를 넘어 장기적으로 참조할 정보를 담는 **콜드 메모리**(벡터 스토어나 파일 기반 저장소)다. 데이터 흐름은 한 방향이 고정돼야 한다. 압축이 워킹 메모리를 건드리기 **전에** 반드시 핫 체크포인트부터 기록한다. 순서가 바뀌면 압축이 먼저 일어나고 체크포인트가 그 이후의 손실된 상태를 받아 적게 되어, 체크포인트 자체가 이미 깨진 정보를 담게 된다. 재개할 때는 체크포인트를 읽어 현재 실제 상태(파일 시스템, 외부 시스템 상태)와 일치하는지 검증한 뒤에야 새 워킹 메모리를 시드한다.

## 선택의 트레이드오프

| 전략 | 구현 난이도 | 정보 손실 위험 | 신뢰성 | 적합한 상황 |
|---|---|---|---|---|
| 압축 없이 윈도우만 키우기 | 매우 낮음 | 낮음(당장은) | 비용·지연시간으로 결국 한계 | 작업 길이가 짧고 예측 가능할 때 |
| Naive 요약 후 압축만 | 낮음 | 높음 — 조용히 정보 소실 | 장기 작업에서 급격히 저하 | 프로토타입, 재현 불가능해도 되는 경우 |
| 압축 전 체크포인트 선기록 | 중간 | 낮음 — 구조화된 상태는 보존 | 중간~높음 | 수십 분~시간 단위 작업 대부분 |
| Hot/Cold 계층 메모리 분리 | 높음 | 매우 낮음 | 가장 높음 — 설계·운영 비용 수반 | 여러 세션에 걸쳐 장기 기억이 필요한 에이전트 |

표에서 중요한 기준은 **"이 작업이 정말로 긴 세션을 요구하는가"**다. 몇 분 안에 끝나는 작업에 체크포인트·계층 메모리까지 설계하는 것은 과설계다. 반대로 수 시간짜리 리팩터링이나 여러 날에 걸친 마이그레이션 작업이라면, naive 압축만으로 버티다가 작업 후반부에 초반의 제약 조건을 잊어버리는 사고가 거의 반드시 일어난다. 또 하나 유의할 점은 메모리 스캐폴드를 추가하는 것 자체가 신뢰성 개선을 보장하지 않는다는 연구 결과다. 체크포인트·장기 메모리를 도입한 뒤에는 반드시 도입 전후로 장기 작업 성공률을 비교 측정해, 실제로 개선되는지 확인해야 한다.

## 실제 프로젝트 진행 순서

1. **작업이 실제로 긴 세션을 요구하는지부터 확인한다.** 평균 작업 시간과 컨텍스트 소모량을 측정해, 압축이 실제로 발생하는 빈도를 먼저 파악한다.
2. **체크포인트의 구조를 먼저 정의한다.** 진행 상황, 남은 작업 목록, 지금까지 생성·수정한 아티팩트 경로를 명시적 필드로 둔다. 자유 형식 요약 텍스트에만 의존하지 않는다.
3. **압축 트리거 직전에 체크포인트 기록이 선행되도록 순서를 코드 레벨에서 강제한다.** 압축과 체크포인트가 같은 트랜잭션처럼 묶여 있지 않으면 순서가 뒤집힐 수 있다.
4. **재개 로직에 검증 단계를 추가한다.** 체크포인트를 그대로 믿지 않고, 파일 시스템이나 외부 상태와 실제로 일치하는지 확인한 뒤 작업을 이어간다.
5. **메모리 스캐폴드 도입 전후로 장기 작업 성공률을 비교 측정한다.** "메모리를 추가했으니 나아졌을 것"이라고 가정하지 않고, 실제 수치로 확인한 뒤에만 운영에 반영한다.

## 실무 포인트

**압축 로직과 체크포인트 로직을 같은 함수 안에 섞지 않는다.** 분리해 둬야 순서를 강제하기 쉽고, 나중에 체크포인트 포맷을 바꿀 때 압축 로직까지 건드릴 필요가 없다.

**체크포인트에 "왜 이 결정을 내렸는가" 같은 근거도 남긴다.** 진행 상황만 남기면 재개 후에 같은 실수를 반복하거나 이미 기각한 접근을 다시 시도할 수 있다.

**콜드 메모리까지는 모든 프로젝트에 필요하지 않다.** 단일 세션 안에서 끝나는 작업이라면 체크포인트만으로 충분하고, 세션을 넘나드는 장기 기억이 실제로 필요할 때만 벡터 스토어·파일 기반 계층을 추가한다.

## 마무리

- 컨텍스트 압축은 윈도우 안에만 있던 정보를 조용히 버릴 수 있고, 메모리 스캐폴드를 그냥 추가하는 것만으로는 장기 작업 신뢰성이 개선되지 않는다는 연구 결과도 있다.
- 압축이 워킹 메모리를 건드리기 전에 구조화된 체크포인트를 durable store에 먼저 기록하는 순서를 지켜야, 재개 시 잃어버린 정보 때문에 같은 실수를 반복하지 않는다.
- 워킹 메모리·핫 체크포인트·콜드 장기 메모리를 계층으로 나누되, 작업이 실제로 긴 세션을 요구하는지부터 확인하고 필요한 계층만 도입해야 한다.
