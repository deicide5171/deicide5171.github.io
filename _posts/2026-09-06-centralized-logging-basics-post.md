## 서버 10대에 SSH로 일일이 들어가 로그를 볼 순 없다

서버가 한 대일 때는 그 서버에 접속해 로그 파일을 보면 됐다. 그런데 서버가 여러 대로 늘어나면, 어느 서버가 에러를 냈는지 모르니 10대에 다 들어가 `grep`을 돌려야 한다. 로드밸런서가 요청을 분산하는 환경에서는 한 사용자의 요청이 여러 서버에 흩어져 추적이 거의 불가능해진다. **중앙 로그 수집**은 모든 서버의 로그를 한 곳으로 모아 검색·분석할 수 있게 하는 것이다.

## 중앙 로그 수집의 기본 흐름

```text
1. 수집(Collect): 각 서버의 로그를 에이전트가 읽어 전송
   (예: Filebeat, Fluent Bit)
2. 저장·색인(Store/Index): 검색 가능하게 저장
   (예: Elasticsearch, Loki)
3. 조회·시각화(Visualize): 대시보드에서 검색하고 그래프로 봄
   (예: Kibana, Grafana)

각 서버 -> 수집 에이전트 -> 중앙 저장소 -> 대시보드
```

## 대표적인 조합

| 스택 | 구성 |
|---|---|
| ELK | Elasticsearch + Logstash + Kibana |
| EFK | Elasticsearch + Fluentd + Kibana |
| Loki 스택 | Loki + Promtail + Grafana(가볍고 저렴) |
| 클라우드 관리형 | CloudWatch Logs, Datadog 등 |

## 로그를 잘 모으기 위한 조건: 구조화

```text
[비구조화 로그 - 검색·필터가 어렵다]
2026-09-06 12:00:01 ERROR 결제 실패 user=123 amount=5000

[구조화 로그(JSON) - 필드로 검색 가능]
{"time":"2026-09-06T12:00:01","level":"ERROR",
 "msg":"결제 실패","user":"123","amount":5000}
```

구조화된 로그(JSON)로 남기면 "level이 ERROR이고 user가 123인 로그만" 같은 조건 검색이 쉬워진다. 중앙 수집의 진가는 이 검색·필터링에서 나온다.

## 실무 포인트

- **로그에 요청 추적 ID를 붙여라.** 한 사용자의 요청이 여러 서버·서비스를 거칠 때, 공통 추적 ID(trace id)를 로그에 함께 남기면 흩어진 로그를 하나의 흐름으로 이어 볼 수 있다.
- **로그 양과 보관 기간이 곧 비용이다.** 모든 로그를 무한정 저장하면 저장 비용이 폭증한다. 중요도에 따라 보관 기간을 다르게 하거나, 오래된 로그는 저렴한 스토리지로 옮기는 정책이 필요하다.
- **민감정보가 로그에 섞이지 않게 하라.** 여러 곳으로 로그가 흘러가는 만큼, 비밀번호·개인정보가 로그에 들어가면 유출 범위가 커진다. 수집 단계에서 마스킹하거나 애초에 남기지 않아야 한다.

## 마무리 요약

- 서버가 여러 대가 되면 로그가 흩어져, 중앙 로그 수집으로 한 곳에 모아 검색·분석해야 한다.
- 수집 에이전트 → 중앙 저장소 → 대시보드의 흐름으로 동작하며 ELK·Loki 등의 스택이 대표적이다.
- 구조화된(JSON) 로그와 요청 추적 ID가 흩어진 로그를 유용하게 만드는 핵심이다.
