내비게이션 앱이나 배달 서비스는 사용자가 출발지와 목적지를 입력하는 순간 몇 초 안에 최단 경로를 보여줘야 한다. 문제는 이 계산이 수행되는 대상이 수백만 개의 도로 세그먼트로 이루어진 거대한 그래프라는 점이다. 단순히 다익스트라(Dijkstra) 알고리즘을 그대로 돌리면 전국 단위 도로망에서는 응답 시간이 사용자가 기다릴 수 있는 수준을 훌쩍 넘어간다.

이 문제를 실용적으로 풀기 위해 등장한 것이 OpenStreetMap(OSM) 데이터를 입력으로 받아 실시간 경로를 계산하는 오픈소스 라우팅 엔진들이다. 그중에서도 OSRM(Open Source Routing Machine)과 Valhalla는 널리 쓰이는 두 축인데, 둘 다 "빠른 질의 응답"이라는 같은 목표를 추구하면서도 그래프를 준비하고 탐색하는 방식이 근본적으로 다르다.

이 글에서는 OSRM이 택한 사전 계산 기반 접근과 Valhalla가 택한 계층적 타일 기반 접근을 비교하고, 각 방식이 어떤 프로젝트 특성에 더 적합한지를 정리한다.

## 핵심 개념 1: OSRM의 Contraction Hierarchies

OSRM은 Contraction Hierarchies(CH)라는 전처리 기법을 기본 알고리즘으로 사용한다. 아이디어는 간단하다. 도로망 그래프에서 상대적으로 덜 중요한 노드(교차로)를 순서대로 제거하면서, 그 노드를 지나가던 경로를 대체할 수 있는 "shortcut" 간선을 미리 추가해 두는 것이다. 이 과정을 반복하면 원래 그래프 위에 여러 단계의 축약된 그래프가 쌓이게 된다.

질의 시점에는 이 축약된 그래프에서 양방향 탐색(bidirectional search)을 수행한다. 출발지에서는 위쪽으로, 목적지에서는 아래쪽으로 동시에 탐색해 나가다가 두 탐색이 만나는 지점을 찾으면 되므로, 방문해야 하는 노드 수가 원본 그래프 대비 크게 줄어든다. 이 방식의 핵심은 무거운 계산을 전처리 단계에 몰아넣고, 실제 질의는 최대한 가볍게 만든다는 데 있다. 다만 그만큼 도로망 데이터가 바뀌면 전처리를 다시 수행해야 하며, 이 전처리에 걸리는 시간은 지역 크기에 따라 상당히 늘어날 수 있다.

## 핵심 개념 2: Valhalla의 계층적 타일 그래프

Valhalla는 접근 방식이 다르다. 도로망을 지리적 타일(tile) 단위로 분할하고, 각 타일 안의 도로를 등급에 따라 여러 계층(hierarchy)으로 나눠 저장한다. 고속도로처럼 장거리 이동에 쓰이는 도로는 상위 계층에, 골목길처럼 근거리 이동에 쓰이는 도로는 하위 계층에 배치하는 식이다. 질의 시에는 출발지·목적지 인근에서는 하위 계층까지 탐색하고, 먼 거리를 이동하는 구간에서는 상위 계층만 사용해 탐색 범위를 줄인다.

Valhalla가 강조하는 또 다른 특징은 비용 모델(costing model)의 유연성이다. 자동차, 자전거, 도보, 화물차 등 이동 수단별로 이미 여러 비용 모델을 내장하고 있고, 도로 유형·경사·회전 제약 같은 요소에 가중치를 다르게 부여하는 커스텀 비용 모델을 직접 정의할 수 있는 구조를 제공한다. 이는 OSM 태그 정보를 최대한 살려서, 단일 알고리즘이 아니라 이동 수단과 정책에 따라 다른 "최적"을 계산하고 싶은 프로젝트에 적합한 설계다.

## 핵심 개념 3: OSRM과 Valhalla 비교

| 구분 | OSRM | Valhalla |
|---|---|---|
| 핵심 알고리즘 | Contraction Hierarchies (사전 계산 기반) | 계층적 타일 그래프 + A* 계열 탐색 |
| 사전 계산(전처리) 시간 | 필요하며, 지역 규모가 클수록 오래 걸릴 수 있음 | 상대적으로 가벼운 타일 생성 위주 |
| 질의(query) 속도 | 매우 빠른 편으로 알려짐(전처리 덕분) | 빠르지만 CH 대비 탐색 범위가 넓을 수 있음 |
| 이동 수단 지원 | car/bike/foot 프로필 지원, 확장 가능 | car/bike/pedestrian/truck 등 다양한 내장 비용 모델 |
| 커스터마이징 유연성 | Lua 기반 프로필 스크립트로 조정 | costing 옵션과 커스텀 비용 모델로 세밀한 조정 |
| 대표 활용처 | 빠른 응답이 중요한 대규모 서비스 | 다양한 이동 수단·상세 옵션이 필요한 서비스 |

두 엔진 모두 OSM 데이터를 입력으로 삼는다는 점은 같지만, OSRM은 "질의를 빠르게 만들기 위해 전처리에 비용을 투자"하는 쪽이고, Valhalla는 "타일 구조와 다양한 비용 모델로 유연성을 확보"하는 쪽에 가깝다.

## 예제

다음은 각 엔진의 대표적인 라우팅 API 요청 형태다. 실제 응답 필드나 옵션은 버전에 따라 달라질 수 있으므로 공식 문서를 함께 참고하는 것이 좋다.

```
# OSRM: 좌표 두 개(경도,위도) 사이의 자동차 경로 요청
GET http://localhost:5000/route/v1/driving/127.0276,37.4979;126.9780,37.5665?overview=full&geometries=geojson
```

```
# Valhalla: /route 엔드포인트에 JSON으로 locations와 costing 전달
POST http://localhost:8002/route
Content-Type: application/json

{
  "locations": [
    {"lat": 37.4979, "lon": 127.0276},
    {"lat": 37.5665, "lon": 126.9780}
  ],
  "costing": "auto",
  "costing_options": {
    "auto": {"use_highways": 0.5}
  }
}
```

OSRM은 경로(path) 파라미터 형태로 좌표를 나열하는 REST 스타일에 가깝고, Valhalla는 요청 본문에 위치 배열과 비용 모델 옵션을 JSON으로 담아 보내는 방식이라는 차이가 있다.

## 실무 포인트

- **도로망 데이터 업데이트 주기를 미리 고려해야 한다.** OSRM은 OSM 데이터가 갱신될 때마다 Contraction Hierarchies 전처리를 다시 수행해야 하므로, 데이터 갱신 빈도가 잦은 서비스라면 전처리 파이프라인 자체를 자동화해 두는 것이 중요하다. Valhalla도 타일을 재생성해야 하지만, 계층 구조상 특정 지역만 부분적으로 갱신하는 운용이 상대적으로 용이하다고 알려져 있다.
- **프로젝트 규모와 요구 사항에 따라 선택 기준이 달라진다.** 단순 최단 경로 위주로 매우 빠른 응답이 최우선인 대규모 서비스라면 OSRM의 CH 방식이 유리할 수 있고, 도보·자전거·화물차 등 다양한 이동 수단과 세밀한 비용 정책이 필요한 서비스라면 Valhalla의 유연한 costing 구조가 더 맞을 수 있다.
- **두 엔진 모두 셀프 호스팅이 전제이므로, 서버 자원(메모리·디스크)과 운영 인력을 함께 고려해야 한다.** 특히 전국 단위나 글로벌 데이터를 다룰 때는 전처리/타일 생성에 필요한 메모리 용량을 사전에 벤치마크하는 과정이 필요하다.

## 3줄 요약

- OSRM은 Contraction Hierarchies로 그래프를 미리 축약해 두어 질의 속도를 극대화하는 전략을 쓴다.
- Valhalla는 계층적 타일 그래프와 다양한 이동 수단별 비용 모델을 통해 유연성과 커스터마이징 가능성에 무게를 둔다.
- 선택 기준은 서비스의 우선순위에 달려 있으며, 응답 속도가 최우선이면 OSRM을, 다양한 이동 수단·세밀한 정책이 필요하면 Valhalla를 검토하는 것이 합리적이다.
