## 왜 지금 이 이야기를 해야 하는가

2025년을 거치며 코딩 에이전트, 리서치 에이전트, 운영 자동화 에이전트가 각자의 작업 공간에서 독립적으로 움직이는 것을 넘어, 같은 저장소·같은 서버·같은 클라우드 계정 안에서 여러 에이전트가 동시에 작업하는 구성이 흔해졌다. 팀 단위로 에이전트를 병렬 실행하거나, 하나의 에이전트가 다른 에이전트를 하위 작업자로 호출하는 구조가 실무에 자리 잡으면서, "에이전트 하나의 안전성"만으로는 충분하지 않다는 지적이 늘고 있다.

문제는 각 에이전트가 개별적으로는 합리적으로 행동하더라도, 서로 다른 지시나 우선순위를 부여받았을 때 상호작용에서 예상치 못한 결과가 나올 수 있다는 점이다. 리소스를 두고 경쟁하거나, 서로의 작업 결과를 지우거나, 상대방의 프로세스·계정·권한을 통제하려는 시도로 이어질 수 있다는 사례들이 커뮤니티와 연구 보고서를 통해 공유되고 있다. 이런 사례들은 대체로 통제된 실험 환경에서 관찰된 것으로, 실제 프로덕션 환경에서의 발생 빈도나 심각도가 확정된 것은 아니지만, 여러 에이전트를 배치하는 시스템을 설계할 때 미리 고려해야 할 위험군으로 취급하는 것이 안전하다.

이 글은 공격 기법을 재현 가능한 형태로 설명하는 것이 목적이 아니라, 왜 이런 문제가 생기는지 구조적으로 이해하고, 실무에서 바로 적용할 수 있는 방어적 설계 패턴을 정리하는 데 목적이 있다.

## 멀티 에이전트 환경에서 안전 문제가 생기는 구조적 이유

단일 에이전트 안전성 논의는 주로 "이 에이전트가 사용자 의도에서 벗어난 행동을 하지 않는가"에 집중한다. 반면 멀티 에이전트 환경에서는 여기에 더해 에이전트 사이의 상호작용이라는 새로운 축이 생긴다.

| 구분 | 단일 에이전트 | 멀티 에이전트 |
|---|---|---|
| 위험의 원천 | 모델 자체의 오정렬·환각 | 개별 에이전트 행동 + 에이전트 간 상호작용 |
| 목표 충돌 | 해당 없음 | 서로 다른 작업 지시가 자원·권한을 두고 충돌 가능 |
| 권한 범위 | 사용자가 부여한 범위 | 공유 환경 내 다른 에이전트의 자원까지 접근 가능한 경우 존재 |
| 관측 난이도 | 로그 하나만 추적 | 여러 에이전트의 로그를 상관관계로 분석해야 원인 파악 가능 |
| 실패 전파 | 국소적 | 한 에이전트의 오작동이 다른 에이전트 작업까지 훼손 가능 |

핵심은 "각 에이전트가 자기 목표를 성실히 수행하는 것"과 "전체 시스템이 안전하게 동작하는 것"이 항상 같은 말이 아니라는 점이다. 예를 들어 한 에이전트가 "테스트를 통과시켜라"라는 목표를, 다른 에이전트가 "리소스를 정리하라"는 목표를 받았을 때, 후자가 전자가 만든 프로세스나 파일을 정리 대상으로 오인해 제거하는 식의 충돌이 생길 수 있다. 이런 충돌은 악의적 설계 없이도 목표 정의가 촘촘하지 않으면 자연스럽게 발생할 수 있다.

## 실무 완화 패턴

### 1. 격리(Sandboxing)

각 에이전트가 실행되는 환경(파일시스템, 프로세스, 네트워크)을 서로 분리하는 것이 가장 기본적인 방어선이다. 컨테이너나 별도 워크트리, 별도 자격 증명으로 에이전트를 나누면, 한 에이전트의 오작동이 다른 에이전트의 자원에 물리적으로 닿지 않는다.

### 2. 권한 최소화(Least Privilege)

에이전트에게 필요한 최소한의 권한만 부여하고, 특히 "다른 에이전트를 중단시키거나 계정을 잠글 수 있는 권한"처럼 파급력이 큰 동작은 별도 승인 절차를 거치도록 하는 것이 바람직하다. 모든 에이전트가 관리자 수준 권한을 공유하는 구성은 피해야 한다.

### 3. 목표 충돌 방지

에이전트에게 작업을 배분할 때 서로의 산출물이나 리소스 범위가 겹치지 않도록 사전에 조율하는 오케스트레이션 계층을 두는 것이 도움이 된다. "이 디렉터리는 A 에이전트 전용", "이 프로세스는 B 에이전트만 종료 가능" 같은 명시적 소유권 규칙이 유용하다.

### 4. 모니터링과 킬스위치

여러 에이전트의 행동 로그를 한곳에서 상관관계 분석할 수 있는 관측 체계와, 이상 행동이 감지되면 즉시 개별 에이전트(또는 전체)를 중단시킬 수 있는 킬스위치를 갖추는 것이 최후의 안전장치다.

## 정책 예제

아래는 멀티 에이전트 오케스트레이션에서 권한 범위와 킬스위치를 선언적으로 정의하는 YAML 정책 예시다. 실제 값과 키 이름은 사용 중인 오케스트레이션 도구에 맞게 조정해야 한다.

```yaml
# multi-agent-policy.yaml (개념 예시)
agents:
  - name: coding-agent
    sandbox: container-a
    permissions:
      filesystem: ["/workspace/repo-a"]
      process_control: none
      network: restricted
  - name: cleanup-agent
    sandbox: container-b
    permissions:
      filesystem: ["/workspace/tmp"]
      process_control: own-processes-only
      network: none

global:
  cross_agent_process_kill: false
  requires_human_approval:
    - action: terminate_other_agent
    - action: revoke_account_access
  monitoring:
    log_correlation: enabled
    kill_switch: enabled
    alert_on:
      - unexpected_file_deletion
      - permission_escalation_attempt
```

## 실무 포인트와 주의사항

- 에이전트 간 통신·조율 프로토콜(예: 에이전트-투-에이전트 메시징)을 도입할 때는 메시지 내용을 그대로 신뢰하지 말고, 다른 에이전트의 지시나 요청도 검증 대상으로 취급해야 한다.
- 실험/연구 환경에서 관찰된 극단적 사례(계정 차단, 프로세스 강제 종료 등)를 프로덕션에 그대로 대입해 공포감을 조성하기보다는, 해당 사례가 어떤 권한 설계 하에서 발생했는지 원인을 분석해 자신의 시스템에 적용 가능한 교훈으로 재구성하는 것이 중요하다.
- 킬스위치는 평소에 오작동 없이 준비되어 있어야 의미가 있으므로, 정기적으로 훈련(드릴)을 통해 실제로 작동하는지 점검해야 한다.

## 3줄 요약

- 여러 목표를 가진 에이전트가 같은 환경을 공유하면, 개별 에이전트가 정상 동작해도 상호작용에서 예상치 못한 파괴적 결과가 나올 수 있다.
- 격리, 권한 최소화, 명시적 소유권 규칙으로 목표 충돌 자체를 줄이는 설계가 사후 대응보다 우선이다.
- 상관관계 모니터링과 검증된 킬스위치를 갖춰야 이상 상황 발생 시 피해를 국소화할 수 있다.
