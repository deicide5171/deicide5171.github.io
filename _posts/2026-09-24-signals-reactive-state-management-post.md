## 왜 지금 시그널을 다시 봐야 하는가

React에서 `useState`로 상태를 바꾸면 그 상태를 참조하는 컴포넌트가 리렌더링되고, 별도로 최적화하지 않으면 그 하위 트리 전체가 함께 리렌더링된다. `useMemo`, `useCallback`, `React.memo`로 이를 세밀하게 제어할 수 있지만, 이는 결국 개발자가 수동으로 "이 계산은 다시 안 해도 된다"는 것을 프레임워크에게 알려주는 보일러플레이트다. Vue 3(Composition API의 `ref`), SolidJS, Preact Signals는 이 문제를 근본적으로 다른 방식으로 푼다. 이들은 상태를 "컴포넌트 리렌더링을 유발하는 값"이 아니라, "그 값을 실제로 읽는 지점만 정밀하게 갱신하는 반응형 원시 타입(시그널)"으로 다룬다. 이 차이를 이해하면 왜 특정 프레임워크에서는 `memo` 최적화가 거의 필요 없어지는지 알 수 있다.

## 핵심 개념 1 — Virtual DOM 리렌더링과 세밀한 반응성의 차이

React의 렌더링 모델은 상태가 바뀌면 컴포넌트 함수를 처음부터 다시 실행하고, 그 결과로 나온 Virtual DOM 트리를 이전 트리와 비교(diffing)해 실제 DOM에 필요한 변경만 적용한다. 즉 "컴포넌트 함수 재실행"이 리렌더링의 단위다. 반면 시그널 기반 시스템은 컴포넌트 함수를 한 번만 실행하고, 그 함수 안에서 시그널 값을 읽는 지점(구독)들을 추적해둔다. 이후 시그널 값이 바뀌면 컴포넌트 함수 전체를 다시 실행하는 대신, 그 값을 직접 읽고 있던 최소한의 DOM 노드나 표현식만 갱신한다. 컴포넌트 함수 재실행 자체가 없기 때문에 "이 자식 컴포넌트는 리렌더링되지 않게 막아야 한다"는 고민 자체가 발생하지 않는다.

## 핵심 개념 2 — 의존성 추적은 컴파일 타임이 아니라 런타임에 자동으로 이뤄진다

시그널의 핵심 메커니즘은 "누가 이 값을 읽었는가"를 런타임에 자동으로 추적하는 것이다. 시그널을 읽는 함수(effect, computed, 또는 렌더 함수)가 실행되는 동안 전역적으로 "지금 실행 중인 구독자"가 기록되고, 그 실행 중에 어떤 시그널의 getter가 호출되면 그 시그널은 "이 구독자가 나를 읽었다"는 관계를 등록한다. 이 의존성 그래프는 코드에 명시적으로 배열(`useEffect`의 dependency array처럼)을 적어줄 필요가 없이 자동으로 구성되고, 갱신된다. `useEffect`의 의존성 배열을 빠뜨려 버그가 나는 클래스의 문제가 시그널 모델에서는 구조적으로 발생하지 않는다.

| 항목 | React (Virtual DOM) | 시그널 기반 (Solid, Vue, Preact Signals) |
|---|---|---|
| 갱신 단위 | 컴포넌트 함수 재실행 | 시그널을 읽는 지점만 정밀 갱신 |
| 의존성 추적 | 개발자가 배열로 명시 | 런타임에 읽기 시점 자동 추적 |
| 자식 리렌더링 방지 | `memo`/`useMemo` 필요 | 구조적으로 불필요 |
| 컴포넌트 함수 재실행 빈도 | 상태 변경마다 | 최초 1회 (이후는 구독 갱신만) |

## 예제 — SolidJS 시그널 기본 사용

```jsx
import { createSignal, createEffect } from 'solid-js';

function Counter() {
  const [count, setCount] = createSignal(0);

  // count()를 읽는 이 effect는 count가 바뀔 때만 재실행됨
  createEffect(() => {
    console.log('현재 카운트:', count());
  });

  return (
    <div>
      {/* 이 텍스트 노드만 직접 갱신되며, Counter 함수 자체는 재실행되지 않음 */}
      <p>카운트: {count()}</p>
      <button onClick={() => setCount(count() + 1)}>증가</button>
    </div>
  );
}
```

`count()`를 호출하는 것이 곧 "이 값을 읽는다"는 구독 등록이다. `Counter` 함수는 최초 렌더링 시 단 한 번만 실행되고, 버튼 클릭 이후에는 `<p>` 안의 텍스트 노드만 직접 업데이트된다.

## 실무 포인트

- **React 생태계에서도 시그널 유사 라이브러리(Preact Signals, Jotai, Zustand의 선택적 구독)를 도입해 리렌더링 범위를 줄일 수 있다.** React 자체의 렌더링 모델을 바꾸는 것은 아니지만, 컴포넌트를 잘게 나누고 시그널 값을 읽는 leaf 컴포넌트만 별도로 분리하면 유사한 효과를 얻을 수 있다.
- **시그널 기반 프레임워크로 마이그레이션을 고려한다면 기존 React 멘탈 모델을 버려야 하는 지점을 미리 파악하라.** "상태가 바뀌면 컴포넌트가 다시 실행된다"는 가정에 기반한 로직(렌더링 중 로그, 클로저 캡처 패턴)이 시그널 모델에서는 다르게 동작한다.
- **대규모 리스트 렌더링처럼 리렌더링 비용이 큰 화면에서 효과를 가장 크게 체감한다.** 반대로 상태 변경이 드문 정적인 페이지에서는 두 모델의 실질적 성능 차이가 크지 않으므로, 전면 마이그레이션보다는 병목 지점에 선택적으로 적용하는 것이 현실적이다.

## 마무리 요약

- React는 상태 변경 시 컴포넌트 함수를 재실행하고 Virtual DOM diffing으로 변경을 적용하지만, 시그널 기반 프레임워크는 값을 읽는 지점만 정밀하게 갱신한다.
- 시그널의 의존성 추적은 런타임에 자동으로 이뤄지므로, `useEffect` 의존성 배열 누락 같은 클래스의 버그가 구조적으로 발생하지 않는다.
- React 생태계에서도 시그널 유사 라이브러리로 리렌더링 범위를 좁힐 수 있으며, 전면 전환보다는 리렌더링 비용이 큰 지점에 선택적으로 적용하는 것이 실무적으로 합리적이다.
