## DB 연결은 생각보다 비싼 작업이다

애플리케이션이 DB에 쿼리를 보내려면 먼저 연결(connection)을 맺어야 한다. 그런데 이 연결을 맺는 과정(인증, 네트워크 핸드셰이크 등)은 생각보다 오래 걸린다. 매 요청마다 새로 연결을 맺고 끊으면, 정작 쿼리 자체보다 연결에 더 많은 시간이 든다. **커넥션 풀(Connection Pool)**은 미리 여러 개의 연결을 만들어두고 재사용하는 방식으로 이 낭비를 없앤다.

## 커넥션 풀이 없을 때와 있을 때

```text
[풀 없음]
요청1: 연결 생성 -> 쿼리 -> 연결 종료
요청2: 연결 생성 -> 쿼리 -> 연결 종료
(매번 연결 생성·종료 비용)

[풀 있음]
시작 시: 연결 N개 미리 생성해 풀에 보관
요청1: 풀에서 연결 빌림 -> 쿼리 -> 풀에 반납
요청2: 풀에서 연결 빌림 -> 쿼리 -> 풀에 반납
(연결을 만들지 않고 빌려 씀)
```

## 핵심 설정값

| 설정 | 의미 |
|---|---|
| 최대 풀 크기 | 동시에 빌려줄 수 있는 최대 연결 수 |
| 최소 유휴 연결 | 항상 대기시켜둘 연결 수 |
| 커넥션 타임아웃 | 연결을 못 빌리고 기다리는 최대 시간 |
| 최대 수명 | 오래된 연결을 교체하는 주기 |

## 풀 크기는 클수록 좋은가

```text
아니다. 풀 크기가 너무 크면:
- DB의 max_connections를 초과해 오히려 에러
- 연결이 너무 많아 DB가 컨텍스트 스위칭으로 느려짐

너무 작으면:
- 연결을 못 빌린 요청들이 대기하다 타임아웃

-> 서비스 특성과 DB 사양에 맞는 적정값을 찾아야 한다.
   무작정 늘리는 것이 아니라 실측으로 조정한다.
```

## 실무 포인트

- **커넥션을 빌린 뒤 반드시 반납해야 한다.** 쿼리 후 연결을 풀에 돌려주지 않으면(try-with-resources 누락 등) 풀이 고갈되어 새 요청이 연결을 못 빌리고 멈춘다. 커넥션 누수는 커넥션 풀 관련 장애의 가장 흔한 원인이다.
- **애플리케이션 인스턴스 수 × 풀 크기가 DB의 max_connections를 넘지 않게 해야 한다.** 서버 5대가 각각 풀 크기 20이면 총 100개 연결을 요구하므로, DB의 최대 연결 수가 이보다 커야 한다.
- **HikariCP 같은 성숙한 풀 라이브러리를 쓰는 것이 좋다.** 직접 구현하기보다 검증된 커넥션 풀을 쓰고, 그 기본값을 이해한 뒤 우리 환경에 맞게 조정하는 것이 안전하다.

## 마무리 요약

- DB 연결을 맺는 것은 비싼 작업이라, 매 요청마다 새로 연결하면 쿼리보다 연결에 시간이 더 든다.
- 커넥션 풀은 연결을 미리 만들어두고 빌려 쓰고 반납하는 방식으로 이 낭비를 없앤다.
- 풀 크기는 클수록 좋은 게 아니며, 커넥션 누수 방지와 DB의 max_connections를 넘지 않는 것이 핵심이다.
