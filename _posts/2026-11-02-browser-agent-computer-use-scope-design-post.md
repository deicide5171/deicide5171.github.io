## 왜 지금 이 판단이 다시 중요해졌는가

"관리자 페이지에 로그인해서 이 설정값들을 매일 체크해주세요", "경쟁사 사이트 가격을 매일 확인해서 알려주세요" 같은 요구가 들어오면, 요즘은 API를 찾기 전에 "그냥 에이전트가 브라우저를 직접 조작하게 하면 안 되나?"라는 질문이 먼저 떠오른다. 화면을 보고, 클릭하고, 입력하고, 결과를 읽는 범용 컴퓨터 제어 능력이 실제로 쓸 만해졌기 때문이다. 그런데 최근 1년 사이 시장에서 재미있는 신호가 나왔다. 독립 제품으로 나왔던 브라우저 전용 에이전트들이 하나둘 접히거나 더 큰 에이전트 플랫폼의 한 기능으로 흡수되고 있다는 점이다.

이 흐름은 단순한 제품 통폐합 뉴스가 아니라, 빌더에게 실제 설계 판단 기준을 준다. "브라우저 자동화"를 별도의 독립 제품·엔드포인트로 만들 가치가 있는지, 아니면 더 넓은 컴퓨터 제어 능력(터미널·파일·데스크톱 앱까지 포괄하는) 안의 한 모드로 흡수시켜야 하는지의 문제다. 그리고 이 판단은 곧바로 "이 작업에 컴퓨터 전체를 내줄 것인가, 전용 API 도구 하나만 내줄 것인가"라는, 모든 에이전트 설계에서 반복되는 더 근본적인 질문으로 이어진다.

## 전체 시스템에서의 위치

이 요구는 셋 중 하나의 자리로 번역된다. 첫째는 **전용 API 도구** — 대상 서비스가 API를 제공하면 그 엔드포인트를 직접 호출하는 함수 하나를 에이전트에 붙인다. 둘째는 **스코프가 좁은 브라우저 자동화** — 특정 사이트의 로그인·클릭·추출 흐름만 스크립트로 고정하고 에이전트는 그 스크립트를 트리거만 한다. 셋째는 **범용 컴퓨터 제어(Computer Use)** — 에이전트가 화면 스크린샷을 보고 마우스·키보드를 직접 움직여 어떤 사이트든, 어떤 앱이든 다룬다.

데이터 흐름으로 보면 세 경로 모두 "요청 → 실행 계층 → 결과 해석 → 응답"이라는 같은 위치에 있지만, 실행 계층의 통제 가능성이 반대 방향으로 좁아진다. API 도구는 입력·출력 스키마가 고정돼 있어 무엇이 일어날지 사전에 완전히 예측할 수 있다. 컴퓨터 제어는 화면에 뭐가 떠 있는지에 따라 에이전트가 매번 다른 경로로 클릭할 수 있어, 실행 전에는 정확히 무엇을 할지 알 수 없다. 이 예측 불가능성이 바로 설계에서 다뤄야 할 핵심 리스크다.

## 선택의 트레이드오프

| 기준 | 전용 API 도구 | 좁은 브라우저 스크립트 | 범용 Computer Use |
|---|---|---|---|
| 적용 범위 | API 있는 서비스만 | 미리 정한 사이트·흐름만 | 화면이 있는 모든 것 |
| 실행 예측 가능성 | 높음 — 스키마 고정 | 중간 — 셀렉터 깨지면 실패 | 낮음 — 매 실행 경로가 다름 |
| 구축 비용 | 서비스당 1회, 낮음 | 사이트당 스크립트 유지보수 | 거의 0 — 즉시 적용 |
| 실패 시 블라스트 반경 | 작음 — 호출 범위로 한정 | 중간 — 스크립트 범위로 한정 | 큼 — 화면에 보이는 모든 조작 가능 |
| 변경에 대한 내성 | UI 변경 영향 없음 | UI 변경 시 깨짐 | UI 변경에도 적응(단, 오작동 가능) |
| 적합한 상황 | API가 있거나 만들 수 있을 때 | 반복적인 고정 작업 소수 | API가 없는 레거시·외부 시스템, 일회성 작업 |

여기서 "전용 브라우저 에이전트 제품이 접혔다"는 신호가 왜 중요한지가 드러난다. 독립 제품으로서의 브라우저 에이전트는 둘째(좁은 스크립트)와 셋째(범용 제어) 사이 애매한 위치에 있었다. 결국 시장은 "브라우저만 따로 떼어 제품화"하기보다, 범용 컴퓨터 제어 능력 하나에 브라우저·터미널·파일·데스크톱 앱을 전부 포함시키는 방향으로 수렴하고 있다. 빌더 입장에서 얻는 교훈은, 브라우저 자동화를 위해 별도 제품·별도 아키텍처를 구축하는 대신 "범용 컴퓨터 제어 vs 전용 도구"라는 더 큰 이분법으로 판단을 단순화하라는 것이다.

## 실제 프로젝트 진행 순서

1. **대상 서비스에 API가 있는지부터 확인한다.** 공식 API, 비공식이지만 안정적인 내부 API가 있다면 무조건 전용 도구가 우선이다. Computer Use는 API가 없을 때의 차선책이지, 기본 선택지가 아니다.
2. **API가 없다면 작업의 반복성을 따진다.** 매번 똑같은 흐름(로그인 → 특정 메뉴 → 다운로드)이 반복된다면 셀렉터 기반 스크립트로 고정하는 편이 Computer Use보다 훨씬 저렴하고 안정적이다.
3. **작업이 비정형적이거나 일회성이라면 그때 Computer Use를 꺼낸다.** 매번 화면 구성이 달라지거나, 사전에 흐름을 못 박을 수 없는 경우(예: "이 레거시 관리 콘솔에서 오늘 뜬 알림을 요약해주세요")가 여기 해당한다.
4. **Computer Use를 쓰기로 했다면 샌드박스 경계부터 먼저 긋는다.** 실제 프로덕션 계정이 아니라 권한을 제한한 전용 계정·격리된 VM·읽기 전용 모드로 시작하고, 쓰기·결제·삭제 같은 되돌리기 어려운 동작은 사람 승인 단계를 강제로 끼워 넣는다.
5. **실행 로그를 전부 남긴다.** 스크린샷·클릭 좌표·입력값을 단계별로 기록해, 예측 불가능한 경로로 움직였을 때 사후에 무엇이 일어났는지 재구성할 수 있게 한다.

## 실무 포인트

**"컴퓨터 전체를 내준다"는 결정은 기능 하나가 아니라 권한 모델 전체를 다시 설계하는 일이다.** API 도구는 함수 시그니처만 검토하면 되지만, Computer Use는 에이전트가 화면에서 할 수 있는 모든 조작이 잠재적 공격면이 된다. 민감한 동작(결제, 계정 설정 변경, 삭제)은 Computer Use 경로에서 아예 차단하거나 별도 승인 게이트를 거치게 해야 한다.

**속도와 비용도 함께 고려해야 한다.** 화면 스크린샷을 반복적으로 모델에 보내고 다음 동작을 추론하는 구조는 API 호출 한 번보다 훨씬 느리고 토큰 비용도 크다. 같은 작업을 API로 할 수 있는데 Computer Use로 돌리고 있다면, 그건 거의 항상 성능·비용 면에서 손해다.

**"일단 Computer Use로 돌려보고, 안정화되면 전용 도구로 교체한다"는 마이그레이션 경로를 미리 설계에 넣어두면 좋다.** 초기에는 API 유무를 몰라도 빠르게 검증할 수 있고, 반복 사용 패턴이 보이면 그 흐름만 전용 도구나 스크립트로 떼어내 비용과 신뢰성을 동시에 개선할 수 있다.

## 마무리

- 독립 브라우저 에이전트 제품들이 접히고 범용 컴퓨터 제어 능력의 한 모드로 흡수되는 흐름은, "브라우저 자동화를 따로 설계하지 말고 전용 API 도구 vs 범용 컴퓨터 제어"라는 더 단순한 이분법으로 판단하라는 신호다.
- API가 있으면 무조건 전용 도구, 반복 작업이면 고정 스크립트, 비정형·일회성 작업에서만 Computer Use를 꺼내는 순서로 판단한다.
- Computer Use를 쓰기로 했다면 기능 추가가 아니라 권한 모델 재설계로 보고, 샌드박스 격리와 민감 동작 승인 게이트를 먼저 구축한다.
