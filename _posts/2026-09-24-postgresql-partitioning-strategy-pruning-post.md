## 왜 지금 파티셔닝을 다시 봐야 하는가

인덱스를 아무리 잘 설계해도 테이블 자체가 수억 건 규모로 커지면 한계가 온다. 인덱스 크기 자체가 메모리에 다 올라가지 않을 만큼 커지고, VACUUM이나 백업 같은 유지보수 작업의 소요 시간도 테이블 크기에 비례해 길어진다. 파티셔닝은 하나의 논리적 테이블을 여러 개의 물리적 하위 테이블(파티션)로 나눠, 쿼리와 유지보수 작업이 필요한 파티션만 건드리도록 만드는 접근이다. 문제는 파티션 키를 어떤 기준으로 나누느냐(Range, List, Hash)에 따라 실제로 얻는 이득이 크게 달라지고, 파티셔닝을 도입했는데도 쿼리 조건이 파티션 키와 맞지 않으면 결국 모든 파티션을 다 스캔하는 최악의 상황에 빠질 수 있다는 점이다.

## 핵심 개념 1 — Range, List, Hash 파티션의 적합한 상황

Range 파티션은 날짜나 숫자 범위로 데이터를 나눈다. 로그, 주문 이력처럼 시간에 따라 계속 쌓이는 데이터에 가장 흔히 쓰이며, 오래된 파티션을 통째로 드롭하는 방식으로 데이터 보관 정책을 구현하기도 쉽다. List 파티션은 특정 값의 목록(국가 코드, 상태값 등)으로 나누며, 값의 종류가 제한적이고 그 값별로 쿼리 패턴이 뚜렷하게 갈릴 때 유용하다. Hash 파티션은 값에 해시 함수를 적용해 균등하게 분산시키는 방식으로, 자연스러운 범위나 카테고리 기준이 없지만 쓰기 부하를 여러 파티션에 고르게 분산시키고 싶을 때 선택한다.

## 핵심 개념 2 — 파티션 프루닝이 실제로 동작하는 조건

파티셔닝의 성능 이득은 대부분 파티션 프루닝(partition pruning)에서 나온다. 쿼리 플래너가 WHERE 절 조건만으로 "이 조건을 만족하는 행은 특정 파티션들에만 있을 수 있다"고 판단하면, 나머지 파티션은 아예 실행 계획에서 제외해버린다. 문제는 이 프루닝이 조건절이 파티션 키를 직접적이고 명시적으로 참조할 때만 확실하게 동작한다는 점이다. 파티션 키에 함수를 씌우거나(예: `DATE(created_at) = '2026-01-01'`), 파티션 키가 아닌 다른 컬럼으로만 조건을 걸면 플래너가 프루닝 가능 여부를 판단하지 못해 모든 파티션을 스캔하는 계획을 세울 수 있다. 파티션 키를 조인 조건에만 쓰고 WHERE 절에는 명시하지 않는 경우에도 프루닝이 기대만큼 동작하지 않을 수 있다.

| 파티션 방식 | 적합한 데이터 | 프루닝이 잘 되는 조건 |
|---|---|---|
| Range | 시계열 데이터(로그, 주문) | 날짜/숫자 컬럼에 대한 범위 조건 |
| List | 값 종류가 제한적인 데이터 | 해당 컬럼에 대한 등치(=) 또는 IN 조건 |
| Hash | 균등 분산이 필요한 쓰기 부하 | 해당 컬럼에 대한 등치(=) 조건 (범위 조건은 프루닝 안 됨) |

## 예제 — Range 파티션 생성과 프루닝 확인

```sql
CREATE TABLE orders (
    id BIGSERIAL,
    created_at TIMESTAMPTZ NOT NULL,
    customer_id BIGINT,
    total NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- 프루닝이 되는 경우: created_at을 직접 조건에 사용
EXPLAIN SELECT * FROM orders WHERE created_at >= '2026-02-10';
-- 실행계획에 orders_2026_02만 등장 (orders_2026_01은 제외됨)

-- 프루닝이 안 되는 경우: 함수로 감싸서 조건을 걸면 플래너가 판단 못 함
EXPLAIN SELECT * FROM orders WHERE DATE_TRUNC('month', created_at) = '2026-02-01';
-- 모든 파티션이 스캔 대상에 포함될 수 있음
```

## 실무 포인트

- **애플리케이션의 실제 쿼리가 파티션 키를 직접 조건절에 사용하는지 먼저 확인하라.** 파티션을 도입해도 애플리케이션 코드가 파티션 키 컬럼에 함수를 씌우거나 다른 컬럼으로만 필터링한다면 프루닝 이득을 전혀 얻지 못한다.
- **파티션 키는 유니크 제약이나 프라이머리 키에도 포함돼야 한다는 PostgreSQL의 제약을 미리 파악하라.** 기존 스키마에 파티셔닝을 나중에 도입할 때 이 제약 때문에 프라이머리 키 구조를 함께 변경해야 하는 경우가 많다.
- **파티션 개수가 지나치게 많아지지 않도록 관리하라.** 파티션이 수백~수천 개로 늘어나면 쿼리 플래너 자체의 계획 수립 시간이 늘어나는 역효과가 날 수 있으므로, 파티션 단위(일별/월별/연도별)를 데이터 증가 속도에 맞게 조정해야 한다.

## 마무리 요약

- 파티셔닝은 테이블을 물리적으로 나눠 쿼리와 유지보수가 필요한 부분만 처리하게 하며, Range·List·Hash는 각각 시계열·범주형·균등분산이라는 서로 다른 상황에 맞는다.
- 실질적인 성능 이득은 파티션 프루닝에서 나오며, 조건절이 파티션 키를 직접적으로 참조해야만 플래너가 불필요한 파티션을 실행 계획에서 제외할 수 있다.
- 파티션 키에 함수를 씌우거나 다른 컬럼으로만 필터링하면 프루닝이 동작하지 않아 파티셔닝의 이점을 얻지 못하므로, 도입 전 실제 쿼리 패턴 검증이 필수다.
