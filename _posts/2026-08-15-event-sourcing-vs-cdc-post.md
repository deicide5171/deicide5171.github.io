## 왜 지금 이 비교가 필요한가

마이크로서비스 사이에 데이터를 동기화하거나, 캐시를 최신 상태로 유지하거나, 검색 색인을 실시간으로 갱신해야 하는 요구는 서비스 규모가 커질수록 흔해진다. 이때 "다른 시스템에 변경 사항을 어떻게 전달할 것인가"라는 질문에 대한 답으로 흔히 두 가지가 거론된다. 하나는 애플리케이션이 상태 변화 자체를 이벤트로 설계해 저장하는 이벤트 소싱(Event Sourcing)이고, 다른 하나는 기존 데이터베이스의 변경 로그(binlog, WAL 등)를 캡처해 외부로 흘려보내는 CDC(Change Data Capture)다.

두 패턴은 겉보기에 비슷해 보인다. 둘 다 "변경 사항을 이벤트 스트림으로 만든다"는 점에서 그렇다. 하지만 이벤트가 어디서 발생하는지, 무엇을 진실의 원천(source of truth)으로 삼는지가 근본적으로 다르다. 이 차이를 이해하지 못하고 도입하면 시스템 복잡도만 늘고 얻는 이점은 없는 경우가 많다.

이 글에서는 두 패턴의 개념적 차이, 각각의 장단점, 그리고 Debezium 같은 실무 도구를 어떻게 적용할지 정리한다.

## 핵심 개념 비교

이벤트 소싱은 애플리케이션 계층에서 "무엇이 일어났는가"를 명시적인 이벤트(예: `OrderPlaced`, `PaymentConfirmed`)로 모델링하고, 이 이벤트들의 누적이 곧 상태다. 현재 상태는 이벤트를 순서대로 재생(replay)해서 얻는 파생 값이며, DB 테이블의 현재 행은 부차적인 캐시(read model)에 가깝다.

CDC는 반대 방향으로 접근한다. 애플리케이션은 평범하게 RDBMS에 CRUD를 수행하고, 진실의 원천은 여전히 테이블이다. CDC 도구는 DB 내부의 트랜잭션 로그를 읽어 "어떤 행이 어떻게 바뀌었는지"를 이벤트로 변환해 다른 시스템에 전파한다. 애플리케이션 코드는 CDC의 존재를 몰라도 동작한다.

| 구분 | 이벤트 소싱 | CDC |
|---|---|---|
| 이벤트의 출처 | 애플리케이션이 직접 발행 | DB 트랜잭션 로그에서 파생 |
| 진실의 원천 | 이벤트 스트림 자체 | 기존 테이블(현재 상태) |
| 이벤트의 의미 | 도메인 의미가 담긴 비즈니스 이벤트 | 로우 단위 변경(insert/update/delete) |
| 도입 난이도 | 높음 (설계·마이그레이션 전면 변경) | 상대적으로 낮음 (기존 DB에 얹음) |
| 감사 이력 | 자연스럽게 완전한 이력 확보 | 별도 설계 없이는 이력 유실 가능 |
| 대표 용도 | 도메인 이벤트 기반 마이크로서비스 | 레거시 DB 연동, 데이터 파이프라인 |

## 장단점과 선택 기준

이벤트 소싱은 도메인 이벤트가 곧 비즈니스 언어이기 때문에, "왜 이 상태가 되었는가"를 코드 수준에서 설명할 수 있다는 강점이 있다. 감사 로그, 시점 조회(temporal query), 이벤트 재생을 통한 버그 재현 등이 자연스럽다. 반면 기존 CRUD 기반 시스템을 이벤트 소싱으로 전환하는 비용은 상당하며, 이벤트 스키마 진화(버전 관리), 스냅샷 전략, 최종 일관성에 대한 팀 전체의 이해가 필요하다.

CDC는 기존 시스템을 건드리지 않고도 실시간에 가까운 데이터 흐름을 만들 수 있다는 점에서 도입 장벽이 낮다. 레거시 DB를 그대로 두면서 검색 색인 갱신, 캐시 무효화, 데이터 웨어하우스 적재 같은 작업을 붙일 수 있다. 다만 캡처되는 이벤트가 "로우가 바뀌었다"는 사실만 담고 있어 왜 바뀌었는지 비즈니스 맥락은 별도로 복원해야 하는 경우가 많고, 스키마 변경에 CDC 파이프라인이 취약할 수 있다.

실무에서는 새 도메인을 처음부터 이벤트 중심으로 설계할 여유와 필요가 있는지, 아니면 기존 DB를 그대로 두고 변경 사항만 다른 시스템에 흘려보내면 되는지로 판단하는 경우가 많다. 두 패턴을 함께 쓰는 조합도 흔하다. 이벤트 소싱으로 도메인 서비스를 만들되, 그 서비스의 read model을 다시 CDC로 다른 시스템에 전파하는 식이다.

## 코드/설정 예제

이벤트 소싱에서 저장되는 도메인 이벤트 예시다.

```json
{
  "eventId": "b3f1c9a2-1234-4a1a-9c1e-2b6a7f9d0001",
  "eventType": "OrderPlaced",
  "aggregateId": "order-98213",
  "version": 1,
  "occurredAt": "2026-08-15T09:12:03Z",
  "payload": {
    "customerId": "cust-4471",
    "items": [
      { "sku": "A-1002", "qty": 2 }
    ],
    "totalAmount": 45800
  }
}
```

Debezium을 이용해 MySQL의 변경을 캡처하는 커넥터 설정 예시다.

```json
{
  "name": "orders-cdc-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "mysql-primary",
    "database.port": "3306",
    "database.user": "cdc_user",
    "database.server.id": "184054",
    "topic.prefix": "shop",
    "database.include.list": "shop_db",
    "table.include.list": "shop_db.orders",
    "schema.history.internal.kafka.topic": "schema-changes.shop"
  }
}
```

## 실무 포인트와 주의사항

이벤트 소싱을 도입한다면 이벤트 스키마의 하위 호환성 정책을 처음부터 정해야 한다. 필드 추가는 대체로 안전하지만 의미 변경이나 필드 삭제는 컨슈머 전체에 영향을 준다. 또한 이벤트가 오래 쌓이면 재생 비용이 커지므로 주기적인 스냅샷 전략을 함께 설계하는 편이 안전하다.

CDC를 도입한다면 DB 스키마 변경(컬럼 추가/삭제, 타입 변경)이 다운스트림 컨슈머를 깨뜨리지 않도록 스키마 레지스트리나 호환성 검사를 함께 두는 것이 좋다. 또한 초기 스냅샷(전체 테이블 적재) 단계와 이후 증분 캡처 단계를 구분해서 설계해야 하며, 트랜잭션 로그 보존 기간이 짧으면 컨슈머가 뒤처졌을 때 데이터 유실 위험이 있으니 로그 보존 정책을 점검할 필요가 있다.

두 패턴 모두 "최종 일관성"을 전제로 한다는 공통점이 있다. 다운스트림 시스템이 이벤트를 소비하는 데는 지연이 따르므로, 강한 일관성이 필수인 경로(예: 결제 승인 직후 즉시 잔액 확인)에는 그대로 적용하기보다 별도의 동기 경로를 함께 고려하는 편이 안전하다.

## 3줄 요약

- 이벤트 소싱은 애플리케이션이 도메인 이벤트를 1급 시민으로 설계해 진실의 원천으로 삼는 방식이고, CDC는 기존 DB 로그를 캡처해 변경 사항을 외부로 전파하는 방식이다.
- 이벤트 소싱은 완전한 이력과 도메인 표현력을 얻는 대신 설계·운영 비용이 크고, CDC는 기존 시스템을 유지한 채 도입할 수 있지만 비즈니스 맥락 복원과 스키마 관리에 신경 써야 한다.
- 새 도메인을 이벤트 중심으로 설계할 여지가 있다면 이벤트 소싱을, 기존 DB를 그대로 두고 변경 전파만 필요하다면 Debezium 같은 CDC 도구를 우선 검토하는 것이 실용적이다.
