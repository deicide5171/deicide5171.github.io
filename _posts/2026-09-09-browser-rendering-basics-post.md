## HTML 텍스트가 어떻게 화면이 되나

브라우저는 서버에서 받은 HTML·CSS라는 "텍스트"를 사람이 보는 화면으로 바꾼다. 이 변환 과정을 알면 왜 어떤 코드가 화면을 느리게 만드는지 이해할 수 있다. 브라우저 렌더링은 크게 **파싱 → 트리 구성 → 배치 → 그리기**의 단계를 거친다.

## 렌더링 단계

| 단계 | 하는 일 |
|---|---|
| 파싱 | HTML→DOM, CSS→CSSOM 트리로 변환 |
| 렌더 트리 | DOM+CSSOM 합쳐 "그릴 것"만 모음 |
| 레이아웃(리플로우) | 각 요소의 위치·크기 계산 |
| 페인트 | 픽셀로 색을 칠함 |

## 흐름

```text
HTML 텍스트 -> DOM 트리
CSS 텍스트  -> CSSOM 트리
         \  /
       렌더 트리 (화면에 보일 요소만)
          |
      레이아웃 (어디에 얼마 크기로?)
          |
      페인트 (실제 픽셀로 칠하기)
          |
        화면 표시
```

## 실무 포인트

- **레이아웃(리플로우)이 가장 비싸다.** 요소의 크기·위치를 바꾸면 브라우저가 배치를 다시 계산한다(리플로우). 반복문 안에서 스타일을 계속 바꾸면 리플로우가 여러 번 일어나 느려진다. 변경을 모아 한 번에 적용하는 것이 좋다.
- **색만 바뀌면 페인트만, 위치가 바뀌면 리플로우.** 배경색 변경은 페인트만 일어나지만, `width`·`top` 등은 리플로우까지 유발한다. 애니메이션은 리플로우를 안 부르는 `transform`·`opacity`로 하는 것이 부드럽다.
- **CSS와 JS는 렌더링을 막을 수 있다.** `<head>`의 큰 CSS나 동기 스크립트는 화면 표시를 지연시킨다. JS는 `defer`/`async`로, CSS는 꼭 필요한 것만 먼저 불러 첫 화면을 빠르게 한다.

## 마무리 요약

- 브라우저는 HTML→DOM, CSS→CSSOM으로 파싱하고 합쳐 렌더 트리를 만든 뒤, 레이아웃·페인트로 화면을 그린다.
- 레이아웃(리플로우)이 가장 비싸므로 스타일 변경을 모아 적용하는 것이 좋다.
- 애니메이션은 `transform`·`opacity`로, CSS·JS는 렌더링을 막지 않게 로딩 방식을 조절한다.
