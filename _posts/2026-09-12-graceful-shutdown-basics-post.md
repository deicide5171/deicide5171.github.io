## 배포할 때마다 일부 요청이 실패한다

새 버전을 배포하려고 서버를 재시작하면, 그 순간 처리 중이던 요청들이 갑자기 끊겨 사용자가 에러를 본다. **그레이스풀 셧다운(graceful shutdown)**은 **종료 신호를 받으면 새 요청은 그만 받되, 처리 중인 요청은 끝까지 마친 뒤 서버를 끄는** 것이다. "우아한 종료"라 부른다.

## 그냥 종료 vs 우아한 종료

| 구분 | 강제 종료 | 그레이스풀 셧다운 |
|---|---|---|
| 처리 중 요청 | 끊김(에러) | 끝까지 마침 |
| 새 요청 | - | 안 받음 |
| 사용자 영향 | 오류 발생 | 거의 없음 |

## 종료 흐름

```text
1. 종료 신호(SIGTERM) 수신
2. 로드밸런서에서 이 서버를 트래픽 대상에서 제외
3. 새 요청은 거부, 처리 중인 요청은 계속 완료
4. 모든 요청이 끝나면(또는 타임아웃) 프로세스 종료
```

## 실무 포인트

- **종료 신호를 처리해야 한다.** OS는 종료 시 `SIGTERM` 신호를 보낸다. 앱이 이 신호를 받아 "정리 후 종료" 로직을 실행하게 해야 한다. 무시하면 강제 종료(SIGKILL)로 끊긴다.
- **드레이닝 시간을 준다.** 쿠버네티스 등은 종료 전 유예 시간(termination grace period)을 준다. 이 시간 안에 진행 중 요청을 마쳐야 하므로, 요청 처리 시간보다 넉넉히 잡는다.
- **정리 작업도 함께.** DB 커넥션 반납, 진행 중 작업 저장, 큐 소비 중단 등도 종료 시 해줘야 한다. 갑자기 끊기면 커넥션 누수나 중복 처리가 생길 수 있다.

## 마무리 요약

- 그레이스풀 셧다운은 종료 시 새 요청은 막고 처리 중인 요청은 마친 뒤 서버를 끄는 것이다.
- 배포·재시작 때 요청이 끊겨 발생하는 오류를 막아 무중단에 가까운 배포를 돕는다.
- `SIGTERM` 신호 처리, 유예 시간 설정, 커넥션·작업 정리를 함께 구현해야 한다.
