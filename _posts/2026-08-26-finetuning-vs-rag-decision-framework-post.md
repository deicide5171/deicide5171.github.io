"우리 도메인 데이터로 파인튜닝해야 할까요, RAG로 충분할까요?"라는 질문은 실무에서 가장 자주 받는 질문 중 하나지만, 정답이 하나로 정해진 질문이 아니다. 두 접근은 애초에 풀려는 문제가 다르다. 파인튜닝은 모델의 **행동 방식**(말투, 형식, 특정 도메인의 추론 패턴)을 바꾸는 것이고, RAG는 모델이 **모르는 사실**을 답변 시점에 검색해 넣어주는 것이다. 이 차이를 이해하지 못한 채 "더 고급스러워 보이는" 쪽을 고르면, 파인튜닝으로 최신 정책 문서를 학습시키려다 매번 재학습에 시달리거나, RAG로 특정 말투를 강제하려다 프롬프트가 산더미처럼 불어나는 결과를 보게 된다.

이 글에서는 "파인튜닝이 나은가 RAG가 나은가"를 가르는 실제 판단 기준 다섯 가지를 정리하고, 실무에서 두 방법을 함께 쓰는 하이브리드 구성이 왜 흔한지 살펴본다.

## 핵심 개념 1: 다섯 가지 판단 질문

| 질문 | 파인튜닝 쪽으로 기우는 답 | RAG 쪽으로 기우는 답 |
|---|---|---|
| 1. 정보가 얼마나 자주 바뀌는가 | 거의 안 바뀜(문체, 분류 규칙) | 매일·매주 바뀜(가격, 재고, 뉴스) |
| 2. 근거를 답변에 인용해야 하는가 | 불필요 | 필수(출처 표기, 감사 대응) |
| 3. 학습 데이터 확보가 가능한가 | 충분한 양질 예시 확보 가능 | 예시보다 원문 문서가 많음 |
| 4. 환각을 얼마나 허용할 수 있는가 | 형식·톤 실수는 허용 가능 | 사실 오류는 허용 불가 |
| 5. 추론 비용·지연 민감도 | 짧은 프롬프트로 비용 절감 필요 | 검색 지연을 감수 가능 |

이 다섯 질문에 대한 답이 한쪽으로 몰리는 경우는 오히려 드물다. "매주 바뀌는 최신 규정을 특정 회사 말투로 요약해야 한다"처럼 질문 1과 2가 서로 다른 방향을 가리키는 경우가 실무에서는 훨씬 흔하다. 이럴 때가 바로 두 방법을 함께 쓰는 하이브리드 구성이 필요한 지점이다.

## 핵심 개념 2: 하이브리드가 기본값이 되는 이유

실무 시스템의 상당수는 결국 "RAG로 최신 사실을 가져오고, 그 위에 파인튜닝(또는 가벼운 LoRA 어댑터)으로 응답 형식·톤·도메인 특화 추론 패턴을 얹는" 구조로 수렴한다. RAG만으로는 모델이 검색된 문서를 도메인에 맞는 형식으로 정리하는 능력이 부족할 수 있고, 파인튜닝만으로는 학습 시점 이후의 사실을 알 방법이 없기 때문이다.

이때 파인튜닝은 전체 파라미터를 다시 학습시키는 방식보다 LoRA/QLoRA 같은 경량 어댑터로 하는 경우가 많다. 어댑터는 베이스 모델은 그대로 두고 소수의 파라미터만 학습하므로, "말투와 응답 형식만 바꾸고 싶다"는 요구에 특히 잘 맞고, 재학습 비용도 훨씬 낮다.

## 예제: 판단 프레임워크를 코드로 표현하면

```python
def choose_approach(update_frequency, needs_citation, has_training_examples,
                     hallucination_tolerance, latency_budget_ms):
    score_finetune = 0
    score_rag = 0

    if update_frequency == "rare":
        score_finetune += 1
    else:
        score_rag += 1

    if needs_citation:
        score_rag += 2  # 근거 인용 요구는 RAG에 강하게 기운다
    else:
        score_finetune += 1

    if has_training_examples:
        score_finetune += 1
    else:
        score_rag += 1

    if hallucination_tolerance == "low":
        score_rag += 2  # 사실 오류를 허용 못하면 검색 근거가 필수
    else:
        score_finetune += 1

    if latency_budget_ms < 500:
        score_finetune += 1  # 검색 단계가 지연을 늘리므로
    else:
        score_rag += 1

    if score_finetune > score_rag + 1:
        return "finetune"
    elif score_rag > score_finetune + 1:
        return "rag"
    else:
        return "hybrid"  # 점수가 팽팽하면 하이브리드가 안전한 기본값
```

실제 의사결정을 점수 몇 개로 완전히 자동화할 수는 없지만, 이런 명시적 체크리스트는 "일단 파인튜닝부터 해보자"는 성급한 결정을 막는 데 효과적이다.

## 실무 포인트

- **최신성 요구를 과소평가하지 않는다**: 파인튜닝된 모델에 "어제 발표된 정책"을 물어보면 필연적으로 실패한다. 재학습 주기가 데이터 변경 주기를 못 따라가는 도메인이라면 RAG가 사실상 유일한 선택지다.
- **RAG의 근거 없이 "환각을 줄이려고" 파인튜닝하지 않는다**: 파인튜닝은 모델이 모르는 사실을 알게 해주는 도구가 아니라 답변 스타일을 바꾸는 도구에 가깝다. 사실 정확도 문제를 파인튜닝으로 해결하려 하면 오히려 잘못된 사실을 더 자신감 있게 말하는 부작용이 생길 수 있다.
- **하이브리드 도입 시 책임 분리를 명확히 한다**: RAG 파이프라인(검색·재순위화)과 파인튜닝 어댑터를 같은 팀이 동시에 튜닝하면 어느 쪽이 응답 품질에 기여했는지 구분하기 어렵다. 검색 품질과 생성 스타일을 독립적으로 평가할 수 있는 평가 셋을 각각 준비해야 한다.

## 3줄 요약

- 파인튜닝은 모델의 행동 방식(말투·형식)을, RAG는 모델이 모르는 최신 사실을 다루는 것으로 애초에 풀려는 문제가 다르다.
- 최신성·근거 인용 요구·환각 허용도·데이터 확보 가능성·지연 민감도 다섯 질문으로 방향을 가늠할 수 있다.
- 다섯 질문의 답이 갈리는 경우가 흔하므로, RAG로 사실을 가져오고 LoRA 등 경량 파인튜닝으로 형식을 다듬는 하이브리드가 실무 기본값이 되고 있다.
