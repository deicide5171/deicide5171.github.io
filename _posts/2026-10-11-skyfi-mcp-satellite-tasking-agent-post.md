## 왜 지금 이 판단이 불거지는가

"경쟁사 매장 앞 주차장이 얼마나 찼는지 매주 확인해서 리포트에 넣어주세요." 예전이었다면 이 요구는 위성영상 업체 영업팀에 견적을 요청하고, 받은 GeoTIFF를 분석가가 QGIS로 열어보는 며칠짜리 작업이었다. 2026년 7월 22일 SkyFi가 공개한 **MCP 서버**는 이 과정을 에이전트 도구 호출 하나로 압축한다. Claude, ChatGPT, Grok 같은 MCP 호환 에이전트가 300여 개 위성·항공 영상 소스의 아카이브를 자연어로 검색하고, 적합한 이미지가 없으면 새 촬영(tasking)을 의뢰하는 것까지 같은 대화 안에서 처리할 수 있게 됐다.

문제는 이게 단순한 조회 도구가 아니라는 점이다. SkyFi 공식 문서는 일부 작업이 **실제로 과금되는 주문**이며 연결된 결제 수단에서 비용이 빠져나간다고 명시한다. 지도에서 마커 하나 찍는 것과 달리, 에이전트가 판단을 잘못하면 실제 돈이 나간다. "위성사진 보여주세요"를 "에이전트가 알아서 주문까지 하게 해주세요"로 확장하려면, 조회와 지출을 명확히 분리하는 설계가 먼저 필요하다.

## 요구사항을 기술 문제로 번역하기

"경쟁사 매장 혼잡도를 확인해주세요"라는 한 문장은 사실 세 단계 판단이 숨어 있다. 첫째, **이미 존재하는 이미지로 충분한가**(아카이브 검색)와 **새로 촬영해야 하는가**(tasking)의 판별. 둘째, 새로 촬영해야 한다면 **그 지역·시점에 실제로 위성 패스가 가능한지**(feasibility check) 확인. 셋째, 가능하다면 **비용과 일정을 사용자(또는 상위 승인자)에게 보여주고 실행 여부를 확정**하는 승인 단계. 이 셋을 하나의 도구 호출로 뭉뚱그리면, 에이전트가 "최신 이미지가 없으니 촬영하겠습니다"라고 판단한 순간 사용자 동의 없이 수백 달러가 빠져나가는 상황이 생긴다. 그래서 실제 작업은 "위성사진 API 연결해주세요"가 아니라, **읽기(검색)와 쓰기(주문)를 분리하고, 쓰기 앞에 사람 또는 정책이 개입하는 승인 게이트를 어디에 둘지** 설계하는 문제로 번역된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-11-skyfi-mcp-satellite-tasking-agent-1.svg" alt="에이전트가 SkyFi MCP 서버를 통해 아카이브 검색과 feasibility 체크를 거쳐, 적합한 이미지가 없을 때만 승인 게이트를 지나 신규 촬영 주문을 넣고 위성 운영사가 촬영한 결과가 분석 파이프라인으로 들어오는 구조도" style="width:100%;">

이 구조에서 SkyFi MCP 서버는 **에이전트의 도구 호출 레이어와 실제 위성 운영사의 촬영 스케줄링·결제 시스템 사이의 중개 계층**이다. 앞단에는 비즈니스 요구사항("매장 혼잡도 확인")을 자연어로 받는 에이전트 워크플로우가 있고, 뒷단에는 실제 위성이 궤도를 돌며 패스 가능 여부가 물리적으로 제약되는 운영사 시스템이 있다. 아카이브 검색은 이 뒷단을 건드리지 않고 이미 찍힌 이미지를 조회하는 읽기 경로지만, tasking은 실제 촬영 자원을 예약하고 결제를 발생시키는 쓰기 경로다. 이 둘을 같은 경로로 섞으면, 에이전트가 "최신 정보가 필요하다"고 과도하게 판단해 불필요한 촬영을 반복 주문하는 비용 폭주가 일어날 수 있다.

## 선택의 트레이드오프

| 경로 | 비용 | 소요 시간 | 신선도 | 적합한 상황 |
|---|---|---|---|---|
| 아카이브 검색 | 상대적으로 저렴(예: 건당 약 100달러대) | 즉시~24시간 내 | 기존 촬영 시점에 고정 | 최근 수일~수주 내 이미지로 충분한 모니터링 |
| 신규 촬영(tasking) | 더 높음(예: 건당 약 250달러 이상) | 3~14일(러시 옵션 시 단축) | 주문 시점 기준 최신 | 지난 24~72시간 내 변화를 반드시 확인해야 하는 경우 |
| 정기 구독형 모니터링 | 건당 단가는 낮아지나 고정 비용 발생 | 재방문 주기에 종속 | 주기적으로 갱신 | 같은 지역을 반복 확인하는 운영성 모니터링 |

아카이브는 가장 싸고 빠르지만 "지금 이 순간"을 보장하지 못한다. tasking은 신선도를 보장하는 대신 위성의 실제 궤도 재방문 주기와 날씨(구름)에 좌우되는 3~14일의 불확실한 리드타임과 더 높은 비용을 감수해야 한다. 같은 지역을 매일·매주 반복 확인해야 하는 요구라면, 매번 개별 tasking을 호출하는 대신 반복 촬영 비용을 미리 계산한 구독형 모니터링 쪽이 총비용 면에서 유리한 경우가 많다. "경쟁사 매장을 매주 확인해주세요" 같은 요구는 십중팔구 아카이브로 충분하고, "오늘 새벽 화재 피해 범위를 당장 확인해주세요" 같은 요구만 tasking이 정당화된다.

## 실제 프로젝트 진행 순서

1. **아카이브 검색만으로 요구사항이 충족되는지 먼저 확인한다.** 대부분의 모니터링 요구는 최신성에 며칠의 여유가 있고, 가장 싸고 빠른 경로부터 시도해야 한다.
2. **feasibility check를 독립된 단계로 분리한다.** 실제 과금 전에 해당 좌표·시점에 위성 패스가 가능한지, 구름 확률이 어느 정도인지부터 확인하는 호출을 먼저 넣는다.
3. **tasking 호출 앞에 금액 상한과 승인 워크플로우를 강제한다.** 에이전트가 스스로 "촬영하겠습니다"라고 결정해 결제를 트리거하지 못하도록, 일정 금액 이상은 사람의 명시적 승인을 거치게 설계한다.
4. **반복 모니터링 요구는 개별 tasking 호출로 쌓지 말고 주기를 먼저 설계한다.** 요구 빈도와 위성 재방문 주기를 비교해, 구독형 또는 배치형 요청으로 묶을 수 있는지 검토한다.
5. **수신한 GeoTIFF를 내부 분석 파이프라인에 연결하는 방식을 정한다.** PostGIS에 적재해 공간 질의로 후속 분석할지, 객체탐지 모델에 바로 흘려보낼지는 별도 설계가 필요하다.

## 코드 예시 — 아카이브 검색과 tasking 호출 분리

```json
{
  "tool": "search_archive",
  "args": {
    "bbox": [127.10, 37.50, 127.11, 37.51],
    "max_age_days": 14,
    "min_resolution_m": 1.0
  }
}
```

```json
{
  "tool": "check_feasibility",
  "args": { "bbox": [127.10, 37.50, 127.11, 37.51], "window_days": 3 }
}
```

```json
{
  "tool": "create_tasking_order",
  "args": { "bbox": [127.10, 37.50, 127.11, 37.51], "max_price_usd": 300 },
  "requires_human_approval": true
}
```

## 실무 포인트

**조회와 지출을 같은 권한으로 묶지 않는다.** search·feasibility 도구는 읽기 전용으로 자유롭게 호출하게 두되, 실제 주문 도구는 별도 승인 플로우를 거치게 구분한다.

**금액 상한을 도구 정의 자체에 박아둔다.** 프롬프트로 "비싼 주문은 하지 마세요"라고 지시하는 것보다, 도구 호출 스키마나 게이트웨이 레벨에서 `max_price_usd` 같은 하드 리밋을 강제하는 편이 훨씬 안전하다.

**재방문 주기를 먼저 계산한다.** 필요한 지역의 위성 재방문 주기가 요구 빈도보다 길면, 아무리 자주 요청해도 더 신선한 이미지를 받을 수 없다. 이 계산 없이 tasking을 반복하면 비용만 늘어난다.

## 마무리

- "위성사진으로 확인해주세요"는 아카이브 검색(읽기)과 신규 촬영 주문(쓰기·과금)을 구분하고, 쓰기 앞에 승인 게이트를 두는 문제로 번역된다.
- SkyFi MCP는 이 두 경로를 에이전트 도구 호출로 열었지만, tasking은 비용·리드타임·위성 궤도 제약이 있는 실제 금전적 행동이다.
- 반복 모니터링 요구는 개별 tasking보다 재방문 주기를 먼저 계산한 구독형 접근이 총비용 면에서 유리한 경우가 많다.
