DNS는 인프라 중에서도 유독 존재감이 없는 축에 속한다. 평소에는 도메인을 치면 곧바로 페이지가 뜨니 그 뒤에서 무슨 일이 일어나는지 신경 쓸 이유가 없다. 그러다 배포 직후 새 서버로 트래픽이 안 옮겨가거나, 오타 하나로 존재하지 않는 서브도메인을 찾다가 애플리케이션이 통째로 응답 불가에 빠지는 순간, DNS는 갑자기 인프라 전체를 좌우하는 변수로 떠오른다.

문제는 DNS 장애가 보통 애매하게 나타난다는 점이다. 서버는 멀쩡히 떠 있고 방화벽도 열려 있는데 클라이언트 쪽에서는 연결 자체가 안 되거나, 어떤 사용자는 새 IP로 붙고 어떤 사용자는 여전히 옛 IP로 붙는 식의 비일관적인 증상이 흔하다. 이런 증상의 대부분은 이름을 IP로 바꾸는 해석(resolution) 단계 어딘가—스텁 리졸버의 로컬 캐시일 수도, 중간 재귀 리졸버일 수도, TTL이 걸어둔 시간일 수도 있다—에서 비롯된다. 이 글에서는 그 해석 과정이 어떤 구성 요소를 거치는지, 캐싱과 TTL이 왜 그렇게 설계됐는지, 그리고 실무에서 반복적으로 마주치는 장애 패턴 몇 가지를 정리한다.

## 핵심 개념 1: 스텁 리졸버에서 권한 네임서버까지

이름 해석에 참여하는 주체는 역할이 뚜렷이 나뉜다. 애플리케이션이 `getaddrinfo` 같은 시스템 콜을 부르면 가장 먼저 만나는 것이 OS에 내장된 **스텁 리졸버**다. 스텁 리졸버는 스스로 답을 찾지 않고, 설정된 **재귀 리졸버**(가정에서는 ISP가, 사내망에서는 내부 DNS 서버가, 혹은 8.8.8.8·1.1.1.1 같은 공용 리졸버가 이 역할을 맡는다)에게 질의를 넘긴다.

재귀 리졸버가 캐시에 답을 갖고 있지 않다면, 이때부터 실제 재귀 탐색이 시작된다. 순서는 항상 위에서 아래로 내려간다.

1. **루트 네임서버**에 질의해 해당 최상위 도메인(TLD, 예: `.com`)을 담당하는 네임서버 주소를 받는다.
2. **TLD 네임서버**에 다시 질의해 해당 도메인을 관리하는 **권한(authoritative) 네임서버** 주소를 받는다.
3. **권한 네임서버**에 최종 질의를 보내 실제 레코드(A, AAAA, CNAME 등) 값을 받는다.

재귀 리졸버는 이 세 단계를 대신 수행한 뒤 최종 답만 스텁 리졸버에 돌려준다. 스텁 리졸버 입장에서는 이 복잡한 과정이 단 한 번의 요청·응답으로 보인다.

## 핵심 개념 2: 캐싱과 TTL

매 질의마다 루트부터 다시 훑는다면 인터넷 전체가 감당할 수 없는 트래픽이 루트·TLD 네임서버로 몰릴 것이다. 이를 막는 장치가 **캐싱**이다. 각 DNS 레코드에는 **TTL(Time To Live)**이 초 단위로 붙어 있고, 재귀 리졸버는 응답을 이 TTL만큼 캐시에 보관한 뒤 재사용한다. TTL이 만료되기 전까지는 같은 질의가 들어와도 권한 네임서버까지 다시 갈 필요가 없다.

캐싱은 여러 계층에서 동시에 일어난다는 점이 중요하다. OS 자체가 캐시를 두는 경우도 있고(운영체제·버전에 따라 동작이 다르므로 단정하기보다 확인이 필요하다), 재귀 리졸버가 캐시를 두며, 브라우저도 자체적으로 짧은 시간 동안 DNS 결과를 캐시하는 경우가 있다. 즉 레코드를 바꿔도 "누구의 어느 캐시가 언제 만료되는가"에 따라 반영 시점이 제각각일 수 있다는 뜻이다.

## 핵심 개념 3: 흔한 장애 패턴

- **DNS 전파 지연(propagation delay)**: 네임서버에서 레코드를 바꿔도, 이미 캐시에 저장된 재귀 리졸버들이 TTL 만료 전까지는 옛 값을 계속 돌려준다. "전 세계에 즉시 반영"되는 구조가 아니라, 각 캐시가 각자의 TTL 시계에 따라 순차적으로 갱신되는 구조라는 점을 이해해야 한다.
- **NXDOMAIN**: 요청한 이름 자체가 어느 권한 네임서버에도 존재하지 않을 때 반환되는 응답이다. 오타, 삭제된 서브도메인, 아직 전파되지 않은 신규 레코드 등이 흔한 원인이다. 이 응답도 캐시된다는 점을 놓치기 쉬운데, 존재하지 않는다는 사실 자체에도 TTL(보통 SOA 레코드의 negative caching TTL 값)이 붙어 한동안 같은 결과가 반복될 수 있다.
- **TTL을 너무 길게 잡아 생기는 문제**: 트래픽을 줄이려고 TTL을 길게(예: 하루 단위) 설정해두면, 정작 인프라를 옮기거나 장애 대응으로 IP를 급히 바꿔야 할 때 옛 값을 들고 있는 클라이언트가 한동안 남아 있게 된다. 반대로 TTL을 지나치게 짧게 잡으면 캐시 효과가 줄어 재귀 리졸버와 권한 네임서버 부하가 늘어난다. 계획된 마이그레이션 전에는 TTL을 미리 낮춰두고, 전환이 끝난 뒤 다시 늘리는 식의 운영이 일반적이다.

## 예제

`dig` 명령으로 재귀 리졸버가 실제로 어떤 답을 캐시하고 있는지, 남은 TTL이 얼마인지 확인할 수 있다.

```bash
$ dig example.com A

;; QUESTION SECTION:
;example.com.                  IN      A

;; ANSWER SECTION:
example.com.            287    IN      A       93.184.216.34

;; Query time: 12 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)
```

`ANSWER SECTION`의 두 번째 컬럼(`287`)이 남은 TTL(초)이다. 이 값이 원래 설정한 TTL과 비슷하게 줄어드는 중이라면 캐시가 정상적으로 동작하는 것이고, 반대로 값을 바꾼 지 한참 지났는데도 옛 IP가 계속 나온다면 어느 경로의 캐시가 아직 만료되지 않았는지를 의심해봐야 한다. `+trace` 옵션을 붙이면 루트부터 권한 네임서버까지 실제 위임 경로를 단계별로 볼 수 있다.

```bash
$ dig +trace example.com

;; global options: +cmd
.                       518400  IN      NS      a.root-servers.net.
com.                    172800  IN      NS      a.gtld-servers.net.
example.com.            172800  IN      NS      ns1.example-dns.com.
example.com.            300     IN      A       93.184.216.34
```

각 줄은 루트 → `.com` TLD → 해당 도메인의 권한 네임서버로 위임이 내려가는 과정을 그대로 보여준다.

## 실무 포인트

- 마이그레이션이나 장애 대응 전에는 대상 레코드의 TTL을 미리 낮춰서, 전환 시점에 옛 캐시가 오래 남아있지 않도록 준비해두는 편이 안전하다.
- 레코드 변경 직후 문제를 확인할 때는 로컬 캐시를 우회할 수 있는 방법(리졸버를 직접 지정해 질의하는 등)을 활용해, 지금 보는 결과가 이미 갱신된 값인지 옛 캐시인지부터 구분한다.
- NXDOMAIN이 예상 밖으로 나온다면 오타나 존재 여부를 먼저 의심하되, negative caching TTL 때문에 방금 고친 레코드가 아직 캐시에 옛 상태로 남아있을 가능성도 함께 고려한다.
- 어떤 리졸버(OS, 사내 DNS, 공용 리졸버, 브라우저)를 거치느냐에 따라 캐시 갱신 시점이 다르게 관측될 수 있으므로, 증상이 사용자마다 다르게 나타난다고 해서 곧바로 서버 문제로 단정하지 않는다.

## 3줄 요약

- 이름 해석은 스텁 리졸버 → 재귀 리졸버 → 루트 → TLD → 권한 네임서버 순으로 내려가며, 재귀 리졸버가 이 과정을 대신 수행해 최종 답만 돌려준다.
- 각 레코드에 붙은 TTL만큼 여러 계층(재귀 리졸버, OS, 브라우저)이 각자 캐시를 유지하기 때문에, 레코드를 바꿔도 반영 시점이 캐시마다 다르게 나타날 수 있다.
- DNS 전파 지연, NXDOMAIN의 negative caching, TTL을 너무 길게 잡아 생기는 지연은 모두 "캐시가 언제 어디서 만료되는가"라는 같은 원인에서 갈라져 나오는 증상이다.
