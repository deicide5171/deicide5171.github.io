## 왜 캐시 하나로 그렇게 큰 차이가 나는가

같은 데이터를 반복해서 요청하는데 매번 DB까지 가서 조회한다면, DB는 불필요한 부하를 계속 받고 응답 속도도 느려진다. **캐시(cache)**는 자주 쓰이는 데이터를 원본 저장소보다 훨씬 빠르게 접근할 수 있는 위치(메모리 등)에 미리 복사해두는 기법이다. 메모리 접근은 디스크 접근보다 수백~수천 배 빠르기 때문에, 캐시 하나로 응답 속도가 극적으로 개선되는 경우가 흔하다.

## 캐시가 있는 곳과 없는 곳의 차이

| 상황 | 캐시 없음 | 캐시 있음 |
|---|---|---|
| 인기 상품 조회 1000번 | DB 쿼리 1000번 실행 | 첫 요청만 DB, 나머지 999번은 캐시에서 응답 |
| 응답 속도 | 수십~수백 ms(디스크 I/O) | 수 ms 이하(메모리) |
| DB 부하 | 요청 수에 비례해 증가 | 캐시 적중률만큼 감소 |

## 캐시를 쓸 때 반드시 마주치는 질문

```text
1. 얼마나 오래 캐시에 둘 것인가? (TTL)
   → 너무 길면 오래된 데이터를 보여주고, 너무 짧으면 캐시 효과가 떨어진다

2. 원본 데이터가 바뀌면 캐시는 어떻게 되는가? (무효화)
   → 캐시를 지우거나(invalidate), 새 값으로 갱신해야 한다

3. 캐시에 없는 데이터를 요청하면? (캐시 미스)
   → 원본에서 가져온 뒤 캐시에 채워 넣는다(cache aside 패턴이 가장 흔하다)
```

## 코드 예제: 가장 기본적인 캐시 조회 패턴

```python
def get_user(user_id, cache, db):
    cached = cache.get(f"user:{user_id}")
    if cached is not None:
        return cached  # 캐시 적중

    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    cache.set(f"user:{user_id}", user, ttl=300)  # 5분간 캐시
    return user
```

이 패턴을 **Cache-Aside(Look-Aside)**라고 부른다. 애플리케이션이 직접 캐시를 확인하고, 없으면 원본을 조회해 캐시를 채우는 가장 널리 쓰이는 방식이다.

## 실무 포인트

- **모든 데이터를 캐싱할 필요는 없다.** 자주 조회되면서 자주 바뀌지 않는 데이터가 캐싱 효과가 가장 크다. 반대로 매번 바뀌는 데이터는 캐시 무효화 비용이 이득보다 클 수 있다.
- **TTL을 짧게 잡을수록 데이터 정합성은 좋아지지만 캐시 효과는 줄어든다.** 서비스 특성에 맞는 균형점을 찾아야 한다.
- **Redis, Memcached 같은 별도 캐시 서버를 두면 여러 애플리케이션 서버가 캐시를 공유할 수 있다.** 애플리케이션 프로세스 내부 메모리 캐시는 서버가 여러 대일 때 각자 다른 캐시를 갖게 되므로 주의해야 한다.

## 마무리 요약

- 캐시는 자주 쓰는 데이터를 빠른 저장소에 미리 복사해 응답 속도를 높이고 원본 저장소의 부하를 줄이는 기법이다.
- TTL(유효기간)과 무효화 전략을 어떻게 설계하느냐가 캐시의 성패를 가른다.
- Cache-Aside 패턴이 가장 기본이 되는 캐시 조회 방식이다.
