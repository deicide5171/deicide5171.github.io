## 도입

"매번 같은 설명을 또 해야 하는 게 너무 피곤해요. 지난번에 말한 코딩 스타일, 이번 프로젝트 배경, 자주 틀리는 부분 좀 기억해 두세요." 에이전트를 몇 주 굴려본 팀이면 반드시 받는 요구다. 단일 세션 안에서는 컨텍스트 윈도우에 다 욱여넣으면 그만이지만, 세션이 끝나고 다음 날 다시 켰을 때도 기억하려면 별도의 영속 저장소와, 그 저장소를 다음 세션의 프롬프트에 다시 꽂아 넣는 회수(retrieval) 경로가 필요하다.

문제는 이 회수 경로가 공격 표면이기도 하다는 것이다. 메모리에 쓰인 문장은 과거의 어느 시점에 — 사용자의 입력일 수도, 에이전트가 처리한 외부 문서나 이메일 내용일 수도 — 만들어졌다. 그 문장이 검증 없이 "신뢰할 수 있는 과거 맥락"으로 미래 세션에 다시 주입되면, 공격자는 굳이 지금 이 순간 프롬프트 인젝션을 성공시킬 필요가 없다. 한 번만 메모리에 악성 지시를 심어 두면 이후 모든 세션에서 조용히 반복 실행된다. 2026년 초 보안 리서치에서 이런 연쇄(메모리에 쓰기 → 이후 세션에서 자동 회수 → 지시로 재해석)가 실제로 데모됐고, 벤더들은 "에이전트가 자기 메모리를 참조하기 전에 그 메모리를 먼저 검증하는 계층"을 별도로 두기 시작했다. 지속 메모리를 켜기로 했다면, 저장 기능과 검증 게이트는 분리해서 설계해야 하는 이유다.

## 전체 시스템에서의 위치

지속 메모리는 "대화 로그를 DB에 저장"하는 일이 아니다. 아래 네 단계로 나눠 보면 위치가 분명해진다.

<img src="/assets/images/posts/2026-10-20-agent-persistent-memory-poisoning-guardrail-1.svg" alt="수집, 위험도 평가 게이트, 저장소, 회수 주입까지 이어지는 에이전트 메모리 파이프라인 구조도" style="width:100%;">

1. **수집(Extraction)** — 세션 종료 시점이나 대화 중간에 "기억할 만한 사실"을 모델이 스스로 요약해 후보로 뽑는다.
2. **위험도 평가 게이트** — 후보 문장이 어디서 왔는지(사용자 직접 발화인지, 외부 문서·이메일에서 모델이 추출한 것인지), 민감 정보를 담고 있는지, 기존 메모리와 충돌하는지를 점수화한다.
3. **저장소** — 통과한 것만 벡터 스토어나 구조화 DB에 출처(provenance) 메타데이터와 함께 저장한다.
4. **회수·주입** — 다음 세션 시작 시 관련 메모리를 꺼내 시스템 프롬프트나 컨텍스트 앞단에 삽입한다. 이 지점이 바로 "과거의 텍스트가 오늘의 지시가 되는" 순간이다.

이 네 단계 중 2번 게이트가 없는 구현이 가장 흔한 실수다. 수집과 저장을 바로 연결해 버리면, 에이전트가 처리한 아무 외부 텍스트나 "기억해야 할 사실"로 둔갑할 수 있다.

## 선택의 트레이드오프

| 설계 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 메모리 없음 (세션 스코프만) | 공격 표면 없음, 구현 단순 | 매 세션 재설명 필요, 사용자 피로 누적 | 민감 데이터 다루는 1회성 작업 도구 |
| 무검증 자동 저장 | 구현 빠름, 즉시 편의 제공 | 포이즈닝·개인정보 누적 위험 그대로 노출 | 금지 — 프로토타입 단계에서도 지양 |
| 사용자 확인 후 저장 | 명시적 동의, 투명성 높음 | 매번 확인 요청이 쌓이면 역시 피로 발생 | 개인용 어시스턴트, 저빈도 저장 |
| 위험도 점수 게이트 + 출처 메타데이터 | 자동화 유지하면서 위험 격리, 사후 감사 가능 | 게이트 자체 구현·튜닝 비용 | 팀·조직 단위 에이전트, 외부 입력을 다루는 에이전트 |

핵심 판단 기준은 "이 에이전트가 신뢰 경계 밖의 텍스트(이메일, 웹 페이지, 타사 문서)를 처리하는가"다. 처리하지 않는 순수 개인 비서형이면 사용자 확인 방식으로 충분하다. 외부 입력을 일상적으로 다루는 업무 에이전트라면 점수 게이트 없이는 메모리 기능을 켜지 않는 것이 안전하다.

## 실제 프로젝트 진행 순서

1. **저장 대상부터 분류한다.** "선호(코드 스타일, 응답 톤)", "프로젝트 사실(레포 구조, 팀 컨벤션)", "민감 정보(자격 증명, PII)"로 나누고, 민감 정보는 애초에 메모리 후보에서 자동 제외하는 필터를 가장 먼저 만든다.
2. **출처 메타데이터 스키마를 정한다.** 모든 메모리 레코드에 `source_type`(사용자 발화 / 도구 출력 / 외부 문서), `confirmed_by_user`(bool), `created_session_id`를 필수 필드로 넣는다. 이게 없으면 나중에 포이즈닝 의심 레코드를 추적할 수 없다.
3. **위험도 게이트를 프로토타입으로 먼저 돌린다.** 처음부터 완벽한 분류기를 만들 필요는 없다 — "외부 문서에서 추출됐고 민감 키워드를 포함하면 자동 격리(quarantine), 사람이 검토 후 승인"하는 간단한 규칙만으로 시작해도 무검증 저장보다 훨씬 낫다.
4. **회수 시점에 2차 방어선을 둔다.** 저장 시점 필터를 통과했더라도, 회수해서 프롬프트에 삽입하기 직전에 "이 메모리가 시스템 지시를 바꾸려는 명령형 문장인지"를 한 번 더 모델이나 규칙으로 점검한다.
5. **감사 로그를 남긴다.** 어떤 메모리가 언제 생성되고, 언제 회수되어 어떤 세션의 응답에 영향을 줬는지 추적 가능해야, 이상 행동이 발견됐을 때 원인이 된 메모리 레코드를 역추적할 수 있다.

예제(의사코드, 저장 전 위험도 게이트):

```python
def evaluate_memory_candidate(candidate):
    score = 0
    if candidate.source_type == "external_document":
        score += 40
    if contains_imperative_pattern(candidate.text):  # "~해라", "앞으로는 ~하지 마" 류
        score += 30
    if contains_sensitive_pattern(candidate.text):
        return "reject"
    if score >= 50:
        return "quarantine"  # 사람 검토 대기열
    return "approve"
```

## 실무 포인트

- 메모리 삭제·수정 UI를 반드시 사용자에게 노출한다. 게이트를 아무리 잘 만들어도 오탐은 생기고, 사용자가 직접 지울 수 있어야 신뢰를 유지한다.
- 메모리 저장소를 팀 전체가 공유하는 구조라면, 개인 선호와 조직 공통 사실을 같은 네임스페이스에 섞지 않는다. 한 사람의 잘못된 메모리가 전체 팀 에이전트의 동작을 바꾸는 사고로 번질 수 있다.
- 벡터 유사도 검색으로 회수하는 구조라면, 유사도 상위 N개를 무조건 주입하지 말고 출처 신뢰도로 한 번 더 재정렬한다.

## 마무리

- 지속 메모리는 "저장소 추가"가 아니라 "과거 텍스트가 미래 지시가 되는 새로운 입력 경로"를 여는 설계 문제다.
- 수집과 저장 사이에 출처 기반 위험도 게이트를 두지 않으면, 포이즈닝된 메모리가 세션마다 조용히 반복 실행될 수 있다.
- 분류 → 출처 메타데이터 → 게이트 프로토타입 → 회수 시점 2차 방어 → 감사 로그 순으로 점진적으로 쌓아가는 것이 가장 안전한 도입 경로다.
