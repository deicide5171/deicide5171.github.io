## 왜 지금 이 판단이 필요한가

"에이전트가 사용자 대신 메일도 보내고, GitHub PR도 올리고, Notion 문서도 정리하게 해주세요." 연동 서비스를 하나씩 늘려가는 팀이라면 피하기 어려운 요구다. 가장 빠른 구현은 사용자가 이미 로그인하며 받은 OAuth 토큰을 그대로 에이전트 실행 컨텍스트에 넘기는 것이다. 사람이 쓰던 토큰이니 권한 범위도 맞고, 추가 인증 플로우를 설계할 필요도 없어 보인다.

문제는 에이전트가 그 토큰을 "사람처럼" 쓰지 않는다는 데 있다. 사람은 하루에 메일을 몇 번 열어보지만, 에이전트는 작업 하나를 처리하면서 같은 토큰으로 수십 번씩 API를 호출하고, 중간에 외부 문서나 PR 본문처럼 신뢰할 수 없는 텍스트를 읽는다. 그 텍스트 안에 숨은 지시문 하나(프롬프트 인젝션)가 에이전트의 다음 행동을 바꿔버리면, 공격자는 에이전트가 쥔 토큰의 전체 권한 범위 — 그 사용자의 메일함, 저장소, 문서함 전부 — 에 접근하는 통로를 얻는다. 2026년 들어 Microsoft가 Entra Agent ID를 프리뷰로 내놓는 등, 업계가 에이전트를 "사람의 연장선"이 아니라 자신만의 권한 경계를 가진 **별도의 principal 유형**으로 다루기 시작한 이유가 여기에 있다.

## 핵심 개념 1 — 사람 토큰을 재사용하면 왜 깨지는가

OAuth의 기본 전제는 "사람이 동의한 범위 안에서 앱이 짧게, 예측 가능한 패턴으로 대신 행동한다"는 것이다. 에이전트는 이 전제를 세 지점에서 깬다. 첫째, 호출 빈도와 패턴이 사람과 다르다 — 짧은 시간에 몰아서 수십 건을 호출하는 것이 정상 동작이라, 이상 탐지 시스템이 사람 기준으로 짜여 있으면 에이전트의 비정상 오남용을 걸러내지 못한다. 둘째, 에이전트는 자율적으로 다음 행동을 "판단"한다 — 사람이 매 단계 승인하지 않는 구간이 존재하므로, 판단이 오염되면 토큰 오용까지 거리가 한 번의 추론으로 좁혀진다. 셋째, 책임 추적의 단위가 다르다 — 사용자 토큰을 그대로 쓰면 로그에는 "사용자 A가 했다"고만 남고, 실제로는 에이전트가 자율적으로 수행한 행동인지 사람이 직접 클릭한 행동인지 구분이 안 된다.

## 핵심 개념 2 — 두 가지 토큰 모델과 선택 기준

실무에서는 크게 두 모델로 나뉜다. **클라이언트 자격증명(client credentials) 모델**은 에이전트 자체를 독립된 서비스 주체로 등록하고, 관리자가 사전 승인한 고정 스코프의 토큰을 발급한다. 반복적이고 저위험인 백그라운드 작업(모니터링, 정기 리포트 생성)에 적합하다. **위임(on-behalf-of, OBO) 모델**은 사용자의 동의 체인을 토큰 안에 유지한 채 에이전트가 그 사용자 대신 행동한다는 사실을 토큰 자체에 남긴다. 메일 발송, 결제, 파일 삭제처럼 "누구의 책임으로 실행됐는가"가 감사·법적 관점에서 중요한 민감 작업에 맞는다.

어느 모델을 쓰든 공통 원칙은 같다. 토큰 수명은 짧게, 스코프는 필요한 최소 범위로, 가능하면 토큰을 특정 클라이언트에 묶는 sender-constrained 방식을 쓴다. 초기 설계에서 넓은 스코프를 받아두고 "나중에 줄이면 된다"고 미루는 팀이 많은데, 실제로 스코프를 나중에 좁히는 작업은 거의 일어나지 않는다 — 처음부터 좁게 설계해야 한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-18-ai-agent-non-human-identity-access-design-1.svg" alt="사용자 요청이 에이전트 오케스트레이터를 거쳐 외부 콘텐츠를 읽고, 토큰 브로커가 작업 위험도에 따라 client credentials 또는 OBO 토큰을 발급해 각 연동 서비스를 호출하는 구조도" style="width:100%;">

사용자의 요청이 에이전트 오케스트레이터로 들어오면, 작업을 수행하는 과정에서 외부 콘텐츠(이메일 본문, PR 설명, 웹페이지)를 읽는 지점이 반드시 생긴다. 이 지점이 프롬프트 인젝션이 유입되는 경계다. 오케스트레이터가 실제 외부 API를 호출하기 전에 **토큰 브로커** 레이어를 하나 두면, 이 레이어가 작업의 위험도를 판단해 저위험 반복 작업에는 client credentials 토큰을, 민감한 위임 작업에는 OBO 토큰을 — 그것도 해당 호출에 필요한 최소 스코프로만 — 발급한다. 외부 API는 이 토큰 브로커를 거치지 않은 직접 호출을 받아들이지 않도록 구성한다.

## 선택의 트레이드오프

| 모델 | 강점 | 약점 | 적합한 상황 |
|---|---|---|---|
| 사용자 토큰 그대로 재사용 | 구현이 가장 빠름 | 탈취 시 사용자 전체 권한 노출, 감사 추적 불명확 | 프로토타입 단계, 실제 서비스엔 권장되지 않음 |
| 전용 client credentials | 스코프를 처음부터 좁게 고정 가능, 관리자 사전 승인 | "누구 대신"이라는 위임 맥락이 토큰에 없음 | 반복적 저위험 백그라운드 작업 |
| OBO 위임 체인 | 위임 맥락 유지, 책임 추적 명확 | 구현 복잡도 높고 토큰 갱신 로직 필요 | 송금·삭제·외부 발송 등 책임 소재가 중요한 작업 |

세 모델을 하나만 골라 전체 시스템에 적용하는 경우는 드물다. 대부분의 실무 설계는 작업 위험도에 따라 client credentials와 OBO를 함께 쓰고, 첫 번째 모델(사용자 토큰 재사용)은 프로토타입 이후 반드시 걷어낸다.

## 실제 프로젝트 진행 순서

1. **연동 서비스별 액션을 위험도로 분류한다.** 삭제·발송·결제처럼 되돌리기 어려운 액션과, 조회·요약처럼 되돌릴 수 있는 액션을 먼저 나눈다.
2. **민감 액션에는 OBO + 사람 승인 게이트를, 반복 저위험 액션에는 client credentials를 배정한다.** 하나의 토큰 모델로 전체를 덮으려 하지 않는다.
3. **토큰 TTL과 스코프를 서비스별로 최소화해 설정한다.** 처음부터 넓게 주고 나중에 줄이겠다는 계획은 실제로 지켜지지 않는다.
4. **감사 로그에 "에이전트가 자율적으로 호출했는가"를 1급 필드로 남긴다.** 사용자 ID만으로는 사람의 행동과 에이전트의 행동을 구분할 수 없다.
5. **호출 빈도·패턴 기반 이상 탐지를 에이전트 전용 기준으로 따로 만든다.** 사람 기준 이상 탐지 규칙은 에이전트의 정상 동작을 오탐하거나, 반대로 진짜 오남용을 놓친다.

```json
{
  "subject_type": "agent",
  "agent_id": "support-agent-07",
  "acting_for": "user_8841",
  "scope": ["gmail.send"],
  "token_binding": "mtls",
  "expires_in": 900
}
```

## 마무리 요약

- 사용자 OAuth 토큰을 에이전트에 그대로 재사용하면, 프롬프트 인젝션 한 번으로 해당 사용자의 모든 연동 서비스 권한이 함께 노출된다.
- client credentials(에이전트 자체 권한)와 OBO(사용자 위임 유지)는 서로 다른 문제를 풀며, 작업의 위험도와 책임 추적 필요성에 따라 나눠 적용해야 한다.
- 토큰 수명을 짧게, 스코프를 최소로 설계하는 원칙은 둘 중 어느 모델을 쓰든 공통이며, 처음부터 좁게 설계하지 않으면 나중에 좁히는 일은 거의 일어나지 않는다.
