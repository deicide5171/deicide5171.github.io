## 도입

"이 할인 로직 하나만 고쳐달라고 했는데, 에이전트가 주문 서비스·가격 서비스·쿠폰 서비스·알림 서비스를 다 뒤지다가 엉뚱한 서비스의 API 응답 형식을 바꿔놨어요." 마이크로서비스로 쪼갠 조직에서 AI 코딩 에이전트를 붙이기 시작하면 이런 보고가 나오기 시작한다. 사람 개발자는 "이 기능은 가격 서비스 담당"이라는 암묵지를 갖고 바로 그 레포로 간다. 에이전트는 그 암묵지가 없어서, 기능이 흩어진 서비스 수만큼 네트워크 경계를 넘어 코드를 탐색하고, 그 과정에서 컨텍스트 윈도우를 실제 도메인 로직이 아니라 API 클라이언트·DTO 변환 같은 연결 코드를 읽는 데 다 써버린다.

마이크로서비스를 쪼갠 이유는 원래 배포 독립성과 팀 자율성이었다. 이 기준 자체는 여전히 유효하다. 다만 2026년 들어 에이전트 중심 개발이 늘면서 여기에 새 변수가 하나 추가됐다 — **에이전트가 한 번에 읽을 수 있는 코드 범위**. 이 글은 이 변수가 모놀리스·마이크로서비스 판단에 왜, 어떻게 들어와야 하는지 정리한다.

## 전체 시스템에서의 위치

기존 판단 기준은 조직 구조(콘웨이의 법칙), 독립 배포 주기, 독립 스케일링 필요성이었다. 여기에 에이전트가 끼어들면 "기능 요청 → 코드 탐색 → 수정"이라는 작업 루프 자체의 비용 구조가 달라진다.

<img src="/assets/images/posts/2026-10-26-ai-agent-context-monolith-microservices-1.svg" alt="모듈러 모놀리스와 마이크로서비스에서 에이전트의 코드 탐색 범위 비교" style="width:100%;">

- **모듈러 모놀리스**: 기능이 하나의 바운디드 컨텍스트(모듈) 안에 모여 있으면, 에이전트는 그 모듈 하나만 컨텍스트에 올려 작업을 끝낼 수 있다. 네트워크 경계를 넘을 필요가 없다.
- **성숙한 내부 개발자 플랫폼(IDP)이 있는 마이크로서비스**: 서비스 카탈로그·API 스펙이 잘 정리돼 있으면 에이전트가 각 서비스의 계약(contract)만 보고도 어디를 고쳐야 할지 좁힐 수 있다. 하지만 여전히 서비스 경계를 넘는 호출마다 왕복과 컨텍스트 소모가 생긴다.
- **IDP 없는 마이크로서비스**: 에이전트에게는 사람에게 없던 암묵지도 없고, 참조할 카탈로그도 없다. 이 경우 분산 시스템이 "에이전트가 딸린 분산 모놀리스"가 된다 — 서비스는 나뉘어 있지만 실제로는 매번 전체를 훑어야 한다.

## 선택의 트레이드오프

| 아키텍처 | 에이전트 작업 효율 | 배포 독립성 | 팀 자율성 | 적합한 상황 |
|---|---|---|---|---|
| 단일 모놀리스(구조 없음) | 초기엔 높음, 코드가 커지면 급격히 떨어짐 | 낮음 | 낮음 | 팀 1~2개, 초기 단계 |
| 모듈러 모놀리스(바운디드 컨텍스트) | 높음 — 모듈 하나가 곧 컨텍스트 범위 | 중간(배포는 단일, 내부 경계는 명확) | 중간~높음(모듈 단위로 소유권 분리 가능) | 팀이 늘었지만 아직 독립 배포·스케일링이 꼭 필요하진 않은 조직 |
| 마이크로서비스(IDP 성숙) | 중간 — 계약은 보이지만 경계 넘는 비용 존재 | 높음 | 높음 | 서비스별 트래픽 패턴이 다르고 플랫폼팀이 카탈로그를 유지하는 조직 |
| 마이크로서비스(IDP 없음) | 낮음 — 매 요청마다 전체 서비스를 탐색 | 높음(이론상) | 높음(이론상) | 거의 없음 — 분리 비용만 지불하고 이점은 못 누리는 상태 |

판단 기준은 단순해졌다. **독립 배포·독립 스케일링이 실제로 필요한 서비스인가**를 먼저 묻고, 그렇지 않다면 모듈러 모놀리스로 통합하는 쪽이 에이전트 작업 효율과 팀 운영 부담을 동시에 줄인다. 독립 배포가 꼭 필요하다면 서비스는 유지하되, 그 비용을 상쇄할 IDP·서비스 카탈로그에 먼저 투자해야 한다 — 이 투자 없이 서비스만 쪼개는 것은 에이전트 시대에 가장 비싼 선택이다.

## 실제 프로젝트 진행 순서

1. **에이전트 작업 로그에서 "기능 하나당 건드린 레포·서비스 수"를 측정한다.** 평균 3개 이상을 넘나든다면 바운디드 컨텍스트 재정의가 필요한 신호다.
2. **도메인 모델 기준으로 바운디드 컨텍스트를 다시 그린다.** 조직도나 배포 이력이 아니라 "같이 바뀌는 코드"를 기준으로 묶는다.
3. **각 서비스에 대해 "독립 배포·독립 스케일링이 실제로 쓰이고 있는가"를 재검증한다.** 배포 주기가 다른 서비스와 똑같고 트래픽도 비슷하다면 분리를 유지할 이유가 약하다.
4. **통합이 어려운 서비스는 유지하되, 서비스 카탈로그와 API 계약 문서를 에이전트가 참조할 수 있는 형태로 정리한다.** 사람에게만 보이던 README가 아니라 에이전트가 로드할 수 있는 구조화된 스펙이어야 한다.
5. **통합은 스트랭글러 피그 패턴으로 점진적으로 진행한다.** 한 번에 합치지 않고, 가장 자주 함께 수정되는 서비스 쌍부터 모듈로 묶어 하나의 배포 단위 안으로 옮긴다.

```text
# 바운디드 컨텍스트 재정의 체크리스트 예시
1. 최근 3개월 PR에서 함께 수정된 파일/서비스 쌍을 집계한다.
2. 같은 PR에서 90% 이상 함께 바뀌는 서비스 쌍을 하나의 모듈 후보로 묶는다.
3. 묶인 모듈이 독립 배포·스케일링 요구가 없는지 트래픽/배포 로그로 확인한다.
4. 요구가 없으면 모듈러 모놀리스 안의 패키지로 통합, 있으면 서비스로 유지하고 카탈로그에 등록한다.
```

## 실무 포인트

- "모놀리스로 돌아가자"는 일반 해법이 아니다. 독립 배포가 실제로 필요한 결제·인증 같은 서비스는 여전히 분리된 상태가 맞다. 판단은 서비스 단위로, 전사 단위로 한 번에 내리지 않는다.
- 모듈러 모놀리스로 합쳐도 모듈 간 경계를 코드 리뷰나 린트 규칙으로 강제하지 않으면 금방 다시 뒤섞인 모놀리스로 퇴화한다. 바운디드 컨텍스트는 그리는 것보다 지키는 게 더 어렵다.
- 에이전트 작업 효율은 아키텍처를 재구성하는 여러 이유 중 하나일 뿐이다. 팀 자율성, 장애 격리, 보안 경계처럼 더 오래된 이유가 여전히 더 중요한 경우도 많다 — 측정 없이 "에이전트가 힘들어하니까"로 전사 리아키텍처를 밀어붙이지 않는다.

## 마무리

- 에이전트 도입은 모놀리스·마이크로서비스 판단에 "에이전트가 한 번에 읽어야 하는 범위"라는 새 변수를 추가했을 뿐, 기존 배포 독립성·팀 자율성 기준을 대체하지 않는다.
- IDP 없는 마이크로서비스는 분리 비용만 지불하고 에이전트 효율 이점은 전혀 못 누리는 가장 나쁜 조합이다.
- 진행 순서는 에이전트 작업 로그로 탐색 범위 측정 → 바운디드 컨텍스트 재정의 → 분리 필요성 재검증 → 카탈로그 정비 → 스트랭글러 피그로 점진 통합이다.
