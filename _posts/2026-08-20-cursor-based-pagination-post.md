## 왜 지금 이 이야기인가

목록 API에 페이지네이션을 붙일 때 가장 먼저 손이 가는 방법은 `LIMIT`과 `OFFSET`이다. 페이지 번호만 받아서 `OFFSET (페이지번호-1) * 페이지크기`로 변환하면 끝이라, 초기 구현 속도가 빠르고 SQL도 직관적이다. 문제는 데이터가 수십만 건을 넘기고 사용자가 뒷페이지까지 파고들기 시작하면서 드러난다. 같은 쿼리, 같은 페이지 크기인데 1페이지는 즉시 응답하고 200페이지는 눈에 띄게 느려지는 현상을 겪게 된다.

원인은 `OFFSET`의 동작 방식 자체에 있다. 데이터베이스는 "몇 번째 행부터 보여줄지"를 미리 알 방법이 없어서, 조건에 맞는 행을 처음부터 순서대로 세면서 `OFFSET`만큼 스캔한 뒤에야 버리고, 그다음 `LIMIT`개만 반환한다. 즉 뒷페이지로 갈수록 실제로 반환하는 행 수는 그대로인데 훑고 지나가야 하는 행 수만 계속 늘어난다. 최근 무한 스크롤 UI와 대용량 API 목록 조회가 늘면서, 이 문제를 피하는 **커서(키셋, keyset) 기반 페이지네이션**이 사실상 표준 대안으로 자리잡았다.

이 글은 OFFSET 방식이 왜 느려지는지, 커서 기반 페이지네이션이 이를 어떻게 해결하는지, 그리고 실제 구현에서 흔히 놓치는 지점을 정리한다.

## 핵심 개념 1: OFFSET/LIMIT의 동작과 한계

`OFFSET`은 "건너뛸 행 수"를 지정하는 것처럼 보이지만, 실제로는 정렬된 결과 집합을 처음부터 순회하며 지정된 개수만큼 세어 넘기는 연산이다. 인덱스를 타더라도 이 "세면서 건너뛰기" 자체는 생략할 수 없어서, 스캔 비용이 대략 `OFFSET + LIMIT`에 비례해 커진다.

- 페이지 번호가 커질수록 매 요청마다 앞부분을 다시 훑어야 하므로 응답 시간이 페이지 번호에 비례해 늘어난다.
- 조회 도중 원본 테이블에 행이 추가되거나 삭제되면, 다음 페이지를 요청하는 시점에는 정렬 순서상 위치가 이미 밀린 상태다. 그 결과 같은 항목이 두 페이지에 걸쳐 중복 노출되거나, 반대로 한 항목이 아예 누락될 수 있다.
- 총 개수(`COUNT(*)`)까지 함께 보여주려면 별도 카운트 쿼리가 필요해, 큰 테이블일수록 그 비용도 무시하기 어렵다.

## 핵심 개념 2: 커서 기반(키셋) 페이지네이션이란

커서 기반 페이지네이션은 "몇 번째 행인지"가 아니라 "마지막으로 본 행이 어디였는지"를 기준으로 다음 페이지를 요청한다. 정렬 기준 컬럼(보통 `id`나 `created_at`처럼 고유하고 순서를 매길 수 있는 값)의 마지막 값을 **커서**로 클라이언트에 돌려주고, 다음 요청 때는 `WHERE 정렬컬럼 > :커서 ORDER BY 정렬컬럼 LIMIT n` 형태로 조회한다.

이 방식은 앞부분을 세면서 건너뛰는 과정이 없다. 인덱스가 커서 값의 위치를 직접 찾아가는(index seek) 방식으로 동작하기 때문에, 몇 페이지째를 요청하든 스캔 비용이 거의 일정하게 유지된다. 또한 커서가 "몇 번째"가 아니라 "어떤 값 이후"를 의미하므로, 중간에 다른 행이 추가·삭제되어도 이미 발급한 커서의 의미 자체는 바뀌지 않는다.

## 핵심 개념 3: 두 방식 비교

| 기준 | OFFSET/LIMIT | 커서 기반(Keyset) |
|---|---|---|
| 다음 페이지 요청 방식 | 페이지 번호 → OFFSET 값 계산 | 이전 페이지 마지막 값(커서) 전달 |
| 뒷페이지로 갈 때 성능 | 페이지 번호에 비례해 저하 | 페이지 번호와 무관하게 거의 일정 |
| 특정 페이지로 바로 이동 | 가능(사용자가 "5페이지" 클릭) | 기본적으로 어려움(순차 이동 전제) |
| 데이터 변경 중 안정성 | 항목 중복·누락 가능 | 커서 기준이라 상대적으로 안정적 |
| 구현 난이도 | 낮음 | 정렬 기준을 신중히 설계해야 함(다음 섹션) |
| 대표 사용처 | 페이지 번호 목록형 화면 | 무한 스크롤, 대용량 API 목록 |

두 방식은 완전한 대체재가 아니라 요구사항이 다르다. "3페이지로 바로 이동" 같은 UI가 꼭 필요하다면 OFFSET(혹은 하이브리드 방식)이 여전히 유효하고, 무한 스크롤이나 순차 조회가 중심이라면 커서 기반이 유리하다.

## 예제: OFFSET vs 커서 기반 SQL

```sql
-- OFFSET/LIMIT 방식: 200번째 페이지(페이지당 20건)
-- 실제로는 앞의 4,000건을 스캔해서 버린 뒤 20건만 반환한다
SELECT id, title, created_at
FROM articles
ORDER BY id
LIMIT 20 OFFSET 4000;
```

```sql
-- 커서 기반 방식: 이전 페이지의 마지막 id(예: 4000)를 커서로 사용
-- id 인덱스를 이용해 4000 이후 위치로 바로 이동(seek)한 뒤 20건만 읽는다
SELECT id, title, created_at
FROM articles
WHERE id > 4000
ORDER BY id
LIMIT 20;
```

정렬 기준이 `created_at`처럼 값이 중복될 수 있는 컬럼이라면, 동일 시각에 생성된 행 사이의 순서가 흔들려 항목이 누락되거나 중복될 수 있다. 이럴 때는 아래처럼 고유한 보조 키(`id`)를 함께 묶어 정렬·비교 기준으로 삼아 순서를 완전히 고정한다.

```sql
-- created_at이 같은 행이 여러 개일 수 있으므로 id를 보조 정렬 기준으로 추가
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

## 실무 포인트

- **정렬 기준 컬럼은 반드시 유니크하게(또는 유니크한 보조 키와 함께) 구성한다.** 값이 중복될 수 있는 컬럼만으로 커서를 만들면 동일 값을 가진 행들의 상대 순서가 보장되지 않아 항목이 빠지거나 중복될 수 있다.
- **커서 컬럼(들)에 인덱스가 있는지 반드시 확인한다.** 인덱스 없이 커서 조건을 걸면 매번 전체 스캔이 일어나 OFFSET 방식보다 오히려 느려질 수 있다.
- **커서 값은 원시 컬럼 값을 그대로 노출하기보다 인코딩(예: base64)해서 클라이언트에 내려주는 편이 안전하다.** 내부 컬럼명이나 값 형식이 그대로 노출되면 나중에 스키마를 바꾸기 어려워진다.
- **"몇 페이지째인지", "전체 몇 건인지"가 꼭 필요한 화면인지 먼저 확인한다.** 커서 기반은 임의 페이지 점프나 정확한 총 개수 표시에 잘 맞지 않으므로, 그런 요구가 있다면 OFFSET과의 하이브리드나 별도의 근사 카운트 전략을 함께 검토해야 한다.
- **양방향(이전/다음) 탐색이 필요하면 커서를 두 방향 모두 발급하도록 설계한다.** 다음 페이지 커서만 만들어두면 "이전 페이지로" 이동 시 별도 로직이 필요해진다.

## 3줄 요약

- OFFSET/LIMIT은 앞부분을 스캔해서 버리는 방식이라, 뒷페이지로 갈수록 스캔 비용이 늘어나고 데이터 변경 중에는 중복·누락도 생길 수 있다.
- 커서 기반 페이지네이션은 마지막으로 본 위치를 기준으로 인덱스를 직접 탐색해, 페이지 번호와 무관하게 비교적 일정한 성능을 낸다.
- 다만 임의 페이지 점프나 정확한 총 개수가 필요한 화면에는 잘 맞지 않으므로, 화면 요구사항에 따라 OFFSET·커서·하이브리드 중 적합한 방식을 선택해야 한다.
