## 왜 지금 이 문제가 불거지는가

"지도 화면에 검색창 하나만 놓고, '우리 강남점 반경 500m 안에 있는 경쟁사 카페 보여줘'라고 치면 바로 지도에 마커가 찍혔으면 좋겠어요." 기획자 입장에서는 이미 사내에 돌아다니는 Text-to-SQL 챗봇에 지도 좌표 테이블 하나만 연결하면 되는 요청처럼 보인다. 그런데 이 한 줄에는 공간 데이터 특유의 함정이 최소 세 겹 숨어 있다 — "반경 500m"라는 거리를 올바른 좌표계로 환산해야 하고, "안에 있는"을 올바른 공간 함수(교차·포함·근접 중 무엇인지)로 번역해야 하며, 결과가 틀렸는지는 숫자가 아니라 지도를 봐야 알 수 있다.

이 문제가 최근 부각된 이유는 에이전트에게 사내 DB 쿼리를 맡기는 사례가 늘면서, 그 DB에 공간 컬럼이 섞여 있을 때 일반 Text-to-SQL 파이프라인이 눈에 띄게 더 자주 실패한다는 보고가 쌓였기 때문이다. 2026년 공개된 Geo-ReAct, SpatialSQL 같은 연구는 바로 이 지점 — 일반 SQL 생성 능력은 충분한데 공간 함수와 좌표계 앞에서 무너지는 현상 — 을 정면으로 다룬다.

## 요구사항을 기술 문제로 번역하기

"반경 500m 안 경쟁사"라는 말은 내부적으로 네 단계 번역을 거쳐야 한다. 첫째, "반경 500m"를 미터 단위 버퍼로 다룰지 지구 곡률을 고려한 geography 타입으로 다룰지 정해야 한다. 둘째, 매장 좌표와 경쟁사 좌표가 같은 SRID(좌표계)로 저장돼 있는지 확인해야 한다 — 위경도(SRID 4326)와 미터 단위 투영 좌표계가 섞여 있으면 "500m"가 실제로는 500도 가까운 엉뚱한 값으로 계산된다. 셋째, "안에 있는"을 `ST_DWithin`(거리 기반 근접)으로 쓸지 `ST_Contains`(폴리곤 포함)로 쓸지 질의 의도에 맞게 골라야 한다. 넷째, 생성된 쿼리가 실행은 되지만 **의미적으로 틀린** 결과를 돌려줄 수 있다는 점 — 예를 들어 좌표 순서를 위경도 대신 경위도로 뒤바꿔도 SQL 자체는 에러 없이 실행된다.

일반 Text-to-SQL 에이전트가 자유롭게 SQL을 생성하게 두면 이 네 가지 선택을 매번 모델의 즉흥적 판단에 맡기는 셈이다. Geo-ReAct와 SpatialSQL류 접근은 공통적으로 "모델이 raw SQL을 직접 쓰게 하지 않는다"는 원칙에서 출발한다. 대신 반경 검색, 포함 판정, 최단거리 같은 패턴을 **개념 기반 도구(concept-grounded tool)**로 미리 정의해, 모델은 어떤 도구를 어떤 파라미터로 호출할지만 결정하게 한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-03-geospatial-text-to-sql-agent-1.svg" alt="자연어 질의가 의도 추출 단계를 거쳐 개념 기반 공간 도구 카탈로그 중 하나를 선택하고, 단위·좌표계 정규화 레이어를 지나 PostGIS에서 실행된 뒤, 검증 에이전트가 결과 건수와 바운딩박스를 점검하고 지도 렌더링으로 사람이 바로 확인하는 구조도" style="width:100%;">

이 구조에서 LLM은 SQL 작성자가 아니라 **도구 선택자**로 역할이 축소된다. 자연어 질의가 들어오면 먼저 의도·개체 추출 단계에서 "기준점(강남점), 거리(500m), 대상 카테고리(카페)"를 뽑아낸다. 다음으로 이 의도를 미리 검증된 공간 도구 카탈로그 — 반경 검색, 폴리곤 포함, 경로 거리 — 중 하나에 매핑한다. 선택된 도구는 내부적으로 단위·좌표계 정규화 레이어를 거쳐 실제 PostGIS 쿼리(`ST_DWithin(geography, geography, 500)` 같은 안전한 템플릿)로 실행된다. 실행 결과는 검증 에이전트가 건수가 비정상적으로 많거나 적은지, 반환된 좌표가 합리적인 바운딩박스 안에 있는지 점검한 뒤에야 지도 렌더링으로 넘어간다. 숫자 결과만으로는 "경위도가 뒤바뀐 좌표"를 걸러내기 어렵기 때문에, 지도라는 시각적 피드백 채널이 검증 파이프라인의 마지막 안전망 역할을 한다.

## 선택의 트레이드오프

| 기준 | 일반 Text-to-SQL | 고정 쿼리 템플릿 | 개념 기반 도구 호출 | 멀티에이전트 파이프라인 |
|---|---|---|---|---|
| 유연성 | 높음(임의 질의 대응) | 낮음(사전 정의 패턴만) | 중간(카탈로그 범위 내) | 중간~높음 |
| 좌표계·단위 안전성 | 낮음(모델이 매번 추론) | 높음(고정) | 높음(도구 내장) | 높음(검증 단계 추가) |
| 구현·유지 비용 | 낮음 | 낮음 | 중간(도구 카탈로그 설계) | 높음(에이전트 간 조율) |
| 적합 상황 | 비공간 일반 질의 | 질의 패턴이 매우 한정적 | 반복되는 핵심 공간 질의 | 다양한 공간 질의 + 높은 정확도 요구 |

일반 Text-to-SQL은 비공간 테이블에는 충분히 쓸 만하지만, 공간 컬럼이 섞인 순간 좌표계·단위 오류를 모델의 "그럴듯한 추측"에 맡기게 되므로 프로덕션 반경 검색 같은 기능에는 권하기 어렵다. 반대로 고정 템플릿은 안전하지만 기획자가 새 질의 패턴을 요청할 때마다 코드를 새로 짜야 한다.

## 실제 프로젝트 진행 순서

1. **지원할 공간 질의 패턴을 좁은 카탈로그로 먼저 확정한다.** "반경 안 검색", "폴리곤 포함 여부", "경로 거리" 정도로 시작하고, 모델이 임의로 새 공간 함수를 호출하지 못하게 범위를 제한한다.
2. **각 패턴을 파라미터화된 안전 도구로 구현한다.** 좌표계 캐스팅과 단위 변환을 도구 내부에 고정해, 모델이 SRID나 미터·도(degree) 변환을 직접 계산하지 않게 한다.
3. **자연어 거리·단위 표현의 정규화 레이어를 추가한다.** "500m", "도보 10분", "반경 1km" 같은 표현을 도구가 받는 단일 단위(미터)로 변환하는 전처리를 별도로 둔다.
4. **결과를 반드시 지도로 먼저 확인할 수 있게 한다.** 텍스트/표 형태의 결과만으로는 좌표 오류를 못 잡으므로, 개발 단계에서부터 지도 렌더링을 1차 디버깅 도구로 쓴다.
5. **검증 에이전트로 건수·바운딩박스 이상치를 걸러낸다.** 결과가 0건이거나 비정상적으로 전역에 퍼져 있으면 좌표계 혼선 신호로 보고 재질의하거나 사람에게 에스컬레이션한다.

## 실무 포인트

**`ST_Distance`와 `ST_DWithin`을 혼용하면 성능이 크게 달라진다.** 전체 거리를 계산해 정렬하는 방식은 인덱스를 못 타지만, `ST_DWithin`은 공간 인덱스를 활용할 수 있어 대규모 테이블에서 체감 성능 차이가 크다. 도구 설계 단계에서부터 이 차이를 반영해야 한다.

**SRID 4326과 미터 단위 투영 좌표계를 섞어 쓰는 실수가 가장 흔하다.** geography 타입을 쓰면 위경도 좌표에서도 미터 단위 거리 계산이 가능하지만, geometry 타입으로 잘못 캐스팅하면 "500m"가 실제로는 좌표값 500 단위(수백 km)로 해석될 수 있다.

**모델이 "그럴듯하지만 틀린" 쿼리를 만들어도 에러는 안 난다.** 공간 SQL은 문법적으로 완전히 유효하면서 의미적으로는 완전히 틀린 결과를 조용히 반환하는 경우가 많아, 실행 성공 여부만으로 품질을 판단하면 안 된다.

## 마무리

- 공간 질의를 자연어로 받겠다는 요구는 일반 Text-to-SQL이 아니라 좌표계·단위·공간 함수 선택이라는 별도 문제로 번역해야 한다.
- 모델을 SQL 작성자가 아닌 개념 기반 도구 선택자로 제한하고, 단위·좌표계 정규화를 도구 내부에 고정하는 것이 안전한 설계 원칙이다.
- 결과 검증은 숫자만으로 끝나지 않으며, 지도 렌더링과 바운딩박스 점검이 마지막 안전망 역할을 한다.
