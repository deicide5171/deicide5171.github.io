LLM 추론 비용을 줄이는 기법은 크게 두 갈래다. 양자화처럼 모델 자체를 가볍게 만드는 쪽과, 같은 모델로 하드웨어를 더 알뜰하게 쓰는 쪽. 전자는 정도의 차이는 있어도 출력 품질에 손을 대는 반면, 후자 중에는 출력 분포를 수학적으로 전혀 바꾸지 않으면서 응답 속도를 끌어올리는 기법이 있다. 바로 **스페큘레이티브 디코딩(speculative decoding)**이다.

아이디어는 직관적이다. 큰 모델이 다음 토큰을 한 개씩 뽑는 대신, 작은 모델이 먼저 여러 토큰의 "초안"을 빠르게 써두고, 큰 모델은 그 초안이 맞는지 **한 번의 순전파로 병렬 검증**만 한다. 초안이 맞으면 여러 토큰이 한꺼번에 확정되고, 틀리면 틀린 지점부터 큰 모델이 바로잡는다. 결과물은 큰 모델 혼자 생성한 것과 통계적으로 동일한데 속도만 빨라진다.

이 글에서는 왜 이런 구조가 가능한지(디코딩의 병목), 검증이 어떻게 무손실을 보장하는지, 그리고 성패를 가르는 수락률과 실무 적용 기준을 정리한다.

## 왜 가능한가 — 디코딩의 병목은 연산이 아니라 메모리

트랜스포머 디코딩이 느린 근본 원인은 GPU 연산량이 아니라 **메모리 대역폭**이다. 자기회귀 생성에서는 토큰을 하나 뽑을 때마다 모델의 전체 가중치를 HBM에서 연산 유닛으로 읽어와야 한다. 70B급 모델이라면 토큰 하나당 수십 GB를 옮기는 셈인데, 이때 실제 부동소수점 연산은 GPU가 낼 수 있는 성능의 극히 일부만 쓴다. 즉 디코딩 단계의 GPU는 대부분 "계산"이 아니라 "가중치 나르기"를 하며 논다.

여기서 중요한 비대칭이 생긴다. 가중치를 한 번 읽어온 김에 토큰 1개 위치를 계산하든 5개 위치를 계산하든, 걸리는 시간은 거의 같다는 점이다(프롬프트 프리필이 생성보다 훨씬 빠른 것과 같은 원리다). 문제는 자기회귀 특성상 다음 토큰을 알아야 그다음 토큰을 만들 수 있어서, 검증할 "미래 토큰 후보"가 없다는 것. 스페큘레이티브 디코딩은 이 후보를 작은 모델에게 만들게 해서 남는 연산 능력을 채운다.

## 드래프트와 검증 — 두 모델의 분업

동작은 한 사이클에 세 단계로 진행된다. 드래프트 모델(예: 1B급)이 자기회귀로 토큰 k개(보통 3~8개)를 빠르게 생성하고, 타깃 모델(예: 70B급)이 그 k개 위치를 **단 한 번의 순전파**로 훑으며 각 위치에서 자기라면 어떤 확률 분포를 냈을지 계산한다. 마지막으로 위치를 앞에서부터 비교해 수락/거절을 결정한다.

<img src="/assets/images/posts/2026-08-23-speculative-decoding-inference-1.svg" alt="스페큘레이티브 디코딩의 드래프트-검증 사이클: 드래프트 모델이 토큰 5개를 생성하고 타깃 모델이 순전파 1회로 병렬 검증해 4개 수락, 1개 거절 후 교정하는 흐름" style="width:100%;">

핵심은 검증 규칙이다. 각 위치에서 드래프트 모델이 그 토큰을 뽑은 확률 q와 타깃 모델이 계산한 확률 p를 비교해, p ≥ q면 무조건 수락하고 p < q면 p/q의 확률로만 수락한다. 거절이 발생하면 그 위치에서 두 분포의 차이(잔여 분포)로부터 토큰을 다시 샘플링하고 사이클을 끝낸다. 이 수정 기각 샘플링(modified rejection sampling) 덕분에 **최종 출력의 확률 분포가 타깃 모델 단독 생성과 정확히 일치**한다는 것이 원 논문의 증명이다. 근사가 아니라 무손실이다.

거절이 나더라도 손해가 아니라는 점도 중요하다. 검증 순전파에서 타깃 모델의 분포를 이미 얻었으므로, 최악의 경우(첫 토큰부터 거절)에도 사이클당 토큰 1개는 반드시 확정된다. 일반 디코딩보다 느려지는 부분은 드래프트 모델 실행 비용뿐이다.

## 수락률이 모든 것을 결정한다

이 기법의 성능은 단 하나의 변수, **수락률(acceptance rate)**로 요약된다. 위치당 수락 확률이 α일 때 k개 초안 중 기대 확정 토큰 수는 대략 (1−α^(k+1))/(1−α)개다. α가 0.8이면 k=5에서 사이클당 3~4토큰이 확정되어 타깃 모델 순전파 횟수가 그만큼 줄지만, α가 0.4면 1~2토큰에 그쳐 드래프트 비용만 얹은 꼴이 된다. 원 논문들과 이후 구현들에서 도메인이 잘 맞을 때 2~3배 수준의 지연 시간 단축이 보고돼 왔다.

수락률을 좌우하는 요인은 세 가지다. 첫째, 드래프트 모델과 타깃 모델의 **분포 정렬** — 같은 계열의 축소판(예: 동일 패밀리의 1B와 70B)이 유리하고, 타깃 모델 출력으로 드래프트를 증류하면 더 좋아진다. 둘째, **텍스트의 예측 가능성** — 코드나 정형 문서처럼 다음 토큰이 뻔한 구간이 많을수록 잘 맞는다. 셋째, **샘플링 온도** — 온도가 높을수록 타깃 분포가 퍼져 수락률이 떨어지는 경향이 있다.

드래프트를 만드는 방식도 여러 갈래로 발전했다.

| 방식 | 드래프트 소스 | 장점 | 한계 |
|---|---|---|---|
| 독립 드래프트 모델 | 별도의 소형 모델 | 구현 단순, 기존 모델 재활용 | 어휘/토크나이저 일치 필요, 별도 메모리 점유 |
| 셀프 드래프팅 (Medusa, EAGLE 계열) | 타깃 모델에 얹은 추가 헤드 | 정렬이 좋아 수락률 높음, 별도 모델 불필요 | 헤드 학습 비용, 모델별 준비 필요 |
| n-gram / 프롬프트 룩업 | 입력 컨텍스트에서 문자열 매칭 | 학습·추가 모델 모두 불필요 | 요약·RAG처럼 입력을 되풀이하는 작업에만 효과 |

## 예제 — vLLM에서 켜보기

vLLM은 스페큘레이티브 디코딩을 설정 한 덩어리로 지원한다. 아래는 소형 드래프트 모델을 붙이는 예다(인자 이름은 버전에 따라 다를 수 있으니 사용 중인 버전의 문서를 확인하자).

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=4,
    speculative_config={
        "model": "meta-llama/Llama-3.2-1B-Instruct",  # 같은 패밀리·같은 토크나이저
        "num_speculative_tokens": 5,                   # 사이클당 초안 토큰 수 k
    },
)

params = SamplingParams(temperature=0.2, max_tokens=512)
outputs = llm.generate(["PostgreSQL의 MVCC를 세 문단으로 설명해줘."], params)
print(outputs[0].outputs[0].text)
```

별도 모델 없이 입력에서 초안을 찾는 n-gram 방식은 요약·문서 QA처럼 입력 문장이 출력에 재등장하는 워크로드에서 공짜에 가까운 이득을 준다.

```python
llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    speculative_config={
        "method": "ngram",
        "num_speculative_tokens": 5,
        "prompt_lookup_max": 4,   # 매칭에 쓸 최대 n-gram 길이
    },
)
```

## 실무 포인트 — 언제 켜고 언제 끄나

**켜야 할 때**: 지연 시간(특히 사용자 체감 응답 속도)이 중요한 대화형 서비스이면서 배치 크기가 작을 때다. GPU가 메모리 대역폭에 묶여 노는 상황일수록 검증 순전파의 "덤 계산"이 공짜에 가깝다.

**끄는 게 나을 때**: 배치 크기가 큰 오프라인 대량 처리다. 배치가 커지면 디코딩이 이미 연산 병목으로 넘어가 있어 검증에 쓸 여유 연산이 없고, 거절된 초안의 계산이 고스란히 낭비가 되어 **전체 처리량이 오히려 떨어질 수 있다**. 스페큘레이티브 디코딩은 지연 시간 최적화 기법이지 처리량 최적화 기법이 아니라는 점을 기억하자.

흔한 함정 하나를 짚자면, **토크나이저가 다른 모델을 드래프트로 붙이는 것**이다. 검증은 토큰 ID 단위로 확률을 비교하므로 두 모델의 어휘(vocabulary)가 일치해야 한다. "작고 빠르다"는 이유로 다른 패밀리의 모델을 골랐다가 아예 동작하지 않거나, 어휘가 겹쳐도 분포 정렬이 나빠 수락률이 바닥을 치는 경우가 많다. 올바른 대안은 같은 패밀리의 최소 사이즈를 쓰거나, EAGLE 계열처럼 타깃 모델에서 파생된 드래프터를 쓰는 것이다. k를 무작정 키우는 것도 안티패턴이다. 수락률이 받쳐주지 않으면 뒤쪽 초안은 대부분 버려져 드래프트 비용만 늘어난다. 사이클당 평균 수락 토큰 수를 지표로 두고 k를 3~8 범위에서 조정하는 편이 안전하다.

## 마무리 요약

- 디코딩의 병목은 메모리 대역폭이라 타깃 모델은 토큰 k개를 1개 비용으로 검증할 수 있고, 스페큘레이티브 디코딩은 이 여유를 드래프트 모델의 초안으로 채운다.
- 수정 기각 샘플링 덕분에 출력 분포는 타깃 모델 단독 생성과 동일한 무손실 가속이며, 성능은 전적으로 수락률(모델 정렬, 텍스트 예측 가능성, 온도)에 달렸다.
- 저지연 대화형·소규모 배치에서 켜고, 대규모 배치 처리량 워크로드에서는 오히려 손해일 수 있다. 드래프트는 반드시 같은 토크나이저를 쓰는 모델로.
