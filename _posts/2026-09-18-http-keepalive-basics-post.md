## 요청마다 연결을 새로 맺으면 느리다

HTTP 요청을 보내려면 먼저 서버와 연결(TCP 핸드셰이크)을 맺어야 한다. 요청마다 매번 새로 연결하고 끊으면, 이 과정의 왕복 시간이 쌓여 느려진다. **Keep-Alive(지속 연결)**는 **한 번 맺은 연결을 끊지 않고 여러 요청에 재사용**해 이 낭비를 줄인다.

## 연결 재사용

```text
[Keep-Alive 없음]
요청1: 연결 -> 응답 -> 끊기
요청2: 연결 -> 응답 -> 끊기  (매번 핸드셰이크)

[Keep-Alive 있음]
연결 -> 요청1 -> 응답 -> 요청2 -> 응답 -> ... -> (나중에)끊기
(한 연결로 여러 요청)
```

## 효과

| 항목 | 효과 |
|---|---|
| 지연 | 핸드셰이크 반복 제거로 빨라짐 |
| 자원 | 연결 생성·해제 비용 절감 |
| TLS | 암호화 핸드셰이크도 재사용해 큰 이득 |

## 실무 포인트

- **HTTP/1.1은 기본 켜짐.** HTTP/1.1부터 Keep-Alive가 기본이다. 보통 신경 안 써도 되지만, 프록시·로드밸런서 설정에서 꺼져 있으면 성능이 떨어지니 확인한다.
- **유휴 타임아웃을 조절.** 연결을 무한정 열어두면 자원이 묶인다. 일정 시간(유휴 타임아웃) 동안 요청이 없으면 닫는다. 너무 짧으면 재사용 이득이 줄고, 너무 길면 연결이 쌓이니 균형을 맞춘다.
- **커넥션 풀과 함께.** 클라이언트(백엔드→외부 API 등)는 커넥션 풀로 Keep-Alive 연결을 재사용한다. 매 요청마다 새 연결을 만들면 Keep-Alive의 이점을 못 살리니, HTTP 클라이언트가 연결을 재사용하도록 설정한다.

## 마무리 요약

- Keep-Alive는 한 번 맺은 연결을 끊지 않고 여러 요청에 재사용하는 지속 연결이다.
- 핸드셰이크(특히 TLS) 반복을 없애 지연과 자원을 크게 절감한다.
- HTTP/1.1은 기본으로 켜져 있고, 유휴 타임아웃 조절과 커넥션 풀 활용이 중요하다.
