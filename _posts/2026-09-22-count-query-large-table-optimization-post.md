## 왜 COUNT(*)는 테이블이 커지면 느려지나

목록 화면에 "전체 12,345건" 같은 총 개수를 보여주거나 페이지네이션의 마지막 페이지 번호를 계산하려면 `COUNT(*)` 쿼리가 필요하다. 테이블이 몇만 건 수준일 때는 이 쿼리가 순식간에 끝나지만, 게시글이나 로그 테이블이 수천만 건을 넘어가면 같은 쿼리가 몇 초씩 걸리기 시작한다.

원인은 DB 엔진마다 조금씩 다르지만 핵심은 비슷하다. MySQL의 InnoDB나 PostgreSQL은 MVCC(다중 버전 동시성 제어) 구조를 쓰기 때문에, 트랜잭션마다 "지금 이 시점에 보여야 할 행이 몇 개인지"가 다를 수 있다. 그래서 미리 계산된 값을 캐싱해두는 대신, `COUNT(*)`가 실행될 때마다 조건에 맞는 행을 실제로 하나하나 스캔하며 세야 한다. 인덱스를 스캔하더라도, 인덱스에 포함된 페이지 수만큼 디스크(또는 버퍼) 접근이 필요하므로 테이블이 커질수록 선형적으로 느려진다.

## 잘못된 접근: 매 페이지 요청마다 COUNT(*)를 함께 실행하기

목록 API를 만들 때 가장 흔한 패턴은 데이터 조회 쿼리와 전체 개수 쿼리를 한 요청 안에서 함께 실행하는 것이다.

```sql
-- 페이지 데이터 조회
SELECT * FROM posts WHERE status = 'PUBLISHED' ORDER BY created_at DESC LIMIT 20 OFFSET 100;

-- 매 요청마다 함께 실행되는 전체 개수 쿼리
SELECT COUNT(*) FROM posts WHERE status = 'PUBLISHED';
```

문제는 사용자가 페이지를 넘길 때마다 이 무거운 `COUNT(*)`가 매번 반복 실행된다는 점이다. 정작 전체 개수는 페이지를 이동할 때마다 거의 바뀌지 않는데도, 매 요청마다 같은 무거운 계산을 새로 하는 것은 명백한 낭비다.

## 올바른 접근 1: 정확한 개수가 꼭 필요한지부터 재검토하기

가장 먼저 할 일은 "정말 정확한 전체 개수가 필요한가"를 되묻는 것이다. 무한 스크롤 UI라면 애초에 전체 개수를 보여줄 필요가 없고, "다음 페이지 있음/없음"만 알면 되는 경우가 많다. 이 경우 `LIMIT`을 요청한 개수보다 하나 더 가져와서, 그 여분의 행이 있는지만 확인하는 방식으로 `COUNT(*)` 자체를 제거할 수 있다.

```sql
-- 20개를 요청했다면 21개를 가져와서 21번째 존재 여부로 다음 페이지 유무 판단
SELECT * FROM posts WHERE status = 'PUBLISHED' ORDER BY created_at DESC LIMIT 21 OFFSET 100;
```

## 올바른 접근 2: 근사치로 충분한 경우 시스템 카탈로그 활용하기

관리자 대시보드처럼 "대략 몇 건"이라는 근사치로도 충분한 화면이라면, PostgreSQL은 정확한 스캔 없이 테이블 통계 정보에서 추정치를 즉시 가져올 수 있다.

```sql
-- 정확하지는 않지만 즉시 반환되는 추정 행 수 (ANALYZE 시점 기준)
SELECT reltuples::bigint AS estimate
FROM pg_class
WHERE relname = 'posts';
```

`reltuples`는 마지막 `ANALYZE`(또는 자동 분석) 시점에 수집된 통계이므로 실제 값과 오차가 있을 수 있지만, 수백만 건 단위에서 몇 퍼센트 오차는 대부분의 대시보드 용도에서 문제가 되지 않는다.

## 올바른 접근 3: 진짜 정확한 값이 필요하면 캐싱하고 별도 갱신하기

전자상거래의 재고 수량처럼 반드시 정확해야 하는 카운트라면, 매 조회마다 실시간으로 계산하는 대신 별도의 카운터 컬럼이나 캐시 테이블에 값을 미리 유지하고 데이터 변경 시점에만 갱신하는 방식을 쓴다.

```sql
-- 게시글 작성/삭제 시 카운터 테이블을 함께 갱신
UPDATE post_stats SET total_count = total_count + 1 WHERE category_id = ?;
```

이 방식은 쓰기 시점에 약간의 추가 비용이 들지만, 조회는 인덱스 하나로 즉시 끝나는 카운터 테이블만 읽으면 되므로 읽기 비중이 압도적으로 높은 서비스에 유리하다.

| 전략 | 정확도 | 조회 비용 | 적합한 상황 |
|---|---|---|---|
| 매번 COUNT(*) 실행 | 정확 | 테이블 크기에 비례해 증가 | 테이블이 작거나 조회 빈도가 낮을 때 |
| LIMIT n+1로 다음 페이지 유무만 확인 | 개수 자체는 모름 | 매우 낮음 | 무한 스크롤, 전체 개수 표시 불필요 |
| 시스템 카탈로그 추정치 | 근사치 | 매우 낮음 | 관리자 대시보드, 대략적 통계 |
| 별도 카운터 컬럼/테이블 | 정확 | 매우 낮음(쓰기 비용 증가) | 정확도와 조회 성능이 모두 중요한 경우 |

## 실무 포인트

- **WHERE 조건이 있는 COUNT는 인덱스 설계와 함께 고려하라.** 조건절에 해당하는 커버링 인덱스가 있으면 테이블 본체 접근 없이 인덱스만으로 COUNT를 끝낼 수 있어 훨씬 빠르다.
- **캐시된 카운터 값은 반드시 정합성 검증 배치를 함께 둬라.** 트랜잭션 실패, 배포 중 장애 등으로 카운터가 실제 값과 어긋날 수 있으므로, 주기적으로 실제 COUNT와 비교해 보정하는 배치 작업을 함께 설계해야 한다.
- **MySQL과 PostgreSQL의 COUNT 동작 차이를 확인하라.** MySQL의 MyISAM(레거시)은 전체 행 수를 메타데이터로 캐싱해 COUNT(*)가 빠르지만, 트랜잭션을 지원하는 InnoDB에서는 이 캐싱이 적용되지 않는다는 점을 오해하기 쉽다.

## 마무리 요약

- COUNT(*)가 느려지는 이유는 MVCC 구조상 실행 시점마다 조건에 맞는 행을 실제로 스캔해야 하기 때문이며, 테이블이 커질수록 이 비용이 선형적으로 늘어난다.
- 정확한 개수가 꼭 필요한지 재검토해 LIMIT n+1 패턴으로 대체하거나, 근사치로 충분하다면 시스템 카탈로그 통계를 활용하는 것이 우선 검토할 대안이다.
- 정확도와 조회 성능이 모두 중요한 경우 별도 카운터 컬럼을 유지하되, 정합성 보정 배치를 반드시 함께 설계해야 한다.
