## 왜 요청을 일부러 막는가

서비스 입장에서는 요청이 많이 들어올수록 좋을 것 같지만, 무제한으로 받으면 문제가 생긴다. 한 사용자가 실수(또는 악의)로 초당 수천 번 요청을 보내면 서버 자원이 그 사용자에게 쏠려 다른 정상 사용자들이 서비스를 못 쓰게 된다. **레이트 리미팅(Rate Limiting)**은 "일정 시간 동안 허용하는 요청 수"에 상한을 둬서, 특정 사용자의 과도한 요청으로부터 전체 서비스를 보호하는 기법이다.

## 레이트 리미팅이 필요한 상황

| 상황 | 없을 때의 문제 |
|---|---|
| 무한 스크롤/새로고침 봇 | 서버 과부하 |
| 로그인 무차별 대입 공격 | 계정 탈취 시도 방치 |
| 유료 API 무단 대량 사용 | 비용 폭증 |
| 특정 고객의 트래픽 독점 | 다른 고객의 서비스 품질 저하 |

## 대표적인 알고리즘

```text
1. 고정 윈도우(Fixed Window)
   - "1분당 100회"처럼 시간 구간을 딱 나눠 센다
   - 간단하지만 구간 경계에서 순간적으로 2배가 몰릴 수 있다

2. 슬라이딩 윈도우(Sliding Window)
   - 현재 시점 기준 최근 1분을 계속 이동하며 센다
   - 경계 문제를 완화하지만 계산이 조금 더 복잡

3. 토큰 버킷(Token Bucket)
   - 일정 속도로 토큰을 채우고, 요청마다 토큰을 하나 소비
   - 평소엔 여유 토큰으로 순간적인 폭주(버스트)를 허용해 유연함
   - 가장 널리 쓰이는 방식
```

## 응답으로 알려주는 방법

레이트 리밋에 걸리면 서버는 보통 **HTTP 429 Too Many Requests**를 반환하고, 헤더로 남은 요청 수와 리셋 시각을 알려준다.

```text
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
Retry-After: 30

-> 클라이언트는 Retry-After가 알려준 30초 뒤에 재시도하면 된다
```

## 실무 포인트

- **무엇을 기준으로 제한할지 먼저 정해야 한다.** IP 기준, 사용자 계정 기준, API 키 기준 등이 있으며, 각각 장단점이 다르다. IP 기준은 같은 회사·학교에서 접속하는 여러 사용자가 한 IP를 공유할 때 억울하게 막힐 수 있다.
- **여러 서버로 확장된 환경에서는 각 서버가 따로 세면 안 된다.** 서버마다 카운트를 따로 관리하면 실제 허용량이 서버 수만큼 늘어나므로, Redis 같은 공유 저장소에 카운트를 두고 모든 서버가 함께 참조해야 한다.
- **정상 사용자를 위한 여유를 남겨두는 것이 좋다.** 제한을 너무 빡빡하게 걸면 정상적인 사용 패턴(예: 페이지를 빠르게 넘기는 사용자)까지 막혀 불만이 생긴다.

## 마무리 요약

- 레이트 리미팅은 특정 사용자의 과도한 요청으로부터 전체 서비스를 보호하는 기법이다.
- 고정 윈도우·슬라이딩 윈도우·토큰 버킷이 대표적 알고리즘이며, 토큰 버킷이 가장 널리 쓰인다.
- 여러 서버 환경에서는 Redis 등 공유 저장소로 카운트를 통합 관리해야 실제 제한이 의도대로 작동한다.
