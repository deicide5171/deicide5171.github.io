## 도입

"팀마다 필요하면 Claude Code 에이전트든 사내 봇이든 알아서 만들어 쓰게 해주세요. 승인 기다리다 일정 늦어지는 거 싫어요." 에이전트 도입 초기에 흔히 나오는 요구다. 처음 한두 개일 때는 문제가 없다. 그런데 반년이 지나면 레포마다, 파이프라인마다, 사이드 프로젝트마다 서비스 계정과 API 키를 가진 에이전트가 하나씩 생겨나 있다. 2026년 보안 업계 조사에서는 평균적인 기업에서 비인간(non-human) 신원이 사람 사용자보다 82배 많다는 수치가 나왔고, 그중 실시간 인벤토리를 유지하는 조직은 21%에 그쳤다. 나머지는 지금 몇 개의 에이전트가 무슨 권한으로 떠 있는지 아무도 정확히 모른다는 뜻이다.

이 글이 다루는 문제는 "이 API 호출이 누구의 권한으로 나가는가"라는 위임 인가(delegated authorization) 설계와는 결이 다르다. 그건 호출 한 건의 신원 체인 문제다. 여기서 다루는 건 그보다 한 단계 위 — 조직 전체에 흩어진 에이전트 신원을 누가 발급하고, 누가 책임지고 소유하며, 언제 회수할 것인가라는 재고·생애주기 관리 문제다. 사람 직원은 입사 때 계정이 생기고 퇴사 때 HR 시스템이 자동으로 계정을 잠그는 트리거가 있다. 에이전트는 그런 트리거가 없다. 프로젝트가 끝나도, 만든 사람이 퇴사해도 credential은 `.env` 파일이나 CI 시크릿에 그대로 남아 계속 유효한 토큰으로 살아있는 "좀비 신원"이 된다.

## 전체 시스템에서의 위치

에이전트 신원 라이프사이클은 발급 하나로 끝나지 않는다. 아래 다섯 단계가 하나의 파이프라인으로 이어져야 한다.

<img src="/assets/images/posts/2026-10-21-agent-fleet-nonhuman-identity-lifecycle-1.svg" alt="에이전트 신원 발급부터 폐기까지의 라이프사이클 구조도" style="width:100%;">

1. **요청** — 팀이 "이런 목적의 에이전트가 필요하다"고 신청한다.
2. **발급(Provisioning)** — 신원이 생성되고, 이 시점에 소유자·목적·만료일이 필수 메타데이터로 함께 기록된다.
3. **런타임 권한 부여** — 표준 OAuth 스코프만으로는 부족한 부분을 작업 단위 JIT(Just-in-Time) 그랜트로 보강한다.
4. **운영·모니터링** — 마지막 사용 시각, 호출 패턴 이상 여부를 추적한다.
5. **회수(Deprovisioning)** — 프로젝트 종료, 소유자 변경, 만료일 도달 시 자동으로 신원이 폐기된다.

이 다섯 단계를 하나의 레지스트리로 묶지 않으면, 2번만 있고 5번이 없는 조직이 된다. 실제로 지금 대부분의 조직이 이 상태다.

## 선택의 트레이드오프

| 방식 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 공유 서비스 계정 돌려쓰기 | 당장 빠르게 시작 가능 | 누가 무엇을 했는지 추적 불가, 한 번 유출되면 전체 영향 | 금지 — 프로토타입 단계에서도 지양 |
| 수동 발급 + 스프레드시트 추적 | 도구 투자 없이 시작 가능 | 사람이 깜빡하면 회수 누락, 규모가 커지면 즉시 깨짐 | 에이전트 5개 미만의 초기 단계 |
| SCIM 확장 기반 자동 프로비저닝 | 기존 IAM 파이프라인과 통합, 표준 기반 | 2026년 현재 에이전트 전용 라이프사이클 이벤트를 SCIM이 완전히 커버하지 못함(실험 단계) | 이미 SCIM으로 사람 계정을 관리 중이고 벤더 지원을 기다릴 여유가 있는 조직 |
| JIT 권한 모델(상시 권한 없음) | 평소엔 권한 없음, 작업 시점에만 범위·시간 제한 그랜트 발급 | 모든 호출 경로에 그랜트 발급 로직을 심어야 해 초기 구현 비용 높음 | 민감한 쓰기·삭제 작업을 수행하는 프로덕션 에이전트 |

Cloud Security Alliance가 2026년 3월 공개한 초안 프레임워크는 OAuth 2.0·OIDC·SPIFFE/SPIRE·SCIM을 모두 검토한 뒤, 결국 핵심은 "상시 권한(standing privilege)을 없애고 의도가 선언된 시점에만, 범위와 시간이 제한된 권한을 발급하는 것"이라고 결론 내린다. 표준이 완성되길 기다리기보다, 지금 당장은 자체 레지스트리와 JIT 그랜트 로직을 먼저 만들어 두는 쪽이 현실적이다.

## 실제 프로젝트 진행 순서

1. **인벤토리부터 센다.** 도구를 고르기 전에, 지금 조직에 떠 있는 서비스 계정·API 키·에이전트 신원이 몇 개인지부터 뽑아본다. 대부분 이 숫자를 처음 보고 놀란다.
2. **소유자 없는 발급을 막는다.** 신원 생성 요청에 `owner`, `purpose`, `expiry` 세 필드를 필수값으로 만든다. 소유자가 없는 신원은 애초에 발급 자체를 거부한다.
3. **만료일을 기본값으로 깐다.** 프로젝트성 에이전트는 90일, 상시 운영 에이전트도 분기 단위 재승인(re-attestation)을 기본으로 둔다. "영구"는 선택이 아니라 예외 승인을 거쳐야만 가능하게 한다.
4. **표준 격차는 자체 레지스트리로 메운다.** SCIM이 에이전트 라이프사이클 이벤트를 완전히 표준화하기 전까지는, 신원·소유자·범위·마지막 사용 시각을 추적하는 내부 테이블을 먼저 둔다. 나중에 표준이 성숙하면 그 위에 얹으면 된다.
5. **민감 작업부터 JIT로 전환한다.** 배포, 삭제, 결제처럼 되돌리기 어려운 작업에 쓰이는 에이전트부터 상시 권한을 걷어내고, 작업 요청 시점에만 범위·시간 제한 그랜트를 발급하는 구조로 바꾼다.
6. **회수 훅을 연결한다.** 소유자 퇴사, 프로젝트 아카이브, 레포 삭제 같은 이벤트가 발생하면 연결된 에이전트 신원도 자동으로 폐기되도록 기존 HR·프로젝트 관리 시스템과 웹훅으로 연결한다.

```text
# 최소 레지스트리 스키마 예시
agent_identity:
  id: svc-ai-invoice-parser
  owner: team-finance-platform
  purpose: "청구서 OCR 파싱 배치"
  scopes: [storage:read, invoice-db:write]
  created_at: 2026-10-21
  expires_at: 2027-01-19
  last_used_at: 2026-10-21T09:12:00Z
  status: active   # active | quarantined | revoked
```

## 실무 포인트

- 이름 규칙을 강제한다. `owner-system-purpose` 형태로 신원 이름을 강제하면, 레지스트리 없이 로그만 봐도 누구 것인지 바로 알 수 있다.
- credential이 코드나 `.env` 파일에 박혀 있는지 정기적으로 스캔한다. 레지스트리에만 의존하면, 레지스트리 밖에서 발급된 "그림자 신원"을 놓친다.
- 90일 이상 호출이 없는 신원은 자동 격리(quarantine) 후 소유자에게 확인을 요청하고, 응답이 없으면 폐기한다. "혹시 몰라서 살려둔다"가 좀비 신원이 쌓이는 가장 흔한 경로다.

## 마무리

- 에이전트가 늘어날수록 진짜 문제는 권한 설계가 아니라 "지금 몇 개가 떠 있고 누가 책임지는가"를 아는 인벤토리 문제다.
- SCIM 같은 표준이 아직 에이전트 라이프사이클을 완전히 커버하지 못하므로, 당장은 소유자·만료일 필수화와 자체 레지스트리로 격차를 메운다.
- 상시 권한을 걷어내고 민감 작업부터 JIT 그랜트로 전환하는 것이, 에이전트 수가 사람보다 수십 배 많아지는 시대의 기본 방어선이다.
