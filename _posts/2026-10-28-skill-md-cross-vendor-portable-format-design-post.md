## 도입

"우리 팀이 만든 PR 리뷰 Skill, Claude Code뿐 아니라 ChatGPT나 Cursor에서도 똑같이 쓰고 싶어요." 사내에 에이전트 확장 기능을 만들어본 팀이라면 자연스럽게 나오는 요구다. 불과 1년 전만 해도 이건 거의 불가능한 요구였다. Claude의 도구 정의, OpenAI의 커스텀 GPT 액션, Cursor의 규칙 파일이 서로 다른 스키마를 썼고, 한 벤더용으로 만든 확장은 다른 벤더에서 처음부터 다시 작성해야 했다.

그런데 이 전제가 최근 몇 달 사이 빠르게 무너지고 있다. OpenAI가 Codex CLI와 ChatGPT에 Anthropic이 공개한 `SKILL.md` 포맷을 그대로 채택했고, Cursor도 `.cursor/skills/` 폴더로 같은 구조를 받아들였다. 2026년 9월 30일에는 구글이 제미나이 앱의 커스텀 어시스턴트 기능인 Gems를 같은 `SKILL.md` 기반 "Skills"로 전환한다고 발표했다(Workspace는 10월 5일, 제미나이 앱은 10월 13일부터 순차 적용). 여러 벤더가 약속이라도 한 듯 같은 파일 포맷으로 수렴하고 있는 셈이다. 빌더에게 질문이 바뀌었다 — "어떤 벤더 전용 포맷으로 만들 것인가"가 아니라 "이 포맷을 벤더 중립적으로 설계해서 한 번 만들고 여러 런타임에서 재사용할 것인가"로.

## 왜 지금까지 파편화돼 있었나

각 에이전트 벤더는 "도구를 어떻게 설명할 것인가"를 각자의 방식으로 풀었다. OpenAI의 함수 호출(function calling)은 JSON 스키마로 파라미터를 정의하고, Claude의 tool_use는 비슷하지만 세부 필드가 다르며, Cursor의 규칙 파일은 자연어 지시문 중심이었다. 세 방식 모두 "모델에게 무엇을 할 수 있는지 알려준다"는 같은 목적을 가지면서도 서로 호환되지 않았다. 사내에 확장 기능을 하나 만들면 지원하는 에이전트 수만큼 같은 로직을 다른 포맷으로 반복해서 작성해야 했다.

`SKILL.md`가 이 파편화를 깨는 방식은 단순하다. YAML 프런트매터로 메타데이터(이름, 설명, 트리거 조건)를 적고, 본문은 순수 마크다운으로 지시문을 적으며, 필요하면 참조 파일을 추가로 둔다. 이 구조가 Progressive Disclosure(필요할 때만 본문 전체를 컨텍스트에 로드)를 지원한다는 점까지 여러 벤더가 똑같이 채택하면서, 포맷 자체가 사실상의 공통 분모가 됐다.

## 전체 시스템에서의 위치

사내에서 만든 Skill 하나가 여러 에이전트 런타임에 걸쳐 동작하려면, "포맷은 공통, 실행 환경은 벤더별"이라는 구조로 설계해야 한다.

<img src="/assets/images/posts/2026-10-28-skill-md-cross-vendor-portable-format-design-1.svg" alt="사내 Skill 저장소에서 작성된 공통 SKILL.md 파일이 Claude Code, Codex CLI, Cursor, Gemini 앱 등 서로 다른 런타임의 각자 다른 discovery·로딩 메커니즘을 통해 각 에이전트에 적재되는 구조를 보여주는 다이어그램" style="width:100%;">

- **사내 Skill 저장소**: `SKILL.md` + 참조 파일(스크립트, 템플릿)을 버전 관리하는 공통 소스.
- **런타임별 로더**: Claude Code는 `.claude/skills/`, Cursor는 `.cursor/skills/`, Codex CLI·ChatGPT는 자체 디렉터리 규칙으로 같은 파일을 읽는다. 포맷은 같아도 "언제 어떻게 로드하는가"의 discovery 메커니즘은 벤더마다 다르다.
- **벤더 고유 확장**: 각 런타임이 `SKILL.md` 표준 필드 외에 자체 확장 필드(특정 도구 접근 권한, 벤더 전용 메타데이터)를 추가로 지원할 수 있다. 공통 포맷에만 의존하면 이 확장 기능은 포기해야 한다.

## 선택의 트레이드오프

| 기준 | 벤더 중립 `SKILL.md` | 벤더 전용 최적화 포맷 |
|---|---|---|
| 이식성 | 여러 런타임에서 재사용 가능 | 해당 벤더에서만 동작 |
| 벤더 고유 기능 활용 | 공통 분모만 활용 가능 | 벤더 특화 기능(확장 tool, 긴 컨텍스트 등) 최대 활용 |
| 유지보수 범위 | 파일 하나만 관리 | 지원 벤더 수만큼 파일 관리 |
| 생태계 재사용 | 마켓플레이스·커뮤니티 Skill을 그대로 가져다 씀 | 자체 생태계만 |
| 표준 성숙도 리스크 | 스펙이 아직 빠르게 바뀌는 중(1년 미만) | 벤더 자체 변경 속도에만 대응 |
| 적합한 상황 | 여러 팀·여러 도구를 넘나드는 범용 작업 | 한 벤더에 강하게 락인되어 있고 그 벤더만의 기능이 핵심일 때 |

단일 벤더에 이미 깊게 결합돼 있고, 그 벤더만의 고유 기능(예: 매우 큰 컨텍스트 윈도우를 전제로 한 워크플로)을 최대로 끌어써야 하는 조직이라면, 벤더 중립 포맷으로 공통분모만 쓰는 것이 오히려 손해일 수 있다. 하지만 여러 팀이 서로 다른 에이전트 도구를 쓰고 있거나, 특정 벤더에 대한 의존도를 낮추고 싶은 조직이라면 지금이 벤더 중립 설계로 전환할 적기다.

## 코드 예제

```markdown
---
name: pr-review-checklist
description: PR 변경분을 사내 코딩 가이드 기준으로 점검한다. 변경된 파일 리스트가 보이면 사용한다.
---

# PR 리뷰 체크리스트

1. 변경된 파일 중 테스트 커버리지가 없는 로직이 있는지 확인한다.
2. 사내 네이밍 컨벤션(`docs/naming.md` 참조)을 따르는지 확인한다.
3. 벤더별 확장 필드는 이 파일에 넣지 않고, 런타임별 설정 파일에서 보강한다.
```

## 실무 포인트

- **벤더 특화 기능은 분리한다.** `SKILL.md` 본문에는 공통 분모 로직만 담고, 특정 벤더의 확장 기능이 필요하면 런타임별 설정 파일이나 래퍼로 분리해 포맷 자체의 이식성을 지킨다.
- **Discovery 동작 차이를 직접 테스트한다.** Progressive Disclosure가 "언제 본문을 로드할지" 판단하는 방식은 벤더마다 구현이 조금씩 다르다. 같은 파일이라도 한 런타임에서 잘 트리거되던 Skill이 다른 런타임에서는 로드되지 않을 수 있다.
- **외부 마켓플레이스에서 가져온 Skill은 별도 검증 게이트를 거친다.** 포맷이 공통이라는 것과 안전하다는 것은 별개 문제다. 설치 전 프롬프트 인젝션·과도한 권한 요구 여부를 점검하는 절차는 그대로 유지해야 한다.
- **표준이 아직 어리다는 점을 감안한다.** 스펙이 1년 안쪽으로 짧은 기간에 여러 벤더로 퍼진 만큼, 세부 필드나 동작이 앞으로도 바뀔 가능성이 있다. 사내 Skill을 설계할 때 버전을 명시하고 변경 이력을 추적할 장치를 함께 둔다.

## 마무리

- Claude·OpenAI·Cursor에 이어 구글까지 제미나이 앱의 Gems를 `SKILL.md` 기반 Skills로 전환하면서, 이 포맷이 사실상 벤더를 넘나드는 공통 표준으로 자리 잡고 있다.
- 포맷은 공통이어도 런타임별 discovery·로딩 메커니즘과 벤더 고유 확장 기능은 다르므로, "포맷은 공통, 실행 환경은 벤더별"이라는 구조로 설계해야 한다.
- 여러 도구를 넘나드는 범용 작업은 벤더 중립 설계가, 특정 벤더 고유 기능이 핵심인 작업은 벤더 전용 최적화가 더 맞는다는 기준으로 판단한다.
