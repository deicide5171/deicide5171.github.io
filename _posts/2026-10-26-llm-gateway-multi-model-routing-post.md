## 도입

"자주 쓰는 간단한 분류 작업은 싼 모델로 돌리고, 복잡한 추론이 필요한 요청만 Claude Opus로 보내주세요." 처음 이 요구를 받으면 가장 빠른 길은 호출 코드에 if문 하나를 추가하는 것이다. 요청 종류를 보고 모델 이름을 바꿔 호출하면 끝나는 것처럼 보인다. 그런데 모델이 세 개, 네 개로 늘고, 제공자마다 요청 포맷과 레이트리밋 정책이 다르고, 한 프로바이더가 장애를 내는 시점마다 이 if문은 감당할 수 없이 복잡해진다.

2026년 들어 OpenAI 호환 엔드포인트 포맷이 사실상 업계 표준처럼 쓰이면서, 이 문제를 애플리케이션 코드가 아니라 별도의 중개 계층 — LLM 게이트웨이 — 에서 풀자는 흐름이 뚜렷해졌다. 이 글은 "여러 모델을 섞어 쓰고 싶다"는 같은 요구가 왜 새로운 시스템 구성요소로 번역되는지, 그리고 그 구성요소를 직접 만들지 기존 도구를 가져다 쓸지 판단하는 기준을 정리한다.

## 전체 시스템에서의 위치

게이트웨이가 없으면 애플리케이션 코드가 각 프로바이더의 SDK를 직접 호출하고, 모델 선택·재시도·비용 집계 로직까지 전부 떠안는다. 게이트웨이를 두면 애플리케이션은 게이트웨이 하나의 엔드포인트만 알면 되고, 모델 선택·정책 적용·실패 복구는 그 뒤에서 처리된다.

<img src="/assets/images/posts/2026-10-26-llm-gateway-multi-model-routing-1.svg" alt="애플리케이션과 여러 LLM 프로바이더 사이에 위치한 게이트웨이의 라우팅 구조" style="width:100%;">

- **애플리케이션 → 게이트웨이**: 요청에는 모델을 직접 지정하지 않고, "작업 종류"나 "품질/비용 선호도" 같은 의도만 실어 보낸다.
- **게이트웨이 내부**: 라우팅 정책(비용, p95 지연시간, 실패율)에 따라 실제 호출할 모델을 고르고, 실패 시 대체 모델로 자동 전환한다.
- **게이트웨이 → 여러 프로바이더**: 각 프로바이더의 고유 포맷 차이를 흡수해 애플리케이션에는 정규화된 응답만 돌려준다.

## 선택의 트레이드오프

| 구성 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 벤더 SDK 직접 호출 | 구조 단순, 추가 지연시간 없음 | 모델 전환마다 호출 코드 전면 수정, 장애 시 폴백 없음 | 모델을 하나만 쓰는 초기 단계 |
| 오픈소스 셀프호스트 게이트웨이 | 요청·응답이 우리 네트워크를 벗어나지 않음, 라우팅 정책 자유도 높음 | 직접 운영·튜닝 부담, 트래픽 늘면 게이트웨이 자체가 성능 병목이 될 수 있음 | 데이터 레지던시 요구가 있거나 이미 플랫폼팀이 있는 조직 |
| 매니지드 게이트웨이 서비스 | 운영 부담 거의 없음, 가격 피드·대시보드 기본 제공 | 게이트웨이 자체가 새 외부 의존성이 됨, 트래픽 기준 약정 비용 | 빠르게 멀티 프로바이더 구성을 붙이고 싶은 소규모 팀 |
| 직접 구축 | 조직 특유의 라우팅·감사 요구에 완전히 맞춤 | 개발·유지보수 비용이 가장 큼 | 규제·감사 요구가 표준 도구로 못 채워지는 경우 |

판단 기준은 두 가지다. 첫째, **요청·응답 데이터가 외부 중개 서비스를 거쳐도 되는가** — 안 된다면 오픈소스를 우리 네트워크 안에 셀프호스트하거나 직접 구축해야 한다. 둘째, **라우팅 정책이 표준적인가, 조직 특유인가** — 비용·지연시간 기준의 일반적인 라우팅이면 기존 도구로 충분하고, 감사 로그 형식이나 내부 쿼터 체계처럼 특수한 요구가 있으면 그 부분만 직접 만든 레이어로 감싼다.

## 실제 프로젝트 진행 순서

1. **현재 호출 중인 모델과 호출 목적을 먼저 나열한다.** 분류·요약처럼 저비용 모델로 내려도 품질 차이가 없는 작업과, 복잡한 추론이 꼭 필요한 작업을 가른다.
2. **라우팅 기준을 비용만으로 정하지 않는다.** p95 지연시간, 실패율, 작업 복잡도를 함께 기준에 넣고 우선순위를 정한다.
3. **오픈소스 게이트웨이를 스테이징에 먼저 붙여 오버헤드를 실측한다.** 초당 요청 수, 추가 지연시간이 실제 트래픽 패턴에서 허용 범위인지 확인한다.
4. **실패 복구 정책을 트래픽이 가장 큰 경로부터 적용한다.** 429·503 응답을 받으면 다른 프로바이더로 자동 전환하는 규칙을 먼저 검증한다.
5. **모델 믹스를 바꾸기 전에 비용 추적 대시보드부터 세운다.** 바꾸고 나서 추적을 붙이면 전후 비교 자체가 불가능해진다.

```yaml
# 셀프호스트 게이트웨이 라우팅 정책 예시
model_list:
  - model_name: fast-classify
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY
  - model_name: deep-reasoning
    litellm_params:
      model: anthropic/claude-opus-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  routing_strategy: latency-based-routing
  fallbacks:
    - deep-reasoning: ["fast-classify"]
  retry_policy:
    rate_limit_error_retries: 2
```

## 실무 포인트

- OpenAI 호환 포맷이 표준처럼 쓰여도 tool-calling 스키마, 안전 설정, 토큰 계산 방식은 모델마다 달라 게이트웨이가 모든 차이를 완전히 숨겨주지는 않는다. 모델 전환 시 이 부분은 여전히 수동 검증이 필요하다.
- 게이트웨이가 전체 LLM 호출의 단일 장애점이 될 수 있다. 게이트웨이 자체의 헬스체크·이중화를 빠뜨리면 "장애 복구를 위해 들인 계층"이 거꾸로 새로운 장애 지점이 된다.
- 배치·비실시간 작업은 프로바이더의 배치 API(지연 허용 대신 저가)를 별도 라우팅 규칙으로 태워야 실제 비용 절감 효과가 난다. 실시간 경로와 같은 규칙을 쓰면 이 이점을 놓친다.

## 마무리

- "여러 모델을 섞어 쓰고 싶다"는 요구는 애플리케이션 코드의 if문이 아니라, 라우팅·실패 복구·비용 추적을 한 곳에 모으는 게이트웨이라는 별도 시스템 구성요소로 번역해야 한다.
- 선택 기준은 데이터가 외부 중개 서비스를 거쳐도 되는지, 라우팅 정책이 표준적인지 조직 특유인지 두 가지다.
- 진행 순서는 작업 분류 → 라우팅 기준 설계 → 오버헤드 실측 → 실패 복구 적용 → 비용 추적 선행 순이다.
