## 왜 지금 API 버저닝인가

API는 한 번 공개되면 그 순간부터 "계약"이 된다. 프론트엔드, 모바일 앱, 외부 파트너, 서드파티 개발자가 이미 그 응답 구조를 가정하고 코드를 짜놓았기 때문에, 필드 이름 하나만 바꿔도 어딘가는 깨진다. 그런데 서비스는 계속 진화해야 하고, 필드는 추가·삭제되고, 응답 구조 자체가 바뀌어야 하는 순간이 반드시 온다. 이 둘 사이의 긴장을 관리하는 것이 API 버저닝이다.

문제는 "버전을 어디에 표시할 것인가"부터 의견이 갈린다는 점이다. URL에 박아 넣을지, 헤더로 뺄지, HTTP의 콘텐츠 협상 메커니즘을 그대로 활용할지에 따라 클라이언트 개발 경험, 캐싱 동작, 라우팅 구현 난이도가 전부 달라진다. 정답은 하나가 아니고, 서비스의 소비자 구성과 운영 방식에 따라 유리한 전략이 다르다.

이 글에서는 실무에서 가장 많이 쓰이는 세 가지 버저닝 전략을 비교하고, 각각 언제 선택하면 좋은지 정리한다.

## 핵심 개념 1: 버전을 바꿔야 하는 변경과 아닌 변경

버저닝 전략을 논의하기 전에 먼저 구분해야 할 것은 "이 변경이 정말 새 버전을 필요로 하는가"이다. 불필요하게 버전을 올리면 유지보수 부담만 늘어난다.

| 변경 유형 | 예시 | 새 버전 필요 여부 |
|---|---|---|
| 필드 추가(선택적) | 응답에 `createdAt` 필드 추가 | 불필요 — 기존 클라이언트는 무시하고 지나감 |
| 필드 이름 변경 | `user_name` → `userName` | 필요 — 기존 클라이언트 파싱 실패 |
| 필드 삭제 | 더 이상 쓰지 않는 필드 제거 | 필요 — 참조하던 클라이언트 깨짐 |
| 응답 구조 변경 | 배열 응답 → 페이지네이션 객체로 감싸기 | 필요 — 파싱 로직 자체가 달라짐 |
| 필수 파라미터 추가 | 요청에 필수 헤더·바디 필드 신설 | 필요 — 기존 요청이 거부됨 |

이 표에서 알 수 있듯 "하위 호환이 깨지는가(breaking change)"가 버전을 올릴지 말지의 유일한 기준이다. 선택적 필드 추가처럼 하위 호환이 유지되는 변경은 같은 버전 안에서 자유롭게 진행해도 된다.

## 핵심 개념 2: 세 가지 버저닝 전략 비교

<img src="/assets/images/posts/2026-08-18-api-versioning-strategy-1.svg" alt="URI 경로, 커스텀 헤더, Accept 헤더 콘텐츠 협상 3가지 API 버저닝 전략이 각각 다른 위치에서 버전을 서버에 전달하는 구조도" style="width:100%;">

| 전략 | 표기 방식 | 장점 | 단점 |
|---|---|---|---|
| URI 경로 버저닝 | `/v2/users/42` | 눈으로 바로 보임, 캐싱·라우팅·문서화 단순, 브라우저에서 바로 테스트 가능 | URI가 "같은 리소스인데 다른 주소"가 되어 REST 원칙상 리소스 식별자 순수성이 흐려짐 |
| 커스텀 헤더 버저닝 | `X-API-Version: 2` | URI는 고정, 리소스 식별자가 버전과 무관해짐 | 헤더는 문서를 봐야 알 수 있음, curl 테스트 시 헤더를 매번 붙여야 함 |
| 콘텐츠 협상(Accept 헤더) | `Accept: application/vnd.api.v2+json` | HTTP 표준 메커니즘을 그대로 활용, 리소스당 버전까지 세밀하게 제어 가능 | 구현이 가장 복잡, 브라우저 주소창 테스트 불가, 클라이언트 라이브러리 설정 필요 |

세 전략 모두 결국 서버 쪽에서 "요청 어딘가에 담긴 버전 신호를 읽어서 적절한 핸들러로 분기한다"는 동작은 동일하다. 차이는 그 신호를 어디에 담느냐, 그리고 그로 인해 캐싱·문서화·클라이언트 구현이 얼마나 쉬워지거나 어려워지느냐에 있다.

## 핵심 개념 3: 실제 구현에서 자주 부딪히는 지점

URI 버저닝은 구현이 단순한 대신, 버전이 늘어날수록 컨트롤러 코드가 `v1`, `v2`, `v3`로 중복되기 쉽다. 이때 변경되지 않은 엔드포인트까지 매번 새 버전 경로로 복사하지 않도록, 버전별 라우팅과 실제 비즈니스 로직을 분리하는 것이 핵심이다.

헤더·콘텐츠 협상 방식은 캐싱 계층(CDN, 리버스 프록시)에서 헤더 값을 캐시 키에 포함시키지 않으면 v1 응답이 v2 요청에도 그대로 반환되는 사고가 날 수 있다. `Vary` 헤더를 정확히 설정하는 것이 필수다.

## 예제: Spring Boot에서 헤더 기반 버저닝 라우팅

```java
@RestController
@RequestMapping("/users")
public class UserController {

    // 헤더가 없거나 값이 1이면 v1 핸들러
    @GetMapping(value = "/{id}", headers = "X-API-Version=1")
    public UserV1Response getUserV1(@PathVariable Long id) {
        return userService.getUserAsV1(id);
    }

    // 헤더 값이 2이면 v2 핸들러 — 응답 구조가 변경된 버전
    @GetMapping(value = "/{id}", headers = "X-API-Version=2")
    public UserV2Response getUserV2(@PathVariable Long id) {
        return userService.getUserAsV2(id);
    }

    // 헤더가 없는 경우 기본 버전(v1)으로 폴백
    @GetMapping("/{id}")
    public UserV1Response getUserDefault(@PathVariable Long id) {
        return userService.getUserAsV1(id);
    }
}
```

핵심은 `headers` 속성으로 스프링 MVC 라우팅 단계에서부터 버전을 분기시킨다는 점이다. 컨트롤러 메서드 안에서 `if (version == 2)` 식으로 분기하지 않아도 되므로, 버전별 응답 DTO와 서비스 로직을 명확히 분리할 수 있다. 헤더가 없는 클라이언트를 위한 기본 버전 폴백도 반드시 함께 정의해야 한다.

## 실무 포인트

- **외부 공개 API일수록 URI 버저닝이 유리하다**: 서드파티 개발자는 문서를 꼼꼼히 안 읽는 경우가 많다. URL에 버전이 보이면 실수로 잘못된 버전을 호출할 가능성이 줄어든다.
- **내부 서비스 간 API는 헤더·콘텐츠 협상이 유리할 수 있다**: 리소스 식별자를 버전과 분리하고 싶고, 클라이언트가 소수의 통제된 서비스뿐이라면 헤더 관리 부담이 크지 않다.
- **버전은 최소한으로 유지한다**: v1, v2, v3가 동시에 운영되는 기간이 길어질수록 테스트·문서·인프라 비용이 배로 늘어난다. 신규 버전 출시 시 구버전 종료(deprecation) 일정을 API 응답 헤더나 문서로 명시하는 것이 좋다.
- **버전은 메이저 변경에만 사용한다**: 하위 호환되는 변경까지 버전을 올리면 클라이언트 마이그레이션 피로가 누적된다. 시맨틱 버저닝의 메이저 버전 개념과 맞춰 사용하는 편이 관리하기 쉽다.
- **캐싱 계층의 `Vary` 헤더 설정을 놓치지 않는다**: 헤더·콘텐츠 협상 방식을 쓴다면 CDN·프록시 설정에서 버전 헤더를 캐시 키에 반드시 포함시켜야 한다.

## 3줄 요약

- API 버저닝은 하위 호환이 깨지는 변경(breaking change)에만 필요하며, 선택적 필드 추가 같은 비파괴적 변경은 같은 버전 안에서 처리한다.
- URI 경로 버저닝은 단순하고 눈에 잘 띄어 외부 공개 API에 유리하고, 헤더·콘텐츠 협상 방식은 리소스 식별자를 버전과 분리할 수 있어 내부 서비스 간 API에 적합하다.
- 어떤 전략을 쓰든 버전 수는 최소로 유지하고, 캐싱 계층의 `Vary` 설정과 구버전 종료 일정 공지를 함께 챙겨야 한다.
