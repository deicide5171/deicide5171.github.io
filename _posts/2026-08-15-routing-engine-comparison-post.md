## 왜 지금 이 이야기인가

지도 위에서 최적 경로를 계산하는 라우팅 엔진은 배달, 물류, 내비게이션 서비스의 핵심 컴포넌트다. 상용 API(구글 다이렉션, 여기(HERE) 등)를 쓰면 빠르게 시작할 수 있지만, 호출량이 많아지면 비용이 급격히 늘어나고 커스텀 비용 함수(도로 통행 제한, 화물차 규격 등)를 적용하기 어렵다는 한계가 있다. 그래서 자체 인프라에 오픈소스 라우팅 엔진을 올려 운영하는 팀이 꾸준히 늘고 있는 것으로 보인다.

대표적인 오픈소스 라우팅 엔진으로 OSRM, Valhalla, GraphHopper가 자주 언급된다. 세 엔진 모두 OpenStreetMap 데이터를 기반으로 하지만 알고리즘 설계와 확장성 철학이 상당히 다르기 때문에, 서비스 요구사항에 따라 선택이 갈린다.

## 세 엔진 비교

| 항목 | OSRM | Valhalla | GraphHopper |
|---|---|---|---|
| 핵심 알고리즘 | Contraction Hierarchies(CH) | 양방향 A* + 동적 비용 | CH 및 Landmark 기반(ALT) |
| 커스터마이징 | 제한적(CH 전처리에 비용 함수 고정) | 유연함(런타임 비용 함수 조정 가능) | 유연함(커스텀 모델 DSL 제공) |
| 다중 교통수단 | 차량 중심, 도보/자전거는 프로필 전환 필요 | 차량/도보/자전거/대중교통 통합 지원 | 차량/도보/자전거 지원, 대중교통은 별도 확장 |
| 경로 재계산 속도 | 매우 빠름(전처리 덕분) | 상대적으로 느림(런타임 계산 비중 큼) | 빠름(CH 사용 시) |
| 메모리 사용 | 낮은 편 | 높은 편(다양한 부가 데이터 포함) | 중간 |
| 대표 사용처 | 대규모 정적 라우팅(배달 ETA 등) | 다중 프로필/등시선(isochrone) 분석 | 범용 라우팅, 커스텀 비용 함수 요구가 많은 서비스 |

## 알고리즘 차이가 만드는 실질적 차이

OSRM은 Contraction Hierarchies를 전처리 단계에서 강하게 적용해 쿼리 시점 계산량을 최소화한다. 이 덕분에 대규모 트래픽에서도 매우 낮은 지연시간을 보여주는 것으로 알려져 있지만, 비용 함수(도로별 가중치)가 전처리 시점에 고정되기 때문에 "화물차는 이 다리를 못 지나간다" 같은 동적 제약을 실시간으로 반영하기 까다롭다. 이런 제약을 우회하려면 프로필을 미리 여러 개 만들어 각각 전처리해두는 방식을 쓰게 된다.

Valhalla는 반대로 런타임에 비용 함수를 계산하는 비중이 크다. 이 때문에 단순 CH 기반보다는 쿼리 속도가 느릴 수 있지만, 그만큼 통행 제한·시간대별 규제·다양한 이동수단별 프로필을 유연하게 다룰 수 있다. 등시선(isochrone) 분석처럼 "특정 시간 내 도달 가능한 영역"을 구하는 기능이 기본으로 강력하게 지원되는 점도 특징이다.

GraphHopper는 CH와 커스텀 모델(Custom Model) DSL을 함께 제공해 두 엔진의 중간 지점을 노린다. JSON 기반의 커스텀 모델로 도로 속성별 가중치를 비교적 유연하게 조정하면서도, CH 프로필을 미리 계산해 속도를 챙기는 절충안을 택하고 있다.

## 예제: 라우팅 서버 실행

```bash
# OSRM: 데이터 전처리 및 서버 실행 예시
osrm-extract -p car.lua seoul.osm.pbf
osrm-contract seoul.osrm
osrm-routed seoul.osrm
```

```yaml
# GraphHopper 커스텀 모델 예시 (화물차 통행 제한 반영)
priority:
  - if: "road_class == MOTORWAY"
    multiply_by: 1.0
  - if: "max_width < 2.5"
    multiply_by: 0
speed:
  - if: "road_class == RESIDENTIAL"
    limit_to: 30
```

## 선택 기준

- **대량 정적 라우팅(배달 ETA, 물류 최적화)**: 전처리 비용을 감수할 수 있고 쿼리 속도가 최우선이라면 OSRM이 유리하다.
- **동적 제약과 등시선 분석이 필요**: 시간대별 규제, 화물차 규격, 등시선 분석을 함께 다뤄야 한다면 Valhalla가 적합하다.
- **커스텀 비용 함수 요구가 잦고 운영 편의성이 중요**: JSON 기반으로 비용 모델을 자주 바꿔야 한다면 GraphHopper의 커스텀 모델이 유리한 것으로 보인다.
- **다중 교통수단 통합**: 대중교통까지 하나의 엔진에서 다뤄야 한다면 Valhalla의 통합 지원이 상대적으로 앞선다.

## 실무 포인트와 주의사항

- 세 엔진 모두 OSM 데이터 품질에 크게 의존하므로, 서비스 지역의 OSM 데이터 완성도를 먼저 점검해야 한다.
- 전처리 기반 엔진(OSRM, GraphHopper CH)은 도로 데이터가 갱신될 때마다 재전처리가 필요하므로 배치 스케줄을 설계해야 한다.
- 메모리 사용량은 지도 범위와 프로필 수에 비례해 커지므로, 전국 단위 이상으로 확장할 계획이라면 사전에 용량 산정이 필요하다.
- 다중 프로필(도보/자전거/화물차 등)을 운영한다면 엔진별로 프로필 관리 방식이 다르므로 초기 설계 단계에서 확인해야 한다.

## 3줄 요약

- OSRM은 CH 기반 전처리로 매우 빠르지만 동적 비용 함수 반영이 어렵다.
- Valhalla는 런타임 계산 비중이 커 유연하고 등시선 분석에 강하다.
- GraphHopper는 커스텀 모델 DSL로 두 엔진의 중간 지점을 노린다.
