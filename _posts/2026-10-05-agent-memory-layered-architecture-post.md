## 왜 지금 이 문제가 불거지는가

"에이전트가 하루 종일 돌아가면서 작업하는데, 어제 내린 결정을 오늘 또 처음부터 설명 안 해도 되게 해주세요." 상시 가동 백그라운드 에이전트, 장시간 코딩 세션, 여러 날에 걸친 리서치 작업이 흔해지면서 이 요구가 거의 모든 프로젝트에 등장한다. 처음 드는 생각은 "컨텍스트 창을 더 큰 모델로 바꾸면 되지 않나"다. 실제로 최근 모델들은 백만 토큰급 컨텍스트와 서버 측 자동 압축을 제공한다. 하지만 이건 문제를 푸는 게 아니라 **문제가 터지는 시점을 뒤로 미루는 것**에 가깝다. 컨텍스트 창이 아무리 커져도 도구 호출 결과, 파일 내용, 중간 추론이 계속 쌓이는 장기 실행 에이전트는 결국 한계에 부딪히고, 그 순간 무엇을 버리고 무엇을 남길지 결정해야 한다.

더 근본적인 문제는 "기억해줘"라는 한 마디가 실제로는 서로 다른 세 가지 요구를 뭉뚱그린다는 점이다. 같은 세션 안에서 수백 번의 도구 호출을 거친 뒤에도 초반 결정을 잊지 않는 것, 세션이 끝나고 다음 날 다시 시작했을 때도 전에 합의한 내용을 아는 것, 그리고 "이 프로젝트에서는 이런 규칙을 지킨다"는 정체성 수준의 지침을 매번 재설명하지 않는 것은 전혀 다른 저장 메커니즘을 요구한다. 이 구분 없이 "메모리 좀 넣어주세요"로 접근하면 벡터 DB 하나 붙이고 끝내는 얕은 설계가 되기 쉽다.

## 요구사항을 기술 문제로 번역하기

"기억해줘"를 들었을 때 먼저 물어야 할 질문은 세 가지다. 첫째, **이 정보가 지금 이 작업 안에서만 필요한가, 아니면 세션이 끝난 뒤에도 다른 작업에서 다시 꺼내 써야 하는가.** 둘째, **압축 과정에서 요약으로 뭉개져도 괜찮은 정보인가, 아니면 원문 그대로 다시 불러올 수 있어야 하는가.** 셋째, **매 세션 시작 시 무조건 로드돼야 하는 규칙인가, 아니면 필요할 때만 검색해서 가져오면 되는 지식인가.** 이 세 질문의 답이 바로 워크스페이스 파일, 런타임 압축, 장기 저장소라는 세 계층에 각각 대응한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-05-agent-memory-layered-architecture-1.svg" alt="워크스페이스 파일, 런타임 컨텍스트와 압축, 장기 메모리 저장소로 구성된 3계층 에이전트 메모리 아키텍처와 각 계층 사이에서 주소 기반으로 원문을 다시 불러오는 아카이브 로그 구조도" style="width:100%;">

가장 바깥층은 **워크스페이스 파일**이다. 프로젝트 규칙, 코딩 컨벤션, 반복되는 지침을 짧은 마크다운 파일로 저장소에 두고 세션 시작 시 항상 읽는다. 비용이 가장 싸고 구현도 단순하지만, 그만큼 담을 수 있는 양도 제한적이다. 중간층은 **런타임 컨텍스트와 압축**이다. 한 세션 안에서 도구 호출과 추론이 쌓이다가 컨텍스트 한계에 가까워지면, 오래된 턴을 지우거나(단순 절단), 요약하거나(계층적 요약), JSON 상태로 접어 넣거나(상태 폴딩), 아카이브에 옮기고 주소만 남기는(Addressable Recall Compaction) 방식 중 하나로 처리한다. 가장 안쪽층은 **장기 저장소**다. 세션이 끝나도 남아야 하는 사실·결정·사용자 선호를 벡터 DB나 그래프 DB에 넣고, 다음 세션에서 검색(RAG)으로 다시 가져온다. 이 세 계층은 독립적으로 동작하지 않는다 — 장기 저장소에서 검색해 온 내용도 결국 런타임 컨텍스트에 들어오고, 거기서 다시 압축 대상이 된다.

압축 전략에서 최근 주목받는 것이 Addressable Recall Compaction(ARC)이다. 기존 방식들은 압축 시점에 "요약할지 버릴지"를 미리 결정해야 하는데, 이 결정이 틀리면 나중에 꼭 필요했던 세부 정보가 영구히 사라진다. ARC는 도구 실행 결과를 추가 전용(append-only) 로그에 원문 그대로 저장하고 짧은 ID만 발급한 뒤, 활성 컨텍스트에는 그 ID와 한 줄 요약만 남긴다. 에이전트는 필요할 때 그 ID로 원문을 다시 요청할 수 있다 — 도구를 재실행하지 않고도 원본을 복원하는 것이다. 핵심은 "압축 시점에 정보를 버리지 않고, 압축 시점과 조회 시점을 분리한다"는 설계다.

## 선택의 트레이드오프

| 전략 | 정보 손실 위험 | 토큰 비용 | 구현 복잡도 | 적합한 상황 |
|---|---|---|---|---|
| 단순 절단(오래된 턴 삭제) | 매우 높음 | 가장 낮음 | 가장 낮음 | 과거 맥락이 거의 불필요한 단발성 작업 |
| 계층적 요약 | 중간~높음(세부 정보 뭉개짐) | 낮음 | 중간 | 전체 흐름만 유지하면 되는 대화형 작업 |
| 상태 폴딩(JSON 구조화) | 중간(스키마 밖 정보 손실) | 낮음 | 중간~높음 | 상태가 명확히 정의되는 반복적 워크플로 |
| RAG 기반 장기 저장 | 낮음(검색 실패 시에만) | 요청당 추가 비용 | 높음 | 세션을 넘나드는 사실·선호 재사용 |
| Addressable Recall Compaction | 가장 낮음(원문 보존) | 아카이브 저장 비용 | 가장 높음 | 장시간 실행·고위험 에이전트 작업 |

표에서 가장 중요한 줄은 토큰 비용과 구현 복잡도의 교환 관계다. 단순 절단과 계층적 요약은 구현이 쉬운 대신 "그때는 안 중요해 보였지만 나중에 필요했던 정보"를 영구히 잃을 위험을 안고 간다. 반대로 ARC처럼 원문을 전부 보존하는 방식은 안전하지만 아카이브 저장소와 조회 인터페이스를 별도로 구축해야 하므로, 짧게 끝나는 작업에는 과한 투자다. Letta·Mem0·Zep·Cognee 같은 오픈소스 메모리 프레임워크들이 이 지점에서 각자 다른 기본값을 택한다는 점도 참고할 만하다 — Mem0는 가볍고 빠른 요약 중심, Zep은 세션 인지형 저장, Cognee는 그래프 구조로 관계를 보존하는 쪽에 가깝다.

## 실제 프로젝트 진행 순서

1. **지금 겪는 망각 실패를 세션 내부와 세션 간으로 분류한다.** "같은 작업 중에 초반 지시를 잊는다"와 "다음 날 다시 설명해야 한다"는 서로 다른 계층의 문제이므로, 섞어서 "메모리가 필요하다"고 뭉뚱그리면 안 된다.
2. **가장 싼 계층부터 도입한다.** 반복되는 규칙·컨벤션은 벡터 DB를 붙이기 전에 워크스페이스 파일(간단한 마크다운)로 먼저 해결되는지 확인한다. 대부분의 "맨날 같은 걸 또 설명한다"는 불만은 이 단계만으로 사라진다.
3. **런타임 압축 전략을 작업 특성에 맞게 고른다.** 되돌릴 일 없는 단순 대화형 작업이면 요약으로 충분하지만, 코드 수정·결제·배포처럼 원문 복원이 중요한 고위험 작업이면 ARC 같은 주소 기반 아카이빙을 검토한다.
4. **세션 간 공유가 실제로 필요한지부터 검증한다.** 장기 저장소는 구축 비용이 가장 크므로, "다음 세션에서 정말 이 정보를 다시 쓰는가"를 먼저 로그로 확인한 뒤 투자한다.
5. **압축 후 성능 저하를 수치로 추적한다.** 요약·압축을 적용한 뒤 과거 세부 정보를 다시 물었을 때의 실패율, 재질의 빈도를 모니터링해 압축 강도를 조정한다.

## 실무 포인트

**"메모리 추가"를 벡터 DB 연동과 동일시하지 않는다.** 많은 경우 워크스페이스 파일 수준의 해결로 충분하며, 장기 저장소는 세션 간 재사용이 데이터로 확인된 뒤에 투자해도 늦지 않다.

**압축 시점과 조회 시점을 분리하는 설계를 우선 검토한다.** 압축 당시에 중요도를 완벽히 판단하기는 불가능하다. 원문을 버리지 않고 주소만 남기는 구조는 나중에 "그 정보가 필요했다"는 후회를 구조적으로 줄여준다.

**프레임워크 선택보다 요구사항 분류가 먼저다.** Letta·Mem0·Zep 중 무엇을 쓸지 고민하기 전에, 지금 문제가 세션 내 압축 문제인지 세션 간 저장 문제인지부터 분명히 해야 엉뚱한 도구를 고르지 않는다.

## 마무리

- "기억해줘"는 세션 내 압축, 세션 간 저장, 정체성 규칙이라는 서로 다른 세 가지 요구를 뭉뚱그린 표현이므로, 먼저 어느 계층의 문제인지 구분해야 한다.
- 워크스페이스 파일 → 런타임 압축 → 장기 저장소 순으로 비용이 커지므로, 가장 싼 계층부터 채워가며 실제로 더 깊은 계층이 필요한지 데이터로 검증한다.
- 압축 전략은 요약·절단처럼 정보를 버리는 방식과 Addressable Recall Compaction처럼 원문을 보존하고 조회만 지연시키는 방식 사이의 트레이드오프이며, 작업의 위험도가 이 선택을 결정해야 한다.
