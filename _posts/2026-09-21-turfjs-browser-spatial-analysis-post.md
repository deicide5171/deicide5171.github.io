## 왜 모든 공간 분석을 서버로 보낼 필요는 없나

"이 지점에서 반경 1km 안에 어떤 매장이 있는가", "이 두 구역이 겹치는가" 같은 공간 분석 질문에 답하려면 대부분 PostGIS 같은 공간 DB에 쿼리를 보내는 방식을 떠올린다. 실제로 대용량 데이터나 정확한 좌표계 변환이 필요한 분석은 서버에서 처리하는 것이 맞다. 하지만 이미 브라우저에 GeoJSON 데이터가 로드되어 있는 상황에서, 사용자가 그린 도형과의 교차 여부를 확인하거나 간단한 버퍼 반경을 계산하는 정도라면, 매번 서버 왕복을 거칠 필요가 없다.

**Turf.js**는 이런 상황을 위한 순수 자바스크립트 공간 분석 라이브러리다. GeoJSON을 입력으로 받아 버퍼, 교차, 최근접점, 면적 계산 같은 연산을 브라우저(혹은 Node.js)에서 바로 수행한다. MapLibre GL JS나 OpenLayers 같은 지도 라이브러리와 함께 쓰면, 사용자가 지도를 조작하는 즉시 서버 요청 없이 결과를 화면에 반영할 수 있다.

## 잘못된 접근: 모든 연산을 서버 왕복으로 처리

"사용자가 원을 그리면 그 안에 포함된 매장을 표시한다"는 기능을 만든다고 하자. 이를 매번 서버에 폴리곤 좌표를 전송하고 PostGIS의 `ST_Contains`로 계산해 결과를 다시 받아오는 식으로 구현하면, 사용자가 원의 반경을 슬라이더로 조금씩 조정할 때마다 네트워크 왕복이 발생한다. 사용자 입장에서는 지도 조작이 버벅이는 것처럼 느껴지고, 서버에는 불필요한 요청이 누적된다.

## 올바른 접근: 클라이언트에서 먼저 걸러내기

```javascript
import * as turf from '@turf/turf';

// 클릭 지점 기준 1km 반경 원 생성
const center = turf.point([126.978, 37.566]);
const radius = 1; // km
const circle = turf.circle(center, radius, { units: 'kilometers' });

// 이미 로드된 매장 GeoJSON 중 원 안에 포함된 것만 필터링
const storesInRange = stores.features.filter(store =>
  turf.booleanPointInPolygon(store, circle)
);
```

이렇게 하면 지도에 이미 로드된 매장 데이터를 대상으로 즉시 필터링이 이뤄져, 슬라이더를 움직이는 동안에도 지연 없이 결과가 갱신된다. 폴리곤 교차 여부는 `turf.booleanIntersects()`, 두 지점 간 거리는 `turf.distance()`, 여러 지점을 감싸는 최소 다각형은 `turf.convex()`로 계산할 수 있다.

## 서버 사이드 분석과의 역할 분담

| 상황 | 적합한 방식 |
|---|---|
| 이미 로드된 소량 데이터의 즉각적인 필터링 | Turf.js (클라이언트) |
| 수백만 건 이상의 대용량 공간 조인 | PostGIS (서버) |
| 정확한 측지선 거리·면적이 중요한 분석 | 서버의 지오데식 함수(더 정밀) |
| 사용자 인터랙션에 실시간 반응해야 하는 미리보기 | Turf.js (클라이언트) |

Turf.js의 계산은 내부적으로 평면 기하 근사를 쓰는 함수가 많아, 아주 넓은 범위나 극지방 근처에서는 오차가 커질 수 있다. 법적·통계적으로 정밀도가 중요한 최종 결과라면 서버의 PostGIS나 지오데식 라이브러리로 다시 검증하는 것이 안전하다.

## 실무 포인트

- **대용량 GeoJSON을 그대로 클라이언트에 올리지 마라.** Turf.js가 빠르다고 해도 수만~수십만 개 피처를 브라우저 메모리에 올리고 연산하면 메인 스레드가 멈출 수 있다. 필요한 범위만 서버에서 미리 잘라 내려주는 것이 기본이다.
- **무거운 연산은 Web Worker로 분리하라.** `turf.buffer()`나 대량 `booleanIntersects()` 반복 같은 연산이 오래 걸리면 UI 스레드가 멈춰 지도 조작이 끊긴다. Web Worker에서 계산하고 결과만 메인 스레드로 넘기는 구조가 안전하다.
- **좌표계는 항상 EPSG:4326(위경도)이어야 한다.** Turf.js 함수 대부분은 GeoJSON 표준에 맞춰 경도-위도 순서, WGS84 좌표계를 전제로 한다. 지도 라이브러리의 내부 렌더링 좌표(EPSG:3857)를 그대로 넘기면 계산이 완전히 틀어진다.
- **버전 간 트리쉐이킹 차이를 확인하라.** `@turf/turf` 전체를 불러오면 번들 크기가 커지므로, 실제 쓰는 함수만 `@turf/buffer`, `@turf/boolean-point-in-polygon`처럼 개별 패키지로 임포트하는 것이 번들 최적화에 유리하다.

## 마무리 요약

- 이미 브라우저에 로드된 GeoJSON을 대상으로 한 즉각적인 공간 분석은 서버 왕복 없이 Turf.js로 처리하는 것이 응답성에 유리하다.
- 대용량 데이터나 정밀한 지오데식 계산이 필요한 경우는 여전히 PostGIS 같은 서버 사이드 공간 DB의 몫이다.
- 무거운 연산의 Web Worker 분리, EPSG:4326 좌표계 준수, 개별 패키지 임포트로 번들 크기를 관리하면 실무에서 안정적으로 쓸 수 있다.
