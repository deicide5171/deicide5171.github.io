## 목록을 한 번에 다 주면 안 되나

게시글이 10만 개인데 한 번에 다 내려주면 서버·네트워크·클라이언트 모두 감당하지 못한다. 그래서 목록을 조금씩 나눠 보여주는 **페이지네이션(pagination)**이 필요하다. 구현 방식은 크게 **OFFSET 기반**과 **커서(cursor) 기반** 두 가지가 있다.

## OFFSET 기반: 흔하지만 함정이 있다

```sql
-- 3페이지(21~30번째) 가져오기
SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 20;
```

OFFSET은 "앞의 N개를 건너뛰고 그다음부터"라는 뜻이다. 구현이 직관적이고 "몇 페이지로 이동" 같은 UI에 적합하다. 하지만 두 가지 문제가 있다.

| 문제 | 설명 |
|---|---|
| 성능 저하 | 뒤 페이지로 갈수록 건너뛸 행이 많아져 느려짐 |
| 데이터 밀림 | 조회 중 새 글이 추가되면 항목이 밀려 중복·누락 발생 |

## 커서 기반: 마지막 위치부터

```sql
-- 마지막으로 본 id(100)보다 작은 것부터 10개
SELECT * FROM posts WHERE id < 100 ORDER BY id DESC LIMIT 10;
```

커서 방식은 "몇 개를 건너뛸까"가 아니라 "마지막으로 본 위치부터"로 접근한다. 앞의 행을 건너뛰지 않고 인덱스로 바로 그 위치를 찾으므로, 뒤 페이지로 가도 성능이 일정하다.

## 두 방식 비교

| 항목 | OFFSET | 커서 |
|---|---|---|
| 구현 난이도 | 쉬움 | 조금 복잡 |
| 뒤 페이지 성능 | 나빠짐 | 일정하게 빠름 |
| 특정 페이지 이동 | 가능(3페이지로) | 어려움(순차 이동 위주) |
| 데이터 밀림 | 발생 | 안 발생 |
| 적합한 UI | 페이지 번호 | 무한 스크롤 |

## 실무 포인트

- **무한 스크롤에는 커서 방식이 정답에 가깝다.** SNS 피드처럼 아래로 계속 넘기는 UI에서는 데이터 밀림이 없고 성능이 일정한 커서 방식이 훨씬 적합하다.
- **"몇 페이지로 이동" 기능이 꼭 필요하면 OFFSET을 쓰되 깊은 페이지를 조심하라.** 관리자 페이지처럼 페이지 번호가 필요하고 데이터가 크지 않다면 OFFSET도 괜찮지만, 수만 페이지 뒤로 가는 경우가 있다면 성능을 반드시 확인해야 한다.
- **커서는 정렬 기준 컬럼에 인덱스가 있어야 빠르다.** `WHERE id < 100 ORDER BY id`가 빠른 이유는 id에 인덱스가 있기 때문이다. 정렬·커서 기준 컬럼에 인덱스가 없으면 커서 방식도 느려진다.

## 마무리 요약

- 페이지네이션은 큰 목록을 나눠 보여주는 기법으로, OFFSET 기반과 커서 기반이 있다.
- OFFSET은 구현이 쉽고 페이지 번호 이동에 적합하지만 뒤 페이지 성능 저하와 데이터 밀림 문제가 있다.
- 커서는 마지막 위치부터 조회해 성능이 일정하고 데이터 밀림이 없어 무한 스크롤에 적합하다.
