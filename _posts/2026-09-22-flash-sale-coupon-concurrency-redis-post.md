## 왜 선착순 이벤트만 만들면 장애가 나는가

"선착순 100명 한정 쿠폰"은 프로덕트 입장에서는 간단한 이벤트지만, 시스템 입장에서는 짧은 시간에 동시 요청이 폭발적으로 몰리는 가장 가혹한 시나리오 중 하나다. 평소 트래픽의 수십~수백 배가 몇 초 안에 쏟아지고, 게다가 그 요청들이 전부 같은 재고 값 하나를 두고 경쟁한다. 일반적인 CRUD API처럼 각 요청이 서로 독립적이지 않다는 점이 문제를 어렵게 만든다.

이 문제를 처음 설계할 때 흔히 저지르는 실수는 "일단 되니까"라는 이유로 애플리케이션 레벨의 단순한 카운터 증가 로직을 그대로 쓰는 것이다. 동시 요청이 적을 때는 문제가 없다가, 실제 이벤트 당일 트래픽이 몰리면 재고가 마이너스로 내려가거나(초과 발급), 반대로 재고가 남았는데도 이벤트가 조기 종료되는 두 가지 사고가 동시에 날 수 있다.

## 잘못된 접근: DB Row에 UPDATE로 재고 차감하기

가장 직관적인 방법은 쿠폰 재고 테이블에 `UPDATE coupon SET stock = stock - 1 WHERE id = ? AND stock > 0` 같은 조건부 UPDATE를 날리는 것이다. 이 자체는 원자적 연산이라 이론적으로는 안전하다. 하지만 문제는 이 방식이 **모든 요청을 DB 커넥션 하나씩 점유**한다는 점이다. 순간적으로 수만 건의 요청이 몰리면 DB 커넥션 풀이 순식간에 고갈되고, 쿠폰 발급과 무관한 다른 API까지 함께 느려지거나 타임아웃이 난다.

```sql
-- 순간 트래픽이 몰리면 이 쿼리 하나가 DB 전체를 잠식한다
UPDATE coupon SET stock = stock - 1
WHERE id = 1001 AND stock > 0;
```

행 단위 락 경합도 무시할 수 없다. 같은 행을 두고 수천 개의 트랜잭션이 동시에 락을 기다리면, 대기 큐가 길어지면서 개별 요청의 응답 시간이 기하급수적으로 늘어난다.

## 올바른 접근: Redis 원자적 연산으로 앞단에서 걸러내기

핵심 아이디어는 "DB까지 가지도 못할 요청을 최대한 앞단에서 걸러낸다"는 것이다. Redis의 `DECR` 명령은 단일 스레드로 동작하는 Redis의 특성 덕분에 별도의 락 없이도 원자적으로 값을 감소시킨다.

```python
import redis

r = redis.Redis()

def try_issue_coupon(coupon_id: str, user_id: str) -> bool:
    remaining = r.decr(f"coupon:stock:{coupon_id}")
    if remaining < 0:
        # 이미 소진됨 — 재고를 원상 복구하고 실패 처리
        r.incr(f"coupon:stock:{coupon_id}")
        return False
    # 재고 확보 성공 — 실제 발급 처리는 비동기 큐로 위임
    r.sadd(f"coupon:issued:{coupon_id}", user_id)
    return True
```

여기서 중요한 디테일이 두 가지 있다. 첫째, `DECR` 결과가 음수가 되면 즉시 `INCR`로 되돌려야 한다. 그렇지 않으면 재고 값이 계속 마이너스로 쌓여 다음 이벤트나 모니터링 지표에 혼란을 준다. 둘째, 같은 사용자가 중복으로 응모하는 것을 막으려면 `SADD`의 반환값(이미 집합에 있으면 0을 반환)을 함께 확인해 원자적으로 중복 참여를 차단해야 한다.

## DB 반영은 비동기로, 재고 확보는 동기로

Redis로 재고를 확보한 뒤, 실제 DB에 발급 이력을 남기는 작업까지 요청 스레드가 동기적으로 기다릴 필요는 없다. 재고 확보에 성공한 요청만 메시지 큐(Kafka, SQS 등)에 적재하고, 별도의 워커가 이를 순차적으로 소비해 DB에 기록하면 DB에 가해지는 부하를 완전히 분리할 수 있다.

| 처리 단계 | 담당 컴포넌트 | 처리 방식 |
|---|---|---|
| 재고 확인·차감 | Redis DECR | 동기, 원자적, 밀리초 단위 응답 |
| 중복 참여 방지 | Redis SADD | 동기, 원자적 |
| 발급 이력 영속화 | DB + 메시지 큐 | 비동기, 순차 처리 |
| 사용자 응답 | API 서버 | Redis 결과만으로 즉시 응답 |

이렇게 나누면 사용자는 "당첨/실패" 여부를 즉시 받아볼 수 있고, DB는 몰린 트래픽의 순간 최대치가 아니라 큐가 흘려보내는 만큼만 순차적으로 처리하면 된다.

## 실무 포인트

- **Redis 자체도 단일 장애 지점이 될 수 있다.** 이벤트 트래픽 규모가 크다면 Redis Cluster나 Sentinel 구성으로 가용성을 확보하고, 이벤트 시작 전 반드시 부하 테스트로 처리량 한계를 확인해야 한다.
- **DECR 대신 Lua 스크립트로 여러 연산을 하나로 묶는 방법도 고려하라.** 재고 확인·중복 체크·기록을 하나의 Lua 스크립트로 묶으면 Redis 서버 내에서 원자적으로 처리되어 네트워크 왕복이 줄어든다.
- **TTL을 반드시 설정하라.** 이벤트가 끝난 뒤에도 재고 키와 참여자 집합이 영구히 남으면 메모리를 계속 잡아먹는다. 이벤트 종료 시점 이후 적절한 TTL을 걸어 자동 정리되게 한다.
- **CDN·API 게이트웨이 단에서도 레이트 리밋을 걸어라.** Redis가 아무리 빨라도 요청 자체가 서버까지 도달하는 네트워크·로드밸런서 단계에서 병목이 생길 수 있으므로, 앞단 방어선을 함께 준비해야 한다.

## 마무리 요약

- 선착순 이벤트는 짧은 시간에 같은 자원을 두고 경쟁하는 트래픽 패턴이라 일반 API와 다른 설계가 필요하다.
- DB UPDATE로 재고를 직접 차감하면 커넥션 고갈과 락 경합으로 장애로 이어지므로, Redis의 원자적 연산으로 앞단에서 요청을 걸러내야 한다.
- 재고 확보는 동기로 즉시 응답하고, DB 영속화는 메시지 큐를 통한 비동기 처리로 분리하는 것이 실전 표준 패턴이다.
