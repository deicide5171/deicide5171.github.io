## 도입

"DB가 응답은 하는데 너무 느려요. 근데 페일오버는 왜 안 일어나죠?" 장애 대응 중에 이 질문을 받아본 적이 있다면, 이미 흔한 함정을 밟은 것이다. 2026년에도 여러 서비스의 공개 포스트모템에 같은 패턴이 반복됐다. 어느 인증 플랫폼은 세션 DB가 완전히 다운되지 않고 그저 느려졌을 뿐인데, 헬스체크가 "살아있음"으로 판정해 자동 장애조치가 끝내 트리거되지 않았다고 밝혔다. 문제는 설정 실수가 아니라, 가장 널리 쓰이는 liveness/readiness 헬스체크 모델 자체가 이런 상태를 구분하지 못하도록 설계돼 있다는 점이다.

"서버가 죽으면 대기 서버로 넘겨주세요"라는 요구를 받으면 대부분 TCP 연결이나 HTTP 200 응답 여부로 "살아있다/죽었다"를 판정하는 헬스체크부터 만든다. 이 모델은 완전한 다운(hard failure)은 잘 잡아낸다. 그런데 실무에서 더 흔하고 더 위험한 것은 프로세스는 응답하지만 지연시간이 수십 배로 늘어난 degraded 상태다. 이 글은 왜 기존 헬스체크 모델이 이 중간 상태를 구조적으로 놓치는지, 그리고 이를 잡기 위해 무엇을 추가로 설계해야 하는지 정리한다.

## 전체 시스템에서의 위치

로드밸런서나 오케스트레이터는 보통 헬스체크 신호 하나만 보고 라우팅 결정을 내린다. 이 신호가 "응답했는가/안 했는가"라는 이진값이면, 그 뒤에 있는 DB·캐시·업스트림 서비스가 "응답은 하지만 5초씩 걸린다"는 상태에 있어도 트래픽은 계속 그쪽으로 흘러간다. 커넥션 풀은 느린 응답을 기다리는 연결로 가득 차고, 대기 중인 요청이 쌓이면서 연쇄적으로 전체 서비스가 느려진다 — 이 시점에는 이미 자동 페일오버로 막을 수 있는 범위를 넘어선 경우가 많다.

<img src="/assets/images/posts/2026-10-25-degraded-state-failover-health-check-design-1.svg" alt="liveness 기반 헬스체크가 degraded 상태를 놓치고 장애가 전파되는 경로" style="width:100%;">

- **liveness 체크**: 프로세스가 떠 있는지만 본다. degraded 상태에서도 "정상"으로 응답한다.
- **readiness 체크**: 트래픽을 받을 준비가 됐는지 보지만, 보통 이것도 단순 응답 성공 여부로만 판정하는 경우가 많다.
- **지연시간 기반 체크**가 빠져 있으면, "응답은 하지만 느리다"는 상태가 두 체크 사이 사각지대에 그대로 남는다.

## 선택의 트레이드오프

| 방식 | 잡아내는 장애 | 놓치는 장애 | 구현 비용 |
|---|---|---|---|
| TCP/HTTP 200 liveness | 완전 다운, 프로세스 크래시 | degraded(느린 응답), 부분 기능 장애 | 낮음 |
| readiness(의존성 ping) | 의존 서비스 완전 단절 | 의존 서비스가 느리기만 한 경우 | 낮음~중간 |
| 지연시간 임계값 기반 체크 | degraded 상태 포함 | 순간적인 지연 스파이크를 오탐할 수 있음 | 중간 |
| 회로차단기(circuit breaker) | 반복되는 느린 응답의 연쇄 전파 | 체크 주기가 길면 반응이 늦음 | 중간~높음 |
| 클라이언트 측 타임아웃+재시도 예산 | 개별 요청 단위의 무한 대기 | 전체 시스템 수준의 조기 경보는 아님 | 낮음 |

판단 기준은 **"이 시스템에서 degraded 상태가 발생할 수 있는가, 그리고 발생했을 때 비용이 얼마나 큰가"**다. 단순 내부 도구처럼 영향 범위가 작다면 기본 liveness/readiness만으로 충분하다. 반면 세션·인증·결제처럼 느린 응답이 연쇄 장애로 번질 수 있는 핵심 경로라면, 지연시간 기반 체크와 회로차단기를 반드시 함께 둬야 한다 — 둘 중 하나만으로는 완전하지 않다. 지연시간 체크는 상태를 "감지"하고, 회로차단기는 감지된 상태에서 트래픽을 실제로 "차단"한다.

## 실제 프로젝트 진행 순서

1. **현재 헬스체크가 실제로 무엇을 보는지 확인한다.** TCP 연결 성공만 보는지, HTTP 200만 보는지, 응답 시간까지 보는지 코드를 직접 읽어 확인한다. 문서와 실제 구현이 다른 경우가 흔하다.
2. **정상 응답 시간의 기준선(baseline)을 측정한다.** 평시 p50·p95·p99 응답 시간을 먼저 알아야 "느리다"의 임계값을 정할 수 있다.
3. **지연시간 임계값 체크를 readiness에 추가한다.** p99의 몇 배를 넘으면 unready로 전환할지 정하고, 오탐을 줄이기 위해 연속 N회 초과 시에만 전환하는 식으로 완충을 둔다.
4. **커넥션 풀에 상한과 타임아웃을 건다.** 느린 응답을 무한정 기다리는 연결이 풀을 고갈시키지 않도록, 풀 크기 상한과 획득 타임아웃을 명시적으로 설정한다.
5. **장애 주입 테스트로 검증한다.** 의존 서비스를 완전히 끊지 말고 "응답은 하되 5초씩 지연"시키는 카오스 테스트를 돌려, 이 상태에서 실제로 페일오버나 회로차단이 발동하는지 확인한다.

```yaml
# readiness probe에 지연시간 기반 판정을 추가하는 예시 (개념적 설정)
readinessProbe:
  httpGet:
    path: /health/ready
  periodSeconds: 5
  failureThreshold: 3   # 연속 3회 실패해야 unready로 전환 (오탐 완충)
# /health/ready 핸들러 내부 로직
# - DB ping 응답 시간이 p99 기준선의 5배를 넘으면 실패 반환
# - 단순 연결 성공 여부가 아니라 "느림"도 실패로 간주
```

## 실무 포인트

- auto-analyze 같은 DB 자동 유지보수 작업이 쿼리 플랜을 갑자기 바꿔 응답 시간을 늘리는 경우가 있다. 이런 변화는 "다운"이 아니라 "degraded"로 나타나므로 지연시간 기반 체크가 아니면 아예 안 잡힌다.
- 긴 실행 쿼리에 문장 타임아웃(statement timeout)을 걸지 않으면, degraded 상태에서 요청이 계속 쌓이며 상황을 더 악화시킨다. 취소 메커니즘은 헬스체크만큼 중요하다.
- 오탐을 줄이려고 임계값을 너무 느슨하게 잡으면 degraded 상태를 또 놓친다. 기준선 측정 없이 임의의 숫자로 임계값을 정하지 않는다.

## 마무리

- liveness/readiness 중심의 헬스체크는 완전 다운은 잘 잡지만, "응답은 하되 느린" degraded 상태는 구조적으로 놓친다.
- 핵심 경로에는 지연시간 기반 체크로 degraded 상태를 감지하고, 회로차단기로 실제 트래픽을 차단하는 두 단계가 함께 필요하다.
- 설계는 현재 체크 대상 확인 → 응답 시간 기준선 측정 → 지연시간 임계값 추가 → 커넥션 풀 상한 설정 → 장애 주입 검증 순서로 진행한다.
