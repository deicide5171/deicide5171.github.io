## 도입

"우리 여행 예약 에이전트가 파트너 항공사의 에이전트와 직접 협상해서 일정을 맞추게 해주세요." 이런 요구가 오면 바로 MCP 서버를 하나 더 붙이려는 반사적 판단을 하기 쉽다. 하지만 MCP는 "내 에이전트가 도구를 쓰게 하는" 프로토콜이지, "서로 다른 조직이 운영하는 독립된 에이전트 두 개가 대화하게 하는" 프로토콜이 아니다. 파트너사의 에이전트는 내가 코드를 보거나 배포를 통제할 수 없는 블랙박스이고, 그쪽도 내 에이전트의 내부 구현을 알 필요가 없어야 한다.

이 "조직 경계를 넘는 에이전트 간 위임"이라는 문제를 풀기 위해 Google이 설계하고 2025년 Linux Foundation에 이관한 A2A(Agent2Agent) 프로토콜이 2026년 들어 빠르게 자리를 잡았다. 2026년 4월 기준 150개 이상 조직이 지원을 선언했고, v1.0이 서명된 Agent Card·멀티테넌시·JSON-RPC와 gRPC 동시 지원을 갖췄으며, Azure AI Foundry·Amazon Bedrock AgentCore·Google ADK에 네이티브로 들어갔다. 2026년 8월에는 거버넌스도 Agentic AI Foundation 산하로 옮겨가며 장기 표준으로서의 입지를 다졌다.

## 핵심 개념: MCP와 A2A는 다른 층을 다룬다

| 구분 | MCP | A2A |
|---|---|---|
| 연결 관계 | 에이전트 ↔ 도구/데이터 소스 | 에이전트 ↔ 에이전트 |
| 신뢰 경계 | 보통 같은 조직 내부 | 서로 다른 조직 사이 |
| 상대의 내부 구현 | 도구 스펙을 알아야 호출 가능 | 몰라도 됨 — Agent Card로 능력만 선언 |
| 핵심 자원 | 도구(tool), 리소스(resource) | 작업(task), 메시지(message) |
| 수명 | 보통 요청-응답으로 짧음 | 장시간 비동기 작업, 상태 추적 포함 |

A2A의 핵심 개념은 **Agent Card**다. 각 에이전트는 `/.well-known/agent.json` 같은 경로에 자신이 무엇을 할 수 있는지, 어떤 인증 방식을 요구하는지를 선언한 문서를 공개한다. 상대 에이전트는 이 카드를 읽고 "이 에이전트에게 이 작업을 맡겨도 되는가"를 판단한 뒤, `Task`라는 단위로 작업을 위임한다. v1.0부터는 이 카드에 서명을 붙일 수 있어, 상대가 선언한 능력이 실제로 그 조직이 발행한 것인지 암호학적으로 검증할 수 있다.

## 시스템에서의 위치

내 에이전트 오케스트레이터 입장에서 A2A는 "내부 서브에이전트를 부르는 것"과 "외부 파트너 에이전트를 부르는 것"을 같은 인터페이스로 다루되, 신뢰 경계에서 인증·인가 계층 하나를 더 끼워 넣는 구조로 봐야 한다. 내부 서브에이전트 호출은 여전히 직접 함수 호출이나 MCP로 처리하고, 조직 경계를 넘는 호출만 A2A 클라이언트를 거치게 분리하는 것이 설계의 핵심이다.

<img src="/assets/images/posts/2026-10-19-a2a-protocol-cross-org-agent-communication-1.svg" alt="내부 에이전트 호출은 직접 호출·MCP로, 조직 경계를 넘는 호출만 A2A로 분리하는 구조도" style="width:100%;">

모든 에이전트 호출을 A2A로 통일하려고 하면, 내부 호출에서도 불필요한 Agent Card 조회와 서명 검증 오버헤드가 붙는다. 신뢰 경계가 없는 곳에 신뢰 검증 계층을 넣는 것은 과설계다.

## 트레이드오프: 언제 A2A가 필요한가

| 상황 | 판단 |
|---|---|
| 같은 조직, 같은 배포 파이프라인의 에이전트끼리 | A2A 불필요 — 직접 호출이나 내부 MCP로 충분 |
| 파트너사·외부 벤더가 운영하는 에이전트와 작업을 위임해야 함 | A2A가 적합 — Agent Card로 능력 선언, 서명으로 신원 검증 |
| 단순히 외부 API를 한 번 호출하면 끝나는 작업 | A2A는 과함 — REST API나 MCP 도구 호출로 충분 |
| 장시간 비동기 작업(예: 여러 날 걸리는 협상)을 상대 에이전트에 맡겨야 함 | A2A의 Task 상태 추적 모델이 유리 |

A2A를 "모든 에이전트 간 통신의 기본값"으로 삼을 이유는 없다. 신뢰 경계가 없는 내부 호출에 A2A를 쓰면 복잡도만 늘고, 반대로 조직 경계를 REST API 직접 호출로 때우면 상대 에이전트의 능력이 바뀔 때마다 내 쪽 통합 코드를 수동으로 다시 짜야 한다.

## 실무 진행 순서

1. **신뢰 경계를 먼저 그린다.** 내 에이전트 호출 그래프에서 어디까지가 내부(직접 호출 가능)이고 어디부터가 외부 조직인지 표시한다. A2A는 오직 이 경계선 위에만 놓는다.
2. **내 에이전트의 Agent Card를 먼저 작성한다.** 외부와 연동하기 전에 내가 무엇을 제공할 수 있는지를 명확히 선언하는 연습이 된다.
3. **파트너 Agent Card를 읽고 Task 위임을 시험한다.** 샌드박스 환경에서 짧은 작업 하나로 Task 생성 → 상태 폴링 → 결과 수신 흐름을 먼저 검증한다.
4. **서명 검증과 인가를 붙인다.** v1.0의 서명된 Agent Card를 실제로 검증하는 로직 없이 그냥 신뢰하면 A2A 도입의 가장 큰 이점(신원 검증)을 버리는 것이다.
5. **장시간 Task의 재시도·타임아웃 정책을 정한다.** 파트너 쪽 에이전트가 응답하지 않거나 중간에 실패했을 때 내 오케스트레이터가 어떻게 복구할지를 미리 설계해야 한다.

예제(Agent Card 최소 형태, JSON):

```json
{
  "name": "travel-booking-agent",
  "description": "항공·호텔 예약 조율 에이전트",
  "url": "https://partner.example.com/a2a",
  "capabilities": { "streaming": true },
  "skills": [
    { "id": "negotiate-itinerary", "description": "일정 조율 및 재협상" }
  ],
  "authentication": { "schemes": ["bearer"] }
}
```

## 실무 포인트

- Agent Card는 정적 문서가 아니라 운영 중 능력이 바뀔 수 있는 살아있는 계약이다. 캐싱하더라도 주기적으로 재조회해 능력 변경을 반영해야 한다.
- gRPC와 JSON-RPC를 동시에 지원하는 구현체가 늘고 있으니, 사내 게이트웨이에서 두 바인딩을 모두 받을지 하나로 강제할지 초기에 정해야 뒤에서 프로토콜 변환 계층을 또 하나 만들지 않는다.
- 거버넌스가 Agentic AI Foundation으로 이관된 지 얼마 안 됐으므로, 스펙 변경 공지를 구독해 두는 것이 안전하다.
- 파트너 에이전트가 실패하거나 느려지는 상황은 내 시스템 장애가 아니라 외부 의존성 장애로 다뤄야 한다. 서킷 브레이커와 타임아웃을 A2A 클라이언트 레이어에 넣어, 파트너 쪽 문제가 내 오케스트레이터 전체를 막지 않게 격리한다.

## 마무리

- A2A는 MCP가 풀지 않는 "서로 다른 조직의 에이전트끼리 위임"이라는 문제를 전담하는 프로토콜이다.
- 내부 호출은 직접 호출·MCP로 두고, 조직 경계를 넘는 호출에만 A2A를 적용하는 것이 복잡도를 최소화하는 설계다.
- Agent Card 선언 → 샌드박스 Task 테스트 → 서명 검증 → 재시도 정책 순서로 좁혀 들어가는 것이 안전한 도입 경로다.
