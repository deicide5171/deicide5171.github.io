## 왜 미디어 쿼리만으로는 한계에 부딪히나

컴포넌트 기반 프론트엔드 개발이 자리잡으면서 같은 카드 컴포넌트를 여러 위치에 재사용하는 일이 흔해졌다. 문제는 같은 카드라도 넓은 메인 영역에 놓였을 때와 좁은 사이드바에 놓였을 때 레이아웃이 달라야 한다는 점이다. 예를 들어 이미지와 텍스트를 가로로 나란히 배치했다가, 카드가 좁은 공간에 들어가면 세로로 쌓이게 만들고 싶다.

기존의 `@media` 쿼리는 **뷰포트(브라우저 창) 크기**를 기준으로 스타일을 분기한다. 그런데 카드 컴포넌트의 실제 폭은 뷰포트 크기가 아니라 "그 카드가 어떤 부모 컨테이너 안에 놓였는가"에 따라 달라진다. 뷰포트가 1920px로 넓어도 사이드바 안의 카드는 300px밖에 안 될 수 있다. 미디어 쿼리는 이 상황을 구분하지 못한다.

## 잘못된 접근: 위치별로 별도 클래스를 만들어 대응

```css
.card { display: flex; flex-direction: row; }
.sidebar .card { flex-direction: column; }  /* 사이드바 전용 오버라이드 */
```

이 방식은 컴포넌트가 놓일 수 있는 위치를 미리 다 알고 있어야 하고, 새로운 배치 위치가 추가될 때마다 오버라이드 규칙을 계속 늘려야 한다. 컴포넌트를 독립적으로 재사용 가능하게 만들자는 애초의 목적과 어긋난다. 카드 컴포넌트 스스로가 "내가 지금 얼마나 넓은 공간에 있는지"를 알고 반응하는 것이 훨씬 자연스럽다.

## 올바른 접근: 컨테이너 쿼리

```css
.card-container {
  container-type: inline-size;
  container-name: card;
}

.card {
  display: flex;
  flex-direction: column;
}

@container card (min-width: 400px) {
  .card {
    flex-direction: row;
  }
}
```

부모 요소에 `container-type: inline-size`를 선언하면 그 요소가 "쿼리 대상이 되는 컨테이너"로 등록된다. 이후 `@container` 규칙 안에서는 뷰포트가 아니라 **그 컨테이너의 폭**을 기준으로 스타일을 분기할 수 있다. 같은 `.card` 컴포넌트를 폭이 400px 이상인 곳에 놓으면 가로 배치, 그보다 좁은 곳에 놓으면 세로 배치가 자동으로 적용된다. 컴포넌트를 어디에 두든 별도의 위치별 클래스 없이 스스로 적응한다.

## 컨테이너 쿼리 vs 미디어 쿼리

| 항목 | 미디어 쿼리 | 컨테이너 쿼리 |
|---|---|---|
| 기준 | 뷰포트 크기 | 부모 컨테이너 크기 |
| 적합한 대상 | 페이지 전체 레이아웃 | 재사용 가능한 컴포넌트 |
| 선언 위치 | 어디서나 사용 가능 | `container-type`이 선언된 조상이 있어야 함 |
| 여러 위치 재사용 | 위치별 오버라이드 필요 | 컴포넌트 자체가 자동 반응 |

두 개념은 경쟁 관계가 아니라 역할이 다르다. 페이지 전체의 레이아웃 전환(예: 모바일에서 네비게이션을 햄버거 메뉴로 바꾸는 것)은 여전히 미디어 쿼리가 맞고, 재사용 가능한 컴포넌트 내부의 세부 레이아웃은 컨테이너 쿼리가 더 적합하다.

## 컨테이너 쿼리 유닛(cqw, cqh 등)

```css
.card-title {
  font-size: clamp(14px, 5cqw, 24px);
}
```

컨테이너의 폭을 기준으로 한 상대 단위 `cqw`(container query width)도 함께 도입됐다. 뷰포트 기준의 `vw`처럼 동작하지만, 기준이 뷰포트가 아니라 가장 가까운 컨테이너다. 카드 안의 글자 크기를 카드 자체의 폭에 비례해 키우고 싶을 때 `clamp()`와 조합해 쓰면 유용하다.

## 실무 포인트

- **`container-type: inline-size`는 레이아웃 격리(containment)를 함께 발생시킨다.** 이 속성이 선언된 요소는 내부 콘텐츠의 크기가 외부로 영향을 주지 않도록 격리되므로, 기존 레이아웃에 예상치 못한 부작용이 생길 수 있다. 적용 전후로 레이아웃을 반드시 비교 확인한다.
- **컨테이너 이름(`container-name`)을 지정하면 중첩된 컨테이너 중 어떤 것을 기준으로 쿼리할지 명시할 수 있다.** 이름을 생략하면 가장 가까운 조상 컨테이너가 기준이 되므로, 여러 단계로 컨테이너가 중첩된 구조에서는 이름을 명시하는 것이 안전하다.
- **구형 브라우저 지원이 필요하면 `@supports`로 폴백을 준비하라.** 주요 브라우저는 대부분 지원하지만, 오래된 웹뷰나 특정 환경에서는 여전히 지원하지 않을 수 있다.
- **컨테이너 쿼리는 상태 기반 스타일링(`:has()`)과도 잘 조합된다.** "카드에 이미지가 있고 폭이 400px 이상이면 가로 배치"처럼 여러 조건을 CSS 레벨에서 조합할 수 있어 자바스크립트 개입을 더 줄일 수 있다.

## 마무리 요약

- 미디어 쿼리는 뷰포트 기준, 컨테이너 쿼리는 부모 컨테이너 기준으로 스타일을 분기한다는 근본적인 차이가 있다.
- `container-type: inline-size`와 `@container` 규칙으로 컴포넌트가 놓인 위치와 무관하게 스스로 적응하는 레이아웃을 만들 수 있다.
- 레이아웃 격리 부작용과 중첩 컨테이너의 이름 지정을 함께 고려해야 실무에서 안전하게 도입할 수 있다.
