## 왜 지금 DNS TTL 전략인가

장애 대응 매뉴얼에 흔히 등장하는 문구가 있다. "DNS를 새 IP로 돌리면 TTL만큼 기다리면 전환된다." 틀린 말은 아니지만, 이 문장은 TTL이 단 하나의 캐시에만 적용된다는 전제를 깔고 있다. 실제로는 애플리케이션, OS, 사내 리졸버, ISP 리졸버까지 여러 계층이 각자의 정책으로 같은 레코드를 따로 캐싱한다. 어느 계층이 TTL을 얼마나 존중하느냐에 따라 "TTL이 지났는데도 옛 서버로만 계속 붙는" 현상이 벌어질 수 있다.

문제는 이 계층 구조가 평소에는 드러나지 않는다는 점이다. 트래픽이 안정적일 때는 어느 리졸버가 캐시를 얼마나 들고 있든 신경 쓸 이유가 없다. 문제는 페일오버, 블루-그린 배포, 인프라 이전처럼 IP를 바꿔야 하는 순간에 터진다. TTL 값 하나만 보고 전환 시간을 예측했다가, 실제로는 훨씬 오래 옛 엔드포인트로 요청이 흘러가는 것을 뒤늦게 발견하는 식이다. DNS 자체는 바뀌었는데 서비스는 여전히 절반쯤 옛 서버를 보고 있는 상태가 바로 이 지점에서 만들어진다.

## 핵심 개념 1: DNS 캐시는 한 겹이 아니다

DNS 조회는 클라이언트에서 권한 네임서버까지 여러 계층을 거치며, 각 계층이 독립적으로 캐싱 여부와 기간을 결정한다.

| 계층 | 예시 | TTL을 다루는 방식 |
|---|---|---|
| 애플리케이션 | JVM, 일부 언어 런타임 | 자체 설정값(`networkaddress.cache.ttl` 등)으로 TTL을 덮어쓰거나 무시할 수 있음 |
| OS 스텁 리졸버 | systemd-resolved, nscd, dnsmasq | 대체로 응답받은 TTL을 그대로 따름 |
| 재귀 리졸버 | 사내 DNS, ISP DNS, 공용 리졸버(8.8.8.8 등) | 다수의 클라이언트가 공유, 최초 조회 시점 기준으로 TTL 카운트다운 |
| 권한 네임서버 | Route 53, BIND 등 | Zone 파일의 TTL 값이 모든 캐싱의 "원본" 기준 |

레코드를 바꾼 시점에 이미 캐싱되어 있던 응답들은 권한 서버의 변경과 무관하게 각자 남은 TTL만큼 그대로 유지된다. 게다가 계층이 늘어날수록 "가장 늦게 만료되는 캐시"가 실제 전환 완료 시점을 결정하므로, 체감 전환 시간은 설정한 TTL보다 길어지는 경우가 흔하다.

## 핵심 개념 2: 짧은 TTL과 긴 TTL의 트레이드오프

| 구분 | 장점 | 단점 |
|---|---|---|
| 짧은 TTL(예: 60초 이하) | 페일오버·배포 전환이 빠르게 반영됨 | 모든 리졸버가 자주 재질의하면서 권한 서버 부하·지연 증가 |
| 긴 TTL(예: 1시간 이상) | 리졸버 부하 낮고 조회 지연 안정적 | 전환 시 옛 IP로 향하는 트래픽이 오래 남음 |
| 네거티브 캐싱 TTL | 존재하지 않는 레코드 재조회를 줄여줌 | 레코드를 새로 만든 직후에도 "없음" 응답이 한동안 캐싱될 수 있음 |

실무에서 흔한 접근은 평상시엔 TTL을 넉넉히 유지하다가, 계획된 전환(마이그레이션, 배포) 며칠 전부터 미리 TTL을 짧게 낮춰 캐시가 충분히 짧은 값으로 갱신되도록 예열한 뒤 전환을 실행하는 방식이다. 전환 직전에야 TTL을 낮추면, 낮추기 전 캐싱된 긴 TTL 레코드가 여전히 곳곳에 남아 있어 효과가 지연된다.

## 예제: TTL 확인과 설정

여러 리졸버에서 실제로 어떤 TTL이 남아있는지 확인하는 것이 장애 상황 판단의 출발점이다.

```bash
# 특정 리졸버(8.8.8.8) 기준으로 남은 TTL 직접 확인
dig @8.8.8.8 example.com +noall +answer

# 응답 예시 — 맨 앞 숫자가 남은 TTL(초)
# example.com.  287  IN  A  203.0.113.10
```

권한 서버(BIND 예시) 쪽 zone 파일에서는 레코드별 TTL과, 레코드를 못 찾았을 때 적용되는 네거티브 캐싱 TTL(SOA의 minimum 필드)을 함께 관리한다.

```
; zone 파일 일부
$TTL 300
@   IN  SOA  ns1.example.com. admin.example.com. (
        2026082001 ; serial
        3600       ; refresh
        900        ; retry
        604800     ; expire
        300        ; minimum(네거티브 캐싱 TTL)
)
www IN  A    203.0.113.10
```

애플리케이션 레벨에서는 JVM처럼 DNS 응답을 별도로 캐싱하는 런타임이 있다는 점도 확인해야 한다.

```properties
# java.security 또는 코드에서 설정 — 기본값은 배포판마다 다르므로 반드시 명시적으로 확인
networkaddress.cache.ttl=60
networkaddress.cache.negative.ttl=10
```

`networkaddress.cache.ttl`이 명시되지 않은 환경에서는 SecurityManager 존재 여부 등에 따라 DNS 응답을 사실상 영구 캐싱하는 경우가 있어, 권한 서버의 TTL을 아무리 짧게 잡아도 애플리케이션이 옛 IP를 계속 붙잡는 원인이 될 수 있다.

## 실무 포인트

- **전환 계획을 세울 때는 TTL 값 자체보다 "가장 오래 캐싱하는 계층"을 기준으로 여유 시간을 잡는다.** 애플리케이션 레벨 캐싱이 있다면 그 값이 실제 병목이 된다.
- **계획된 마이그레이션은 전환 며칠 전부터 TTL을 낮춰 예열한다.** 전환 직전에 TTL만 낮추면 이미 캐싱된 긴 TTL 레코드가 그대로 남아 효과가 늦게 나타난다.
- **네거티브 캐싱 TTL을 별도로 점검한다.** 새 레코드를 추가한 직후에도 이전의 "없음" 응답이 한동안 캐싱되어 있을 수 있으므로, 레코드 신설 직후 전파 확인이 필요하다.
- **애플리케이션 런타임의 자체 DNS 캐싱 설정을 명시적으로 확인한다.** 런타임이 권한 서버의 TTL과 무관하게 별도 정책으로 캐싱한다면, 그 값을 서비스의 페일오버 요구 시간에 맞춰 명시적으로 설정해야 한다.
- **여러 리졸버에서 동시에 TTL과 응답을 확인하며 전파 상태를 판단한다.** 사내 리졸버 하나만 보고 "전환 완료"를 단정하면, 다른 경로로 들어오는 트래픽은 여전히 옛 서버를 보고 있을 수 있다.
- **DNS만으로 즉시 전환이 필요한 경우라면 Anycast나 로드밸런서 계층에서 트래픽을 분산하는 구조를 함께 검토한다.** DNS 캐싱의 근본적인 지연 특성 자체를 우회하는 방법이기 때문이다.

## 3줄 요약

- DNS 캐시는 애플리케이션부터 권한 네임서버까지 여러 계층으로 나뉘어 있고, 각 계층이 TTL을 다루는 방식이 다르기 때문에 실제 전파 시간은 설정한 TTL보다 길어질 수 있다.
- 짧은 TTL은 전환은 빠르지만 리졸버 부하를, 긴 TTL은 그 반대를 대가로 치르며, 네거티브 캐싱 TTL은 별도로 관리해야 하는 값이다.
- 계획된 전환은 TTL을 미리 낮춰 예열하고, 애플리케이션 런타임의 자체 DNS 캐싱 정책을 명시적으로 확인하는 것이 장애를 줄이는 실무 대응이다.
