## 도입

"지도 타일 요청이 몰릴 때마다 데이터 다운로드(WFS)까지 같이 느려져요. 지도 서버를 더 늘려주세요." 트래픽이 늘어난 GeoServer 운영팀이 흔히 던지는 요구다. 그런데 "서버를 늘려달라"는 말을 그대로 받아 인스턴스를 수평으로 복제하면, WMS든 WFS든 GWC든 똑같이 전부 복제된다. 정작 트래픽이 몰리는 건 타일 렌더링(WMS)뿐인데, 거의 쓰이지 않는 WPS나 관리 UI까지 함께 n배로 늘어나는 것이다. 모놀리식 GeoServer는 OGC 서비스 전부와 관리 콘솔, 카탈로그를 한 JVM 프로세스 안에 묶어 두기 때문에 "일부만 늘린다"는 선택지 자체가 없다.

이 한계를 겨냥한 것이 GeoServer Cloud다. WMS, WFS, WCS, WPS, GWC, REST API, 웹 관리 UI, 게이트웨이를 각각 독립된 마이크로서비스로 쪼개고, 카탈로그(레이어·스타일 설정)는 공유 백엔드로, 설정 변경 알림은 메시지 버스로 동기화한다. 2026년 기준 camptocamp의 공식 Helm 차트로 쿠버네티스 배포가 안정화되면서, "타일만 몰린다"는 요구를 "WMS 파드만 늘린다"로 그대로 번역할 수 있게 됐다. 하지만 이 전환은 공짜가 아니다 — 단일 프로세스였던 운영 모델이 분산 시스템 운영 모델로 바뀌기 때문에, 언제 쪼개야 하고 언제 모놀리식을 유지해야 하는지부터 따져야 한다.

## 전체 시스템에서의 위치

모놀리식 GeoServer에서는 리버스 프록시 뒤에 동일한 GeoServer 인스턴스 여러 대가 떠 있고, 각 인스턴스가 WMS·WFS·GWC·관리 기능을 전부 처리한다. GeoServer Cloud는 이 앞단에 게이트웨이를 두고, 요청 경로(WMS인지 WFS인지)에 따라 서로 다른 서비스로 라우팅한다. 각 서비스는 같은 카탈로그 백엔드(pgconfig 또는 공유 데이터 디렉터리)를 읽고, 설정이 바뀌면 메시지 버스(RabbitMQ)로 변경 사실을 전파받아 캐시를 무효화한다.

<img src="/assets/images/posts/2026-10-25-geoserver-cloud-microservices-scaling-1.svg" alt="모놀리식 GeoServer와 GeoServer Cloud의 서비스 분리 구조 비교" style="width:100%;">

- **모놀리식**: 모든 서비스가 같은 프로세스 안에 있어 카탈로그 동기화 문제가 없다. 대신 한 서비스의 부하가 전체 프로세스의 응답성에 영향을 준다.
- **GeoServer Cloud**: WMS 파드가 트래픽에 눌려도 WFS·WPS 파드는 영향받지 않는다. 대신 카탈로그를 공유 DB로 분리하고, 설정 변경을 메시지 버스로 전파하는 새로운 동기화 계층이 생긴다.
- 캐시 계층(GWC)도 독립 서비스가 되므로, "타일 캐시 히트율 튜닝"과 "원본 WMS 렌더링 스케일"을 완전히 분리된 축으로 다룰 수 있다.

## 선택의 트레이드오프

| 전략 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 모놀리식 + 단순 수평 복제 | 운영 단순, 카탈로그 동기화 걱정 없음 | 서비스별 부하 편차를 반영 못 함, 전체가 n배로 늘어남 | 트래픽 패턴이 균일하거나 소규모 운영 |
| GeoServer Cloud (K8s) | 서비스별 독립 스케일, 장애 격리 | 공유 카탈로그 백엔드·메시지 버스 운영 부담 추가 | WMS·WFS 트래픽 편차가 크고 이미 쿠버네티스 운영 역량 보유 |
| GWC만 분리 (모놀리식 유지) | 가장 흔한 병목인 타일 캐시만 선제적으로 격리 | WFS·WPS는 여전히 함께 스케일됨 | 타일 트래픽 비중이 압도적으로 큰 경우 |
| 레이어별 인스턴스 분리(수동) | 추가 플랫폼 없이도 격리 가능 | 레이어 늘어날수록 운영 복잡도 선형 증가 | 서비스 종류가 아니라 특정 레이어 하나가 핫스팟인 경우 |

판단 기준은 **"부하 편차가 서비스 종류를 따라 생기는가, 아니면 균일한가"**다. 타일 요청(WMS/GWC)만 폭증하고 WFS·WPS는 거의 호출되지 않는 패턴이 뚜렷하다면 GeoServer Cloud의 서비스별 분리가 투자 대비 효과가 크다. 반대로 전체 트래픽이 완만하게 늘어나는 패턴이라면 모놀리식을 단순 복제하는 쪽이 운영 복잡도 대비 이득이 크다 — 분산 시스템을 하나 더 들이는 비용은 생각보다 크다.

## 실제 프로젝트 진행 순서

1. **서비스별 부하를 먼저 측정한다.** 현재 모놀리식 인스턴스에서 WMS/WFS/WPS/GWC 각각의 요청 수·응답 시간을 분리해 로깅하고, 실제로 편차가 있는지부터 확인한다.
2. **카탈로그 백엔드부터 정한다.** 공유 데이터 디렉터리(NFS)는 가장 빠르게 시작할 수 있지만 다중 쓰기 충돌에 취약하다. pgconfig(PostgreSQL 기반 카탈로그)가 멀티 인스턴스 운영에는 더 안전하다.
3. **스테이징에서 서비스 분리본을 먼저 띄운다.** camptocamp의 Helm 예제로 WMS·WFS·GWC·게이트웨이를 분리 배포하고, 기존 모놀리식과 응답을 diff해 회귀가 없는지 확인한다.
4. **메시지 버스 장애 시나리오를 검증한다.** RabbitMQ가 잠깐 끊겼을 때 설정 변경 전파가 늦어지는 것을 허용할 수 있는지, 아니면 즉시 일관성이 필요한지 운영 요구사항에 맞춰 판단한다.
5. **가장 부하가 큰 서비스부터 분리 전환한다.** 전체를 한 번에 쪼개지 말고, 측정에서 병목으로 드러난 서비스(보통 WMS/GWC)부터 독립 스케일링을 적용해 실제 효과를 확인한 뒤 나머지로 확장한다.

```yaml
# Helm values.yaml 예시 — WMS만 더 많은 레플리카로 스케일
wms:
  replicaCount: 6
  resources:
    requests: { cpu: "500m", memory: "1Gi" }
wfs:
  replicaCount: 2
wps:
  replicaCount: 1
catalog:
  backend: pgconfig
  pgconfig:
    host: geoserver-catalog-db
```

## 실무 포인트

- GWC를 분리해도 GWC는 여전히 원본 WMS 렌더링 결과를 캐시할 뿐이다. 캐시 미스가 잦은 레이어라면 WMS 서비스 스케일이 함께 필요하다는 점을 놓치기 쉽다.
- 공유 카탈로그 백엔드로 pgconfig를 쓰면 레이어·스타일 설정 자체가 단일 장애점이 된다. 이 DB의 가용성 설계가 전체 시스템의 가용성 상한이 된다.
- 소규모 트래픽에서 GeoServer Cloud를 먼저 도입하면 분산 시스템 운영 비용이 트래픽 처리 이득보다 커지는 경우가 많다. 모놀리식에서 병목이 실제로 측정된 뒤 전환하는 순서를 지킨다.

## 마무리

- GeoServer Cloud는 모놀리식이 강제하던 "전체 서비스 동시 복제"를 깨고, WMS·WFS·GWC를 독립적으로 스케일할 수 있게 한다.
- 전환 판단 기준은 서비스별 부하 편차이며, 균일한 트래픽이라면 모놀리식 단순 복제가 더 합리적이다.
- 전환은 부하 측정 → 카탈로그 백엔드 선정 → 스테이징 검증 → 메시지 버스 장애 시나리오 확인 → 병목 서비스부터 순차 분리 순서로 진행한다.
