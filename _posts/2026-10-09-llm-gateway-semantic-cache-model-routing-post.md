## 왜 지금 이 판단이 불거지는가

"우리 서비스가 지금은 Claude만 쓰는데, GPT나 Gemini도 섞어 쓰고 싶고, 한쪽이 느려지거나 장애 나면 자동으로 다른 쪽으로 넘어가게 해주세요. 그리고 비용도 좀 줄여주세요." 프로덕션에 LLM을 올린 지 몇 달만 지나면 반드시 듣게 되는 요구다. 처음엔 각 제공자 SDK를 if-else로 분기하는 코드 한 줄로 시작하지만, 제공자가 둘 셋으로 늘고 재시도·레이트리밋·비용 추적까지 겹치면 이 분기 로직은 금세 감당 못 할 크기로 불어난다.

2026년 들어 이 문제를 애플리케이션 코드가 아니라 별도의 **LLM 게이트웨이** 계층으로 분리하는 패턴이 자리 잡았다. 애플리케이션과 여러 모델 제공자 사이에 인증, 요청 라우팅, 응답 캐싱, 레이트리밋, 장애 복구를 한 곳에서 처리하는 추상화 층을 두는 구조다. Redis가 공개한 아키텍처 가이드는 이 게이트웨이 안에서도 시맨틱 캐시를 라우터보다 앞에 두라고 권고한다. 캐시 히트가 나면 모델 선택도, 실제 LLM 호출도 건너뛰기 때문에 캐시가 가장 먼저 거치는, 가장 저렴한 체크포인트가 되어야 한다는 논리다. LiteLLM, Portkey, OpenRouter 같은 제품이 이미 이 구조를 제품화해 놓은 지금, 직접 짤지 기존 제품에 올라탈지를 판단해야 하는 시점이 됐다.

## 요구사항을 기술 문제로 번역하기

"여러 모델 호출을 관리해주세요"는 사실 하나의 문제가 아니라 서로 독립적으로 결정해야 하는 네 가지 관심사가 섞여 있다. 첫째는 **인증·비용 추적**(누가, 어떤 모델을, 얼마나 호출했는가), 둘째는 **캐싱**(의미적으로 같은 질문에 모델을 다시 호출하지 않기), 셋째는 **라우팅**(이 요청에 어떤 제공자·모델이 비용 대비 품질이 가장 좋은가), 넷째는 **장애 격리**(한 제공자가 느려지거나 죽었을 때 트래픽을 다른 쪽으로 넘기기)다. 이 네 가지를 하나의 래퍼 함수에 욱여넣으면 캐시 정책을 바꿀 때마다 라우팅 로직까지 건드리게 되는 결합이 생긴다. 그래서 실제 작업은 "게이트웨이 하나 만들어주세요"가 아니라, 이 네 관심사를 순서가 있는 파이프라인의 독립된 단계로 분리해 설계하는 문제로 번역된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-09-llm-gateway-semantic-cache-model-routing-1.svg" alt="클라이언트 앱의 요청이 LLM 게이트웨이의 인증·쿼터 체크, 시맨틱 캐시, 모델 라우터, 서킷 브레이커·폴백 단계를 순서대로 거친 뒤 Claude·GPT·Gemini·자체 호스팅 모델 중 하나로 전달되고 응답이 다시 캐시에 저장되는 구조도" style="width:100%;">

이 구조에서 게이트웨이는 애플리케이션 코드와 여러 모델 제공자 API 사이의 통제 계층에 위치한다. 앞단에서 들어온 요청은 먼저 인증·쿼터 체크를 통과하고, 그다음 시맨틱 캐시에서 의미적으로 동일한 과거 질의가 있었는지 확인한다. 캐시 미스일 때만 라우터로 넘어가 어떤 제공자·모델을 쓸지 결정하고, 실제 호출 직전에 서킷 브레이커가 해당 제공자의 최근 에러율을 확인해 임계치를 넘겼으면 다른 제공자로 폴백한다. 뒷단에는 Claude, GPT, Gemini 같은 외부 제공자와 필요하다면 자체 호스팅 모델이 있다. 게이트웨이를 빼면 이 네 가지 결정이 애플리케이션 코드 곳곳에 흩어져, 제공자를 하나 추가할 때마다 호출부 전체를 다시 손봐야 하는 상태로 남는다.

## 선택의 트레이드오프

| 접근 | 셀프호스팅 여부 | 시맨틱 캐시 | 벤더 종속 | 적합한 상황 |
|---|---|---|---|---|
| 직접 구축(사내 게이트웨이) | 완전 자체 운영 | 직접 구현 필요 | 없음 | 요구사항이 매우 특수하거나 규제가 엄격한 경우 |
| LiteLLM(오픈소스, 셀프호스팅) | 자체 운영 | Redis 연동 기본 수준 | 낮음 | 초기 비용을 낮추고 직접 제어하고 싶은 경우 |
| OpenRouter(SaaS) | 불필요 | 미지원 | 중간 | 여러 모델을 빠르게 실험해보려는 경우 |
| Portkey(관리형/셀프호스팅) | 선택 가능 | 전용 구현 | 중간~높음 | 캐싱·라우팅을 제품 수준으로 바로 쓰고 싶은 경우 |

직접 구축하면 네 관심사를 서비스 특성에 맞게 세밀히 조정할 수 있지만, 서킷 브레이커 임계치나 캐시 유사도 threshold 같은 세부 튜닝을 처음부터 다 맞혀야 하는 부담이 크다. 반대로 SaaS형 게이트웨이는 빠르게 시작할 수 있지만 캐싱 같은 핵심 기능이 아예 없거나(OpenRouter) 벤더의 라우팅 로직에 트래픽 흐름을 맡기게 된다. 트래픽이 적을 때는 캐싱·라우팅 없이 인증과 로깅만 하는 얇은 프록시로 시작하고, 호출량과 비용이 실제로 문제가 될 때 레이어를 하나씩 추가하는 편이 과도한 선행 투자를 피하는 길이다.

## 실제 프로젝트 진행 순서

1. **가장 단순한 프록시부터 시작한다.** 인증, 요청·응답 로깅, 모델별 비용 집계만 하는 얇은 레이어를 먼저 두고, 캐싱이나 라우팅 없이도 어떤 모델이 얼마나 호출되는지부터 눈으로 본다.
2. **실패율을 관찰하며 서킷 브레이커를 가장 먼저 추가한다.** 특정 제공자의 에러율이 짧은 시간 창에서 임계치를 넘으면 트래픽을 멈추고 대체 제공자로 넘기는 로직은, 캐싱보다 먼저 들어가야 할 안전장치다.
3. **중복 질의 패턴이 실제로 관찰될 때만 캐시를 도입한다.** 유사도 threshold는 처음엔 보수적으로 잡아 오탐(서로 다른 질문을 같은 답으로 처리)을 피하고, 캐시 히트율을 모니터링하며 점진적으로 조정한다.
4. **비용·품질 트레이드오프가 분명해지면 라우팅을 추가한다.** 저렴한 모델이 먼저 답하고 품질이 부족하면 상위 모델이 다듬는 캐스케이딩부터 시도하고, 요청을 분석해 최적 제공자를 고르는 시맨틱 라우팅은 그다음 단계로 미룬다.
5. **라우팅 정확도를 평가 하네스로 검증한다.** 캐스케이딩이나 시맨틱 라우팅을 프로덕션에 올리기 전에, 대표 질의 샘플로 어느 모델이 실제로 선택되고 그 선택이 타당한지 오프라인에서 먼저 확인한다.
6. **관측성을 처음부터 끝까지 유지한다.** 모든 단계(캐시 히트 여부, 선택된 라우팅 전략, 실제 호출된 제공자)를 요청 단위로 로그에 남겨, 비용이나 지연이 튈 때 어느 레이어가 원인인지 바로 추적할 수 있게 한다.

## 코드 예시 — LiteLLM 스타일 라우터와 폴백 설정

```yaml
model_list:
  - model_name: primary-chat
    litellm_params:
      model: anthropic/claude-sonnet
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: fallback-chat
    litellm_params:
      model: openai/gpt-5
      api_key: os.environ/OPENAI_API_KEY

router_settings:
  routing_strategy: "latency-based"
  fallbacks:
    - primary-chat: ["fallback-chat"]
  cooldown_time: 60
  allowed_fails: 3
```

```python
# 서킷 브레이커 임계치 판단을 단순화한 의사코드
if provider_error_rate(window="5m") > 0.3:
    route_to(fallback_provider)
    schedule_recovery_check(after_seconds=60)
```

## 실무 포인트

**캐시를 라우팅보다 먼저 두되, 신선도 문제를 간과하지 않는다.** 시맨틱 캐시는 의미적으로 같은 질문에 몇 달 전 답을 그대로 돌려줄 수 있다. 대화 맥락이 섞이는 멀티턴 요청이나 최신 정보가 중요한 질의는 캐시 대상에서 제외하는 규칙을 따로 둬야 한다.

**유사도 threshold를 숫자 하나로 고정하지 않는다.** threshold가 너무 낮으면 서로 다른 질문이 같은 캐시로 오인되고, 너무 높으면 캐시 히트율이 거의 나지 않는다. 실제 트래픽에서 오탐·누락 사례를 수집하며 점진적으로 조정해야 한다.

**벤더가 제공하는 절감률 수치를 그대로 믿지 않는다.** 캐싱·라우팅 제품들이 제시하는 비용 절감 수치는 대부분 벤더 자체 측정이므로, 자사 트래픽 패턴으로 직접 캐시 히트율과 실제 절감액을 측정한 뒤 도입 여부를 판단한다.

## 마무리

- "여러 모델 호출을 관리해주세요"는 인증·캐싱·라우팅·장애 격리라는 네 개의 독립된 관심사로 분해해, 순서가 있는 게이트웨이 파이프라인으로 설계하는 문제로 번역된다.
- 게이트웨이는 애플리케이션과 여러 모델 제공자 사이의 통제 계층에 위치하며, 시맨틱 캐시를 라우터보다 앞에 두는 구성이 비용 절감 관점에서 효율적이다.
- 도입은 단순 프록시 → 서킷 브레이커 → 캐시 → 라우팅 순으로 트래픽이 실제로 문제를 드러낼 때마다 한 층씩 추가하는 것이 과도한 선행 투자를 피하는 길이다.
