## 왜 세 가지를 동시에 가질 수 없다는 것인가

분산 시스템 관련 글을 보면 "CAP 정리에 따르면 일관성과 가용성을 동시에 가질 수 없다"는 문장이 자주 나온다. 이 말을 제대로 이해하려면 먼저 **네트워크 파티션(Partition)**이 뭔지 알아야 한다. 네트워크 파티션은 여러 서버로 이뤄진 시스템에서 서버 간 통신이 끊기는 상황을 말한다. 케이블 장애, 스위치 고장, 일시적인 네트워크 지연 등으로 언제든 발생할 수 있다.

## CAP의 세 요소

| 요소 | 의미 |
|---|---|
| Consistency(일관성) | 모든 노드가 동시에 같은 최신 데이터를 본다 |
| Availability(가용성) | 요청을 보내면 항상 응답을 받는다(에러 없이) |
| Partition Tolerance(분단 내성) | 네트워크 파티션이 발생해도 시스템이 계속 동작한다 |

## 왜 셋 다는 안 되는가

```text
분산 시스템은 네트워크 위에서 동작하는 이상 파티션(P)은 언젠가 반드시 일어난다.
그래서 실질적인 선택은 "P가 발생했을 때 C를 포기할 것인가, A를 포기할 것인가"다.

파티션 발생 시:
- C를 선택(CP) -> 최신 데이터를 보장 못 하면 응답을 거부한다 (일부 요청 실패)
- A를 선택(AP) -> 무조건 응답은 하지만, 오래된 데이터를 보여줄 수도 있다
```

## 예시로 보는 CP vs AP

```text
CP 선택 예시 (은행 계좌 잔액):
두 데이터센터 사이 통신이 끊겼다.
어느 쪽이 최신 잔액인지 확실하지 않으므로, 잔액 조회 요청을 일단 거부한다.
-> 사용자는 "일시적으로 조회할 수 없습니다" 에러를 본다 (가용성 희생)

AP 선택 예시 (SNS 좋아요 수):
두 데이터센터 사이 통신이 끊겼다.
정확한 좋아요 수를 몰라도 일단 각 서버가 알고 있는 값으로 응답한다.
-> 사용자는 살짝 다른 숫자를 볼 수 있지만 서비스는 멈추지 않는다 (일관성 희생)
```

## 실무 포인트

- **평소(파티션이 없을 때)는 C와 A를 둘 다 가질 수 있다.** CAP 트레이드오프는 오직 파티션이 실제로 발생했을 때만 강제로 선택해야 하는 상황이다. "항상 둘 중 하나만 가능하다"는 흔한 오해다.
- **모든 데이터가 같은 선택을 할 필요는 없다.** 결제·재고처럼 정확성이 중요한 데이터는 CP로, 좋아요 수·조회수처럼 약간의 오차가 허용되는 데이터는 AP로 설계를 나누는 것이 실무에서 흔한 접근이다.
- **CAP은 세 글자로 단순화된 프레임이라 현실을 완벽히 설명하지 못한다는 비판도 있다.** 실무에서는 CAP보다 더 세분화된 PACELC(파티션이 없을 때 지연시간과 일관성의 트레이드오프까지 고려하는 모델)를 함께 참고하기도 한다.

## 마무리 요약

- 네트워크 파티션은 분산 시스템에서 서버 간 통신이 끊기는 상황이며 언젠가 반드시 발생한다.
- CAP 정리는 파티션이 실제로 발생했을 때 일관성과 가용성 중 하나를 선택해야 한다는 것을 말한다.
- 모든 데이터를 같은 기준으로 설계할 필요 없이, 데이터 성격에 따라 CP와 AP를 나눠 적용하는 것이 현실적이다.
