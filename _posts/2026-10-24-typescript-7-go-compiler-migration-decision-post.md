## 왜 지금 이 판단이 필요한가

"레포가 커지니까 `tsc --noEmit` CI 단계가 3분, 5분씩 걸려요. 좀 빠르게 해주세요." 모노레포를 운영하는 팀이라면 한 번쯤 받아봤을 요구사항이다. 그동안 답은 늘 비슷했다 — 프로젝트 레퍼런스로 쪼개거나, 증분 빌드 캐시를 쓰거나, 아예 타입체크를 빌드 파이프라인에서 분리해 별도 잡으로 돌리거나. 어느 쪽도 근본적으로 "타입체커 자체가 JavaScript로 짜여 있어서 느리다"는 문제를 건드리지 못했다.

Microsoft는 2026년 7월 8일 TypeScript 7.0을 정식 출시(GA)하며 이 전제를 뒤집었다. 코드명 Corsa, tsc의 핵심 로직을 Go로 완전히 재작성한 네이티브 컴파일러다. 공식 발표에 따르면 전체 빌드 기준 8~12배 속도 향상이 보고됐고, VS Code 자체의 타입스크립트 프로젝트 같은 대형 코드베이스에서도 체감 가능한 수준의 개선이 확인됐다. 문제는 이 재작성이 단순 포팅이 아니라는 점이다. 기존 TypeScript(코드명 Strada)의 JavaScript 기반 프로그래매틱 컴파일러 API 위에 지어진 생태계 — ts-patch, 커스텀 AST 트랜스포머, ts-morph 같은 도구들 — 가 7.0의 Go 바이너리에서는 동작할 API 표면 자체가 없다. "그냥 버전만 올려주세요"가 통하지 않는 이유가 여기에 있다. 빌더 입장에서 중요한 질문은 "더 빨라지는가"가 아니라 "우리 툴체인 중 무엇이 그 API에 의존하고 있고, 지금 올려도 되는가"다.

## 핵심 개념 1 — Strada와 Corsa, 같은 tsc가 아니다

TypeScript 7.0은 두 개의 컴파일러가 공존하는 과도기 산물이다. `tsc` 실행 파일 자체는 이제 Go로 짠 Corsa 엔진을 가리키고, 일반적인 "컴파일하고 타입 에러 보여주기" 용도로는 기존 6.x와 거의 동일하게 동작한다. Microsoft는 타입 체크 로직 자체를 구조적으로 동일하게 포팅했다고 밝혔고, 실제로 평범한 프로젝트는 설정 변경 없이 그대로 컴파일된다.

문제는 "평범하지 않은" 지점이다. Strada 시절 `ts.createProgram`, `ts.transpileModule` 같은 내부 API를 직접 호출해 커스텀 변환을 끼워 넣던 도구들은 Corsa에 대응하는 API가 아직 없다. 프로그래매틱 컴파일러 API 자체가 7.1로 연기됐기 때문이다. 에디터 안에서 자동완성·호버를 담당하는 Language Service Plugin API는 7.0에도 남아 있다고 보고되지만, 빌드 타임에 타입 정보를 직접 조작하는 깊은 수준의 프로그래매틱 접근은 당분간 막혀 있다고 보는 편이 안전하다.

## 핵심 개념 2 — 가장 흔하게, 가장 조용히 깨지는 지점

- **ts-patch·커스텀 트랜스포머**: `transform` 플러그인을 `tsconfig.json`에 등록해 쓰던 프로젝트(데코레이터 메타데이터 가공, 경로 별칭 치환 등)는 Corsa가 해당 플러그인 훅 자체를 무시하거나 에러 없이 조용히 건너뛸 수 있다. "컴파일은 되는데 런타임에 뭔가 빠져 있다"는 형태로 나타나기 쉽다.
- **ts-morph 기반 코드 생성 스크립트**: 스키마에서 타입을 뽑아내거나 리팩터링 스크립트를 짜는 데 쓰던 ts-morph는 내부적으로 Strada의 프로그램 API에 의존한다. 7.1 API가 나오기 전까지는 구버전 TypeScript를 별도로 고정해 그 스크립트만 구버전으로 돌려야 한다.
- **ts-jest 등 테스트 러너 통합**: 내부 Strada API를 직접 호출하는 통합은 Corsa 네이티브 러너를 가리키게 하면 깨진다는 보고가 있다. 테스트 파이프라인만 당분간 구버전 `typescript` 패키지에 묶어두는 보수적 선택지가 현실적이다.
- **에디터 플러그인**: 커스텀 린트 규칙이나 자동완성 확장이 Language Service Plugin API만 쓴다면 비교적 안전하지만, 내부 체커 구조에 직접 접근한다면 재검증이 필요하다.

다행히 우회로는 있다. 7.0은 개발 도구가 구버전 JavaScript 기반 API로 폴백하고, 실제 컴파일만 네이티브 Go 러너가 맡는 **듀얼 설치** 구성을 지원한다. 전부 한 번에 올리는 대신, "빌드 타입체크는 Corsa, 플러그인 의존 스크립트는 당분간 구버전"으로 분리하는 것이 안전한 전환 경로다.

## 전체 시스템에서의 위치

TypeScript 컴파일러는 혼자 동작하지 않는다. 에디터 LSP, CI 타입체크, 번들러의 트랜스파일, 그리고 플러그인 생태계가 같은 `typescript` 패키지를 서로 다른 방식으로 호출한다. Corsa 전환이 이 중 어느 경로를 건드리는지 구분하는 것이 디버깅의 절반이다.

<img src="/assets/images/posts/2026-10-24-typescript-7-go-compiler-migration-decision-1.svg" alt="에디터 LSP, CI 타입체크, 번들러 트랜스파일, 플러그인 생태계가 각각 Strada(JS) API와 Corsa(Go) 바이너리 중 어디에 연결되는지 보여주는 구조도" style="width:100%;">

번들러의 실제 트랜스파일(JS로 벗겨내는 작업)은 이미 대부분 esbuild·SWC·oxc 같은 별도 네이티브 도구가 맡고 있었기 때문에 Corsa 전환의 직접 영향권 밖이다. Corsa가 실제로 바꾸는 것은 **타입 체크 자체**가 일어나는 경로 — 에디터의 실시간 타입 힌트와 CI의 `tsc --noEmit` — 그리고 그 타입 체크 결과에 프로그래매틱으로 접근하던 플러그인·스크립트 계층이다. 번들링 파이프라인을 손대지 않고도 타입체크 레이어만 교체할 수 있다는 뜻이기도 하다.

## 선택의 트레이드오프

| 선택지 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 즉시 전면 전환 | 8~12배 빌드 속도 확보, CI 비용 즉시 절감 | 커스텀 트랜스포머·ts-morph 스크립트 전수 재검증 필요 | 플러그인·프로그래매틱 API 의존이 거의 없는 프로젝트 |
| 듀얼 설치(타입체크만 전환) | 빌드 속도 개선 + 기존 툴체인 유지 | 두 버전을 당분간 함께 관리해야 함 | ts-patch·ts-jest 등에 의존하는 중형 이상 모노레포 |
| 당분간 6.x 유지 | 리스크 제로 | 7.1 프로그래매틱 API 공개 전까지 속도 이점 전혀 없음 | 레거시 코드 생성 파이프라인이 핵심 의존인 조직 |

모노레포에 데코레이터 메타데이터를 가공하는 커스텀 트랜스포머가 하나라도 박혀 있다면, 첫 번째 선택지는 사실상 배제해야 한다. 듀얼 설치로 타입체크 레이어만 먼저 옮기고, 플러그인 의존 스크립트는 7.1 프로그래매틱 API 공개 이후로 미루는 쪽이 현실적인 중간 지점이다.

## 실제 프로젝트 진행 순서

1. **`tsconfig.json`의 `plugins`·`transform` 설정과 `ts-patch`, `ttypescript` 같은 레지스트리 의존을 전수 조사한다.** 이게 하나라도 있으면 즉시 전면 전환은 배제한다.
2. **ts-morph·커스텀 코드 생성 스크립트를 찾아 별도 디렉터리로 분리하고, 그 스크립트의 `package.json`만 TypeScript 6.x에 고정한다.**
3. **CI의 타입체크 단계만 먼저 Corsa(`tsc` 7.0)로 교체해 속도를 측정한다.** 번들러 트랜스파일은 손대지 않는다.
4. **ts-jest 등 테스트 통합이 내부 API를 직접 호출하는지 확인하고, 깨지면 테스트 전용으로 구버전을 고정한다.**
5. **에디터 플러그인은 Language Service Plugin API만 쓰는지 확인 후 적용한다.**
6. **7.1 프로그래매틱 API 공개 공지를 구독해 두고, 공개 즉시 남은 구버전 의존을 정리하는 2차 전환을 계획한다.**

```json
// package.json — 듀얼 설치 구성 예시
{
  "devDependencies": {
    "typescript": "^7.0.0",
    "typescript-strada": "npm:typescript@^6.9.0"
  },
  "scripts": {
    "typecheck": "tsc --noEmit",
    "generate:types": "typescript-strada-node scripts/generate-types.ts"
  }
}
```

## 마무리 요약

- TypeScript 7.0(Corsa)은 tsc 자체를 Go로 재작성해 8~12배 빠른 타입체크를 제공하지만, 프로그래매틱 컴파일러 API는 7.1로 연기돼 ts-patch·ts-morph·일부 테스트 통합이 조용히 깨질 수 있다.
- 번들러의 트랜스파일 경로는 이미 esbuild·SWC가 맡고 있어 영향이 적고, 실제 영향은 에디터 LSP와 CI 타입체크, 플러그인 계층에 집중된다.
- 플러그인·코드 생성 의존이 있는 프로젝트는 타입체크 레이어만 먼저 Corsa로 옮기는 듀얼 설치 전략이 안전하다.
