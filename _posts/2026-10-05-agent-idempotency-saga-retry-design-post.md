## 왜 지금 이 문제가 불거지는가

"API 호출이 타임아웃 나면 에이전트가 알아서 재시도하게 해주세요." 이 요구는 전통적인 분산 시스템에서는 이미 풀린 문제처럼 보인다. 클라이언트가 요청마다 고유한 Idempotency Key를 발급하고, 서버는 같은 키로 들어온 요청을 중복 처리하지 않으면 된다. 그런데 실제로 한 팀은 이 패턴을 에이전트에 그대로 적용했다가 테스트 고객에게 847달러를 두 번 청구하는 사고를 냈다. 결제 API 호출이 타임아웃 났고, 재시도 로직이 "첫 번째 호출이 실제로는 성공해서 결제가 이미 걸렸는지"를 확인하지 않은 채 다시 호출한 것이다.

문제는 단순한 구현 실수가 아니라 더 근본적인 데 있다. 전통적인 재시도에서는 **재시도된 요청이 원본과 완전히 동일하다**는 전제가 성립한다. 그런데 에이전트 시스템에서는 같은 논리적 작업을 다시 수행해도 LLM이 다른 토큰 샘플링, 다른 도구 선택, 다른 행동 순서를 거칠 수 있다 — 사이드이펙트는 여전히 결정적이어야 하는데, 그 사이드이펙트를 만들어내는 추론 과정은 결정적이지 않다. "도쿄행 항공편을 예약해줘"라는 작업이 첫 시도에서는 항공사 A의 API를, 재시도에서는 항공사 B의 API를 호출할 수 있다는 뜻이다. 이 경우 첫 시도의 Idempotency Key는 재시도를 전혀 보호하지 못한다 — 근본적으로 다른 작업이기 때문이다. 2026년 들어 이 문제가 비결정적 노드 출력, 추론 실패를 주요 에러 유형으로 다뤄야 한다는 점, 비멱등적 재시도라는 세 가지 특성으로 공식적으로 정리됐을 만큼, 전통적인 워크플로 엔진이 겪어보지 못한 새로운 난제로 자리 잡았다.

## 요구사항을 기술 문제로 번역하기

"실패하면 재시도해주세요"는 실제로 세 가지 다른 보장을 요구한다. 첫째, **같은 논리적 행동이 중복 실행되지 않도록 보장**하는 것(결제가 두 번 걸리지 않게). 둘째, **재시도 시 행동 자체가 달라질 수 있다는 전제 위에서 안전하게 처리**하는 것(항공사가 바뀌어도 예약이 꼬이지 않게). 셋째, **여러 단계로 구성된 작업 중 일부만 성공했을 때 나머지를 보정**하는 것(호텔은 예약됐는데 항공편이 실패했을 때 호텔 예약을 취소). 이 세 요구를 하나의 "재시도 로직"으로 뭉뚱그리면, 단일 호출에는 통하지만 멀티스텝 에이전트 워크플로에서는 반드시 깨진다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-05-agent-idempotency-saga-retry-design-1.svg" alt="에이전트의 도구 호출이 tool-call ID, 세션 ID, 도구 이름, 인자 해시를 조합해 Idempotency Key를 만들고 원장에 확인 후 실행 후 기록하는 순서를 거쳐 외부 API에 도달하는 구조와, 멀티스텝 워크플로에서 각 단계마다 보정 액션을 갖는 Saga 패턴을 결합한 구조도" style="width:100%;">

에이전트의 도구 호출이 사이드이펙트가 있는 외부 API에 도달하기 전, 먼저 **Idempotency 레이어**를 거친다. 키는 모델이 생성한 tool-call ID, 대화·세션 ID, 도구 이름, 그리고 직렬화된 인자의 해시를 조합해 만든다 — 같은 논리적 행동의 모든 재시도에서는 동일하지만, 진짜로 다른 행동(다른 항공사, 다른 금액)에서는 다른 키가 나오도록 설계하는 것이 핵심이다. 이 키는 **원장(ledger)**에 먼저 확인되고, 실행이 끝난 뒤에야 결과가 기록된다. 순서를 뒤집어 "실행 후 확인"으로 짜면 그 사이 타이밍에 중복 실행이 이미 벌어진 뒤이므로 멱등성 자체가 깨진다. 여러 단계로 구성된 워크플로(항공편 예약 → 호텔 예약 → 결제)에서는 이 원장이 각 단계의 성공 여부와 함께 **보정 액션**(취소, 환불, 역방향 호출)을 같이 들고 있어야 한다. 한 단계가 실패하면 원장을 보고 이미 완료된 단계들을 역순으로 보정하거나, 실패한 단계만 다시 시도할지를 판단한다 — 이것이 전통적 분산 시스템의 Saga 패턴을 에이전트 워크플로에 맞게 가져온 형태다.

## 선택의 트레이드오프

| 전략 | 비결정적 재시도 대응 | 멀티스텝 실패 처리 | 구현 복잡도 | 적합한 상황 |
|---|---|---|---|---|
| 클라이언트 생성 UUID 키 | 불가능(행동이 바뀌면 보호 실패) | 없음 | 가장 낮음 | 단일 호출, 행동이 절대 바뀌지 않는 작업 |
| 인자 해시 기반 키 | 가능(행동이 바뀌면 다른 키) | 없음 | 낮음~중간 | 단일 사이드이펙트 호출(결제, 전송) |
| 원장 + 체크-실행-기록 순서 | 가능 | 단일 단계 한정 | 중간 | 타임아웃·네트워크 재시도가 잦은 단일 작업 |
| Saga + 보정 액션 | 가능 | 전체 워크플로 보정 가능 | 높음 | 여행 예약처럼 여러 외부 API를 묶는 워크플로 |
| 재시도 없음(실패 시 중단) | 해당 없음 | 사람이 수동 개입 | 가장 낮음 | 되돌리기 어려운 고위험 단일 행동 |

표에서 가장 중요한 함정은 "클라이언트 생성 UUID 키"다. 이 방식은 전통적인 API 클라이언트에서는 충분하지만, 에이전트가 재시도마다 다른 행동을 선택할 수 있다는 전제를 반영하지 못한다. 반대로 Saga + 보정 액션은 가장 안전하지만, 모든 사이드이펙트 도구마다 "되돌리는 법"을 정의해야 하므로 구현 비용이 크다 — 멱등성 키의 TTL도 함께 고려해야 한다. 결제 API의 Idempotency Key는 보통 24시간짜리지만, 에이전트 워크플로는 예약을 며칠씩 들고 있다가 확정하는 경우가 있어 키가 만료된 뒤 재시도하면 보호가 사라진다.

## 실제 프로젝트 진행 순서

1. **사이드이펙트가 있는 도구 호출을 전부 식별한다.** 읽기 전용 조회와 결제·예약·전송처럼 되돌리기 어려운 쓰기 작업을 구분하고, 후자부터 설계 대상으로 좁힌다.
2. **키 생성 전략을 정의한다.** tool-call ID, 세션 ID, 도구 이름, 인자 해시를 조합해 "같은 행동의 재시도"와 "다른 행동"을 구분할 수 있는 키 체계를 만든다.
3. **원장에서 체크-실행-기록 순서를 코드 레벨에서 강제한다.** 실행 후 확인하는 순서로 짜인 코드가 없는지 리뷰 체크리스트에 명시적으로 넣는다.
4. **멀티스텝 워크플로에는 단계별 보정 액션을 미리 설계한다.** 모든 쓰기 도구에 "취소/환불/역방향 호출"이 정의돼 있는지 먼저 확인하고, 없는 도구는 워크플로에 넣기 전에 보정 방법부터 만든다.
5. **키 TTL을 에이전트 워크플로의 실제 수명에 맞춘다.** 결제 API 기본값(보통 24시간)을 그대로 쓰지 말고, 워크플로가 실제로 얼마나 오래 지속될 수 있는지 측정해 TTL을 재설정한다.

## 실무 포인트

**"재시도 가능"을 모든 도구에 기본값으로 두지 않는다.** 되돌리기 어려운 고위험 행동은 자동 재시도 대신 실패 시 사람에게 넘기는 것이 더 안전한 기본값이다.

**인자 해시 키를 만들 때 비본질적인 필드를 제외한다.** 타임스탬프나 요청 ID처럼 매번 달라지는 필드가 해시에 섞이면, 같은 논리적 행동인데도 매번 다른 키가 나와 멱등성이 무력화된다.

**보정 액션은 사이드이펙트 도구를 설계하는 시점에 함께 만든다.** 워크플로를 다 짜고 나서 "이 결제를 어떻게 취소하지"를 고민하면 이미 늦다 — 결제 도구를 추가할 때 환불 도구도 같이 추가하는 것을 원칙으로 삼는다.

## 마무리

- "실패하면 재시도해주세요"는 중복 실행 방지, 비결정적 재시도 대응, 멀티스텝 보정이라는 서로 다른 세 가지 보장을 요구하므로 하나의 재시도 로직으로 뭉뚱그리면 안 된다.
- 전통적인 클라이언트 생성 Idempotency Key는 에이전트가 재시도마다 다른 행동을 선택할 수 있다는 전제를 반영하지 못하므로, tool-call ID·세션·인자 해시를 조합한 키와 체크-실행-기록 순서가 필요하다.
- 여러 외부 API를 묶는 워크플로에는 Saga 패턴의 보정 액션을 도구 설계 시점부터 함께 만들어야, 일부 단계만 성공했을 때도 안전하게 되돌릴 수 있다.
