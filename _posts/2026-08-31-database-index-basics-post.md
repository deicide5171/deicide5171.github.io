## 왜 인덱스를 다 걸면 안 된다고 하는가

"쿼리가 느리면 인덱스를 걸어라"는 조언은 절반만 맞다. 인덱스는 읽기(SELECT)를 빠르게 해주는 대신, 쓰기(INSERT/UPDATE/DELETE)마다 인덱스도 함께 갱신해야 하므로 쓰기 성능을 떨어뜨리고 저장 공간도 추가로 쓴다. 이 트레이드오프를 모르고 모든 컬럼에 인덱스를 걸면 오히려 전체 성능이 나빠질 수 있다.

## 인덱스가 하는 일: 책의 찾아보기

인덱스가 없으면 DB는 원하는 행을 찾기 위해 테이블 전체를 처음부터 끝까지 훑어야 한다(Full Table Scan). 이는 마치 책에서 특정 단어를 찾기 위해 첫 페이지부터 넘기는 것과 같다. 인덱스는 정렬된 별도의 자료구조(대부분 B-Tree)에 값과 그 값이 있는 행 위치를 저장해두어, 찾아보기 페이지처럼 훨씬 빠르게 원하는 행에 도달하게 해준다.

| 상황 | 인덱스 없음 | 인덱스 있음 |
|---|---|---|
| 100만 건 중 1건 조회 | 최악의 경우 100만 건 전체 스캔 | B-Tree 탐색으로 log(N) 수준 |
| INSERT 1건 | 테이블에만 추가 | 테이블 + 인덱스 구조 모두 갱신 |

## 코드 예제: 인덱스 유무의 차이 확인

```sql
-- 인덱스가 없을 때 실행 계획
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- type: ALL (Full Table Scan) -> 전체 스캔

-- 인덱스 생성
CREATE INDEX idx_users_email ON users(email);

-- 다시 실행
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- type: ref/const -> 인덱스를 타고 바로 접근
```

`EXPLAIN`의 `type` 값이 `ALL`이면 인덱스를 못 타고 전체 스캔 중이라는 뜻이므로, 이 컬럼이 인덱스 후보인지 검토해야 한다.

## 어떤 컬럼에 인덱스를 걸어야 하나

- **`WHERE` 절에 자주 등장하는 컬럼**: 조회 조건으로 자주 쓰이는 컬럼이 우선순위 1순위다.
- **`JOIN`의 연결 키로 쓰이는 컬럼**: 조인 성능에 직접적인 영향을 준다.
- **카디널리티(값의 다양성)가 높은 컬럼**: `성별`처럼 값이 두세 가지뿐인 컬럼은 인덱스 효과가 거의 없다. 이메일, 주문번호처럼 값이 거의 유일한 컬럼이 인덱스에 적합하다.

## 실무 포인트

- **자주 갱신되는 테이블에 인덱스를 과도하게 걸면 쓰기 성능이 크게 저하된다.** 쓰기가 압도적으로 많은 로그성 테이블은 인덱스를 최소화해야 한다.
- **인덱스를 걸었다고 항상 쓰이는 것은 아니다.** 옵티마이저가 판단하기에 전체 스캔이 더 빠르다고 보면(예: 테이블이 매우 작을 때) 인덱스를 무시하고 스캔한다.
- **여러 컬럼을 함께 조회 조건으로 쓴다면 복합 인덱스를 고려하되, 컬럼 순서가 매우 중요하다.** `(a, b)` 인덱스는 `a`만으로 조회할 때도 쓰이지만 `b`만으로 조회할 때는 쓰이지 않는다.

## 마무리 요약

- 인덱스는 읽기를 빠르게 하는 대신 쓰기 성능과 저장 공간을 대가로 치른다.
- `EXPLAIN`으로 `type: ALL`이 나오는 쿼리가 인덱스 후보를 찾는 시작점이다.
- 값이 다양한(카디널리티 높은) 컬럼, 특히 WHERE·JOIN에 자주 쓰이는 컬럼이 인덱스 우선순위가 높다.
