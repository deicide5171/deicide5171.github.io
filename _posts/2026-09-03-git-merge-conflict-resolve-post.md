## 충돌 메시지를 봐도 뭘 해야 할지 모르겠다면

`git merge`나 `git pull` 후 `CONFLICT (content): Merge conflict in file.js`가 뜨면 초보자는 당황하기 쉽다. 하지만 충돌은 에러가 아니라 **Git이 "두 사람이 같은 부분을 다르게 고쳤으니 어느 쪽이 맞는지 사람이 정해달라"고 요청하는 상태**일 뿐이다. 절차만 알면 침착하게 해결할 수 있다.

## 충돌 표시 기호 읽는 법

충돌이 난 파일을 열면 다음과 같은 표시가 들어가 있다.

```text
<<<<<<< HEAD
내 브랜치의 코드 (현재 체크아웃한 브랜치)
=======
병합하려는 브랜치의 코드
>>>>>>> feature-branch
```

| 기호 | 의미 |
|---|---|
| `<<<<<<< HEAD` | 여기부터 내 쪽 코드 시작 |
| `=======` | 내 쪽과 상대 쪽의 경계 |
| `>>>>>>> 브랜치명` | 여기까지 상대 쪽 코드 |

## 해결 단계

```bash
# 1. 어떤 파일이 충돌났는지 확인
git status

# 2. 충돌난 파일을 에디터로 열어 <<<<, ====, >>>> 표시를 찾는다
#    -> 내 코드만 남길지, 상대 코드만 남길지, 둘을 합칠지 직접 결정
#    -> 결정 후 <<<<, ====, >>>> 표시 줄은 모두 삭제한다

# 3. 해결한 파일을 스테이징
git add file.js

# 4. 병합 완료
git commit   # merge 커밋 메시지가 자동으로 채워져 있다
```

핵심은 `<<<<`, `====`, `>>>>` 세 종류의 표시 줄을 **반드시 모두 지워야** 한다는 것이다. 이 표시가 하나라도 코드에 남아있으면 문법 오류로 빌드가 깨진다.

## 실무 포인트

- **충돌이 무서워서 무작정 한쪽을 통째로 선택하지 마라.** "내 것으로 다 덮어쓰기"를 하면 상대방이 작업한 내용이 통째로 사라질 수 있다. 두 변경이 각각 무엇을 의도했는지 이해하고 합치는 것이 원칙이다.
- **잘못 건드렸다면 병합을 취소하고 처음부터 다시 할 수 있다.** `git merge --abort`를 쓰면 병합 시작 전 상태로 안전하게 되돌아간다. 꼬였다고 느끼면 억지로 밀어붙이기보다 abort 후 다시 시작하는 것이 낫다.
- **충돌을 줄이려면 작은 단위로 자주 병합하는 것이 좋다.** 오래된 브랜치를 뒤늦게 병합하면 그동안 쌓인 변경이 한꺼번에 충돌하므로, 주기적으로 기본 브랜치를 병합해 두는 습관이 충돌을 크게 줄인다.
- **에디터의 3-way merge 도구를 활용하면 훨씬 수월하다.** VS Code 등은 충돌 부분을 "현재 변경 수락 / 수신 변경 수락 / 둘 다 수락" 버튼으로 보여줘 기호를 직접 지우는 실수를 줄여준다.

## 마무리 요약

- 병합 충돌은 에러가 아니라 사람이 판단해달라는 Git의 요청 상태다.
- `<<<<`, `====`, `>>>>` 표시를 읽고 어느 코드를 남길지 정한 뒤 그 표시 줄은 모두 지워야 한다.
- 꼬이면 `git merge --abort`로 안전하게 되돌리고, 작은 단위로 자주 병합해 충돌 자체를 줄이는 것이 좋다.
