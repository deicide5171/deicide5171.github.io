## 왜 지금 이 판단이 불거지는가

"우리 팀은 Claude Code로 기능 구현하고, 리뷰는 Copilot한테 시키고, 개인 작업은 Cursor를 쓰는데, 레포 지침을 세 번 따로 써야 하나요?" 요즘 팀이라면 한 번쯤 받아봤을 질문이다. 처음엔 CLAUDE.md 하나만 관리하면 됐지만, 팀원마다 선호하는 도구가 다르고 CI에서는 Codex CLI를 돌리기 시작하면서 지침 파일이 `.cursorrules`, `.github/copilot-instructions.md`, `CLAUDE.md`로 늘어난다. 코딩 컨벤션을 하나 바꾸면 서너 파일을 동시에 고쳐야 하고, 깜빡하고 하나만 수정하면 도구마다 다른 방식으로 동작하는 일이 생긴다.

이 파편화를 줄이려는 움직임이 AGENTS.md다. OpenAI가 공개한 이 포맷은 이후 MCP, Block의 goose와 함께 리눅스 재단 산하의 새로운 Agentic AI Foundation으로 거버넌스가 이관됐고, Google·Cursor·Sourcegraph·JetBrains 등 여러 벤더가 공동으로 밀고 있다. 레포 루트에 두는 평범한 마크다운 파일이며 필수 필드도 특별한 문법도 없다. 공식 문서는 이를 "에이전트를 위한 README"라고 부른다. 2026년 기준 수만 개 저장소가 이 파일을 채택했고, Codex CLI·Cursor·Windsurf·Copilot·Gemini CLI·Aider·Devin 등 수십 개 도구가 네이티브로 읽는다. 다만 Claude Code가 AGENTS.md를 직접 읽는지, 여전히 CLAUDE.md를 우선하는지는 출처마다 설명이 갈리므로 실제 적용 전에 Anthropic 공식 문서로 확인해야 한다.

## 요구사항을 기술 문제로 번역하기

"지침을 한 곳에 모아주세요"는 사실 두 가지 서로 다른 요구가 섞여 있다. 하나는 "여러 도구가 같은 코딩 컨벤션·아키텍처 설명·테스트 실행법을 공유하게 해주세요"이고, 다른 하나는 "도구별로만 의미 있는 설정(권한 범위, MCP 서버 목록, 자동 승인 규칙)은 그 도구 안에 남겨주세요"다. 전자는 AGENTS.md 한 파일로 충분히 해결되지만, 후자는 AGENTS.md 스펙 자체에 없는 개념이라 도구별 파일로 남을 수밖에 없다. 그래서 실제 작업은 "모든 걸 한 파일로 합쳐주세요"가 아니라, "공유 가능한 지침과 도구 전용 설정을 구분하고, 전자는 단일 소스로, 후자는 그 단일 소스를 참조하는 얇은 어댑터로 설계해주세요"라는 계층 설계 문제로 번역된다. 모노레포라면 여기에 한 가지가 더 붙는다. 하위 디렉터리마다 다른 지침이 필요할 때, AGENTS.md는 가장 가까운(디렉터리 트리상 최근접) 파일이 우선 적용되는 중첩 구조를 지원하므로, 이 우선순위 규칙을 어디까지 활용할지도 설계에 포함해야 한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-09-agents-md-multi-tool-config-standard-1.svg" alt="레포 루트의 AGENTS.md가 공유 지침의 단일 소스로 존재하고, CLAUDE.md·.cursor/rules·copilot-instructions.md 같은 도구별 어댑터 파일이 이를 참조하며 도구 전용 설정만 따로 가지고, 각 AI 코딩 도구가 이 계층을 읽어 실제 에이전트 세션으로 이어지는 구조도" style="width:100%;">

이 구조에서 AGENTS.md는 사람이 작성하는 설정과 에이전트가 소비하는 설정 사이의 공유 계층에 위치한다. 앞단에는 팀의 코딩 컨벤션, 아키텍처 개요, 테스트·빌드 명령처럼 어떤 도구를 쓰든 똑같이 적용돼야 하는 지식이 있다. 이 지식이 AGENTS.md 하나로 들어간다. 뒷단에는 Claude Code·Cursor·Copilot·Codex CLI 같은 개별 도구가 있고, 이들은 각자의 포맷(심볼릭 링크, `@AGENTS.md` 임포트, 또는 네이티브 읽기)으로 AGENTS.md를 참조하면서 자기만의 추가 설정(권한 경계, 등록된 MCP 서버, 자동 실행 허용 명령)을 별도 파일에 보관한다. AGENTS.md를 빼면 이 공유 지식이 도구 수만큼 복제되고, 하나를 고칠 때마다 나머지를 수동으로 동기화해야 하는 상태로 되돌아간다.

## 선택의 트레이드오프

| 접근 | 유지보수 비용 | 도구별 기능 활용 | 적합한 상황 |
|---|---|---|---|
| 도구별 파일을 각각 독립 관리 | 높음(파일 수만큼 중복) | 높음 | 팀이 도구 하나만 표준으로 쓰는 경우 |
| AGENTS.md 단일 파일만 사용 | 낮음 | 낮음(도구 전용 설정 표현 불가) | 소규모 팀, 공유 지침만으로 충분한 경우 |
| AGENTS.md + 도구별 얇은 어댑터(하이브리드) | 중간 | 높음 | 여러 도구를 혼용하는 팀, 모노레포 |
| 사내 자체 설정 포맷 + 변환 스크립트 | 높음(스크립트 유지보수) | 매우 높음 | 사내 도구까지 포함해 세밀한 제어가 필요한 경우 |

단일 AGENTS.md만으로 끝내고 싶어지는 유혹이 있지만, 그 안에 권한 설정이나 MCP 서버 목록처럼 도구마다 의미가 다른 내용을 억지로 욱여넣으면 스펙 밖의 비표준 필드가 생기고, 그 도구가 스펙을 엄격히 따를수록 오히려 무시된다. 반대로 도구별 파일을 완전히 독립적으로 유지하면 처음에는 편하지만, 코딩 컨벤션 한 줄 바꿀 때마다 반복 작업이 선형으로 늘어난다. 결국 "공유 지식은 하나, 도구 전용 설정은 각자"로 역할을 분리하는 하이브리드가 대부분의 멀티 도구 팀에 현실적인 지점이다.

## 실제 프로젝트 진행 순서

1. **현재 흩어진 지침 파일을 먼저 전수 조사한다.** CLAUDE.md, `.cursorrules`, `.github/copilot-instructions.md` 등 레포에 존재하는 모든 지침 파일을 나열하고, 내용이 겹치는 부분과 도구 전용인 부분을 표로 구분한다.
2. **겹치는 부분만 추출해 AGENTS.md를 새로 작성한다.** 코딩 컨벤션, 디렉터리 구조 설명, 빌드·테스트 명령처럼 도구 중립적인 내용만 담는다.
3. **도구별 파일을 어댑터로 전환한다.** 가능한 도구는 AGENTS.md를 참조하는 심볼릭 링크나 임포트 구문으로 바꾸고, 도구 전용 설정만 그 파일에 남긴다.
4. **모노레포라면 서브디렉터리 중첩 구조를 설계한다.** 프론트엔드·백엔드처럼 컨벤션이 다른 영역에는 하위 디렉터리에 더 구체적인 AGENTS.md를 추가해 최근접 우선 규칙을 활용한다.
5. **CI에 지침 드리프트 체크를 추가한다.** AGENTS.md와 도구별 어댑터 파일의 참조 관계가 깨졌는지(예: 심볼릭 링크가 끊겼는지) 자동으로 검사하는 린트 스텝을 넣는다.
6. **팀 전체 전환 전에 한 레포에서 먼저 검증한다.** 실제로 각 도구가 기대한 지침을 읽고 있는지 세션을 띄워 직접 확인한 뒤 점진적으로 확대한다.

## 코드 예시 — AGENTS.md와 CLAUDE.md 어댑터 구성

```markdown
# AGENTS.md
## 프로젝트 개요
Jekyll 기반 정적 블로그. 빌드: `bundle exec jekyll build`

## 코딩 컨벤션
- 커밋 메시지는 한국어, 50자 이내 요약 줄 우선
- 마크다운 포스트는 frontmatter 필수 필드 유지

## 테스트
- `bundle exec htmlproofer ./_site` 로 링크 검증
```

```bash
# CLAUDE.md는 AGENTS.md를 가리키는 심볼릭 링크로 전환
ln -sf AGENTS.md CLAUDE.md

# 도구 전용 설정(권한, MCP 서버 목록)은 별도 파일에만 둔다
# .claude/settings.json, .cursor/mcp.json 등
```

## 실무 포인트

**AGENTS.md를 권한·보안 설정의 저장소로 쓰지 않는다.** 이 포맷은 공개 저장소에 커밋되는 경우가 많고 특정 필드를 강제하지 않으므로, 자동 실행 허용 명령 목록이나 API 키 같은 민감한 설정은 반드시 도구별 설정 파일이나 환경 변수로 분리해야 한다.

**심볼릭 링크가 안 되는 환경을 가정하고 대안을 준비한다.** 일부 CI 러너나 Windows 환경에서는 심볼릭 링크가 깨지거나 체크아웃 시 무시될 수 있다. 이런 경우 빌드 스크립트 단계에서 AGENTS.md 내용을 CLAUDE.md로 복사하는 전처리 스텝을 둔다.

**표준이 아직 움직이고 있다는 점을 감안한다.** 거버넌스가 리눅스 재단으로 넘어간 지 얼마 안 됐고 도구별 지원 수준도 계속 바뀌고 있으므로, 벤더 블로그보다 각 도구의 공식 문서와 agents.md 공식 사이트를 분기마다 다시 확인하는 루틴을 팀에 넣어두는 편이 안전하다.

## 마무리

- "지침을 한 곳에 모아주세요"는 공유 가능한 지식과 도구 전용 설정을 구분하는 계층 설계 문제로 번역된다.
- AGENTS.md는 사람이 쓰는 지침과 각 AI 코딩 도구 사이의 공유 계층에 위치하며, 도구별 파일은 그 위에 얇은 어댑터로 남는 하이브리드 구조가 대부분의 멀티 도구 팀에 현실적이다.
- 전환은 기존 지침 전수 조사 → 공유분 추출 → 도구별 어댑터화 → 모노레포 중첩 설계 → CI 드리프트 체크 순으로 점진적으로 진행한다.
