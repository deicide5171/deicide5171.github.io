## 왜 지금 이 문제가 불거지는가

"담당 구역 레이어만 보이게 하고, 다른 부서 데이터는 못 보게 해주세요." 다부서가 하나의 GeoServer를 공유할 때 거의 반드시 나오는 요구다. GeoFence나 GeoServer 내장 ACL로 레이어·속성 단위 보안을 걸면 이 요구 자체는 어렵지 않게 풀린다. 문제는 그다음이다. "지도가 느려요, 캐시 좀 걸어주세요"라는 요구가 같은 레이어에 겹치는 순간, 오랫동안 GeoWebCache(GWC)는 두 요구를 동시에 만족시키지 못했다.

GWC는 원래 보안 subsystem을 전혀 모르는 상태로 설계됐다. WMS 요청이 들어오면 레이어 이름과 bbox·zoom 조합으로 캐시 키를 만들고, 같은 키로 들어오는 다음 요청에는 저장된 타일을 그대로 돌려준다. 이 구조에서 보안이 걸린 레이어를 캐싱하면, A 사용자가 먼저 요청해 구워진 타일이 B 사용자에게도 똑같이 나간다. A의 권한으로 렌더링된 타일에 B가 봐서는 안 되는 속성이 그려져 있어도 캐시는 구분할 방법이 없다. 그래서 그동안 실무에서 쓸 수 있는 선택지는 사실상 하나뿐이었다 — 보안이 걸린 레이어는 캐싱을 아예 끈다. 캐시가 꺼지는 순간 해당 레이어는 매 요청마다 렌더링 비용을 그대로 지불하고, 트래픽이 몰리면 가장 먼저 느려지는 레이어가 된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-31-geowebcache-security-aware-tiling-gsip-241-1.svg" alt="타일 요청이 GeoServer 보안 관리자를 거쳐 ACCESS_LIMITS_KEY와 SECURITY_TAGS_KEY가 합성 파라미터로 주입된 뒤 GWC 캐시 키에 반영되어, 서로 다른 권한의 요청이 같은 bbox라도 별도 캐시 엔트리로 분리 저장되는 구조도" style="width:100%;">

Andrea Aime가 제안해 통과된 GSIP 241(GeoWebCache Security-Aware Tiling)은 이 구멍을 캐시 키 설계 자체로 메운다. 핵심은 **보안 평가 결과를 캐시 키의 일부로 만드는 것**이다. 요청이 GWC에 도달하기 전에 GeoServer의 접근 관리자(GeoFence·내장 ACL)가 먼저 현재 사용자의 권한을 평가해 `ACCESS_LIMITS_KEY`라는 합성 파라미터를 타일 요청에 끼워 넣는다. 속성 단위 CQL 필터처럼 더 세밀한 제약이 걸려 있으면 `SECURITY_TAGS_KEY`가 추가로 붙는다(이 값이 붙으려면 `ACCESS_LIMITS_KEY`가 먼저 있어야 한다). 이 두 키가 실제 캐시 저장 경로에 포함되기 때문에, 권한이 다른 두 사용자가 같은 bbox·zoom을 요청해도 서로 다른 캐시 엔트리를 받게 된다. 데이터가 들어오고(벡터 소스·보안 규칙) → GeoServer 접근 관리자가 평가하고 → GWC가 권한별로 분리된 타일을 캐싱해 내보내는, 이전 글에서 다룬 GWC 캐싱 파이프라인 앞단에 '보안 평가' 단계가 새로 끼어든 구조다.

## 선택의 트레이드오프

| 방식 | 보안성 | 캐시 효율 | 운영 복잡도 | 적합한 상황 |
|---|---|---|---|---|
| 보안 레이어 캐시 비활성화 (기존 방식) | 확실함 | 사실상 0 — 매번 렌더링 | 낮음 | 트래픽이 적고 레이어 수가 적을 때 |
| GSIP 241 security-aware caching | 확실함 | 권한 조합 수에 반비례 | 중간 — 무효화 전략 별도 필요 | 권한 조합이 소수(역할 몇 개)로 수렴할 때 |
| 공개·개인화 레이어 분리 설계 | 확실함 | 공개 레이어는 기존과 동일 | 중간 — 레이어·엔드포인트 이원화 | 공개 데이터가 대부분이고 개인화는 일부일 때 |
| 프록시 계층에서 사용자 그룹별 캐시 네임스페이스 분리 | 확실함 | 그룹 수만큼 캐시 중복 | 높음 — 별도 인프라 구축 | GWC 자체를 못 바꾸는 레거시 환경 |

표에서 가장 중요한 변수는 **권한 조합의 카디널리티**다. 같은 bbox·zoom이라도 캐시 키가 `ACCESS_LIMITS_KEY` 값만큼 쪼개지기 때문에, 역할이 3~5개로 고정돼 있다면 캐시 히트율은 거의 그대로 유지된다. 반대로 사용자 ID별로 동적 필터가 걸리거나(예: "내 소속 부서 데이터만") 권한 조합이 수백 가지로 흩어지면, 캐시 엔트리가 조합 수만큼 쪼개져 사실상 캐시가 무력화된다. 이 경우 GSIP 241을 켜는 것보다 공개 레이어와 개인화 레이어를 애초에 분리하는 설계가 더 안전하다. 또 하나 중요한 한계는 **무효화**다. 보안 규칙이 바뀌어도(예: 사용자 역할 변경) 이미 구워진 타일을 즉시 지우는 기능은 아직 어떤 보안 subsystem도 구현하지 않았다 — 공식 문서도 "eager removal을 구현하는 보안 subsystem이 현재는 없다"고 명시한다. 결국 stale 타일은 디스크 쿼터 기반 축출에 맡겨지고, 역할이 바뀐 직후 짧은 시간 동안은 이전 권한으로 구워진 타일이 남아 있을 수 있다는 뜻이다.

## 실제 프로젝트 진행 순서

1. **먼저 권한 조합의 카디널리티를 추정한다.** GeoFence·ACL 규칙을 역할 × 레이어 × 속성필터 축으로 세어 본다. 조합이 10개 이하로 수렴하면 캐싱 효과를 기대할 수 있다.
2. **GWC Caching defaults 페이지에서 Data Security 옵션을 켜고, 스테이징 환경에서 캐시 히트율을 측정한다.** 운영 환경에 바로 올리지 않는다.
3. **조합이 많아 히트율이 기대만큼 안 나오면, 레이어를 공개용과 개인화용으로 분리하는 쪽으로 설계를 바꾼다.** 개인화 레이어는 캐싱을 포기하고 쿼리 최적화(인덱스, 속성 필터 단순화)로 응답 시간을 줄이는 쪽에 집중한다.
4. **역할·권한 변경 운영 절차에 캐시 무효화 단계를 명시적으로 추가한다.** 자동 eager invalidation이 없으므로, 민감 레이어는 역할 변경 직후 수동 truncate나 디스크 쿼터 강제 축출을 절차화해야 한다.
5. **`gwc.security.maxKeyLength` 같은 시스템 프로퍼티를 운영 규모에 맞춰 점검한다.** 기본 64KB 제한을 넘는 긴 보안 제약(복잡한 CQL 필터 다수)이 있다면 캐시 키 생성 자체가 실패할 수 있다.

## 실무 포인트

**캐시 히트율을 보안 적용 전후로 반드시 비교 측정한다.** "보안도 걸고 캐시도 걸었으니 다 됐다"가 아니라, 캐시가 실제로 효과를 내고 있는지를 숫자로 확인해야 한다.

**공개 데이터와 개인화 데이터를 애초에 다른 레이어로 설계해 둔다.** 둘을 섞어 두면 나중에 캐시 전략을 바꿀 때 레이어를 쪼개는 마이그레이션 자체가 큰 작업이 된다.

**역할 변경이 잦은 조직이라면 GSIP 241만으로 충분하지 않을 수 있다.** 무효화가 쿼터 기반이라는 한계를 운영팀에 미리 공유해 두어야, 권한이 바뀐 직후 "왜 아직도 예전 데이터가 보이냐"는 문의에 당황하지 않는다.

## 마무리

- GWC는 원래 보안 subsystem을 모르고 캐싱했기 때문에, 보안이 걸린 레이어는 캐시를 아예 끄는 것이 유일한 안전한 선택지였다.
- GSIP 241은 보안 평가 결과(`ACCESS_LIMITS_KEY`, `SECURITY_TAGS_KEY`)를 캐시 키에 섞어 넣어, 권한이 다른 요청을 서로 다른 캐시 엔트리로 분리한다.
- 효과는 권한 조합의 카디널리티에 달려 있고, 무효화가 디스크 쿼터 기반이라는 한계 때문에 역할 변경이 잦은 환경에서는 공개·개인화 레이어 분리 설계를 함께 검토해야 한다.
