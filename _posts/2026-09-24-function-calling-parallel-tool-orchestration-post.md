## 왜 지금 Function Calling을 다시 봐야 하는가

에이전트에 도구(tool) 두세 개를 붙여 프로토타입을 만들 때는 모델이 어떤 도구를 언제 쓸지 잘 판단하는 것처럼 보인다. 문제는 실제 서비스에 필요한 도구가 수십 개로 늘어나는 순간부터다. 이름이나 설명이 비슷한 도구가 여러 개 있으면 모델이 엉뚱한 것을 고르는 빈도가 늘고, 파라미터 스키마가 복잡하거나 애매하면 필수 인자를 빠뜨리거나 타입을 잘못 채워 호출 자체가 실패하는 경우도 늘어난다. 게다가 여러 도구를 동시에 호출해야 하는 상황(예: "서울과 부산의 날씨를 모두 알려줘")에서 이를 순차 처리하면 지연시간이 도구 개수에 비례해 늘어난다. Function Calling을 프로덕션 수준으로 안정화하려면 스키마를 어떻게 설계하고, 여러 호출을 어떻게 안전하게 병렬화할지에 대한 별도의 설계가 필요하다.

## 핵심 개념 1 — 도구 스키마는 API 문서이자 모델을 위한 프롬프트다

도구의 이름, 설명, 파라미터 스키마는 사람이 읽는 API 문서인 동시에, 모델이 "이 상황에 이 도구를 써야 하는가"를 판단하는 유일한 근거다. 도구 설명이 짧고 모호하면("날씨 조회") 비슷한 다른 도구와 구분이 안 돼 잘못 선택되기 쉽고, 반대로 파라미터에 자유 형식 문자열을 너무 많이 허용하면 모델이 형식을 일관되게 채우지 못한다. 열거형(enum)으로 제한 가능한 파라미터는 반드시 enum으로 좁히고, 도구 설명에는 "언제 쓰고 언제 쓰지 않아야 하는지"를 예시와 함께 명시하는 것이 스키마 설계의 핵심 원칙이다.

## 핵심 개념 2 — 병렬 도구 호출과 결과 재주입의 순서 문제

최신 모델 다수는 한 번의 응답에서 여러 도구 호출을 동시에 요청할 수 있다. 이때 애플리케이션 코드는 이 호출들을 실제로 병렬 실행한 뒤, 각 호출의 결과를 모델이 원래 요청한 순서와 매칭되는 식별자(tool_call_id)와 함께 다시 모델에 돌려줘야 한다. 이 매칭이 어긋나면 모델은 "서울 날씨는 부산 결과다"처럼 결과를 뒤바꿔 최종 답변에 반영하는 문제가 생긴다. 또한 병렬 호출 중 일부가 실패했을 때, 이를 어떻게 모델에 알릴지(에러 메시지를 그대로 결과로 돌려줄지, 재시도할지)도 별도의 정책으로 정의해야 한다.

| 설계 요소 | 잘못된 예 | 개선 방향 |
|---|---|---|
| 도구 이름 | `get_data`, `fetch_info` | 목적이 명확한 이름 (`get_weather_by_city`) |
| 파라미터 타입 | 자유 형식 문자열 남발 | enum·정수 범위 등으로 제약 |
| 도구 설명 | 한 줄 요약만 | 사용 시점·예시·제약 조건 명시 |
| 병렬 호출 결과 반환 | 순서만 믿고 매칭 | tool_call_id로 명시적 매칭 |

## 예제 — 병렬 도구 호출 실행과 결과 매칭

```python
async def execute_tool_calls(tool_calls, tool_registry):
    async def run_one(call):
        try:
            fn = tool_registry[call.name]
            result = await fn(**call.arguments)
            return {"tool_call_id": call.id, "content": json.dumps(result)}
        except Exception as e:
            # 실패도 결과 형태로 모델에 되돌려줘 스스로 판단하게 함
            return {"tool_call_id": call.id, "content": json.dumps({"error": str(e)})}

    # 여러 도구 호출을 동시에 실행하고, 완료된 순서가 아니라
    # 원래 요청 순서에 맞춰 결과 리스트를 구성
    results = await asyncio.gather(*(run_one(c) for c in tool_calls))
    return sorted(results, key=lambda r: [c.id for c in tool_calls].index(r["tool_call_id"]))
```

`tool_call_id`를 결과에 명시적으로 포함시키면, 병렬 실행 중 완료 순서가 뒤바뀌더라도 모델에게 돌려줄 때 원래 요청과의 대응 관계가 깨지지 않는다.

## 실무 포인트

- **도구 개수가 많아지면 계층적 라우팅을 고려하라.** 수십 개 도구를 한 번에 모델에 다 노출하는 대신, 먼저 도구 카테고리를 고르게 하고 그 카테고리 안의 세부 도구만 다음 단계에서 노출하면 선택 정확도가 올라간다.
- **실패한 도구 호출의 에러 메시지를 모델이 이해할 수 있는 형태로 가공하라.** 원본 스택 트레이스를 그대로 넘기기보다 "위치를 찾을 수 없음", "권한 없음"처럼 모델이 다음 행동(재시도, 사용자에게 되묻기)을 판단할 수 있는 구조화된 에러를 돌려주는 것이 낫다.
- **부작용이 있는 도구(결제, 삭제 등)는 병렬 실행 대상에서 명시적으로 제외하거나 별도 확인 단계를 거치게 하라.** 조회성 도구와 달리 부작용 도구를 병렬로, 확인 없이 실행하면 사용자가 의도하지 않은 결과가 한꺼번에 발생할 위험이 있다.

## 마무리 요약

- 도구 스키마는 모델이 도구를 선택하고 인자를 채우는 유일한 근거이므로, 모호한 이름과 자유 형식 파라미터를 피하고 enum과 명확한 설명으로 제약해야 한다.
- 병렬 도구 호출은 지연시간을 줄이지만, tool_call_id로 결과를 명시적으로 매칭하지 않으면 결과가 뒤바뀌는 문제가 생긴다.
- 도구 수가 많아질수록 계층적 라우팅으로 선택 범위를 좁히고, 부작용이 있는 도구는 병렬 실행에서 별도로 다뤄야 안전하다.
