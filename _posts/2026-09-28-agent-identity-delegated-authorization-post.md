## "사용자 대신 처리해 주세요"라는 한 줄이 만드는 문제

기획자가 이렇게 말한다. "회의 요청 메일이 오면 에이전트가 알아서 캘린더를 확인하고 일정을 잡아주면 좋겠어요." 요구사항 자체는 한 문장이지만, 이 문장이 코드로 번역되는 순간 가장 먼저 부딪히는 질문은 프롬프트도 모델 선택도 아니다. **그 캘린더 API 호출은 누구의 권한으로 나가는가**이다.

가장 빠른 구현은 사용자가 로그인할 때 받은 액세스 토큰을 그대로 에이전트 런타임에 넘겨서 쓰는 것이다. 동작은 한다. 그런데 이 순간 시스템에는 조용히 세 가지 부채가 생긴다. 첫째, 에이전트는 사용자가 가진 모든 권한을 갖는다 — 일정 하나 잡으라고 시켰는데 메일 삭제 권한까지 들고 있다. 둘째, 로그에 남는 행위자가 사용자이므로 사고가 났을 때 사람이 한 일인지 에이전트가 한 일인지 구분할 방법이 없다. 셋째, 프롬프트 인젝션으로 에이전트가 오작동하면 그 피해 범위가 곧 사용자 권한 전체가 된다.

2026년 들어 이 영역이 갑자기 뜨거워진 이유가 여기에 있다. 에이전트가 데모를 넘어 실제로 남의 계정에서 행동하기 시작하자, 사람용으로 설계된 인증 체계에 에이전트를 억지로 끼워 넣은 구조의 한계가 동시다발적으로 드러났다. 사람은 느리고 한 번에 한 가지를 하지만, 에이전트는 빠르고 병렬이며 자기 판단으로 도구를 고른다.

## 전체 시스템에서 이 결정이 놓이는 자리

<img src="/assets/images/posts/2026-09-28-agent-identity-delegated-authorization-1.svg" alt="사용자의 동의가 인가 서버를 거쳐 토큰 교환으로 좁혀지고, 좁혀진 단기 토큰이 에이전트 런타임과 MCP 툴 서버를 지나 외부 API에 도달하며 각 단계가 감사 로그에 기록되는 흐름도" style="width:100%;">

위임 권한 설계는 모델 앞단이 아니라 **에이전트 런타임과 도구 사이**에 놓인다. 앞단에서는 사용자의 동의와 인가 서버가 들어오고, 뒷단에서는 MCP 서버나 사내 API가 그 토큰을 검증한다. 그래서 이 층을 나중에 끼워 넣기가 유난히 어렵다. 도구 호출 코드가 이미 "환경변수에 있는 토큰 하나"를 가정하고 짜여 있으면, 호출마다 다른 주체의 다른 토큰을 실어 보내도록 바꾸는 일은 사실상 도구 계층 전면 수정이 된다. 에이전트 프로젝트에서 이 결정을 초기에 못 박아야 하는 이유다.

## 네 가지 위임 구조와 선택 기준

현장에서 쓰이는 구조는 크게 네 가지로 갈린다. 핵심 질문은 "호출을 받는 쪽이 보게 되는 신원이 누구인가"다.

| 구조 | 뒷단이 보는 신원 | 강점 | 약점 | 적합한 상황 |
|---|---|---|---|---|
| 사용자 토큰 전달 | 사용자 | 구현이 가장 빠름 | 권한 과다, 책임 추적 불가 | 사내 PoC, 데모 |
| 서비스 계정 | 에이전트(고정) | 운영 단순, 토큰 관리 쉬움 | 사용자별 데이터 경계가 사라짐 | 배치·크론성 자동화 |
| 토큰 교환(위임) | 사용자 + 행위자 에이전트 | 책임 추적과 권한 축소 동시 달성 | 인가 서버 구현 필요 | 사용자 대행 기능 전반 |
| 좁힌 임퍼소네이션 | 사용자(스코프 제한) | 뒷단 수정 없이 적용 | 행위자 구분이 로그에 안 남음 | 레거시 API 연동 |

새로 짓는 시스템이라면 세 번째, **토큰 교환 기반 위임**이 기본값이 될 만하다. 표준이 이미 있기 때문이다. OAuth 2.0 Token Exchange(RFC 8693)는 이미 가진 토큰을 더 좁은 토큰으로 바꿔 받는 흐름을 정의하고, 이때 `actor_token`으로 "누가 대신 행동하는지"를 함께 실어 보낸다. 발급된 토큰에는 `act` 클레임이 붙어 사용자와 에이전트가 한 토큰 안에 같이 담긴다. 권한을 "캘린더 쓰기"처럼 뭉뚱그리지 않고 구조화된 형태로 요청하려면 Rich Authorization Requests(RFC 9396)를 얹는다.

에이전트 전용 표준은 아직 정리 중이다. 2026년 9월 현재 IETF에는 에이전트 위임을 다루는 초안이 몇 건 올라와 있지만 워킹그룹 채택 전이고, 그중 일부는 이미 만료됐다. 그래서 지금 시점의 현실적인 판단은 **초안을 기다리지 말고 RFC 8693 위에 사내 규약을 얹는 것**이다. 초안이 표준이 되더라도 토큰을 좁혀 발급하는 구조 자체는 그대로 재사용된다.

## 교차 규칙 — 권한은 언제나 두 신원의 교집합

위임 구조를 도입할 때 가장 자주 틀리는 지점이 권한 계산이다. 올바른 규칙은 단순하다. **최종 권한 = 사용자가 가진 권한 ∩ 에이전트에 허용된 권한 ∩ 이번 작업에 필요한 권한.** 세 집합의 교집합이다.

이 규칙이 왜 중요한지는 반례를 보면 분명해진다. 관리자 권한을 가진 사용자가 "회의 잡아줘"라고 말했다고 해서, 그 에이전트가 관리자 API를 부를 수 있어야 할 이유는 없다. 반대로 에이전트에 결제 권한이 허용돼 있더라도 일반 사용자를 대신할 때는 그 사용자 한도를 넘을 수 없다. 교집합을 인가 서버에서 계산해 토큰에 박아 두면, 뒷단 API는 토큰만 검증하면 되고 도구 코드는 권한 판단을 아예 하지 않아도 된다.

## 코드 예제 — 토큰 교환으로 스코프 좁히기

에이전트 런타임이 도구를 부르기 직전에 인가 서버로 보내는 교환 요청이다.

```http
POST /oauth2/token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<사용자 액세스 토큰>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&actor_token=<에이전트 자신의 토큰>
&actor_token_type=urn:ietf:params:oauth:token-type:access_token
&scope=calendar.events.write
&resource=https://api.example.com/calendar
```

발급된 토큰의 페이로드에는 두 신원이 함께 남는다.

```json
{
  "sub": "user-8213",
  "act": { "sub": "agent://scheduler-bot/v3" },
  "scope": "calendar.events.write",
  "exp": 1790000000
}
```

`sub`는 대행 대상인 사용자, `act.sub`는 실제로 호출한 에이전트다. 이 토큰으로 들어온 요청은 감사 로그에서 "user-8213의 일정을 scheduler-bot v3가 변경함"으로 정확히 남는다.

## 실무 포인트 — 놓치기 쉬운 세 가지

**토큰 수명은 작업 단위로 잡는다.** 사람용 토큰의 한 시간 수명을 그대로 쓰면, 탈취된 토큰이 에이전트 속도로 악용될 시간을 한 시간 주는 셈이다. 도구 호출 직전에 발급하고 수 분 내로 만료시키는 편이 안전하다.

**스코프는 도구 단위가 아니라 호출 단위로 좁힌다.** "캘린더 도구를 쓸 수 있다"가 아니라 "이번 요청에서 이 캘린더에 이벤트 하나를 만들 수 있다"까지 내려가야 프롬프트 인젝션의 피해 범위가 실제로 줄어든다.

**되돌릴 수 없는 행위에는 사람 확인을 남긴다.** 결제·삭제·외부 발송처럼 취소 비용이 큰 도구는 권한 설계와 별개로 승인 단계를 둔다. 권한 축소는 사고의 크기를 줄이지만 사고 자체를 막지는 못한다.

## 정리

- 에이전트가 남의 계정에서 행동하는 순간, 인증은 "로그인 붙이기"가 아니라 **두 신원을 동시에 다루는 위임 설계** 문제가 된다.
- 새로 짓는다면 RFC 8693 토큰 교환을 기본값으로 두고, 권한은 사용자·에이전트·작업 세 집합의 교집합으로 계산해 토큰에 박아 둔다.
- 도구 계층이 "토큰 하나"를 가정하고 굳기 전에 결정해야 하는 항목이다. 나중에 끼워 넣으면 도구 전면 수정이 된다.
