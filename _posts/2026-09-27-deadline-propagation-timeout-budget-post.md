## 왜 서비스마다 독립적인 타임아웃은 위험한가

마이크로서비스 아키텍처에서 서비스 A가 B를 호출하고, B가 다시 C와 D를 호출하는 구조를 생각해보자. 흔한 실수는 각 서비스가 "이 호출은 3초 안에 끝나야 한다"는 타임아웃을 자기 기준으로 독립적으로 정하는 것이다. 문제는 클라이언트가 이미 5초 만에 타임아웃되어 연결을 끊었는데도, 그 요청이 만든 하위 호출 체인의 C와 D는 이 사실을 전혀 모른 채 각자의 타임아웃(예: 10초)까지 계속 작업을 이어간다는 점이다. 이미 아무도 결과를 기다리지 않는 작업에 스레드, DB 커넥션, CPU를 계속 소비하는 것이다. 트래픽이 몰릴 때는 이런 "좀비 요청"들이 누적되어 실제로 처리해야 할 유효한 요청의 리소스까지 잠식하는 연쇄 장애로 이어진다.

## 핵심 개념 1 — 남은 시간 예산을 호출 체인에 전파하기

Deadline propagation의 핵심 아이디어는 타임아웃을 "각 홉(hop)마다 고정된 값"이 아니라 "전체 요청이 언제까지 유효한가"라는 **절대 시각(deadline)**으로 표현하고, 이를 호출 체인 전체에 걸쳐 전파하는 것이다. 클라이언트가 요청을 시작할 때 "이 요청은 지금부터 5초 안에 끝나야 한다"고 정하면, 이는 곧 절대 시각 `now + 5s`로 변환된다. A가 B를 호출할 때 이 절대 시각을 그대로 전달하고, B는 자신이 걸린 처리 시간을 뺀 **남은 시간**만큼만 C와 D에게 다시 전달한다. 만약 B가 이미 4초를 썼다면 C에게는 1초짜리 예산만 남아있다는 것을 알려줄 수 있고, 이미 예산이 0 이하라면 아예 하위 호출을 시도하지 않고 즉시 실패를 반환할 수 있다.

## 핵심 개념 2 — 상대 시간이 아니라 절대 시각을 전달해야 하는 이유

여기서 흔한 함정은 남은 시간을 상대적인 값("앞으로 1초")으로 전달하는 것이다. 이 방식은 네트워크 전송 지연이나 직렬화·역직렬화에 걸리는 시간을 계산에서 빠뜨리기 쉽고, 여러 홉을 거치며 그 오차가 누적된다. 절대 시각(예: 유닉스 타임스탬프)을 전달하면 각 서비스는 자신의 로컬 시계로 `deadline - now()`를 계산해 정확한 남은 예산을 구할 수 있다. 단, 이 방식이 정확히 동작하려면 분산 시스템 전반의 시계가 NTP 등으로 충분히 동기화되어 있어야 한다는 전제가 따른다. gRPC는 이 패턴을 프로토콜 레벨에서 지원해, `grpc-timeout` 메타데이터 헤더로 남은 시간을 매 홉마다 자동으로 갱신해 전달한다.

| 방식 | 문제점 | 해결 여부 |
|---|---|---|
| 서비스별 독립 타임아웃 | 상위에서 포기해도 하위가 계속 작업 | 해결 안 됨 |
| 상대 시간 전파("앞으로 1초") | 전송 지연이 누적돼 오차 발생 | 부분 해결 |
| 절대 시각(deadline) 전파 | 각 홉이 로컬 시계로 정확히 계산 | 해결(시계 동기화 전제) |

## 코드 예제 — gRPC 컨텍스트로 데드라인 전파하기

```go
// 클라이언트: 5초 데드라인으로 요청 시작
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
resp, err := client.GetOrder(ctx, &pb.OrderRequest{Id: orderId})

// 서비스 B의 핸들러: 이 ctx를 그대로 하위 호출에 전달하면
// gRPC가 자동으로 남은 시간을 계산해 grpc-timeout 헤더를 갱신한다
func (s *Server) GetOrder(ctx context.Context, req *pb.OrderRequest) (*pb.OrderResponse, error) {
    if deadline, ok := ctx.Deadline(); ok && time.Until(deadline) < 200*time.Millisecond {
        // 남은 예산이 너무 적으면 하위 호출을 아예 시도하지 않고 조기 실패
        return nil, status.Error(codes.DeadlineExceeded, "insufficient time budget")
    }
    return s.inventoryClient.CheckStock(ctx, &pb.StockRequest{Id: req.Id})
}
```

## 실무 포인트

- **최소 예산 임계값을 두고 조기 실패시켜라.** 남은 시간이 네트워크 왕복 시간보다도 적게 남았다면 호출을 시도하는 것 자체가 낭비이므로, 최소 임계값 이하에서는 즉시 실패를 반환해 불필요한 네트워크 호출을 막아야 한다.
- **비동기 팬아웃에서는 가장 느린 응답이 아니라 데드라인을 기준으로 삼아라.** 여러 서비스에 병렬로 요청을 보내는 팬아웃 패턴에서, 개별 응답을 기다리는 타임아웃이 아니라 전체 요청의 데드라인을 기준으로 취소 신호를 보내야 일관된 동작을 보장한다.
- **HTTP 기반 REST API에도 같은 원칙을 적용할 수 있다.** gRPC처럼 표준화된 헤더는 없지만, 커스텀 헤더(`X-Deadline` 등)로 절대 시각을 전달하고 각 서비스가 이를 해석해 자체 타임아웃과 하위 호출 예산을 계산하도록 구현할 수 있다.

## 마무리 요약

- 서비스마다 독립적인 타임아웃을 두면, 상위에서 이미 포기한 요청을 하위 서비스들이 계속 처리하며 리소스를 낭비하는 좀비 요청 문제가 생긴다.
- Deadline propagation은 남은 시간을 상대값이 아니라 절대 시각으로 호출 체인 전체에 전파해, 각 홉이 정확한 남은 예산을 계산하게 한다.
- gRPC는 이 패턴을 프로토콜 레벨에서 지원하며, 최소 예산 임계값과 팬아웃 취소 전략을 함께 설계해야 실질적인 리소스 절약 효과를 얻는다.
