## 왜 다음 학습 주제로 코드 리뷰인가

지금까지 이 블로그에서는 Flutter 앱 개발, PostGIS 기반 지리공간 데이터 처리, 분산 SQL과 이벤트소싱 같은 분산시스템 주제, AI 에이전트 평가와 LLM 가격 전쟁, 메시지 큐 비교 같은 인프라 주제를 폭넓게 다뤄왔다. 이런 주제들의 공통점은 결국 "혼자 잘 짜는 코드"가 아니라 "팀이 함께 유지보수할 수 있는 코드"를 만드는 문제로 수렴한다는 점이다.

아무리 좋은 아키텍처를 설계하고 최신 기술 스택을 도입해도, 코드 리뷰 프로세스가 부실하면 그 설계 의도가 코드베이스에 제대로 반영되지 않은 채 흩어지기 쉽다. 반대로 코드 리뷰가 잘 작동하는 팀은 새로운 기술(예: 이 블로그에서 다룬 Java Virtual Threads나 React Compiler 같은 변화)을 도입할 때도 지식이 팀 전체로 훨씬 빠르게 퍼진다. 그래서 이번에는 기술 주제 자체보다 "기술을 팀에 잘 스며들게 하는 방법"인 코드 리뷰 방법론을 다음 학습 주제로 추천한다.

## 학습 로드맵

| 단계 | 주제 | 왜 필요한가 |
|---|---|---|
| 1 | 작은 PR 만들기 습관 | 리뷰 부담을 줄이고 피드백 반영 속도를 높이는 가장 기본적인 전제 조건 |
| 2 | 리뷰어용 체크리스트 설계 | 사람마다 다른 리뷰 기준을 팀 표준으로 맞추는 출발점 |
| 3 | 건설적 피드백 언어 익히기 | 같은 지적이라도 표현 방식에 따라 팀 분위기와 수용도가 크게 달라짐 |
| 4 | 자동화 가능한 것과 사람이 봐야 하는 것 구분 | 린트/포맷터/CI에 맡길 부분과 리뷰어가 집중할 부분을 나눠 리뷰 품질을 높임 |
| 5 | 리뷰 프로세스 자체를 회고하기 | 리뷰 소요 시간, 반려율 등 지표를 보며 프로세스를 지속적으로 개선 |

## 핵심 개념

### 효과적인 리뷰의 원칙

- **작은 PR**: 변경 범위가 작을수록 리뷰어가 맥락을 파악하는 부담이 줄고, 버그도 더 잘 발견된다. 큰 기능은 기능 플래그 등을 활용해 단계적으로 병합하는 편이 낫다.
- **명확한 리뷰어 체크리스트**: "동작하는가"뿐 아니라 "테스트가 있는가", "롤백 계획이 있는가", "네이밍이 팀 컨벤션과 맞는가"처럼 구체적인 항목으로 나눠야 리뷰어에 따라 편차가 줄어든다.
- **건설적 피드백 언어**: "이거 왜 이렇게 짰어요?" 대신 "이 부분은 ~한 이유로 다르게 짜면 어떨까요?"처럼 제안형으로 표현하면 방어적인 반응을 줄일 수 있다. 최근에는 Conventional Comments처럼 피드백에 라벨(예: nitpick, question, blocking)을 붙여 리뷰 의도를 명확히 하는 방식도 널리 쓰인다.
- **자동화와 사람 역할 분리**: 포맷팅, 정적 분석, 타입 체크처럼 규칙이 명확한 항목은 CI/린터에 맡기고, 사람은 설계 의도·엣지 케이스·비즈니스 로직 타당성처럼 기계가 판단하기 어려운 부분에 집중해야 리뷰 피로도가 줄어든다.

## 예제

```yaml
# PR 템플릿에 넣을 수 있는 리뷰어 체크리스트 예시
review_checklist:
  - "변경 범위가 하나의 목적에 집중되어 있는가"
  - "관련 테스트가 추가되었거나 기존 테스트가 갱신되었는가"
  - "롤백이 필요할 경우 되돌릴 수 있는 방법이 있는가"
  - "로그/모니터링 지표가 필요한 변경이라면 추가되었는가"
  - "네이밍과 구조가 팀 컨벤션과 일치하는가"
```

## 실무 포인트와 주의사항

- 체크리스트는 강제 규칙이 아니라 리뷰어의 사고를 돕는 가이드로 운영해야 형식적인 체크박스 클릭으로 전락하지 않는다.
- "blocking"과 "nitpick"처럼 피드백에 우선순위 라벨을 붙이면 작성자가 무엇부터 반영해야 할지 헷갈리지 않는다.
- 리뷰 소요 시간이 지나치게 길어지는 PR은 크기 자체를 줄이는 방향으로 먼저 접근하는 것이 근본적인 해결책인 경우가 많다.
- 코드 리뷰 문화는 도구(체크리스트, 린트 설정)만으로 완성되지 않으며, 팀 내 심리적 안전감이 뒷받침되어야 건설적 피드백이 실제로 작동한다.

## 3줄 요약

- 좋은 아키텍처와 최신 기술도 부실한 코드 리뷰 프로세스 위에서는 팀에 제대로 스며들지 못한다.
- 작은 PR, 명확한 체크리스트, 건설적 피드백 언어, 자동화-사람 역할 분리가 효과적인 리뷰의 핵심 축이다.
- 코드 리뷰는 도구뿐 아니라 팀의 심리적 안전감이 함께 갖춰져야 실제로 작동한다.
