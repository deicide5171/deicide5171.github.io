## 왜 지금 이 판단이 불거지는가

"전국 매장 중 옥상에 냉방 설비가 없는 지점을 찾아서 보고서로 만들어주세요." 시설관리팀에서 이런 요구가 내려오면, 과거의 답은 늘 비슷했다. 위성·항공 이미지를 구매하고, 라벨링 팀을 꾸려 "냉방 설비"가 찍힌 수천 장의 샘플에 바운딩 박스를 그리고, 객체탐지 모델을 파인튜닝한 뒤, 그 모델을 전국 타일에 돌려 좌표를 뽑아낸다. 몇 주에서 몇 달이 걸리는 파이프라인이다.

Google Research가 2026년 하반기 공개 범위를 넓힌 Geospatial Reasoning은 이 흐름 자체를 바꾼다. 분석가가 "대형 HVAC 냉방탑이 있는 건물을 찾아줘" 같은 평범한 문장을 입력하면, 시스템이 그 문장을 지리공간 작업으로 분해하고, 객체 인식·변화 탐지·토지 피복 분류 등 이미 학습된 여러 전문 파운데이션 모델 중 적합한 것을 골라 호출한 뒤, 결과를 지도 위에 합성해 돌려준다. 모델을 새로 학습시키는 대신 **이미 존재하는 전문 모델들을 오케스트레이션하는 에이전트 레이어**를 추가하는 접근이다. 이게 빌더에게 중요한 이유는 단순하다 — "모델을 학습시킬지 말지"였던 질문이 "어떤 모델을 어떤 순서로 조합할지"라는 질문으로 바뀌었기 때문이다.

## 요구사항을 기술 문제로 번역하기

자연어로 들어오는 지리공간 질의는 실제로는 서로 다른 성격의 하위 작업으로 쪼개진다. "냉방 설비가 없는 건물을 찾아줘"는 ①대상 지역의 건물 풋프린트를 특정하고(공간 필터링), ②각 건물 옥상 이미지에서 특정 객체의 유무를 판별하고(객체 탐지), ③결과를 신뢰도 순으로 정렬해 사람이 검토할 수 있는 형태로 묶는(결과 합성) 세 단계로 번역된다. 여기에 "작년과 비교해 새로 생긴 걸 찾아줘"가 섞이면 변화 탐지 모델이, "숲인지 농경지인지 구분해줘"가 섞이면 토지 피복 분류 모델이 추가로 필요해진다. 이 전체를 하나의 거대한 멀티모달 모델이 end-to-end로 처리하게 만드는 대신, 질의를 해석해 적절한 전문 모델에 위임하는 오케스트레이터를 두는 쪽이 현재로서는 훨씬 실용적이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-06-satellite-nl-query-multi-model-orchestration-1.svg" alt="분석가의 자연어 질의가 오케스트레이터 LLM으로 들어가 객체탐지, 변화탐지, 토지피복분류 등 전문 파운데이션 모델 중 필요한 것을 호출하고, 각 모델이 위성·항공 이미지 타일 인덱스를 조회한 뒤 결과가 지도 합성 레이어로 모여 최종 시각화와 보고서로 출력되는 구조를 보여주는 다이어그램" style="width:100%;">

질의가 들어오는 입구에는 오케스트레이터 역할을 하는 LLM이 있다. 이 모델 자체는 픽셀을 직접 보지 않는다. 대신 함수 호출(tool-calling) 형태로 "이 AOI(관심 영역)에서 객체 탐지를 수행하라", "이 두 시점 사이의 변화를 탐지하라" 같은 작업을 전문 모델에 위임한다. 전문 모델들은 뒷단의 위성·항공 이미지 타일 인덱스(대개 STAC 카탈로그나 클라우드 네이티브 래스터 저장소)를 조회해 실제 추론을 수행하고, 그 결과(좌표, 신뢰도 점수, 바운딩 박스)를 오케스트레이터에게 돌려준다. 오케스트레이터는 여러 모델의 결과를 하나의 지도 레이어로 합성하고, 필요하면 추가 질의를 스스로 던져 결과를 좁혀간다. 이 구조에서 앞단은 자연어 인터페이스, 뒷단은 기존 GIS 파이프라인(타일 서버, 공간 인덱스, 지도 렌더링)과 그대로 맞닿아 있다 — 오케스트레이션 레이어가 그 사이에 새로 끼어든 셈이다.

## 선택의 트레이드오프

| 기준 | 단일 end-to-end 비전-언어 모델 | 전문 모델 오케스트레이션 | 기존 수작업 GIS 분석 |
|---|---|---|---|
| 정확도(좁은 태스크) | 중간(범용이라 특화 태스크에 약함) | 높음(전문 모델이 각자 최적화됨) | 높음(사람이 직접 검증) |
| 신규 질의 유형 대응 속도 | 빠름(프롬프트만 바꾸면 됨) | 중간(새 전문 모델 통합 필요) | 느림(새 파이프라인 구축) |
| 결과 설명가능성 | 낮음(근거 추적 어려움) | 중간~높음(어떤 모델이 어떤 근거로 판단했는지 추적 가능) | 높음 |
| 운영 비용 | 모델 호출 비용 집중 | 여러 모델 호출 누적 + 오케스트레이션 오버헤드 | 인건비 집중 |
| 전국 단위 스케일 | 가능하지만 검증 어려움 | 가능(모델별 배치 처리) | 사실상 불가능 |

결정적인 줄은 "설명가능성"이다. 단일 거대 모델이 "이 건물에 냉방 설비가 있다"고 답하면 왜 그렇게 판단했는지 추적하기 어렵다. 반면 오케스트레이션 구조에서는 "객체 탐지 모델이 이 바운딩 박스에서 0.87 신뢰도로 탐지했다"는 식으로 책임 소재가 모델 단위로 분리된다. 시설 점검처럼 오탐이 실제 비용(인력 파견, 오판)으로 이어지는 도메인에서는 이 추적 가능성이 정확도 수치보다 더 중요한 선택 기준이 된다.

## 기존 임베딩 재사용 전략과의 차이

위성 이미지 파운데이션 모델을 처음부터 학습할지, 사전계산된 임베딩(AlphaEarth·Clay류)에 분류기만 얹을지를 고르는 문제는 "표현을 누가 만들 것인가"에 대한 질문이었다. 이번 오케스트레이션은 다른 층위다 — 표현 학습이 이미 끝난 여러 전문 모델이 존재한다고 가정하고, 그 모델들을 자연어 질의 하나에 어떻게 조합해 호출할지를 다룬다. 실제 프로젝트에서는 임베딩으로 저비용 1차 필터링을 하고, 그 결과를 오케스트레이터가 정교한 전문 모델로 재확인하는 2단계 구조로 결합되는 경우가 많다.

## 실제 프로젝트 진행 순서

1. **질의 유형부터 목록화한다.** "어떤 종류의 자연어 질문이 들어올 것인가"를 먼저 분류한다. 객체 탐지만으로 끝나는 질의와, 변화 탐지·시계열 분석까지 필요한 질의는 완전히 다른 전문 모델 조합을 요구한다.
2. **전문 모델은 자체 학습보다 기존 상용·오픈 모델을 먼저 검토한다.** Google Geospatial Reasoning이나 유사 플랫폼이 제공하는 사전 학습 모델로 시작하고, 도메인 특화가 정말 필요한 지점에서만 파인튜닝을 고려한다.
3. **오케스트레이터의 함수 호출 스키마를 먼저 설계한다.** 자연어 질의 전에, "이 모델은 어떤 입력을 받고 어떤 형태로 결과를 반환하는가"를 명확히 정의해야 LLM이 올바르게 위임할 수 있다.
4. **신뢰도 임계값과 사람 검수 루프를 처음부터 넣는다.** 오탐이 실제 비용으로 이어지는 영역이라면, 일정 신뢰도 이하 결과는 자동 승인하지 않고 사람에게 넘기는 게이트를 설계 단계에서 박아둔다.
5. **비용과 지연시간을 질의 단위로 계측한다.** 여러 모델을 순차 호출하는 구조는 단일 모델보다 지연시간이 누적되기 쉬우므로, 어떤 전문 모델 호출이 병목인지 초기부터 추적한다.

## 실무 포인트

**오케스트레이터의 모델 오선택 실패 모드를 검증한다.** LLM이 질의를 잘못 해석해 변화 탐지가 필요한데 객체 탐지만 호출하는 경우가 실제로 발생한다. 함수 호출 로그를 남겨 어떤 모델이 왜 선택됐는지 사후 추적이 가능해야 한다.

**위성 이미지 비용과 라이선스를 가볍게 보지 않는다.** 고해상도 상업 위성 이미지는 AOI 면적과 갱신 주기에 따라 비용이 크게 뛰며, 오케스트레이션은 호출 횟수를 늘리기 쉬운 만큼 같은 이미지의 중복 호출을 캐싱으로 막아야 한다.

**범위가 고정된 좁은 문제에는 오케스트레이션을 과하게 적용하지 않는다.** "이 지역에서 이 객체만 찾으면 된다"처럼 요구가 고정돼 있다면, 전문 모델을 직접 호출하는 편이 지연시간과 복잡도 모두에서 유리하다.

## 마무리

- 자연어 지리공간 질의는 공간 필터링·객체 탐지·변화 탐지·결과 합성 같은 서로 다른 하위 작업으로 번역되며, 이를 전문 모델 하나로 전부 처리하려 하기보다 LLM 오케스트레이터가 적절한 전문 모델에 위임하는 구조가 현재 더 실용적이다.
- 오케스트레이션은 단일 거대 모델보다 결과의 설명가능성과 책임 소재 추적에서 유리하지만, 모델 간 호출이 누적되며 지연시간과 비용이 쌓이는 트레이드오프를 가진다.
- 기존 지리공간 파운데이션 모델 임베딩 재사용 전략과는 다른 층위의 문제이며, 실무에서는 임베딩 기반 1차 필터링과 오케스트레이션 기반 정밀 재확인을 함께 쓰는 2단계 구조로 결합되는 경우가 많다.
