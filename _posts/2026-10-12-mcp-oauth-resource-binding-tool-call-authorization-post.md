## 왜 지금 이 판단이 불거지는가

"에이전트 하나가 사내 캘린더, 이슈 트래커, 사내 위키를 전부 MCP로 붙여서 쓰게 해주세요." 도구를 하나씩 붙일 때는 문제가 안 보인다. 그런데 서버가 두세 개를 넘어가는 순간, "이 에이전트가 캘린더 서버에서 받은 액세스 토큰을 이슈 트래커 서버에도 그대로 들이밀면 통과되는가?"라는 질문이 생긴다. OAuth 플로우 자체는 멀쩡히 끝났는데, 토큰이 어느 리소스 서버를 위해 발급된 것인지 서버가 검증하지 않으면 한 서버용 토큰이 다른 서버에서도 먹히는 **토큰 오용(confused deputy)** 구조가 그대로 뚫린다. 에이전트가 사람 대신 여러 외부 시스템을 동시에 호출하는 구조이기 때문에, 이 문제는 사람이 브라우저로 로그인하던 시절보다 훨씬 자주, 훨씬 조용히 일어난다.

MCP 스펙은 2026-07-28 리비전에서 이 문제를 정면으로 겨눴다. 동적 클라이언트 등록(DCR)을 대체하는 CIMD(Client ID Metadata Document)를 권장 방식으로 올리고, 토큰을 재발급받을 때 RFC 9207의 `iss` 파라미터를 반드시 검증하게 했으며, 인가 요청과 토큰 요청 양쪽에 RFC 8707의 `resource` 파라미터를 강제했다. 그런데 이 개편은 "누가 이 토큰을 들고 있어도 되는가"만 다룬다. "이 세션이 지금 이 순간 이 도구를 호출해도 되는가"는 완전히 다른 층위의 문제이고, OAuth 스코프는 애초에 이 질문에 답하도록 설계되지 않았다.

## 요구사항을 기술 문제로 번역하기

"여러 도구를 에이전트가 쓰게 해주세요"는 실제로는 두 개의 분리된 인가 문제를 하나로 뭉뚱그린 말이다. 첫째는 **발급 시점 문제** — 이 토큰이 어느 리소스 서버를 위해 만들어졌는지, 다른 서버에 재사용되지 않는지를 서버가 확인하는가. 둘째는 **호출 시점 문제** — 토큰이 유효하더라도 지금 이 특정 호출(예: 운영 DB에 쓰기 호출)이 이 세션의 현재 맥락에서 허용되는가. 전자는 OAuth 프로토콜 레벨에서 리소스 인디케이터로 고칠 수 있지만, 후자는 프로토콜이 아니라 **에이전트 런타임과 각 MCP 서버 사이에 둘 런타임 정책 레이어**의 문제다. 이 둘을 하나의 "인증만 잘 설정하면 되는 문제"로 뭉쳐서 설계하면, 토큰 바인딩은 완벽한데 프롬프트 인젝션으로 주입된 지시가 멀쩡한 토큰으로 위험한 도구를 호출하는 상황을 그대로 허용하게 된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-12-mcp-oauth-resource-binding-tool-call-authorization-1.svg" alt="에이전트 런타임이 인가 서버에서 리소스 인디케이터가 바인딩된 토큰을 발급받고, 각 MCP 리소스 서버가 그 바인딩을 검증한 뒤, 런타임 정책 레이어가 다시 한번 개별 툴콜을 허용할지 판단하는 2단계 구조도" style="width:100%;">

이 그림에서 인가 서버는 "어떤 클라이언트가 어떤 리소스 서버를 대상으로 토큰을 받을 자격이 있는가"만 책임진다. 토큰에는 `resource` 파라미터로 대상 서버가 못 박혀 있고, 각 MCP 서버는 자신에게 들어온 토큰의 `aud`(대상)가 자기 자신인지 반드시 검증한다. 여기까지가 2026-07-28 개편이 표준화한 영역이다. 그 뒤에 오는 런타임 정책 레이어는 완전히 별개 계층으로, 토큰이 유효해도 "이 세션이 지금 쓰기 작업을 요청했는가", "이 호출이 도구 정의가 승인 당시와 달라지지 않았는가(rug-pull 방지)" 같은 질문을 매 호출마다 다시 판단한다. 앞단에는 사용자 요청을 해석하는 LLM 추론 루프가 있고, 뒷단에는 실제 데이터를 쥔 리소스 서버들이 있으며, 이 둘 사이에 토큰 바인딩과 런타임 정책이라는 두 개의 독립된 관문이 있어야 한다.

## 선택의 트레이드오프

| 접근 | 막는 위협 | 구현 위치 | 한계 |
|---|---|---|---|
| OAuth 스코프만 사용 | 과도하게 넓은 권한 부여 | 인가 서버 | 토큰이 다른 서버로 재사용되는 것은 못 막음 |
| 리소스 인디케이터 바인딩(신규 표준) | 토큰 오용(confused deputy) | 인가 서버 + 리소스 서버 양쪽 검증 | 호출 시점의 맥락(프롬프트 인젝션, 과도한 자동화)은 다루지 않음 |
| 툴콜 단위 런타임 정책 게이트 | 유효한 토큰의 오남용, 변조된 도구 정의 | 에이전트 런타임(게이트웨이) | 자체 구현·운영 비용, 표준 없음 |
| 두 레이어 병행 | 위 세 가지 전부 | 인가 서버 + 리소스 서버 + 런타임 게이트웨이 | 설계·운영 복잡도가 가장 높음 |

스코프만 믿는 조직이 가장 흔하지만, MCP처럼 같은 클라이언트가 여러 독립 리소스 서버를 넘나드는 구조에서는 가장 먼저 뚫리는 지점이다. 리소스 인디케이터 바인딩은 지금 표준으로 확정된 부분이라 우선 채택 대상이지만, 이것만으로 "프롬프트 인젝션으로 유효한 토큰이 위험한 도구를 호출하는" 상황까지 막아주지는 않는다. 결국 프로덕션에서 여러 MCP 서버를 운영한다면 두 레이어를 함께 두는 쪽이 맞고, 사이드 프로젝트나 서버 하나짜리 내부 도구라면 리소스 인디케이터 검증만으로도 당장은 충분하다.

## 실제 프로젝트 진행 순서

1. **먼저 지금 쓰는 MCP 클라이언트/SDK가 2026-07-28 리비전을 지원하는지 확인한다.** `resource` 파라미터를 토큰 요청에 자동으로 싣는지, DCR 대신 CIMD를 쓸 수 있는지부터 본다.
2. **각 MCP 리소스 서버에서 `aud` 검증 로직이 실제로 동작하는지 테스트한다.** 한 서버에서 받은 토큰을 다른 서버 엔드포인트에 그대로 찔러 넣어보는 모의 공격을 직접 해본다 — 통과되면 바인딩이 제대로 안 걸린 것이다.
3. **그 다음에야 런타임 정책 레이어를 설계한다.** 쓰기 작업·외부 발신·결제처럼 되돌리기 어려운 도구만 먼저 추려 사람 승인이나 추가 확인을 끼워 넣는다.
4. **도구 정의 변경 감지(rug-pull 방지)를 넣는다.** 승인 시점의 도구 설명과 실행 시점의 도구 설명 해시를 비교해, 서버 쪽에서 몰래 바뀐 도구 정의를 걸러낸다.
5. **로그를 호출 단위로 남긴다.** 어느 세션이 어느 토큰으로 어느 도구를 호출했는지 추적 가능해야, 사고가 나도 바인딩 문제인지 런타임 정책 문제인지 구분할 수 있다.

## 코드 예시 — 리소스 인디케이터를 포함한 토큰 요청

```
POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=abc123
&resource=https://issue-tracker.example.com/mcp
&client_id=agent-runtime-01
```

```python
# 리소스 서버 쪽 최소 검증
def verify_token(token_claims: dict, this_server_url: str) -> bool:
    audience = token_claims.get("aud")
    return audience == this_server_url  # 다른 서버용 토큰이면 거부
```

## 실무 포인트

**토큰 바인딩을 했다고 인가 설계가 끝났다고 생각하지 않는다.** 리소스 인디케이터는 "어느 서버로 가는 토큰인가"만 보장할 뿐, "지금 호출이 안전한가"는 보장하지 않는다. 이 둘을 같은 체크리스트 항목으로 섞으면 런타임 정책 레이어를 빠뜨리기 쉽다.

**DCR을 당장 걷어낼 필요는 없다.** CIMD를 아직 지원하지 않는 인가 서버도 많으므로, 스펙은 DCR을 하위 호환으로 남겨뒀다. 지원 여부를 먼저 확인하고 점진적으로 옮긴다.

**런타임 정책은 과도하게 촘촘히 짜지 않는다.** 모든 도구 호출에 승인 절차를 걸면 에이전트가 쓸모없어진다. 되돌리기 어려운 소수의 도구에만 집중한다.

## 마무리

- "여러 MCP 서버를 에이전트가 쓰게 해주세요"는 토큰이 서버 경계를 넘나드는 순간 발급 시점 문제(토큰 바인딩)와 호출 시점 문제(런타임 정책)로 쪼개지는 설계 과제다.
- 2026-07-28 MCP 인가 스펙 개편은 리소스 인디케이터·CIMD·발급자 검증으로 전자를 표준화했지만, 후자는 여전히 각 조직이 직접 설계해야 한다.
- 토큰 바인딩부터 우선 채택하고, 되돌리기 어려운 도구에 한해 런타임 정책 게이트를 별도 레이어로 얹는 순서가 안전하다.
