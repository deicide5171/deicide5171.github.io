## API를 함부로 바꾸면 안 되는 이유

내가 만든 API를 모바일 앱이 쓰고 있다고 하자. 응답 형식을 바꾸면 이미 설치된 앱들이 갑자기 오작동한다. 앱은 사용자가 업데이트해야 새 버전이 되므로, 옛 버전 앱도 한동안 계속 쓰인다. **API 버저닝(versioning)**은 API를 바꿀 때 옛 버전과 새 버전을 함께 제공해, 기존 사용자를 깨뜨리지 않으면서 발전시키는 방법이다.

## 버저닝 방법 3가지

| 방법 | 예시 |
|---|---|
| URI 경로 | `/v1/users`, `/v2/users` |
| 쿼리 파라미터 | `/users?version=2` |
| 헤더 | `Accept: application/vnd.api.v2+json` |

가장 흔하고 직관적인 것은 **URI 경로 방식**(`/v1/`, `/v2/`)이다. URL만 봐도 버전을 알 수 있어 이해하기 쉽다.

## 언제 새 버전이 필요한가

```text
버전을 올려야 하는 변경(호환성을 깨는 변경):
- 응답 필드 이름·타입 변경
- 필드 삭제
- 필수 파라미터 추가

버전을 안 올려도 되는 변경(하위 호환):
- 새 선택적 필드 추가
- 새 엔드포인트 추가
- 응답에 정보만 더 추가

-> "기존 클라이언트가 계속 동작하는가?"가 판단 기준이다.
```

## 실무 포인트

- **버전은 함부로 올리지 말고, 하위 호환을 최대한 유지하라.** 버전이 여러 개가 되면 그만큼 유지보수 부담이 커진다. 새 필드 추가처럼 기존을 안 깨는 변경은 버전을 올리지 않고 처리하는 것이 좋다.
- **옛 버전의 지원 종료(deprecation) 계획을 미리 알려라.** v2를 내놓았다고 v1을 갑자기 없애면 v1 사용자가 깨진다. "언제까지 v1을 지원하고 언제 종료한다"를 미리 공지해 마이그레이션 시간을 줘야 한다.
- **버전이 무한정 늘어나지 않게 관리하라.** v1, v2, v3, v4가 모두 살아있으면 유지보수가 지옥이 된다. 오래된 버전은 계획적으로 정리하고, 큰 변경을 자주 하지 않도록 설계 단계에서 신중해야 한다.

## 마무리 요약

- API 버저닝은 API를 바꿀 때 옛 버전을 함께 제공해 기존 사용자를 깨뜨리지 않는 방법이다.
- URI 경로(`/v1/`) 방식이 가장 직관적이며, 헤더·쿼리 파라미터 방식도 있다.
- "기존 클라이언트가 계속 동작하는가"가 새 버전 필요 여부의 기준이고, 하위 호환 유지와 지원 종료 공지가 중요하다.
