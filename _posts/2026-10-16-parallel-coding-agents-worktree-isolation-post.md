## 왜 지금 이 판단이 필요한가

"리팩터링 범위가 넓으니까 에이전트 여러 개한테 나눠서 동시에 시켜주세요." 코딩 에이전트가 한 세션에서 수십 개 파일을 몇 시간씩 걸려 처리하는 걸 지켜본 팀이라면 자연스럽게 나오는 요구다. 문제는 "나눠서 동시에"라는 말이 숨기고 있는 아키텍처 질문이다. 에이전트 둘이 같은 저장소의 같은 브랜치를 동시에 건드리면, 한쪽이 커밋하는 사이 다른 쪽이 읽은 파일 상태는 이미 낡은 것이 된다. 사람 개발자 둘이 같은 로컬 디렉터리에서 동시에 `git commit`을 치는 상황과 같다 — 누구도 그렇게 일하지 않는다.

2026년 들어 Claude Code의 Agent Teams(세션 하나가 팀원 에이전트를 소환해 공유 작업 목록을 나눠 갖는 기능)와 Claude DevFleet 같은 서드파티 오케스트레이터가 이 문제를 각자 다른 층위에서 풀고 있다. 둘 다 핵심 전제는 같다 — **병렬화는 격리 전략이 먼저고, 작업 분할은 그다음이다.** 격리 없이 병렬 수부터 늘리면 충돌 해결에 쓰는 시간이 병렬화로 번 시간을 역전시킨다.

## 핵심 개념 1 — 세 단계 병렬화 모델

| 층위 | 구조 | 적합한 작업 | 조율 방식 |
|---|---|---|---|
| 세션 내 서브에이전트 | 오케스트레이터 하나가 자식 에이전트를 포크, 조사·검증 등 읽기 위주 | 코드 탐색, 영향 범위 분석, 테스트 설계안 리뷰 | 부모가 결과를 받아 직접 통합 |
| Agent Teams(단일 머신) | 리드 세션이 팀원을 소환, 공유 작업 목록과 git worktree로 각자 분리 | 같은 저장소 안 독립적인 파일 그룹 작업(모듈별 리팩터링) | 공유 작업 목록 + 병합 단계에서 리드가 조정 |
| 외부 오케스트레이터 | 저장소·레포 단위로 완전히 분리된 환경에서 각자 작업, 결과는 PR로 수렴 | 서로 다른 레포, 또는 같은 레포의 장기 병행 기능 개발 | PR 리뷰·CI가 통합 지점 |

세션 내 서브에이전트는 코드를 **쓰지** 않는 조사 작업에는 안전하다. 쓰기 작업이 들어가는 순간, 격리 경계가 "컨텍스트"에서 "파일시스템"으로 올라가야 한다. 이게 Agent Teams가 각 팀원에게 별도 git worktree를 붙이는 이유다 — 워킹 디렉터리 자체가 갈라져 있으면 같은 파일을 동시에 쓰다 서로 덮어쓰는 일이 구조적으로 불가능해진다.

## 핵심 개념 2 — git worktree가 격리를 만드는 방식

`git worktree`는 하나의 `.git` 저장소(커밋·오브젝트·히스토리)를 공유하면서, 서로 다른 브랜치를 체크아웃한 여러 작업 디렉터리를 동시에 둘 수 있게 한다. 각 에이전트는 자기 worktree 안에서 자유롭게 파일을 고치고 테스트를 돌리고 커밋하는데, 다른 에이전트의 워킹 디렉터리에는 전혀 영향을 주지 않는다. 충돌은 각자의 브랜치를 메인에 **병합하는 순간**으로 미뤄지고, 그때는 git의 일반적인 머지 충돌 해결 절차로 처리된다 — 작업 도중 실시간으로 파일을 두고 경쟁하는 것보다 훨씬 다루기 쉬운 문제다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-16-parallel-coding-agents-worktree-isolation-1.svg" alt="리드 세션이 공유 작업 목록을 두고 팀원 에이전트마다 별도 git worktree를 배정하며, 각자 작업 완료 후 병합 단계에서 충돌을 해결해 메인 브랜치로 수렴하는 구조도" style="width:100%;">

리드 세션은 요청을 받아 작업을 파일/모듈 단위로 쪼개 공유 작업 목록에 올린다. 각 팀원 에이전트는 자기 worktree에서 독립적으로 구현·테스트를 마치고 커밋한다. CI는 이 단계에서 개별 브랜치를 검증한다. 마지막으로 리드(또는 사람)가 병합 순서를 정해 메인 브랜치로 모은다 — 이 병합 단계가 바로 "동시에 일했지만 충돌 없이 합쳐지는가"를 실제로 검증하는 지점이다.

## 선택의 트레이드오프

- 작업이 **읽기 위주**(조사, 분석, 리뷰)라면 세션 내 서브에이전트로 충분하다. worktree까지 갈 필요가 없다.
- 같은 저장소 안에서 **파일 그룹이 명확히 분리**되는 작업(예: 모듈 A·B·C를 각각 다른 패턴으로 리팩터링)은 Agent Teams가 적합하다. 단, 공유 인터페이스나 공통 설정 파일을 여러 팀원이 동시에 건드리면 병합 단계에서 충돌이 몰린다 — 사전에 그 파일만큼은 한 에이전트에게 전담시킨다.
- 서로 다른 레포, 또는 같은 레포라도 수일 단위로 병행되는 큰 기능은 외부 오케스트레이터로 완전히 분리하고 PR 단위로만 통합한다.
- 병렬 에이전트 수가 늘수록 토큰 비용은 선형 이상으로 늘고, 조율 오버헤드도 함께 는다. "빨리 끝내려고" 무작정 늘리면 병합 충돌 해결에 쓰는 시간이 절약한 시간을 잡아먹는다.

## 실제 프로젝트 진행 순서

1. **작업을 파일/모듈 단위 의존성 그래프로 먼저 그린다.** 서로 파일을 공유하지 않는 작업 묶음을 찾는 게 병렬화 가능 여부를 가르는 첫 단계다.
2. **공유 접점(공통 설정, 인터페이스 정의, 마이그레이션 파일)을 식별하고 한 에이전트에게만 배정한다.** 이 파일들을 여러 팀원이 동시에 건드리게 두면 반드시 충돌한다.
3. **팀원마다 worktree를 분리하고 작업을 시작시킨다.** Claude Code 기준 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 설정으로 활성화한다.
4. **개별 브랜치 단위로 CI를 먼저 통과시킨다.** 병합 전에 각 작업의 정상 동작을 따로 검증해야 병합 단계의 디버깅 범위가 좁아진다.
5. **병합 순서를 사람 또는 리드 에이전트가 정하고, 순차적으로 메인에 합친다.** 동시에 여러 브랜치를 한꺼번에 머지하지 않는다 — 충돌이 나면 어느 조합이 원인인지 알 수 없어진다.

```bash
# worktree로 팀원별 격리 작업공간 만들기
git worktree add ../repo-module-a feature/module-a-refactor
git worktree add ../repo-module-b feature/module-b-refactor

# 작업 완료 후 정리
git worktree remove ../repo-module-a
```

## 마무리 요약

- 병렬 코딩 에이전트는 작업 분할보다 **격리 전략**이 먼저다 — 격리 없는 병렬화는 충돌 해결 비용으로 역전된다.
- 읽기 위주는 서브에이전트, 같은 저장소 내 분리 가능한 쓰기 작업은 Agent Teams+worktree, 완전히 독립된 작업은 외부 오케스트레이터로 층위를 맞춘다.
- 공유 접점 파일을 사전에 한 에이전트에게 전담시키고, 병합은 순차적으로 — 이 두 가지만 지켜도 대부분의 충돌을 피한다.
