건물 외곽선을 수십 개의 정점으로 정밀하게 그린 원본 데이터를, 전국 단위로 줌아웃한 화면에 그대로 뿌리면 무슨 일이 벌어질까? 화면에는 몇 픽셀짜리 점 하나로 보일 도형을 위해 브라우저는 여전히 수십 개의 정점을 파싱하고 좌표 변환하고 렌더링한다. 프레임 드랍은 물론이고, 애초에 그 정밀도가 시각적으로 아무 의미가 없다.

LOD(Level of Detail) 제너럴라이제이션은 이 문제를 "줌 레벨에 맞는 만큼만 상세하게 보여준다"는 원칙으로 해결한다. 저줌에서는 형상을 크게 단순화하고, 고줌으로 갈수록 원본에 가까운 정밀도를 노출한다. 이 글에서는 정적(사전 생성) 방식과 동적(런타임) 방식의 차이, 그리고 실무에서 겪는 함정을 정리한다.

## 핵심 개념 1: 정적 제너럴라이제이션 — 타일 생성 시점에 미리 단순화

가장 널리 쓰이는 방식은 벡터 타일을 생성하는 시점에 줌 레벨별로 다른 단순화 강도를 적용해 저장해두는 것이다. tippecanoe가 대표적인 도구로, `-z`/`-Z` 옵션으로 최소/최대 줌 레벨을 지정하고 `--simplification`으로 Douglas-Peucker 계열 알고리즘의 허용 오차(tolerance)를 조정한다.

```bash
# 줌 5~16 범위의 벡터 타일을 생성하되, 단순화 강도를 10으로 설정
tippecanoe -o buildings.mbtiles \
  -z16 -Z5 \
  --simplification=10 \
  --drop-densest-as-needed \
  buildings.geojson
```

`--drop-densest-as-needed`는 단순화만으로 타일 크기가 목표치를 넘으면 밀도가 높은 지역의 피처를 일부 제외하는 옵션이다. 저줌에서 도시 전체의 건물을 전부 그리는 대신, 시각적으로 중요한 것만 남기는 방식이다. 이렇게 생성된 타일은 런타임에 추가 연산 없이 그대로 서빙되므로 CPU/GPU 부담이 없다는 것이 최대 장점이다.

## 핵심 개념 2: 동적 제너럴라이제이션 — 런타임 스타일 표현식

정적 방식이 타일 자체를 여러 버전으로 미리 만드는 것이라면, 동적 방식은 하나의 벡터 데이터를 두고 스타일 표현식으로 줌마다 다르게 렌더링한다. MapLibre GL이나 Mapbox GL 스타일 스펙의 `interpolate`/`step` 표현식이 대표적이다.

```json
{
  "id": "buildings-fill",
  "type": "fill",
  "source": "buildings",
  "paint": {
    "fill-opacity": [
      "interpolate", ["linear"], ["zoom"],
      8, 0,
      12, 0.6,
      16, 0.9
    ]
  },
  "filter": [
    "step", ["zoom"],
    ["==", ["get", "importance"], "major"],
    14, true
  ]
}
```

이 예제는 줌 8~16 사이에서 투명도를 점진적으로 올리고, 줌 14 미만에서는 중요 건물만 필터링해 보여준다. 타일 자체는 하나만 유지하면서 표현 방식만 줌에 따라 바꾸는 방식이라 유연하지만, 필터링·보간 연산이 매 프레임 클라이언트에서 일어나므로 GPU/CPU 비용이 따른다.

## 핵심 개념 3: 정적 vs 동적 비교

| 구분 | 정적(사전 생성) | 동적(런타임 표현식) |
|---|---|---|
| 처리 시점 | 타일 빌드 시점 | 렌더링 시점(매 프레임) |
| 런타임 비용 | 거의 없음 | 표현식 평가 비용 발생 |
| 유연성 | 재생성 없이 변경 불가 | 스타일만 바꾸면 즉시 반영 |
| 저장 공간 | 줌별 타일로 다소 증가 | 원본 데이터 하나만 저장 |
| 대표 도구 | tippecanoe, ogr2ogr | MapLibre/Mapbox GL 스타일 표현식 |

실무에서는 두 방식을 함께 쓰는 경우가 많다. 정점 수 자체를 줄이는 형상 단순화는 정적으로 미리 처리하고, 어떤 피처를 보여줄지/얼마나 진하게 보여줄지 같은 표현은 동적 표현식으로 유연하게 조정하는 조합이다.

## 실무 포인트

- **단순화 허용 오차는 줌 레벨의 픽셀 크기에 맞춰 정한다**: 저줌에서 1픽셀 미만으로 보일 굴곡까지 정점으로 유지하는 것은 낭비다. 각 줌 레벨에서 지도 1픽셀이 커버하는 실제 거리를 계산해, 그보다 작은 굴곡은 단순화로 제거하는 것이 tippecanoe 튜닝의 기본 원칙이다.
- **과도한 단순화는 토폴로지 오류를 만든다**: 인접한 두 폴리곤을 각각 독립적으로 단순화하면 원래 맞닿아 있던 경계선이 벌어지거나 겹치는 문제가 생길 수 있다. 토폴로지를 인식하는 단순화 알고리즘(TopoJSON 기반 처리, 또는 tippecanoe의 경계 인식 옵션)을 우선 고려해야 한다.
- **줌 전환 시 시각적 튐(pop-in)을 완화한다**: LOD 단계가 명확히 나뉘어 있으면 줌인/줌아웃 애니메이션 중 피처가 갑자기 나타나거나 사라지는 것이 눈에 띈다. 페이드 인/아웃 트랜지션을 스타일에 추가하거나, 인접 줌 레벨 간 단순화 강도 차이를 완만하게 설계해 이 튐을 줄이는 것이 사용자 경험에 중요하다.

## 3줄 요약

- LOD 제너럴라이제이션은 줌 레벨에 맞지 않는 과도한 정밀도를 제거해, 렌더링 성능과 시각적 명료성을 동시에 확보하는 웹 지도의 핵심 기법이다.
- tippecanoe 같은 도구로 타일 생성 시점에 미리 단순화하는 정적 방식과, MapLibre 스타일 표현식으로 런타임에 조정하는 동적 방식은 각각 성능과 유연성의 트레이드오프가 다르다.
- 줌별 픽셀 크기에 맞춘 허용 오차 설정, 토폴로지 오류 방지, 줌 전환 시 시각적 튐 완화가 실무 적용에서 놓치기 쉬운 지점이다.
