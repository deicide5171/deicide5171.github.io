## 왜 지금 이 주제인가

서비스가 특정 지역에 국한되지 않고 전 세계 사용자를 대상으로 하게 되면, 단일 리전 구조는 두 가지 벽에 부딪힌다. 하나는 지연시간이다. 서울에 있는 서버로 미국이나 유럽 사용자가 요청을 보내면 물리적 거리 때문에 왕복 지연이 커지고, 이는 사용자 체감 품질에 직접 영향을 준다. 다른 하나는 재해 복구다. 하나의 리전에 장애가 발생했을 때 전체 서비스가 멈추는 구조는 가용성 요구가 높아질수록 받아들이기 어려워진다.

이 두 문제를 동시에 해결하려는 접근이 멀티 리전 액티브-액티브 아키텍처다. 액티브-패시브(하나의 리전만 쓰기를 받고 나머지는 대기)와 달리, 액티브-액티브는 여러 리전이 동시에 읽기와 쓰기를 모두 처리한다. 문제는 여기서부터 시작된다. 같은 데이터에 대해 서로 다른 리전에서 동시에 쓰기가 들어오면, 그 결과를 어떻게 하나의 일관된 상태로 수렴시킬 것인가라는 근본적인 질문이 남는다.

이 글에서는 액티브-액티브 구조가 필요한 이유를 짚고, 동시 쓰기 충돌을 다루는 대표적 전략(CRDT, 벡터 클록, 최종 일관성)을 비교한 뒤, 리전 간 지연이 만들어내는 분할 뇌 문제와 실무에서 흔히 쓰이는 패턴을 정리한다.

## 액티브-액티브가 필요한 이유

- **지연시간 최소화**: 사용자와 가장 가까운 리전에서 요청을 처리하므로 왕복 지연이 줄어든다.
- **재해 복구와 가용성**: 한 리전이 완전히 다운되어도 다른 리전이 트래픽을 흡수할 수 있어, 페일오버 시간을 최소화하거나 아예 없앨 수 있다.
- **트래픽 분산**: 특정 리전에 트래픽이 몰리는 상황에서도 여러 리전이 부하를 나눠 받는다.

다만 이 이점은 공짜가 아니다. 같은 레코드를 여러 리전에서 동시에 수정할 수 있다는 것은, 결국 그 리전들이 서로 다른 순간에 서로 다른 값을 "정답"이라고 믿게 될 수 있다는 뜻이다.

## 핵심 개념: 동시 쓰기 충돌을 다루는 전략들

동시 쓰기가 충돌했을 때 이를 감지하고 병합하는 방식은 대체로 아래 세 갈래로 나뉜다.

| 전략 | 기본 아이디어 | 강점 | 한계 |
|---|---|---|---|
| CRDT (Conflict-free Replicated Data Type) | 데이터 구조 자체를 병합이 항상 안전하게 수렴하도록 설계 | 병합 로직을 애플리케이션이 신경 쓸 필요가 없음 | 지원 가능한 자료구조가 제한적(카운터, 셋, 맵 등)이고 설계가 까다로움 |
| 벡터 클록 (Vector Clock) | 각 리전(노드)의 이벤트 순서를 논리적 시계로 추적해 인과관계 판단 | 실제 인과관계를 정확히 구분 가능(동시성 vs 순서) | 충돌이 감지된 이후의 병합 정책은 별도로 필요, 노드 수만큼 메타데이터 증가 |
| 최종 일관성 (Eventual Consistency) | 강한 순서 보장 없이, 결국 모든 복제본이 같은 상태로 수렴하도록만 보장 | 가용성과 지연시간에서 유리 | 일시적으로 리전 간 값이 다를 수 있어 애플리케이션이 이를 감내해야 함 |

세 접근은 배타적이지 않다. 실무에서는 최종 일관성을 기본 모델로 채택하면서, 충돌 감지에는 벡터 클록류의 메타데이터를, 자동 병합이 가능한 자료구조에는 CRDT를 부분적으로 적용하는 조합이 흔하다.

## 분할 뇌 문제와 리전 간 지연

리전 간 네트워크는 데이터센터 내부 네트워크보다 지연이 훨씬 크고, 드물지만 완전히 단절되는 경우도 있다. 이때 각 리전이 서로 다른 값을 정답으로 계속 받아들이면서 독립적으로 진화하는 상황, 즉 분할 뇌(split-brain)가 발생할 수 있다. 강한 일관성을 유지하려는 시스템은 이런 상황에서 쓰기를 거부하거나 지연시켜 가용성을 희생하고, 최종 일관성 기반 시스템은 우선 쓰기를 받아들인 뒤 나중에 충돌을 병합하는 방향을 택한다. 이는 결국 CAP 정리에서 말하는 일관성과 가용성 사이의 트레이드오프를 리전 단위로 다시 마주하는 것과 같다.

## 예제: 벡터 클록으로 동시성 판단하기

아래는 두 리전(A, B)이 각자의 카운터를 증가시키며 벡터 클록을 갱신하는 과정을 단순화한 의사코드다.

```python
# 각 리전은 자신의 클록을 포함한 전체 벡터를 유지한다
clock_a = {"A": 0, "B": 0}
clock_b = {"A": 0, "B": 0}

def local_write(clock, region):
    clock[region] += 1
    return dict(clock)

def happens_before(c1, c2):
    # c1이 c2보다 인과적으로 앞선다면 True
    return all(c1[k] <= c2[k] for k in c1) and c1 != c2

def is_concurrent(c1, c2):
    # 어느 쪽도 다른 쪽보다 앞서지 않으면 동시 쓰기(충돌 후보)
    return not happens_before(c1, c2) and not happens_before(c2, c1)

# 리전 A와 B에서 각각 로컬 쓰기가 발생
va = local_write(clock_a, "A")  # {"A": 1, "B": 0}
vb = local_write(clock_b, "B")  # {"A": 0, "B": 1}

if is_concurrent(va, vb):
    # 충돌 발생: 병합 정책(LWW, 애플리케이션 로직, CRDT 등)이 필요
    pass
```

인과관계가 명확하지 않은 두 쓰기가 감지되면, 이후 병합은 별도의 정책(예: 마지막 쓰기 우선, 즉 Last-Write-Wins)이나 애플리케이션 수준의 병합 함수에 위임된다.

## 실무 포인트와 주의사항

- **LWW(Last-Write-Wins)는 단순하지만 데이터 유실 위험이 있다.** 타임스탬프 기준으로 승자를 정하면 구현은 간단하지만, 패자 쪽 쓰기 내용은 조용히 사라질 수 있다.
- **모든 데이터에 액티브-액티브가 필요한 것은 아니다.** 강한 일관성이 필수인 도메인(결제 잔액 등)은 특정 리전으로 쓰기를 집중시키고, 조회 위주 데이터만 여러 리전에서 쓰기를 허용하는 하이브리드 구성도 실무에서 자주 쓰인다.
- **충돌 해소 로직은 테스트하기 어렵다.** 네트워크 파티션과 동시 쓰기를 재현하는 카오스 테스트나 시뮬레이션 없이는 프로덕션에서야 문제가 드러나는 경우가 많다.
- **모니터링 대상에 리전 간 복제 지연을 반드시 포함해야 한다.** 복제 지연이 커질수록 충돌 가능성과 사용자에게 노출되는 불일치 시간이 함께 늘어난다.

## 3줄 요약

- 멀티 리전 액티브-액티브는 지연시간 최소화와 재해 복구를 동시에 노리지만, 그 대가로 동시 쓰기 충돌 문제를 떠안는다.
- CRDT, 벡터 클록, 최종 일관성은 서로 대체재라기보다 조합해서 쓰는 보완적 도구에 가깝다.
- 리전 간 지연이 커지는 상황에서는 일관성과 가용성 사이의 트레이드오프(분할 뇌 문제)를 어떤 정책으로 감내할지 미리 설계해두어야 한다.
