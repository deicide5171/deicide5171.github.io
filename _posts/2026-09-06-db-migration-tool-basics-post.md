## 스키마 변경을 손으로 하면 생기는 문제

새 기능을 만들며 테이블에 컬럼을 추가한다고 하자. 내 로컬 DB에는 `ALTER TABLE`을 직접 실행했는데, 팀원과 스테이징·운영 DB에도 똑같이 적용해야 한다. 손으로 하면 어디에 적용했는지, 순서가 맞는지 관리가 안 되고, 누군가 빠뜨리면 환경마다 스키마가 달라진다. **DB 마이그레이션 도구**는 스키마 변경을 코드처럼 버전 관리해 이 혼란을 없앤다.

## 마이그레이션 도구의 핵심 아이디어

```text
스키마 변경 하나하나를 번호가 붙은 SQL 파일로 관리한다.

V1__create_users.sql       (사용자 테이블 생성)
V2__add_email_to_users.sql (이메일 컬럼 추가)
V3__create_orders.sql      (주문 테이블 생성)

도구가 각 DB에 "어디까지 적용됐는지" 기록하고,
아직 적용 안 된 파일만 순서대로 실행한다.
```

## 어떻게 동작하나

| 동작 | 설명 |
|---|---|
| 버전 기록 | 도구가 전용 테이블에 적용된 버전을 기록 |
| 자동 적용 | 앱 시작 시 아직 안 된 마이그레이션만 순서대로 실행 |
| 일관성 보장 | 모든 환경이 같은 순서로 같은 변경을 거침 |

## Flyway 마이그레이션 파일 예제

```sql
-- V2__add_email_to_users.sql
ALTER TABLE users ADD COLUMN email VARCHAR(255);
CREATE INDEX idx_users_email ON users(email);
```

파일 이름의 `V2`가 버전, `__` 뒤가 설명이다. Flyway는 이 파일들을 버전 순서대로 각 DB에 적용하고, 이미 적용된 것은 건너뛴다. 개발자는 SQL 파일만 추가하면 되고, 어디에 적용됐는지는 도구가 관리한다.

## 실무 포인트

- **이미 적용된 마이그레이션 파일은 절대 수정하지 마라.** 도구는 각 파일의 체크섬을 기록하는데, 적용된 파일을 고치면 체크섬이 안 맞아 오류가 난다. 변경이 필요하면 기존 파일을 고치지 말고 새 마이그레이션 파일(V4, V5...)을 추가해야 한다.
- **롤백보다 앞으로 가는 마이그레이션을 선호하라.** 운영에서 스키마를 되돌리는 것은 위험하므로, 잘못된 변경을 되돌릴 때도 "되돌리는 새 마이그레이션"을 추가하는 방식이 안전하다.
- **무중단 배포와 함께 고려해야 한다.** 컬럼 삭제·이름 변경 같은 파괴적 변경은 배포 중 옛 버전 코드와 충돌할 수 있으므로, 여러 단계로 나눠 적용하는 전략(Expand-Contract)이 필요하다.

## 마무리 요약

- DB 마이그레이션 도구는 스키마 변경을 번호 붙은 SQL 파일로 버전 관리해 모든 환경의 일관성을 보장한다.
- 도구가 어디까지 적용됐는지 기록하고, 아직 안 된 변경만 순서대로 자동 적용한다.
- 이미 적용된 파일은 수정하지 말고 새 파일을 추가하는 것이 핵심 규칙이다.
