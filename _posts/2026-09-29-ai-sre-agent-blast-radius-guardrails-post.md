## "새벽에 장애 나면 사람 안 깨워도 자동으로 조치되게 해주세요"

온콜을 서 본 사람이라면 한 번쯤 들어본 요구다. 표면적으로는 알림·자동화 문제처럼 보이지만, 실제로는 훨씬 무거운 질문으로 번역된다. **이 시스템이 프로덕션에 쓰기 작업을 실행하도록 얼마나 허용할 것인가.** 읽기 전용 진단이야 위험이 적지만, 파드를 재시작하거나 배포를 롤백하는 실행 권한을 에이전트에게 준다는 것은 장애 하나가 두 개로 늘어날 가능성을 시스템에 들이는 일이다.

2026년은 이 질문에 실제 프로덕션 답이 나온 해다. Microsoft의 Azure SRE Agent가 2026년 3월 정식 출시돼 마이크로소프트 내부에서만 1,300개 이상 에이전트가 3만 5천 건 넘는 인시던트를 완화했고, 여러 벤더가 유사한 AI SRE 제품을 내놓았다. 이들이 공통으로 수렴한 설계는 "완전 자율"이 아니라 **경계가 명확한 자율**이다. 이 글은 그 경계를 어디에, 어떤 순서로 그어야 하는지를 정리한다.

## 파이프라인에서 에이전트가 들어갈 자리

자동 장애 대응은 하나의 시스템이 아니라 다섯 단계로 이뤄진 파이프라인이다. 알림 감지 → 진단(로그·메트릭 조회) → 판단(원인 가설과 조치안 수립) → 실행 → 감사·학습. 여기서 흔한 설계 실수는 "에이전트"를 이 파이프라인 전체를 관장하는 하나의 블랙박스로 만드는 것이다. 실제로 프로덕션에서 검증된 구조는 역할을 분리한다 — 로그·메트릭을 읽는 진단 에이전트, 가설을 세우고 신뢰도를 매기는 슈퍼바이저, 그리고 **실행은 별도의 범위 제한된 실행기(bounded actuator)**가 맡는다.

<img src="/assets/images/posts/2026-09-29-ai-sre-agent-blast-radius-guardrails-1.svg" alt="알림 감지부터 진단 에이전트, 슈퍼바이저의 판단, 신뢰도에 따라 사람에게 에스컬레이션하거나 범위 제한 실행기로 보내는 승인 게이트, 화이트리스트 액션만 지정된 namespace 안에서 실행하는 실행기, 감사 로그와 롤백 경로, 포스트모템을 통한 플레이북 갱신까지 이어지는 AI SRE 파이프라인 구조도" style="width:100%;">

이렇게 나누는 이유는 명확하다. 진단과 판단은 아무리 틀려도 프로덕션에 직접 영향을 주지 않는다. 실제 영향은 실행 단계에서만 발생하므로, **권한 경계를 그어야 할 지점은 오직 실행기 하나뿐**이라는 것을 시스템 설계 단계에서 명시적으로 정해두면 나머지 단계는 비교적 자유롭게 설계할 수 있다.

## 자율성의 수준 — 무엇을 기준으로 고를까

| 수준 | 실행 권한 | 대표 사례 | 위험 |
|---|---|---|---|
| 읽기 전용 진단 | 없음, 조회만 | 로그·메트릭 상관관계 분석 | 낮음 — 장애 전파 없음 |
| 화이트리스트 실행 | 사전 정의된 액션만 (재시작·스케일·롤백) | namespace 범위 내 pod 재시작 | 중간 — 정책 밖 행동은 원천 차단 |
| 승인 후 자유 실행 | 사람이 승인한 임의 명령 | 사람이 확인 버튼을 누른 뒤 실행 | 중간 — 병목은 사람이지만 안전 |
| 완전 자율 실행 | 제한 없이 자체 판단으로 실행 | 없음(2026년 기준 프로덕션에 없음) | 높음 — 장애 반경 예측 불가 |

실무에서 통용되는 원칙은 "Act 단계는 반드시 유계(bounded)여야 한다"는 것이다. 에이전트에게 클러스터 루트 권한을 주지 않고, 미리 정의된 네임스페이스 안에서 미리 정의된 동작(재시작·스케일·롤백)만 하도록 제한한다. 이 제한이 있어야 에이전트의 판단이 틀리더라도 피해 범위가 그 네임스페이스를 벗어나지 않는다.

## 진행 순서 — 신뢰는 단계적으로 확장한다

**1단계**: 읽기 전용 진단 에이전트부터 붙인다. 온콜 담당자가 알림을 받았을 때 로그·메트릭 조회를 대신 해주는 수준으로 시작하면, 실행 권한 없이도 대응 시간을 단축하는 효과를 곧바로 확인할 수 있다.

**2단계**: 반복적으로 나타나는 장애 패턴 중 되돌리기 쉬운(reversible) 조치부터 화이트리스트에 올린다. 파드 재시작이나 최근 배포 롤백처럼 실행해도 상태를 원래대로 되돌릴 수 있는 액션이 첫 후보다. 데이터를 삭제하거나 스키마를 바꾸는 종류의 조치는 이 단계에 절대 넣지 않는다.

**3단계**: 신뢰도 임계값과 승인 게이트를 설계한다. 슈퍼바이저가 산출한 신뢰도가 기준을 넘으면 화이트리스트 액션을 바로 실행하고, 기준에 못 미치면 사람에게 넘긴다. 이 임계값은 처음엔 보수적으로 잡고, 실제 실행 결과가 쌓이면서 점진적으로 낮춘다.

```yaml
# 실행기에 부여하는 정책 예시 — 특정 네임스페이스, 특정 동작만 허용
apiVersion: sre-agent/v1
kind: ActionPolicy
metadata:
  name: payment-service-remediation
spec:
  namespace: payment-prod
  allowedActions:
    - restartPod
    - rollbackDeployment
    - scaleReplicas
  maxReplicaChange: 3
  requiresApprovalIfConfidenceBelow: 0.85
  forbiddenActions:
    - deleteResource
    - modifySecret
    - scaleToZero
```

**4단계**: 모든 실행에 감사 로그와 자동 롤백 경로를 붙이고, 인시던트가 끝나면 포스트모템에서 그 판단이 옳았는지 검증해 플레이북을 갱신한다. 이 학습 루프가 없으면 에이전트는 매번 같은 실수를 반복한다.

## 실무 포인트

**"되돌릴 수 있는가"가 화이트리스트의 첫 기준이다.** 실행 전에 액션의 가역성을 분류해두지 않으면, 화이트리스트가 편의성 기준으로 점점 넓어지다가 되돌릴 수 없는 조치까지 포함되는 사고가 난다.

**감사 로그는 사후 검증용이 아니라 승인 게이트의 입력값이다.** 과거 실행 이력이 신뢰도 산출에 직접 반영되도록 설계해야, 3단계의 임계값 조정이 실제 데이터 기반으로 이뤄진다.

**"에이전트가 판단했다"는 것과 "에이전트가 실행했다"는 것을 코드 레벨에서 분리한다.** 슈퍼바이저와 실행기를 같은 프로세스·같은 권한으로 묶으면, 판단 로직의 버그가 곧바로 실행 권한 남용으로 이어진다.

## 정리

- 자동 장애 대응 설계의 핵심 질문은 "얼마나 똑똑한가"가 아니라 "실행 권한을 어디까지 유계(bounded)로 제한하는가"다.
- 진단·판단·실행을 역할별로 분리하고, 권한 경계는 실행기 한 곳에만 명시적으로 그어 나머지 단계를 자유롭게 설계할 여지를 남긴다.
- 되돌리기 쉬운 액션부터 화이트리스트에 올리고, 신뢰도 임계값과 감사 로그·포스트모템 학습 루프를 함께 설계해야 자율성을 안전하게 넓혀갈 수 있다.
