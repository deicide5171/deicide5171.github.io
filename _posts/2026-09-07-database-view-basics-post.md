## 같은 복잡한 쿼리를 여기저기서 반복한다면

여러 테이블을 JOIN하고 조건을 거는 복잡한 조회 쿼리를 여러 곳에서 똑같이 쓴다고 하자. 쿼리가 바뀌면 그걸 쓰는 모든 곳을 고쳐야 하고, 실수도 잦다. **뷰(View)**는 이 복잡한 쿼리에 이름을 붙여 "가상의 테이블"처럼 저장해두는 것이다. 한 번 뷰를 만들어두면 그냥 그 이름으로 조회하면 된다.

## 뷰의 기본

```sql
-- 복잡한 조회를 뷰로 저장
CREATE VIEW active_user_orders AS
SELECT u.name, o.item, o.price
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.status = 'ACTIVE';

-- 이제 이렇게 간단히 조회
SELECT * FROM active_user_orders WHERE price > 10000;
```

뷰는 실제로 데이터를 저장하는 게 아니라, 조회할 때 그 안의 쿼리가 실행된다. 즉 "저장된 쿼리"에 가깝다. 그래서 원본 테이블의 데이터가 바뀌면 뷰의 결과도 자동으로 최신 상태를 반영한다.

## 뷰가 유용한 경우

| 상황 | 이점 |
|---|---|
| 복잡한 쿼리 재사용 | 이름 하나로 간단히 |
| 접근 제어 | 민감한 컬럼을 제외한 뷰만 노출 |
| 하위 호환 | 테이블 구조가 바뀌어도 뷰로 옛 형태 유지 |

## 일반 뷰 vs 구체화 뷰

```text
일반 뷰(View):
- 데이터를 저장하지 않고 조회할 때마다 쿼리 실행
- 항상 최신이지만, 무거운 쿼리면 매번 느림

구체화 뷰(Materialized View):
- 쿼리 결과를 실제로 저장해둠
- 조회는 빠르지만, 원본이 바뀌면 갱신(refresh)해줘야 함
```

## 실무 포인트

- **일반 뷰는 성능을 마법처럼 개선해주지 않는다.** 뷰는 조회 시 안의 쿼리를 그대로 실행하므로, 원본 쿼리가 느리면 뷰도 느리다. 뷰는 "편의성·재사용"을 위한 것이지 성능 최적화 도구가 아니다.
- **반복되고 무거운 집계는 구체화 뷰를 검토하라.** 매번 계산하기 아까운 통계·집계는 구체화 뷰로 결과를 저장해두면 조회가 빨라진다. 대신 데이터가 바뀔 때 갱신 전략(주기적/트리거)을 정해야 한다.
- **뷰로 접근 권한을 나눌 수 있다.** 예를 들어 급여 컬럼을 뺀 직원 뷰를 만들어 일반 사용자에게는 뷰만 조회하게 하면, 민감한 컬럼을 노출하지 않고 필요한 정보만 제공할 수 있다.

## 마무리 요약

- 뷰는 복잡한 조회 쿼리에 이름을 붙여 가상 테이블처럼 재사용하는 기능이다.
- 일반 뷰는 조회 시마다 쿼리를 실행해 항상 최신이지만 성능은 원본 쿼리에 달렸다.
- 무거운 집계는 결과를 저장하는 구체화 뷰를, 접근 제어에는 컬럼을 제한한 뷰를 활용할 수 있다.
