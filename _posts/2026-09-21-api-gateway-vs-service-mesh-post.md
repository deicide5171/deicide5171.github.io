## 왜 이 둘이 자주 헷갈리는가

마이크로서비스로 전환한 팀이 어느 정도 서비스 개수가 늘어나면 공통으로 마주치는 질문이 있다. "인증, 재시도, 서킷 브레이커, 로드밸런싱을 어디에 둘 것인가?" 이 질문에 대한 답으로 API 게이트웨이와 서비스 메시가 동시에 후보로 떠오르는데, 둘 다 "트래픽을 가로채 정책을 적용한다"는 점이 비슷해 보여서 하나만 있으면 충분하다고 오해하기 쉽다.

실제로는 두 기술이 다루는 **트래픽 방향과 관점**이 근본적으로 다르다. API 게이트웨이는 클러스터 바깥에서 들어오는 요청(North-South 트래픽)의 단일 진입점이고, 서비스 메시는 클러스터 내부 서비스끼리 주고받는 요청(East-West 트래픽)을 다룬다. 이 구분을 놓치면 "게이트웨이 하나로 서비스 간 통신까지 다 처리하자"는 식의 설계를 하게 되고, 결국 게이트웨이가 모든 서비스 정보를 알아야 하는 병목이자 단일 장애점이 되어버린다.

## 각자의 책임 범위

| 항목 | API 게이트웨이 | 서비스 메시 |
|---|---|---|
| 트래픽 방향 | 외부 → 내부 (North-South) | 내부 서비스 간 (East-West) |
| 배치 위치 | 클러스터 경계, 단일 진입점 | 각 서비스 옆 사이드카(프록시) |
| 주요 기능 | 인증, 라우팅, 속도 제한, API 버전 관리 | 서비스 디스커버리, mTLS, 재시도, 서킷 브레이커 |
| 대표 도구 | Kong, Spring Cloud Gateway, AWS API Gateway | Istio, Linkerd, Cilium Service Mesh |
| 관측 대상 | 외부 클라이언트 관점의 API | 서비스 간 호출 그래프 전체 |

게이트웨이는 "외부에서 어떤 API를 어떻게 호출할 수 있는가"를 정의하는 계약의 문 앞에 서 있고, 서비스 메시는 "내부 서비스 A가 서비스 B를 호출할 때 무슨 일이 일어나는가"를 촘촘히 제어한다.

## 잘못된 접근: 게이트웨이 하나로 다 해결하려는 시도

서비스가 5~10개 수준일 때는 API 게이트웨이 레이어에 서비스 간 호출 로직(재시도, 타임아웃, 서킷 브레이커)까지 몰아넣어도 큰 문제가 없어 보인다. 하지만 서비스 수가 수십 개로 늘면 게이트웨이가 모든 서비스의 위치와 상태를 알아야 하는 중앙 집중 지점이 되고, 게이트웨이 설정 파일이 서비스 팀 수만큼 늘어난 규칙으로 뒤엉킨다. 배포 하나 바꾸려 해도 게이트웨이 설정을 함께 건드려야 해서 팀 간 결합도가 오히려 높아지는 역설이 생긴다.

반대로 "서비스 메시가 있으니 게이트웨이는 필요 없다"는 접근도 문제다. 서비스 메시는 클러스터 내부 트래픽을 위해 설계된 것이라, 외부 클라이언트를 위한 API 키 발급, 요금제별 속도 제한, 공개 API 문서화 같은 "외부 계약" 역할을 대신하기엔 적합하지 않다.

## 올바른 접근: 계층을 분리해서 함께 쓴다

```
[외부 클라이언트]
      │
      ▼
[API 게이트웨이]  ← 인증, 속도 제한, API 버전 관리
      │
      ▼
[서비스 메시 사이드카] ← mTLS, 재시도, 서킷 브레이커, 관측
      │
      ▼
[내부 마이크로서비스들 간 호출]
```

작은 규모(서비스 5~10개 이하, 팀 하나가 전체를 관리)라면 서비스 메시 없이 API 게이트웨이만으로도 충분한 경우가 많다. 서비스 간 통신 정책이 복잡해지고, 서로 다른 팀이 서로 다른 언어로 서비스를 만들어 언어별로 재시도·서킷 브레이커 로직을 중복 구현하게 되는 시점이 서비스 메시 도입을 검토할 신호다.

## 실무 포인트

- **서비스 메시 도입 비용을 과소평가하지 마라.** 사이드카 프록시가 모든 Pod에 붙으면서 리소스 사용량과 지연시간이 늘어난다(사이드카당 수 ms의 추가 홉). 성능이 민감한 소수 서비스는 오히려 메시에서 제외하는 선택지도 있다.
- **관측 데이터를 이중으로 만들지 마라.** 게이트웨이 레벨 로그와 메시 레벨 트레이싱을 별도 대시보드로 관리하면 장애 시 두 시스템을 오가며 원인을 찾아야 해서 대응이 느려진다. OpenTelemetry로 트레이스 ID를 양쪽에서 일관되게 전파하는 것이 중요하다.
- **인증은 경계를 명확히 나눠라.** 외부 사용자 인증(OAuth2, API Key)은 게이트웨이에서, 서비스 간 신원 검증(mTLS, SPIFFE)은 메시에서 처리하도록 역할을 겹치지 않게 설계한다.

## 마무리 요약

- API 게이트웨이는 외부→내부 트래픽의 단일 진입점, 서비스 메시는 내부 서비스 간 트래픽 제어라는 서로 다른 문제를 푼다.
- 규모가 작을 때는 게이트웨이만으로 충분하지만, 서비스 간 통신 정책이 언어·팀별로 중복되기 시작하면 메시 도입을 검토한다.
- 두 레이어를 함께 쓸 때는 인증 역할을 겹치지 않게 나누고, 관측 데이터를 트레이스 ID로 일관되게 연결해야 한다.
