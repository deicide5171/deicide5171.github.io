## 도입

"에이전트가 최신 정보도 검색하고, 필요하면 코드도 돌려서 결과를 보여주게 해주세요." 이 요구를 받으면 보통 머릿속에 그려지는 그림은 정해져 있다. 모델이 도구 호출 의도를 뱉으면, 우리 서버가 그 요청을 받아 실제 검색 API를 때리거나 샌드박스에서 코드를 실행하고, 결과를 다시 모델에 넘겨주는 루프. MCP(Model Context Protocol)가 표준화한 것도 바로 이 구조였다 — 클라이언트가 서버를 띄우고, 모델은 그 서버가 노출한 도구 목록만 보고 호출한다.

그런데 2026년 Claude 5 세대부터 WebSearch, WebFetch, Code Execution, MCP 커넥터 같은 도구가 API 제공자 쪽 인프라에서 직접 실행되는 "서버사이드 도구"로 제공되기 시작했다. 겉보기엔 똑같이 "도구를 호출한다"지만, 실행 주체가 우리 서버에서 Anthropic 인프라로 넘어가면 지연시간·비용·데이터 통제권의 구조 자체가 달라진다. 이 글은 "검색·코드 실행 기능을 붙여달라"는 같은 요구가, 어디서 실행할지에 따라 완전히 다른 아키텍처로 번역되는 이유를 정리한다.

## 전체 시스템에서의 위치

기존 MCP 구조에서는 모델이 도구 호출 의도를 뱉을 때마다 응답이 클라이언트로 돌아오고, 클라이언트가 우리 MCP 서버를 호출하고, 그 결과를 다시 API 요청에 실어 모델에 돌려줘야 한다. 멀티턴 도구 호출 하나당 왕복이 최소 두 번이다. 서버사이드 도구는 이 왕복을 API 제공자 인프라 안에서 끝내, 모델이 도구 결과까지 받은 상태로 최종 응답만 클라이언트에 돌려준다.

<img src="/assets/images/posts/2026-10-25-claude-server-side-tools-architecture-1.svg" alt="자체 MCP 서버 경로와 서버사이드 도구 경로의 왕복 구조 비교" style="width:100%;">

- **자체 MCP 서버 경로**: 우리가 실행 환경(검색 API 키, 샌드박스, 네트워크 정책)을 전부 소유한다. 대신 모델-클라이언트-MCP 서버 사이를 매 도구 호출마다 왕복해야 한다.
- **서버사이드 도구 경로**: 왕복이 API 제공자 인프라 안에서 끝난다. 대신 실행 환경(어떤 검색 엔진을 쓰는지, 샌드박스 런타임이 뭔지)은 우리가 선택할 수 없다.
- 두 경로는 배타적이지 않다. 범용 웹 검색·코드 실행은 서버사이드 도구로, 사내 DB 조회처럼 우리 데이터에만 접근해야 하는 도구는 자체 MCP 서버로 나눠 쓰는 하이브리드 구성이 2026년 기준 가장 흔한 형태다.

## 선택의 트레이드오프

| 기준 | 서버사이드 도구 | 자체 MCP 서버 |
|---|---|---|
| 지연시간 | 왕복 1회로 단축 (에이전트 루프 안에서 처리) | 호출마다 클라이언트 왕복 발생 |
| 인프라 부담 | 거의 없음 (샌드박스·검색 인덱스 관리 불필요) | 샌드박스·API 키·네트워크 정책 직접 운영 |
| 데이터 통제권 | 제공자 인프라를 거침 — 데이터 잔류·로깅 정책 확인 필요 | 우리 네트워크 안에서 완결 |
| 커스터마이징 | 제공자가 정한 범위로 제한 | 임의의 내부 API·DB·레거시 시스템 연동 가능 |
| 과금 구조 | 도구 호출량에 따른 별도 과금 | 우리 인프라 비용으로 흡수 |
| 적합한 용도 | 범용 웹 검색, 일반 코드 실행, 공개 정보 조회 | 사내 전용 데이터, 규제·망분리 요구가 있는 도구 |

판단 기준은 단순하다. **"이 도구가 다루는 데이터가 우리만 아는 것인가, 아니면 공개된 것인가"**다. 공개 웹 검색이나 범용 계산처럼 실행 환경 자체에 민감 정보가 없다면 서버사이드 도구로 옮겨 왕복과 운영 부담을 줄이는 쪽이 이득이다. 반대로 사내 데이터베이스, 내부 결제 시스템, 망분리 구역 안의 리소스를 다뤄야 한다면 자체 MCP 서버로 남겨야 한다 — 이 데이터는 애초에 제공자 인프라를 거칠 이유가 없다.

## 실제 프로젝트 진행 순서

1. **현재 MCP 도구 목록을 데이터 민감도 기준으로 분류한다.** 웹 검색·공개 API 호출처럼 바깥 데이터만 다루는 도구와, 사내 시스템에 접근하는 도구를 먼저 나눈다.
2. **분류상 "공개 데이터" 도구부터 서버사이드 도구로 전환한다.** 기존 자체 MCP 서버 코드를 걷어내고 API 호출 시 도구 정의만 추가하면 되는 경우가 많아, 전환 비용이 낮은 쪽부터 손댄다.
3. **전환 후 지연시간을 실측한다.** 도구 호출이 잦은 멀티턴 시나리오에서 왕복 횟수가 실제로 줄었는지, 응답 체감 속도가 개선됐는지 비교한다.
4. **데이터 잔류·로깅 정책을 확인한다.** 서버사이드 도구가 처리하는 요청·응답이 제공자 쪽에 얼마나 보관되는지 약관과 설정을 확인하고, 규제 요구사항과 맞는지 따진다.
5. **사내 전용 도구는 자체 MCP 서버로 명시적으로 남긴다.** 전환 대상에서 의도적으로 제외하고, 이유를 아키텍처 문서에 기록해 나중에 "왜 이건 서버사이드로 안 옮겼냐"는 질문에 답할 수 있게 한다.

```python
# 서버사이드 도구와 자체 MCP 도구를 한 요청에 함께 등록하는 예시
response = client.messages.create(
    model="claude-sonnet-5-5",
    tools=[
        {"type": "web_search_20250305", "name": "web_search"},  # 서버사이드: 공개 웹 검색
        {"type": "code_execution_20250522", "name": "code_execution"},  # 서버사이드: 범용 코드 실행
        {
            "type": "mcp_connector",
            "server_url": "https://internal.example.com/mcp",  # 자체 서버: 사내 DB 전용 도구
        },
    ],
    messages=[{"role": "user", "content": "최근 분기 매출과 업계 평균을 비교해줘"}],
)
```

## 실무 포인트

- 서버사이드 도구는 모델 제공자가 바뀌면 그대로 못 옮긴다. 멀티 프로바이더 전략을 쓰는 조직이라면 이 종속성을 미리 감안해야 한다.
- 코드 실행 서버사이드 도구는 보통 시간·메모리 제한이 있는 공용 샌드박스다. 장시간 배치 연산처럼 무거운 작업은 여전히 자체 인프라가 맞다.
- 과금은 토큰 사용량과 별도로 도구 호출량에 붙는 경우가 많다. 트래픽이 큰 서비스는 전환 전 비용 시뮬레이션을 먼저 돌려봐야 한다.

## 마무리

- 서버사이드 도구는 도구 실행 주체를 우리 인프라에서 API 제공자 인프라로 옮겨 왕복과 운영 부담을 줄이는 선택지다.
- 판단 기준은 "이 도구가 다루는 데이터가 공개된 것인가, 사내 전용인가"이며, 둘을 섞어 쓰는 하이브리드 구성이 현실적인 기본값이다.
- 전환은 데이터 민감도 분류 → 공개 데이터 도구부터 전환 → 지연시간 실측 → 로깅 정책 확인 → 사내 전용 도구 명시적 유지 순서로 진행한다.
