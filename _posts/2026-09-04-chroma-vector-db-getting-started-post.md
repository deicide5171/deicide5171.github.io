## 왜 벡터 DB가 따로 필요한가

임베딩으로 텍스트를 벡터로 바꿨다면, 이제 "질문 벡터와 가장 가까운 문서 벡터를 빠르게 찾는" 저장소가 필요하다. 일반 DB로도 벡터를 저장할 수는 있지만, 수만~수백만 개 벡터 중에서 유사한 것을 찾는 연산은 전용 벡터 DB가 훨씬 효율적이다. **Chroma**는 별도 서버 없이 파이썬 라이브러리로 바로 쓸 수 있어, 처음 배우거나 프로토타입을 만들 때 진입장벽이 가장 낮은 편이다.

## Chroma의 특징

| 항목 | 설명 |
|---|---|
| 설치 | `pip install chromadb` 한 줄 |
| 실행 형태 | 임베디드(내 코드 안에서 바로 동작) 또는 서버 모드 |
| 임베딩 | 텍스트만 넣으면 내장 임베딩 함수가 자동 변환 |
| 적합한 용도 | 학습, 프로토타입, 중소 규모 검색 |

## 코드 예제: 설치부터 검색까지

```python
import chromadb

client = chromadb.Client()
collection = client.create_collection(name="docs")

# 1. 문서 추가 (텍스트만 넣으면 임베딩은 자동)
collection.add(
    documents=[
        "파이썬은 배우기 쉬운 프로그래밍 언어다",
        "고양이는 하루 대부분을 잠으로 보낸다",
        "자바스크립트는 웹 브라우저에서 동작한다",
    ],
    ids=["doc1", "doc2", "doc3"],
)

# 2. 시맨틱 검색 (키워드가 정확히 일치하지 않아도 의미로 찾음)
results = collection.query(
    query_texts=["코딩 언어 추천해줘"],
    n_results=2,
)
print(results["documents"])
# -> 파이썬·자바스크립트 문서가 상위로 나온다 (의미가 가깝기 때문)
```

"코딩 언어 추천"이라는 질문에 "프로그래밍 언어"를 다룬 문서가 걸리는 것이 시맨틱 검색의 핵심이다. 키워드 매칭이라면 "코딩"이라는 단어가 없어서 못 찾았을 것이다.

## 실무 포인트

- **기본 임베딩 함수는 편하지만 한국어 성능이 아쉬울 수 있다.** 한국어 문서가 많다면 한국어에 강한 임베딩 모델(예: 다국어 지원 모델)을 명시적으로 지정하는 것이 검색 품질에 도움이 된다.
- **Chroma는 프로토타입에 최적이지만 대규모 프로덕션에는 한계가 있다.** 데이터가 수백만 건을 넘거나 고가용성이 필요하면 Qdrant, Pinecone, pgvector 같은 대안을 검토해야 한다.
- **`metadata`를 함께 저장하면 검색 결과를 필터링할 수 있다.** 예를 들어 문서에 카테고리·작성일 메타데이터를 붙여두면 "특정 카테고리 안에서만 유사 검색" 같은 조합이 가능해진다.

## 마무리 요약

- 벡터 DB는 수많은 벡터 중 유사한 것을 빠르게 찾기 위한 전용 저장소이며, Chroma는 설치가 가장 간단한 편이다.
- 텍스트만 넣으면 임베딩이 자동 처리되어, 키워드가 아니라 의미로 문서를 검색할 수 있다.
- 프로토타입에는 Chroma가 좋지만, 대규모·고가용성이 필요하면 Qdrant·pgvector 등을 검토해야 한다.
