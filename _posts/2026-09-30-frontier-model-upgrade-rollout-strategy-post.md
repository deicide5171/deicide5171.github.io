## 왜 지금 이 문제가 커지는가

"더 똑똑한 모델 나왔다는데 바로 바꿔주세요." PM이나 팀장에게서 이런 요청을 받는 빈도가 최근 눈에 띄게 늘었다. 실제로 2026년 9월 22일 하루에만 Anthropic이 Claude Opus 5.5를 출시해 Claude Code의 기본 모델을 교체했고, OpenAI는 같은 날 GPT-6 Sol과 GPT-6 Luna를 내놓으며 유료 Codex 플랜의 GPT-5.5를 대체했다. 코딩 에이전트 벤치마크 리더보드에서도 Codex+GPT-6 Astra가 Terminal-Bench 4.0에서 58.2%, Claude Code+Fable 5.1이 57.9%로 순위가 몇 주 단위로 뒤바뀌는 상황이다.

이런 속도에서 "새 모델이 나오면 그냥 바꾼다"는 태도는 위험하다. 모델을 바꾸는 순간 같은 프롬프트도 다른 방식으로 해석되고, 도구 호출 패턴이 달라지고, 지연시간과 비용 구조까지 함께 바뀐다. 빌더에게 중요한 질문은 "언제 더 똑똑한 모델을 쓸 것인가"가 아니라 "**모델 교체를 어떤 절차로 검증하고 얼마나 점진적으로 반영할 것인가**"다.

## 요구사항을 기술 문제로 번역하기

"새 모델로 바꿔주세요"라는 한 줄은 실제로 릴리스 엔지니어링의 표준 질문과 동일하다. 이 변경이 기존 사용자 경험을 깨뜨리지 않는가, 문제가 생겼을 때 얼마나 빨리 되돌릴 수 있는가, 그리고 전체 트래픽에 반영하기 전에 일부에게만 노출해 검증할 방법이 있는가. 새 코드를 배포할 때 카나리 배포나 블루-그린 배포를 쓰는 것과 원리는 같다. 다만 모델 교체는 코드 배포와 달리 **출력의 질적 변화**를 함께 검증해야 한다는 점이 다르다. 응답 속도가 빨라졌다고 좋은 게 아니라, 같은 입력에 대해 툴 호출 순서나 최종 판단이 이전과 달라지지 않았는지까지 봐야 한다.

여기서 앞서 다룬 트레일젝토리 평가 체계가 그대로 재사용된다. 골든 데이터셋으로 새 모델의 오프라인 점수를 먼저 확인하고, 통과하면 소규모 실트래픽으로 카나리를 돌리는 구조다. 모델 교체는 "평가 파이프라인이 이미 있어야 안전하게 할 수 있는 작업"이라는 뜻이다.

## 전체 시스템에서의 위치

모델은 애플리케이션 스택에서 고정된 부품이 아니라 **교체 가능한 컴포넌트**로 취급해야 한다. 이를 위해 애플리케이션 코드와 모델 선택 사이에 라우팅 게이트웨이 계층을 둔다.

<img src="/assets/images/posts/2026-09-30-frontier-model-upgrade-rollout-strategy-1.svg" alt="사용자 요청이 모델 라우팅 게이트웨이를 거쳐 대다수 트래픽은 기존 pinned 버전으로, 소규모 트래픽은 신규 모델 카나리로 나뉘고, 양쪽 결과를 eval 지표로 비교해 기준 충족 시 비중을 확대하거나 미달 시 즉시 롤백하는 구조도" style="width:100%;">

게이트웨이가 트래픽을 나누는 이유는 두 가지다. 하나는 위험 격리(신규 모델의 이상 동작이 전체 사용자에게 퍼지지 않도록), 다른 하나는 비교 가능한 실측 데이터 확보(같은 시점, 같은 사용자 분포에서 두 모델의 결과를 나란히 볼 수 있도록)다. 이 계층이 없으면 "모델을 바꿨더니 뭔가 이상해졌다"는 사후 보고만 남고, 정확히 무엇이 바뀌었는지 재현하기 어렵다.

## 선택의 트레이드오프

| 전략 | 방식 | 장점 | 위험 |
|---|---|---|---|
| Latest 별칭 자동 추적 | `model: "latest"`로 벤더가 갱신하는 최신 버전을 자동 반영 | 항상 최신 성능, 운영 부담 최소 | 예고 없는 동작 변화, 재현 불가능한 버그 |
| 버전 완전 고정 | 특정 버전 문자열을 코드에 박고 수동 승격 | 예측 가능, 재현성 확보 | 승격이 늦어져 성능·비용 이점을 놓침 |
| 카나리 점진 확대 | 소규모 트래픽부터 시작해 지표 통과 시 비중 확대 | 위험 격리 + 실측 데이터 기반 의사결정 | 게이트웨이·모니터링 구축 비용 필요 |

"latest 별칭 자동 추적"은 편리해 보이지만 프로덕션 에이전트에는 함정이다. 벤더가 모델을 조용히 교체하면 어제까지 잘 작동하던 프롬프트가 오늘 다른 이유로 실패할 수 있고, 원인 추적이 "그날 무슨 모델이 떴는지"를 벤더 릴리스 노트에서 역추적하는 일이 된다. 반대로 완전 고정만 고집하면 몇 주 만에 뒤바뀌는 벤치마크 순위에서 뒤처진 모델을 계속 쓰게 된다. 대부분의 프로덕션 팀에게는 카나리 점진 확대가 가장 균형 잡힌 선택이다.

## 실제 프로젝트 진행 순서

1. **모델 교체에 민감한 지표를 먼저 정의한다.** 정확도뿐 아니라 툴 호출 패턴 변화, p99 지연시간, 토큰당 비용까지 같은 대시보드에 놓는다.
2. **기존 골든 데이터셋으로 신규 모델의 오프라인 점수를 먼저 확인한다.** 여기서 기준 미달이면 카나리 단계로 넘어가지 않는다.
3. **소규모 트래픽(5% 내외)으로 카나리를 돌린다.** 이때 신규 모델과 기존 모델에 같은 유형의 요청이 고르게 분배되도록 라우팅 규칙을 설계한다.
4. **모니터링 기간과 확대 기준을 미리 문서화한다.** "며칠간, 어떤 지표가 어떤 임계값을 넘으면 비중을 몇 %까지 올린다"를 사전에 정해두지 않으면 판단이 감에 의존하게 된다.
5. **롤백 경로를 항상 열어둔다.** 이전 버전을 즉시 호출할 수 있는 상태를 유지하다가, 신규 모델이 전체 트래픽을 감당할 만큼 검증되면 그때 이전 버전을 폐기한다.

## 마무리

- 모델 교체는 코드 배포와 같은 릴리스 엔지니어링 문제이며, 벤치마크 순위가 아니라 우리 워크로드의 골든셋 점수로 판단해야 한다.
- latest 별칭 자동 추적은 편리하지만 예고 없는 동작 변화로 재현 불가능한 장애를 만든다.
- 카나리 점진 확대 구조를 쓰려면 트레일젝토리 평가 파이프라인이 먼저 갖춰져 있어야 한다.
