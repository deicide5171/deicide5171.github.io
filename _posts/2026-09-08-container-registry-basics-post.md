## 만든 이미지는 어디에 두나

도커로 애플리케이션을 이미지로 만들면, 이 이미지를 다른 서버나 팀원과 공유해야 한다. 내 PC에만 있으면 배포 서버가 쓸 수 없다. **컨테이너 레지스트리(container registry)**는 이 **이미지를 저장하고 배포하는 중앙 창고**다. 깃허브가 코드 저장소이듯, 레지스트리는 이미지 저장소다. Docker Hub가 대표적인 공개 레지스트리다.

## push와 pull

| 동작 | 방향 | 설명 |
|---|---|---|
| push | 내 PC → 레지스트리 | 만든 이미지를 창고에 올린다 |
| pull | 레지스트리 → 서버 | 창고에서 이미지를 내려받는다 |

개발자가 이미지를 **push**하면, 배포 서버나 쿠버네티스가 그 이미지를 **pull**해서 컨테이너로 실행한다. 이 흐름 덕분에 "내 PC에선 됐는데" 문제 없이 같은 이미지가 어디서나 동일하게 실행된다.

## 사용 흐름

```text
1. docker build -t myapp:1.0 .        # 이미지 빌드
2. docker tag myapp:1.0 레지스트리주소/myapp:1.0
3. docker push 레지스트리주소/myapp:1.0  # 창고에 업로드
--- 배포 서버에서 ---
4. docker pull 레지스트리주소/myapp:1.0  # 창고에서 다운로드
5. docker run 레지스트리주소/myapp:1.0   # 실행
```

## 실무 포인트

- **공개 레지스트리와 비공개 레지스트리를 구분하라.** Docker Hub 공개 저장소는 누구나 볼 수 있어 회사 코드가 담긴 이미지엔 부적절하다. AWS ECR, GCP Artifact Registry, GitHub Container Registry, Harbor(자체 호스팅) 등 **비공개 레지스트리**를 쓴다.
- **태그(tag)를 잘 관리하라.** `latest` 태그만 쓰면 어떤 버전이 배포됐는지 알기 어렵다. `1.0.3`처럼 명확한 버전 태그를 붙이면 롤백과 추적이 쉽다.
- **이미지 취약점 스캔을 켜라.** 대부분의 레지스트리는 업로드된 이미지의 보안 취약점을 자동 스캔해준다. 오래된 베이스 이미지에 알려진 취약점이 있을 수 있으니 정기적으로 확인한다.

## 마무리 요약

- 컨테이너 레지스트리는 도커 이미지를 저장·공유하는 중앙 창고다.
- 개발자가 push한 이미지를 배포 서버가 pull해 어디서나 동일하게 실행한다.
- 회사 이미지엔 비공개 레지스트리를 쓰고, 버전 태그 관리와 취약점 스캔을 챙겨야 한다.
