## 왜 서버 한 대로는 부족한가

서비스가 커지면 서버 한 대가 감당할 수 있는 트래픽에 한계가 온다. 여러 대의 서버를 두고 트래픽을 나눠 받게 하면 되는데, 이때 클라이언트의 요청을 여러 서버 중 하나로 알맞게 분배해주는 장치가 **로드밸런서**다. 로드밸런서는 동작하는 네트워크 계층에 따라 크게 L4와 L7로 나뉜다.

## L4 vs L7 로드밸런서

| 항목 | L4 로드밸런서 | L7 로드밸런서 |
|---|---|---|
| 동작 계층 | 전송 계층(TCP/UDP) | 애플리케이션 계층(HTTP) |
| 확인 가능한 정보 | IP, 포트 | URL 경로, 헤더, 쿠키, 메서드 |
| 라우팅 예시 | 단순히 서버 IP:포트로 전달 | `/api/*`는 A서버, `/static/*`는 B서버로 분기 |
| 처리 속도 | 빠름(패킷 레벨) | 상대적으로 느림(내용 분석 필요) |
| 대표 예시 | AWS NLB, LVS | AWS ALB, Nginx, HAProxy |

## 언제 무엇을 쓸까

```text
1. 단순히 여러 서버에 트래픽만 고르게 나누면 되는가?
   → L4로 충분하다. 성능 오버헤드가 적다.

2. URL 경로나 헤더 값에 따라 다른 서버로 보내야 하는가?
   (예: /api는 백엔드, /는 프론트엔드 정적 파일 서버)
   → L7이 필요하다. 내용을 봐야 라우팅할 수 있다.

3. SSL 종료(HTTPS 복호화)를 로드밸런서에서 처리하고 싶은가?
   → L7에서 처리하는 것이 일반적이다.

4. 매우 높은 처리량과 낮은 지연이 최우선인가?
   → L4를 앞단에 두고, 필요하면 L7을 그 뒤에 두는 계층 구조도 흔하다.
```

## 로드밸런싱 알고리즘 몇 가지

- **라운드 로빈**: 순서대로 돌아가며 서버에 요청을 분배. 서버 성능이 비슷할 때 적합.
- **최소 연결(Least Connections)**: 현재 연결 수가 가장 적은 서버로 보낸다. 요청 처리 시간이 서버마다 다를 때 유리.
- **IP 해시**: 같은 클라이언트 IP는 항상 같은 서버로 보낸다. 세션 유지가 필요할 때 사용.

## 실무 포인트

- **헬스체크를 반드시 설정해야 한다.** 죽은 서버로 계속 트래픽을 보내면 사용자에게 에러가 노출된다. 로드밸런서가 주기적으로 헬스체크 엔드포인트를 확인해 죽은 서버를 자동으로 제외해야 한다.
- **세션을 서버 메모리에 저장하는 구조라면 IP 해시나 쿠키 기반 스티키 세션이 필요하다.** 다만 이는 확장성을 해치므로, 가능하면 세션을 Redis 같은 외부 저장소로 옮기는 것이 더 나은 장기 해법이다.
- **클라우드 환경에서는 관리형 로드밸런서(ALB, NLB 등)를 쓰는 것이 직접 HAProxy를 운영하는 것보다 대부분 유지보수 부담이 적다.**

## 마무리 요약

- L4는 IP·포트만 보고 빠르게 분배하고, L7은 URL·헤더까지 확인해 더 정교하게 라우팅한다.
- 단순 분산이면 L4, 경로 기반 라우팅이나 SSL 종료가 필요하면 L7을 선택한다.
- 헬스체크 설정은 로드밸런서 도입 시 절대 빠뜨리면 안 되는 기본 항목이다.
