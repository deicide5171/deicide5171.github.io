## 왜 지금 이 판단이 불거지는가

"사내 주문 시스템 API를 MCP 서버로 열어서, 여러 팀의 에이전트가 동시에 접속해 쓰게 해주세요." 이 요구를 받으면 지금까지는 MCP의 `initialize` 핸드셰이크로 세션을 하나 발급받고, 그 세션 ID를 키 삼아 인증 컨텍스트·진행 중인 작업 상태·서버가 클라이언트에 먼저 말을 거는 샘플링 요청까지 전부 그 세션에 묶어 설계하는 게 당연했다. 클라이언트 하나가 서버 인스턴스 하나에 고정(sticky)되는 구조를 전제로 깔고 갔다는 뜻이다.

그런데 2026년 7월 28일 공개된 MCP 스펙 개정은 이 전제를 통째로 걷어냈다. `initialize` 핸드셰이크와 `Mcp-Session-Id` 헤더가 사라졌고, 모든 요청은 완전히 독립적으로 취급된다. Roots·Sampling·Logging 기능도 12개월의 유예 기간과 함께 폐기 예정으로 지정됐다. 론칭 이후 가장 큰 폭의 개정이라는 평가가 나올 만큼, 세션을 전제로 설계해 둔 MCP 서버들은 이번 개정으로 아키텍처를 다시 그려야 하는 상황에 놓였다. 실제로 광고 기술 업계에서는 세션이 사라지면서 에이전트 서버를 다시 구축해야 했던 사례까지 보고됐다. 이게 빌더에게 중요한 이유는 간단하다 — "MCP 서버를 어떻게 만들 것인가"가 아니라 "상태를 어디에 둘 것인가"라는 더 근본적인 질문으로 되돌아갔기 때문이다.

## 요구사항을 기술 문제로 번역하기

"여러 에이전트가 동시에 우리 API를 쓰게 해주세요"라는 한 문장은 세 가지 서로 다른 상태 관리 문제를 품고 있다. 첫째, **요청자가 누구인지 매 요청마다 증명해야 하는 인증 문제** — 예전엔 세션 발급 시 한 번만 검증하고 이후엔 세션 ID로 넘어갔지만, 이제는 매 요청이 자체적으로 완결된 자격증명을 들고 와야 한다. 둘째, **몇 분~몇 시간씩 걸리는 장시간 작업의 진행 상태를 어디에 보관할지의 문제** — 세션이라는 그릇이 없어졌으니 작업 상태를 서버 메모리가 아닌 다른 곳에 둬야 한다. 셋째, **서버가 클라이언트에게 먼저 알려야 하는 이벤트(진행률 업데이트, 승인 요청)를 어떤 메커니즘으로 보낼지의 문제** — 세션에 묶인 지속 연결이 없으니 새로운 통신 패턴이 필요하다. 스펙은 이 셋째 문제를 MRTR(Multi Round-Trip Requests)이라는 반복 요청 패턴으로 대체했다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-06-mcp-stateless-spec-server-state-design-1.svg" alt="세션 기반 구 구조에서는 클라이언트가 로드밸런서를 거쳐 세션 ID로 고정된 서버 인스턴스에 매번 연결되어 인증·작업상태·알림이 서버 메모리에 묶여 있었지만, 스테이트리스 신 구조에서는 모든 요청이 라운드로빈으로 아무 서버 인스턴스에나 도달하고 인증 토큰은 요청에 직접 포함되며 작업 상태와 알림은 외부 저장소(Redis/DB)와 MRTR 폴링으로 분리되는 구조를 비교한 다이어그램" style="width:100%;">

예전 구조에서는 클라이언트 → 로드밸런서 → (세션 ID로 고정된) 특정 서버 인스턴스로 이어지는 경로가 고정돼 있었고, 그 서버 인스턴스의 메모리 안에 인증 컨텍스트와 작업 상태가 같이 살았다. 로드밸런서는 sticky session을 지원해야 했고, 서버 인스턴스가 죽으면 그 세션에 묶인 모든 상태가 함께 사라졌다. 개정 이후 구조에서는 모든 요청이 완전히 독립적이므로 로드밸런서는 평범한 라운드로빈으로 단순화된다. 대신 인증은 요청 자체에 포함된 자체완결적 토큰(서명된 OAuth 액세스 토큰 등)으로 검증하고, 장시간 작업의 상태와 진행률은 서버 프로세스가 아니라 Redis나 DB 같은 외부 저장소에 task ID로 보관한다. 클라이언트는 그 task ID를 들고 MRTR로 반복 질의하거나 폴링해 진행 상황을 확인한다. 상태가 서버 바깥으로 완전히 빠져나간 셈이다.

## 선택의 트레이드오프

| 기준 | 세션 기반(구 스펙) | 스테이트리스(2026-07-28 신 스펙) |
|---|---|---|
| 수평 확장성 | sticky session 필요, 인스턴스 추가가 번거로움 | 라운드로빈만으로 충분, 확장이 단순 |
| 장애 복구 | 서버 인스턴스 다운 시 세션 상태 유실 | 상태가 외부 저장소에 있어 인스턴스 교체에 영향 없음 |
| 구현 복잡도(단기) | 세션 수명주기 관리가 프레임워크 레벨에서 처리됨 | 인증·작업 상태·알림을 직접 설계해야 함 |
| 장시간 작업 처리 | 세션에 묶인 연결로 진행률을 푸시 | task ID 발급 + MRTR 폴링으로 클라이언트가 당겨감 |
| 기존 서버와의 호환성 | 그대로 동작 | Roots/Sampling/Logging 의존 기능은 마이그레이션 필요 |

표에서 가장 눈여겨봐야 할 줄은 "구현 복잡도"다. 스테이트리스 구조는 확장성과 장애 복구에서 명백히 유리하지만, 그 대가로 예전엔 프로토콜이 대신 처리해주던 세션 수명주기 관리를 서버 구현자가 직접 떠안아야 한다. "서버가 가벼워졌다"가 아니라 "서버가 책임져야 할 범위가 바뀌었다"로 읽는 게 정확하다.

## 실제 프로젝트 진행 순서

1. **기존 서버에서 세션에 의존하는 부분부터 전수 조사한다.** 인증 캐싱, 진행 중인 작업의 메모리 내 상태, 서버 주도 알림(Sampling 등)이 코드 어디에 박혀 있는지 먼저 목록화한다.
2. **인증을 요청 단위 자체완결형으로 전환한다.** 세션 발급 시 한 번만 검증하던 구조를, 매 요청마다 서명된 토큰을 독립적으로 검증하는 구조로 바꾼다.
3. **장시간 작업을 task ID + 외부 저장소 패턴으로 재설계한다.** 작업을 시작하면 task ID를 즉시 반환하고, 실제 상태는 Redis나 DB에 저장해 어떤 서버 인스턴스가 받아도 동일하게 조회 가능하게 만든다.
4. **Roots·Sampling·Logging에 의존하는 기능은 12개월 유예 기간 안에 MRTR 기반 대안으로 옮긴다.** 유예 기간이 끝나기 전에 마이그레이션 완료 시점을 미리 못 박아 둔다.
5. **로드밸런서 설정을 단순화하고 모니터링 포인트를 다시 잡는다.** sticky session 설정을 걷어내고, 대신 외부 상태 저장소의 지연시간과 가용성을 새로운 관찰 대상으로 추가한다.

## 실무 포인트

**하위 호환이 깨진다는 것을 가볍게 보지 않는다.** 이번 개정은 명시적으로 비하위호환 변경을 포함하고 있다. 기존 클라이언트·서버 조합이 암묵적으로 세션을 전제했다면, 업그레이드 시점에 양쪽을 동시에 맞추지 않으면 바로 깨진다.

**MRTR을 "폴링으로 퇴보했다"고만 보지 않는다.** 세션 기반 푸시 알림은 구현이 간단했던 대신 서버 인스턴스 고정이라는 비용을 숨기고 있었다. MRTR은 그 비용을 명시적으로 드러내는 대신 어떤 인스턴스가 받아도 동작하는 구조를 보장한다.

**모든 MCP 서버가 당장 재설계가 필요한 건 아니다.** 단일 인스턴스로만 운영되고 수평 확장 계획이 없는 내부 도구라면, 세션 기반 구조를 당장 걷어낼 필요성은 낮다. 여러 에이전트·여러 인스턴스로 트래픽이 늘어날 예정인 서버부터 우선순위를 매겨야 한다.

## 마무리

- 2026-07-28 MCP 스펙 개정은 세션과 `initialize` 핸드셰이크를 완전히 제거해, MCP 서버를 로드밸런서 뒤의 평범한 스테이트리스 HTTP 서비스처럼 다룰 수 있게 만들었다.
- 그 대가로 인증·장시간 작업 상태·서버 주도 알림을 서버 구현자가 직접 외부 저장소와 MRTR 패턴으로 설계해야 하며, "서버가 가벼워졌다"보다 "책임 범위가 바뀌었다"로 이해하는 게 정확하다.
- 실제 마이그레이션은 세션 의존 부분을 전수 조사하고, 인증을 요청 단위로, 작업 상태를 외부 저장소 기반으로 바꾼 뒤, Roots/Sampling/Logging 의존 기능을 유예 기간 안에 옮기는 순서로 진행해야 한다.
