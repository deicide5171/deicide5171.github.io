조직이 커지면 데이터 파이프라인도 자연스럽게 중앙 집중화된다. 각 도메인 팀은 자신의 데이터를 중앙 데이터 엔지니어링팀에 넘기고, 그 팀이 ETL을 짜고 데이터 웨어하우스에 적재하고 품질을 관리한다. 문제는 도메인 팀 수가 늘어날수록 이 중앙팀 하나에 모든 파이프라인 변경 요청이 쌓인다는 것이다. 도메인 팀은 자기 데이터의 스키마조차 마음대로 못 바꾸고, 중앙팀은 자신이 깊이 이해하지 못하는 수십 개 도메인의 파이프라인을 떠안는다. 이 구조적 병목은 팀을 늘리는 것으로는 해결되지 않는다.

데이터 메시(Data Mesh)는 이 문제를 조직 구조부터 다시 설계해서 푼다. 핵심 주장은 "데이터도 마이크로서비스처럼 도메인 팀이 직접 소유해야 한다"는 것이다. 중앙팀은 파이프라인을 대신 만들어주는 대신, 도메인 팀이 스스로 데이터 제품을 만들 수 있는 셀프서비스 플랫폼과 거버넌스 표준을 제공하는 역할로 바뀐다. 이 글에서는 데이터 메시의 네 가지 원칙과, 이를 도입할 때 실제로 마주치는 트레이드오프를 정리한다.

## 핵심 개념 1: 데이터 메시의 네 가지 원칙

데이터 메시는 Zhamak Dehghani가 제시한 네 가지 원칙 위에 서 있다.

| 원칙 | 의미 |
|---|---|
| 도메인 오너십 | 각 도메인 팀이 자신의 데이터를 생산·소유·품질 책임을 진다 |
| 제품으로서의 데이터 | 데이터를 다른 팀이 쓸 수 있는 "제품"으로 취급해 문서화·SLA·버전 관리를 갖춘다 |
| 셀프서비스 데이터 플랫폼 | 중앙팀은 파이프라인 대신 도메인 팀이 쓸 인프라·툴링을 제공한다 |
| 연합 컴퓨테이셔널 거버넌스 | 스키마 표준·보안 정책은 중앙에서 정하되 자동화된 정책으로 강제한다 |

이 네 원칙 중 어느 하나만 적용하면 데이터 메시가 아니다. 예를 들어 "도메인 오너십"만 적용하고 거버넌스를 생략하면, 팀마다 제각각인 스키마와 명명 규칙 때문에 데이터를 조합하는 소비자 팀이 오히려 더 큰 혼란을 겪는다. 데이터 메시가 자주 실패하는 지점이 바로 여기다 — 조직 개편(도메인 오너십)만 하고 플랫폼·거버넌스 투자를 하지 않는 경우다.

## 핵심 개념 2: "데이터 제품"이라는 계약

데이터 메시에서 각 도메인이 발행하는 데이터는 단순한 테이블이 아니라 **데이터 제품(data product)**으로 취급된다. 데이터 제품은 스키마, 갱신 주기, 품질 보증(SLA), 접근 방법(API/쿼리 인터페이스), 소유 팀 연락처를 명시한 메타데이터를 갖춘 배포 단위다. 소비하는 팀은 이 계약을 신뢰하고 사용할 수 있고, 생산 팀은 계약을 깨는 변경(breaking change) 시 버전을 올려 하위 호환을 관리할 책임을 진다.

```yaml
# data-product.yaml — 주문 도메인 팀이 발행하는 데이터 제품 메타데이터 예시
name: orders-data-product
domain: order-management
owner_team: order-platform-team
version: 2.1.0
schema:
  format: parquet
  location: s3://data-mesh/order-management/orders/
  fields:
    - name: order_id
      type: string
      nullable: false
    - name: status
      type: string
      description: "pending|paid|shipped|cancelled"
sla:
  freshness: "매 15분마다 갱신"
  availability: "99.9%"
access:
  query_interface: "Trino를 통한 SQL 쿼리"
  contact: order-platform-team@company.com
```

이런 메타데이터를 중앙 데이터 카탈로그에 등록해두면, 다른 도메인 팀이 필요한 데이터를 찾을 때 어느 팀에게 무엇을 요청해야 하는지 스스로 탐색할 수 있다. 중앙 데이터팀이 모든 요청의 중개자가 될 필요가 없어지는 지점이다.

## 실무 포인트

- **조직 규모가 작다면 데이터 메시는 과잉설계일 수 있다**: 도메인이 서너 개뿐이고 중앙 데이터팀이 병목이 아니라면, 데이터 메시가 요구하는 조직 개편과 플랫폼 투자 비용이 얻는 이득보다 클 수 있다. 데이터 메시는 "도메인 수가 많고 중앙집중이 실제로 병목인" 조직에 맞는 해법이다.
- **셀프서비스 플랫폼 없이 도메인 오너십만 넘기지 않는다**: 도메인 팀에 "이제 너희가 파이프라인 만들어라"라고만 하고 데이터 엔지니어링 툴링을 제공하지 않으면, 각 팀이 제각각의 방식으로 조악한 파이프라인을 만들어 오히려 품질이 떨어진다. 배포 템플릿, 데이터 품질 체크 자동화, 카탈로그 등록 자동화가 선행돼야 한다.
- **연합 거버넌스는 문서가 아니라 자동화로 강제한다**: "스키마 명명 규칙을 지켜주세요" 같은 문서만으로는 지켜지지 않는다. CI 파이프라인에서 스키마 검증, PII 필드 자동 태깅, 접근 권한 정책을 코드로 강제하는 것이 연합 컴퓨테이셔널 거버넌스의 실제 구현이다.

## 3줄 요약

- 데이터 메시는 모든 파이프라인이 중앙팀에 몰리는 병목을, 도메인 팀이 데이터를 직접 소유하는 조직 구조 변화로 재구성한다.
- 도메인 오너십·데이터 제품화·셀프서비스 플랫폼·연합 거버넌스 네 원칙이 함께 갖춰져야 하며, 하나만 적용하면 오히려 혼란이 커진다.
- 중앙집중이 실제로 병목인 대규모 조직에 맞는 해법이며, 플랫폼·거버넌스 투자 없이 조직 개편만 하면 실패로 이어지기 쉽다.
