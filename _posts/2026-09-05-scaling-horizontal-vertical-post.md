## 트래픽이 늘면 무엇을 해야 하나

서비스가 잘 되어 사용자가 몰리면 서버 한 대로는 감당이 안 된다. 이때 선택지는 크게 둘이다. 서버 한 대의 성능(CPU·메모리)을 더 좋게 만드는 **수직 확장(스케일 업)**, 그리고 같은 성능의 서버를 여러 대로 늘리는 **수평 확장(스케일 아웃)**이다.

## 두 방식 비교

| 항목 | 수직 확장(스케일 업) | 수평 확장(스케일 아웃) |
|---|---|---|
| 방법 | 서버 성능 업그레이드 | 서버 대수 늘리기 |
| 난이도 | 쉬움(코드 변경 거의 없음) | 부하 분산·상태 관리 필요 |
| 한계 | 한 대의 성능에 물리적 상한 | 이론상 계속 늘릴 수 있음 |
| 장애 영향 | 그 서버가 죽으면 전체 정지 | 한 대 죽어도 나머지가 처리 |
| 비용 | 고성능 장비는 비쌈 | 보급형 장비 여러 대로 분산 가능 |

## 언제 무엇을 선택하나

```text
- 당장 급하고 트래픽이 아주 크지 않다 -> 수직 확장(서버 사양 올리기)
  가장 빠르고 간단하다. 코드도 거의 안 바꿔도 된다.

- 트래픽이 계속 늘어날 것이고 고가용성이 필요하다 -> 수평 확장
  서버를 계속 추가할 수 있고, 한 대가 죽어도 서비스가 유지된다.

현실에서는 둘을 함께 쓴다. 어느 정도까지는 사양을 올리다가,
한계에 다다르면 여러 대로 늘리는 식이다.
```

## 수평 확장이 어려운 이유: 상태(state)

수평 확장의 핵심 난제는 **상태 관리**다. 서버가 한 대일 때는 로그인 세션을 그 서버 메모리에 두면 됐지만, 여러 대가 되면 문제가 생긴다.

```text
서버 A에서 로그인한 사용자가 다음 요청에서 서버 B로 갔다면?
-> B는 그 사용자의 세션을 모른다 -> 로그아웃된 것처럼 보인다

해결: 세션을 서버 메모리가 아니라 Redis 같은 공유 저장소에 두어
      어느 서버가 요청을 받든 같은 세션을 참조하게 한다
```

이래서 "상태를 서버 밖으로 빼는(stateless)" 설계가 수평 확장의 전제 조건이 된다.

## 실무 포인트

- **처음부터 무리하게 수평 확장을 설계할 필요는 없다.** 트래픽이 감당 가능한 수준이면 수직 확장이 훨씬 간단하고 저렴하다. 확장성은 실제로 필요해질 때 도입해도 늦지 않다.
- **DB는 수평 확장이 특히 까다롭다.** 애플리케이션 서버는 늘리기 쉽지만, 데이터를 나눠 저장하는 DB 샤딩·복제는 복잡도가 크게 올라간다. 그래서 DB는 읽기 복제본을 두거나 캐시를 앞에 붙이는 방식부터 검토한다.
- **오토스케일링은 수평 확장을 자동화한 것이다.** 트래픽에 따라 서버 수를 자동으로 늘리고 줄이는 클라우드 기능인데, 이 역시 stateless 설계가 되어 있어야 제대로 동작한다.

## 마무리 요약

- 수직 확장은 서버 성능을 키우는 것이고, 수평 확장은 서버 수를 늘리는 것이다.
- 수직 확장은 간단하지만 물리적 한계가 있고, 수평 확장은 확장성·가용성이 좋지만 상태 관리가 어렵다.
- 수평 확장의 전제는 상태를 서버 밖(Redis 등)으로 빼는 stateless 설계다.
