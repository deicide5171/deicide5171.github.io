## 왜 지금 이 구분이 필요한가

에이전트에 상태를 붙여야 하는 순간이 오면 팀들이 가장 먼저 던지는 질문은 "메모리 시스템을 만들까, RAG를 붙일까"다. 그런데 이 둘은 경쟁 관계가 아니라 애초에 다른 문제를 푸는 도구다. 장기기억은 "이 사용자·이 세션에 대해 무엇이 참인가"를 다루고, RAG는 "우리가 아는 지식 중 지금 질문과 관련 있는 것은 무엇인가"를 다룬다. 둘을 구분하지 않고 아무 정보나 벡터DB 하나에 몰아넣으면, 어제 사용자가 말한 선호가 회사 정책 문서와 같은 검색 풀에서 경쟁하는 이상한 구조가 된다.

문제는 실무에서 이 경계가 생각보다 애매하다는 점이다. "사용자가 지난주에 물어본 질문"은 메모리인가 검색 대상인가? "매주 갱신되는 FAQ 문서"는 RAG로 충분한가, 아니면 캐싱된 메모리로 다뤄야 하는가? 이 글은 아키텍처 설계(3계층 메모리 구조)나 검색 파이프라인 튜닝(청킹·재순위화)이 아니라, 애초에 "이 정보를 어느 쪽에 넣을지" 정하는 의사결정 기준에 집중한다.

## 핵심 개념 1: 두 시스템이 푸는 문제는 다르다

| 구분 | 장기기억(Memory) | RAG |
|---|---|---|
| 정보의 소유자 | 특정 사용자·세션·에이전트 인스턴스 | 조직·도메인 전체가 공유 |
| 생성 주체 | 대화 중 관찰·추론으로 자연 발생 | 사람이 미리 작성·수집한 문서 |
| 변경 빈도 | 대화할 때마다 계속 갱신됨 | 배치·수동 인덱싱 주기로 갱신 |
| 정답의 성격 | "이 사용자에게는 이것이 참" (주관적) | "문서에 이렇게 쓰여 있다" (근거 기반) |
| 실패했을 때 | 사용자를 처음 본 사람처럼 대함 | 틀린 사실을 그럴듯하게 답함 |

이 표에서 가장 중요한 줄은 "생성 주체"다. RAG용 문서는 누군가 검토하고 게시한 결과물이라 어느 정도 품질이 보장되지만, 메모리는 대화 중 자동으로 추출되므로 애초에 노이즈가 섞여 있다고 가정하고 설계해야 한다. 반대로 RAG는 "이 조직이 이미 알고 있는 것"을 벗어난 개인화된 판단은 절대 하지 못한다.

## 핵심 개념 2: 세 가지 질문으로 저장 위치를 정한다

새로운 정보 조각을 마주쳤을 때 아래 순서로 질문하면 대부분 답이 나온다.

1. **누구의 정보인가?** — 여러 사용자에게 동일하게 적용되면 RAG(공유 지식), 특정 사용자·세션에만 유효하면 메모리.
2. **얼마나 자주, 누가 바꾸는가?** — 사람이 검토 후 배포하는 주기로 바뀌면 RAG 인덱싱, 대화 도중 실시간으로 계속 바뀌면 메모리.
3. **틀렸을 때 비용이 어디로 튀는가?** — 잘못된 검색이 조직 차원의 오답으로 이어지면 RAG 쪽 검증을 강화하고, 잘못된 기억이 한 사용자와의 관계만 망가뜨린다면 메모리 쪽에서 신뢰도·출처를 관리한다.

경계 사례는 대개 첫 번째 질문에서 걸린다. 예컨대 "이 고객이 이전에 환불받은 이력"은 사용자 개인 정보이므로 메모리처럼 보이지만, 실제로는 트랜잭션 시스템의 정형 데이터라 메모리도 RAG도 아닌 별도의 API 조회로 처리하는 편이 낫다. 메모리와 RAG는 "비정형·의미 기반 검색이 필요한 정보"를 다루는 도구이지, 모든 상태 저장 문제의 정답은 아니다.

## 예제: 요청을 두 경로로 분기하는 라우팅 로직

```python
def route_context(user_id, query, has_structured_lookup):
    context = {"memory": [], "rag": []}

    # 1) 정형 데이터는 둘 다 아님 - API/DB 직접 조회
    if has_structured_lookup(query):
        return context  # 별도 시스템에서 처리, 여기서는 스킵

    # 2) "나에 대한" 질문인가 -> 메모리 우선
    if is_personal_reference(query):  # "내가 전에 말한", "내 취향" 등
        context["memory"] = memory_store.search(user_id, query, top_k=5)

    # 3) 도메인 지식이 필요한가 -> RAG
    if needs_domain_knowledge(query):  # 정책, 매뉴얼, 공식 문서 참조
        context["rag"] = rag_store.search(query, top_k=5)

    # 두 출처를 함께 쓰되, 응답에서는 반드시 출처를 구분해 표시한다
    return context
```

라우팅 로직 자체보다 중요한 것은 마지막 줄이다. 메모리에서 온 정보("사용자가 이렇게 말했다")와 RAG에서 온 정보("문서에 이렇게 쓰여 있다")를 컨텍스트 조립 단계에서 섞어버리면, LLM이 둘을 구분하지 못하고 사용자의 주관적 발언을 조직 공식 정책처럼 답하는 사고가 생긴다. 프롬프트 안에서도 두 출처를 별도 섹션으로 나눠 표시하는 것이 안전하다.

## 실무 포인트

- **메모리를 RAG처럼 벡터 검색만으로 운영하지 않는다**: 사용자 프로필 같은 핵심 정보는 검색에 걸리지 않으면 아예 사라진 것과 같으므로, 자주 참조되는 항목은 검색 없이 항상 포함하는 구조(요약 프로필 등)를 함께 둔다.
- **RAG 문서에 개인정보를 섞지 않는다**: 공유 벡터 인덱스에 특정 사용자의 대화 내용이 섞여 들어가면 다른 사용자 요청에 노출될 위험이 생긴다. 저장 전에 반드시 분리한다.
- **출처 라벨을 응답 생성 단계까지 유지한다**: "기억에 근거함" vs "문서에 근거함"을 UI나 로그에서 구분할 수 있어야, 사용자가 틀린 정보를 지적했을 때 원인을 메모리 오류인지 RAG 검색 오류인지 빠르게 좁힐 수 있다.
- **애매하면 둘 다 시도하고 실패 로그로 판단한다**: 처음부터 완벽하게 분류하기보다, 실제 실패 사례(엉뚱한 문서를 근거로 들거나 기억을 못 찾는 경우)를 모아 라우팅 규칙을 점진적으로 다듬는 편이 현실적이다.

## 3줄 요약

- 장기기억은 "이 사용자에 대한 참"을, RAG는 "조직이 아는 지식"을 다루는 서로 다른 시스템이며 하나로 뭉뚱그리면 오답의 원인을 추적할 수 없다.
- 정보의 소유자·변경 주체·실패 비용이라는 세 질문으로 저장 위치를 정하면 대부분의 경계 사례가 정리되고, 정형 데이터는 애초에 둘 다 아닌 별도 조회로 처리해야 한다.
- 두 출처를 함께 쓸 때도 컨텍스트 조립·응답 단계에서 출처를 구분해 표시해야 원인 추적과 신뢰도 관리가 가능하다.
