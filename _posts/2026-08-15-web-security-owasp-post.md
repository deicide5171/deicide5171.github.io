## 왜 지금 이 주제인가

이 블로그는 Flutter 앱 개발과 네이버 클라우드 지도 API 연동에서 시작해, PostGIS 기반 공간 데이터, DB 인덱스 내부 구조, 테스트 피라미드, Docker와 CI/CD 파이프라인, 그리고 최근에는 AI 에이전트 프로토콜(MCP, A2A)과 분산 시스템, TCP/TLS 네트워크 심화까지 폭넓게 다뤄왔다. 그런데 이 모든 글이 전제하고 있는 것이 하나 있다. "이 애플리케이션이 안전하게 사용자 입력을 받고, 안전하게 인증하고, 안전하게 데이터를 내보낸다"는 가정이다.

CI/CD로 배포를 자동화하고 DB 인덱스로 조회를 최적화해도, 로그인 폼 하나에 SQL 인젝션 취약점이 있으면 그 데이터베이스 전체가 위험해진다. 지도 API나 AI 에이전트처럼 외부 입력과 외부 서비스를 계속 다뤄온 만큼, 이제는 "이 입력을 얼마나 믿을 수 있는가"라는 질문을 정면으로 다룰 차례다. 그래서 다음 학습 주제로 **OWASP Top 10 기반 웹 애플리케이션 보안 기초**(SQL 인젝션, XSS, 인증/세션 관리, 접근 통제 등)를 추천한다.

네트워크 심화 글에서 TLS로 전송 구간을 암호화하는 법을 다뤘다면, 이번 주제는 그 안전한 통로로 들어온 데이터를 애플리케이션이 어떻게 다뤄야 하는지에 관한 것이다. 즉 전송 계층 보안의 다음 단계로 애플리케이션 계층 보안을 채우는 셈이다.

## 학습 로드맵

| 단계 | 주제 | 왜 필요한가 |
|---|---|---|
| 1 | 입력 검증과 SQL 인젝션 방어 | DB와 상호작용하는 모든 기능의 최소 방어선을 확보한다 |
| 2 | 출력 인코딩과 XSS 방어 | 사용자 입력이 다시 화면에 렌더링되는 모든 지점을 점검한다 |
| 3 | 인증·세션 관리 | 비밀번호 저장, 세션 토큰 관리의 표준 관행을 익힌다 |
| 4 | 접근 통제(Access Control) | 로그인 여부뿐 아니라 "이 리소스에 이 권한이 있는가"를 검증한다 |
| 5 | 보안 헤더·의존성 관리 | CSP·HSTS 같은 브라우저 방어선과 취약 라이브러리 관리 습관을 갖춘다 |

이 순서는 OWASP Top 10의 상위 항목과도 맞닿아 있어, 각 단계를 익히며 실제 공식 문서를 함께 참고하면 이해가 훨씬 빨라진다.

## 핵심 개념: SQL 인젝션과 XSS를 방어적으로 이해하기

**SQL 인젝션**은 사용자 입력이 SQL 쿼리 문자열에 그대로 이어 붙여질 때, 입력값이 쿼리의 구조 자체를 바꿔버리는 취약점이다. 방어의 핵심은 입력을 "쿼리의 일부"가 아니라 "쿼리에 바인딩되는 값"으로 다루는 것이다. 즉 문자열 조합 대신 **파라미터라이즈드 쿼리(prepared statement)**를 쓰고, ORM을 쓰더라도 raw query에 사용자 입력을 직접 문자열 결합하지 않는 것이 원칙이다.

**XSS(Cross-Site Scripting)**는 사용자 입력이 검증 없이 HTML/JS 컨텍스트로 그대로 출력될 때, 입력값이 스크립트로 실행되어버리는 취약점이다. 방어의 핵심은 "출력 시점의 컨텍스트에 맞는 인코딩"이다. HTML 텍스트로 출력할 때, 속성값으로 출력할 때, JS 문자열로 출력할 때 필요한 이스케이프 방식이 각각 다르며, 최신 프레임워크(React, Vue 등)는 기본적으로 이 인코딩을 자동 처리해준다는 점을 이해하는 것이 중요하다.

## 예제: 안전한 쿼리 작성 패턴 (Node.js)

아래는 파라미터라이즈드 쿼리를 사용해 SQL 인젝션을 방어하는 기본 패턴이다. 사용자 입력은 절대 쿼리 문자열에 직접 이어붙이지 않고, 항상 바인딩 파라미터로 전달한다.

```javascript
// 안전한 패턴: 사용자 입력을 파라미터로 바인딩
const { rows } = await pool.query(
  'SELECT id, email FROM users WHERE email = $1 AND status = $2',
  [inputEmail, 'active']
);

// ORM(Sequelize 예시)을 쓸 때도 원칙은 동일하다:
// raw query에 사용자 입력을 문자열로 직접 삽입하지 않는다.
const user = await User.findOne({
  where: { email: inputEmail, status: 'active' },
});
```

문자열을 직접 이어 붙여 쿼리를 만드는 방식은 입력값에 따라 쿼리의 의미 자체가 바뀔 수 있으므로 사용하지 않는다. 파라미터 바인딩을 사용하면 입력값은 항상 "값"으로만 취급되어 쿼리 구조에 영향을 주지 못한다.

## 실무 포인트

- **비밀번호는 반드시 해싱한다**: bcrypt, argon2 같은 느린 해시 함수를 사용하고, 절대 평문이나 단순 해시(MD5, SHA-1 단독)로 저장하지 않는다.
- **세션 쿠키에 보안 플래그를 설정한다**: `HttpOnly`, `Secure`, `SameSite` 속성을 기본으로 켜서 세션 탈취와 CSRF 위험을 줄인다.
- **접근 통제는 매 요청마다 서버에서 재검증한다**: 프론트엔드에서 버튼을 숨기는 것은 UX일 뿐, 실제 권한 검증은 API 레벨에서 반드시 다시 확인한다.
- **의존성 취약점을 정기적으로 스캔한다**: `npm audit`, Dependabot, Snyk 같은 도구를 CI 파이프라인에 넣어 취약한 라이브러리를 조기에 발견한다.
- **에러 메시지에 내부 정보를 노출하지 않는다**: 스택 트레이스나 쿼리 구조가 그대로 사용자에게 보이지 않도록 운영 환경의 에러 처리를 분리한다.

## 3줄 요약

- CI/CD, 인덱스 최적화, 네트워크 심화까지 다뤄온 지식이 실전에서 안전하게 동작하려면 애플리케이션 계층의 보안 기초가 필요하다.
- SQL 인젝션은 파라미터라이즈드 쿼리로, XSS는 컨텍스트에 맞는 출력 인코딩으로 방어하는 것이 핵심이며, 여기에 인증·세션 관리와 접근 통제가 더해져야 한다.
- 비밀번호 해싱, 안전한 쿠키 플래그, 서버 측 권한 재검증, 의존성 스캔부터 작게 시작하는 것을 추천한다.
