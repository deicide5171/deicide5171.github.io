LLM 애플리케이션을 만들다 보면 반드시 겪는 순간이 있다. 모델을 바꾸거나, 시스템 프롬프트에 문장 하나를 추가했더니 다른 부분의 출력 품질이 흔들리는 경우다. 프롬프트는 코드처럼 버전 관리는 되지만 컴파일도, 타입 체크도, 리팩터링 도구도 없는 텍스트 뭉치이기 때문이다. "이 문장을 앞에 넣으면 더 잘 될까?"라는 질문에 답하려면 결국 사람이 직접 프롬프트를 고쳐보고 눈으로 결과를 비교하는 수작업이 반복된다.

DSPy(Declarative Self-improving Python)는 이 문제를 프롬프트 엔지니어링이 아니라 **프로그래밍 문제**로 바꿔서 접근한다. 개발자는 "무엇을 입력받아 무엇을 출력할지"를 시그니처로 선언하고, 좋은 출력이 무엇인지 판별하는 평가 지표(metric)를 정의한다. 실제 프롬프트 문자열과 few-shot 예시 선택은 DSPy의 옵티마이저가 학습 데이터를 돌려가며 자동으로 탐색해 채운다. 프롬프트를 "짜는" 것이 아니라 "컴파일"하는 셈이다.

이 글에서는 DSPy의 핵심 개념인 시그니처·모듈·옵티마이저 구조와, 이것이 기존의 수동 프롬프트 엔지니어링과 어떻게 다른지, 그리고 실무에서 도입할 때 고려할 점을 정리한다.

## 핵심 개념 1: 시그니처와 모듈 — 프롬프트 대신 인터페이스를 선언한다

DSPy에서 프롬프트 작성자가 가장 먼저 하는 일은 프롬프트 문장을 쓰는 것이 아니라 **시그니처(Signature)**를 정의하는 것이다. 시그니처는 "질문과 문맥을 받아 답변을 낸다"처럼 입력·출력 필드와 각 필드의 의미를 선언한 명세로, 함수 시그니처와 비슷한 역할을 한다. 이 시그니처를 `Predict`, `ChainOfThought`, `ReAct` 같은 **모듈**에 감싸면, 모듈이 시그니처에 맞는 실제 프롬프트 텍스트를 내부적으로 생성해 LLM을 호출한다.

핵심은 개발자가 "생각의 사슬을 유도하는 문장을 어떻게 쓸지" 고민할 필요가 없다는 점이다. `ChainOfThought` 모듈을 쓰면 단계적 추론을 유도하는 프롬프트 템플릿은 DSPy가 내부적으로 관리하고, 개발자는 그 위에 여러 모듈을 파이프라인처럼 조합하기만 하면 된다. RAG 파이프라인이라면 "검색 모듈 → 문맥 정리 모듈 → 답변 생성 모듈"을 각각의 시그니처를 가진 모듈로 선언하고 파이썬 코드로 연결하는 식이다.

## 핵심 개념 2: 옵티마이저 — 프롬프트와 예시를 데이터로 탐색한다

DSPy의 차별점은 **옵티마이저(구 버전 명칭은 Teleprompter)**에 있다. 옵티마이저는 학습용 입력 몇 개와 평가 지표 함수를 받아, 모듈이 내부적으로 사용할 지시문 문장과 few-shot 예시 조합을 자동으로 탐색해 점수가 가장 높은 조합을 찾아낸다. 대표적으로 `BootstrapFewShot`은 모델 스스로 생성한 성공적인 추론 과정을 예시로 재활용하고, `MIPROv2`는 지시문 문장 후보와 예시 조합을 베이지안 탐색으로 함께 최적화한다.

이 과정을 "컴파일(compile)"이라고 부르는 이유는, 개발 중에는 시그니처와 파이프라인 구조만 신경 쓰다가 배포 직전에 옵티마이저를 한 번 돌려 최적화된 프롬프트 세트를 산출물로 얻기 때문이다. 모델을 GPT 계열에서 다른 모델로 바꾸는 경우에도, 프롬프트를 손으로 다시 쓰는 대신 같은 학습 데이터로 재컴파일하면 새 모델에 맞는 프롬프트 조합이 다시 탐색된다.

| 구분 | 수동 프롬프트 엔지니어링 | DSPy |
|---|---|---|
| 산출물 | 프롬프트 문자열 | 시그니처 + 파이프라인 코드 |
| 실제 프롬프트 텍스트 | 개발자가 직접 작성 | 옵티마이저가 탐색해 생성 |
| 모델 교체 시 | 프롬프트 재작성·재튜닝 | 같은 데이터로 재컴파일 |
| 품질 검증 | 눈으로 비교 | 평가 지표 함수로 정량 비교 |
| 버전 관리 대상 | 프롬프트 텍스트 | 코드 + 컴파일된 프롬프트 아티팩트 |

## 핵심 개념 3: 평가 지표 설계가 성패를 가른다

옵티마이저가 아무리 정교해도 **평가 지표(metric)**가 부실하면 엉뚱한 방향으로 최적화된다. 지표는 "예측 출력과 정답(또는 정답이 없다면 판정 기준)을 받아 점수를 반환하는 함수"로, 단순 문자열 일치부터 LLM-as-judge까지 자유롭게 구현할 수 있다. 예를 들어 요약 태스크라면 ROUGE 유사 지표만으로는 "그럴듯하지만 사실과 다른 요약"을 걸러내지 못하므로, 원문에 없는 사실이 포함되면 감점하는 별도 판정 로직을 지표에 넣어야 한다.

실무에서 흔한 실수는 지표를 정의하지 않고 few-shot 예시 개수만 늘려서 옵티마이저를 돌리는 것이다. 지표가 실제 목표(정확성, 톤, 형식 준수 등)를 제대로 반영하지 못하면 옵티마이저는 그 지표에서만 높은 점수를 내는 프롬프트를 찾아내고, 실제 프로덕션 품질과는 괴리가 생긴다. LLM Eval 프레임워크를 이미 구축했다면 그 골든 데이터셋과 판정 로직을 DSPy 지표 함수로 그대로 재사용하는 것이 가장 안전한 시작점이다.

## 예제: 간단한 RAG 파이프라인 컴파일

```python
import dspy

# 1. 시그니처 정의 — 입력/출력 필드만 선언, 프롬프트 문장은 없음
class GenerateAnswer(dspy.Signature):
    """주어진 문맥만 근거로 질문에 답하라. 문맥에 없으면 모른다고 답하라."""
    context = dspy.InputField(desc="검색된 관련 문서")
    question = dspy.InputField()
    answer = dspy.OutputField(desc="한두 문장의 간결한 답변")

# 2. 모듈 파이프라인 정의
class RAG(dspy.Module):
    def __init__(self, retriever):
        super().__init__()
        self.retrieve = retriever
        self.generate = dspy.ChainOfThought(GenerateAnswer)

    def forward(self, question):
        context = self.retrieve(question).passages
        return self.generate(context=context, question=question)

# 3. 평가 지표 — 문맥 근거 없는 답변은 감점
def metric(example, pred, trace=None):
    grounded = pred.answer_supported_by(example.context)  # 사실성 검증 로직
    return 1.0 if grounded and example.answer in pred.answer else 0.0

# 4. 옵티마이저로 컴파일 — 학습 예시 30~50개면 충분히 시작 가능
optimizer = dspy.MIPROv2(metric=metric, auto="medium")
compiled_rag = optimizer.compile(RAG(retriever=my_retriever), trainset=train_examples)

compiled_rag.save("compiled_rag_v1.json")  # 최적화된 프롬프트·예시를 아티팩트로 저장
```

## 실무 포인트

- **작은 학습 세트로 시작한다**: 옵티마이저는 학습 예시 수십 개만으로도 효과를 낸다. 처음부터 수백 개를 모으려다 도입 자체가 미뤄지는 것보다, 30~50개로 먼저 컴파일해 보고 점수 곡선을 보며 늘리는 편이 낫다.
- **컴파일 결과물은 코드와 별도로 버전 관리한다**: `compile()`의 산출물(최적화된 프롬프트·예시 조합)은 JSON으로 저장되므로, 이를 Git에 커밋하거나 모델 아티팩트처럼 버전을 매겨 배포 파이프라인에 태운다. 재컴파일할 때마다 결과가 달라질 수 있으므로 회귀 테스트 없이 무작정 교체하지 않는다.
- **지표 함수부터 리뷰한다**: 옵티마이저 결과가 이상하면 먼저 의심할 곳은 프롬프트가 아니라 평가 지표다. 지표가 실제 원하는 품질(사실성, 형식, 톤)을 제대로 반영하는지부터 사람이 검토해야 한다.

## 3줄 요약

- DSPy는 프롬프트 문자열을 직접 쓰는 대신 입출력 시그니처와 모듈 파이프라인을 코드로 선언하고, 실제 프롬프트는 옵티마이저가 학습 데이터로 탐색해 컴파일한다.
- `BootstrapFewShot`, `MIPROv2` 같은 옵티마이저는 지시문 문장과 few-shot 예시 조합을 평가 지표 점수 기준으로 자동 탐색하며, 모델을 바꿔도 같은 데이터로 재컴파일하면 된다.
- 옵티마이저의 품질은 결국 평가 지표 설계에 좌우되므로, 지표가 실제 목표(사실성·형식 준수)를 반영하지 못하면 프롬프트를 아무리 최적화해도 프로덕션 품질과는 괴리가 생긴다.
