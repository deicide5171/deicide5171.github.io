## 왜 지금 데드락 탐지 원리를 다시 봐야 하는가

애플리케이션에서 `could not serialize access due to deadlock` 같은 에러를 만나면 대부분 "재시도 로직을 추가하면 되겠지"로 넘어가고 끝낸다. 하지만 왜 하필 그 트랜잭션이 실패로 선택됐는지, DB가 애초에 두 트랜잭션이 서로 영원히 기다리고 있다는 것을 어떻게 알아냈는지를 이해하지 못하면, 데드락이 반복적으로 발생하는 근본 원인(락 획득 순서의 불일치)을 못 찾고 재시도로만 덮어버리는 경우가 많다. DB는 무한정 기다리다가 타임아웃되는 게 아니라, 능동적으로 락 대기 상태를 그래프로 구성해 순환(cycle)이 생기는 순간을 실시간으로 찾아낸다. 이 탐지 메커니즘을 이해하면 데드락을 사후에 처리하는 것을 넘어, 애초에 발생하지 않도록 설계하는 감각을 얻을 수 있다.

## 핵심 개념 1 — Wait-For Graph: 트랜잭션 간 대기 관계를 그래프로 표현하기

Wait-For Graph는 트랜잭션을 노드로, "트랜잭션 A가 트랜잭션 B가 쥔 락을 기다린다"는 관계를 A에서 B로 향하는 방향성 엣지로 표현한 그래프다. 트랜잭션 A가 행 X에 대한 락을 요청했는데 이미 트랜잭션 B가 그 락을 쥐고 있다면, A→B 엣지가 그래프에 추가된다. 데드락은 정확히 이 그래프에 순환(cycle)이 생기는 순간과 일치한다 — A가 B를 기다리고, B가 다시 A를 기다리면 A→B→A라는 사이클이 만들어지고, 이 사이클 안의 트랜잭션들은 누구도 먼저 락을 풀지 못하므로 영원히 대기하게 된다. DB의 락 매니저는 새로운 대기 관계가 추가될 때마다 이 그래프에 사이클이 생기는지 확인하는 방식으로 데드락을 실시간에 가깝게 탐지한다.

## 핵심 개념 2 — 사이클이 발견되면 누구를 희생시킬 것인가

사이클을 발견했다고 끝이 아니다. 사이클에 참여한 트랜잭션 중 하나를 강제로 중단(rollback)시켜야 나머지가 진행될 수 있는데, 이 "희생자(victim)"를 고르는 기준이 DB마다 다르다. PostgreSQL은 비교적 단순하게 데드락을 탐지한 트랜잭션(또는 그 탐지를 유발한 요청) 자체를 롤백시키는 경향이 있고, 다른 시스템은 이미 수행한 작업량이 적은 트랜잭션, 또는 롤백 시 영향받는 하위 트랜잭션이 적은 것을 우선적으로 희생시키는 등 더 정교한 비용 기반 전략을 쓴다. 어떤 기준이든 핵심은 "누군가는 반드시 희생되어야 나머지가 살 수 있다"는 것이며, 애플리케이션은 이 희생을 특정 에러 코드로 통보받아 재시도할 책임을 진다.

| 항목 | 설명 |
|---|---|
| Wait-For Graph 노드 | 트랜잭션(또는 세션) |
| Wait-For Graph 엣지 | "A가 B의 락을 기다린다"는 방향성 관계 |
| 데드락 판정 조건 | 그래프에 순환(cycle)이 존재 |
| 해소 방법 | 사이클 내 트랜잭션 중 하나를 강제 롤백(victim 선정) |

## 예제 — 락 획득 순서 불일치로 데드락을 재현하기

```sql
-- 트랜잭션 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 이 시점에서 트랜잭션 2가 id=2를 먼저 잠근 뒤 id=1을 기다리게 하면 데드락 발생
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- 트랜잭션 2 (트랜잭션 1과 반대 순서로 락을 건다)
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
COMMIT;

-- 결과: 두 트랜잭션이 서로 상대가 쥔 행의 락을 기다리며 Wait-For Graph에 사이클 형성
-- ERROR: deadlock detected
-- DETAIL: Process 1234 waits for ShareLock on transaction 5678; ...
```

두 트랜잭션이 같은 두 행을 다른 순서로 잠그려 할 때 데드락이 발생하는 이 패턴이 실무에서 가장 흔한 원인이다.

## 실무 포인트

- **여러 행을 갱신하는 트랜잭션은 항상 동일한 순서로 락을 획득하도록 코드를 정렬하라.** 예를 들어 계좌 이체 로직이라면 항상 더 작은 ID의 행부터 잠그도록 강제하면, 위 예제 같은 순환 대기 자체가 구조적으로 발생하지 않는다.
- **데드락 에러는 반드시 애플리케이션 레벨에서 재시도하도록 처리하라.** 데드락으로 롤백된 트랜잭션은 데이터 정합성 문제가 아니라 단순히 타이밍 문제이므로, 짧은 backoff 후 동일 트랜잭션을 재시도하는 것이 일반적으로 안전하고 올바른 대응이다.
- **데드락 로그를 주기적으로 모니터링하라.** PostgreSQL의 `log_lock_waits`나 데드락 상세 로그를 분석하면 어떤 트랜잭션 조합에서 반복적으로 데드락이 발생하는지 파악해, 근본적인 락 순서 문제를 찾아 고칠 수 있다.

## 마무리 요약

- 데드락은 DB가 타임아웃으로 어림짐작하는 것이 아니라, Wait-For Graph에 순환이 생기는 순간을 실시간으로 탐지해 판정한다.
- 사이클이 발견되면 그 안의 트랜잭션 중 하나가 희생자로 선정돼 강제 롤백되며, 희생자 선정 기준은 DB마다 다르다.
- 여러 행을 갱신하는 로직에서 항상 동일한 순서로 락을 획득하도록 강제하면 데드락의 근본 원인인 순환 대기 자체를 예방할 수 있다.
