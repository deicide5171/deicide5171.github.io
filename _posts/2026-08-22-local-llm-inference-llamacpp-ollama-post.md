클라우드 LLM API는 편리하지만 두 가지 문제에서 자유롭지 못하다. 하나는 비용이다. 토큰 단위 과금은 프로토타입 단계에서는 부담이 적어 보여도, 반복 실험이나 대량 배치 작업으로 이어지면 빠르게 누적된다. 다른 하나는 데이터 프라이버시다. 사내 문서나 개인정보가 섞인 입력을 외부 API로 계속 보내는 것이 부담스러운 조직도 적지 않다. 이 두 가지가 겹치면서 "모델을 아예 내 컴퓨터 안에서 돌릴 수는 없을까"라는 질문이 자연스럽게 나오게 됐다.

이 질문에 실용적인 답을 준 것이 llama.cpp다. 원래 메타의 LLaMA 모델을 순수 C/C++로 재구현해 GPU 없이도 노트북이나 데스크톱 CPU에서 추론이 가능하게 만든 프로젝트로 시작했고, 이후 다양한 오픈소스 모델과 양자화 포맷을 지원하며 로컬 추론의 사실상 표준 엔진 중 하나로 자리 잡았다. 다만 llama.cpp를 직접 빌드하고 커맨드라인 옵션을 맞춰가며 쓰는 것은 진입 장벽이 있는데, 이 부분을 감싸 "모델 하나 받아서 바로 대화하기"를 가능하게 한 것이 Ollama다.

이 글에서는 llama.cpp가 로컬 추론을 가능하게 만든 핵심 메커니즘과, Ollama가 그 위에 어떤 구조를 얹어 사용성을 높였는지, 그리고 실제로 로컬에서 모델을 돌릴 때 고려해야 할 하드웨어 조건을 정리한다.

## 핵심 개념 1: llama.cpp의 CPU/GPU 혼합 추론과 GGUF 양자화 포맷

llama.cpp의 출발점은 "GPU가 없어도 돌아가야 한다"는 제약이었다. 이를 위해 행렬 연산을 CPU 명령어 집합에 맞춰 최적화하고, 필요한 경우 일부 레이어만 GPU로 오프로드하는 방식을 지원한다. 즉 전체 모델을 GPU 메모리에 다 올릴 필요 없이, VRAM이 허용하는 만큼만 레이어를 GPU에 올리고 나머지는 CPU와 시스템 RAM에서 처리하는 혼합 실행이 가능하다. 이 덕분에 고사양 GPU가 없는 환경에서도 속도는 느리더라도 모델을 아예 돌리지 못하는 상황은 피할 수 있다.

이 구조를 뒷받침하는 것이 GGUF(GPT-Generated Unified Format)라는 파일 포맷이다. GGUF는 모델 가중치와 함께 토크나이저, 메타데이터를 하나의 파일에 담고, 4비트·5비트·8비트 등 다양한 양자화 수준을 지원한다. 이전 포맷인 GGML의 뒤를 잇는 것으로, 양자화된 가중치를 CPU 친화적인 메모리 레이아웃으로 배치해 로딩과 추론 속도를 함께 개선한 것이 특징이다. 사용자 입장에서는 원하는 양자화 수준(예: Q4_K_M, Q8_0 등 접미사)에 따라 파일 하나만 받으면 되므로, 별도의 변환 파이프라인을 직접 구성할 필요가 크게 줄었다.

## 핵심 개념 2: Ollama가 모델 다운로드·서빙·API 노출을 감싸는 구조

Ollama는 내부적으로 llama.cpp 계열 추론 엔진을 사용하면서, 그 위에 세 가지 계층을 추가로 얹은 도구로 볼 수 있다. 첫째는 모델 배포다. Docker의 이미지 레지스트리와 비슷한 개념으로 모델 레지스트리를 두고, `ollama pull` 명령 한 줄로 원하는 모델의 이미 양자화된 GGUF 가중치를 받아올 수 있게 했다. 둘째는 서빙이다. Ollama는 로컬에 백그라운드 서버 프로세스를 띄워 모델을 메모리에 상주시키고, 여러 요청을 순차적으로 처리하거나 필요에 따라 모델을 스왑하는 역할을 담당한다.

셋째는 API 노출이다. Ollama는 로컬 HTTP 엔드포인트를 열어 REST API 형태로 추론 요청을 받는데, 이 인터페이스가 OpenAI API와 유사한 형태를 취하고 있어 기존에 OpenAI SDK로 작성된 코드를 큰 수정 없이 로컬 엔드포인트로 돌리는 것도 어느 정도 가능하다. 결과적으로 사용자는 llama.cpp의 빌드 옵션이나 GGUF 파일 경로를 직접 신경 쓰지 않고, Modelfile이라는 선언적 설정 파일로 시스템 프롬프트나 파라미터를 조정하며 모델을 쓸 수 있게 된다.

## 핵심 개념 3: 로컬 추론 시 하드웨어 요구사항(RAM/VRAM) 고려사항

로컬 LLM 추론에서 가장 먼저 부딪히는 벽은 메모리다. 양자화된 모델이라 해도 파라미터 수에 비례해 최소한의 RAM 또는 VRAM이 필요하며, 여기에 컨텍스트 길이가 늘어날수록 KV 캐시가 추가로 메모리를 소비한다. 같은 파라미터 수의 모델이라도 4비트 양자화와 8비트 양자화는 필요한 메모리 양이 다르고, 이 차이가 그대로 "내 컴퓨터에서 돌아가는지 여부"를 가르는 경우가 많다.

GPU가 있다면 VRAM 용량 안에 모델과 KV 캐시가 얼마나 들어가는지가 관건이고, GPU가 없거나 VRAM이 부족하다면 CPU 추론 속도와 시스템 RAM 대역폭이 체감 성능을 좌우한다. 다만 구체적으로 어떤 모델이 어느 정도의 RAM/VRAM에서 어떤 속도로 돌아가는지는 모델 아키텍처, 양자화 수준, 하드웨어 세대에 따라 편차가 크므로, 특정 수치를 일반화하기보다는 실제 사용하려는 모델과 환경에서 직접 확인하는 편이 안전하다.

## 예제

Ollama를 설치한 뒤 모델을 받아 실행하는 기본 흐름은 다음과 같다.

```bash
# 모델 다운로드 및 대화형 실행
ollama pull llama3
ollama run llama3
```

로컬 서버가 열려 있는 상태에서는 REST API로도 호출할 수 있다.

```bash
curl http://localhost:11434/api/generate -d '{
  "model": "llama3",
  "prompt": "로컬 LLM 추론이란 무엇인가?",
  "stream": false
}'
```

두 예시 모두 모델명은 예시일 뿐이며, 실제 사용 시에는 Ollama 라이브러리에 등록된 모델명과 태그를 확인해 지정해야 한다.

## 실무 포인트

- **모델 크기별 성능/정확도 트레이드오프를 감안해야 한다.** 파라미터 수가 작은 모델일수록 로컬에서 돌리기 쉽지만, 복잡한 추론이나 긴 문맥 이해에서는 대형 모델 대비 응답 품질이 떨어질 수 있다. 어떤 크기의 모델을 쓸지는 실제 사용하려는 태스크의 난이도와 로컬 하드웨어 제약을 함께 고려해 정해야 한다.
- **상용 API 대비 한계도 분명히 존재한다.** 최신 대형 모델이 제공하는 수준의 추론 능력이나 멀티모달 지원을 로컬 환경에서 동일하게 재현하기는 어려운 경우가 많고, 동시 요청 처리량이나 안정적인 SLA 측면에서도 상용 API가 유리한 경우가 일반적이다. 로컬 추론은 비용·프라이버시 이점과 성능·편의성 사이의 트레이드오프로 접근하는 것이 현실적이다.
- **버전과 생태계 변화가 빠르다.** llama.cpp와 Ollama 모두 활발히 개발되는 프로젝트이므로, 지원 모델 목록이나 API 세부 사항이 바뀔 수 있다. 실제 도입 전에는 공식 문서에서 최신 정보를 확인하는 과정이 필요하다.

## 3줄 요약

- llama.cpp는 GPU 없이도 CPU/GPU 혼합 방식으로 LLM을 돌릴 수 있게 하고, GGUF 포맷으로 다양한 수준의 양자화된 가중치를 다룬다.
- Ollama는 모델 다운로드, 로컬 서빙, OpenAI 유사 API 노출을 하나로 감싸 llama.cpp 기반 추론을 손쉽게 쓸 수 있게 해주는 도구다.
- 로컬 추론은 모델 크기에 따른 RAM/VRAM 요구량과 성능·정확도 트레이드오프를 함께 고려해야 하며, 상용 API 대비 한계도 존재한다.
