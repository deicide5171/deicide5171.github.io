RAG 파이프라인을 구축할 때 임베딩 모델 선택은 종종 "MTEB 리더보드에서 점수가 제일 높은 걸로 하자"로 끝난다. 벡터 검색 품질을 좌우하는 핵심 컴포넌트인데도 의외로 가장 가볍게 결정되는 경우가 많다. 문제는 MTEB 같은 공개 벤치마크가 일반 도메인 텍스트, 주로 영어 위주 데이터셋으로 구성돼 있어서, 실제 서비스가 다루는 한국어 고객 상담 로그나 사내 용어가 잔뜩 섞인 기술 문서에서는 리더보드 순위와 실제 검색 품질이 따로 노는 경우가 드물지 않다는 점이다.

임베딩 모델 선택은 "가장 성능 좋은 모델"이 아니라 "우리 데이터와 쿼리 분포에 가장 잘 맞는 모델"을 찾는 문제에 가깝다. 이 글에서는 임베딩 모델을 고를 때 실제로 따져야 할 세 가지 축 — 도메인 적응, 다국어 처리, 차원 수 — 을 정리한다.

## 핵심 개념 1: 도메인 적응 — 범용 벤치마크와 실제 데이터의 간극

임베딩 모델은 사전학습 데이터의 분포에 강하게 영향을 받는다. 위키백과와 웹 텍스트로 학습된 범용 모델은 일반 상식 문장의 의미 유사도는 잘 잡아내지만, 법률·의료·금융처럼 전문 용어 밀도가 높은 도메인에서는 표면적으로 비슷한 단어를 가진 문장들을 실제 의미와 무관하게 가깝다고 판단하는 실수를 저지르기 쉽다. 예를 들어 "담보"와 "담보권"처럼 법률 도메인에서는 뜻이 크게 갈리는 단어쌍을 범용 임베딩은 거의 동일하게 취급할 수 있다.

이 문제를 완화하는 방법은 크게 두 가지다. 하나는 도메인 데이터로 파인튜닝된 임베딩 모델(또는 자체 파인튜닝)을 쓰는 것이고, 다른 하나는 임베딩 자체는 범용 모델을 쓰되 검색 결과를 도메인 특화 리랭커(reranker)로 재정렬하는 것이다. 파인튜닝은 초기 투자가 크지만 검색 자체의 recall을 근본적으로 높이고, 리랭커 조합은 구현이 간단하지만 임베딩 단계에서 이미 관련 문서가 top-k 밖으로 밀려나면 리랭커도 구제할 수 없다는 한계가 있다.

## 핵심 개념 2: 다국어 처리 — 언어별 성능 편차를 확인한다

"multilingual" 표기가 붙은 임베딩 모델이라고 모든 언어를 균등하게 잘 처리하는 것은 아니다. 대부분의 다국어 임베딩 모델은 학습 데이터에서 영어와 중국어 비중이 압도적으로 높고, 한국어 같은 언어는 상대적으로 데이터가 적어 같은 모델이라도 언어별 검색 품질 편차가 크다. 특히 교차 언어 검색(한국어 쿼리로 영어 문서 검색)을 지원해야 하는 서비스라면, 단일 언어 성능뿐 아니라 언어 간 임베딩 공간이 실제로 잘 정렬돼 있는지를 별도로 검증해야 한다.

| 확인 항목 | 확인 방법 |
|---|---|
| 한국어 단일 언어 성능 | 한국어 벤치마크(KorSTS, KLUE-STS 등) 또는 자체 골든셋으로 검증 |
| 교차 언어 정렬 | 같은 의미의 한/영 문장쌍 임베딩 간 코사인 유사도 확인 |
| 토크나이저의 한국어 처리 | 조사·어미 분리로 의미 단위가 과도하게 쪼개지지 않는지 확인 |
| 도메인 혼용 시 성능 저하 | 한국어 문서 안에 영어 전문용어가 섞인 실제 케이스로 검증 |

## 핵심 개념 3: 차원 수 — 크다고 항상 좋은 건 아니다

임베딩 차원이 높을수록 더 많은 의미 정보를 담을 수 있다는 직관은 어느 정도까지만 맞다. 차원이 커지면 벡터 DB의 저장 공간과 검색 연산량이 그대로 늘어나고, 학습 데이터 규모 대비 차원이 지나치게 크면 오히려 노이즈에 과적합되어 실제 검색 품질이 떨어지는 경우도 있다. 최근에는 Matryoshka Representation Learning(MRL) 기법으로 하나의 임베딩 모델이 여러 차원(예: 1536, 768, 256)으로 잘라 써도 성능이 크게 떨어지지 않도록 학습된 모델들도 나와 있어, 저장 비용과 품질 사이의 트레이드오프를 배포 후에도 유연하게 조정할 수 있게 됐다.

## 실무 포인트

- **리더보드 순위보다 자체 골든셋을 먼저 만든다**: 골든셋 구축이 번거롭다는 이유로 생략하면, 모델 교체 후 검색 품질이 실제로 좋아졌는지 나빠졌는지조차 판단할 근거가 없어진다. 수십~수백 개 규모라도 실제 쿼리-정답 문서 쌍을 만들어 두는 것이 장기적으로 훨씬 저렴하다.
- **임베딩 모델 교체는 재인덱싱 비용을 동반한다**: 벡터 차원이나 모델이 바뀌면 기존에 저장된 모든 벡터를 다시 계산해야 한다. 이 비용을 과소평가해 잦은 모델 교체를 반복하면 실제로는 성능 개선보다 재인덱싱 리스크가 더 커질 수 있다.
- **쿼리와 문서의 길이 분포 차이를 확인한다**: 일부 임베딩 모델은 짧은 쿼리와 긴 문서를 같은 방식으로 인코딩하면 성능이 떨어진다. 쿼리·문서 각각에 다른 프리픽스나 인코딩 방식을 요구하는 모델(예: `query:`, `passage:` 프리픽스)인지 반드시 문서를 확인한다.

## 3줄 요약

- 임베딩 모델은 리더보드 점수가 아니라 자체 도메인 데이터와 쿼리 분포로 만든 골든셋 평가로 최종 선택해야 한다.
- 다국어 모델은 언어별 성능 편차가 크므로 한국어 단일 성능뿐 아니라 교차 언어 정렬까지 별도로 검증해야 한다.
- 차원 수는 무조건 클수록 좋은 것이 아니며, Matryoshka 학습 모델처럼 저장 비용과 품질을 배포 후에도 조정 가능한 선택지를 고려할 수 있다.
