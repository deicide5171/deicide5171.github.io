## 결제 버튼을 두 번 누르면 두 번 결제되나

사용자가 결제 버튼을 눌렀는데 응답이 늦어 다시 눌렀다면? 또는 네트워크 오류로 클라이언트가 자동 재시도했다면? 같은 요청이 서버에 두 번 도착해 결제가 두 번 될 수 있다. **멱등성(Idempotency)**은 "같은 요청을 여러 번 보내도 결과가 한 번 처리한 것과 같다"는 성질이다. 멱등성이 보장되면 중복 요청이 와도 안전하다.

## HTTP 메서드의 멱등성

| 메서드 | 멱등한가 | 이유 |
|---|---|---|
| GET | 예 | 여러 번 조회해도 상태 안 바뀜 |
| PUT | 예 | 같은 값으로 여러 번 덮어써도 결과 동일 |
| DELETE | 예 | 여러 번 삭제해도 "없음" 상태 동일 |
| POST | 아니오 | 호출할 때마다 새로 생성될 수 있음 |

`POST`는 기본적으로 멱등하지 않다. 그래서 결제·주문 생성 같은 POST 작업에 중복 방지가 특히 중요하다.

## 멱등성 키로 중복 막기

```text
1. 클라이언트가 요청마다 고유한 "멱등성 키"를 만들어 함께 보냄
   (예: Idempotency-Key: abc-123)
2. 서버는 그 키로 이미 처리한 요청인지 확인
3. 처음 보는 키면 -> 처리하고 결과를 키와 함께 저장
4. 이미 본 키면 -> 다시 처리하지 않고 저장된 결과를 그대로 반환

-> 같은 키로 100번 와도 실제 처리는 한 번, 결과는 항상 동일
```

## 실무 포인트

- **결제·주문처럼 돈이나 상태가 바뀌는 작업에는 멱등성 키가 거의 필수다.** 네트워크는 언제든 불안정할 수 있고 클라이언트는 재시도하므로, 중복 요청은 "혹시 오는 것"이 아니라 "반드시 오는 것"으로 가정하고 설계해야 한다.
- **멱등성 키에는 만료 시간을 두는 것이 일반적이다.** 처리한 키를 영원히 저장할 수는 없으므로, 일정 기간(예: 24시간) 후 정리한다. 재시도가 그 기간 안에 일어난다는 전제다.
- **재시도 로직과 함께 생각해야 한다.** 클라이언트가 재시도할 때 매번 새 키를 만들면 중복 방지가 안 된다. "같은 논리적 요청"은 재시도해도 같은 키를 유지해야 멱등성이 성립한다.

## 마무리 요약

- 멱등성은 같은 요청을 여러 번 보내도 결과가 한 번 처리한 것과 같은 성질이다.
- GET·PUT·DELETE는 기본적으로 멱등하지만 POST는 그렇지 않아 중복 방지가 필요하다.
- 멱등성 키로 이미 처리한 요청인지 확인해 중복을 막으며, 결제·주문 같은 작업에는 거의 필수다.
