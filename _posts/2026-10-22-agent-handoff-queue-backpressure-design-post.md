## 도입

"조사 에이전트가 자료를 모으면, 바로 작성 에이전트가 이어받아서 보고서를 써주세요." 멀티에이전트 파이프라인을 처음 짤 때 가장 직관적인 구현은 A의 코드 안에서 B를 함수처럼 호출하는 것이다. 코드도 짧고, 디버깅도 한 호출 스택 안에서 끝난다. 문제는 이 직관이 두 에이전트를 완전히 결합시킨다는 데 있다. B가 느려지면 A는 블로킹되고, B가 실패하면 A가 이미 한 작업까지 함께 유실된다.

더 나쁜 경우는 재시도다. LLM 호출 하나가 레이트 리밋에 걸려 재시도를 시작하면, 그 호출을 직접 물고 있던 상위 에이전트의 재시도 로직까지 함께 발동해 요청량이 기하급수적으로 불어난다. 2026년 초 공개된 한 분석은 초당 5건을 처리하던 파이프라인이 재시도 연쇄로 초당 50건의 요청을 쏟아내는 사례를 "레이트 리밋 캐스케이드"로 설명했다. 7개 오픈소스 멀티에이전트 프레임워크의 1,600여 개 실행 트레이스를 분석한 MAST 연구(2025)는 실패 원인 대부분이 모델 한계가 아니라 시스템 설계 문제와 에이전트 간 정합성 붕괴에서 비롯된다고 지적하는데, 누가 누구를 어떻게 호출하는지의 설계가 바로 그 핵심 변수다. AWS가 2025년 말 공개한 Well-Architected 에이전틱 AI 렌즈 역시 "즉각적인 응답이 꼭 필요한 경우를 제외하면 비동기 메시징을 기본값으로 하라"고 명시하며, 에이전트 간 직접 호출을 안티패턴으로 지목한다.

## 전체 시스템에서의 위치

같은 "A가 끝나면 B가 이어받는다"는 요구가, 전송 계층을 어떻게 짜느냐에 따라 완전히 다른 장애 전파 경로를 만든다.

<img src="/assets/images/posts/2026-10-22-agent-handoff-queue-backpressure-design-1.svg" alt="에이전트 간 직접 호출 구조와 큐를 끼운 비동기 핸드오프 구조의 장애 전파 범위를 비교한 구조도" style="width:100%;">

- **직접 호출 구조**: A가 B를 동기 호출한다. B의 지연·실패·재시도가 호출 스택을 타고 그대로 A에 전달된다. A 위에 오케스트레이터나 사용자 요청이 있다면 그 지연까지 함께 전파된다.
- **큐 기반 구조**: A는 작업 완료를 큐(SQS·Kafka 등)에 메시지로 적재하고 끝난다. B는 자신의 속도로 큐를 소비한다. B가 느려지거나 일시적으로 멈춰도 메시지는 큐에 쌓일 뿐 A는 영향받지 않는다. 메시지는 전체 데이터가 아니라 참조(ID, 경로)만 담아 페이로드를 가볍게 유지한다.
- **상태 저장소**: 에이전트 자체는 상태를 들고 있지 않는 무상태 워커로 둔다. "지금 몇 단계까지 진행됐는가"는 별도 DB에 기록하고, 큐 메시지가 중복 전달돼도 소비자가 단계를 먼저 확인해 중복 실행을 막는다(멱등 처리).

## 선택의 트레이드오프

| 접근 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| 직접 함수 호출(동기) | 구현 단순, 지연 최소, 디버깅 쉬움 | B의 장애·재시도가 A까지 전파, 백프레셔 없음 | 호출 체인이 짧고 각 에이전트가 빠르게 끝나는 단순 파이프라인 |
| 큐 기반 비동기 핸드오프 | 장애 격리, 자연스러운 백프레셔, 재처리·DLQ로 복구 용이 | 전체 지연 증가, 운영 복잡도(큐 인프라·모니터링) 추가 | 조직 경계·서비스 경계를 넘나드는 핸드오프, 처리 시간이 들쭉날쭉한 작업 |
| 하이브리드(사용자 응답은 동기, 후속 작업은 비동기 큐) | 체감 응답성과 안정성을 동시에 확보 | 경계 설계와 상태 동기화가 더 복잡함 | 사용자에게 즉시 확인 응답을 주고 나머지는 백그라운드로 처리하는 경우 |
| 공유 블랙보드(중앙 상태 저장소를 통한 느슨한 결합) | 에이전트 간 결합도 최소화 | 상태 관리 자체가 새로운 난제, 경쟁 조건 위험 | 다수 에이전트가 같은 작업 맥락을 비동기로 함께 갱신하는 경우 |

판단 기준은 "B의 실패가 A의 실패여도 괜찮은가"다. 괜찮다면 직접 호출로 충분하다. 반대로 B가 외부 LLM API처럼 지연이 들쭉날쭉하거나 레이트 리밋에 걸리기 쉬운 자원을 쓴다면, 그 변동성을 A까지 전달하지 않도록 큐 한 겹을 끼워 넣어야 한다.

## 실제 프로젝트 진행 순서

1. **먼저 직접 호출로 파이프라인을 완성한다.** 핸드오프 지점이 어디인지, 각 단계가 얼마나 걸리는지부터 파악해야 어디에 큐가 필요한지 판단할 수 있다.
2. **지연·실패가 전파되는 지점을 찾는다.** 특히 외부 LLM API 호출이나 재시도가 걸리기 쉬운 단계를 표시해둔다.
3. **그 지점부터 큐를 끼워 넣는다.** 전체를 한 번에 큐 기반으로 바꾸지 않는다. 장애 격리가 실제로 필요한 경계부터 시작한다.
4. **소비자를 멱등하게 만든다.** 메시지를 처리하기 전에 "이 작업이 이미 이 단계를 지났는가"를 먼저 확인하는 로직을 넣어, 재전달된 메시지가 중복 실행되지 않게 한다.
5. **데드레터 큐(DLQ)와 재처리 경로를 마련한다.** 계속 실패하는 메시지를 큐에서 격리해 전체 소비를 막지 않게 한다.
6. **백프레셔 지표를 계측한다.** 큐 길이, 소비 지연, 재시도율을 대시보드로 노출해 특정 에이전트가 쌓아두는 작업량이 보이게 한다.

```python
# 직접 호출 — A가 B의 실패·지연을 그대로 떠안는다
def run_pipeline(task):
    research = research_agent.run(task)
    report = writer_agent.run(research)  # writer가 느려지면 여기서 블로킹
    return report

# 큐 기반 핸드오프 — A는 적재만 하고 끝난다
def run_research_stage(task):
    research = research_agent.run(task)
    save_result(task.id, "research", research)
    queue.publish("writer-stage", {"task_id": task.id})

def writer_worker(message):
    task_id = message["task_id"]
    if get_stage(task_id) != "research_done":
        return  # 중복 전달 방어
    research = load_result(task_id, "research")
    report = writer_agent.run(research)
    save_result(task_id, "writer", report)
```

## 실무 포인트

- 큐를 끼운다고 메시지 순서가 자동으로 보장되지는 않는다. 재시도나 다중 컨슈머 환경에서는 순서가 깨질 수 있으므로, 순서가 중요한 흐름이라면 파티션 키나 로그 기반 큐(Kafka 등)로 순서 보장 범위를 명확히 정의한다.
- 직접 호출을 쓰더라도 최소한의 백프레셔는 필요하다. 동시 실행 가능한 하위 에이전트 수를 제한하는 세마포어만 추가해도 재시도 폭주를 어느 정도 억제할 수 있다.
- 큐 기반 구조는 지연을 완전히 없애주지 않는다. 사용자가 즉시 응답을 기대하는 구간은 동기로 남기고, 그 뒤에 이어지는 후속 처리만 비동기로 분리하는 하이브리드 경계 설정이 실무에서 가장 흔하다.

## 마무리

- 에이전트 간 직접 호출은 구현은 쉽지만 지연·실패·재시도를 그대로 전파시켜, 레이트 리밋 캐스케이드 같은 연쇄 장애의 원인이 된다.
- AWS Well-Architected 에이전틱 AI 렌즈는 즉각 응답이 필요한 경우를 제외하면 비동기 메시징을 기본값으로 권고하며, 직접 호출을 안티패턴으로 분류한다.
- 전환은 한 번에 전체를 바꾸는 게 아니라, 지연이 들쭉날쭉한 경계부터 큐를 끼우고 소비자를 멱등하게 만드는 순서로 진행한다.
