## 왜 이벤트 스키마 변경이 위험한가

이벤트 기반 아키텍처의 매력은 프로듀서와 컨슈머가 서로를 몰라도 된다는 느슨한 결합이지만, 이 느슨함은 스키마가 바뀌는 순간 정확히 그 이유 때문에 위험해진다. REST API라면 클라이언트가 요청할 때마다 버전을 명시하거나 즉시 오류를 받아 문제를 알아챌 수 있지만, 이벤트 스트림은 프로듀서가 새 필드를 추가하거나 필드 타입을 바꿔서 배포한 순간, 그 이벤트를 몇 시간 뒤에 처리할 수도 있는 여러 컨슈머가 **각자 다른 시점에** 그 변경과 마주친다. 배포 순서를 프로듀서와 모든 컨슈머 사이에 완벽히 맞추는 것은 현실적으로 불가능하므로, 스키마 자체가 특정한 호환성 규칙을 지키도록 설계 단계에서 강제해야 한다.

## 핵심 개념 1 — 하위 호환성과 상위 호환성

**하위 호환성(backward compatibility)**은 새 스키마로 쓰인 데이터를 옛 스키마를 가진 컨슈머가 읽을 수 있는 것을 말한다. 컨슈머를 나중에 업그레이드해도 되는 상황, 즉 "프로듀서 먼저 배포"가 가능한 조건이다. **상위 호환성(forward compatibility)**은 반대로 옛 스키마로 쓰인 데이터를 새 스키마를 가진 컨슈머가 읽을 수 있는 것으로, "컨슈머 먼저 배포"가 가능한 조건이다. **완전 호환성(full compatibility)**은 둘 다 만족해 배포 순서에 아예 제약이 없는 가장 안전한 상태다. Avro와 Protobuf 모두 이 세 단계의 호환성을 정의할 수 있는 진화 규칙을 제공하지만, 규칙을 지키지 않으면 컴파일은 되어도 런타임에 역직렬화가 실패한다.

## 핵심 개념 2 — 안전한 변경과 위험한 변경

Avro에서 하위 호환을 지키려면 새 필드를 추가할 때 반드시 **기본값(default)**을 지정해야 한다. 기본값이 없는 새 필드를 추가하면, 옛 데이터에는 그 필드가 없으므로 새 스키마로 읽으려 할 때 값을 채울 방법이 없어 실패한다. 필드를 삭제할 때도 마찬가지로 그 필드에 기본값이 있었어야 안전하다. Protobuf는 필드 번호(field number) 기반이라 필드를 추가하는 것은 항상 안전하지만, **기존 필드 번호를 재사용**하면 완전히 다른 의미의 데이터가 같은 번호로 해석되어 조용한 데이터 손상으로 이어진다. 두 포맷 모두 "필드 타입을 호환 불가능하게 바꾸는 것"(예: string을 int로)은 공통적으로 위험하다.

| 변경 유형 | Avro | Protobuf |
|---|---|---|
| 필드 추가(기본값 있음) | 안전(하위·상위 호환) | 안전(새 필드는 옵셔널 취급) |
| 필드 추가(기본값 없음) | 하위 호환 깨짐 | 영향 없음(옵셔널이 기본) |
| 필드 삭제 | 기본값 있었으면 안전 | 필드 번호 예약(reserved) 필요 |
| 필드 번호/이름 재사용 | 이름 재사용 시 위험 | 번호 재사용 시 치명적 |
| 타입 변경 | 호환 가능한 승격만 허용(int→long) | 와이어 타입이 같아야 안전 |

## 코드 예제 — Confluent 스키마 레지스트리로 호환성 자동 검증

```json
// schema-registry에 새 버전을 등록할 때 호환성 모드를 BACKWARD로 강제
// (이 설정이면 새 스키마로 쓴 데이터를 옛 컨슈머가 읽을 수 있어야만 등록 허용)
{
  "compatibility": "BACKWARD"
}
```

```java
// Avro 스키마에 새 필드를 추가할 때 기본값을 명시해야 등록이 통과한다
{
  "type": "record",
  "name": "OrderEvent",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "currency", "type": "string", "default": "KRW"}
  ]
}
```

스키마 레지스트리는 새 스키마가 등록될 때마다 지정된 호환성 모드를 기준으로 이전 버전과 자동 비교해, 규칙을 위반하면 등록 자체를 거부한다. 이를 통해 문제가 실제 프로덕션 트래픽에서 터지기 전에 CI/배포 단계에서 차단할 수 있다.

## 실무 포인트

- **호환성 모드를 팀 차원에서 명시적으로 결정하라.** 기본값인 `BACKWARD`가 대부분의 팀에 적합하지만, 컨슈머 배포가 프로듀서보다 항상 늦는 조직 구조라면 `FORWARD`가, 배포 순서를 아예 통제할 수 없다면 `FULL`이 필요하다.
- **Enum 값 추가도 생각보다 위험하다.** 옛 컨슈머가 새로 추가된 enum 값을 만나면 기본 처리 로직(unknown 분기)이 없을 경우 예외를 던질 수 있으므로, enum을 다루는 컨슈머 코드는 항상 "알 수 없는 값" 케이스를 명시적으로 처리해야 한다.
- **스키마 변경도 코드 리뷰 대상이어야 한다.** 스키마 파일을 애플리케이션 코드와 별도로 관리하면 리뷰 프로세스에서 누락되기 쉬우므로, 스키마 저장소를 CI 파이프라인에 통합해 호환성 검사를 PR 단계에서 강제하는 것이 안전하다.

## 마무리 요약

- 이벤트 스트림은 프로듀서와 컨슈머의 배포 시점을 맞출 수 없으므로, 스키마 자체가 하위·상위 호환성 규칙을 지키도록 설계해야 한다.
- Avro는 기본값 유무, Protobuf는 필드 번호 재사용 여부가 안전한 변경과 위험한 변경을 가르는 핵심 기준이다.
- 스키마 레지스트리로 호환성 검증을 자동화하면 배포 전 CI 단계에서 파싱 실패를 사전에 차단할 수 있다.
