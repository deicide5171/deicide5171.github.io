## 왜 지금 프론트엔드 모노레포인가

디자인 시스템, 웹앱, 어드민, 랜딩 페이지가 저장소별로 흩어져 있으면 공통 컴포넌트 하나를 고칠 때마다 각 저장소에 패키지를 재배포하고 버전을 맞추는 작업이 반복된다. 프론트엔드 팀이 커질수록 "UI 라이브러리 변경이 어느 앱까지 영향을 주는가"를 저장소 경계 때문에 한눈에 파악하기 어려워지는 문제가 커진다. 모노레포는 여러 앱과 공유 패키지를 한 저장소, 하나의 의존성 그래프 안에 두어 이 문제를 구조적으로 없앤다.

다만 모노레포 자체는 "여러 패키지를 한 저장소에 두는 것" 이상의 의미가 없다. 실제로 팀 생산성을 좌우하는 것은 그 위에서 빌드·테스트·린트를 어떻게 실행하느냐이며, 이 역할을 맡는 것이 Turborepo, Nx 같은 **빌드 오케스트레이션 도구**다. pnpm/yarn 워크스페이스로 패키지 링크만 잡아 두고 실행 계층 없이 버티는 팀도 있지만, 저장소가 커질수록 "바뀐 것만 다시 빌드하고 나머지는 캐시에서 즉시 복원한다"는 캐싱 계층 없이는 CI 시간이 선형적으로 늘어난다.

## 핵심 개념 1: 모노레포가 해결하는 것과 안 하는 것

| 구분 | 여러 개의 저장소 | 워크스페이스만 (pnpm/yarn) | Turborepo/Nx 포함 모노레포 |
|---|---|---|---|
| 코드 공유 | npm 배포·버전 관리 필요 | 심볼릭 링크로 즉시 참조 | 동일 + 그래프 기반 영향 분석 |
| 빌드 순서 | 각 저장소 CI가 독립 실행 | 수동으로 순서 관리 필요 | 의존성 그래프로 자동 위상 정렬 |
| 변경 영향 파악 | 어렵다(저장소 경계) | 그래프는 있지만 캐시 없음 | 영향받은 패키지만 재실행 |
| 반복 작업 캐시 | 저장소별 별도 CI 캐시 | 없음 | 로컬·원격 캐시로 중복 실행 제거 |

핵심은 워크스페이스가 "코드를 어떻게 연결할지"를 정의한다면, Turborepo·Nx는 "무엇을 다시 실행해야 하는지"를 판단한다는 점이다. 이 판단은 각 패키지의 소스 파일, 의존 패키지, 환경 변수까지 포함한 해시를 계산해 이전 실행과 비교하는 방식으로 이루어진다.

## 핵심 개념 2: Turborepo vs Nx, 무엇이 다른가

<img src="/assets/images/posts/2026-08-18-frontend-monorepo-turborepo-nx-1.svg" alt="모노레포 패키지 의존성 그래프와 build 실행 시 캐시 히트/미스 판단 흐름도" style="width:100%;">

두 도구 모두 "의존성 그래프 기반 실행 + 로컬/원격 캐싱"이라는 핵심 아이디어는 같지만, 접근 방식과 부가 기능에서 갈린다.

| 항목 | Turborepo | Nx |
|---|---|---|
| 설정 방식 | `turbo.json`에 태스크 파이프라인 선언 | `nx.json` + 프로젝트별 `project.json`(또는 추론 기반 설정) |
| 학습 곡선 | 상대적으로 단순, 설정 최소화 지향 | 기능이 많은 만큼 개념(target, executor 등) 습득 필요 |
| 코드 생성기 | 기본 제공 없음(직접 스크립트 작성) | generator/플러그인으로 보일러플레이트 자동화 |
| 시각화 | 기본 CLI 로그 중심 | 프로젝트 그래프를 그래픽으로 보여주는 내장 뷰어 제공 |
| 원격 캐시 | Vercel 연동 캐시 서비스 | Nx Cloud, 자체 캐시 서버 구성도 가능 |
| 적합한 팀 규모 | 소~중규모, 빠른 도입 선호 팀 | 다수 팀·다수 앱이 얽힌 대규모 조직 |

두 도구 중 하나가 절대적으로 우월하다기보다, 이미 잘 짜인 소수의 앱+공유 패키지 구조라면 Turborepo의 단순함이, 여러 팀이 각기 다른 앱을 소유하고 표준화된 생성기·린트 규칙이 필요하다면 Nx의 플러그인 생태계가 더 잘 맞는 경우가 많다.

## 예제: 캐시 가능한 태스크 파이프라인 정의 (Turborepo)

```json
// turbo.json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "lint": {
      "outputs": []
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
```

`dependsOn`의 `^build`는 "이 패키지가 의존하는 패키지들의 build 태스크가 먼저 끝나야 한다"는 뜻이다. `outputs`에 명시한 경로만 캐시 대상이 되므로, 여기에 빠진 산출물은 캐시 히트가 나더라도 복원되지 않는다는 점을 팀 컨벤션으로 공유해 둘 필요가 있다. `dev`처럼 계속 떠 있는 태스크는 `cache: false`로 캐시 대상에서 제외한다.

## 실무 포인트

- **캐시 키에 무엇이 들어가는지 반드시 확인한다**: 소스 파일 해시뿐 아니라 환경 변수도 캐시 키에 포함되도록 설정하지 않으면, 환경 변수만 바뀐 빌드가 이전 캐시를 그대로 반환하는 사고가 날 수 있다.
- **원격 캐시는 CI에서 가장 효과가 크다**: 로컬 캐시만으로도 재실행은 줄지만, 여러 브랜치·여러 CI 러너가 캐시를 공유하려면 원격 캐시 연동이 사실상 필수다.
- **의존성 그래프를 정기적으로 시각화해 확인한다**: 순환 의존성이나 의도치 않은 결합은 패키지 수가 늘어날수록 코드 리뷰만으로 잡아내기 어려워진다.
- **마이그레이션은 한 번에 하지 않는다**: 기존 워크스페이스 구조 위에 태스크 파이프라인만 먼저 얹고, 캐시 적중률을 관찰하며 outputs·dependsOn 설정을 점진적으로 다듬는 편이 안전하다.

## 3줄 요약

- 모노레포는 여러 앱·공유 패키지를 하나의 의존성 그래프로 관리하지만, 실제 생산성은 그 위에서 도는 빌드 오케스트레이션 도구가 좌우한다.
- Turborepo는 단순한 설정으로 빠르게 캐싱을 도입하기 좋고, Nx는 코드 생성기·그래프 시각화 등 대규모 조직에 필요한 기능이 더 풍부하다.
- 캐시 키 구성(소스+환경 변수)과 outputs 지정을 정확히 하지 않으면 캐시 히트가 오히려 잘못된 산출물을 반환할 수 있으므로 도입 초기에 꼼꼼히 검증해야 한다.
