## 왜 지금 이 구조가 중요해졌는가

"챗봇 켜놓고 대화하는 건 이제 지겹다. 메신저로 한 줄만 요청하면 알아서 조사하고, 코드도 짜고, 끝나면 결과만 보여주는 비서가 필요하다." 이런 요구사항은 몇 달 전까지는 "일단 스트리밍 챗 UI부터 만들고 나중에 생각하자"로 넘어갈 수 있었다. 그런데 2026년 9월 말 OpenAI가 공개한 상시 가동 에이전트 '닷츠(Dots)'는 정확히 이 모델을 상품화했다. 가상 컴퓨터 위에서 조사·문서 작업·개발을 스스로 수행하고, 사용자가 미리 정한 규칙과 명시적 승인으로만 민감한 작업을 통제하며, 대화가 쌓일수록 사용자의 과거 선호와 의사결정을 학습해 다음 작업에 반영한다.

이건 단순히 "더 똑똑한 챗봇"이 아니라 완전히 다른 실행 모델이다. 지금까지 대부분의 에이전트 서비스는 "사용자가 메시지를 보내고, 몇 초~몇 분 안에 응답이 돌아오는" 동기식 요청-응답 구조를 전제로 설계됐다. 상시 가동 에이전트는 그 전제 자체를 깬다. 요청과 응답 사이에 몇 시간, 길게는 밤새가 걸릴 수 있고, 그 사이 에이전트는 사람 없이 혼자 수십 번의 도구 호출과 판단을 이어간다. 이 차이가 서버 아키텍처, 실패 복구, 권한 설계를 전부 다시 쓰게 만든다.

## 요구사항을 기술 문제로 번역하기

"메신저로 요청만 하면 알아서 처리해주는 비서"라는 한 줄은 풀어보면 적어도 네 가지 설계 문제로 나뉜다.

첫째, 요청을 받은 즉시 응답할 수 없으니 **작업을 어딘가에 큐잉하고 비동기로 실행**해야 한다. 둘째, 그 실행은 사용자의 컴퓨터가 아니라 **격리된 실행 환경(가상 컴퓨터)** 안에서 벌어져야 한다 — 그래야 에이전트가 파일을 만들고, 코드를 실행하고, 웹을 돌아다녀도 사용자 환경이나 다른 작업에 영향을 주지 않는다. 셋째, 작업이 몇 시간씩 걸리므로 중간에 서버가 재시작되거나 네트워크가 끊겨도 **진행 상태를 체크포인트로 남겨 이어서 재개**할 수 있어야 한다. 넷째, 사람이 지켜보지 않는 상태에서 결제·메일 발송·외부 API 호출처럼 되돌리기 어려운 행동을 하려 하면 **그 자리에서 멈추고 승인을 기다리는 게이트**가 있어야 한다.

이 네 가지를 묶으면 상시 가동 에이전트는 "LLM 호출 하나"가 아니라 하나의 작은 분산 시스템이 된다.

## 전체 시스템에서의 위치

요청이 들어와 결과가 사용자에게 돌아가기까지, 데이터는 다음 경로를 지난다.

<img src="/assets/images/posts/2026-10-01-always-on-background-agent-architecture-1.svg" alt="사용자 요청이 작업 큐를 거쳐 가상 컴퓨터 샌드박스에서 실행되고, 민감 작업은 승인 게이트를 거치며, 완료 후 알림과 선호 메모리 저장소로 피드백되는 구조도" style="width:100%;">

메신저나 앱에서 들어온 요청은 바로 LLM을 호출하지 않고 **작업 큐**에 적재된다. 워커가 큐에서 작업을 꺼내 **가상 컴퓨터(격리된 컨테이너 또는 마이크로 VM)**를 띄우고, 그 안에서 에이전트가 웹 검색, 코드 실행, 파일 조작 같은 도구를 반복 호출하며 작업을 진행한다. 진행 중 결제·외부 전송·삭제처럼 사전에 정의된 "민감 행동 목록"에 해당하는 호출이 나오면 실행을 멈추고 **승인 게이트**로 넘어가 사람의 확인을 기다린다. 작업이 끝나면 알림 채널로 결과를 전달하고, 이 과정에서 드러난 사용자의 선택(이 보고서는 짧게, 이 어조는 싫다 등)은 **선호 메모리 저장소**에 쌓여 다음 작업을 시작할 때 시스템 프롬프트나 컨텍스트에 자동으로 반영된다. 이 메모리 되먹임 루프가 없으면 매번 처음 쓰는 사람처럼 같은 지시를 반복해야 한다.

## 선택의 트레이드오프 — 동기식 챗 에이전트와 무엇이 다른가

| 기준 | 동기식 챗 에이전트 | 상시 가동 백그라운드 에이전트 |
|---|---|---|
| 응답 모델 | 요청-응답, 수 초~수십 초 | 큐잉-실행-알림, 수 분~수 시간 |
| 실행 환경 | 요청 처리 중에만 존재 | 작업 단위로 격리된 샌드박스 상주 |
| 실패 복구 | 재요청하면 그만 | 체크포인트에서 재개해야 함 |
| 비용 구조 | 요청당 토큰 비용 | 유휴 샌드박스·장시간 실행 인프라 비용 추가 |
| 신뢰 설계 | 매 응답을 사람이 바로 확인 | 사람이 안 보는 사이의 행동에 선승인 규칙 필요 |
| 적합한 작업 | 즉답이 필요한 질의, 짧은 코드 수정 | 리서치 보고서, 다단계 리팩터링, 반복 모니터링 |

핵심 함정은 "일단 에이전트 루프를 비동기로만 바꾸면 된다"는 착각이다. 동기식 설계를 그대로 비동기 큐 위에 얹으면, 승인 게이트 없이 밤새 결제 API를 반복 호출하거나, 서버 재시작 한 번에 몇 시간짜리 작업이 통째로 날아가는 사고로 이어진다. 반대로 모든 서비스가 상시 가동 모델을 필요로 하는 것도 아니다. 사용자가 화면 앞에서 즉시 답을 기다리는 서비스라면 샌드박스·큐·승인 게이트는 지연과 복잡도만 늘리는 과잉 설계다.

## 실제 프로젝트 진행 순서

1. **위임 가능한 작업과 승인이 필요한 행동부터 분류한다.** "조사·초안 작성"처럼 되돌릴 수 있는 작업과 "결제·외부 전송·삭제"처럼 되돌릴 수 없는 행동을 먼저 목록으로 나눠야, 어디에 승인 게이트를 박을지가 정해진다. 이 목록 없이 샌드박스부터 만들면 나중에 전체 실행 로직을 다시 짜야 한다.
2. **격리 실행 환경을 먼저 검증한다.** 컨테이너로 할지 마이크로 VM(Firecracker류)으로 할지, 네트워크 아웃바운드를 어디까지 열지부터 결정한다. 에이전트가 실행하는 임의 코드가 호스트나 다른 사용자의 작업에 닿지 않는지가 이 단계의 유일한 검증 기준이다.
3. **체크포인트 가능한 작업 상태 모델을 설계한다.** 중간 추론, 도구 호출 이력, 생성한 파일을 재구성 가능한 형태로 저장해, 워커가 죽어도 같은 지점에서 이어 실행할 수 있게 만든다.
4. **승인 게이트와 알림 채널을 연결한다.** 민감 행동이 감지되면 실행을 멈추고 사람에게 묻는 흐름을, 작업 완료 알림과 같은 채널로 통일해 사용자가 하나의 창에서 승인·확인을 모두 처리하게 한다.
5. **선호 메모리는 가장 마지막에 넣는다.** 앞 네 단계 없이 메모리부터 쌓으면, 신뢰할 수 없는 실행 결과 위에 잘못된 선호 학습이 누적된다. 실행이 안정화된 뒤에 선호 되먹임을 붙여야 한다.

## 마무리

- 상시 가동 에이전트는 "LLM 응답을 비동기로 바꾼 것"이 아니라 작업 큐·샌드박스·체크포인트·승인 게이트로 이뤄진 작은 분산 시스템이다.
- 동기식 챗 에이전트와 상시 가동 에이전트는 지연·비용·신뢰 설계가 근본적으로 달라, 요구사항이 즉답인지 위임인지부터 구분해야 한다.
- 승인 게이트와 체크포인트를 먼저 안정화한 뒤에야 선호 메모리 같은 개인화 기능을 얹어야 누적된 실행이 신뢰할 수 있는 기반 위에 쌓인다.
