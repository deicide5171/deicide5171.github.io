## 두 사람이 같은 데이터를 동시에 고치면

재고가 1개 남았는데 두 명이 동시에 주문하면 어떻게 될까? 각자 "재고 1개 확인 → 주문 → 재고 0으로" 하면, 둘 다 성공해 재고가 -1이 되는 사고가 난다. 이런 **동시 수정 충돌**을 막는 방법이 **낙관적 락**과 **비관적 락**이다.

## 두 방식의 차이

| 구분 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 가정 | 충돌이 자주 난다 | 충돌이 드물다 |
| 방식 | 먼저 잠그고 작업 | 잠그지 않고, 저장 시 검사 |
| 충돌 시 | 대기(줄 서기) | 저장 실패 → 재시도 |
| 적합 | 충돌 잦은 경우 | 충돌 드문 경우 |

## 동작 방식

```text
[비관적 락]
A가 재고 행을 잠금 -> B는 기다림 -> A 완료 후 B 진행
(SELECT ... FOR UPDATE 로 미리 잠금)

[낙관적 락]
version 컬럼을 둔다.
읽을 때 version=5 -> 저장 시 "version이 아직 5인가?" 확인
누가 먼저 바꿔 version=6이면 -> 내 저장 실패 -> 다시 시도
```

## 실무 포인트

- **충돌 빈도로 선택하라.** 충돌이 드물면 낙관적 락이 효율적이다(대기 없음). 충돌이 잦으면 낙관적 락은 재시도가 많아져 오히려 느리니 비관적 락이 낫다.
- **비관적 락은 데드락을 조심하라.** 여러 행을 잠그다 서로 상대의 잠금을 기다리면 교착 상태(데드락)에 빠진다. 잠그는 순서를 통일하고 잠금 범위·시간을 최소화한다.
- **낙관적 락은 재시도 로직이 필요하다.** 저장이 충돌로 실패하면 다시 읽어서 재시도해야 한다. 사용자에게는 "다른 사람이 먼저 수정했습니다"를 안내하고 최신 값을 보여주는 것이 좋다.

## 마무리 요약

- 낙관적/비관적 락은 여러 사용자의 동시 수정 충돌을 막는 두 방법이다.
- 비관적 락은 먼저 잠그고 작업(대기 발생), 낙관적 락은 저장 시 버전을 검사(실패 시 재시도)한다.
- 충돌이 드물면 낙관적, 잦으면 비관적이 유리하며 각각 재시도·데드락 대비가 필요하다.
