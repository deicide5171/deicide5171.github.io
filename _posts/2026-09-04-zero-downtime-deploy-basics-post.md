## 배포할 때마다 서비스가 멈춘다면

새 버전을 배포하려고 서버를 껐다 켜는 동안 사용자가 접속하면 에러 화면을 본다. 하루에도 여러 번 배포하는 요즘 서비스에서는 이 잠깐의 다운타임도 큰 문제다. **무중단 배포(Zero-Downtime Deployment)**는 서비스를 멈추지 않고 새 버전으로 교체하는 배포 전략이다. 핵심은 "새 버전이 준비될 때까지 기존 버전이 계속 요청을 받는 것"이다.

## 대표적인 두 방식

| 방식 | 개념 | 특징 |
|---|---|---|
| 롤링(Rolling) | 서버를 몇 대씩 순차적으로 새 버전으로 교체 | 추가 서버 자원 적게 듦, 배포 중 두 버전 공존 |
| 블루그린(Blue-Green) | 새 버전(그린) 환경을 통째로 띄운 뒤 트래픽을 한 번에 전환 | 즉시 롤백 가능, 서버 자원 2배 필요 |

## 롤링 배포의 흐름

```text
서버 4대가 v1을 돌리는 중:
1. 1대를 트래픽에서 빼고 v2로 교체 -> 헬스체크 통과하면 다시 투입
2. 다음 1대를 v2로 교체... (반복)
3. 4대 모두 v2가 되면 완료

배포 중에는 v1과 v2가 잠깐 함께 서비스한다
```

## 블루그린 배포의 흐름

```text
1. 현재 운영(블루)은 v1으로 계속 서비스
2. 옆에 그린 환경을 v2로 통째로 띄우고 검증
3. 로드밸런서가 트래픽을 블루 -> 그린으로 한 번에 전환
4. 문제가 있으면 다시 블루로 즉시 되돌림(롤백)
```

## 실무 포인트

- **무중단 배포의 전제는 헬스체크다.** 새 버전 서버가 "정상적으로 요청을 받을 준비가 됐는지"를 로드밸런서가 확인한 뒤에 트래픽을 보내야 한다. 헬스체크 없이 전환하면 아직 부팅 중인 서버로 트래픽이 가서 에러가 난다.
- **배포 중 두 버전이 공존하는 순간을 고려해야 한다.** 특히 롤링 배포에서는 v1과 v2가 동시에 도는데, 이때 DB 스키마가 서로 호환되지 않으면 문제가 생긴다. 그래서 스키마 변경은 "이전·새 버전 모두와 호환되게" 단계적으로 하는 것(Expand-Contract)이 안전하다.
- **블루그린은 롤백이 빠르지만 비용이 든다.** 두 배의 서버를 잠깐이라도 동시에 운영해야 하므로, 자원 여유와 비용을 함께 고려해 방식을 선택해야 한다.

## 마무리 요약

- 무중단 배포는 서비스를 멈추지 않고 새 버전으로 교체하는 전략으로, 기존 버전이 계속 요청을 받게 하는 것이 핵심이다.
- 롤링은 서버를 순차 교체해 자원 부담이 적고, 블루그린은 환경을 통째로 띄워 즉시 롤백이 가능하다.
- 헬스체크가 전제이며, 배포 중 두 버전 공존과 DB 스키마 호환성을 반드시 고려해야 한다.
