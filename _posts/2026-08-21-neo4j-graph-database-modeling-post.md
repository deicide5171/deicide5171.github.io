관계형 데이터베이스에서 "내 친구의 친구 중 아직 내 친구가 아닌 사람"을 찾으려면, `users` 테이블과 `friendships` 테이블을 자기 자신과 여러 번 조인해야 한다. 2단계까지는 그럭저럭 견딜 만하지만, "친구의 친구의 친구"처럼 단계가 하나씩 늘어날 때마다 조인 횟수와 중간 결과 집합의 크기가 함께 불어난다. 옵티마이저가 매 단계마다 인덱스를 다시 타고 조인 순서를 다시 계산해야 하므로, 관계의 깊이가 늘어날수록 쿼리는 급격히 느려지고 실행 계획도 예측하기 어려워진다.

이 문제는 소셜 네트워크의 친구 추천만이 아니라, 상품 추천("이 상품을 산 사람이 함께 산 다른 상품"), 사기 탐지("이 계좌와 3단계 이내로 연결된 계좌들"), 조직도나 지식 그래프처럼 개체 사이의 연결 자체가 질의의 핵심인 도메인에서 공통적으로 나타난다. 이런 도메인은 데이터를 "테이블과 외래키"가 아니라 "노드와 그 사이의 관계"로 표현하는 편이 자연스럽고, 그래프 데이터베이스는 이 표현을 저장 구조 자체로 삼는다.

**Neo4j**는 이런 그래프 데이터베이스 중 가장 널리 쓰이는 구현체로, 그래프 전용 질의 언어인 **Cypher**를 통해 노드와 관계를 패턴으로 표현하고 매칭하는 방식을 제공한다. 이 글에서는 그래프 모델의 기본 구성 요소, RDB와의 구조적 차이, 그리고 Neo4j가 다단계 관계 탐색에서 빠른 이유가 되는 인덱스-프리 어드저센시를 정리한다.

## 핵심 개념 1: 노드, 관계, 속성으로 이루어지는 그래프 모델

그래프 데이터베이스의 데이터 모델은 세 요소로 구성된다. **노드(Node)**는 하나의 개체(사람, 상품, 계좌 등)를 나타내며, 하나 이상의 **레이블**(`:Person`, `:Product`처럼 노드의 종류를 나타내는 태그)을 가질 수 있다. **관계(Relationship)**는 두 노드를 잇는 연결로, 반드시 방향과 하나의 **타입**(`FRIEND_OF`, `PURCHASED`처럼 관계의 의미를 나타내는 이름)을 가진다. 노드와 관계는 둘 다 키-값 형태의 **속성(Property)**을 가질 수 있어서, "언제부터 친구였는지" 같은 정보를 관계 자체에 저장할 수 있다.

여기서 중요한 점은 관계가 RDB의 외래키처럼 두 레코드 사이의 부수적인 참조가 아니라, 그 자체로 속성을 가지는 **1급 데이터**라는 것이다. RDB에서 "누가 언제 무엇을 구매했는지"를 표현하려면 별도의 연결 테이블을 만들어야 하지만, 그래프 모델에서는 `PURCHASED` 관계에 `date` 속성을 바로 붙이면 된다.

## 핵심 개념 2: RDB 테이블 모델과의 비교

같은 데이터를 두 모델이 어떻게 다르게 표현하는지 비교하면 차이가 뚜렷하다.

| 구분 | RDB | 그래프 DB |
|---|---|---|
| 개체 표현 | 테이블의 행(row) | 노드(Node) |
| 관계 표현 | 외래키 + 조인 | 관계(Relationship), 1급 데이터 |
| 다단계 관계 조회 | 조인을 단계마다 반복 | 패턴을 한 번에 매칭 |
| 스키마 | 고정된 컬럼 구조 강제 | 노드마다 다른 속성 허용(스키마 유연) |
| 강점 도메인 | 집계, 정형 트랜잭션 | 연결 탐색, 다단계 관계 질의 |

RDB는 "이 조건에 맞는 행을 모두 찾아 집계하라" 같은 질의에 강하도록 설계되어 있고, 그래프 DB는 "이 노드에서 출발해 이런 패턴으로 연결된 노드를 찾아라" 같은 질의에 강하도록 설계되어 있다. 어느 한쪽이 항상 우월한 것이 아니라, 질의의 성격이 다르다.

## 핵심 개념 3: 인덱스-프리 어드저센시

Neo4j가 다단계 관계 탐색에서 유리한 근본적인 이유는 **인덱스-프리 어드저센시(index-free adjacency)**에 있다. RDB에서 조인은 보통 인덱스를 통해 "이 값과 일치하는 행이 어디 있는지" 매번 다시 찾아야 하는 연산이다. 반면 그래프 DB에서는 각 노드가 자신과 연결된 관계에 대한 포인터를 저장 구조상 직접 들고 있다. 그래서 노드 A에서 노드 B로, 다시 노드 C로 이동하는 것은 인덱스 조회가 아니라 포인터를 따라가는 연산에 가까워, 전체 그래프의 크기와 무관하게 지역적인 연결 정보만으로 다음 단계로 넘어갈 수 있다.

이 구조 덕분에 관계의 깊이가 늘어나도(친구의 친구의 친구, 4~5단계 이상) 탐색 비용이 전체 데이터 규모에 비례해 커지지 않고, 실제로 방문하는 노드와 관계의 수에 비례하는 경향을 보인다. 다만 이는 그래프의 형태와 질의 패턴에 따라 달라지므로, 구체적인 성능 수치는 실제 데이터셋으로 측정해 확인하는 편이 안전하다.

## 예제

다음은 Cypher로 노드와 관계를 생성하는 예시다.

```cypher
// 노드 생성: 레이블과 속성
CREATE (alice:Person {name: 'Alice', age: 32})
CREATE (bob:Person {name: 'Bob', age: 29})
CREATE (neo4j:Company {name: 'Neo4j Inc'})

// 관계 생성: 방향, 타입, 속성
CREATE (alice)-[:FRIEND_OF {since: 2019}]->(bob)
CREATE (alice)-[:WORKS_AT]->(neo4j)
CREATE (bob)-[:WORKS_AT]->(neo4j)
```

패턴 매칭으로 "같은 회사에 다니는 친구"를 찾는 쿼리는 다음과 같다.

```cypher
MATCH (me:Person {name: 'Alice'})-[:FRIEND_OF]->(friend:Person)
MATCH (me)-[:WORKS_AT]->(company)<-[:WORKS_AT]-(friend)
RETURN friend.name, company.name
```

`MATCH` 절의 화살표 패턴이 그래프 모양을 그대로 표현하고 있어서, 여러 단계의 조인을 명시적으로 나열하는 SQL보다 관계 중심 질의의 의도가 더 직관적으로 드러난다.

## 실무 포인트

그래프 DB는 도메인에 따라 유불리가 뚜렷하게 갈린다.

- **유리한 도메인**: 소셜 네트워크의 관계 탐색, 추천 시스템(협업 필터링의 연결 기반 추천), 사기 탐지(계좌·거래 사이의 다단계 연결 패턴), 조직도·지식 그래프처럼 "연결 자체"가 질의의 핵심인 경우.
- **불리한 도메인**: 대량의 행을 스캔해 집계하는 배치 리포팅, 엄격한 스키마와 강한 트랜잭션 무결성이 필요한 정형 업무 시스템, 관계보다 정형 컬럼 위주의 집계·필터링이 주된 작업인 경우. 이런 경우 RDB의 인덱스 기반 집계가 더 성숙하고 예측 가능하다.
- 마이그레이션을 고려한다면 전체 시스템을 교체하기보다, 관계 탐색이 병목인 특정 기능만 그래프 DB로 분리하는 편이 리스크가 작다.
- Neo4j는 클러스터 구성, 트랜잭션 격리 수준, 백업 전략 등에서 RDB와 다른 운영 지식을 요구하므로, 도입 전 팀의 학습 곡선도 함께 고려해야 한다.

## 3줄 요약

- RDB에서 다단계 관계 조회는 조인이 반복될수록 느려지지만, 그래프 DB는 노드-관계-속성 모델로 연결 자체를 1급 데이터로 다룬다.
- Neo4j가 다단계 탐색에 유리한 이유는 인덱스-프리 어드저센시 덕분으로, 각 노드가 연결 정보를 포인터로 직접 들고 있어 인덱스 재조회 없이 이웃으로 이동한다.
- 그래프 DB는 추천·소셜·사기 탐지처럼 연결 탐색이 핵심인 도메인에 강하고, 정형 집계나 강한 트랜잭션 무결성이 중요한 업무에는 RDB가 더 적합하다.
