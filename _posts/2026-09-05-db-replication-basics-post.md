## 읽기가 많은 서비스의 고민

대부분의 서비스는 쓰기보다 읽기가 훨씬 많다. 게시글 하나를 쓰면 수천 명이 읽는 식이다. 이 모든 읽기를 DB 한 대가 처리하면 금방 한계에 부딪힌다. **복제(Replication)**는 원본 DB(마스터)의 데이터를 복사한 사본 DB(리플리카)를 여러 대 두고, 읽기 요청을 사본들에 분산시키는 방법이다.

## 마스터-리플리카 구조

| 역할 | 하는 일 |
|---|---|
| 마스터(Primary) | 쓰기(INSERT/UPDATE/DELETE)를 담당 |
| 리플리카(Replica) | 마스터의 변경을 복사받아 읽기(SELECT)를 담당 |

```text
쓰기 요청 -> 마스터 -> (변경 내용을 리플리카들에 전파)
읽기 요청 -> 리플리카1, 리플리카2, ... (분산)

읽기가 많아지면 리플리카를 더 추가해 읽기 처리량을 늘린다.
```

## 복제가 주는 이점

- **읽기 부하 분산**: 읽기를 여러 사본에 나눠 처리량을 늘린다.
- **고가용성**: 마스터가 죽으면 리플리카 중 하나를 새 마스터로 승격(failover)할 수 있다.
- **백업·분석 분리**: 무거운 분석 쿼리나 백업을 리플리카에서 돌려 마스터 부하를 줄인다.

## 복제 지연이라는 함정

복제의 가장 큰 함정은 **복제 지연(replication lag)**이다. 마스터에 쓴 내용이 리플리카에 반영되기까지 아주 짧지만 시간이 걸린다.

```text
1. 사용자가 글을 작성 -> 마스터에 저장
2. 곧바로 그 글 목록을 조회 -> 리플리카에서 읽음
3. 그런데 아직 리플리카에 복제가 안 됨!
-> 방금 쓴 글이 안 보이는 현상 (Read-Your-Writes 문제)
```

## 실무 포인트

- **방금 쓴 데이터를 바로 읽어야 하는 경우엔 마스터에서 읽어야 한다.** 회원가입 직후 내 정보 조회처럼 "내가 방금 한 작업의 결과"는 복제 지연 때문에 리플리카에서 안 보일 수 있으므로, 이런 요청은 마스터로 보내는 예외 처리가 필요하다.
- **복제는 샤딩과 다르다.** 복제는 같은 데이터를 여러 곳에 복사(읽기 분산)하는 것이고, 샤딩은 데이터를 나눠 저장(쓰기 분산·용량 분산)하는 것이다. 읽기가 병목이면 복제, 쓰기·용량이 병목이면 샤딩을 검토한다.
- **복제 지연을 모니터링해야 한다.** 리플리카가 마스터를 얼마나 못 따라오는지(lag)를 감시하지 않으면, 지연이 커졌을 때 사용자에게 오래된 데이터가 보이는 문제를 눈치채기 어렵다.

## 마무리 요약

- 복제는 마스터의 데이터를 리플리카에 복사해 읽기 요청을 분산하는 방법이다.
- 읽기 부하 분산, 고가용성(failover), 분석·백업 분리의 이점이 있다.
- 복제 지연 때문에 방금 쓴 데이터가 리플리카에서 안 보일 수 있어, 즉시 읽어야 하는 요청은 마스터로 보내야 한다.
