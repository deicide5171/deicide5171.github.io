## 왜 지금 이 이야기인가

단일 데이터베이스 인스턴스로 감당할 수 있는 트래픽과 데이터 규모에는 한계가 있다. 수직 확장(더 큰 서버)은 언젠가 물리적·비용적 한계에 부딪히고, 이 지점에서 많은 팀이 샤딩(sharding)을 고려하게 된다. 하지만 샤딩은 "일단 넣고 보자"식으로 접근하면 나중에 되돌리기 매우 어려운 결정이다. 샤딩 키를 잘못 고르면 특정 샤드에만 트래픽이 몰리는 핫스팟이 생기고, 리샤딩이 필요해지는 순간 서비스 전체에 영향을 주는 대규모 마이그레이션을 감수해야 한다.

이 글에서는 샤딩 키 선택 기준, 샤딩 방식별 비교, 그리고 실무에서 자주 마주치는 핫스팟과 리샤딩 문제를 정리한다.

## 샤딩 방식 비교

| 방식 | 원리 | 장점 | 단점 |
|---|---|---|---|
| 해시 기반 | 키를 해시 함수에 통과시켜 샤드 결정 | 데이터 분산이 균등한 편 | 범위 쿼리 비효율, 리샤딩 시 재배치 부담 |
| 레인지 기반 | 키 값의 범위로 샤드 결정 | 범위 쿼리 효율적, 리샤딩이 상대적으로 쉬움 | 특정 범위에 트래픽이 몰리면 핫스팟 발생 |
| 디렉토리 기반 | 별도 매핑 테이블(라우터)로 샤드 결정 | 유연한 재배치, 세밀한 제어 가능 | 매핑 테이블이 병목/단일장애점이 될 수 있음 |

세 방식 모두 실무에서는 조합해서 쓰는 경우가 많다. 예를 들어 해시로 1차 분산을 시키되, 특정 대형 테넌트만 별도 샤드로 디렉토리 매핑을 두는 식이다.

## 샤딩 키 선택 기준

좋은 샤딩 키는 다음 조건을 동시에 만족해야 하는 것으로 보인다.

- **쓰기 분산**: 특정 키 값에 쓰기가 몰리지 않아야 한다(예: 시간순 증가하는 ID를 그대로 쓰면 최신 데이터에 쓰기가 집중될 수 있다).
- **쿼리 지역성**: 애플리케이션에서 가장 빈번한 조회 패턴이 단일 샤드 안에서 해결되는 것이 이상적이다. 예를 들어 멀티테넌트 SaaS라면 tenant_id를 샤딩 키로 쓰면 대부분의 쿼리가 한 샤드에서 끝난다.
- **카디널리티**: 샤딩 키의 고유값 개수가 충분히 많아야 균등 분산이 가능하다.
- **조인 최소화**: 크로스 샤드 조인은 애플리케이션 레벨에서 처리해야 하므로, 자주 조인되는 테이블은 같은 키로 묶는 것이 유리하다.

## 리샤딩의 어려움

샤딩 키를 처음부터 완벽하게 고르기는 사실상 불가능하다. 서비스가 성장하면 트래픽 패턴이 바뀌고, 결국 샤드 수를 늘리거나 재배치해야 하는 시점이 온다. 문제는 리샤딩이 단순 스케일 아웃이 아니라는 점이다.

- 해시 기반 샤딩에서 샤드 수를 바꾸면 대부분의 키가 다른 샤드로 재배치되어야 한다(컨시스턴트 해싱을 쓰지 않는 한).
- 온라인 상태로 데이터를 이동시키려면 이중 쓰기(dual write), 백필(backfill), 컷오버(cutover) 단계를 거쳐야 하고 각 단계마다 데이터 정합성 검증이 필요하다.
- 애플리케이션 코드에서 샤드 라우팅 로직을 하드코딩해뒀다면 리샤딩 자체가 배포를 동반한 큰 작업이 된다.

이런 이유로 처음부터 컨시스턴트 해싱을 쓰거나, Vitess/Citus처럼 리샤딩을 지원하는 미들웨어를 도입해 이 문제를 미리 흡수하는 접근이 실무에서 자주 언급된다.

## 핫스팟(핫키) 문제와 완화

특정 샤드에만 트래픽이 몰리는 핫스팟은 샤딩을 도입한 후에도 반복적으로 발생하는 문제다. 대표적인 원인과 완화책은 다음과 같다.

| 원인 | 완화책 |
|---|---|
| 시간순 증가 ID를 그대로 샤딩 키로 사용 | ID 앞에 랜덤 프리픽스 추가, 혹은 해시 기반 전환 |
| 인기 테넌트/유저 쏠림 | 대형 테넌트 전용 샤드 분리, 서브 샤딩 |
| 특정 시간대 트래픽 집중(예: 이벤트) | 캐시 레이어 추가, 샤드 간 로드밸런싱 |

## 예제: 컨시스턴트 해싱 기반 샤드 라우팅

```python
import hashlib

def get_shard(key: str, shard_count: int) -> int:
    digest = hashlib.md5(key.encode()).hexdigest()
    return int(digest, 16) % shard_count

# tenant_id 기반 샤딩 예시
shard_id = get_shard("tenant_8823", shard_count=16)
```

```yaml
# 샤드 라우팅 설정 예시
sharding:
  strategy: hash
  key: tenant_id
  shard_count: 16
  hot_tenants:
    - id: tenant_0001
      dedicated_shard: shard_special_01
```

## 실무 포인트와 주의사항

- 샤딩은 되돌리기 어려운 결정이므로 도입 전 파티셔닝(단일 DB 내 테이블 분할)으로 버틸 수 있는지 먼저 검토해야 한다.
- 크로스 샤드 트랜잭션은 가급적 피하고, 필요하다면 사가 패턴 등 별도 보상 로직을 설계해야 한다.
- 샤드 수는 향후 성장을 고려해 넉넉히 잡되(가상 샤드), 물리 노드 수는 유연하게 조정하는 방식이 리샤딩 부담을 줄인다.
- 모니터링에서 샤드별 트래픽/스토리지 불균형을 상시 추적해야 핫스팟을 조기에 발견할 수 있다.

## 3줄 요약

- 샤딩 키는 쓰기 분산, 쿼리 지역성, 카디널리티를 모두 만족해야 한다.
- 리샤딩은 단순 스케일 아웃이 아니라 이중 쓰기·백필·컷오버가 필요한 큰 작업이다.
- 핫스팟은 ID 설계나 대형 테넌트 분리로 완화할 수 있으며 상시 모니터링이 필요하다.
