## 왜 같은 질문인데 답변 품질이 다른가

"코드 짜줘"와 "Python으로 CSV 파일을 읽어서 특정 컬럼의 평균을 구하는 함수를 작성해줘. 타입 힌트를 포함하고, 예외 처리도 넣어줘"는 같은 주제의 요청이지만 결과물의 품질은 완전히 다르다. LLM은 사용자의 의도를 추측해서 답하는데, 정보가 부족하면 가장 무난하고 일반적인 답을 고르게 된다. **프롬프트 엔지니어링**은 LLM이 추측할 여지를 줄이고 원하는 결과에 가깝게 유도하는 질문 작성 기술이다.

## 좋은 프롬프트의 4가지 요소

| 요소 | 설명 | 예시 |
|---|---|---|
| 역할(Role) | 어떤 입장에서 답할지 지정 | "너는 시니어 백엔드 개발자야" |
| 맥락(Context) | 필요한 배경 정보 제공 | "이 함수는 초당 수천 건 호출되는 API에서 쓰여" |
| 지시(Instruction) | 구체적으로 무엇을 원하는지 | "함수로 작성하고, 타입 힌트를 포함해줘" |
| 형식(Format) | 출력 형태를 명시 | "코드만 출력하고 설명은 주석으로 넣어줘" |

## 나쁜 프롬프트 vs 좋은 프롬프트

```text
나쁜 예:
"이 코드 고쳐줘"

좋은 예:
"아래 Python 코드에서 리스트를 순회하며 중복 항목을 제거하는 부분이
O(n^2)으로 동작해서 느려. 시간 복잡도를 O(n)으로 개선해줘.
기존 함수 시그니처는 유지하고, 개선한 이유도 한 줄 주석으로 남겨줘.

[코드 붙여넣기]"
```

나쁜 예는 "무엇을", "왜", "어떻게" 중 아무것도 specify하지 않아서 모델이 임의로 해석해야 한다. 좋은 예는 문제, 목표, 제약조건을 모두 명시해 모델이 추측할 부분을 최소화한다.

## 실무에서 바로 쓸 수 있는 기법 3가지

- **예시 제공(Few-shot)**: 원하는 출력 형태의 예시를 1~2개 먼저 보여주면, 모델이 그 패턴을 따라간다. 형식이 중요한 작업(JSON 출력, 특정 톤의 글쓰기)에 특히 효과적이다.
- **단계별로 생각하게 하기(Chain-of-Thought)**: "단계별로 생각해봐"라는 지시를 추가하면, 복잡한 추론이 필요한 문제에서 정확도가 올라가는 경우가 많다.
- **부정 지시보다 긍정 지시**: "이렇게 하지 마"보다 "이렇게 해줘"로 표현하는 것이 모델이 더 정확히 따르는 경향이 있다.

## 실무 포인트

- **프롬프트를 한 번에 완벽하게 쓰려 하지 말고 반복 개선하라.** 첫 응답이 만족스럽지 않으면 어떤 부분이 부족했는지 짚어 후속 질문으로 다듬는 것이 효율적이다.
- **같은 프롬프트라도 모델마다 반응이 다를 수 있다.** 한 모델에서 잘 통하던 프롬프트 패턴이 다른 모델에서는 덜 효과적일 수 있으므로, 모델을 바꿀 때는 재검증이 필요하다.
- **민감한 작업(코드 실행, 자동화)에 쓸 프롬프트는 반드시 여러 입력값으로 테스트해봐야 한다.** 한두 번 잘 되는 것과 프로덕션에서 안정적으로 동작하는 것은 다른 문제다.

## 마무리 요약

- 프롬프트 엔지니어링은 모델이 추측할 여지를 줄여 원하는 결과에 가깝게 유도하는 기술이다.
- 역할, 맥락, 지시, 형식 네 가지를 명시하면 답변 품질이 크게 개선된다.
- Few-shot 예시 제공과 단계별 사고 유도가 실무에서 바로 써먹을 수 있는 기본 기법이다.
