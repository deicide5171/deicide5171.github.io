## 테이블에서 특정 행을 어떻게 콕 집나

수백만 개의 행이 있는 테이블에서 "이 사용자"를 정확히 가리키려면 겹치지 않는 식별자가 필요하다. 그것이 **기본키(Primary Key, PK)**다. 그리고 주문 테이블에서 "이 주문은 어느 사용자의 것"인지 연결하려면, 사용자 테이블의 기본키를 참조해야 하는데 그것이 **외래키(Foreign Key, FK)**다. 이 두 키가 관계형 DB에서 테이블들을 연결하는 핵심이다.

## 기본키(PK)의 조건

| 조건 | 설명 |
|---|---|
| 유일성 | 값이 중복되지 않는다(각 행을 구별) |
| NOT NULL | 비어 있을 수 없다 |
| 불변성 권장 | 한 번 정하면 잘 바뀌지 않는 값이 좋다 |

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,   -- 기본키: 각 사용자를 고유하게 식별
    name VARCHAR(100)
);
```

## 외래키(FK)로 테이블 연결

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,          -- 외래키: users 테이블의 id를 참조
    item VARCHAR(100),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

`orders.user_id`가 `users.id`를 참조하므로, "이 주문이 누구 것인지"를 연결할 수 있다. 외래키 덕분에 JOIN으로 두 테이블을 이어 조회할 수 있고, DB가 "존재하지 않는 사용자의 주문"이 생기지 않도록 무결성을 지켜준다.

## 외래키가 지켜주는 것: 참조 무결성

```text
외래키 제약이 있으면:
- users에 없는 user_id로 orders를 만들려 하면 -> 거부
- 주문이 딸린 사용자를 지우려 하면 -> 거부(또는 설정에 따라 함께 삭제)

-> "고아 데이터(참조 대상이 없는 데이터)"가 생기는 것을 DB가 막아준다.
```

## 실무 포인트

- **기본키로 의미 없는 값(자동 증가 ID, UUID)을 쓰는 것이 안전하다.** 이메일이나 주민번호처럼 의미 있는 값을 PK로 쓰면, 그 값이 바뀔 때 참조하는 모든 곳을 함께 바꿔야 하는 문제가 생긴다.
- **외래키 제약을 걸지 않는 팀도 있다.** 대규모·고성능 환경에서는 외래키 제약이 성능·유연성에 부담이 될 수 있어, 애플리케이션 레벨에서 무결성을 관리하고 DB 제약은 생략하기도 한다. 다만 그만큼 실수로 고아 데이터가 생길 위험은 커진다.
- **외래키 컬럼에는 인덱스를 걸어두는 것이 좋다.** JOIN과 참조 무결성 검사에서 이 컬럼이 자주 쓰이므로, 인덱스가 없으면 데이터가 많을 때 느려진다.

## 마무리 요약

- 기본키(PK)는 테이블의 각 행을 고유하게 식별하는 값으로 유일하고 비어 있으면 안 된다.
- 외래키(FK)는 다른 테이블의 기본키를 참조해 테이블들을 연결하고 참조 무결성을 지킨다.
- PK는 의미 없는 값(자동 ID, UUID)을 쓰고, FK 컬럼에는 인덱스를 거는 것이 실무 관례다.
