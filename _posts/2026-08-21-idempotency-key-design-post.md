결제 요청을 보낸 클라이언트가 응답을 받지 못한 채 타임아웃이 나는 경우를 생각해보자. 서버는 결제 처리를 이미 끝냈는데 응답 패킷만 유실됐을 수도 있고, 서버가 처리를 시작하기 전에 요청 자체가 끊겼을 수도 있다. 클라이언트 입장에서는 이 두 상황을 구분할 방법이 없다. 안전을 위해 재시도를 하면, 앞의 경우에는 같은 결제가 두 번 청구된다.

이 문제는 네트워크가 불안정한 환경에서, 혹은 모바일 앱처럼 연결이 자주 끊기는 클라이언트에서 특히 자주 발생한다. 결제, 주문 생성, 포인트 적립처럼 부작용이 있고 되돌리기 번거로운 API일수록 재시도로 인한 중복 실행의 대가가 크다. 단순히 "재시도하지 마라"는 답은 현실적이지 않다. 네트워크 오류에 대한 재시도는 클라이언트의 정상적인 복원력 전략이고, 문제는 재시도 자체가 아니라 서버가 같은 요청을 알아보지 못한다는 데 있다.

멱등성 키는 이 문제를 클라이언트와 서버가 함께 푸는 표준적인 방식이다. 같은 논리적 요청은 몇 번을 다시 보내도 서버에서 딱 한 번만 실행된 것과 같은 결과를 받도록 만드는 것이 목표다. 이번 글에서는 이 설계의 핵심 개념과, 실무에서 자주 놓치는 지점들을 정리한다.

## 핵심 개념 1: 클라이언트가 키를 생성한다

멱등성 키 설계에서 가장 중요한 전제는, 이 키를 서버가 아니라 **클라이언트**가 생성한다는 점이다. 서버가 키를 발급하려면 발급 자체가 별도의 요청-응답을 거쳐야 하는데, 그 요청도 실패할 수 있으니 문제가 근본적으로 해결되지 않는다. 대신 클라이언트가 요청을 시도하기 전에 UUID 같은 고유 값을 하나 만들어 `Idempotency-Key` 헤더에 실어 보내고, 타임아웃이나 연결 실패로 재시도할 때도 **동일한 키**를 그대로 재사용한다.

여기서 실수하기 쉬운 지점은, 재시도 로직이 매번 새 키를 생성해버리는 경우다. 이렇게 되면 서버 입장에서는 매번 새로운 요청으로 보이므로 멱등성 키를 붙인 의미가 없어진다. 키는 "이 논리적 요청 한 건"을 식별하는 값이어야 하므로, 재시도 루프의 바깥, 즉 사용자의 결제 버튼 클릭 시점 같은 곳에서 한 번만 생성하고 이후의 재전송에는 계속 같은 값을 써야 한다.

## 핵심 개념 2: 서버 측 키 저장소와 응답 캐싱

서버는 들어온 요청의 멱등성 키를 별도 저장소(주로 Redis 같은 키-값 스토어나 별도 테이블)에 기록해두고, 같은 키로 다시 들어온 요청은 실제 로직을 다시 실행하는 대신 **처음 처리했을 때의 응답을 그대로 반환**한다. 저장소에는 대략 다음과 같은 정보가 들어간다.

- 멱등성 키 값
- 요청 상태(처리 중 / 완료 / 실패)
- 완료된 경우의 응답 본문과 상태 코드
- 요청 바디의 해시(핵심 개념 2 뒷부분에서 다룸)
- 생성 시각과 만료(TTL) 시각

키는 영구히 보관하지 않고 TTL을 둔다. 결제 재시도는 대개 초 단위에서 길어야 몇 분 안에 끝나므로, 이 시간대만 커버하면 충분하다. TTL을 너무 짧게 두면 늦게 도착한 재시도가 캐시를 놓쳐 중복 처리로 이어지고, 너무 길게 두면 저장소 용량이 계속 불어난다. 이 값은 서비스의 재시도 정책(최대 재시도 횟수와 백오프 간격)에 맞춰 결정하는 것이 합리적이다.

## 핵심 개념 3: 동시 요청 처리

같은 멱등성 키로 두 요청이 거의 동시에 도착하는 경우도 고려해야 한다. 클라이언트가 타임아웃을 짧게 잡고 재시도를 너무 빨리 보내면, 첫 번째 요청이 아직 처리 중인 상태에서 두 번째 요청이 도착할 수 있다. 이때 두 번째 요청까지 그대로 로직을 실행해버리면 멱등성이 깨진다.

이를 막으려면 키를 저장소에 기록하는 시점에 원자적인(atomic) 조건부 쓰기를 사용해야 한다. 예를 들어 "키가 존재하지 않을 때만 생성"(SET NX 같은 연산)하는 방식으로 첫 번째 요청만 처리 권한을 얻고, 뒤따라온 요청은 상태가 "처리 중"인 것을 보고 409 Conflict를 반환하거나, 첫 요청이 끝날 때까지 짧게 대기했다가 완료된 응답을 반환하도록 설계한다. 이 부분은 애플리케이션 로직에서 별도로 락을 구현하기보다, 저장소가 제공하는 원자적 연산에 기대는 편이 안전하다.

## 예제

아래는 멱등성 키 처리 미들웨어의 의사코드다. 실제 락 구현은 사용하는 저장소의 원자적 연산에 따라 달라진다.

```
function handleRequest(request):
    key = request.headers["Idempotency-Key"]
    if key is None:
        return process(request)  # 멱등성 키 없이 그냥 처리(선택 사항)

    bodyHash = sha256(request.body)
    record = store.getOrCreate(key, {
        status: "processing",
        bodyHash: bodyHash,
        createdAt: now(),
        ttl: 10분
    })  # 원자적 연산: 이미 존재하면 기존 record 반환, 없으면 생성

    if record.status == "completed":
        if record.bodyHash != bodyHash:
            return 422 "키가 이미 다른 요청 본문에 사용되었습니다"
        return record.response  # 캐시된 응답 그대로 반환

    if record.status == "processing" and record.createdAt != now():
        return 409 "동일 키로 요청이 이미 처리 중입니다"

    # 이 요청이 처리 권한을 획득한 경우
    try:
        response = process(request)
        store.update(key, { status: "completed", response: response })
        return response
    except error:
        store.update(key, { status: "failed" })
        raise error
```

핵심은 "키를 원자적으로 선점"하는 단계와, "완료된 요청은 재실행 없이 저장된 응답을 돌려주는" 단계를 분리하는 것이다. 실패로 끝난 요청은 상태를 "failed"로 남겨서 재시도가 다시 로직을 실행할 수 있게 열어두는 편이 일반적이다(실패한 결제를 캐시해서 영구히 막아버리면 안 되기 때문이다).

## 실무 포인트

- **TTL은 재시도 정책에 맞춰 정한다**: 클라이언트의 최대 재시도 시간창보다 넉넉하게, 그러나 무한정 길지 않게 설정한다. Stripe는 멱등성 키를 24시간 동안 보관한다고 문서에 명시하는데, 이는 참고할 만한 기준점이지 절대적인 정답은 아니며 서비스의 재시도 특성에 맞춰 조정해야 한다.
- **요청 바디 해시로 키 오남용을 막는다**: 같은 멱등성 키가 서로 다른 요청 본문과 함께 재사용되는 경우(버그거나, 악의적인 재사용이거나)를 걸러내려면 최초 요청의 바디 해시를 함께 저장해두고, 이후 같은 키로 들어온 요청의 바디 해시가 다르면 에러로 거절해야 한다. 이 검증이 없으면 키가 "요청 식별자"가 아니라 그저 "캐시 무효화 우회 통로"로 잘못 쓰일 위험이 있다.
- **멱등성 보장 범위를 명확히 한다**: 멱등성 키는 API 계층의 중복 실행을 막아줄 뿐, 그 안에서 외부 결제 게이트웨이 같은 다른 시스템을 호출하는 로직까지 자동으로 멱등하게 만들어주지는 않는다. 하위 시스템 호출에도 동일한 키를 전달하거나 별도의 멱등성 처리를 두어야 전체 체인이 안전해진다.

## 3줄 요약

- 네트워크 재시도는 정상적인 클라이언트 동작이지만, 서버가 같은 요청을 알아보지 못하면 결제 같은 부작용 있는 API에서 중복 실행으로 이어진다.
- 클라이언트가 생성한 멱등성 키를 서버가 저장소에 캐싱해 완료된 응답을 재반환하고, 동시 요청은 원자적 선점으로 처리한다.
- TTL 설계와 요청 바디 해시 검증이 실무에서 멱등성 키를 안전하게 운영하는 데 핵심적인 디테일이다.
