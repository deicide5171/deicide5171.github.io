## 도입

"회의 끝나고 손 쓸 필요 없이, 말로 '이거 캘린더에 등록하고 참석자한테 슬랙으로 알려줘'라고만 하면 바로 처리되게 해주세요." 텍스트 챗봇이라면 이 요구는 익숙하다 — 메시지를 보내고, 화면에 뜬 "일정을 등록할까요?" 버튼을 누르면 끝난다. 그런데 음성 인터페이스에는 그 버튼이 없다. 확인을 받아야 할 행동(일정 등록, 메시지 발송처럼 되돌리기 어려운 것)과 그냥 물어보고 끝나는 행동(캘린더 조회, 이메일 요약처럼 읽기만 하는 것)을 사람이 눈으로 구분해주던 장치가 사라지는 것이다.

2026년 7월 Claude 음성 모드가 Opus·Sonnet 모델로 확장되면서 Gmail, Google Calendar, Slack, Canva, Notion 같은 연결 앱에 걸쳐 직접 행동하는 크로스앱 자동화가 들어왔다. 말로 캘린더를 확인하고, 이메일 맥락을 읽고, 슬랙 메시지 초안까지 작성하게 할 수 있다. 이 글은 "음성으로 여러 앱에 걸친 작업을 처리해달라"는 요구가 왜 확인(confirmation) 설계의 문제로 번역되는지, 그리고 화면이 없는 턴 기반 음성 아키텍처에서 그 확인을 어디에 넣어야 하는지 정리한다.

## 전체 시스템에서의 위치

음성 에이전트의 흐름은 텍스트 에이전트와 같은 뼈대 위에서 돌아가지만, 입력·출력 계층과 확인 지점의 위치가 다르다.

<img src="/assets/images/posts/2026-10-26-voice-agent-cross-app-action-confirmation-1.svg" alt="음성 입력부터 다중 앱 실행까지, 확인 게이트가 들어가는 위치를 보여주는 구조도" style="width:100%;">

- **음성 인식(STT) → 의도·슬롯 추출**: "캘린더에 등록하고 슬랙으로 알려줘"라는 발화에서 대상 일정, 시간, 참석자, 메시지 내용을 분리해낸다. 텍스트 입력과 달리 되묻지 않으면 모호함이 그대로 다음 단계로 넘어간다.
- **커넥터 오케스트레이션**: Calendar, Slack 같은 각 앱에 대한 호출은 텍스트 에이전트와 동일하게 MCP류 커넥터 구조를 그대로 탄다. 음성이라고 이 계층의 구조가 바뀌지는 않는다.
- **확인 게이트**: 읽기 전용 행동(조회·요약)은 바로 실행하고, 되돌리기 어려운 쓰기 행동(일정 생성, 메시지 발송)은 실행 전에 반드시 음성으로 되물어 확인을 받는다. 화면 버튼이 없으므로 이 되묻기 자체가 UI다.
- Claude 음성 모드는 **턴 기반(turn-based)** 구조다 — 듣고, 생각하고, 응답하는 순서가 명확히 나뉘어 완전 양방향(full-duplex) 대화가 끼어들 수 없다. 확인 질문과 사용자의 답("네, 보내줘" / "아니, 취소해")도 이 턴 구조 안에서 한 번의 왕복으로 처리된다.

## 선택의 트레이드오프

| 구성 | 커스터마이징 | 확인 UX 구현 난이도 | 지연시간 | 적합한 상황 |
|---|---|---|---|---|
| Claude 음성 모드 내장 크로스앱 자동화 | 지원 커넥터 범위로 제한(Gmail·Calendar·Slack·Canva·Notion 등) | 낮음 — 확인 흐름이 이미 내장 | 턴 기반, 체감상 자연스러운 수준 | 지원 앱만으로 충분한 일반적인 업무 자동화 |
| STT + 커스텀 NLU + 자체 MCP 오케스트레이션 | 사내 시스템까지 자유롭게 연동 | 높음 — 확인 게이트를 직접 설계·구현 | 구성에 따라 가변적, 보통 더 긺 | 사내 전용 앱이 많거나 특수한 확인 정책이 필요한 조직 |
| 음성은 받아쓰기만, 텍스트 에이전트로 전환 | 기존 텍스트 에이전트 자산 재사용 | 중간 — 화면이 있다면 버튼 확인도 가능 | STT 변환 지연 추가 | 이미 성숙한 텍스트 에이전트가 있고 입력만 음성으로 바꾸려는 경우 |

판단 기준은 **비가역적 행동을 얼마나 세밀하게 통제해야 하는가**다. 내장 자동화는 일반적인 업무용으로는 충분하지만 확인 문구·타임아웃·취소 조건을 조직이 원하는 대로 바꿀 수 없다. 사내 결제·배포처럼 확인 정책 자체가 규정으로 정해진 영역이라면 자체 오케스트레이션으로 확인 게이트를 직접 짜야 한다.

## 실제 프로젝트 진행 순서

1. **음성으로 처리할 행동을 읽기 전용 / 가역적 / 비가역적 세 등급으로 분류한다.** 조회·요약은 즉시 실행, 초안 작성처럼 되돌릴 수 있는 것은 가벼운 확인, 발송·등록처럼 되돌리기 어려운 것은 반드시 되묻는다.
2. **비가역적 행동마다 확인 문구와 취소 명령어를 먼저 설계한다.** "내일 3시 회의로 등록하고 참석자 3명에게 슬랙 메시지를 보낼까요?"처럼 행동의 결과를 구체적으로 되읽어주는 문구가, 모호한 "진행할까요?"보다 오작동을 줄인다.
3. **턴 기반 구조를 전제로 지연시간 예산을 정한다.** 확인 질문부터 사용자 답변, 실제 실행까지 왕복이 몇 초 안에 끝나야 자연스러운지 먼저 정하고 설계 전체를 거기 맞춘다.
4. **언어 전환 미지원 같은 한계를 사용자에게 먼저 고지한다.** 대화 중 언어를 바꾸면 인식이 깨질 수 있다는 점을 숨기면, 확인 단계 자체가 엉뚱한 언어로 잘못 해석되는 사고로 이어진다.
5. **파일럿은 읽기 전용 작업부터 시작한다.** 캘린더 조회, 이메일 요약처럼 되돌릴 게 없는 작업으로 먼저 신뢰를 쌓은 뒤, 메시지 발송·일정 생성 같은 쓰기 작업으로 넓힌다.

```text
# 행동 등급별 확인 정책 설계 메모
읽기 전용(조회, 요약)        → 확인 없이 즉시 실행
가역적 쓰기(초안 작성)        → 가벼운 확인 ("초안을 보여드릴까요?")
비가역적 쓰기(발송, 일정 등록) → 결과를 구체적으로 되읽는 확인 필수
                           → "취소" 발화 시 즉시 중단, 실행 전 상태 유지
```

## 실무 포인트

- 음성 확인은 텍스트의 버튼 확인보다 모호함에 취약하다. "네"라는 대답 하나가 여러 보류 중인 행동 중 무엇을 가리키는지 명확하지 않으면, 한 번에 하나의 비가역적 행동만 확인 대기 상태로 두는 것이 안전하다.
- 다국어 지원을 턴마다 자동으로 바꿔주지 않는 한계는 확인 단계에서 특히 위험하다 — 확인 질문이 엉뚱한 언어로 나가면 사용자가 내용을 제대로 못 알아듣고 습관적으로 "네"라고 답할 수 있다.
- 내장 자동화를 쓰더라도 조직 내부 민감 행동(결제, 권한 변경)은 애초에 음성 자동화 대상에서 제외하고 사람이 직접 처리하도록 범위를 명시적으로 그어두는 편이 낫다.

## 마무리

- 음성으로 여러 앱에 걸친 작업을 처리해달라는 요구는 화면 버튼이 사라진 자리에 확인(confirmation)을 어떻게 재설계할지의 문제로 번역된다.
- 선택 기준은 비가역적 행동을 얼마나 세밀하게 통제해야 하는가이며, 일반 업무는 내장 자동화로, 규정이 있는 영역은 자체 오케스트레이션으로 확인 게이트를 짠다.
- 진행 순서는 행동 등급 분류 → 확인 문구·취소 명령 설계 → 지연시간 예산 설정 → 한계 고지 → 읽기 전용 작업부터 파일럿 순이다.
