## "직접 호출" 대신 "이벤트 발행"

주문이 완료되면 재고 차감, 포인트 적립, 알림 발송이 일어나야 한다. 주문 서비스가 이 세 서비스를 직접 호출하면, 새 후속 작업이 생길 때마다 주문 서비스 코드를 고쳐야 한다. **이벤트 기반 아키텍처**는 이를 뒤집는다. 주문 서비스는 "주문이 완료됐다"는 **이벤트**만 발행하고, 그 이벤트에 관심 있는 서비스들이 알아서 구독해 반응한다.

## 발행/구독(Pub/Sub) 구조

| 역할 | 하는 일 |
|---|---|
| 발행자(Publisher) | 이벤트를 발행 (예: "주문완료") |
| 구독자(Subscriber) | 관심 있는 이벤트를 받아 처리 |
| 이벤트 브로커 | 발행자와 구독자 사이에서 이벤트를 전달 |

```text
[직접 호출]
주문서비스 -> 재고서비스 호출
          -> 포인트서비스 호출
          -> 알림서비스 호출
(새 작업 추가 시 주문서비스 수정 필요)

[이벤트 기반]
주문서비스 -> "주문완료" 이벤트 발행
              ├─ 재고서비스가 구독해서 반응
              ├─ 포인트서비스가 구독해서 반응
              └─ 알림서비스가 구독해서 반응
(새 작업은 구독만 추가, 주문서비스는 그대로)
```

## 이벤트 기반의 장점

- **느슨한 결합**: 발행자는 누가 구독하는지 몰라도 된다. 새 구독자를 추가해도 발행자 코드는 그대로다.
- **확장 유연성**: "주문완료 시 추천 데이터도 갱신"하고 싶으면 구독자 하나만 추가하면 된다.
- **장애 격리**: 알림 서비스가 잠깐 죽어도 주문 자체는 이벤트만 발행하고 정상 완료된다.

## 실무 포인트

- **이벤트가 잘 전달됐는지, 처리에 실패하면 어떻게 할지를 반드시 설계해야 한다.** 발행만 하고 끝이 아니라, 구독자가 처리에 실패한 이벤트를 재시도하거나 별도 큐(dead letter queue)에 모아 나중에 처리하는 장치가 필요하다.
- **이벤트 순서와 중복을 고려해야 한다.** 네트워크 사정으로 이벤트가 순서가 바뀌거나 두 번 도착할 수 있으므로, 구독자는 멱등성(같은 이벤트를 여러 번 받아도 결과가 같음)을 갖추는 것이 안전하다.
- **디버깅이 어려워질 수 있다.** 직접 호출은 흐름을 코드로 따라가기 쉽지만, 이벤트는 "누가 이 이벤트를 구독하는지" 한눈에 안 보인다. 이벤트 흐름을 추적하는 관측 체계가 있어야 문제를 파악하기 쉽다.

## 마무리 요약

- 이벤트 기반 아키텍처는 서비스가 서로를 직접 호출하는 대신 이벤트를 발행/구독해 반응하는 방식이다.
- 발행자는 구독자를 몰라도 되므로 느슨한 결합과 확장 유연성, 장애 격리를 얻는다.
- 이벤트 실패 처리, 순서·중복 대응(멱등성), 흐름 추적 관측 체계가 실무에서 반드시 필요하다.
