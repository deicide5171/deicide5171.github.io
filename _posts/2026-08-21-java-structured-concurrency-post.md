`ExecutorService`로 여러 서브태스크를 병렬 실행해본 사람이라면 한 번쯤 겪었을 상황이 있다. 사용자 조회, 주문 조회, 재고 조회를 각각 별도 스레드로 던져놓고 `Future.get()`으로 결과를 기다리는데, 그중 하나가 예외를 던지면 나머지 두 작업은 어떻게 될까. 명시적으로 취소 로직을 짜두지 않는 한 그냥 백그라운드에서 계속 실행된다. 이미 필요 없어진 작업인데도 스레드 풀 자원을 붙잡고 스레드는 좀비처럼 살아있는 셈이다.

이 문제는 사실 `ExecutorService`나 `CompletableFuture` 자체의 결함이라기보다, 동시성 작업의 "생명주기"를 코드 구조가 강제하지 않기 때문에 생긴다. 서브태스크를 던지는 코드와 결과를 기다리는 코드가 물리적으로는 같은 메서드 안에 있어도, 논리적으로는 서로 독립된 생명주기를 갖는다. 하나가 실패했을 때 나머지를 취소하고, 부모 스레드가 인터럽트되면 모든 자식도 함께 종료되는 흐름을 만들려면 개발자가 매번 직접 배선해야 했다.

가상 스레드(virtual thread)가 정식으로 도입되면서 이 문제는 더 두드러지게 됐다. 스레드를 값싸게 수백만 개 만들 수 있게 되니 요청마다, 서브태스크마다 스레드를 띄우는 패턴이 자연스러워졌는데, 그럴수록 "이 스레드들이 하나의 작업 단위로 묶여 있다"는 사실을 코드로 표현할 방법이 필요해졌다. 구조화된 동시성은 바로 이 지점, 즉 동시에 실행되는 여러 스레드를 하나의 작업 단위로 묶어 실패·취소·완료를 일관되게 처리하려는 시도다. 다만 이 글을 쓰는 시점에도 관련 API는 여러 차례 인큐베이터·프리뷰 단계를 거치며 세부 사양이 계속 다듬어지고 있어서, 특정 JDK 버전에서 완전히 확정된 정식 기능이라고 단정하기는 어렵다.

## 핵심 개념 1: 서브태스크의 생명주기를 부모 범위에 묶기

구조화된 동시성의 핵심 아이디어는 단순하다. 여러 서브태스크를 병렬로 실행하더라도, 그 서브태스크들의 생명주기는 반드시 하나의 코드 블록(scope) 안에 포함되어야 한다는 원칙이다. 일반적인 구조화 프로그래밍에서 함수 호출이 끝나기 전에는 그 함수가 만든 지역 변수나 하위 호출이 살아있을 수 없는 것처럼, 동시성에서도 "부모 작업이 끝났는데 자식 스레드가 어딘가에서 계속 돌고 있는" 상황을 원천적으로 막자는 것이다.

이렇게 스코프를 명시하면 몇 가지가 자동으로 따라온다. 스코프 블록을 벗어나기 전에 모든 서브태스크가 완료되거나 취소된 상태여야 하고, 서브태스크 중 하나가 실패하면 스코프가 그 실패를 감지해 나머지 서브태스크를 취소할 수 있으며, 부모 스레드가 인터럽트되면 그 인터럽트가 자식 서브태스크에도 전파된다. 결과적으로 동시 실행 코드의 흐름이 일반 순차 코드처럼 "하나의 실행 단위 안에서 여러 갈래가 뻗어나갔다가 다시 합류하는" 형태로 읽히게 된다.

## 핵심 개념 2: StructuredTaskScope의 기본 사용법

이 아이디어를 구현한 API가 `java.util.concurrent.StructuredTaskScope`다. 기본적인 사용 흐름은 다음과 같다. try-with-resources 블록으로 스코프를 열고, `fork()`로 서브태스크를 제출한 뒤, `join()`으로 모든 서브태스크가 끝나기를 기다린다. 스코프가 닫힐 때(블록을 벗어날 때) 아직 끝나지 않은 서브태스크가 있다면 자동으로 취소를 시도한다.

스코프에는 실패 처리 정책을 다르게 가져가는 여러 구현체가 제공된다. 예를 들어 "서브태스크 중 하나라도 실패하면 즉시 나머지를 취소한다"는 정책과 "모든 서브태스크의 결과를 끝까지 모은다"는 정책이 구분되어 있어서, 상황에 맞는 스코프를 선택해 쓰는 식이다. 정확한 클래스 이름과 팩토리 메서드는 버전에 따라 조정되어 왔으므로, 실제 프로젝트에 적용할 때는 사용 중인 JDK 버전의 문서를 확인하는 편이 안전하다.

## 핵심 개념 3: 기존 CompletableFuture 조합 방식과의 차이

`CompletableFuture`로도 여러 비동기 작업을 조합하고 `allOf`나 `anyOf`로 완료를 기다릴 수 있다. 하지만 이 방식은 콜백과 조합자(combinator)를 체이닝하는 구조라서, 코드를 읽을 때 "지금 이 시점에 어떤 작업들이 동시에 살아있는가"를 한눈에 파악하기 어렵다. 특히 예외가 발생했을 때 어느 단계에서 어떤 콜백까지 실행됐는지 추적하기 번거롭고, 취소 전파도 개발자가 `cancel()` 호출을 직접 연결해줘야 명시적으로 이루어진다.

구조화된 동시성은 이런 콜백 체인 대신, 스코프라는 블록 구조로 동시성의 경계를 시각적으로도 코드 구조적으로도 명확하게 드러낸다. 스택 트레이스에도 어떤 스코프에서 어떤 서브태스크가 실패했는지가 더 자연스럽게 드러나서, 디버깅 시 "이 예외가 어느 동시 실행 단위에서 왔는가"를 추적하기 수월해진다는 장점이 있다. 다만 이는 새로운 패러다임이라기보다, 기존에도 가능했던 일을 언어·런타임 차원에서 강제하고 가독성을 높이는 방향에 가깝다.

## 예제

다음은 사용자 정보와 주문 정보를 병렬로 조회하다가, 하나가 실패하면 나머지를 취소하는 흐름을 나타낸 자바 코드다. 실제 클래스명과 메서드 시그니처는 프리뷰 단계의 변경 가능성을 감안해 개념적으로 단순화했다.

```java
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.ShutdownOnFailure;
import java.util.concurrent.StructuredTaskScope.Subtask;

class OrderService {

    Response handle(String userId, String orderId) throws InterruptedException {
        try (var scope = new ShutdownOnFailure()) {
            Subtask<User> userTask = scope.fork(() -> fetchUser(userId));
            Subtask<Order> orderTask = scope.fork(() -> fetchOrder(orderId));

            scope.join();           // 두 서브태스크가 끝날 때까지 대기
            scope.throwIfFailed();  // 하나라도 실패했으면 예외로 전파

            // 여기 도달했다면 두 서브태스크 모두 성공한 것
            return new Response(userTask.get(), orderTask.get());
        }
        // 스코프 블록을 벗어나기 전에, 실패한 서브태스크가 있었다면
        // 나머지 서브태스크는 이미 취소가 시도된 상태다.
    }

    User fetchUser(String userId) { /* 원격 호출 등 */ return null; }
    Order fetchOrder(String orderId) { /* 원격 호출 등 */ return null; }
}
```

`fetchOrder`가 예외를 던지면 `scope.join()` 시점에 스코프가 이를 감지하고 `fetchUser` 서브태스크에 취소(인터럽트)를 시도한다. 개발자가 별도로 `Future.cancel()`을 호출하거나 취소 신호를 수동으로 배선할 필요가 없다는 점이 기존 방식과의 가장 실질적인 차이다.

## 실무 포인트

- **프리뷰/인큐베이터 단계로서의 API 안정성**: 구조화된 동시성 관련 API는 여러 JDK 버전에 걸쳐 인큐베이터와 프리뷰 단계를 반복해왔고, 클래스명이나 메서드 시그니처가 버전 사이에 조정된 이력이 있다. 프로덕션 코드에 도입하기 전에는 사용 중인 JDK 버전에서 이 기능이 정식(GA)인지, 여전히 `--enable-preview` 플래그가 필요한 프리뷰 상태인지 반드시 확인해야 한다.
- **가상 스레드와의 시너지**: 구조화된 동시성은 가상 스레드와 함께 쓸 때 특히 효과적이다. 서브태스크마다 가상 스레드를 하나씩 띄워도 플랫폼 스레드처럼 자원 부담이 크지 않기 때문에, "요청 하나마다 필요한 만큼 서브태스크를 fork하고 스코프로 묶는" 패턴을 부담 없이 쓸 수 있다.
- **관측 가능성 개선 여지**: 스코프 단위로 작업이 묶이면 스레드 덤프나 로깅에서도 어떤 서브태스크들이 하나의 논리적 작업에 속하는지 더 명확하게 드러날 여지가 있다. 다만 이는 API 성숙도와 함께 도구 생태계(APM, 프로파일러 등)의 지원이 따라와야 완전히 체감되는 부분이다.
- **기존 코드 전환은 점진적으로**: `ExecutorService` 기반 코드를 한 번에 전면 교체하기보다는, 실패 시 취소 로직이 특히 복잡했던 부분부터 구조화된 동시성으로 옮겨보고 안정성을 검증하는 편이 안전하다.

## 3줄 요약

- 기존 `ExecutorService`/`CompletableFuture` 조합 방식은 서브태스크 중 하나가 실패해도 나머지를 취소하는 로직을 개발자가 직접 배선해야 했다.
- 구조화된 동시성은 서브태스크의 생명주기를 부모 스코프 블록 안에 강제로 묶어, 실패 시 자동 취소와 인터럽트 전파를 일관되게 처리하려는 접근이다.
- `StructuredTaskScope` API는 가상 스레드와 시너지가 크지만 여전히 프리뷰/인큐베이터 단계를 거치는 중이므로, 실무 도입 전에는 사용 중인 JDK 버전의 기능 상태를 반드시 확인해야 한다.
