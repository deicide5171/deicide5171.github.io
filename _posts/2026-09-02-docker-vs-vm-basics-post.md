## 왜 둘 다 "격리된 환경"인데 이름이 다른가

가상머신도 컨테이너도 "하나의 서버 안에서 여러 애플리케이션을 서로 영향받지 않게 격리해서 실행한다"는 목표는 같다. 하지만 격리를 만드는 방식이 완전히 다르다. 이 차이를 모르면 "왜 컨테이너는 이렇게 가볍고 빠르게 뜨는가"를 이해할 수 없다.

## 구조적 차이

| 항목 | 가상머신(VM) | 컨테이너(Docker) |
|---|---|---|
| 격리 단위 | 하이퍼바이저 위에 OS 전체를 통째로 실행 | 호스트 OS 커널을 공유하며 프로세스 단위로 격리 |
| 부팅 시간 | 수십 초~수 분(OS 전체 부팅) | 1초 내외(프로세스 시작 수준) |
| 자원 오버헤드 | 큼(OS마다 커널·드라이버 중복) | 작음(커널 공유) |
| 이식성 | 이미지 용량이 크고 무거움 | 이미지가 상대적으로 작고 빠르게 배포 가능 |
| 격리 강도 | 강함(커널 자체가 분리) | VM보다 약함(커널을 공유하므로) |

## 그림으로 보는 구조 차이

```text
가상머신 구조:
하드웨어 -> 하이퍼바이저 -> [Guest OS + 앱A] [Guest OS + 앱B]
(각 VM마다 완전한 OS 커널을 따로 가짐)

컨테이너 구조:
하드웨어 -> 호스트 OS 커널 -> [컨테이너A: 앱A+라이브러리] [컨테이너B: 앱B+라이브러리]
(커널은 하나를 공유하고, 프로세스와 파일시스템만 격리)
```

## 코드 예제: 체감 차이

```bash
# 컨테이너: 몇 초 안에 격리된 환경이 뜬다
docker run -it ubuntu:22.04 bash

# 가상머신: OS 설치·부팅 과정을 거쳐야 한다 (수 분 소요)
# VirtualBox, VMware 등으로 OS 이미지를 통째로 부팅
```

컨테이너는 호스트의 리눅스 커널을 그대로 빌려 쓰기 때문에, 실행할 때 커널을 새로 부팅할 필요가 없다. 이것이 컨테이너가 VM보다 압도적으로 빠르게 시작되는 이유다.

## 실무 포인트

- **컨테이너는 호스트와 커널을 공유하므로, 리눅스 컨테이너는 리눅스 호스트에서만 네이티브로 동작한다.** macOS나 Windows에서 Docker를 쓰면 내부적으로 경량 리눅스 VM을 하나 띄우고 그 위에서 컨테이너를 실행하는 구조다.
- **보안이 매우 중요한 멀티테넌시 환경(여러 고객사의 코드를 한 서버에서 돌리는 경우)에서는 컨테이너의 격리 강도가 VM보다 약하다는 점을 고려해야 한다.** 이런 경우 gVisor나 Firecracker 같은 경량 VM 기반 격리 기술을 함께 검토하기도 한다.
- **"컨테이너가 VM을 완전히 대체한다"는 것은 오해다.** 실무에서는 클라우드 VM(예: EC2) 위에 컨테이너 오케스트레이션(쿠버네티스)을 올리는 구조가 흔하다. 즉 둘은 경쟁 관계라기보다 계층을 이루는 관계에 가깝다.

## 마무리 요약

- 가상머신은 OS 전체를 통째로 격리하고, 컨테이너는 호스트 커널을 공유하며 프로세스 단위로 격리한다.
- 이 구조 차이 때문에 컨테이너는 VM보다 훨씬 가볍고 빠르게 시작된다.
- 격리 강도는 VM이 더 강하므로, 강한 보안 격리가 필요한 상황에서는 컨테이너의 한계를 고려해야 한다.
