## 왜 지금 이 판단이 불거지는가

"결제 직전에 사기 거래인지 체감 지연 없이 판단해주세요." "사용자가 입력하는 즉시 개인화 추천이 바뀌어야 합니다." 이런 요구를 받으면 흔히 "모델을 더 가볍게 만들자" 또는 "캐시를 더 늘리자"로 접근하기 쉽지만, 2026년 들어 더 근본적인 해법이 실용적인 선택지로 올라왔다. 바로 계산 자체를 사용자와 물리적으로 가까운 곳에서 수행하는 엣지 배치다. 중앙집중형 클라우드에서 왕복 지연이 100~250ms인 데 비해, 엣지 네트워크에서는 네트워크 지연이 2~15ms, 경량 모델 추론도 NPU가 붙은 엣지 노드에서 약 50ms 수준으로 내려왔다는 수치가 보고되고 있다. Cloudflare Workers AI 같은 플랫폼은 330개가 넘는 전 세계 거점에서 V8 isolate 기반으로 콜드 스타트 없이 코드를 실행하고, 텍스트 분류·임베딩·모더레이션처럼 가벼운 추론을 거점에서 직접 처리한다. 실제 사례로 AI API 호출 지연을 850ms에서 150ms로 줄인 경우까지 보고됐다.

이게 빌더에게 중요한 이유는, "성능이 부족하면 서버를 늘린다"는 익숙한 해법만으로는 물리적 거리에서 오는 지연을 줄일 수 없기 때문이다. 서울 사용자의 요청이 버지니아 리전까지 왕복하는 데 걸리는 시간은 서버를 아무리 늘려도 광속의 한계 안에서 고정돼 있다. 엣지 컴퓨팅은 이 문제를 "더 빠른 서버"가 아니라 "더 가까운 서버"로 접근한다. 하지만 모든 로직을 엣지로 밀어 넣을 수는 없다. 이 글은 어떤 로직이 엣지로 내려갈 수 있고, 무엇은 절대 안 되는지를 가르는 기준을 정리한다.

## 요구사항을 기술 문제로 번역하기

"체감 지연 없이 처리해주세요"라는 요구는 사실 그 로직이 필요로 하는 **데이터의 범위와 신선도**를 먼저 따지는 문제로 번역된다. 사기 탐지 로직이 "이 거래 하나의 금액·시간·디바이스 정보"만으로 판단 가능하다면 요청 안에 담긴 정보만으로 완결되므로 엣지에서 처리할 수 있다. 하지만 "이 사용자의 최근 30일 거래 패턴 전체와 대조해야 한다"면 그 패턴 데이터가 중앙 데이터베이스에만 있으므로, 엣지에서 처리하려는 순간 결국 중앙으로 왕복 조회가 발생해 엣지의 이점이 사라진다. 즉 핵심 질문은 "이 요청을 처리하는 데 **요청 자체에 포함된 정보만으로 충분한가, 아니면 공유된 중앙 상태를 참조해야 하는가**"이다. 전자는 엣지 배치의 후보고, 후자는 아키텍처를 바꾼다고 해결되지 않는 근본적 제약이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-07-edge-vs-central-compute-placement-1.svg" alt="사용자 요청이 가장 가까운 엣지 PoP에 먼저 도달해 요청 자체로 완결되는 가벼운 로직과 경량 모델 추론을 즉시 처리하고, 중앙 상태나 트랜잭션 일관성이 필요한 요청만 origin 리전의 중앙 서버와 DB로 전달되는 하이브리드 구조를 보여주는 다이어그램" style="width:100%;">

엣지 배치를 도입한 시스템에서 요청은 더 이상 곧장 중앙 리전으로 가지 않는다. 사용자와 가장 가까운 엣지 PoP(Point of Presence)가 1차 관문이 된다. 여기서 요청 자체에 담긴 정보만으로 완결되는 로직 — 입력값 검증, 간단한 라우팅 결정, 경량 모델을 통한 텍스트 분류나 모더레이션 — 은 origin까지 왕복하지 않고 그 자리에서 끝난다. 반면 사용자 전체 이력 조회, 재고 차감처럼 트랜잭션 일관성이 필요한 쓰기, 여러 사용자 간 공유 상태를 다뤄야 하는 로직은 여전히 origin 리전의 중앙 서버와 데이터베이스로 전달된다. 즉 엣지는 중앙 인프라를 대체하는 게 아니라, 중앙 인프라 앞단에 놓인 "빠른 필터이자 1차 처리 계층"으로 시스템에 자리 잡는다.

## 선택의 트레이드오프

| 기준 | 완전 중앙 집중 | 완전 엣지 배치 | 하이브리드(엣지 1차 + 중앙 2차) |
|---|---|---|---|
| 체감 지연 | 거리에 비례해 증가 | 매우 낮음 | 로직별로 다름 |
| 모델/로직 크기 제약 | 제약 거의 없음 | 메모리·실행시간 제한 엄격 | 엣지는 경량, 중앙은 자유 |
| 데이터 일관성 | 강함 | 공유 상태 접근 시 깨지기 쉬움 | 상태가 필요한 로직은 중앙에 남김 |
| 운영·디버깅 복잡도 | 낮음 | 분산된 거점의 로그·트레이스 수집이 어려움 | 중간 (관측성 설계가 핵심) |
| 비용 구조 | 리전 단위 정산 | 요청 단위 과금이 흔함 | 트래픽 패턴에 따라 유불리 갈림 |

이 표에서 가장 자주 오판하는 줄은 "모델/로직 크기 제약"이다. 엣지 런타임은 기본적으로 메모리와 실행 시간에 엄격한 제한을 두기 때문에, 중앙에서 잘 돌아가던 모델이나 로직을 그대로 옮기는 건 거의 항상 불가능하다. 엣지로 내릴 로직은 애초에 그 제약에 맞게 다시 설계해야 한다는 전제를 깔고 시작해야 한다.

## 실제 프로젝트 진행 순서

1. **지연에 가장 민감한 요청 경로부터 식별한다.** 사용자가 체감하는 지연이 이탈률이나 전환율에 직접 영향을 주는 구간(결제 직전 검증, 실시간 추천, 입력 즉시 반응)을 먼저 추린다.
2. **그 경로가 필요로 하는 데이터의 범위를 파악한다.** 요청 자체의 정보만으로 완결되는지, 아니면 중앙의 공유 상태를 참조해야 하는지 하나씩 확인한다. 후자라면 엣지 배치 후보에서 바로 제외한다.
3. **엣지 런타임의 제약에 맞게 로직·모델을 축소할 수 있는지 검증한다.** 메모리 한도, 실행 시간 한도, 지원되는 라이브러리 범위를 먼저 확인하고, 중앙 버전을 그대로 포팅하려 하지 않는다.
4. **엣지에서 처리 불가능한 예외 케이스의 폴백 경로를 설계한다.** 엣지 판단이 애매하거나 실패하면 중앙 origin으로 즉시 넘기는 라우팅을 함께 설계해, 엣지가 단일 장애점이 되지 않게 한다.
5. **분산된 거점의 관측성을 먼저 확보한다.** 엣지로 트래픽을 내리기 전에 각 거점의 로그·트레이스를 중앙에서 수집할 수 있는 파이프라인부터 갖춘다. 이게 없으면 장애 발생 시 어느 거점에서 무슨 일이 있었는지 알 방법이 없다.
6. **퍼센트 기반 트래픽 분할로 점진적으로 검증한다.** 전체 트래픽을 한 번에 엣지로 옮기지 말고, 일부 비율만 엣지 경로로 보내 지연 개선 효과와 오류율을 비교한 뒤 범위를 넓힌다.

## 코드 예시 — 엣지에서 완결되는 경량 판단

```javascript
// Cloudflare Workers 스타일 — 요청 자체 정보만으로 완결되는 1차 필터
export default {
  async fetch(request, env) {
    const body = await request.json();
    const risk = quickRiskScore(body.amount, body.deviceFingerprint);

    if (risk < env.EDGE_THRESHOLD) {
      return Response.json({ decision: "approve", processedAt: "edge" });
    }
    // 애매하거나 고위험이면 중앙 origin으로 폴백
    return fetch(env.ORIGIN_URL + "/fraud-check", { method: "POST", body: JSON.stringify(body) });
  }
};
```

## 실무 포인트

**콜드 스타트가 없다고 "상태를 유지할 수 있다"로 착각하지 않는다.** V8 isolate 기반 엣지 런타임은 매 요청을 거의 독립적으로 처리하도록 설계돼 있다. 세션이나 누적 상태가 필요한 로직을 엣지에 그대로 옮기면 예상치 못한 불일치가 생긴다.

**모든 걸 엣지로 보내려는 유혹을 경계한다.** 지연을 줄이고 싶은 마음에 공유 상태가 필요한 로직까지 억지로 엣지로 내리면, 결국 매 요청이 중앙으로 왕복 조회를 하게 되어 엣지의 이점이 사라지고 복잡도만 늘어난다.

**디버깅 난이도 상승을 미리 각오한다.** 문제가 특정 거점에서만 재현되는 경우, 그 거점의 런타임 버전·네트워크 상태까지 함께 확인해야 하므로 중앙 집중 구조보다 장애 분석에 걸리는 시간이 늘어날 수 있다.

## 마무리

- 중앙 집중 구조는 서버를 늘려도 물리적 거리에서 오는 지연을 줄이지 못하며, 엣지 컴퓨팅은 "더 빠른 서버"가 아니라 "더 가까운 서버"로 이 문제에 접근한다.
- 핵심 판단 기준은 "요청 자체의 정보만으로 완결되는가, 공유된 중앙 상태를 참조해야 하는가"이며, 후자는 아키텍처를 바꿔도 해결되지 않는 근본 제약이다.
- 실제 도입은 지연에 민감한 경로를 먼저 식별하고, 엣지 런타임 제약에 맞게 로직을 다시 설계한 뒤, 폴백 경로와 관측성을 먼저 갖추고 점진적으로 트래픽을 옮기는 순서로 진행해야 안전하다.
