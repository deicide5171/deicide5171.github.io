`docker run`으로 컨테이너 하나를 띄우면 마치 독립된 작은 머신이 하나 생긴 것처럼 느껴진다. 자기만의 프로세스 목록, 자기만의 네트워크 인터페이스, 자기만의 파일시스템 루트를 갖는 것처럼 보인다. 하지만 실제로는 호스트와 완전히 같은 리눅스 커널 위에서 돌아가는 평범한 프로세스일 뿐이다. VM처럼 하이퍼바이저가 하드웨어를 가상화하고 별도의 커널을 부팅하는 구조가 아니다.

이 "격리된 것처럼 보이는 프로세스"를 만드는 실체는 도커나 컨테이너 런타임이 새로 발명한 기술이 아니라, 리눅스 커널에 오래전부터 존재해 온 두 가지 기능이다. 하나는 **네임스페이스(namespace)** 로, 프로세스가 커널 자원을 바라보는 뷰 자체를 분리한다. 다른 하나는 **cgroups(control groups)** 로, 프로세스 그룹이 실제로 소비할 수 있는 자원의 양에 상한을 건다. 도커·containerd·podman 같은 도구들은 이 두 커널 기능을 조합해서 호출해주는 편의 계층에 가깝고, 격리와 제한의 실질적인 작업은 커널이 한다.

이 글에서는 "컨테이너 기술"이라는 하나의 덩어리로 뭉뚱그려 보던 것을 네임스페이스와 cgroups라는 두 축으로 나눠서, 각각이 정확히 무엇을 하는지 살펴본다.

## 핵심 개념 1: 네임스페이스 — 무엇이 보이는지를 분리한다

네임스페이스는 프로세스마다 특정 커널 자료구조에 대해 서로 다른 "뷰"를 부여하는 기능이다. 자원을 실제로 나누는 것이 아니라, 같은 커널 안에 있는 자원 중 어디까지를 보여줄지를 프로세스 단위로 다르게 설정한다는 점이 핵심이다. 대표적인 네임스페이스 종류는 다음과 같다.

- **PID 네임스페이스**: 컨테이너 안의 첫 프로세스가 PID 1로 보이도록 만든다. 호스트에서는 그 프로세스가 실제로는 수천 번대 PID를 가진 평범한 프로세스일 수 있지만, 해당 네임스페이스 안에서는 자신이 PID 1이라고 인식한다.
- **네트워크(net) 네임스페이스**: 독자적인 네트워크 인터페이스, 라우팅 테이블, 포트 공간을 부여한다. 컨테이너 여러 개가 같은 80번 포트를 각자 사용할 수 있는 이유가 여기에 있다.
- **마운트(mnt) 네임스페이스**: 파일시스템 마운트 지점의 뷰를 분리한다. 컨테이너 이미지의 루트 파일시스템을 호스트의 실제 디렉터리 구조와 다르게 보이도록 만드는 기반이다.
- **UTS 네임스페이스**: 호스트명(hostname)과 도메인명을 분리해, 컨테이너마다 다른 호스트명을 가질 수 있게 한다.
- **IPC 네임스페이스**: 공유 메모리 세그먼트, 세마포어, 메시지 큐 같은 프로세스 간 통신 자원을 분리한다.
- **유저(user) 네임스페이스**: 컨테이너 내부의 UID/GID를 호스트의 UID/GID와 다르게 매핑한다. 컨테이너 안에서는 root(UID 0)처럼 보이는 프로세스가 호스트에서는 권한 없는 일반 사용자로 매핑되도록 구성할 수 있어, 컨테이너 탈출 시 피해 범위를 줄이는 데 쓰인다.

이 여섯 가지 외에도 cgroup 자체의 뷰를 분리하는 cgroup 네임스페이스, 시간 관련 값을 분리하는 time 네임스페이스가 존재한다. 중요한 것은 이들이 각각 독립적으로 켜고 끌 수 있다는 점이다. 컨테이너 런타임은 보통 이 여러 네임스페이스를 한꺼번에 새로 만들어 프로세스를 그 안에 넣는 방식으로 동작한다.

## 핵심 개념 2: cgroups — 얼마나 쓸 수 있는지를 제한한다

네임스페이스가 "무엇이 보이는가"를 다룬다면, cgroups는 "얼마나 쓸 수 있는가"를 다룬다. 프로세스를 하나의 그룹으로 묶고, 그 그룹 전체에 대해 CPU 시간, 메모리, 블록 I/O, 네트워크 대역폭 같은 자원의 사용량 상한이나 우선순위를 커널이 강제하도록 설정하는 기능이다.

cgroups는 컨트롤러(controller) 단위로 나뉜다. `cpu` 컨트롤러는 CPU 시간 할당 비율이나 상한을, `memory` 컨트롤러는 메모리 사용량 상한과 초과 시 동작(OOM kill 등)을, `io`(구 버전에서는 `blkio`) 컨트롤러는 디스크 I/O 대역폭을 제어한다. 각 컨트롤러는 파일시스템처럼 마운트된 가상 파일시스템(`/sys/fs/cgroup` 하위)의 파일을 읽고 쓰는 방식으로 설정값을 조회하고 변경한다. 별도의 API 호출이 아니라 일반 파일 읽기·쓰기 인터페이스라는 점이 리눅스답다.

네임스페이스가 "이 프로세스는 다른 프로세스를 못 보게 하자"는 격리라면, cgroups는 "이 프로세스 그룹이 호스트의 CPU를 다 잡아먹지 못하게 하자"는 자원 통제다. 컨테이너 하나가 폭주해도 같은 호스트의 다른 컨테이너나 호스트 자체의 프로세스에 영향을 최소화하는 것이 cgroups의 역할이다.

## 핵심 개념 3: 두 메커니즘의 결합이 "컨테이너"다

정리하면, "컨테이너를 만든다"는 것은 커널 관점에서 다음 두 단계로 요약된다.

1. 새 프로세스를 여러 네임스페이스(PID, net, mnt, UTS, IPC, user 등) 안에 격리해서 실행한다.
2. 그 프로세스(정확히는 프로세스가 속한 cgroup)에 CPU·메모리·I/O 사용량 상한을 건다.

도커 같은 런타임이 하는 일은 이 두 커널 기능을 이미지 레이어, 네트워크 설정, 볼륨 마운트 같은 개념과 엮어서 사용자에게 편리한 CLI로 제공하는 것이다. 실제 격리와 제한이 일어나는 지점은 어디까지나 커널의 네임스페이스·cgroups 서브시스템이다. 이 관점을 이해하면 "컨테이너 보안"이 곧 "네임스페이스가 얼마나 촘촘히 분리되어 있는가"와 "cgroups가 자원 남용을 얼마나 잘 막는가"의 문제로 좁혀진다는 것도 자연스럽게 이해된다.

## 예제

`unshare` 명령으로 네임스페이스가 실제로 프로세스의 뷰를 바꾸는 모습을 직접 확인할 수 있다.

```bash
# 새 PID·마운트·UTS 네임스페이스에서 셸을 실행
sudo unshare --pid --mount --uts --fork --mount-proc /bin/bash

# 이 셸 안에서 hostname을 바꿔도 호스트에는 영향을 주지 않는다
hostname sandbox-test
hostname

# ps를 보면 자신이 PID 1(또는 그에 가까운 낮은 번호)로 보인다
ps aux
```

cgroup v2는 `/sys/fs/cgroup` 아래 가상 파일시스템을 통해 조작한다.

```bash
# 새 cgroup 생성 (디렉터리를 만드는 것만으로 cgroup이 생성된다)
sudo mkdir /sys/fs/cgroup/demo

# CPU 사용량을 100ms 주기 중 20ms로 제한 (약 20%)
echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max

# 메모리 사용량 상한을 200MB로 설정
echo "200M" | sudo tee /sys/fs/cgroup/demo/memory.max

# 현재 셸 프로세스를 이 cgroup에 등록
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs
```

## 실무 포인트

- **cgroup v1과 v2의 계층 구조가 다르다**: v1은 컨트롤러마다 독립된 계층 트리를 가질 수 있어 같은 프로세스가 CPU 계층에서는 A 그룹, 메모리 계층에서는 B 그룹에 속하는 구조가 가능했다. v2는 단일 통합 계층(unified hierarchy)으로 정리되어 하나의 트리에 모든 컨트롤러가 함께 붙는다. 최근 배포판과 컨테이너 런타임은 대부분 v2를 기본으로 채택하는 추세이지만, 운영 중인 호스트가 어느 버전을 쓰는지는 `mount | grep cgroup` 등으로 직접 확인해야 하며 배포판·커널 버전에 따라 차이가 있을 수 있다.
- **메모리 제한과 OOM 동작을 함께 이해해야 한다**: `memory.max`를 넘기면 해당 cgroup 안의 프로세스가 커널 OOM killer에 의해 종료될 수 있다. 애플리케이션이 이 상한을 알지 못한 채 힙 크기를 호스트 전체 메모리 기준으로 잡으면, 컨테이너 안에서만 예기치 않게 죽는 문제가 반복될 수 있다.
- **네임스페이스 격리와 커널 취약점은 별개 문제다**: 네임스페이스는 커널이 제공하는 논리적 격리이지, 하드웨어 수준의 격리가 아니다. 커널 자체의 취약점이 발견되면 네임스페이스 경계를 우회해 호스트나 다른 컨테이너에 영향을 줄 수 있다는 점은 VM 대비 컨테이너의 구조적 한계로 남아 있다.
- **자원 제한을 안 걸어두면 "하나가 다 죽인다"는 흔한 실수가 재현된다**: cgroup 자원 제한 없이 컨테이너를 띄우면, 컨테이너 하나의 프로세스 폭주가 같은 호스트의 다른 워크로드까지 함께 무너뜨릴 수 있다. 오케스트레이션 도구에서 리소스 request/limit을 설정하는 것은 결국 이 cgroups 상한을 대신 관리해주는 것이라는 점을 기억할 만하다.

## 3줄 요약

- 컨테이너는 별도 커널을 가진 VM이 아니라, 같은 리눅스 커널 위에서 네임스페이스로 뷰가 분리되고 cgroups로 자원이 제한된 프로세스일 뿐이다.
- 네임스페이스(PID, 네트워크, 마운트, UTS, IPC, 유저 등)는 "무엇이 보이는가"를, cgroups(CPU, 메모리, I/O 컨트롤러)는 "얼마나 쓸 수 있는가"를 각각 담당한다.
- 컨테이너 런타임은 이 두 커널 기능을 편리하게 조합해주는 계층일 뿐이며, cgroup v1/v2 차이와 메모리 상한 초과 시 OOM 동작을 실무에서 미리 점검해야 한다.
