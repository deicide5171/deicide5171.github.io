## 컨테이너가 많아지면 손으로 관리할 수 없다

Docker로 컨테이너 하나 띄우는 건 쉽다. 그런데 서비스가 커져 컨테이너가 수십 개가 되고, 여러 서버에 흩어져 돌고, 하나가 죽으면 다시 띄워야 하고, 트래픽에 따라 개수를 조절해야 한다면 손으로는 불가능하다. **쿠버네티스(Kubernetes)**는 이 수많은 컨테이너를 자동으로 배치·복구·확장·관리해주는 컨테이너 오케스트레이션 도구다.

## 쿠버네티스가 자동으로 해주는 것

| 기능 | 설명 |
|---|---|
| 스케줄링 | 컨테이너를 어느 서버에 배치할지 자동 결정 |
| 자가 복구 | 죽은 컨테이너를 감지해 자동으로 다시 띄움 |
| 오토스케일링 | 트래픽에 따라 컨테이너 개수 자동 조절 |
| 로드밸런싱 | 여러 컨테이너로 요청을 나눠 보냄 |
| 롤링 업데이트 | 서비스 중단 없이 새 버전 배포 |

## 핵심 용어 몇 가지

```text
Pod: 쿠버네티스가 배포하는 가장 작은 단위(보통 컨테이너 1개)
Deployment: Pod를 몇 개 유지할지, 어떻게 업데이트할지 정의
Service: Pod들에 접근하는 안정적인 주소·로드밸런싱 제공
Node: Pod가 실제로 돌아가는 서버(물리/가상)
```

## 선언적 방식이 핵심

```yaml
# "이 앱을 3개 유지해줘"라고 원하는 상태를 선언
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3   # 항상 3개가 돌도록
  ...
```

쿠버네티스의 핵심 철학은 **선언적 관리**다. "이렇게 해라"가 아니라 "이런 상태였으면 좋겠다"를 선언하면, 쿠버네티스가 현재 상태를 그 목표 상태로 계속 맞춘다. 하나가 죽어 2개가 되면 알아서 1개를 더 띄워 3개를 유지한다.

## 실무 포인트

- **작은 서비스에는 쿠버네티스가 과할 수 있다.** 컨테이너 몇 개 수준이라면 쿠버네티스의 복잡도가 이득보다 클 수 있다. 관리형 서비스(ECS, Cloud Run 등)나 단순 배포로 충분한 경우도 많다.
- **학습 곡선이 가파르다.** 개념과 용어가 많아 처음에는 어렵다. 직접 클러스터를 운영하기보다 관리형 쿠버네티스(EKS, GKE 등)로 시작하면 인프라 관리 부담을 덜 수 있다.
- **선언적 상태 관리에 익숙해지는 것이 중요하다.** 명령형으로 하나씩 조작하기보다, 원하는 상태를 YAML로 선언하고 버전 관리(GitOps)하는 방식이 쿠버네티스를 제대로 쓰는 길이다.

## 마무리 요약

- 쿠버네티스는 수많은 컨테이너를 자동으로 배치·복구·확장·관리하는 오케스트레이션 도구다.
- 스케줄링·자가 복구·오토스케일링·롤링 업데이트를 자동으로 해준다.
- "원하는 상태를 선언"하는 선언적 관리가 핵심 철학이며, 작은 서비스에는 과할 수 있다.
