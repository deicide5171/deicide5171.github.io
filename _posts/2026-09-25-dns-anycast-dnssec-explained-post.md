## 왜 지금 Anycast와 DNSSEC을 다시 봐야 하는가

CDN이나 퍼블릭 DNS 리졸버(1.1.1.1, 8.8.8.8)를 쓰다 보면 당연하게 여기는 사실이 있다 — 서울에서 접속하든 뉴욕에서 접속하든 같은 IP 주소로 요청을 보내는데, 실제로는 각자 물리적으로 가장 가까운 서버가 응답한다는 것이다. 이게 어떻게 가능한지 이해하려면 유니캐스트(Unicast)라는 기본 전제 자체를 다시 봐야 한다. 인터넷 라우팅은 원래 "하나의 IP는 하나의 물리적 위치를 가리킨다"는 유니캐스트를 기본으로 설계됐다. Anycast는 이 전제를 의도적으로 깨는 라우팅 기법으로, 오늘날 대규모 DNS 인프라와 CDN의 가용성·지연시간을 지탱하는 핵심 기술이다. 한편 DNS 자체는 애초에 보안을 염두에 두지 않고 설계된 프로토콜이라, 응답을 위조해 사용자를 가짜 사이트로 유도하는 캐시 포이즈닝 공격에 취약했다. DNSSEC은 DNS 응답에 암호학적 서명을 추가해 이 취약점을 구조적으로 메꾸는 확장 표준이다.

## 핵심 개념 1 — Anycast: 같은 IP를 여러 위치에서 동시에 광고한다

Anycast의 핵심 아이디어는 전 세계에 흩어진 여러 물리적 서버(또는 데이터센터)가 정확히 동일한 IP 주소를 BGP(Border Gateway Protocol)를 통해 동시에 광고(announce)하는 것이다. 인터넷을 구성하는 라우터들은 이 IP로 가는 여러 경로 중 자신에게 가장 홉 수가 적거나 비용이 낮은 경로를 선택해 트래픽을 전달한다. 결과적으로 서울의 사용자는 자연스럽게 서울(또는 가장 가까운) 리전의 서버로, 뉴욕의 사용자는 뉴욕 리전의 서버로 라우팅된다 — 클라이언트나 DNS 계층의 별도 개입 없이, 순수하게 BGP 라우팅 테이블 수준에서 트래픽 분산이 일어난다. 이 구조는 지연시간 감소뿐 아니라 DDoS 방어에도 강력한데, 공격 트래픽이 전 세계에서 발생하면 그 트래픽도 각 지역의 Anycast 노드로 자동 분산되어 한 곳에 집중되지 않기 때문이다.

## 핵심 개념 2 — DNSSEC: 응답에 서명을 붙여 위조를 검증 가능하게 만든다

일반 DNS는 UDP 기반의 평문 프로토콜이라, 공격자가 정당한 응답보다 먼저 위조된 응답을 리졸버에 주입하면(캐시 포이즈닝) 사용자를 가짜 IP로 유도할 수 있다. DNSSEC은 이 문제를 "응답이 진짜인지 확인할 방법"을 추가해서 해결한다. 각 DNS 존(zone)은 자신의 레코드에 개인키로 서명한 RRSIG 레코드를 함께 배포하고, 그 서명을 검증할 공개키(DNSKEY)도 함께 공개한다. 여기서 핵심은 이 신뢰가 DNS의 계층 구조를 따라 사슬처럼 이어진다는 점이다 — 루트 존이 최상위 도메인(.com 등)의 공개키가 진짜임을 서명하고, .com 존이 그 하위 도메인의 공개키가 진짜임을 서명하는 식으로, 루트의 신뢰가 각 도메인까지 체인으로 전파된다. 리졸버는 이 체인을 루트부터 끝까지 검증해, 중간의 어느 한 링크라도 위조되면 검증에 실패해 응답을 폐기한다.

| 항목 | 일반 DNS | DNSSEC |
|---|---|---|
| 응답 위조 방지 | 없음(평문, 검증 불가) | RRSIG 서명으로 검증 가능 |
| 신뢰 근거 | 없음(먼저 도착한 응답을 신뢰) | 루트부터 이어지는 서명 체인 |
| 데이터 기밀성 | 제공 안 함(암호화 아님) | 마찬가지로 제공 안 함(서명일 뿐) |
| 도입 부담 | 없음 | 키 관리·롤오버 운영 필요 |

## 예제 — DNSSEC 체인 확인 및 Anycast IP 조회

```bash
# DNSSEC 서명 체인이 유효한지 확인 (dig +dnssec)
dig +dnssec example.com A
# ad(Authenticated Data) 플래그가 있으면 검증 성공

# 신뢰 체인을 단계별로 추적
delv example.com A  # BIND의 delv 도구가 루트부터 체인 검증 과정을 출력

# 같은 Anycast IP가 지역마다 다른 물리 서버로 응답하는 것을 간접 확인
dig @1.1.1.1 whoami.cloudflare.com TXT +short  # 접속한 위치의 엣지 서버 정보 반환
```

## 실무 포인트

- **자체 서비스에 Anycast를 직접 구축하려면 자체 AS(Autonomous System) 번호와 BGP 피어링이 필요해, 대부분의 조직에는 비현실적이다.** 실무에서는 Cloudflare, AWS Global Accelerator, Route 53 같은 관리형 Anycast 네트워크를 활용하는 것이 일반적인 선택이다.
- **DNSSEC은 위조를 막을 뿐 가용성 문제를 만들 수도 있다는 점을 알아야 한다.** 서명 키 롤오버를 잘못 수행하면 도메인 전체가 검증 실패로 응답 불가 상태에 빠질 수 있으므로, 키 교체 작업은 TTL과 겹침 기간을 충분히 고려해 신중히 진행해야 한다.
- **DNSSEC은 기밀성을 제공하지 않는다는 점을 혼동하지 마라.** 서명은 "이 응답이 변조되지 않았다"를 보장할 뿐, 질의 내용 자체를 암호화하지는 않는다. 질의 프라이버시가 필요하다면 DoH(DNS over HTTPS)나 DoT(DNS over TLS)를 별도로 검토해야 한다.

## 마무리 요약

- Anycast는 여러 물리적 위치가 동일한 IP를 BGP로 동시에 광고해, 별도 리다이렉트 없이 라우팅 테이블 수준에서 사용자를 가장 가까운 서버로 자동 연결하는 기법이다.
- DNSSEC은 루트부터 도메인까지 이어지는 서명 체인으로 DNS 응답의 위조 여부를 검증 가능하게 만들어 캐시 포이즈닝 공격을 구조적으로 막는다.
- 두 기술 모두 대부분의 조직에서는 직접 구축하기보다 관리형 서비스를 활용하는 것이 현실적이며, DNSSEC은 키 롤오버 운영 실수가 오히려 장애를 유발할 수 있다는 점을 유의해야 한다.
