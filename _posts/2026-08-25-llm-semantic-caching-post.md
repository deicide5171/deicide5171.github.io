프로덕션에 붙인 LLM 기능의 API 비용 로그를 뜯어보면 의외로 "완전히 새로운 질문"은 그렇게 많지 않다. 고객 지원 챗봇이라면 "환불 어떻게 하나요", "환불 절차 알려주세요", "환불받고 싶은데 어떻게 해요" 같은 문장이 하루에도 수백 번 들어온다. 문자열은 다 다르지만 의미는 같다. 그런데 흔히 쓰는 캐시는 요청 문자열이나 그 해시가 완전히 일치해야만 캐시 히트가 나는 exact-match 방식이라, 표현이 조금만 달라도 매번 모델을 다시 호출하고 비용과 지연을 그대로 지불한다.

시맨틱 캐싱(semantic caching)은 이 틈을 임베딩으로 메운다. 요청 문자열이 아니라 그 **의미 벡터**를 키로 써서, 이미 캐시에 있는 질문과 벡터 거리가 충분히 가까우면 새 응답 생성 없이 저장된 답을 재사용한다. RAG 파이프라인이나 사용자 대면 챗봇처럼 같은 의도의 질문이 반복되는 서비스에서는 캐시 히트율과 함께 p99 지연, 토큰 비용이 동시에 줄어드는 효과가 크다.

이 글에서는 시맨틱 캐싱의 동작 구조, exact-match 캐시와의 차이, 그리고 실무에서 가장 까다로운 문제인 "얼마나 비슷하면 같다고 볼 것인가"의 임계값 설계를 정리한다.

## 핵심 개념 1: 시맨틱 캐싱의 동작 구조

시맨틱 캐싱은 대략 다음 순서로 동작한다.

1. 들어온 요청 텍스트를 임베딩 모델로 벡터화한다.
2. 벡터 DB(또는 인메모리 벡터 인덱스)에서 기존 캐시 항목 중 코사인 유사도가 가장 높은 것을 찾는다.
3. 유사도가 설정한 임계값 이상이면 **캐시 히트** — 저장된 응답을 즉시 반환한다.
4. 임계값 미만이면 **캐시 미스** — LLM을 호출하고, 그 결과를 요청 벡터와 함께 새 캐시 항목으로 저장한다.

exact-match 캐시가 문자열 자체를 키로 쓰는 것과 달리, 시맨틱 캐시는 "의미가 같은 질문의 군집"을 하나의 캐시 항목으로 묶는다. 그만큼 히트율은 크게 오르지만, 대신 "실제로는 다른 질문인데 비슷하다고 오판"하는 위험이 새로 생긴다는 점이 핵심 트레이드오프다.

## 핵심 개념 2: 캐시 종류별 비교

| 구분 | Exact-match 캐시 | 시맨틱 캐시 | 캐시 없음 |
|---|---|---|---|
| 캐시 키 | 요청 문자열/해시 | 임베딩 벡터 | 없음 |
| 표현이 다른 동의 질문 | 미스 처리 | 히트 가능 | 항상 미스 |
| 오탐(false hit) 위험 | 없음 | 임계값에 따라 존재 | 없음 |
| 추가 인프라 | 키-값 저장소 | 벡터 인덱스 + 임베딩 호출 | 없음 |
| 적합한 상황 | 완전히 동일한 요청 반복 | 표현이 다양한 반복 의도 | 매번 다른 컨텍스트 |

exact-match와 시맨틱 캐시는 대체 관계가 아니라 계층 관계로 쓰는 경우가 많다. 문자열이 완전히 같으면 임베딩 계산 없이 exact-match로 즉시 히트시키고, 그렇지 않을 때만 시맨틱 캐시를 조회하는 2단 구조가 임베딩 호출 비용도 아끼고 히트율도 챙긴다.

## 핵심 개념 3: 임계값과 안전장치

시맨틱 캐싱에서 가장 어려운 결정은 유사도 임계값이다. 임계값을 낮게 잡으면 히트율은 오르지만 "환불 절차 알려주세요"와 "환불 취소하고 싶어요"처럼 표면적으로 비슷해도 의도가 정반대인 질문을 같은 답으로 잘못 응답할 위험이 커진다. 반대로 임계값을 너무 높게 잡으면 캐시가 사실상 exact-match와 다를 바 없어져 효과가 사라진다.

실무에서는 다음 안전장치를 함께 둔다.

- **도메인별 임계값 분리**: 사실 조회성 질문(영업시간, 정책 안내)은 임계값을 낮춰도 되지만, 개인화된 응답이나 수치가 섞인 질문은 임계값을 높이거나 캐시 대상에서 제외한다.
- **응답 재검증**: 캐시 히트 시에도 사용자 질문에 담긴 개체(주문번호, 날짜 등)가 캐시된 응답과 맞는지 가벼운 규칙으로 재확인한다.
- **TTL과 무효화**: 정책이 바뀌는 주제는 TTL을 짧게 두거나, 소스 문서가 갱신되면 관련 캐시를 명시적으로 삭제한다.

## 예제: 2단 캐시 조회 흐름 (Python 의사코드)

```python
def get_response(query: str, cache, embed_model, llm, threshold=0.92):
    # 1단계: exact-match (해시 키)
    exact_hit = cache.get_exact(query)
    if exact_hit:
        return exact_hit

    # 2단계: 시맨틱 캐시 (임베딩 유사도)
    query_vec = embed_model.embed(query)
    match, score = cache.search_semantic(query_vec, top_k=1)

    if match and score >= threshold:
        return match.response  # 캐시 히트

    # 캐시 미스: 실제 LLM 호출
    response = llm.generate(query)
    cache.put_exact(query, response)
    cache.put_semantic(query_vec, response, ttl_seconds=3600)
    return response
```

## 실무 포인트

- **임계값은 상수가 아니라 실험 대상이다**: 서비스 초기에는 임계값을 보수적으로(높게) 잡고, 실제 캐시 히트 로그를 사람이 샘플링해 오탐률을 확인하며 점진적으로 낮추는 것이 안전하다.
- **PII가 섞인 요청은 캐시하지 않거나 별도 격리한다**: 개인정보가 포함된 질문과 응답을 벡터로 저장하면 다른 사용자의 요청과 유사도 매칭이 일어날 때 정보가 노출될 수 있다. 테넌트/사용자 단위로 캐시 네임스페이스를 분리해야 한다.
- **임베딩 호출 자체도 비용이다**: 캐시 조회마다 임베딩을 새로 계산하므로, 임베딩 모델은 가볍고 빠른 것을 쓰고 가능하면 임베딩 결과 자체도 짧게 캐시한다.

## 3줄 요약

- 시맨틱 캐싱은 요청 문자열이 아니라 임베딩 유사도를 키로 써서, 표현이 다른 동의 질문까지 캐시 히트로 묶어 LLM 호출 비용과 지연을 줄인다.
- exact-match 캐시와 경쟁 관계가 아니라 앞단에 두고 함께 쓰는 2단 구조가 실무에서 가장 효율적이다.
- 유사도 임계값은 히트율과 오탐률의 트레이드오프이므로, 도메인별로 분리하고 TTL·재검증 같은 안전장치를 함께 설계해야 한다.
