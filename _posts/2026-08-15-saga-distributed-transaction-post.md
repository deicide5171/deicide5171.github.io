## 왜 지금 이 이야기인가

마이크로서비스 아키텍처가 보편화되면서 하나의 비즈니스 트랜잭션이 여러 서비스와 여러 데이터베이스에 걸쳐 실행되는 상황이 흔해졌다. 주문 서비스, 결제 서비스, 재고 서비스가 각각 독립된 DB를 갖고 있을 때, "주문 생성 - 결제 승인 - 재고 차감"이 하나의 트랜잭션처럼 원자적으로 성공하거나 실패해야 한다면 어떻게 처리해야 할까. 단일 DB 안에서는 트랜잭션으로 간단히 해결되지만, 서비스 경계를 넘어가는 순간 이 문제는 훨씬 복잡해진다.

전통적으로는 2단계 커밋(2PC, Two-Phase Commit)이 분산 트랜잭션의 표준 해법으로 여겨졌지만, 마이크로서비스 환경에서는 여러 한계 때문에 실무에서 잘 쓰이지 않는 경향이 있다. 대신 그 대안으로 자리 잡은 것이 사가(Saga) 패턴이다. 이 글에서는 2PC의 한계와 사가 패턴의 두 가지 구현 방식, 그리고 보상 트랜잭션 설계 시 고려할 점을 정리한다.

## 2PC의 한계

| 항목 | 2PC의 문제점 |
|---|---|
| 가용성 | 코디네이터가 모든 참여자의 커밋 준비 완료를 기다려야 하며, 한 노드라도 응답이 늦으면 전체가 블로킹된다 |
| 락 유지 시간 | 커밋이 완료될 때까지 각 참여자가 리소스 락을 계속 들고 있어야 해 동시성이 크게 떨어진다 |
| 장애 대응 | 코디네이터가 죽으면 참여자들이 커밋도 롤백도 못한 채 대기 상태에 빠질 수 있다(블로킹 프로토콜) |
| 이종 시스템 호환 | 서로 다른 벤더의 DB, 메시지 큐 등 이종 리소스가 섞이면 2PC 프로토콜(XA 등)을 모두 지원하지 않는 경우가 많다 |

이런 이유로 2PC는 단일 데이터센터 안의 동종 DB 클러스터에서는 여전히 쓰이지만, 여러 마이크로서비스와 여러 종류의 저장소가 얽힌 환경에서는 가용성과 확장성 문제로 인해 기피되는 경향이 강하다.

## 사가 패턴 개념: 코레오그래피 vs 오케스트레이션

사가 패턴은 하나의 큰 트랜잭션을 "각자 로컬 트랜잭션으로 커밋되는 여러 단계"로 쪼개고, 중간에 실패하면 이미 완료된 단계들을 역순으로 취소하는 **보상 트랜잭션**을 실행해 정합성을 회복하는 방식이다.

| 구분 | 코레오그래피(Choreography) | 오케스트레이션(Orchestration) |
|---|---|---|
| 제어 방식 | 각 서비스가 이벤트를 구독/발행하며 자율적으로 다음 단계 진행 | 중앙 오케스트레이터가 각 서비스에 명령을 내리고 흐름을 관리 |
| 결합도 | 서비스 간 결합도는 낮지만 전체 흐름 파악이 어려움 | 흐름이 한 곳에 명시되어 가시성이 좋음 |
| 장애 시 대응 | 각 서비스가 자신의 실패를 이벤트로 알리고 보상 로직을 각자 수행 | 오케스트레이터가 실패를 감지해 보상 단계를 순서대로 지시 |
| 적합한 규모 | 단계 수가 적고 서비스 간 관계가 단순할 때 | 단계가 많고 복잡한 워크플로우일 때 |

실무에서는 단계가 3~4개를 넘어가면 코레오그래피의 "흐름이 코드 여기저기 흩어진다"는 단점이 부각되어, 오케스트레이션 방식(또는 Temporal, AWS Step Functions 같은 워크플로우 엔진)을 선호하는 경우가 많은 것으로 보인다.

## 보상 트랜잭션 설계

보상 트랜잭션은 단순히 "원래 상태로 되돌리는 것"이 아니라, 이미 외부에 노출된 부작용까지 고려해 설계해야 한다.

- 결제 승인의 보상은 단순 취소가 아니라 **환불**일 수 있다.
- 재고 차감의 보상은 **재고 복구**이지만, 그 사이 다른 주문이 그 재고를 또 차감했을 가능성을 고려해야 한다.
- 보상 트랜잭션 자체가 실패할 수도 있으므로, 재시도와 알림(수동 개입) 경로를 함께 설계해야 한다.
- 각 단계는 멱등성(idempotency)을 갖도록 만들어야 재시도 시 중복 실행을 방지할 수 있다.

## 예제

오케스트레이션 방식의 사가 흐름을 의사코드로 표현하면 다음과 같다.

```python
def order_saga(order):
    try:
        reserve_inventory(order)
        charge_payment(order)
        confirm_order(order)
    except PaymentFailed:
        release_inventory(order)   # 보상 트랜잭션
        cancel_order(order)
    except InventoryUnavailable:
        cancel_order(order)
```

이벤트 기반 코레오그래피에서 각 서비스가 발행/구독하는 이벤트 예시:

```json
{
  "event": "OrderCreated",
  "orderId": "o-1001",
  "compensationEvent": "OrderCancelled"
}
```

## 실무 포인트와 주의사항

- 사가는 최종 일관성(eventual consistency)을 전제로 하므로, "일시적으로 불일치 상태가 보일 수 있다"는 점을 프론트엔드/사용자 경험 설계에도 반영해야 한다.
- 보상 트랜잭션이 실패했을 때의 데드레터 큐, 알림, 수동 개입 프로세스를 처음부터 설계에 포함시켜야 한다.
- 워크플로우 엔진(Temporal, AWS Step Functions, Camunda 등)을 활용하면 오케스트레이션 로직의 상태 관리와 재시도를 직접 구현하지 않아도 되는 경우가 많다.
- 사가 전체 흐름에 대한 관찰 가능성(각 단계의 성공/실패 로그, 트레이싱)을 확보해야 장애 시 원인 파악이 쉬워진다.

## 3줄 요약

- 2PC는 가용성과 락 유지 시간 문제로 마이크로서비스 환경에서는 기피되는 경향이 있다.
- 사가 패턴은 로컬 트랜잭션들의 연쇄와 보상 트랜잭션으로 정합성을 확보하며, 코레오그래피와 오케스트레이션 두 방식으로 구현된다.
- 보상 트랜잭션은 멱등성과 부작용까지 고려해 설계해야 하며, 실패 시 대응 경로도 함께 준비해야 한다.
