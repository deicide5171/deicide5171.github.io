## 왜 지금 이 판단이 필요한가

"에이전트가 열 단계짜리 조사 작업을 하다가 배포 때문에 프로세스가 재시작되면, 이미 끝낸 LLM 호출은 다시 부르지 말고 그다음부터 이어서 해주세요." 이 요구는 평범한 재시도 로직으로는 풀리지 않는다. 일반적인 재시도는 "실패하면 처음부터 다시"인데, LLM 호출은 비싸고 느리고 결과가 매번 달라질 수 있어서 "이미 성공한 호출을 또 하는 것" 자체가 비용이자 버그다. 전통적인 워크플로 엔진(Temporal 같은)이 쓰는 저널-리플레이 모델은 원래 이 문제를 풀려고 나온 것이지만, 그 모델의 전제 자체가 "워크플로 코드는 결정적이다"라는 가정 위에 서 있다. LLM 호출은 이 가정을 정면으로 깬다.

이 판단이 지금 특히 중요해진 이유는 생태계가 막 요동치고 있어서다. 2026년 9월 Temporal이 125억 달러 기업가치로 5억5천만 달러 시리즈E를 유치했고, 3주도 안 돼 베를린의 Restate가 2천만 달러 시리즈A를 발표했다. Restate는 "durability는 복잡한 워크플로 전용 도구가 아니라 범용 백엔드 빌딩 블록"이라는 메시지를 들고 나왔다. 두 투자 소식이 겹쳤다는 건, 업계가 "에이전트 워크로드에 durable execution이 필요하다"는 데는 합의했지만 "어떤 엔진으로"는 아직 안 정해졌다는 뜻이다. 그래서 지금 이 선택을 내리는 팀은 벤더 마케팅이 아니라 각 엔진의 내부 모델을 직접 비교해 판단해야 한다.

## 핵심 개념 1 — 저널-리플레이와 비결정성의 충돌

Temporal과 Restate는 둘 다 **저널-리플레이** 모델을 쓴다. 워크플로가 진행하면서 발생하는 이벤트(함수 호출, 응답)를 저널에 기록해두고, 프로세스가 재시작되면 저널을 처음부터 재생(replay)해서 이미 완료된 단계는 건너뛰고 아직 안 끝난 지점부터 이어간다. 이게 성립하려면 워크플로 코드가 **결정적**이어야 한다 — 같은 입력이면 재생할 때도 같은 분기를 타야 저널과 실제 실행이 어긋나지 않는다.

LLM 호출은 같은 프롬프트를 넣어도 매번 다른 응답이 나올 수 있다. 그래서 LLM 호출을 워크플로 로직 안에 그냥 섞어 넣으면 안 되고, 반드시 "활동(activity)" 또는 "스텝"으로 명시적으로 분리해 **그 결과를 저널에 한 번 기록하고 재생 시에는 그 기록을 그대로 재사용**하도록 설계해야 한다. 이 경계를 안 긋고 LLM 호출을 워크플로 코드에 직접 넣으면, 재생 때마다 LLM을 또 호출하면서 비용이 배로 늘고 결과까지 달라지는 사고가 난다.

## 핵심 개념 2 — 세 엔진의 실제 차이

| 엔진 | 모델 | 에이전트 워크로드에서의 특징 |
|---|---|---|
| Temporal | 저널-리플레이, 이벤트 히스토리 전체 보관 | 성숙하고 생태계가 크지만, LLM 응답처럼 큰 페이로드가 이벤트 히스토리를 부풀려 별도 오프로드 전략이 필요 |
| Restate | 저널-리플레이, 더 가벼운 런타임 | 애플리케이션 레벨 멱등성 키 없이도 exactly-once 쓰기를 보장한다고 주장 — 다만 생태계가 아직 Temporal보다 작음 |
| Inngest | 스텝별 체크포인트(저널-리플레이와 다른 모델) | 각 스텝의 출력만 저장해 모델이 더 단순하지만, 멀티모델 호출·재시도가 늘수록 스텝 단위 과금이 빠르게 커질 수 있음 |

세 엔진 모두 공통으로 요구하는 실무 규칙이 있다 — LLM 출력은 **한 번 기록하고 재생 시 재사용**해야 하고, 워크플로 코드 자체는 결정적이어야 하며, 부수효과가 있는 툴 호출(결제, 메일 발송 등)은 별도로 멱등하게 짜야 한다. 엔진이 다르다고 이 세 규칙이 면제되지는 않는다.

## 전체 시스템에서의 위치

에이전트 오케스트레이터 입장에서 워크플로 엔진은 "내가 이 작업을 끝까지 책임지고 이어가 줄게"라고 약속하는 신뢰 경계다. 오케스트레이터가 직접 상태를 테이블에 적고 폴링하는 대신, 워크플로 코드를 평범한 함수로 짜고 엔진이 저널·재생·재시도를 대신 맡는다. 이 경계 안에서 LLM 호출과 외부 툴 호출은 "활동"으로 명시적으로 쪼개져, 각각이 성공했는지 실패했는지가 저널에 남는다.

## 선택의 트레이드오프 — 언제 엔진 없이 가도 되는가

- 요청-응답이 수 초 안에 끝나고 중간 장애 복구가 애초에 문제되지 않는다면, 워크플로 엔진은 **과잉 설계**다. 큐 하나와 멱등성 키만으로 충분하다.
- 작업이 분 단위 이상 걸리고 중간에 여러 LLM·툴 호출이 섞이며 재시작 복구가 실제로 자주 발생한다면, 세 엔진 중 하나를 검토할 시점이다.
- LLM 응답이나 첨부 파일처럼 큰 페이로드를 자주 다룬다면 Temporal은 오프로드 전략(저널에는 참조만, 실제 데이터는 외부 저장소)을 처음부터 설계에 넣어야 한다.
- 멱등성 키를 애플리케이션 레벨에서 직접 관리하고 싶지 않다면 Restate의 exactly-once 쓰기 모델이 유리하지만, 이미 Temporal 생태계(테스트 도구, 운영 노하우)에 투자했다면 전환 비용을 따져야 한다.
- 스텝 수가 적고 단순한 체이닝 위주라면 Inngest의 체크포인트 모델이 구현 부담은 가장 적지만, 재시도가 잦은 워크로드에서는 과금 구조를 미리 시뮬레이션해봐야 한다.

## 실제 프로젝트 진행 순서

1. **크래시 복구가 실제로 문제인지부터 확인한다.** 지금 장애 로그에 "중간에 죽어서 처음부터 다시 돌린" 사례가 실제로 있는지부터 센다. 없다면 엔진 도입은 다음 단계다.
2. **LLM 호출과 부수효과 호출의 경계를 먼저 긋는다.** 워크플로 코드 안에서 어디까지가 "활동"으로 분리돼야 하는지 설계 문서에 명시한다. 엔진을 고르기 전에 이 경계부터 확정해야 한다.
3. **페이로드 크기를 측정한다.** LLM 응답·첨부파일이 평균 몇 KB인지 재서, Temporal을 고려 중이라면 오프로드가 필요한지 미리 판단한다.
4. **PoC로 세 엔진 중 하나를 붙여본다.** 실제 에이전트 워크플로 하나를 골라 작게 이식해보고, 장애를 인위적으로 주입해 저널 재생이 의도대로 동작하는지 확인한다.
5. **과금·운영 비용을 재시도 시나리오로 시뮬레이션한다.** 특히 Inngest처럼 스텝 단위 과금이 있는 엔진은 재시도가 잦은 워크로드에서 비용이 비선형으로 늘 수 있다.

```python
# 워크플로 코드(개념 예시) — LLM 호출을 활동으로 명시적으로 분리
async def research_workflow(query: str):
    # 활동으로 분리: 저널에 결과가 기록되고, 재생 시 재호출되지 않음
    plan = await call_activity(llm_plan_activity, query)

    results = []
    for step in plan.steps:
        # 각 스텝도 독립된 활동 — 일부만 실패해도 그 지점부터 재개 가능
        r = await call_activity(llm_execute_step_activity, step)
        results.append(r)

    summary = await call_activity(llm_summarize_activity, results)
    return summary
```

## 마무리 요약

- LLM 호출은 비결정적이므로 저널-리플레이 모델을 쓰는 엔진에서는 반드시 별도 활동으로 분리해 한 번만 기록·재사용해야 한다.
- Temporal·Restate·Inngest는 저널 모델, 페이로드 처리, 과금 구조에서 실질적으로 다르며, "뭐가 제일 유명한가"가 아니라 자신의 페이로드 크기와 재시도 빈도로 골라야 한다.
- 크래시 복구가 실제로 드문 짧은 요청-응답 워크로드라면, 엔진 자체가 과잉 설계일 수 있다 — 큐와 멱등성 키로 먼저 시작하는 것이 맞는 경우도 많다.
