## 왜 지금 이 문제가 불거지는가

이벤트 소싱(Event Sourcing)을 도입하는 이유는 명확하다. 상태의 현재 값만 저장하는 대신 상태를 변화시킨 모든 이벤트를 순서대로 저장하면, 감사 추적·시점 복원·디버깅이 훨씬 쉬워진다. 초기 도입 단계에서는 이벤트 몇백~몇천 건을 재생(replay)해 현재 상태를 복원하는 데 문제가 없다. 하지만 서비스가 성숙하면서 특정 애그리게이트의 이벤트가 수만~수십만 건으로 쌓이면, 매번 처음부터 이벤트를 재생해 상태를 복원하는 방식은 응답 시간을 감당할 수 없는 수준으로 늘려버린다.

CQRS(Command Query Responsibility Segregation)와 함께 쓰는 경우도 마찬가지 문제를 겪는다. 쓰기 모델(이벤트 스토어)과 읽기 모델(프로젝션)을 분리해 조회 성능을 최적화하는 것이 CQRS의 핵심인데, 프로젝션 로직에 버그가 있었거나 새로운 조회 뷰가 필요해질 때마다 전체 이벤트 스트림을 처음부터 재생해 프로젝션을 재구축해야 한다. 이벤트가 많아질수록 이 재구축 작업 자체가 몇 시간씩 걸리는 배치 작업이 되어버려, 장애 복구나 신규 기능 배포의 발목을 잡는다.

## 핵심 개념 1 — 스냅샷으로 재생 시간 줄이기

스냅샷은 특정 시점까지의 이벤트를 재생한 결과인 애그리게이트 상태를 별도로 저장해두는 것이다. 이후 상태를 복원할 때는 가장 최근 스냅샷을 불러온 뒤, 그 스냅샷 이후에 발생한 이벤트만 추가로 재생하면 된다. N개의 이벤트마다(예: 100개) 자동으로 스냅샷을 남기는 정책이 일반적이며, 스냅샷 자체도 이벤트 스토어와 별도 테이블이나 컬렉션에 버전 번호와 함께 저장한다.

주의할 점은 스냅샷이 이벤트 스트림을 대체하는 것이 아니라 어디까지나 캐시라는 사실이다. 스냅샷 포맷이 바뀌거나 손상됐을 때도 이벤트 스트림에서 처음부터 재생하면 항상 정합성 있는 상태를 복원할 수 있어야 한다. 스냅샷을 신뢰의 원천(source of truth)으로 착각하고 이벤트 일부를 삭제하는 순간, 이벤트 소싱의 핵심 이점을 스스로 포기하는 셈이 된다.

## 핵심 개념 2 — 프로젝션 재구축 파이프라인

프로젝션 재구축은 보통 세 가지 트리거로 발생한다. 새로운 읽기 모델(뷰) 추가, 기존 프로젝션 로직의 버그 수정, 그리고 프로젝션 데이터 손상 복구다. 각 상황에서 이벤트 스트림 전체를 순차 재생하는 것은 동일하지만, 서비스 운영 중 재구축을 어떻게 진행하느냐가 실무의 핵심 난이도다.

| 방식 | 설명 | 트레이드오프 |
|---|---|---|
| 오프라인 재구축 | 서비스 중단 후 처음부터 재생 | 단순하지만 다운타임 발생 |
| 블루-그린 재구축 | 새 프로젝션 테이블을 별도로 채운 뒤 스위칭 | 다운타임 없음, 이중 저장 공간 필요 |
| 체크포인트 병렬 재생 | 여러 파티션으로 나눠 병렬 재생 후 병합 | 재구축 속도 향상, 파티셔닝 설계 필요 |
| 증분 마이그레이션 | 기존 프로젝션에 델타만 적용 | 빠르지만 로직 변경 폭이 클 때 부적합 |

## 예제 — 스냅샷 기반 상태 복원 의사코드

```typescript
async function loadAggregate(aggregateId: string) {
  const snapshot = await snapshotStore.getLatest(aggregateId);
  const fromVersion = snapshot ? snapshot.version + 1 : 0;

  const events = await eventStore.readStream(aggregateId, fromVersion);
  let state = snapshot ? snapshot.state : initialState();

  for (const event of events) {
    state = applyEvent(state, event);
  }
  // N개마다 새 스냅샷 저장 (여기서는 예시로 즉시 조건 체크)
  if (events.length >= SNAPSHOT_THRESHOLD) {
    await snapshotStore.save(aggregateId, state, fromVersion + events.length - 1);
  }
  return state;
}
```

## 실무 포인트

- **스냅샷 주기를 애그리게이트별 이벤트 발생 빈도에 맞춰 다르게 가져가라.** 이벤트가 자주 쌓이는 핫 애그리게이트와 거의 변하지 않는 것을 동일한 주기로 스냅샷하면 자원 낭비이거나 재생 지연이 반복된다.
- **프로젝션 재구축은 반드시 블루-그린 방식으로 설계하라.** 재구축 중인 프로젝션 테이블에 실시간 조회 트래픽이 붙지 않도록 스위칭 시점을 명확히 관리해야 한다.
- **이벤트 스키마 버전 관리를 프로젝션 재구축과 함께 고려하라.** 오래된 이벤트 포맷을 재생할 때 업캐스터(upcaster)로 최신 스키마로 변환하는 계층이 없으면 재구축 자체가 실패한다.

## 마무리 요약

- 이벤트 스트림이 길어질수록 매번 처음부터 재생하는 방식은 지속 가능하지 않으며, 스냅샷은 이 문제를 완화하는 캐시 계층이다.
- 스냅샷은 신뢰의 원천이 아니라 재생 속도를 위한 최적화이므로, 이벤트 스트림 자체의 무결성은 항상 유지해야 한다.
- 프로젝션 재구축은 새 뷰 추가·버그 수정·데이터 복구 시 반복적으로 필요한 작업이므로, 처음부터 블루-그린이나 병렬 재생 파이프라인으로 설계해두는 것이 장기적으로 훨씬 저렴하다.
