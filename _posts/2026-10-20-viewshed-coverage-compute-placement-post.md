## 어떤 요구에서 출발하는가

"이번 중계기 설치 후보지를 지도에서 클릭하면, 거기서 전파가 어디까지 닿는지 바로 색칠해서 보여주세요." 통신사나 재난 대응 조직에서 흔히 나오는 요구다. CCTV 배치, 드론 비행 경로의 통신 음영 구간 확인, 산불 감시탑 위치 선정도 같은 질문의 변형이다 — "이 지점에서 저 지점이 보이는가(line-of-sight)"를 지형 전체에 대해 한 번에 계산하는 가시권(viewshed) 분석이다.

겉으로는 "지도에 레이어 하나 색칠하기"처럼 들리지만, 실제로는 후보 지점을 바꿀 때마다 수십만~수백만 개 셀에 대해 시선과 지형 표면의 교차 여부를 다시 계산해야 하는 연산 집약 작업이다. "바로 보여주세요"라는 말에는 이미 지연 시간 요구사항이 숨어 있고, 그 요구사항이 연산을 어디서 돌릴지를 결정한다.

## 전체 시스템에서의 위치

가시권 분석은 지도 레이어 하나가 아니라 DEM(수치표고모델)부터 화면 픽셀까지 이어지는 파이프라인의 중간 연산 단계다.

<img src="/assets/images/posts/2026-10-20-viewshed-coverage-compute-placement-1.svg" alt="DEM 소스부터 가시권 연산 단계, 결과 캐시, 지도 렌더링까지 이어지는 구조도와 세 가지 연산 배치 방식" style="width:100%;">

DEM은 국토지리정보원이나 SRTM 같은 공개 지형 데이터에서 타일 단위로 들어오고, 이 지형 격자 위에서 관측점의 고도·관측 반경·지구 곡률 보정을 적용해 가시/비가시 셀을 분류하는 것이 연산의 핵심이다. 결과는 보통 이진 래스터(보임/안 보임)나 다중 관측점을 합산한 커버리지 그리드로 나오고, 이것이 다시 지도 레이어로 렌더링된다. 앞단은 지형 데이터 파이프라인(타일 캐시·재투영)이고, 뒷단은 커버리지 결과를 벡터/래스터 타일로 변환해 지도 클라이언트에 내려주는 타일 서버다 — 가시권 연산 자체는 이 둘 사이 어디에 둘지가 설계의 핵심이다.

## 선택의 트레이드오프

| 방식 | 응답 시간 | 데이터 최신성 | 적합한 상황 |
|---|---|---|---|
| 서버 사전계산 + 그리드 캐시 | 매우 빠름 (캐시 조회) | 낮음 — 후보지 변경 시 재계산 필요 | 후보지가 고정된 커버리지 맵(기존 기지국 전수 조사) |
| 서버 온디맨드 (CPU, GRASS r.viewshed 등) | 수백ms~수초 (격자 규모에 비례) | 높음 — 임의 지점 즉시 반영 | 사용자가 후보지를 자유롭게 클릭해 탐색하는 계획 도구 |
| 클라이언트 GPU 컴퓨트 셰이더 (WebGPU) | 수십~수백ms, 네트워크 왕복 없음 | 매우 높음 — 로컬에서 즉시 재계산 | 반경이 좁고 디바이스 성능을 신뢰할 수 있는 현장 앱 |

사전계산 캐시는 후보지가 몇 개로 정해져 있을 때는 최선이지만, "아무 데나 클릭해서 탐색"하는 UX에는 맞지 않는다. 서버 온디맨드는 범용적이지만 동시 요청이 몰리면 연산 서버가 병목이 된다. WebGPU 컴퓨트 셰이더는 2023년 이후 주요 브라우저에 폭넓게 탑재되면서 현실적인 선택지가 됐지만, 구형 디바이스나 모바일 저사양 환경에서는 폴백(서버 계산)이 필요하다. 세 방식을 섞어 "넓은 반경은 서버 사전계산, 좁은 반경 탐색은 WebGPU"처럼 역할을 나누는 하이브리드 구성도 실무에서 흔하다.

## 실제 프로젝트 진행 순서

1. **지연 시간 요구를 숫자로 못 박는다.** "바로"가 1초인지 5초인지에 따라 아키텍처가 완전히 달라진다. 이 숫자를 정하지 않고 구현부터 시작하면 나중에 방식을 통째로 바꿔야 한다.
2. **격자 해상도와 반경을 정한다.** 10m 격자에 반경 20km면 셀 수가 수백만 개로 뛴다. 해상도를 낮추거나 관심 반경을 제한하는 협상이 연산 비용을 결정적으로 줄인다.
3. **서버 온디맨드로 먼저 프로토타입을 돌린다.** GRASS GIS의 `r.viewshed`나 PostGIS의 래스터 함수로 임의 지점 하나를 계산해 실제 걸리는 시간을 측정한다. 이 숫자가 1번에서 정한 목표보다 느리면 캐시나 GPU 이전을 검토한다.
4. **동시 요청 패턴을 가정해 부하를 검증한다.** 사용자가 지도를 드래그하며 여러 지점을 연속 클릭하는 패턴을 흉내 내 서버가 버티는지 확인한다. 여기서 막히면 디바운싱(클릭 후 일정 시간 대기)이나 이전 요청 취소 로직이 먼저 필요하다.
5. **필요시 WebGPU 경로를 추가한다.** 반경을 좁힌 "빠른 미리보기"는 클라이언트에서, 정밀한 최종 결과는 서버에서 재계산해 보여주는 2단계 UX가 체감 속도와 정확도를 함께 잡는다.

예제(의사코드, 서버 온디맨드 가시권 호출):

```python
import subprocess

def compute_viewshed(dem_path, obs_lon, obs_lat, obs_height_m, max_radius_m):
    result = subprocess.run([
        "grass", "--exec", "r.viewshed",
        f"input={dem_path}",
        f"coordinates={obs_lon},{obs_lat}",
        f"observer_elevation={obs_height_m}",
        f"max_distance={max_radius_m}",
        "output=viewshed_result",
        "--overwrite",
    ], capture_output=True, timeout=10)
    return result.returncode == 0
```

## 실무 포인트

- 지구 곡률과 대기 굴절 보정을 빼먹으면 장거리(10km 이상) 가시권에서 오차가 눈에 띄게 커진다. 통신 커버리지처럼 정확도가 중요한 도메인에서는 반드시 보정 옵션을 켠다.
- DEM 해상도가 건물을 반영하지 않는 지형 DEM(DTM)인지, 건물까지 포함한 표면 DEM(DSM)인지에 따라 도심 지역 결과가 크게 달라진다. 요구사항에 건물 차폐가 중요한지부터 확인한다.
- 다중 관측점 커버리지(여러 기지국을 동시에 깔았을 때 합산 커버리지)는 단일 지점 계산을 단순히 N번 반복하면 안 된다 — 합산 전용 알고리즘(총 가시권, total viewshed)을 쓰지 않으면 연산량이 선형이 아니라 급격히 늘어난다.

## 마무리

- "클릭하면 바로 보여주세요"라는 요구는 가시권 연산을 서버 사전계산·서버 온디맨드·클라이언트 GPU 중 어디에 둘지 정하는 설계 문제로 번역된다.
- 선택 기준은 지연 시간 목표와 후보지가 고정인지 자유 탐색인지 두 가지로 압축된다.
- 지연 목표 확정 → 격자·반경 결정 → 서버 프로토타입 측정 → 부하 검증 → 필요시 GPU 경로 추가 순으로 진행하면 과설계를 피할 수 있다.
