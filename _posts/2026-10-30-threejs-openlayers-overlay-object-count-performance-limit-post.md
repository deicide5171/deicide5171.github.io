## 왜 지금 이 문제가 불거지는가

OpenLayers 지도 위에 three.js로 특정 건물 몇 개만 3D로 얹는 설계는 이전 글에서 정리했다. 문제는 이런 PoC가 거의 예외 없이 같은 다음 요구로 이어진다는 점이다. "건물 10개짜리 데모 잘 봤습니다. 이제 지역 전체 500개 건물로 넓혀서 보여주세요." 요구 자체는 숫자 하나만 바뀐 것처럼 보이지만, 실제로는 카메라 동기화 설계 문제에서 **프레임 예산 관리 문제**로 성격이 완전히 바뀐다. 10개 메시를 그리던 렌더 루프와 500개 메시를 그리는 렌더 루프는 같은 코드라도 전혀 다른 병목에서 끊긴다.

이 병목이 눈에 띄게 드러나는 시점은 보통 QA 단계다. 개발자 로컬 머신에서는 멀쩡하던 지도가, 실제 서비스 규모의 데이터로 바뀌고 저사양 노트북에서 열어보면 60fps는커녕 드래그할 때마다 화면이 끊긴다. 이 시점에 "왜 느려졌는가"를 바로 답하지 못하면 "그럼 처음부터 Cesium으로 다시 짜자"는 과잉 대응이나 "일단 오브젝트 수를 억지로 줄이자"는 임시방편으로 흐르기 쉽다.

## 요구사항을 기술 문제로 번역하기

"지역 전체로 넓혀주세요"는 세 가지 질문으로 번역해야 한다. 첫째, **지금 병목이 CPU(지오메트리 갱신, 카메라 동기화 계산)에 있는가, GPU(드로우콜, 셰이더)에 있는가.** 둘째, **오브젝트 수가 늘어도 메시 형태가 단순 반복이라면 최적화로 버틸 수 있는가, 아니면 애초에 이 조합이 감당할 범위를 넘었는가.** 셋째, **최적화로 버티는 것과 다른 렌더링 스택으로 전환하는 것 중 어느 쪽이 남은 개발 기간 안에 더 안전한가.** 이 세 질문에 답하지 않고 바로 "Instancing 적용해봅시다"로 뛰어들면, 병목이 실제로는 OpenLayers 쪽 벡터타일 재계산에 있는 경우를 놓치게 된다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-30-threejs-openlayers-overlay-object-count-performance-limit-1.svg" alt="하나의 프레임 예산 16.6밀리초 안에서 OpenLayers의 2D 캔버스 렌더와 three.js의 WebGL 드로우콜이 순차적으로 시간을 나눠 쓰고, 오브젝트 수가 늘수록 three.js 쪽 드로우콜 시간이 예산을 넘어서면서 프레임 드랍이 발생하는 구조도와, Instancing 적용 후 드로우콜이 하나로 합쳐지는 전후 비교" style="width:100%;">

두 렌더러를 캔버스로 포개는 구조에서는 **하나의 프레임 예산(60fps 기준 16.6ms)을 두 렌더 루프가 순차적으로 나눠 쓴다.** OpenLayers가 먼저 벡터타일을 Canvas2D/WebGL로 그리고, 그다음 three.js가 자신의 캔버스에 메시들을 그린다. 메시 수가 적을 때는 three.js 쪽 시간이 무시할 만큼 작아 문제가 드러나지 않는다. 메시가 수백 개로 늘면 개별 `Mesh` 객체마다 드로우콜이 하나씩 발생해 GPU 쪽 오버헤드가 선형에 가깝게 증가하고, 동시에 카메라 동기화 로직이 매 프레임 모든 객체의 위치를 재계산한다면 CPU 쪽도 함께 무거워진다. 둘 중 어느 쪽이 실제 병목인지는 브라우저 개발자 도구의 Performance 탭에서 프레임 하나를 녹화해, Scripting(CPU)과 GPU 구간의 비중을 직접 재야 알 수 있다.

## 선택의 트레이드오프

| 대응 | 효과 | 한계 | 적합한 상황 |
|---|---|---|---|
| InstancedMesh로 전환 | 동일 형태 메시 드로우콜을 1회로 합침 | 메시 형태·재질이 거의 같은 경우에만 유효 | 같은 모양의 건물 매스를 수백~수천 개 그릴 때 |
| LOD·거리 기반 컬링 | 화면 밖·먼 객체 연산 생략 | 구현 복잡도 증가, 팝인 현상 관리 필요 | 넓은 지역에 걸쳐 객체가 분산된 경우 |
| 카메라 동기화 빈도 조절 | CPU 측 재계산 부담 감소 | 빠른 드래그 시 미세한 지연 체감 가능 | CPU 병목이 확인된 경우에 한해 |
| Cesium 3D Tiles로 전환 | 대용량 스트리밍·타일링 LOD를 엔진이 전담 | 기존 OpenLayers 스타일·인터랙션 재구축 필요 | 전체 지도를 3D로 쓰거나 객체 수가 수천 단위를 넘을 때 |
| deck.gl ScenegraphLayer | GPU 인스턴싱이 내장, React 생태계 친화적 | OpenLayers와의 합성보다 deck.gl 자체 지도 스택 전제 | 2D 지도를 deck.gl/MapLibre 조합으로 바꿀 수 있는 경우 |

표에서 중요한 분기점은 "같은 형태를 반복해서 많이 그리는가"다. 재건축 예정 건물처럼 형태가 제각각이면 Instancing 효과가 제한적이고, 결국 어느 지점부터는 전체 스택 전환을 검토해야 한다. 반대로 가로수·가로등처럼 동일 모델을 반복 배치하는 경우라면 Instancing만으로 수천 개까지도 버티는 경우가 많다.

## 실제 프로젝트 진행 순서

1. **먼저 측정한다.** 현재 오브젝트 수에서 Performance 탭으로 프레임을 녹화해 CPU·GPU 중 어디가 예산을 넘기는지 수치로 확인한다. 추측으로 최적화를 시작하지 않는다.
2. **같은 형태 메시부터 InstancedMesh로 합친다.** 드로우콜 수가 줄어드는 정도를 다시 측정해, 이 한 가지 조치만으로 목표 오브젝트 수를 감당하는지 확인한다.
3. **화면 밖 객체의 컬링과 거리 기반 LOD를 추가한다.** 사용자가 실제로 보는 범위는 전체 데이터의 일부인 경우가 많다.
4. **목표 오브젝트 수와 측정치 사이의 간극을 수치로 정리해 의사결정 라인에 공유한다.** "조금 더 최적화하면 될 것 같다"가 아니라 "현재 구조로는 N개가 한계이고, M개를 원하면 전환이 필요하다"는 구체적 숫자로 말한다.
5. **전환이 필요하다고 판단되면, 전체를 한 번에 바꾸지 말고 영향이 큰 레이어(가장 객체 수가 많은 레이어)부터 Cesium·deck.gl 프로토타입으로 이식해 성능을 재검증한다.**

## 실무 포인트

**"일단 되니까" 단계에서 오브젝트 수 목표를 먼저 확인한다.** PoC 단계에서 최종 규모를 묻지 않으면, 10개용으로 설계한 구조가 500개 요구에 부딪혀 처음부터 다시 설계해야 하는 상황이 반복된다.

**최적화와 전환을 동시에 검토 대상으로 올려둔다.** Instancing·LOD로 버틸 수 있는 범위를 먼저 측정하고, 그 범위를 넘는 목표치라면 최적화에 시간을 더 쓰기보다 전환 비용을 바로 견적한다.

**카메라 동기화 코드와 렌더링 최적화 코드를 분리해 둔다.** 둘을 뒤섞어 두면 나중에 Cesium·deck.gl로 전환할 때 재사용 가능한 부분과 버려야 할 부분을 가려내기 어려워진다.

## 마무리

- OpenLayers 위에 three.js를 포개는 구조는 하나의 프레임 예산을 두 렌더 루프가 나눠 쓰므로, 오브젝트 수가 늘면 카메라 동기화 설계 문제에서 프레임 예산 관리 문제로 성격이 바뀐다.
- InstancedMesh와 LOD·컬링으로 버틸 수 있는 범위는 메시 형태가 얼마나 반복되는지에 달려 있고, 이 범위를 넘으면 Cesium 3D Tiles나 deck.gl ScenegraphLayer로의 전환을 수치 기반으로 검토해야 한다.
- 추측이 아니라 Performance 탭 측정값으로 병목(CPU vs GPU)을 먼저 확인한 뒤 최적화 순서를 정해야, 엉뚱한 곳을 고치고도 문제가 그대로 남는 상황을 피한다.
