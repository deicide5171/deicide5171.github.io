## 왜 지금 이 문제가 불거지는가

"우리 고객지원 에이전트가 환불 정책 관련 티켓에서 계속 같은 실수를 해요. 그때마다 '이런 경우엔 이렇게 처리하세요'를 시스템 프롬프트에 한 줄씩 추가하는데, 몇 주 지나니 프롬프트가 거대해지고 오히려 엉뚱한 상황에서도 그 규칙을 끌어다 쓰기 시작했어요." 이 요구는 표면적으로는 "프롬프트를 더 잘 쓰면 되는 문제"처럼 보이지만, 실제로는 **에이전트가 실행 피드백에서 무엇을 배우고 어떻게 저장할 것인가**라는 메모리 아키텍처 문제다.

이 문제가 지금 수면 위로 올라온 이유는 에이전트가 프로덕션에서 장기간 반복 실행되기 시작했기 때문이다. 한 번 쓰고 버리는 챗봇이 아니라, 같은 종류의 작업을 하루에도 수백 번 수행하는 상시 가동 에이전트가 늘면서 "지난 실행에서 배운 것을 다음 실행에 어떻게 반영할까"가 실질적인 설계 질문이 됐다. 2026년 공개된 ACE(Agentic Context Engineering) 프레임워크는 바로 이 지점을 겨냥한다 — 컨텍스트를 매번 새로 쓰는 프롬프트가 아니라, 실행할수록 누적·정제되는 **플레이북**으로 다룬다.

## 요구사항을 기술 문제로 번역하기

"같은 실수를 반복하지 않게 해달라"는 말은 구현 수준에서 세 가지 선택지로 갈린다. 첫째, 사람이 직접 프롬프트에 규칙을 추가하는 수동 방식 — 위 사례처럼 선형적으로 비대해지다 특정 임계점을 넘으면 서로 다른 규칙이 충돌하거나 관련 없는 상황에 오염된다. 둘째, 실패 사례를 모아 모델을 파인튜닝하는 방식 — 효과는 있지만 라벨링 비용과 재학습 주기가 커서 "이번 주에 발견한 패턴"을 당장 반영하기 어렵다. 셋째, LLM 스스로 자신의 컨텍스트를 요약·압축해 메모리로 쓰는 방식 — 그런데 연구에 따르면 이 방식은 **brevity bias**(간결한 요약을 선호하도록 학습된 모델이 도메인 디테일을 계속 깎아낸다)와 **context collapse**(반복적으로 다시 쓸 때마다 정보가 누적 손실되는 현상)에 취약하다.

ACE는 이 세 선택지와 다른 네 번째 경로를 제시한다. 컨텍스트를 하나의 문단이 아니라 **구조화된 전략 단위(불릿)의 집합**으로 유지하고, 매 실행마다 전체를 다시 쓰는 대신 추가·수정·폐기의 **증분 델타(delta)**만 적용한다. 요약이 아니라 축적이라는 점이 기존 "메모리 압축" 접근과의 근본적 차이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-03-ace-agentic-context-engineering-1.svg" alt="Generator가 작업을 실행하고 실행 결과 피드백을 남기면, Reflector가 그 피드백에서 전략적 통찰을 추출하고, Curator가 기존 플레이북에 증분 델타 형태로 병합해 다음 실행의 Generator 컨텍스트로 되먹임되는 ACE의 3모듈 순환 구조도" style="width:100%;">

ACE는 Generator-Reflector-Curator 세 모듈이 순환한다. Generator는 현재 플레이북을 컨텍스트로 받아 실제 작업(API 호출, 코드 수정, 티켓 응답)을 수행한다. 실행이 끝나면 성공·실패·중간 로그 같은 **자연 실행 피드백**(사람이 매긴 라벨이 아니라 테스트 통과 여부, 재시도 횟수 같은 신호)이 남는다. Reflector는 이 피드백을 보고 "왜 실패했는지, 다음엔 뭘 다르게 해야 하는지"를 전략 단위로 추출한다. Curator는 그 전략을 기존 플레이북과 대조해 중복이면 보강하고, 모순이면 조건을 분리하고, 쓸모없어졌으면 제거하는 식으로 **구조를 유지한 채** 병합한다. 다음 Generator 실행은 이 갱신된 플레이북을 그대로 이어받는다 — 사람이 프롬프트 파일을 직접 고치는 단계가 빠진다.

## 선택의 트레이드오프

| 기준 | 수동 프롬프트 수정 | 파인튜닝 | 단순 요약 메모리 | ACE 구조화 플레이북 |
|---|---|---|---|---|
| 반영 속도 | 빠름(즉시) | 느림(재학습 필요) | 빠름 | 빠름 |
| 지식 보존 | 사람이 관리하는 동안만 | 가중치에 영구 반영 | context collapse로 유실 | 델타 누적으로 보존 |
| 운영 비용 | 사람 개입 필수 | 데이터·GPU 비용 | 낮음 | 실행 피드백 설계 비용 |
| 적합 규모 | 규칙 수십 개 이하 | 패턴이 안정적일 때 | 단발성 세션 | 반복 실행되는 상시 에이전트 |

파인튜닝은 모델 자체의 능력을 바꾸고 싶을 때, ACE류 플레이북은 모델은 그대로 두고 **도메인 지식과 절차만 빠르게 진화**시키고 싶을 때 적합하다. 둘은 배타적이지 않고, 플레이북으로 먼저 패턴을 검증한 뒤 안정화된 규칙만 파인튜닝 데이터로 승격하는 조합도 가능하다.

## 실제 프로젝트 진행 순서

1. **라벨 없는 실행 피드백 신호부터 정의한다.** 사람이 매번 성공/실패를 채점할 수 없으므로, 테스트 통과·API 에러 코드·후속 재작업 여부처럼 시스템이 자동으로 관찰 가능한 신호를 먼저 설계한다.
2. **Reflector가 뽑을 "전략 단위"의 포맷을 정한다.** 자유 텍스트가 아니라 "상황 조건 + 권장 행동 + 근거가 된 사례"처럼 구조를 고정해야 Curator가 중복·모순을 기계적으로 판별할 수 있다.
3. **Curator의 병합 규칙을 먼저 보수적으로 설계한다.** 초기에는 "완전히 동일한 조건만 교체, 나머지는 추가"처럼 단순한 규칙으로 시작해 플레이북이 통제 불능으로 커지는 것을 막는다.
4. **플레이북 크기 상한과 정리 주기를 둔다.** 구조화돼 있어도 무한히 쌓이면 Generator 컨텍스트 비용이 늘어나므로, 오래되거나 적중률 낮은 항목을 주기적으로 솎아낸다.
5. **오프라인(시스템 프롬프트 최적화)과 온라인(실행 중 메모리 갱신) 적용 범위를 분리한다.** 안정적인 도메인 규칙은 오프라인 배치로 정제해 반영하고, 세션 중 실시간으로 바뀌는 맥락만 온라인 갱신 대상으로 좁힌다.

## 실무 포인트

**brevity bias는 모델 선택과 무관하게 발생한다.** 요약 지시를 받은 LLM은 기본적으로 짧고 일반적인 문장을 선호하도록 정렬돼 있어, "요약해서 메모리에 남겨라"라는 지시 자체가 이미 디테일 손실을 내장하고 있다. 구조화된 델타 누적이 필요한 이유다.

**실행 피드백의 품질이 전체 구조의 품질을 결정한다.** Reflector와 Curator가 아무리 정교해도, 애초에 "이번 실행이 잘됐는지"를 판별하는 신호가 부정확하면 잘못된 전략이 플레이북에 그대로 쌓인다. 신호 설계가 선행 과제다.

**플레이북은 감사 가능해야 한다.** 블랙박스로 진화하는 메모리는 왜 특정 행동을 하게 됐는지 추적이 안 돼 디버깅이 불가능하다. 각 델타에 추가된 시점과 근거 사례를 남겨야 한다.

## 마무리

- "같은 실수를 반복하지 말라"는 요구는 프롬프트 땜질이 아니라 실행 피드백 → 전략 추출 → 구조화 병합이라는 메모리 파이프라인 설계 문제다.
- ACE는 Generator-Reflector-Curator 순환과 증분 델타로 brevity bias와 context collapse를 피하면서 컨텍스트를 플레이북처럼 누적시킨다.
- 적용의 성패는 라벨 없는 실행 피드백 신호 설계와 Curator의 병합 규칙 보수성에 달려 있다.
