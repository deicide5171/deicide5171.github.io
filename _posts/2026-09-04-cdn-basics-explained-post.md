## 왜 서버 하나로는 전 세계 사용자를 감당하기 어려운가

서버가 서울에 있는데 미국 사용자가 접속하면, 요청이 태평양을 건너갔다 와야 해서 느리다. 게다가 이미지·CSS·JS 같은 정적 파일을 모든 사용자가 매번 서울 서버에서 받아가면 서버 부하도 커진다. **CDN(Content Delivery Network)**은 전 세계 곳곳에 캐시 서버(엣지 서버)를 두고, 사용자와 가장 가까운 서버에서 콘텐츠를 전달하는 네트워크다.

## CDN이 있을 때와 없을 때

| 항목 | CDN 없음 | CDN 있음 |
|---|---|---|
| 콘텐츠 전달 위치 | 항상 원본 서버(서울) | 사용자와 가까운 엣지 서버 |
| 응답 속도 | 거리에 비례해 느려짐 | 가까운 곳에서 받아 빠름 |
| 원본 서버 부하 | 모든 요청을 직접 처리 | 캐시된 콘텐츠는 엣지가 처리 |
| 트래픽 급증 대응 | 원본 서버가 몰림 | 엣지 서버들이 분산 흡수 |

## 동작 원리

```text
1. 사용자가 이미지를 요청한다
2. 가까운 엣지 서버에 그 이미지가 캐시돼 있으면 -> 바로 전달 (Cache HIT)
3. 캐시에 없으면 -> 엣지 서버가 원본 서버에서 한 번 가져와 캐시하고 전달 (Cache MISS)
4. 다음 사용자부터는 그 엣지 서버에서 바로 받는다
```

첫 요청(MISS)은 원본까지 가지만, 그 뒤로는 엣지에 캐시된 것을 쓰므로 대부분의 요청이 빠르고 원본 서버는 한가해진다.

## 무엇을 CDN에 올리나

- **정적 파일**: 이미지, CSS, JS, 폰트, 동영상처럼 자주 안 바뀌는 파일이 CDN의 주 대상이다.
- **동적 콘텐츠도 일부 가능**: 최근 CDN은 짧은 시간 캐싱이나 엣지 컴퓨팅으로 동적 응답도 일부 가속한다.
- **자주 바뀌는 개인화 데이터**: 사용자마다 다른 정보(장바구니 등)는 캐싱이 까다로워 보통 원본에서 처리한다.

## 실무 포인트

- **캐시 무효화(purge)가 CDN 운영의 핵심 골칫거리다.** 파일을 바꿨는데 엣지에 옛날 버전이 캐시돼 있으면 사용자가 계속 옛 파일을 본다. 그래서 파일명에 버전이나 해시를 붙여(`app.a1b2c3.js`) 바뀔 때마다 새 URL이 되게 하는 방식이 널리 쓰인다.
- **캐시 헤더(`Cache-Control`)를 제대로 설정해야 한다.** 얼마나 오래 캐시할지(`max-age`)를 지정하지 않으면 CDN이 캐싱을 제대로 못 하거나 반대로 너무 오래 잡아둔다.
- **HTTPS 인증서가 엣지에서 처리되는 경우가 많다.** CDN을 붙이면 SSL 종료 위치가 원본이 아니라 CDN 쪽일 수 있으므로, 인증서 갱신 위치를 헷갈리지 않아야 한다.

## 마무리 요약

- CDN은 전 세계에 분산된 엣지 서버로 사용자와 가까운 곳에서 콘텐츠를 전달해 속도를 높이고 원본 부하를 줄인다.
- 이미지·CSS·JS 같은 정적 파일이 주 대상이며, 첫 요청만 원본까지 가고 이후엔 엣지 캐시를 쓴다.
- 캐시 무효화 문제를 파일명 버저닝으로 해결하고, Cache-Control 헤더를 제대로 설정하는 것이 운영의 핵심이다.
