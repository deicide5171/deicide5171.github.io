## 왜 지금 이 문제가 불거지는가

"에이전트 프롬프트 한 줄만 고쳤는데, 다른 시나리오가 같이 망가지지 않았는지 확인해주세요." 코딩 보조부터 고객 상담 에이전트까지, 프롬프트나 도구 구성을 조금만 손봐도 이 요구가 따라붙는다. 문제는 전통적인 유닛테스트 방식이 여기서 그대로 작동하지 않는다는 점이다. 입력 하나에 정답 하나가 매칭되는 구조가 아니라, 같은 입력에도 매 호출마다 다른 문장이 나올 수 있고 도구 호출 순서까지 바뀔 수 있다. 그래서 그동안 실무에서는 "개발자가 몇 가지 시나리오를 수동으로 돌려보고 괜찮아 보이면 배포"하는 방식이 흔했는데, 이 방식은 눈에 보이는 시나리오 몇 개만 확인할 뿐 안 보이는 리그레션을 구조적으로 놓친다.

2026년 들어 에이전트를 프로덕션에 올린 팀들이 공통으로 수렴한 패턴이 있다. 계측(instrument) → 트레이스 수집 → 데이터셋 구축 → 평가자(evaluator) → 점수화 → CI 게이트라는 6단계 파이프라인이다. 핵심 아이디어는 단순하다. 실제 트래픽에서 실패 사례를 뽑아 '정답 세트'로 승격시키고, 이후 모든 변경을 이 세트에 자동으로 다시 돌려 점수가 떨어지면 배포를 막는다. "느낌상 괜찮다"는 판단을 "이 골든셋 기준 몇 점"이라는 숫자로 바꾸는 것이 이 파이프라인의 유일한 목적이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-31-agent-eval-pipeline-golden-dataset-judge-gate-1.svg" alt="프로덕션 트래픽에서 트레이스를 수집하고 실패 사례를 샘플링해 골든 데이터셋으로 승격시킨 뒤, 변경된 에이전트 버전을 이 데이터셋에 재실행해 LLM 저지와 결정론적 검증으로 점수를 매기고, 점수가 기준 밑으로 떨어지면 CI 게이트가 배포를 막는 평가 파이프라인 구조도" style="width:100%;">

이 파이프라인은 기존 관측성(observability) 스택과 입력은 공유하지만 목적이 다르다. OpenTelemetry 기반 트레이싱이 "이 특정 요청이 왜 이렇게 응답했는가"를 사후에 디버깅하는 도구라면, 평가 파이프라인은 "이 변경이 과거에 확인했던 품질을 유지하는가"를 변경 시점마다 자동으로 되묻는 장치다. 트레이스에서 뽑은 어려운 케이스가 골든셋의 재료가 되고, 골든셋은 레포지토리에 버전으로 고정되어 에이전트 코드와 함께 리뷰·머지 대상이 된다. 배포 파이프라인 앞단에 이 게이트가 끼어들면서, 사람이 모든 시나리오를 수동으로 재확인하지 않아도 회귀를 자동으로 걸러내는 구조가 완성된다.

## 선택의 트레이드오프

| 평가 방식 | 정확도 | 비용 | 커버리지 | 적합한 상황 |
|---|---|---|---|---|
| 사람 수동 회귀 확인 | 높음(사람 기준) | 매우 높음(시간) | 낮음 — 확인한 시나리오만 | 초기 PoC, 변경 빈도 낮을 때 |
| 출력 전체를 LLM 저지로 채점 | 중간 — 보정 전 ~70% 수준 | 낮음 | 높음 — 자동 전수 실행 | 자유 형식 응답이 대부분일 때 |
| 구조화된 출력의 결정론적 검증 | 매우 높음 | 매우 낮음 | 스키마가 있는 부분만 | JSON·함수 호출 인자처럼 형식이 고정된 출력 |
| 도구 호출 단위 step-level 평가 | 높음 | 중간 | 중간 경로까지 — 운 좋게 맞은 케이스 포착 | 다단계 에이전트의 중간 판단을 검증할 때 |

표에서 가장 흔한 실수는 **LLM 저지 하나로 모든 것을 끝내려는 것**이다. 저지 모델이 사람 평가와 상관관계가 얼마나 되는지 보정하지 않으면, 점수가 올라가도 실제 사용자 체감 품질은 그대로이거나 나빠질 수 있다. 특히 평가 대상 모델과 저지 모델이 같은 계열이면 자기 선호(self-preference) 편향이 생기기 쉬워, 저지는 가능하면 다른 모델 계열로 분리하는 것이 안전하다. 반대로 구조화된 출력(함수 호출 인자, JSON 필드)이 있는 부분까지 굳이 LLM 저지에 맡기는 것도 낭비다 — 이런 부분은 스키마 검증이나 값 비교 같은 결정론적 체크로 훨씬 싸고 정확하게 잡을 수 있다.

## 실제 프로젝트 진행 순서

1. **가장 흔한 실패 패턴부터 작은 골든셋으로 시작한다.** 30~50개 케이스로도 충분하다. 일반 사용 60%, 엣지 케이스 30%, 적대적 입력 10% 비율을 기준점으로 삼는다.
2. **구조화된 출력이 있는 부분부터 결정론적 검증으로 커버한다.** LLM 저지를 투입하기 전에 싸고 정확한 체크부터 깔아 둔다.
3. **자유 형식 출력에만 LLM 저지를 도입하고, 사람이 매긴 점수와 비교해 저지의 정확도를 보정한다.** 보정 없이 저지 점수를 그대로 신뢰하지 않는다.
4. **최종 응답만이 아니라 도구 호출 단위로 step-level 점수를 추가한다.** 최종 출력만 보면 중간에 엉뚱한 도구를 호출했다가 운 좋게 맞은 경로를 놓친다.
5. **골든셋을 에이전트 코드와 같은 저장소에 버전 고정하고, 변경이 들어올 때마다 CI에서 자동 재실행해 점수 하락 시 머지를 막는다.**

## 실무 포인트

**골든셋은 한 번 만들고 끝내는 것이 아니라 계속 커지는 자산으로 다룬다.** 프로덕션에서 새로운 실패 유형이 발견될 때마다 골든셋에 추가하는 절차를 팀 루틴에 넣어야 파이프라인이 실제로 리그레션을 잡아낸다.

**저지 모델 교체·프롬프트 변경도 평가 대상 변경만큼 신중하게 다룬다.** 저지 자체가 바뀌면 같은 에이전트도 점수가 달라질 수 있으므로, 저지 변경 전후로 기존 골든셋 점수를 다시 비교해 기준선을 재확인해야 한다.

**모든 것을 LLM 저지로 풀려는 유혹을 경계한다.** 구조화된 부분은 결정론적 검증으로, 자유 형식 부분만 저지로 나누는 것이 비용과 정확도 양쪽에서 더 낫다.

## 마무리

- 에이전트의 비결정적 출력은 전통적 유닛테스트로 검증되지 않으며, 수동 회귀 확인은 안 보이는 리그레션을 구조적으로 놓친다.
- 트레이스→골든데이터셋→평가자→점수화→CI 게이트로 이어지는 파이프라인이 "느낌상 괜찮다"를 "이 골든셋 기준 몇 점"이라는 숫자로 바꾼다.
- LLM 저지는 사람 평가와의 상관관계를 보정해야 신뢰할 수 있고, 구조화된 출력은 결정론적 검증으로, 중간 판단은 step-level 평가로 나눠서 커버해야 한다.
