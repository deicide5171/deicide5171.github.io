"평소 대비 5배 트래픽이 예상되니 서버를 5배로 늘리자"는 계획은 십중팔구 틀린다. 트래픽이 5배가 돼도 DB 커넥션 풀, 캐시 히트율, 다운스트림 서비스의 처리 한계 같은 병목은 선형으로 늘어나지 않기 때문이다. 애플리케이션 서버는 넉넉히 늘렸는데 정작 병목이던 DB 커넥션 풀은 그대로 둬서 장애가 나는 사례가 반복되는 이유가 여기에 있다.

**용량 계획(capacity planning)**은 트래픽 예측만으로 끝나는 작업이 아니라, 시스템의 각 구성 요소가 실제로 어디서 먼저 무너지는지를 찾고 그 가정을 실제 부하로 검증하는 과정이다. 이 글에서는 용량 계획을 트래픽 모델링, 병목 식별, 부하 테스트 검증의 3단계로 나누어 각 단계에서 실무자가 흔히 놓치는 지점을 정리한다.

## 핵심 개념 1: 트래픽 모델링 — 평균이 아니라 형태를 예측한다

용량 계획의 첫 단계는 "얼마나 많은 트래픽이 올 것인가"를 숫자 하나로 답하는 게 아니라 트래픽의 **형태(shape)**를 예측하는 것이다. 평시 대비 배수만 보면 놓치는 것이 세 가지다. 첫째, 피크가 지속되는 시간 — 순간 스파이크 5분과 지속 부하 3시간은 캐시 워밍업, 오토스케일링 반응 시간 관점에서 완전히 다른 문제다. 둘째, 트래픽의 요청 구성 변화 — 세일 시작 시점에는 상품 조회(읽기)가 압도적으로 늘고, 그 뒤에는 결제(쓰기)가 상대적으로 늘어나는 식으로 워크로드 프로파일 자체가 시간에 따라 바뀐다. 셋째, 캐시 히트율의 변화 — 평소엔 인기 상품 몇 개에 트래픽이 몰려 캐시 히트율이 높지만, 프로모션으로 다양한 상품이 동시에 조회되면 캐시 미스가 급증해 DB 부하가 트래픽 증가율보다 더 가파르게 늘 수 있다.

## 핵심 개념 2: 병목 식별 — 시스템은 가장 약한 고리 속도로 달린다

트래픽 형태를 예측했다면, 다음은 그 트래픽이 시스템의 어느 구성 요소를 가장 먼저 포화시키는지 찾는 일이다. 실무에서 자주 병목이 되는 지점은 애플리케이션 서버 CPU가 아니라 그 뒤에 숨어 있다.

| 병목 후보 | 흔한 징후 | 확인 방법 |
|---|---|---|
| DB 커넥션 풀 | 앱은 idle인데 요청이 큐잉됨 | 풀 사용률·대기 큐 길이 모니터링 |
| 다운스트림 외부 API 레이트리밋 | 특정 API 호출부터 지연 급증 | 서드파티 호출 응답시간 분리 측정 |
| 캐시 계층 처리량 | 캐시 히트율 급락과 동시에 지연 증가 | 캐시 서버 CPU·네트워크 대역 |
| 메시지 큐 컨슈머 처리 속도 | 큐 적체(consumer lag) 증가 | 컨슈머 처리량 vs 프로듀서 발행률 |
| 오토스케일링 반응 지연 | 스케일 아웃 전까지의 초반 몇 분 장애 | 신규 인스턴스 부팅+워밍업 시간 |

이 표에서 중요한 점은 병목이 대개 "가장 눈에 잘 띄는 지표"가 아니라는 것이다. CPU 사용률이 여유로워도 커넥션 풀이 고갈되면 시스템 전체가 느려지고, 이때 흔히 저지르는 실수가 "CPU가 여유롭다"는 이유로 애플리케이션 서버부터 늘리는 것이다. 실제 필요한 조치는 커넥션 풀 크기나 DB 자체의 처리 능력 확장이었을 수 있다.

## 핵심 개념 3: 부하 테스트 — 추정을 검증으로 바꾼다

병목 후보를 식별했다면, 실제 부하 테스트로 그 가정을 검증해야 한다. 부하 테스트에는 목적에 따라 몇 가지 다른 방식이 있다. **부하 테스트(load test)**는 예상 피크 트래픽을 그대로 재현해 시스템이 견디는지 확인하고, **스트레스 테스트(stress test)**는 시스템이 무너지는 지점까지 트래픽을 계속 올려 한계와 장애 양상을 관찰하며, **스파이크 테스트(spike test)**는 트래픽이 급격히 치솟았다가 가라앉는 패턴을 재현해 오토스케일링 반응 속도를 검증하고, **소크 테스트(soak test)**는 중간 부하를 오래(수 시간~하루) 유지해 메모리 누수나 커넥션 누수처럼 시간이 지나야 드러나는 문제를 잡는다.

## 예제: k6로 단계적 부하 테스트 시나리오 작성

```javascript
// checkout-load-test.js — 단계적 부하 증가 + 병목 지점 체크
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

const dbBottleneckErrors = new Rate('db_connection_errors');
const checkoutDuration = new Trend('checkout_duration');

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // 평시 수준으로 워밍업
    { duration: '5m', target: 500 },   // 예상 피크까지 점진 증가
    { duration: '10m', target: 500 },  // 피크 유지 (지속 부하 확인)
    { duration: '3m', target: 1500 },  // 예상치의 3배 — 병목 한계 탐색
    { duration: '5m', target: 0 },     // 회복 속도 관찰
  ],
  thresholds: {
    http_req_duration: ['p(95)<800'],       // 95%ile 800ms 이내
    db_connection_errors: ['rate<0.01'],    // 커넥션 에러율 1% 미만
  },
};

export default function () {
  const res = http.post('https://staging.example.com/api/checkout', JSON.stringify({
    userId: `user-${__VU}`,
    items: [{ productId: 'sku-1234', qty: 1 }],
  }), { headers: { 'Content-Type': 'application/json' } });

  checkoutDuration.add(res.timings.duration);
  dbBottleneckErrors.add(res.status === 503);

  check(res, { '결제 성공': (r) => r.status === 200 });
  sleep(1);
}
```

이 스크립트는 예상 피크(500 VU)를 검증하는 데서 그치지 않고, 그 3배(1500 VU)까지 밀어붙여 어디서 먼저 무너지는지를 관찰하는 스트레스 테스트 요소까지 포함한다. 회복 단계(마지막 5분)를 넣은 이유는 트래픽이 빠져도 커넥션 풀이나 큐 적체가 즉시 회복되지 않는 시스템을 잡아내기 위해서다.

## 실무 포인트

- **부하 테스트는 프로덕션과 최대한 동일한 환경에서 해야 의미가 있다.** 스테이징 환경의 DB 인스턴스 사양이나 커넥션 풀 크기가 프로덕션과 다르면, 병목 지점 자체가 다르게 나타나 테스트 결과가 프로덕션에 그대로 적용되지 않는다. 완전히 동일한 사양을 유지하기 어렵다면 최소한 병목 후보로 지목한 구성 요소(DB, 캐시)만이라도 동일 사양으로 맞춰야 한다.
- **서드파티 의존성은 실제로 호출하지 말고 격리해서 테스트하라.** 결제 게이트웨이, 알림 발송 API 같은 외부 서비스를 부하 테스트에서 실제로 호출하면 그쪽 레이트리밋에 걸리거나 상대 서비스에 피해를 줄 수 있다. 목(mock) 서버로 대체하되, 그 목 서버가 실제 서드파티의 지연 시간 분포를 흉내 내도록 만들어야 결과가 왜곡되지 않는다.
- **용량 계획 문서는 한 번 쓰고 끝내는 게 아니라 이벤트마다 갱신해야 한다.** 지난 세일 때의 병목 지점이 이번에도 그대로일 거라는 보장이 없다 — 그 사이 코드 변경, 인프라 변경, 트래픽 패턴 변화가 있었을 수 있으므로 이전 용량 계획을 그대로 재사용하지 말고 매번 최신 상태로 병목 재식별과 부하 테스트를 다시 수행해야 한다.

## 3줄 요약

- 용량 계획은 트래픽 배수를 예측하는 것으로 끝나지 않고, 트래픽의 형태(지속 시간, 요청 구성 변화, 캐시 히트율 변화)를 모델링하는 데서 시작한다.
- 실제 병목은 애플리케이션 서버가 아니라 DB 커넥션 풀, 다운스트림 API, 캐시 계층처럼 눈에 덜 띄는 곳에 숨어 있는 경우가 많아, CPU 여유만 보고 잘못된 곳을 확장하는 실수를 피해야 한다.
- 부하·스트레스·스파이크·소크 테스트를 목적에 맞게 조합해 병목 가정을 실제 트래픽으로 검증하고, 이 계획은 이벤트마다 최신 상태로 갱신해야 한다.
