## 왜 지금 A2A인가

한동안 "에이전트 상호운용성" 논의는 MCP(Model Context Protocol) 하나로 수렴되는 듯 보였다. 하지만 MCP는 에이전트가 **도구·데이터 소스**에 접근하는 방식을 표준화한 것이지, 서로 다른 벤더가 만든 **에이전트끼리 작업을 위임하고 진행 상황을 주고받는** 문제는 다루지 않는다.

실무에서 여러 팀이 각자 프레임워크(LangGraph, AutoGen, 사내 커스텀 에이전트 등)로 에이전트를 만들다 보면, "내 여행 예약 에이전트가 파트너사의 항공권 에이전트에게 검색을 맡기고 결과를 받는" 식의 협업이 필요해진다. 이 빈틈을 메우려는 시도가 **Agent2Agent(A2A)** 계열 프로토콜이며, MCP와 상호 보완적으로 함께 논의되는 경우가 늘고 있다.

블로그에서 지난 글로 MCP를 다뤘으니, 이번엔 그 위에서 "에이전트 간" 계층을 어떻게 표준화하려 하는지 살펴본다.

## MCP와 A2A, 무엇이 다른가

| 항목 | MCP | A2A |
|---|---|---|
| 연결 대상 | 도구, 데이터 소스, 파일 시스템 | 다른 에이전트(원격 서비스) |
| 핵심 단위 | Tool, Resource | Task, Agent Card |
| 통신 방향 | 에이전트 → 도구(단방향 호출) | 에이전트 ↔ 에이전트(양방향, 장시간 작업) |
| 상태 관리 | 대체로 stateless 호출 | Task 진행 상태(작업 중/입력 필요/완료) 추적 |
| 대표 시나리오 | DB 조회, 파일 읽기, API 호출 | 하위 에이전트에 조사·예약·결제 위임 |

두 프로토콜은 경쟁 관계라기보다, MCP가 "에이전트-도구" 축을, A2A가 "에이전트-에이전트" 축을 맡는 형태로 자리를 잡아가고 있다.

## 핵심 개념: Agent Card와 Task 생명주기

A2A에서 각 에이전트는 자신의 능력을 알리는 **Agent Card**(JSON 메타데이터)를 공개한다. 여기에는 지원하는 스킬, 인증 방식, 입출력 형식이 담긴다. 요청자는 이 카드를 보고 어떤 에이전트에게 작업을 맡길지 판단한다.

작업은 **Task**로 표현되며, 생성 → 진행 중 → (필요 시) 추가 입력 요청 → 완료/실패의 생명주기를 갖는다. 이는 단순 요청-응답이 아니라 "사람 승인 대기" 같은 장시간 상호작용을 표준적으로 표현하기 위함이다.

## 예제: Agent Card 선언

```json
{
  "name": "flight-search-agent",
  "description": "항공권 검색 및 가격 비교를 수행하는 에이전트",
  "url": "https://partner.example.com/a2a",
  "capabilities": { "streaming": true, "pushNotifications": false },
  "skills": [
    { "id": "search-flight", "description": "출발지/도착지/날짜로 항공권 검색" }
  ]
}
```

요청 에이전트는 이 카드의 `skills`를 보고 `search-flight` 작업을 Task로 생성해 위임한다.

## 실무 포인트

- **아직 표준이 유동적이다**: 여러 벤더가 참여하는 초기 단계라, 사양이 바뀔 수 있음을 감안하고 추상화 계층을 얇게 유지한다.
- **인증·신뢰 경계를 먼저 설계한다**: 외부 에이전트에게 작업을 위임하는 순간 새로운 공격 표면이 생긴다. Agent Card의 출처 검증과 권한 범위 제한이 필수다.
- **MCP와 역할을 혼동하지 않는다**: "이 호출이 도구 접근인가, 다른 에이전트에게 작업을 맡기는 것인가"를 먼저 구분하고 프로토콜을 선택한다.
- **Task 상태를 로깅한다**: 장시간 비동기 작업이 많아지므로, 각 Task의 상태 전이를 추적할 수 있어야 장애 원인 파악이 쉬워진다.

## 3줄 요약

- MCP가 에이전트와 도구를 연결한다면, A2A는 서로 다른 벤더의 에이전트끼리 작업을 위임·협상하는 계층을 표준화하려 한다.
- 핵심 단위는 능력을 알리는 Agent Card와, 상태 전이를 갖는 Task다.
- 아직 표준이 유동적인 초기 단계이므로 얇은 추상화와 신뢰 경계 설계가 우선이다.
