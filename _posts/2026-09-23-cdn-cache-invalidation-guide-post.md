## 왜 배포 직후에도 옛날 화면이 보일까

배포 파이프라인이 성공적으로 끝났는데도 일부 사용자에게는 여전히 어제자 CSS나 깨진 레이아웃이 보인다는 문의가 들어온다. 서버는 이미 새 파일을 서빙하고 있는데, 정작 사용자 브라우저와 그 사이에 있는 CDN 엣지 서버가 예전 응답을 여전히 캐시에 들고 있기 때문이다. 원본 서버(오리진)를 아무리 새로 배포해도, CDN이 그 앞에서 옛날 응답을 계속 돌려주면 사용자 입장에서는 배포가 반영되지 않은 것처럼 보인다.

이 문제가 골치 아픈 이유는 재현이 들쭉날쭉하다는 점이다. 어떤 사용자는 캐시가 만료돼 새 화면을 보고, 어떤 사용자는 며칠 지난 캐시를 그대로 본다. "내 컴퓨터에서는 잘 되는데요"의 CDN 버전이라고 봐도 무방하다.

## 핵심 개념 1 — 캐시 무효화 방법은 크게 세 가지다

CDN에 캐시된 옛 콘텐츠를 새 것으로 바꾸는 방법은 아래 세 가지로 나뉘고, 각각 트레이드오프가 다르다.

| 방법 | 동작 방식 | 장점 | 단점 |
|---|---|---|---|
| Purge(강제 삭제) | CDN API로 특정 URL 캐시를 즉시 삭제 | 즉각 반영 | 전 세계 엣지에 전파되는 데 수초~수분 소요, API 비용/횟수 제한 |
| TTL 짧게 설정 | Cache-Control max-age를 짧게 유지 | 별도 조작 불필요 | 캐시 적중률이 낮아져 오리진 부하 증가 |
| 파일명 버저닝(캐시 버스팅) | 파일명에 해시를 넣어 URL 자체를 바꿈 | 무효화가 필요 없음, TTL을 길게 잡아도 안전 | HTML처럼 자주 바뀌는 파일 자체에는 적용 어려움 |

세 가지 중 가장 견고한 방법은 파일명 버저닝이다. `app.js`가 아니라 `app.a1b2c3.js`처럼 빌드마다 내용 해시를 파일명에 박아 넣으면, 파일 내용이 바뀌지 않는 한 URL도 바뀌지 않고 내용이 바뀌면 URL도 반드시 바뀐다. 이러면 이 파일에는 `max-age=31536000, immutable`처럼 1년짜리 캐시를 걸어도 안전하다 — 어차피 내용이 바뀌면 새 URL로 요청되기 때문이다.

## 핵심 개념 2 — HTML은 버저닝할 수 없으니 짧은 TTL이 필요하다

정적 자산(JS, CSS, 이미지)은 파일명 버저닝으로 해결되지만, 그 자산들을 참조하는 HTML 파일 자체는 사람이 접속하는 URL(`/`, `/about`)이라 파일명을 바꿀 수 없다. 그래서 HTML에는 반대로 **캐시를 거의 하지 않거나 매우 짧게** 설정해야 한다. HTML이 오래 캐시되면, 그 안에 담긴 정적 자산 참조 링크 자체가 옛날 버전을 가리키게 되어 버저닝 전략 전체가 무의미해진다.

```
# 정적 자산(해시 파일명 포함): 길게, 불변으로
Cache-Control: public, max-age=31536000, immutable

# HTML 문서: 짧게, 매번 재검증
Cache-Control: public, max-age=0, must-revalidate
```

## 예제 — 긴급 상황에서 특정 경로만 강제 무효화하기

새 배포에 심각한 버그가 있어 즉시 롤백하면서 CDN 캐시도 강제로 지워야 하는 상황이라면, 대부분의 CDN이 제공하는 Purge API를 스크립트로 호출한다.

```bash
# Cloudflare 예시: 특정 경로 캐시 강제 삭제
curl -X POST "https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/purge_cache" \
  -H "Authorization: Bearer ${API_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{"files":["https://example.com/index.html"]}'
```

전체 캐시를 통째로 지우는(Purge Everything) 옵션도 있지만, 이건 순간적으로 모든 요청이 오리진으로 몰리는 캐시 스탬피드를 유발할 수 있어 트래픽이 많은 서비스에서는 특정 경로만 골라 지우는 편이 안전하다.

## 실무 포인트

- **stale-while-revalidate를 활용하면 즉시성과 부하를 동시에 잡을 수 있다.** 이 지시어를 쓰면 캐시가 만료된 직후에도 일단 오래된 응답을 즉시 내려주면서, 백그라운드에서 새 응답을 가져와 다음 요청부터 반영한다. 사용자는 항상 빠른 응답을 받고, 콘텐츠도 곧 최신화된다.
- **배포 파이프라인에 Purge 단계를 자동으로 넣어라.** 사람이 수동으로 CDN 콘솔에 들어가 캐시를 지우는 방식은 잊어버리기 쉽다. CI/CD 스크립트 마지막 단계에 Purge API 호출을 포함시켜야 재발을 막을 수 있다.
- **CDN 엣지 전파 지연을 감안하라.** Purge를 호출했다고 전 세계 모든 엣지 서버에 즉시 반영되는 것은 아니다. 리전에 따라 수초에서 길게는 1~2분까지 걸릴 수 있으므로, 배포 직후 스모크 테스트는 이 지연을 감안해 타이밍을 잡아야 한다.

## 마무리 요약

- 배포 직후 옛 화면이 보이는 문제는 대부분 오리진이 아니라 CDN 엣지 캐시가 원인이다.
- 정적 자산은 파일명에 해시를 넣는 버저닝으로 캐시를 길게, HTML은 캐시를 짧게 설정하는 것이 가장 견고한 조합이다.
- 긴급 상황에서는 Purge API로 특정 경로만 무효화하고, 배포 파이프라인에 자동화해 재발을 막아야 한다.
