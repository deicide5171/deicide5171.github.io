## 왜 지금 이 문제가 불거지는가

2026년 들어 AI 에이전트를 실제 업무 프로세스에 투입하는 기업이 빠르게 늘고 있다. 단순 챗봇 수준을 넘어, 코드 작성·데이터 분석·고객 응대·워크플로우 자동화까지 에이전트가 여러 단계를 스스로 계획하고 실행하는 사례가 많아지는 추세다. 문제는 이 과정에서 발생하는 비용을 사전에 정확히 산정하기가 예전보다 훨씬 어려워졌다는 점이다.

기존의 SaaS나 클라우드 인프라 비용은 사용자 수, 트래픽량 같은 비교적 예측 가능한 지표에 기반해 왔다. 반면 에이전트 비용은 "작업 하나를 완료하는 데 모델이 몇 번의 추론을 거쳤는가"에 좌우된다. 같은 작업이라도 에이전트가 한 번에 답을 내는 경우와 열 번의 도구 호출과 재시도를 거치는 경우의 비용 차이가 수십 배에 이를 수 있다고 보고된다. 이 때문에 재무팀과 엔지니어링팀 모두 1~3년 단위의 AI 비용 예산을 세우는 데 어려움을 겪고 있는 것으로 알려졌다.

이 글에서는 에이전트 비용 예측이 어려운 근본 원인을 짚어보고, 실무에서 비용 폭증 리스크를 완화하기 위해 쓰이는 패턴들을 정리한다.

## 비용 예측을 어렵게 만드는 요인들

| 요인 | 설명 |
|---|---|
| 토큰 소비 변동성 | 같은 프롬프트라도 컨텍스트 길이, 검색된 문서량, 대화 히스토리 누적에 따라 토큰 수가 크게 달라진다 |
| 에이전트 루프 | 목표 달성 전까지 스스로 반복 추론하는 구조라 종료 시점이 사전에 고정되지 않는다 |
| 재시도·오류 복구 | 도구 호출 실패, API 타임아웃 등으로 동일 단계를 여러 번 재시도하면 비용이 누적된다 |
| 멀티 에이전트 협업 | 하나의 작업을 여러 서브 에이전트가 나눠 처리할 경우 호출 횟수가 조합적으로 늘어난다 |
| 모델 가격 변동 | 공급자별 가격 정책과 신규 모델 출시 주기가 짧아 장기 단가 가정 자체가 흔들린다 |

특히 에이전트 루프는 전통적인 API 과금 모델과 근본적으로 다르다. 일반 API 호출은 요청 1건당 응답 1건으로 비용이 선형적이지만, 에이전트는 "작업 완료"라는 불확실한 종료 조건을 향해 스스로 단계를 늘려갈 수 있어 최악의 경우 비용이 기하급수적으로 증가할 위험이 있다는 지적이 나온다.

## 비용 폭증을 막는 실무 패턴

**1. 사용량 상한(budget guardrail)**

작업당 최대 토큰 수, 최대 도구 호출 횟수, 최대 실행 시간을 미리 설정해 에이전트가 이를 초과하면 강제 종료하거나 사람에게 확인을 요청하도록 한다.

**2. 프롬프트·응답 캐싱**

반복되는 시스템 프롬프트나 문서 컨텍스트를 캐싱하면 동일 입력에 대한 재계산 비용을 크게 줄일 수 있다. 대부분의 최신 LLM API는 프롬프트 캐싱 기능을 제공하며, 캐시 적중률이 높을수록 단가가 낮아지는 구조다.

**3. 모델 라우팅**

모든 단계에 고성능·고비용 모델을 쓰는 대신, 단순 분류나 요약처럼 난이도가 낮은 하위 작업은 경량 모델로, 복잡한 추론이 필요한 단계만 상위 모델로 라우팅하는 방식이다.

**4. 관측성(observability) 확보**

토큰 사용량, 호출 횟수, 실패율을 작업 단위로 추적하는 대시보드가 없으면 비용 급증을 사후에야 알아차리게 된다. 아래는 간단한 예산 상한 설정 예시다.

```yaml
# agent-budget-policy.yaml
agent:
  max_tool_calls: 20
  max_tokens_per_task: 150000
  max_runtime_seconds: 300
  on_limit_exceeded: "halt_and_notify"
  model_routing:
    default: "small-model"
    escalate_on:
      - "complex_reasoning"
      - "multi_step_planning"
```

```python
# 토큰 사용량 실시간 추적 예시
def run_agent_step(step_fn, budget):
    if budget.tokens_used >= budget.max_tokens:
        raise BudgetExceededError("작업 예산 초과, 실행 중단")
    result = step_fn()
    budget.tokens_used += result.usage.total_tokens
    return result
```

## 실무 포인트와 주의사항

비용 상한을 지나치게 타이트하게 잡으면 에이전트가 작업을 끝내지 못하고 중도 실패하는 사례가 늘어날 수 있다. 반대로 상한이 없으면 재시도 루프 하나가 예상치 못한 청구서로 이어질 위험이 있다. 따라서 초기에는 여유 있는 상한과 알림 체계로 시작해, 실제 사용 패턴 데이터를 쌓은 뒤 점진적으로 조정하는 접근이 안전하다고 여겨진다. 또한 공급자별 모델 가격은 자주 변동되므로, 장기 예산안에는 고정 단가 대신 범위(range) 형태의 시나리오를 넣는 편이 현실적이다.

## 3줄 요약

- 에이전트 비용은 루프·재시도 구조 때문에 전통적인 API 과금보다 예측이 훨씬 어렵다.
- 사용량 상한, 프롬프트 캐싱, 모델 라우팅, 관측성 확보가 실무에서 검증된 완화 패턴이다.
- 장기 예산은 고정 단가보다 범위 기반 시나리오로 세우는 것이 현실적이다.
