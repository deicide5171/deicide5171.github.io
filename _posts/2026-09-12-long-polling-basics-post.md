## 새 알림을 계속 물어보는 건 낭비다

서버에 새 소식이 있는지 확인하려고 1초마다 요청을 보내면(일반 폴링), 대부분은 "없음" 응답이라 낭비가 크다. **롱 폴링(long polling)**은 이 낭비를 줄이는 기법이다. 서버가 요청을 받으면 **바로 답하지 않고, 새 데이터가 생길 때까지(또는 타임아웃까지) 응답을 붙잡고 기다린다.**

## 일반 폴링 vs 롱 폴링

| 구분 | 일반 폴링 | 롱 폴링 |
|---|---|---|
| 응답 시점 | 즉시(없어도) | 데이터 생기면 |
| 빈 응답 | 많음(낭비) | 거의 없음 |
| 실시간성 | 주기만큼 지연 | 거의 즉시 |

## 동작 흐름

```text
[일반 폴링] 1초마다: 요청 -> "없음" -> 요청 -> "없음" ...
[롱 폴링]  요청 -> 서버가 붙잡고 대기 -> 데이터 생김 -> 응답
           클라이언트는 응답받자마자 다시 요청(연결 유지)
```

## 실무 포인트

- **웹소켓을 못 쓸 때의 대안이다.** 진짜 양방향 실시간은 웹소켓이 낫다. 하지만 웹소켓을 지원 못 하는 환경이거나 서버 → 클라이언트 알림만 필요하면 롱 폴링이 간단한 대안이 된다. 요즘은 SSE도 많이 쓴다.
- **타임아웃을 설정하라.** 서버가 무한정 붙잡으면 자원이 묶인다. 일정 시간(예: 30초) 지나면 "없음"으로 응답하고, 클라이언트가 다시 요청하게 한다.
- **연결 수와 자원에 주의.** 롱 폴링은 각 클라이언트가 응답을 기다리며 연결을 점유한다. 동시 사용자가 많으면 대기 중 연결이 서버 자원을 잡아먹으니 규모를 고려한다.

## 마무리 요약

- 롱 폴링은 서버가 새 데이터가 생길 때까지 응답을 붙잡아 실시간에 가깝게 알림을 준다.
- 일반 폴링의 빈 응답 낭비를 줄이면서 웹소켓 없이 구현할 수 있다.
- 타임아웃 설정과 동시 연결 자원 관리가 필요하며, 요즘은 SSE·웹소켓이 대안이다.
