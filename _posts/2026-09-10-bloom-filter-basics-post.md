## "이 값이 있나?"를 매번 DB에 물어보면 느리다

회원가입에서 "이미 쓰는 아이디인가?"를 매번 DB에서 확인하면 부하가 크다. 특히 대부분이 "없는" 값이라면 헛조회가 많다. **블룸 필터(Bloom filter)**는 **적은 메모리로 "이 값이 확실히 없다"를 빠르게 판정**하는 자료구조다. "없다"고 하면 진짜 없으니, DB를 안 봐도 된다.

## 핵심 특징

| 블룸 필터의 답 | 의미 |
|---|---|
| "없다" | 100% 확실히 없다 (DB 조회 불필요) |
| "있다(아마)" | 있을 수도, 없을 수도 (DB로 확인 필요) |

즉 **없다는 확실하지만, 있다는 불확실**하다. 이 "가끔 틀리는 있음(거짓 양성)"을 감수하는 대신, 메모리를 아주 적게 쓴다.

## 어떻게 동작하나

```text
값을 여러 해시 함수로 돌려 비트 배열의 여러 자리를 1로 켠다.
"apple" 추가 -> 3, 7, 11번 비트 켜짐

조회: "banana" -> 해시 결과 2, 7, 11번 확인
  2번이 0 -> 하나라도 0이면 "확실히 없음"
  모두 1 -> "아마 있음" (다른 값이 켰을 수도)
```

## 실무 포인트

- **캐시 앞단에서 헛조회를 막는다.** "DB에 없는 키"를 계속 조회하는 요청(캐시 관통, cache penetration)을 블룸 필터로 먼저 걸러 DB 부하를 줄인다. Redis 등에서 활용된다.
- **삭제가 어렵다.** 비트를 껐다가는 같은 비트를 공유하는 다른 값까지 "없음"이 되어버린다. 삭제가 필요하면 카운팅 블룸 필터 같은 변형을 쓴다.
- **크기와 오탐률은 트레이드오프다.** 비트 배열이 작으면 메모리는 절약되지만 "거짓 양성"이 늘어난다. 예상 데이터 수에 맞춰 크기와 해시 개수를 정한다.

## 마무리 요약

- 블룸 필터는 적은 메모리로 "이 값이 확실히 없다"를 빠르게 판정하는 자료구조다.
- "없다"는 확실하고 "있다"는 불확실(거짓 양성 가능)해, DB 헛조회를 줄이는 데 쓴다.
- 삭제가 어렵고 크기·오탐률이 트레이드오프이므로 데이터 규모에 맞게 설계한다.
