## 왜 요금이 '글자 수'가 아니라 '토큰'인가

LLM API 요금표를 보면 "100만 토큰당 얼마"라고 표시된다. 컨텍스트 길이 제한도 "128K 토큰"처럼 토큰 단위로 표현된다. 그런데 정작 "토큰이 몇 글자인가"는 딱 잘라 말하기 어렵다. **토큰(token)**은 LLM이 텍스트를 처리하는 최소 단위로, 글자도 단어도 아닌 그 중간쯤의 조각이기 때문이다.

## 토큰은 어떻게 쪼개지는가

| 텍스트 | 대략적인 토큰 수 | 설명 |
|---|---|---|
| "hello" | 1토큰 | 흔한 영어 단어는 통째로 1토큰 |
| "tokenization" | 2~3토큰 | 긴 단어는 여러 조각으로 나뉨 |
| "안녕하세요" | 3~5토큰 | 한국어는 영어보다 토큰이 더 많이 나오는 경향 |
| "1234567890" | 여러 토큰 | 숫자도 조각으로 나뉨 |

일반적인 경험칙으로 **영어는 1토큰이 약 4글자**, **한국어는 글자당 토큰 수가 영어보다 많다**. 즉 같은 의미의 문장이라도 한국어로 쓰면 영어보다 토큰이 더 많이 소모되는 경향이 있어 요금과 길이 제한에 불리할 수 있다.

## 왜 이렇게 쪼개는가

```text
LLM은 자주 등장하는 문자 조합을 하나의 토큰으로 미리 학습해둔다(BPE 등의 방식).
- 자주 쓰는 단어("the", "and")는 통째로 1토큰 -> 효율적
- 드문 단어나 오타는 여러 조각으로 분해 -> 그래도 처리 가능

이 방식 덕분에 모델이 처음 보는 단어도 조각 단위로는 이해할 수 있고,
어휘 사전 크기를 무한정 키우지 않아도 된다.
```

## 코드 예제: 토큰 수 세어보기

```python
import tiktoken  # OpenAI 계열 토크나이저

enc = tiktoken.get_encoding("cl100k_base")

text = "안녕하세요, 토큰을 세어봅시다."
tokens = enc.encode(text)
print(f"토큰 수: {len(tokens)}")
print(f"글자 수: {len(text)}")
# 한국어는 글자 수보다 토큰 수가 더 많이 나오는 것을 확인할 수 있다
```

실제 요청을 보내기 전에 토큰 수를 미리 계산하면, 컨텍스트 길이 초과 에러를 사전에 방지하고 예상 비용도 가늠할 수 있다.

## 실무 포인트

- **입력 토큰과 출력 토큰은 보통 요금이 다르다.** 대부분 출력 토큰이 더 비싸므로, 응답을 불필요하게 길게 생성하지 않도록 `max_tokens`를 적절히 제한하는 것이 비용 절감에 직접적이다.
- **긴 시스템 프롬프트를 반복 호출한다면 프롬프트 캐싱을 검토하라.** 같은 앞부분을 매번 다시 처리하는 대신 캐시하면 토큰 비용을 크게 줄일 수 있다.
- **컨텍스트 길이 제한은 입력과 출력을 합친 값이다.** 입력을 제한까지 꽉 채우면 정작 답변을 생성할 토큰 여유가 없어져 응답이 잘리므로, 출력 공간을 미리 남겨둬야 한다.

## 마무리 요약

- 토큰은 LLM이 텍스트를 처리하는 최소 단위로, 글자도 단어도 아닌 중간 크기의 조각이다.
- 한국어는 영어보다 같은 의미에 더 많은 토큰을 소모하는 경향이 있어 비용·길이에 불리할 수 있다.
- 입력·출력 토큰 요금이 다르고 컨텍스트 제한은 둘의 합이므로, max_tokens 관리가 비용과 안정성에 직접 영향을 준다.
