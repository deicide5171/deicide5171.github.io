## 왜 지금 이 판단이 필요한가

"에이전트가 짠 PR, CI만 초록불이면 바로 머지해주세요. 리뷰어 한 명 붙이는 것도 병목이에요." 코딩 에이전트를 팀 파이프라인에 들인 뒤 한 번쯤 듣게 되는 요구다. 실제로 2026년 하반기 들어 여러 팀이 리뷰 병목을 줄이려고 "PR 한 건당 사람 리뷰어 1명, 때로는 작성자 본인"까지 승인 범위를 좁히는 실험을 공개적으로 이야기하고 있다. 자동 테스트만 통과하면 사람이 거의 개입하지 않는 쪽으로 파이프라인을 밀어붙이는 흐름이다.

문제는 "테스트 통과"라는 신호 자체가 생각보다 약하다는 데 있다. 2026년 3월 METR이 scikit-learn·Sphinx·pytest 세 프로젝트의 실제 메인테이너를 불러 AI 생성 기여 296건을 검토하게 한 연구에서, 자동 테스터를 통과한 해결책의 절반 가까이가 실제 메인테이너라면 머지하지 않을 수준이었다고 보고했다. 더 놀라운 건 사람이 작성해 실제로 배포까지 된 참조 해결책조차 같은 심사에서 68%만 재승인됐다는 점이다. "테스트 통과"와 "머지해도 되는 코드"는 애초에 같은 말이 아니었던 셈이다.

여기에 더해 2026년 8월 공개된 한 arXiv 논문(2608.14711)은 업계가 흔히 쓰는 pass@k 구현 방식 자체의 허점을 짚었다. 같은 작업에 딸린 여러 단위 테스트를 서로 독립적인 시도처럼 세는 바람에 점수가 절대값 기준 0.85~0.97포인트까지 부풀려지고, 심하면 모델 순위까지 뒤집힌다는 것이다. 이 논문은 대안으로 reliability@k 지표와 신뢰할 만한 순위를 위해 최소 5회 반복 실행을 권고한다. "에이전트 벤치마크 몇 점"이라는 숫자 하나로 머지 게이트의 신뢰 수준을 정하는 설계는 이제 근거가 빈약하다.

## pass@k와 pass^k(reliability@k), 무엇이 다른가

두 지표는 같은 반복 실행 결과에서 전혀 다른 질문에 답한다.

- **pass@k** — 같은 작업을 k번 시도했을 때 **적어도 한 번**은 성공하는가. 모델의 역량 상한(capability ceiling)을 잰다. 에이전트가 "할 수 있는가"를 보여주는 지표다.
- **pass^k (reliability@k)** — 같은 작업을 k번 시도했을 때 **k번 전부** 성공하는가. 모델이 실제로 매번 안정적으로 내놓는 신뢰 바닥(reliability floor)을 잰다. "항상 이 결과를 보장하는가"를 보여주는 지표다.

이 격차는 숫자로 보면 더 분명하다. 2026년 5월 공개된 SWE Atlas 벤치마크는 같은 모델·스캐폴드 조합에서 Pass@3 대비 Pass^3이 2~3배 떨어진다고 보고했다. 컴퓨터 사용 에이전트 리서치에서도 Agent S3가 pass@10 기준 약 78%를 기록했지만 pass^10은 약 36%에 그친 사례가 있다. 시행당 성공률이 75%인 에이전트조차 3회 연속 전부 성공할 확률은 약 42%에 불과하다는 계산도 함께 인용된다. 벤치마크 발표자료의 헤드라인 숫자는 거의 항상 pass@k이고, pass^k를 함께 보고하는 사례는 드물다는 점이 이 문제를 더 키운다.

## 전체 파이프라인에서 이 게이트는 어디에 있는가

머지 게이트는 코드 생성과 배포 사이, 딱 한 지점에 있는 것 같지만 실제로는 "무엇을 측정해서 어디로 라우팅하는가"라는 분기 로직 전체를 가리킨다. 기존에는 에이전트가 PR 하나를 만들고, CI가 테스트를 한 번 돌려 통과하면 그대로(혹은 리뷰어 1명만 거쳐) 머지되는 단일 경로였다. 이 경로가 METR이 지적한 간극을 그대로 통과시킨다.

바뀐 설계에서는 에이전트가 같은 작업을 k회(통상 3~5회) 반복 실행하고, 각 결과에 테스트와 필요하면 별도 리뷰 에이전트의 채점을 적용한 뒤 reliability@k를 산출한다. 이 값을 작업 유형별로 미리 정해둔 임계값과 비교해, 기준을 넘으면 자동 머지 경로로, 못 미치면 사람 리뷰로 에스컬레이션한다. 결제·인증·마이그레이션처럼 되돌리기 비용이 큰 작업일수록 임계값을 높이고, 포맷팅이나 사소한 리팩터링처럼 리버트 비용이 낮은 작업은 기존처럼 가볍게 흘려보내는 식으로 작업 종류와 게이트 강도를 분리하는 것이 핵심이다.

## 선택의 트레이드오프

| 게이트 방식 | 측정하는 것 | 비용 | 적합한 상황 |
|---|---|---|---|
| pass@1 (단일 CI 실행) | 한 번이라도 통과했는가 | 가장 낮음(1회 실행) | 리버트 비용이 낮고 되돌리기 쉬운 변경 |
| pass@k (k회 중 1회 성공) | 역량 상한 — 에이전트가 할 수는 있는가 | 중간(k회 실행, 결과 1개만 채택) | 모델·프롬프트 비교, 벤치마크 리포트 |
| reliability@k / pass^k (k회 전부 성공) | 신뢰 바닥 — 매번 보장되는가 | 높음(k회 실행 + 채점 전부 통과 확인) | 자동 머지·배포처럼 되돌리기 비용이 큰 결정 |
| 사람 리뷰 100% 유지 | 통계적 측정 자체를 생략 | 리뷰어 시간이 병목 | 팀 규모가 작거나 아직 신뢰 기준선이 없을 때 |

reliability@k는 공짜가 아니다. k를 3~5로만 잡아도 실행 비용과 CI 시간이 그만큼 늘어난다. 그래서 모든 PR에 똑같이 적용하기보다, 되돌리기 어려운 변경에만 선택적으로 거는 것이 현실적이다. 또한 pass^k는 "집계된" 지표라 과제별 편차를 가린다는 한계도 있다. 작업 A는 항상 성공하고 작업 B는 항상 실패해도, 평균을 내면 중간값처럼 보일 수 있다. 과제 단위로 분해해서 보는 것까지가 설계의 일부다.

## 실제 프로젝트 진행 순서

1. **현재 머지 게이트가 실제로 무엇을 측정하는지부터 점검한다.** 대부분은 암묵적으로 pass@1이다. 이 사실을 팀에 명시적으로 알리는 것부터 시작이다.
2. **작업을 되돌리기 비용 기준으로 분류한다.** 결제·인증·스키마 마이그레이션처럼 리버트가 비싼 작업과, 포맷팅·문서 수정처럼 싼 작업을 나눈다.
3. **비싼 작업군에만 k=3 수준의 반복 샘플링을 먼저 시범 적용한다.** 전체 파이프라인에 한꺼번에 걸지 않는다. CI 시간과 비용 증가분을 먼저 측정한다.
4. **reliability@k 임계값을 보수적으로 잡고, 실제 리버트율 데이터를 쌓으며 조정한다.** 처음부터 완벽한 숫자를 정하려 하지 말고, 실패 사례를 기준으로 임계값을 올리거나 내린다.
5. **과제별 분산을 모니터링한다.** 평균 reliability@k가 괜찮아 보여도 특정 작업 유형에서 계속 실패한다면, 그 유형은 아예 자동 머지 대상에서 빼는 것이 낫다.

## 코드 예제: reliability@k 계산

```python
from itertools import combinations

def reliability_at_k(results: list[bool], k: int) -> float:
    """같은 작업을 n회 실행한 결과(results)에서 k회 전부 성공할 확률(pass^k) 추정."""
    n = len(results)
    successes = sum(results)
    if n < k:
        raise ValueError("실행 횟수가 k보다 적습니다")
    from math import comb
    return comb(successes, k) / comb(n, k) if successes >= k else 0.0

# 같은 작업을 5회 실행해 3회 성공한 경우
runs = [True, True, False, True, False]
print(reliability_at_k(runs, k=3))  # k=3 전부 성공할 확률 추정치
```

## 마무리 요약

- pass@k는 "할 수 있는가"(역량 상한), reliability@k(pass^k)는 "항상 하는가"(신뢰 바닥)를 재는 다른 지표다.
- 테스트 통과율 하나만 보고 자동 머지를 설계하면 METR 연구가 보여준 간극(통과해도 절반은 머지 부적격)을 그대로 통과시킨다.
- 되돌리기 비용이 큰 작업에만 선택적으로 k회 반복 샘플링과 임계값 기반 에스컬레이션을 걸고, 과제별 분산까지 모니터링하는 것이 현실적인 설계다.
