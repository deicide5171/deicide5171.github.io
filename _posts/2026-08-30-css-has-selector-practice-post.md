CSS는 오랫동안 "부모를 고를 수 없는" 언어였다. `.card`가 `.card-error`를 자식으로 가질 때 `.card` 자체의 테두리 색을 바꾸고 싶어도, CSS 선택자는 항상 자손·형제 방향으로만 뻗어나갈 수 있었고 위쪽(부모) 방향으로는 갈 수 없었다. 그래서 이런 요구가 생길 때마다 `MutationObserver`나 이벤트 리스너로 자바스크립트가 부모에 클래스를 붙이는 우회로를 써야 했다. `:has()` 의사 클래스가 주요 브라우저에 전부 안착하면서 이 제약이 사라졌다 — 흔히 "부모 선택자(parent selector)"라고 불리지만 실제로는 그보다 훨씬 일반적인, 조건부 매칭 도구다.

이 글은 `:has()`가 정확히 무엇을 할 수 있는지, 그리고 실무에서 자주 쓰이는 패턴 — 폼 검증 상태 표시, 조건부 레이아웃, 콘텐츠 유무에 따른 스타일 분기 — 을 정리한다. 아울러 성능 특성과 남용했을 때의 함정도 함께 짚는다.

## 핵심 개념 1: :has()는 "포함하면"이 아니라 "관계가 성립하면"이다

`:has()`의 본질은 "이 요소를 기준으로, 괄호 안 선택자가 매칭되는 무언가가 이 요소와 특정 관계에 있으면 선택한다"는 관계 조건자다. 괄호 안에는 자손 결합자뿐 아니라 형제 결합자(`~`, `+`)도 쓸 수 있어서, "부모 선택자"라는 별명이 오히려 이 기능의 절반만 설명한다.

```css
/* 1) 자손 관계: 에러 메시지를 포함한 폼 그룹만 강조 */
.form-group:has(.error-message) {
  border-left: 3px solid #d0413b;
}

/* 2) 형제 관계: 체크된 체크박스 바로 다음에 오는 라벨 강조 */
.option:has(input:checked) + .option-label {
  font-weight: bold;
}

/* 3) 자기 자신 상태 결합: 포커스된 입력을 담은 필드셋 강조 */
fieldset:has(:focus-visible) {
  outline: 2px solid #2e9e63;
}
```

세 번째 예시가 특히 강력하다 — `:has(:focus-visible)`처럼 다른 의사 클래스와 조합하면, 자바스크립트 없이 "이 컨테이너 안 어딘가에 포커스가 있다"는 상태 자체를 CSS가 직접 판정할 수 있다.

## 핵심 개념 2: 실전 패턴 — JS 없이 되던 것과 안 되던 것

`:has()` 이전에도 순수 CSS로 형제 요소를 스타일링하는 트릭(체크박스 해킹)은 있었지만 항상 "뒤에 오는 형제"로만 가능했고, 부모나 앞쪽 형제를 건드리려면 JS가 필요했다. `:has()`는 이 방향 제약을 없앴다.

| 요구사항 | :has() 이전 | :has()로 |
|---|---|---|
| 자식에 이미지가 있는 카드만 다른 레이아웃 | JS로 클래스 토글 | `.card:has(img) { ... }` |
| 체크된 라디오의 앞쪽 형제 강조 | 불가능(형제 결합자는 뒤로만) | `:has(~ input:checked)` |
| 빈 셀렉트박스에 placeholder 스타일 | JS로 값 감지 | `select:has(option:checked[value=""])` |
| 폼 전체에 미입력 필수 필드 존재 여부 표시 | JS 유효성 검사 후 클래스 부여 | `form:has(:required:invalid)` |
| 다크모드 등 조상 속성과 무관하게 조건부 카드 개수 스타일 | JS로 개수 세기 | `.grid:has(> .item:nth-child(5))` |

특히 폼 유효성 검사 표시는 `:has()`가 가장 빛을 발하는 영역이다. `:invalid`, `:required`, `:out-of-range` 같은 상태 의사 클래스와 결합하면, 자바스크립트 유효성 검사 라이브러리 없이도 "필수 항목 중 하나라도 비어 있으면 제출 버튼 영역에 경고 테두리"까지 순수 CSS로 표현할 수 있다.

## 핵심 개념 3: 성능 특성과 남용 주의

`:has()`는 편리하지만 공짜가 아니다. 브라우저는 `:has()`가 포함된 규칙을 만나면, 그 선택자가 매칭되는지 확인하기 위해 대상 요소의 하위 트리(또는 형제)를 탐색해야 한다. 즉 일반적인 자손 선택자보다 계산 비용이 높고, 특히 **DOM이 변경될 때마다 재평가 범위가 넓어질 수 있다** — `:has()`가 걸린 조상 요소는 그 하위 어딘가의 DOM 변경에도 스타일을 다시 계산해야 할 수 있기 때문이다.

브라우저 엔진들은 이를 위해 "이 하위 트리에 :has() 매칭에 영향을 줄 수 있는 변경이 있었는가"를 추적하는 최적화를 구현해 두었지만, 그래도 대규모 리스트(수천 개 항목)의 각 항목에 `:has()`를 거는 패턴은 스타일 재계산 비용이 눈에 띄게 늘어날 수 있다. 실무에서는 `:has()`를 목록의 각 아이템 단위가 아니라, 명확히 경계가 좁은 컨테이너(폼, 카드, 위젯 단위)에 한정해서 쓰는 것이 안전하다.

## 예제: 이미지 유무에 따른 카드 레이아웃 분기

```css
/* 이미지가 있는 카드는 그리드, 없는 카드는 텍스트 전용 레이아웃 */
.card {
  display: flex;
  flex-direction: column;
  padding: 16px;
}

.card:has(img) {
  display: grid;
  grid-template-columns: 120px 1fr;
  gap: 12px;
}

/* 첨부파일이 있는 댓글만 여백 확장 */
.comment:has(.attachment) {
  padding-bottom: 20px;
}

/* 자식 입력이 비어있지 않은 검색창에만 지우기 버튼 표시 */
.search-box:has(input:not(:placeholder-shown)) .clear-button {
  display: inline-flex;
}
```

## 실무 포인트

- **폴백을 완전히 생략하지는 말 것.** 최신 브라우저는 대부분 `:has()`를 지원하지만, 오래된 브라우저 지원이 필요한 프로젝트라면 `@supports selector(:has(a))`로 지원 여부를 감지해 JS 폴백(클래스 토글)을 조건부로 로드하는 편이 안전하다.
- **선택자 범위를 좁게 유지하라.** `:has()` 자체를 금지할 필요는 없지만, 페이지 전체에 걸리는 넓은 선택자(`body:has(.modal-open) *`)보다는 영향 범위가 국소적인 컨테이너 단위 선택자가 재계산 비용과 디버깅 난이도 양쪽에서 유리하다.
- **`:has()`로 상태를 "읽을" 수는 있어도 상태를 "만들" 수는 없다.** 즉 여전히 상태 변경 자체(체크박스 체크, 입력값 변경)는 사용자 상호작용이나 JS로 일어나야 하고, `:has()`는 그 상태가 이미 DOM에 반영된 뒤 그것을 조건으로 스타일을 분기하는 역할만 한다. 상태 자체를 만드는 로직과 상태를 반영하는 스타일링을 혼동하지 않아야 설계가 깔끔해진다.

## 3줄 요약

- `:has()`는 "부모 선택자"로 불리지만 실제로는 자손·형제·자기 자신의 상태를 조건으로 삼는 일반적인 관계 조건자이며, 이전엔 JS가 필요했던 조건부 스타일링 상당수를 순수 CSS로 대체한다.
- 폼 유효성 상태 표시, 콘텐츠 유무에 따른 레이아웃 분기, 포커스 상태 감지 같은 패턴에서 특히 강력하지만, 대규모 리스트 각 항목에 걸면 스타일 재계산 비용이 늘 수 있어 컨테이너 단위로 범위를 좁혀 쓰는 것이 안전하다.
- 오래된 브라우저 지원이 필요하면 `@supports selector(:has(a))`로 폴백 경로를 마련해야 하며, `:has()`는 상태를 읽을 뿐 만들지는 않는다는 점을 설계에 반영해야 한다.
