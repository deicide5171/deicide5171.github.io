## 도입

"침수 시뮬레이션은 지도에서 재생이 되는데, 대피 시뮬레이션도 똑같이 지도에서 보여줄 수 있나요?" 재난안전 담당 부서에서 흔히 받는 요구다. 침수나 가시권 연산은 이미 다뤘지만, 대피는 결이 다르다. 침수는 물리 현상이 지형을 따라 퍼지는 문제이고, 대피는 **사람들이 선택하고 서로 영향을 주며 도로망 위를 이동하는 문제**다. "지도에서 재생해서 보여주세요"라는 한 문장 안에는 사실 두 개의 분리된 기술 문제가 들어 있다. 대피 시간과 경로를 계산하는 연산 엔진을 어떻게 설계할 것인가, 그리고 그 결과를 시간축을 따라 지도 위에서 어떻게 재생할 것인가다.

2026년 공개된 디지털 트윈 연구들은 이 연산 엔진의 선택지를 구체적으로 보여준다. 고베시는 CrowdWalk 에이전트 기반 시뮬레이터에 OpenStreetMap 도로망과 휴대폰 인구 통계를 결합해, 신호 통제를 바꿨을 때 대피 시간이 기존의 37%까지 줄어드는 것을 확인했다. 중국 뤄창현 연구는 GIS 최단경로 분석 기반 에이전트 모델로 정보 전파 순서(무질서 대피 vs 질서 있는 대피)에 따른 소요 시간 차이를 비교했다. 니코시아 구시가지는 Unity 기반 하이브리드 에이전트 모델로 도로 폐쇄·대피소 변경 시나리오를 검증했다. 이 글은 이 사례들을 기준으로 대피 시뮬레이션의 연산 방식을 어떻게 고를지 정리한다.

## 전체 시스템에서의 위치

대피 시뮬레이션은 입력 데이터부터 지도 재생까지 네 단계를 거친다. 도로망·건물·인구 데이터가 연산 엔진에 들어가고, 연산 엔진이 만든 결과(경로별 소요 시간, 혼잡 구간, 전체 대피 완료 시간)가 시계열 포맷으로 저장된 뒤, 웹 지도의 시간축 재생 레이어가 이를 애니메이션으로 보여준다.

<img src="/assets/images/posts/2026-10-27-evacuation-simulation-agent-based-vs-graph-based-1.svg" alt="도로망·인구 데이터가 그래프 기반 또는 에이전트 기반 연산 엔진을 거쳐 시계열 결과로 저장되고, 웹 지도의 시간축 재생 레이어가 이를 애니메이션으로 보여주는 전체 데이터 흐름도" style="width:100%;">

- **입력 데이터**: OpenStreetMap이나 자체 GIS 도로망 그래프, 건물·인구 밀도 데이터, 통제 지점(도로 폐쇄, 신호 변경)과 대피소 위치.
- **연산 엔진**: 그래프 기반 모델(최단경로 + 용량 제약)이거나 에이전트 기반 모델(개별 보행자·차량이 규칙에 따라 움직임). 여기가 이 글의 핵심 선택지다.
- **시계열 결과**: 이전 침수 시뮬레이션 글에서 다룬 것과 같은 시간축 포맷으로 저장하면, 재생 레이어를 그대로 재사용할 수 있다.
- **재생 레이어**: 지도 위에서 시간을 슬라이더로 넘기며 혼잡 구간과 경로 변화를 보여주는 부분으로, 연산 엔진과는 독립적으로 설계할 수 있다.

## 선택의 트레이드오프

| 기준 | 그래프 기반(최단경로+용량) | 에이전트 기반(개별 보행자) |
|---|---|---|
| 연산 비용 | 가볍다 — 그래프 알고리즘 수준 | 무겁다 — 개체 수 × 시간 스텝만큼 반복 연산 |
| 행동 현실성 | 병목·혼잡으로 인한 속도 저하 반영 어려움 | 개인별 속도·망설임·군중 밀집 반영 가능 |
| 필요 데이터 | 도로망 그래프 + 용량 추정치 | 도로망 + 개체별 행동 규칙 + 보정용 실측 데이터 |
| 적합한 상황 | 정책 비교의 1차 스크리닝, 빠른 반복 검토 | 세부 혼잡 지점 식별, 정밀한 정책 평가 |
| 어디서 돌리는가 | 서버 배치로 수 초~수 분 내 완료 | 서버 배치 전용, 보통 수 분~수십 분 |

뤄창현 연구처럼 "정보 전파 순서를 바꾸면 얼마나 빨라지는가"를 비교하는 수준이라면 그래프 기반 최단경로 모델로도 충분하다. 반면 고베시나 니코시아 사례처럼 "이 교차로에서 사람들이 왜 몰리는가"를 봐야 한다면 에이전트 기반 모델이 필요하다. 2026년 리뷰 논문들이 공통으로 지적하는 지점은 **행동 현실성 검증과 실시간 데이터 통합의 부재**다 — 에이전트 모델을 쓰더라도 실제 훈련 데이터나 통제군과 대조하지 않으면 숫자만 그럴듯한 시뮬레이션이 된다.

## 실제 프로젝트 진행 순서

1. **목적부터 확정한다.** 정책 비교용 1차 스크리닝인지, 실제 대피 계획 수립에 쓸 정밀 검증인지에 따라 그래프 기반으로 시작할지 바로 에이전트 기반으로 갈지가 갈린다.
2. **도로망 그래프 소스를 정한다.** OpenStreetMap은 빠르게 시작할 수 있지만 통제 지점·대피소 정보가 없으므로 자체 GIS 데이터로 보강해야 한다.
3. **그래프 기반 베이스라인부터 구축한다.** 최단경로 + 구간별 용량 제약만으로 전체 대피 완료 시간의 대략적인 추정치를 먼저 뽑는다.
4. **필요한 구간만 에이전트 기반으로 확장한다.** 베이스라인에서 병목으로 의심되는 구간만 개체 단위 시뮬레이션으로 정밀화하면, 전체를 에이전트 기반으로 돌리는 것보다 연산 비용을 크게 줄일 수 있다.
5. **결과를 시간축 포맷으로 저장해 기존 재생 레이어에 연결한다.** 침수 시뮬레이션에서 쓴 시계열 재생 구조를 그대로 재사용하면 프론트엔드를 새로 만들 필요가 없다.
6. **실측 데이터로 검증한다.** 실제 대피 훈련 기록이나 휴대폰 이동 데이터와 대조해, 시뮬레이션이 그럴듯한 숫자만 내는 것이 아닌지 확인한다.

```python
# 그래프 기반 베이스라인: 도로망을 용량 제약이 있는 그래프로 모델링
import networkx as nx

G = nx.DiGraph()
G.add_edge("A", "B", capacity=50, travel_time=4)   # 분당 통과 가능 인원, 소요 시간(분)
G.add_edge("B", "shelter", capacity=30, travel_time=6)

# 최단 경로 기반 1차 추정 — 용량을 고려하지 않은 베이스라인
path = nx.shortest_path(G, "A", "shelter", weight="travel_time")
total_time = nx.path_weight(G, path, weight="travel_time")
# 이후 구간별 인원 수 / capacity로 병목 구간을 찾아 에이전트 기반 정밀화 대상 선정
```

## 실무 포인트

- "지도에서 재생해서 보여주세요"라는 요구를 받으면 먼저 연산과 시각화를 분리해서 되묻는 것이 중요하다. 시각화는 기존 시계열 재생 레이어를 재사용할 수 있지만, 연산 방식은 목적에 따라 완전히 새로 설계해야 한다.
- 에이전트 기반 모델을 전체 지역에 적용하면 연산 시간이 급격히 늘어난다. 그래프 기반으로 먼저 병목 구간을 좁히고, 그 구간에만 에이전트 기반을 적용하는 단계적 접근이 현실적이다.
- 2026년 리뷰에서 반복적으로 지적되는 것처럼, 실시간 데이터(통제 상황, 실제 보행 속도)를 반영하지 못하면 아무리 정교한 모델도 정책 결정에 쓰기 어렵다. 검증 없이 결과만 지도에 올리는 것은 피해야 한다.

## 마무리

- "대피 시뮬레이션을 지도에서 보여주세요"는 연산 엔진 선택(그래프 기반 vs 에이전트 기반)과 시간축 재생이라는 두 문제로 나뉜다.
- 판단 기준은 정책 비교용 스크리닝인지 정밀 검증인지이며, 그래프 기반 베이스라인에서 병목만 에이전트 기반으로 확장하는 단계적 접근이 연산 비용을 줄인다.
- 실측 데이터로 검증하지 않은 시뮬레이션은 숫자만 그럴듯한 결과가 될 수 있다는 점을 항상 전제로 둬야 한다.
