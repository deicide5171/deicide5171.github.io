## 왜 이 결정을 가볍게 넘기면 안 되나

사용자가 "계정을 삭제해주세요"라고 요청했을 때, 정말로 `DELETE FROM users WHERE id = ?`를 실행해도 될까? 실무에서는 대부분 그렇게 하지 않는다. 삭제된 사용자가 작성한 게시글, 결제 내역, 참조 관계가 남아 있는 상태에서 원본 행이 사라지면 외래키 무결성이 깨지거나, "탈퇴한 사용자"라는 표시조차 할 수 없게 된다. 그래서 많은 서비스가 실제 삭제 대신 `deleted_at` 같은 컬럼을 두고 값을 채우는 것으로 "삭제"를 표현한다. 이것이 **Soft Delete(소프트 삭제)** 패턴이다.

문제는 이 패턴이 "그냥 컬럼 하나 추가하면 되는" 간단한 결정처럼 보이지만, 실제로는 조회 로직, 인덱스 설계, 유니크 제약, 심지어 법적 요구사항(개인정보 완전 삭제 의무)까지 건드리는 결정이라는 점이다.

## Soft Delete vs Hard Delete 비교

| 항목 | Soft Delete | Hard Delete |
|---|---|---|
| 복구 가능성 | 가능(플래그만 되돌리면 됨) | 불가능(백업 없이는 영구 손실) |
| 참조 무결성 | 유지됨(연관 데이터가 그대로 남음) | 깨질 위험(CASCADE 설정 필요) |
| 조회 쿼리 | 모든 SELECT에 조건 추가 필요 | 조건 불필요 |
| 저장 공간 | 계속 누적됨 | 즉시 회수됨 |
| 개인정보 완전 삭제 | 별도 조치 필요(GDPR 등) | 기본적으로 충족 |

## 잘못된 접근: 생각 없이 모든 테이블에 적용

흔한 실수는 "삭제는 위험하니 모든 테이블에 Soft Delete를 적용하자"는 일괄 방침이다. 이렇게 하면 몇 가지 문제가 누적된다.

첫째, **모든 조회 쿼리에 `WHERE deleted_at IS NULL` 조건을 빠뜨리면 삭제된 데이터가 그대로 노출된다.** 개발자가 신규 기능을 추가할 때마다 이 조건을 기억해야 하는데, ORM을 쓰지 않고 원시 SQL을 섞어 쓰는 프로젝트에서는 누락 사고가 반복해서 난다.

둘째, **유니크 제약이 깨진다.** 이메일에 유니크 제약을 걸어둔 테이블에서 사용자를 소프트 삭제한 뒤 같은 이메일로 재가입하려 하면, 삭제된 행이 여전히 유니크 인덱스를 점유하고 있어 제약 위반 에러가 난다.

셋째, **개인정보 관련 규제 대상 데이터를 소프트 삭제만 해두면 법적 요구를 충족하지 못한다.** "삭제 요청"이 들어왔는데 실제로는 DB에 값이 그대로 남아 있으면, 접근 권한이 있는 누구나 조회할 수 있는 상태가 된다.

## 올바른 접근

```sql
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMP NULL;

-- 유니크 제약을 부분 인덱스로 재설계 (PostgreSQL)
CREATE UNIQUE INDEX users_email_active_uidx
  ON users (email)
  WHERE deleted_at IS NULL;
```

부분 인덱스(partial index)를 쓰면 "삭제되지 않은 행에서만" 유니크를 보장하므로, 삭제된 이메일로 재가입하는 시나리오가 정상 동작한다. MySQL처럼 부분 인덱스를 지원하지 않는 DBMS라면, `email`과 `deleted_at`을 합친 복합 유니크 키를 쓰거나 삭제 시 이메일에 타임스탬프를 덧붙여 값 자체를 바꾸는 우회 전략을 쓴다.

조회 로직은 ORM의 글로벌 스코프(예: JPA `@Where`, Hibernate 필터)나 뷰(View)로 감싸서 "삭제되지 않은 행만 보이는" 기본 인터페이스를 강제하는 것이 안전하다. 개발자가 조건을 매번 기억하게 만드는 대신, 실수해도 안전한 기본값을 시스템이 제공해야 한다.

## 실무 포인트

- **모든 테이블에 일괄 적용하지 말고 테이블별로 판단하라.** 감사·복구가 중요한 테이블(주문, 결제)은 Soft Delete, 임시성이 강한 테이블(세션, 캐시성 데이터)은 Hard Delete가 더 적합하다.
- **오래된 소프트 삭제 데이터는 배치로 완전 삭제(하드 삭제)하는 정책을 함께 설계하라.** 그렇지 않으면 테이블이 무한정 커져 인덱스 스캔·백업 시간이 계속 늘어난다.
- **개인정보는 소프트 삭제와 별개로 익명화/파기 프로세스를 둬라.** "논리적으로 삭제됨" 표시와 "실제 개인정보가 남아있음"은 법적으로 다른 문제다.
- **삭제된 행이 섞인 대용량 테이블은 파티셔닝을 검토하라.** `deleted_at`이 오래된 행을 별도 파티션으로 분리하면 활성 데이터 조회 성능을 지킬 수 있다.

## 마무리 요약

- Soft Delete는 복구 가능성과 참조 무결성을 지켜주지만, 모든 조회에 조건을 강제해야 하고 유니크 제약을 부분 인덱스로 재설계해야 한다.
- 무조건 모든 테이블에 적용하기보다, 테이블 성격(감사 필요성, 개인정보 여부)에 따라 Soft/Hard를 구분해서 결정한다.
- 소프트 삭제 데이터도 결국 배치로 정리하거나 파티셔닝하는 후속 정책이 필요하다.
