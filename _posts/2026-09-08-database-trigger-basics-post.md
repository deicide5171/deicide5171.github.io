## 데이터가 바뀔 때 자동으로 뭔가 하고 싶다면

"주문이 생성되면 자동으로 재고를 줄인다", "데이터가 수정되면 변경 이력을 남긴다" 같은 작업을 애플리케이션 코드가 아니라 DB가 알아서 하게 할 수 있다. **트리거(Trigger)**는 특정 테이블에 INSERT·UPDATE·DELETE가 발생할 때 자동으로 실행되도록 미리 등록해둔 동작이다.

## 트리거의 구성 요소

| 요소 | 설명 |
|---|---|
| 이벤트 | 언제 (INSERT / UPDATE / DELETE) |
| 시점 | 이벤트 전(BEFORE) / 후(AFTER) |
| 대상 | 어느 테이블에 |
| 동작 | 실행할 SQL·로직 |

## 예제: 변경 이력 남기기

```sql
-- users 테이블이 수정되면 이력 테이블에 자동 기록
CREATE TRIGGER log_user_update
AFTER UPDATE ON users
FOR EACH ROW
BEGIN
    INSERT INTO user_history (user_id, old_name, changed_at)
    VALUES (OLD.id, OLD.name, NOW());
END;
```

이 트리거를 걸어두면, 애플리케이션에서 이력 남기는 코드를 따로 짜지 않아도 `users`가 수정될 때마다 DB가 알아서 이력을 기록한다. `OLD`는 변경 전 값, `NEW`는 변경 후 값을 가리킨다.

## 트리거가 유용한 경우와 위험한 경우

```text
유용:
- 감사 로그(변경 이력) 자동 기록
- 데이터 무결성 강제(특정 조건 검증)
- 집계 값 자동 갱신

위험:
- 로직이 DB에 숨어 있어 "왜 이 데이터가 바뀌었지?" 추적이 어려움
- 트리거가 또 다른 트리거를 부르는 연쇄로 성능·디버깅 악화
- 애플리케이션 코드만 봐서는 동작을 알 수 없음
```

## 실무 포인트

- **트리거는 "숨은 로직"이 되기 쉽다.** 애플리케이션 코드 어디에도 없는데 데이터가 바뀌면, 신입 개발자가 원인을 못 찾고 헤맨다. 트리거를 쓴다면 문서화하고 팀이 그 존재를 알아야 한다.
- **복잡한 비즈니스 로직은 트리거보다 애플리케이션에 두는 것이 낫다.** 트리거에 로직이 많아지면 테스트·디버깅·버전 관리가 어렵다. 트리거는 단순하고 DB에 밀접한 작업(이력, 무결성)에 한정하는 것이 좋다.
- **트리거의 실패가 원래 작업을 막을 수 있다.** BEFORE 트리거나 같은 트랜잭션 내 트리거가 실패하면 원래의 INSERT·UPDATE도 롤백될 수 있다. 트리거 안의 로직이 원래 작업의 성패에 영향을 준다는 점을 알아야 한다.

## 마무리 요약

- 트리거는 특정 테이블에 데이터 변경이 일어날 때 자동 실행되는 DB 동작이다.
- 변경 이력 기록·무결성 강제 같은 DB 밀접 작업에 유용하다.
- 다만 로직이 코드 밖에 숨어 추적이 어려워지므로, 복잡한 비즈니스 로직은 애플리케이션에 두는 것이 좋다.
