LLM을 쓰는 서비스가 하나의 프로바이더에만 의존하는 시대는 사실상 끝났다. 특정 프로바이더의 API 장애나 레이트 리밋(429)이 곧 우리 서비스의 장애가 되는 구조는 받아들이기 어렵고, 모델 가격과 성능의 판도가 몇 달 단위로 바뀌는 상황에서 코드 곳곳에 특정 SDK 호출이 박혀 있으면 모델 교체 한 번이 대규모 리팩토링이 된다. 여기에 팀마다 API 키를 따로 발급받아 쓰다 보면 "이번 달 LLM 비용이 왜 이렇게 나왔는지" 아무도 설명하지 못하는 상태가 된다.

이 문제들을 한 계층에서 해결하는 것이 **LLM 게이트웨이**다. LiteLLM, Portkey, OpenRouter 같은 도구들이 이 범주에 속하며, 핵심 아이디어는 단순하다. 애플리케이션과 프로바이더 사이에 프록시 계층을 하나 두고, 라우팅·폴백·키 관리·비용 집계를 전부 그 계층으로 밀어 넣는 것이다. 애플리케이션 코드는 게이트웨이가 제공하는 통합 인터페이스 하나만 바라보면 된다.

이 글에서는 LLM 게이트웨이가 담당하는 네 가지 책임과 설계 시 판단 기준, 그리고 실무에서 자주 빠지는 함정을 정리한다.

## 게이트웨이의 네 가지 책임

| 책임 | 하는 일 | 없으면 생기는 문제 |
|---|---|---|
| 통합 인터페이스·라우팅 | 모델 별칭(alias) 하나를 여러 프로바이더 배포(deployment)에 매핑 | 모델 교체 = 전체 코드 수정 |
| 폴백·재시도 | 429/5xx 발생 시 다른 배포로 자동 전환, 실패 배포는 쿨다운 | 프로바이더 장애 = 서비스 장애 |
| 키 관리 | 실제 프로바이더 키는 게이트웨이만 보유, 앱에는 가상 키 발급 | 키 유출 시 전체 회수, 권한 분리 불가 |
| 비용 통제 | 가상 키·팀 단위 예산 상한, 레이트 리밋, 사용량 로깅 | 비용 폭주를 월말 청구서로 발견 |

이 중 어느 하나만 필요해도 게이트웨이 도입을 검토할 가치가 있지만, 실제 효과는 네 가지가 결합될 때 나온다. 예컨대 폴백이 동작하려면 라우팅 테이블이 있어야 하고, 팀별 예산 통제가 의미 있으려면 모든 트래픽이 게이트웨이를 지나야 한다.

## 라우팅과 폴백 — 전략과 함께 '전환 기준'을 설계한다

라우팅 전략은 크게 세 가지다. **우선순위 기반**(기본 배포를 두고 실패 시에만 폴백), **가중치 기반**(비용이나 쿼터에 따라 트래픽을 비율로 분산), **지연시간/사용량 기반**(응답이 빠르거나 여유 있는 배포를 동적으로 선택). 대부분의 서비스는 우선순위 기반으로 시작하는 것이 예측 가능성 면에서 낫고, 트래픽이 커져 단일 프로바이더의 레이트 리밋에 자주 걸릴 때 가중치·사용량 기반으로 넘어가는 편이 자연스럽다.

폴백에서 정작 중요한 것은 "어디로 넘길 것인가"보다 "무엇을 실패로 볼 것인가"다. 429와 5xx, 타임아웃은 폴백 대상이지만, 400(잘못된 요청)은 어느 프로바이더로 보내도 실패하므로 폴백하면 안 된다. 콘텐츠 정책에 의한 거부도 마찬가지로 구분이 필요하다. 그리고 실패한 배포는 일정 시간 라우팅에서 제외하는 **쿨다운**을 걸어야 한다. 쿨다운 없이 매 요청마다 죽은 배포를 다시 두드리면, 폴백이 오히려 지연시간을 늘리는 원인이 된다. 서킷 브레이커와 같은 원리다.

재시도 횟수 설계도 신중해야 한다. 애플리케이션 SDK가 2회, 게이트웨이가 2회, 폴백 배포가 다시 2회 재시도하는 식으로 계층마다 재시도가 중첩되면, 프로바이더 장애 순간 실제 요청량이 몇 배로 증폭되는 **재시도 폭풍**이 발생한다. 재시도의 책임은 게이트웨이 한 곳으로 모으고, 애플리케이션 쪽 재시도는 끄거나 최소화하는 것이 안전하다.

## 키 관리와 비용 통제 — 가상 키가 핵심이다

게이트웨이의 키 관리는 단순한 비밀 보관이 아니라 **간접화 계층**이다. 실제 프로바이더 키는 게이트웨이 서버에만 존재하고, 각 팀·서비스에는 게이트웨이가 발급한 가상 키(virtual key)를 준다. 가상 키에는 접근 가능한 모델 목록, 월 예산 상한, 분당 요청/토큰 한도(RPM/TPM), 만료일을 붙일 수 있다. 이렇게 하면 프로바이더 키 로테이션이 게이트웨이 설정 변경 한 번으로 끝나고, 특정 팀의 프롬프트 실험이 폭주해도 그 팀의 예산에서 차단된다.

비용 집계도 이 지점에서 자연스럽게 해결된다. 모든 요청이 게이트웨이를 지나므로 "어느 키가, 어느 모델로, 몇 토큰을 썼는지"가 한 곳에 쌓이고, 이를 팀·기능 단위 태그로 묶으면 LLM 비용의 원가 배분이 가능해진다. 같은 자리에서 요청·응답 로깅과 지연시간 메트릭을 관측 도구로 내보내면, 프롬프트 품질 분석과 장애 진단까지 한 계층에서 해결된다. 예산 상한을 걸 때는 하드 컷오프(초과 시 즉시 차단)와 알림만 보내는 소프트 리밋 중 무엇이 맞는지 워크로드별로 정해야 한다. 사용자 대면 기능을 예산 초과로 갑자기 차단하면 비용 사고가 서비스 사고로 바뀐다.

## 예제 — LiteLLM 프록시 설정과 클라이언트 호출

아래는 LiteLLM 프록시의 설정 예시다. `chat-default`라는 별칭 하나에 두 프로바이더 배포를 묶고, 폴백과 쿨다운, 예산 통제를 선언한다.

```yaml
# litellm config.yaml
model_list:
  - model_name: chat-default            # 앱이 호출하는 별칭
    litellm_params:
      model: anthropic/claude-sonnet-4-6
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: chat-default            # 같은 별칭의 두 번째 배포
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY

router_settings:
  routing_strategy: simple-shuffle      # 배포 간 분산
  num_retries: 2
  cooldown_time: 60                     # 실패 배포 60초 제외
  fallbacks:
    - chat-default: ["chat-cheap"]      # 별칭 단위 폴백 체인

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY  # 가상 키 발급용
```

애플리케이션은 OpenAI 호환 인터페이스로 게이트웨이만 호출한다. 프로바이더가 바뀌어도 이 코드는 그대로다.

```python
import openai

client = openai.OpenAI(
    base_url="https://llm-gateway.internal.example.com",
    api_key="sk-team-a-virtual-key",   # 게이트웨이가 발급한 가상 키
)

resp = client.chat.completions.create(
    model="chat-default",              # 별칭만 지정
    messages=[{"role": "user", "content": "이 문서를 세 줄로 요약해줘"}],
)
print(resp.choices[0].message.content)
```

## 언제 쓰고, 언제 쓰지 말아야 하나

**도입이 맞는 경우**: 두 개 이상의 프로바이더나 모델을 운영 중이거나 곧 그렇게 될 때, 여러 팀이 LLM을 공유하며 비용 배분이 필요할 때, 프로바이더 장애에 대한 가용성 요구가 있을 때다.

**과한 경우**: 단일 프로바이더, 단일 서비스, 낮은 트래픽이라면 게이트웨이는 운영해야 할 인프라만 하나 늘린다. 이 단계에서는 SDK의 자체 재시도와 환경변수 키 관리로 충분하고, 코드에서 모델 이름을 설정값으로 빼두는 것만으로 향후 이전 비용을 낮출 수 있다. 게이트웨이 자체가 **단일 장애점(SPOF)** 이 된다는 점도 잊으면 안 된다. 도입한다면 게이트웨이는 무상태에 가깝게 유지하고 다중 인스턴스로 띄우는 것이 전제다.

**흔한 함정 — "폴백은 공짜 교체"라는 착각.** 폴백 모델은 같은 API 형태를 흉내 낼 뿐 같은 모델이 아니다. 첫째, 프롬프트 캐시는 프로바이더·모델 단위이므로 폴백 순간 캐시 적중이 사라져 비용과 지연이 튄다. 둘째, 툴 호출 스키마의 엄격함, 구조화 출력 지원, 컨텍스트 길이 같은 기능 차이 때문에 주 모델에서 멀쩡하던 요청이 폴백 모델에서 400으로 죽을 수 있다. 올바른 대안은 폴백 체인에 넣을 모델을 **기능 호환성 기준으로 미리 검증**하고, 폴백 경로도 평상시에 소량의 트래픽(카나리)으로 상시 검증하는 것이다. 장애 날 때 처음 밟아보는 폴백 경로는 폴백이 아니라 두 번째 장애다.

## 3줄 요약

- LLM 게이트웨이는 라우팅·폴백·키 관리·비용 통제를 애플리케이션 밖의 한 계층으로 모아, 프로바이더 장애와 모델 교체로부터 서비스 코드를 분리한다.
- 폴백 설계의 핵심은 전환 대상이 아니라 전환 기준이다 — 429/5xx만 폴백하고, 실패 배포는 쿨다운으로 제외하며, 폴백 경로는 평시에 검증해 둔다.
- 가상 키에 모델 접근 범위·예산·레이트 리밋을 붙이면 키 유출 대응과 팀별 비용 배분이 게이트웨이 설정 문제로 단순해진다. 단, 단일 프로바이더·저트래픽 단계에서는 도입을 미루는 것이 낫다.
