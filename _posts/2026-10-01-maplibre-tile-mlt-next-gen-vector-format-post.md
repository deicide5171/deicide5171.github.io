## 왜 지금 이 판단이 필요한가

"전국 단위로 건물·도로·POI를 다 보여주는 지도인데, 저사양 기기에서 로딩이 너무 느려요." 이 요구사항을 받으면 지금까지 빌더가 쥔 카드는 정해져 있었다. 타일을 더 잘게 쪼개거나(zoom 레벨 세분화), 서버를 늘리거나, PMTiles 같은 정적 서빙으로 네트워크 홉을 줄이는 것. 타일 하나의 **포맷 자체**를 바꾸는 선택지는 10년 가까이 없었다. Mapbox Vector Tile(MVT)이 사실상 유일한 표준이었기 때문이다.

이 전제가 2026년에 깨졌다. MapLibre 재단이 MVT를 대체할 목적으로 설계한 차세대 포맷 **MapLibre Tile(MLT)**을 발표했고, 압축 후 타일 크기를 MVT 대비 최대 3배, 큰 타일에서는 6배 이상 줄이면서 디코딩 속도도 최대 3배 빠르다는 벤치마크를 공개했다. 빌더 입장에서 중요한 질문은 "압축률이 좋으니 당장 바꾼다"가 아니라 "이 포맷 전환이 지금 내 서비스의 병목을 실제로 풀어주는가, 그리고 생태계가 이걸 받아들일 준비가 됐는가"다.

## 요구사항을 기술 문제로 번역하기

"지도가 느리다"는 말은 실제로 세 가지 서로 다른 병목 중 하나다. 네트워크 전송량이 문제인가(타일 파일 크기), 클라이언트 CPU가 문제인가(파싱·디코딩 시간), 아니면 GPU 렌더링이 문제인가(피처 수, 스타일 표현식 복잡도). MLT가 직접 공략하는 지점은 앞의 두 가지다. MVT는 피처 하나하나의 속성을 행(row) 단위로 저장하는데, MLT는 같은 종류의 속성값을 모아 저장하는 **열(column) 지향 구조**로 바꿔 압축 알고리즘이 훨씬 효율적으로 동작하게 만든다. 여기에 SIMD 친화적인 경량 인코딩을 적용해 디코딩 자체도 빠르게 만들었다. 즉 "전송량과 파싱 시간이 병목"이라는 진단이 맞을 때만 MLT가 문제를 풀어준다. 렌더링(GPU) 단계가 병목이라면 포맷을 바꿔도 체감 개선은 제한적이다.

## 전체 시스템에서의 위치

벡터 타일 포맷은 지도 파이프라인의 한 구간일 뿐, 앞뒤로 연결된 단계들이 전환 가능 여부를 함께 결정한다.

<img src="/assets/images/posts/2026-10-01-maplibre-tile-mlt-next-gen-vector-format-1.svg" alt="원본 공간 데이터가 타일 생성 도구를 거쳐 MVT 또는 MLT 포맷으로 인코딩되고, CDN을 거쳐 클라이언트 렌더러가 디코딩해 화면에 그리는 파이프라인 비교도" style="width:100%;">

원본 데이터(PostGIS, GeoParquet, OSM 추출본)는 tippecanoe나 Planetiler 같은 타일 생성 도구를 거쳐 포맷으로 인코딩된 뒤 CDN이나 PMTiles로 서빙되고, 최종적으로 MapLibre GL JS 같은 클라이언트 렌더러가 디코딩해 GPU로 넘긴다. MLT로 전환한다는 것은 이 체인의 **인코딩 단계(타일 생성 도구)**와 **디코딩 단계(클라이언트 렌더러)** 양쪽이 모두 MLT를 지원해야 한다는 뜻이다. 서버만 MLT 타일을 만들어도 구버전 MapLibre나 Mapbox GL JS, 혹은 OpenLayers 같은 다른 렌더러는 이 타일을 읽지 못한다. 반대로 렌더러만 지원을 추가해도 타일 생성 파이프라인이 MLT 인코더를 갖추지 못하면 쓸 수 없다.

## 선택의 트레이드오프

| 기준 | MVT (기존) | MLT (신규) |
|---|---|---|
| 압축률 | 기준선 | 최대 3~6배 향상 |
| 디코딩 속도 | 기준선 | 최대 3배 향상 |
| 생태계 지원 | MapLibre·Mapbox·OpenLayers·QGIS·대부분 타일 서버 | MapLibre GL JS 최신 버전 중심, 서드파티 렌더러 지원 초기 단계 |
| 타일 생성 도구 | tippecanoe·Planetiler·pg_tileserv 전부 지원 | MLT 인코더 지원 도구 제한적, 변환 단계 추가 필요 |
| 데이터 타입 | 기본 스칼라 속성 위주 | 중첩 타입(리스트·구조체), 3D 좌표, m-좌표 직접 지원 |
| 적합한 경우 | 범용 서비스, 여러 렌더러·도구 혼용 환경 | 자체 렌더러 스택을 MapLibre 최신 버전으로 통일한 대용량 서비스 |

가장 큰 함정은 "압축률이 좋다는 벤치마크만 보고 전사 전환을 결정하는 것"이다. MLT는 MVT와 같은 내용을 담을 수 있도록 설계됐지만, 이는 "데이터 모델이 호환된다"는 뜻이지 "타일 파일 자체가 호환된다"는 뜻이 아니다. 사내에서 QGIS로 타일을 검수하거나, 일부 화면에 OpenLayers를 섞어 쓰고 있다면, 그 구간만 MVT를 유지하는 **이중 포맷 서빙**이 현실적인 과도기 전략이다.

## 실제 프로젝트 진행 순서

1. **병목을 먼저 진단한다.** 브라우저 개발자 도구로 타일 다운로드 시간, 파싱 시간, 렌더링 시간을 각각 측정해 실제 병목이 전송·디코딩 구간에 있는지부터 확인한다. 렌더링이 병목이면 MLT 전환은 우선순위가 아니다.
2. **렌더러 스택을 점검한다.** 서비스에서 쓰는 모든 지도 렌더러(웹, 모바일 네이티브, 내부 분석 도구)가 MLT 디코딩을 지원하는 버전인지 확인한다. 하나라도 지원하지 않으면 전면 전환은 보류한다.
3. **타일 생성 파이프라인에 변환 단계를 추가한다.** 기존 tippecanoe/Planetiler 산출물을 MLT 인코더로 변환하는 단계를 별도로 넣거나, MLT를 직접 생성하는 도구로 교체할지 결정한다.
4. **트래픽 일부에만 먼저 적용한다.** 신규 기능이나 내부 대시보드처럼 렌더러 버전을 완전히 통제할 수 있는 구간에 먼저 적용해 실제 압축률·속도 개선을 자체 데이터로 검증한다.
5. **이중 서빙 기간을 명시적으로 정한다.** 레거시 렌더러가 남아 있는 동안은 MVT와 MLT를 동시에 서빙하고, CDN 캐시 키에 포맷을 구분해 넣어 전환 완료 시점을 추적한다.

## 마무리

- MLT는 열 지향 저장과 경량 인코딩으로 MVT 대비 압축률과 디코딩 속도를 크게 끌어올리지만, 전송·파싱이 병목일 때만 효과가 있다.
- 포맷 전환은 타일 생성 도구와 클라이언트 렌더러 양쪽이 동시에 MLT를 지원해야 완성되므로, 생태계 지원 수준을 먼저 확인해야 한다.
- 전사 전환보다 렌더러 버전을 통제할 수 있는 구간부터 이중 서빙으로 시작하는 점진적 전략이 현실적이다.
