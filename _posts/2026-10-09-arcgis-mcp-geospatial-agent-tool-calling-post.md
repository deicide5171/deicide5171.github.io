## 왜 지금 이 판단이 불거지는가

"우리 서비스에 붙인 AI 비서가 '여기서 제일 가까운 지점 찾아줘', '이 주소로 길찾기 해줘' 같은 요청도 바로 처리하게 해주세요." 챗봇에 에이전트 프레임워크를 얹기 시작한 팀이라면 자연스럽게 마주치는 요구다. 예전 같으면 "지오코딩 API 붙이고, 라우팅 엔진 붙이고, 각각 LLM 프롬프트에 결과를 요약해서 넣어주세요" 정도로 끝났겠지만, 에이전트가 스스로 도구를 고르고 호출하는 지금은 "어떤 공간 연산을, 어떤 입출력 스키마의 도구로 노출할 것인가"라는 설계 질문이 먼저 온다.

2026년 7월 Esri User Conference에서 이 질문에 대한 벤더 쪽 답이 나왔다. Esri는 ArcGIS Enterprise·ArcGIS Online·ArcGIS Location Platform에 걸쳐 Model Context Protocol(MCP) 지원을 단계적으로 공개했고, 지오코딩·라우팅·공간 질의·지오프로세싱·콘텐츠 검색·지도 내보내기·지오인리치먼트·고도 조회 같은 연산을 MCP 호환 에이전트라면 GIS 전문 지식 없이 바로 호출할 수 있게 열었다. 동시에 Google Earth AI, CARTO 같은 AI 네이티브 경쟁자들도 비슷한 에이전틱 레이어를 빠르게 쫓아오고 있다. 벤더가 호스팅하는 공간 도구 계층에 올라탈지, 이미 운영 중인 PostGIS·라우팅 엔진 위에 직접 MCP 서버를 얹을지를 지금 판단해야 하는 이유다.

## 요구사항을 기술 문제로 번역하기

"지도 기능을 에이전트가 쓰게 해주세요"는 "자연어 요청 하나를 지도 API 호출 하나로 바꿔주세요"가 아니다. 실제로는 **에이전트가 호출할 수 있는 이산적(discrete) 공간 연산 도구 세트를 정의하고, 각 도구의 입출력 스키마·좌표계·단위를 모호함 없이 고정하는 문제**로 번역된다. 이전에 다룬 Text-to-SQL 에이전트가 "자연어를 SQL 한 줄로 직접 생성"하면서 좌표계·단위 실수를 저지르는 것과 달리, 도구화 접근은 "반경 검색", "최단 경로", "주소→좌표 변환" 같은 연산을 미리 검증된 도구로 고정해 두고 에이전트는 어떤 도구를, 어떤 인자로 부를지만 판단하게 만든다. 여기에 더해 "이 도구를 누가 운영하는가"라는 두 번째 질문이 붙는다. Esri의 호스팅 MCP 엔드포인트를 그대로 쓸지, 자체 데이터와 라우팅 엔진 위에 같은 역할을 하는 MCP 서버를 직접 짤지 결정해야 한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-09-arcgis-mcp-geospatial-agent-tool-calling-1.svg" alt="AI 에이전트가 MCP 클라이언트를 통해 Esri ArcGIS의 호스팅 MCP 서버 또는 자체 PostGIS 기반 MCP 서버 중 하나(또는 둘 다)를 호출하고, 각각 전세계 커버리지 데이터와 자체 서비스 데이터로부터 지오코딩·라우팅·공간질의 결과를 받아 에이전트 응답으로 합쳐지는 구조도" style="width:100%;">

이 구조에서 MCP 서버는 LLM의 자연어 판단과 실제 공간 연산 엔진 사이의 도구화 계층에 위치한다. 앞단에는 사용자의 자연어 요청을 받아 어떤 공간 연산이 필요한지 판단하는 에이전트가 있다. 에이전트는 등록된 도구 목록(지오코딩, 라우팅, 반경 질의 등)만 보고 호출할 도구와 인자를 고른다. 뒷단에는 두 갈래 선택지가 있다. 하나는 Esri가 호스팅하는 MCP 서버로, ArcGIS의 전 세계 기준 데이터와 지오프로세싱 엔진을 그대로 빌려 쓴다. 다른 하나는 자체 PostGIS 데이터베이스와 라우팅 엔진(OSRM 등) 위에 직접 짠 MCP 서버로, 자체 매장·배달 구역 같은 서비스 특화 데이터를 반영한다. 실무에서는 둘을 혼용하는 경우가 많다. 전 세계 범용 연산(주소 지오코딩)은 벤더 쪽에, 자체 데이터가 필요한 연산(우리 매장 반경 검색)은 자체 서버에 맡기는 식이다.

## 선택의 트레이드오프

| 접근 | 커버리지 | 데이터 주권 | 초기 구축 비용 | 적합한 상황 |
|---|---|---|---|---|
| ArcGIS 호스팅 MCP | 전 세계, 벤더 범용 데이터 | 낮음(외부 호출) | 낮음(연동만) | 범용 지오코딩·라우팅이 핵심 |
| 자체 PostGIS 기반 MCP 서버 | 자체 데이터 범위로 한정 | 높음(완전 내재화) | 높음(서버·스키마 설계) | 자체 매장·배달권 등 고유 데이터 필요 |
| 서드파티 라우팅 엔진 MCP 래퍼(OSRM 등) | 도로망 데이터 범위 | 중간 | 중간 | 경로 탐색 비중이 크고 비용 민감 |
| 벤더+자체 혼합 구성 | 넓음(연산별로 분기) | 연산별로 다름 | 중간~높음(라우팅 로직 추가) | 범용 연산과 고유 데이터가 함께 필요 |

ArcGIS MCP를 그대로 쓰면 지오코딩·라우팅 같은 범용 연산을 직접 운영하지 않아도 되지만, 지원 연산 범위가 아직 단계적으로 확장되는 중이라 필요한 연산이 특정 티어(ArcGIS Online vs Enterprise)에서만 열려 있을 수 있고, 벤더 쪽 요금·쿼터에 종속된다. 반대로 자체 MCP 서버는 완전한 통제권을 주지만, 전 세계 지오코딩 품질을 Esri 수준으로 맞추려는 시도는 대부분 비효율적이다. 그래서 "범용 연산은 빌려 쓰고, 자체 데이터가 들어가는 연산만 직접 짠다"는 혼합 구성이 많은 서비스에서 현실적인 기본값이 된다.

## 실제 프로젝트 진행 순서

1. **에이전트가 실제로 필요로 하는 공간 연산을 먼저 목록화한다.** 지오코딩, 라우팅, 반경 검색, 최근접 시설 찾기처럼 구체적인 동사 단위로 적는다. "지도 기능 전체"가 아니라 이 목록이 설계의 출발점이다.
2. **각 연산이 ArcGIS MCP로 이미 열려 있는지 공식 문서로 확인한다.** 지원 범위가 계속 확장 중이므로 벤더 블로그가 아니라 ArcGIS 아키텍처 문서에서 현재 티어별 지원 연산을 직접 확인한다.
3. **자체 데이터가 필요한 연산만 골라 자체 MCP 서버로 래핑한다.** 기존 PostGIS 쿼리나 라우팅 엔진 호출을 그대로 도구 함수로 옮기되, 입력 스키마에 좌표계(EPSG 코드)와 단위(미터 vs 킬로미터)를 명시적으로 고정한다.
4. **도구 설명(description)에 모호성을 남기지 않는다.** "반경"이라는 단어 하나도 미터인지 킬로미터인지 도구 스키마에 적어두지 않으면 에이전트가 임의로 해석해 틀린 값을 넣는다.
5. **벤더 연산과 자체 연산을 섞어 쓸 분기 로직을 설계한다.** 같은 "장소 찾기" 요청도 전역 데이터면 ArcGIS로, 자체 매장 데이터면 자체 서버로 보내는 라우팅 규칙을 에이전트 오케스트레이션 레이어에 둔다.
6. **실제 질의 샘플로 도구 호출 정확도를 먼저 검증한다.** 프로덕션에 앞서 다양한 자연어 표현(반경, 거리, 근처 등)이 올바른 도구와 올바른 단위로 매핑되는지 테스트 케이스를 쌓는다.

## 코드 예시 — 공간 연산을 MCP 도구 스키마로 고정하기

```json
{
  "name": "search_nearby_stores",
  "description": "주어진 좌표(WGS84, EPSG:4326)에서 반경(미터 단위) 안의 자체 매장을 조회한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "lat": { "type": "number", "description": "위도, EPSG:4326" },
      "lon": { "type": "number", "description": "경도, EPSG:4326" },
      "radius_m": { "type": "integer", "description": "검색 반경, 단위는 반드시 미터" }
    },
    "required": ["lat", "lon", "radius_m"]
  }
}
```

```sql
-- MCP 도구 핸들러 내부에서 실행되는 PostGIS 쿼리
SELECT store_id, name,
       ST_Distance(geom::geography, ST_MakePoint($1, $2)::geography) AS dist_m
FROM stores
WHERE ST_DWithin(geom::geography, ST_MakePoint($1, $2)::geography, $3)
ORDER BY dist_m;
```

## 실무 포인트

**좌표계와 단위 모호성이 가장 흔한 실패 지점이다.** "반경 500m"를 도구 스키마에 숫자형으로만 받으면 LLM이 가끔 킬로미터로 착각해 값을 그대로 넘긴다. 단위를 필드명(`radius_m`)과 설명 양쪽에 중복해서 명시하는 것이 방어선이다.

**벤더 지원 범위를 고정으로 가정하지 않는다.** ArcGIS MCP는 계속 확장 중이므로, 특정 연산이 지금 지원 범위 밖이라고 영구히 자체 구축해야 한다고 단정하지 말고 분기마다 재확인한다.

**자체 서버와 벤더 서버의 장애를 분리해 모니터링한다.** 두 MCP 서버를 혼용하면 한쪽 장애가 다른 쪽 연산까지 실패한 것처럼 보일 수 있으므로, 도구 호출 로그에 어느 서버를 거쳤는지 반드시 남긴다.

## 마무리

- "지도 기능을 에이전트가 쓰게 해주세요"는 이산적 공간 연산을 도구로 고정하고, 각 도구의 좌표계·단위를 명확히 하는 문제로 번역된다.
- MCP 서버는 LLM의 자연어 판단과 실제 공간 연산 엔진 사이의 도구화 계층에 위치하며, ArcGIS 호스팅 MCP와 자체 PostGIS 기반 MCP 서버를 연산 성격에 따라 혼용하는 구성이 많은 서비스의 현실적인 출발점이다.
- 도입 순서는 필요한 연산 목록화 → 벤더 지원 범위 확인 → 자체 데이터 연산만 래핑 → 단위·좌표계 스키마 고정 → 분기 로직 설계 → 실제 질의로 호출 정확도 검증 순으로 진행한다.
