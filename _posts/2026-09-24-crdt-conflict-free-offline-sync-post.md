## 왜 지금 CRDT를 다시 봐야 하는가

여러 기기나 사용자가 동시에, 심지어 네트워크가 끊긴 상태에서도 같은 데이터를 수정할 수 있어야 하는 협업 도구(공동 문서 편집)나 오프라인 우선(offline-first) 모바일 앱을 만들다 보면 반드시 충돌 해결 문제에 부딪힌다. 흔한 접근은 "마지막으로 쓴 사람이 이긴다(Last-Write-Wins)"는 단순한 타임스탬프 비교지만, 이는 한쪽의 변경 내용을 통째로 날려버리는 손실이 생긴다. 서버에서 3-way merge 같은 수동 병합 로직을 짜는 것은 가능하지만 도메인마다 병합 규칙을 새로 설계해야 해서 확장성이 떨어진다. CRDT(Conflict-free Replicated Data Type)는 자료구조 자체를 "어떤 순서로 병합해도 항상 같은 결과에 수렴한다"는 수학적 성질을 만족하도록 설계해, 애플리케이션이 충돌 해결 로직을 따로 짜지 않아도 자동으로 병합되게 만드는 접근이다.

## 핵심 개념 1 — 병합 연산이 만족해야 할 대수적 성질

CRDT가 성립하려면 데이터에 대한 병합(merge) 연산이 결합법칙(associative), 교환법칙(commutative), 멱등법칙(idempotent)을 만족해야 한다. 결합·교환법칙은 "병합하는 순서나 그룹 짓는 방식과 무관하게 최종 결과가 같다"는 것을 보장하는데, 이는 네트워크가 불안정해 업데이트가 어떤 순서로 도착할지 예측할 수 없는 분산 환경에서 핵심적인 성질이다. 멱등법칙은 "같은 업데이트를 두 번 적용해도 결과가 달라지지 않는다"는 것으로, 네트워크 재전송으로 같은 메시지가 중복 도착해도 안전하게 만든다. 일반적인 리스트의 `append`나 카운터의 `increment` 같은 연산은 이 성질을 만족하지 않으므로, CRDT는 이를 만족하도록 특별히 설계된 자료구조를 쓴다.

## 핵심 개념 2 — 상태 기반(CvRDT)과 연산 기반(CmRDT)의 차이

CRDT는 크게 두 가지 방식으로 구현된다. 상태 기반(state-based, CvRDT)은 각 복제본이 전체 상태를 주고받고, 두 상태를 합치는 join 연산이 항상 두 상태 중 "더 큰" 상태로 수렴하도록 설계한다(격자 이론의 최소 상한, least upper bound). 연산 기반(operation-based, CmRDT)은 상태 전체가 아니라 적용된 연산(operation)만 전파하며, 이 연산들이 순서와 무관하게 적용돼도 같은 결과가 나오도록 설계한다. 상태 기반은 구현이 단순하지만 전체 상태를 계속 주고받아 네트워크 비용이 크고, 연산 기반은 대역폭 효율적이지만 연산이 반드시 한 번씩 정확히 전달돼야 한다는 전제가 필요하다.

| CRDT 종류 | 예시 자료구조 | 병합 방식 |
|---|---|---|
| G-Counter | 노드별 카운터 배열 | 각 노드 값의 최댓값 유지 후 합산 |
| PN-Counter | 증가/감소 G-Counter 두 개 | 증가분 - 감소분 |
| OR-Set | 태그가 붙은 추가/삭제 이력 | 추가 태그가 삭제 태그보다 최신이면 존재 |
| RGA/LSEQ (텍스트) | 각 문자에 고유 위치 식별자 부여 | 위치 식별자 순서로 정렬해 병합 |

## 예제 — G-Counter로 분산 카운터 구현하기

```javascript
class GCounter {
  constructor(nodeId, nodeIds) {
    this.nodeId = nodeId;
    this.counts = Object.fromEntries(nodeIds.map((id) => [id, 0]));
  }

  increment() {
    this.counts[this.nodeId] += 1;
  }

  value() {
    return Object.values(this.counts).reduce((a, b) => a + b, 0);
  }

  // 병합: 각 노드별로 더 큰 값을 취한다 — 순서·중복 무관하게 항상 같은 결과
  merge(other) {
    for (const id of Object.keys(this.counts)) {
      this.counts[id] = Math.max(this.counts[id], other.counts[id]);
    }
  }
}
```

각 노드가 자신의 슬롯만 증가시키고, 병합할 때는 슬롯별로 더 큰 값을 취하기만 하면 되므로 몇 번을 병합하든, 어떤 순서로 병합하든 항상 같은 최종 값에 수렴한다.

## 실무 포인트

- **협업 텍스트 편집처럼 순서가 중요한 데이터에는 전용 시퀀스 CRDT(RGA, LSEQ, YATA 등)를 직접 구현하기보다 Yjs, Automerge 같은 검증된 라이브러리를 먼저 검토하라.** 텍스트 CRDT는 이론은 단순해도 실제 구현에는 성능·메모리 최적화를 위한 미묘한 트릭이 많다.
- **모든 데이터를 CRDT로 모델링하려 하지 마라.** 은행 잔액처럼 "정확히 하나의 값으로 강하게 일관돼야 하는" 데이터는 CRDT의 결과적 일관성 모델과 잘 맞지 않으므로, 오프라인 우선이 정말 필요한 데이터에만 선택적으로 적용해야 한다.
- **삭제된 데이터의 튬스톤(tombstone)이 계속 쌓이는 문제를 관리하라.** OR-Set 같은 구조는 삭제된 항목의 이력을 완전히 지우지 못하고 튬스톤으로 남기므로, 이 튬스톤을 주기적으로 가비지 컬렉션하는 전략(예: 벡터 시계 기반 안전한 시점 판단)을 별도로 마련해야 한다.

## 마무리 요약

- CRDT는 병합 연산이 결합·교환·멱등법칙을 만족하도록 설계된 자료구조로, 어떤 순서로 병합해도 항상 같은 결과에 수렴해 수동 충돌 해결 로직이 필요 없다.
- 상태 기반(CvRDT)은 구현이 단순하지만 대역폭 비용이 크고, 연산 기반(CmRDT)은 효율적이지만 연산 전달 보장이 필요하다.
- 강한 일관성이 필요한 데이터에는 적합하지 않으므로, 오프라인 우선이나 협업 편집처럼 결과적 일관성이 허용되는 도메인에 선택적으로 적용해야 한다.
