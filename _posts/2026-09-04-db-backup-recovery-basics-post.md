## 백업이 있다고 안심하면 안 되는 이유

"백업을 돌리고 있으니 괜찮다"는 말은 절반만 맞다. 정작 사고가 났을 때 그 백업으로 실제 복구가 되는지 확인해본 적이 없다면, 백업이 있어도 데이터를 못 살릴 수 있다. DB 백업을 이해할 때는 **어떻게 백업하는가**와 **어떻게 복구하는가**를 함께 봐야 한다.

## 논리 백업 vs 물리 백업

| 항목 | 논리 백업 | 물리 백업 |
|---|---|---|
| 방식 | 데이터를 SQL 문이나 텍스트로 추출 | DB 파일 자체를 통째로 복사 |
| 대표 도구 | `mysqldump`, `pg_dump` | 파일 복사, `pg_basebackup`, 스냅샷 |
| 속도 | 느림(대용량일수록) | 빠름 |
| 이식성 | 좋음(버전·환경 간 이동 쉬움) | 제한적(같은 엔진·버전 권장) |
| 용도 | 소규모, 특정 테이블만, 마이그레이션 | 대용량 전체 백업 |

## 논리 백업 예제

```bash
# PostgreSQL 전체 백업
pg_dump -U user mydb > backup.sql

# 복구
psql -U user mydb < backup.sql

# MySQL 특정 테이블만 백업
mysqldump -u user mydb users > users_backup.sql
```

논리 백업은 결과물이 사람이 읽을 수 있는 SQL이라 이해하기 쉽고, 특정 테이블만 골라 백업하거나 다른 버전의 DB로 옮기기 편하다. 대신 데이터가 크면 느리다.

## 백업 전략의 핵심 개념 두 가지

```text
RPO (Recovery Point Objective): 데이터를 얼마나 잃어도 되는가
  - "최대 1시간치 데이터 손실 허용" -> 최소 1시간마다 백업 필요

RTO (Recovery Time Objective): 얼마나 빨리 복구해야 하는가
  - "2시간 안에 복구" -> 그 안에 끝낼 수 있는 백업·복구 방식 선택
```

이 두 목표를 먼저 정해야 "얼마나 자주, 어떤 방식으로" 백업할지가 결정된다.

## 실무 포인트

- **복구 테스트를 안 한 백업은 백업이 아니다.** 백업 파일이 손상됐거나, 복구 절차가 잘못됐거나, 필요한 데이터가 빠졌을 수 있다. 정기적으로 백업으로 실제 복구가 되는지 검증해야 진짜 대비가 된다.
- **백업을 원본과 같은 서버·디스크에만 두면 의미가 없다.** 그 서버가 통째로 망가지면 백업도 함께 사라진다. 반드시 별도 위치(다른 서버, 클라우드 스토리지 등)에 보관해야 한다.
- **특정 시점으로 되돌리는 복구(PITR)가 필요하면 백업만으로는 부족하다.** 전체 백업에 더해 그 이후의 변경 로그(WAL/binlog)를 함께 보관해야 "어제 오후 3시 상태"처럼 원하는 시점으로 복구할 수 있다.

## 마무리 요약

- 논리 백업은 SQL로 추출해 이식성이 좋고, 물리 백업은 파일을 통째로 복사해 대용량에 빠르다.
- RPO(허용 손실)와 RTO(복구 시간) 목표를 먼저 정해야 백업 주기와 방식이 결정된다.
- 복구 테스트를 안 한 백업은 신뢰할 수 없고, 백업은 반드시 원본과 다른 위치에 보관해야 한다.
