## 페이지를 넘길 때 새로고침이 되나 안 되나

웹사이트를 쓸 때 링크를 누르면 화면이 하얗게 깜빡이며 새로고침되는 곳도 있고, 깜빡임 없이 부드럽게 바뀌는 곳도 있다. 이 차이가 **MPA(Multi-Page Application)**와 **SPA(Single-Page Application)**의 구분이다. MPA는 페이지마다 서버에서 새 HTML을 받아오고, SPA는 하나의 페이지에서 자바스크립트로 화면만 바꾼다.

## SPA vs MPA

| 항목 | SPA | MPA |
|---|---|---|
| 페이지 전환 | JS로 화면만 교체(새로고침 없음) | 서버에서 새 HTML 로드 |
| 첫 로딩 | 느릴 수 있음(JS 번들 큼) | 페이지별로 필요한 만큼 |
| 이후 전환 | 빠름(부분만 갱신) | 매번 서버 왕복 |
| SEO | 별도 대응 필요(SSR 등) | 유리(완성된 HTML) |
| 대표 예시 | Gmail, 대시보드 앱 | 블로그, 문서 사이트, 쇼핑몰 상세 |

## 각 방식의 동작

```text
[MPA]
링크 클릭 -> 서버에 요청 -> 새 HTML 페이지 받음 -> 전체 새로고침
(페이지마다 독립적, 서버가 HTML을 완성해 보냄)

[SPA]
링크 클릭 -> JS가 필요한 데이터만 받아옴 -> 화면 일부만 교체
(첫 로딩 후엔 서버에서 HTML을 다시 안 받음)
```

## 실무 포인트

- **SPA는 SEO에 불리할 수 있어 대응이 필요하다.** SPA는 초기 HTML이 거의 비어 있고 JS가 화면을 그리므로, 검색엔진이 내용을 못 읽을 수 있다. 이를 해결하려고 서버 사이드 렌더링(SSR)이나 정적 생성(SSG)을 함께 쓴다. Next.js 같은 프레임워크가 이 조합을 제공한다.
- **첫 로딩 성능을 신경 써야 한다.** SPA는 JS 번들을 먼저 받아야 화면이 뜨므로, 번들이 크면 첫 화면이 느리다. 코드 분할로 필요한 부분만 먼저 로드하는 것이 중요하다.
- **모든 사이트가 SPA일 필요는 없다.** 블로그·문서·마케팅 페이지처럼 콘텐츠 중심 사이트는 MPA(또는 정적 사이트)가 SEO와 초기 로딩에 유리하다. 상호작용이 많은 앱형 서비스에 SPA가 적합하다.

## 마무리 요약

- MPA는 페이지마다 서버에서 새 HTML을 받고, SPA는 하나의 페이지에서 JS로 화면만 바꾼다.
- SPA는 전환이 부드럽고 빠르지만 첫 로딩과 SEO에서 불리해 SSR·SSG로 보완한다.
- 상호작용 많은 앱은 SPA, 콘텐츠 중심 사이트는 MPA가 적합하며 무조건 SPA가 정답은 아니다.
