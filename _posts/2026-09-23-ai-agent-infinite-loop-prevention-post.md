## 왜 에이전트가 멈추지 않을까

AI 에이전트에게 "이 버그를 찾아서 고쳐줘"처럼 다단계 작업을 맡겼는데, 로그를 보니 같은 파일을 읽고 같은 검색을 반복하며 몇 분째 끝나지 않는 경우를 겪게 된다. 결제 대시보드를 열어보면 토큰 사용량이 예상보다 몇 배는 더 찍혀 있다. 챗봇처럼 한 번 답하고 끝나는 구조와 달리, 에이전트는 스스로 "다음에 뭘 할지"를 판단하며 도구를 반복 호출하는 구조이기 때문에, 이 판단 로직에 틈이 있으면 종료 조건을 스스로 찾지 못하고 계속 맴돌 수 있다.

이 문제가 특히 골치 아픈 이유는 코드에 명백한 버그가 있는 게 아니라는 점이다. 모델이 매번 "이 정보로는 부족하니 한 번 더 찾아보자"는 그럴듯한 판단을 반복하는 것이므로, 로그만 봐서는 정상 동작과 무한 루프를 구분하기 어려울 때가 많다.

## 핵심 개념 1 — 루프가 생기는 세 가지 전형적인 패턴

- **같은 도구를 같은 인자로 반복 호출**: 검색 결과가 기대에 못 미쳐 "다시 검색"을 반복하지만 같은 쿼리라 결과도 똑같다.
- **A→B→A 진동**: 파일을 고쳤다가, 테스트가 실패하니 원래대로 되돌렸다가, 다시 고치는 식으로 두 상태를 오간다.
- **컨텍스트 누적으로 인한 판단력 저하**: 대화가 길어질수록 컨텍스트 윈도우 앞부분의 중요한 제약사항이 밀려나면서, 이미 시도했던 접근을 다시 시도하게 된다.

세 번째 패턴이 가장 알아채기 어렵다. 겉으로는 매번 조금씩 다른 시도처럼 보이지만, 실제로는 몇 스텝 전에 실패했던 접근을 형태만 바꿔 반복하는 경우가 많기 때문이다.

## 핵심 개념 2 — 종료 조건은 모델에게 맡기지 말고 코드로 강제해야 한다

모델에게 "충분하다고 판단되면 멈춰"라고 프롬프트로만 지시하는 것은 안전장치가 되지 못한다. 모델은 결국 확률적으로 다음 행동을 고르는 존재라, 드물지만 "한 번 더 확인해볼게"를 반복해서 고를 가능성이 항상 남아 있다. 실무에서 신뢰할 수 있는 방식은 에이전트를 감싸는 오케스트레이션 코드 레벨에서 하드 리밋을 거는 것이다.

## 예제 — 반복 횟수 제한과 반복 감지 로직

```python
class AgentLoopGuard:
    def __init__(self, max_iterations=15, max_repeat=3):
        self.max_iterations = max_iterations
        self.max_repeat = max_repeat
        self.iteration = 0
        self.call_history = []

    def check(self, tool_name: str, tool_args: dict) -> bool:
        """계속 진행해도 되면 True, 중단해야 하면 False."""
        self.iteration += 1
        if self.iteration > self.max_iterations:
            return False  # 절대적 상한선

        call_signature = (tool_name, tuple(sorted(tool_args.items())))
        self.call_history.append(call_signature)

        # 최근 N번 안에 동일한 호출이 max_repeat번 이상 반복되면 중단
        recent = self.call_history[-6:]
        if recent.count(call_signature) >= self.max_repeat:
            return False

        return True
```

이 가드는 두 겹으로 동작한다. 절대적인 최대 스텝 수(`max_iterations`)로 어떤 상황에서든 결국은 멈추게 하고, 최근 호출 이력에서 동일한 (도구, 인자) 조합이 반복되는지 감지해 더 빨리 개입한다.

## 흔한 실수와 대안

| 실수 | 결과 | 대안 |
|---|---|---|
| 프롬프트에 "무한 루프 방지" 문구만 추가 | 확률적으로 여전히 반복 가능 | 코드 레벨 하드 리밋 병행 |
| 최대 반복 횟수를 너무 낮게 설정 | 복잡한 작업이 중간에 잘림 | 작업 유형별로 다른 상한 설정 |
| 반복 감지 없이 횟수 제한만 둠 | 진동 패턴을 늦게 잡아냄 | 최근 호출 이력 기반 반복 감지 병행 |
| 중단 시 아무 안내 없이 조용히 종료 | 사용자가 실패 이유를 모름 | 중단 사유와 진행 상황을 요약해 반환 |

마지막 항목이 실무에서 자주 간과된다. 루프를 강제로 끊는 것 자체는 쉽지만, "왜 멈췄는지, 그때까지 뭘 했는지"를 사용자에게 보여주지 않으면 그냥 먹통이 된 것처럼 보인다. 중단 시점의 상태를 요약해 반환하는 것이 실패를 실패답게 처리하는 방법이다.

## 실무 포인트

- **작업 유형별로 다른 반복 상한을 두어라.** 단순 조회 작업은 5회, 복잡한 리팩터링 작업은 30회처럼 작업의 예상 복잡도에 맞춰 상한을 다르게 설정해야 지나친 조기 종료나 과도한 비용 낭비를 둘 다 피할 수 있다.
- **비용 상한도 함께 걸어라.** 스텝 수뿐 아니라 누적 토큰 사용량이나 API 호출 비용 자체에 상한을 걸어두면, 한 스텝에서 비정상적으로 큰 컨텍스트를 반복 처리하는 경우까지 방어할 수 있다.
- **사람 개입 지점(human-in-the-loop)을 중간에 넣어라.** 특정 반복 횟수를 넘기면 자동으로 계속하는 대신 사람에게 "계속 진행할까요?"라고 확인받는 체크포인트를 두면, 완전 자동화와 안전성 사이의 절충점을 만들 수 있다.

## 마무리 요약

- 에이전트의 무한 루프는 코드 버그가 아니라 모델이 그럴듯한 판단을 반복해서 내리는 구조적 문제이므로 로그만으로는 정상 동작과 구분하기 어렵다.
- 종료 조건은 프롬프트가 아니라 오케스트레이션 코드 레벨에서 최대 반복 횟수와 반복 감지를 함께 걸어 강제해야 신뢰할 수 있다.
- 루프를 끊을 때는 조용히 종료하지 말고 중단 사유와 진행 상황을 요약해 사용자에게 돌려줘야 실패를 실패답게 처리할 수 있다.
