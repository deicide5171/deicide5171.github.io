CSS는 오랫동안 "자식이나 형제의 상태를 보고 부모를 스타일링한다"는 방향의 선택자를 제공하지 않았다. `.card img`처럼 조상에서 자손으로 내려가는 선택자는 있어도, 그 반대 방향인 부모 선택자는 명세에 존재한 적이 없었다. 그래서 "이미지가 있는 카드에만 여백을 다르게 준다"거나 "체크박스가 선택된 항목의 부모 li에 배경색을 넣는다" 같은 흔한 요구사항조차 CSS만으로는 해결할 수 없었고, 결국 자바스크립트로 자식 요소의 상태를 감지해 부모에 클래스를 토글하는 우회가 사실상 표준 관행이 됐다.

이 한계는 단순히 코드 몇 줄을 더 쓰는 문제가 아니었다. 상태가 바뀔 때마다 이벤트 리스너를 등록하고, DOM을 순회하고, 클래스 이름 충돌을 관리해야 했으며, 이 모든 로직이 원래는 스타일링 문제인데도 자바스크립트 레이어로 새어 나갔다. `:has()` 의사클래스는 이 구조적 공백을 정면으로 메운다. 인자로 받은 선택자에 매칭되는 자손(또는 형제)이 하나라도 존재하는 요소를 선택할 수 있게 되면서, 그동안 자바스크립트가 떠맡던 조건부 스타일링의 상당 부분을 순수 CSS로 되돌려 놓았다.

## 핵심 개념 1: :has()의 기본 문법과 동작 원리

`:has()`는 관계형 의사클래스(relational pseudo-class)로 분류된다. `A:has(B)`는 "B에 해당하는 요소를 하나 이상 포함하는 A"를 의미하며, 여기서 B 자리에는 자손 결합자뿐 아니라 인접 형제(`+`), 일반 형제(`~`) 결합자도 함께 쓸 수 있다. 즉 `.card:has(img)`는 "img 자손을 가진 .card"이고, `h2:has(+ p)`는 "바로 다음에 p가 오는 h2"다. 후자는 기존 CSS 선택자 체계에서는 아예 표현할 방법이 없던 관계였다.

동작 원리 면에서 중요한 점은, `:has()`의 인자는 문서 트리 안에서 매칭 여부만 판단하는 조건일 뿐, 실제로 선택되어 스타일이 적용되는 대상은 항상 `:has()` 앞에 놓인 요소라는 것이다. `.card:has(img)`를 적용해도 img 자체의 스타일은 바뀌지 않고, .card의 스타일만 바뀐다. 또한 `:has()`는 다른 의사클래스처럼 체이닝과 중첩이 가능해서 `.form:has(input:invalid)`, `body:has(.modal:not(.hidden))`처럼 상태 조건을 조합할 수 있다.

## 핵심 개념 2: 실전 활용 패턴

가장 널리 쓰이는 패턴은 폼 유효성 스타일링이다. 입력값이 유효하지 않을 때 해당 입력창뿐 아니라 그 입력창을 감싸는 필드 그룹 전체의 테두리나 배경을 바꾸고 싶은 경우, 기존에는 `input`에 `blur` 이벤트를 걸어 부모에 클래스를 추가해야 했다. `:has()`를 쓰면 `.field:has(input:invalid)` 같은 선택자 하나로 동일한 효과를 자바스크립트 없이 얻을 수 있다.

두 번째로 흔한 패턴은 콘텐츠 유무에 따른 레이아웃 분기다. 카드 컴포넌트에 이미지가 있을 때와 없을 때 그리드 배치를 다르게 하고 싶다면, 과거에는 서버·클라이언트 렌더링 단계에서 조건부로 클래스를 붙여야 했다. `:has(img)` 여부로 이를 CSS 셀렉터 단에서 바로 분기할 수 있어, 마크업을 생성하는 쪽의 책임이 줄어든다. 이 밖에도 `label:has(input:checked)`로 체크된 라디오/체크박스의 라벨을 강조하거나, `dialog:has(.error)`로 에러 메시지가 있을 때만 모달 크기를 키우는 식의 패턴이 자주 쓰인다.

## 핵심 개념 3: 성능 고려사항과 브라우저 지원

`:has()`는 매칭 판단을 위해 자손·형제 방향으로 트리를 추가로 탐색해야 하므로, 일반 자손 선택자보다 계산 비용이 더 든다고 알려져 있다. 브라우저 엔진들은 이를 위해 별도의 최적화(변경 감지 범위를 좁히는 방식 등)를 적용하고 있지만, 문서 규모가 매우 크고 `:has()`의 인자가 복잡한 경우 스타일 재계산 비용이 커질 가능성은 남아 있다. 정확한 임계치는 브라우저 버전과 문서 구조에 따라 달라지므로, 특정 수치로 단정하기보다는 실제 프로젝트에서 개발자 도구의 성능 패널로 확인하는 편이 안전하다.

| 브라우저 | 지원 여부(개략) |
|---|---|
| Chrome / Edge | 버전 105부터 지원 |
| Safari | 버전 15.4부터 지원 |
| Firefox | 버전 121부터 지원 |

주요 브라우저는 모두 안정 버전에서 `:has()`를 지원하는 단계에 이르렀지만, 여전히 구형 브라우저를 지원해야 하는 프로젝트라면 폴리필 없이 사용할 경우 해당 규칙만 조용히 무시된다는 점을 감안해 점진적 향상(progressive enhancement) 관점에서 도입하는 것이 안전하다.

## 예제

```css
/* 유효하지 않은 입력이 있는 필드 그룹만 강조 */
.field:has(input:invalid) {
  border-color: #e53e3e;
  background-color: #fff5f5;
}

.field:has(input:invalid) label {
  color: #e53e3e;
}

/* 체크된 체크박스의 부모 항목 강조 */
.todo-item:has(input[type="checkbox"]:checked) {
  text-decoration: line-through;
  opacity: 0.6;
}
```

```css
/* 이미지 유무에 따라 카드 레이아웃 분기 */
.card {
  display: grid;
  grid-template-columns: 1fr;
  gap: 8px;
}

.card:has(img) {
  grid-template-columns: 96px 1fr;
  align-items: center;
}

.card:has(img) img {
  width: 96px;
  height: 96px;
  object-fit: cover;
}
```

## 실무 포인트

- **선택자를 남용하면 가독성이 떨어진다**: `:has()`를 여러 단계 중첩하거나 다른 관계형 의사클래스와 겹겹이 조합하면, 스타일이 어떤 조건에서 적용되는지 코드만 보고 파악하기 어려워진다. 조건이 복잡해질수록 클래스 토글 방식이 오히려 더 읽기 쉬울 수 있다.
- **대규모 문서에서는 영향 범위를 가늠하고 쓴다**: 트리 전체를 대상으로 하는 `:has()` 조건은 DOM 변경이 잦은 영역(예: 실시간으로 갱신되는 리스트)에 걸어두면 재계산 비용이 누적될 수 있으므로, 변경 빈도가 높은 곳일수록 선택자 범위를 좁게 유지하는 것이 좋다.
- **폴백 전략을 세워둔다**: 구형 브라우저 지원이 필요하다면 `:has()`가 무시돼도 레이아웃이 깨지지 않도록, 핵심 기능은 자바스크립트 폴백 없이도 동작하게 설계하고 `:has()`는 시각적 개선 용도로 얹는 편이 안전하다.

## 3줄 요약

- CSS에는 원래 부모 선택자가 없어 자바스크립트로 클래스를 토글해야 했지만, `:has()`가 관계형 의사클래스로 이 공백을 메운다.
- 폼 유효성 강조, 콘텐츠 유무에 따른 카드 레이아웃 분기 등에서 자바스크립트 없이 조건부 스타일링을 구현할 수 있다.
- 주요 브라우저는 대체로 지원하지만, 복잡한 `:has()` 남용은 가독성과 성능 모두를 해칠 수 있어 범위를 좁게 유지해야 한다.
