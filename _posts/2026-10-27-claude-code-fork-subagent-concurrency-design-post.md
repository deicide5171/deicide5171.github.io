## 도입

"이 리서치, 서브에이전트 다섯 개한테 나눠서 동시에 맡기고 결과만 모아주세요." 팀에서 AI 코딩 에이전트를 쓰다 보면 자연스럽게 나오는 요구다. 처음엔 "서브에이전트를 여러 개 띄운다"는 말이 단순해 보이지만, 실제로는 매번 두 가지 결정이 따라붙는다. 하나는 **그 서브에이전트가 부모의 대화 맥락을 그대로 물려받을 것인가(fork), 아니면 백지 상태에서 시작할 것인가(신규 서브에이전트)**이고, 다른 하나는 **그 작업을 사용자가 보는 화면 앞에서 돌릴 것인가, 뒤에서 돌릴 것인가**이다.

2026년 10월 16일 출시된 Claude Code v2.1.302는 이 두 결정의 기본값을 한 번에 바꿨다. fork 서브에이전트(`subagent_type: "fork"`)가 터미널뿐 아니라 `claude -p`, Agent SDK, 데스크톱 앱, VS Code 확장에서도 기본으로 켜졌고, 신선 설치본이나 텔레메트리를 끈 환경에서는 SDK 세션의 권한 모드 자체가 조용히 바뀌는 경우도 생겼다. 이런 변화는 "설정을 건드리지 않았는데 동작이 달라졌다"는 사고로 이어지기 쉽다. 이 글은 fork와 신규 서브에이전트, 포그라운드와 백그라운드 실행을 가르는 설계 기준을 정리하고, 기본값 변경 시점에 무엇을 점검해야 하는지 다룬다.

## 전체 시스템에서의 위치

부모 세션이 작업을 서브에이전트에 넘기는 순간, 요청은 두 갈래 경로 중 하나를 탄다. fork는 부모의 대화 맥락과 프롬프트 캐시를 그대로 이어받아 같은 모델이 연속해서 작업하는 모양이고, 신규 서브에이전트는 처음부터 새 지시문만 가지고 독립적으로 시작한다.

<img src="/assets/images/posts/2026-10-27-claude-code-fork-subagent-concurrency-design-1.svg" alt="fork 서브에이전트와 신규 서브에이전트가 부모 세션으로부터 분기되는 구조, 그리고 포그라운드·백그라운드 실행 경로를 비교한 다이어그램" style="width:100%;">

- **fork**: 부모의 컨텍스트 윈도우·도구 접근 권한·프롬프트 캐시를 그대로 상속한다. 캐시가 적중하면 추가 비용이 거의 들지 않지만, 부모가 가진 모든 맥락(민감 정보 포함)이 자식에게도 그대로 넘어간다.
- **신규 서브에이전트**: 지정한 프롬프트만으로 새 컨텍스트에서 시작한다. 캐시를 새로 쌓아야 해서 토큰 비용이 더 들 수 있지만, 부모의 불필요한 맥락이 섞이지 않아 결과가 더 좁고 명확해진다.
- 두 경로 모두 **백그라운드**로 돌 수 있다. 기본값에서는 결과가 바로 필요하지 않은 작업이 백그라운드로 빠지고, 권한 확인이 필요한 순간에만 부모 세션 화면에 프롬프트가 올라온다.
- 동시성에는 상한이 있다 — 동시 서브에이전트 약 20개, 중첩(서브에이전트가 또 서브에이전트를 부르는) 깊이 3단계. 이 상한을 넘는 설계는 애초에 성립하지 않는다.

## 선택의 트레이드오프

| 기준 | fork | 신규 서브에이전트 |
|---|---|---|
| 컨텍스트 상속 | 부모 대화 전체를 이어받음 | 지정한 프롬프트만, 백지 상태 |
| 캐시·비용 | 프롬프트 캐시 재사용으로 저렴 | 새 캐시를 처음부터 쌓음 |
| 적합한 상황 | "이 맥락 그대로 조사만 더 해줘"처럼 대화의 연장 | 독립적으로 검증받고 싶은 작업, 다른 관점이 필요한 리뷰 |
| 위험 | 민감한 맥락이 자식에게까지 그대로 전파 | 부모가 아는 배경을 다시 설명해야 해서 프롬프트가 길어짐 |

| 기준 | 포그라운드 | 백그라운드 |
|---|---|---|
| 사용자 체감 | 결과를 기다리는 동안 다른 작업 불가 | 다른 작업을 계속하다가 완료 알림만 받음 |
| 적합한 상황 | 다음 행동이 결과에 바로 의존할 때 | 독립적으로 진행 가능한 조사·구현 |
| 위험 | 불필요하게 대기 시간 발생 | 완료 시점을 놓치거나, 여러 개를 동시에 띄워 추적이 어려워짐 |

판단 기준은 단순하다. **같은 대화의 연장이면 fork, 독립된 새 임무면 신규 서브에이전트**. 그리고 **다음 행동이 결과를 기다려야만 하면 포그라운드, 아니면 백그라운드**. 이 두 축을 매번 의식적으로 정하지 않으면, 기본값이 알아서 정해버린다.

## 실제 프로젝트 진행 순서

1. **병렬화하려는 작업의 성격부터 분류한다.** 같은 코드베이스·같은 맥락을 공유해야 하는 작업(리뷰, 이어쓰기)은 fork 후보, 서로 독립적이어야 하는 작업(여러 관점의 검증, 서로 다른 모듈 구현)은 신규 서브에이전트 후보다.
2. **기본값이 바뀌었다는 전제로 명시적으로 지정한다.** `subagent_type`을 비워두면 환경·버전에 따라 결과가 달라질 수 있으므로, 팀 공용 스크립트나 CI에서 쓰는 호출은 항상 명시한다.
3. **동시성 상한(약 20개, 중첩 3단계)을 설계에 반영한다.** 작업을 잘게 쪼개 수십 개를 한 번에 띄우는 설계는 상한에 걸려 조용히 큐잉되거나 실패할 수 있다.
4. **권한 모드 기본값 변화를 조직 정책에 맞게 고정한다.** 신선 설치본에서 권한 모드가 달라질 수 있으므로, CI나 배치 파이프라인에서는 설정 파일에 권한 모드를 명시적으로 박아둔다.
5. **비용 가드레일을 직접 세운다.** 기본값에는 지출 상한(spend cap)이 없다고 보고된 만큼, fork로 캐시를 재사용하더라도 동시 실행 개수와 총 토큰 사용량을 모니터링하는 장치를 먼저 둔다.
6. **환경변수로 조직 표준을 강제한다.** `CLAUDE_CODE_FORK_SUBAGENT=0`으로 포크를 끄거나 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`로 모든 서브에이전트를 포그라운드로 고정하는 식으로, 팀 전체에 일관된 기본값을 적용할 수 있다.

```bash
# CI 파이프라인에서 서브에이전트 기본값을 조직 표준으로 고정
export CLAUDE_CODE_FORK_SUBAGENT=0            # 기본 fork를 끄고 매번 명시적으로만 사용
export CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 # 백그라운드 실행을 막고 포그라운드로 강제

# 호출부에서는 작업 성격에 따라 명시적으로 타입을 지정
claude -p "PR 변경분을 버그·성능·보안 세 관점에서 각각 서브에이전트로 검토해줘" \
  --subagent-type fork --max-concurrent-subagents 3
```

## 실무 포인트

- 서브에이전트 정의에서 `tools` 필드를 비워두면 부모가 가진 도구를 그대로 상속한다. fork가 아니더라도 도구 권한은 이미 넓게 상속될 수 있으므로, 민감한 도구(결제·삭제·배포)를 쓰는 서브에이전트는 `tools`를 명시적으로 좁혀야 한다.
- 기본값 변경은 터미널에서만 조용히 적용되지 않는다. `claude -p`나 SDK로 자동화 파이프라인을 짠 팀은 다음 배포에서 동작이 달라질 수 있다는 점을 변경 로그에서 직접 확인해야 한다.
- 이번 변화는 third-party 블로그·릴리스 노트 재구성에 의존한 보고가 섞여 있다. 프로덕션에 반영하기 전에는 반드시 공식 체인지로그(`code.claude.com`)와 실제 버전에서 동작을 재현해 확인한다.

## 마무리

- fork는 컨텍스트·캐시를 상속하는 대화의 연장, 신규 서브에이전트는 독립된 임무라는 축으로 먼저 나눈다.
- 포그라운드·백그라운드는 "다음 행동이 결과를 기다려야 하는가"로 정하고, 동시성 상한(약 20개, 중첩 3단계)을 설계에 미리 반영한다.
- 기본값이 바뀌는 시점에는 CI·자동화 스크립트에서 타입과 권한 모드를 환경변수로 명시적으로 고정해 리스크를 차단한다.
