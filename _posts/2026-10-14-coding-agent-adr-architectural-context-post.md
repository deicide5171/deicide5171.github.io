## 왜 지금 이 판단이 필요한가

"이 서비스는 이벤트를 꼭 Kafka로 보내야 해요. 예전에 동기 호출로 했다가 장애가 전파된 적이 있거든요." 사람 신입 엔지니어는 이 말을 코드 리뷰나 복도 대화에서 한 번 듣고 나면 다음부터 알아서 지킨다. 그런데 코딩 에이전트에게는 이 맥락이 전달될 경로 자체가 없다. 에이전트는 리포지터리에 쓰여 있는 것만 보고, PR 코멘트에서 사람이 "왜 그렇게 짰냐"고 물으면 그제야 자기가 깬 규칙을 알게 된다. 2026년 5월 한 엔지니어링 블로그가 정리한 문제의식이 정확히 이것이다 — 에이전트는 대화나 암묵지로 맥락을 흡수하지 못하므로, 아키텍처 결정은 **글로 남아 에이전트가 읽을 수 있는 곳**에 있어야만 지켜진다.

이 문제를 푸는 도구로 다시 주목받는 것이 Architecture Decision Record(ADR)다. ADR 자체는 새로운 개념이 아니지만, "누가 읽는가"의 답이 사람 엔지니어에서 코딩 에이전트로 넓어지면서 ADR을 어디에 두고 어떻게 노출할지가 다시 설계 문제가 됐다. 단순히 "ADR을 쓰자"가 아니라, 그 ADR을 에이전트의 작업 흐름 어느 지점에 강제로 끼워 넣을 것인가 — 이게 지금 팀이 실제로 내려야 하는 판단이다.

## 핵심 개념 1 — 전달 경로: Git에 둘 것인가, MCP 서버로 노출할 것인가

ADR을 에이전트에게 전달하는 방식은 크게 두 갈래로 갈린다.

| 방식 | 구조 | 강점 | 약점 |
|---|---|---|---|
| Git 저장소에 Markdown으로 보관 | `docs/adr/0001-xxx.md` 형태로 코드와 같은 리포에 커밋 | 버전 관리·리뷰·diff가 코드와 동일하게 적용됨 | 아키텍처가 여러 서비스·리포에 걸치면 어디에 둘지 애매해짐 |
| MCP 서버로 노출 | 위키·내부 시스템에 흩어진 ADR을 MCP 툴로 질의 가능하게 래핑 | 여러 리포·여러 소스에 흩어진 결정을 한 지점에서 검색 가능 | 서버 운영·인증 등 인프라 오버헤드가 추가됨 |

2026년 5월 Benjamin Cane의 분석은 이 둘을 대립이 아니라 **데이터가 어디 있는가에 따른 선택**으로 본다. ADR이 위키나 여러 시스템에 흩어져 있다면 MCP 서버가 적합하고, 아키텍처가 대체로 한 리포 안에서 완결된다면 Git과 Markdown만으로 충분하며 버전 관리·리뷰 측면에서 오히려 더 깔끔하다. "MCP가 최신 기술이니 무조건 MCP로"가 아니라, 지금 ADR이 실제로 흩어져 있는 정도를 먼저 진단하는 것이 순서다.

## 핵심 개념 2 — 전체 개발 흐름에서의 위치: 생성, 참조, 강제

ADR을 에이전트 워크플로에 끼워 넣는 지점은 한 곳이 아니라 세 곳이다.

<img src="/assets/images/posts/2026-10-14-coding-agent-adr-architectural-context-1.svg" alt="에이전트가 작업을 시작할 때 ADR 저장소를 참조하고, 작업 중 새로운 아키텍처 결정이 생기면 ADR 초안을 제안하며, PR 머지 전 게이트가 변경 사항을 기존 ADR과 대조해 위반 여부를 확인하는 세 지점의 순환 구조도" style="width:100%;">

1. **참조(Context)**: 작업을 시작하기 전 에이전트가 관련 ADR을 읽어 제약을 파악하는 지점. Git 기반이든 MCP 기반이든 여기서 "이미 결정된 것"을 주입한다.
2. **생성(Authoring)**: 에이전트가 작업 중 새로운 아키텍처 결정을 내리면, 그 결정을 자신이 왜 그렇게 했는지와 함께 ADR 초안으로 남기게 하는 지점. 일부 도구는 MADR 템플릿에 "어떤 모델이 이 결정을 제안했는가"를 기록하는 Agent Context 섹션을 추가로 두자고 제안한다.
3. **강제(Gating)**: PR 머지 전에 변경 사항이 기존 ADR을 위반하는지, 혹은 새 아키텍처 결정이 생겼는데 ADR 없이 넘어가려 하는지를 자동으로 점검하는 지점. 2026년 3월 사례에서는 GitHub Copilot을 리뷰어로 붙여 `docs/adr/`의 결정과 어긋나는 PR을 실제로 거부시키는 실험이 보고됐다.

세 지점 중 하나라도 빠지면 ADR은 "쓰여 있지만 아무도 안 읽는 문서"로 되돌아간다. 특히 강제 지점이 없으면, 참조는 에이전트가 운 좋게 관련 ADR을 찾아 읽었을 때만 작동하는 희망적 설계에 그친다.

## 선택의 트레이드오프

| 팀 상황 | 권장 설계 | 이유 |
|---|---|---|
| 모노레포, ADR이 한 곳에 몰려 있음 | Git + 머지 전 린트 스크립트 | 추가 인프라 없이 시작 가능 |
| 폴리레포, 위키에 ADR 산재 | MCP 서버로 통합 질의 | 에이전트가 여러 소스를 수동으로 뒤지지 않아도 됨 |
| 아키텍처 변경 빈도가 낮은 안정적 서비스 | 참조만 하고 강제 게이트는 생략 | 게이트 운영 비용 대비 위반 빈도가 낮음 |
| AI 에이전트가 PR의 상당 비중을 생성 | 강제 게이트 필수 | 사람 리뷰어가 매번 아키텍처 위반을 잡아내기 어려움 |
| ADR 자체가 아직 거의 없는 팀 | ADR 작성 관행부터 정착 | 도구를 먼저 들여도 채울 콘텐츠가 없으면 무의미 |

흔한 함정은 두 가지다. 하나는 "일단 MCP 서버부터 만들자"며 ADR 자체가 몇 개 없는 상태에서 인프라부터 구축하는 것 — 참조할 결정이 없으면 서버는 빈 껍데기다. 다른 하나는 참조 지점만 만들고 강제 게이트를 생략하는 것 — 에이전트가 ADR을 "읽을 수는 있지만 안 읽어도 아무 일도 안 생기는" 상태에 머문다.

## 실무 설정 예제

```yaml
# .github/workflows/adr-gate.yml — PR 머지 전 ADR 위반 점검
name: ADR Compliance Check
on: pull_request
jobs:
  check-adr:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Diff 변경분을 ADR과 대조해 위반 여부 점검
        run: |
          # 변경된 파일이 docs/adr/의 결정과 상충하는지
          # 코딩 에이전트(리뷰어 역할)에게 diff + ADR 목록을 함께 전달해 판정받는다
          agent-review --context docs/adr/ --diff "$(git diff origin/main...HEAD)"
```

## 실제 프로젝트 진행 순서

1. **먼저 ADR이 몇 개나 있고 어디 흩어져 있는지 집계한다.** 위키, Confluence, 각 리포의 README에 흩어진 결정을 한 번 모아보는 것 자체가 MCP냐 Git이냐를 결정하는 데이터가 된다.
2. **흩어진 정도가 낮다면 Git + Markdown으로 먼저 시작한다.** 인프라 투자 없이 참조 지점부터 검증할 수 있다.
3. **에이전트가 실제로 ADR을 참조하는지 먼저 확인한다.** 참조 지점이 작동하지 않는데 강제 게이트부터 만들면, 게이트가 계속 오탐·누락을 일으켜 신뢰를 잃는다.
4. **참조가 안정화된 뒤에만 머지 전 게이트를 추가한다.** 처음엔 경고만 띄우는 소프트 게이트로 시작해, 오탐률이 낮아진 뒤 실제 차단으로 승격한다.

## 마무리 요약

- 코딩 에이전트는 사람처럼 대화나 암묵지로 아키텍처 맥락을 흡수하지 못하므로, 결정은 글로 남아 에이전트가 읽을 수 있는 경로에 있어야 한다.
- ADR 전달은 Git이냐 MCP냐의 기술 선택이 아니라, 지금 ADR이 얼마나 흩어져 있는가에 따라 달라지는 진단의 결과다.
- 참조·생성·강제라는 세 지점 중 강제 게이트가 빠지면 ADR은 "쓰여 있지만 안 지켜지는 문서"로 되돌아간다.
