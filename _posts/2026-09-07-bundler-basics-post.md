## 파일이 수백 개인데 브라우저는 어떻게 읽나

모던 웹 프로젝트는 수십~수백 개의 JS·CSS 파일과 `import`로 얽힌 의존성으로 이뤄진다. 이걸 브라우저가 하나하나 요청하면 느리고, 옛 브라우저는 `import` 문법을 이해하지 못하기도 한다. **번들러(bundler)**는 이 흩어진 파일들을 의존성 순서대로 묶고 변환해, 브라우저가 바로 실행할 수 있는 소수의 파일로 만들어준다.

## 번들러가 하는 일

| 작업 | 설명 |
|---|---|
| 번들링 | 여러 모듈을 의존성 따라 하나(또는 몇 개)로 합침 |
| 트랜스파일 | 최신 문법·TypeScript를 구형 브라우저용 JS로 변환 |
| 최소화(Minify) | 공백·주석 제거로 파일 크기 축소 |
| 코드 분할 | 필요한 부분만 나중에 로드(lazy loading) |
| 에셋 처리 | 이미지·CSS도 함께 처리 |

## 대표적인 번들러

```text
webpack: 오랫동안 표준. 강력하지만 설정이 복잡
Vite:    개발 중엔 네이티브 ESM으로 빠르고, 배포 시 Rollup으로 번들
esbuild: Go로 작성돼 매우 빠름 (다른 도구의 내부 엔진으로도 쓰임)
Rollup:  라이브러리 번들링에 강점
```

최근 신규 프로젝트는 개발 서버가 빠른 Vite를 많이 택한다. webpack은 여전히 널리 쓰이지만 설정 복잡도가 높은 편이다.

## 왜 개발 서버가 빠르고 느린 차이가 나나

```text
전통적 번들러(webpack): 개발 서버 시작 시 전체를 번들링
-> 프로젝트가 크면 시작이 느려짐

Vite: 개발 중엔 번들링 없이 브라우저의 네이티브 ESM을 그대로 사용
-> 시작이 거의 즉시, 변경된 모듈만 갱신
```

## 실무 포인트

- **번들러 설정을 직접 만질 일은 프레임워크가 많이 줄여준다.** Next.js·Vite 템플릿 등은 번들러 설정을 대부분 알아서 해주므로, 초보자가 처음부터 webpack 설정을 익힐 필요는 없다. 필요할 때 조금씩 배우면 된다.
- **번들 크기를 주기적으로 확인하라.** 무심코 큰 라이브러리를 import하면 번들이 커져 로딩이 느려진다. 번들 분석 도구로 무엇이 크기를 차지하는지 확인하고, 트리 셰이킹(안 쓰는 코드 제거)이 잘 되는지 점검하는 것이 좋다.
- **코드 분할로 초기 로딩을 줄여라.** 첫 화면에 필요 없는 코드까지 한 번에 내려받으면 초기 로딩이 느리다. 라우트별·기능별로 코드를 나눠 필요할 때 로드하면 첫 화면이 빨라진다.

## 마무리 요약

- 번들러는 흩어진 여러 모듈을 의존성 순서대로 묶고 변환해 브라우저가 실행할 수 있는 파일로 만든다.
- 번들링·트랜스파일·최소화·코드 분할 등을 담당하며 webpack·Vite·esbuild가 대표적이다.
- 프레임워크가 설정을 많이 대신해주므로, 번들 크기 확인과 코드 분할 정도만 신경 써도 충분하다.
