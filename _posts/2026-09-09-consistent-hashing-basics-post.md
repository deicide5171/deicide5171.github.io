## 서버를 늘렸더니 캐시가 다 날아갔다

데이터를 여러 서버에 나눌 때 흔히 `해시값 % 서버수`로 위치를 정한다. 그런데 서버를 3대에서 4대로 늘리면 **나누는 수가 바뀌어 거의 모든 키의 위치가 달라진다.** 캐시라면 전부 무효화되어 DB로 요청이 몰린다. **일관된 해싱(consistent hashing)**은 서버가 늘거나 줄어도 **영향받는 키를 최소화**하는 방법이다.

## 단순 나머지 방식의 문제

| 서버 수 | key=100의 위치 (100 % N) |
|---|---|
| 3대 | 100 % 3 = 1번 서버 |
| 4대 | 100 % 4 = 0번 서버 |

이렇게 서버 수만 바뀌어도 대부분 키가 다른 서버로 옮겨간다. 대규모 캐시에선 재앙이다.

## 링(ring)으로 생각하기

```text
0 ~ 최대값을 원형(링)으로 배치한다.
서버들도 링 위 한 지점에 놓는다.
키는 자기 위치에서 시계방향으로 가장 가까운 서버에 저장된다.

서버 하나가 빠지면 -> 그 서버가 맡던 키만 다음 서버로 이동
나머지 키는 그대로 유지된다.
```

핵심은 서버 추가·제거 시 **인접 구간의 키만 이동**하고 나머지는 건드리지 않는다는 것이다.

## 실무 포인트

- **가상 노드(virtual node)로 쏠림을 막는다.** 서버를 링에 하나씩만 두면 특정 서버에 키가 몰릴 수 있다. 서버 하나를 여러 가상 지점으로 흩뿌리면 부하가 고르게 분산된다.
- **캐시·분산 저장소에서 널리 쓰인다.** Redis 클러스터, 카산드라, DynamoDB, CDN 등 데이터를 여러 노드에 나누는 시스템의 기본 기법이다. 직접 구현하기보다 이런 시스템이 내부적으로 해준다.
- **완벽한 균등 분배는 아니다.** 가상 노드를 써도 약간의 불균형은 남는다. 노드 수와 가상 노드 개수를 조절해 허용 범위 안으로 맞춘다.

## 마무리 요약

- 단순 `해시 % 서버수`는 서버 수가 바뀌면 거의 모든 키가 이동해 캐시가 무너진다.
- 일관된 해싱은 키와 서버를 원형 링에 놓아, 서버 변화 시 인접 키만 이동하게 한다.
- 가상 노드로 쏠림을 줄이며, Redis 클러스터·카산드라 등 분산 시스템의 기본 기법이다.
