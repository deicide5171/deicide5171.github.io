## 왜 프롬프트만으로는 구조를 보장할 수 없는가

에이전트 파이프라인에서 LLM의 출력을 다음 단계 코드가 그대로 파싱해야 하는 경우, JSON 스키마 위반 하나가 전체 파이프라인을 멈춘다. 시스템 프롬프트에 "반드시 유효한 JSON만 출력하라"고 아무리 강하게 지시해도, 이는 모델에게 그렇게 하라고 **부탁**하는 것일 뿐 강제하는 것이 아니다. 모델은 여전히 다음 토큰을 확률 분포에서 샘플링하므로, 드물게 스키마를 깨는 토큰(설명 문장, 따옴표 누락, 잘못된 콤마)이 선택될 여지가 항상 남는다. 제약 디코딩(constrained decoding)은 이 문제를 프롬프트 레벨이 아니라 **토큰 생성 단계 자체**에서 해결한다. 스키마를 위반하는 토큰은 아예 선택될 확률을 0으로 만들어버리는 것이다.

## 핵심 개념 1 — 유한 오토마타로 스키마를 표현하기

Outlines, xgrammar, llguidance 같은 라이브러리의 핵심 아이디어는 JSON 스키마(또는 정규식, 컨텍스트 프리 문법)를 **유한 상태 오토마타(FSM)**나 푸시다운 오토마타로 컴파일하는 것이다. 예를 들어 `{"name": string, "age": number}`라는 스키마는 "여는 중괄호 → `"name"` 문자열 리터럴 → 콜론 → 문자열 값 → 콤마 → `"age"` → 콜론 → 숫자 값 → 닫는 중괄호"라는 정확한 상태 전이 그래프로 표현된다. 디코딩이 진행되는 매 스텝마다, 현재 오토마타 상태에서 허용되는 다음 문자(또는 토큰)가 무엇인지 계산할 수 있다.

## 핵심 개념 2 — 로짓 마스킹으로 샘플링을 강제하기

모델이 다음 토큰의 확률 분포(로짓)를 계산하면, 제약 디코딩 엔진은 현재 FSM 상태에서 **문법적으로 불가능한 토큰들의 로짓을 -∞로 마스킹**한다. 이렇게 하면 softmax 이후 그 토큰들의 확률은 정확히 0이 되어, 온도(temperature)나 top-p 같은 샘플링 전략과 무관하게 절대 선택되지 않는다. 어려운 부분은 이 작업이 토큰 단위가 아니라 문자(바이트) 단위로 정의된 문법을, LLM의 서브워드 토크나이저 어휘와 맞춰야 한다는 점이다. 하나의 토큰이 여러 문자에 걸치거나 문법 경계를 가로지를 수 있어서, 효율적인 구현은 어휘 전체를 미리 순회해 각 FSM 상태별로 허용되는 토큰 집합을 캐싱해두는 전처리(컴파일) 단계를 거친다. xgrammar 같은 최신 구현은 이 전처리를 CPU에서 GPU 디코딩과 겹쳐 실행해 오버헤드를 거의 0에 가깝게 만든다.

| 방식 | 강제력 | 성능 오버헤드 | 표현 가능한 구조 |
|---|---|---|---|
| 프롬프트 지시("JSON만 출력") | 없음(확률적 준수) | 없음 | 제한 없음(위반 가능) |
| 출력 후 검증·재시도 | 사후적(실패 시 재요청) | 재시도 비용 | 검증 가능한 모든 구조 |
| 제약 디코딩(FSM 로짓 마스킹) | 100%(구조적으로 불가능) | 낮음(사전 컴파일로 상쇄) | 정규식/CFG로 표현 가능한 구조 |

## 코드 예제 — Outlines로 Pydantic 스키마 강제하기

```python
import outlines
from pydantic import BaseModel

class Extraction(BaseModel):
    name: str
    age: int
    is_active: bool

model = outlines.models.transformers("meta-llama/Llama-3.1-8B-Instruct")
generator = outlines.generate.json(model, Extraction)

# 생성된 문자열은 파싱 실패 가능성 없이 항상 Extraction 스키마를 만족한다
result = generator("이름은 김민준, 32세, 활성 사용자입니다.")
print(result.name, result.age, result.is_active)
```

## 실무 포인트

- **문법이 복잡할수록 사전 컴파일 비용이 커진다.** 매우 깊게 중첩된 스키마나 재귀적 구조는 FSM 상태 공간이 커져 초기 컴파일 시간이 늘어날 수 있으므로, 자주 쓰는 스키마는 컴파일 결과를 캐싱해 재사용하는 것이 좋다.
- **문법적으로 유효해도 의미적으로 틀릴 수 있다.** 제약 디코딩은 "형식"을 보장할 뿐 "내용"의 정확성을 보장하지 않는다. 스키마는 지켰지만 존재하지 않는 필드값을 채워 넣는 환각은 여전히 별도의 검증이 필요하다.
- **서빙 엔진 통합 여부를 확인하라.** vLLM, SGLang, TGI 등 주요 서빙 엔진은 각각 xgrammar나 자체 구현으로 제약 디코딩을 지원하지만, 지원하는 문법 표현력(정규식만/전체 JSON Schema/임의 CFG)이 엔진마다 다르므로 실제 사용할 스키마 복잡도에 맞는 엔진을 선택해야 한다.

## 마무리 요약

- 프롬프트로 구조를 요청하는 것은 확률적 준수일 뿐이며, 제약 디코딩은 토큰 생성 단계에서 문법 위반 토큰의 확률을 0으로 만들어 구조를 구조적으로 강제한다.
- JSON 스키마나 정규식을 FSM으로 컴파일하고, 매 디코딩 스텝마다 허용된 토큰만 남기는 로짓 마스킹으로 100% 유효한 출력을 보장한다.
- 형식의 정확성은 보장되지만 내용의 사실성은 보장되지 않으므로, 여전히 후처리 검증이 함께 필요하다.
