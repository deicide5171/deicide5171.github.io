## 왜 지금 이 구분이 필요한가

"여행 예약 에이전트 하나 만들어서, 항공사·호텔·렌터카 예약을 한 번에 처리하게 해주세요." 이런 요구사항을 받으면 초기에는 대부분 MCP 서버를 늘리는 방식으로 접근한다. 항공사 API를 MCP 도구로 감싸고, 호텔 API도 MCP 도구로 감싸는 식이다. 문제는 항공사·호텔·렌터카 회사가 각각 자기 시스템 내부에 이미 자율적인 예약 에이전트를 운영하고 있을 때 발생한다. 그들은 자기 내부 로직(재고, 취소 정책, 가격 협상)을 API 스펙으로 전부 공개하지 않는다. 이 시점에서 "도구를 호출한다"는 모델 자체가 깨진다.

2026년 들어 이 문제에 대한 업계 합의가 사실상 굳어졌다. MCP는 다운로드 9,700만 건을 넘기며 에이전트-도구 계층(Layer 1)을 사실상 장악했고, Google이 만들어 리눅스 재단으로 이관한 A2A(Agent2Agent) 프로토콜은 AWS·Cisco·Microsoft·Salesforce·SAP·ServiceNow 등 150개 이상 조직의 지지를 받으며 에이전트-에이전트 위임 계층(Layer 2)의 표준으로 자리잡았다. 두 프로토콜은 경쟁 관계가 아니라 스택의 서로 다른 층이라는 것이 2026년 기준 정리된 그림이다. 빌더 입장에서 중요한 것은 이 둘을 언제 나눠 써야 하는가를 설계 초기에 판단하는 일이다.

## 요구사항을 기술 문제로 번역하기

기획자의 "예약을 한 번에 처리해주세요"라는 말은 실제로 두 가지 전혀 다른 상호작용을 뭉쳐서 표현한 것이다.

- **내가 소유·신뢰하는 자원에 대한 접근**: 사내 재고 DB 조회, 결제 게이트웨이 호출, 사내 캘린더 등록. 이건 "함수를 호출한다"에 가깝다. 스펙을 내가 정의하고, 신뢰 경계 안에서 동기적으로 처리된다.
- **내가 소유하지 않은 자율 에이전트에 대한 업무 위임**: 항공사 에이전트에게 "이 조건에 맞는 좌석을 찾아서 홀드해달라"고 요청하는 것. 상대 에이전트가 내부적으로 무엇을 하는지 나는 모른다. 상대는 승인이 필요할 수도 있고, 비동기로 응답할 수도 있고, 협상 과정에서 대안을 제시할 수도 있다.

이 두 상호작용을 같은 프로토콜로 처리하려 하면 문제가 생긴다. MCP로 항공사 API를 억지로 감싸면, 항공사 쪽 내부 상태(좌석 홀드 만료, 가격 변동, 재승인 요청)를 실시간으로 반영하기 어렵고, 항공사가 API 스펙을 바꿀 때마다 내 MCP 서버도 같이 깨진다. 반대로 사내 결제 게이트웨이 호출까지 A2A로 처리하면 불필요한 협상·핸드셰이크 오버헤드가 붙는다.

## 전체 시스템에서의 위치

아래 구조도는 오케스트레이터 에이전트를 기준으로 두 계층이 어떻게 갈라지는지 보여준다. 왼쪽은 MCP로 연결되는 "내 소유 자원", 오른쪽은 A2A로 연결되는 "타 조직 자율 에이전트"다.

<img src="/assets/images/posts/2026-09-30-mcp-a2a-protocol-layer-separation-1.svg" alt="MCP와 A2A의 역할 분리 구조도" style="width:100%;">

A2A 쪽에서 핵심 개념은 **Agent Card**다. 상대 에이전트가 무엇을 할 수 있는지, 어떤 입력을 받는지, 인증은 어떻게 하는지를 선언한 메타데이터 문서로, 마치 OpenAPI 스펙이 REST API의 계약이듯 Agent Card가 에이전트 위임의 계약 역할을 한다. 오케스트레이터는 이 카드를 보고 "이 작업을 이 에이전트에게 맡길 수 있는가"를 판단한 뒤 태스크를 생성하고, 상대 에이전트는 자기 페이스로 작업을 수행하다가 상태를 업데이트해 돌려준다.

## 선택의 트레이드오프

| 기준 | MCP (Layer 1) | A2A (Layer 2) |
|---|---|---|
| 관계 | 내가 소유·신뢰하는 자원 | 내가 소유하지 않은 자율 에이전트 |
| 상호작용 모델 | 함수 호출에 가까움, 대체로 동기적 | 태스크 위임, 비동기·장기 실행 허용 |
| 스펙 소유권 | 내가 도구 스펙을 정의 | 상대가 Agent Card로 자기 능력을 선언 |
| 신뢰 경계 | 조직 내부 | 조직 간 |
| 실패 처리 | 재시도, 타임아웃 위주 | 협상 실패, 거부, 대안 제시까지 고려 |
| 대표 사례 | 사내 DB 조회, 결제 API, 내부 캘린더 | 파트너사 예약 에이전트, 외부 조사 에이전트 위임 |

한 가지 함정은 "일단 다 MCP로 시작해서 나중에 필요하면 A2A로 옮기면 되지 않나"라는 생각이다. 실제로는 초기부터 어떤 상호작용이 "내가 통제할 수 있는 함수 호출"이고 어떤 것이 "상대의 자율성을 전제한 위임"인지 구분해두지 않으면, MCP 서버가 우후죽순으로 늘어나면서 각 서버가 실질적으로는 외부 조직의 비동기 워크플로우를 동기 호출처럼 흉내 내는 안티패턴이 굳어진다. 반대로 사내 시스템까지 전부 A2A 태스크로 감싸면 불필요한 프로토콜 오버헤드와 보안 표면만 늘어난다. A2ABreak 같은 보안 연구가 지적하듯, A2A는 조직 경계를 넘나드는 만큼 인증·권한 위임(이 부분은 앞서 다룬 에이전트 신원·위임 권한 설계와 직접 맞닿는다)과 거버넌스를 처음부터 설계에 넣어야 하는 계층이다.

## 실제 프로젝트 진행 순서

1. **경계부터 그린다.** 요구사항에 등장하는 모든 연동 지점을 "내가 소유한 자원인가, 타 조직 자율 에이전트인가"로 먼저 분류한다. 이 분류표가 이후 프로토콜 선택의 기준이 된다.
2. **MCP로 내부 도구를 먼저 정리한다.** 사내 DB, 결제, 캘린더 같은 확실한 Layer 1 자원부터 MCP 서버로 노출한다. 여기서 도구 스키마·에러 처리 관례를 팀 표준으로 굳힌다.
3. **위임이 필요한 지점을 식별한다.** 외부 파트너와의 연동 중 "상대가 비동기로 작업하고, 중간에 승인·협상이 끼어들 수 있는가"를 기준으로 A2A 후보를 추린다.
4. **Agent Card와 인증 모델을 먼저 설계한다.** 태스크 정의보다 먼저 "누구에게 어디까지 위임 권한을 줄 것인가"를 결정한다. 여기서 앞서 다룬 위임 토큰 교환(RFC 8693) 구조가 그대로 재사용된다.
5. **오케스트레이터에 라우팅 로직을 넣는다.** 요청이 들어오면 MCP 도구 호출로 처리할지, A2A 태스크로 위임할지 판단하는 계층을 명시적으로 둔다. 이 라우팅 로직 자체가 이 시스템의 핵심 설계 자산이 된다.

## 마무리

- MCP는 "내가 신뢰하는 자원에 대한 함수 호출", A2A는 "내가 통제하지 않는 자율 에이전트에 대한 업무 위임"이다.
- 두 계층을 처음부터 구분해두지 않으면 MCP 서버가 비동기 워크플로우를 흉내 내는 안티패턴이 굳어진다.
- A2A를 쓰기로 했다면 태스크 설계보다 Agent Card·인증·위임 권한 모델을 먼저 확정해야 한다.
