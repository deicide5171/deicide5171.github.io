## 왜 API 키를 코드에 그냥 쓰면 안 되나

DB 비밀번호나 API 키를 코드에 직접 적어두면 편하지만, 그 코드를 GitHub에 올리는 순간 전 세계에 비밀번호가 공개된다. 실제로 공개 저장소에 올라간 API 키를 봇이 몇 분 만에 발견해 악용하는 사고가 흔하다. **환경변수**는 이런 민감한 설정값을 코드 밖으로 분리해, 코드는 그대로 두고 환경마다 다른 값을 주입하는 방식이다.

## 환경변수를 쓰는 이유

| 이유 | 설명 |
|---|---|
| 보안 | 비밀번호·키를 코드와 분리해 유출 위험 감소 |
| 환경 분리 | 개발·스테이징·운영마다 다른 값 사용 |
| 유연성 | 코드 수정·재배포 없이 설정만 변경 가능 |

## .env 파일 기본 사용법

```bash
# .env 파일 (프로젝트 루트에 두고 git에는 올리지 않는다)
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
API_KEY=sk-abc123
NODE_ENV=development
```

```javascript
// Node.js에서 읽기 (dotenv 라이브러리)
import 'dotenv/config';
const apiKey = process.env.API_KEY;
```

## 초보자가 자주 하는 실수

```text
1. .env를 git에 커밋해버림
   -> .gitignore에 .env를 반드시 추가! 이미 올렸다면 키를 즉시 폐기·재발급

2. .env.example을 안 만듦
   -> 실제 값 대신 키 이름만 담은 .env.example을 커밋해두면
      팀원이 어떤 환경변수가 필요한지 알 수 있다

3. 프론트엔드 환경변수에 비밀 키를 넣음
   -> 프론트엔드 빌드 결과물은 브라우저에서 다 보인다.
      프론트에 넣은 "환경변수"는 비밀이 아니다!

4. 배포 환경에 환경변수 등록을 빼먹음
   -> 로컬 .env는 배포 서버에 올라가지 않는다.
      서버·CI의 환경변수 설정에 따로 등록해야 한다
```

## 실무 포인트

- **`.env`는 이미 한 번 커밋되면 git 히스토리에 영구히 남는다.** `.gitignore`에 뒤늦게 추가해도 과거 커밋에는 그대로 남아있으므로, 실수로 올렸다면 파일을 지우는 것으로 끝내지 말고 그 안의 키를 반드시 폐기·재발급해야 한다.
- **운영 환경에서는 .env 파일보다 시크릿 관리 서비스를 검토하라.** AWS Secrets Manager, Vault 같은 도구는 키를 암호화 저장하고 접근 권한과 교체 주기를 관리해준다.
- **프론트엔드의 "환경변수"는 빌드 시점에 코드에 박혀 공개된다.** API 키처럼 진짜 비밀이 필요한 작업은 반드시 백엔드를 거치도록 설계해야 한다.

## 마무리 요약

- 환경변수는 비밀번호·API 키 같은 민감 설정을 코드 밖으로 분리해 유출을 막고 환경별로 다른 값을 쓰게 한다.
- `.env`는 반드시 `.gitignore`에 넣고, 키 이름만 담은 `.env.example`을 대신 공유하는 것이 관례다.
- 프론트엔드 환경변수는 비밀이 아니며, 실수로 커밋한 키는 삭제가 아니라 즉시 폐기·재발급해야 한다.
