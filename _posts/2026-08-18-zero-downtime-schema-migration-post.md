## 왜 지금 이 이야기인가

서비스가 커질수록 스키마는 초기 설계와 점점 멀어진다. 컬럼 이름이 어색해지고, 타입이 부족해지고, 정규화 방향을 바꿔야 하는 순간이 온다. 문제는 "그냥 `ALTER TABLE`을 돌리면 되지 않나"라는 생각이 통하지 않는 규모에 도달했을 때다. 큰 테이블에 컬럼을 추가하거나 이름을 바꾸는 순간 테이블 전체에 락이 걸릴 수 있고, 애플리케이션 코드는 스키마가 바뀐 그 순간에 딱 맞춰 배포될 수 없다. 배포는 순차적으로 굴러가고, 그 사이 구버전 코드와 신버전 코드가 동시에 같은 테이블을 바라보는 시간이 반드시 존재한다.

이 문서는 이미 이 블로그에서 다룬 샤딩·리샤딩의 "데이터 이동" 문제와는 결이 다르다. 여기서 다루는 것은 데이터를 옮기는 문제가 아니라, **스키마 자체를 안전하게 바꾸는 절차**다. 컬럼 추가·삭제·이름 변경·타입 변경처럼 단일 테이블 안에서 일어나는 변경을, 서비스를 멈추지 않고 롤백 가능한 상태를 유지하면서 어떻게 진행하는지가 핵심이다.

## 핵심 개념 1: Expand-Contract 패턴

**Expand-Contract**(확장-축소)는 스키마 변경을 한 번의 배포가 아니라 여러 단계로 쪼개는 패턴이다. 핵심 아이디어는 "스키마 변경"과 "애플리케이션 배포"가 원자적으로 동시에 일어날 수 없다는 전제를 받아들이고, 그 사이 어떤 시점에도 구버전·신버전 애플리케이션이 모두 정상 동작하도록 스키마를 설계하는 것이다.

| 단계 | 하는 일 | 위험 요소 |
|---|---|---|
| Expand(확장) | 기존 컬럼은 그대로 두고 새 컬럼·테이블을 추가만 한다 | 대용량 테이블에 짧은 락이라도 걸릴 수 있어 저트래픽 시간대 권장 |
| Migrate(이행) | 애플리케이션이 신·구 컬럼에 동시에 쓰고(dual write), 배치로 과거 데이터를 백필한다 | 배치가 너무 크면 락 경합·복제 지연 발생 |
| Contract(축소) | 검증이 끝난 뒤 신규 컬럼만 쓰도록 전환하고, 옛 컬럼을 제거한다 | 되돌릴 수 없는 단계이므로 충분한 관찰 기간 필요 |

세 단계 모두 "스키마 변경"과 "코드 배포"가 분리되어 있다는 점이 중요하다. 스키마는 항상 코드보다 한 걸음 먼저 움직이고, 코드는 이전 스키마와 이후 스키마 양쪽을 다 이해할 수 있는 상태를 거쳐야 한다.

## 핵심 개념 2: 변경 유형별 위험도

모든 스키마 변경이 똑같이 위험한 것은 아니다. 변경 유형에 따라 락 범위와 서비스 영향이 크게 달라진다.

| 변경 유형 | 위험도 | 이유 |
|---|---|---|
| 컬럼 추가(NULL 허용, DEFAULT 없음) | 낮음 | 대부분의 RDBMS에서 메타데이터만 바뀌고 테이블 재작성이 필요 없다 |
| 컬럼 추가(NOT NULL + DEFAULT) | 중간~높음 | 엔진·버전에 따라 기존 행 전체를 다시 써야 할 수 있다 |
| 컬럼 삭제 | 중간 | 삭제 직후 구버전 코드가 남아있다면 즉시 오류로 이어진다 |
| 컬럼 이름 변경 | 높음 | 이름 변경은 사실상 "삭제+추가"와 같아서 애플리케이션과 스키마의 동시성 문제가 가장 크다 |
| 인덱스 추가 | 중간 | 인덱스 생성 방식에 따라 쓰기 잠금 여부가 갈린다(온라인 인덱스 빌드 옵션 확인 필요) |

이름 변경이 가장 위험하다고 표시한 이유는, 이름을 바꾸는 순간 옛 이름을 참조하던 코드가 즉시 깨지기 때문이다. 그래서 실무에서는 "이름 변경"을 그대로 실행하지 않고, 항상 Expand-Contract로 풀어서 "새 이름 컬럼 추가 → 이행 → 옛 이름 컬럼 삭제"로 바꾼다.

## 예제: 컬럼 이름 변경을 Expand-Contract로 처리하기

`name` 컬럼을 `full_name`으로 바꾸는 상황을 가정한다. `ALTER TABLE ... RENAME COLUMN`을 한 번에 실행하면 배포 타이밍이 어긋나는 순간 구버전 코드가 즉시 에러를 낸다. 대신 아래처럼 나눈다.

```sql
-- 1단계 Expand: 새 컬럼만 추가 (NULL 허용, 짧은 락)
ALTER TABLE users ADD COLUMN full_name VARCHAR(255);

-- 2단계 Migrate: 과거 데이터 백필 (한 번에 전체를 돌리지 않고 배치로 나눈다)
UPDATE users
SET full_name = name
WHERE full_name IS NULL
  AND id BETWEEN :batch_start AND :batch_end;
```

배치를 나누는 이유는 대량 UPDATE가 테이블 전체를 잠그거나 트랜잭션 로그를 폭증시켜 복제 지연을 유발할 수 있기 때문이다. 애플리케이션 레이어에서는 이 기간 동안 두 컬럼에 동시에 쓰는 dual write 로직이 필요하다.

```java
// 애플리케이션 v2: 이행 기간 동안 두 컬럼에 동시 저장
public void updateUserName(Long userId, String newName) {
    userRepository.updateNameAndFullName(userId, newName, newName);
    // name, full_name 두 컬럼 모두 갱신 — 어느 한쪽만 읽는 코드가 있어도 안전
}
```

백필이 끝나고 두 컬럼 값이 100% 일치함을 확인한 뒤에야 3단계로 넘어간다.

```sql
-- 3단계 Contract: 검증 완료 후 옛 컬럼 제거
ALTER TABLE users DROP COLUMN name;
```

## 실무 포인트

- **단계마다 독립적으로 롤백 가능해야 한다.** Expand 단계는 컬럼을 추가만 하므로 언제든 되돌릴 수 있다. 반대로 Contract 단계(컬럼 삭제)는 사실상 되돌릴 수 없으므로, 삭제 전 반드시 실제 트래픽으로 신규 컬럼만 사용해보는 관찰 기간을 둬야 한다.
- **배치 백필은 크기와 속도를 제한한다.** 한 트랜잭션에 너무 많은 행을 담으면 락 경합과 복제 지연이 커진다. 배치 크기, 배치 간 대기 시간을 조절 가능하게 만들어두는 편이 안전하다.
- **대용량 테이블의 컬럼 추가·인덱스 생성은 온라인 DDL 도구를 검토한다.** MySQL 계열은 `pt-online-schema-change`나 `gh-ost` 같은 온라인 스키마 변경 도구가, PostgreSQL은 버전별 락 동작 차이(예: 상수 DEFAULT를 갖는 컬럼 추가가 메타데이터 변경만으로 끝나는 개선)가 존재하므로, 사용 중인 DB 엔진·버전의 공식 문서로 락 동작을 먼저 확인해야 한다.
- **애플리케이션 배포 순서를 스키마 변경 순서와 맞춘다.** "스키마 먼저, 코드는 그 다음"이 원칙이다. 코드가 스키마보다 먼저 배포되면 존재하지 않는 컬럼을 참조하게 된다.
- **불일치 모니터링을 이행 단계에 반드시 넣는다.** dual write 기간 중 신·구 컬럼 값이 어긋나는 사례가 있다면, 백필 로직이나 애플리케이션 코드에 버그가 있다는 신호다.

## 3줄 요약

- Expand-Contract 패턴은 스키마 변경을 "확장 → 이행(dual write·백필) → 축소" 세 단계로 쪼개, 어느 시점에도 구·신 버전 코드가 동시에 정상 동작하게 만든다.
- 컬럼 이름 변경처럼 위험도가 높은 변경도 "새 컬럼 추가 → 백필·검증 → 옛 컬럼 삭제"로 풀면 무중단으로 처리할 수 있다.
- 축소(Contract) 단계는 되돌리기 어려우므로 충분한 관찰 기간과 불일치 모니터링을 거친 뒤에만 실행해야 한다.
