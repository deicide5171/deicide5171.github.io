## 왜 지금 이 판단이 중요해졌는가

"이 체크리스트 좀 만들어서 팀원들이 같이 체크하게 해주세요"라는 요구는 몇 달 전까지만 해도 명확히 두 단계로 쪼개졌다. AI 에이전트에게 정적 HTML 페이지 하나를 받아 빠르게 프로토타입을 보여주는 단계, 그리고 "이제 진짜로 써야겠다"는 순간 DB·인증·API 서버를 갖춘 풀스택 서비스로 처음부터 다시 만드는 단계. 이 사이에 다리가 없었다.

그런데 최근 Claude의 Artifact(대화 중 즉석에서 생성되는 실행 가능한 페이지)에 런타임 capabilities라는 개념이 추가됐다. 페이지가 단순히 브라우저 안에서만 동작하는 정적 문서가 아니라, 공유 데이터베이스를 선언해 여러 사람이 같은 데이터를 보고 쓰거나, 누가 보고 있는지 식별하거나, 파일을 저장받는 등 백엔드가 하던 일의 일부를 명시적으로 요청할 수 있게 된 것이다. 이건 "AI가 코드를 더 잘 짠다"는 류의 발전이 아니라, 빌더가 "이 요구사항을 프로토타입으로 끝낼지, 백엔드를 갖춘 서비스로 만들지"를 가르는 경계선 자체가 이동했다는 신호다.

## 전체 시스템에서의 위치

정적 Artifact 페이지는 브라우저 하나의 로컬 환경 안에서 완결된다 — 상태가 있다면 그 브라우저의 `localStorage`뿐이고, 다른 사람이 같은 링크를 열어도 서로 다른 데이터를 본다. capabilities를 선언한 페이지는 이 위치가 달라진다. 페이지는 여전히 가볍게 즉석에서 생성되지만, 데이터 읽기·쓰기 요청이 그 페이지를 서빙하는 플랫폼의 공유 저장소를 거치게 되면서, 사실상 "클라이언트 전용 프로토타입"과 "직접 구축한 백엔드를 가진 서비스" 사이에 중간 지점 하나가 새로 생긴 셈이다.

이 중간 지점이 커버하는 범위를 정확히 아는 것이 설계의 핵심이다. 여러 뷰어가 같은 데이터를 보고 쓰는 것, 뷰어를 식별하는 것, 파일을 올리고 받는 것까지는 이 지점이 처리한다. 하지만 복잡한 쿼리, 대용량 데이터, 외부 시스템과의 연동, 세밀한 권한 모델처럼 전통적인 백엔드가 하던 일 전부를 대체하지는 않는다. 그 경계를 넘는 순간부터는 여전히 직접 구축한 서버가 필요하다.

## 선택의 트레이드오프

| 기준 | 정적 Artifact(localStorage) | capabilities 선언 Artifact(공유 상태) | 직접 구축한 풀스택 서비스 |
|---|---|---|---|
| 데이터 공유 범위 | 브라우저 하나로 한정 | 같은 페이지를 보는 모든 뷰어가 공유 | 설계한 대로 완전히 통제 |
| 구축 속도 | 즉시 | 즉시 ~ 수 분 | 수 시간~수 주 |
| 데이터 영속성·용량 | 브라우저 삭제 시 소실, 사실상 무제한 아님 | 플랫폼이 관리, 용량·보존 정책에 제약 | 설계한 대로 완전히 통제 |
| 권한·인증 모델 | 없음 | 제한적(뷰어 식별 수준) | 세밀하게 설계 가능 |
| 복잡한 쿼리·연산 | 불가 | 제한적 | 완전히 가능 |
| 적합한 상황 | 개인용 도구, 일회성 계산기 | 팀 내 소규모 공유 도구, 빠른 검증 | 외부 공개 서비스, 규모가 커질 도구 |

가장 많이 저지르는 실수는 이 중간 지점을 "완성된 백엔드"로 착각하고 그 위에 점점 더 많은 기능을 쌓는 것이다. capabilities는 "이 프로토타입이 실제로 쓸모 있는지 빠르게 검증하는" 용도로 설계된 지점이지, 외부에 공개하는 정식 서비스의 최종 아키텍처가 아니다. 반대로 "어차피 나중에 다시 만들 거니까"라며 처음부터 풀스택으로 시작하면, 애초에 필요했던 건 팀원 세 명이 체크리스트를 같이 보는 정도였는데 과설계가 된다.

## 실제 프로젝트 진행 순서

1. **요구사항에서 "공유가 정말 필요한가"부터 가른다.** 나 혼자 쓰는 도구라면 capabilities 없이 로컬 상태만으로 충분하다. 여러 사람이 같은 데이터를 봐야 한다는 조건이 확인된 뒤에만 다음 단계로 넘어간다.
2. **공유가 필요하다면 capabilities를 선언한 Artifact로 먼저 만든다.** 이 단계에서 실제 사용자가 이 도구를 계속 쓰는지, 어떤 기능이 부족한지를 하루 이틀 안에 검증할 수 있다.
3. **사용량과 데이터가 늘어나는 지점을 지켜본다.** 뷰어 수가 많아지거나, 외부 시스템과 연동해야 하거나, 복잡한 권한 분기가 필요해지는 시점이 바로 전통적 백엔드로 넘어갈 신호다.
4. **그 신호가 오면 마이그레이션 범위를 좁게 잡는다.** 이미 검증된 데이터 모델과 화면 구조가 있으므로, 처음부터 설계하는 것보다 "이 Artifact가 하던 일을 그대로 서버·DB로 옮긴다"는 좁은 범위의 작업이 된다.
5. **민감한 데이터는 애초에 capabilities 단계에 올리지 않는다.** 공유 저장소는 접근 범위가 넓어질 수 있으므로, 개인정보나 내부 기밀이 들어가는 도구는 처음부터 직접 구축한 백엔드로 시작한다.

## 실무 포인트

**"뷰어들이 같은 데이터를 본다"는 것을 처음 여는 사람에게 분명히 알려야 한다.** 공유 저장소 기반 도구는 첫 입력이 다른 사람에게도 보인다는 사실을 모르고 민감한 값을 적어 넣는 사고로 이어지기 쉽다. 이런 도구를 팀에 배포할 때는 이 점을 사용 안내에 명시해야 한다.

**이 중간 지점을 "데모용 샌드박스"로 못 박고 쓰는 것이 안전하다.** 실서비스로 전환할 계획이 없는, 수명이 짧은 팀 내부 도구에만 쓰고, 그 경계를 넘을 조짐이 보이면 바로 정식 설계로 옮긴다.

**이 변화의 진짜 의미는 "검증 비용이 줄었다"는 것이다.** 예전에는 "여러 사람이 공유하는 도구가 필요한가"를 확인하려면 최소한의 백엔드를 먼저 지어야 했다. 이제는 그 가설 자체를 백엔드 없이 몇 분 안에 검증할 수 있으므로, 팀의 리소스를 "검증된 요구에만" 쓸 수 있게 됐다는 점이 핵심 이득이다.

## 마무리

- Claude Artifacts에 추가된 런타임 capabilities는 "클라이언트 전용 정적 페이지"와 "직접 구축한 풀스택 서비스" 사이에 공유 상태를 가진 중간 지점을 새로 만들었다.
- 이 지점은 소규모 공유·빠른 검증에 적합할 뿐, 복잡한 쿼리·세밀한 권한·대용량 데이터까지 대체하는 완성된 백엔드가 아니다.
- 공유가 실제로 필요한지부터 가리고, 사용량·데이터 복잡도가 늘어나는 신호가 보일 때만 전통적 백엔드로 좁은 범위의 마이그레이션을 수행하는 순서가 가장 비용 효율적이다.
