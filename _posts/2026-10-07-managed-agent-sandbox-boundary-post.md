## 왜 지금 이 판단이 불거지는가

"고객 데이터를 다루는 에이전트를 운영하고 싶은데, 그 에이전트가 실제로 코드를 실행하는 환경만큼은 반드시 우리 VPC 안에 있어야 합니다." 금융·의료·공공 분야 고객을 상대하는 팀이라면 이런 요구를 숱하게 들어봤을 것이다. 에이전트를 완전 관리형 서비스로 붙이자니 "우리 데이터가 외부 컨테이너에서 실행된다"는 컴플라이언스 벽에 막히고, 그렇다고 오케스트레이션·추론·에러 복구까지 전부 직접 구현하자니 결국 또 하나의 에이전트 프레임워크를 처음부터 만드는 셈이 된다.

이 긴장을 정면으로 다룬 것이 2026년 5월 19일 퍼블릭 베타로 나와 같은 해 5~6월 사이 Claude API와 AWS Bedrock 플랫폼에서 정식 출시(GA)된 Claude Managed Agents의 셀프호스티드 샌드박스다. 핵심 아이디어는 단순하다 — 에이전트 루프를 통째로 맡기거나 통째로 직접 만드는 양자택일 대신, 루프를 둘로 쪼개서 절반씩 나눠 가진다. 이게 빌더에게 중요한 이유는, 지금까지 "에이전트 인프라를 쓸 것인가 만들 것인가"로 묻던 질문이 "루프의 어느 절반을 누구에게 맡길 것인가"라는 훨씬 세밀한 질문으로 바뀌었기 때문이다.

## 요구사항을 기술 문제로 번역하기

"코드 실행 환경은 우리 VPC 안에 있어야 한다"는 한 문장은 사실 에이전트 루프 내부의 서로 다른 책임을 분리해야 하는 문제다. 에이전트가 한 번의 턴을 처리할 때 일어나는 일을 쪼개보면 이렇다. 첫째, **무엇을 할지 판단하는 부분** — 컨텍스트를 관리하고, 모델을 호출해 다음 행동을 추론하고, 도구 호출이 실패하면 복구 전략을 세우는 오케스트레이션 레이어. 둘째, **실제로 손을 움직이는 부분** — bash 명령 실행, 파일 읽기·쓰기·수정, 네트워크 요청 같은 실행 레이어. 기존 완전 관리형 구조에서는 이 둘이 전부 Anthropic이 운영하는 컨테이너 안에서 일어난다. 셀프호스티드 샌드박스는 첫째는 그대로 Anthropic 인프라에 맡기고, 둘째만 떼어내 고객이 운영하거나 위임한 샌드박스 호스트에서 실행하게 만든다. "데이터 레지던시를 지켜라"는 추상적인 요구가 "실행 레이어의 물리적 위치를 통제하라"는 구체적인 아키텍처 결정으로 번역되는 지점이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-07-managed-agent-sandbox-boundary-1.svg" alt="완전 관리형 구조에서는 오케스트레이션과 실행 레이어가 모두 Anthropic 컨테이너 안에 있지만, 셀프호스티드 샌드박스 구조에서는 오케스트레이션(두뇌)만 Anthropic에 남고 실행 레이어(손)는 고객의 VPC 안 샌드박스 호스트로 분리되어 파일마운트·네트워크 egress·allowlist를 고객이 직접 통제하는 구조를 비교한 다이어그램" style="width:100%;">

완전 관리형 구조에서는 클라이언트의 요청이 Anthropic이 운영하는 단일 경계 안으로 들어가, 추론부터 bash 실행까지 전부 그 안에서 끝난다. 네트워크 egress도, 파일 마운트도 Anthropic이 통제한다. 셀프호스티드 구조에서는 그 경계가 둘로 나뉜다. 모델 추론과 컨텍스트 관리, 에러 복구 판단은 여전히 Anthropic 쪽 오케스트레이션 레이어에서 일어나지만, 실제 도구 실행 요청은 API를 거쳐 고객이 운영하는 샌드박스 호스트로 전달된다. 이 샌드박스 호스트는 Kubernetes 기반 Agent Sandbox 같은 오픈소스 프로젝트로 직접 구성할 수도 있고, 전용 샌드박스 벤더에 위임할 수도 있다. 여기서 중요한 건 라우팅·프록시·allowlist·파일 경로 감사까지 전부 고객의 책임 범위로 넘어온다는 점이다. 뒷단에는 고객의 내부 데이터베이스나 사내 API가, 앞단에는 사용자 요청이 있는 전체 파이프라인에서, 이 경계는 "에이전트가 내 인프라의 어디까지 만질 수 있는가"를 가르는 유일한 지점이 된다.

## 선택의 트레이드오프

| 기준 | 완전 관리형 | 셀프호스티드 샌드박스 | 완전 자체 구축 |
|---|---|---|---|
| 데이터 레지던시 | 실행 환경도 외부에 위치 | 실행 환경만 내 VPC 안 | 전부 내 인프라 |
| 구현 속도 | 가장 빠름 | 중간 (프록시·allowlist 설계 필요) | 가장 느림 |
| 운영 부담 | Anthropic이 대부분 흡수 | 샌드박스 호스트 운영·패치는 내 몫 | 오케스트레이션까지 전부 내 몫 |
| 메모리 기능 | 완전 지원 | 아직 미지원(2026-10 기준) | 직접 설계해야 함 |
| 모델 교체 유연성 | Anthropic 의존 | Anthropic 의존 | 모델 벤더 자유 선택 |
| 보안 경계 책임 | Anthropic | 실행 레이어는 고객, 추론 레이어는 Anthropic | 전부 고객 |

이 표에서 눈여겨볼 줄은 "메모리 기능"이다. "일부만 넘긴다"는 선택이 공짜가 아니라 현재 시점의 기능 제약을 동반한다는 뜻이다. AWS Bedrock에서는 이 조합이 아직 전면 지원되지 않으므로, 멀티클라우드 전략을 쓰는 팀이라면 플랫폼별 지원 범위부터 확인해야 한다.

## 실제 프로젝트 진행 순서

1. **규제·컴플라이언스 요구를 구체적인 경계로 번역한다.** "데이터가 외부로 나가면 안 된다"를 "실행 레이어만 내 VPC 안에 두면 충분한가, 아니면 추론 과정에서 모델에 보내는 프롬프트 자체도 문제가 되는가"로 쪼개서 확인한다. 후자라면 셀프호스티드 샌드박스로도 해결이 안 된다.
2. **샌드박스 호스트를 직접 운영할지, 위임할지 정한다.** Kubernetes 기반 오픈소스 Agent Sandbox를 자체 클러스터에 올릴 여력이 있는지, 아니면 전용 샌드박스 호스팅 벤더에 맡길지는 팀의 인프라 운영 역량에 달려 있다.
3. **네트워크 egress 정책을 먼저 설계한다.** 에이전트가 실행 레이어에서 호출할 수 있는 도메인·포트를 allowlist로 못 박아 두지 않으면, 셀프호스티드로 가져온 통제권이 무용지물이 된다.
4. **파일 마운트 범위를 최소 권한 원칙으로 정한다.** 에이전트가 읽고 쓸 수 있는 디렉터리를 작업 단위로 좁혀서 마운트하고, 감사 로그를 샌드박스 호스트 쪽에서 직접 수집한다.
5. **메모리 기능이 빠진 공백을 어떻게 메울지 설계한다.** 세션 간 컨텍스트 유지가 필요한 워크플로라면, 메모리 기능 없이도 돌아가도록 외부 저장소에 직접 상태를 적재하는 보완 설계를 먼저 검증한다.
6. **저위험 워크플로부터 점진적으로 전환한다.** 처음부터 핵심 업무 전체를 셀프호스티드로 옮기지 말고, 데이터 민감도가 높은 워크플로 하나를 골라 파일럿으로 검증한 뒤 범위를 넓힌다.

## 실무 포인트

**"샌드박스를 셀프호스팅한다"가 "보안을 책임진다"와 동의어라는 점을 가볍게 보지 않는다.** 실행 레이어를 가져오는 순간 egress 통제, 파일 경로 감사, 호스트 패치까지 전부 떠안게 된다. 이걸 감당할 운영 역량이 없다면 완전 관리형이 오히려 더 안전한 선택일 수 있다.

**추론 레이어가 여전히 외부에 있다는 사실을 놓치지 않는다.** 셀프호스티드 샌드박스는 "코드 실행 환경"만 내부화할 뿐, 프롬프트와 모델 추론 자체는 여전히 Anthropic 인프라를 거친다. 프롬프트에 담기는 내용 자체가 민감 정보라면 이 구조로는 문제가 해결되지 않는다.

## 마무리

- 2026년 5~6월 GA된 Claude Managed Agents 셀프호스티드 샌드박스는 에이전트 루프를 오케스트레이션(두뇌)과 실행(손)으로 분리해, 추론은 Anthropic에 맡기고 코드 실행 환경만 자체 VPC 안에 둘 수 있게 한다.
- 데이터 레지던시 요구는 추상적인 "데이터를 외부로 보내지 않는다"가 아니라 "실행 레이어의 물리적 위치를 통제한다"는 구체적인 아키텍처 결정으로 번역해야 하며, 완전 관리형·셀프호스티드·완전 자체 구축 세 선택지 사이의 트레이드오프를 운영 역량 기준으로 판단해야 한다.
- 실제 도입은 규제 요구를 구체적 경계로 번역하고, egress·파일 마운트 정책을 먼저 설계한 뒤, 메모리 기능 공백을 보완하면서 저위험 워크플로부터 점진적으로 확장하는 순서로 진행하는 게 안전하다.
