## 왜 지금 이 이야기인가

신규 서비스의 스키마를 짤 때는 대체로 정규화 원칙을 충실히 따른다. 중복을 없애고, 하나의 사실은 한 곳에만 저장하고, 갱신 이상(update anomaly)이 생기지 않도록 테이블을 쪼갠다. 문제는 서비스가 커진 뒤다. 주문 목록 하나를 보여주는 데 조인이 4~5개씩 붙기 시작하고, 리포팅 쿼리는 실행 계획이 점점 복잡해진다. 이 시점에서 팀은 항상 같은 질문을 마주한다. "이 테이블, 다시 합쳐도 되나?"

정규화와 반정규화는 서로 반대되는 기법이 아니라, 같은 데이터를 두고 무엇을 우선할지 정하는 두 가지 답이다. 정규화는 쓰기 일관성과 저장 효율을, 반정규화는 읽기 성능을 우선한다. 어느 쪽이 "정답"인지는 스키마 자체가 아니라 워크로드가 결정한다. 이 글은 두 접근을 원칙적으로 비교하고, 실무에서 반정규화를 도입할 때 흔히 부딪히는 지점을 정리한다.

## 핵심 개념 1: 정규화 단계 이해하기

정규화(Normalization)는 테이블을 중복 없이, 각 데이터가 정확히 한 곳에만 존재하도록 분해하는 절차다. 실무에서 대부분의 OLTP 스키마는 3정규형(3NF)까지만 신경 쓰면 충분하다.

| 단계 | 규칙 | 제거하는 문제 |
|---|---|---|
| 1NF | 모든 컬럼 값이 원자값(더 이상 쪼갤 수 없는 값)이어야 함, 반복 그룹 금지 | 한 셀에 여러 값을 콤마로 욱여넣는 구조 |
| 2NF | 1NF를 만족하고, 복합키의 일부에만 종속된 컬럼(부분 함수 종속)이 없어야 함 | 복합키 테이블에서 특정 컬럼이 키의 절반에만 의존하는 문제 |
| 3NF | 2NF를 만족하고, 기본키가 아닌 컬럼끼리 서로 종속(이행적 종속)되지 않아야 함 | "고객명이 고객ID를 통해서만 결정돼야 하는데, 실제로는 우편번호가 도시명을 결정하는" 식의 간접 종속 |

3NF까지 적용하면 하나의 사실(예: 고객 이메일)은 정확히 한 테이블의 한 행에만 존재한다. 그 값을 바꿀 때 갱신해야 할 곳도 정확히 한 곳뿐이다.

## 핵심 개념 2: 반정규화는 언제 선택하는가

반정규화(Denormalization)는 정규화 규칙을 의도적으로 깨고 중복을 허용해, 조회 시 조인 횟수를 줄이거나 집계 연산을 미리 계산해두는 기법이다. "정규화를 몰라서" 쓰는 게 아니라 "정규화된 구조로는 특정 쿼리의 성능이 요구사항을 못 맞춰서" 쓰는 선택이다.

일반적으로 아래 상황에서 검토 대상이 된다.

- 읽기 트래픽이 쓰기보다 압도적으로 많고, 같은 조인이 매 요청마다 반복 실행될 때
- 리포팅·대시보드처럼 여러 테이블을 묶어 집계하는 쿼리가 배치나 실시간으로 자주 도는 OLAP성 워크로드
- 조인 경로가 깊어(3~4단계 이상) 실행 계획 최적화만으로는 한계에 부딪힐 때

| 반정규화 기법 | 방법 | 대가 |
|---|---|---|
| 컬럼 중복 저장 | 조인 없이 바로 쓰도록 참조 테이블 값을 복사해 둠 | 원본이 바뀌면 중복된 모든 곳을 함께 갱신해야 함 |
| 파생/집계 컬럼 캐싱 | 합계·개수 같은 계산 결과를 별도 컬럼에 미리 저장 | 트랜잭션마다 캐시 값도 함께 갱신해야 정합성 유지 |
| 구체화 뷰(Materialized View) | 조인·집계 결과를 물리적으로 저장, 주기적 갱신 | 갱신 주기 동안 최신 데이터가 아닐 수 있음(staleness) |
| 리포팅 전용 테이블 분리 | OLTP 원본은 그대로 두고 집계 결과만 별도 테이블/DB로 복제 | 별도 파이프라인(배치·CDC 등) 운영 부담 |

## 핵심 개념 3: 두 접근 비교

| 기준 | 정규화 | 반정규화 |
|---|---|---|
| 데이터 중복 | 없음(원칙적으로) | 의도적으로 허용 |
| 쓰기 복잡도 | 한 곳만 갱신 | 여러 곳을 동시에 갱신, 정합성 관리 필요 |
| 조회 성능 | 조인 비용 발생 | 조인 없이 빠른 조회 |
| 무결성 보장 | 강함(제약조건으로 강제 가능) | 애플리케이션·트리거 로직에 의존 |
| 적합 워크로드 | 쓰기가 잦은 OLTP | 읽기 집약적 리포팅·분석, 캐시성 조회 |

## 예제: 정규화된 조회 vs 반정규화된 캐시 컬럼

먼저 정규화된 3개 테이블(orders, customers, products)을 조인해 주문 상세를 조회하는 기본 쿼리다.

```sql
-- 정규화(3NF): 조인으로 최신 값을 항상 정확히 조회
SELECT o.order_id, c.name AS customer_name, p.name AS product_name,
       o.qty, p.price, (o.qty * p.price) AS line_total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN products  p ON o.product_id  = p.product_id
WHERE o.order_id = 1001;
```

이 쿼리는 고객·상품 정보가 바뀌어도 항상 최신 값을 정확히 반환한다. 하지만 고객별 누적 주문 통계처럼 자주 조회되는 집계값까지 매번 이렇게 계산하면 비용이 커진다. 이럴 때 반정규화로 집계 캐시 컬럼을 두는 방법을 검토할 수 있다.

```sql
-- 반정규화: 자주 조회하는 집계값을 customers 테이블에 캐시 컬럼으로 저장
ALTER TABLE customers ADD COLUMN total_orders INT NOT NULL DEFAULT 0;
ALTER TABLE customers ADD COLUMN total_spent  DECIMAL(12,2) NOT NULL DEFAULT 0;

-- 주문 생성 트랜잭션 안에서 원본 삽입과 캐시 갱신을 함께 커밋
BEGIN;
  INSERT INTO orders (customer_id, product_id, qty) VALUES (:customer_id, :product_id, :qty);
  UPDATE customers
     SET total_orders = total_orders + 1,
         total_spent  = total_spent + :line_total
   WHERE customer_id = :customer_id;
COMMIT;
```

캐시 컬럼은 조회 시 조인·집계 연산을 완전히 없애주지만, 이제 "주문 생성"이라는 하나의 이벤트가 두 테이블을 동시에 갱신해야 하는 트랜잭션이 됐다. 둘 중 하나만 반영되면 데이터가 어긋난다는 점이 이 방식의 핵심 대가다.

## 실무 포인트

- **기본값은 정규화, 반정규화는 예외로 취급한다.** 처음부터 반정규화된 스키마로 시작하면 나중에 어떤 이상현상이 원본 설계 때문인지, 성능 때문에 감수한 것인지 구분하기 어려워진다.
- **측정 없이 반정규화하지 않는다.** 실제로 느린 쿼리를 실행 계획으로 확인한 뒤, 그 쿼리 하나를 위해 국소적으로 캐시 컬럼이나 구체화 뷰를 두는 편이 스키마 전체를 반정규화하는 것보다 안전하다.
- **캐시 컬럼·중복 값은 반드시 원본과 같은 트랜잭션 안에서 갱신한다.** 별도 배치로 나중에 동기화하는 방식은 그 사이 구간의 불일치를 감수해야 한다.
- **구체화 뷰를 쓸 경우 갱신 주기와 staleness 허용 범위를 먼저 정한다.** 실시간 재고 수량처럼 최신성이 중요한 값에는 적합하지 않을 수 있다.
- **반정규화 결정은 반드시 문서로 남긴다.** 왜 특정 컬럼이 중복 저장되는지 기록이 없으면, 이후 합류한 팀원이 실수로 한쪽만 갱신하는 버그를 만들기 쉽다.

## 3줄 요약

- 정규화는 데이터를 한 곳에만 두어 무결성을 보장하지만, 조회 시 조인 비용이 따른다.
- 반정규화는 중복을 허용해 읽기 성능을 얻는 대신, 여러 곳을 동시에 갱신해야 하는 쓰기 복잡도를 감수해야 한다.
- 선택 기준은 워크로드다 — 쓰기 일관성이 중요한 OLTP는 정규화를 기본으로 하고, 측정으로 확인된 병목에 한해 국소적으로 반정규화한다.
