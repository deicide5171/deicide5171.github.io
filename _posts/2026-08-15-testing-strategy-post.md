## 왜 지금 이 주제인가

이 블로그는 Flutter 앱 개발과 네이버 클라우드 지도 API 연동에서 시작해, PostGIS 기반 공간 데이터, H3/Geohash 공간 인덱스, DB 인덱스 내부 구조, 분산 SQL과 캐시 스탬피드 같은 백엔드 심화 주제, 그리고 최근에는 MCP·A2A 같은 AI 에이전트 프로토콜과 Docker/CI-CD 파이프라인까지 폭넓게 다뤄왔다. 그런데 이 모든 글의 밑바탕에 깔려 있어야 할 질문 하나가 아직 정면으로 다뤄지지 않았다. "이 코드가 실제로 의도한 대로 동작하는지 어떻게 확신할 것인가"이다.

지난 글에서 CI/CD 파이프라인을 다루며 "테스트 실패 시 배포를 반드시 막는다"는 원칙을 언급했지만, 정작 그 파이프라인 안에서 무엇을 어떤 비율로 테스트해야 하는지는 다루지 않았다. Flutter 위젯 테스트, PostGIS 쿼리의 정합성 검증, 분산 시스템에서의 장애 시나리오 재현, AI 에이전트의 도구 호출 결과 검증까지 — 지금까지 다룬 모든 영역은 결국 "무엇을, 어느 계층에서, 얼마나 자주 테스트할 것인가"라는 동일한 문제로 수렴한다. 그래서 다음 학습 주제로 **테스트 피라미드**와 **실전 테스팅 전략**을 추천한다.

## 학습 로드맵

| 단계 | 주제 | 왜 필요한가 |
|---|---|---|
| 1 | 단위 테스트와 테스트 더블(Mock/Stub/Fake) | 외부 의존성 없이 로직 자체의 정확성을 빠르게 검증한다 |
| 2 | 통합 테스트(DB, API, 메시지 큐 연동) | 컴포넌트 간 경계에서 발생하는 실제 버그를 잡는다 |
| 3 | E2E 테스트와 계약 테스트(Contract Test) | 사용자 시나리오와 서비스 간 API 계약을 함께 지킨다 |
| 4 | 테스트 커버리지·플레이키 테스트 관리 | 숫자에 매몰되지 않고 신뢰할 수 있는 테스트만 유지한다 |
| 5 | CI 파이프라인에 테스트 단계 통합 | 앞서 다룬 CI/CD 파이프라인과 자연스럽게 연결한다 |

이 순서는 실행 속도가 빠르고 저렴한 테스트부터 쌓아 올려, 느리고 비싼 테스트는 꼭 필요한 만큼만 두는 "피라미드" 구조를 그대로 반영한다.

## 핵심 개념: 테스트 피라미드가 말하는 것

테스트 피라미드는 단위 테스트를 가장 넓은 기반에, 통합 테스트를 중간에, E2E 테스트를 가장 좁은 꼭대기에 배치하는 모델이다. 단위 테스트는 실행이 빠르고 실패 원인을 즉시 특정할 수 있지만 실제 환경의 문제(네트워크 지연, DB 락 경합 등)는 잡지 못한다. 반대로 E2E 테스트는 실제 사용자 흐름을 검증하지만 느리고, 환경 변화에 취약해 자주 실패하는 "플레이키 테스트"가 되기 쉽다.

이 블로그에서 다룬 캐시 스탬피드나 분산 SQL의 장애 시나리오처럼, 동시성·타이밍 이슈는 단위 테스트만으로는 재현되지 않는다. 이런 경우엔 통합 테스트 계층에서 실제 캐시·DB를 띄우고 부하를 재현하는 것이 훨씬 효과적이다. 즉 계층마다 "무엇을 검증할 책임이 있는가"를 명확히 나누는 것이 테스트 전략의 핵심이다.

## 예제: 단위 테스트와 통합 테스트의 역할 분리

```javascript
// 단위 테스트: 순수 로직만 빠르게 검증 (외부 의존성 없음)
test('할인율 계산은 최대 30%를 넘지 않는다', () => {
  expect(calculateDiscount(1000, 0.5)).toBe(300); // 30% 상한 적용
});

// 통합 테스트: 실제 DB 연결로 쿼리 정합성까지 검증
test('주문 생성 시 재고가 정확히 차감된다', async () => {
  await db.seed({ stock: 10 });
  await createOrder({ productId: 1, qty: 3 });
  const stock = await db.query('SELECT stock FROM products WHERE id = 1');
  expect(stock).toBe(7);
});
```

## 실무 포인트

- **테스트 더블은 최소한으로 쓴다**: 모든 것을 Mock으로 대체하면 테스트는 통과하지만 실제 통합 지점의 버그는 놓친다.
- **플레이키 테스트는 즉시 격리한다**: 간헐적으로 실패하는 테스트를 방치하면 팀 전체가 CI 실패를 무시하는 습관이 생긴다.
- **커버리지 숫자보다 경계 조건을 챙긴다**: 100% 커버리지보다 널 값, 동시성, 예외 경로 같은 실제 버그가 숨는 지점을 테스트하는 것이 중요하다.
- **E2E는 핵심 시나리오에만 집중한다**: 회원가입, 결제처럼 실패하면 치명적인 흐름만 E2E로 남기고 나머지는 하위 계층에 맡긴다.

## 3줄 요약

- 지금까지 다룬 Flutter, PostGIS, 분산 시스템, AI 에이전트, Docker/CI-CD 지식이 실제로 신뢰할 수 있으려면 테스트 전략이 뒷받침되어야 한다.
- 테스트 피라미드는 단위 테스트를 기반으로, 통합 테스트와 E2E 테스트를 필요한 만큼만 얹는 구조다.
- 플레이키 테스트 관리와 경계 조건 검증부터 CI 파이프라인에 자연스럽게 통합하는 것을 추천한다.
