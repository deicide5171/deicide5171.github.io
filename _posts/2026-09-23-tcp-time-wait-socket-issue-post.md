## 왜 갑자기 연결이 안 맺어질까

평소엔 멀쩡하던 서버가 트래픽이 몰리는 시간대나 부하 테스트 중에 갑자기 새 연결을 못 맺기 시작한다. `netstat -an`으로 확인해 보면 `TIME_WAIT` 상태의 소켓이 수만 개씩 쌓여 있는 걸 발견하게 된다. 언뜻 보면 "연결이 안 끊겨서" 문제가 생긴 것 같지만, 실제로는 정반대다 — TCP 연결을 정상적으로 종료하는 과정 자체가 TIME_WAIT라는 대기 상태를 만들어내고, 이 상태가 쌓이는 속도가 정리되는 속도보다 빠르면 사용 가능한 포트가 고갈되는 것이다.

이 문제는 특히 짧은 연결을 아주 많이 맺고 끊는 구조(HTTP/1.1 keep-alive 없이 매번 새 연결을 여는 레거시 클라이언트, 또는 아웃바운드 프록시)에서 흔하게 나타난다.

## 핵심 개념 1 — TIME_WAIT는 버그가 아니라 TCP의 안전장치다

TCP 연결을 능동적으로 닫는(FIN을 먼저 보내는) 쪽은 연결을 끊은 뒤에도 일정 시간(보통 2×MSL, 리눅스 기본값 기준 약 60초) 동안 TIME_WAIT 상태를 유지한다. 이 대기 시간은 두 가지 이유로 반드시 필요하다.

1. 마지막 ACK가 유실됐을 때 상대가 재전송한 FIN을 받아 다시 응답해줄 수 있어야 한다.
2. 네트워크에 떠돌던 지연 패킷이 나중에 도착했을 때, 그 패킷이 완전히 다른 새 연결로 잘못 전달되는 것을 막아야 한다.

문제는 이 TIME_WAIT 소켓이 "로컬 IP + 로컬 포트 + 상대 IP + 상대 포트" 조합, 즉 4-튜플을 계속 점유한다는 점이다. 특정 상대(같은 DB, 같은 백엔드)와 짧은 연결을 초당 수백~수천 번 맺고 끊으면, 사용 가능한 로컬 포트(기본적으로 약 28000~32000개 범위)가 TIME_WAIT 상태로 묶여 새 연결을 맺을 포트가 바닥난다.

## 핵심 개념 2 — 서버 쪽에서 능동적으로 닫지 않게 만드는 것이 근본 해법이다

TIME_WAIT는 연결을 먼저 닫는 쪽에서 발생한다. 그런데 흔한 오해와 달리, HTTP 서버가 클라이언트 요청을 처리한 뒤 응답하고 연결을 먼저 닫는 구조라면 TIME_WAIT는 서버 쪽에 쌓인다. 이 경우 아무리 서버 커널 파라미터를 조정해도 근본 해결이 안 되고, **클라이언트가 연결을 닫도록(또는 Keep-Alive로 재사용하도록) 구조를 바꾸는 것**이 우선이다.

```bash
# 현재 TIME_WAIT 소켓 개수 확인
ss -tan state time-wait | wc -l

# 상태별 연결 수 요약
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
```

## 예제 — 리눅스 커널 파라미터로 완화하기

근본적인 구조 개선(Keep-Alive 활성화, 커넥션 풀링) 전에 당장 급하다면 아래 커널 파라미터로 완화할 수 있다.

```bash
# /etc/sysctl.conf 또는 sysctl -w로 즉시 적용

# TIME_WAIT 소켓을 다시 사용하도록 허용 (아웃바운드 연결에 유용)
net.ipv4.tcp_tw_reuse = 1

# 로컬 포트 범위를 넓혀 가용 포트 수 확보
net.ipv4.ip_local_port_range = 1024 65535

# 소켓 백로그 및 재사용 관련 튜닝
net.ipv4.tcp_fin_timeout = 30
```

`tcp_tw_recycle`은 커널 4.12 이후 제거됐고, NAT 환경에서 연결 거부를 유발하는 부작용이 있었던 옵션이므로 절대 켜지 말아야 한다. 반면 `tcp_tw_reuse`는 아웃바운드(내가 클라이언트로서 외부에 요청을 보내는) 연결에 한해 비교적 안전하게 쓸 수 있다.

## 흔한 실수와 오해

| 오해 | 실제 |
|---|---|
| TIME_WAIT는 커널 버그다 | TCP 스펙에 명시된 정상 동작 |
| 무조건 tw_recycle을 켜면 해결된다 | NAT 뒤 클라이언트 연결 거부 유발, 커널에서 제거됨 |
| 서버 파라미터만 튜닝하면 끝 | 어느 쪽이 능동적으로 닫는지부터 확인해야 함 |
| ip_local_port_range만 넓히면 근본 해결 | 임시방편일 뿐, 연결 재사용 구조 개선이 우선 |

## 실무 포인트

- **애플리케이션 레벨에서 커넥션 풀링과 Keep-Alive를 우선 검토하라.** DB 클라이언트, HTTP 클라이언트 모두 연결을 매번 새로 맺지 않고 재사용하도록 설정하는 것이 커널 튜닝보다 훨씬 근본적인 해결책이다.
- **로드밸런서나 리버스 프록시 앞단에서도 같은 문제가 생길 수 있다.** Nginx의 업스트림 연결도 keepalive 지시어 없이는 매 요청마다 새 연결을 맺어 TIME_WAIT를 유발할 수 있다.
- **모니터링에 TIME_WAIT 소켓 수를 지표로 추가하라.** 문제가 터진 뒤에야 netstat을 열어보는 대신, 평소 추세를 그래프로 봐두면 포트 고갈 직전에 미리 알아챌 수 있다.

## 마무리 요약

- TIME_WAIT는 TCP가 유실된 패킷과 지연 패킷을 안전하게 처리하기 위한 정상 동작이며, 능동적으로 연결을 닫는 쪽에서 발생한다.
- 근본 해결은 커널 파라미터 튜닝이 아니라 Keep-Alive와 커넥션 풀링으로 연결 재사용 구조를 만드는 것이다.
- tcp_tw_recycle은 부작용 때문에 커널에서 제거됐으므로 절대 사용하지 말고, tcp_tw_reuse와 포트 범위 확장은 임시 완화책으로만 활용해야 한다.
