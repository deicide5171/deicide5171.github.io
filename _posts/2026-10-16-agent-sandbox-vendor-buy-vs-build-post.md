## 왜 지금 이 판단이 필요한가

"사용자가 입력한 요구사항으로 에이전트가 코드를 직접 짜고 바로 실행까지 보여주세요. 근데 당연히 다른 사용자 코드나 데이터는 서로 못 보게 해주세요." AI 코딩 어시스턴트, 데이터 분석 에이전트, 노코드 자동화 플랫폼을 만드는 팀이면 반드시 마주치는 요구다. 이 한 문장은 두 개의 서로 다른 설계 질문으로 쪼개진다. 하나는 "어떤 격리 기술을 쓸 것인가"(컨테이너냐 microVM이냐)이고, 이미 많이 다뤄진 질문이다. 다른 하나는 훨씬 덜 다뤄지는 질문 — **"이 격리 인프라 자체를 내가 운영할 것인가, 그걸 서비스로 파는 벤더에게 맡길 것인가"**다.

2026년 들어 E2B, Daytona, Modal, Vercel Sandbox 같은 "에이전트 코드 실행 전용" 샌드박스 SaaS가 빠르게 성숙했다. 모두 격리 기술 자체(Firecracker microVM, gVisor 등)는 검증된 걸 쓰지만, 콜드 스타트 속도·세션 재개 방식·과금 모델·셀프호스팅 가능 여부에서 전혀 다른 선택지를 제공한다. 격리 기술 하나를 골랐다고 끝나는 게 아니라, 그 위에 "누구 인프라에서, 어떤 비용 구조로 운영할 것인가"까지 결정해야 실제 서비스가 돌아간다.

## 핵심 개념 1 — 격리 기술은 이미 전제조건이지 선택지가 아니다

컨테이너 하나로는 커널을 호스트와 공유하기 때문에 여러 테넌트의 코드를 신뢰 경계 없이 같은 머신에서 돌릴 수 없다. 그래서 멀티테넌트 코드 실행 서비스는 거의 예외 없이 Firecracker microVM(하드웨어 수준 격리, 빠른 스냅숏 복원) 또는 gVisor(유저스페이스 커널 에뮬레이션, 상대적으로 가벼움) 위에 올라간다. 이 선택은 이미 벤더들이 내려놓은 결정이다 — 빌더가 실제로 내려야 하는 결정은 그 위 레이어다.

## 핵심 개념 2 — 벤더마다 다른 건 운영 모델이다

| 비교 축 | 자체 구축(Firecracker/gVisor 직접 운영) | 샌드박스 SaaS(E2B·Daytona·Modal류) |
|---|---|---|
| 격리 신뢰 경계 | 직접 검증·감사 가능 | 벤더 보안 모델을 신뢰해야 함 |
| 콜드 스타트 | 튜닝 여지 크지만 직접 최적화 필요 | 스냅숏 기반 수백 ms급 복원 제공(벤더별 상이) |
| 멀티턴 세션 재개 | 직접 구현해야 함(스냅숏 저장·복원 로직) | 대부분 네이티브 지원 |
| GPU 워크로드 | 직접 드라이버·스케줄링 구성 | 벤더별 지원 편차 큼(Modal은 GPU 특화) |
| 데이터 주권/규제 | 인프라를 직접 통제 | BYOC(자체 클라우드에 벤더 컨트롤플레인 배치) 옵션 유무 확인 필요 |
| 비용 구조 | 고정 인프라비 + 운영 인건비 | 실행 시간·요청 단위 종량제, 트래픽 적을 땐 유리 |
| 셀프호스팅 | 기본값 | 벤더별 상이(오픈소스 공개 여부가 갈림) |

멀티턴 세션(사용자가 대화를 이어가며 같은 실행 환경 상태를 유지해야 하는 경우) 재개 기능은 특히 자체 구현 비용이 크다 — 스냅숏을 언제·어떻게 저장하고, 몇 분 뒤 다시 복원할 때 상태 일관성을 어떻게 보장할지가 생각보다 까다롭다. 이 기능이 핵심 요구사항이라면 벤더 위탁 쪽으로 저울이 기운다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-16-agent-sandbox-vendor-buy-vs-build-1.svg" alt="에이전트 오케스트레이터가 코드 실행이 필요할 때 샌드박스 프로비저닝 레이어를 거치며, 이 레이어가 자체 운영 Firecracker 클러스터이거나 벤더 API 호출일 수 있고 결과적으로 테넌트별로 격리된 실행 환경에서 코드가 돌고 결과만 오케스트레이터로 돌아오는 구조도" style="width:100%;">

에이전트 오케스트레이터는 LLM이 생성한 코드를 직접 실행하지 않는다. "코드를 실행해달라"는 요청을 샌드박스 프로비저닝 레이어에 위임하고, 이 레이어가 테넌트 ID를 기준으로 격리된 실행 환경(자체 Firecracker 클러스터 또는 벤더 API로 받은 microVM)을 할당한다. 실행 결과(stdout, 생성 파일, 에러)만 오케스트레이터로 돌아오고, 실행 환경 자체는 테넌트 경계를 넘어 재사용되지 않는다. 이 프로비저닝 레이어가 자체 구축이냐 벤더 API 호출이냐는 오케스트레이터 입장에서는 인터페이스 차이일 뿐이지만, 운영 조직 입장에서는 완전히 다른 팀과 비용 구조를 필요로 한다.

## 선택의 트레이드오프

- **트래픽이 작고 아직 제품-시장 적합성을 찾는 단계**라면 벤더 SaaS로 시작한다. 종량제라 초기 고정비가 없고, 세션 재개 같은 기능을 처음부터 직접 구현할 필요가 없다.
- **코드 실행이 핵심 제품이고 실행 볼륨이 크게 예측 가능한 단계**(예: 자체 코딩 어시스턴트 제품의 메인 기능)라면 자체 구축이 장기 비용에서 유리해진다 — 단, 보안 감사·패치 관리 인력을 전제로 한다.
- **규제 산업(금융·의료·공공)**이라 데이터가 특정 리전·네트워크를 벗어나면 안 된다면, 벤더의 BYOC(자체 클라우드에 벤더 컨트롤플레인만 배치) 옵션 유무를 먼저 확인한다. 없으면 자체 구축 외에 선택지가 없다.
- **GPU가 필요한 실행 워크로드**(이미지 생성, 로컬 모델 추론)라면 GPU 특화 벤더를 우선 검토한다 — 일반 CPU 샌드박스 벤더에 GPU를 무리하게 끼워 맞추면 비용·성능 모두 불리하다.
- 벤더로 시작했다가 나중에 자체 구축으로 전환하는 경로는 가능하지만, 실행 환경 API 계약(함수 시그니처, 파일시스템 레이아웃)을 처음부터 벤더에 강결합시키지 않아야 전환 비용이 낮다.

## 실제 프로젝트 진행 순서

1. **멀티턴 세션 재개가 필요한지부터 확정한다.** 필요하면 벤더 위탁 쪽 선택지가 크게 늘어나고, 자체 구축의 초기 구현 범위가 확 커진다.
2. **예상 실행 볼륨과 테넌트 수로 종량제 vs 고정비 손익분기점을 계산한다.** 벤더 가격표 기준으로 월 실행 시간을 추정해 자체 구축 인프라비와 비교한다.
3. **규제·데이터 주권 요구사항을 먼저 걸러낸다.** BYOC가 필요한데 벤더가 지원 안 하면 이후 단계를 생략하고 자체 구축으로 바로 간다.
4. **오케스트레이터와 샌드박스 레이어 사이 인터페이스를 벤더 중립적으로 설계한다.** "코드 실행 요청 → 결과" 계약을 추상화해두면 나중에 벤더를 바꾸거나 자체 구축으로 전환할 때 오케스트레이터 코드를 다시 짤 필요가 없다.
5. **소규모 트래픽으로 PoC를 돌려 콜드 스타트·세션 재개·테넌트 격리 경계를 실측한다.** 벤더 문서의 수치보다 자신의 실제 워크로드로 잰 수치를 기준으로 결정한다.

```python
# 벤더 중립적인 샌드박스 실행 인터페이스 예
class SandboxProvider(Protocol):
    def create_session(self, tenant_id: str) -> str: ...
    def run_code(self, session_id: str, code: str) -> ExecutionResult: ...
    def resume_session(self, session_id: str) -> None: ...

# 구현체만 교체하면 오케스트레이터는 변경 없음
provider: SandboxProvider = E2BProvider() if use_vendor else SelfHostedFirecracker()
```

## 마무리 요약

- 격리 기술(microVM, gVisor) 선택은 이미 전제조건이고, 진짜 판단은 그 운영 주체를 직접 맡을지 벤더에 맡길지다.
- 멀티턴 세션 재개 요구와 규제상 데이터 주권 요구가 빌드 vs 바이를 가르는 가장 강한 두 가지 기준이다.
- 오케스트레이터와 샌드박스 레이어 사이를 벤더 중립 인터페이스로 설계해두면 나중에 전환 비용을 크게 줄인다.
