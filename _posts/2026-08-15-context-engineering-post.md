## 왜 지금 컨텍스트 엔지니어링인가

2023~2024년의 LLM 개발 담론은 대체로 "프롬프트를 어떻게 잘 쓰느냐"에 집중되어 있었다. 역할극(role-play) 지시, few-shot 예제 배치, chain-of-thought 유도 문구 같은 것들이 핵심 기술로 다뤄졌다. 그런데 에이전트가 여러 턴에 걸쳐 도구를 호출하고, 파일을 읽고, 외부 API 결과를 소비하면서 작업을 이어가는 구조가 보편화되자, 단일 프롬프트를 잘 쓰는 것만으로는 해결되지 않는 문제들이 드러나기 시작했다. 모델이 몇 턴 전에 준 지시를 잊어버리거나, 컨텍스트 윈도우가 관련 없는 로그와 중복 정보로 가득 차서 정작 중요한 신호가 묻히는 현상이 대표적이다.

이런 배경에서 "컨텍스트 엔지니어링(context engineering)"이라는 용어가 자연스럽게 자리를 잡아가고 있는 것으로 보인다. 프롬프트 엔지니어링이 "모델에게 무엇을 말할 것인가"에 대한 기술이라면, 컨텍스트 엔지니어링은 "모델의 제한된 컨텍스트 윈도우에 무엇을, 어떤 형식으로, 어느 시점에 넣을 것인가"를 설계하는 더 넓은 개념이다. 에이전트형 애플리케이션이 늘어날수록 이 차이는 실무 성능에 직접적인 영향을 준다.

## 프롬프트 엔지니어링과 컨텍스트 엔지니어링의 차이

| 구분 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|---|---|---|
| 초점 | 단일 요청의 문구, 지시사항 표현 | 전체 컨텍스트 윈도우의 구성과 정보 흐름 |
| 시간축 | 한 번의 호출 | 여러 턴에 걸친 세션 전체 |
| 다루는 대상 | 시스템 프롬프트 문구, few-shot 예제 | 도구 결과, 대화 이력, 검색된 문서, 메모리 요약 |
| 실패 유형 | 지시를 잘못 이해함 | 컨텍스트 과적재(context bloat), 관련 정보 누락 |
| 대표 기법 | 역할 지정, CoT 유도, 출력 형식 지정 | 관련성 필터링, 요약/압축, 장단기 메모리 분리 |

두 개념이 배타적인 것은 아니다. 컨텍스트 엔지니어링은 프롬프트 엔지니어링을 포함하는 상위 개념에 가깝고, 잘 설계된 시스템 프롬프트 역시 컨텍스트 구성의 일부로 다뤄진다.

## 컨텍스트 윈도우 관리 전략

에이전트가 길게 동작할수록 컨텍스트 윈도우는 금방 채워진다. 대표적으로 다음 세 가지 전략이 함께 쓰이는 것으로 보인다.

**관련성 필터링**: 도구 호출 결과나 검색 결과를 그대로 다 넣지 않고, 현재 태스크와 관련 있는 부분만 추려서 넣는다. 예를 들어 파일 전체를 읽어오기보다 관련 함수나 라인 범위만 발췌하는 식이다.

**압축(compaction)**: 대화가 길어지면 오래된 턴을 요약본으로 대체한다. 다만 요약 과정에서 세부 정보(구체적인 변수명, 에러 메시지 등)가 유실될 위험이 있어, 어떤 정보를 원문 그대로 보존할지 규칙을 정해두는 것이 중요하다.

**장기기억/단기기억 구분**: 세션 내에서만 유효한 정보(현재 작업 중인 파일, 최근 도구 결과)와, 세션을 넘어 지속되어야 하는 정보(사용자 선호, 프로젝트 규칙)를 분리해서 관리한다. 후자는 별도 저장소나 파일(예: 프로젝트 설정 파일)에 두고 필요할 때만 불러오는 방식이 흔히 쓰인다.

## 도구 설명과 시스템 프롬프트 설계 원칙

에이전트에게 제공하는 도구(tool) 설명 역시 컨텍스트의 일부이기 때문에 설계 대상이 된다. 도구가 많아질수록 설명 텍스트가 컨텍스트를 잠식하므로, 실무에서는 다음을 신경 쓰는 편이다.

- 도구 이름과 파라미터 설명을 명확하고 간결하게 유지해 모델이 잘못 호출할 가능성을 줄인다.
- 유사한 기능의 도구는 통합하거나, 사용 빈도가 낮은 도구는 필요 시점에만 동적으로 노출한다.
- 시스템 프롬프트에는 "무엇을 해야 하는가"뿐 아니라 "언제 도구를 쓰지 말아야 하는가"도 명시해 불필요한 호출을 줄인다.

## 예제

```yaml
# 도구 설명 예시 - 관련성 높은 정보만 노출
tools:
  - name: search_codebase
    description: >
      코드베이스에서 관련 파일을 검색한다.
      결과는 최대 5개 파일, 각 파일당 관련 라인 범위만 반환한다.
    parameters:
      query: string
      max_results: integer (default 5)
```

```python
# 간단한 컨텍스트 조립 로직 예시 (개념 시연용 의사코드)
def build_context(session, current_task):
    long_term = load_persistent_memory(session.user_id)  # 규칙, 선호도 등
    recent_turns = summarize_if_needed(session.history, max_tokens=4000)
    relevant_snippets = filter_by_relevance(
        session.tool_results, current_task, top_k=5
    )
    return {
        "system": long_term,
        "history": recent_turns,
        "context": relevant_snippets,
    }
```

## 실무 포인트와 주의사항

- 컨텍스트가 길다고 항상 성능이 좋아지는 것은 아니다. 오히려 관련 없는 정보가 섞이면 모델의 주의가 분산될 수 있다.
- 압축/요약 단계에서 어떤 정보를 "반드시 원문 보존"할지 규칙을 미리 정의해두어야 디버깅 시 원인 추적이 쉬워진다.
- 도구 설명도 토큰을 소비한다는 점을 기억하고, 사용 빈도가 낮은 도구는 카탈로그 형태로 분리해 필요할 때만 로드하는 방식을 고려한다.
- 컨텍스트 구성 방식을 바꿀 때는 정성적인 느낌만으로 판단하지 말고, 실제 태스크 성공률 등의 지표로 비교해보는 것이 안전하다.

## 3줄 요약

- 컨텍스트 엔지니어링은 "무엇을 말하느냐"가 아니라 "무엇을 보여주느냐"를 설계하는, 프롬프트 엔지니어링보다 넓은 개념이다.
- 관련성 필터링, 압축, 장단기 메모리 분리가 컨텍스트 윈도우 관리의 핵심 축이다.
- 도구 설명과 시스템 프롬프트 역시 컨텍스트의 일부이므로 토큰 예산을 고려해 설계해야 한다.
