## "새 소식 있어?"를 어떻게 확인하나

결제가 완료됐는지, 새 주문이 들어왔는지 등 **다른 시스템의 변경을 알아채는 방법**은 크게 두 가지다. 내가 주기적으로 물어보는 **폴링(polling)**과, 상대가 변경 시 나에게 알려주는 **웹훅(webhook)**이다. 택배로 비유하면, 폴링은 내가 계속 문 앞에 나가 확인하는 것이고, 웹훅은 택배기사가 초인종을 눌러주는 것이다.

## 폴링 vs 웹훅

| 항목 | 폴링 | 웹훅 |
|---|---|---|
| 방향 | 내가 주기적으로 요청 | 상대가 변경 시 호출 |
| 실시간성 | 주기만큼 지연 | 거의 즉시 |
| 서버 부하 | 변경 없어도 계속 요청 | 변경 있을 때만 |
| 구현 난이도 | 쉬움(요청 반복) | 수신 엔드포인트·검증 필요 |

## 각 방식의 흐름

```text
[폴링]
내 서버 -> "변경됐어?" -> 상대 서버 (5초마다 반복)
상대: "아니" / "아니" / "응, 여기 있어"
-> 대부분의 요청이 헛수고

[웹훅]
상대 서버: 변경 발생! -> 내 서버의 URL로 POST 전송
내 서버: 알림 받고 바로 처리
-> 변경 있을 때만 통신
```

## 실무 포인트

- **웹훅은 받을 URL(엔드포인트)을 공개해야 한다.** 상대가 내 서버로 요청을 보내므로, 인터넷에서 접근 가능한 주소가 필요하다. 아무나 가짜 요청을 보낼 수 있으므로 **서명 검증**으로 진짜 발신자인지 확인해야 한다.
- **웹훅은 실패에 대비해야 한다.** 내 서버가 잠깐 죽어 있으면 알림을 놓칠 수 있다. 상대가 재시도를 해주는지 확인하고, 중요한 데이터는 폴링으로 주기적 보정을 겸하기도 한다.
- **폴링은 주기 설정이 관건이다.** 너무 자주 하면 낭비, 너무 뜸하면 지연이 크다. 웹훅을 못 쓰는 외부 API에선 폴링이 유일한 선택일 때가 많으니, 지수 백오프 등으로 부하를 조절한다.

## 마무리 요약

- 폴링은 내가 주기적으로 물어보는 방식, 웹훅은 상대가 변경 시 알려주는 방식이다.
- 웹훅은 실시간성이 좋고 부하가 적지만 수신 URL과 서명 검증, 실패 대비가 필요하다.
- 폴링은 구현이 쉽지만 지연·낭비가 있어 주기 조절이 중요하며, 둘을 함께 쓰기도 한다.
