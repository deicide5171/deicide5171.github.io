## 왜 지금 이 문제가 불거지는가

"우리 팀은 PR을 만들 때마다 같은 체크리스트를 돈다. 커밋 메시지 컨벤션, 테스트 커버리지 확인, 변경 범위 설명 작성 순서까지 — 이걸 에이전트가 알아서 했으면 좋겠다." 이런 요구사항을 받으면 많은 빌더가 반사적으로 MCP 도구를 하나 더 만든다. 그런데 이 요구는 외부 시스템에 접근하는 문제가 아니라 **"어떻게 하는지"를 아는 절차적 노하우**를 에이전트에게 전달하는 문제다. 체크리스트, 스타일 가이드, 사내 컨벤션은 API 호출로 가져올 데이터가 아니라 에이전트가 과제 수행 중 참조해야 할 지식이다.

이 구분이 실무에서 중요해진 이유는 MCP 도구가 쌓일수록 생기는 부작용 때문이다. MCP 서버를 여러 개 연결하면 각 도구의 이름·설명·파라미터 스키마가 전부 시스템 프롬프트에 상주한다. 도구가 많아질수록 매 요청마다 소비되는 기본 토큰이 늘고, 모델이 비슷한 도구 여러 개 중 무엇을 골라야 할지 헷갈리는 사례도 늘어난다. 2025년 10월 Claude Skills로 처음 등장해 2025년 12월 오픈 표준으로 공개된 Agent Skills는 바로 이 지점, 즉 "쓸모 있는 절차적 지식을 등록할수록 에이전트가 느려지는" 딜레마를 정면으로 겨냥한다.

## 요구사항을 기술 문제로 번역하기

"체크리스트대로 해줘"라는 한 줄은 최소 세 가지 구현 선택지로 갈린다. 첫째, 체크리스트 전문을 시스템 프롬프트에 항상 박아 넣는 방법 — 동작은 하지만 PR 작업이 아닌 요청에서도 매번 그 토큰 비용을 치른다. 둘째, 체크리스트를 반환하는 MCP 도구를 만드는 방법 — 결국 정적 텍스트 하나를 위해 도구 정의 하나가 상주 목록에 추가될 뿐이다. 셋째, Agent Skills처럼 **이름과 설명(약 100토큰)만 상시 로드하고, 실제로 관련 작업이 들어왔을 때만 본문을 읽어 들이는 방법**이다.

세 번째 방식의 핵심은 3단계 점진적 공개(Progressive Disclosure)다. 1단계는 모든 스킬의 메타데이터(name, description)를 세션 시작 시 전부 로드해 "이런 역량들이 있다"는 목록만 유지한다. 2단계는 사용자 요청이 특정 스킬의 설명과 매칭되면 그 SKILL.md 본문(통상 5,000토큰 이하)을 그 순간에 컨텍스트로 끌어온다. 3단계는 본문이 가리키는 스크립트·템플릿·참고자료를 필요할 때만 파일로 읽거나 실행한다. 등록된 스킬이 몇십 개가 되어도 실제 컨텍스트 비용은 "지금 쓰는 것"에만 비례한다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-02-agent-skills-progressive-disclosure-1.svg" alt="세션 시작 시 모든 스킬의 메타데이터가 약 100토큰씩 상시 로드되고, 사용자 요청이 특정 스킬 설명과 매칭되면 그 SKILL.md 본문만 컨텍스트로 로드되며, 본문이 가리키는 스크립트나 참고자료는 실제 실행·조회 시점에만 읽히는 3단계 점진적 공개 구조도" style="width:100%;">

이 구조에서 Skill은 MCP나 서브에이전트를 대체하지 않는다. 세 메커니즘은 서로 다른 레이어를 담당한다. MCP는 에이전트와 **외부 시스템**(DB, 사내 API, 깃헙) 사이의 연결 표준이고, 서브에이전트는 **독립된 컨텍스트**에서 별도 조사나 작업을 위임받는 실행 단위이며, Skill은 에이전트 **자신의 행동 절차**에 관한 지식이다. 실제 파이프라인에서는 하나의 요청 안에서 셋이 함께 동작한다 — Skill이 "PR을 어떻게 검토하는지" 절차를 로드하면, 그 절차 안에서 MCP 도구로 깃헙 API를 호출하고, 변경량이 크면 서브에이전트에게 파일별 분석을 위임하는 식이다.

## Skill vs MCP 도구 vs 서브에이전트 — 무엇을 기준으로 고를까

| 기준 | MCP 도구 | Agent Skill | 서브에이전트 |
|---|---|---|---|
| 담당 영역 | 외부 시스템·데이터 연결 | 절차적 노하우·컨벤션 주입 | 독립 조사·작업 위임 |
| 상시 비용 | 도구 스키마 전체가 매 요청 상주 | 메타데이터(~100토큰)만 상시 로드 | 부모 컨텍스트엔 0, 조율 오버헤드 발생 |
| 본문 로드 시점 | 호출 시 즉시 실행 | 설명과 매칭될 때만 본문 로드 | 위임 시점에 별도 세션 시작 |
| 상태 성격 | 상태 없는 단일 호출 | 파일 기반 지식 번들(스크립트 포함 가능) | 독립된 대화 컨텍스트 |
| 적합한 경우 | "이 데이터를 가져와라/반영해라" | "이 일을 할 땐 이 순서·이 기준을 따라라" | "이 조사는 따로 떼어 깊게 파라" |

가장 흔한 실수는 모든 걸 MCP 도구로 해결하려는 것이다. 체크리스트나 스타일 가이드처럼 반환값이 고정된 지식은 도구 호출 왕복 비용과 도구 목록 부담만 늘릴 뿐 얻는 게 없다. 반대로 실시간 데이터가 필요한 작업까지 Skill 본문에 하드코딩하면 데이터가 바뀔 때마다 SKILL.md를 고쳐야 하는 유지보수 부담이 생긴다.

## 실제 프로젝트 진행 순서

1. **반복되는 절차부터 후보로 추린다.** 팀 안에서 "매번 똑같이 설명해야 하는 작업 순서"가 있는지 찾는다. PR 체크리스트, 장애 대응 런북, 코드 리뷰 기준이 전형적인 후보다.
2. **SKILL.md의 description을 가장 먼저, 가장 신중하게 쓴다.** 이 설명 한 줄이 "언제 이 스킬을 불러올지"를 결정하는 유일한 신호다. 너무 모호하면 매번 불필요하게 로드되고, 너무 좁으면 필요할 때도 매칭되지 않는다.
3. **본문은 5,000토큰 이하로 절차 위주로 쓰고, 코드·템플릿은 별도 파일로 분리한다.** 본문에 모든 걸 다 적으면 2단계 로드 비용 자체가 커져 점진적 공개의 이점이 사라진다.
4. **실제 트리거 테스트를 반복한다.** 의도한 요청에서 스킬이 로드되는지, 무관한 요청에서는 로드되지 않는지 여러 문구로 확인하며 description을 튜닝한다.
5. **등록 스킬 수가 늘어나면 메타데이터 총량도 거버넌스 대상이 된다.** 스킬이 수십 개를 넘으면 1단계 상주 비용만으로도 무시 못 할 토큰이 쌓이므로, 쓰이지 않는 스킬은 주기적으로 정리한다.

## 실무 포인트

**description은 스펙이지 설명문이 아니다.** "커밋 관련 작업을 돕는다" 같은 느슨한 문장은 거의 모든 요청과 매칭되거나 거의 아무 요청과도 매칭되지 않는다. "feat/fix/refactor 접두사 규칙에 맞춰 커밋 메시지를 작성해야 할 때"처럼 트리거 조건을 구체적으로 적어야 한다.

**오픈 표준이 됐다고 모든 벤더 구현이 동일하진 않다.** 2025년 12월 공개 표준화 이후 여러 에이전트 프레임워크가 Skill 포맷을 지원하기 시작했지만, 3단계 로드를 얼마나 엄격히 지키는지는 구현체마다 다르다. 다른 벤더 환경으로 포팅할 때는 실제 토큰 사용량을 직접 측정해야 한다.

**Skill은 권한 경계가 아니다.** 스크립트 실행이 포함된 Skill을 쓸 때는 그 스크립트가 어떤 권한으로 도는지 별도로 설계해야 한다. Skill 자체는 지식 전달 메커니즘일 뿐 샌드박싱 메커니즘이 아니다.

## 마무리

- "절차·컨벤션을 알아서 따라달라"는 요구는 MCP 도구가 아니라 Agent Skills의 영역이다. MCP는 외부 연결, Skill은 행동 절차, 서브에이전트는 독립 위임으로 역할이 나뉜다.
- Progressive Disclosure는 메타데이터(상시)·본문(매칭 시)·리소스(실행 시)의 3단계로 컨텍스트 비용을 "지금 쓰는 만큼만" 지불하게 만든다.
- description 작성과 실제 트리거 테스트가 성패를 가르며, 스킬 수가 늘어나면 메타데이터 총량도 관리 대상이 된다.
