## 왜 지금 이 판단이 불거지는가

"배달 기사가 지나온 경로를 지도에 선으로 그려서 보여주세요." 단순해 보이는 이 요구를 그대로 구현하면 결과물이 지저분해진다. GPS 수신기는 도심에서 수 미터, 고층 빌딩 사이나 터널 근처에서는 수십 미터까지 오차가 난다. 그 원시 좌표를 순서대로 이어 그으면 경로가 건물 안으로 들어갔다 나오고, 강을 가로지르고, 분명 직진 중인데 선이 옆 차선으로 들쭉날쭉 튄다. 배달·공유 모빌리티·물류 자동화가 늘면서 실시간 위치 스트림의 양이 크게 늘었고, 이 지저분한 원시 궤적을 그대로 사용자에게 보여주거나 ETA 계산에 넣으면 신뢰도가 바로 깨진다.

흔한 임시방편은 각 GPS 점을 가장 가까운 도로에 그냥 스냅하는 것이다. 하지만 이 방식은 교차로 근처에서 치명적인 실수를 저지른다. 두 도로가 가까이 붙어 있는 구간에서 GPS 오차 때문에 점 하나가 실제로는 지나지 않은 옆 도로에 더 가깝게 찍히면, 최근접 스냅은 주저 없이 그 옆 도로로 경로를 꺾어버린다. 결과적으로 차량이 다니지 않을 법한 경로가 그려지고, 이게 바로 "점 하나하나를 독립적으로 보지 말고, 전체 궤적을 도로망이라는 그래프 위에서 가장 그럴듯한 하나의 경로로 복원해야 한다"는 문제의식으로 이어진다. Hidden Markov Model(HMM) 기반 맵매칭은 바로 이 문제를 정면으로 겨냥한 고전적이면서도 여전히 업계 표준으로 쓰이는 해법이다.

## 요구사항을 기술 문제로 번역하기

"경로를 깔끔하게 그려주세요"는 사실 두 가지 확률을 동시에 고려하는 문제로 번역된다. 첫째, **방출 확률(emission probability)** — 특정 GPS 관측점이 주어졌을 때, 그 점이 실제로 어느 도로 세그먼트 위에 있었을 가능성이다. GPS 오차를 가우시안 분포로 모델링해, 관측점과 후보 도로 사이의 거리가 가까울수록 이 확률이 높아진다. 둘째, **전이 확률(transition probability)** — 연속된 두 관측점 사이에서, 한 도로 세그먼트에서 다음 도로 세그먼트로 실제로 이동했을 가능성이다. 두 후보 도로 사이의 최단경로 네트워크 거리가 직선거리(GPS 점 사이 거리)와 비슷할수록 그럴듯한 이동으로 본다. 이 두 확률을 결합해 전체 궤적에 대해 가장 그럴듯한 도로 세그먼트의 연속을 찾는 문제가 바로 고전적인 Viterbi 알고리즘으로 푸는 최적 은닉 상태열 추정 문제다. "도로에 붙여라"는 말이 "관측 확률과 이동 확률을 함께 최적화하는 동적 계획법 문제"로 바뀌는 지점이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-07-gps-trajectory-map-matching-hmm-1.svg" alt="GPS 센서에서 나온 원시 좌표 스트림이 맵매칭 엔진으로 들어가 도로망 그래프(OSM/Overture Maps)의 후보 세그먼트들과 대조되고, HMM과 Viterbi 알고리즘으로 가장 그럴듯한 도로 경로로 보정된 뒤 라우팅 엔진·ETA 계산·지도 렌더링으로 이어지는 파이프라인 구조도" style="width:100%;">

맵매칭은 파이프라인의 중간, 정확히는 원시 GPS 스트림과 라우팅 엔진 사이에 위치하는 전처리 계층이다. 앞단에는 차량·단말기의 GPS 센서가 일정 주기로 쏘아 보내는 (위도, 경도, 타임스탬프) 좌표 스트림이 있다. 맵매칭 엔진은 이 스트림을 받아 도로망 그래프(OpenStreetMap이나 Overture Maps의 transportation 레이어에서 구축)에서 각 관측점 주변 반경 안의 후보 도로 세그먼트들을 추출하고, HMM으로 가장 그럴듯한 경로를 복원한다. 뒷단에는 이렇게 깨끗해진 경로가 두 갈래로 쓰인다 — 라우팅 엔진이 실제 이동 거리와 소요 시간을 다시 계산해 ETA를 보정하는 데 쓰이거나, MapLibre 같은 지도 렌더러가 매끄러운 폴리라인으로 그려 사용자에게 보여주는 데 쓰인다. 맵매칭을 빼먹으면 이 두 뒷단 모두 지저분한 원시 좌표를 그대로 받아 품질이 떨어진다.

## 선택의 트레이드오프

| 방식 | 정확도 | 지연시간 | 교차로 모호성 처리 | 적합한 사용처 |
|---|---|---|---|---|
| 최근접 도로 스냅 | 낮음 | 매우 낮음 | 처리 못 함 | 프로토타입, 정확도 요구 낮은 시각화 |
| HMM 오프라인 배치(Viterbi) | 높음 | 전체 궤적 완료 후 일괄 처리 | 전체 궤적 문맥으로 해결 | 완료된 주행 로그 정산, 사후 분석 |
| HMM 온라인(슬라이딩 윈도우) | 중~높음 | 수 초 내 | 윈도우 범위 안에서만 해결 | 실시간 위치 추적, 라이브 ETA |
| 딥러닝 기반(시퀀스 모델) | 높음(데이터 품질에 의존) | 모델 크기에 따라 다름 | 학습 데이터 범위 내 일반화 | 대규모 궤적 데이터 보유 시 |

실무에서 가장 많이 선택하는 지점은 둘째와 셋째 사이다. 완료된 배달 건의 경로를 정산용으로 다시 그릴 때는 전체 궤적을 한 번에 보고 최적해를 찾는 오프라인 Viterbi가 유리하지만, 사용자에게 "지금 기사가 어디 있는지" 실시간으로 보여줘야 한다면 전체 궤적을 기다릴 수 없으므로 최근 N개 관측점만 보는 슬라이딩 윈도우 방식으로 타협해야 한다. 이 선택은 "지연시간을 얼마나 허용할 수 있는가"라는 제품 요구사항에서 역산해야지, 알고리즘 성능표만 보고 정할 문제가 아니다.

## 실제 프로젝트 진행 순서

1. **도로망 그래프부터 준비한다.** OpenStreetMap이나 Overture Maps의 도로 데이터를 받아 세그먼트 단위 그래프로 구축한다. 그래프 품질이 낮으면(끊긴 도로, 누락된 교차로) 이후 모든 단계의 정확도가 함께 낮아진다.
2. **공간 인덱스로 후보 세그먼트 검색을 빠르게 만든다.** 각 GPS 관측점마다 전체 도로망을 훑을 수 없으므로, R-tree 같은 공간 인덱스로 일정 반경 안의 후보 세그먼트만 빠르게 추려낸다.
3. **방출 확률과 전이 확률의 파라미터를 튜닝한다.** GPS 오차의 표준편차(보통 도심 기준 10~20m)를 방출 확률의 가우시안 파라미터로, 도로망 최단경로 거리와 직선거리의 비율을 전이 확률 감쇠 함수로 설정한다.
4. **Viterbi로 최적 경로를 복원하고 검증한다.** 실제 주행 블랙박스 영상이나 수동으로 확인한 경로와 대조해 매칭 정확도를 측정한다.
5. **실시간 요구사항이 있다면 윈도우 크기를 제품 요구와 맞춘다.** 지연 허용 범위와 교차로 밀집 지역의 모호성 해소 사이에서 윈도우 크기(보통 수십 초~수 분 분량의 관측점)를 정한다.
6. **샘플링 주기를 함께 점검한다.** GPS 전송 주기가 너무 길면(예: 30초 이상) 관측점 사이 거리가 멀어져 전이 확률 추정 자체가 불안정해지므로, 맵매칭 품질 문제를 알고리즘이 아니라 수집 주기에서 먼저 의심해야 할 때도 많다.

## 코드 예시 — 방출 확률 개념 구현

```python
import math

def emission_probability(gps_point, candidate_segment, gps_error_std=15.0):
    perpendicular_distance = distance_to_segment(gps_point, candidate_segment)
    exponent = -0.5 * (perpendicular_distance / gps_error_std) ** 2
    return math.exp(exponent) / (gps_error_std * math.sqrt(2 * math.pi))

def transition_probability(prev_candidate, curr_candidate, gps_straight_line_dist, beta=5.0):
    network_dist = shortest_path_distance(prev_candidate, curr_candidate)
    diff = abs(network_dist - gps_straight_line_dist)
    return (1 / beta) * math.exp(-diff / beta)
```

## 실무 포인트

**도로망 데이터 품질이 결과의 상한선을 정한다.** 아무리 HMM 파라미터를 잘 튜닝해도 도로망 그래프에 교차로 연결이 빠져 있거나 일방통행 정보가 틀리면, 맵매칭은 애초에 존재하지 않는 경로로 안내한다.

**고가도로·지하차도 같은 층(level) 구분을 놓치면 엉뚱하게 매칭된다.** 같은 위경도에 서로 다른 층의 도로가 겹쳐 있는 구간에서는 2차원 거리만으로 방출 확률을 계산하면 아래위 도로를 혼동한다. 도로망 데이터의 층 속성을 방출 확률 계산에 함께 반영해야 한다.

**실시간 온라인 매칭은 "확정"이 아니라 "잠정 결론"이라는 점을 사용자 경험에 반영한다.** 슬라이딩 윈도우 방식은 새 관측점이 들어오면 직전 구간의 매칭 결과가 바뀔 수 있다. 지도에 이미 그려둔 선을 매끄럽게 수정하는 UI 처리가 함께 필요하다.

## 마무리

- GPS 원시 좌표를 그대로 지도에 이으면 오차 때문에 경로가 지저분해지고, 단순 최근접 스냅은 교차로에서 엉뚱한 도로로 꺾이는 문제를 일으킨다.
- HMM 기반 맵매칭은 방출 확률(관측점과 도로의 거리)과 전이 확률(연속 관측점 사이 도로망 이동 가능성)을 함께 고려해 Viterbi로 가장 그럴듯한 경로를 복원하며, 이는 원시 GPS 스트림과 라우팅 엔진 사이의 전처리 계층에 위치한다.
- 실무 선택은 오프라인 배치(사후 정산)와 온라인 슬라이딩 윈도우(실시간 추적) 사이에서 지연시간 요구사항을 기준으로 정해야 하고, 도로망 데이터 품질과 층 구분 처리가 전체 정확도를 좌우한다.
