## HTTP만으로는 실시간이 어렵다

일반 HTTP는 "클라이언트가 요청하면 서버가 응답"하는 단방향 구조다. 서버가 새 데이터가 생겼다고 클라이언트에게 먼저 말을 걸 수 없다. 그래서 채팅이나 실시간 알림을 HTTP로 구현하려면 클라이언트가 계속 "새 거 있어요?"라고 물어봐야 한다(폴링). **웹소켓(WebSocket)**은 클라이언트와 서버가 연결을 한 번 맺으면 양쪽 모두 언제든 메시지를 보낼 수 있는 양방향 통신을 제공한다.

## HTTP 폴링 vs 웹소켓

| 항목 | HTTP 폴링 | 웹소켓 |
|---|---|---|
| 통신 방향 | 클라이언트가 물어봐야 함 | 양방향, 서버도 먼저 보냄 |
| 연결 | 요청마다 새로 맺음 | 한 번 맺어 계속 유지 |
| 실시간성 | 폴링 주기만큼 지연 | 즉시 전달 |
| 오버헤드 | 매 요청마다 헤더 등 반복 | 연결 후엔 가벼움 |

## 웹소켓의 동작

```text
1. 클라이언트가 HTTP로 "웹소켓으로 업그레이드하자"고 요청 (핸드셰이크)
2. 서버가 수락하면 연결이 웹소켓으로 전환됨
3. 이후 양쪽이 이 연결로 자유롭게 메시지를 주고받음
4. 어느 쪽이든 연결을 닫을 때까지 유지

-> "전화를 걸어두고 계속 통화"하는 것과 비슷하다.
   매번 편지를 새로 보내는 HTTP와 대조된다.
```

## 언제 웹소켓이 필요한가

```text
웹소켓이 적합:
- 채팅, 실시간 협업(문서 공동 편집)
- 실시간 게임, 주식·코인 시세
- 서버가 클라이언트에게 자주 먼저 알려야 하는 경우

웹소켓이 과한 경우:
- 가끔 오는 알림 -> SSE(Server-Sent Events)가 더 간단
- 단순 조회 -> 그냥 HTTP가 낫다
```

## 실무 포인트

- **모든 실시간이 웹소켓을 요구하는 것은 아니다.** 서버 → 클라이언트 한 방향 알림만 필요하면 SSE가 구현이 더 간단하다. 진짜 양방향이 필요할 때만 웹소켓을 쓰는 것이 좋다.
- **연결 유지 관리가 부담이 될 수 있다.** 웹소켓은 연결을 계속 열어두므로, 동시 접속자가 많으면 서버가 관리해야 할 연결 수가 늘어난다. 확장 시 연결 상태를 어떻게 분산할지 고려해야 한다.
- **연결이 끊길 수 있으니 재연결 로직이 필요하다.** 네트워크가 불안정하면 웹소켓 연결이 끊긴다. 클라이언트가 끊김을 감지해 자동으로 재연결하고, 끊긴 동안의 메시지를 어떻게 처리할지 설계해야 한다.

## 마무리 요약

- 웹소켓은 한 번 연결하면 양쪽이 언제든 메시지를 보낼 수 있는 양방향 통신을 제공한다.
- HTTP 폴링과 달리 서버도 먼저 메시지를 보낼 수 있어 실시간 채팅·협업·게임에 적합하다.
- 한 방향 알림만 필요하면 SSE가 더 간단하고, 웹소켓은 연결 관리·재연결 설계가 필요하다.
