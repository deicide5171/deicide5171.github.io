HTTP/2가 멀티플렉싱으로 "요청을 줄 세우던" 문제를 해결한 지 오래지만, 실무에서 모바일 사용자 비중이 높은 서비스의 지연시간 분포를 뜯어보면 여전히 꼬리 지연(p95, p99)이 유독 긴 구간이 발견된다. 원인을 추적해 보면 상당수가 애플리케이션이 아니라 전송 계층, 즉 TCP 자체에서 온다. 패킷 하나가 유실되면 그 뒤에 도착한 멀쩡한 데이터까지 전부 대기하는 TCP의 순서 보장이, 무손실에 가까운 유선망에서는 미덕이지만 손실이 잦은 무선망에서는 족쇄가 되기 때문이다.

HTTP/3는 이 문제를 프로토콜 튜닝이 아니라 전송 계층 교체로 풀었다. TCP를 버리고 UDP 위에 구현된 QUIC을 채택한 것이다. 현 시점 기준 주요 브라우저와 대형 CDN이 모두 HTTP/3를 지원하고, nginx도 안정 버전에서 HTTP/3 모듈을 제공하면서 "우리도 켜야 하나"를 고민하는 팀이 많아졌다. 이 글은 QUIC이 실제로 무엇을 바꾸는지(HOL 블로킹, 핸드셰이크, 커넥션 마이그레이션), 그리고 도입 전에 반드시 확인해야 할 것들을 정리한다.

## HOL 블로킹, HTTP/2는 절반만 해결했다

HTTP/1.1의 HOL(Head-of-Line) 블로킹은 애플리케이션 계층 문제였다. 하나의 커넥션에서 앞선 응답이 끝나야 다음 응답을 보낼 수 있었고, HTTP/2는 하나의 TCP 커넥션 안에 여러 스트림을 멀티플렉싱하는 것으로 이를 해결했다.

문제는 그 아래 계층이다. HTTP/2의 스트림이 논리적으로는 독립적이어도, 실제로는 하나의 TCP 바이트 스트림에 직렬화되어 흐른다. TCP는 스트림 개념을 모르기 때문에, 패킷 하나가 유실되면 그것이 어느 스트림의 데이터였는지와 무관하게 **재전송이 도착할 때까지 커넥션 전체의 수신 데이터 전달을 멈춘다**. 스트림 A의 패킷 손실이 이미 도착해 있는 스트림 B, C의 데이터까지 붙잡아 두는 셈이다. 오히려 커넥션을 6개씩 나눠 쓰던 HTTP/1.1보다 손실에 취약해지는 역설이 생긴다.

QUIC은 스트림을 전송 계층의 일급 개념으로 끌어올렸다. 손실 감지와 재전송이 스트림 단위로 이뤄지므로, 한 스트림의 패킷이 유실돼도 다른 스트림의 데이터는 즉시 애플리케이션에 전달된다. HOL 블로킹이 손실이 발생한 스트림 하나로 격리되는 것이다.

## 핸드셰이크: 전송과 암호화를 한 번에, 그리고 0-RTT

TCP + TLS 1.3 조합은 커넥션 수립에 TCP 3-way 핸드셰이크 1-RTT, TLS 핸드셰이크 1-RTT를 합쳐 첫 요청까지 최소 2-RTT가 필요하다. QUIC은 TLS 1.3을 전송 프로토콜 내부에 통합해 전송 수립과 키 교환을 같은 왕복에서 처리한다. 첫 연결이 **1-RTT**로 끝나고, 한 번 연결했던 서버라면 세션 티켓을 이용해 핸드셰이크 완료 전에 애플리케이션 데이터를 실어 보내는 **0-RTT**도 가능하다. RTT가 100ms를 넘는 국제 구간이나 모바일 환경에서는 이 차이가 체감 가능한 수준으로 나타난다.

또 하나 실무에서 유용한 것이 **커넥션 마이그레이션**이다. TCP 커넥션은 (출발지 IP, 포트, 목적지 IP, 포트) 4-튜플로 식별되므로 Wi-Fi에서 LTE로 넘어가는 순간 커넥션이 끊긴다. QUIC은 커넥션 ID로 연결을 식별하기 때문에 클라이언트 IP가 바뀌어도 세션이 유지된다. 이동 중 사용이 많은 모바일 앱 API라면 이 특성만으로도 도입 가치가 있다.

| 구분 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | QUIC (UDP 기반) |
| 멀티플렉싱 | 없음 (커넥션 병렬화) | 스트림 (앱 계층) | 스트림 (전송 계층) |
| HOL 블로킹 | 앱 + 전송 계층 모두 | 전송 계층에 잔존 | 스트림 단위로 격리 |
| 첫 연결 핸드셰이크 | 2-RTT (TLS 1.3 기준) | 2-RTT (TLS 1.3 기준) | 1-RTT (0-RTT 재개 가능) |
| IP 변경 시 | 커넥션 끊김 | 커넥션 끊김 | 커넥션 ID로 유지 |
| 암호화 | 선택 (사실상 필수) | 사실상 필수 | 프로토콜 자체에 내장 |

## 예제: nginx에서 HTTP/3 켜기

nginx 안정 버전 기준으로 HTTP/3 활성화는 아래처럼 구성한다. 핵심은 `listen ... quic`으로 UDP 443을 여는 것과, TCP로 접속한 클라이언트에게 `Alt-Svc` 헤더로 "HTTP/3도 가능하다"고 광고하는 것이다. 브라우저는 첫 방문에서는 TCP(HTTP/2)로 붙고, 이 헤더를 본 뒤부터 HTTP/3로 전환한다.

```nginx
server {
    # HTTP/3 (QUIC) — UDP 443
    listen 443 quic reuseport;
    # HTTP/2 폴백 — TCP 443 (반드시 함께 유지)
    listen 443 ssl;
    http2 on;

    server_name example.com;

    ssl_certificate     /etc/ssl/certs/example.com.pem;
    ssl_certificate_key /etc/ssl/private/example.com.key;
    ssl_protocols       TLSv1.3;

    # TCP로 온 클라이언트에게 HTTP/3 지원을 광고
    add_header Alt-Svc 'h3=":443"; ma=86400' always;

    location / {
        root /var/www/html;
    }
}
```

적용 후에는 커널의 UDP 버퍼 크기(`net.core.rmem_max` 등)를 함께 점검하고, 확인은 다음처럼 한다.

```bash
# HTTP/3로 직접 요청 (curl이 HTTP/3 지원 빌드여야 함)
curl -sI --http3 https://example.com | head -3
# 응답에 "HTTP/3 200"이 보이면 성공
```

## 함정: 0-RTT를 아무 요청에나 허용하면 안 된다

가장 흔한 안티패턴은 "0-RTT가 빠르다니 전부 켜자"이다. 0-RTT로 전송되는 조기 데이터(early data)는 **리플레이 공격에 취약하다**. 핸드셰이크가 완료되기 전에 보내는 데이터이므로, 공격자가 이 패킷을 캡처해 그대로 다시 보내면 서버가 같은 요청을 두 번 처리할 수 있다. `POST /orders` 같은 요청이 0-RTT로 들어와 재생되면 주문이 중복 생성되는 것이다.

올바른 접근은 이렇다. 첫째, 0-RTT는 GET처럼 멱등한 요청에만 허용한다. 둘째, 리버스 프록시가 조기 데이터로 받은 요청에 `Early-Data: 1` 헤더를 붙여 백엔드로 넘기게 하고, 백엔드는 상태를 바꾸는 요청이라면 `425 Too Early`로 거부해 클라이언트가 핸드셰이크 완료 후 재시도하게 만든다. 이 방어선 없이 0-RTT를 켜는 것은 성능 몇십 ms를 얻고 결제 중복 리스크를 떠안는 거래다. 확신이 없다면 0-RTT는 끄고 1-RTT만으로 시작해도 이득의 대부분을 챙길 수 있다.

## 언제 켜고, 언제 미뤄야 하나

**켜야 할 때**: 모바일·무선 사용자 비중이 높고, 손실률이 있는 네트워크에서 꼬리 지연이 문제이며, 국제 구간처럼 RTT가 긴 트래픽이 많은 대외 서비스. CDN 뒤에 있다면 CDN의 HTTP/3 옵션을 켜는 것만으로 엣지 구간의 이득을 얻을 수 있어 시작 비용도 낮다.

**미뤄도 될 때**: 데이터센터 내부의 서비스 간 통신이다. 내부망은 손실률이 사실상 0이고 RTT가 밀리초 미만이라 QUIC의 장점이 발휘될 무대가 없다. 오히려 QUIC은 암호화·패킷 처리가 사용자 공간에서 이뤄져 같은 처리량에서 TCP보다 CPU를 더 쓰는 경향이 있고, TCP가 누려온 커널·NIC 오프로드 최적화의 혜택도 아직 온전히 받지 못한다. 내부 gRPC 통신을 서둘러 HTTP/3로 바꿀 이유는 없다.

도입 시 체크리스트도 짚어두자. ① 방화벽·보안장비에서 **UDP 443 아웃바운드가 막힌 기업망**이 존재하므로 TCP 폴백 경로는 절대 제거하면 안 된다. ② L4 로드밸런서가 4-튜플 해싱만 지원하면 커넥션 마이그레이션 시 다른 백엔드로 패킷이 흘러갈 수 있어, 커넥션 ID 기반 라우팅 지원 여부를 확인해야 한다. ③ QUIC은 헤더까지 암호화되므로 기존 패킷 기반 모니터링 장비가 내용을 보지 못한다. 관측은 서버/클라이언트 측 로그와 qlog 같은 엔드포인트 계측으로 옮겨야 한다.

## 마무리 요약

- HTTP/2는 애플리케이션 계층의 HOL 블로킹만 해결했고, QUIC은 스트림을 전송 계층으로 내려 손실의 영향 범위를 스트림 하나로 격리한다.
- QUIC은 TLS 1.3 통합으로 첫 연결 1-RTT, 재연결 0-RTT를 제공하지만, 0-RTT는 리플레이 위험 때문에 멱등 요청으로 제한하고 `425 Too Early` 처리를 갖춰야 한다.
- 대외 모바일 트래픽에는 이득이 크지만 내부 통신에는 CPU 비용 대비 실익이 적으며, UDP 차단 대비 TCP 폴백과 LB의 커넥션 ID 라우팅 확인이 필수다.
