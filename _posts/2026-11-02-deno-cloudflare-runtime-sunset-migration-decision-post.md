## 왜 지금 이 판단이 중요해졌는가

"우리 백엔드, Deno로 짰는데 괜찮나요?" 이 질문에 최근까지는 "Node 대비 기본 보안 샌드박스, TypeScript 네이티브 지원이 강점"이라고 답하면 충분했다. 그런데 Deno 팀이 Cloudflare에 합류하면서, 독자적인 Deno 런타임 개발을 1년간의 유지보수 기간 이후 종료하고 Deno Deploy도 그로부터 6개월 뒤 서비스를 종료한다는 공지가 나왔다. 복수의 소식통이 같은 내용을 전하고 있어 신뢰도가 낮은 루머는 아니다.

이건 단순한 "한 런타임이 사라진다"는 뉴스가 아니라, 빌더에게 실제 실행 과제를 던지는 사건이다. 이미 Deno로 서비스를 운영 중이라면 당장 다음 분기 로드맵에 "런타임 마이그레이션"이라는 항목을 넣어야 하는지 판단해야 하고, 지금 새 프로젝트를 고르는 입장이라면 이 사건 자체가 런타임 선택 기준에 새 변수를 추가한다. 중요한 건 "일단 공지가 났으니 전부 옮기자"는 패닉이 아니라, 우리 서비스의 Deno 의존도와 남은 유지보수 기간을 놓고 실제로 지금 움직여야 하는지를 계산하는 것이다.

## 전체 시스템에서의 위치

이 판단은 런타임 하나를 바꾸는 일처럼 보이지만, 실제로는 서비스 스택 전체를 관통한다. 런타임은 애플리케이션 코드와 OS·클라우드 인프라 사이에 있는 실행 계층이다. 여기가 바뀌면 그 위에 얹힌 패키지 생태계 호환성(npm 호환 레이어 차이), 배포 파이프라인(Deno Deploy 전용 설정), 내장 API 사용 범위(Deno.serve, 권한 플래그 등 Deno 고유 API), 그리고 모니터링·로깅 연동까지 전부 영향을 받는다.

즉 "런타임만 바꾸면 된다"는 생각은 틀렸다. 런타임 교체는 배포 인프라 교체, 의존성 호환성 재검증, 플랫폼 고유 API를 범용 API로 재작성하는 작업을 동시에 요구하는 시스템 전반의 변경이다. 이 영향 범위를 먼저 그려야, 마이그레이션 공수를 제대로 추정할 수 있다.

## 선택의 트레이드오프

| 기준 | Deno에 잔류 | Bun으로 이전 | Node.js로 이전 |
|---|---|---|---|
| 남은 지원 기간 | 1년 유지보수 + Deploy 6개월 유예 | 해당 없음(활발히 개발 중) | 해당 없음(LTS 체계로 장기 지원) |
| TypeScript 네이티브 지원 | 최상 — 설계 철학 자체 | 우수 — 트랜스파일 내장 | 별도 설정 필요(ts-node 등) |
| npm 생태계 호환성 | 호환 레이어 존재하나 간헐적 이슈 | 대부분 호환, 일부 네이티브 모듈 이슈 | 최상 — 생태계 기준점 자체 |
| 배포 플랫폼 | Deno Deploy 종료 예정 — 재검토 필수 | 다양한 플랫폼 지원 확대 중 | 가장 폭넓은 호스팅 선택지 |
| 마이그레이션 공수 | 0(단, 리스크 보유) | 중간 — API 유사도 높음 | 큼 — 권한 모델·일부 API 차이 |
| 장기 안정성 신호 | 낮음(공식 축소 발표) | 중간(단일 벤더 의존) | 높음(다자 거버넌스·오랜 검증) |

여기서 핵심은 "Deno 런타임 개발이 1년 뒤 끝난다"가 "내일 당장 서비스가 멈춘다"를 의미하지 않는다는 점이다. 유지보수 기간과 Deploy 유예 기간이 남아 있으므로, 당장 올인 마이그레이션을 할 필요는 없다. 다만 신규 기능을 Deno 고유 API에 계속 묶어두는 선택은 이제 명백히 기술부채를 늘리는 결정이 됐다.

## 실제 프로젝트 진행 순서

1. **Deno 의존도를 코드베이스 단위로 측정한다.** `Deno.*` 네임스페이스 직접 호출, Deno Deploy 전용 설정, Deno 전용 테스트·빌드 스크립트가 얼마나 퍼져 있는지 정량화한다. 의존도가 낮다면 마이그레이션 비용이 생각보다 적을 수 있다.
2. **Deno Deploy에 직접 묶인 부분부터 분리한다.** 서비스 종료 유예가 가장 짧은 지점이 배포 플랫폼이므로, 컨테이너 기반 배포(Docker + 범용 클라우드)로 먼저 바꿔두면 런타임 자체 교체는 나중으로 미뤄도 급하지 않다.
3. **신규 코드는 Deno 고유 API 대신 Web 표준 API(fetch, Request/Response 등)로 작성하도록 가이드를 바꾼다.** 이렇게 하면 나중에 Bun이나 Node로 옮길 때 변경 범위가 크게 줄어든다.
4. **마이그레이션 대상을 고를 때 팀의 TypeScript 의존도와 기존 npm 패키지 사용 범위를 함께 본다.** TypeScript 네이티브 경험을 유지하고 싶다면 Bun이 상대적으로 적은 변경으로 전환 가능하고, 생태계 안정성과 장기 지원을 최우선으로 두면 Node.js LTS가 더 안전하다.
5. **1년이라는 유지보수 기간을 마감일이 아니라 여유로 활용한다.** 급하게 전면 전환하기보다, 신규 서비스부터 새 런타임으로 시작하고 기존 서비스는 트래픽이 적은 구간부터 점진적으로 옮기는 단계적 전환 계획을 세운다.

## 실무 포인트

**"아직 1년 남았으니 괜찮다"와 "1년 동안 아무것도 안 해도 된다"는 다른 말이다.** 유지보수 기간은 보안 패치만 들어오는 기간이지, 새 기능이 계속 추가되는 기간이 아니다. 이 기간에 새로 추가하는 코드가 Deno 고유 기능에 계속 묶이면, 유예 기간이 끝나는 시점에 마이그레이션해야 할 범위만 더 커진다.

**단일 벤더 런타임을 고를 때는 항상 "이 벤더의 전략이 바뀌면 어떻게 되는가"를 설계에 넣어야 한다.** 이번 사건은 Deno만의 특수한 리스크가 아니라, 특정 회사가 주도하는 오픈소스 런타임 전반에 적용되는 구조적 리스크를 보여준 사례다. 다음에 새 런타임을 평가할 때는 거버넌스 구조(단일 회사 주도 vs 재단·다자 운영)를 성능 벤치마크만큼 중요하게 봐야 한다.

**팀 내부 설득에는 "지금 멈춰야 한다"보다 "지금부터 새 코드는 이식 가능하게 짜자"는 프레이밍이 더 현실적으로 받아들여진다.** 전면 중단 요청은 반발을 사기 쉽지만, 신규 코드 작성 가이드 변경은 기존 일정에 거의 영향을 주지 않으면서 실질적인 리스크를 줄인다.

## 마무리

- Deno 팀이 Cloudflare에 합류하며 독자 런타임 개발을 1년 뒤 종료하고 Deno Deploy도 6개월 뒤 종료하기로 한 공지는, Deno 기반 서비스에 즉각적인 위기가 아니라 계획된 전환 유예 기간을 준다.
- 런타임 교체는 애플리케이션 코드뿐 아니라 배포 인프라·패키지 호환성·플랫폼 고유 API까지 함께 바뀌는 시스템 전반의 변경이므로, 코드만 보고 공수를 추정하면 안 된다.
- 당장 전면 마이그레이션보다 Deno Deploy 의존 분리와 Web 표준 API로의 신규 코드 전환을 먼저 시작하고, 유지보수 기간을 단계적 전환의 여유로 활용하는 것이 현실적이다.
