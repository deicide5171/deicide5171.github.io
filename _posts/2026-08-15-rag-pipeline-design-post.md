## 왜 지금 이 이야기인가

RAG(Retrieval-Augmented Generation)는 이제 "해보면 되는" 기술이 아니라 "제대로 설계해야 하는" 시스템이 됐다. 초기에는 문서를 적당히 잘라 임베딩하고 벡터DB에 넣기만 해도 데모는 그럴듯하게 동작했지만, 실제 서비스로 넘어가면 검색 품질이 곧바로 답변 품질의 상한선이 된다는 사실이 드러난다. LLM이 아무리 똑똑해도 검색된 컨텍스트가 부실하면 환각(hallucination)만 그럴듯하게 포장될 뿐이다.

최근에는 순수 벡터 검색만으로는 부족하다는 공감대가 커지면서 하이브리드 검색, 재순위화(reranking), 청킹 전략 최적화 등 파이프라인 각 단계를 세밀하게 튜닝하는 흐름이 자리 잡고 있다. 이 글에서는 RAG 파이프라인을 단계별로 나눠 각 단계에서 무엇을 고민해야 하는지 정리한다.

## RAG 파이프라인 단계

| 단계 | 핵심 고려사항 |
|---|---|
| 문서 수집 | 포맷 정규화(PDF/HTML/표), 메타데이터 보존, 증분 인덱싱 |
| 청킹 | 크기, 오버랩, 의미 단위 분리 여부 |
| 임베딩 | 모델 선택, 다국어 지원, 차원 수와 비용 |
| 벡터DB | ANN 인덱스 종류, 필터링(메타데이터) 지원 |
| 검색 | top-k, 하이브리드(BM25+벡터) 결합 방식 |
| 재순위화 | cross-encoder 기반 정밀 재정렬 |
| 컨텍스트 조립 | 토큰 예산 내 순서·중복 제거 |

각 단계는 독립적으로 최적화할 수 없다는 점이 중요하다. 예컨대 청킹을 너무 잘게 하면 재순위화 대상이 늘어나 지연시간이 커지고, 반대로 너무 크게 하면 임베딩이 뭉뚱그려져 검색 정밀도가 떨어진다.

## 청킹 전략: 크기와 오버랩의 트레이드오프

청킹은 RAG 품질을 좌우하는 가장 저평가된 단계로 보인다. 흔히 쓰이는 방식은 다음과 같다.

- **고정 크기 청킹**: 토큰 수 기준(예: 300~500토큰)으로 자르고 일부(10~20%) 오버랩을 둔다. 구현이 단순하지만 문장이나 문단 경계를 무시할 수 있다.
- **의미 기반 청킹(semantic chunking)**: 문장 임베딩 유사도가 급격히 떨어지는 지점을 경계로 삼는다. 품질은 좋지만 전처리 비용이 늘어난다.
- **구조 기반 청킹**: 마크다운 헤딩, HTML 태그, 표 경계를 활용해 문서 구조를 그대로 반영한다.

오버랩을 너무 넉넉히 주면 같은 정보가 여러 청크에 중복 저장되어 인덱스 크기와 검색 노이즈가 늘어나고, 반대로 오버랩이 없으면 문맥이 청크 경계에서 끊겨 중요한 문장이 반쪽만 검색되는 문제가 생긴다. 정답은 도메인에 따라 다르며, 실무에서는 300~800토큰 범위에서 여러 값을 오프라인 평가로 비교해보는 방식이 일반적으로 보인다.

## 하이브리드 검색과 재순위화

벡터 검색은 의미적 유사도에는 강하지만 정확한 키워드·고유명사·코드 식별자 매칭에는 약점이 있다. 이를 보완하기 위해 BM25 같은 어휘 기반 검색과 벡터 검색을 함께 사용하고, 두 결과를 RRF(Reciprocal Rank Fusion) 등으로 결합하는 하이브리드 검색이 널리 쓰인다.

```python
def reciprocal_rank_fusion(bm25_results, vector_results, k=60):
    scores = {}
    for rank, doc_id in enumerate(bm25_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    for rank, doc_id in enumerate(vector_results):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

하이브리드 검색으로 top-50 정도를 넉넉히 뽑은 뒤, cross-encoder 기반 재순위화 모델(Cohere Rerank, BGE-reranker 등)로 상위 3~10개만 추려 LLM 컨텍스트에 넣는 2단계 구조가 정밀도와 비용의 균형을 맞추는 방식으로 자주 언급된다.

```yaml
retrieval:
  bm25_top_k: 50
  vector_top_k: 50
  fusion: rrf
  rerank:
    model: bge-reranker-large
    top_n: 8
```

## 평가 방법

검색 품질은 감이 아니라 지표로 확인해야 한다. 대표적으로 다음을 본다.

| 지표 | 의미 |
|---|---|
| Precision@k | 상위 k개 중 실제 관련 문서 비율 |
| Recall@k | 전체 관련 문서 중 상위 k에 포함된 비율 |
| MRR | 첫 정답이 등장한 순위의 역수 평균 |
| nDCG | 순위 가중치를 반영한 랭킹 품질 |
| Faithfulness | 생성 답변이 검색된 컨텍스트에 근거하는 정도 |

질문-정답-근거문서 쌍으로 구성된 골든셋을 만들어 청킹 크기, top-k, 재순위화 유무를 바꿔가며 A/B로 비교하는 것이 가장 확실한 방법으로 보인다.

## 실무 포인트와 주의사항

- 청킹 파라미터는 한 번 정하고 끝내는 게 아니라 문서 유형이 바뀔 때마다 재검증해야 한다.
- 메타데이터 필터링(날짜, 부서, 권한 등)을 벡터 검색과 함께 지원하지 않으면 실무에서 바로 발목을 잡힌다.
- 재순위화는 지연시간을 늘리므로 top-k 후보 수와 SLA를 함께 고려해야 한다.
- 컨텍스트 조립 시 같은 내용의 중복 청크를 제거하지 않으면 토큰 낭비와 답변 품질 저하로 이어진다.

## 3줄 요약

- RAG 품질의 상한선은 검색 품질이며, 청킹·하이브리드 검색·재순위화가 핵심 레버다.
- 청킹은 고정/의미/구조 기반 중 도메인에 맞는 방식을 오프라인 평가로 골라야 한다.
- Precision@k, Recall@k, Faithfulness 같은 지표로 파이프라인 변경 효과를 정량 검증해야 한다.
