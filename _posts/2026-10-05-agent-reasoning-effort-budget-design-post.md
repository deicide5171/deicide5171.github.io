## 왜 지금 이 문제가 불거지는가

"가끔 에이전트가 틀린 답을 내니까 더 꼼꼼히 생각하게 해주세요." 이 요구를 들으면 가장 쉬운 해법은 확장 추론(extended thinking)을 항상 켜두는 것처럼 보인다. 그런데 같은 제품의 다른 화면에서는 정반대 요구가 들어온다. "응답이 너무 느려요, 토큰 비용도 감당이 안 돼요." 하나의 에이전트 세션이 결과를 내기까지 천만 토큰 가까이 태울 수 있다는 보고가 나올 만큼, 추론을 많이 시킬수록 정확도는 오르지만 지연시간과 비용이 같이 치솟는 구조다. 두 요구를 동시에 만족시키려면 "항상 많이 생각하게 할지, 항상 적게 생각하게 할지"의 이분법이 아니라 **작업마다 추론 예산을 다르게 배정하는 설계**가 필요하다.

API 쪽의 변화도 이 방향을 가리킨다. 한동안은 "토큰 N개만큼 생각해"처럼 추론 깊이를 수동으로 지정하는 방식이 표준이었지만, 최근에는 "이 작업이 얼마나 어려운지 알아서 판단해서 필요한 만큼만 생각해"로 API 설계 자체가 옮겨가고 있다 — 실제로 일부 최신 모델에서는 수동 추론 예산 지정이 아예 거부되고, 모델이 요청의 난이도를 보고 스스로 추론 깊이를 결정하는 방식으로 바뀌었다. 이 변화는 빌더에게 "더 이상 신경 쓸 필요 없다"는 뜻이 아니라, **추론 예산을 어느 레이어에서 통제할 것인가**라는 질문을 모델 내부에서 애플리케이션 설계 레벨로 옮겨 놓았다는 뜻이다.

## 요구사항을 기술 문제로 번역하기

"정확하게 답해주세요"라는 말은 실제로 세 가지 서로 다른 설계 문제를 품고 있다. 첫째, **작업 난이도에 따라 추론 깊이를 다르게 배정해야 하는 문제**(단순 조회와 다단계 추론을 같은 예산으로 다루면 안 된다). 둘째, **세션 전체의 비용을 토큰 단위가 아니라 턴 단위로 통제해야 하는 문제**(한 번의 긴 추론보다 여러 턴에 걸친 누적 비용이 실제 청구서를 결정한다). 셋째, **지연시간에 민감한 경로에서는 추론 자체를 줄이거나 체감 대기시간을 다르게 설계해야 하는 문제**(채팅 UI에서 추론을 켜면 응답까지 수십~수백 초가 걸릴 수 있다). 이 세 문제를 뭉뚱그려 "똑똑하게 만들어주세요"로 접근하면, 모든 요청에 가장 비싼 설정을 쓰거나 반대로 정확도가 필요한 곳까지 줄여버리는 실수로 이어진다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-05-agent-reasoning-effort-budget-design-1.svg" alt="들어오는 요청이 난이도·지연 민감도 분류기를 거쳐 경량 모델과 저예산 추론 또는 프론티어 모델과 고예산 추론으로 라우팅되고, 세션 예산 매니저가 턴별 누적 토큰을 추적하다 한도에 도달하면 다운그레이드하거나 사람에게 에스컬레이션하는 구조도" style="width:100%;">

요청이 들어오면 가장 먼저 **난이도·지연 민감도 분류기**를 거친다. 단순 조회, 형식 변환처럼 실패 비용이 낮은 작업은 경량 모델과 낮은 추론 예산으로 바로 라우팅하고, 다단계 계획이 필요하거나 실패 시 되돌리기 어려운 작업은 프론티어 모델과 높은 추론 예산으로 보낸다. 이 라우팅 뒤에는 **세션 예산 매니저**가 있어, 단일 요청의 토큰 수가 아니라 세션 전체에 걸친 누적 비용을 턴 단위로 추적한다. 에이전트가 여러 번의 턴에 걸쳐 같은 작업을 반복하면, 개별 턴은 저렴해 보여도 전체 세션은 쉽게 예산을 넘을 수 있기 때문이다. 누적 비용이 한도에 가까워지면 두 가지 선택지가 있다 — 남은 턴을 더 저렴한 모델로 다운그레이드하거나, 자동 진행을 멈추고 사람에게 에스컬레이션하는 것이다. 지연시간이 중요한 대화형 경로에서는 여기에 더해, 깊은 추론이 끝나기를 기다리게 하는 대신 짧은 예고 응답(preamble)을 먼저 보여주고 이어서 본 답변을 내는 패턴도 함께 설계된다.

## 선택의 트레이드오프

| 전략 | 정확도 | 비용·지연 | 구현 복잡도 | 적합한 상황 |
|---|---|---|---|---|
| 항상 최대 추론 | 가장 높음 | 가장 나쁨 | 가장 낮음 | 실패 비용이 극도로 큰 소수 작업 |
| 항상 최소 추론 | 가장 낮음 | 가장 좋음 | 가장 낮음 | 단순 반복 작업만 있는 경우 |
| 작업 유형별 고정 라우팅 | 중간~높음 | 중간 | 중간 | 작업 유형이 명확히 구분되는 제품 |
| 모델 자율 판단(최신 방식) | 높음(평균적으로) | 중간~좋음 | 낮음(모델에 위임) | 작업 다양성이 크고 세밀한 규칙 설계가 부담될 때 |
| 세션 단위 턴 예산 캡 | 중간~높음 | 가장 통제 가능 | 높음 | 장시간 실행되는 에이전트 세션 |

표에서 주목할 지점은 "모델 자율 판단"이 구현 복잡도를 낮춰주지만 비용 통제를 완전히 대체하지는 못한다는 것이다. 모델이 작업 난이도를 보고 스스로 추론 깊이를 정하더라도, 그 판단이 누적되는 세션 전체의 비용 상한까지 알아서 지켜주지는 않는다. 그래서 실제 운영에서는 모델 자율 판단과 턴 단위 예산 캡을 같이 두는 조합이 흔하다 — 개별 턴의 추론 깊이는 모델에 맡기고, 세션 전체의 소비는 애플리케이션 레이어에서 상한을 건다.

## 실제 프로젝트 진행 순서

1. **현재 처리하는 작업들을 난이도와 지연 민감도 두 축으로 분류한다.** 실패했을 때 되돌리기 쉬운지, 사용자가 즉시 응답을 기다리는지를 기준으로 사분면을 나눈다.
2. **저위험·저지연 민감 경로부터 경량 모델과 낮은 추론 예산을 적용해 본다.** 이 구간에서 정확도 저하 없이 비용이 얼마나 줄어드는지 먼저 데이터로 확인한다.
3. **세션 단위 토큰 상한과 에스컬레이션 정책을 설계한다.** 개별 요청이 아니라 세션 전체의 누적 소비를 기준으로 한도를 정하고, 한도 도달 시 다운그레이드할지 사람에게 넘길지 미리 정해둔다.
4. **지연 민감 경로에는 예고 응답 패턴을 적용한다.** 깊은 추론이 끝날 때까지 아무 반응이 없는 UI는 체감 대기시간을 실제보다 훨씬 길게 느끼게 만든다.
5. **비용 절감분을 실제 작업 성공률과 함께 추적한다.** 추론 예산을 줄인 뒤 비용은 내려갔는데 재작업·오류 처리 비용이 늘었다면, 절감이 아니라 비용을 다른 곳으로 옮긴 것일 수 있다.

## 실무 포인트

**"항상 최대 추론 모드"를 기본값으로 두지 않는다.** 소수의 고위험 작업을 위해 설계한 설정을 전체 트래픽에 기본 적용하면, 체감하지 못하는 사이 비용과 지연이 함께 불어난다.

**턴 단위 예산 추적 없이 모델의 자율 판단만 믿지 않는다.** 모델이 개별 요청의 추론 깊이를 알아서 조절해도, 여러 턴에 걸쳐 누적되는 세션 전체 비용은 애플리케이션이 별도로 관리해야 한다.

**추론 예산을 낮췄을 때의 실패를 어디서 흡수할지 미리 정한다.** 저예산 경로에서 실패가 늘어나는 것 자체는 문제가 아니다 — 그 실패를 사람에게 넘길지, 자동으로 고예산 경로로 재시도할지를 설계해두지 않은 것이 문제다.

## 마무리

- "정확하게 답해주세요"는 작업별 추론 깊이, 세션 단위 비용 통제, 지연 민감 경로 설계라는 서로 다른 세 가지 문제를 뭉뚱그린 요구이므로 분리해서 접근해야 한다.
- 추론 예산을 모델에 수동으로 지정하던 방식에서 모델이 난이도를 보고 스스로 판단하는 방식으로 API가 옮겨가고 있지만, 이것이 세션 전체의 비용 상한까지 대신 지켜주지는 않는다.
- 난이도·지연 민감도로 요청을 분류해 라우팅하고, 세션 단위 턴 예산 캡과 에스컬레이션 정책을 함께 설계해야 정확도와 비용·지연 사이의 트레이드오프를 실제로 통제할 수 있다.
