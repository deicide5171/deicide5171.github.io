## 왜 지금 이 판단이 필요한가

"3D 건물 모델은 이미 떠 있는데, 그 위에 도로 경계선이랑 행정구역 라벨도 같이 보여주세요." 3D Tiles로 도시 전체를 올려둔 서비스에 이런 요구가 들어오면, 생각보다 간단하지 않다. 3D Tiles는 메쉬·포인트클라우드 같은 3차원 지오메트리를 위한 타일 피라미드이고, 도로·경계선·라벨 같은 벡터 데이터는 전혀 다른 포맷(MVT)과 전혀 다른 타일 그리드로 서빙된다. 지금까지는 이 둘을 각자의 스트리밍 파이프라인으로 따로 로드한 뒤 화면에서 겹쳐 그리는 수밖에 없었고, 줌 레벨이나 타일 경계가 미묘하게 어긋나면 라벨이 건물을 뚫고 지나가거나 엉뚱한 높이에 떠 있는 문제가 났다.

2026년 9월 2일 Cesium이 공개한 Vector Tiles 기술 프리뷰는 이 문제를 "두 파이프라인을 잘 맞추는 법"이 아니라 "애초에 하나의 파이프라인으로 합친다"는 방향으로 풀려는 시도다. 벡터 지오메트리를 3D Tiles 1.1과 glTF 확장 포맷으로 직접 인코딩해, 같은 타일셋·같은 LOD 체계 안에서 메쉬와 벡터를 함께 스트리밍한다. 아직 정식 스펙이 아니라 프리뷰 단계이지만, 올해 안에 3D Tiles 2.0으로 승격될 예정이라 빌더 입장에서는 지금부터 설계 판단을 준비해 둘 가치가 있다.

## 핵심 개념 1 — 기존 방식은 왜 어긋나는가

기존 구조에서 메쉬 타일 피라미드는 지오메트리 복잡도와 화면상 크기(screen-space error)를 기준으로 LOD를 나누고, 벡터 타일 피라미드는 보통 슬리피맵 방식의 정수 줌 레벨(z/x/y)로 LOD를 나눈다. 두 체계의 타일 경계와 갱신 주기가 다르기 때문에, 카메라가 움직일 때 메쉬는 아직 저해상도 타일을 보여주는데 벡터 라벨은 이미 고해상도 타일로 전환되는 식의 "따로 노는" 현상이 생긴다. 게다가 좌표계 변환(지형 고도, 건물 높이 보정)도 두 파이프라인에서 각각 따로 맞춰야 해서, 합성 지점에서 미세한 오차가 누적되기 쉽다.

## 핵심 개념 2 — Vector Tiles 프리뷰가 바꾸는 것

Cesium의 접근은 벡터 피처(선·폴리곤·라벨 앵커)를 3D Tiles 타일셋 안의 glTF 확장 데이터로 집어넣는 것이다. 이렇게 하면 벡터 데이터도 메쉬와 똑같은 implicit tiling 구조, 똑같은 screen-space error 기준 LOD 전환을 따르게 되어, 카메라가 움직여도 메쉬와 벡터가 같은 타이밍에 같은 해상도로 전환된다. 동시에 이번 프리뷰가 함께 가져온 glTF 확장은 공통 지오메트리 패턴을 더 압축적으로 인코딩해, 기존 glTF 대비 파일 크기를 최대 5배까지 줄이는 사례가 보고됐다 — 이 압축 이득은 벡터 데이터뿐 아니라 기존 메쉬 타일에도 적용될 수 있어, 순수 네트워크 대역폭 절감 관점에서도 독립적으로 검토할 가치가 있다.

다만 "프리뷰"라는 표현을 가볍게 넘기면 안 된다. 정식 3D Tiles 2.0으로 OGC에 승격되기 전까지는 포맷 세부 사항이 바뀔 수 있고, CesiumJS 외 다른 3D Tiles 클라이언트(일부 상용 뷰어, 타 엔진 플러그인)가 이 확장을 바로 지원하지 않을 가능성이 높다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-18-cesium-3d-tiles-vector-tiles-gltf-compression-1.svg" alt="기존에는 메쉬 타일 파이프라인과 벡터 타일 파이프라인이 분리되어 화면에서 합성되지만, Vector Tiles 프리뷰에서는 하나의 3D Tiles 타일셋 안에서 메쉬와 벡터가 함께 스트리밍되는 구조 비교도" style="width:100%;">

기존 구조에서는 원본 데이터(3D 모델, 벡터 소스)가 각자의 타일링 파이프라인을 거쳐 별도의 타일셋으로 서버에 올라가고, 클라이언트는 두 스트림을 독립적으로 요청해 화면 합성 단계에서 좌표를 맞춘다. 프리뷰 구조에서는 벡터 피처가 타일링 단계에서부터 3D Tiles glTF 확장으로 인코딩되어, 클라이언트는 하나의 타일셋 요청만으로 메쉬와 벡터를 동시에 받는다 — 합성 지점이 서버 쪽 타일링 단계로 옮겨가는 셈이다.

## 선택의 트레이드오프

| 접근 | 강점 | 약점 | 적합한 상황 |
|---|---|---|---|
| 기존 분리형(3D Tiles + MVT 오버레이) | 안정적, 모든 Cesium 버전·클라이언트에서 검증됨 | LOD·좌표 동기화를 직접 관리해야 함 | 지금 당장 운영 중인 프로덕션 서비스 |
| Cesium Vector Tiles 프리뷰 | LOD·좌표계가 자동으로 맞음, glTF 압축 이득 | 스펙 미확정, 클라이언트 호환성 제한적 | 신규 PoC, 2.0 정식화 이후 전환을 염두에 둔 실험 |
| OpenLayers+three.js 식 합성(별도 레이어 카메라 동기화) | 기존 2D 벡터 지도 자산을 그대로 유지 | 특정 오브젝트만 3D로 얹는 용도에 한정, 대규모 메쉬 스트리밍엔 부적합 | 2D 지도 위에 소수 3D 오브젝트만 필요한 경우 |

세 번째 옵션은 "지도 전체를 3D로 바꾸지 않고 특정 건물만 3D로 띄운다"는, 이전에 다룬 OpenLayers·three.js 합성 설계와 같은 선상에 있다. 반대로 도시 전체 3D Tiles를 이미 운용 중이고 그 위에 벡터 레이어를 정합성 있게 얹어야 하는 경우라면 Vector Tiles 쪽이 구조적으로 더 맞는 방향이다 — 단, 아직 프로덕션에 쓸 단계는 아니다.

## 실제 프로젝트 진행 순서

1. **지금 겪는 어긋남이 실제로 사용자 경험을 해치는 수준인지 먼저 측정한다.** 라벨이 몇 픽셀 어긋나는 수준이면 기존 분리형을 유지하며 LOD 전환 타이밍만 보정하는 게 더 저비용일 수 있다.
2. **운영 서비스와 분리된 PoC 환경에서 Vector Tiles 프리뷰를 먼저 검증한다.** 정식 스펙이 아니므로 운영 코드베이스에 바로 통합하지 않는다.
3. **glTF 압축 확장만 독립적으로 분리해 기존 메쉬 타일에 적용해 본다.** 벡터 통합과 별개로 대역폭 절감만 먼저 가져올 수 있는지 확인한다.
4. **3D Tiles 2.0이 OGC 정식 표준으로 승격되는 시점을 모니터링한다.** 승격 이후 CesiumJS와 주요 클라이언트의 지원 상태를 재확인한 뒤 프로덕션 전환을 결정한다.

```javascript
// 기존 분리형 구조에서 메쉬 타일셋과 벡터 레이어를 각각 로드하는 예
const tileset = await Cesium.Cesium3DTileset.fromUrl("buildings/tileset.json");
viewer.scene.primitives.add(tileset);

const vectorLayer = new Cesium.GeoJsonDataSource();
await vectorLayer.load("roads.geojson", { clampToGround: true });
viewer.dataSources.add(vectorLayer); // LOD·좌표 동기화는 별도로 관리해야 함
```

## 마무리 요약

- 3D 건물 위에 벡터 데이터를 얹는 요구는 메쉬 타일과 벡터 타일이라는 서로 다른 LOD·좌표 체계를 어떻게 맞출지의 문제다.
- Cesium Vector Tiles 프리뷰는 벡터를 3D Tiles glTF 확장으로 인코딩해 하나의 타일셋·LOD 체계로 합치고, 덤으로 glTF 압축을 최대 5배까지 끌어올린다.
- 아직 기술 프리뷰 단계이므로 운영 서비스는 기존 분리형을 유지하되, PoC로 미리 검증하고 3D Tiles 2.0 정식화 시점을 지켜보는 것이 현실적인 진행 순서다.
