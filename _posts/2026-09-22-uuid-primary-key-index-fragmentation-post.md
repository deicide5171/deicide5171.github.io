## 왜 UUID 기본키가 처음엔 괜찮다가 나중에 문제가 되나

여러 서버에서 동시에 레코드를 생성해도 충돌 걱정이 없다는 이유로, 많은 팀이 auto-increment 대신 UUID(v4)를 기본키로 채택한다. 개발 초기, 데이터가 몇만 건 수준일 때는 이 선택의 대가가 거의 눈에 띄지 않는다. 문제는 테이블이 수천만 건 이상으로 커지고 나서야 서서히 드러난다는 점이다. 같은 스펙의 서버인데 INSERT 처리량이 예전만 못하고, 인덱스가 차지하는 디스크 용량이 예상보다 훨씬 크다는 사실을 뒤늦게 깨닫는다.

이 현상의 원인을 이해하려면 관계형 DB의 기본키 인덱스가 대부분 **B-tree 구조**로 만들어진다는 사실부터 짚어야 한다. B-tree는 정렬된 순서로 데이터를 저장하는 구조이기 때문에, 새로 삽입되는 값이 기존 값들과 어떤 순서 관계를 갖는지에 따라 성능이 크게 갈린다.

## auto-increment는 왜 빠른가 — 순차 삽입의 이점

auto-increment(또는 시퀀스) 기반 기본키는 새 레코드가 항상 "지금까지 중 가장 큰 값"으로 생성된다. B-tree 인덱스 입장에서 이는 언제나 맨 오른쪽 끝 페이지에만 값을 추가하면 되는 가장 이상적인 상황이다. 페이지 분할(page split)이 거의 일어나지 않고, 디스크에 기록되는 위치도 순차적이라 물리적인 쓰기 효율도 높다.

```sql
-- auto-increment: 항상 마지막 페이지에 순차적으로 추가됨
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    ...
);
```

## UUID(v4)는 왜 느려지는가 — 무작위 삽입의 대가

반면 UUID v4는 값 자체가 완전히 무작위로 생성된다. 새로 삽입될 값이 인덱스 트리의 어느 위치에 꽂힐지 예측할 수 없다는 뜻이다. 이미 가득 찬 중간 페이지에 새 값이 끼어들어야 하는 상황이 반복되면, DB는 그 페이지를 둘로 쪼개는 **페이지 분할**을 계속 수행해야 한다.

```sql
-- UUID v4: 완전히 무작위라 인덱스 트리 전체에 흩어져 삽입됨
CREATE TABLE orders (
    id CHAR(36) PRIMARY KEY DEFAULT (UUID()),
    ...
);
```

페이지 분할이 반복되면 두 가지 문제가 함께 커진다. 첫째, 분할된 페이지들 사이에 빈 공간이 많이 남아 인덱스가 실제 데이터양보다 훨씬 크게 부풀어 오른다(단편화). 둘째, 논리적으로는 연속된 인덱스 항목이 물리적으로는 디스크 여기저기에 흩어지면서, 인덱스를 순서대로 읽는 범위 쿼리의 디스크 I/O가 늘어난다.

## 잘못된 절충안: 기본키는 auto-increment, 외부 노출용은 별도 UUID

이 문제를 접한 팀 중 일부는 "그럼 UUID를 아예 안 쓰면 되지 않나"라는 결론으로 건너뛴다. 하지만 분산 환경에서 여러 서비스가 독립적으로 ID를 발급해야 하거나, URL에 순차 ID를 그대로 노출하고 싶지 않은 보안상의 이유는 여전히 유효하다. 그래서 "내부 기본키는 auto-increment BIGINT, 외부에 노출하는 식별자는 별도 UUID 컬럼"으로 분리하는 절충안이 널리 쓰인다. 다만 이 방식은 컬럼이 두 개로 늘고 외부 UUID로 조회할 때 별도 인덱스가 하나 더 필요하다는 비용이 따른다.

## 더 나은 대안: 정렬 가능한 UUID (UUIDv7, ULID)

최근 표준화된 UUIDv7이나 ULID는 이 딜레마를 다른 방식으로 푼다. 값의 앞부분에 밀리초 단위 타임스탬프를 넣고 뒷부분만 무작위로 채워, **전역적으로 고유하면서도 생성 순서대로 정렬되는** 식별자를 만든다.

```sql
-- UUIDv7: 앞부분이 타임스탬프라 시간순으로 자연스럽게 정렬됨
-- 018f4d2a-1234-7890-abcd-ef1234567890
--  └──────┬──────┘
--     타임스탬프 (48비트)
```

이렇게 하면 UUID의 장점(분산 환경에서 충돌 없는 생성, ID 추측 방지)을 유지하면서도, 새 값이 거의 항상 B-tree의 오른쪽 끝 근처에 삽입되어 auto-increment에 가까운 삽입 성능을 얻을 수 있다.

| 방식 | 분산 생성 | 삽입 성능 | ID 추측 방지 | 정렬성 |
|---|---|---|---|---|
| auto-increment | 어려움(중앙 시퀀스 필요) | 우수 | 취약 | 우수 |
| UUID v4 | 쉬움 | 나쁨(단편화) | 우수 | 없음 |
| UUIDv7 / ULID | 쉬움 | 우수에 가까움 | 우수 | 우수(생성 순서) |

## 실무 포인트

- **이미 UUID v4로 운영 중인 테이블을 당장 바꾸는 것은 신중해야 한다.** 기본키 타입 변경은 관련된 모든 외래키·인덱스에 영향을 주는 대규모 마이그레이션이다. 신규 테이블부터 UUIDv7을 채택하고, 기존 테이블은 성능 문제가 실제로 발목을 잡을 때 별도 프로젝트로 계획하는 편이 안전하다.
- **DB 엔진별 UUID 컬럼 타입 선택에 주의하라.** 일부 DB는 UUID를 문자열(CHAR(36))로 저장하면 이진 표현보다 공간을 더 차지한다. PostgreSQL의 네이티브 `UUID` 타입처럼 이진 저장을 지원하는 타입을 우선 고려한다.
- **정렬 가능한 ID라고 해서 시간 정보가 그대로 노출되는 것을 간과하지 마라.** UUIDv7의 타임스탬프 부분은 생성 시각을 유추할 수 있게 하므로, 완전한 비추측성이 필요한 보안 토큰 용도로는 부적합하다.

## 마무리 요약

- UUID v4를 기본키로 쓰면 B-tree 인덱스에 무작위로 삽입되어 페이지 분할과 단편화가 누적되고, 테이블이 커질수록 INSERT 성능과 인덱스 용량 모두 나빠진다.
- auto-increment는 항상 순차적으로 삽입되어 이 문제가 없지만 분산 환경에서의 ID 발급과 추측 방지라는 UUID의 장점을 포기해야 한다.
- UUIDv7·ULID 같은 정렬 가능한 식별자는 두 방식의 장점을 절충한 실전 대안으로, 신규 테이블 설계 시 우선 검토할 가치가 있다.
