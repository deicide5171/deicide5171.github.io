## 왜 지금 이 문제가 불거지는가

"에이전트가 뭘 하고 있는지 매번 물어보기 귀찮으니, 배포 상태나 현재 작업 큐를 채팅 옆에 계속 떠 있게 해주세요." 이런 요구를 받으면 먼저 Skill을 떠올리게 된다. 그런데 Skill은 모델에게 "이렇게 행동하라"는 지시문 묶음일 뿐, 화면에 패널을 그리는 수단이 아니다. MCP 도구를 붙여도 마찬가지다. 도구는 모델이 호출해 데이터를 받아오는 통로이지, 그 결과를 상시 보이는 위젯으로 유지하는 장치가 아니다. 지금까지 Claude Code를 확장하는 방법은 "모델의 행동을 바꾸는 것"과 "모델이 쓸 수 있는 도구를 늘리는 것" 두 갈래뿐이었고, "화면 자체를 바꾸는 것"은 빈 자리였다.

2026년 10월 1일 공개된 Claude Code Mods가 이 빈 자리를 채운다. Mod는 플러그인 형태로 배포되는 JavaScript·TypeScript 이벤트 핸들러로, 트랜스크립트 옆 패널이나 입력창 위 밴드 같은 렌더 사이트에 직접 UI를 그리고, 도구 호출 줄이나 스피너 같은 기존 요소의 스타일도 바꿀 수 있다. 확장점이 하나 늘었다는 것은 반갑지만, 동시에 "이 요구는 Skill인가 MCP 도구인가 Mod인가"를 매번 새로 판단해야 하는 숙제도 함께 생겼다.

## 요구사항을 세 갈래로 번역하기

사용자의 말 한 줄은 보통 세 가지 중 하나, 혹은 그 조합으로 번역된다. 첫째, "이럴 때는 이렇게 처리해주세요"는 **행동 지시**이므로 Skill의 영역이다. 둘째, "저 시스템 데이터를 가져와서 판단에 써주세요"는 **외부 연동**이므로 MCP 도구의 영역이다. 셋째, "이 정보를 화면에 계속 보여주세요" 또는 "이 UI 요소 모양을 바꿔주세요"는 **렌더링**이므로 이번에 추가된 Mod의 영역이다. 실무에서 걸려 넘어지는 지점은 세 번째를 두 번째로 잘못 번역하는 경우다. MCP 도구는 모델이 필요할 때 한 번 호출해 결과를 컨텍스트에 넣는 구조라, 사람이 쳐다보고 있는 동안 계속 갱신되는 화면을 만드는 데는 애초에 맞지 않는다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-30-claude-code-mods-extension-point-choice-1.svg" alt="사용자 요구가 행동 지시, 외부 연동, 렌더링 세 갈래로 번역되어 각각 Skill, MCP 도구, Mod로 이어지고, Mod만 터미널과 데스크톱 Code 탭에서 렌더되며 VS Code 패널과 Agent SDK에서는 훅만 실행되고 화면에는 나타나지 않는 구조도" style="width:100%;">

플러그인 하나 안에 Skill·MCP 서버·Mod가 함께 들어갈 수 있다는 점이 설계를 더 유연하게 만들지만, 동시에 실행 위치의 차이를 가린다. Skill은 모델의 시스템 프롬프트에 얹히므로 어디서 실행되든 동일하게 작동하고, MCP 도구는 서버만 떠 있으면 클라이언트를 가리지 않는다. 반면 Mod의 화면 렌더링은 **터미널과 데스크톱 앱의 Code 탭에서만** 그려진다. VS Code 채팅 패널에서는 훅 코드는 실행되지만 커스텀 패널·밴드는 화면에 나타나지 않고, Agent SDK나 `claude -p`로 돌리는 무인 실행 환경에서도 마찬가지다. 즉 Mod로 설계한 UI를 CI 파이프라인이나 백그라운드 자동화에 그대로 가져가면 그 부분만 조용히 사라진다.

## 선택의 트레이드오프

| 확장점 | 바꾸는 것 | 실행 위치 제약 | 보안 범위 | 적합한 요구 |
|---|---|---|---|---|
| Skill | 모델의 행동·절차 | 없음(어디서나 동일) | 낮음(지시문 텍스트) | "이런 상황엔 이렇게 하라" |
| MCP 도구 | 모델이 쓰는 외부 기능 | 서버 연결만 있으면 됨 | 중간(도구별 권한 범위) | "저 데이터를 가져와 판단에 써라" |
| Mod(UI) | 화면 자체 | 터미널·데스크톱 Code 탭만 | 높음(머신 전체 접근) | "이 정보를 상시 보여줘라" |

Mod의 보안 범위가 높다고 표시한 이유는, Mod가 Claude Code 프로세스 안에서 실행되는 임의의 JS/TS 코드라 사실상 로컬 머신 전체에 접근할 수 있기 때문이다. 외부 마켓플레이스에서 받은 Mod를 그대로 설치하는 것은 출처가 불분명한 VS Code 확장을 설치하는 것과 같은 수준의 신뢰 결정이다. 권한 프롬프트 화면만큼은 Mod가 덮어쓸 수 없게 막아둔 것도 이 때문이다.

## 실제 프로젝트 진행 순서

1. **요구를 셋 중 어디에 넣을지부터 가른다.** "항상 이렇게 동작해라"면 Skill로 끝날 일을 Mod로 만들지 않는다.
2. **UI가 꼭 필요한지, 꼭 상시 노출이어야 하는지 다시 확인한다.** 한 번 조회해 보여주는 정도면 MCP 도구 결과를 채팅에 출력하는 것으로 충분할 수 있다.
3. **이 UI가 실제로 쓰일 환경을 먼저 적는다.** 터미널·데스크톱 Code 탭에서만 쓰는가, 아니면 VS Code나 CI 무인 실행에서도 봐야 하는가. 후자가 섞여 있으면 Mod 단독 설계로는 구멍이 생긴다.
4. **렌더 사이트를 하나만 골라 최소 기능으로 먼저 만든다.** 패널 전체를 한 번에 설계하지 말고, 스피너 옆 상태 텍스트 하나처럼 작은 단위부터 붙여 렌더링 생명주기를 확인한다.
5. **배포 전 출처 검증 절차를 넣는다.** 사내 마켓플레이스에만 올리거나, 코드 리뷰를 거친 Mod만 설치하도록 팀 규칙을 먼저 정한다.

## 실무 포인트

**Mod를 "더 강력한 Skill"로 오해하지 않는다.** Mod는 화면을 그리는 수단이지 모델의 판단력을 더 똑똑하게 만드는 수단이 아니다. 행동을 바꾸고 싶으면 여전히 Skill이 맞는 자리다.

**VS Code·Agent SDK 사용자가 섞인 팀이면 Mod에 핵심 정보를 몰아주지 않는다.** 같은 팀 안에서도 터미널 사용자와 VS Code 사용자가 다른 경험을 하게 되므로, 중요한 상태는 채팅 응답 자체에도 남겨 두는 이중화가 필요하다.

**설치 전 Mod의 권한 범위를 코드 리뷰 대상으로 삼는다.** 플러그인 하나가 Skill·도구·Mod를 함께 담고 있으면, 리뷰할 때 UI 코드 부분만 따로 떼어 "이 코드가 로컬에서 무엇에 접근하는가"를 점검해야 한다.

## 마무리

- Claude Code Mods는 "모델의 행동을 바꾼다"(Skill), "모델이 쓰는 기능을 늘린다"(MCP 도구)에 이어 "화면 자체를 바꾼다"는 세 번째 확장점을 추가했다.
- Mod가 그리는 UI는 터미널과 데스크톱 Code 탭에서만 보이고 VS Code 패널과 Agent SDK·`claude -p` 환경에서는 나타나지 않으므로, 사용 환경이 섞인 팀은 핵심 정보를 UI에만 의존시키면 안 된다.
- Mod는 로컬 머신에 접근하는 임의 코드이므로 권한 프롬프트만 예외일 뿐 보안 범위가 가장 넓고, 도입 전 출처 검증과 코드 리뷰 절차가 반드시 선행되어야 한다.
