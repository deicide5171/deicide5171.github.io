## 왜 지금 이 판단이 필요한가

"우리 팀이 쓰는 Slack, Notion, GitHub, Figma, 사내 티켓 시스템까지 에이전트한테 다 붙여주세요." 요구 자체는 평범하다. 문제는 이 요구를 곧이곧대로 들어주면 벌어지는 일이다. MCP 서버 하나가 보통 10~15개 툴을 노출하는데, 이 서버를 10개쯤 붙이면 각 툴의 이름·설명·파라미터 스키마가 전부 매 턴 시스템 프롬프트에 통째로 실린다. 한 업계 측정치는 이 스키마 세금만으로 대화 시작 전에 이미 5만5천~14만 토큰이 날아간다고 보고한다. 캐싱으로 일부 완화되긴 하지만, 캐시가 미스되는 순간 그 비용이 고스란히 되돌아온다.

더 나쁜 건 토큰값이 아니라 **정확도 저하**다. 붙은 툴이 많아질수록 모델이 지금 이 요청에 맞는 툴을 고르는 정확도가 떨어진다는 측정(RAG-MCP 기준 43%→14%대)이 있다. "기능을 더 붙였는데 에이전트가 더 똑똑해지기는커녕 엉뚱한 툴을 고르기 시작한다"는 역설이 바로 이 지점에서 생긴다. Cursor가 툴 40개, OpenAI Tools API가 128개에서 아예 캡을 거는 것도 같은 이유다. 그래서 "툴을 몇 개까지 붙일 것인가"는 더 이상 구현 디테일이 아니라, MCP 통합을 설계할 때 제일 먼저 내려야 하는 아키텍처 판단이 됐다.

## 핵심 개념 1 — 문제의 뿌리: 스키마를 전부 선적재한다

클라이언트가 MCP 서버에 접속하면 그 서버의 전체 툴 카탈로그를 한 번에 받아와 시스템 프롬프트에 접어 넣는다. 그리고 이 상태가 **매 턴** 반복된다. 서버 10개를 붙였다면 지금 당장 필요 없는 130개 넘는 툴의 스키마까지 매번 모델에 욱여넣고 있는 셈이다. 이 구조에서는 서버를 더 연결할수록 "지금 쓸 일 없는 설명문"이 컨텍스트에서 차지하는 비중만 커진다.

## 핵심 개념 2 — 해결 패턴 네 갈래

| 패턴 | 방식 | 강점 | 약점 |
|---|---|---|---|
| Allow-list | 자주 쓰는 툴만 상시 로딩, 나머지는 아예 연결 안 함 | 구현이 가장 단순, 토큰 비용 예측 가능 | 드물게 쓰는 툴은 아예 접근 불가 |
| Tool Search(지연 로딩) | 툴 이름만 먼저 노출하고, 실제 스키마는 검색 호출 시점에 가져옴 | 전체 카탈로그 접근을 유지하면서 토큰은 85% 수준까지 절감 | 검색 자체가 한 단계 호출을 더 필요로 함 |
| Code Mode | 전체 API 표면을 타입 있는 SDK 코드로 감싸 하나의 실행 환경만 노출 | 수십만 토큰짜리 툴 정의가 코드 한 벌로 압축됨 | 에이전트가 코드 실행 샌드박스를 다뤄야 함 |
| 서브에이전트 분리 | 도메인별로 툴을 나눠 서로 다른 서브에이전트에 배정 | 한 세션이 보는 툴 수 자체가 줄어듦 | 서브에이전트 간 조율 오버헤드 발생 |

바로 지금 이 글을 쓰는 세션 구조가 Tool Search 패턴의 실물 사례다. 자주 쓰는 툴은 상시 로딩되어 있고, Slack·Notion·Figma 같은 나머지는 이름만 노출된 채 "필요하면 검색해서 스키마를 가져오라"는 지시만 받는다. 실제로 그 툴을 호출해야 하는 순간에만 전체 스키마가 로딩된다 — 이게 바로 지연 로딩이 실전에서 동작하는 방식이다.

## 전체 시스템에서의 위치

<img src="/assets/images/posts/2026-10-15-mcp-tool-explosion-progressive-disclosure-1.svg" alt="선적재 방식은 접속 시점에 전체 툴 스키마를 시스템 프롬프트에 넣고 매 턴 반복 전송하는 반면, 지연 로딩 방식은 이름 목록만 상시 유지하고 실제 호출 직전에만 해당 툴의 스키마를 검색해 가져오는 구조 비교도" style="width:100%;">

에이전트 오케스트레이터 입장에서 MCP 서버는 "앞단"이 아니라 "옆단"에 매달리는 확장 포인트다. 요청이 들어오면 오케스트레이터는 (1) 지금 당장 결정을 내리는 데 필요한 컨텍스트와 (2) 작업 수행에 필요한 툴 카탈로그를 둘 다 모델에 쥐여줘야 한다. 선적재 구조에서는 이 둘이 뒤섞여 매 턴 같이 커지지만, 지연 로딩 구조에서는 툴 카탈로그 쪽을 "필요할 때 당겨오는" 별도 검색 경로로 분리해 컨텍스트 예산을 지킨다.

## 선택의 트레이드오프 — 언제 어떤 걸 쓰는가

- 자주 쓰는 핵심 툴(파일 읽기, 커밋, 테스트 실행)은 **allow-list로 상시 로딩**하는 게 맞다. 검색 비용을 추가할 이유가 없다.
- 가끔 쓰는 통합(사내 티켓, 디자인 툴, 분석 대시보드)은 **Tool Search로 지연 로딩**해야 한다. 쓸 일 없는 턴에서 스키마를 끌고 다닐 필요가 없다.
- 이미 REST API가 잘 정리돼 있고 복잡한 다단계 오케스트레이션이 필요하면 **Code Mode**로 아예 SDK화를 검토한다.
- 완전히 다른 두 업무(코딩 vs 고객 응대)를 한 세션이 동시에 처리해야 한다면 **서브에이전트로 쪼개는 쪽**이 툴 수를 근본적으로 줄인다.
- 반대로 툴이 10~20개 수준으로 애초에 적다면, 이 모든 패턴은 과잉 설계다. 먼저 실측부터 하고 손대야 한다.

## 실제 프로젝트 진행 순서

1. **먼저 측정한다.** 지금 붙은 MCP 서버·툴 개수와, 시스템 프롬프트에 매 턴 들어가는 토큰량을 잰다. 체감이 아니라 숫자로 시작해야 한다.
2. **핫패스 툴을 추린다.** 로그에서 실제로 가장 자주 호출되는 툴 5~10개를 골라 allow-list에 고정한다.
3. **나머지를 지연 로딩으로 전환한다.** Claude Code 기준 v2.1.7부터는 이 전환이 설정 수준에서 가능하다.
4. **정확도를 재측정한다.** 전환 전후로 "의도한 툴을 정확히 골랐는가"를 샘플링해 비교한다. 토큰만 줄고 정확도가 함께 떨어지면 분리 기준이 잘못된 것이다.
5. **캐시 히트율을 모니터링한다.** 선적재 구조를 완전히 버리지 못하는 핫패스 영역은 프롬프트 캐싱으로 비용을 추가 완화한다.

```yaml
# MCP 클라이언트 설정 예 — 핫패스는 상시, 나머지는 지연 로딩
mcp_servers:
  github:
    tools: ["get_file_contents", "create_pull_request"]  # allow-list, 상시 로딩
    mode: eager
  notion:
    mode: deferred   # 이름만 노출, 호출 직전 스키마 검색
  figma:
    mode: deferred
```

## 마무리 요약

- MCP 서버를 많이 붙일수록 토큰 비용뿐 아니라 툴 선택 **정확도 자체**가 떨어진다 — 이건 구현 디테일이 아니라 설계 판단이다.
- 핫패스 툴은 allow-list로 상시 로딩하고, 가끔 쓰는 통합은 Tool Search 같은 지연 로딩으로 분리하는 것이 기본 패턴이다.
- 전환 전후로 반드시 "정확도"와 "토큰"을 함께 측정한다. 한쪽만 보고 설계를 확정하면 안 된다.
