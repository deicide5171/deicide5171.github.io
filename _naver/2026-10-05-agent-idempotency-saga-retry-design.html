에이전트가 재시도할 때는 같은 요청이 아니다 — 비결정적 행동의 Idempotency 설계

시스템 설계

한 줄 요약 — "실패하면 에이전트가 알아서 재시도하게 해주세요"는 전통적인 Idempotency Key 설계를 그대로 가져다 쓰면 깨집니다. 재시도할 때마다 LLM이 다른 도구를 고르거나 다른 순서로 행동할 수 있기 때문입니다. 같은 키가 더 이상 같은 요청을 보장하지 못하는 상황에서 결제·예약 같은 사이드이펙트를 안전하게 재시도시키는 설계 기준을 정리했습니다.

 

왜 지금 이 문제가 불거지는가

"API 호출이 타임아웃 나면 에이전트가 알아서 재시도하게 해주세요." 이 요구는 전통적인 분산 시스템에서는 이미 풀린 문제처럼 보입니다. 클라이언트가 요청마다 고유한 Idempotency Key를 발급하고, 서버는 같은 키로 들어온 요청을 중복 처리하지 않으면 됩니다. 그런데 실제로 한 팀은 이 패턴을 에이전트에 그대로 적용했다가 테스트 고객에게 847달러를 두 번 청구하는 사고를 냈습니다. 결제 API 호출이 타임아웃 났고, 재시도 로직이 첫 번째 호출이 실제로는 성공해서 결제가 이미 걸렸는지를 확인하지 않은 채 다시 호출한 것입니다.

문제는 단순한 구현 실수가 아니라 더 근본적인 데 있습니다. 전통적인 재시도에서는 재시도된 요청이 원본과 완전히 동일하다는 전제가 성립합니다. 그런데 에이전트 시스템에서는 같은 논리적 작업을 다시 수행해도 LLM이 다른 토큰 샘플링, 다른 도구 선택, 다른 행동 순서를 거칠 수 있습니다 — 사이드이펙트는 여전히 결정적이어야 하는데, 그 사이드이펙트를 만들어내는 추론 과정은 결정적이지 않습니다. "도쿄행 항공편을 예약해줘"라는 작업이 첫 시도에서는 항공사 A의 API를, 재시도에서는 항공사 B의 API를 호출할 수 있다는 뜻입니다. 이 경우 첫 시도의 Idempotency Key는 재시도를 전혀 보호하지 못합니다 — 근본적으로 다른 작업이기 때문입니다.

 

요구사항을 기술 문제로 번역하기

"실패하면 재시도해주세요"는 실제로 세 가지 다른 보장을 요구합니다. 첫째, 같은 논리적 행동이 중복 실행되지 않도록 보장하는 것입니다. 둘째, 재시도 시 행동 자체가 달라질 수 있다는 전제 위에서 안전하게 처리하는 것입니다. 셋째, 여러 단계로 구성된 작업 중 일부만 성공했을 때 나머지를 보정하는 것입니다. 이 세 요구를 하나의 "재시도 로직"으로 뭉뚱그리면, 단일 호출에는 통하지만 멀티스텝 에이전트 워크플로에서는 반드시 깨집니다.

 

전체 시스템에서의 위치

 

에이전트의 도구 호출이 사이드이펙트가 있는 외부 API에 도달하기 전, 먼저 Idempotency 레이어를 거칩니다. 키는 모델이 생성한 tool-call ID, 대화·세션 ID, 도구 이름, 그리고 직렬화된 인자의 해시를 조합해 만듭니다 — 같은 논리적 행동의 모든 재시도에서는 동일하지만, 진짜로 다른 행동에서는 다른 키가 나오도록 설계하는 것이 핵심입니다. 이 키는 원장(ledger)에 먼저 확인되고, 실행이 끝난 뒤에야 결과가 기록됩니다. 순서를 뒤집어 "실행 후 확인"으로 짜면 그 사이 타이밍에 중복 실행이 이미 벌어진 뒤이므로 멱등성 자체가 깨집니다. 여러 단계로 구성된 워크플로에서는 이 원장이 각 단계의 성공 여부와 함께 보정 액션(취소, 환불, 역방향 호출)을 같이 들고 있어야 합니다 — 이것이 전통적 분산 시스템의 Saga 패턴을 에이전트 워크플로에 맞게 가져온 형태입니다.

 

선택의 트레이드오프
전략 비결정적 재시도 대응 멀티스텝 실패 처리 적합한 상황
클라이언트 생성 UUID 키 불가능 없음 행동이 절대 바뀌지 않는 단일 호출
인자 해시 기반 키 가능 없음 단일 사이드이펙트 호출
원장 + 체크-실행-기록 가능 단일 단계 한정 재시도가 잦은 단일 작업
Saga + 보정 액션 가능 전체 워크플로 보정 여러 API를 묶는 워크플로
재시도 없음 해당 없음 사람이 수동 개입 되돌리기 어려운 고위험 행동

 

표에서 가장 중요한 함정은 "클라이언트 생성 UUID 키"입니다. 전통적인 API 클라이언트에서는 충분하지만, 에이전트가 재시도마다 다른 행동을 선택할 수 있다는 전제를 반영하지 못합니다. 반대로 Saga + 보정 액션은 가장 안전하지만, 모든 사이드이펙트 도구마다 "되돌리는 법"을 정의해야 하므로 구현 비용이 큽니다. 결제 API의 Idempotency Key는 보통 24시간짜리지만, 에이전트 워크플로는 예약을 며칠씩 들고 있다가 확정하는 경우가 있어 키가 만료된 뒤 재시도하면 보호가 사라집니다.

 

실제 프로젝트 진행 순서

1단계: 사이드이펙트가 있는 도구 호출을 전부 식별하고, 되돌리기 어려운 쓰기 작업부터 설계 대상으로 좁힙니다.

2단계: tool-call ID, 세션 ID, 도구 이름, 인자 해시를 조합한 키 체계를 정의합니다.

3단계: 원장에서 체크-실행-기록 순서를 코드 레벨에서 강제하고 리뷰 체크리스트에 명시합니다.

4단계: 멀티스텝 워크플로에는 단계별 보정 액션을 미리 설계합니다.

5단계: 키 TTL을 결제 API 기본값이 아니라 워크플로의 실제 수명에 맞춰 재설정합니다.

주의 — "재시도 가능"을 모든 도구에 기본값으로 두지 마세요. 되돌리기 어려운 고위험 행동은 자동 재시도 대신 실패 시 사람에게 넘기는 것이 더 안전한 기본값입니다. 결제 도구를 추가할 때 환불 도구도 같이 추가하는 것을 원칙으로 삼으세요.

 

정리

"실패하면 재시도해주세요"는 중복 실행 방지, 비결정적 재시도 대응, 멀티스텝 보정이라는 서로 다른 세 가지 보장을 요구하므로 하나의 재시도 로직으로 뭉뚱그리면 안 됩니다. tool-call ID·세션·인자 해시를 조합한 키와 체크-실행-기록 순서, 그리고 Saga 패턴의 보정 액션을 도구 설계 시점부터 함께 만드는 것이 순서입니다.
