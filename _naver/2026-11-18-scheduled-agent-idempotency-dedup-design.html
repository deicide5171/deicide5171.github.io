"매일 자동으로 콘텐츠를 만들어서 올려주세요" — 상시 에이전트가 같은 일을 두 번 하지 않게 만드는 멱등성 설계

AI

한 줄 요약 — 크론·스케줄러가 보장하는 것은 "적어도 한 번" 실행이지 "딱 한 번" 실행이 아닙니다. 재시도나 세션 재개 중 같은 사이드이펙트가 중복으로 일어나지 않게 하려면, 되돌릴 수 없는 작업 직전에 멱등성 키를 원자적으로 선점하는 경계를 설계해야 합니다.

 

왜 지금 이 판단이 필요한가

"이 작업, 매일 아침 자동으로 돌아가게 해주세요. 사람이 안 봐도 알아서 하고, 끊기면 다시 이어서 하면 돼요"라는 요구는 더 이상 특이한 주문이 아닙니다. 최근 몇 달 사이 여러 플랫폼이 서브워크플로 라우팅, 상시 가동 에이전트 런타임, "항상 켜져 있는 팀원" 제품을 잇따라 내놓은 것도 같은 흐름입니다. 에이전트를 한 번 호출하고 끝내는 게 아니라, 크론이나 트리거로 반복 실행시키는 패턴이 기본값이 되고 있습니다.

이 요구를 그대로 받으면 머릿속에 바로 "크론 → 에이전트 실행 → 결과 반영" 파이프라인이 그려지지만, 빠뜨리기 쉬운 질문이 하나 있습니다. 실행 도중 rate limit이나 네트워크 오류로 세션이 끊기고, 스케줄러가 안전하게 "다시 한번 돌려봐"라고 재시도하면 무슨 일이 생기는가입니다. 실제로 반복 배치 파이프라인에서 세션이 끊겼다가 재개되는 과정에 이미 만든 결과물과 사실상 동일한 결과물이 한 번 더 만들어져 그대로 반영된 사례가 보고된 적이 있습니다.

 

전체 시스템에서의 위치

상시 에이전트 파이프라인은 대체로 트리거(크론·웹훅) → 에이전트 실행 → 사이드이펙트(커밋·API 호출·알림) → 상태 기록, 네 단계로 이어집니다. 멱등성 문제는 네 번째 단계인 상태 기록이 세 번째 단계인 사이드이펙트보다 늦게, 혹은 아예 기록되지 못하고 중단될 때 생깁니다. 핵심은 "언제 기록하느냐"가 아니라, 사이드이펙트와 기록을 하나의 원자적 연산으로 묶을 수 있느냐입니다.

 

선택의 트레이드오프
방식레이스 컨디션 안전성적합한 상황
사전 체크(존재 확인 후 실행)낮음 — 체크·실행 사이 틈재시도 빈도 낮고 사람이 점검하는 배치
DB/파일 유니크 제약 선점높음 — DB가 원자성 보장사이드이펙트가 트랜잭션화 가능한 경우
분산 락(Redis 등)높음, 해제 타이밍 관리 필요여러 워커가 동시에 트리거를 받는 환경
외부 상태 저장소에 키 기록높음, 키 설계가 핵심사이드이펙트가 외부 API 호출인 경우

 

자연키(날짜+슬롯처럼 의미 있는 값)로 멱등성 키를 만들면 디버깅이 쉽지만, 같은 자리에서 내용이 바뀌는 재시도를 구분하지 못하는 함정이 있습니다. 반대로 매 실행마다 새 UUID를 키로 쓰면 애초에 "같은 작업"이라는 식별 자체가 불가능해집니다. 멱등성 키는 "무엇이 같으면 같은 작업인가"라는 질문에 먼저 답한 뒤 설계해야 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 멱등성 경계를 어디에 그을지 정하는 것입니다. "에이전트가 생각을 시작하는 시점"이 아니라, 되돌릴 수 없는 사이드이펙트가 일어나는 시점 바로 앞이 경계여야 합니다.

KEY="post:${TODAY}:${SLOT}"

if ! claim_idempotency_key "$KEY"; then
  echo "이미 처리된 작업 — 재시도 중복, 스킵"
  exit 0
fi

run_side_effect   # 파일 커밋, PR 생성 등
mark_idempotency_key_done "$KEY"

그다음 이 경계를 재시도 테스트로 직접 검증합니다. 같은 트리거를 의도적으로 두 번 쏴서 사이드이펙트가 정말 한 번만 일어나는지 확인하지 않으면, 설계는 서류상으로만 멱등하고 실전에서는 뚫립니다. 마지막으로 멱등성 체크 자체가 실패했을 때의 기본 동작을 정해야 합니다 — 안전을 우선해 작업을 건너뛸지, 가용성을 우선해 일단 실행할지는 사이드이펙트를 되돌리는 비용에 따라 달라집니다.

 

주의 — exit code나 "프로세스가 끝났다"는 신호만으로 작업 완료를 판단하지 마세요. 사이드이펙트가 실제로 반영됐는지와, 그 사실이 멱등성 저장소에 기록됐는지는 서로 다른 질문이며, 이 둘 사이의 틈에서 중복 사고가 납니다.
