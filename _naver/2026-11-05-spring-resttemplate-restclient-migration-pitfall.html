"RestTemplate 쓰던 코드, 그냥 바꿔치기해주세요" — Spring 7.1 Deprecated 앞에서 RestClient 전환이 조용히 깨뜨리는 것들

Stack

한 줄 요약 — Spring Framework 7.1에서 RestTemplate이 공식 Deprecated 표시를 받습니다. 흔히 권장되는 RestClient.create(restTemplate) 감싸기 전환이 실제로는 요청 인코딩과 병렬 호출 성능을 조용히 바꿔놓는 이유를, 전환 전 반드시 검증해야 할 지점 중심으로 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"외부 API 호출하는 코드, RestTemplate 쓰던 거 그냥 RestClient로 바꿔치기해주세요." 간단해 보이는 요청입니다. Spring Framework 7.1부터 RestTemplate에 forRemoval 플래그가 붙은 Deprecated 표시가 생기고, 8.0에서 완전히 제거될 예정입니다. 공식 가이드가 제시하는 가장 안전한 경로는 한 번에 새로 짜지 말고 기존 RestTemplate 인스턴스를 RestClient로 감싸서 점진적으로 옮기는 것입니다. RestClient.create(restTemplate) 한 줄이면 끝나 보입니다.

그런데 이 한 줄짜리 전환이 실제로는 조용히 동작을 바꿉니다. 커뮤니티에 보고된 사례에서는 new RestTemplate()을 RestClient.create()로 바꾸자 병렬 호출 처리량이 4배 느려졌는데, 예외도 로그도 남지 않았습니다. 다른 사례에서는 기본 RestTemplate을 감쌀 때 URI 인코딩 방식이 달라져서 쿼리 스트링의 특수문자가 다르게 인코딩됐습니다. 둘 다 로컬 재현 수준의 보고지만, "구현체만 바꾸면 동작은 그대로"라는 전제 자체가 깨질 수 있다는 신호입니다.

 

전체 시스템에서의 위치

외부 API를 호출하는 HTTP 클라이언트는 요청 팩토리(커넥션 생성 방식), 커넥션 풀, URI 인코딩 규칙까지 함께 묶인 조립체입니다. RestTemplate은 이를 ClientHttpRequestFactory 인터페이스로 추상화했고, 팀마다 타임아웃·커넥션 풀 크기를 이 팩토리에 직접 설정해둔 경우가 많습니다.

RestClient.create(restTemplate)로 감싸면 기존 요청 팩토리는 유지되지만, 그 위에 RestClient 고유의 기본 동작(인터셉터 체인, URI 빌더 기본값)이 덧씌워집니다. 밑단은 그대로인데 그 위에서 요청을 조립하는 규칙이 바뀌는 셈입니다. 동시 호출이 많은 서비스에서 이 변화가 커넥션 재사용 패턴에 영향을 주면, 네트워크 설정은 안 건드렸는데 처리량이 떨어지는 것처럼 보일 수 있습니다.

 

선택의 트레이드오프
기준그대로 유지감싸서 점진 전환신규 작성
작업량없음적음(한 줄 치환)많음
8.0 제거 대비안 됨부분적완전 대비
숨은 동작 변경 위험없음있음(인코딩·동시성)낮음
적합한 대상곧 종료될 서비스호출 지점 많은 레거시새 모듈, 호출 적은 서비스

 

표가 보여주는 결론은 "감싸서 전환"이 작업량은 가장 적지만 공짜가 아니라는 점입니다. 그 적은 작업량의 대가로 "진짜 동작이 유지되는지"를 검증하는 책임이 통째로 넘어옵니다. 호출 지점이 수십 개를 넘는 레거시라면 이 트레이드오프가 합리적이지만, 호출 지점이 몇 개뿐이라면 처음부터 명시적으로 다시 쓰는 편이 검증 비용을 오히려 줄입니다.

 

실제 프로젝트 진행 순서

1) RestTemplate 호출 지점을 전수 조사해 수를 셉니다. 적으면 바로 신규 작성 경로가 전체 비용이 적습니다.
2) 호출 지점이 많다면, 동시 호출이 많은 지점을 먼저 식별해 우선순위를 높입니다.
3) 전환 전 해당 지점의 현재 처리량·지연시간을 측정해 기준선으로 남깁니다.
4) URI에 특수문자가 들어가는 호출부터 전환하고 인코딩 결과를 직접 비교합니다.
5) 전환 후 병렬 호출 벤치마크를 기준선과 비교하고, 차이가 나면 커넥션 풀·타임아웃을 명시적으로 재설정합니다.

 

주의 — "컴파일이 되면 동작도 같다"는 가정을 버리세요. RestClient.create(restTemplate)는 타입만 맞춰줄 뿐 내부 조립 규칙까지 동일하다는 보장은 공식 문서 어디에도 없습니다. TestRestTemplate을 쓰는 통합 테스트도 함께 점검하지 않으면, 테스트가 검증하는 경로와 운영 경로가 어긋날 수 있습니다.

 

정리

RestTemplate은 Spring Framework 7.1에서 Deprecated, 8.0에서 완전히 제거될 예정이며, 공식 권장 경로는 RestClient로 감싸는 점진적 전환입니다. 그러나 감싸기는 요청 팩토리 위의 조립 규칙(인코딩, 인터셉터 기본값)을 바꾸므로, 병렬 처리량과 URI 인코딩에서 조용한 회귀가 보고됐습니다. 호출 지점 수와 동시성 패턴을 기준으로 감싸기와 신규 작성 중 선택하고, 전환 전후를 직접 측정해 비교하는 과정을 생략하지 마세요.
