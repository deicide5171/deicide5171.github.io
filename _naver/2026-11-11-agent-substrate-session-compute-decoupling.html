에이전트 수백 개를 배경에서 돌려야 하는데요 — Google이 CNCF에 넘긴 Agent Substrate로 보는 세션-컴퓨트 분리 설계

AI

한 줄 요약 — '사용자마다 조사·코딩을 맡기는 에이전트를 배경에서 수백 개 띄워주세요'라는 요구는 컨테이너를 계속 켜둘 비용과 매번 새로 띄우는 콜드스타트 사이에서 막힙니다. Google이 2026년 11월 CNCF에 기증한 Agent Substrate가 보여준 '세션 상태와 컴퓨트 분리' 패턴으로 이 막힘을 어떻게 푸는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"사용자가 메신저로 요청만 남기면, 그 뒤로는 에이전트가 알아서 조사하고 코드까지 짜서 돌아오게 해주세요." 상시 가동형 에이전트 자체는 더 이상 새로운 요구가 아닙니다. 문제는 이 요구가 "사용자 한 명"이 아니라 "동시 사용자 수백~수천 명"으로 번역되는 순간 터집니다. 요청마다 컨테이너를 띄우고 계속 켜 두면 대부분의 세션이 실제로는 사용자의 다음 답장을 기다리며 유휴 상태인데도 컴퓨트 비용이 그대로 청구됩니다. 반대로 요청이 들어올 때만 컨테이너를 새로 띄우면, 그 세션이 쌓아 온 대화 맥락·작업 중이던 파일·중간 추론 상태를 다시 복원하는 데 시간이 걸리거나 아예 사라집니다.

2026년 11월 KubeCon North America에서 Google Cloud가 Agent Substrate·gVisor·OpenRL 세 프로젝트를 CNCF Sandbox에 기증하면서 이 문제를 정면으로 겨냥한 설계가 공개됐습니다. Agent Substrate의 핵심 주장은 단순합니다 — 에이전트 세션의 "정체성과 상태"를 "그걸 실행하는 컴퓨트"에서 분리하면, 세션을 500밀리초 안에 멈췄다 복원할 수 있다는 것입니다. 빌더가 답해야 할 질문은 "컨테이너를 얼마나 오래 켜 둘 것인가"가 아니라 "이 세션에서 끝까지 들고 가야 할 상태는 무엇이고, 그 상태를 컴퓨트 없이도 어디에 보관할 것인가"로 바뀝니다.

 

세션은 데이터, 실행은 그때그때 빌리는 자원

기존의 "상시 가동 에이전트" 설계는 세션 하나당 가상 컴퓨터를 길게 띄워 두고, 대화 기록·파일시스템·실행 중인 프로세스를 전부 함께 보관했습니다. Agent Substrate는 이 묶음을 둘로 쪼갭니다. 대화 히스토리, 메모리, 파일시스템 스냅샷, 승인 대기 작업 같은 "세션 상태"는 별도 저장소에 직렬화해 두고, 실제 코드 실행이 필요한 순간에만 격리된 샌드박스를 빌려와 그 상태를 주입합니다. 사용자가 응답을 기다리는 동안에는 컴퓨트를 완전히 반납하고, 다음 메시지가 오면 저장해 둔 상태로 새 샌드박스를 복원합니다. 이 복원이 500ms 안에 끝난다는 것이 이 설계의 실용적 핵심입니다.

 

gVisor가 메우는 신뢰 경계

세션을 자유롭게 멈췄다 복원하려면, 애초에 여러 세션을 같은 하드웨어 위에서 안전하게 돌릴 수 있어야 합니다. 에이전트가 사용자 대신 임의의 코드를 생성해 실행하는 구조에서는 이 코드를 신뢰할 수 없는 입력으로 다뤄야 하는데, Agent Substrate는 커널 시스템 콜을 가로채는 gVisor를 격리층으로 씁니다. 일반 VM보다 가볍게 다수의 세션을 밀집시키면서도, 한 세션의 코드가 호스트 커널이나 다른 세션의 상태를 건드리지 못하게 막습니다. 다만 공개된 문서 기준으로 GPU passthrough를 지원하지 않고, 일시정지 시점에 열려 있던 소켓 연결은 끊어진다는 한계가 명시돼 있습니다 — 설계 초기에 반드시 확인해야 할 체크포인트입니다.

 

전체 시스템에서의 위치

사용자 요청은 먼저 세션 상태 저장소에서 이 세션의 직렬화된 상태를 찾습니다. 상태가 있으면 샌드박스 풀에서 격리된 실행 환경을 빌려와 그 상태를 주입해 복원하고, 작업이 끝나거나 응답을 기다려야 하면 다시 상태만 저장소에 남기고 샌드박스는 풀로 반납합니다. 항상 떠 있는 것은 상태 저장소뿐이고, 비용이 드는 연산 자원은 요청이 있을 때만 잠깐씩 쓰입니다. 이 저장소가 망가지면 복원할 세션 자체가 사라진다는 점에서, 여기가 이 아키텍처의 진짜 정체성 보관소입니다.

동시 활성 세션 수가 적고 응답성이 최우선이라면 상시 가동을 유지할 이유가 충분합니다. 반대로 세션 수가 수백 단위로 늘고 대부분이 유휴 상태라면, 그 비용을 어디로 돌릴지가 아키텍처의 핵심 질문이 됩니다. GPU 추론이나 장시간 소켓 연결이 필수인 워크로드라면 이 패턴을 그대로 들여오기보다 하이브리드로 설계해야 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 코드를 바꾸는 게 아니라 트래픽 패턴을 재는 것입니다. 동시 활성 세션 수와 각 세션의 유휴 시간 분포를 실측해, 유휴 비용이 실제로 전체 비용의 큰 비중을 차지하는지부터 확인합니다. 두 번째로 세션마다 "끝까지 들고 가야 할 상태"와 "실행 중에만 필요한 것"을 나눕니다. 세 번째로 작은 PoC에서 실제 pause-resume 지연시간을 직접 측정합니다 — 공개 수치 500ms는 Google 환경 기준이며 자체 인프라에서는 달라질 수 있습니다. 마지막으로 GPU나 장시간 연결이 필요한 기능이 있다면, 그 기능만 상시 가동 풀로 분리해 부분 적용부터 시작하는 편이 안전합니다.

 

주의 — GPU passthrough 미지원과 일시정지 시 소켓 끊김은 공개 문서에 명시된 현재 한계입니다. 해당 워크로드가 있다면 전면 전환 전에 반드시 확인해야 합니다.
