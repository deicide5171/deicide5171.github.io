Hibernate 2차 캐시 딥다이브 — 영속성 컨텍스트 캐시와 무엇이 다른가

백엔드

한 줄 요약 — 2차 캐시는 트랜잭션 하나에 국한된 1차 캐시와 달리 애플리케이션 전체에 살아있으며, 동시성 전략 선택이 정합성과 성능의 트레이드오프를 결정합니다.

 

왜 완전히 다른 문제인가

1차 캐시는 트랜잭션 하나의 생명주기 안에서만 유효한 단순한 캐시입니다. 실무에서 필요한 것은 대개 여러 트랜잭션, 여러 요청, 여러 서버 인스턴스에 걸쳐 자주 조회되지만 잘 바뀌지 않는 데이터를 캐싱하는 것으로, 이 역할을 하는 것이 2차 캐시입니다.

 

엔티티 캐시와 쿼리 캐시는 다르다

엔티티 캐시는 PK로 조회한 필드값을 저장하고, 컬렉션 캐시는 연관관계의 ID 목록을, 쿼리 캐시는 JPQL 결과의 엔티티 ID 목록을 캐싱합니다. 이 세 영역은 각각 별도 리전에 저장되고 독립적으로 무효화됩니다.

동시성 전략이 정합성을 결정한다

READ_ONLY는 절대 변경 안 되는 데이터에만 씁니다. READ_WRITE는 소프트 락으로 정합성을 맞춰 대부분의 가변 데이터에 적합합니다. NONSTRICT_READ_WRITE는 잠금 없이 성능을 얻는 대신 일시적 stale을 허용합니다.

전략 정합성 적합한 데이터
READ_ONLY 완벽 불변 데이터
READ_WRITE 강함 가끔 바뀌는 데이터
NONSTRICT_READ_WRITE 약함 통계성 데이터

 

엔티티/쿼리 캐시 활성화 예제
@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class ProductCategory {
    @Id
    private Long id;
    private String name;

    @OneToMany(mappedBy = "category")
    @org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
    private List<Product> products;
}

 

실무 포인트

쓰기가 잦은 엔티티에 캐시를 걸면 오히려 손해입니다. 무효화 오버헤드와 소프트 락 경합이 이득보다 커질 수 있으므로 캐시 히트율을 반드시 모니터링해야 합니다.

분산 환경에서는 캐시 복제 방식을 이해해야 합니다. 인스턴스마다 로컬 캐시를 가지면 변경이 즉시 반영되지 않을 수 있습니다.

주의 — 같은 영속성 컨텍스트 안에서는 1차 캐시가 항상 우선하므로, 2차 캐시의 효과는 새로운 트랜잭션에서 같은 엔티티를 조회할 때만 체감됩니다.
