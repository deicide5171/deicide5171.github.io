"데이터 한눈에 보이는 페이지 만들어주세요" — Claude Docs·Dashboards GA 이후 타입드 아티팩트 vs 직접 설계의 경계

AI

한 줄 요약 — Claude Docs·Slides·Design이 정식 전환되고 Dashboards·Motion이 베타로 들어오면서, 에이전트가 페이지를 만들 때마다 "기성 타입에 맡길지, 직접 설계할지"를 판단해야 하는 구조가 생겼습니다. 판단 기준을 요청의 성격과 데이터 공유 범위로 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"우리 팀 KPI를 한눈에 보여주는 페이지 좀 만들어주세요." 이런 요청을 받으면 에이전트는 더 이상 빈 HTML 파일부터 그리지 않습니다. 최근 Claude Docs·Slides·Design이 모든 플랜(무료 포함)에서 정식 기능으로 전환됐고, 같은 시점에 Claude Dashboards와 Claude Motion이 베타로 들어왔습니다. 핵심은 기능이 늘었다는 것이 아니라, 산출물을 만들기 전에 "이 요청에 맞는 기성 타입이 이미 있는가"를 먼저 확인하는 단계가 하나 더 생겼다는 점입니다.

지금까지는 무엇을 요청하든 에이전트가 처음부터 HTML·CSS를 짜는 경로로 수렴했습니다. 그런데 문서·슬라이드·디자인·대시보드처럼 쓰임새가 뚜렷한 영역은 플랫폼이 이미 틀을 갖춘 전용 타입으로 분리됐습니다. 이제 "페이지를 만들어주세요"라는 말을 들을 때마다 실제로 번역해야 하는 질문은 "기성 타입에 맡길 것인가, 처음부터 설계할 것인가"로 바뀌었습니다. 이 판단을 직감으로만 하면 과도하게 커스텀 HTML을 짜거나, 반대로 기성 타입의 제약에 요구사항을 억지로 욱여넣는 비일관성이 생깁니다.

 

전체 시스템에서의 위치

요청이 들어왔을 때 시스템이 거치는 경로는 두 갈래입니다. 첫 번째는 "문서를 공유하고 싶다", "발표 자료가 필요하다", "데이터를 보여주는 페이지가 필요하다"처럼 의도가 뚜렷할 때입니다. 이때는 먼저 의도를 분류해 맞는 기성 타입이 있는지 확인하고, 있으면 그 타입의 고정된 틀 위에 데이터만 채웁니다. 데이터가 계속 바뀌어야 한다면 그 타입 자체의 저장소로 흐릅니다.

두 번째는 기성 타입이 없는 일반적인 페이지(설명 페이지, 인터랙티브 도구, 커스텀 UI)입니다. 이때는 직접 HTML을 설계하는데, "이 페이지가 상태를 기억해야 하는가, 여러 사람이 같이 써야 하는가"에 따라 런타임 기능을 선택적으로 붙입니다. 여러 사람이 손으로 기록을 추가하는 트래커라면, 데이터를 페이지 소스나 브라우저 저장소에 두는 대신 공유 데이터베이스 계층을 붙여야 합니다. 결국 두 경로 모두 "데이터가 어디 머물고 누가 갱신하는가"의 문제로 수렴합니다.

 

선택의 트레이드오프
기준플랫폼 타입드 아티팩트직접 설계한 HTML
초기 구축 속도빠름 — 틀에 데이터만 채움느림 — 레이아웃까지 직접 설계
디자인 일관성플랫폼 기준 자동 통일매번 판단이 들어가 편차 발생
커스터마이징타입이 정한 구조로 제한요구사항대로 임의 확장 가능
적합한 요청문서·발표·데이터 요약 페이지특정 방식으로 작동하는 도구·화면

 

표가 보여주는 결론은 "항상 플랫폼 타입을 먼저 쓰라"가 아니라, 요청의 성격이 이미 존재하는 틀에 들어맞는지 먼저 확인하는 습관이 비용을 줄인다는 점입니다. 틀에 맞지 않는 요청을 억지로 끼워 맞추면 나중에 커스터마이징 벽에 부딪히고, 틀에 맞는 요청을 매번 처음부터 설계하면 같은 일을 반복하게 됩니다.

 

실제 프로젝트 진행 순서

1) 요청을 받으면 먼저 의도를 분류합니다(문서인가, 슬라이드인가, 데이터 화면인가, 그 외 인터랙티브한 것인가).
2) 앞의 세 가지라면 기성 타입이 있는지부터 확인합니다. 이 확인을 건너뛰면 이미 있는 틀을 다시 만드는 중복 작업이 됩니다.
3) 기성 타입이 있으면 데이터 규격에 맞춰 내용만 채우고 레이아웃 판단에 시간을 쓰지 않습니다.
4) 없다면 직접 설계로 전환하되, 상태가 필요한지(한 번 보여주고 끝인지, 계속 값이 쌓이는지)부터 따집니다.
5) 상태를 공유해야 한다면 그 단위를 먼저 설계하고 저장 계층을 고릅니다. 이 설계를 건너뛰면 나중에 데이터 구조를 바꾸는 비용이 커집니다.

 

주의 — 브라우저 로컬 저장소와 공유 데이터베이스를 혼동하면 안 됩니다. 로컬 저장소는 그 사람의 그 기기에만 남는 개인 편의 기능입니다. 여러 사람이 같이 보는 체크리스트처럼 모두가 같은 값을 봐야 하는 데이터를 로컬 저장소로 설계하면, 사용자마다 다른 화면을 보는 버그로 이어집니다.

 

정리

Claude Docs·Slides·Design의 정식 전환과 Dashboards·Motion의 베타 진입은 "페이지를 만들어주세요"라는 요청을 플랫폼 타입과 직접 설계라는 두 경로로 쪼갰습니다. 판단 기준은 디자인 취향이 아니라 요청의 성격과 상태의 공유 범위입니다. 기성 타입을 확인하는 습관 하나가 중복 구현을 줄이고, 상태의 공유 범위를 먼저 설계하는 습관 하나가 나중의 재설계 비용을 줄입니다.
