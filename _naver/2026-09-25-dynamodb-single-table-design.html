DynamoDB 싱글 테이블 설계 — 관계형 사고를 버리고 접근 패턴으로 모델링하기

DB·데이터 모델링

한 줄 요약 — JOIN이 없는 DynamoDB에서 관련 엔티티를 한 테이블에 미리 배치해 한 번의 쿼리로 가져오는 싱글 테이블 설계를 정리했습니다.

 

왜 지금 싱글 테이블 설계를 다시 봐야 하는가

DynamoDB를 RDB처럼 엔티티마다 테이블을 나눠 설계하면, JOIN이 없어 애플리케이션 코드가 여러 테이블에 여러 번 요청을 보내고 결과를 직접 조립해야 합니다. 요청이 늘수록 지연시간과 비용이 함께 늘어납니다. 싱글 테이블 설계는 서로 다른 엔티티를 의도적으로 한 테이블에 함께 저장해 이 문제를 해결합니다.

 

스키마가 아니라 접근 패턴부터 설계한다

RDB는 데이터 구조를 먼저 정의하고 쿼리는 나중에 짭니다. DynamoDB는 반대입니다. 실제로 어떤 조회를 얼마나 자주 하는지 먼저 전부 나열한 뒤, 그 패턴을 파티션 키(PK)와 정렬 키(SK) 설계 하나로 커버하도록 데이터를 배치합니다. 그래서 접근 패턴을 최대한 철저히 미리 뽑아내는 것이 중요합니다.

 

오버로딩된 키와 GSI로 여러 엔티티를 한 테이블에

PK와 SK를 여러 엔티티 타입이 공유하는 범용 필드로 오버로딩합니다. 고객 정보는 PK=CUSTOMER#123, SK=CUSTOMER#123으로, 주문은 PK=CUSTOMER#123, SK=ORDER#456으로 저장하면 한 번의 Query로 고객과 모든 주문을 함께 받아옵니다. 역방향 조회는 Global Secondary Index(GSI)로 지원합니다.

고객·주문을 한 테이블에 오버로딩
table.put_item(Item={
    'PK': 'CUSTOMER#123', 'SK': 'CUSTOMER#123',
    'type': 'Customer', 'name': '김민준'
})

table.put_item(Item={
    'PK': 'CUSTOMER#123', 'SK': 'ORDER#456',
    'type': 'Order', 'status': 'SHIPPED'
})

response = table.query(
    KeyConditionExpression='PK = :pk',
    ExpressionAttributeValues={':pk': 'CUSTOMER#123'}
)

 

실무 포인트

모든 워크로드에 싱글 테이블 설계가 정답은 아닙니다. 접근 패턴이 자주 바뀌는 초기 서비스나 분석 쿼리가 잦은 워크로드라면 여러 테이블로 나누는 것이 더 유연합니다. 접근 패턴이 안정된 고트래픽 서비스에 특히 유리한 기법입니다.

엔티티 타입을 구분하는 type 속성과 일관된 키 네이밍 규칙을 처음부터 강제하세요. 규칙이 흐트러지면 싱글 테이블의 장점인 예측 가능한 쿼리가 무너집니다.

주의 — GSI 개수와 프로젝션 설계는 비용에 직접 영향을 줍니다. 필요 이상으로 많은 속성을 GSI에 복제하면 쓰기 비용이 늘어나므로, 실제 조회에 필요한 속성만 최소한으로 선택해야 합니다.
