COUNT(*)가 느릴 때 — 대용량 테이블 카운트 최적화 방법

데이터베이스

한 줄 요약 — 테이블이 커질수록 COUNT(*)는 조건에 맞는 행을 매번 실제로 스캔해야 해 느려집니다. 정확도가 꼭 필요한지부터 재검토하세요.

 

왜 테이블이 커지면 느려지나

MySQL InnoDB나 PostgreSQL은 MVCC 구조라 트랜잭션마다 보여야 할 행 수가 다를 수 있습니다. 그래서 미리 계산된 값을 캐싱하는 대신, COUNT(*)가 실행될 때마다 조건에 맞는 행을 실제로 스캔하며 세야 하므로 테이블이 커질수록 선형적으로 느려집니다.

 

 

해결책 1: 정말 정확한 개수가 필요한지 재검토

무한 스크롤 UI라면 애초에 전체 개수를 보여줄 필요가 없습니다. LIMIT을 요청 개수보다 하나 더 가져와서 다음 페이지 유무만 확인하면 COUNT(*) 자체를 제거할 수 있습니다.

-- 20개 요청 시 21개를 가져와 다음 페이지 유무 판단
SELECT * FROM posts WHERE status = 'PUBLISHED'
ORDER BY created_at DESC LIMIT 21 OFFSET 100;
해결책 2: 근사치는 시스템 카탈로그로

관리자 대시보드처럼 대략적인 개수로 충분하다면 PostgreSQL의 pg_class.reltuples로 즉시 추정치를 가져올 수 있습니다. ANALYZE 시점 기준 통계라 오차가 있지만 대부분의 대시보드 용도에서는 문제가 되지 않습니다.

주의 — 재고 수량처럼 반드시 정확해야 하는 카운트는 별도 카운터 컬럼을 유지하고 데이터 변경 시점에만 갱신하세요. 단, 정합성이 어긋날 수 있으니 주기적으로 실제 COUNT와 비교해 보정하는 배치가 필요합니다.
