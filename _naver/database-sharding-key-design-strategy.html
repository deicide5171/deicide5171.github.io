샤딩 키 설계 심화 — 해시 샤딩 vs 레인지 샤딩과 리샤딩 전략

DB·데이터 모델링

한 줄 요약 — 샤딩 키를 잘못 고르면 핫스팟과 크로스 샤드 쿼리 지옥에 빠집니다. 해시·레인지 샤딩 트레이드오프와 리샤딩 전략을 정리했습니다.

 

왜 지금 샤딩 키 설계를 다시 봐야 하는가

수직 확장이나 읽기 복제본 추가로도 쓰기 처리량 한계에 부딪히면 결국 샤딩을 고려하게 됩니다. 문제는 샤딩 키를 잘못 골라 특정 샤드에만 트래픽이 몰리는 핫스팟이나, 거의 모든 쿼리가 여러 샤드를 조인해야 하는 크로스 샤드 쿼리 지옥에 빠지는 경우가 흔하다는 점입니다. 샤딩은 한번 적용하면 되돌리기 어려운 결정입니다.

 

해시 샤딩과 레인지 샤딩의 구조 차이

해시 샤딩은 키에 해시 함수를 적용해 나머지 연산으로 샤드를 결정합니다. 데이터가 고르게 퍼져 핫스팟이 적습니다. 레인지 샤딩은 키의 범위로 샤드를 나누며, 범위 조회 성능은 좋지만 최근 데이터에 트래픽이 몰리면 마지막 샤드에 부하가 집중되기 쉽습니다.

항목 해시 샤딩 레인지 샤딩
데이터 분포 균등 (핫스팟 적음) 불균등해지기 쉬움
범위 조회 성능 나쁨 (여러 샤드 스캔) 좋음 (단일 샤드로 국한)
리샤딩 시 이동량 대부분 재배치 필요 특정 범위만 분할 가능

 

크로스 샤드 쿼리를 피하는 키 선택

샤딩 키 설계의 핵심 원칙은 가장 빈번한 쿼리 패턴이 단일 샤드 안에서 끝나도록 키를 고르는 것입니다. 커머스 서비스에서 주문 조회가 대부분 사용자별이라면 user_id를 샤딩 키로 써야 합니다. order_id를 쓰면 단건 조회는 빨라지지만, 사용자별 목록 조회가 모든 샤드를 뒤지는 scatter-gather가 됩니다.

 

예제 — 일관된 해싱으로 리샤딩 비용 줄이기
class ConsistentHashRing:
    def __init__(self, nodes, virtual_nodes=150):
        self.ring = {}
        for node in nodes:
            for i in range(virtual_nodes):
                key = self._hash(f"{node}-{i}")
                self.ring[key] = node
        self.sorted_keys = sorted(self.ring.keys())

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_node(self, key):
        h = self._hash(key)
        for ring_key in self.sorted_keys:
            if h <= ring_key:
                return self.ring[ring_key]
        return self.ring[self.sorted_keys[0]]

단순 hash(key) % N 방식은 샤드 수(N)가 바뀌면 거의 모든 키의 소속 샤드가 바뀝니다. 일관된 해싱을 쓰면 재배치가 필요한 키의 비율을 극히 일부로 줄일 수 있습니다.

 

실무 포인트

샤딩 키는 실제 쿼리 로그를 분석한 뒤 정하세요. 이론적으로 균등해 보이는 키라도 실제 트래픽에서는 특정 값에 쏠릴 수 있습니다.

테넌트 기반 서비스라면 대형 테넌트가 샤드를 독점하지 않도록 서브 샤딩이나 전용 샤드 분리를 함께 설계하세요.

주의 — 리샤딩 계획을 처음부터 문서화해두세요. 샤드 수를 2배로 늘릴 때 데이터 이동 방식(더블 라이트, 백그라운드 마이그레이션)을 미리 정하지 않으면 리샤딩 시점에 다운타임이 커집니다.
