AI

한 줄 요약 — 클라우드 에이전트가 사용자의 로컬 파일에 접근해야 한다는 요구는, 세션과 로컬 폴더를 1:1로 묶고 매 요청마다 사람 승인을 받는 신뢰 경계 설계 문제로 번역됩니다. 승인 유효 기간과 해제 권한을 누구에게 주는지가 전체 설계의 핵심입니다.

 

왜 지금 이 판단이 불거지는가

"에이전트를 클라우드에서 돌리고 있는데, 로컬에만 있는 라이브러리나 사내 전용 레지스트리, 로컬 DB 덤프 파일은 어떻게 쓰나요?" 클라우드 기반 에이전트 세션을 도입한 팀이라면 금방 마주치는 질문입니다. 코드 저장소는 깃헙에 올려두면 되지만, 실무에서는 아직 커밋되지 않은 작업 파일, 회사 VPN 안에서만 열리는 내부 도구, 개발자의 로컬 환경에만 설치된 바이너리처럼 "깃헙에는 없고 내 컴퓨터에만 있는" 자원이 항상 남습니다. 이 요구를 그대로 들어주면, 클라우드에 떠 있는 에이전트 프로세스가 사용자의 개인 컴퓨터 파일시스템에 직접 손을 대는 통로가 하나 열립니다.

문제는 이 통로가 편도가 아니라는 데 있습니다. 한 번 열어주면 에이전트가 그 컴퓨터의 다른 폴더로, 또 다른 세션으로 옮겨 다닐 수 있을까요? 승인은 한 번만 받으면 영구히 유효할까요, 아니면 매번 다시 물어야 할까요? 이런 질문에 답하지 않고 "로컬 접근 기능"부터 구현하면, 보안 사고가 나기 전까지는 편리하다가 사고가 나는 순간 전체 신뢰 모델을 재설계해야 하는 상황에 몰립니다.

 

전체 시스템에서의 위치

이 기능은 세 개의 서로 다른 신뢰 영역을 잇습니다. 첫째는 클라우드 컨테이너 — 에이전트 세션이 실제로 실행되는 곳으로, 이미 저장소나 업로드 파일, 컨테이너 이미지가 들어 있습니다. 둘째는 사람의 승인이라는 관문으로, 어떤 자동화 설정으로도 건너뛸 수 없는 지점입니다. 셋째는 사용자의 로컬 컴퓨터로, 상주 프로세스가 돌면서 "이 폴더는 외부 세션에 내줘도 된다"고 미리 지정해 둔 폴더 목록을 들고 있습니다. 신뢰 확인이 한 곳에서 끝나지 않는다는 점이 중요합니다. "이 컨테이너 안의 코드·파일을 믿는가"와 "이 세션이 내 다른 컴퓨터·세션에 손대도 되는가"는 서로 다른 질문이라서 별도의 승인 게이트로 분리돼 있습니다.

 

선택의 트레이드오프
방식승인 시점노출 범위해제 주체
장기 SSH 키최초 1회키가 접근 가능한 전체 경로사람(수동 키 폐기)
VPN + 서비스 계정계정 발급 시네트워크 세그먼트 전체관리자
브라우저 네이티브 메시징설치 시 1회호스트가 노출한 범위사용자(확장 제거)
세션-폴더 1:1 바인딩요청마다 매번세션당 폴더 정확히 1개사람만

 

세션-폴더 1:1 바인딩 방식이 다른 셋과 가장 크게 다른 점은 "승인의 유효 기간"입니다. 장기 키나 VPN 계정은 한 번 발급되면 누군가 명시적으로 회수할 때까지 계속 살아 있어서, 시간이 지날수록 "이게 아직도 필요한 접근인가"를 아무도 추적하지 못하는 상태가 됩니다. 반면 이 설계는 세션이 끝나면 접근도 함께 끝납니다. 대신 그 대가로 세션마다 사람이 다시 응답해야 하므로, 완전 자동화된 배치 작업에는 쓸 수 없습니다 — 이건 결함이 아니라 의도된 제약입니다. 반대로 사람이 매번 응답할 수 없는 배치 작업이라면 이 패턴은 처음부터 맞지 않으며, 범위를 좁힌 서비스 계정과 짧은 TTL 토큰 조합이 낫습니다.

 

실제 프로젝트 진행 순서

1) 경계부터 숫자로 정의합니다 — 세션 하나당 외부 자원 몇 개까지 연결 가능한지. 여러 개를 허용하면 "이 세션이 지금 뭘 쥐고 있는지" 추적하는 별도 장부가 필요해집니다.
2) 실제 파일 전송 로직보다 승인 UX부터 끝까지 동작하게 만듭니다 — 요청·승인 질문·attached/refused/무응답 세 가지 결과 흐름이 먼저입니다.
3) 승인을 UI가 아니라 서버 쪽에서 강제합니다. 클라이언트에서만 막으면 우회될 수 있습니다.
4) 모든 연결·해제 이벤트를 로그로 남깁니다. 그렇지 않으면 사고가 났을 때 당시 상태를 복원할 수 없습니다.
5) "컨텐츠를 믿는가"와 "다른 자원에 손대도 되는가"를 하나의 승인으로 합치지 않고 기능 단위로 분리합니다.

 

주의 — 에이전트 쪽에 연결 해제 도구를 일부러 주지 않는 것은 실수가 아니라 설계 의도입니다. 에이전트가 스스로 연결을 끊을 수 있다면, 반대로 스스로 다시 연결을 요청하는 루프를 만들 유인도 함께 생깁니다. 해제를 전적으로 사람에게만 맡겨야, 적어도 연결 유지 방향으로는 에이전트가 자동화를 밀어붙일 수 없습니다.

 

정리

클라우드 에이전트의 로컬 자원 접근은 기능이 아니라 신뢰 경계 설계 문제로 먼저 다뤄야 합니다. 세션-자원 1:1 바인딩과 매 요청 승인은 장기 키·VPN 방식보다 노출 범위를 좁히는 대신 완전 자동화와는 양립하지 않으며, 데이터 전송 로직보다 승인 UX와 서버 측 강제, 연결·해제 로깅을 먼저 완성해야 사고 시 복원 가능한 설계가 됩니다.
