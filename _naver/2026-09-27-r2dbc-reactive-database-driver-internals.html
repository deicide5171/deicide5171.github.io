R2DBC 내부 동작 — JDBC를 리액티브로 감싸는 게 안 되는 이유

백엔드

한 줄 요약 — JDBC는 API 자체가 블로킹을 전제하므로, R2DBC는 소켓 레벨부터 논블로킹으로 새로 구현해 리액티브 스택의 이점을 지킵니다.

 

왜 JDBC를 그냥 감싸면 안 되는가

Spring WebFlux로 애플리케이션을 논블로킹으로 구성했다면, 소수의 이벤트 루프 스레드가 절대 블로킹되지 않아야 합니다. 그런데 JDBC의 Connection, Statement, ResultSet API는 애초에 동기 블로킹 호출을 전제로 설계됐습니다. Mono.fromCallable로 감싸도 그 순간 리액티브 스택의 핵심 이점인 "적은 스레드로 많은 동시 연결 처리"가 사라집니다.

 

SPI 자체가 리액티브 스트림 기반

R2DBC는 데이터베이스와 통신하는 SPI 자체를 Reactive Streams Publisher(Mono/Flux)로 정의했습니다. 드라이버 구현체는 DB와의 통신을 처음부터 Netty 같은 논블로킹 네트워크 라이브러리 위에 직접 구현해, 데이터를 기다리는 동안 스레드를 점유하지 않습니다.

커넥션 풀과 트랜잭션도 리액티브하게

전통적인 커넥션 풀은 블로킹 getConnection() 호출 구조라 그대로 쓸 수 없어, r2dbc-pool이라는 자체 풀 구현이 있습니다. 트랜잭션 경계도 Reactive Context를 통해 전파되는데, 리액티브 체인은 여러 스레드를 오갈 수 있으므로 트랜잭션 상태를 스레드가 아니라 구독 컨텍스트에 묶어야 하기 때문입니다.

항목 JDBC R2DBC
API 모델 동기 블로킹 Reactive Streams
네트워크 I/O 블로킹 소켓 논블로킹(Netty)
트랜잭션 전파 ThreadLocal Reactive Context

 

Spring Data R2DBC 예제
public interface OrderRepository extends ReactiveCrudRepository<Order, Long> {
    Flux<Order> findByStatus(String status);
}

@Service
public class OrderService {
    private final OrderRepository repository;
    private final TransactionalOperator txOperator;

    public Mono<Order> createOrder(Order order) {
        return repository.save(order)
                .flatMap(saved -> updateInventory(saved))
                .as(txOperator::transactional);
    }
}

 

실무 포인트

JPA/Hibernate와의 조합은 아직 성숙하지 않습니다. 복잡한 연관관계 매핑이 많은 도메인이라면 R2DBC + Spring Data R2DBC의 단순한 매핑 모델이 한계로 작용할 수 있습니다.

드라이버 지원 범위를 먼저 확인하세요. PostgreSQL, MySQL, MariaDB, SQL Server, H2는 지원되지만 오래된 상용 DB는 드라이버 자체가 없을 수 있습니다.

주의 — R2DBC로 전환해도 같은 요청 경로에서 블로킹 HTTP 클라이언트나 JDBC 기반 캐시 라이브러리를 호출하면 이벤트 루프 스레드가 그 지점에서 멈춥니다. 스택 전체가 논블로킹이어야 이점이 살아납니다.
