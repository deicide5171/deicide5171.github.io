"이 체크리스트, 팀원들이 같이 체크하게 해주세요" — 정적 페이지 하나가 상태를 가진 앱으로 바뀌는 경계선

AI

한 줄 요약 — AI가 그 자리에서 만들어주는 정적 페이지가 '팀원들과 같이 쓰는 도구'로 바뀌려면 어디서부터 백엔드가 필요한지, Claude Artifacts에 추가된 런타임 capabilities(공유 데이터베이스·뷰어 식별)를 기준으로 로컬 프로토타입과 풀스택 서비스 사이의 설계 경계를 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"이 체크리스트 좀 만들어서 팀원들이 같이 체크하게 해주세요"라는 요구는 몇 달 전까지만 해도 명확히 두 단계로 쪼개졌습니다. AI 에이전트에게 정적 HTML 페이지 하나를 받아 빠르게 프로토타입을 보여주는 단계, 그리고 "이제 진짜로 써야겠다"는 순간 DB·인증·API 서버를 갖춘 풀스택 서비스로 처음부터 다시 만드는 단계. 이 사이에 다리가 없었습니다.

그런데 최근 Claude의 Artifact(대화 중 즉석에서 생성되는 실행 가능한 페이지)에 런타임 capabilities라는 개념이 추가됐습니다. 페이지가 단순히 브라우저 안에서만 동작하는 정적 문서가 아니라, 공유 데이터베이스를 선언해 여러 사람이 같은 데이터를 보고 쓰거나, 누가 보고 있는지 식별하는 등 백엔드가 하던 일의 일부를 명시적으로 요청할 수 있게 된 것입니다. 빌더 입장에서는 "이 요구사항을 프로토타입으로 끝낼지, 백엔드를 갖춘 서비스로 만들지"를 가르는 경계선 자체가 이동했다는 신호입니다.

 

전체 시스템에서의 위치

정적 Artifact 페이지는 브라우저 하나의 로컬 환경 안에서 완결됩니다 — 상태가 있다면 그 브라우저의 localStorage뿐이고, 다른 사람이 같은 링크를 열어도 서로 다른 데이터를 봅니다. capabilities를 선언한 페이지는 이 위치가 달라집니다. 데이터 읽기·쓰기 요청이 공유 저장소를 거치면서, "클라이언트 전용 프로토타입"과 "직접 구축한 백엔드를 가진 서비스" 사이에 중간 지점 하나가 새로 생긴 셈입니다.

이 중간 지점이 커버하는 범위를 정확히 아는 것이 설계의 핵심입니다. 여러 뷰어가 같은 데이터를 보고 쓰는 것, 뷰어를 식별하는 것까지는 처리하지만, 복잡한 쿼리, 대용량 데이터, 외부 시스템 연동, 세밀한 권한 모델처럼 전통적인 백엔드가 하던 일 전부를 대체하지는 않습니다.

가장 많이 저지르는 실수는 이 중간 지점을 "완성된 백엔드"로 착각하고 점점 더 많은 기능을 쌓는 것입니다. capabilities는 프로토타입이 실제로 쓸모 있는지 빠르게 검증하는 용도이지, 외부에 공개하는 정식 서비스의 최종 아키텍처가 아닙니다.

 

실제 프로젝트 진행 순서

1) 요구사항에서 "공유가 정말 필요한가"부터 가립니다.
2) 공유가 필요하다면 capabilities를 선언한 Artifact로 먼저 만들어 하루 이틀 안에 검증합니다.
3) 사용량·데이터가 늘어나는 지점을 지켜봅니다.
4) 그 신호가 오면 이미 검증된 데이터 모델을 그대로 서버·DB로 옮기는 좁은 범위의 마이그레이션을 수행합니다.
5) 민감한 데이터는 애초에 capabilities 단계에 올리지 않고 처음부터 직접 구축한 백엔드로 시작합니다.

 

주의 — 공유 저장소 기반 도구는 첫 입력이 다른 사람에게도 보인다는 사실을 모르고 민감한 값을 적어 넣는 사고로 이어지기 쉽습니다. 팀에 배포할 때는 이 점을 사용 안내에 명시하고, 실서비스로 전환할 계획이 없는 수명이 짧은 내부 도구로만 범위를 못 박아 쓰세요.

 

정리

Claude Artifacts의 런타임 capabilities는 "클라이언트 전용 정적 페이지"와 "직접 구축한 풀스택 서비스" 사이에 공유 상태를 가진 중간 지점을 새로 만들었습니다. 이 지점은 소규모 공유·빠른 검증에만 적합할 뿐 완성된 백엔드가 아니므로, 공유가 실제로 필요한지부터 가리고 사용량이 늘어나는 신호가 보일 때만 전통적 백엔드로 좁은 범위의 마이그레이션을 수행하는 순서가 가장 비용 효율적입니다.
