한 줄 요약 — 도구가 늘어날수록 모델이 잘못 선택하거나 인자를 잘못 채웁니다. 스키마 설계 원칙과 병렬 호출 결과 매칭 전략을 정리했습니다.

 

왜 지금 Function Calling을 다시 봐야 하는가

도구 두세 개로 프로토타입을 만들 때는 잘 되지만, 실제 서비스에서 도구가 수십 개로 늘어나면 모델이 엉뚱한 것을 고르거나 필수 인자를 빠뜨리는 경우가 늘어납니다. 여러 도구를 동시에 호출해야 하는 상황을 순차 처리하면 지연시간도 도구 개수에 비례해 늘어납니다.

 

도구 스키마는 API 문서이자 모델을 위한 프롬프트다

도구 설명이 짧고 모호하면 비슷한 다른 도구와 구분이 안 돼 잘못 선택되기 쉽습니다. 열거형으로 제한 가능한 파라미터는 반드시 enum으로 좁히고, 언제 쓰고 쓰지 않아야 하는지를 예시와 함께 명시하는 것이 핵심 원칙입니다.

 

병렬 도구 호출과 결과 재주입의 순서 문제

여러 도구 호출을 병렬 실행한 뒤 tool_call_id로 명시적으로 매칭해 모델에 돌려줘야 합니다. 매칭이 어긋나면 결과가 뒤바뀌어 잘못된 답변이 나올 수 있습니다.

설계 요소 잘못된 예 개선 방향
도구 이름 get_data, fetch_info 목적이 명확한 이름
파라미터 타입 자유 형식 문자열 enum·범위로 제약
병렬 호출 결과 순서만 믿고 매칭 tool_call_id 명시 매칭

 

예제 — 병렬 도구 호출 실행과 결과 매칭
async def execute_tool_calls(tool_calls, tool_registry):
    async def run_one(call):
        try:
            fn = tool_registry[call.name]
            result = await fn(**call.arguments)
            return {"tool_call_id": call.id, "content": json.dumps(result)}
        except Exception as e:
            return {"tool_call_id": call.id, "content": json.dumps({"error": str(e)})}

    results = await asyncio.gather(*(run_one(c) for c in tool_calls))
    return sorted(results, key=lambda r: [c.id for c in tool_calls].index(r["tool_call_id"]))

tool_call_id를 결과에 명시적으로 포함시키면 완료 순서가 뒤바뀌어도 원래 요청과의 대응 관계가 깨지지 않습니다.

 

실무 포인트

도구 개수가 많아지면 계층적 라우팅을 고려하세요. 카테고리를 먼저 고르게 하고 세부 도구를 다음 단계에서 노출하면 선택 정확도가 올라갑니다.

실패한 도구 호출의 에러 메시지를 모델이 이해할 수 있는 형태로 가공하세요. 구조화된 에러를 돌려주면 모델이 다음 행동을 더 잘 판단합니다.

주의 — 부작용이 있는 도구(결제, 삭제 등)는 병렬 실행 대상에서 명시적으로 제외하거나 별도 확인 단계를 거치게 하세요. 확인 없이 병렬 실행하면 의도하지 않은 결과가 한꺼번에 발생할 수 있습니다.
