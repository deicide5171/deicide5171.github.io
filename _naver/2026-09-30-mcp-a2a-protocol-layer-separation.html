에이전트에게 도구를 줄 것인가, 다른 에이전트에게 위임할 것인가 — MCP와 A2A의 역할 분리

AI

한 줄 요약 — MCP는 내가 소유·신뢰하는 자원에 대한 함수 호출, A2A는 내가 통제하지 않는 자율 에이전트에 대한 업무 위임입니다. 2026년 두 프로토콜이 각각 에이전트 스택의 Layer 1과 Layer 2로 자리잡은 지금, 무엇을 언제 써야 하는지 정리합니다.

 

"여러 회사 예약 시스템을 한 번에 묶어주세요"

여행 예약 에이전트를 만들어 항공사·호텔·렌터카 예약을 한 번에 처리해달라는 요구를 받으면, 초기에는 대부분 MCP 서버를 늘리는 방식으로 접근합니다. 항공사 API도, 호텔 API도 MCP 도구로 감쌉니다. 문제는 그 회사들이 이미 자기 내부에 자율적인 예약 에이전트를 운영하고 있을 때 시작됩니다. 그들은 재고·취소 정책·가격 협상 로직을 API 스펙으로 전부 공개하지 않으니, "도구를 호출한다"는 모델 자체가 이 지점에서 깨집니다.

2026년 들어 이 문제에 대한 업계 합의가 굳어졌습니다. MCP는 다운로드 9,700만 건을 넘기며 에이전트-도구 계층을 사실상 장악했고, Google이 만들어 리눅스 재단으로 이관한 A2A(Agent2Agent) 프로토콜은 AWS·Cisco·Microsoft·Salesforce 등 150개 이상 조직의 지지를 받으며 에이전트 간 위임 계층의 표준이 됐습니다. 둘은 경쟁 관계가 아니라 스택의 서로 다른 층이라는 것이 정리된 그림입니다.

 

요구사항을 기술 문제로 번역하기

"예약을 한 번에 처리해주세요"라는 말은 실제로 전혀 다른 두 상호작용을 뭉쳐서 표현한 것입니다. 하나는 내가 소유·신뢰하는 자원에 대한 접근(사내 재고 DB, 결제 게이트웨이, 캘린더)으로, 함수 호출에 가깝고 신뢰 경계 안에서 동기적으로 처리됩니다. 다른 하나는 내가 소유하지 않은 자율 에이전트에 대한 업무 위임으로, 상대가 내부적으로 무엇을 하는지 나는 모르며 비동기 응답과 협상이 끼어들 수 있습니다.

이 둘을 같은 프로토콜로 처리하려 하면 문제가 생깁니다. MCP로 항공사 API를 억지로 감싸면 좌석 홀드 만료나 가격 변동 같은 상대의 내부 상태를 실시간 반영하기 어렵고, 스펙이 바뀔 때마다 내 서버도 같이 깨집니다. 반대로 사내 결제 호출까지 A2A로 처리하면 불필요한 협상·핸드셰이크 오버헤드만 늘어납니다.

 

A2A 쪽 핵심 개념은 Agent Card입니다. 상대 에이전트가 무엇을 할 수 있고, 어떤 입력을 받고, 인증은 어떻게 하는지 선언한 메타데이터 문서로, OpenAPI 스펙이 REST API의 계약이듯 Agent Card가 위임의 계약 역할을 합니다. 오케스트레이터는 이 카드를 보고 위임 가능 여부를 판단해 태스크를 생성하고, 상대는 자기 페이스로 작업하다가 상태를 업데이트해 돌려줍니다.

 

선택의 트레이드오프
기준 MCP (Layer 1) A2A (Layer 2)
관계 내가 소유·신뢰하는 자원 내가 소유하지 않은 자율 에이전트
상호작용 함수 호출, 대체로 동기 태스크 위임, 비동기·장기 실행
스펙 소유권 내가 도구 스펙 정의 상대가 Agent Card로 선언
신뢰 경계 조직 내부 조직 간
대표 사례 사내 DB·결제·캘린더 파트너사 예약 에이전트 위임

 

"일단 다 MCP로 시작해서 나중에 A2A로 옮기면 되지 않나"라는 생각은 함정입니다. 초기부터 구분해두지 않으면 MCP 서버가 우후죽순 늘어나며 외부 조직의 비동기 워크플로우를 동기 호출처럼 흉내 내는 안티패턴이 굳어집니다. 반대로 사내 시스템까지 A2A로 감싸면 불필요한 오버헤드와 보안 표면만 늘어납니다. A2A는 조직 경계를 넘나드는 만큼 인증·권한 위임과 거버넌스를 처음부터 설계에 넣어야 하는 계층입니다.

 

실제 진행 순서

1단계: 요구사항에 등장하는 모든 연동 지점을 "내가 소유한 자원인가, 타 조직 자율 에이전트인가"로 먼저 분류합니다.

2단계: 사내 DB·결제·캘린더 같은 확실한 Layer 1 자원부터 MCP 서버로 정리하고, 도구 스키마·에러 처리 관례를 팀 표준으로 굳힙니다.

3단계: 상대가 비동기로 작업하고 중간에 승인·협상이 끼어들 수 있는 연동을 A2A 후보로 추립니다.

4단계: 태스크 정의보다 먼저 Agent Card와 인증·위임 권한 모델을 확정합니다.

5단계: 오케스트레이터에 "이 요청을 MCP 도구 호출로 처리할지, A2A 태스크로 위임할지" 판단하는 라우팅 로직을 명시적으로 둡니다.

주의 — A2A는 조직 경계를 넘나드는 프로토콜이라 보안 표면이 넓습니다. Agent Card 검증, 위임 토큰의 유효 범위·만료, 상대가 반환한 결과의 신뢰도 검증을 태스크 설계보다 먼저 확정해야 합니다.

 

정리

MCP는 내가 신뢰하는 자원에 대한 함수 호출, A2A는 내가 통제하지 않는 자율 에이전트에 대한 업무 위임입니다. 두 계층을 처음부터 구분해두지 않으면 MCP 서버가 비동기 워크플로우를 흉내 내는 안티패턴이 굳어집니다. A2A를 쓰기로 했다면 태스크 설계보다 Agent Card·인증·위임 권한 모델을 먼저 확정해야 합니다.
