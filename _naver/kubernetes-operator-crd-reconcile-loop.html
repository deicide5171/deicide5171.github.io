Kubernetes Operator 내부 동작 — Reconcile Loop는 왜 이벤트가 아니라 상태를 본다

네트워크·OS·분산처리·DevOps

한 줄 요약 — Operator는 이벤트를 처리 대상이 아니라 신호로만 쓰고, 매번 현재 상태를 다시 읽어 desired state와 비교하는 레벨 트리거링으로 이벤트 누락에도 강건합니다.

 

이벤트 핸들러로 오해하면 안 되는 이유

Operator를 "리소스 변경 이벤트를 받아서 처리하는 핸들러"로 설계하면, 이벤트를 하나라도 놓쳤을 때 시스템 상태가 영원히 어긋난 채 남는 근본적인 약점이 있습니다. Kubernetes의 내장 컨트롤러들은 엣지 트리거링이 아니라 레벨 트리거링으로 이 문제를 피합니다.

 

레벨 트리거링 — 진실은 항상 다시 읽는다

이벤트는 "무언가 바뀌었을 수도 있으니 다시 확인하라"는 신호일 뿐입니다. Reconcile 함수가 호출되면 항상 현재 클러스터의 실제 상태를 API 서버에서 새로 조회하고, CRD에 선언된 원하는 상태와 비교해 그 차이를 줄입니다. 이벤트를 몇 개 놓쳐도 다음 reconcile에서 다시 비교하므로 결과적으로 같은 최종 상태로 수렴합니다.

Informer, Work Queue, Reconciler의 3단 구조

Informer는 API 서버에 watch 커넥션을 열고 변경 감지 시 리소스 키를 Work Queue에 넣습니다. Work Queue는 중복을 제거하고 실패 시 지수 백오프로 재큐잉합니다. 워커는 큐에서 키를 꺼내 Reconcile 함수를 호출하는데, 이 함수는 이벤트 내용이 아니라 키만 받으므로 항상 리소스를 다시 조회해야 합니다.

구성 요소 역할
Informer watch, 캐시 유지, 큐에 키 추가
Work Queue 중복 제거, 재시도 백오프
Reconciler 현재 상태 재조회 후 수렴 동작

 

controller-runtime Reconcile 함수 골격
func (r *AppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app appsv1.MyApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    var deploy appsv1.Deployment
    err := r.Get(ctx, types.NamespacedName{Name: app.Name, Namespace: app.Namespace}, &deploy)
    if errors.IsNotFound(err) {
        return ctrl.Result{}, r.Create(ctx, buildDeployment(&app))
    }

    if *deploy.Spec.Replicas != app.Spec.Replicas {
        deploy.Spec.Replicas = &app.Spec.Replicas
        return ctrl.Result{}, r.Update(ctx, &deploy)
    }

    return ctrl.Result{RequeueAfter: 30 * time.Second}, nil
}

 

실무 포인트

Reconcile은 여러 번 호출돼도 안전해야 합니다. 멱등성을 지키지 않으면 재시도 시 리소스를 중복 생성하거나 상태를 어긋나게 만듭니다.

외부 API 호출은 반드시 타임아웃을 두세요. Reconcile 안에서 무한정 블로킹되면 Work Queue 워커가 고갈되어 다른 리소스 처리까지 지연됩니다.

주의 — watch 이벤트만 믿지 말고, Kubernetes API가 감지할 수 없는 외부 상태 변화는 RequeueAfter로 주기적 재확인을 명시적으로 설계해야 합니다.
