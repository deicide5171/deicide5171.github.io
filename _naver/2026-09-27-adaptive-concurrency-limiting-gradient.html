Adaptive Concurrency Limiting — 고정 스레드풀 대신 지연시간으로 동시성 한도를 자동 조절하기

아키텍처·시스템 설계

한 줄 요약 — TCP 혼잡 제어에서 착안해, 지연시간 변화를 관찰하며 동시성 한도를 사람이 아니라 시스템이 실시간으로 자동 조절합니다.

 

왜 고정 한도는 항상 틀린 값이 되는가

스레드풀 크기나 최대 동시 요청 수를 부하 테스트로 한 번 고정하면, 이 숫자가 정확한 순간은 그 벤치마크를 수행한 순간뿐입니다. 백엔드가 느려지거나 GC 일시정지가 길어지면 같은 요청 수라도 실제 처리 가능 용량은 크게 달라집니다.

 

TCP 혼잡 제어에서 빌려온 아이디어

TCP는 네트워크 혼잡도를 사전에 알 수 없으므로 전송 속도를 점진적으로 늘리다가 지연 증가가 관찰되면 줄이는 피드백 루프를 씁니다. Netflix의 concurrency-limits 라이브러리는 이 원리를 애플리케이션 서버에 그대로 적용해, 지연시간이 늘면 한도를 낮추고 안정적이면 서서히 늘립니다.

Little's Law와 그래디언트 기반 계산

"동시성 = 처리량 × 평균 응답시간"이라는 Little's Law를 이용합니다. 그래디언트 알고리즘은 여유로울 때의 기준 지연시간과 현재 지연시간의 비율을 계산해, 비율이 1에 가까우면 한도를 늘리고 커지면 줄이는 방향으로 매 요청마다 미세 조정합니다.

항목 고정 한도 Adaptive
한도 결정 사전 벤치마크 실시간 관찰
백엔드 상태 변화 대응 불가 자동 반영

 

Java 서버 적용 예제
Limiter<Void> limiter = SimpleLimiter.newBuilder()
    .limit(Gradient2Limit.newBuilder()
        .initialLimit(20)
        .minLimit(10)
        .maxConcurrency(200)
        .build())
    .build();

public Response handleRequest(Request request) {
    Optional<Limiter.Listener> listener = limiter.acquire(null);
    if (!listener.isPresent()) {
        return Response.status(503).build();
    }
    try {
        Response result = processRequest(request);
        listener.get().onSuccess();
        return result;
    } catch (Exception e) {
        listener.get().onIgnore();
        throw e;
    }
}

 

실무 포인트

RTT_noload 측정 구간에 주의하세요. 배포 직후 캐시가 덜 데워진 상태를 기준으로 학습하면 이후 정상 상태를 포화로 오판할 수 있습니다.

고정 한도와 병행 운용하는 것이 안전합니다. 최소·최대 한도를 명시적으로 설정해 알고리즘의 조정 범위를 제한하세요.

주의 — 하나의 서비스가 여러 다운스트림을 호출한다면 전체를 하나의 풀로 묶지 말고 의존성별로 독립된 리미터를 두어야, 한 다운스트림 장애가 다른 호출까지 막지 않습니다.
