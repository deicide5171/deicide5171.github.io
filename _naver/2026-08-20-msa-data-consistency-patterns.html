사가 하나로는 부족합니다 — 마이크로서비스 데이터 정합성 패턴 조합 가이드

2026. 8. 20. · 아키텍처·시스템설계

한 줄 요약 — 사가, 아웃박스, 이벤트소싱, CDC는 각각 따로 설명되는 경우가 많지만 실무에서는 조합이 기본값입니다. 어떤 조건에서 무엇을 겹쳐 써야 하는지 의사결정 관점으로 정리했습니다.

 

왜 지금 이 정리가 필요한가

사가(Saga), 트랜잭셔널 아웃박스(Outbox), 이벤트소싱(Event Sourcing), CDC(Change Data Capture) — 마이크로서비스의 데이터 정합성을 다루는 이 네 가지 패턴은 각각 블로그 글 하나씩으로 설명될 만큼 이미 잘 알려져 있습니다. 문제는 실무에서 마주치는 질문이 "사가가 뭔가요?"가 아니라 "우리 주문-결제-재고 흐름에는 사가만 쓰면 되나, 아웃박스도 같이 써야 하나?" 같은 조합 문제라는 점입니다. 패턴을 개별로 아는 것과, 여러 패턴이 겹쳐 있는 실제 시스템에서 무엇을 먼저 넣고 무엇을 나중에 더할지 판단하는 것은 전혀 다른 능력입니다.

이 글에서는 각 패턴의 내부 구현을 다시 설명하지 않습니다. 대신 네 패턴이 정합성 문제의 서로 다른 축을 담당한다는 점에서 출발해, 실제 시나리오에서 어떤 조합이 기본값이고 어떤 조합이 과설계인지를 의사결정 기준으로 정리해보겠습니다.

 

핵심 개념 1 — 패턴마다 책임지는 축이 다릅니다

네 패턴을 경쟁 관계로 놓고 하나만 고르려 하면 조합 판단 자체가 불가능해집니다. 각 패턴이 정합성 문제의 어느 축을 책임지는지부터 구분해야 합니다.

패턴 책임지는 축 다루지 않는 것
사가 여러 서비스에 걸친 트랜잭션 흐름 조율과 실패 시 보상 각 단계의 이벤트 발행 자체가 유실되지 않는지는 보장 안 함
아웃박스 로컬 DB 커밋과 이벤트 발행을 하나의 트랜잭션으로 묶기(이중 쓰기 방지) 여러 서비스 간의 흐름 조율은 다루지 않음
이벤트소싱 상태 변화 자체를 도메인 이벤트로 영속화해 완전한 이력 확보 이벤트를 어떻게 안전하게 내보낼지는 별도 문제
CDC 기존 테이블의 변경 로그를 실시간으로 다른 시스템에 전파 애플리케이션 계층의 트랜잭션 조율이나 도메인 이벤트 설계는 관여 안 함

 

이 표에서 눈여겨볼 부분은 사가와 아웃박스가 서로 배타적이지 않고 겹치지도 않는다는 점입니다. 사가는 "어떤 순서로 무엇을 호출하고 실패하면 무엇을 되돌릴지"를 결정하고, 아웃박스는 "그 각 단계에서 발행하는 이벤트가 DB 커밋과 함께 원자적으로 나가는지"를 결정합니다. 사가만 넣고 아웃박스를 빠뜨리면, 사가의 각 단계 자체는 정확히 설계했더라도 그 단계의 이벤트 발행에서 이중 쓰기 문제가 그대로 재발합니다.

 

핵심 개념 2 — 시나리오별 기본 조합 매트릭스

실무에서 반복적으로 등장하는 조건은 크게 두 가지입니다. "여러 서비스에 걸친 트랜잭션 조율이 필요한가"와 "각 단계의 이벤트 발행 안정성을 보장해야 하는가"입니다. 이 두 질문만으로 상당수 상황의 기본 조합이 정해집니다.

 

여기에 두 축이 더 얹힙니다. 첫째, "이 도메인이 완전한 변경 이력·재생 능력을 요구하는가"라면 위 조합 위에 이벤트소싱을 더합니다 — 정산, 대출 심사처럼 "왜 이 상태가 되었는가"를 사후에 설명해야 하는 도메인이 대표적입니다. 둘째, "쓴 직후 같은 사용자가 바로 조회하는 화면의 일관성이 중요한가"라면 읽기 경로에 Read-Your-Writes 전략을 별도로 얹습니다. 이 두 축은 트랜잭션 조율·발행 안정성 축과 독립적이라, 사분면 어디에 있든 필요하면 추가로 결합할 수 있습니다.

시나리오 기본 조합 이유
주문-결제-재고처럼 여러 서비스를 순서대로 조율하고, 이벤트 유실도 허용 안 됨 사가(오케스트레이션) + 아웃박스 조율은 사가가, 각 단계 이벤트의 원자적 발행은 아웃박스가 담당
정산·감사 도메인처럼 "왜 이 상태가 됐는지" 이력이 핵심 사가 + 아웃박스 + 이벤트소싱 조율·발행 안정성 위에 완전한 이력 확보까지 필요
레거시 DB를 그대로 두고 검색 색인·캐시만 동기화 CDC 단독 서비스 간 조율 자체가 없으므로 사가는 불필요
단일 서비스 내부에서 DB 쓰기 + 이벤트 발행만 원자적으로 묶으면 되는 경우 아웃박스 단독 조율할 다른 서비스가 없어 사가는 과설계

 

CDC와 이벤트소싱을 같은 시스템에 함께 쓰는 조합도 흔합니다. 이벤트소싱으로 도메인 서비스를 만들되, 그 서비스의 조회 전용 모델(read model)을 CDC로 다시 다른 시스템에 전파하는 식입니다. 이 경우 이벤트소싱이 "진실의 원천"을 만들고, CDC는 그 원천에서 파생된 read model의 변경을 전파하는 역할로 계층이 나뉩니다.

 

예제 — 사가 단계에 아웃박스를 결합하는 지점

두 패턴을 따로 아는 것과 실제로 겹쳐서 구현하는 것의 차이는 "사가의 각 단계가 정확히 어느 지점에서 outbox 테이블에 기록하는가"에 있습니다. 오케스트레이터가 재고 예약 단계를 호출하면, 재고 서비스는 자신의 로컬 트랜잭션 안에서 재고 차감과 outbox 이벤트 기록을 함께 커밋해야 합니다.

@Transactional
public void reserveInventory(SagaStep step) {
    inventory.decreaseStock(step.getSku(), step.getQty());

    // 사가 오케스트레이터에게 보낼 결과도 outbox를 경유한다
    outboxRepository.save(new OutboxEvent(
        "Inventory", step.getSagaId(),
        "InventoryReserved", toJson(step)
    ));
} // 재고 차감과 이벤트 기록이 하나의 트랜잭션으로 커밋

오케스트레이터는 이 이벤트를(Kafka 등을 거쳐) 구독해 다음 단계를 진행하거나, 실패 이벤트라면 보상 트랜잭션을 지시합니다. 만약 이 단계에서 outbox 없이 재고 차감 직후 곧바로 오케스트레이터에 HTTP로 결과를 통보한다면, 통보가 네트워크 문제로 유실됐을 때 재고는 이미 차감됐는데 오케스트레이터는 이 사실을 영영 모르는 상태에 빠집니다 — 사가 하나만으로는 막을 수 없는 실패 지점입니다.

 

실무 도입 시 이것만은 챙기세요
1. 패턴을 추가할 때마다 축이 겹치는지 먼저 확인 — 겹치지 않는데 패턴을 하나 더 얹는다면 이력·읽기 일관성 등 정말 새로운 요구사항이 생겼다는 뜻이어야 합니다
2. 이벤트소싱은 가장 무거운 조합이므로 마지막에 검토 — "이력이 있으면 좋겠다"가 아니라 "이력 없이는 도메인이 성립하지 않는다"는 근거가 있을 때만 사가·아웃박스 위에 얹습니다
3. CDC를 아웃박스 릴레이로 쓰는 것과 독립적 레거시 연동으로 쓰는 것을 구분 — 전자는 아웃박스 패턴의 구현 디테일이고, 후자는 애초에 사가나 아웃박스가 필요 없는 별개 시나리오입니다
4. 조합이 늘어날수록 관찰 가능성 비용도 함께 증가 — 사가 흐름, outbox 미발행 건수, CDC 커넥터 지연, 이벤트소싱 재생 시간을 각각 모니터링해야 하므로 그만한 운영 비용을 감당할 준비가 됐는지 미리 확인해야 합니다

 

마무리 — 3줄 요약

① 사가·아웃박스·이벤트소싱·CDC는 경쟁 관계가 아니라 정합성 문제의 서로 다른 축(조율, 발행 안정성, 이력, 전파)을 담당하는 보완 관계입니다.
② 여러 서비스 조율과 이벤트 발행 안정성이 함께 필요한 흐름(주문-결제-재고형)에서는 사가(오케스트레이션)와 아웃박스의 조합이 실무 기본값입니다.
③ 완전한 이력이 필요하면 이벤트소싱을, 쓴 직후 조회 일관성이 필요하면 Read-Your-Writes를 별도 축으로 추가하되, 조합이 늘어날수록 관찰 가능성 비용도 함께 커진다는 점을 감안해야 합니다.
