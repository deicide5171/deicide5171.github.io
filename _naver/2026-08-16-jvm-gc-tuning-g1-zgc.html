JVM GC 튜닝 실전 — G1과 ZGC, 언제 무엇을 골라야 할까

2026. 8. 16. · 백엔드

한 줄 요약 — G1은 처리량과 지연시간의 균형을 노리는 범용 기본 GC이고, ZGC는 짧고 예측 가능한 일시정지를 목표로 설계된 저지연 특화 GC입니다. 언제 무엇을 선택해야 하는지 실전 관점에서 정리했습니다.

 

왜 지금 GC 튜닝인가

JVM 애플리케이션을 운영하다 보면 결국 마주치는 질문이 있습니다. "왜 가끔씩 요청이 수백 ms씩 튀는가"라는 질문입니다. 대부분은 코드나 인프라가 아니라 GC(Garbage Collection)의 일시정지(Stop-the-world) 때문입니다. G1 GC가 JDK 9부터 기본 GC 자리를 지켜온 덕분에 많은 팀이 GC 튜닝을 뒤로 미뤄왔지만, 실시간 트레이딩·게임 서버는 물론 최근에는 LLM 서빙 게이트웨이처럼 응답 지연에 민감한 서비스가 늘면서 GC 선택이 다시 중요한 설계 결정이 되고 있습니다.

최근 JDK 릴리스 흐름도 한몫합니다. ZGC는 JDK 15에서 프로덕션 지원으로 승격됐고, JDK 21에서는 세대(Generational) 개념을 도입한 Generational ZGC가 실험적으로 추가되면서 처리량 약점을 상당 부분 보완했습니다. 세대별 모드는 이후 릴리스에서 기본 동작 방향으로 자리잡아가는 추세이니, 사용 중인 JDK 버전의 릴리스 노트는 미리 확인해 두는 것이 안전합니다.

 

핵심 개념: G1과 ZGC는 무엇이 다른가

G1(Garbage-First) GC는 힙을 고정 크기의 여러 Region으로 나누고, 각 Region을 Young/Old/Humongous(거대 객체용)로 유동적으로 배정합니다. GC가 필요할 때는 가비지가 가장 많은 Region부터 우선 회수하며, 개발자가 지정한 MaxGCPauseMillis 목표치에 맞춰 회수량을 조절합니다. 다만 이 목표치는 "노력 목표"에 가까워서, 힙이 크고 살아있는 객체가 많아지면 목표를 넘는 정지가 발생할 수 있습니다.

ZGC는 애플리케이션 스레드와 대부분의 GC 작업(마킹, 압축, 재배치)을 동시(Concurrent)에 수행하도록 설계됐습니다. 컬러 포인터와 로드 배리어 기법으로 객체 이동 중에도 안전하게 참조할 수 있게 만든 것이 핵심이며, 그 결과 일시정지 시간이 힙 크기에 거의 비례하지 않도록 설계되어 있습니다. 다만 정확한 수치는 워크로드·하드웨어에 따라 달라지므로 특정 ms 값을 절대적인 보장치로 받아들이기보다는 "설계상 목표"로 이해하는 편이 맞습니다.

 

 

언제 무엇을 선택할까
항목 G1 GC ZGC (Generational)
설계 목표 처리량과 지연시간의 균형 저지연 우선, 짧고 예측 가능한 정지
일시정지 시간 MaxGCPauseMillis로 설정(노력 목표) 힙 크기에 덜 민감하게 짧은 정지 목표
리소스 오버헤드 상대적으로 낮음 동시 실행 작업만큼 CPU·메모리 여유 필요
적합한 상황 범용 웹 서비스, 배치+온라인 혼합 엄격한 응답 지연 SLA, 대형 힙 운용

 

일반적인 CRUD 백엔드나 배치가 섞인 서비스라면 G1로 충분한 경우가 많습니다. 반면 P99 레이턴시 자체가 SLA인 서비스거나 힙을 수십 GB 이상 크게 잡는데 GC 정지가 그 크기에 비례해 길어지는 게 부담스럽다면 ZGC를 검토할 이유가 충분합니다.

 

예제: G1과 ZGC JVM 옵션 비교

아래는 두 GC를 각각 켜고 GC 로그를 남기는 기본 옵션 예시입니다. 실제 값은 서비스의 힙 크기와 지연 목표에 맞춰 조정해야 합니다.

# G1 GC — 범용 튜닝 예시
java \
  -XX:+UseG1GC \
  -Xms4g -Xmx4g \
  -XX:MaxGCPauseMillis=200 \
  -XX:G1HeapRegionSize=8m \
  -Xlog:gc*:file=gc-g1.log:time,uptime,level,tags \
  -jar app.jar

# ZGC(Generational) — 저지연 튜닝 예시
java \
  -XX:+UseZGC \
  -XX:+ZGenerational \
  -Xms8g -Xmx8g \
  -XX:SoftMaxHeapSize=6g \
  -Xlog:gc*:file=gc-zgc.log:time,uptime,level,tags \
  -jar app.jar

-XX:+ZGenerational 플래그는 이후 릴리스에서 기본값으로 흡수되는 방향으로 발전 중이라 JDK 버전마다 필요 여부가 다를 수 있으니, 배포 전 공식 문서로 유효성을 확인해야 합니다. SoftMaxHeapSize는 ZGC에게 "가능하면 이 크기 이하로 유지하라"는 힌트를 주는 옵션으로, Xmx보다 낮게 잡아 여유분을 남겨두는 용도입니다.

 

실무 도입 시 이것만은 챙기세요
1. GC 로그 없이 튜닝하지 않는다 — -Xlog:gc*를 항상 켜 두고 일시정지 빈도·길이·Full GC 여부를 먼저 관찰
2. 컨테이너 CPU 제한을 함께 고려한다 — cgroup 제한과 인식된 코어 수가 어긋나면 GC가 예상보다 느려질 수 있음(ActiveProcessorCount로 명시 가능)
3. ZGC는 동시 실행만큼 리소스 여유가 필요하다 — 리소스가 빠듯하면 오히려 처리량이 G1보다 떨어질 수 있으니 부하 테스트로 실측
4. 워밍업 이후 기준으로 판단한다 — JIT 컴파일이 안정화되기 전 초기 구간의 GC 지표는 정상 운영 상태를 대표하지 않음

 

마무리 — 3줄 요약

① G1은 처리량과 지연시간의 균형을 노리는 범용 기본 GC이고, ZGC는 짧고 예측 가능한 일시정지를 목표로 설계된 저지연 특화 GC입니다.
② 응답 지연 SLA가 엄격하거나 대형 힙을 운용해야 하는 서비스라면 Generational ZGC 도입을 검토할 가치가 있습니다.
③ 어떤 GC든 로그 기반 관찰, 컨테이너 CPU 제한 고려, 워밍업 이후 지표 비교라는 기본 원칙 없이는 제대로 튜닝하기 어렵습니다.
