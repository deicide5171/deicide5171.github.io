"매일 아침 자동으로 상태 체크해서, 문제 있을 때만 알려주세요" — 상시 에이전트의 알림 경계 설계

AI

한 줄 요약 — Claude Code 스케줄드 태스크(옛 루틴)는 기본 알림이 없습니다. "문제 있을 때만 알려주세요"는 채널 선택이 아니라, 침묵(기본값)과 발화(예외) 사이의 경계선을 코드로 명시해야 하는 설계 문제입니다.

 

왜 지금 이 판단이 필요한가

"이거 매일 아침 자동으로 돌려놓고, 문제 있을 때만 알려주세요." 상시 에이전트를 붙여본 팀이라면 한 번쯤 듣는 요구입니다. 얼핏 "알림 보내기" 한 줄을 추가하는 문제처럼 보이지만, 실제로 맞닥뜨리는 건 "문제"가 무엇인지, "알려주세요"가 어느 채널로 언제 닿아야 하는지를 시스템이 스스로 판단하게 만드는 일입니다. Anthropic은 2026년 4월 14일 Claude Code에 예약 실행 기능인 루틴(Routines)을 공개했고, 이후 스케줄드 태스크(Scheduled Tasks)로 이름을 바꿔 크론·API·GitHub 이벤트로 트리거되는 완전 자율 클라우드 세션을 제공합니다. 그런데 이 기능엔 기본 제공 푸시·이메일 알림이 없습니다 — 알림을 받으려면 Slack·Gmail 커넥터나 Channels를 직접 연동해 "알려야 할 때 알리는" 로직을 설계해 넣어야 합니다.

이 공백은 의도된 설계에 가깝습니다. 2026년 업계 논의에서는 상시 에이전트의 알림을 "유한한 예산"으로 보는 관점이 자리 잡고 있습니다 — 사람이 하루에 받아들일 수 있는 인터럽트 총량은 정해져 있고, 에이전트가 발견한 모든 이상 신호를 경쟁시켜 예산을 쓸 가치가 있는 것만 통과시켜야 한다는 것입니다. "bounded autonomy" 패턴도 비슷하게, 에이전트가 정해진 범위 안에서는 조용히 행동하고 그 범위를 벗어나는 예외에서만 에스컬레이션하라고 제안합니다.

 

전체 시스템에서의 위치

상시 에이전트 파이프라인에서 알림은 맨 끝에 붙는 부가 기능이 아니라, 트리거와 실행 사이에 끼어드는 독립된 판단 게이트입니다. 스케줄 트리거가 세션을 깨우면, 세션은 작업을 수행한 뒤 반드시 "이 결과가 알림 예산을 쓸 가치가 있는가"를 판정하는 게이트를 거칩니다. 게이트를 통과하지 못하면 결과는 로그에만 남고, 통과하면 비로소 Push·Email·Channels 같은 실제 전달 경로를 탑니다. 여기서 중요한 건 "침묵"도 데이터라는 점입니다 — 아무 신호 없이 넘어가는 것과 "확인했는데 이상 없음"을 적극적으로 기록하는 것은 다릅니다. 이 구분이 없으면 알림이 안 왔을 때 그것이 정상인지 장애인지 알 방법이 없어집니다.

Push는 가장 빠르고 확실하지만 예산 소진도 가장 빠릅니다. 모든 사소한 변화마다 Push를 쓰면 2주 안에 사람이 알림을 끄거나 무시하게 되고, 그 순간부터 자동화는 존재하지 않는 것과 같아집니다. 실무에서는 Push를 정말 예외적인 조건 하나에만 걸고, 나머지는 이메일이나 주간 다이제스트로 묶어 내려보내는 계층화가 필요합니다.

 

실제 프로젝트 진행 순서

알림 채널 선정보다 먼저 손대야 할 건 "무엇이 일어나면 사람이 와야 하는가"를 문장으로 적어보는 일입니다. 이 문장이 모호하면 임계값을 과도하게 민감하게 잡아 알림 피로를 만들거나, 반대로 너무 둔감하게 잡아 중요한 실패를 놓치게 됩니다. 아래는 이 판정을 게이트 함수 하나로 분리해 두는 최소 구조입니다.

def should_notify(result, history):
    # 1. 작업 자체가 실패했는가
    if result.status == "failed":
        return True, "critical"
    # 2. 관찰 대상이 실제로 변했는가
    if not result.changed:
        history.record_noop()
        return False, None
    # 3. 임계값 안인가
    if result.severity < history.notification_threshold:
        return False, None
    return True, "normal"

여기서 흔히 막히는 지점은 두 가지입니다. 하나는 실패 자체를 알리는 경로를 깜빡하는 것 — 정상 결과만 알림 대상으로 설계하면 "오늘 이 작업이 아예 돌지 않았다"는 가장 치명적인 신호가 조용히 사라집니다. 다른 하나는 알림 본문의 내용입니다. "문제가 있습니다"만 보내면 사람은 세션을 다시 열어 전체 로그를 뒤져야 하고, 그 순간 알림의 가치가 반으로 줄어듭니다. 알림은 "무엇이 일어났는지"와 "다음에 뭘 해야 하는지"를 한 번에 담아야 합니다.

 

주의 — 임계값을 바로 실서비스에 걸지 말고, 먼저 일주일 정도 모든 판정 결과를 로그로만 쌓아 "이 임계값이었다면 몇 번 울렸을까"를 역산해 보는 게 안전합니다. 실제 알림을 내보내기 전에 노이즈 예산을 소진하는 실수를 미리 걸러낼 수 있습니다.
