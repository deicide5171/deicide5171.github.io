"캐시 서버 라이선스 문제라던데, 그냥 최신 버전으로 올리면 안 되나요?" — Redis EOL 이후 Valkey 마이그레이션 판단 기준

Dev Strategy

한 줄 요약 — Redis Software 7.2가 2026년 2월 EOL을 맞으면서 "버전 업그레이드"가 아니라 라이선스·거버넌스가 다른 Redis 8과 Valkey 중 하나를 고르는 아키텍처 결정이 됐습니다. 모듈 의존성 인벤토리부터 시작하는 실제 진행 순서를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"캐시 서버 라이선스 문제가 있다고 들었는데, 그냥 최신 버전으로 올리면 되는 거 아닌가요?" 플랫폼팀에 이런 질문이 들어오면 대부분 마이너 업그레이드 티켓 하나로 끝낼 일이라고 생각합니다. 하지만 실제로는 "버전을 올릴 것인가"가 아니라 "어떤 라이선스·거버넌스 아래 있는 캐시 레이어를 계속 쓸 것인가"를 다시 정하는 문제입니다. Redis Inc.는 2024년 3월 Redis 7.4부터 라이선스를 RSALv2·SSPLv1 이중 라이선스로 바꿨고, 이후 Redis 8.0에서 AGPLv3를 세 번째 선택지로 추가했습니다. 그런데 구버전 라인업인 Redis Software 7.2가 2026년 2월 28일부로 공식 EOL을 맞아 보안 패치와 지원이 끊겼습니다. 즉 7.2를 그대로 쓰는 팀은 지금 이 순간 패치되지 않는 캐시 서버를 운영 중이라는 뜻입니다.

실제로 갈리는 선택지는 셋입니다. Redis 8 계열로 올려 AGPLv3 트랙을 타거나, Redis Cloud·Redis Software 상용 라이선스로 전환하거나, Linux Foundation 산하 멀티 벤더 거버넌스로 포크된 BSD 라이선스의 Valkey로 옮기는 것입니다. 세 선택지는 "같은 제품의 버전 차이"가 아니라 거버넌스 주체와 라이선스 조건이 완전히 다른 별개의 제품이므로, 캐시 레이어 하나를 고르는 일이 곧 앞으로 몇 년간의 라이선스 리스크를 고르는 결정이 됩니다.

 

전체 시스템에서의 위치

캐시 레이어는 보통 단순 키-값 캐시, 세션·락 같은 상태 저장소, 그리고 모듈을 얹은 보조 인덱스(검색·시계열·JSON) 세 역할을 겸합니다. 이 중 어디까지 맡고 있는지에 따라 마이그레이션 난이도가 전혀 달라집니다. 단순 캐시로만 쓰면 와이어 프로토콜 호환성만 확인하면 되지만, RedisSearch로 벡터 검색을 하거나 RedisTimeSeries로 메트릭을 쌓고 있다면 그 모듈이 이전 대상에도 존재하는지부터 확인해야 합니다. 관리형 서비스를 쓰는 팀이라면 한 단계가 더 있습니다 — AWS는 ElastiCache·MemoryDB 둘 다 Valkey를 지원하지만, Azure Cache for Redis는 이 글을 쓰는 시점까지 Valkey를 지원하지 않습니다.

 

선택의 트레이드오프
기준Redis 8Valkey
라이선스AGPLv3 또는 RSALv2/SSPLv1/상용BSD 3-Clause (OSI 승인)
거버넌스Redis Inc. 단일 벤더Linux Foundation 멀티 벤더
모듈 생태계RedisSearch·JSON·TimeSeries 네이티브9부터 일부 모듈 추가, 격차 일부 남음
관리형 서비스Redis Cloud 등AWS 지원, Azure 미지원

 

모듈 생태계 줄을 가장 보수적으로 읽어야 합니다. "Valkey 9가 벡터 검색을 추가했다"는 소식만 보고 전환을 결정하면, 실제로 쓰는 RedisSearch 쿼리 문법 일부가 아직 구현되지 않아 마이그레이션 중간에 막히는 경우가 나옵니다. AGPLv3 조항도 가볍게 볼 게 아닙니다 — 이 캐시 레이어를 포함한 서비스를 외부 SaaS로 제공한다면 네트워크 서비스 제공 자체를 소스 공개 트리거로 보는 해석이 있어 법무 검토가 선행돼야 합니다.

 

실제 프로젝트 진행 순서

첫 번째로 손대야 할 것은 버전 비교표가 아니라 모듈 의존성 인벤토리입니다. 운영 중인 인스턴스에서 로드된 모듈을 먼저 확인하고, 코드베이스에서 모듈 전용 명령 사용처를 전수 검색합니다.

# 현재 인스턴스에 로드된 모듈 확인
redis-cli MODULE LIST

# 코드베이스에서 모듈 전용 명령 사용처 전수 검색
grep -rEn "FT\.(SEARCH|CREATE)|JSON\.(SET|GET)|TS\.(ADD|RANGE)" src/

이 인벤토리가 비어 있다면 Valkey 전환은 엔드포인트만 바꾸는 수준으로 끝날 가능성이 높습니다. 반대로 모듈 전용 명령이 다수 나온다면, 그 모듈이 Valkey 쪽에서 어느 수준까지 구현됐는지 기능 단위로 대조하는 작업이 전체 일정의 핵심이 됩니다. 실제 전환 사례들을 보면 "주말 하나면 끝날 것"이라 예상했다가 클라이언트 라이브러리 버전 감사, 부하 테스트, 롤백 사고까지 겪으며 3주가 걸린 경우가 보고됩니다. 이 간극은 대부분 모듈 의존성을 사전에 전수 조사하지 않고 "와이어 호환이니 괜찮겠지"라고 낙관했기 때문에 생깁니다.

 

주의 — 진행 순서는 ① 모듈 의존성 인벤토리 → ② 스테이징에서 그림자 테스트 → ③ 클라이언트·관리형 서비스 호환성 확인 → ④ 롤백 플랜 포함 단계적 트래픽 전환이어야 합니다. ①을 건너뛰고 바로 테스트부터 시작하면, 테스트 단계에서야 모듈 격차를 발견해 일정이 뒤로 밀립니다.
