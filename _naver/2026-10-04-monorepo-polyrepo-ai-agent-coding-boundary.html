AI 에이전트가 레포 하나만 본다면 — 모노레포·폴리레포 경계를 다시 긋는 기준

dev-strategy

한 줄 요약 — "프론트는 프론트대로, 백엔드는 백엔드대로 레포를 나눠주세요"는 사람 팀 조직 기준으로는 합리적이지만, AI 코딩 에이전트에게는 교차 서비스 리팩터링을 통째로 못 보게 만드는 경계입니다. AI 에이전트 생산성이 모노레포 쪽으로 저울을 기울이는 2026년, 전면 이관 없이도 경계 문제를 완화하는 합성 모노레포 접근까지 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"프론트엔드, 백엔드, 인프라 설정까지 팀별로 레포를 나눠서 독립적으로 배포할 수 있게 해주세요." 몇 년 전까지는 이 요구가 거의 자동으로 폴리레포 구조로 이어졌습니다. 팀 경계와 레포 경계를 일치시키면 소유권이 명확해지고 배포도 독립적이기 때문입니다. 그런데 AI 코딩 에이전트가 PR 단위로 코드를 짜기 시작하면서, 같은 요구가 전혀 다른 결과를 낳습니다. 폴리레포에서 에이전트는 한 번에 레포 하나만 봅니다. UI 컴포넌트 라이브러리를 바꾸면 어떤 애플리케이션이 그걸 쓰는지, 백엔드 API 응답 형식을 바꾸면 프론트엔드 어디가 깨지는지 — 에이전트는 이걸 알 방법이 없습니다. 사람에게 가장 시간이 많이 드는 작업인 교차 서비스 리팩터링이, 정확히 폴리레포에서 AI 에이전트가 가장 못하는 작업이 됐습니다.

2026년 들어 "AI가 2026년을 모노레포의 해로 만들 것"이라는 논의가 업계에서 반복적으로 등장하는 이유가 여기에 있습니다. 다만 이 논의를 "그럼 전부 모노레포로 합치면 된다"로 단순화하면, 수백 개 서비스를 운영하는 조직에 비현실적인 대규모 이관 프로젝트를 떠안기는 셈이 됩니다. 실제로 판단해야 하는 것은 이분법이 아니라 "코드 경계와 에이전트의 가시성 경계를 어디서 맞출 것인가"입니다.

 

요구사항을 기술 문제로 번역하기

"레포 구조를 정해주세요"라는 말은 세 가지 질문을 품고 있습니다. 첫째, 에이전트가 자주 수행해야 하는 변경이 한 서비스 안에서 끝나는가, 여러 서비스에 걸치는가. 둘째, 팀 간 소유권과 배포 독립성을 코드 분리가 아닌 다른 방식으로도 지킬 수 있는가. 셋째, 지금 폴리레포 전체를 모노레포로 이관하는 비용이, 교차 서비스 리팩터링을 에이전트 없이 사람이 계속 처리하는 비용보다 정말로 큰가.

이 질문의 답은 조직마다 다릅니다. 마이크로서비스 수십 개가 독립적으로 진화하고 교차 변경이 드문 조직이라면 폴리레포의 비용은 생각보다 작습니다. 반대로 공유 타입 정의, 공통 컴포넌트, API 계약이 자주 동시에 바뀌는 조직이라면 폴리레포의 "에이전트가 못 본다"는 비용이 빠르게 누적됩니다.

 

전체 시스템에서의 위치

 

폴리레포 구조에서 에이전트의 작업 범위는 그 순간 체크아웃된 레포 하나로 물리적으로 제한됩니다. 프론트엔드 레포 안의 에이전트는 백엔드 레포의 API 핸들러 코드를 볼 수 없으므로, 백엔드가 응답 필드를 바꿔도 프론트엔드 쪽 영향을 추론하지 못합니다. 반대로 모노레포에서는 에이전트의 컨텍스트 창 안에 여러 서비스의 코드가 동시에 들어올 수 있어, 의존 관계를 추적하고 20개 프로젝트에 걸친 변경을 PR 하나로 묶어낼 수 있습니다. 다만 이 장점은 공짜가 아닙니다. 레포가 커질수록 검색·인덱싱 전략이 따로 필요해지고, 빌드 캐싱과 CI 파이프라인 분리도 다시 설계해야 합니다. 최근에는 기존 폴리레포를 물리적으로 합치지 않고, 가상 레이어로 여러 레포를 하나의 작업 공간처럼 보이게 하는 합성 모노레포 접근도 등장했습니다. 전면 이관의 리스크 없이 에이전트에게만 넓은 가시성을 제공하려는 절충안입니다.

 

선택의 트레이드오프
기준 폴리레포 유지 전면 모노레포 이관 합성 모노레포
교차 변경 시 에이전트 정확도 낮음 높음 중간~높음
이관 비용·리스크 없음 높음 낮음
팀별 배포 독립성 자연스럽게 보장 별도 설계 필요 기존 방식 유지
가장 흔한 함정 계약 변경을 양쪽이 모름 불필요한 레포까지 한꺼번에 이관 쓰기 권한·충돌 해석 설계 소홀

 

모노레포 전환이 만능 해법이라는 결론으로 가면 안 됩니다. 교차 서비스 변경이 애초에 드문 조직에서는 폴리레포의 명확한 소유권이 여전히 더 큰 가치를 줍니다. 반대로 공유 타입·API 계약이 수시로 같이 바뀌는 조직에서 폴리레포를 고집하면, 그 비용을 사람 리뷰어가 계속 떠안게 됩니다.

 

실제 프로젝트 진행 순서

1단계: 최근 3~6개월의 PR을 교차 서비스 변경 비율로 분석합니다. 이 숫자가 낮다면 레포 구조를 바꿀 근거 자체가 약합니다.

2단계: 전면 이관이 아니라 가장 자주 함께 바뀌는 레포 쌍부터 식별합니다.

3단계: 합성 모노레포로 먼저 가시성 문제만 분리해서 검증합니다. 물리적 이관 전에 교차 변경 정확도가 얼마나 개선되는지 측정합니다.

4단계: 배포 독립성을 레포 분리가 아닌 빌드 그래프 기반 선택적 배포로 재설계합니다.

5단계: 구조 변경 후에도 에이전트 PR의 정확도를 지속적으로 추적해, 실제로 개선됐는지 데이터로 확인합니다.

주의 — 모노레포 전환을 에이전트 성능 개선의 만능 해법으로 포장하지 마세요. 레포를 합쳐도 검색·인덱싱 전략이 뒷받침되지 않으면 에이전트가 오히려 무관한 코드에 묻혀 더 느려질 수 있습니다. 팀 소유권 경계는 CODEOWNERS·접근 제어로 레포 경계와 별개로 보존하세요.

 

정리

폴리레포에서 AI 코딩 에이전트는 한 번에 레포 하나만 보기 때문에, 사람에게 가장 비용이 큰 교차 서비스 리팩터링을 정확히 못하는 구조적 한계를 갖습니다. 그렇다고 전면 모노레포 이관이 기본 정답은 아닙니다 — 교차 서비스 변경 비율을 먼저 데이터로 측정하고, 가장 자주 함께 바뀌는 레포 쌍부터 합성 모노레포 같은 저비용 가시성 확보 방법으로 검증하는 것이 순서입니다.
