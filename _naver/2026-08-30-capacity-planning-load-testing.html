블랙프라이데이는 예측이 아니라 검증이다 — 용량 계획과 부하 테스트 방법론

시스템 설계

한 줄 요약 — 용량 계획은 트래픽 배수 예측으로 끝나지 않습니다. 트래픽 모델링 → 병목 식별 → 부하 테스트 검증의 3단계로 나누어, 각 단계에서 흔히 놓치는 지점을 정리했습니다.

 

"5배 트래픽이니 서버도 5배로"는 십중팔구 틀립니다

평소 대비 5배 트래픽이 예상되니 서버를 5배로 늘리자는 계획은 십중팔구 틀립니다. 트래픽이 5배가 돼도 DB 커넥션 풀, 캐시 히트율, 다운스트림 서비스의 처리 한계 같은 병목은 선형으로 늘어나지 않기 때문입니다. 애플리케이션 서버는 넉넉히 늘렸는데 정작 병목이던 DB 커넥션 풀은 그대로 둬서 장애가 나는 사례가 반복되는 이유가 여기에 있습니다.

용량 계획(capacity planning)은 시스템의 각 구성 요소가 실제로 어디서 먼저 무너지는지를 찾고 그 가정을 실제 부하로 검증하는 과정입니다.

 

핵심 개념 1 — 트래픽 모델링: 평균이 아니라 형태를 예측합니다

용량 계획의 첫 단계는 얼마나 많은 트래픽이 올 것인가를 숫자 하나로 답하는 게 아니라 트래픽의 형태를 예측하는 것입니다. 평시 대비 배수만 보면 놓치는 것이 세 가지입니다. 첫째, 피크가 지속되는 시간 — 순간 스파이크 5분과 지속 부하 3시간은 완전히 다른 문제입니다. 둘째, 요청 구성 변화 — 세일 시작 시점에는 조회가 늘고 그 뒤엔 결제가 늘어나는 식으로 워크로드 프로파일이 시간에 따라 바뀝니다. 셋째, 캐시 히트율 변화 — 프로모션으로 다양한 상품이 동시에 조회되면 캐시 미스가 급증해 DB 부하가 트래픽 증가율보다 더 가파르게 늘 수 있습니다.

 

핵심 개념 2 — 병목 식별: 시스템은 가장 약한 고리 속도로 달립니다
병목 후보 흔한 징후 확인 방법
DB 커넥션 풀 앱은 idle인데 요청이 큐잉됨 풀 사용률·대기 큐 길이
다운스트림 API 레이트리밋 특정 API 호출부터 지연 급증 서드파티 호출 응답시간 분리 측정
오토스케일링 반응 지연 스케일 아웃 전까지 초반 장애 신규 인스턴스 부팅+워밍업 시간

이 표에서 중요한 점은 병목이 대개 가장 눈에 잘 띄는 지표가 아니라는 것입니다. CPU 사용률이 여유로워도 커넥션 풀이 고갈되면 시스템 전체가 느려지는데, 이때 흔한 실수가 CPU가 여유롭다는 이유로 애플리케이션 서버부터 늘리는 것입니다.

 

핵심 개념 3 — 부하 테스트: 추정을 검증으로 바꿉니다

부하 테스트는 예상 피크 트래픽을 재현해 시스템이 견디는지 확인하고, 스트레스 테스트는 무너지는 지점까지 트래픽을 계속 올려 한계를 관찰하며, 스파이크 테스트는 트래픽 급증·급감을 재현해 오토스케일링 반응 속도를 검증하고, 소크 테스트는 중간 부하를 오래 유지해 메모리·커넥션 누수처럼 시간이 지나야 드러나는 문제를 잡습니다.

 

 

예제 — k6로 단계적 부하 테스트 시나리오
export const options = {
  stages: [
    { duration: '2m', target: 100 },   // 평시 수준으로 워밍업
    { duration: '5m', target: 500 },   // 예상 피크까지 점진 증가
    { duration: '10m', target: 500 },  // 피크 유지
    { duration: '3m', target: 1500 },  // 예상치의 3배 — 병목 한계 탐색
    { duration: '5m', target: 0 },     // 회복 속도 관찰
  ],
  thresholds: {
    http_req_duration: ['p(95)<800'],
    db_connection_errors: ['rate<0.01'],
  },
};

이 스크립트는 예상 피크를 검증하는 데서 그치지 않고 그 3배까지 밀어붙여 어디서 먼저 무너지는지 관찰하며, 회복 단계를 넣어 트래픽이 빠져도 즉시 회복되지 않는 시스템을 잡아냅니다.

 

실무 포인트

부하 테스트는 프로덕션과 최대한 동일한 환경에서 해야 의미가 있습니다. 스테이징 환경의 DB 사양이나 커넥션 풀 크기가 다르면 병목 지점 자체가 다르게 나타납니다.

서드파티 의존성은 격리해서 테스트하세요. 결제 게이트웨이 같은 외부 서비스를 실제로 호출하면 레이트리밋에 걸리거나 상대 서비스에 피해를 줄 수 있습니다.

주의 — 용량 계획 문서는 한 번 쓰고 끝내는 게 아니라 이벤트마다 갱신해야 합니다. 지난 세일 때의 병목 지점이 이번에도 그대로일 거라는 보장이 없습니다 — 코드·인프라·트래픽 패턴 변화가 있었을 수 있으므로 매번 최신 상태로 재검증해야 합니다.
