Web Components와 프레임워크 상호운용성 — React·Vue에서 커스텀 엘리먼트 제대로 쓰기

2026. 8. 19. · 프론트엔드

한 줄 요약 — 디자인 시스템을 프레임워크 경계 없이 재사용하려는 수요가 커지는 지금, Web Components(커스텀 엘리먼트)를 React·Vue에서 안전하게 소비하는 방법과 흔한 상호운용 함정을 정리했습니다.

 

왜 지금 Web Components 상호운용성일까요

한 회사 안에서도 제품마다 React, Vue, 혹은 레거시 jQuery 화면이 섞여 있는 경우가 드물지 않습니다. 디자인 시스템 팀 입장에서는 버튼 하나, 날짜 선택기 하나를 프레임워크별로 각각 구현·유지보수하는 비용이 상당합니다. Web Components(Custom Elements + Shadow DOM + HTML Templates)는 브라우저 표준이기 때문에 이 문제의 자연스러운 답으로 다시 주목받고 있습니다. 실제로 Adobe의 Spectrum, SAP의 UI5, Shoelace(현 Web Awesome) 같은 다수의 상용 디자인 시스템이 내부적으로 커스텀 엘리먼트를 표준 배포 형태로 채택했습니다.

다만 "프레임워크 독립적"이 "아무 마찰 없이 붙는다"는 뜻은 아닙니다. React는 오랫동안 커스텀 엘리먼트에 값을 넘길 때 모든 prop을 문자열 HTML 속성으로 취급해 객체·배열 prop과 궁합이 좋지 않았습니다. React 19에서는 커스텀 엘리먼트 인스턴스에 해당 프로퍼티가 실제로 존재하면 속성이 아닌 프로퍼티로 대입하도록 개선됐습니다. Vue는 defineCustomElement API로 SFC를 네이티브 커스텀 엘리먼트로 컴파일해 배포할 수 있어 상호운용에 더 유리한 편입니다.

 

핵심 개념 1 — 속성(Attribute)과 프로퍼티(Property)는 다릅니다

Web Components를 프레임워크에서 다룰 때 가장 먼저 부딪히는 개념입니다. HTML 속성은 항상 문자열이고 마크업에 그대로 보입니다. 프로퍼티는 JS 객체 인스턴스의 필드로, 문자열이 아닌 어떤 값도 담을 수 있습니다. 커스텀 엘리먼트 저자는 보통 원시값(문자열·불리언·숫자)은 속성으로 반영하고, 배열·객체·함수 같은 복합 데이터는 프로퍼티로만 받도록 설계합니다.

데이터 종류 전달 방식 흔한 실수
문자열·숫자·불리언 속성(attribute) 문제 대부분 없음
배열·객체 프로퍼티(property) 문자열로 직렬화해 넘기는 실수
콜백 함수 프로퍼티(property) JSX 속성으로 넘기면 무시됨
상태 변화 알림 CustomEvent dispatch onChange prop을 기대하다 못 받음

 

핵심 개념 2 — 프레임워크별 처리 방식 비교
항목 React Vue
원시값 prop 속성으로 전달, 대부분 정상 속성으로 전달, 정상 동작
객체·배열 prop ref로 직접 프로퍼티 대입 권장 컴파일러가 프로퍼티로 자동 바인딩
커스텀 이벤트 수신 ref + addEventListener 필요한 경우 많음 @event-name으로 바로 수신
Shadow DOM 스타일 ::part() 필요 ::part() 필요
SSR 설정에 따라 지원 여부 다름 설정에 따라 지원 여부 다름

 

React·Vue 모두 결국 "속성 대신 프로퍼티를 명시적으로 대입하고, onXxx 대신 실제 DOM 이벤트 리스너로 커스텀 이벤트를 받는다"는 원칙은 같습니다. 차이는 이 처리를 프레임워크가 자동으로 해주는지, 개발자가 ref로 직접 손을 대야 하는지에 있습니다.

 

예제: React에서 커스텀 엘리먼트에 안전하게 값 전달하기
import { useEffect, useRef } from 'react';

function DatePickerField({ value, onDateChange }) {
  const elRef = useRef(null);

  useEffect(() => {
    const el = elRef.current;
    if (!el) return;

    // 배열·객체 등 non-string 값은 속성이 아니라 프로퍼티로 직접 대입
    el.value = value;

    const handleChange = (e) => onDateChange(e.detail.date);
    el.addEventListener('date-change', handleChange);
    return () => el.removeEventListener('date-change', handleChange);
  }, [value, onDateChange]);

  return <my-date-picker ref={elRef} />;
}

value를 JSX 속성으로 바로 넘기지 않는 이유는, 커스텀 엘리먼트가 value를 객체로 기대할 경우 문자열로 직렬화되어 전달될 위험이 있기 때문입니다. 이벤트도 onDateChange 같은 React 컨벤션 prop이 아니라 실제 CustomEvent(date-change)를 리스닝해야 합니다.

 

예제: Vue에서 SFC를 커스텀 엘리먼트로 배포하고 소비하기
// 1. 커스텀 엘리먼트로 컴파일해 등록 (배포 측)
import { defineCustomElement } from 'vue';
import DatePicker from './DatePicker.ce.vue';

const MyDatePickerElement = defineCustomElement(DatePicker);
customElements.define('my-date-picker', MyDatePickerElement);

<!-- 2. 다른 Vue 앱에서 그대로 소비 (사용 측) -->
<template>
  <my-date-picker :value="date" @date-change="date = $event.detail.date" />
</template>

defineCustomElement로 감싸면 Vue의 반응형 prop이 커스텀 엘리먼트의 프로퍼티로 자동 매핑되고, 내부에서 emit한 이벤트도 표준 CustomEvent로 변환되어 나갑니다. 소비 측은 이 컴포넌트가 Vue로 만들어졌는지 몰라도 익숙한 문법 그대로 사용할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. 프로퍼티가 필요한 값은 JSX/템플릿 속성 문법에 의존하지 않기 — 배열·객체·함수는 ref로 DOM 프로퍼티에 직접 대입
2. Shadow DOM 스타일은 ::part()와 CSS 커스텀 프로퍼티로만 조정 가능 — Tailwind·CSS-in-JS는 Shadow 경계를 넘지 못함
3. 커스텀 이벤트 이름과 detail 스키마를 팀 컨벤션으로 문서화 — 프레임워크마다 수신 방식이 달라 혼란 방지
4. SSR 사용 시 Declarative Shadow DOM 지원 여부를 프레임워크·번들러별로 개별 확인

 

마무리 — 3줄 요약

① Web Components는 프레임워크 독립적 디자인 시스템 배포 수단으로 다시 주목받지만, "속성은 문자열, 프로퍼티는 복합 데이터"라는 원칙을 프레임워크별로 다르게 보정해줘야 합니다.
② React는 ref + 프로퍼티 직접 대입과 addEventListener로 커스텀 엘리먼트를 감싸는 패턴이 여전히 필요하고, Vue는 defineCustomElement로 이 과정을 상당 부분 자동화해 줍니다.
③ Shadow DOM 스타일 경계(::part())와 커스텀 이벤트 스키마를 팀 컨벤션으로 미리 문서화해야 상호운용 마찰을 줄일 수 있습니다.
