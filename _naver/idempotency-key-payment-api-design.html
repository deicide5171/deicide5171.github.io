멱등성(Idempotency) 키 설계 — 결제 API에서 중복 요청을 안전하게 처리하기

아키텍처·시스템 설계

한 줄 요약 — 타임아웃 후 재시도된 결제 요청이 중복 청구로 이어지지 않도록, 멱등성 키의 원자적 선점과 동시성 처리 설계 방법을 정리했습니다.

 

왜 지금 멱등성 키를 다시 봐야 하는가

결제 요청 도중 네트워크가 끊기면 클라이언트는 성공 여부를 알 수 없어 재시도할 수밖에 없습니다. 그런데 원래 요청이 서버에서는 이미 처리됐을 가능성이 있어, 재시도를 그대로 새 결제로 처리하면 중복 청구가 발생합니다. 멱등성 키는 같은 키로 여러 번 요청해도 실제 부작용은 한 번만 일어나게 하는 계약입니다.

 

멱등성 키는 클라이언트가 생성하고, 요청 내용과 함께 저장해야 한다

키는 클라이언트가 생성해 헤더로 보냅니다. 서버는 키를 받으면 저장소에서 조회하고, 처음이면 요청 해시와 함께 처리를 진행합니다. 이미 있는 키라면 요청 본문이 동일한지, 처리가 끝났는지를 확인해야 합니다.

 

동시에 들어온 같은 키 요청 사이의 경쟁 조건

타임아웃 직후 즉시 재시도하면 첫 요청이 처리 중인데 같은 키로 두 번째 요청이 거의 동시에 들어올 수 있습니다. 키를 저장소에 기록하는 시점을 원자적 연산(유니크 제약, Redis SETNX)으로 만들어야 두 번째 요청이 안전하게 대기하거나 충돌 응답을 받습니다.

상태 의미 두 번째 요청 처리
키 없음 최초 요청 정상 처리, 키 선점
처리 중 같은 요청 진행 중 대기 또는 409
완료 + 요청 동일 완료된 재시도 저장된 응답 반환

 

예제 — 원자적 키 선점과 상태 확인
@Transactional
public PaymentResponse processPayment(String idempotencyKey, PaymentRequest request) {
    String requestHash = hash(request);
    IdempotencyRecord record;
    try {
        record = idempotencyRepository.insertIfAbsent(idempotencyKey, requestHash, Status.IN_PROGRESS);
    } catch (DuplicateKeyException e) {
        record = idempotencyRepository.findByKey(idempotencyKey);
        if (!record.getRequestHash().equals(requestHash)) {
            throw new IdempotencyKeyReusedException(idempotencyKey);
        }
        if (record.getStatus() == Status.IN_PROGRESS) {
            throw new PaymentInProgressException(idempotencyKey);
        }
        return record.getStoredResponse();
    }

    PaymentResponse response = executeActualPayment(request);
    idempotencyRepository.markCompleted(idempotencyKey, response);
    return response;
}

insertIfAbsent가 유니크 제약 위반을 던지는 방식이면, 동시 요청 중 하나만 실제 처리 권한을 갖고 나머지는 안전하게 대기하거나 저장된 결과를 받습니다.

 

실무 포인트

멱등성 키의 유효 기간을 명시적으로 정하세요. 무기한 보관하면 저장소가 계속 커지므로 24시간~수일 정도로 만료 정책을 두어야 합니다.

요청 본문 해시 비교를 빠뜨리지 마세요. 본문이 다른데도 저장된 응답을 돌려주면 클라이언트의 키 재사용 버그를 조용히 감추게 됩니다.

주의 — "처리 중" 상태에서의 클라이언트 동작까지 API 계약에 명시하세요. Retry-After나 상태 조회 엔드포인트를 함께 제공하면 클라이언트 구현이 훨씬 안전해집니다.
