Zero Trust 네트워크 아키텍처 심화 — mTLS와 SPIFFE/SPIRE로 서비스 신원 증명하기

네트워크·OS·분산처리·DevOps

한 줄 요약 — 네트워크 위치가 아니라 신원(identity)을 기준으로 검증하는 Zero Trust 원칙을, SPIFFE/SPIRE로 mTLS를 자동화하는 방식으로 구현하는 법을 정리했습니다.

 

왜 지금 Zero Trust를 다시 봐야 하는가

전통적 보안 모델은 "사내망 안에 있으면 신뢰할 수 있다"는 경계 기반 사고에 기댔습니다. 마이크로서비스·컨테이너 환경에서는 파드가 수시로 뜨고 사라지고 IP가 재사용돼 이 경계가 무의미해집니다. Zero Trust는 신원을 기준으로 매 요청을 검증하는 원칙이며, 핵심 메커니즘이 mTLS와 SPIFFE/SPIRE입니다.

 

SPIFFE: 워크로드에게 검증 가능한 신원을 부여하는 표준

SPIFFE는 워크로드마다 SPIFFE ID라는 고유 URI 신원을 부여하는 표준입니다. IP나 호스트명과 달리 배포 환경에 따라 바뀌지 않는 논리적 정체성이며, X.509 인증서(SVID) 형태로 발급돼 암호학적으로 신원을 증명할 수 있습니다.

 

SPIRE가 인증서 발급·회전을 자동화하는 방식

SPIRE Agent는 커널 정보(프로세스 UID, cgroup, 서비스 어카운트 등)로 워크로드 신원을 증명(attestation)합니다. 통과하면 SPIRE Server가 짧은 수명의 SVID를 발급하고 만료 전 자동 갱신합니다. 사람이 수동으로 인증서를 관리하던 과정을 완전히 자동화합니다.

항목 전통적 인증서 관리 SPIFFE/SPIRE
신원 발급 사람이 수동 신청 커널 증거 기반 자동 증명
인증서 수명 수개월~1년 수 시간~수 일, 자동 회전
회전 실패 위험 담당자가 놓치면 장애 에이전트가 자동 갱신

 

예제 — Envoy에서 SPIFFE mTLS 검증 설정
transport_socket:
  name: envoy.transport_sockets.tls
  typed_config:
    common_tls_context:
      tls_certificate_sds_secret_configs:
        - name: spiffe://example.org/ns/payments/sa/order-service
      validation_context:
        custom_validator_config:
          name: envoy.tls.cert_validator.spiffe
          typed_config:
            trust_domains:
              - name: example.org
                trust_bundle: { filename: "/run/spire/bundle/bundle.pem" }

Envoy는 SVID를 인증서로 사용하고, 상대방 SVID가 신뢰 도메인 번들로 검증 가능한지 확인해 mTLS 핸드셰이크를 완료합니다.

 

실무 포인트

처음부터 모든 서비스에 강제 적용하지 마세요. 신뢰 도메인 설계와 attestation 정책을 소수 서비스로 먼저 검증한 뒤 확대하는 것이 안전합니다.

서비스 메시가 이미 SPIFFE 기반 mTLS를 지원하는 경우가 많습니다. Istio, Linkerd가 이 기능을 제공하는지 먼저 확인하면 구현 비용이 크게 줄어듭니다.

주의 — 레거시 워크로드(VM, 베어메탈)를 포함해야 한다면 attestation 방식을 별도로 설계하세요. 쿠버네티스 서비스 어카운트 기반 증명은 파드에만 맞으므로 VM에는 다른 attestation 플러그인이 필요합니다.
