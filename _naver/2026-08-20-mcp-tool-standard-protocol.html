MCP(Model Context Protocol)로 도구 연동 표준화하기 — 에이전트마다 제각각이던 통합 방식 정리

2026. 8. 20. · AI

한 줄 요약 — 에이전트마다 도구 연동 코드를 따로 짜야 했던 N×M 문제를 표준 프로토콜로 풀려는 MCP의 호스트-클라이언트-서버 구조와, Tools·Resources·Prompts 개념을 정리했습니다.

 

왜 지금 MCP일까요

AI 에이전트가 외부 도구를 쓰게 만들려면, 그동안은 에이전트 프레임워크마다 별도의 통합 코드를 새로 짜야 했습니다. 어떤 도구를 A 에이전트에 붙이려면 A 전용 커넥터를, 같은 도구를 B 에이전트에도 쓰려면 B 전용 커넥터를 또 만들어야 하는 식이었습니다. 에이전트가 N개, 도구가 M개라면 필요한 통합 코드는 N×M에 가까워집니다. 도구를 제공하는 쪽은 인기 있는 에이전트마다 연동을 유지보수해야 했고, 에이전트를 만드는 쪽은 새 도구 하나를 붙일 때마다 그 도구의 API를 처음부터 익혀야 했습니다.

MCP(Model Context Protocol)는 이 문제를 표준 프로토콜로 풀어보려는 시도입니다. Anthropic이 오픈소스로 공개한 뒤 여러 벤더가 클라이언트·서버 구현체를 내놓으면서 사실상 업계 표준처럼 자리잡아가고 있습니다. 도구를 제공하는 쪽은 MCP 서버 하나만 구현하면 MCP를 지원하는 모든 애플리케이션에서 그 도구를 쓸 수 있게 되고, 에이전트를 만드는 쪽은 MCP 클라이언트 하나만 구현하면 MCP 서버로 노출된 모든 도구에 접근할 수 있게 됩니다. N×M이 N+M으로 줄어드는 셈입니다.

 

핵심 개념 1 — 호스트, 클라이언트, 서버의 3자 구조

MCP는 세 역할로 구성됩니다. 호스트(Host)는 사용자가 직접 쓰는 AI 애플리케이션입니다. 데스크톱 앱이나 IDE 플러그인, 자체 개발한 에이전트가 여기 해당합니다. 클라이언트(Client)는 호스트 내부에서 하나의 MCP 서버와 1:1로 연결을 유지하는 컴포넌트로, 호스트가 서버 여러 개에 붙으면 클라이언트도 그만큼 여러 개 생겨납니다. 서버(Server)는 파일 시스템, 데이터베이스, 이슈 트래커 API처럼 특정 도구나 데이터 소스를 MCP 규격으로 감싸 노출하는 별도 프로세스입니다.

통신은 JSON-RPC 2.0 메시지로 이루어지며, 전송 방식은 두 가지가 대표적입니다. 로컬 프로세스를 표준입출력으로 붙이는 stdio와, 원격 서버에 HTTP로 접속하는 Streamable HTTP입니다. 로컬 파일 시스템 접근처럼 신뢰 경계 안에 있는 도구는 stdio로, 여러 사용자가 함께 쓰는 원격 서비스는 Streamable HTTP로 노출하는 편이 자연스럽습니다.

 

핵심 개념 2 — Tools, Resources, Prompts는 통제 주체가 다릅니다

서버가 클라이언트에 노출하는 항목은 세 종류로 나뉘는데, 누가 그 사용 여부를 결정하는지가 서로 다르다는 점이 중요합니다. Tools는 모델이 필요하다고 판단할 때 호출하는 함수이고, Resources는 애플리케이션이 컨텍스트에 넣을지 말지 결정하는 데이터이며, Prompts는 사용자가 UI에서 직접 선택하는 정형화된 요청 템플릿입니다.

항목 통제 주체 성격 예시
Tools 모델이 판단 모델이 호출하는 함수(부작용 있음) 이슈 생성, 메일 발송
Resources 애플리케이션이 판단 모델에 제공할 데이터(조회에 가까움) 파일 내용, DB 레코드, 로그
Prompts 사용자가 판단 재사용 가능한 프롬프트 템플릿 슬래시 커맨드로 노출되는 정형 질의

 

Tools는 기존 tool use API의 함수 호출과 비슷하지만, MCP 서버가 스키마째로 정의해 여러 호스트에서 재사용된다는 점이 다릅니다. Prompts는 반복되는 작업 패턴을 서버 쪽에 미리 정의해둘 수 있다는 점에서, 매번 같은 요청을 새로 타이핑하지 않아도 되게 해줍니다.

 

예제 — MCP 서버 정의(TypeScript)

아래는 날씨 정보를 제공하는 최소한의 MCP 서버 예시입니다. 도구(get_weather)와 리소스(recent-alerts)를 각각 하나씩 등록하고, stdio 전송으로 연결을 엽니다.

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "weather-server", version: "1.0.0" });

// Tool: 모델이 필요할 때 호출하는 함수
server.tool(
  "get_weather",
  "주어진 도시의 현재 날씨를 조회한다.",
  { city: z.string().describe("도시 이름, 예: Seoul") },
  async ({ city }) => {
    const data = await fetchWeather(city);
    return { content: [{ type: "text", text: `${city}: ${data.summary}` }] };
  }
);

// Resource: 애플리케이션이 컨텍스트로 읽어들이는 데이터
server.resource("recent-alerts", "weather://alerts/recent", async (uri) => ({
  contents: [{ uri: uri.href, text: await getRecentAlerts() }],
}));

const transport = new StdioServerTransport();
await server.connect(transport);

간단한 예시지만, 이 서버 하나만 배포하면 stdio를 지원하는 어떤 MCP 호스트에서도 get_weather 도구와 recent-alerts 리소스를 그대로 쓸 수 있습니다. 별도의 통합 코드를 호스트마다 다시 짤 필요가 없어지는 부분이 바로 이 지점입니다.

 

실무 도입 시 이것만은 챙기세요
1. 서버는 신뢰 경계 밖의 코드로 다뤄야 합니다 — MCP 서버는 임의의 코드를 실행할 수 있으므로, 검증되지 않은 서드파티 서버를 그대로 연결하는 것은 임의 코드 실행을 허용하는 것과 다르지 않습니다. 출처가 분명한 서버만 연결하고, 파일 시스템 접근 경로나 API 스코프 같은 권한 범위를 최소화하세요.
2. 전송 방식은 신뢰 경계에 맞춰 고릅니다 — 로컬 전용 도구는 stdio, 여러 사용자나 원격 배포가 필요한 도구는 Streamable HTTP(및 OAuth 인증)를 쓰는 편이 자연스럽습니다.
3. 스펙이 계속 바뀌고 있습니다 — MCP는 아직 활발히 개정되는 표준이라 클라이언트·서버 SDK 버전 간 호환성 문제가 생길 수 있습니다. 프로덕션에 붙이기 전에 사용 중인 호스트가 지원하는 프로토콜 버전을 확인하는 편이 안전합니다.
4. 도구 설명이 곧 성능입니다 — 도구 설명(description)이 부실하거나 도구 수가 지나치게 많으면 모델이 적절한 도구를 고르지 못합니다. 서버 쪽에서부터 설명을 충실히 작성하는 것이, 호스트 프롬프트를 아무리 다듬어도 못 채우는 부분을 채워줍니다.

 

마무리 — 3줄 요약

① MCP는 에이전트마다 제각각이던 도구 연동을 표준 프로토콜로 통일해, N×M 통합 문제를 N+M으로 줄이려는 시도입니다.
② 호스트-클라이언트-서버 구조 위에서 Tools(모델이 호출), Resources(앱이 읽음), Prompts(사용자가 선택) 세 가지를 표준 방식으로 주고받습니다.
③ 실무에서는 서버를 신뢰 경계 밖 코드로 다루고, 전송 방식(stdio/Streamable HTTP)을 용도에 맞게 고르며, 스펙 변경에 미리 대비해야 합니다.
