세션이 사라진 MCP — 상태를 어디에 둘 것인가

AI

한 줄 요약 — "우리 내부 API를 MCP로 열어서 여러 에이전트가 동시에 쓰게 해주세요"라는 요구는 2026-07-28 MCP 스펙 개정 이후 완전히 다른 서버 설계를 요구합니다. 세션과 initialize 핸드셰이크가 통째로 사라지고 서버가 순수 HTTP 함수가 된 이번 개정이, 인증·장시간 작업·실시간 알림을 어디에 둘지 다시 판단하게 만드는 이유를 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"사내 주문 시스템 API를 MCP 서버로 열어서, 여러 팀의 에이전트가 동시에 접속해 쓰게 해주세요." 이 요구를 받으면 지금까지는 MCP의 initialize 핸드셰이크로 세션을 하나 발급받고, 그 세션 ID를 키 삼아 인증 컨텍스트·진행 중인 작업 상태·서버가 클라이언트에 먼저 말을 거는 샘플링 요청까지 전부 그 세션에 묶어 설계하는 게 당연했습니다. 클라이언트 하나가 서버 인스턴스 하나에 고정(sticky)되는 구조를 전제로 깔고 갔다는 뜻입니다.

그런데 2026년 7월 28일 공개된 MCP 스펙 개정은 이 전제를 통째로 걷어냈습니다. initialize 핸드셰이크와 Mcp-Session-Id 헤더가 사라졌고, 모든 요청은 완전히 독립적으로 취급됩니다. Roots·Sampling·Logging 기능도 12개월의 유예 기간과 함께 폐기 예정으로 지정됐습니다. 론칭 이후 가장 큰 폭의 개정이라는 평가가 나올 만큼, 세션을 전제로 설계해 둔 MCP 서버들은 이번 개정으로 아키텍처를 다시 그려야 하는 상황에 놓였습니다. 실제로 광고 기술 업계에서는 세션이 사라지면서 에이전트 서버를 다시 구축해야 했던 사례까지 보고됐습니다.

 

요구사항을 기술 문제로 번역하기

"여러 에이전트가 동시에 우리 API를 쓰게 해주세요"라는 한 문장은 세 가지 서로 다른 상태 관리 문제를 품고 있습니다. ①요청자가 누구인지 매 요청마다 증명해야 하는 인증 문제 — 이제는 매 요청이 자체적으로 완결된 자격증명을 들고 와야 합니다. ②몇 분~몇 시간씩 걸리는 장시간 작업의 진행 상태를 어디에 보관할지의 문제 — 세션이라는 그릇이 없어졌으니 다른 곳에 둬야 합니다. ③서버가 클라이언트에게 먼저 알려야 하는 이벤트를 어떤 메커니즘으로 보낼지의 문제 — 스펙은 이를 MRTR(Multi Round-Trip Requests)이라는 반복 요청 패턴으로 대체했습니다.

 

전체 시스템에서의 위치

 

예전 구조에서는 클라이언트 → 로드밸런서 → (세션 ID로 고정된) 특정 서버 인스턴스로 이어지는 경로가 고정돼 있었고, 그 서버 인스턴스의 메모리 안에 인증 컨텍스트와 작업 상태가 같이 살았습니다. 개정 이후 구조에서는 모든 요청이 완전히 독립적이므로 로드밸런서는 평범한 라운드로빈으로 단순화됩니다. 대신 인증은 요청 자체에 포함된 자체완결적 토큰으로 검증하고, 장시간 작업의 상태와 진행률은 Redis나 DB 같은 외부 저장소에 task ID로 보관합니다. 클라이언트는 그 task ID를 들고 MRTR로 반복 질의해 진행 상황을 확인합니다. 상태가 서버 바깥으로 완전히 빠져나간 셈입니다.

 

선택의 트레이드오프
기준 세션 기반(구 스펙) 스테이트리스(신 스펙)
수평 확장성 sticky session 필요 라운드로빈만으로 충분
장애 복구 인스턴스 다운 시 상태 유실 외부 저장소라 영향 없음
구현 복잡도(단기) 프로토콜이 대신 처리 직접 설계 필요
장시간 작업 처리 세션으로 진행률 푸시 task ID + MRTR 폴링

 

표에서 가장 눈여겨봐야 할 줄은 "구현 복잡도"입니다. 스테이트리스 구조는 확장성과 장애 복구에서 명백히 유리하지만, 그 대가로 예전엔 프로토콜이 대신 처리해주던 세션 수명주기 관리를 서버 구현자가 직접 떠안아야 합니다. "서버가 가벼워졌다"가 아니라 "서버가 책임져야 할 범위가 바뀌었다"로 읽는 게 정확합니다.

 

실제 프로젝트 진행 순서

1단계: 기존 서버에서 세션에 의존하는 부분부터 전수 조사합니다. 인증 캐싱, 메모리 내 작업 상태, 서버 주도 알림이 코드 어디에 있는지 목록화합니다.

2단계: 인증을 요청 단위 자체완결형으로 전환합니다. 매 요청마다 서명된 토큰을 독립적으로 검증하는 구조로 바꿉니다.

3단계: 장시간 작업을 task ID + 외부 저장소 패턴으로 재설계합니다. 작업을 시작하면 task ID를 즉시 반환하고, 실제 상태는 Redis나 DB에 저장합니다.

4단계: Roots·Sampling·Logging에 의존하는 기능은 12개월 유예 기간 안에 MRTR 기반 대안으로 옮깁니다.

5단계: 로드밸런서 설정을 단순화하고, 외부 상태 저장소의 지연시간과 가용성을 새로운 모니터링 대상으로 추가합니다.

주의 — 이번 개정은 명시적으로 비하위호환 변경을 포함합니다. 기존 클라이언트·서버 조합이 암묵적으로 세션을 전제했다면, 업그레이드 시점에 양쪽을 동시에 맞추지 않으면 바로 깨집니다. 단일 인스턴스로만 운영되는 내부 도구라면 당장 재설계가 급하지 않을 수도 있으니, 트래픽 확장 계획이 있는 서버부터 우선순위를 매기세요.

 

정리

2026-07-28 MCP 스펙 개정은 세션과 initialize 핸드셰이크를 완전히 제거해, MCP 서버를 로드밸런서 뒤의 평범한 스테이트리스 HTTP 서비스처럼 다룰 수 있게 만들었습니다. 그 대가로 인증·장시간 작업 상태·서버 주도 알림을 서버 구현자가 직접 외부 저장소와 MRTR 패턴으로 설계해야 합니다. 세션 의존 부분을 전수 조사하고 순서대로 마이그레이션하는 것이 핵심입니다.
