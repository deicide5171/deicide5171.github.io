AI가 코드를 빨리 쏟아낼수록 팀이 못 따라가는 '인지 부채' — 아키텍처 적합성 함수로 되갚기

개발 전략

한 줄 요약 — 기술부채는 코드 안에 쌓이지만 인지 부채는 개발자의 머릿속에 쌓입니다. AI 코딩 에이전트가 변경 속도를 끌어올릴수록 팀이 '왜 이렇게 짰는지'를 놓치는 인지 부채가 더 빨리 쌓입니다. Thoughtworks Radar가 제시한 아키텍처 적합성 함수를 어떻게 설계에 끼워 넣는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"이번 스프린트는 에이전트한테 많이 맡겨서 평소보다 PR이 세 배 나왔어요." 팀 입장에선 희소식처럼 들리지만, 이 상황을 두 달쯤 끌고 가본 팀이라면 다른 질문을 하게 됩니다 — 이 코드를 왜 이렇게 짰는지, 지금 이 레포에서 설명할 수 있는 사람이 몇 명이나 되는가. 기술부채라는 말은 익숙합니다. 코드 안에 쌓인 임시방편, 테스트 없는 분기 — 전부 코드를 읽으면 보입니다. 그런데 AI 에이전트가 변경 속도를 끌어올리면서 전혀 다른 종류의 부채가 드러나기 시작했습니다. 코드 자체는 멀쩡히 동작하는데, 왜 이런 구조로 짰는지를 아무도 설명하지 못하는 상황입니다.

Thoughtworks Technology Radar Volume 34(2026년 4월)는 이 현상에 "codebase cognitive debt"라는 이름을 붙였습니다. 정의는 명확합니다 — 시스템의 실제 구현과, 팀이 그 시스템이 왜 그렇게 동작하는지에 대해 공유하고 있는 이해 사이의 간극입니다. 기술부채가 코드 안에 있다면, 인지 부채는 개발자들의 머릿속에 있습니다. 여러 에이전트가 동시에 코드를 바꾸는 "코딩 에이전트 스웜"이 흔해질수록 이 간극은 더 빨리 벌어집니다 — 변경은 빠른데 그 설계 의도를 따라잡는 속도는 사람 머릿속 용량에 묶여 있기 때문입니다.

 

전체 시스템에서의 위치

기존 CI 파이프라인(린트, 테스트, 보안 스캔)은 코드의 "동작"만 검증합니다. 인지 부채를 다루려면 "이 변경이 팀의 아키텍처 이해와 얼마나 어긋났는가"를 재는 별도 체크포인트가 필요합니다 — 이게 바로 아키텍처 적합성 함수(architectural fitness function)가 들어갈 자리입니다.

 

기술부채 관리와 인지 부채 관리는 다른 도구를 쓴다
기준기술부채인지 부채
존재하는 곳코드 자체개발자들의 공유 이해
측정 수단정적 분석, 복잡도 지표적합성 함수, 온보딩 소요 시간
되갚는 방법리팩터링, 중복 제거설계 의도 기록, 아키텍처 리뷰
방치 시 결과버그·성능 저하아무도 시스템을 설명 못 함

 

두 부채를 같은 도구로 다루려는 시도가 가장 흔한 실수입니다. 린트 규칙을 더 깐깐하게 돌린다고 인지 부채가 줄지 않습니다. 코드는 깨끗한데 "왜 이 모듈이 저 모듈을 직접 호출하면 안 되는지"를 아무도 모르는 상태는 얼마든지 가능합니다. 두 축을 별도로 측정하고 별도로 갚아야 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 코드를 더 많이 리뷰하는 게 아니라, 우리 아키텍처의 "깨지면 안 되는 규칙"을 목록으로 적는 것입니다 — 예를 들어 "도메인 레이어는 인프라 레이어를 직접 import하지 않는다" 같은 것들입니다. 목록이 생기면 ArchUnit(Java)이나 dependency-cruiser(JS) 같은 도구로 이 규칙들을 자동 체크로 바꿔, 사람이 아니라 에이전트가 만든 변경에도 똑같이 적용되게 만듭니다.

// ArchUnit 예시 — 도메인 레이어가 인프라 레이어를 직접 참조하지 못하도록 고정
@ArchTest
static final ArchRule domain_should_not_depend_on_infrastructure =
    noClasses().that().resideInAPackage("..domain..")
        .should().dependOnClassesThat().resideInAPackage("..infrastructure..");

두 번째로는 변경이 머지될 때 "왜 이렇게 짰는가"를 코드와 함께 남기는 습관을 제도화합니다. 마지막으로 분기마다 온보딩하는 사람이 특정 모듈을 설명하는 데 걸리는 시간을 재봅니다. 이 시간이 늘어나고 있다면 적합성 함수가 놓치고 있는 인지 부채가 쌓이고 있다는 신호입니다.

 

주의 — 적합성 함수만 있으면 규칙을 왜 세웠는지는 여전히 코드에 안 남고, 설계 의도 기록만 있으면 아무도 안 읽어서 깨져도 아무도 모릅니다. 두 장치를 함께 갖춰야 합니다.
