Next.js 16.3 Instant Navigations — Partial Prefetching은 페이지 전환을 어떻게 즉시로 만드나

프론트엔드

한 줄 요약 — 라우트를 정적 셸과 동적 데이터로 분리해, 셸은 미리 프리페치·캐시하고 나머지만 클릭 시점에 스트리밍하는 Next.js 16.3 Instant Navigations의 원리를 정리했습니다.

 

왜 지금 내비게이션 캐싱을 다시 봐야 하는가

Next.js App Router는 초기 로드는 빠르지만, 페이지 전환 시점에는 서버에 다시 요청을 보내고 기다리는 구간이 존재했습니다. 동적 데이터가 섞인 라우트에서는 매번 서버 렌더링을 처음부터 다시 수행해야 했기 때문에, 링크를 눌러도 곧바로 화면이 바뀌지 않는 경우가 많았습니다. 이 몇백 밀리초의 공백이 "느린 앱"이라는 인상을 만듭니다.

 

정적 셸과 동적 데이터의 분리 캐싱

Partial Prefetching은 라우트를 정적 셸(레이아웃, 스켈레톤)과 동적 부분(로그인 데이터, 실시간 값)으로 나눠 다르게 취급합니다. 링크가 뷰포트에 들어오는 순간 정적 셸 전체를 즉시 프리페치해 캐시하고, 사용자가 실제로 클릭하면 캐시된 셸이 즉시 화면에 그려지며 그 안의 동적 슬롯만 서버에 스트리밍 요청을 보내 채워집니다. "뼈대는 즉시, 살은 스트리밍으로"로 바뀌는 것입니다.

방식 클릭 시 첫 화면 서버 요청 시점
기존 App Router 전체 렌더링 대기 클릭 시점
Instant Navigations 셸 즉시 + 스트리밍 셸은 사전, 데이터는 클릭 시점

 

캐시 무효화와 스테일 데이터 트레이드오프

정적 셸을 미리 캐싱해둔다는 것은 그 셸이 오래된 상태일 수 있다는 위험을 동반합니다. Next.js는 라우트별 staleTime 설정과 재검증(revalidate) 호출로 캐시를 무효화합니다. 실무에서 주의할 점은 정적 셸 자체에 사용자별로 달라지는 정보(장바구니 개수 배지 등)를 넣으면, 캐시가 다른 세션 간에 재사용되며 오정보가 노출될 위험이 있다는 것입니다.

동적 슬롯 분리 예제
export default function DashboardPage() {
  return (
    <StaticShell>
      <Suspense fallback={<StatsSkeleton />}>
        <DynamicUserStats />
      </Suspense>
    </StaticShell>
  );
}

Suspense 경계 바깥의 StaticShell은 프리페치 시점에 캐시되고, 경계 안의 DynamicUserStats만 실제 내비게이션이 일어날 때 서버에서 새로 가져옵니다.

 

실무 포인트

정적 셸 안에 사용자별 개인화 데이터를 넣지 말아야 합니다. 캐시가 공유되므로 다른 사용자의 오래된 정보가 잠깐 노출될 수 있습니다. 개인화 값은 항상 Suspense로 감싼 동적 슬롯에 둬야 합니다.

프리페치 대상 링크가 너무 많으면 오히려 낭비입니다. 리스트 페이지에서는 prefetch={false}로 선택적으로 끄는 것이 필요할 수 있습니다.

주의 — staleTime 설정은 라우트의 데이터 변경 빈도에 맞춰야 합니다. 거의 안 바뀌는 정적 페이지는 길게, 실시간성이 중요한 라우트는 짧게 잡아야 캐시 이득과 신선도 사이의 균형이 맞습니다.
