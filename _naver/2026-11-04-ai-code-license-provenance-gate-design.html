"이 기능 빨리 만들어주세요"가 끌고 들어오는 오픈소스 라이선스 — AI 코드 프로비넌스 게이트 설계

dev-strategy

한 줄 요약 — 에이전트가 생성한 코드는 패키지 매니저를 거치지 않고 저장소에 들어오기 때문에, 의존성 매니페스트만 보는 기존 라이선스 스캐너는 이를 놓칩니다. 업계 조사는 코드베이스 68%에서 라이선스 충돌이 발견됐다고 보고합니다. 이 구조적 빈틈을 어느 단계에 게이트로 막을지 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"이 기능, 빨리 구현해주세요." 코딩 에이전트에게 흔히 던지는 요청입니다. 에이전트는 학습 데이터에 포함된 수많은 오픈소스 코드의 패턴을 참고해 결과물을 내놓는데, 이 과정에서 특정 오픈소스 프로젝트의 코드 스니펫과 거의 동일한 블록이 그대로 섞여 들어올 수 있습니다. 문제는 이 코드가 package.json 같은 의존성 매니페스트에 전혀 등록되지 않는다는 점입니다. 에이전트가 직접 타이핑하듯 생성한 코드는 흔적 없이 소스 파일에 바로 섞여 들어갑니다.

그래서 기존에 조직이 써오던 SCA(Software Composition Analysis) 도구는 이 경로를 아예 보지 못합니다. 업계 보고서는 오픈소스 컴포넌트의 상당수가 표준 패키지 매니저 바깥 경로로 코드베이스에 들어오고 있다고 지적합니다. 같은 흐름에서 상용 코드 감사 보고서는 조사 대상 코드베이스의 68%에서 라이선스 충돌이 발견됐다고 밝혔는데, 이는 전년 대비 증가한 수치입니다. AI 코딩 도구를 쓰는 조직 중 공식 정책을 가진 비율이 20%를 밑돈다는 조사 결과까지 겹치면, 지금 이 틈을 메우지 않으면 문제가 계속 쌓이는 구조라는 뜻이 됩니다.

 

전체 시스템에서의 위치

지금 많은 조직의 파이프라인은 "에이전트가 코드를 생성 → PR 생성 → CI가 테스트·린트 → 매니페스트 기반 SCA가 의존성 라이선스 검사 → 머지" 순서로 짜여 있습니다. 이 흐름에서 SCA는 import나 require로 선언된 외부 패키지만 봅니다. 에이전트가 함수 본문에 직접 써 넣은, 다른 오픈소스 프로젝트와 거의 동일한 코드 블록은 이 검사망에 전혀 걸리지 않습니다.

이 빈틈을 메우려면 "코드 블록 단위의 유사도·출처 검사"라는 새 계층이 기존 파이프라인 중간에 들어가야 합니다. 위치는 PR 생성 직후, 기존 SCA 단계와 나란히 두는 것이 합리적입니다. 너무 이르게 넣으면 작업 흐름을 막고, 너무 늦게 넣으면 이미 섞인 코드를 되돌리는 비용이 커집니다.

 

선택의 트레이드오프
기준Pre-commit 훅PR 생성 시 CI 게이트Merge 블로킹 게이트사후 정기 감사
탐지 시점가장 이름리뷰와 동시머지 직전이미 머지된 뒤
개발 속도 영향커밋마다 지연리뷰 대기에 흡수머지 지연없음
우회 가능성쉽게 우회됨리뷰어가 무시 가능우회 어려움이미 늦음
도입 난이도환경마다 설정 필요기존 CI에 단계 추가정책적 합의 필요가장 쉬움

 

표가 보여주는 결론은 하나의 단계만으로 충분하지 않다는 점입니다. 처음에는 사후 정기 감사로 시작해 충돌 빈도와 false positive율을 측정하고, 그 데이터를 근거로 PR CI 게이트로 끌어올리는 점진적 전환이 현실적입니다.

 

실제 프로젝트 진행 순서

1) 조직에 AI 코딩 도구 사용에 대한 명시적 정책이 있는지부터 확인합니다.
2) 스니펫·유사도 기반 스캔 도구를 드라이런 모드로 기존 CI에 먼저 붙입니다.
3) 커밋·PR 메타데이터에 AI 생성 여부·모델·생성 시각을 기록하는 관행부터 도입합니다.
4) 드라이런 데이터를 근거로 PR 생성 시 CI 게이트로 전환합니다.
5) false positive율이 충분히 낮아졌을 때만 merge 블로킹 게이트로 격상합니다.

 

주의 — 매니페스트 기반 SCA를 이미 쓰고 있다고 해서 라이선스 관리가 끝났다고 안심하지 마세요. AI가 직접 작성한 코드 블록을 원천적으로 볼 수 없는 구조이므로 서로 다른 문제입니다. 순수 AI 생성 결과물의 저작권 귀속 자체도 법적으로 불확실하니 법무팀과 별도로 검토해야 합니다.

 

정리

에이전트가 생성하는 코드는 패키지 매니저를 거치지 않기 때문에 매니페스트 기반 라이선스 스캐너의 검사망 바깥에 있고, 업계 조사는 이미 코드베이스 다수에서 라이선스 충돌을 보고하고 있습니다. 이 빈틈을 메우는 프로비넌스 게이트는 기존 CI의 SCA 단계와 나란히, PR 생성 시점에 두는 것이 균형점입니다. 사후 감사 → PR 게이트 → merge 블로킹의 순서로 점진적으로 격상하는 편이 현실적입니다.
