"반경 1km 매장 집계, 대시보드에서 바로 돌려주세요" — 공간 분석을 PostGIS에 얹을 것인가 DuckDB Spatial로 뗄 것인가

GIS

한 줄 요약 — 매장 반경 안 경쟁사 수를 대시보드에서 실시간 집계해달라는 요구를 서비스 PostGIS에 그대로 얹을지, 같은 날 나온 DuckDB 2.0과 PostGIS 3.7 RC를 계기로 분석 전용 DuckDB Spatial 레이어로 뗄지 판단하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"신규 매장 입점 검토용으로, 반경 1km 안에 경쟁사가 몇 곳 있는지 대시보드에서 바로 보여주세요"라는 요구는 흔합니다. 가장 빠른 답은 서비스 운영에 쓰는 PostGIS에 공간 쿼리를 하나 더 얹는 것입니다. 매장이 수만 개로 늘고 분석 축이 업종별·시간대별 교차 집계로 복잡해지면, 무거운 공간 조인이 주문 생성 같은 트랜잭션 쿼리와 자원을 두고 경쟁하기 시작합니다.

2026년 10월 21일 PostGIS 3.7.0rc3와 DuckDB 2.0이 같은 날 나온 건 우연이지만, 이 판단을 다시 보기 좋은 계기가 됐습니다. DuckDB는 spatial 확장을 통해 S3에 쌓인 GeoParquet·COG 파일을 import 없이 바로 읽어 집계할 수 있는 임베디드 분석 엔진으로 자리 잡았습니다. 질문은 이제 "공간 분석 쿼리를 어디서 돌릴까"가 아니라 트랜잭션 레이어와 분석 레이어를 아예 분리할 것인가입니다.

 

전체 시스템에서의 위치

대시보드가 PostGIS를 직접 바라보면 데이터는 항상 최신이지만 분석 부하가 트랜잭션 경로와 섞입니다. GeoParquet 내보내기를 중간에 끼우면 분석은 완전히 격리된 엔진에서 돌지만, 내보내기 주기만큼의 데이터 지연이 생깁니다. 이 지연을 1분으로 둘지 하루로 둘지는 "실시간 운영 지표"냐 "입점 검토용 리포트"냐에 따라 달라지므로, 신선도 요구를 먼저 확정해야 합니다.

 

선택의 트레이드오프
기준PostGIS 직접 쿼리DuckDB Spatial 분리
데이터 신선도항상 최신내보내기 주기만큼 지연
트랜잭션 영향자원 경쟁 발생완전 격리
복잡한 교차 집계조인 많아지면 느려짐컬럼형+벡터화로 유리
운영 복잡도추가 구성 없음내보내기 파이프라인 관리 필요

 

DuckDB의 컬럼형 저장·벡터화 실행은 업종별·시간대별 교차 집계 같은 작업에서 구조적으로 유리합니다. 다만 이 이점은 데이터가 이미 GeoParquet로 빠져나와 있을 때만 성립하므로, 내보내기 파이프라인을 안정적으로 운영할 수 있느냐가 실제 도입 여부를 가릅니다.

 

실제 프로젝트 진행 순서

가장 먼저 지금 PostGIS에 걸리는 쿼리 로그에서 "분석성 쿼리"를 가려냅니다. GROUP BY가 들어가고 스캔 범위가 넓은 쿼리를 pg_stat_statements로 식별해, 분리가 당장 필요한지 숫자로 판단합니다.

-- DuckDB: spatial 확장으로 GeoParquet 직접 읽어 반경 집계
INSTALL spatial; LOAD spatial;
SELECT a.store_id,
       count(*) FILTER (WHERE ST_DWithin(a.geom, b.geom, 1000)) AS nearby
FROM read_parquet('s3://bucket/stores.parquet') a,
     read_parquet('s3://bucket/stores.parquet') b
WHERE a.store_id <> b.store_id
GROUP BY a.store_id;

내보내기 주기는 처음부터 "실시간"을 목표로 잡지 않고 1시간 주기로 먼저 운영한 뒤, 사용자가 실제로 더 짧은 신선도를 요구하는지 보고 줄여 갑니다. 동시에 PostGIS 쪽 분석 쿼리를 하나씩 걷어내며 트랜잭션 지연시간이 실제로 개선되는지 추적해야 합니다.

 

주의 — 내보내기 파이프라인이 멈췄을 때 대시보드가 오래된 데이터를 "최신"인 것처럼 보여주지 않도록, 내보내기 시각을 반드시 함께 노출하세요.
