트랜잭셔널 아웃박스 패턴 — DB 변경과 이벤트 발행을 안전하게 묶기

시스템설계

한 줄 요약 — DB 저장과 메시지 발행을 따로 하면 한쪽만 성공하는 사고가 나므로, 아웃박스 테이블에 이벤트를 함께 기록해 원자성을 확보합니다.

 

왜 이 문제가 생기는가

주문을 저장하면서 동시에 "주문 완료" 이벤트를 카프카에 발행하는 코드를 생각해봅시다. DB 커밋은 성공했는데 메시지 전송 중 네트워크가 끊기면 주문은 저장됐지만 이벤트는 유실됩니다. 반대 순서라면 이벤트는 나갔는데 트랜잭션이 롤백되는 상황도 생깁니다.

재고 차감, 알림 발송처럼 이벤트 하나가 여러 시스템을 움직이는 구조에서는 이 어긋남이 곧바로 데이터 불일치로 이어집니다.

 

 

잘못된 해결 시도들

분산 트랜잭션(2PC)으로 묶으려는 시도가 흔하지만, 카프카 같은 현대 메시지 브로커는 2PC를 지원하지 않는 경우가 많고, 지원해도 코디네이터가 단일 장애점이 되어 지연시간이 늘어납니다. 발행 순서를 바꿔도 서로 다른 두 리소스를 하나의 원자적 단위로 묶을 수 없다는 근본 문제는 남습니다.

아웃박스 패턴의 핵심

메시지를 브로커로 직접 보내지 않고, 같은 DB 트랜잭션 안의 아웃박스 테이블에 먼저 기록합니다. 비즈니스 데이터 저장과 이벤트 기록이 하나의 로컬 트랜잭션이 되므로 원자성이 보장됩니다. 이후 별도 릴레이 프로세스가 아웃박스 테이블을 읽어 실제 브로커로 전달합니다.

발행 방식 동작 특징
폴링 스케줄러가 주기 조회 후 전송 구현 간단, 지연 발생
CDC(Debezium) 트랜잭션 로그를 읽어 즉시 전달 지연 최소화, 구성요소 증가

 

실무 포인트

아웃박스는 최소 한 번(at-least-once) 전달을 전제로 합니다. 릴레이가 전송 후 완료 표시 전에 죽으면 중복 발행될 수 있으므로, 소비자 쪽에서 이벤트 ID 기준 멱등 처리가 반드시 필요합니다. 발행 완료된 행은 주기적으로 정리해 테이블이 비대해지지 않게 관리해야 합니다.

주의 — 아웃박스는 로컬 트랜잭션의 원자성만 보장합니다. 브로커로의 전달은 여전히 비동기이므로, 소비자 설계에 지연 가능성을 반드시 반영하세요.
