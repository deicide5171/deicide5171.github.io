같은 저장소를 셋이 동시에 고치면 — 병렬 코딩 에이전트의 작업 분할과 격리 설계

AI

한 줄 요약 — "큰 리팩터링을 에이전트 여러 개한테 나눠서 시켜주세요"라는 요구는 같은 저장소를 여러 에이전트가 동시에 건드리는 순간 파일 충돌과 중복 작업 문제를 만듭니다. 서브에이전트, Agent Teams, 외부 오케스트레이터라는 세 단계 병렬화 중 어디서부터 손대야 하는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"리팩터링 범위가 넓으니까 에이전트 여러 개한테 나눠서 동시에 시켜주세요." 코딩 에이전트가 한 세션에서 수십 개 파일을 몇 시간씩 걸려 처리하는 걸 지켜본 팀이라면 자연스럽게 나오는 요구입니다. 문제는 "나눠서 동시에"라는 말이 숨기고 있는 아키텍처 질문입니다. 에이전트 둘이 같은 저장소의 같은 브랜치를 동시에 건드리면, 한쪽이 커밋하는 사이 다른 쪽이 읽은 파일 상태는 이미 낡은 것이 됩니다.

2026년 들어 Claude Code의 Agent Teams와 서드파티 멀티에이전트 오케스트레이터가 이 문제를 각자 다른 층위에서 풀고 있습니다. 둘 다 전제는 같습니다 — 병렬화는 격리 전략이 먼저고, 작업 분할은 그다음입니다. 격리 없이 병렬 수부터 늘리면 충돌 해결에 쓰는 시간이 병렬화로 번 시간을 역전시킵니다.

 

핵심 개념 — 세 단계 병렬화 모델
층위 구조 적합한 작업
세션 내 서브에이전트 오케스트레이터가 자식 에이전트를 포크 코드 탐색, 영향 범위 분석(읽기 위주)
Agent Teams(단일 머신) 공유 작업 목록 + 팀원별 git worktree 같은 저장소 내 분리 가능한 쓰기 작업
외부 오케스트레이터 레포·환경 단위로 완전히 분리 서로 다른 레포, 장기 병행 기능

 

세션 내 서브에이전트는 코드를 쓰지 않는 조사 작업에는 안전합니다. 쓰기 작업이 들어가는 순간, 격리 경계가 "컨텍스트"에서 "파일시스템"으로 올라가야 합니다. 이게 Agent Teams가 각 팀원에게 별도 git worktree를 붙이는 이유입니다 — 워킹 디렉터리 자체가 갈라져 있으면 같은 파일을 동시에 쓰다 서로 덮어쓰는 일이 구조적으로 불가능해집니다.

 

전체 시스템에서의 위치

 

리드 세션은 요청을 파일/모듈 단위로 쪼개 공유 작업 목록에 올립니다. 각 팀원 에이전트는 자기 worktree에서 독립적으로 구현·테스트를 마치고 커밋합니다. CI는 이 단계에서 개별 브랜치를 검증하고, 마지막으로 리드(또는 사람)가 병합 순서를 정해 메인 브랜치로 모읍니다 — 이 병합 단계가 "동시에 일했지만 충돌 없이 합쳐지는가"를 실제로 검증하는 지점입니다.

 

선택의 트레이드오프

작업이 읽기 위주라면 세션 내 서브에이전트로 충분합니다. 같은 저장소 안에서 파일 그룹이 명확히 분리되는 작업은 Agent Teams가 적합하지만, 공유 인터페이스나 공통 설정 파일을 여러 팀원이 동시에 건드리면 병합 단계에서 충돌이 몰립니다. 서로 다른 레포, 또는 수일 단위로 병행되는 큰 기능은 외부 오케스트레이터로 완전히 분리하고 PR 단위로만 통합해야 합니다. 병렬 에이전트 수가 늘수록 토큰 비용과 조율 오버헤드도 함께 늘어난다는 점도 잊지 말아야 합니다.

 

실무 명령 예제
git worktree add ../repo-module-a feature/module-a-refactor
git worktree add ../repo-module-b feature/module-b-refactor

# 작업 완료 후 정리
git worktree remove ../repo-module-a

 

실제 프로젝트 진행 순서

1단계: 작업을 파일/모듈 단위 의존성 그래프로 먼저 그려 병렬화 가능 여부를 가립니다.

2단계: 공유 접점(공통 설정, 인터페이스, 마이그레이션)을 식별해 한 에이전트에게만 배정합니다.

3단계: 팀원마다 worktree를 분리하고 작업을 시작시킵니다.

4단계: 개별 브랜치 단위로 CI를 먼저 통과시킨 뒤, 사람 또는 리드가 순서를 정해 순차적으로 병합합니다. 동시에 여러 브랜치를 한꺼번에 머지하지 않는 게 핵심입니다.

 

주의 — 병렬 에이전트 수를 늘리는 게 항상 더 빠른 건 아닙니다. 공유 접점 파일을 미리 정리하지 않으면 병합 충돌 해결 시간이 병렬화로 번 시간을 역전시킵니다.

 

정리

병렬 코딩 에이전트는 작업 분할보다 격리 전략이 먼저입니다. 읽기 위주는 서브에이전트, 분리 가능한 쓰기 작업은 Agent Teams+worktree, 완전히 독립된 작업은 외부 오케스트레이터로 층위를 맞추고, 공유 접점 파일을 사전에 전담시키고 병합은 순차적으로 — 이 두 가지만 지켜도 대부분의 충돌을 피할 수 있습니다.
