Java Record Pattern Matching과 Sealed Classes 심화 (JDK 21)

백엔드

한 줄 요약 — Sealed Classes와 Record Pattern을 결합하면 새 하위 타입 처리 누락을 컴파일 타임에 강제로 잡아낼 수 있습니다. 동작 원리를 정리했습니다.

 

왜 지금 Record Pattern과 Sealed Classes를 다시 봐야 하는가

instanceof 체이닝은 새 하위 타입이 추가돼도 분기 누락을 컴파일러가 알려주지 않습니다. switch의 default 분기도 새 타입 처리를 깜빡한 사실을 숨기기 쉽습니다. Sealed Classes와 Record Pattern이 결합되면 컴파일러가 모든 경우를 다뤘는지 검증하는 완전성 검사가 가능해집니다.

 

Sealed Classes: 하위 타입의 닫힌 집합을 선언한다

sealed로 선언하면 permits 절에 명시한 타입만 하위 타입이 될 수 있습니다. 이는 컴파일러에게 전체 타입 목록을 알려주는 것이며, switch에서 모든 하위 타입을 다루면 default 없이도 완전성 검사를 통과합니다. 하나라도 빠뜨리면 컴파일 에러가 발생합니다.

 

Record Pattern: 타입 검사와 필드 분해를 한 번에

Record Pattern은 "이 타입이면서 필드를 이렇게 분해해서 꺼내라"를 한 문장으로 표현합니다. 중첩된 레코드도 패턴을 중첩해 한 번에 분해할 수 있고, when 가드로 조건까지 결합할 수 있습니다.

항목 기존 방식 Sealed + Record Pattern
새 타입 추가 시 누락을 못 잡음 완전성 검사로 컴파일 에러
필드 접근 getter 별도 호출 패턴 안에서 즉시 분해
조건부 매칭 타입 매칭 후 별도 if when 가드로 결합

 

예제 — Sealed 계층과 Record Pattern으로 결제 이벤트 처리
sealed interface PaymentEvent permits PaymentApproved, PaymentFailed, PaymentRefunded {}

record PaymentApproved(String orderId, long amountCents) implements PaymentEvent {}
record PaymentFailed(String orderId, String reason) implements PaymentEvent {}
record PaymentRefunded(String orderId, long amountCents, String refundReason) implements PaymentEvent {}

String describe(PaymentEvent event) {
    return switch (event) {
        case PaymentApproved(String orderId, long amount) when amount > 1_000_000 ->
            "고액 결제 승인: " + orderId;
        case PaymentApproved(String orderId, long amount) ->
            "결제 승인: " + orderId;
        case PaymentFailed(String orderId, String reason) ->
            "결제 실패: " + orderId;
        case PaymentRefunded(String orderId, long amount, String reason) ->
            "환불 처리: " + orderId;
    };
}

PaymentEvent에 새 하위 타입을 추가하면 이 switch 문은 그 케이스를 다루지 않았다는 이유로 즉시 컴파일 에러를 냅니다.

 

실무 포인트

도메인 이벤트나 API 응답처럼 종류가 유한한 타입 계층에 sealed를 우선 적용하세요. 외부 사용자가 자유롭게 구현체를 추가해야 하는 인터페이스에는 적합하지 않습니다.

Record Pattern의 이점을 온전히 누리려면 하위 타입을 레코드로 설계하는 것이 자연스럽습니다.

주의 — 기존 instanceof 체이닝 코드를 한 번에 다 바꾸려 하지 마세요. 새로 추가하는 도메인 이벤트·명령 계층부터 점진적으로 적용하는 편이 리스크가 적습니다.
