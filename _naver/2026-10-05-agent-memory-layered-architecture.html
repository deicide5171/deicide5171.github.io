"어제 뭘 했는지 기억해줘" — 에이전트 메모리를 3계층으로 설계한다는 것

AI

한 줄 요약 — "에이전트가 어제 결정한 걸 오늘도 기억했으면 좋겠어요"라는 요구는 컨텍스트 창을 늘리는 것으로 풀리지 않습니다. 워크스페이스 파일·런타임 압축·장기 저장소로 나뉘는 3계층 메모리 아키텍처와, 요약 대신 원본을 주소로 불러오는 Addressable Recall Compaction까지 설계 기준을 정리했습니다.

 

왜 지금 이 문제가 불거지는가

"에이전트가 하루 종일 돌아가면서 작업하는데, 어제 내린 결정을 오늘 또 처음부터 설명 안 해도 되게 해주세요." 상시 가동 백그라운드 에이전트, 장시간 코딩 세션, 여러 날에 걸친 리서치 작업이 흔해지면서 이 요구가 거의 모든 프로젝트에 등장합니다. 처음 드는 생각은 "컨텍스트 창을 더 큰 모델로 바꾸면 되지 않나"입니다. 실제로 최근 모델들은 백만 토큰급 컨텍스트와 서버 측 자동 압축을 제공합니다. 하지만 이건 문제를 푸는 게 아니라 문제가 터지는 시점을 뒤로 미루는 것에 가깝습니다. 컨텍스트 창이 아무리 커져도 도구 호출 결과, 파일 내용, 중간 추론이 계속 쌓이는 장기 실행 에이전트는 결국 한계에 부딪히고, 그 순간 무엇을 버리고 무엇을 남길지 결정해야 합니다.

더 근본적인 문제는 "기억해줘"라는 한 마디가 실제로는 서로 다른 세 가지 요구를 뭉뚱그린다는 점입니다. 같은 세션 안에서 수백 번의 도구 호출을 거친 뒤에도 초반 결정을 잊지 않는 것, 세션이 끝나고 다음 날 다시 시작했을 때도 전에 합의한 내용을 아는 것, 그리고 "이 프로젝트에서는 이런 규칙을 지킨다"는 정체성 수준의 지침을 매번 재설명하지 않는 것은 전혀 다른 저장 메커니즘을 요구합니다. 이 구분 없이 접근하면 벡터 DB 하나 붙이고 끝내는 얕은 설계가 되기 쉽습니다.

 

요구사항을 기술 문제로 번역하기

"기억해줘"를 들었을 때 먼저 물어야 할 질문은 세 가지입니다. 첫째, 이 정보가 지금 이 작업 안에서만 필요한가, 아니면 세션이 끝난 뒤에도 다른 작업에서 다시 꺼내 써야 하는가. 둘째, 압축 과정에서 요약으로 뭉개져도 괜찮은 정보인가, 아니면 원문 그대로 다시 불러올 수 있어야 하는가. 셋째, 매 세션 시작 시 무조건 로드돼야 하는 규칙인가, 아니면 필요할 때만 검색해서 가져오면 되는 지식인가. 이 세 질문의 답이 바로 워크스페이스 파일, 런타임 압축, 장기 저장소라는 세 계층에 각각 대응합니다.

 

전체 시스템에서의 위치

 

가장 바깥층은 워크스페이스 파일입니다. 프로젝트 규칙, 코딩 컨벤션, 반복되는 지침을 짧은 마크다운 파일로 저장소에 두고 세션 시작 시 항상 읽습니다. 비용이 가장 싸고 구현도 단순하지만, 그만큼 담을 수 있는 양도 제한적입니다. 중간층은 런타임 컨텍스트와 압축입니다. 한 세션 안에서 도구 호출과 추론이 쌓이다가 컨텍스트 한계에 가까워지면, 오래된 턴을 지우거나(단순 절단), 요약하거나(계층적 요약), JSON 상태로 접어 넣거나(상태 폴딩), 아카이브에 옮기고 주소만 남기는(Addressable Recall Compaction) 방식 중 하나로 처리합니다. 가장 안쪽층은 장기 저장소입니다. 세션이 끝나도 남아야 하는 사실·결정·사용자 선호를 벡터 DB나 그래프 DB에 넣고, 다음 세션에서 검색(RAG)으로 다시 가져옵니다. 이 세 계층은 독립적으로 동작하지 않습니다 — 장기 저장소에서 검색해 온 내용도 결국 런타임 컨텍스트에 들어오고, 거기서 다시 압축 대상이 됩니다.

압축 전략에서 최근 주목받는 것이 Addressable Recall Compaction(ARC)입니다. 기존 방식들은 압축 시점에 "요약할지 버릴지"를 미리 결정해야 하는데, 이 결정이 틀리면 나중에 꼭 필요했던 세부 정보가 영구히 사라집니다. ARC는 도구 실행 결과를 추가 전용(append-only) 로그에 원문 그대로 저장하고 짧은 ID만 발급한 뒤, 활성 컨텍스트에는 그 ID와 한 줄 요약만 남깁니다. 에이전트는 필요할 때 그 ID로 원문을 다시 요청할 수 있습니다 — 도구를 재실행하지 않고도 원본을 복원하는 것입니다. 핵심은 압축 시점과 조회 시점을 분리하는 설계입니다.

 

선택의 트레이드오프
전략 정보 손실 위험 구현 복잡도 적합한 상황
단순 절단 매우 높음 가장 낮음 과거 맥락이 거의 불필요한 단발성 작업
계층적 요약 중간~높음 중간 전체 흐름만 유지하면 되는 대화형 작업
상태 폴딩 중간 중간~높음 상태가 명확히 정의되는 반복적 워크플로
RAG 기반 장기 저장 낮음 높음 세션을 넘나드는 사실·선호 재사용
Addressable Recall Compaction 가장 낮음 가장 높음 장시간 실행·고위험 에이전트 작업

 

표에서 가장 중요한 줄은 토큰 비용과 구현 복잡도의 교환 관계입니다. 단순 절단과 계층적 요약은 구현이 쉬운 대신 "그때는 안 중요해 보였지만 나중에 필요했던 정보"를 영구히 잃을 위험을 안고 갑니다. 반대로 ARC처럼 원문을 전부 보존하는 방식은 안전하지만 아카이브 저장소와 조회 인터페이스를 별도로 구축해야 하므로, 짧게 끝나는 작업에는 과한 투자입니다. Letta·Mem0·Zep·Cognee 같은 오픈소스 메모리 프레임워크들이 이 지점에서 각자 다른 기본값을 택한다는 점도 참고할 만합니다 — Mem0는 가볍고 빠른 요약 중심, Zep은 세션 인지형 저장, Cognee는 그래프 구조로 관계를 보존하는 쪽에 가깝습니다.

 

실제 프로젝트 진행 순서

1단계: 지금 겪는 망각 실패를 세션 내부와 세션 간으로 분류합니다. 서로 다른 계층의 문제이므로 섞어서 접근하면 안 됩니다.

2단계: 가장 싼 계층부터 도입합니다. 반복되는 규칙은 벡터 DB 전에 워크스페이스 파일로 먼저 해결되는지 확인합니다.

3단계: 작업 특성에 맞게 압축 전략을 고릅니다. 고위험 작업이면 ARC 같은 주소 기반 아카이빙을 검토합니다.

4단계: 세션 간 공유가 실제로 필요한지부터 로그로 검증한 뒤 장기 저장소에 투자합니다.

5단계: 압축 후 재질의 실패율을 수치로 추적해 압축 강도를 조정합니다.

주의 — "메모리 추가"를 벡터 DB 연동과 동일시하지 마세요. 많은 경우 워크스페이스 파일 수준의 해결로 충분하며, 장기 저장소는 세션 간 재사용이 데이터로 확인된 뒤에 투자해도 늦지 않습니다.

 

정리

"기억해줘"는 세션 내 압축, 세션 간 저장, 정체성 규칙이라는 서로 다른 세 가지 요구를 뭉뚱그린 표현이므로, 먼저 어느 계층의 문제인지 구분해야 합니다. 워크스페이스 파일 → 런타임 압축 → 장기 저장소 순으로 비용이 커지므로, 가장 싼 계층부터 채워가며 실제로 더 깊은 계층이 필요한지 데이터로 검증하는 것이 순서입니다.
