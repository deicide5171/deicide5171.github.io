"GPT도 붙이고 더 싼 모델도 섞어주세요" — LLM 게이트웨이, 어디에 둘 것인가

AI

한 줄 요약 — 분류 작업엔 싼 모델을, 복잡한 추론엔 비싼 모델을 섞어 쓰고 싶다는 요구는 애플리케이션 코드 안의 if문으로 풀리지 않습니다. 라우팅·실패 복구·비용 추적을 한 곳에 모으는 LLM 게이트웨이 계층이 필요한 이유와, 직접 만들지 기존 오픈소스·매니지드를 쓸지 판단하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"자주 쓰는 간단한 분류 작업은 싼 모델로 돌리고, 복잡한 추론이 필요한 요청만 Claude Opus로 보내주세요." 처음 이 요구를 받으면 가장 빠른 길은 호출 코드에 if문 하나를 추가하는 것입니다. 요청 종류를 보고 모델 이름을 바꿔 호출하면 끝나는 것처럼 보입니다. 그런데 모델이 세 개, 네 개로 늘고, 제공자마다 요청 포맷과 레이트리밋 정책이 다르고, 한 프로바이더가 장애를 내는 시점마다 이 if문은 감당할 수 없이 복잡해집니다.

2026년 들어 OpenAI 호환 엔드포인트 포맷이 사실상 업계 표준처럼 쓰이면서, 이 문제를 애플리케이션 코드가 아니라 별도의 중개 계층 — LLM 게이트웨이 — 에서 풀자는 흐름이 뚜렷해졌습니다.

 

전체 시스템에서의 위치

게이트웨이가 없으면 애플리케이션 코드가 각 프로바이더의 SDK를 직접 호출하고, 모델 선택·재시도·비용 집계 로직까지 전부 떠안습니다. 게이트웨이를 두면 애플리케이션은 게이트웨이 하나의 엔드포인트만 알면 되고, 모델 선택·정책 적용·실패 복구는 그 뒤에서 처리됩니다.

애플리케이션은 모델을 직접 지정하지 않고 "작업 종류"나 "품질/비용 선호도" 같은 의도만 실어 보냅니다. 게이트웨이 내부에서는 라우팅 정책에 따라 실제 호출할 모델을 고르고, 실패 시 대체 모델로 자동 전환합니다.

 

선택의 트레이드오프
구성 장점 단점
벤더 SDK 직접 호출 구조 단순, 추가 지연 없음 모델 전환마다 코드 전면 수정
오픈소스 셀프호스트 게이트웨이 데이터가 우리 네트워크를 안 벗어남 직접 운영·튜닝 부담
매니지드 게이트웨이 운영 부담 거의 없음 새 외부 의존성, 약정 비용
직접 구축 조직 특유 요구에 완전히 맞춤 개발·유지보수 비용 가장 큼

 

판단 기준은 두 가지입니다. 첫째, 요청·응답 데이터가 외부 중개 서비스를 거쳐도 되는가 — 안 된다면 오픈소스를 우리 네트워크 안에 셀프호스트하거나 직접 구축해야 합니다. 둘째, 라우팅 정책이 표준적인가, 조직 특유인가 — 비용·지연시간 기준의 일반적인 라우팅이면 기존 도구로 충분합니다.

 

실제 프로젝트 진행 순서

1. 현재 호출 중인 모델과 호출 목적을 먼저 나열합니다.
2. 라우팅 기준을 비용만으로 정하지 않고 지연시간·실패율도 함께 넣습니다.
3. 오픈소스 게이트웨이를 스테이징에 먼저 붙여 오버헤드를 실측합니다.
4. 실패 복구 정책을 트래픽이 가장 큰 경로부터 적용합니다.
5. 모델 믹스를 바꾸기 전에 비용 추적 대시보드부터 세웁니다.

 

예제 코드:

# 셀프호스트 게이트웨이 라우팅 정책 예시
model_list:
  - model_name: fast-classify
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY
  - model_name: deep-reasoning
    litellm_params:
      model: anthropic/claude-opus-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  routing_strategy: latency-based-routing
  fallbacks:
    - deep-reasoning: ["fast-classify"]

 

주의 — OpenAI 호환 포맷이 표준처럼 쓰여도 tool-calling 스키마, 안전 설정, 토큰 계산 방식은 모델마다 달라 게이트웨이가 모든 차이를 완전히 숨겨주지는 않습니다. 게이트웨이 자체가 전체 LLM 호출의 단일 장애점이 될 수 있으니 헬스체크·이중화를 빠뜨리지 마세요. 배치·비실시간 작업은 별도 라우팅 규칙으로 태워야 실제 비용 절감 효과가 납니다.

 

정리

"여러 모델을 섞어 쓰고 싶다"는 요구는 애플리케이션 코드의 if문이 아니라, 라우팅·실패 복구·비용 추적을 한 곳에 모으는 게이트웨이라는 별도 시스템 구성요소로 번역해야 합니다. 선택 기준은 데이터가 외부 중개 서비스를 거쳐도 되는지, 라우팅 정책이 표준적인지 조직 특유인지 두 가지입니다.
