Load Shedding — 트래픽 폭주 시 우선순위 기반으로 요청을 의도적으로 버리는 설계

아키텍처·시스템 설계

한 줄 요약 — 과부하 상황에서 낮은 우선순위 요청을 의도적으로 즉시 거절해 중요한 요청만이라도 지키는 Load Shedding 설계를 정리했습니다.

 

왜 지금 Load Shedding을 다시 봐야 하는가

트래픽이 순간적으로 용량을 초과하면 흔히 "모든 요청을 어떻게든 처리해보려는" 태도를 보입니다. 큐가 쌓이고 스레드 풀이 고갈되면서 처리량 자체가 무너져 정상 트래픽까지 타임아웃되는 상태에 빠집니다. 필요한 건 더 열심히 처리하는 게 아니라, 일부는 처리하지 않기로 결정하는 것입니다.

 

언제, 무엇을 기준으로 버릴 것인가

첫 번째 결정은 과부하 여부 판단 방식입니다. 정적 임계값도 쓸 수 있지만, 더 정교한 방식은 최근 요청의 실제 지연시간 분포를 관찰해 적응적으로 동시 처리 한도를 조절하는 적응형 동시성 제한입니다. 두 번째 결정은 무엇을 버릴지입니다. 결제 요청과 로그 수집 요청에 서로 다른 우선순위를 부여하고, 낮은 우선순위부터 먼저 거절하는 방식이 일반적입니다.

 

LIFO 큐와 데드라인 전파

과부하 상황에서는 FIFO보다 LIFO(후입선출) 큐가 유리할 때가 많습니다. FIFO는 이미 클라이언트가 타임아웃으로 포기했을 오래된 요청까지 처리하느라 리소스를 낭비하지만, LIFO는 방금 들어온 요청을 우선 처리합니다. 클라이언트의 데드라인 정보를 헤더로 전달하는 데드라인 전파를 결합하면, 이미 지난 요청을 하위 서비스로 넘기지 않고 즉시 버릴 수 있습니다.

전략 판단 기준 주의점
정적 임계값 셰딩 CPU/큐 길이 고정값 워크로드 변화에 둔감
적응형 동시성 제한 실측 지연시간 추이 초기 튜닝·관찰 필요
우선순위 기반 셰딩 요청 타입·비즈니스 가치 분류 체계 사전 설계 필요

 

우선순위 기반 셰딩 필터 예제
public void doFilter(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
    Priority priority = classify(req); // CRITICAL, NORMAL, BEST_EFFORT

    if (!limiter.tryAcquire(priority)) {
        res.setStatus(503);
        res.setHeader("Retry-After", "1");
        return;
    }

    Duration deadline = parseDeadline(req.getHeader("X-Deadline-Ms"));
    if (deadline.isNegative()) {
        res.setStatus(504);
        return;
    }

    chain.doFilter(req, res);
}

 

실무 포인트

셰딩은 부끄러운 실패가 아니라 설계된 성공입니다. 일부 요청에 즉시 503을 돌려주는 것이, 모든 요청이 타임아웃될 때까지 대기시키는 것보다 낫습니다. 셰딩 비율을 정상 동작 지표로 대시보드에 노출하는 것이 좋습니다.

우선순위 분류는 비즈니스팀과 미리 합의해야 합니다. 결제·인증은 최고 우선순위로, 추천·로깅은 최저 우선순위로 명시적으로 분류해두지 않으면 장애 상황에서 즉흥적으로 판단하게 됩니다.

주의 — 셰딩 지점은 가능한 한 앞단(로드밸런서·게이트웨이)에 두는 것이 자원 효율적입니다. DB 커넥션까지 소모한 뒤 버리는 것보다 게이트웨이 단계에서 버리는 것이 하위 리소스를 아낍니다.
