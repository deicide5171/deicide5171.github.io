이벤트 설계의 갈림길 — Event Notification과 Event-Carried State Transfer

아키텍처·시스템 설계

한 줄 요약 — 이벤트에 ID만 담을지 전체 상태를 담을지는 컨슈머-프로듀서 간 런타임 결합도를 결정하는 아키텍처 선택입니다.

 

왜 사소한 문제가 아닌가

"주문이 완료됐다"는 이벤트에 ID만 넣을지, 상품 목록·금액까지 전부 넣을지는 컨슈머가 데이터를 다시 얻기 위해 프로듀서에게 동기 호출을 해야 하는지를 결정합니다. 이 선택이 이벤트 기반 아키텍처가 추구하는 느슨한 결합이 실제로 달성되는지를 좌우합니다.

 

Event Notification — 무슨 일이 있었다만 알린다

최소한의 정보만 담는 방식으로, 컨슈머는 상세 정보가 필요하면 프로듀서 API를 다시 호출해야 합니다. 이벤트는 작고 단순하지만, 프로듀서에 대한 동기 의존성이 생겨 프로듀서가 다운되면 컨슈머도 처리를 못하는 상황이 생깁니다.

Event-Carried State Transfer — 데이터를 통째로 옮긴다

필요한 데이터를 이벤트 자체에 전부 실어 보내, 컨슈머가 프로듀서에 대한 런타임 의존성 없이 동작합니다. 대신 이벤트가 커지고, 프로듀서의 내부 데이터 모델이 사실상 외부에 노출되어 스키마 진화 부담이 커지며 데이터 중복에 따른 최종 일관성을 감수해야 합니다.

항목 Notification State Transfer
페이로드 작음(ID) 큼(전체 상태)
결합도 동기 의존 독립적

 

같은 이벤트를 두 방식으로 설계한 예제
// Event Notification
{
  "eventType": "OrderCompleted",
  "orderId": "12345",
  "occurredAt": "2026-09-27T12:00:00Z"
}

// Event-Carried State Transfer
{
  "eventType": "OrderCompleted",
  "orderId": "12345",
  "occurredAt": "2026-09-27T12:00:00Z",
  "customerId": "cust-9981",
  "items": [{"sku": "SKU-001", "quantity": 2, "price": 15000}],
  "totalAmount": 30000,
  "shippingAddress": { "city": "서울", "zipcode": "04524" }
}

두 번째 방식이면 배송 서비스가 이 이벤트 하나만으로 배송 준비를 시작할 수 있습니다.

 

실무 포인트

컨슈머 수와 조회 패턴을 먼저 파악하세요. 컨슈머가 하나뿐이면 Notification으로 충분하지만, 여러 개고 독립적 가용성이 필요하면 State Transfer가 정당화됩니다.

혼합 전략도 흔합니다. 자주 필요한 핵심 필드는 이벤트에 포함하고 드문 상세 정보는 별도 API로 남겨두는 절충안이 있습니다.

주의 — Fat 이벤트를 선택했다면 내부 도메인 모델을 그대로 노출하지 말고, 이벤트 전용 DTO를 별도로 두어 내부 리팩터링이 컨슈머에 영향을 주지 않도록 해야 합니다.
