PostgreSQL 논리적 복제와 CDC 내부 동작 원리

DB·데이터 모델링

한 줄 요약 — Debezium 같은 CDC 도구는 PostgreSQL의 WAL을 논리적 디코딩 플러그인이 해석하고 Replication Slot이 읽기 위치를 관리하는 구체적인 파이프라인 위에서 동작합니다.

 

왜 내부 동작을 알아야 하는가

CDC 도구를 붙이면 신기하게도 변경이 실시간으로 이벤트로 쌓이는데, 많은 분들이 이를 블랙박스로 다룹니다. 이 내부 구조를 모르면 replication slot이 쌓여 디스크가 가득 차거나, 스키마 변경 후 커넥터가 죽는 사고를 원인도 모른 채 겪게 됩니다.

 

WAL과 논리적 디코딩

PostgreSQL은 모든 변경을 커밋 전에 WAL에 먼저 기록합니다. 논리적 복제는 이 WAL 레코드를 사람이 읽을 수 있는 논리적 변경으로 디코딩하는데, 이를 수행하는 것이 출력 플러그인(pgoutput, wal2json 등)입니다. Debezium은 이 플러그인을 통해 WAL을 읽고 자체 이벤트 포맷으로 변환해 Kafka Connect로 보냅니다.

Replication Slot — 상태를 기억하는 책갈피

논리적 디코딩만으로는 어디까지 읽었는지 알 수 없습니다. Replication Slot은 컨슈머가 마지막으로 확인한 WAL 위치를 서버에 영구히 기록해둡니다. 문제는 slot이 확인되지 않은 WAL을 서버가 절대 삭제하지 않는다는 점입니다. 컨슈머가 오랫동안 멈추면 WAL이 누적되어 디스크를 잠식하는 유명한 장애 패턴이 발생합니다.

구성 요소 역할
WAL 모든 변경의 원본 로그
출력 플러그인 WAL을 논리적 변경으로 디코딩
Replication Slot 읽기 위치 기록, 미확인 WAL 보존

 

Publication과 Slot 생성 예제
CREATE PUBLICATION debezium_pub FOR TABLE orders, order_items;

SELECT pg_create_logical_replication_slot('debezium_slot', 'pgoutput');

SELECT slot_name, active,
       pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
FROM pg_replication_slots;

lag_bytes가 계속 증가한다면 컨슈머가 slot을 제대로 소비하지 못하고 있다는 신호이므로, 이 값을 모니터링하는 것이 CDC 운영의 기본입니다.

 

실무 포인트

쓰지 않는 slot은 즉시 제거하세요. 커넥터를 폐기했는데 slot을 지우지 않으면 WAL이 무한정 쌓입니다.

DDL은 논리 복제의 약점입니다. 컬럼 추가·삭제는 기본적으로 스트림에 포함되지 않으므로, Debezium은 별도 스키마 히스토리로 이를 추적합니다.

주의 — 커넥터를 처음 붙이면 기존 데이터 전체를 읽어오는 초기 스냅샷 단계가 필요한데, 대용량 테이블에서는 상당한 I/O 부하를 유발하므로 저트래픽 시간대에 시작하는 것이 안전합니다.
