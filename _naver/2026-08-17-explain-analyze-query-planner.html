EXPLAIN ANALYZE 해부하기 — 쿼리 플래너가 남기는 단서 읽는 법

2026. 8. 17. · DB·데이터모델링

한 줄 요약 — EXPLAIN ANALYZE 출력에서 cost, rows, actual time, loops가 각각 무엇을 뜻하는지, 실행 계획 트리를 어떤 순서로 읽어야 하는지를 예제와 함께 정리했습니다.

 

왜 지금 EXPLAIN ANALYZE인가

인덱스를 걸었는데도 쿼리가 여전히 느리거나, 반대로 인덱스가 왜 안 타는지 궁금할 때 결국 마주치는 것이 EXPLAIN 출력입니다. 문제는 이 출력이 처음 보면 숫자와 노드 이름이 뒤섞인 트리일 뿐이라는 점입니다. "이 쿼리는 Seq Scan을 한다"까지는 읽어도 그게 왜 문제인지, 어느 줄을 먼저 고쳐야 하는지는 별개의 문제입니다.

인덱스 설계를 아무리 잘해도, 플래너가 그 인덱스를 실제로 쓰는지 확인하는 도구가 바로 EXPLAIN ANALYZE입니다. 이번 글에서는 인덱스 설계 이야기 대신, 그 설계가 실제로 쿼리 플래너에게 어떻게 받아들여지는지를 읽는 법에 집중해서 정리해보겠습니다.

 

핵심 개념: EXPLAIN과 EXPLAIN ANALYZE는 다른 도구입니다

EXPLAIN은 플래너가 세운 계획만 보여줍니다. 실제로 쿼리를 실행하지 않고, 통계 정보를 바탕으로 각 단계의 예상 비용과 예상 행 수만 추정합니다. 반면 EXPLAIN ANALYZE는 쿼리를 실제로 실행하면서 각 단계가 걸린 실제 시간과 실제로 처리한 행 수까지 함께 보여줍니다.

구분 EXPLAIN EXPLAIN ANALYZE
쿼리 실행 여부 실행하지 않음 실제로 실행함
보여주는 값 예상 cost, 예상 rows 예상값 + 실측 actual time·rows·loops
DML(INSERT/UPDATE/DELETE) 안전 실제로 데이터가 바뀔 수 있음

DML 문에 EXPLAIN ANALYZE를 쓰면 실제로 커밋될 수 있다는 점이 가장 흔한 실수입니다. 운영 DB에서 확인이 필요하면 트랜잭션을 열고 ROLLBACK으로 마무리하는 것이 안전합니다.

 

핵심 개념: 실행 계획은 트리이고, 안쪽부터 실행됩니다

실행 계획은 들여쓰기로 표현된 트리 구조입니다. 가장 안쪽(리프 노드)이 먼저 실행되어 그 결과가 바깥쪽 노드로 전달되므로, 읽는 순서는 출력 순서가 아니라 안에서 바깥으로입니다.

노드 유형 의미
Seq Scan 테이블 전체를 순차적으로 읽음
Index Scan 인덱스로 위치를 찾은 뒤 실제 행까지 접근
Index Only Scan 인덱스만으로 결과 반환(힙 접근 없음)
Nested Loop 바깥 결과의 각 행마다 안쪽을 반복 탐색
Hash Join 한쪽을 해시테이블로 만들고 다른 쪽과 매칭

 

핵심 개념: cost, rows, actual time — 각 숫자가 말하는 것

cost=시작..종료는 추정 비용이며 단위는 시간(ms)이 아니라 플래너 내부 상대값입니다. rows는 통계 정보로 추정한 행 수이고, actual time=시작..종료(EXPLAIN ANALYZE에서만 표시)는 실제로 걸린 시간(ms)입니다. loops는 이 노드가 몇 번 반복 실행됐는지를 나타내며, 1보다 크면 actual time은 1회 평균이므로 총 소요 시간은 actual time × loops로 다시 계산해야 합니다.

가장 중요한 습관은 rows(예상)와 actual rows(실측)를 비교하는 것입니다. 둘의 차이가 크면 통계가 최신 데이터 분포를 반영하지 못해 플래너가 잘못된 조인 방식이나 스캔 방식을 골랐을 가능성이 큽니다. 이 경우 통계 갱신(ANALYZE 명령)이 인덱스를 새로 만드는 것보다 먼저 시도할 조치입니다.

 

예제: 실행 계획 읽어보기

아래는 주문 테이블과 고객 테이블을 조인하는 쿼리와 그 실행 계획입니다.

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total_amount, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE c.grade = 'VIP';

Hash Join  (cost=54.00..1120.30 rows=820 width=48)
           (actual time=0.6..14.2 rows=795 loops=1)
  Hash Cond: (o.customer_id = c.id)
  ->  Seq Scan on orders o  (cost=0.00..820.00 rows=40000 width=24)
                            (actual time=0.02..8.1 rows=40000 loops=1)
  ->  Hash  (cost=42.50..42.50 rows=180 width=28)
            (actual time=0.5..0.5 rows=175 loops=1)
        ->  Index Scan using idx_customers_grade on customers c
              (cost=0.29..42.10 rows=180 width=28)
              (actual time=0.01..0.4 rows=175 loops=1)
              Index Cond: (grade = 'VIP')
Planning Time: 0.31 ms
Execution Time: 14.6 ms

이 계획에서 확인할 점은 두 가지입니다. 첫째, orders에는 인덱스 없이 Seq Scan이 걸리지만 예상(40000)과 실측(40000) rows가 일치해 통계는 정확합니다. 둘째, customers는 idx_customers_grade 인덱스를 타는 Index Scan이고 예상(180)과 실측(175)도 거의 일치합니다. 즉 이 쿼리에서 시간을 대부분 잡아먹는 건 orders 전체를 훑는 Seq Scan이며, orders가 앞으로 더 커질 걸 감안하면 조인 조건이나 자주 쓰는 WHERE 조건에 맞는 인덱스 추가를 검토할 지점이라는 것을 이 한 줄만으로 판단할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. BUFFERS 옵션을 항상 같이 켠다 — shared hit(캐시 적중)와 read(디스크 읽기) 횟수를 함께 확인
2. loops가 1보다 큰 노드는 곱해서 본다 — actual time만 보고 "빠르다"고 오판하기 쉬운 지점
3. Planning Time도 무시하지 않는다 — 파티션·통계 대상이 큰 테이블에서는 계획 수립 시간도 무시 못할 수 있음
4. 환경별 실측치를 그대로 비교하지 않는다 — 캐시 상태·동시 부하·하드웨어가 다르면 같은 쿼리도 시간이 달라짐
5. DML에는 트랜잭션으로 감싸서 실행 — ROLLBACK으로 마무리해 실수로 데이터가 바뀌는 것을 방지

 

마무리 — 3줄 요약

① EXPLAIN은 계획만, EXPLAIN ANALYZE는 실제 실행까지 하므로 DML에 함부로 쓰지 않습니다.
② 실행 계획은 트리이며 리프 노드부터 실행되고, cost는 추정치·actual time은 실측치·loops는 반복 횟수라는 점을 구분해서 읽습니다.
③ rows(예상)와 actual rows(실측)의 차이가 크면 통계 갱신부터 의심하는 것이 인덱스 재설계보다 먼저입니다.
