FID가 사라진 자리에 INP가 왔다 — Core Web Vitals 응답성 최적화 실전

2026. 8. 26. · 프론트엔드

한 줄 요약 — Core Web Vitals의 응답성 지표가 FID에서 INP(Interaction to Next Paint)로 완전히 교체됐습니다. 무엇을 측정하고, 어떤 코드 패턴이 INP를 악화시키는지, 어떻게 줄이는지 정리했습니다.

 

FID는 좋았는데 INP는 왜 나빠졌을까요

Core Web Vitals의 세 지표 중 응답성을 담당하던 FID(First Input Delay)는 이제 완전히 퇴역했고, 그 자리를 INP가 대체했습니다. 두 지표의 차이는 단순한 이름 교체가 아닙니다. FID는 첫 입력이 처리되기까지의 지연만 쟀지만, INP는 페이지 생애주기 전체에 걸쳐 발생하는 모든 상호작용 중 가장 느렸던 것을 기준으로 삼습니다. 첫 클릭은 빨랐지만 스크롤 후 나온 드롭다운을 열 때 500ms가 걸린다면, FID로는 잡히지 않았을 그 지연이 INP에서는 그대로 점수에 반영됩니다.

이 차이 때문에 "FID는 좋았는데 INP 도입 후 점수가 나빠졌다"는 사이트가 많았습니다. 특히 SPA처럼 페이지 전환 없이 오래 머무는 애플리케이션일수록 상호작용 총량이 많아 INP가 나쁘게 잡히기 쉽습니다.

 

핵심 개념 1 — INP는 세 구간의 합입니다

INP는 사용자가 상호작용을 시작한 시점부터 다음 프레임이 화면에 그려지기까지의 시간을 측정하며, 이 시간은 세 구간으로 나뉩니다.

구간 내용 흔한 지연 원인
Input Delay 이벤트 발생 후 핸들러 실행 시작까지 대기 메인 스레드가 긴 작업으로 점유됨
Processing Time 이벤트 핸들러 실행 자체 무거운 동기 연산, 불필요한 리렌더
Presentation Delay 핸들러 종료 후 다음 프레임 그리기까지 큰 DOM 변경, 레이아웃 스래싱

이 중 실무에서 가장 흔히 문제가 되는 것은 Input Delay입니다. 메인 스레드가 50ms 이상 걸리는 "긴 작업(long task)"으로 막혀 있으면, 그 작업이 끝날 때까지 클릭 이벤트 핸들러 자체가 시작되지 못합니다.

 

핵심 개념 2 — 긴 작업을 쪼개는 것이 첫 번째 해법입니다

메인 스레드를 막는 긴 작업을 발견했다면, 가장 효과적인 대응은 그 작업을 작은 단위로 쪼개 브라우저가 중간에 입력을 처리할 틈을 주는 것입니다. React 18 이상에서는 startTransition으로 긴급하지 않은 렌더링을 낮은 우선순위로 미룰 수 있습니다.

// 나쁜 예: 대량의 리스트를 한 번에 동기 렌더링해 긴 작업을 만든다
function handleSearch(query) {
  const filtered = hugeList.filter(item => item.name.includes(query));
  setResults(filtered);
}

// 개선: 무거운 렌더 결과를 낮은 우선순위로 표시
import { startTransition } from 'react';

function handleSearch(query) {
  setSearchInput(query); // 입력창은 즉시 업데이트(긴급)

  startTransition(() => {
    const filtered = hugeList.filter(item => item.name.includes(query));
    setResults(filtered); // 낮은 우선순위로 스케줄링
  });
}

startTransition으로 감싼 업데이트는 더 급한 입력이 들어오면 중단·재시작될 수 있어, 사용자가 입력하는 동안 메인 스레드가 결과 렌더링에 발이 묶이지 않습니다.

 

실무 도입 시 이것만은 챙기세요
1. 이벤트 핸들러 안의 동기 연산을 의심하세요 — 대량 배열 정렬, JSON 파싱, 동기 API 호출은 Processing Time을 그대로 늘립니다. 가능하면 웹 워커로 옮기거나 결과를 캐시하세요.
2. 서드파티 스크립트의 이벤트 리스너를 점검하세요 — 광고·분석 스크립트가 전역 click 리스너를 걸어두면 내 코드와 무관하게 INP가 나빠집니다. DevTools Performance 패널에서 Long Task 콜스택을 확인하세요.
3. 측정은 필드 데이터를 우선하세요 — 랩 환경에서 빠른 상호작용도 저사양 기기에서는 느릴 수 있습니다. CrUX나 자체 RUM으로 실제 분포를 확인하세요.

 

마무리 — 3줄 요약

① INP는 FID와 달리 페이지 생애주기 전체의 모든 상호작용 중 가장 느렸던 것을 기준으로 삼아, SPA에서 특히 나빠지기 쉽습니다.
② INP는 Input Delay·Processing Time·Presentation Delay 세 구간의 합이며, 메인 스레드를 막는 긴 작업이 가장 흔한 원인입니다.
③ 긴 작업을 startTransition이나 스케줄링 API로 쪼개고, 서드파티 스크립트 영향을 점검하며, 필드 데이터로 실제 체감을 확인해야 합니다.
