@Transactional은 왜 조용히 배신하는가 — 전파, self-invocation, rollbackFor 실전 정리

2026. 8. 23. · 백엔드

한 줄 요약 — 스프링의 @Transactional이 적용되지 않거나 의도와 다르게 롤백되는 3대 함정, 즉 self-invocation, 체크 예외와 rollbackFor, readOnly의 실체를 프록시 동작 원리부터 실전 대안까지 정리했습니다.

 

왜 이 어노테이션은 '조용히' 실패할까요

@Transactional은 스프링에서 가장 많이 쓰이는 어노테이션 중 하나지만, 동시에 "분명히 붙였는데 동작하지 않는" 사고가 가장 자주 나는 어노테이션이기도 합니다. 문제는 이 어노테이션이 실패할 때 컴파일 에러도, 경고 로그도 없이 조용히 실패한다는 점입니다. 트랜잭션이 걸린 줄 알았던 메서드가 사실은 트랜잭션 없이 돌고 있었고, 그 사실을 데이터 정합성이 깨진 뒤에야 알게 되는 경우가 많습니다.

이런 사고의 뿌리는 대부분 하나로 수렴합니다. @Transactional은 마법이 아니라 프록시 기반 AOP라는 것입니다. 스프링은 대상 빈을 프록시 객체로 감싸고, 외부에서 들어오는 호출을 프록시가 가로채 트랜잭션을 시작하고 커밋하거나 롤백합니다. 이 구조를 이해하면 self-invocation이 왜 안 되는지, 전파 옵션이 왜 필요한지, rollbackFor를 언제 써야 하는지가 한 줄로 꿰어집니다.

 

핵심 개념 1 — 전파(Propagation) 옵션, 언제 무엇을 써야 할까요

트랜잭션 전파는 "이미 트랜잭션이 진행 중인 상태에서 또 다른 트랜잭션 메서드가 호출되면 어떻게 할 것인가"에 대한 정책입니다. 기본값인 REQUIRED는 기존 트랜잭션이 있으면 합류하고 없으면 새로 만듭니다. 대부분의 경우 이 기본값이 정답이지만, 나머지 옵션이 필요한 순간도 분명히 있습니다.

전파 옵션 기존 트랜잭션이 있을 때 대표 사용처
REQUIRED (기본) 합류 일반적인 서비스 로직
REQUIRES_NEW 기존 것을 일시 중단하고 새 트랜잭션 시작 감사 로그·이력 저장 (본 작업이 롤백돼도 남겨야 할 때)
NESTED 세이브포인트 생성 (부분 롤백 가능) JDBC 세이브포인트 지원 환경의 부분 실패 허용
MANDATORY 합류 (없으면 예외 발생) "반드시 트랜잭션 안에서만 호출"이라는 계약 강제
NOT_SUPPORTED 일시 중단 후 트랜잭션 없이 실행 트랜잭션이 오히려 해가 되는 장시간 조회

 

가장 오해가 많은 것은 REQUIRES_NEW입니다. "독립 트랜잭션"이라는 말 때문에 가볍게 생각하기 쉽지만, 실제로는 바깥 트랜잭션의 커넥션을 잡아둔 채로 새 커넥션을 하나 더 가져옵니다. 커넥션 풀이 작은 환경에서 REQUIRES_NEW가 중첩되면 커넥션 고갈로 전체 서비스가 멈출 수 있습니다. "롤백돼도 남아야 하는 기록"이라는 명확한 요구가 있을 때만 쓰시는 것이 안전합니다.

또 하나의 고전적인 함정은 REQUIRED끼리의 합류에서 나옵니다. 내부 메서드에서 예외가 발생해 트랜잭션이 rollback-only로 마킹됐는데 바깥 메서드가 그 예외를 catch로 삼켜버리면, 바깥은 정상 커밋을 시도하다가 UnexpectedRollbackException을 만나게 됩니다. "예외를 잡았는데 왜 롤백되지?"라는 질문의 답은, 두 메서드가 물리적으로 같은 트랜잭션 하나를 공유하고 있기 때문입니다.

 

핵심 개념 2 — self-invocation, 어노테이션이 무시되는 대표 사례

가장 흔한 함정부터 보겠습니다. 같은 클래스 안에서 this로 자기 자신의 @Transactional 메서드를 부르면, 프록시를 거치지 않기 때문에 트랜잭션이 적용되지 않습니다. 외부에서 직접 부르면 프록시가 가로채 트랜잭션을 열지만, 내부 호출은 원본 객체의 메서드를 직접 부르는 것이라 어노테이션이 개입할 틈이 없습니다. private 메서드에 붙인 @Transactional이 무시되는 것도 같은 원리입니다.

@Service
public class OrderService {

    public void processOrders(List<Long> ids) {
        for (Long id : ids) {
            // this.saveOrder(...) — 프록시를 우회하는 내부 호출!
            // @Transactional이 완전히 무시됩니다
            saveOrder(id);
        }
    }

    @Transactional
    public void saveOrder(Long id) {
        // 트랜잭션이 걸려 있을 것이라 믿지만, 위 경로로 오면 없습니다
    }
}

 

 

올바른 대안은 두 가지입니다. 첫째, 트랜잭션 경계가 필요한 로직을 별도 빈으로 분리해 프록시를 거치는 외부 호출로 만드는 것입니다. 둘째, 선언적 방식 대신 TransactionTemplate으로 트랜잭션 경계를 코드로 명시하는 것입니다. 아래는 두 번째 방식의 예시입니다.

@Service
public class OrderService {

    private final TransactionTemplate txTemplate;
    private final OrderRepository orderRepository;

    public OrderService(TransactionTemplate txTemplate,
                        OrderRepository orderRepository) {
        this.txTemplate = txTemplate;
        this.orderRepository = orderRepository;
    }

    public void processOrders(List<Long> ids) {
        for (Long id : ids) {
            // 건별로 트랜잭션 경계를 명시적으로 엽니다
            txTemplate.executeWithoutResult(status ->
                orderRepository.save(new Order(id)));
        }
    }
}

AopContext.currentProxy()로 자기 프록시를 꺼내 호출하는 우회법도 있지만, 별도 설정이 필요하고 코드가 AOP 구현에 결합되므로 구조 개선이 가능한 상황에서는 권하지 않습니다.

 

핵심 개념 3 — 체크 예외는 기본적으로 롤백되지 않습니다

스프링의 기본 정책은 언체크 예외(RuntimeException, Error)만 롤백하고, 체크 예외는 커밋하는 것입니다. "체크 예외는 호출자가 복구할 수 있는 비즈니스 상황"이라는 오래된 가정이 깔려 있는데, 실무 코드가 항상 이 가정대로 작성되지는 않는다는 것이 문제입니다. 예를 들어 파일을 읽어 DB에 저장하는 메서드에서 중간에 IOException이 던져지면, 예외 이전에 저장한 데이터는 그대로 커밋되는 부분 커밋 사고가 납니다.

@Transactional  // IOException이 던져져도 여기까지의 DB 변경은 커밋됩니다!
public void importAndSave(MultipartFile file) throws IOException {
    memberRepository.save(parseHeader(file));
    parseBody(file);  // IOException 발생 가능 — 그래도 위 save는 커밋
}

// 해결: 롤백 범위를 명시적으로 넓힙니다
@Transactional(rollbackFor = Exception.class)
public void importAndSave(MultipartFile file) throws IOException { ... }

근본적으로는 도메인 예외를 RuntimeException 기반으로 설계하는 것이 좋고, 외부 라이브러리의 체크 예외를 통과시키는 메서드라면 rollbackFor를 명시하는 습관이 안전합니다.

 

핵심 개념 4 — readOnly는 쓰기 방지 장치가 아닙니다

@Transactional(readOnly = true)는 이름 때문에 "쓰기를 막아주는 안전장치"로 오해받지만, 실제로는 최적화 힌트입니다. JPA(Hibernate)에서는 플러시 모드가 조정되고 더티 체킹 비용이 줄어 조회 성능과 메모리에 이득이 있고, 리더-라이터 분리 환경에서는 라우팅 데이터소스가 이 플래그를 보고 읽기 요청을 레플리카로 보내는 기준으로 사용합니다.

뒤집어 말하면, readOnly = true를 붙였다고 해서 쓰기 SQL이 항상 차단된다는 보장은 없습니다(동작은 DB와 드라이버에 따라 다릅니다). 반대로 레플리카 라우팅 환경에서 습관적으로 이 플래그를 빼먹으면 조회 트래픽이 전부 프라이머리로 몰리고, 쓰기 직후 조회에 잘못 붙이면 복제 지연 때문에 방금 쓴 데이터가 안 보이는 사고로 이어집니다. 조회 전용 메서드에는 일관되게 붙이되, "쓰기 방지"가 목적이라면 DB 계정 권한 분리로 해결하셔야 합니다.

 

실무 도입 시 이것만은 챙기세요
1. 트랜잭션 경계는 진입점에서 한 번만 선언하세요 — 서비스 계층의 공개 메서드에 선언하고, 내부 헬퍼 메서드에는 붙이지 마세요. 붙여봐야 self-invocation으로 무시되거나 혼란만 줍니다.
2. 트랜잭션이 실제로 걸렸는지 확인하는 습관을 들이세요 — 개발 중에는 org.springframework.transaction.interceptor 로거를 TRACE로 올려 시작/커밋 로그를 확인하거나, TransactionSynchronizationManager.isActualTransactionActive()로 테스트에서 검증할 수 있습니다.
3. 트랜잭션 안에서 외부 API를 호출하지 마세요 — HTTP 호출이나 메시지 발행이 트랜잭션 안에 들어오면 커넥션 점유 시간이 외부 지연에 묶입니다. 커밋 후 처리가 필요하면 @TransactionalEventListener(phase = AFTER_COMMIT)를 사용하세요.

 

마무리 — 3줄 요약

① @Transactional은 프록시 기반이므로 같은 빈 내부 호출(self-invocation)과 private 메서드에는 적용되지 않으며, 빈 분리 또는 TransactionTemplate으로 해결해야 합니다.
② 체크 예외는 기본적으로 롤백되지 않으므로 rollbackFor를 명시해야 하고, REQUIRES_NEW는 커넥션을 추가로 점유한다는 비용을 알고 써야 합니다.
③ readOnly = true는 쓰기 방지 장치가 아니라 플러시 생략과 레플리카 라우팅을 위한 최적화 힌트이므로, 조회 메서드에 일관되게 붙이되 안전장치로 믿어서는 안 됩니다.
