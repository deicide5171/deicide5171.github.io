"스펙만 써주면 에이전트가 코드는 다 짤게요"라는 말의 함정 — Spec-Driven Development 성숙도 3단계와 Spec Drift 거버넌스

dev-strategy

한 줄 요약 — '스펙 먼저 쓰고 에이전트한테 시키자'는 도구 설치 문제가 아니라, 스펙을 어느 성숙도 단계로 운영할지 정하는 거버넌스 문제입니다. GitHub Spec Kit의 급성장과 Thoughtworks의 spec-first/spec-anchored/spec-as-source 구분을 기준으로 spec drift를 막는 설계를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"우리 팀도 스펙 먼저 쓰고 에이전트한테 구현시키자. Spec Kit 깔면 되는 거 아니야?" 요즘 팀 리드에게서 자주 나오는 말입니다. 그런데 이 말에는 숨은 전제가 하나 있습니다 — 스펙 문서를 만드는 일과 스펙을 계속 맞는 상태로 유지하는 일을 같은 문제로 취급한다는 것입니다. 도구를 설치해 스펙 한 장을 뽑아내는 것은 하루면 끝나지만, 그 스펙이 6개월 뒤에도 실제 코드를 설명하고 있을지는 전혀 다른 질문입니다.

GitHub의 Spec Kit은 2026년 8월 21일 v1.0.0을, 9월 10일에는 v1.0.6을 내놓으며 스펙 주도 개발(SDD) 도구 중 가장 빠르게 퍼졌습니다. 그런데 Thoughtworks Technology Radar 2026은 엔지니어 Birgitta Böckeler의 3단계 구분을 인용하며 Spec Kit을 명확히 spec-first 단계로만 분류합니다 — "시간이 지나도 spec-anchored는 아니다"라는 단서를 달아서입니다. 이 구분을 모르고 도구만 들이면, 몇 달 뒤 스펙 문서는 아무도 안 보는 장식품이 되는 "Spec Drift"가 조용히 시작됩니다.

 

전체 시스템에서의 위치 — 세 가지 성숙도

spec-first는 스펙을 일회성 뼈대로 씁니다 — 에이전트가 스펙을 읽고 코드를 생성하면, 이후부터는 사람이 코드를 직접 편집·소유하고 스펙은 다시 들여다보지 않습니다. spec-anchored는 스펙이 시스템이 살아 있는 동안 계속 진실의 원천으로 남습니다. spec-as-source는 스펙이 산출물로 직접 컴파일됩니다 — Tessl 같은 도구가 시도 중이지만 2026년 기준으로는 여전히 베타 수준입니다.

Spec Kit 같은 인기 도구는 spec-first만 자동으로 해주고, spec-anchored로 가는 길은 아무것도 대신해주지 않습니다. Thoughtworks는 또 다른 함정도 지적합니다 — 에이전트가 스펙을 더 잘 지키게 하려고 프로젝트 지시문을 계속 추가하면 오히려 성능이 떨어지는 컨텍스트 부패(context rot)가 나타난다는 것입니다.

 

선택의 트레이드오프
기준 spec-first spec-anchored spec-as-source
스펙의 생애주기 생성 시점에만 유효 시스템 생애 내내 원천 스펙이 곧 산출물
사후 동기화 장치 없음 — 자연 발산 CI가 diff 지속 검증 컴파일 자체가 동기화
필요 인프라 도구 설치만으로 충분 소유권 메타데이터, diff 게이트 대부분 베타, 자체 구축 위험
적합한 조직 1인 또는 짧은 프로토타입 다인 팀 + 멀티세션 작업 아직 대부분 조직에 이름

 

전환점을 가르는 질문은 하나입니다 — "이 작업이 여러 사람, 여러 세션에 걸쳐 이어지고, 나중에 누군가 감사 가능한 인수인계 문서가 필요한가?" 답이 "그렇다"면 spec-first로는 이미 부족합니다.

 

예제 코드:

# .github/workflows/spec-drift-check.yml (개념 예시)
- name: Spec vs Code Drift Check
  run: |
    # 변경된 코드 파일이 참조하는 스펙 섹션의 최종 수정일과
    # 코드 커밋 시각을 비교해, 스펙이 더 오래됐으면 리뷰를 블로킹한다.
    python3 scripts/check_spec_freshness.py \
      --spec-dir docs/specs \
      --max-staleness-days 14

 

주의 — Spec Kit 같은 도구의 셸 실행 단계는 로컬 사용자 권한으로 그대로 돌아갑니다. 여러 팀이 같은 저장소에서 자동화를 돌리려면 자체 샌드박스·권한 레이어를 따로 얹어야 합니다. 에이전트의 스펙 준수율을 높이려고 지시문을 무한정 누적하면 컨텍스트 부패로 오히려 성능이 떨어지니, 지시문은 주기적으로 가지치기하세요. spec-as-source는 2026년 기준 베타 단계이므로 핵심 아닌 작은 모듈에서만 실험하세요.

 

정리

"스펙 먼저 쓰자"는 도구 선택이 아니라 성숙도 선택입니다. 다인 팀·여러 세션에 걸친 작업·감사 가능한 인수인계가 필요해지는 순간이 spec-anchored로 전환해야 하는 신호입니다. 이를 지원하는 표준 도구는 아직 없으므로 CI 기반 drift 체크와 소유권 메타데이터를 직접 설계해야 하며, spec-as-source는 아직 성급한 베팅입니다.
