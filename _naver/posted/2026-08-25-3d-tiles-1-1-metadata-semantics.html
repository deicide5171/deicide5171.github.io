3D 모델에 '이 건물은 몇 층인가'를 묻는다 — 3D Tiles 1.1의 메타데이터·시맨틱스 확장

2026. 8. 25. · GIS

한 줄 요약 — 3D Tiles가 렌더링을 위한 LOD 스트리밍 표준을 넘어, 각 타일 지오메트리에 건물 층수·용도 같은 구조화된 속성을 부여하는 1.1의 메타데이터·시맨틱스 확장을 정리했습니다.

 

렌더링만 잘 되는 3D 모델은 정교한 배경 그림입니다

도시 전체 3D 모델을 웹에서 매끄럽게 렌더링하는 문제는 3D Tiles 표준과 CesiumJS의 LOD 스트리밍 구조로 상당 부분 해결됐습니다. 그런데 렌더링이 잘 된다고 해서 그 3D 모델이 곧바로 쓸모 있는 디지털 트윈이 되는 것은 아닙니다. 화면에 예쁘게 그려진 건물 메시를 클릭했을 때 "이 건물은 몇 층이고 준공 연도는 언제인가"를 물어볼 수 없다면, 그 3D 모델은 사실 정교한 배경 그림에 가깝습니다.

3D Tiles 1.1은 이 문제를 정면으로 다룹니다. 타일 안의 지오메트리 하나하나에 구조화된 속성을 붙이고, 그 속성으로 3D 공간을 실제 데이터베이스처럼 질의할 수 있게 만드는 메타데이터·시맨틱스 확장을 정식 명세에 담았습니다.

 

핵심 개념 1 — 이전에는 메타데이터가 부가 확장이었습니다

3D Tiles 1.0 시절에도 3DTILES_batch_table이라는 확장으로 속성 데이터를 붙이는 것이 가능했지만, 표준의 정식 명세가 아니라 벤더 확장으로 존재해서 뷰어마다 지원 여부가 제각각이었고 스키마 검증도 부족했습니다. 3D Tiles 1.1은 OGC 표준으로 정식 승격되면서 이 메타데이터 체계를 gLTF의 EXT_structural_metadata, EXT_mesh_features와 정렬시켰습니다.

 

핵심 개념 2 — 시맨틱 클래스와 프로퍼티 테이블

메타데이터 확장의 핵심은 스키마-클래스-프로퍼티의 조합입니다. 스키마에서 "Building" 클래스를 정의하고 height, floors, yearBuilt, usage 같은 프로퍼티를 갖도록 선언합니다. 실제 데이터는 프로퍼티 테이블에 컬럼형으로 저장되고, 각 지오메트리는 이 테이블의 특정 행을 가리키는 방식으로 값이 연결됩니다.

이 구조 덕분에 "20층 이상, 준공 20년 이상 된 건물만 강조 표시"처럼 렌더링과 무관하게 순수하게 속성 기반의 질의·필터링이 가능해집니다.

 

핵심 개념 3 — EXT_mesh_features, 메시의 어느 부분이 어느 개체인가

건물 하나가 벽, 창문, 지붕 등 여러 서브 파트로 이뤄진 경우, EXT_mesh_features는 gLTF 메시의 각 프리미티브에 feature ID를 부여해 어떤 개체에 속하는지 식별합니다. 이 feature ID가 프로퍼티 테이블의 행 인덱스와 연결되면서, 렌더링 메시 → 개체 식별 → 구조화된 속성이라는 전체 파이프라인이 완성됩니다.

구분 3D Tiles 1.0 3D Tiles 1.1
표준화 수준 벤더 확장 OGC 정식 명세
개체 식별 batch ID EXT_mesh_features

 

예제 — 3D Tiles 메타데이터 스키마 정의
{
  "schema": {
    "classes": {
      "building": {
        "properties": {
          "height": { "type": "SCALAR", "componentType": "FLOAT32" },
          "floors": { "type": "SCALAR", "componentType": "UINT8" },
          "usage": { "type": "ENUM", "enumType": "usageType" }
        }
      }
    }
  }
}

CesiumJS에서는 Cesium3DTileFeature.getProperty('floors')로 즉시 조회하고, 스타일 표현식에서 ${floors} >= 20 같은 조건을 직접 넣을 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. 속성을 타일 생성 파이프라인 초기부터 설계하세요 — BIM, CityGML 원본 속성이 변환 과정에서 누락되지 않도록 스키마를 미리 정의하세요.
2. 프로퍼티 테이블 크기와 스트리밍 성능을 함께 고려하세요 — 자주 조회되는 속성만 테이블에 넣고 상세 정보는 별도 API로 지연 조회하세요.
3. 스타일링과 속성 필터링을 분리해서 설계하세요 — 목적이 다르므로 UI상 별개 조작으로 노출하는 것이 좋습니다.

 

마무리 — 3줄 요약

① 3D Tiles 1.1은 벤더 확장이던 배치 테이블 방식을 OGC 정식 명세로 승격시키고 gLTF와 메타데이터 모델을 정렬시켰습니다.
② 스키마-클래스-프로퍼티 테이블 구조로 지오메트리에 타입이 있는 속성을 부여해 3D 공간을 속성 질의 대상으로도 다룰 수 있습니다.
③ EXT_mesh_features가 메시 개체를 식별해 프로퍼티 테이블과 연결하며 디지털 트윈 파이프라인이 완성됩니다.
