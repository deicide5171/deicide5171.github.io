WebGL 다음은 WebGPU — deck.gl 렌더러 마이그레이션 실전

2026. 8. 24. · GIS

한 줄 요약 — 대용량 포인트클라우드 렌더링에서 WebGL의 구조적 한계를 짚고, deck.gl이 luma.gl 추상화 계층을 통해 WebGPU 렌더러로 전환하는 배경과 실무 고려사항을 정리했습니다.

 

WebGL의 구조적 한계

수백만 포인트를 그리는 3D 웹 지도에서 WebGL의 병목은 렌더링 자체보다 CPU-GPU 사이의 커맨드 전달 오버헤드와, 필터링·집계 같은 범용 연산을 GPU에서 직접 할 수 없다는 구조적 한계에서 옵니다.

WebGPU는 이 문제를 겨냥해 설계된 차세대 브라우저 그래픽 API입니다. 명령형 상태 머신 대신 커맨드 버퍼 기반의 명시적 API를 쓰고, 컴퓨트 셰이더를 네이티브로 지원해 범용 GPU 연산도 브라우저에서 실행할 수 있습니다. deck.gl은 자체 GPU 추상화 계층인 luma.gl을 통해 이 새 렌더러로의 전환을 점진적으로 지원하고 있습니다.

 

핵심 개념 1 — WebGL과 WebGPU의 아키텍처 차이

WebGL은 전역 상태를 바인딩하고 그리는 명령형 스타일이며, 상태 전환 하나하나가 드라이버 검증을 거치므로 CPU 오버헤드가 누적됩니다. WebGPU는 커맨드를 미리 인코딩해 커맨드 버퍼로 한 번에 제출하는 방식을 쓰고, 파이프라인 상태를 사전에 컴파일해두고 재사용할 수 있어 검증 비용이 크게 줄어듭니다.

 

 

핵심 개념 2 — WebGL vs WebGPU 비교
구분 WebGL WebGPU
API 스타일 명령형 상태 머신 커맨드 버퍼 기반
컴퓨트 셰이더 미지원 네이티브 지원
브라우저 지원 사실상 전 브라우저 확대 중

 

deck.gl 관점에서 WebGPU의 실질적 이득은 대용량 레이어에서 두드러집니다. 컴퓨트 셰이더로 뷰포트 밖 포인트를 GPU에서 미리 걸러내거나 집계 연산을 GPU로 옮기면 CPU 쪽 병목이 크게 줄어듭니다.

 

예제 — deck.gl에서 WebGPU 디바이스 지정
import { Deck } from '@deck.gl/core';

const deck = new Deck({
  deviceProps: {
    type: 'webgpu', // 'webgl'로 두면 기존 방식 유지
  },
  initialViewState: {
    longitude: 127.0, latitude: 37.5, zoom: 10
  },
  layers: [
    new PointCloudLayer({
      id: 'point-cloud',
      data: 'https://example.com/large-pointcloud.bin',
      getPosition: d => d.position,
      pointSize: 2
    })
  ]
});

deviceProps.type을 명시하지 않으면 luma.gl은 브라우저 지원 여부를 감지해 WebGPU를 우선 시도하고 지원하지 않으면 WebGL로 자동 폴백하는 방식을 지향합니다.

 

실무 도입 시 이것만은 챙기세요
1. 브라우저 지원 현황을 배포 전에 반드시 재확인하세요 — 지원하지 않는 브라우저를 위한 WebGL 폴백 경로는 항상 유지해야 합니다.
2. luma.gl과 deck.gl의 호환 매트릭스를 확인하세요 — 두 라이브러리 모두 활발히 개발 중이라 마이너 버전 간에도 API가 바뀔 수 있습니다.
3. 성능 이득은 데이터 규모와 레이어 종류에 따라 다릅니다 — 실제 프로덕션 데이터 규모로 벤치마크한 뒤 전환 여부를 결정하세요.

 

마무리 — 3줄 요약

① WebGPU는 커맨드 버퍼 기반 API와 네이티브 컴퓨트 셰이더 지원으로 WebGL의 구조적 한계를 해결합니다.
② deck.gl은 luma.gl 추상화 계층을 통해 두 렌더러를 모두 지원하며, 대용량 포인트클라우드 레이어에서 이득이 가장 큽니다.
③ 브라우저 지원 현황과 라이브러리 호환성을 배포 시점마다 재확인하고, 실제 벤치마크 후 전환을 결정하는 것이 중요합니다.
