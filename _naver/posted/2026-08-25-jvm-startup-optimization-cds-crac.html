네이티브 이미지 없이 JVM 시작 시간 줄이기 — AppCDS와 CRaC

2026. 8. 25. · 백엔드

한 줄 요약 — GraalVM 네이티브 이미지로 전환하지 않고도 순수 JVM에서 시작 시간을 줄이는 AppCDS(클래스 로딩 캐시)와 CRaC(체크포인트/복원) 방식을 비교했습니다.

 

몇 초의 시작 시간이 스케일링 속도를 깎아먹습니다

서버리스나 쿠버네티스 환경에서 파드를 스케일 아웃할 때마다 JVM이 클래스를 로딩하고 JIT 컴파일을 워밍업하는 데 수 초가 걸리면, 그 몇 초가 트래픽 급증 대응 속도를 그대로 깎아먹습니다. 가장 화끈한 해법은 GraalVM 네이티브 이미지로 AOT 컴파일하는 것이지만, 리플렉션·동적 프록시가 많은 기존 Spring 애플리케이션을 호환시키는 작업은 결코 가볍지 않습니다.

네이티브 이미지로 가지 않고도 순수 JVM 위에서 시작 시간을 단축하는 방법이 두 가지 있습니다. 클래스 로딩 단계를 캐시하는 AppCDS와, 애플리케이션이 완전히 초기화된 상태를 스냅숏으로 저장했다가 복원하는 CRaC입니다.

 

핵심 개념 1 — AppCDS, 클래스 로딩과 검증을 미리 끝내둡니다

JVM 시작 시간의 상당 부분은 클래스 파일을 읽고 파싱하고 바이트코드를 검증하는 과정에서 소모됩니다. AppCDS(Application Class-Data Sharing)는 애플리케이션 클래스와 의존 라이브러리 클래스까지 미리 아카이브(.jsa 파일)로 만들어 메모리 매핑으로 공유하는 기능입니다. 이후 실행에서는 이 아카이브를 매핑하기만 하면 되므로 클래스 파싱·검증 비용이 크게 줄어듭니다. JDK 19부터는 -XX:+AutoCreateSharedArchive 옵션으로 아카이브 생성·갱신을 JVM이 자동 관리해줍니다.

 

핵심 개념 2 — CRaC, 실행 중인 프로세스 자체를 스냅숏합니다

CRaC는 접근 방식이 근본적으로 다릅니다. 애플리케이션이 완전히 부팅되고 워밍업까지 끝난 시점의 JVM 프로세스 전체 상태를 리눅스 체크포인트 기능(CRIU)으로 통째로 저장합니다. 이후 컨테이너를 새로 띄울 때는 그 스냅숏을 복원하기만 하면, 이미 한참 실행되어 워밍업이 끝난 프로세스가 그 자리에서 이어 실행되는 것처럼 동작합니다. 다만 체크포인트 시점에 열려 있던 소켓·파일 핸들을 애플리케이션이 직접 정리하고 복원 후 재개하는 협조가 필요합니다.

 

핵심 개념 3 — 세 가지 접근 비교
구분 AppCDS CRaC
접근 방식 클래스 로딩 결과 캐시 프로세스 전체 상태 스냅숏
시작 시간 개선 중간 큼(수십ms대 가능)
코드 호환성 거의 그대로 체크포인트 훅 대응 필요

 

예제 — AppCDS 아카이브 생성과 CRaC 체크포인트/복원
# AppCDS: 클래스 로딩 목록 기록
java -XX:ArchiveClassesAtExit=app-cds.jsa -jar app.jar

# AppCDS: 아카이브를 사용해 구동
java -XX:SharedArchiveFile=app-cds.jsa -jar app.jar

# CRaC: 체크포인트 생성
java -XX:CRaCCheckpointTo=/checkpoint/app -jar app.jar
jcmd <pid> JDK.checkpoint

# CRaC: 체크포인트로부터 복원 (수십 ms 내 기동)
java -XX:CRaCRestoreFrom=/checkpoint/app

 

실무 도입 시 이것만은 챙기세요
1. CRaC 도입 전 체크포인트-복원 훅을 반드시 점검하세요 — DB 커넥션, 파일 디스크립터처럼 그대로 복원하면 안 되는 리소스는 org.crac.Resource 인터페이스로 명시적으로 처리해야 합니다.
2. AppCDS 아카이브는 배포 파이프라인의 일부로 관리하세요 — 코드나 의존성이 바뀌면 아카이브도 다시 만들어야 합니다.
3. 컨테이너 이미지 크기와 시작 시간을 함께 보세요 — CRaC 스냅숏 파일은 힙 크기에 비례해 커질 수 있습니다.

 

마무리 — 3줄 요약

① AppCDS는 클래스 로딩·검증만 캐시하는 저위험·저효과 접근이고, CRaC는 프로세스 전체를 스냅숏하는 고효과·고관리비용 접근입니다.
② CRaC는 체크포인트 시점의 소켓·파일 상태를 애플리케이션이 직접 정리·재개해야 하는 협조형 생명주기가 필요합니다.
③ 두 방식 모두 GraalVM 네이티브 이미지로 전환하기 어려운 기존 JVM 애플리케이션의 현실적인 대안이며, 병행해서 쓸 수 있습니다.
