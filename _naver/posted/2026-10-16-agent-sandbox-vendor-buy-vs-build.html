에이전트가 짠 코드, 어디서 돌릴 것인가 — 멀티테넌트 샌드박스 직접 구축 vs 벤더 위탁

시스템 설계

한 줄 요약 — "사용자 요구사항으로 에이전트가 코드를 직접 짜고 실행까지 하게 해주세요, 근데 다른 사용자 데이터는 못 보게 해주세요"라는 요구는 격리 기술 선택이 아니라 '이 격리층을 내가 운영할 것인가 벤더에게 맡길 것인가'라는 빌드 vs 바이 판단입니다. E2B·Daytona·Modal 같은 샌드박스 SaaS와 자체 구축을 가르는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"사용자가 입력한 요구사항으로 에이전트가 코드를 직접 짜고 바로 실행까지 보여주세요. 근데 당연히 다른 사용자 코드나 데이터는 서로 못 보게 해주세요." AI 코딩 어시스턴트, 데이터 분석 에이전트, 노코드 자동화 플랫폼을 만드는 팀이면 반드시 마주치는 요구입니다. 이 한 문장은 두 개의 설계 질문으로 쪼개집니다. 하나는 "어떤 격리 기술을 쓸 것인가"이고, 다른 하나는 훨씬 덜 다뤄지는 질문 — "이 격리 인프라 자체를 내가 운영할 것인가, 그걸 서비스로 파는 벤더에게 맡길 것인가"입니다.

2026년 들어 E2B, Daytona, Modal, Vercel Sandbox 같은 "에이전트 코드 실행 전용" 샌드박스 SaaS가 빠르게 성숙했습니다. 모두 격리 기술 자체는 검증된 걸 쓰지만, 콜드 스타트 속도·세션 재개 방식·과금 모델·셀프호스팅 가능 여부에서 전혀 다른 선택지를 제공합니다.

 

핵심 개념 — 격리 기술은 이미 전제조건이다

컨테이너 하나로는 커널을 호스트와 공유하기 때문에 여러 테넌트의 코드를 신뢰 경계 없이 같은 머신에서 돌릴 수 없습니다. 그래서 멀티테넌트 코드 실행 서비스는 거의 예외 없이 Firecracker microVM 또는 gVisor 위에 올라갑니다. 이 선택은 이미 벤더들이 내려놓은 결정입니다 — 빌더가 실제로 내려야 하는 결정은 그 위 레이어입니다.

 

벤더마다 다른 건 운영 모델이다
비교 축 자체 구축 샌드박스 SaaS
콜드 스타트 직접 최적화 필요 스냅숏 기반 수백 ms급
멀티턴 세션 재개 직접 구현 필요 대부분 네이티브 지원
데이터 주권 인프라 직접 통제 BYOC 옵션 유무 확인 필요
비용 구조 고정 인프라비+인건비 실행 시간 종량제

 

멀티턴 세션 재개 기능은 특히 자체 구현 비용이 큽니다. 스냅숏을 언제·어떻게 저장하고, 몇 분 뒤 다시 복원할 때 상태 일관성을 어떻게 보장할지가 생각보다 까다롭습니다. 이 기능이 핵심 요구사항이라면 벤더 위탁 쪽으로 저울이 기웁니다.

 

전체 시스템에서의 위치

 

에이전트 오케스트레이터는 LLM이 생성한 코드를 직접 실행하지 않습니다. "코드를 실행해달라"는 요청을 샌드박스 프로비저닝 레이어에 위임하고, 이 레이어가 테넌트 ID를 기준으로 격리된 실행 환경을 할당합니다. 이 프로비저닝 레이어가 자체 구축이냐 벤더 API 호출이냐는 오케스트레이터 입장에서는 인터페이스 차이일 뿐이지만, 운영 조직 입장에서는 완전히 다른 팀과 비용 구조를 필요로 합니다.

 

선택의 트레이드오프

트래픽이 작고 제품-시장 적합성을 찾는 단계라면 벤더 SaaS로 시작하세요. 코드 실행이 핵심 제품이고 볼륨이 크게 예측 가능하면 자체 구축이 장기 비용에서 유리해집니다. 규제 산업이라 데이터가 특정 리전을 벗어나면 안 된다면 벤더의 BYOC 옵션 유무를 먼저 확인하고, 없으면 자체 구축 외에 선택지가 없습니다. GPU가 필요한 워크로드라면 GPU 특화 벤더를 우선 검토해야 비용·성능 모두 유리합니다.

 

벤더 중립 인터페이스 예제
class SandboxProvider(Protocol):
    def create_session(self, tenant_id: str) -> str: ...
    def run_code(self, session_id: str, code: str) -> ExecutionResult: ...
    def resume_session(self, session_id: str) -> None: ...

# 구현체만 교체하면 오케스트레이터는 변경 없음
provider = E2BProvider() if use_vendor else SelfHostedFirecracker()

 

실제 프로젝트 진행 순서

1단계: 멀티턴 세션 재개가 필요한지부터 확정합니다. 필요하면 벤더 위탁 선택지가 크게 늘어납니다.

2단계: 예상 실행 볼륨과 테넌트 수로 종량제 vs 고정비 손익분기점을 계산합니다.

3단계: 규제·데이터 주권 요구사항을 먼저 걸러냅니다.

4단계: 오케스트레이터와 샌드박스 레이어 사이 인터페이스를 벤더 중립적으로 설계하고, 소규모 PoC로 콜드 스타트·세션 재개·격리 경계를 직접 실측합니다.

 

주의 — 이 영역은 벤더 기능·가격 변화가 빠릅니다. 결정 전 반드시 각 벤더의 최신 문서와 SLA를 직접 확인하세요.

 

정리

격리 기술 선택은 이미 전제조건이고, 진짜 판단은 운영 주체를 직접 맡을지 벤더에 맡길지입니다. 멀티턴 세션 재개와 규제상 데이터 주권이 빌드 vs 바이를 가르는 가장 강한 두 기준이며, 벤더 중립 인터페이스로 설계해두면 나중에 전환 비용을 크게 줄일 수 있습니다.
