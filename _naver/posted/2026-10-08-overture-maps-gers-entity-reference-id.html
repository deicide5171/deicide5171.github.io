"여러 지도 데이터를 하나로 합쳐주세요"라는 요청 — Overture Maps GERS로 전 세계 건물·장소에 영구 ID 붙이기

GIS

한 줄 요약 — 같은 건물·매장이 OSM·파트너 피드·자체 수집 데이터에 조금씩 다른 좌표와 이름으로 흩어져 있을 때, 이를 하나로 합치는 건 좌표 거리 비교만으로 풀리지 않습니다. Overture Maps의 GERS(Global Entity Reference System)가 전 세계 건물·장소에 릴리스 간 안정적인 영구 ID를 붙여 이 문제를 해결하려는 방식과, 직접 매칭 로직을 짜는 것과의 트레이드오프를 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"우리 지도 앱에 OSM 데이터랑 파트너사가 준 매장 리스트, 우리가 직접 수집한 POI를 다 합쳐서 중복 없이 보여주세요." 이 요구를 받으면 바로 떠오르는 방법은 좌표 거리와 이름 유사도로 매칭하는 것입니다. 하지만 실제로 해보면 금방 막힙니다. 같은 매장이 OSM에는 건물 중심점으로, 파트너 피드에는 출입구 좌표로, 자체 수집 데이터에는 GPS 오차가 낀 지점으로 찍혀 있어 수십 미터씩 어긋나고, 이름 표기도 제각각입니다. 매칭 규칙을 아무리 정교하게 짜도 릴리스마다(건물 리모델링, 매장 이전) 다시 깨집니다.

Overture Maps Foundation(리눅스 재단 산하)은 이 문제를 각 데이터 사용자가 매번 풀지 않도록, 전 세계 건물·장소·도로·행정구역에 릴리스 간 안정적으로 유지되는 전역 ID를 붙이는 GERS(Global Entity Reference System)를 공식 데이터 모델의 일부로 운영합니다. 2026년 들어 회원사 50곳을 넘겼고, OGC(Open Geospatial Consortium)가 올해 초부터 GERS를 국제 표준으로 검토하기 시작했다는 보도도 나왔습니다. 자체 매칭 로직에 계속 투자할지, 이 공유 ID 체계에 올라탈지를 판단해야 하는 시점이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"데이터를 합쳐주세요"는 실제로는 엔티티 해상도(entity resolution), 더 정확히는 컨플레이션(conflation) 문제로 번역됩니다. 서로 다른 소스에서 온 두 레코드가 "같은 실세계 객체를 가리키는가"를 판정하고, 그렇다면 하나의 식별자로 묶어야 합니다. GERS는 이 판정을 Overture가 릴리스마다 직접 수행해 결과를 ID 형태로 미리 제공합니다. 결국 "매칭해주세요"라는 요구가 "조인 키를 자체 PK 대신 GERS ID로 바꾸고, 릴리스마다 바뀌는 변경 내역을 소비하는 파이프라인을 짜주세요"라는 구체적인 엔지니어링 작업으로 바뀝니다.

 

전체 시스템에서의 위치

 

GERS는 원시 다중 소스 데이터와 자체 공간 데이터베이스 사이의 데이터 정합 계층입니다. 앞단에는 OpenStreetMap, 상업 파트너 피드, 자체 현장 수집 데이터처럼 독립적으로 생성되는 공간 데이터 소스들이 있습니다. Overture는 이들을 릴리스마다 받아 매칭하고, 그 결과를 전역 레지스트리와 변경 내역으로 공개합니다. 뒷단에서는 이 GERS ID를 조인 키로 채택해 검색 랭킹·추천 시스템·지도 렌더링에서 중복 없는 통합 뷰를 제공합니다. GERS를 빼면 이 통합은 각 팀이 자체적으로 매칭 로직을 짜고 유지보수해야 하는, 반복적이고 깨지기 쉬운 작업으로 남습니다.

 

선택의 트레이드오프
접근 초기 비용 릴리스 간 안정성 적합한 상황
자체 규칙 기반 매칭 낮음 낮음(재검증 필요) 소규모·지역 한정 서비스
자체 ML 기반 해상도 높음 중간 도메인 특화 매칭이 중요한 경우
Overture GERS ID 채택 중간 높음 글로벌 서비스, 다중 소스 통합
상용 MDM/컨플레이션 높음(라이선스) 높음(벤더 SLA) 예산 충분, 벤더 종속 감수 가능

 

GERS를 채택한다고 매칭 문제가 완전히 사라지는 건 아닙니다. 커버리지 밖의 소규모·지역 특화 엔티티는 여전히 자체 매칭이 필요하고, GERS ID도 건물이 실제로 분할·합병되면 함께 바뀝니다. GERS는 매칭 로직을 완전히 대체하기보다, 전 세계 커버리지가 필요한 핵심 엔티티의 매칭 비용을 외부화하고 자체 로직은 롱테일에 집중하는 분업 구조로 가져가는 게 현실적입니다.

 

실제 프로젝트 진행 순서

1단계: 필요한 Overture 테마(Buildings, Places, Transportation, Divisions)만 좁혀서 시작합니다.

2단계: GERS 레지스트리와 변경 내역을 먼저 받아 스키마와 이벤트 타입(생성·병합·분할·소멸)을 파악합니다.

3단계: 자체 데이터와 GERS 엔티티를 1회성으로 매칭(온보딩)하고, 매칭률이 낮은 롱테일 영역을 파악합니다.

4단계: changelog 소비 파이프라인을 설계해 병합·분할을 자동 반영합니다.

5단계: 커버리지 밖 영역의 폴백 전략(자체 매칭 유지, 신규 엔티티 기여)을 별도로 마련합니다.

6단계: 두 릴리스에 걸쳐 ID 안정성을 직접 검증한 뒤에야 프로덕션 조인 키로 전환합니다.

INSTALL spatial; LOAD spatial;
INSTALL httpfs; LOAD httpfs;

CREATE TABLE overture_places AS
SELECT id AS gers_id, names.primary AS name, geometry
FROM read_parquet('s3://overturemaps-us-west-2/release/2026-07-22.0/theme=places/*/*.parquet');

SELECT my_poi.poi_id, my_poi.internal_name,
       overture_places.name AS gers_name, overture_places.gers_id
FROM my_poi
JOIN overture_places ON my_poi.gers_id = overture_places.gers_id;

 

주의 — GERS ID를 자체 PK 대신 쓰지 말고 함께 보관하세요. 외부 표준에 전적으로 의존하면 Overture의 스키마 변경이나 커버리지 축소에 자체 시스템이 그대로 노출됩니다. changelog를 소비하지 않으면 매핑이 서서히 썩으므로, 병합·분할 이벤트를 반영하는 배치 잡을 반드시 운영 파이프라인에 포함하세요. 도입 전에 자체 서비스 지역의 매칭률을 샘플링해 커버리지 격차를 미리 확인하는 것도 중요합니다.

 

정리

여러 소스의 공간 데이터를 합치는 문제는 좌표 거리 비교가 아니라 엔티티 해상도(컨플레이션) 문제이며, Overture Maps의 GERS는 이 작업을 릴리스마다 전역 레지스트리와 변경 내역 형태로 외부화해 제공합니다. GERS ID는 다중 소스 데이터와 자체 공간 데이터베이스 사이의 정합 계층에 위치하며, 자체 매칭 로직을 완전히 대체하기보다 커버리지가 좋은 핵심 엔티티의 매칭 비용을 외부화하는 역할을 합니다. 도입 시에는 필요한 테마만 좁혀서 시작하고, changelog 소비와 폴백 전략을 함께 설계해야 시간이 지나도 매핑이 깨지지 않습니다.
