로그만으로는 부족한 지점이 있습니다

그동안 장애 대응, 로그 설계 같은 주제를 통해 시스템을 안정적으로 운영하는 방법을 다뤄왔습니다. 로그는 "특정 순간에 무슨 일이 있었는지"를 알려주는 가장 기본적인 도구이지만, "지금 시스템 전체가 건강한가"라는 질문에는 잘 답하지 못합니다. 하나의 요청이 여러 마이크로서비스를 거칠 때, 로그만으로는 어디서 지연이 발생했는지 재구성하기도 매우 어렵습니다.

이 지점에서 필요한 것이 메트릭(metrics)과 분산 트레이싱(distributed tracing)입니다. 로그, 메트릭, 트레이싱은 흔히 "옵저버빌리티의 세 기둥"으로 불리며, 로그 설계를 다뤄본 다음 단계로 이 두 가지를 추천하는 이유가 여기에 있습니다.

로그·메트릭·트레이싱의 삼각형

로그는 특정 시점의 이산적 이벤트를, 메트릭은 시간에 따라 집계된 수치를, 트레이싱은 하나의 요청이 여러 서비스를 거치는 전체 경로를 보여줍니다. 최근에는 이 세 가지를 통합해서 계측하는 OpenTelemetry가 사실상의 표준으로 자리 잡아가는 것으로 보입니다.

Node.js 애플리케이션에 OpenTelemetry로 트레이싱을 계측하는 간단한 예시입니다.

const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({ url: 'http://otel-collector:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();

 

실무 도입 시 이것만은 챙기세요
1. 샘플링 전략 설계 — 트레이싱을 100% 수집하면 비용 부담이 크므로 샘플링 전략을 함께 설계하세요.
2. 메트릭 카디널리티 주의 — 레이블 조합이 과도하게 늘어나면 저장 비용이 급격히 커질 수 있습니다.
3. 세 데이터를 서로 연결 — trace ID를 로그에 남기는 식으로 연결해야 원인을 오가며 추적할 수 있습니다.
4. SLO 기반 알림 설계 — 단순 임계치보다 사용자 경험에 실제 영향을 주는 신호에 집중해 알림 피로를 줄이세요.
