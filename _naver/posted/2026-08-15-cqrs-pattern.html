CQRS, 읽기와 쓰기를 나눠야 할 때

2026. 8. 15. · 시스템 설계

한 줄 요약 — CQRS는 데이터를 저장하는 방식(이벤트소싱)과는 별개로, 읽기와 쓰기 모델을 나누는 것만으로도 충분히 적용할 수 있는 패턴입니다.

 

왜 읽기와 쓰기를 나눌까요

하나의 서비스 안에서도 데이터를 저장하는 방식과 데이터를 보여주는 방식이 크게 다른 경우가 많습니다. 예를 들어 주문 데이터를 저장할 때는 무결성이 중요하지만, 대시보드나 검색 화면에서는 이미 가공된 형태로 빠르게 보여주는 것이 더 중요합니다. 이럴 때 등장하는 패턴이 바로 CQRS(명령과 조회의 책임 분리)입니다.

CQRS는 종종 이벤트소싱과 함께 소개되다 보니, "이벤트소싱을 써야만 CQRS를 쓸 수 있다"고 오해하기 쉽습니다. 하지만 실제로는 두 패턴이 서로 독립적이며, 이벤트소싱 없이 CQRS만 도입하는 경우가 훨씬 흔합니다.

 

전통적인 방식과 CQRS 비교
구분 전통적인 CRUD CQRS
모델 수 읽기·쓰기 공용 1개 쓰기 모델과 조회 모델 분리
데이터 형태 정규화된 테이블 조회용은 비정규화된 전용 스토어
적합한 상황 단순한 CRUD 서비스 읽기·쓰기 패턴 차이가 큰 서비스

 

코드로 보는 예시

쓰기 모델은 정규화된 테이블로, 읽기 모델은 화면에 바로 쓸 수 있는 비정규화 테이블로 나눈 예시입니다.

-- 쓰기 모델
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    customer_id UUID NOT NULL,
    status VARCHAR(20) NOT NULL,
    total_amount NUMERIC(12,2) NOT NULL
);

-- 읽기 모델 (대시보드용 비정규화 뷰)
CREATE TABLE order_summary_view (
    order_id UUID PRIMARY KEY,
    customer_name TEXT,
    status_label TEXT,
    total_amount NUMERIC(12,2)
);

 

실무 도입 시 이것만은 챙기세요
1. 지연을 사용자에게 어떻게 설명할지 정하세요 — 읽기 모델이 쓰기 모델을 따라가는 데 시간이 걸릴 수 있습니다.
2. 조회 뷰가 단순하다면 과한 설계일 수 있습니다 — 규모가 작은 서비스라면 CQRS가 오히려 복잡도만 늘릴 수 있습니다.
3. 동기화 로직도 장애 지점입니다 — 읽기 모델 갱신이 실패했을 때의 재처리 전략을 마련하세요.
4. 이벤트소싱과 혼동하지 마세요 — 두 패턴은 각각 필요한 만큼만 독립적으로 적용해도 됩니다.

 

마무리 — 3줄 요약

① CQRS는 읽기와 쓰기 모델을 분리하는 패턴이며 이벤트소싱과는 독립적으로 적용됩니다.
② 읽기 모델은 조회 성능을 위해 비정규화된 전용 스토어로 두는 경우가 많습니다.
③ 조회 패턴이 단순하다면 CQRS는 오히려 오버엔지니어링이 될 수 있습니다.

읽어주셔서 감사합니다. 서비스의 읽기·쓰기 패턴이 얼마나 다른지 먼저 살펴보신 뒤 CQRS 도입 여부를 판단해 보시길 권해 드립니다.
