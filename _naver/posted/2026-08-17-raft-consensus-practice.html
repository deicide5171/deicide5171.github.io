2026. 8. 17. · 네트워크·OS·분산처리·DevOps

한 줄 요약 — etcd, Kafka KRaft, Consul이 공통으로 쓰는 Raft 합의 알고리즘을 리더 선출과 로그 복제라는 두 축으로 나눠 실무 관점에서 정리했습니다.

 

왜 지금 Raft인가

분산 시스템에서 "노드 하나가 죽어도 서비스가 멈추지 않아야 한다"는 요구는 당연해 보이지만, 그 이면에는 항상 같은 질문이 숨어 있습니다. 여러 노드가 서로 다른 상태를 가질 수 있는 상황에서, 어떻게 하나의 정답에 합의할 것인가라는 질문입니다. 이 문제를 이해 가능한 형태로 정리한 것이 Raft 합의 알고리즘입니다.

Raft는 난해하기로 유명한 Paxos의 대안으로 이해 가능성(understandability)을 설계 목표로 삼아 등장했고, 지금은 etcd, Kafka의 KRaft 모드, Consul, CockroachDB 등 핵심 인프라 컴포넌트의 합의 계층으로 널리 쓰이고 있습니다. 쿠버네티스 클러스터를 운영하다 보면 결국 "etcd가 리더를 잃으면 무슨 일이 일어나는가"라는 질문과 마주치게 되는데, 이 질문에 답하려면 Raft의 리더 선출과 로그 복제 메커니즘을 알아야 합니다.

 

핵심 개념: 노드의 세 가지 상태와 Term

Raft 클러스터의 모든 노드는 항상 셋 중 하나의 상태에 있습니다.

상태 역할 전환 조건
Follower 리더의 명령을 수동적으로 따름 초기 상태, 또는 더 높은 term 발견 시 복귀
Candidate 선거에 나서 투표를 요청 election timeout 동안 리더 신호를 못 받으면 전환
Leader 요청을 처리하고 로그를 복제 Candidate가 과반 득표에 성공하면 전환

여기서 term(임기)은 논리적 시계 역할을 하는 단조 증가 정수입니다. 모든 메시지에는 term이 실려 있고, 노드는 자신보다 높은 term을 보면 무조건 Follower로 돌아갑니다. 이 규칙 하나만으로 구 리더가 살아 돌아와 새 리더와 충돌하는 상황을 term 비교로 정리할 수 있습니다.

 

핵심 개념: 리더 선출과 로그 복제 흐름

Follower는 각자 무작위화된 election timeout을 갖습니다. 이 시간이 지나도록 리더의 하트비트를 못 받으면 스스로 Candidate로 전환해 term을 올리고 다른 노드들에 투표를 요청합니다. 타임아웃을 무작위화하는 이유는, 모든 노드가 같은 시점에 동시에 후보가 되어 표가 갈리는 split vote를 줄이기 위해서입니다. 노드마다 타임아웃 값을 흩뿌리면 한 노드가 먼저 선거를 시작해 다른 노드들이 투표할 시간을 벌어주는 확률이 높아집니다.

리더로 선출되면 클라이언트 요청은 오직 리더만 받습니다. 리더는 요청을 자신의 로그에 엔트리로 추가하고 AppendEntries RPC로 모든 Follower에 복제를 요청합니다. 과반 노드가 해당 엔트리를 기록했다고 응답하면, 그 엔트리는 커밋된 것으로 간주되어 상태 머신에 적용됩니다.

RPC 트리거 핵심 역할
RequestVote election timeout 경과 후보가 과반 지지를 확보하는지 확인
AppendEntries 새 요청 발생 또는 하트비트 주기 로그 복제 및 리더 생존 신호

"과반 복제 = 커밋" 규칙 덕분에, 소수 노드가 죽거나 네트워크가 분할돼도 과반이 살아있는 쪽에서는 서비스가 계속됩니다. 반대로 과반을 확보하지 못한 소수파는 새 리더도 뽑지 못하고 쓰기도 커밋할 수 없습니다 — 이것이 Raft가 일관성을 지키는 핵심 트레이드오프입니다.

 

예제: 리더 선출과 로그 복제 의사코드

아래는 실제 구현체의 상세를 단순화한 의사코드로, 핵심 흐름만 보여줍니다.

// Candidate가 되었을 때
function startElection(node):
    node.state = CANDIDATE
    node.currentTerm += 1
    votes = 1  // 자기 자신에게 투표

    for peer in otherNodes:
        reply = sendRequestVote(peer, node.currentTerm)
        if reply.term > node.currentTerm:
            node.state = FOLLOWER   // 더 높은 term 발견 시 즉시 물러남
            return
        if reply.voteGranted:
            votes += 1

    if votes > totalNodes / 2:
        node.state = LEADER

// Leader가 로그 엔트리를 복제할 때
function replicateEntry(leader, entry):
    leader.log.append(entry)
    acked = 1
    for peer in followers:
        response = sendAppendEntries(peer, leader.currentTerm, entry)
        if response.success:
            acked += 1

    if acked > totalNodes / 2:
        commitIndex = entry.index   // 과반 확보 시 커밋
        applyToStateMachine(entry)

 

실무 도입 시 이것만은 챙기세요
1. election timeout은 네트워크 지연을 감안 — 너무 짧으면 불필요한 재선출, 너무 길면 장애 복구 지연. etcd 등 구현체의 권장값을 따르는 편이 안전
2. 과반 계산이 클러스터 크기 설계 기준 — 5노드는 2노드가 죽어도 과반 유지, 3노드는 1노드만 죽어도 마진 소멸. 짝수보다 홀수 구성이 일반적
3. 네트워크 분할 시 소수파는 쓰기를 멈춤 — 버그가 아니라 설계. 클라이언트 측 리더 탐색·재시도 로직 필요
4. 로그 압축(snapshot)도 함께 이해 — 로그가 무한히 쌓이지 않도록 주기적으로 상태 머신 스냅샷을 찍고 오래된 로그를 정리

 

마무리 — 3줄 요약

① Raft는 term이라는 논리적 시계와 Follower/Candidate/Leader 상태 전이로 리더 선출을 이해 가능한 형태로 단순화합니다.
② 리더만 쓰기를 받아 로그에 기록하고, 과반 노드가 복제를 확인해야 커밋되는 구조 덕분에 소수 노드 장애에도 데이터 일관성이 유지됩니다.
③ etcd·Kafka KRaft 등을 운영할 때는 election timeout, 클러스터 크기(홀수 개수), 클라이언트 재시도 로직을 함께 설계해야 합니다.
