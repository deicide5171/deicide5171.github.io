PostGIS와 pgvector, 한 DB에 모을 때의 트레이드오프 — 공간 검색과 의미 검색을 합치는 법

GIS

한 줄 요약 — 공간 필터와 의미 검색을 동시에 요구하는 기능은 아키텍처 선택부터 시작합니다. 매장 규모가 수백만 건 이하라면 PostGIS+pgvector 통합형으로 시작하는 편이 정합성과 운영 부담 모두에서 유리합니다.

 

"근처에서 '아이랑 가기 좋은 카페' 찾아주세요"

지도 서비스에 이런 요구사항이 들어오면 곧바로 두 종류의 필터가 동시에 걸립니다. 하나는 공간 필터("근처에서" — 현재 좌표 반경 2km 이내), 다른 하나는 의미 필터("아이랑 가기 좋은" — 키워드 매칭이 아니라 설명 텍스트의 의미로 판단)입니다. 기존에는 이 둘을 담당하는 시스템이 완전히 갈라져 있었습니다. 공간 검색은 PostGIS, 의미 검색은 Pinecone·Weaviate 같은 벡터 전용 DB였죠. 그런데 2026년 들어 pgvector가 HNSW 인덱스와 필터 결합 성능을 계속 개선하면서, "굳이 DB를 두 개로 나눠야 하나"라는 질문이 실무 선택지로 올라왔습니다.

이 글은 새 기술 소개가 아니라 아키텍처 결정에 관한 것입니다. 같은 Postgres 안에 PostGIS와 pgvector를 함께 두는 통합형과, 벡터 전용 DB를 따로 쓰는 분리형 중 무엇을 고를지, 그리고 통합형을 골랐을 때 실제 쿼리를 어떻게 짜야 두 인덱스가 서로를 방해하지 않는지를 정리합니다.

 

전체 구조에서의 위치

매장 등록 API에서 설명 텍스트를 임베딩 모델에 보내 벡터를 생성하고, 위경도를 geometry로 변환한 뒤, 검색 시점에 공간 필터와 벡터 유사도를 함께 적용해 순위를 매기는 흐름입니다.

 

핵심 함정은 분리형에서 "후보 부족" 문제입니다. 벡터 DB에서 유사도 top-100을 먼저 받아온 뒤 그중 반경 안에 있는 것만 걸러내면, 반경 안에 진짜 좋은 매장이 있어도 벡터 유사도 순위에서 100등 밖으로 밀려 있으면 애초에 후보에 들어오지 못합니다.

 

통합형 vs 분리형 — 무엇을 기준으로 고를까
기준 통합형 분리형
정합성 트랜잭션 하나로 보장 두 시스템 간 동기화 필요
운영 부담 낮음 (DB 한 대) 높음 (동기화 파이프라인 관리)
적합한 규모 수십만~수백만 건 수억 건, 매우 높은 QPS

 

통합형 쿼리 설계 — 인덱스 순서가 성능을 가른다
CREATE TABLE places (
  id bigserial PRIMARY KEY,
  name text,
  description text,
  geom geometry(Point, 4326),
  embedding vector(768)
);

CREATE INDEX idx_places_geom ON places USING GIST (geom);
CREATE INDEX idx_places_embedding ON places USING HNSW (embedding vector_cosine_ops);

SELECT id, name,
       embedding <=> :query_embedding AS cos_dist
FROM places
WHERE ST_DWithin(geom::geography, ST_MakePoint(:lng, :lat)::geography, 2000)
ORDER BY embedding <=> :query_embedding
LIMIT 20;

여기서 공간 필터를 WHERE 절에, 벡터 정렬을 ORDER BY에 두는 순서가 중요합니다. 옵티마이저가 GiST 인덱스로 후보군을 좁힌 뒤 그 안에서만 HNSW 정렬을 시도하도록 유도해야, 전체 테이블에 대해 벡터 거리를 계산하는 최악의 경우를 피할 수 있습니다. 실행 계획을 EXPLAIN ANALYZE로 반드시 확인하세요.

 

실무 포인트

코사인 거리와 미터 단위는 스케일이 다릅니다. 두 값을 단순히 더해 하나의 점수로 합치면 안 됩니다. 공간 거리는 반경 대비 비율로, 벡터 거리는 0~1 정규화값으로 바꾼 뒤 가중합을 적용하는 편이 안전합니다.

임베딩 재계산 시점을 정해둡니다. 매장 설명이 수정될 때마다 동기적으로 임베딩을 다시 계산하면 쓰기 지연이 늘어납니다. 큐에 넣고 비동기로 갱신하는 편이 현실적입니다.

주의 — HNSW 인덱스는 메모리를 많이 먹습니다. GiST와 HNSW가 같은 Postgres 인스턴스의 shared_buffers를 나눠 쓰므로, 통합형을 쓰기로 했다면 인덱스 메모리 사용량부터 먼저 측정해 인스턴스 크기를 정하세요.

 

정리

공간 필터와 의미 검색을 동시에 요구하는 기능은 아키텍처 선택부터 시작합니다. 매장 규모가 수백만 건 이하라면 통합형으로 시작하고, 분리형을 쓸 때는 top-K 후보 부족 문제를 반드시 검증하세요. 통합형 쿼리는 WHERE의 공간 필터가 먼저 후보를 좁히도록 실행 계획을 확인하고, 거리 단위는 반드시 정규화해서 합칩니다.
