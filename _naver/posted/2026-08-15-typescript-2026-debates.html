TypeScript가 이겼다는 지금, 남은 논쟁은 무엇일까요

2026. 8. 15. · 웹개발

한 줄 요약 — TypeScript 채택이 사실상 보편화되었다는 이야기가 나올 정도로 자리 잡은 지금, 실무에서 여전히 부딪히는 strict 모드 수준, 타입 우선 설계, 빌드 없는 실행, 컴파일 성능 논쟁을 정리해보았습니다.

 

왜 지금 이 이야기를 하는가

몇 년 전까지만 해도 TypeScript 도입 여부는 프로젝트 초반에 진지하게 토론하던 주제였습니다. 그런데 최근에는 신규 JavaScript 프로젝트 대부분이 처음부터 TypeScript로 시작한다는 이야기가 여러 설문과 커뮤니티에서 반복적으로 나오고 있습니다. 정확한 수치는 조사마다 다를 수 있어 단정하기는 조심스럽지만, 방향성 자체는 뚜렷해 보입니다.

문제는 도입 여부가 논쟁의 끝이 아니라는 점입니다. TypeScript를 쓰기로 정한 이후에도 팀마다 방식이 크게 갈립니다. strict 모드를 얼마나 켤지, 타입을 먼저 설계할지 나중에 붙일지, 빌드 없이 바로 실행해도 되는지, 대형 프로젝트에서 컴파일 속도를 어떻게 관리할지가 새로운 실무 논쟁으로 떠올랐습니다. 오늘은 이 네 가지 쟁점을 정리해보겠습니다.

 

쟁점 1 — strict 모드, 어디까지 켤 것인가

strict: true는 이제 신규 프로젝트의 기본값처럼 여겨지지만, 그 안에 포함된 세부 옵션들을 전부 같은 강도로 켤지는 팀마다 다릅니다. 특히 기존 코드베이스를 마이그레이션하는 상황에서는 한 번에 전부 켜기보다 옵션을 하나씩 순서대로 켜는 방식이 많이 권장됩니다.

접근 방식 장점 단점
처음부터 전체 strict 타입 안전성 최대화 신규 팀원 진입 장벽
단계적 strict 적용 기존 코드 마이그레이션 용이 과도기 타입 커버리지 불균일
strict 최소화 빠른 프로토타이핑 any 남용 위험

 

쟁점 2 — 타입 우선 설계 vs 점진적 타이핑

타입 우선 설계는 도메인 모델과 인터페이스를 먼저 정의하고 구현을 채워나가는 방식이고, 점진적 타이핑은 기존 JavaScript 코드에 타입을 나중에 덧입히는 방식입니다. 신규 프로젝트에서는 타입 우선 방식이 API 계약을 명확히 해주어 선호되는 경우가 많지만, 기존 대형 코드베이스에서는 점진적 타이핑이 현실적인 선택지로 남아 있습니다.

두 방식을 굳이 양자택일할 필요는 없다고 생각합니다. 핵심 도메인 로직은 타입 우선으로 설계하고, 주변부 유틸리티 코드는 점진적으로 타입을 붙여나가는 혼합 전략도 실무에서 널리 쓰이고 있습니다.

 

쟁점 3 — 빌드 없이 TypeScript 실행하기

Node.js가 실험적으로 지원하기 시작한 native type stripping 기능은 별도의 트랜스파일 빌드 단계 없이 .ts 파일을 바로 실행할 수 있게 해줍니다. 다만 이 기능은 타입을 검사하는 것이 아니라 타입 표기를 제거만 하는 것이므로, 타입 오류를 실제로 잡으려면 여전히 별도의 타입 검사 단계가 필요합니다.

따라서 프로덕션 빌드 파이프라인 전체를 이 기능으로 대체하기보다는, 로컬 개발이나 간단한 스크립트를 빠르게 실행할 때 편의성을 높이는 용도로 먼저 도입하는 편이 안전하다고 생각합니다.

// tsconfig.json — 단계적으로 strict를 켜는 예시
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "skipLibCheck": true
  }
}
// native type stripping 환경 실행 예시 (개념 코드)
// 실행: node --experimental-strip-types app.ts
interface User {
  id: string;
  name: string;
}

function greet(user: User): string {
  return `안녕하세요, ${user.name}님`;
}

console.log(greet({ id: "1", name: "지연" }));

 

실무 도입 시 이것만은 챙기세요
1. any 대신 unknown — 외부 타입이 부실할 때 any로 임시 봉합하면 시간이 지나며 조용히 퍼집니다, unknown과 타입 가드로 대체하는 습관을 들이는 것이 좋습니다
2. ESLint no-explicit-any — CI에 규칙을 걸어두면 any 남용을 코드 리뷰 이전에 걸러낼 수 있습니다
3. native type stripping은 검사 도구가 아닙니다 — 빌드 없이 실행되더라도 tsc --noEmit 같은 별도 타입 검사 단계는 그대로 유지해야 합니다
4. 대형 모노레포는 project references 검토 — 컴파일·타입 검사 속도가 개발 경험을 좌우하므로 증분 빌드 캐시 활용도 함께 점검해볼 만합니다

 

마무리 — 3줄 요약

① TypeScript 도입 자체는 더 이상 논쟁거리가 아니며, 논쟁은 strict 수준·설계 순서·실행 방식·성능으로 옮겨갔습니다.
② native type stripping은 빌드 단계를 줄여주지만 타입 검사를 대체하지는 않으므로 별도 검사 단계가 여전히 필요합니다.
③ any 남용을 막고 타입 커버리지를 유지하려면 ESLint 규칙, 단계적 strict 적용, project references 같은 장치를 실무 규칙으로 정해두는 것이 중요합니다.
