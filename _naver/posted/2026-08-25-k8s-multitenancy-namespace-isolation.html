네임스페이스만으로는 부족하다 — 쿠버네티스 멀티테넌시 격리 실전

2026. 8. 25. · 인프라

한 줄 요약 — 네임스페이스는 이름과 권한 범위만 나눌 뿐입니다. NetworkPolicy, ResourceQuota, Pod Security를 함께 설계해야 완성되는 쿠버네티스 소프트 멀티테넌시를 정리했습니다.

 

네임스페이스를 나눴다고 격리된 게 아닙니다

여러 팀이 하나의 쿠버네티스 클러스터를 공유할 때 가장 먼저 하는 일은 팀별로 네임스페이스를 나누는 것입니다. 그런데 네임스페이스는 기본적으로 이름 충돌을 막는 논리적 구분일 뿐, 그 자체로 네트워크 트래픽을 막거나 자원 사용을 제한하지 않습니다. 한 팀의 배치 작업이 노드 CPU를 독점해 다른 팀의 서비스가 자원 부족으로 죽는 일도 네임스페이스만으로는 막히지 않습니다.

쿠버네티스가 제공하는 멀티테넌시는 흔히 "소프트 멀티테넌시"라 불립니다. 네임스페이스·RBAC·NetworkPolicy·ResourceQuota 같은 여러 리소스를 조합해서 논리적 격리를 만들어야 합니다.

 

핵심 개념 1 — 네임스페이스가 격리하는 것과 하지 않는 것
항목 네임스페이스만으로 격리 별도 설정 필요
네트워크 트래픽 X NetworkPolicy
CPU/메모리 사용량 X ResourceQuota, LimitRange
파드 보안 설정 X Pod Security Admission

 

핵심 개념 2 — NetworkPolicy, 기본은 전부 허용입니다

쿠버네티스의 기본 네트워크 모델은 클러스터 내 모든 파드가 서로 통신 가능한 flat network입니다. NetworkPolicy를 하나도 만들지 않으면 네임스페이스를 아무리 나눠도 모든 파드가 서로 자유롭게 접근할 수 있습니다. NetworkPolicy는 CNI 플러그인이 실제로 강제해야 동작하며, CNI가 지원하지 않으면 정책을 만들어도 효과가 없습니다.

실무에서 권장되는 패턴은 기본 거부(default-deny)를 먼저 깔고 필요한 통신만 명시적으로 허용하는 것입니다.

 

핵심 개념 3 — ResourceQuota와 LimitRange로 자원 경합 방지

네트워크가 격리돼도 한 네임스페이스의 워크로드가 노드 자원을 과도하게 점유하면 다른 팀의 파드가 자원 부족을 겪습니다("noisy neighbor" 문제). ResourceQuota는 네임스페이스 단위 상한을, LimitRange는 개별 컨테이너의 요청/제한값 기본값과 상한을 지정합니다. 이 둘을 함께 쓰지 않으면 허점이 생깁니다.

 

예제 — 네임스페이스 단위 기본 거부와 쿼터
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: team-a
spec:
  podSelector: {}
  policyTypes:
    - Ingress
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    pods: "100"

 

실무 도입 시 이것만은 챙기세요
1. CNI가 NetworkPolicy를 실제로 지원하는지 먼저 확인하세요 — 일부 관리형 쿠버네티스는 기본 CNI가 강제하지 않을 수 있습니다.
2. 노이즈 네이버 문제는 네임스페이스만으로 완전히 막을 수 없습니다 — 더 엄격한 격리는 노드 풀 분리나 별도 클러스터를 고려하세요.
3. Pod Security Admission으로 컨테이너 권한도 함께 통제하세요 — privileged 모드가 허용돼 있으면 다른 격리가 우회될 수 있습니다.

 

마무리 — 3줄 요약

① 쿠버네티스 네임스페이스는 이름과 API 권한 범위를 나눌 뿐, 네트워크와 자원 사용량은 저절로 격리하지 않습니다.
② NetworkPolicy는 CNI 지원이 필요하고 기본 거부 패턴이 안전하며, ResourceQuota와 LimitRange는 함께 써야 합니다.
③ 더 엄격한 격리가 필요하면 노드 풀 분리나 별도 클러스터 같은 하드 멀티테넌시를 고려해야 합니다.
