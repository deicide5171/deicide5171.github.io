지도가 트래픽만 몰리면 죽는다 — GeoServer GWC 캐시 전략과 WMS 요청 폭주 방어

GIS

한 줄 요약 — "지도 로딩이 느려요, 트래픽 몰릴 때마다 지도 서비스가 죽어요"라는 요구는 레이어 하나 더 캐싱하는 걸로 끝나지 않습니다. GeoWebCache가 캐싱할 수 있는 레이어와 할 수 없는 레이어를 가르는 기준, 그리고 캐시 밖으로 새는 요청을 Control Flow 모듈로 막는 2단 방어 설계를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"지도 로딩이 느려요, 사람들이 한꺼번에 들어올 때마다 지도 서비스가 멈춰요." GeoServer 위에 PostGIS 레이어 몇 개를 올려 서비스를 시작한 팀이 트래픽이 붙기 시작하면 반드시 듣는 말입니다. 단순해 보이는 이 요구는 사실 두 가지 다른 문제를 뭉뚱그리고 있습니다. 하나는 "같은 타일을 반복 렌더링하지 말고 캐싱하라"는 성능 문제고, 다른 하나는 "캐싱이 안 되는 요청이 몰려도 서버가 넘어지지 않게 하라"는 생존 문제입니다. 많은 팀이 GeoWebCache(GWC)를 켜는 데서 멈추는데, 실제로는 캐싱 범위 밖에 있는 요청 — 필터가 붙은 WMS, 복잡한 SQL 뷰 레이어, WFS 대용량 응답 — 이 여전히 서버를 쓰러뜨립니다.

GeoServer가 오픈소스 공간 데이터 서버의 사실상 표준으로 자리 잡으면서, "WMS·WFS를 직접 열어주는 수준"을 넘어 실제 운영 부하를 견디는 설계가 빌더에게 필수 지식이 됐습니다. 레이어를 몇 개 올렸느냐가 아니라, 그중 몇 개가 캐시 가능한 후보인지, 그리고 캐시가 안 되는 나머지를 어떻게 제한할지가 운영 안정성을 가릅니다.

 

핵심 개념 — GWC는 타일 피라미드 앞에 서는 캐시 계층

GWC는 WMS 요청을 받아 매번 PostGIS를 조회해 렌더링하는 대신, 미리 정의된 줌 레벨·타일 격자(gridset) 조합으로 렌더링 결과를 디스크에 저장해 재사용합니다. 공식 가이드는 전체 레이어를 사전 시딩(pre-seed)했을 때 순수 WMS 대비 처리량이 10~100배까지 올라간다고 보고합니다 — 단, 이건 "캐시가 이미 채워져 있을 때" 이야기입니다.

캐싱이 잘 맞는 레이어는 자주 안 바뀌고 동적 파라미터가 적은 배경 레이어(행정구역, 도로망, 베이스맵)입니다. 반대로 CQL 필터·다중 스타일·시간 차원이 붙는 레이어는 조합이 폭발해 캐시 적중률이 바닥을 칩니다 — 캐시가 있어도 매번 새로 렌더링하는 꼴이라 캐시를 켠 의미가 없습니다.

 

캐시 밖 요청은 Control Flow로 막는다

캐싱 가능 레이어를 다 캐싱해도, WFS로 전체 피처를 한 번에 요청하거나 복잡한 CQL 필터를 건 WMS 요청은 여전히 캐시를 우회해 데이터베이스를 직접 때립니다. 이 요청들을 무제한으로 받으면 동시 요청 몇 개만으로 GeoServer의 스레드 풀과 DB 커넥션 풀이 고갈돼 캐시된 요청까지 함께 느려집니다. GeoServer의 Control Flow 확장은 요청을 더 빠르게 처리하는 게 아니라 동시 처리 개수 자체를 제한해 서버가 쓰러지기 전에 초과분을 큐잉하거나 거절합니다.

 

전체 시스템에서의 위치

 

요청이 들어오면 가장 먼저 Control Flow 모듈이 현재 동시 처리 수를 확인해 한도를 넘는 요청을 대기열에 둡니다. 통과한 요청은 GWC로 가서 캐시 적중 여부를 확인하고, 적중이면 디스크 타일을 바로 반환합니다. 미스이거나 캐시 불가능한 요청이면 GeoServer 렌더링 엔진이 PostGIS에 질의해 결과를 그리고, 캐시 가능한 조합이었다면 그 결과를 GWC에 저장합니다.

 

선택의 트레이드오프
전략 강점 약점
전체 사전 시딩 첫 요청부터 캐시 적중 디스크·시딩 부하 큼
온디맨드 캐싱 디스크 절약 초기 요청은 느림
Direct WMS Integration 동적 요청도 같은 엔드포인트로 처리 Disk Quota 없이 켜면 무한 증가
Control Flow 동시 제한 전체 다운 방지 한도 초과 시 대기·거절 경험

 

Direct WMS Integration을 켤 때는 반드시 Disk Quota(디스크 사용량 상한 + LFU/LRU 자동 만료 정책)를 함께 설정해야 합니다. 그렇지 않으면 캐시가 끝없이 쌓여 디스크를 채웁니다 — 공식 문서도 이 조합을 명시적으로 권장합니다.

 

gridset 설정 예제
gridSet:
  name: "EPSG:3857_custom"
  srs: "EPSG:3857"
  minZoom: 0
  maxZoom: 12
  tileWidth: 256
  tileHeight: 256

 

실제 프로젝트 진행 순서

1단계: 레이어를 캐시 가능/불가능으로 분류합니다. 갱신 주기, CQL 필터 사용 여부, 스타일 종류 수가 기준입니다.

2단계: 캐시 가능 레이어부터 gridset을 클라이언트 줌 레벨에 맞춰 설계하고 시딩합니다.

3단계: Disk Quota를 먼저 켠 뒤에 Direct WMS Integration을 활성화합니다.

4단계: 캐시 불가 레이어에 Control Flow로 동시 처리 한도를 걸고, 부하 테스트로 캐시 적중률과 대기열 거동을 확인합니다.

 

주의 — "10~100배" 같은 처리량 수치는 레이어 특성과 하드웨어에 따라 크게 달라집니다. 자신의 레이어 구성으로 직접 부하 테스트를 해보고 캐시 적중률을 확인하세요.

 

정리

GWC 캐싱은 자주 안 바뀌고 동적 파라미터가 적은 레이어에만 효과가 있습니다. 캐시 밖 요청은 캐싱이 아니라 Control Flow의 동시 처리 제한으로 막아야 서버 전체 다운을 피할 수 있고, Direct WMS Integration은 반드시 Disk Quota와 함께 켜야 합니다.
