에이전트 기능을 여러 도구에 다 배포해주세요 — Agent Plugins 1.0으로 MCP·Skills 묶기

AI

한 줄 요약 — 우리 팀 도구를 Claude Code에서도, Cursor에서도, Copilot CLI에서도 똑같이 쓰게 해달라는 요구는 런타임마다 MCP 서버와 Skills를 따로 등록하는 반복 작업으로 이어졌습니다. GitHub·AWS·Microsoft·OpenAI·Vercel·Google이 공동 발표한 Agent Plugins 1.0이 이 반복을 하나의 패키지 포맷으로 묶는 방식과, 지금 이 표준에 올라타야 하는지 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"우리 팀이 쓰는 사내 API 호출 도구랑 PR 체크리스트 절차를 Claude Code에서도, Cursor에서도, 회사가 깔아준 Copilot CLI에서도 똑같이 쓸 수 있게 해주세요." 에이전트 코딩 도구를 두 개 이상 쓰는 팀이라면 반드시 마주치는 요구입니다. 지금까지는 MCP 서버 하나를 만들고, 거기에 더해 Claude Code용 Skills 디렉터리를 따로 만들고, Copilot용 커스텀 명령 포맷을 또 따로 맞추는 식으로 같은 기능을 세 번 포장해야 했습니다. 런타임이 하나 늘 때마다 포장 작업도 그만큼 늘어나는 구조였습니다.

2026년 8월 6일 GitHub, AWS, Anysphere(Cursor), Microsoft, OpenAI, Vercel이 공동 발표하고 같은 날 Google이 핵심 메인테이너로 합류한 Agent Plugins 1.0은 이 반복을 패키지 포맷 하나로 묶으려는 시도입니다. MCP 서버와 Agent Skills를 이미 각자 따로 만들어 쓰고 있는 팀이라면, 지금 이 표준에 맞춰 재포장할 가치가 있는지 판단해야 할 시점이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"여러 도구에서 다 쓰게 해주세요"는 사실 배포 대상이 하나가 아니라 여럿이라는 문제입니다. 기능 자체(도구 호출 로직, 절차적 노하우)는 런타임과 무관하게 동일하지만, 각 런타임은 그 기능을 인식하는 방식이 다릅니다. MCP 서버는 도구 호출 프로토콜만 정의할 뿐 "언제 이 절차를 따르라"는 지시는 담지 못하고, Skills는 절차는 담지만 외부 API 연결은 못합니다. 그래서 실제 작업은 "플러그인 하나 짜주세요"가 아니라, MCP 서버(도구)와 Skills(절차)를 같은 폴더 안에 함께 선언하고, 그 선언을 여러 런타임이 공통으로 읽을 수 있는 매니페스트 형식으로 표준화하는 문제로 번역됩니다.

 

전체 시스템에서의 위치

 

플러그인은 필수 매니페스트 plugin.json, 선택적인 skills/(Agent Skills), 선택적인 mcp.json(MCP 서버 선언)으로 구성된 폴더 하나입니다. 각 클라이언트는 이 폴더를 읽어 자신의 방식대로 설치·정책·UX를 결정하지만, 포맷 자체는 공유합니다. GitHub Copilot 전용 기능(커스텀 에이전트, 명령, 훅)은 com.github.copilot/ 같은 네임스페이스 폴더에 격리해, 다른 클라이언트가 그 폴더를 무시해도 나머지 플러그인은 정상 동작하게 설계했습니다. 이 레이어가 없으면 같은 기능을 런타임 수만큼 반복 구현해야 하고, 기능을 하나 고칠 때마다 그 수만큼 다시 수정해야 하는 상태로 남습니다.

 

선택의 트레이드오프
접근 배포 범위 유지보수 부담 적합한 상황
MCP 서버만 단독 배포 도구 호출만, 런타임 제한적 런타임별 재등록 반복 도구가 하나뿐이고 런타임도 하나뿐인 초기 단계
Skills만 단독 배포 특정 클라이언트 전용 클라이언트 바뀌면 이식 불가 외부 연결 없이 절차·노하우만 전달할 때
런타임별 커스텀 포맷 유지 런타임마다 다른 포맷 포맷 수만큼 중복 작업 특정 런타임에 깊게 특화해야 하는 경우
Agent Plugins 1.0 30여 개 클라이언트 공통 매니페스트 1벌로 통합 2개 이상 런타임을 조직적으로 지원해야 할 때

 

표준을 따르면 포맷 중복은 줄지만, 공개된 지 두 달 남짓이라 클라이언트별 세부 동작(설치 UX, 권한 모델)은 아직 서로 다르고 생태계 문서도 유동적입니다. 런타임이 하나뿐이거나 당장 늘릴 계획이 없다면 네이티브 포맷을 유지하는 편이 단순합니다. 조직 내에서 Claude Code와 Copilot CLI를 동시에 승인해 쓰는 경우처럼 런타임이 실제로 둘 이상 섞여 있을 때 표준화 이득이 분명해집니다.

 

실제 프로젝트 진행 순서

1단계: 지금 쓰는 MCP 서버와 Skills를 먼저 인벤토리하고, 도구 호출(MCP)과 절차 지시(Skills)를 명확히 구분합니다.

2단계: 런타임이 실제로 2개 이상인지 확인합니다. 하나뿐이면 재포장 비용이 이득을 넘어설 수 있습니다.

3단계: 공통 매니페스트로 가장 자주 쓰는 기능 하나만 시범 이전해 포맷과 설치 과정을 검증합니다.

4단계: 벤더 전용 기능은 네임스페이스 폴더로 분리해 다른 클라이언트에서 오류가 나지 않게 합니다.

5단계: 팀 내 설치 경로를 문서화해 신규 합류자가 런타임별로 어떻게 켜는지 안내합니다.

{
  "name": "pr-review-checklist",
  "version": "1.0.0",
  "description": "사내 PR 리뷰 체크리스트와 API 호출 도구",
  "skills": "./skills",
  "mcpServers": "./mcp.json"
}

 

주의 — Agent Plugins 1.0은 설치·정책·UX를 각 클라이언트에 맡기는 공존 모델입니다. 패키지 포맷만 통일됐을 뿐, 모든 런타임에서 똑같이 동작한다고 보장하지 않습니다. 기존 Copilot 플러그인은 마이그레이션 없이 계속 지원되니 급하게 전체를 재작성할 필요는 없고, 공식 지원 목록에 이름이 있어도 실제 설치 경험은 직접 확인해야 합니다.

 

정리

"여러 도구에서 똑같이 쓰게 해주세요"는 MCP(도구)와 Skills(절차)를 하나의 패키지로 묶어, 여러 런타임이 공통으로 읽을 매니페스트로 표준화하는 문제로 번역됩니다. Agent Plugins 1.0은 설치·정책·UX는 각 클라이언트에 맡기고 패키지 포맷만 통일하는 공존 모델이며, GitHub·AWS·Microsoft·OpenAI·Vercel·Google이 공동으로 추진 중입니다. 도입은 런타임이 실제로 2개 이상일 때, 가장 자주 쓰는 기능 하나를 시범 이전하는 것부터 시작하는 것이 안전합니다.
