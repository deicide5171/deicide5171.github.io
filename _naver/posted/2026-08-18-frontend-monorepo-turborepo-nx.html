프론트엔드 모노레포 실전 비교 — Turborepo vs Nx, 캐싱과 의존성 그래프로 고르기

2026. 8. 18. · 프론트엔드

한 줄 요약 — 여러 앱과 공유 패키지를 한 저장소에서 관리하는 프론트엔드 모노레포가 늘어나는 지금, 대표 도구인 Turborepo와 Nx를 캐싱 전략과 의존성 그래프 처리 방식 중심으로 비교해봤습니다.

 

왜 지금 프론트엔드 모노레포일까요

디자인 시스템, 웹앱, 어드민, 랜딩 페이지가 저장소별로 흩어져 있으면 공통 컴포넌트 하나를 고칠 때마다 각 저장소에 패키지를 재배포하고 버전을 맞추는 작업이 반복됩니다. 팀이 커질수록 "UI 라이브러리 변경이 어느 앱까지 영향을 주는가"를 저장소 경계 때문에 한눈에 파악하기 어려워지는 문제도 함께 커집니다. 모노레포는 여러 앱과 공유 패키지를 한 저장소, 하나의 의존성 그래프 안에 두어 이 문제를 구조적으로 없앱니다.

다만 모노레포 자체는 "여러 패키지를 한 저장소에 두는 것" 이상의 의미가 없습니다. 실제로 팀 생산성을 좌우하는 것은 그 위에서 빌드·테스트·린트를 어떻게 실행하느냐이며, 이 역할을 맡는 것이 Turborepo, Nx 같은 빌드 오케스트레이션 도구입니다. 워크스페이스로 패키지 링크만 잡아 두고 실행 계층 없이 버티는 팀도 있지만, 저장소가 커질수록 "바뀐 것만 다시 빌드하고 나머지는 캐시에서 즉시 복원한다"는 캐싱 계층 없이는 CI 시간이 계속 늘어나게 됩니다.

 

핵심 개념 1 — 모노레포가 해결하는 것과 안 하는 것
구분 여러 개의 저장소 워크스페이스만 Turborepo/Nx 포함
코드 공유 npm 배포·버전 관리 필요 심볼릭 링크로 즉시 참조 동일 + 그래프 기반 영향 분석
빌드 순서 저장소별 독립 CI 수동으로 순서 관리 필요 의존성 그래프로 자동 정렬
반복 작업 캐시 저장소별 별도 CI 캐시 없음 로컬·원격 캐시로 중복 제거

 

핵심은 워크스페이스가 "코드를 어떻게 연결할지"를 정의한다면, Turborepo·Nx는 "무엇을 다시 실행해야 하는지"를 판단한다는 점입니다. 이 판단은 각 패키지의 소스 파일, 의존 패키지, 환경 변수까지 포함한 해시를 계산해 이전 실행과 비교하는 방식으로 이루어집니다.

 

핵심 개념 2 — Turborepo vs Nx, 무엇이 다를까요

두 도구 모두 "의존성 그래프 기반 실행 + 로컬/원격 캐싱"이라는 핵심 아이디어는 같지만, 접근 방식과 부가 기능에서 갈립니다.

항목 Turborepo Nx
설정 방식 turbo.json에 태스크 파이프라인 선언 nx.json + 프로젝트별 설정(또는 추론 기반)
학습 곡선 상대적으로 단순, 설정 최소화 지향 기능이 많은 만큼 개념 습득 필요
코드 생성기 기본 제공 없음(직접 스크립트 작성) generator/플러그인으로 보일러플레이트 자동화
시각화 기본 CLI 로그 중심 프로젝트 그래프를 보여주는 내장 뷰어
원격 캐시 Vercel 연동 캐시 서비스 Nx Cloud, 자체 캐시 서버 구성도 가능
적합한 규모 소~중규모, 빠른 도입 선호 팀 다수 팀·다수 앱이 얽힌 대규모 조직

 

두 도구 중 하나가 절대적으로 우월하다기보다, 이미 잘 짜인 소수의 앱+공유 패키지 구조라면 Turborepo의 단순함이, 여러 팀이 각기 다른 앱을 소유하고 표준화된 생성기·린트 규칙이 필요하다면 Nx의 플러그인 생태계가 더 잘 맞는 경우가 많습니다.

 

예제: 캐시 가능한 태스크 파이프라인 정의 (Turborepo)

아래는 turbo.json에서 build, lint, test 태스크의 의존 순서와 캐시 대상 산출물을 지정하는 기본 예시입니다.

// turbo.json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "lint": {
      "outputs": []
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

dependsOn의 ^build는 "이 패키지가 의존하는 패키지들의 build 태스크가 먼저 끝나야 한다"는 뜻입니다. outputs에 명시한 경로만 캐시 대상이 되므로, 여기에 빠진 산출물은 캐시 히트가 나더라도 복원되지 않는다는 점을 팀 컨벤션으로 공유해 둘 필요가 있습니다. dev처럼 계속 떠 있는 태스크는 cache: false로 캐시 대상에서 제외합니다.

 

실무 도입 시 이것만은 챙기세요
1. 캐시 키에 무엇이 들어가는지 반드시 확인 — 소스 해시뿐 아니라 환경 변수도 포함되도록 설정하지 않으면 잘못된 캐시가 반환될 수 있음
2. 원격 캐시는 CI에서 효과가 가장 큼 — 여러 브랜치·러너가 캐시를 공유하려면 원격 캐시 연동이 사실상 필수
3. 의존성 그래프를 정기적으로 시각화해 확인 — 순환 의존성·의도치 않은 결합은 패키지가 늘수록 리뷰만으로 잡기 어려움
4. 마이그레이션은 한 번에 하지 않기 — 기존 워크스페이스 위에 파이프라인만 먼저 얹고 캐시 적중률을 보며 점진적으로 다듬기

 

마무리 — 3줄 요약

① 모노레포는 여러 앱·공유 패키지를 하나의 의존성 그래프로 관리하지만, 실제 생산성은 그 위에서 도는 빌드 오케스트레이션 도구가 좌우합니다.
② Turborepo는 단순한 설정으로 빠르게 캐싱을 도입하기 좋고, Nx는 코드 생성기·그래프 시각화 등 대규모 조직에 필요한 기능이 더 풍부합니다.
③ 캐시 키 구성과 outputs 지정을 정확히 하지 않으면 캐시 히트가 오히려 잘못된 산출물을 반환할 수 있으니 도입 초기에 꼼꼼히 검증해야 합니다.
