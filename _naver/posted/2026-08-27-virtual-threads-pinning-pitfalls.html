가상 스레드가 갑자기 안 가벼워지는 순간 — Virtual Thread Pinning 문제와 해결

2026. 8. 27. · 백엔드

한 줄 요약 — 가상 스레드를 도입했는데 캐리어 스레드 개수만큼만 동시성이 나온다면 피닝을 의심해야 합니다. 원인과 감지, 해결 방법을 정리했습니다.

 

가상 스레드가 왜 조용히 무거워질까요

Virtual Thread를 도입하면서 기대하는 것은 수백만 개를 만들어도 가벼운 동시성입니다. 캐리어 스레드(OS 스레드) 소수 위에 가상 스레드 수만 개를 올려두고, 블로킹 호출이 발생하면 가상 스레드는 캐리어 스레드에서 내려가(unmount) 다른 가상 스레드가 그 캐리어를 쓸 수 있게 양보합니다. 그런데 특정 상황에서는 이 양보가 일어나지 않고 가상 스레드가 캐리어 스레드에 "고정(pinned)"된 채 블로킹됩니다. 이렇게 되면 그 캐리어 스레드는 다른 가상 스레드를 전혀 처리하지 못해, 결국 동시성이 캐리어 스레드 개수로 축소됩니다.

문제는 이 현상이 조용히 일어난다는 것입니다. 부하 테스트에서 처리량이 예상보다 훨씬 낮게 나오고, 원인을 찾아보면 흔한 라이브러리 코드 안의 synchronized 블록이 범인인 경우가 많습니다.

 

핵심 개념 1 — 피닝이 발생하는 두 가지 경우

첫째, synchronized 블록/메서드 안에서 블로킹 작업을 수행할 때입니다. JDK 21~23까지는 synchronized로 잠근 모니터를 쥔 채로 블로킹 호출을 하면 JVM이 가상 스레드를 캐리어에서 분리할 수 없었습니다. 둘째, JNI(네이티브 코드) 호출 중에 블로킹할 때입니다. 네이티브 프레임이 스택에 있는 동안은 JVM이 가상 스레드를 다른 캐리어로 옮길 수 없습니다.

중요한 변화가 있습니다. JEP 491(JDK 24)은 synchronized로 인한 피닝 문제를 근본적으로 해결했습니다. 다만 JNI로 인한 피닝은 JDK 24에서도 여전히 남아 있고, JDK 24 미만 버전을 쓰는 프로덕션 환경은 여전히 synchronized 피닝에 노출돼 있습니다.

 

핵심 개념 2 — 피닝 감지하기
# 1. JFR(Java Flight Recorder)로 jdk.VirtualThreadPinned 이벤트 기록
java -XX:StartFlightRecording=filename=app.jfr,settings=profile MyApp

# 2. 피닝 발생 시 스택 트레이스를 즉시 로그로 출력 (문턱값 20ms 초과 시)
java -Djdk.tracePinnedThreads=full MyApp

tracePinnedThreads=full은 피닝이 20ms 넘게 지속될 때마다 그 시점의 전체 스택을 표준 출력에 찍어줍니다. 로컬 개발 중 의심 가는 코드 경로를 빠르게 확인할 때 유용하고, 운영 환경에서는 JFR로 지속 수집해 나중에 분석하는 편이 오버헤드가 적습니다.

 

 

예제 — synchronized를 ReentrantLock으로 교체하기
// 피닝 위험: synchronized 블록 안에서 블로킹 I/O 호출
public class LegacyCache {
    private final Map<String, String> store = new HashMap<>();

    public synchronized String getOrFetch(String key) {
        if (!store.containsKey(key)) {
            String value = httpClient.fetch(key); // 블로킹 I/O — 캐리어 고정!
            store.put(key, value);
        }
        return store.get(key);
    }
}

// 개선: ReentrantLock은 가상 스레드 인식 구현이라 언마운트가 정상 동작
public class VirtualThreadFriendlyCache {
    private final Map<String, String> store = new HashMap<>();
    private final ReentrantLock lock = new ReentrantLock();

    public String getOrFetch(String key) {
        lock.lock();
        try {
            if (!store.containsKey(key)) {
                String value = httpClient.fetch(key); // 언마운트되어 캐리어 반납
                store.put(key, value);
            }
            return store.get(key);
        } finally {
            lock.unlock();
        }
    }
}

java.util.concurrent.locks.ReentrantLock은 애초에 가상 스레드를 염두에 두고 구현돼 있어, 락을 쥔 채로 블로킹해도 가상 스레드가 정상적으로 캐리어에서 분리됩니다.

 

실무 도입 시 이것만은 챙기세요
1. JDBC 드라이버 호환성을 먼저 확인하세요 — 사용 중인 JDBC 드라이버와 커넥션 풀이 가상 스레드 친화적인지 확인해야 합니다.
2. 핫 패스의 synchronized부터 우선 교체하세요 — 트래픽이 몰리는 핫 패스부터 우선순위를 정해 ReentrantLock으로 교체합니다.
3. JDK 24 이상으로 올릴 수 있다면 우선 검토하세요 — JEP 491 적용 버전으로 올리면 synchronized 피닝 문제 자체가 사라집니다.

 

마무리 — 3줄 요약

① 가상 스레드는 synchronized 블록 안에서의 블로킹이나 JNI 네이티브 호출 중 블로킹 시 캐리어 스레드에 고정돼 동시성이 무너집니다.
② -Djdk.tracePinnedThreads=full이나 JFR의 jdk.VirtualThreadPinned 이벤트로 피닝 발생 지점을 구체적으로 찾아낼 수 있습니다.
③ JDK 24(JEP 491)는 synchronized 피닝을 해결했지만, 그 이전 버전이거나 JNI 호출이 있다면 ReentrantLock으로의 교체가 여전히 필요합니다.
