백엔드

한 줄 요약 — 레코드, sealed 인터페이스, 레코드 패턴, switch 패턴 매칭이 함께 맞물리면서, 자바에서도 데이터 모델링과 분기 처리를 대수적 데이터 타입에 가깝게 표현할 수 있게 됐습니다.

 

데이터 클래스, 언제까지 손으로 채우실 건가요

자바에서 데이터만 담는 불변 클래스를 만들려면 오랫동안 필드·생성자·getter·equals/hashCode/toString을 손으로 다 채워야 했습니다. Lombok이 보일러플레이트를 줄여줬지만 그건 애노테이션 프로세서에 의존한 우회로였습니다. 자바 16의 레코드부터 최근 버전의 레코드 패턴, sealed 인터페이스, switch 패턴 매칭까지 몇 개 버전에 걸쳐 추가된 기능들이 합쳐지면서, 이제는 언어 차원에서 훨씬 선언적인 모델링이 가능해졌습니다.

 

핵심 개념 1 — 레코드가 보일러플레이트를 없앱니다

레코드는 "이 클래스는 필드 몇 개를 그대로 담는 불변 데이터"라는 의도를 한 줄로 선언하게 해줍니다. record Point(int x, int y) {} 라고 쓰면 컴파일러가 접근자, equals/hashCode/toString, 표준 생성자를 자동 생성합니다. 필드는 자동으로 final이라 불변성이 보장됩니다.

 

핵심 개념 2 — sealed 인터페이스가 허용된 하위 타입을 제한합니다

sealed 인터페이스는 "이 타입을 상속할 수 있는 타입은 여기 나열한 것뿐"이라고 컴파일러에 선언하는 기능입니다. 결제 결과처럼 성공 아니면 몇 가지 실패 사유 중 하나라는 것이 명확한 도메인에서, sealed 인터페이스와 레코드를 결합하면 다른 언어의 대수적 데이터 타입과 거의 동일한 모델링이 됩니다.

 

핵심 개념 3 — 레코드 패턴과 switch가 분해와 분기를 한 번에

기존 자바에서 타입에 따라 분기하며 내부 필드까지 꺼내 쓰려면 instanceof 캐스팅과 접근자 호출을 반복해야 했습니다. 레코드 패턴은 이를 타입 검사와 필드 분해를 동시에 하도록 바꿔줍니다. switch 패턴 매칭과 결합하면 sealed 타입의 모든 경우를 다뤘는지 컴파일 타임에 검증(exhaustiveness)할 수 있어, 새 하위 타입 추가 시 놓친 분기를 즉시 찾아줍니다.

 

예제 — 코드 비교
sealed interface PaymentResult permits Approved, Declined, NetworkError {}
record Approved(String transactionId, long amountCents) implements PaymentResult {}
record Declined(String reasonCode) implements PaymentResult {}
record NetworkError(int httpStatus) implements PaymentResult {}

String message = switch (result) {
    case Approved(String txId, long amount) ->
        "승인: " + txId + " / " + amount + "원";
    case Declined(String reason) ->
        "거절: " + reason;
    case NetworkError(int status) when status >= 500 ->
        "서버 오류(" + status + ") - 재시도 가능";
    case NetworkError(int status) ->
        "네트워크 오류(" + status + ")";
};
// PaymentResult에 새 하위 타입을 추가하면
// 이 switch가 모든 경우를 안 다룰 시 컴파일 에러 발생

 

구분 이전 방식 레코드 + 패턴 매칭
데이터 클래스 정의 필드·생성자·getter 수동 작성 record 한 줄
타입 분기 instanceof 캐스팅 반복 switch 패턴 매칭
누락된 분기 감지 런타임에야 발견 컴파일 타임 검사

 

실무 도입 시 이것만은 챙기세요
1. 모든 클래스를 레코드로 바꾸려 하지 마세요 — 가변 상태나 복잡한 생명주기를 가진 객체까지 레코드로 바꾸면 설계가 어색해집니다.
2. sealed 계층은 도메인이 실제로 닫혀 있을 때 쓰세요 — 경우의 수를 우리가 다 안다는 확신이 있을 때 가치가 큽니다.
3. exhaustiveness 검사를 안전망으로 활용하세요 — default 분기를 습관적으로 넣으면 이 안전망이 무력화됩니다.

 

마무리 — 3줄 요약

① 레코드는 불변 데이터 클래스의 보일러플레이트를 언어 차원에서 제거하고, sealed 인터페이스는 허용된 하위 타입을 컴파일러가 알게 합니다.
② 레코드 패턴은 instanceof/switch에서 타입 검사와 필드 분해를 동시에 수행합니다.
③ sealed 타입과 switch 패턴 매칭을 결합하면 모든 경우를 다뤘는지 컴파일 타임에 검증할 수 있습니다.
