MCP만으로는 부족하다 — 에이전트끼리 대화하는 A2A 프로토콜

2026. 8. 15. · AI

한 줄 요약 — 도구 연결 표준인 MCP에 이어, 서로 다른 회사·프레임워크의 에이전트끼리 작업을 위임하는 A2A(Agent2Agent) 프로토콜이 왜 필요한지 정리했습니다.

 

왜 지금 A2A인가

한동안 "에이전트 상호운용성" 논의는 MCP 하나로 수렴되는 듯 보였습니다. 하지만 MCP는 에이전트가 도구·데이터 소스에 접근하는 방식을 표준화한 것이지, 서로 다른 벤더가 만든 에이전트끼리 작업을 위임하고 진행 상황을 주고받는 문제는 다루지 않습니다.

실무에서 여러 팀이 각자 프레임워크로 에이전트를 만들다 보면, "내 에이전트가 파트너사 에이전트에게 작업을 맡기고 결과를 받는" 협업이 필요해집니다. 이 빈틈을 메우려는 시도가 Agent2Agent(A2A) 계열 프로토콜이며, MCP와 상호 보완적으로 함께 논의되는 경우가 늘고 있습니다.

 

MCP와 A2A, 무엇이 다른가
항목 MCP A2A
연결 대상 도구, 데이터 소스 다른 에이전트(원격 서비스)
핵심 단위 Tool, Resource Task, Agent Card
통신 방향 단방향 호출 양방향, 장시간 작업
대표 시나리오 DB 조회, 파일 읽기 하위 에이전트에 조사·예약 위임

 

두 프로토콜은 경쟁 관계라기보다, MCP가 에이전트-도구 축을, A2A가 에이전트-에이전트 축을 맡는 형태로 자리를 잡아가고 있습니다.

 

핵심 개념: Agent Card와 Task 생명주기

A2A에서 각 에이전트는 자신의 능력을 알리는 Agent Card(JSON 메타데이터)를 공개합니다. 여기엔 지원하는 스킬, 인증 방식, 입출력 형식이 담기며, 요청자는 이 카드를 보고 어떤 에이전트에게 작업을 맡길지 판단합니다.

작업은 Task로 표현되며, 생성 → 진행 중 → (필요 시) 추가 입력 요청 → 완료/실패의 생명주기를 갖습니다. 단순 요청-응답이 아니라 "사람 승인 대기" 같은 장시간 상호작용을 표준적으로 표현하기 위함입니다.

 

예제: Agent Card 선언
{
  "name": "flight-search-agent",
  "description": "항공권 검색 및 가격 비교 에이전트",
  "url": "https://partner.example.com/a2a",
  "capabilities": { "streaming": true, "pushNotifications": false },
  "skills": [
    { "id": "search-flight", "description": "출발지/도착지/날짜로 항공권 검색" }
  ]
}

요청 에이전트는 이 카드의 skills를 보고 search-flight 작업을 Task로 생성해 위임합니다.

 

실무 도입 시 이것만은 챙기세요
1. 아직 표준이 유동적 — 초기 단계라 사양이 바뀔 수 있으니 추상화 계층을 얇게 유지
2. 신뢰 경계를 먼저 설계 — 외부 에이전트에 작업을 위임하는 순간 새 공격 표면이 생기므로 Agent Card 출처 검증 필수
3. MCP와 역할 구분 — 도구 접근인지, 다른 에이전트 위임인지 먼저 구분하고 프로토콜 선택
4. Task 상태 로깅 — 장시간 비동기 작업이 많으므로 상태 전이를 추적해야 장애 원인 파악이 쉬움

 

마무리 — 3줄 요약

① MCP가 에이전트와 도구를 연결한다면, A2A는 서로 다른 벤더의 에이전트끼리 작업을 위임·협상하는 계층을 표준화하려 합니다.
② 핵심 단위는 능력을 알리는 Agent Card와, 상태 전이를 갖는 Task입니다.
③ 아직 표준이 유동적인 초기 단계이므로 얇은 추상화와 신뢰 경계 설계가 우선입니다.
