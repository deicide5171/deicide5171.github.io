세 번째 클라이언트가 등장했다 — Backend for Agent, 에이전트 전용 API 설계

시스템 설계

한 줄 요약 — "우리 API를 AI 에이전트가 직접 호출하게 해주세요"라는 요구는 화면 맞춤이 아니라 컨텍스트 예산·구조화된 에러·재시도 안전성이라는 전혀 다른 설계 기준을 요구합니다. 웹·앱을 위한 BFF 패턴이 풀지 못하는 에이전트 전용 API 계층, Backend for Agent의 설계 원칙과 2026년 IETF 초안을 정리했습니다.

 

왜 지금 이 설계가 필요한가

"우리 주문 API를 AI 에이전트가 직접 호출해서 고객 문의에 답하게 해주세요." 몇 년 전이었다면 이 요구는 웹과 모바일 클라이언트를 구분하던 BFF(Backend for Frontend) 패턴으로 충분히 풀렸을 것입니다. 화면마다 필요한 데이터 모양이 다르니 클라이언트별로 집계 계층을 하나씩 두면 됐습니다. 그런데 에이전트는 화면이 없습니다. 에이전트는 응답을 렌더링하지 않고 다음 추론의 입력으로 소비합니다. 이 차이가 API 설계의 전제를 통째로 바꿉니다.

사람이 쓰던 API를 그대로 에이전트에게 노출하면 두 가지 문제가 바로 드러납니다. 첫째, 응답 하나가 에이전트의 컨텍스트 윈도우를 그대로 잡아먹습니다 — 사람은 화면에서 필요한 부분만 눈으로 훑지만, 에이전트는 응답 전체를 토큰으로 "기억"해야 합니다. 둘째, 네트워크 타임아웃이나 모호한 에러에 대해 에이전트는 사람처럼 "다시 시도하기" 버튼을 누르는 게 아니라 같은 요청을 스스로 재시도하는데, 이때 API가 멱등성을 보장하지 않으면 중복 주문이나 중복 결제가 그대로 발생합니다. 2026년 상반기 IETF에 제출된 "Agent-Friendly HTTP API Profile" 초안이 이 문제를 처음으로 표준화 논의 테이블에 올린 것도 이런 배경에서입니다. 웹·앱에 이은 세 번째 클라이언트 유형, 에이전트를 위한 API 계층 — Backend for Agent(BFA) — 을 언제, 어떻게 설계할지가 이제 실무 판단의 영역이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"에이전트가 우리 API를 쓰게 해주세요"라는 말은 실제로 네 가지 분리된 질문을 담고 있습니다. 에이전트에게 어떤 도구 단위로 기능을 나눠 보여줄 것인가(엔드포인트 1:1 노출이 아니라), 응답을 얼마나 압축해 컨텍스트 예산을 지킬 것인가, 실패했을 때 에이전트가 스스로 복구할 수 있도록 에러를 얼마나 설명적으로 만들 것인가, 그리고 같은 요청이 여러 번 들어와도 결과가 달라지지 않도록 멱등성을 어디에 보장할 것인가. 이 네 가지는 사람을 위한 REST API 설계 원칙(RESTful, 리소스 중심 설계)과 상당 부분 충돌합니다. 리소스마다 깔끔하게 엔드포인트를 쪼개는 설계가 사람에게는 이해하기 쉽지만, 에이전트에게는 도구가 너무 많고 저수준이라 어떤 조합을 호출해야 하는지 스스로 판단하기 어려워집니다.

 

전체 시스템에서의 위치

기존 BFF는 웹 클라이언트용 계층과 모바일 클라이언트용 계층을 코어 서비스 앞에 나란히 둡니다. BFA는 이 옆에 나란히 서는 세 번째 계층이 아니라, 완전히 다른 축의 설계 기준(토큰 예산, 재시도 안전성)을 갖는 계층으로 봐야 합니다.

 

 

코어 서비스의 리소스 API는 그대로 두고, BFA 계층이 "여러 리소스 호출을 묶은 고수준 도구"로 재포장합니다. 예를 들어 "주문 취소"라는 도구 하나가 내부적으로는 주문 조회 → 취소 가능 여부 확인 → 결제 환불 요청 → 상태 업데이트라는 네 번의 코어 API 호출을 순서대로 묶는 식입니다. 에이전트는 이 묶음을 도구 하나로 보고, 실패 시 어느 단계에서 실패했는지를 구조화된 에러로 돌려받습니다. MCP 서버를 코어 API 앞에 두는 구성이 실무에서 이 BFA 계층의 가장 흔한 구현체입니다.

 

선택의 트레이드오프
설계 축 사람을 위한 API(BFF) 에이전트를 위한 API(BFA)
단위 화면에 맞춘 리소스 집계 작업 단위로 묶은 고수준 도구
응답 크기 화면에 맞게 일부만 노출 매 턴 컨텍스트에 남으므로 더 공격적으로 압축
에러 형태 사람이 읽을 메시지 + 코드 원인·재시도 가능 여부·다음 행동까지 구조화
재시도 안전성 사람이 수동으로 판단 멱등성 키를 모든 쓰기 엔드포인트에 필수화
네이밍·상태값 일관성 엔드포인트별로 다소 느슨해도 됨 전체 API에 걸쳐 완전히 통일 필요

 

가장 흔한 함정은 기존 리소스 API에 OpenAPI 스펙만 붙여 "에이전트도 이거 보고 알아서 쓰겠지"라고 넘기는 것입니다. 엔드포인트 하나하나를 도구로 그대로 노출하면 도구 목록이 크고 저수준이라 에이전트가 적절한 조합을 찾는 데 실패율이 올라갑니다. 반대로 BFA 계층을 처음부터 너무 두껍게 만들면 — 모든 가능한 조합을 미리 고수준 도구로 예측해 만들면 — 업무 요구가 바뀔 때마다 BFA 계층을 다시 설계해야 하는 유지보수 부담이 커집니다. 트래픽이 적고 에이전트 사용 패턴이 아직 불확실한 초기 단계라면 코어 API를 그대로 노출하되 에러 구조화와 멱등성 키만 먼저 갖추는 것이, 전용 BFA 계층을 미리 구축하는 것보다 낫습니다.

  }

POST /tools/cancel_order HTTP/1.1

Idempotency-Key: agent-session-8f2a-cancel-order-991

{ "order_id": "ORD-20261013-0042" }

 

구조화된 에러에서 핵심은 retryable 같은 필드로 "이 실패가 재시도하면 해결되는 종류인가"를 명시하는 것입니다. 이게 없으면 에이전트는 일시적 네트워크 오류와 영구적인 비즈니스 규칙 위반을 구분하지 못하고 똑같이 재시도를 반복하거나, 반대로 재시도하면 되는 상황에서 포기해버립니다. Idempotency-Key는 클라이언트(에이전트 런타임)가 세션·작업 단위로 생성해, 같은 키로 들어온 요청은 실제 작업을 중복 실행하지 않고 이전 결과를 그대로 돌려주도록 서버가 구현해야 합니다.

 

실제 프로젝트 진행 순서

1단계: 먼저 코어 API에 멱등성 키와 구조화된 에러부터 추가합니다. BFA 계층을 새로 만들기 전에, 가장 비용이 큰 실패 모드(중복 쓰기)부터 코어 API 레벨에서 막습니다.

2단계: 에이전트가 실제로 호출하는 패턴을 로그로 관찰합니다. 어떤 리소스 조합이 반복적으로 함께 호출되는지 확인한 뒤에야 그 조합을 고수준 도구로 묶습니다 — 추측으로 먼저 설계하지 않습니다.

3단계: 도구 설명(스키마 문서)을 API 계약의 일부로 취급합니다. 엔드포인트 코드만 바뀌고 도구 설명이 그대로면 에이전트가 변경된 동작을 모른 채 호출합니다.

4단계: 응답 크기를 턴 단위로 측정합니다. 도구 하나의 평균 응답이 에이전트 컨텍스트의 몇 퍼센트를 차지하는지 재보고, 과도하게 크면 페이지네이션이나 요약 필드를 먼저 추가합니다.

 

주의 — BFA 계층을 만든다고 코어 API의 일관성 문제가 저절로 해결되지는 않습니다. pending과 IN_PROGRESS처럼 엔드포인트마다 상태값 표기가 제각각이면, 그 위에 아무리 좋은 도구 설명을 얹어도 에이전트는 오동작합니다. 멱등성 키 역시 서버 쪽 구현 없이 헤더만 받아주는 흉내만 내면 의미가 없습니다 — 실제로 같은 키로 중복 요청을 보내보는 테스트를 반드시 거치세요.

 

정리

에이전트는 화면이 아니라 다음 추론의 입력으로 응답을 소비하므로, 토큰 예산·구조화된 에러·멱등성이라는 BFF와는 다른 설계 기준이 필요합니다. 엔드포인트를 그대로 도구로 노출하지 말고, 실제 호출 패턴을 관찰한 뒤 고수준 도구로 묶는 BFA 계층을 점진적으로 구축하세요. 전용 계층을 만들기 전에 멱등성 키와 재시도 가능 여부를 포함한 구조화된 에러부터 코어 API에 갖추는 것이 비용 대비 효과가 가장 큽니다.
