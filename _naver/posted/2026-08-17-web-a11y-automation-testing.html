axe-core로 완성하는 웹 접근성 자동화 테스트 파이프라인

2026. 8. 17. · 프론트엔드

한 줄 요약 — 자동화 도구가 잡을 수 있는 영역과 잡을 수 없는 영역을 정확히 구분하고, axe-core와 Playwright, Lighthouse CI를 조합해 접근성 회귀를 매 PR마다 검증하는 파이프라인을 구축해봅니다.

 

왜 지금 웹 접근성 자동화인가요

유럽 접근성법(European Accessibility Act)이 시행되면서 EU 시장을 대상으로 하는 서비스는 접근성 준수가 더 이상 권장 사항이 아니라 법적 의무가 되었습니다. 국내에서도 공공기관을 넘어 일부 민간 서비스까지 웹 접근성 인증 요구가 확대되는 흐름이 이어지고 있습니다. 이제 접근성은 출시 직전에 한 번 확인하는 체크리스트가 아니라, 매 PR마다 검증해야 하는 회귀 테스트 대상으로 다뤄야 합니다.

문제는 수동 접근성 감사에 시간과 비용이 많이 들고, 하루에도 여러 번 배포하는 요즘 릴리스 주기와는 속도가 맞지 않는다는 점입니다. 반면 axe-core 같은 자동화 도구는 코드가 바뀔 때마다 몇 초 안에 실행할 수 있어, CI 파이프라인에 넣어두면 접근성 회귀를 커밋 단위로 잡아낼 수 있습니다.

최근에는 Playwright가 접근성 트리 스냅샷과 axe-core 결합(@axe-core/playwright)을 공식 지원 범위로 다루고, Storybook의 a11y addon과 eslint-plugin-jsx-a11y 같은 정적 분석 도구까지 생태계가 성숙해지면서, 개발 초기 단계부터 접근성을 검증하는 '시프트 레프트' 접근이 프론트엔드 팀의 표준 관행으로 자리 잡는 중입니다.

 

자동화가 잡아낼 수 있는 것과 없는 것

자동화 도구를 도입하기 전에 가장 먼저 정리해야 할 것은 기대치입니다. axe-core 같은 도구는 마크업에 드러나는 정적 규칙 위반은 정확히 잡지만, '의미가 맞는지'는 판단하지 못합니다.

구분 자동 탐지 예시
정적 규칙 위반 가능 alt 속성 누락, 폼 라벨 누락, 색상 대비 미달, 중복 id
ARIA 오용 패턴 부분적 잘못된 role 지정, 필수 aria-* 속성 누락
논리적 흐름·문맥 수동 필요 탭 순서가 시각적 순서와 일치하는지, 안내 문구가 자연스러운지
실제 보조기술 호환성 수동 필요 실제 스크린리더(NVDA, VoiceOver)로 읽었을 때 이해가 되는지

정확한 비율은 도구·측정 기준마다 다르지만, axe-core 등 자동화 도구 개발사들은 대체로 '자동화만으로는 전체 WCAG 이슈 중 일부만 탐지할 수 있다'는 점을 공통으로 안내합니다. 자동화는 접근성 검증을 대체하는 것이 아니라, 반복적으로 재발하는 이슈를 저비용으로 걸러내는 1차 방어선으로 이해하는 것이 정확합니다.

 

테스트 레벨별 접근성 검증 도구

접근성 테스트도 일반적인 테스트 피라미드처럼 레벨을 나눠 배치하는 것이 효율적입니다.

레벨 대표 도구 검증 대상
정적 분석(커밋 전) eslint-plugin-jsx-a11y JSX 마크업 규칙 위반을 편집 시점에 즉시 경고
단위/컴포넌트 jest-axe, vitest-axe 컴포넌트 렌더 결과에 axe 규칙 적용, 회귀 방지
E2E @axe-core/playwright 실제 라우팅·상태가 반영된 페이지 전체 스캔
품질 게이트 Lighthouse CI 접근성 점수 임계값을 CI에서 강제

각 레벨은 서로 다른 실패 지점을 잡습니다. 정적 분석은 컴포넌트 작성 순간의 실수를 막고, 단위 테스트는 컴포넌트 단위 회귀를 잡으며, E2E는 여러 컴포넌트가 조합된 실제 페이지에서만 드러나는 문제(포커스 순서, 동적으로 삽입된 콘텐츠 등)를 잡습니다.

 

예제: Playwright + axe-core로 E2E 접근성 스캔

아래는 상품 목록 페이지를 대상으로 심각한 접근성 위반이 없는지 자동으로 검증하는 예제입니다. impact가 critical·serious인 위반만 우선 실패로 처리하는 전략을 함께 적용했습니다.

// a11y.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('상품 목록 페이지는 심각한 접근성 위반이 없어야 한다', async ({ page }) => {
  await page.goto('/products');

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag22aa'])
    .exclude('#third-party-widget')
    .analyze();

  const blocking = results.violations.filter(
    (v) => v.impact === 'critical' || v.impact === 'serious'
  );

  expect(blocking, JSON.stringify(blocking, null, 2)).toEqual([]);
});

withTags로 검사 기준을 WCAG 버전·레벨 단위로 명시할 수 있고, exclude로 통제할 수 없는 외부 위젯 영역을 스캔에서 제외할 수 있습니다. 처음부터 모든 위반을 실패로 처리하면 팀의 반발이 크므로, impact 값으로 critical·serious만 우선 게이트에 걸고 moderate·minor는 리포트로만 축적하는 전략이 현실적입니다.

 

 

실무 도입 시 이것만은 챙기세요
1. 게이트 정책은 단계적으로 강화 — 처음부터 전체 실패 처리하면 기존 코드베이스 누적 이슈로 파이프라인이 곧바로 막힙니다. critical·serious부터 시작하세요.
2. 동적 콘텐츠·색상 대비는 오탐 가능성 유의 — 그라디언트 배경이나 이미지 위 텍스트는 자동 계산이 부정확할 수 있습니다.
3. 키보드 내비게이션은 부분 자동화 — Tab 시퀀스는 스크립트로 검증 가능하지만 포커스 트랩·논리적 순서는 수동 리뷰가 필요합니다.
4. 스크린리더 실사용 테스트는 자동화가 대체 불가 — NVDA·VoiceOver로 주기적 수동 감사를 릴리스 사이클에 포함하세요.
5. WCAG 버전을 명시적으로 관리 — 팀의 목표 준수 레벨(예: AA)을 설정에 명시해 기준이 흔들리지 않게 하세요.

 

마무리 — 3줄 요약

① 자동화 도구는 정적 규칙 위반은 정확히 잡지만 논리적 흐름이나 실제 보조기술 호환성까지는 판단하지 못하므로, 자동화와 수동 감사를 함께 운영해야 합니다.
② eslint-plugin-jsx-a11y(정적 분석) → jest-axe(단위) → @axe-core/playwright(E2E) → Lighthouse CI(품질 게이트) 순으로 레벨을 나눠 배치하면 서로 다른 실패 지점을 효율적으로 잡을 수 있습니다.
③ CI 게이트는 처음부터 전체 실패 처리하지 말고 impact가 critical·serious인 위반부터 단계적으로 강제해야 팀의 저항 없이 정착시킬 수 있습니다.
