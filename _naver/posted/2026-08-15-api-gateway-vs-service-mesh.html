API Gateway와 Service Mesh, 트래픽 관리는 어디서 해야 할까요

2026. 8. 15. · 시스템 설계

한 줄 요약 — MSA 환경에서 API Gateway는 외부에서 들어오는 트래픽을, Service Mesh는 서비스 간 트래픽을 각각 담당한다는 점을 정리하고, 언제 무엇을 써야 하는지 소개해 드리겠습니다.

 

왜 지금 이 고민이 생길까요

서비스를 MSA로 쪼개다 보면 트래픽 관리 문제가 두 군데에서 동시에 나타납니다. 하나는 외부 요청을 어떻게 인증하고 라우팅할지의 문제이고, 다른 하나는 서비스 수가 늘어나면서 서비스끼리 주고받는 호출을 어떻게 안전하게 유지할지의 문제입니다. 이 두 가지를 한 도구로 해결하려다 보면 게이트웨이에 너무 많은 역할을 몰아주거나, 반대로 메시를 도입해놓고도 엣지 문제는 그대로 남는 경우가 생깁니다.

최근에는 Istio, Linkerd 같은 Service Mesh와 Kong, Envoy Gateway 같은 API Gateway가 함께 언급되는 일이 많아지면서, "게이트웨이 하나로 다 되는 거 아닌가"라는 질문도 자주 나옵니다. 오늘은 두 도구가 실제로 어떤 역할을 나눠 맡는지, 그리고 언제 함께 써야 하는지 정리해 보겠습니다.

 

두 도구의 역할 비교

API Gateway는 클러스터 경계, 즉 엣지에서 동작하는 단일 진입점입니다. 외부 클라이언트 요청을 받아 인증·인가를 처리하고, 적절한 백엔드로 라우팅하며, 레이트리밋 같은 정책을 적용합니다. 반면 Service Mesh는 클러스터 내부, 서비스와 서비스 사이의 통신을 다룹니다. 각 서비스 옆에 사이드카 프록시를 붙여 mTLS를 자동 적용하고, 회로 차단이나 재시도, 세밀한 트래픽 분할을 관측 가능한 형태로 제공합니다.

구분 API Gateway Service Mesh
트래픽 위치 외부 → 내부(남북) 서비스 간(동서)
주 관심사 인증, 레이트리밋, 라우팅 mTLS, 회로 차단, 재시도
배치 단위 엣지에 소수 배치 서비스마다 사이드카
대표 도구 Kong, Envoy Gateway Istio, Linkerd

 

언제 무엇을 써야 할까요

서비스 수가 적고 서비스 간 호출 구조가 단순하다면 API Gateway만으로도 충분한 경우가 많습니다. 엣지에서 인증과 레이트리밋만 잘 잡아도 초기 단계 요구사항은 대부분 해결됩니다. 반면 서비스가 늘어나고 mTLS 강제나 세밀한 트래픽 분할, 장애 격리가 필요해지는 시점부터는 Service Mesh 도입을 검토해볼 만합니다.

두 도구를 함께 쓰는 조합도 흔합니다. Gateway가 엣지에서 외부 트래픽을 인증·라우팅한 뒤 클러스터 내부로 넘기고, 이후 서비스 간 호출은 Mesh가 mTLS와 회로 차단으로 관리하는 구조입니다. 다만 사이드카를 모든 서비스에 붙이는 구조는 운영 복잡도를 크게 늘리므로, 정말 그 정도 제어가 필요한지부터 확인하시는 것을 권해드립니다.

 

설정 예제로 살펴보기

먼저 Envoy Gateway 기준 엣지 레벨 레이트리밋 설정 예시입니다.

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: api-ratelimit
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: orders-route
  rateLimit:
    type: Global
    global:
      rules:
        - clientSelectors:
            - headers:
                - name: x-api-key
                  type: Distinct
          limit:
            requests: 100
            unit: Minute

다음은 Istio 기준 서비스 간 회로 차단(DestinationRule) 설정 예시입니다.

apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: payments-circuit-breaker
spec:
  host: payments.svc.cluster.local
  trafficPolicy:
    connectionPool:
      http:
        http1MaxPendingRequests: 50
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 30s
      baseEjectionTime: 30s

 

실무 도입 시 이것만은 챙기세요
1. Mesh 도입 전 범위 검토 — 사이드카는 모든 파드의 리소스 사용량을 늘리므로 필요한 네임스페이스부터 단계적으로 적용
2. Gateway 이중화 — 단일 진입점이 장애 나면 전체 트래픽에 영향을 주므로 헬스체크와 이중화 필수
3. 정책 중복 방지 — 레이트리밋은 Gateway에서, 재시도 정책은 Mesh에서 정의하는 식으로 경계를 명확히 구분
4. 관측성 일관성 — 두 계층을 함께 쓸 때는 분산 트레이싱을 양쪽 모두 연결해야 장애 지점을 빠르게 좁힐 수 있음

 

마무리 — 3줄 요약

① API Gateway는 엣지에서 외부→내부 트래픽의 인증·라우팅·레이트리밋을 담당하고, Service Mesh는 서비스 간 트래픽의 mTLS·회로 차단을 담당합니다.
② 서비스 수와 호출 복잡도가 낮으면 Gateway만으로 충분하며, 복잡도가 커질 때 Mesh 도입을 단계적으로 검토하는 것이 안전합니다.
③ 함께 쓸 때는 정책 중복을 피하고 역할 경계를 명확히 나눠야 운영 부담을 줄일 수 있습니다.
