쿠버네티스 Pod가 Pending에서 안 넘어갈 때 체크리스트

인프라

한 줄 요약 — Pending은 스케줄러가 노드를 못 찾았다는 뜻이므로 kubectl describe pod의 Events부터 확인하면 원인이 대부분 그대로 나옵니다.

 

왜 Pending은 원인이 안 보이는가

Running이나 CrashLoopBackOff는 최소한 컨테이너가 뜨긴 떴다는 신호지만, Pending은 아예 노드에 배치조차 안 됐다는 뜻이라 로그를 볼 컨테이너 자체가 없습니다. 결국 스케줄러가 왜 배치하지 못했는지를 describe의 Events에서 찾아야 합니다.

 

Pending의 흔한 원인 4가지
원인 Events 메시지 예시 해결
리소스 부족 Insufficient cpu/memory 노드 추가 또는 요청량 축소
PVC 바인딩 실패 unbound PersistentVolumeClaims StorageClass·PV 상태 확인
노드 어피니티 불일치 didn't match node affinity 라벨·톨러레이션 확인

 

진단 순서
# 1. 이벤트 확인
kubectl describe pod <pod-name> | grep -A 20 Events

# 2. 클러스터 리소스 여유 확인
kubectl top nodes

# 3. PVC 상태 확인
kubectl get pvc

# 4. 노드 셀렉터·어피니티 확인
kubectl get nodes --show-labels

Events에 "0/5 nodes are available: 3 Insufficient cpu..."처럼 노드별로 왜 제외됐는지 구체적으로 나옵니다. 이 메시지를 그대로 읽는 것이 가장 빠른 진단법입니다.

 

실무 포인트

리소스 요청(requests)을 실제 사용량보다 과도하게 크게 잡으면, 클러스터 자원이 남아 있어도 스케줄링이 안 됩니다. 실제 사용량 프로파일링 후 현실적으로 조정해야 합니다.

오토스케일러가 있어도 즉시 노드가 늘지 않습니다. 새 노드 프로비저닝에는 보통 1~3분이 걸리므로 트래픽 급증 직후 잠깐의 Pending은 정상일 수 있습니다.

주의 — PVC가 특정 존의 PV에 묶여 있는데 Pod는 다른 존에 스케줄링하려 하면 영원히 Pending입니다. 멀티 AZ 클러스터에서 스토리지와 컴퓨트의 존을 맞추는 것을 놓치기 쉽습니다.
