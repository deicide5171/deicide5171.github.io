피처 플래그, 직접 만들 것인가 LaunchDarkly를 쓸 것인가 — 백엔드 구현 실전

백엔드

한 줄 요약 — 배포와 기능 노출을 분리하는 피처 플래그를 자체 구현할 때 필요한 최소 구조와, LaunchDarkly·Unleash 같은 전용 도구가 그 위에 추가로 해결해주는 문제를 비교해 언제 무엇을 선택할지 정리했습니다.

 

배포와 릴리스를 분리한다는 것

배포(deploy)와 릴리스(release)를 분리하는 것이 피처 플래그의 핵심 가치입니다. 코드는 프로덕션에 배포됐지만 기능은 아직 사용자에게 보이지 않는 상태를 만들 수 있으면, 배포 자체의 위험도가 크게 줄어듭니다. 문제가 생기면 재배포 없이 플래그만 끄면 되고, 카나리 릴리스도 코드 배포와 무관하게 진행할 수 있습니다.

그런데 피처 플래그를 얼마나 진지하게 구현할지는 팀마다 크게 갈립니다. 단순한 온오프 스위치로 시작한 플래그가 몇 년 뒤 수백 개로 불어나 아무도 지우지 못하는 코드 잔해가 되는 경우도 흔하고, 반대로 처음부터 SaaS를 도입했다가 실제로 쓰는 기능은 몇 개뿐이라 비용 대비 효용이 안 맞는 경우도 있습니다.

 

핵심 개념 1 — 피처 플래그의 네 가지 유형
유형 목적 수명
릴리스 플래그 미완성 기능을 배포하되 숨김 짧음(기능 완성 후 제거)
실험 플래그 A/B 테스트 실험 기간 동안만
운영 플래그 장애 시 긴급 차단(킬 스위치) 김(상시 유지)
권한 플래그 요금제·권한별 기능 차등 매우 김(비즈니스 로직)

 

이 구분이 중요한 이유는 유형마다 "언제 지워도 되는가"의 기준이 다르기 때문입니다. 릴리스 플래그는 반드시 제거해야 하는 임시 코드지만, 권한 플래그는 사실상 영구적인 비즈니스 로직이라 같은 방식으로 관리하면 안 됩니다.

핵심 개념 2 — 자체 구현의 최소 구조

실무에서 최소한으로 필요한 구조는 세 가지입니다. ① 평가 컨텍스트 — 사용자, 환경, 요금제 등을 담는 객체, ② 규칙 기반 평가 — 조건과 퍼센티지 롤아웃을 함께 평가, ③ 캐시된 로컬 평가 — 매 요청마다 원격 호출하지 않고 로컬 메모리에서 평가.

핵심 개념 3 — 전용 도구가 추가로 푸는 문제

전용 도구는 감사 추적, 점진적 롤아웃 자동화, 다중 환경 동기화, 비개발자용 관리 UI를 추가로 해결합니다.

기준 자체 구현 LaunchDarkly / Unleash
감사·거버넌스 직접 구현 필요 기본 제공
비개발자 접근성 낮음 높음(전용 대시보드)
벤더 종속 없음 있음(SaaS) / 낮음(Unleash OSS)

 

예제 — Spring Boot 자체 구현 최소 버전
public record EvaluationContext(String userId, String plan, String environment) {}

@Component
public class FeatureFlagEvaluator {
    private final Map<String, FlagRule> localCache;

    public boolean isEnabled(String flagKey, EvaluationContext ctx) {
        FlagRule rule = localCache.get(flagKey);
        if (rule == null || !rule.enabled()) return false;
        if (rule.targetPlans() != null && !rule.targetPlans().contains(ctx.plan())) {
            return false;
        }
        int bucket = Math.abs(ctx.userId().hashCode()) % 100;
        return bucket < rule.rolloutPercentage();
    }
}

퍼센티지 롤아웃에서 사용자 ID를 해시해 버킷을 결정하는 방식은 같은 사용자가 새로고침할 때마다 다른 결과를 보지 않도록 일관성을 보장하는 핵심 장치입니다.

 

실무 도입 시 이것만은 챙기세요
1. 릴리스 플래그는 제거 기한을 티켓으로 걸어두세요 — 안정화 후에도 남은 릴리스 플래그는 코드 복잡도만 높입니다.
2. 로컬 캐시의 폴백 값을 반드시 정하세요 — 설정 서버 장애 시 어떤 값을 반환할지 명시적으로 결정해둬야 장애가 연쇄되지 않습니다.
3. 팀 규모와 플래그 개수로 도구를 결정하세요 — 킬 스위치 몇 개면 자체 구현으로 충분하고, 수십~수백 개 플래그와 비개발자 참여가 필요하면 전용 도구가 유리합니다.

 

마무리 — 3줄 요약

① 피처 플래그는 배포와 릴리스를 분리하지만, 릴리스/실험/운영/권한 네 유형은 수명과 관리 방식이 다릅니다.
② 자체 구현의 최소 구조는 평가 컨텍스트, 규칙 기반 평가, 로컬 캐시이며 사용자 해시 기반 버킷팅으로 일관성을 보장해야 합니다.
③ 전용 도구는 감사·거버넌스·비개발자 접근성을 추가로 제공하므로 규모와 조직 구조에 따라 선택해야 합니다.
