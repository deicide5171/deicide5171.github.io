OFFSET의 함정과 커서 기반 페이지네이션 — 페이지 번호 대신 마지막 위치로 넘기기

2026. 8. 20. · DB·데이터 모델링

한 줄 요약 — OFFSET/LIMIT 페이지네이션은 구현은 쉽지만 뒷페이지로 갈수록 조용히 느려집니다. 커서(키셋) 기반 페이지네이션으로 전환해야 하는 이유와 실무 주의점을 정리했습니다.

 

왜 지금 이 이야기인가

목록 API에 페이지네이션을 붙일 때 가장 먼저 손이 가는 방법은 LIMIT과 OFFSET입니다. 페이지 번호만 받아서 OFFSET (페이지번호-1) * 페이지크기로 변환하면 끝이라 초기 구현 속도가 빠릅니다. 문제는 데이터가 수십만 건을 넘기고 사용자가 뒷페이지까지 파고들기 시작하면서 드러납니다. 같은 쿼리, 같은 페이지 크기인데 1페이지는 즉시 응답하고 200페이지는 눈에 띄게 느려지는 현상을 겪게 됩니다.

원인은 OFFSET의 동작 방식 자체에 있습니다. 데이터베이스는 "몇 번째 행부터 보여줄지"를 미리 알 방법이 없어서, 조건에 맞는 행을 처음부터 순서대로 세면서 OFFSET만큼 스캔한 뒤에야 버리고, 그다음 LIMIT개만 반환합니다. 즉 뒷페이지로 갈수록 실제로 반환하는 행 수는 그대로인데 훑고 지나가야 하는 행 수만 계속 늘어납니다. 무한 스크롤 UI와 대용량 API 목록 조회가 늘면서, 이 문제를 피하는 커서(키셋, keyset) 기반 페이지네이션이 사실상 표준 대안으로 자리잡았습니다.

 

핵심 개념: OFFSET/LIMIT의 동작과 한계

OFFSET은 "건너뛸 행 수"를 지정하는 것처럼 보이지만, 실제로는 정렬된 결과 집합을 처음부터 순회하며 지정된 개수만큼 세어 넘기는 연산입니다. 인덱스를 타더라도 이 "세면서 건너뛰기" 자체는 생략할 수 없어서, 스캔 비용이 대략 OFFSET + LIMIT에 비례해 커집니다.

더 큰 문제는 조회 도중 원본 테이블에 행이 추가·삭제되는 경우입니다. 다음 페이지를 요청하는 시점에는 정렬 순서상 위치가 이미 밀린 상태라, 같은 항목이 두 페이지에 걸쳐 중복 노출되거나 반대로 한 항목이 아예 누락될 수 있습니다.

 

핵심 개념: 커서 기반(키셋) 페이지네이션이란

커서 기반 페이지네이션은 "몇 번째 행인지"가 아니라 "마지막으로 본 행이 어디였는지"를 기준으로 다음 페이지를 요청합니다. 정렬 기준 컬럼(보통 id나 created_at처럼 고유하고 순서를 매길 수 있는 값)의 마지막 값을 커서로 클라이언트에 돌려주고, 다음 요청 때는 WHERE 정렬컬럼 > 커서 ORDER BY 정렬컬럼 LIMIT n 형태로 조회합니다.

이 방식은 앞부분을 세면서 건너뛰는 과정이 없습니다. 인덱스가 커서 값의 위치를 직접 찾아가는(index seek) 방식으로 동작하기 때문에, 몇 페이지째를 요청하든 스캔 비용이 거의 일정하게 유지됩니다.

 

두 방식 비교
기준 OFFSET/LIMIT 커서 기반(Keyset)
다음 페이지 요청 페이지 번호 → OFFSET 값 계산 이전 페이지 마지막 값(커서) 전달
뒷페이지 성능 페이지 번호에 비례해 저하 페이지 번호와 무관하게 거의 일정
특정 페이지 바로 이동 가능 기본적으로 어려움
데이터 변경 중 안정성 항목 중복·누락 가능 커서 기준이라 상대적으로 안정적
대표 사용처 페이지 번호 목록형 화면 무한 스크롤, 대용량 API 목록

 

예제: OFFSET vs 커서 기반 SQL

아래는 200번째 페이지(페이지당 20건)를 OFFSET 방식으로 조회하는 쿼리입니다. 실제로는 앞의 4,000건을 스캔해서 버린 뒤 20건만 반환합니다.

-- OFFSET/LIMIT 방식
SELECT id, title, created_at
FROM articles
ORDER BY id
LIMIT 20 OFFSET 4000;

같은 결과를 커서 기반으로 조회하면, 이전 페이지의 마지막 id(예: 4000)를 커서로 사용해 인덱스로 바로 이동한 뒤 20건만 읽습니다.

-- 커서 기반 방식
SELECT id, title, created_at
FROM articles
WHERE id > 4000
ORDER BY id
LIMIT 20;

정렬 기준이 created_at처럼 값이 중복될 수 있는 컬럼이라면, 동일 시각에 생성된 행 사이의 순서가 흔들려 항목이 누락되거나 중복될 수 있습니다. 이럴 때는 아래처럼 고유한 보조 키(id)를 함께 묶어 정렬·비교 기준으로 삼아 순서를 완전히 고정합니다.

-- created_at이 같은 행이 여러 개일 수 있으므로 id를 보조 정렬 기준으로 추가
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

 

실무 도입 시 이것만은 챙기세요
1. 정렬 기준 컬럼은 반드시 유니크하게 — 중복 가능한 컬럼만으로 커서를 만들면 순서가 보장되지 않아 항목 누락·중복 위험
2. 커서 컬럼에 인덱스가 있는지 확인 — 인덱스가 없으면 매번 전체 스캔이 일어나 OFFSET보다 오히려 느려질 수 있음
3. 커서 값은 원시 값 대신 인코딩(base64 등)해서 노출 — 내부 컬럼명·값 형식이 그대로 노출되지 않도록 함
4. 임의 페이지 점프·정확한 총 개수가 꼭 필요한 화면인지 먼저 확인 — 필요하다면 OFFSET과의 하이브리드 검토
5. 양방향(이전/다음) 탐색이 필요하면 커서를 두 방향 모두 발급하도록 설계

 

마무리 — 3줄 요약

① OFFSET/LIMIT은 앞부분을 스캔해서 버리는 방식이라, 뒷페이지로 갈수록 스캔 비용이 늘어나고 데이터 변경 중에는 중복·누락도 생길 수 있습니다.
② 커서 기반 페이지네이션은 마지막으로 본 위치를 기준으로 인덱스를 직접 탐색해, 페이지 번호와 무관하게 비교적 일정한 성능을 냅니다.
③ 다만 임의 페이지 점프나 정확한 총 개수가 필요한 화면에는 잘 맞지 않으므로, 화면 요구사항에 따라 OFFSET·커서·하이브리드 중 적합한 방식을 선택해야 합니다.
