'매장 반경에 들어오면 알려주세요'라는 요구 — 실시간 지오펜싱, 어디서 판정할 것인가

GIS

한 줄 요약 — '매장 반경에 들어오면 쿠폰을 보내주세요'라는 요구사항은 좌표 비교 한 줄이 아니라 '어디서 판정할 것인가'라는 아키텍처 질문으로 번역됩니다. 디바이스 SDK, 서버 스트리밍 파이프라인, 통신사 네트워크 구독형 모델이라는 세 갈래 선택지의 트레이드오프와 작은 폴링부터 대규모 이벤트 파이프라인까지 가는 진행 순서를 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"배달 기사가 도착 반경 200m 안에 들어오면 고객한테 알려주세요." 또는 "우리 매장 반경 500m 안에 들어온 사용자한테 쿠폰을 푸시로 보내주세요." 둘 다 똑같이 '지오펜스 진입 이벤트'를 다루지만, 요구되는 규모와 지연 민감도는 전혀 다릅니다. 테스트 단계에서는 앱이 5초마다 GPS를 폴링하고 모든 반경을 순회 비교하는 코드로도 충분합니다. 하지만 사용자가 수만 명, 매장이 수천 곳으로 늘면 이 방식은 배터리와 서버 CPU를 동시에 태우면서도 진입 순간을 놓치기 시작합니다.

지오펜싱을 다루는 실무 가이드들이 공통으로 짚는 전환점은 "폴링에서 이벤트 기반으로" 옮기는 시점입니다. GPS 업데이트가 들어올 때마다 그 좌표를 모든 지오펜스와 매번 비교하는 대신, 위치 스트림을 공간 인덱스와 조인해 변화가 생긴 순간에만 이벤트를 발행하는 구조로 바꾸는 것입니다. 여기에 더해 통신사가 네트워크 자체에서 진입·이탈만 구독형으로 알려주는 CAMARA Geofencing Subscriptions 같은 모델까지 등장하면서, "어디서 판정할 것인가"를 디바이스·서버·네트워크 세 층위에서 비교해야 하는 상황이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"반경에 들어오면 알려주세요"는 하나의 쿼리가 아니라 지속적으로 흐르는 위치 스트림과 여러 지오펜스 집합 사이의 공간 조인을 실시간으로 유지하는 문제입니다. 여기에는 세 가지 결정이 숨어 있습니다. 첫째, 판정을 누가 하는가(디바이스 자체, 내 서버, 또는 통신사 네트워크). 둘째, 경계 근처에서 GPS 오차로 진입·이탈이 반복 발생하는 떨림을 어떻게 걸러낼 것인가(디바운스·dwell 시간). 셋째, 같은 이벤트가 중복 발행되지 않도록 멱등성을 어떻게 보장할 것인가. 이 세 결정을 분리하지 않고 하나의 조건문에 욱여넣으면, 지오펜스 개수가 늘어날 때마다 로직 전체를 다시 손봐야 하는 구조가 됩니다.

 

전체 시스템에서의 위치

 

위치 데이터는 디바이스에서 출발해 세 갈래 중 하나로 판정 지점에 도달합니다. 디바이스 SDK가 온디바이스에서 직접 판정하면 서버로는 전환 이벤트만 올라오고, 서버 스트리밍 방식이면 GPS 좌표 자체가 Kafka 같은 스트림을 타고 판정 엔진까지 흘러가 공간 인덱스와 조인되며, 통신사 네트워크 구독형이면 모바일 네트워크가 진입·이탈만 애플리케이션에 통지합니다. 판정 엔진을 통과한 결과는 디바운스·dwell 로직을 거쳐 ENTER/EXIT 이벤트로 발행되고, 이 이벤트가 알림 발송·운영 대시보드·웹훅 같은 다운스트림으로 전달됩니다. 이 분리가 없으면 판정 로직과 알림 로직이 뒤섞여, 알림 템플릿 하나를 바꾸는 작업이 판정 정확도에까지 영향을 주는 상태가 됩니다.

 

선택의 트레이드오프
판정 위치 배터리/네트워크 비용 처리량 확장성 적합한 상황
디바이스 SDK 낮음 서버 부담 없음 소비자 앱, 배터리·오프라인 민감
서버 스트리밍 파이프라인 높음 수평 확장 가능, 직접 통제 지오펜스 수가 많고 로직이 복잡한 B2B/운영 시스템
통신사 네트워크 구독 매우 낮음 통신사 인프라에 의존 앱 설치 없이도 위치 기반 서비스가 필요한 경우

 

디바이스 SDK는 배터리와 프라이버시에서 유리하지만 판정 로직을 바꿀 때마다 앱을 업데이트·배포해야 하는 지연이 생깁니다. 서버 스트리밍은 로직을 서버에서 즉시 바꿀 수 있고 수천 개 지오펜스를 동시에 평가할 수 있지만, 좌표를 계속 전송해야 하므로 네트워크·배터리 비용과 위치 데이터 보관 책임이 따릅니다. 통신사 네트워크 구독은 아직 지원 지역과 통신사가 제한적이라 글로벌 서비스에는 아직 보조 수단에 가깝습니다. 지오펜스 개수가 적고 로직이 단순하면 디바이스 SDK만으로 충분하고, 지오펜스가 수백 개를 넘고 운영팀이 조건을 자주 바꿔야 한다면 서버 스트리밍으로 무게중심이 옮겨갑니다.

 

실제 프로젝트 진행 순서

1단계: 가장 단순한 폴링+순회 비교로 먼저 동작을 검증합니다.

2단계: 지오펜스 개수가 늘어나기 시작하면 공간 인덱스(R-tree, 그리드)부터 추가합니다.

3단계: 디바운스·dwell 임계값을 가장 먼저 튜닝해 GPS 오차로 인한 반복 발생을 줄입니다.

4단계: 처리량이 실제로 문제가 될 때 폴링 대신 이벤트 스트림으로 전환합니다.

5단계: 이벤트 발행에 멱등 키를 부여해 중복 소비로 알림이 두 번 나가지 않게 합니다.

6단계: 온디바이스 전환은 비용이 실제로 드러날 때, 배터리·프라이버시 요구가 분명해진 뒤에만 검토합니다.

-- 위치 스트림 테이블과 지오펜스 테이블을 공간 인덱스로 조인
SELECT g.fence_id, l.device_id,
       ST_DWithin(l.point, g.boundary, 0) AS is_inside
FROM location_stream l
JOIN geofences g
  ON ST_DWithin(l.point, g.boundary, g.buffer_margin)
WHERE l.event_time > now() - interval '5 seconds';

 

주의 — 실제 매장·캠퍼스 경계는 원이 아닌 경우가 많으니 정밀도가 필요하면 폴리곤으로 정의하세요. 멱등성 설계는 알림 발송 시점이 아니라 이벤트 발행 시점에 끝내야 웹훅·대시보드 등 모든 다운스트림이 혜택을 봅니다. 통신사 네트워크 구독형은 아직 지원 지역이 제한적이므로 주 경로가 아닌 보조 수단으로만 고려하세요.

 

정리

"반경에 들어오면 알려주세요"는 위치 스트림과 지오펜스 집합 사이의 실시간 공간 조인 문제로 번역되며, 판정 위치·디바운스·멱등성이라는 세 가지 결정을 분리해 설계해야 합니다. 디바이스 SDK는 배터리·프라이버시에, 서버 스트리밍은 확장성·로직 유연성에, 통신사 네트워크 구독은 앱 비설치 시나리오에 강점이 있습니다. 도입은 단순 폴링 → 공간 인덱스 → 디바운스 튜닝 → 이벤트 스트림 전환 → 멱등 키 설계 순으로, 지오펜스 규모가 실제로 문제를 드러낼 때마다 한 단계씩 옮겨가는 것이 안전합니다.
