한 줄 요약 — "AI 에이전트는 들여보내고 가짜 스크래퍼는 막아주세요"라는 요구는 User-Agent 문자열이나 IP 대역으로는 풀리지 않습니다. Cloudflare·Anthropic·OpenAI가 함께 프로덕션에 올린 Web Bot Auth가 HTTP Message Signatures로 에이전트 신원을 암호학적으로 증명하는 방식과, 신원 검증과 접근 허가를 분리해 설계해야 하는 이유를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"검색엔진 크롤러나 Claude 같은 AI 에이전트는 콘텐츠를 가져가게 두되, User-Agent만 흉내 낸 스크래퍼는 막아주세요." 콘텐츠·API를 가진 서비스라면 2026년 들어 거의 매달 듣게 되는 요구입니다. 기존 대응은 User-Agent 문자열 매칭이나 IP 대역 화이트리스트, robots.txt 정도였는데, 셋 다 같은 구조적 결함을 공유합니다 — 전부 요청자가 자진 신고하는 정보에 의존하고, 그 정보는 누구나 똑같이 흉내 낼 수 있습니다.

Cloudflare가 2025년 7월 Verified Bots Program에 메시지 서명 검증을 추가하고, Anthropic·OpenAI가 함께 프로덕션에 적용하면서 Web Bot Auth가 사실상의 업계 표준처럼 자리 잡기 시작했습니다. 2026년 7월에는 Cloudflare가 BotBase 메타데이터에 Direct(본인 직접 요청)와 Intermediary(대행 요청)를 구분하는 필드까지 추가했습니다. 다만 IETF 초안은 아직 워킹그룹 문서로 채택되지 않은 상태라, "표준이니 그대로 믿고 쓴다"가 아니라 이게 정확히 무엇을 증명하고 무엇을 증명하지 않는지부터 짚어야 합니다.

 

HTTP Message Signatures로 자진 신고를 암호학적 증명으로

Web Bot Auth의 핵심은 RFC 9421(HTTP Message Signatures)입니다. 에이전트 운영사는 공개키를 .well-known 경로에 공시해 두고, 실제 요청을 보낼 때는 요청의 핵심 구성요소를 자신의 개인키로 서명해 헤더에 실어 보냅니다. 요청을 받는 서버나 CDN은 운영사의 공개키 위치에서 공개키를 가져와 서명을 검증합니다. 서명이 유효하다는 것은 그 개인키를 가진 주체가 보냈다는 사실을 암호학적으로 증명합니다 — User-Agent 문자열과 달리 개인키 없이는 위조할 수 없습니다.

 

신원 검증과 접근 허가는 다른 문제다

여기서 가장 자주 놓치는 지점이 있습니다. Web Bot Auth가 증명하는 것은 "이 요청을 보낸 주체가 누구인가"뿐입니다. 그 주체에게 접근 권한을 줄 것인가는 완전히 별도의 정책 결정입니다. 신원이 Claude라고 확인됐다고 해서 자동으로 전체 콘텐츠를 무제한 크롤링하게 둬야 하는 건 아닙니다 — 검증된 신원별로 접근 범위, 속도 제한, 과금 여부를 따로 설계해야 합니다. Direct/Intermediary 구분도 이 맥락에서 의미가 있습니다. 사용자를 대신해 실시간으로 페이지 하나를 읽어오는 에이전트와, 운영사가 대규모로 콘텐츠를 수집하는 크롤러는 신원은 같아도 허용해야 할 접근 패턴이 다릅니다.

또한 IETF 표준화가 아직 끝나지 않았다는 점도 설계에 반영해야 합니다. 모든 AI 에이전트 운영사가 이 방식을 지원하는 것은 아니며, 미서명 트래픽을 무조건 차단하면 아직 서명을 구현하지 않은 정상적인 에이전트·크롤러까지 함께 막힐 수 있습니다.

 

전체 시스템에서의 위치

 

요청은 에이전트에서 출발해 개인키로 서명된 채로 CDN 계층에 도달합니다. CDN은 운영사의 공개키를 조회해 서명을 검증하고, 성공하면 신원과 Direct/Intermediary 구분 정보를 확보해 신원별 접근 정책을 적용한 뒤 오리진 서버로 전달합니다. 서명이 없거나 검증에 실패한 트래픽은 기존 휴리스틱(User-Agent, IP 평판)으로 넘어가 별도 판정을 받습니다 — 두 체계가 과도기 동안 공존하는 구조입니다.

 

선택의 트레이드오프
방식 강점 약점
User-Agent/IP 휴리스틱 구현 간단 위조 쉬움
robots.txt 의사 표시 명확 강제력 없음
Web Bot Auth(서명 검증) 암호학적 신원 증명 IETF 미표준, 미지원 존재

 

세 방식은 대체재가 아니라 레이어입니다. 서명된 트래픽을 우선 신뢰하고, 서명이 없는 트래픽은 기존 휴리스틱으로 보조 판정하며, robots.txt는 그 위에 허용 의사를 명시하는 최소한의 신호로 남겨두는 조합이 현실적입니다.

 

실제 프로젝트 진행 순서

1단계: 현재 트래픽에서 자칭 AI 에이전트·크롤러 비중과 패턴을 로그로 먼저 분석합니다.

2단계: CDN·프록시 계층이 Web Bot Auth 검증을 지원하는지 확인합니다.

3단계: 검증된 신원별로 접근 정책을 별도로 설계합니다 — "검증됐다"와 "다 허용한다"는 다릅니다.

4단계: 미서명 트래픽용 기존 휴리스틱을 당장 걷어내지 않고, 위반 로그부터 쌓아 영향도를 확인한 뒤 차단을 적용합니다.

 

서명 헤더 개념 예제
GET /.well-known/http-message-signatures-directory HTTP/1.1
Host: agent-operator.example

Signature-Input: sig1=("@method" "@path" "@authority");keyid="agent-operator-key-2026"
Signature: sig1=:base64signature:

 

주의 — IETF 표준화가 아직 끝나지 않았습니다. 미서명 트래픽을 무조건 차단하면 정상 트래픽까지 막힐 수 있으니 과도기 공존 설계를 먼저 검토하세요.

 

정리

User-Agent·IP 기반 봇 판별은 쉽게 위조되며, Web Bot Auth는 RFC 9421 서명으로 이를 암호학적 증명으로 바꿉니다. 신원 검증과 접근 허가는 분리된 문제이며, 같은 신원이라도 Direct/Intermediary 구분에 따라 정책을 달리 둬야 합니다. 표준화가 끝나지 않았으므로 서명 검증과 기존 휴리스틱을 당분간 함께 운영하는 설계가 현실적입니다.
