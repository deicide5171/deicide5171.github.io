@Cacheable 한 줄이 전부가 아니다 — Spring 캐시 추상화 + Redis 실전 설정

2026. 8. 23. · 백엔드

한 줄 요약 — Spring 캐시 추상화에 Redis를 붙일 때 기본 설정 그대로 두면 안 되는 세 가지, 즉 직렬화 방식 교체, 캐시별 TTL 설계, 캐시 스탬피드 방지(sync 옵션)를 복사해서 바로 쓸 수 있는 설정 코드와 함께 정리했습니다.

 

@Cacheable, 붙이기는 쉬운데 왜 사고가 날까요

조회 API가 느려지면 가장 먼저 떠오르는 처방이 캐시입니다. Spring에서는 메서드에 @Cacheable 애너테이션 하나만 붙이면 반환값이 캐시에 저장되고, 같은 인자로 다시 호출하면 메서드 본문을 건너뛴 채 캐시된 값이 돌아옵니다. RedisTemplate으로 get/set을 직접 짜던 코드와 비교하면 비즈니스 로직에서 캐싱 관심사가 깔끔하게 분리되니 도입 장벽이 아주 낮아 보입니다.

문제는 이 낮은 장벽이 착시라는 점입니다. Spring Boot에 Redis 의존성을 넣고 @EnableCaching만 켠 기본 상태는 JDK 직렬화로 사람이 읽을 수 없는 바이너리를 저장하고, TTL은 무기한이며, 캐시가 만료되는 순간 몰려든 요청이 전부 DB로 쏟아지는 것도 막아주지 않습니다. 이번 글에서는 운영 환경에 올리기 전에 반드시 손봐야 할 세 가지를 실제 설정 코드와 함께 살펴보겠습니다.

 

 

동작 원리 — AOP 프록시라는 사실이 모든 함정의 출발점입니다

@Cacheable은 마법이 아니라 AOP입니다. Spring 컨테이너가 대상 빈을 프록시로 감싸고, 외부에서 그 빈을 호출할 때 프록시가 먼저 캐시를 조회한 뒤 미스일 때만 실제 메서드로 위임하는 구조입니다. 여기서 가장 흔한 함정이 나옵니다. 바로 같은 클래스 안에서의 자기 호출(self-invocation)인데요, 아래 코드처럼 내부에서 this 경유로 캐시 메서드를 부르면 프록시를 거치지 않기 때문에 캐시가 전혀 동작하지 않습니다.

@Service
public class ProductService {

    @Cacheable(cacheNames = "product", key = "#id")
    public ProductDto getProduct(Long id) { /* DB 조회 */ }

    public List<ProductDto> getProductList(List<Long> ids) {
        // 잘못된 코드: this 경유 호출은 프록시를 우회해 캐시가 무시됩니다
        return ids.stream().map(this::getProduct).toList();
    }
}

이때 로그에는 아무 에러도 없이 DB 쿼리만 조용히 반복됩니다. 올바른 대안은 캐시 대상 메서드를 별도 빈으로 분리해서 주입받아 호출하는 것입니다. 같은 이유로 private 메서드나 final 메서드에 붙인 @Cacheable도 동작하지 않는다는 점, 기억해 두시면 좋습니다.

 

직렬화 — 기본값 그대로 두면 나중에 반드시 후회합니다

Spring Data Redis 캐시의 기본 직렬화는 JDK 직렬화입니다. 값 클래스가 Serializable을 구현해야 하고, 저장된 바이트는 redis-cli로 들여다볼 수 없으며, 클래스 필드가 바뀌면 배포 직후 기존 캐시의 역직렬화가 예외로 터집니다. 그래서 실무에서는 JSON 계열로 교체하는 것이 사실상 표준입니다.

직렬화 방식 가독성 주의점
JDK 직렬화 (기본값) 없음 (바이너리) 클래스 변경에 매우 취약, 운영 디버깅 곤란
GenericJackson2JsonRedisSerializer JSON 타입 정보(@class)가 함께 저장됨 — 클래스 이동 시 깨짐
Jackson2JsonRedisSerializer JSON 캐시마다 타입 고정 필요, 다형성 미지원

 

범용으로는 GenericJackson2JsonRedisSerializer가 무난합니다. 다만 JSON 안에 클래스 전체 경로가 저장되므로 패키지 이동이나 클래스 이름 변경이 곧 캐시 호환성 깨짐이 됩니다. 스키마가 바뀌는 배포에서는 캐시 이름에 버전 접미사(product:v2)를 붙여 구버전 캐시와 분리하는 방법이 실용적입니다.

 

TTL 설계 — 캐시 이름별로 다르게, 무기한은 금지입니다

기본 설정의 TTL은 무기한입니다. 캐시 갱신 로직(@CacheEvict)이 한 군데라도 빠지면 낡은 데이터가 영원히 남는다는 뜻입니다. TTL은 "이 데이터가 최대 얼마나 오래되어도 서비스가 견딜 수 있는가"를 기준으로 캐시 이름별로 다르게 잡아야 합니다. 아래는 직렬화 교체와 캐시별 TTL을 한 번에 처리하는 설정 예시입니다.

@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration base = RedisCacheConfiguration.defaultCacheConfig()
                .serializeKeysWith(SerializationPair
                        .fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer()))
                .disableCachingNullValues()
                .entryTtl(Duration.ofMinutes(5));  // 기본 TTL

        return RedisCacheManager.builder(factory)
                .cacheDefaults(base)
                .withInitialCacheConfigurations(Map.of(
                        "product",  base.entryTtl(Duration.ofMinutes(30)),
                        "ranking",  base.entryTtl(Duration.ofSeconds(60)),
                        "codeMeta", base.entryTtl(Duration.ofHours(12))
                ))
                .build();
    }
}

한 가지 짚어둘 점은 disableCachingNullValues()가 양날의 검이라는 것입니다. null 캐싱을 막으면 "존재하지 않는 키"를 반복 조회하는 캐시 관통에 무방비가 되므로, 없는 데이터 조회가 잦은 캐시라면 오히려 null을 짧은 TTL로 캐싱하는 편이 낫습니다. 일괄 적용하지 말고 캐시 성격별로 판단하시기 바랍니다.

 

스탬피드 방지 — sync=true의 효용과 명확한 한계

인기 키의 TTL이 만료되는 순간, 대기하던 요청 수백 개가 동시에 캐시 미스를 맞고 전부 DB로 향하는 것이 캐시 스탬피드입니다. Spring이 제공하는 1차 방어선은 @Cacheable(sync = true)입니다. 같은 키에 대한 동시 호출 중 하나만 실제 메서드를 실행하고, 나머지는 그 결과를 기다리게 만듭니다.

@Cacheable(cacheNames = "ranking", key = "#category", sync = true)
public RankingDto getRanking(String category) {
    return rankingRepository.calculate(category); // 무거운 집계 쿼리
}

다만 이 락은 JVM 프로세스 로컬입니다. 인스턴스가 10대라면 최악의 경우 10개의 요청이 동시에 DB를 조회합니다. 그래도 수만 건이 10건으로 줄어드는 것만으로 충분한 경우가 대부분이므로, 복잡한 장치를 도입하기 전에 sync부터 켜는 것이 옳은 순서입니다. 그래도 부족하다면 TTL에 무작위 지터를 더해 만료 시점이 겹치지 않게 하고, 그다음 단계로 분산 락(Redisson 등)이나 만료 전 비동기 재계산을 검토하시면 됩니다.

 

언제 쓰고, 언제 쓰지 말아야 할까요
어울리는 곳 — 읽기가 압도적으로 많고, 약간의 낡음(staleness)이 허용되며, 키-값 형태로 떨어지는 조회입니다. 상품 상세, 코드성 메타데이터, 랭킹 집계가 전형적입니다.
피해야 하는 곳 — 잔액·재고처럼 정합성이 돈과 직결되는 데이터, 조건 조합이 많아 히트율이 낮은 검색 쿼리, 트랜잭션 안에서 갱신 직후 재조회가 일어나는 흐름입니다. 특히 @Transactional과 함께 쓸 때 커밋 전에 캐시가 갱신되는 타이밍 문제가 있으므로, 쓰기 경로가 얽힌 데이터라면 캐시 없이 DB 튜닝으로 해결하는 쪽이 단순하고 안전한 경우가 많습니다.

 

마무리 — 3줄 요약

① @Cacheable은 AOP 프록시로 동작하므로 자기 호출·private 메서드에서는 조용히 무시됩니다 — 캐시 대상은 별도 빈으로 분리해야 합니다.
② 기본 JDK 직렬화와 무기한 TTL은 운영 사고의 예약입니다 — GenericJackson2JsonRedisSerializer와 캐시 이름별 TTL을 첫 배포 전에 설정하세요.
③ 스탬피드 방어는 sync=true → TTL 지터 → 분산 락/논리적 만료 순으로, 트래픽 근거가 생길 때마다 한 단계씩 올리는 것이 좋습니다.
