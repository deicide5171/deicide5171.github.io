'이 건물만 3D로 띄워주세요' — OpenLayers 위에 three.js를 합성하는 카메라 동기화 설계

GIS

한 줄 요약 — 지도 전체를 3D 지구본으로 바꾸지 않고 특정 건물·분석 결과만 3D로 얹고 싶을 때, OpenLayers 카메라 상태를 three.js 퍼스펙티브 카메라에 매 프레임 동기화하는 설계를 정리했습니다. 좌표계 변환, 렌더 루프 공유, Cesium·deck.gl과의 선택 기준까지 다룹니다.

 

왜 지금 이 판단이 필요한가

"지도는 지금 쓰는 2D 벡터타일 그대로 두고, 재건축 예정 건물 몇 개만 3D 매스로 올려서 보여주세요." 기획자 입장에서는 소박한 요구입니다. 그런데 "그럼 Cesium으로 다 바꾸죠"로 받으면 과잉 대응이 됩니다. 전체 지도를 3D 지구본 엔진으로 옮기면 기존에 공들여 만든 OpenLayers 스타일, 벡터타일 소스, 클릭 인터랙션을 전부 다시 짜야 합니다. 반대로 "그냥 3D 모델 이미지 하나 얹죠"로 받으면, 지도를 줌·회전할 때 그 건물만 따로 놀아서 금방 들통납니다.

진짜 필요한 건 기존 2D 지도는 그대로 두고, 그 위에 3D 렌더 레이어 하나를 포개어 카메라를 동기화하는 것입니다. 다만 이 조합에는 공식 브리지 라이브러리가 없습니다 — Mapbox 생태계의 Threebox나 OpenLayers-Cesium을 잇는 OLCS 같은 성숙한 다리가 three.js+OpenLayers 조합에는 아직 없습니다. 그래서 카메라 동기화를 직접 구현해야 합니다.

 

핵심 개념 — 좌표계와 카메라 동기화

OpenLayers는 EPSG:3857(Web Mercator) 평면 좌표를 미터 단위로 다루고, three.js는 원점이 임의인 로컬 3D 좌표계를 씁니다. 둘을 합성하려면 화면 중심의 지도 좌표를 기준점으로 잡고, 주변 객체의 좌표를 그 기준점 상대 좌표(미터)로 바꿔야 합니다. 고위도로 갈수록 Web Mercator 축척 왜곡이 커지므로 위도별 보정 계수도 곱해야 합니다.

OpenLayers의 view가 가진 center, resolution(줌), rotation을 three.js `PerspectiveCamera`의 위치·투영행렬로 매 프레임 변환해야, 지도를 드래그·줌할 때 3D 객체가 같이 움직입니다. `map.on('postrender', ...)` 이벤트로 이 훅을 겁니다.

 

전체 시스템에서의 위치

 

가장 쉬운 방법은 OpenLayers 캔버스 위에 three.js 전용 캔버스를 투명 배경으로 포개는 것입니다. 구현이 단순하지만 마우스 이벤트가 막히고, 두 레이어가 각자 그리다 보니 깊이 테스트가 레이어 간에 작동하지 않아 어색함이 남습니다. 더 정교한 방법은 Google Maps의 WebGL Overlay View처럼 같은 WebGL 컨텍스트를 공유하는 것으로, 깊이 테스트가 자연스럽지만 `renderer.resetState()`로 GL 상태를 직접 되돌려야 합니다.

 

선택의 트레이드오프
상황 적합한 선택 이유
특정 건물만 국소적으로 3D 강조 three.js + OpenLayers 합성 기존 2D 지도 자산 재사용
지형·지하·시간축 포함 전역 3D 분석 Cesium 지구 타원체·3D Tiles 기본 제공
대량 포인트·폴리곤 3D 집계 deck.gl 대용량 집계 시각화에 최적화
라벨·객체 간 가려짐까지 정확해야 함 GL 컨텍스트 공유 폐색 처리가 자연스러움

 

실무 설정 예제
// OpenLayers 뷰 변경을 three.js 카메라에 동기화 (개념 예시)
map.on('postrender', () => {
  const view = map.getView();
  const center = view.getCenter();
  const resolution = view.getResolution();
  const rotation = view.getRotation();

  const local = toLocalCoords(center, origin, latitudeScaleFactor);
  camera.position.set(local.x, local.y, cameraHeightFromResolution(resolution));
  camera.rotation.z = -rotation;
  camera.updateProjectionMatrix();

  threeRenderer.render(scene, camera);
});

 

실제 프로젝트 진행 순서

1단계: 요구를 "전역 3D 분석"인지 "국소 3D 오버레이"인지부터 가릅니다. 이 판단이 Cesium과 three.js+OpenLayers 중 어디로 갈지를 결정합니다.

2단계: 카메라 동기화부터 프로토타입합니다. 실제 3D 모델 없이 좌표축 하나만 그려서 지도와 함께 움직이는지부터 검증합니다.

3단계: 좌표 변환 유틸을 독립 모듈로 분리합니다. 기준점 재설정 시 영향 범위를 좁히기 위함입니다.

4단계: 두 렌더 루프의 프레임 버짓을 함께 측정합니다. 객체 수가 늘었을 때 어디서 프레임이 떨어지는지 프로파일링합니다.

 

주의 — "3D가 필요하니 무조건 Cesium"으로 바로 건너뛰지 마세요. 요구가 국소적 강조라면 전체 지도 스택을 바꾸는 비용이 얻는 가치보다 훨씬 큽니다. 반대로 별도 캔버스 오버레이로 시작해놓고 깊이 처리 방식을 나중에 정하면 라벨이 3D 객체 뒤로 숨었다 나타났다 하는 버그를 뒤늦게 만나게 됩니다.

 

정리

"국소 3D 강조"와 "전역 3D 분석"을 먼저 구분해야 과잉 설계를 피합니다. 카메라 동기화는 OpenLayers의 postrender 이벤트에서 뷰 상태를 읽어 three.js 투영행렬을 매 프레임 갱신하는 구조이며, 별도 캔버스와 GL 컨텍스트 공유 중 어느 쪽을 택할지는 깊이·폐색 요구 수준에 따라 결정합니다.
