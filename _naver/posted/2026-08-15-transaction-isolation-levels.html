트랜잭션 격리수준, PostgreSQL과 MySQL은 왜 다르게 동작할까요

2026. 8. 15. · 데이터베이스

한 줄 요약 — 같은 이름의 REPEATABLE READ라도 PostgreSQL과 MySQL은 내부 동시성 처리 방식이 달라 동작이 다릅니다. MVCC 스냅샷 아이솔레이션의 원리와 write skew 함정을 정리했습니다.

 

왜 이 주제가 중요할까요

트래픽이 적을 때는 잘 돌던 잔액 차감 로직이 동시 요청 몇 개가 겹치자 잔액이 음수로 떨어지는 버그를 만들어낸 경험, 한 번쯤 있으실 겁니다. 원인은 대부분 코드가 아니라 트랜잭션 격리수준을 정확히 이해하지 못한 것에 있습니다. ANSI SQL 표준이 정의한 네 가지 격리수준은 이름은 같아도 DBMS마다 구현 방식이 다르고, 그 차이가 실제 동시성 버그로 이어집니다.

특히 PostgreSQL과 MySQL(InnoDB)은 둘 다 "REPEATABLE READ"라는 이름을 쓰지만, 내부적으로는 서로 다른 방식으로 동시성을 제어합니다. 이 차이를 모르고 한쪽 DB에서 검증한 로직을 다른 DB로 그대로 옮기면 예상치 못한 동시성 버그를 만나기 쉽습니다.

 

네 가지 격리수준과 이상 현상

ANSI SQL은 격리수준이 낮을수록 허용되는 이상 현상(anomaly)이 늘어난다고 정의합니다.

격리수준 Dirty Read Non-repeatable Read Phantom Read
Read Uncommitted 발생 가능 발생 가능 발생 가능
Read Committed (PostgreSQL 기본) 방지 발생 가능 발생 가능
Repeatable Read (MySQL 기본) 방지 방지 표준상 가능
Serializable 방지 방지 방지

 

표에서 눈여겨볼 지점은 Repeatable Read입니다. 표준은 phantom read를 허용하지만, 실제 구현은 표준보다 강한 보장을 주기도 합니다. 여기서부터 DB마다 이야기가 갈립니다.

 

MVCC 스냅샷 아이솔레이션, DB별로 뭐가 다를까요

PostgreSQL과 MySQL 모두 락 대신 MVCC(Multi-Version Concurrency Control)로 Repeatable Read를 구현합니다. 트랜잭션이 시작되는 시점의 데이터 스냅샷을 확보하고, 트랜잭션이 끝날 때까지 그 스냅샷만 본다는 점은 동일합니다. 차이는 쓰기 충돌을 어떻게 처리하느냐에서 갈립니다.

 

PostgreSQL은 Repeatable Read 이상에서 같은 행을 두 트랜잭션이 동시에 수정하려 하면, 먼저 커밋한 트랜잭션만 성공하고 나머지는 오류로 abort시킵니다. 애플리케이션이 재시도 로직을 갖추고 있어야 합니다.

MySQL(InnoDB)은 Repeatable Read에서 넥스트 키 락(next-key lock)을 함께 사용해 phantom read를 상당 부분 실무적으로 방지합니다. 표준상으로는 허용되지만, 넥스트 키 락 덕분에 범위 조회에 대한 삽입까지 막히는 경우가 많습니다.

즉 "REPEATABLE READ면 다 똑같겠지"라고 가정하고 한쪽 DB에서 검증한 동시성 로직을 다른 DB에 그대로 옮기면, 락 대기 시간이나 실패 처리 방식이 달라져 문제가 생길 수 있습니다.

 

예제: Write Skew — Repeatable Read로도 못 막는 함정

Repeatable Read까지 올려도 막히지 않는 대표적인 이상 현상이 write skew입니다. 서로 다른 행을 각자 수정하지만 그 조합이 비즈니스 규칙을 깨는 경우입니다.

-- 온콜 당직자가 최소 1명은 있어야 한다는 규칙

-- T1
BEGIN;
SELECT count(*) FROM oncall WHERE active = true; -- 2명 확인
UPDATE oncall SET active = false WHERE user_id = 'alice';
COMMIT;

-- T2 (T1과 거의 동시에 실행)
BEGIN;
SELECT count(*) FROM oncall WHERE active = true; -- 역시 2명 확인 (같은 스냅샷)
UPDATE oncall SET active = false WHERE user_id = 'bob';
COMMIT;

-- 결과: 두 트랜잭션 모두 성공 → 당직자 0명 (규칙 위반)

두 트랜잭션이 서로 다른 행(alice, bob)을 수정하기 때문에 MVCC의 write-write 충돌 감지에 걸리지 않습니다. 이 문제를 막으려면 SERIALIZABLE 격리수준을 쓰거나, SELECT ... FOR UPDATE로 읽은 행에 명시적 락을 걸어야 합니다.

 

실무 도입 시 이것만은 챙기세요
1. 기본값부터 확인하세요 — PostgreSQL은 Read Committed, MySQL(InnoDB)은 Repeatable Read가 기본값입니다.
2. 재시도 로직은 선택이 아니라 필수입니다 — 직렬화 실패에 대비해 짧은 backoff 재시도를 넣어야 합니다.
3. Serializable은 공짜가 아닙니다 — 술어 락 추적 비용이 있어 처리량이 떨어질 수 있으니 임계 구간에만 좁혀 적용하세요.
4. SELECT ... FOR UPDATE를 적극 활용하세요 — 격리수준을 통째로 올리는 대신 충돌 위험이 있는 조회에만 명시적 락을 거는 편이 성능에 유리합니다.

 

마무리 — 3줄 요약

① 격리수준이 낮을수록 dirty read·non-repeatable read·phantom read 같은 이상 현상이 더 많이 허용됩니다.
② PostgreSQL과 MySQL은 같은 이름의 Repeatable Read라도 MVCC 충돌 처리 방식이 달라 동작이 다릅니다.
③ write skew처럼 Repeatable Read로도 막히지 않는 함정이 있으니 Serializable이나 SELECT ... FOR UPDATE를 상황에 맞게 선택해야 합니다.
