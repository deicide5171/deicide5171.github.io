상태관리가 왜 필요한가 — props drilling부터 Context까지

프론트엔드

한 줄 요약 — Context는 데이터를 상위에 보관하고 하위에서 직접 꺼내 써서 props drilling을 없애지만, 남용하면 리렌더링 성능 문제를 부릅니다.

 

왜 useState만으로는 부족해지는가

상태를 멀리 떨어진 깊은 자식에서 써야 할 때 문제가 생깁니다. 중간 컴포넌트들이 자기는 쓰지도 않는 데이터를 props로 계속 전달만 하게 되는데, 이것이 props drilling입니다.

 

props drilling의 문제
App -> Layout(user 전달만) -> Header(전달만) -> Avatar(실제 사용)

중간 컴포넌트가 상관없는 user를 계속 넘기느라 지저분해지고, user 구조가 바뀌면 거쳐가는 모든 컴포넌트를 수정해야 합니다.

 

Context: 전역으로 꺼내 쓰기
const UserContext = createContext(null);

<UserContext.Provider value={user}>
  <Layout /> // user를 props로 안 넘겨도 됨
</UserContext.Provider>

function Avatar() {
  const user = useContext(UserContext); // 직접 꺼내 씀
}

 

언제 무엇을 쓰나
도구 적합한 경우
useState 한 컴포넌트 지역 상태
Context 로그인·테마 등 자주 안 바뀌는 전역
Redux/Zustand 복잡한 전역, 잦은 업데이트

 

실무 포인트

Context 값이 바뀌면 구독하는 모든 컴포넌트가 리렌더링됩니다. 자주 바뀌는 값을 큰 Context에 몰아넣으면 불필요한 렌더링이 늘어납니다.

주의 — 처음부터 Redux 같은 무거운 도구를 넣기보다 props·Context로 시작해 필요성이 명확해지면 도입하세요.
