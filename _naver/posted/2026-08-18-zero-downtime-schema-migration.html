무중단 스키마 마이그레이션 — Expand-Contract 패턴으로 서비스 안 멈추고 DB 구조 바꾸기

2026. 8. 18. · DB·데이터 모델링

한 줄 요약 — 컬럼 이름 하나 바꾸는 일도 서비스를 멈추지 않으려면 확장(Expand) → 이행(Migrate) → 축소(Contract) 세 단계로 나눠야 하는 이유와, 실제로 어떻게 나누는지를 정리했습니다.

 

왜 지금 이 이야기인가

서비스가 커질수록 스키마는 초기 설계와 점점 멀어집니다. 컬럼 이름이 어색해지고, 타입이 부족해지고, 정규화 방향을 바꿔야 하는 순간이 옵니다. 문제는 "그냥 ALTER TABLE 한 번 돌리면 되지 않나"라는 생각이 통하지 않는 규모에 도달했을 때입니다. 큰 테이블에 컬럼을 추가하거나 이름을 바꾸는 순간 테이블 전체에 락이 걸릴 수 있고, 애플리케이션 배포는 스키마가 바뀌는 그 순간에 딱 맞춰 일어날 수 없습니다.

배포는 서버 인스턴스마다 순차적으로 굴러가기 때문에, 그 사이 구버전 코드와 신버전 코드가 동시에 같은 테이블을 바라보는 시간이 반드시 존재합니다. 이 글은 데이터를 다른 서버로 옮기는 문제(샤딩·리샤딩)가 아니라, 하나의 테이블 안에서 컬럼을 추가·삭제·이름 변경·타입 변경하는 스키마 자체를 안전하게 바꾸는 절차를 다룹니다.

 

핵심 개념: Expand-Contract 패턴

Expand-Contract(확장-축소)는 스키마 변경을 한 번의 배포가 아니라 여러 단계로 쪼개는 패턴입니다. 핵심은 "스키마 변경"과 "애플리케이션 배포"가 원자적으로 동시에 일어날 수 없다는 전제를 받아들이고, 그 사이 어느 시점에도 구버전·신버전 애플리케이션이 모두 정상 동작하도록 스키마를 설계하는 것입니다.

단계 하는 일 위험 요소
Expand(확장) 기존 컬럼은 그대로 두고 새 컬럼·테이블을 추가만 함 대용량 테이블은 짧은 락이라도 저트래픽 시간대 권장
Migrate(이행) 신·구 컬럼에 동시에 쓰고(dual write), 배치로 과거 데이터 백필 배치가 크면 락 경합·복제 지연 발생
Contract(축소) 검증이 끝난 뒤 신규 컬럼만 쓰도록 전환, 옛 컬럼 제거 되돌릴 수 없는 단계이므로 충분한 관찰 기간 필요

 

핵심 개념: 변경 유형별 위험도

모든 스키마 변경이 똑같이 위험한 것은 아닙니다. 변경 유형에 따라 락 범위와 서비스 영향이 크게 달라집니다.

변경 유형 위험도 이유
컬럼 추가(NULL 허용) 낮음 대부분 메타데이터만 변경, 테이블 재작성 불필요
컬럼 추가(NOT NULL + DEFAULT) 중간~높음 엔진·버전에 따라 기존 행 전체 재작성 가능
컬럼 삭제 중간 구버전 코드가 남아있으면 즉시 오류
컬럼 이름 변경 높음 사실상 "삭제+추가"와 같아 동시성 문제가 가장 큼

이름 변경이 가장 위험한 이유는, 이름을 바꾸는 순간 옛 이름을 참조하던 코드가 즉시 깨지기 때문입니다. 그래서 실무에서는 이름 변경을 그대로 실행하지 않고, 항상 Expand-Contract로 풀어서 "새 이름 컬럼 추가 → 이행 → 옛 이름 컬럼 삭제"로 바꿉니다.

 

예제: 컬럼 이름 변경을 Expand-Contract로 처리하기

name 컬럼을 full_name으로 바꾸는 상황을 가정합니다. RENAME COLUMN을 한 번에 실행하면 배포 타이밍이 어긋나는 순간 구버전 코드가 즉시 에러를 냅니다. 대신 아래처럼 나눕니다.

-- 1단계 Expand: 새 컬럼만 추가 (NULL 허용, 짧은 락)
ALTER TABLE users ADD COLUMN full_name VARCHAR(255);

-- 2단계 Migrate: 과거 데이터 백필 (배치로 나눠서 실행)
UPDATE users
SET full_name = name
WHERE full_name IS NULL
  AND id BETWEEN :batch_start AND :batch_end;

-- 3단계 Contract: 검증 완료 후 옛 컬럼 제거
ALTER TABLE users DROP COLUMN name;

배치를 나누는 이유는 대량 UPDATE가 테이블 전체를 잠그거나 트랜잭션 로그를 폭증시켜 복제 지연을 유발할 수 있기 때문입니다. 이행 기간 동안 애플리케이션은 두 컬럼에 동시에 쓰는 dual write 로직을 거쳐야 하고, 백필이 끝나고 두 컬럼 값이 100% 일치함을 확인한 뒤에야 3단계로 넘어갑니다.

 

실무 도입 시 이것만은 챙기세요
1. 단계마다 독립적으로 롤백 가능해야 함 — Expand는 언제든 되돌릴 수 있지만 Contract(삭제)는 사실상 불가역
2. 배치 백필은 크기·속도를 제한 — 한 트랜잭션에 너무 많은 행을 담지 않도록 배치 크기·대기 시간 조절
3. 대용량 테이블은 온라인 DDL 도구 검토 — MySQL 계열의 pt-online-schema-change, gh-ost 등, 사용 중인 DB 버전의 락 동작을 공식 문서로 먼저 확인
4. 배포 순서는 항상 "스키마 먼저, 코드는 그 다음" — 코드가 먼저 배포되면 존재하지 않는 컬럼을 참조하게 됨
5. 이행 단계에는 불일치 모니터링 필수 — dual write 중 신·구 컬럼 값이 어긋나면 백필·애플리케이션 로직에 버그가 있다는 신호

 

마무리 — 3줄 요약

① Expand-Contract 패턴은 스키마 변경을 "확장 → 이행(dual write·백필) → 축소" 세 단계로 쪼개, 어느 시점에도 구·신 버전 코드가 모두 정상 동작하게 만듭니다.
② 컬럼 이름 변경처럼 위험도가 높은 변경도 "새 컬럼 추가 → 백필·검증 → 옛 컬럼 삭제"로 풀면 무중단으로 처리할 수 있습니다.
③ 축소(Contract) 단계는 되돌리기 어려우므로 충분한 관찰 기간과 불일치 모니터링을 거친 뒤에만 실행해야 합니다.
