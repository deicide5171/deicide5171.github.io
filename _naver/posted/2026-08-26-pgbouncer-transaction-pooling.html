커넥션 풀 위에 커넥션 풀을 얹었더니 — PgBouncer 트랜잭션 풀링과 앱 풀의 상호작용

2026. 8. 26. · 데이터베이스

한 줄 요약 — 애플리케이션의 HikariCP 풀과 DB 앞단의 PgBouncer 풀을 함께 쓸 때, 트랜잭션 풀링 모드가 세션 상태를 어떻게 깨뜨리는지 정리했습니다.

 

PgBouncer가 필요한 이유

PostgreSQL 커넥션은 하나당 프로세스 하나를 포크하는 구조라 생성 비용이 크고, 동시 연결 수에도 실질적인 상한이 있습니다. 서비스 인스턴스가 여러 대이고 인스턴스마다 HikariCP 같은 애플리케이션 커넥션 풀을 유지하면, 인스턴스 수 × 풀 크기만큼 DB에 실제 연결이 열려 이 상한을 쉽게 넘습니다. PgBouncer는 애플리케이션과 DB 사이에 경량 프록시를 두어, 수백 개의 클라이언트 연결을 훨씬 적은 수의 실제 DB 연결로 다중화합니다.

문제는 가장 효율적인 트랜잭션 풀링(transaction pooling)을 쓰는 순간, "커넥션은 세션 하나에 고정된다"는 가정이 깨진다는 것입니다. 이 가정이 깨지면 prepared statement, 세션 레벨 설정, advisory lock처럼 세션에 상태를 남기는 기능들이 예측 불가능하게 오작동합니다.

 

핵심 개념 1 — 세 가지 풀링 모드의 차이
모드 커넥션 반환 시점 세션 상태 유지
Session pooling 연결을 끊을 때 완전히 유지(효율 낮음)
Transaction pooling 트랜잭션 종료 시 트랜잭션 내에서만 유지
Statement pooling 쿼리 하나 종료 시 유지 안 됨

Transaction pooling은 트랜잭션이 끝나는 즉시 그 물리 연결을 다른 클라이언트가 재사용할 수 있어 다중화 효율이 가장 높고, 실무에서 가장 많이 쓰입니다.

 

핵심 개념 2 — 트랜잭션 풀링이 깨뜨리는 것들

트랜잭션 풀링에서는 매 트랜잭션마다 다른 물리 연결에 배정될 수 있으므로, 세션 범위 상태에 의존하는 기능이 깨집니다. JDBC 드라이버가 자동으로 만드는 prepared statement는 그것을 준비한 물리 연결에만 존재하고, SET search_path 같은 세션 설정은 다음 트랜잭션에서 사라져 있을 수 있습니다. advisory lock도 커넥션이 반환되면 의도치 않은 락 유지·해제가 일어날 수 있고, LISTEN/NOTIFY는 근본적으로 트랜잭션 풀링과 맞지 않습니다.

 

예제 — PgBouncer 설정과 JDBC 드라이버 대응
; pgbouncer.ini
[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 25
server_reset_query = DISCARD ALL
// HikariCP + PgBouncer(transaction mode) 조합 시 JDBC URL 설정
String url = "jdbc:postgresql://pgbouncer-host:6432/mydb"
    + "?prepareThreshold=0"
    + "&preferQueryMode=simple";

server_reset_query = DISCARD ALL은 커넥션이 반환될 때마다 세션 상태를 강제로 초기화합니다. 애플리케이션 쪽에서는 prepareThreshold=0을 설정해 서버 사이드 prepared statement 자동 생성을 막는 것이 가장 흔한 대응입니다.

 

실무 도입 시 이것만은 챙기세요
1. 애플리케이션 풀 크기와 PgBouncer 풀 크기를 같이 설계하세요 — 두 계층의 풀 크기는 독립적으로 정하지 말고 실제 DB max_connections를 기준으로 역산해야 합니다.
2. 세션 상태에 의존하는 코드를 찾아 제거하세요 — SET search_path, advisory lock, temp table 사용처를 미리 파악하세요.
3. 트랜잭션 밖에서 실행되는 쿼리를 주의하세요 — autocommit 쿼리는 매번 다른 물리 연결에 배정될 수 있어 세션 값 의존 로직이 버그로 이어집니다.

 

마무리 — 3줄 요약

① PgBouncer는 연결 수를 다중화하지만, 트랜잭션 풀링 모드는 "연결이 세션에 고정된다"는 가정을 깨뜨립니다.
② prepared statement, 세션 SET, advisory lock, LISTEN/NOTIFY는 세션 범위 상태에 의존하므로 충돌하기 쉽습니다.
③ prepareThreshold 비활성화와 DISCARD ALL 설정으로 방어하고, 세션 의존 로직은 사전에 찾아 제거해야 합니다.
