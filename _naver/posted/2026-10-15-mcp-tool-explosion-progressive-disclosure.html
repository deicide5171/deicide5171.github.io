도구를 100개 붙였더니 에이전트가 더 멍청해졌다 — MCP 툴 폭발과 지연 로딩 설계

AI

한 줄 요약 — "우리 팀이 쓰는 툴을 에이전트한테 다 붙여주세요"라는 요구는 MCP 서버 10개를 연결하는 순간 컨텍스트 창을 7만 토큰 넘게 잡아먹고 툴 선택 정확도를 반토막냅니다. Tool Search 같은 지연 로딩 설계로 이 문제를 풀어야 하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"우리 팀이 쓰는 Slack, Notion, GitHub, Figma, 사내 티켓 시스템까지 에이전트한테 다 붙여주세요." 요구 자체는 평범합니다. 문제는 이걸 곧이곧대로 들어주면 벌어지는 일입니다. MCP 서버 하나가 보통 10~15개 툴을 노출하는데, 이 서버를 10개쯤 붙이면 각 툴의 이름·설명·파라미터 스키마가 전부 매 턴 시스템 프롬프트에 통째로 실립니다. 한 업계 측정치는 이 스키마 세금만으로 대화 시작 전에 이미 5만5천~14만 토큰이 날아간다고 보고합니다.

더 나쁜 건 토큰값이 아니라 정확도 저하입니다. 붙은 툴이 많아질수록 모델이 지금 이 요청에 맞는 툴을 고르는 정확도가 떨어진다는 측정(RAG-MCP 기준 43%→14%대)이 있습니다. "기능을 더 붙였는데 에이전트가 더 똑똑해지기는커녕 엉뚱한 툴을 고르기 시작한다"는 역설이 바로 이 지점에서 생깁니다. Cursor가 툴 40개, OpenAI Tools API가 128개에서 캡을 거는 것도 같은 이유입니다.

 

핵심 개념 — 해결 패턴 네 갈래
패턴 방식 약점
Allow-list 자주 쓰는 툴만 상시 로딩 드문 툴은 아예 접근 불가
Tool Search(지연 로딩) 이름만 노출, 호출 시점에 스키마 검색 검색 호출이 한 단계 추가됨
Code Mode API 표면을 타입 있는 SDK로 래핑 코드 실행 샌드박스가 필요
서브에이전트 분리 도메인별로 툴을 나눠 배정 서브에이전트 간 조율 오버헤드

 

바로 이 글을 쓰는 세션 구조가 Tool Search 패턴의 실물 사례입니다. 자주 쓰는 툴은 상시 로딩되어 있고, 나머지는 이름만 노출된 채 "필요하면 검색해서 스키마를 가져오라"는 지시만 받습니다. 실제로 그 툴을 호출해야 하는 순간에만 전체 스키마가 로딩되는 구조입니다.

 

전체 시스템에서의 위치

 

에이전트 오케스트레이터 입장에서 MCP 서버는 "앞단"이 아니라 "옆단"에 매달리는 확장 포인트입니다. 선적재 구조에서는 지금 당장 필요한 컨텍스트와 전체 툴 카탈로그가 뒤섞여 매 턴 같이 커지지만, 지연 로딩 구조에서는 툴 카탈로그를 "필요할 때 당겨오는" 별도 검색 경로로 분리해 컨텍스트 예산을 지킵니다.

 

선택의 트레이드오프

자주 쓰는 핵심 툴(파일 읽기, 커밋, 테스트 실행)은 allow-list로 상시 로딩하는 게 맞습니다. 가끔 쓰는 통합(사내 티켓, 디자인 툴)은 Tool Search로 지연 로딩해야 합니다. 이미 REST API가 정리돼 있다면 Code Mode로 SDK화를 검토하고, 완전히 다른 업무를 한 세션이 동시에 처리해야 한다면 서브에이전트로 쪼개는 쪽이 근본적입니다. 반대로 툴이 10~20개 수준으로 적다면 이 모든 패턴은 과잉 설계이니 먼저 실측부터 해야 합니다.

 

실무 설정 예제
mcp_servers:
  github:
    tools: ["get_file_contents", "create_pull_request"]
    mode: eager      # 핫패스, 상시 로딩
  notion:
    mode: deferred   # 이름만 노출, 호출 직전 스키마 검색
  figma:
    mode: deferred

 

실제 프로젝트 진행 순서

1단계: 지금 붙은 MCP 서버·툴 개수와 매 턴 토큰량을 먼저 측정합니다. 체감이 아니라 숫자로 시작해야 합니다.

2단계: 로그에서 가장 자주 호출되는 툴 5~10개를 골라 allow-list에 고정합니다.

3단계: 나머지를 지연 로딩으로 전환합니다. Claude Code 기준 v2.1.7부터는 설정 수준에서 전환이 가능합니다.

4단계: 전환 전후로 "의도한 툴을 정확히 골랐는가"를 샘플링해 비교합니다. 토큰만 줄고 정확도가 함께 떨어지면 분리 기준이 잘못된 것입니다.

 

주의 — "85% 토큰 절감" 같은 수치는 벤더·커뮤니티 측정치로 환경마다 다를 수 있습니다. 자신의 서버 구성에서 전환 전후 토큰과 정확도를 직접 재보고 결정하세요.

 

정리

MCP 서버를 많이 붙일수록 토큰 비용뿐 아니라 툴 선택 정확도 자체가 떨어집니다. 핫패스 툴은 allow-list로, 가끔 쓰는 통합은 지연 로딩으로 분리하는 것이 기본 패턴이며, 전환 전후로 반드시 정확도와 토큰을 함께 측정해야 합니다.
