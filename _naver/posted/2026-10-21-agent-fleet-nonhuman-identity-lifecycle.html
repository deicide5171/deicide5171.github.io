에이전트가 1,000개로 늘어나면 — Non-Human Identity 라이프사이클 거버넌스 설계

AI

한 줄 요약 — 팀마다 자유롭게 에이전트를 만들어 쓰게 해달라는 요구는 권한 설계가 아니라 '지금 몇 개의 에이전트 신원이 떠 있고 누가 책임지는가'를 아무도 모르는 재고 관리 문제로 번집니다. 발급-소유-만료-회수 라이프사이클을 SCIM·JIT 권한 모델로 설계하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"팀마다 필요하면 에이전트든 사내 봇이든 알아서 만들어 쓰게 해주세요. 승인 기다리다 일정 늦어지는 거 싫어요." 에이전트 도입 초기에 흔히 나오는 요구입니다. 처음 한두 개일 때는 문제가 없지만, 반년이 지나면 레포마다 파이프라인마다 서비스 계정과 API 키를 가진 에이전트가 하나씩 생겨나 있습니다. 2026년 보안 업계 조사에서는 평균적인 기업에서 비인간(non-human) 신원이 사람 사용자보다 82배 많다는 수치가 나왔고, 실시간 인벤토리를 유지하는 조직은 21%에 그쳤습니다.

이 글이 다루는 문제는 "이 API 호출이 누구의 권한으로 나가는가"라는 위임 인가 설계와는 결이 다릅니다. 그건 호출 한 건의 신원 체인 문제입니다. 여기서 다루는 건 그보다 한 단계 위 — 조직 전체에 흩어진 에이전트 신원을 누가 발급하고 책임지며 언제 회수할 것인가라는 생애주기 관리 문제입니다. 사람 직원은 퇴사 때 HR 시스템이 계정을 자동으로 잠그지만, 에이전트는 그런 트리거가 없어 프로젝트가 끝나도 credential이 계속 유효한 "좀비 신원"으로 남습니다.

 

전체 시스템에서의 위치

에이전트 신원 라이프사이클은 발급 하나로 끝나지 않습니다. 아래 다섯 단계가 하나의 파이프라인으로 이어져야 합니다.

① 요청 — 팀이 목적을 명시해 신청합니다. ② 발급 — 소유자·목적·만료일이 필수 메타데이터로 기록됩니다. ③ 런타임 권한 — 표준 스코프만으로 부족한 부분을 작업 단위 JIT 그랜트로 보강합니다. ④ 운영·모니터링 — 마지막 사용 시각과 이상 호출을 추적합니다. ⑤ 회수 — 만료·소유자 이탈 시 자동으로 신원이 폐기됩니다. 이 다섯 단계를 하나의 레지스트리로 묶지 않으면 ②만 있고 ⑤가 없는 조직이 됩니다.

 

선택의 트레이드오프
방식 장점 단점
공유 서비스 계정 돌려쓰기 당장 빠르게 시작 가능 추적 불가, 유출 시 전체 영향
수동 발급 + 스프레드시트 도구 투자 없이 시작 규모 커지면 즉시 깨짐
SCIM 확장 기반 자동화 기존 IAM과 통합, 표준 기반 에이전트 라이프사이클 커버 아직 실험 단계
JIT 권한 모델(상시 권한 없음) 평소 권한 없음, 범위·시간 제한 모든 호출 경로에 그랜트 로직 필요

 

Cloud Security Alliance가 2026년 3월 공개한 초안 프레임워크는 결국 핵심이 "상시 권한을 없애고 의도가 선언된 시점에만, 범위와 시간이 제한된 권한을 발급하는 것"이라고 결론 내립니다. 표준이 완성되길 기다리기보다 자체 레지스트리와 JIT 그랜트 로직을 먼저 만들어 두는 쪽이 현실적입니다.

 

실제 프로젝트 진행 순서

1. 도구를 고르기 전에 지금 떠 있는 서비스 계정·에이전트 신원이 몇 개인지부터 센다.
2. 신원 생성 요청에 owner·purpose·expiry를 필수값으로 만들고, 소유자 없는 발급은 거부한다.
3. 프로젝트성 에이전트는 90일, 상시 운영 에이전트는 분기 단위 재승인을 기본값으로 둔다.
4. SCIM이 완전히 표준화되기 전까지는 신원·소유자·범위·마지막 사용 시각을 추적하는 내부 레지스트리를 먼저 둔다.
5. 배포·삭제·결제처럼 되돌리기 어려운 작업부터 상시 권한을 걷어내고 JIT 그랜트로 전환한다.
6. 소유자 퇴사, 프로젝트 아카이브 같은 이벤트에 신원 자동 폐기 웹훅을 연결한다.

 

최소 레지스트리 스키마 예시:

agent_identity:
  id: svc-ai-invoice-parser
  owner: team-finance-platform
  purpose: "청구서 OCR 파싱 배치"
  scopes: [storage:read, invoice-db:write]
  expires_at: 2027-01-19
  last_used_at: 2026-10-21T09:12:00Z
  status: active

 

주의 — 이름 규칙(owner-system-purpose)을 강제하고, credential이 코드나 .env 파일에 박혀 있는지 정기적으로 스캔하세요. 90일 이상 호출이 없는 신원은 자동 격리 후 소유자 확인을 요청하고, 응답이 없으면 폐기하세요. "혹시 몰라서 살려둔다"가 좀비 신원이 쌓이는 가장 흔한 경로입니다.

 

정리

에이전트가 늘어날수록 진짜 문제는 권한 설계가 아니라 지금 몇 개가 떠 있고 누가 책임지는가를 아는 인벤토리 문제입니다. SCIM 같은 표준이 아직 에이전트 라이프사이클을 완전히 커버하지 못하므로, 당장은 소유자·만료일 필수화와 자체 레지스트리로 격차를 메우고, 민감 작업부터 JIT 그랜트로 전환하는 것이 기본 방어선입니다.
