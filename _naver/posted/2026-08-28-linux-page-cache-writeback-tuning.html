쓰기 몰릴 때 서버가 멈추는 이유 — 리눅스 페이지 캐시와 writeback 튜닝

인프라

한 줄 요약 — 리눅스는 쓰기를 페이지 캐시에 모아뒀다 나중에 디스크로 흘려보냅니다. dirty_ratio 계열 파라미터를 잘못 두면 대량 쓰기 순간 프로세스가 동기 블로킹에 걸려 서버가 멎어버립니다. 원리와 튜닝법을 정리했습니다.

 

쓰기가 몰릴 때 애플리케이션이 통째로 멈추는 이유

대량 파일 쓰기나 로그 몰림이 있을 때 갑자기 애플리케이션 전체가 몇 초에서 몇십 초씩 응답을 멈추는 현상을 겪어본 적이 있다면, 원인은 애플리케이션 코드가 아니라 리눅스 커널의 페이지 캐시 writeback 메커니즘일 가능성이 높습니다. write() 시스템 콜은 기본적으로 데이터를 디스크가 아니라 메모리(페이지 캐시)에만 쓰고 즉시 반환합니다.

실제 디스크 반영은 커널이 백그라운드에서 나중에 처리하는데, 이 "나중에"를 제어하는 파라미터를 모르면 메모리가 가득 찬 순간 커널이 응답 없는 동기 쓰기 모드로 강제 전환되며 애플리케이션이 통째로 멈춥니다.

 

핵심 개념 1 — write()는 디스크가 아니라 메모리에 씁니다

애플리케이션이 파일에 write()를 호출하면 커널은 데이터를 페이지 캐시에 복사하고 해당 페이지를 "더티(dirty)"로 표시한 뒤 즉시 반환합니다. 디스크에는 아직 아무것도 쓰이지 않았습니다. 더티 페이지는 커널의 flusher 스레드가 백그라운드에서 주기적으로 디스크에 내려보냅니다.

핵심 개념 2 — dirty_ratio와 dirty_background_ratio, 두 개의 임계값
파라미터 의미 초과 시 동작
dirty_background_ratio 낮은 임계값 flusher가 백그라운드에서 조용히 flush 시작
dirty_ratio 높은 임계값 쓰기 프로세스 자신이 동기 블로킹

 

dirty_background_ratio(기본 10~20)를 넘으면 커널이 알아서 백그라운드로 쓰기 시작하므로 애플리케이션은 눈치채지 못합니다. 문제는 dirty_ratio(기본 20~40)까지 넘어설 때입니다. 이때부터는 write()를 호출하는 프로세스 자신이 강제로 멈춰서 더티 페이지가 임계값 아래로 내려갈 때까지 동기적으로 디스크 쓰기를 떠맡습니다.

 

핵심 개념 3 — 메모리가 클수록 비율 기반 설정이 위험해집니다

dirty_ratio는 절대량이 아니라 전체 메모리 대비 비율입니다. 메모리 16GB 서버에서 20%면 최대 3.2GB, 256GB 서버라면 같은 20%가 51.2GB에 달합니다. 디스크 쓰기 대역폭은 메모리 용량과 함께 늘지 않으므로, 메모리가 큰 서버일수록 비율 기반 기본값 대신 dirty_bytes / dirty_background_bytes로 절대 상한을 직접 지정하는 것이 더 예측 가능합니다.

예제 — sysctl로 writeback 파라미터 조정
# 현재 값 확인
sysctl vm.dirty_ratio vm.dirty_background_ratio vm.dirty_expire_centisecs

# 메모리가 큰 서버는 비율 대신 절대 바이트로 상한 고정
sudo sysctl -w vm.dirty_background_bytes=209715200
sudo sysctl -w vm.dirty_ratio=0
sudo sysctl -w vm.dirty_bytes=1073741824

# 더티 페이지가 이 시간(1/100초)보다 오래되면 강제 flush 대상
sudo sysctl -w vm.dirty_expire_centisecs=3000   # 30초

값을 바꾼 뒤에는 iostat -x 1로 %util과 await가 대량 쓰기 구간에서 어떻게 변하는지, 애플리케이션 p99 지연이 flush 타이밍과 겹치는지 함께 관찰해야 튜닝 효과를 확인할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. dirty_ratio를 낮추는 게 항상 답은 아닙니다 — 너무 낮추면 flush가 너무 자주 일어나 평상시 쓰기 처리량이 떨어집니다. 목표는 동기 블로킹 자체를 없애는 것입니다.
2. 로그 몰림·배치 작업 시간대는 별도로 관찰하세요 — 로그 로테이션, 대량 백업, 배치 익스포트는 더티 페이지 급증을 유발합니다.
3. 컨테이너 환경은 cgroup v2 단위 writeback도 고려하세요 — 한 컨테이너의 대량 쓰기가 다른 컨테이너에 전이되는 것을 줄일 수 있습니다.

 

마무리 — 3줄 요약

① write()는 즉시 디스크가 아니라 페이지 캐시에만 쓰고, 실제 디스크 반영은 커널이 백그라운드에서 나중에 처리합니다.
② dirty_background_ratio를 넘으면 조용히 백그라운드 flush가 시작되지만, dirty_ratio를 넘으면 쓰기 프로세스가 동기 블로킹되며 응답이 멎습니다.
③ 메모리가 큰 서버일수록 비율 기반 기본값은 위험하므로 dirty_bytes 계열로 절대 상한을 직접 지정해야 합니다.
