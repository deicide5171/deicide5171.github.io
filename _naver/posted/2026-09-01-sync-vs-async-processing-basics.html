동기 vs 비동기 처리, 언제 무엇을 써야 할까

시스템설계

한 줄 요약 — 사용자가 즉시 결과를 알아야 하는 작업은 동기로, 그렇지 않은 작업은 비동기로 분리하는 것이 기본 원칙입니다.

 

왜 모든 요청을 즉시 처리하면 안 되는가

회원가입 시 DB 저장은 즉시 끝나야 하지만 환영 이메일 발송은 몇 초 늦어져도 문제없습니다. 두 작업을 똑같이 동기로 묶으면, 이메일 서버가 느려질 때 회원가입 자체가 실패하는 불필요한 결합이 생깁니다.

 

동기 처리 vs 비동기 처리
항목 동기 비동기
처리 방식 결과 나올 때까지 대기 요청만 넣고 즉시 응답
실패 영향 하나가 느리면 전체 지연 전체 응답에 영향 없음
적합한 작업 결제 승인 이메일 발송, 통계 집계

 

예제 — 메시지 큐를 이용한 비동기 처리
@PostMapping("/signup")
public ResponseEntity<?> signup(@RequestBody SignupRequest request) {
    User user = userService.createUser(request); // 동기

    eventPublisher.publish(new UserSignedUpEvent(user.getId())); // 비동기

    return ResponseEntity.ok(user);
}

@EventListener
public void handleUserSignedUp(UserSignedUpEvent event) {
    emailService.sendWelcomeEmail(event.getUserId());
}

회원가입 응답 시간은 이메일 발송 속도와 무관해지고, 이메일 서버 장애가 있어도 회원가입은 성공합니다.

 

실무 포인트

비동기로 처리한 작업의 실패는 눈에 보이지 않습니다. 큐에 넣고 끝이 아니라 재시도·알림 모니터링 체계가 함께 있어야 합니다.

주의 — 모든 것을 비동기로 만들면 시스템이 오히려 복잡해집니다. 결과를 바로 알아야 하는 핵심 흐름까지 비동기로 만들면 나쁜 UX가 됩니다.
