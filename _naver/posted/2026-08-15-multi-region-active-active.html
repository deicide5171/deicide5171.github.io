멀티 리전 액티브-액티브 아키텍처, 여러 지역에서 동시에 쓰기를 받는다는 것

2026. 8. 15. · 시스템 설계

한 줄 요약 — 여러 지역(리전)에서 동시에 쓰기 트래픽을 받는 액티브-액티브 구조가 왜 필요한지, 그리고 이때 반드시 마주치게 되는 데이터 일관성 문제를 CRDT, 벡터 클록, 최종 일관성 중심으로 정리했습니다.

 

왜 지금 이 주제인가요

서비스가 특정 지역에만 머물지 않고 전 세계 사용자를 상대하게 되면, 하나의 리전만 두는 구조는 두 가지 문제에 부딪힙니다. 첫째는 지연시간입니다. 물리적으로 먼 리전으로 요청이 오가면 사용자가 체감하는 응답 속도가 나빠집니다. 둘째는 재해 복구입니다. 하나의 리전에 장애가 생겼을 때 서비스 전체가 멈추는 구조는 가용성 요구가 높아질수록 받아들이기 어려워집니다.

이 두 문제를 함께 풀기 위해 등장한 것이 멀티 리전 액티브-액티브 구조입니다. 하나의 리전만 쓰기를 담당하는 액티브-패시브와 달리, 여러 리전이 동시에 읽기와 쓰기를 모두 처리합니다. 그런데 같은 데이터를 여러 리전에서 동시에 고칠 수 있다는 것은, 결국 그 결과를 하나의 값으로 어떻게 수렴시킬 것인가라는 어려운 질문을 남깁니다.

 

액티브-액티브가 주는 이점과 그 대가
이점 설명
지연시간 최소화 사용자와 가장 가까운 리전에서 요청을 처리해 왕복 지연을 줄입니다.
재해 복구 한 리전이 완전히 다운되어도 다른 리전이 트래픽을 이어받을 수 있습니다.
트래픽 분산 특정 리전에 부하가 몰리는 상황을 여러 리전이 나눠 흡수합니다.

 

다만 이 이점은 공짜가 아닙니다. 같은 레코드에 서로 다른 리전에서 동시에 쓰기가 들어오면, 각 리전이 서로 다른 순간에 서로 다른 값을 정답이라고 믿게 될 수 있습니다. 이제부터가 데이터 일관성 문제의 시작입니다.

 

핵심 개념: 동시 쓰기 충돌을 다루는 세 가지 전략
전략 기본 아이디어 한계
CRDT 데이터 구조 자체가 항상 안전하게 병합되도록 설계 지원 가능한 자료구조가 제한적이고 설계가 까다로움
벡터 클록 각 리전의 이벤트 순서를 논리적 시계로 추적해 인과관계 판단 충돌 감지 이후 병합 정책은 별도로 필요
최종 일관성 강한 순서 보장 없이 결국 같은 상태로 수렴하도록만 보장 일시적으로 리전 간 값이 달라 애플리케이션이 이를 감내해야 함

 

세 전략은 서로 배타적이지 않습니다. 실무에서는 최종 일관성을 기본 모델로 삼으면서, 충돌 감지에는 벡터 클록류의 메타데이터를 쓰고, 자동 병합이 가능한 자료구조에는 CRDT를 부분적으로 적용하는 조합을 자주 볼 수 있습니다.

 

분할 뇌 문제, 리전 간 지연이 만드는 함정

리전 간 네트워크는 데이터센터 내부 네트워크보다 지연이 훨씬 크고, 드물게 완전히 단절되는 경우도 있습니다. 이때 각 리전이 서로 다른 값을 계속 받아들이며 독립적으로 진화하는 상황, 즉 분할 뇌(split-brain)가 발생할 수 있습니다. 강한 일관성을 지키려는 시스템은 이런 상황에서 쓰기를 거부하거나 지연시켜 가용성을 희생하고, 최종 일관성 기반 시스템은 우선 쓰기를 받아들인 뒤 나중에 충돌을 병합하는 쪽을 택합니다. 결국 CAP 정리가 말하는 일관성과 가용성의 트레이드오프를 리전 단위로 다시 마주하는 셈입니다.

 

예제: 벡터 클록으로 동시성 판단하기

아래는 두 리전(A, B)이 각자의 카운터를 증가시키며 벡터 클록을 갱신하는 과정을 단순화한 의사코드입니다.

# 각 리전은 자신의 클록을 포함한 전체 벡터를 유지한다
clock_a = {"A": 0, "B": 0}
clock_b = {"A": 0, "B": 0}

def local_write(clock, region):
    clock[region] += 1
    return dict(clock)

def happens_before(c1, c2):
    # c1이 c2보다 인과적으로 앞선다면 True
    return all(c1[k] <= c2[k] for k in c1) and c1 != c2

def is_concurrent(c1, c2):
    # 어느 쪽도 다른 쪽보다 앞서지 않으면 동시 쓰기(충돌 후보)
    return not happens_before(c1, c2) and not happens_before(c2, c1)

# 리전 A와 B에서 각각 로컬 쓰기가 발생
va = local_write(clock_a, "A")  # {"A": 1, "B": 0}
vb = local_write(clock_b, "B")  # {"A": 0, "B": 1}

if is_concurrent(va, vb):
    # 충돌 발생: 병합 정책(LWW, 애플리케이션 로직, CRDT 등)이 필요
    pass

인과관계가 명확하지 않은 두 쓰기가 감지되면, 이후 병합은 별도의 정책(예: 마지막 쓰기 우선, 즉 Last-Write-Wins)이나 애플리케이션 수준의 병합 함수에 맡겨집니다.

 

실무 도입 시 이것만은 챙기세요
1. LWW(Last-Write-Wins)의 위험 인지 — 구현은 단순하지만 패자 쪽 쓰기 내용이 조용히 사라질 수 있음
2. 모든 데이터에 액티브-액티브가 필요한 것은 아님 — 결제 잔액처럼 강한 일관성이 필수인 도메인은 특정 리전으로 쓰기를 집중시키는 하이브리드 구성 고려
3. 충돌 해소 로직은 사전에 테스트 — 네트워크 파티션과 동시 쓰기를 재현하는 카오스 테스트 없이는 프로덕션에서야 문제가 드러나는 경우가 많음
4. 리전 간 복제 지연을 모니터링 대상에 포함 — 복제 지연이 커질수록 충돌 가능성과 불일치 노출 시간이 함께 늘어남

 

마무리 — 3줄 요약

① 멀티 리전 액티브-액티브는 지연시간 최소화와 재해 복구를 동시에 노리지만, 그 대가로 동시 쓰기 충돌 문제를 떠안습니다.
② CRDT, 벡터 클록, 최종 일관성은 서로 대체재라기보다 조합해서 쓰는 보완적 도구에 가깝습니다.
③ 리전 간 지연이 커지는 상황에서는 일관성과 가용성 사이의 트레이드오프를 어떤 정책으로 감내할지 미리 설계해두어야 합니다.
