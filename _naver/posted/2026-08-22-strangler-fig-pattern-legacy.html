스트랭글러 무화과 패턴 — 레거시 시스템을 죽이지 않고 교체하는 법

2026. 8. 22. · 시스템 설계

한 줄 요약 — 레거시 시스템을 한 번에 갈아엎는 빅뱅 재작성 대신, 파사드/프록시로 트래픽을 조금씩 옮기며 새 기능이 레거시를 서서히 감싸도록 만드는 스트랭글러 무화과 패턴의 단계별 전략을 정리했습니다.

 

왜 '한 번에 다시 짜기'는 실패하기 쉬울까요

오래 운영된 레거시 시스템을 전면 재작성(빅뱅 리라이트)하려는 시도는 실무에서 실패담으로 자주 언급됩니다. 기존 시스템은 수년간 쌓인 예외 처리, 암묵적인 업무 규칙, 문서화되지 않은 연동 관계를 품고 있는데, 재작성 프로젝트의 설계 문서에는 이런 세부 사항이 온전히 담기지 않는 경우가 많기 때문입니다.

게다가 재작성이 진행되는 동안에도 기존 시스템은 계속 운영해야 하므로, 조직은 사실상 두 시스템을 동시에 유지·개선해야 하는 부담을 지게 됩니다. 프로젝트 기간이 길어질수록 그 사이 비즈니스 요구사항도 바뀌어서, 완성 시점에는 이미 낡은 설계가 되어 있는 경우도 드물지 않습니다.

이런 문제를 피하는 대안으로 자주 언급되는 것이 마틴 파울러가 이름 붙인 스트랭글러 무화과 패턴(Strangler Fig Pattern)입니다. 스트랭글러 무화과는 다른 나무를 타고 올라가며 서서히 그 나무를 감싸고, 결국 숙주 나무가 죽어 썩어도 무화과 자신은 그 형태를 유지한 채 홀로 서 있게 되는 식물인데요, 이 패턴은 레거시 시스템을 하루아침에 뽑아버리는 대신 새 기능을 하나씩 옆에 세우고 트래픽을 조금씩 옮겨가며 레거시가 자연스럽게 역할을 잃도록 만드는 접근을 말합니다.

 

핵심 개념 1 — 파사드/프록시로 트래픽을 조금씩 옮깁니다

스트랭글러 패턴의 핵심 장치는 레거시 시스템 앞에 두는 파사드(facade) 또는 프록시 계층입니다. 모든 외부 요청은 이 계층을 반드시 거치도록 하고, 마이그레이션 초기에는 라우팅 규칙이 100% 레거시 시스템을 가리키게 합니다. 이 상태에서는 사용자나 클라이언트 입장에서 아무것도 달라진 게 없습니다.

새 기능이 필요하거나 특정 모듈을 재작성하기로 하면, 그 기능만 신규 서비스로 구현하고 파사드의 라우팅 규칙을 갱신해 해당 엔드포인트나 요청 패턴만 신규 서비스로 보냅니다. 나머지 요청은 여전히 레거시로 향합니다. 이 과정을 기능 단위, 엔드포인트 단위로 반복하면서 신규 서비스가 감당하는 트래픽 비율을 점차 늘려가는 것이죠. 각 단계가 작은 단위로 쪼개져 있기 때문에, 특정 기능 이전에서 문제가 생기면 그 부분의 라우팅 규칙만 되돌리면 되고 전체 시스템에 영향을 주지 않는다는 것이 이 구조의 가장 큰 장점입니다.

 

 

핵심 개념 2 — 데이터 동기화 문제와 이중 쓰기 전략

트래픽 라우팅만으로는 마이그레이션이 끝나지 않습니다. 신규 서비스가 레거시와 다른 데이터 저장소를 쓰기 시작하면, 두 시스템이 같은 개념(고객, 주문 등)을 각자의 스키마로 들고 있으면서 데이터 정합성 문제가 생깁니다. 아직 레거시로 라우팅되는 화면에서 데이터를 조회할 때 신규 서비스 쪽에서만 갱신된 값이 반영되지 않으면, 사용자에게는 그대로 오류로 보이게 됩니다.

가장 단순한 대응은 이중 쓰기(dual write)입니다. 애플리케이션 코드가 하나의 요청 처리 안에서 레거시 DB와 신규 DB 양쪽에 같은 변경을 반영하는 방식인데요, 구현은 직관적이지만 두 쓰기가 하나의 트랜잭션으로 묶이지 않으면 한쪽만 성공하고 다른 쪽이 실패하는 부분 실패가 생길 수 있어 별도의 재시도·보정 로직이 필요합니다. 이보다 견고한 방법은 CDC(Change Data Capture)를 이용해 레거시 DB의 변경 로그를 신규 시스템으로 비동기 복제하는 것입니다. 애플리케이션 코드에 동기화 로직을 심지 않아도 되고 일관성 보장 수준도 높지만, CDC 파이프라인 자체를 구축하고 운영하는 추가 인프라 비용이 듭니다.

방식 장점 단점
이중 쓰기
(Dual Write)		 구현이 직관적이고 별도 인프라가 필요 없음 부분 실패 시 데이터 불일치 위험
CDC
(Change Data Capture)		 애플리케이션 코드와 분리되어 일관성 보장 수준이 높음 파이프라인 구축·운영 비용 추가

 

어느 쪽을 택하든 데이터 동기화는 마이그레이션 기간 내내 짊어져야 하는 임시 비용이라는 점을 처음부터 계획에 포함해두시는 편이 좋습니다.

 

핵심 개념 3 — 마이그레이션이 끝났다고 볼 수 있는 기준

스트랭글러 패턴은 시작하기는 쉽지만 언제 끝났다고 볼지가 애매해지기 쉽습니다. 단순히 "라우팅 규칙이 100% 신규 서비스를 가리킨다"는 상태만으로는 부족합니다. 레거시 시스템으로 향하는 실제 요청이 없는지 접근 로그로 일정 기간 관찰하고, 배치 작업이나 관리자 도구처럼 눈에 띄지 않는 경로로 여전히 레거시를 호출하는 곳이 없는지 확인해야 합니다.

데이터 측면에서도 신규 시스템의 데이터가 레거시 데이터와 완전히 일치하는지, 혹은 의도적으로 변환된 경우 그 변환이 검증되었는지 확인하는 절차가 필요합니다. 이 검증이 끝난 뒤에도 곧바로 레거시를 폐기하기보다, 문제 발생 시 되돌릴 수 있는 일정한 유예 기간을 두고 그 기간이 지난 뒤에 인프라를 정리하는 것이 안전합니다.

 

예제 — API 게이트웨이 라우팅 규칙(nginx 스타일)

아래는 API 게이트웨이에서 신규/레거시 트래픽을 엔드포인트 단위로 분기하는 라우팅 규칙 예시입니다. 이미 이전이 끝난 엔드포인트, 아직 레거시가 처리하는 엔드포인트, 그리고 일부 트래픽만 신규 서비스로 보내는 이전 중인 엔드포인트를 함께 보여줍니다.

# /api/orders/* 는 아직 레거시가 처리
location /api/orders/ {
    proxy_pass http://legacy-monolith:8080;
}

# /api/customers/* 는 신규 서비스로 이전 완료
location /api/customers/ {
    proxy_pass http://customer-service:9090;
}

# /api/payments/* 는 이전 중: 헤더 기반으로 일부만 신규 서비스로
location /api/payments/ {
    if ($http_x_migration_cohort = "canary") {
        proxy_pass http://payment-service:9091;
    }
    proxy_pass http://legacy-monolith:8080;
}

실제 운영 환경에서는 이런 규칙을 API 게이트웨이(Kong, Envoy, AWS API Gateway 등)의 설정이나 기능 플래그 시스템으로 관리해서, 코드 배포 없이도 라우팅 비율을 즉시 조정할 수 있게 하는 경우가 많습니다.

 

실무 도입 시 이것만은 챙기세요
1. 이중 유지보수 비용을 미리 계산하세요 — 마이그레이션이 진행되는 동안 신규 서비스와 레거시 시스템 양쪽 모두 장애 대응, 보안 패치, 인프라 비용의 대상이 됩니다. 이 기간이 예상보다 길어지면 조직이 부담하는 운영 비용도 그만큼 늘어나므로, 계획 단계에서부터 이 기간을 되도록 짧게 설정하고 진행 상황을 주기적으로 점검하시는 편이 좋습니다.
2. 롤백 계획은 기능 단위로 준비하세요 — 스트랭글러 패턴의 장점은 문제가 생겼을 때 전체가 아니라 방금 이전한 기능만 되돌릴 수 있다는 점입니다. 이 장점을 실제로 누리려면 각 라우팅 규칙 변경을 손쉽게 되돌릴 수 있는 배포 체계(기능 플래그, 게이트웨이 설정 버전 관리 등)를 미리 마련해두어야 합니다.
3. 데이터 동기화 로직도 임시 코드로 취급하세요 — 이중 쓰기나 CDC 파이프라인은 마이그레이션이 끝나면 제거해야 할 임시 구조물입니다. 완료 후에도 이런 동기화 코드가 방치되어 오히려 새로운 레거시가 되는 경우가 있으니, 폐기 대상 목록에 처음부터 포함해두시는 것이 좋습니다.

 

마무리 — 3줄 요약

① 레거시 시스템을 한 번에 재작성하는 빅뱅 방식은 리스크가 크므로, 파사드/프록시로 트래픽을 점진적으로 신규 서비스로 옮기는 스트랭글러 무화과 패턴이 대안이 될 수 있습니다.
② 신규 시스템이 별도 데이터 저장소를 쓰는 경우 이중 쓰기나 CDC 같은 동기화 전략이 필요하며, 이는 마이그레이션 기간 동안만 유지할 임시 비용으로 계획해야 합니다.
③ 마이그레이션 완료는 라우팅 규칙뿐 아니라 실제 트래픽, 데이터 정합성까지 확인한 뒤 유예 기간을 두고 판단하는 것이 안전합니다.
