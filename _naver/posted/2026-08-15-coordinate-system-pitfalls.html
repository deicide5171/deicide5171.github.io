좌표계, 개발자가 자주 실수하는 것들

2026. 8. 15. · GIS

한 줄 요약 — 위경도 순서, EPSG 코드 불일치, 투영 왜곡 무시까지 좌표계 변환에서 자주 발생하는 실수들과, PostGIS·pyproj로 안전하게 처리하는 방법을 정리했습니다.

 

왜 이 주제가 중요한가

지도 기반 서비스를 만들다 보면 "좌표값은 분명 맞는데 지도에 찍히는 위치가 이상하다"는 버그를 종종 만나게 됩니다. 원인을 추적해보면 대부분 좌표계 자체의 문제가 아니라, 좌표계를 다루는 코드의 가정이 어긋난 경우입니다. 위경도 순서를 반대로 넣었거나, 서로 다른 좌표계의 데이터를 변환 없이 그대로 섞었거나, 미터 단위인 줄 알았던 값이 실은 도(degree) 단위였던 식입니다.

최근에는 국내 공공데이터가 EPSG:5179, EPSG:5186 같은 지역 좌표계로 제공되는 경우가 많아졌고, 여기에 지도 SDK가 기본으로 쓰는 WGS84(EPSG:4326)와 타일 서버가 쓰는 Web Mercator(EPSG:3857)까지 겹치면서, 하나의 파이프라인 안에 서너 개 좌표계가 동시에 존재하는 일이 흔해졌습니다. 좌표계 실수는 화면에는 그럴듯하게 보이다가 특정 지역에서만 어긋나는 식으로 드러나서 발견이 늦어지기 쉽습니다.

이 글에서는 개발자들이 자주 저지르는 실수 유형을 정리하고, PostGIS의 ST_Transform과 Python의 pyproj로 이를 안전하게 다루는 방법을 소개합니다.

 

자주 저지르는 실수 유형

위경도 순서 혼동이 가장 흔합니다. GeoJSON은 [경도, 위도] 순서를 쓰지만, 지도 API나 사람이 말할 때는 "위도, 경도" 순서가 익숙해서 뒤바뀐 채로 저장되는 경우가 많습니다. 좌표가 지구 반대편이나 바다 한가운데로 튀면 이 문제일 확률이 높습니다.

그 다음은 좌표계 불일치 방치입니다. 서로 다른 EPSG 코드로 만든 레이어를 변환 없이 겹쳐서 그리면, 값 자체는 유효한 숫자이기 때문에 에러 없이 조용히 어긋난 위치에 표시됩니다. 또한 투영 왜곡을 무시하고 Web Mercator 좌표에서 바로 면적이나 거리를 계산하면, 위도가 높은 지역일수록 오차가 커질 수 있습니다.

마지막으로 정밀도 손실과 SRID 미설정도 자주 나오는 실수입니다. 위경도를 소수점 자릿수를 줄여 저장하거나 부동소수점을 문자열로 왕복 변환하는 과정에서 오차가 누적될 수 있고, 좌표값만 저장하고 좌표계 정보를 남기지 않으면 나중에 그 데이터를 다시 쓸 때 좌표계를 추측해야 하는 상황이 생깁니다.

 

좌표계 비교
좌표계 EPSG 단위 주 용도
WGS84 4326 도(degree) GPS, 위경도 저장/교환
Web Mercator 3857 미터(투영) 웹 지도 타일(구글맵 등)
한국 중부원점 5186 미터 국내 측량·공공데이터
UTM-K(단일계) 5179 미터 전국 단일 좌표계, 국내 GIS

 

정확한 거리나 면적 계산이 필요할 때는 해당 지역에 맞는 미터 단위 투영 좌표계로 변환한 뒤 계산하는 것이 일반적으로 권장됩니다.

 

예제: PostGIS와 pyproj로 변환하기

PostGIS는 컬럼에 SRID를 명시해두고, 다른 좌표계와 연산할 때는 반드시 ST_Transform으로 맞춰주는 방식을 기본으로 합니다.

-- WGS84(4326) 좌표를 한국 중부원점(5186)으로 변환 후 면적 계산
SELECT
  id,
  ST_Area(
    ST_Transform(geom, 5186)
  ) AS area_sqm
FROM parcels
WHERE ST_SRID(geom) = 4326;

-- 서로 다른 SRID를 가진 두 레이어 비교 시 한쪽을 변환해서 맞춤
SELECT a.id
FROM layer_a a
JOIN layer_b b
  ON ST_Intersects(a.geom, ST_Transform(b.geom, ST_SRID(a.geom)));

Python에서는 pyproj의 Transformer를 사용합니다. always_xy=True 옵션을 명시하면 축 순서를 (경도, 위도)로 고정할 수 있습니다.

from pyproj import Transformer

# WGS84(4326) -> 한국 UTM-K(5179), always_xy=True로 (경도, 위도) 순서 고정
transformer = Transformer.from_crs("EPSG:4326", "EPSG:5179", always_xy=True)

lon, lat = 127.0276, 37.4979  # 경도, 위도 순서
x, y = transformer.transform(lon, lat)
print(x, y)

 

실무에서 이것만은 챙기세요
1. SRID를 항상 함께 저장 — 좌표값만 보고 좌표계를 추측하지 않도록 EPSG 코드를 메타데이터로 남깁니다
2. 불필요한 변환 피하기 — 입력·목표 좌표계가 실제로 다른지 먼저 확인 후 변환을 적용합니다
3. 계산 단위 명시 — 거리·면적 계산 로직에는 어떤 좌표계에서 계산했는지 주석으로 남깁니다
4. 여러 지역으로 테스트 — 원점에서 먼 지역의 좌표도 테스트 데이터에 섞어 두면 실수를 조기에 발견할 수 있습니다

 

마무리 — 3줄 요약

① 좌표가 어긋나는 버그는 대부분 좌표계 자체가 아니라 위경도 순서, SRID 누락, 변환 생략 같은 코드 쪽 가정 문제입니다.
② 거리·면적처럼 단위가 의미를 갖는 계산은 WGS84 도 단위 그대로 하지 말고 지역 맞춤 투영 좌표계로 변환한 뒤 계산하는 것이 안전합니다.
③ PostGIS의 ST_Transform, pyproj의 Transformer(always_xy=True)처럼 축 순서와 SRID를 명시적으로 다루는 습관이 실수를 줄이는 가장 확실한 방법입니다.
