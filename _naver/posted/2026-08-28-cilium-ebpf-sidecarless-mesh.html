사이드카 없이 서비스 메시를 — Cilium eBPF 기반 사이드카리스 메시 실무

인프라

한 줄 요약 — 파드마다 붙는 Envoy 사이드카 없이 커널의 eBPF로 트래픽을 직접 처리하는 Cilium의 사이드카리스 서비스 메시 구조와, 기존 사이드카 모델 대비 얻는 것과 잃는 것을 정리했습니다.

 

파드 수에 비례해 늘어나는 사이드카 오버헤드

Istio나 Linkerd 같은 전통적인 서비스 메시는 각 파드에 Envoy 사이드카 컨테이너를 함께 띄워, 그 파드로 들고 나는 모든 트래픽을 사이드카를 거치도록 강제합니다. 문제는 파드 수가 늘어날수록 사이드카 개수도 똑같이 늘어난다는 점입니다. 수천 개 파드를 운영하는 클러스터에서는 이 오버헤드가 누적되어 상당한 인프라 비용과 지연으로 돌아옵니다.

사이드카리스(sidecarless) 서비스 메시는 파드마다 프록시를 띄우는 대신, 각 노드에 하나씩 있는 커널의 eBPF 프로그램이 해당 노드의 모든 트래픽을 커널 레벨에서 직접 처리하도록 구조를 바꿉니다. Cilium이 이 접근을 대표하는 구현체입니다.

 

핵심 개념 1 — 트래픽 경로의 차이

사이드카 모델에서 트래픽은 애플리케이션 컨테이너 → iptables 리다이렉션 → 같은 파드의 Envoy 사이드카 → 실제 목적지로 흐릅니다. 매 홉마다 컨테이너 네트워크 네임스페이스 경계를 넘고 사용자 공간 프록시를 거치므로 지연이 누적됩니다. eBPF 모델에서는 커널 안에 로드된 프로그램이 커널 공간에서 직접 처리해 이 홉 자체가 없어집니다.

 

핵심 개념 2 — 노드 단위 자원 vs 파드 단위 자원
기준 사이드카 모델 eBPF 사이드카리스
프록시 배치 단위 파드마다 1개 노드마다 1개
파드 증가 시 오버헤드 선형 증가 상대적으로 완만
L7 기능 사이드카가 전담 노드 단위 프록시로 보완

 

핵심 개념 3 — 잃는 것: L7 기능과 장애 격리 단위

eBPF는 L3/L4 레벨 처리에는 강력하지만, HTTP 헤더 기반 라우팅처럼 L7 지식이 필요한 기능은 커널 안에서 직접 처리하기 어렵습니다. 그래서 Cilium은 L7 기능이 필요할 때 노드당 하나의 공유 프록시를 별도로 두는 하이브리드 구조를 취합니다. 이 공유 구조는 장애 격리 단위도 파드에서 노드로 넓힙니다.

예제 — Cilium 설치와 L7 정책
# Cilium CLI로 kube-proxy 대체 + eBPF 기반 데이터 플레인 설치
cilium install --set kubeProxyReplacement=true
cilium status --wait
cilium connectivity test
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-get-only
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
    - fromEndpoints:
        - matchLabels:
            app: frontend
      toPorts:
        - ports:
            - port: "8080"
              protocol: TCP
          rules:
            http:
              - method: "GET"
                path: "/api/.*"

L7 규칙이 포함된 정책은 내부적으로 노드 단위 프록시로 위임되어 처리되고, L3/L4만으로 충분한 규칙은 eBPF가 직접 처리해 프록시를 거치지 않습니다.

 

실무 도입 시 이것만은 챙기세요
1. L7 정책 목록부터 감사하세요 — HTTP 경로 기반 라우팅이 많다면 마이그레이션 후에도 프록시 경유가 필요한 부분이 많습니다.
2. 커널 버전 요구사항을 미리 확인하세요 — 오래된 커널을 쓰는 노드 풀은 일부 기능이 제한될 수 있습니다.
3. 관측성 도구를 별도로 준비하세요 — Hubble 같은 Cilium 전용 관측 도구를 익혀야 합니다.

 

마무리 — 3줄 요약

① 사이드카리스 메시는 노드당 하나의 eBPF 프로그램이 커널 레벨에서 트래픽을 직접 처리해 파드 수에 비례하던 오버헤드를 줄입니다.
② L7 기능은 여전히 노드 단위 공유 프록시가 필요한 경우가 많아 "완전히 프록시가 없다"기보다는 공유 구조에 가깝습니다.
③ 장애 격리 단위가 노드로 넓어지므로 L7 정책 의존도와 커널 버전을 함께 점검해야 합니다.
