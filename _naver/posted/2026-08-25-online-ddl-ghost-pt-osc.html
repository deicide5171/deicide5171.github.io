테이블을 잠그지 않고 바꾼다 — gh-ost와 pt-online-schema-change 내부 동작

2026. 8. 25. · 데이터베이스

한 줄 요약 — 수억 건짜리 MySQL 테이블 변경 시 서비스를 멈추지 않게 해주는 gh-ost와 pt-online-schema-change가 그림자 테이블 복사·변경 반영을 어떻게 다르게 처리하는지 비교했습니다.

 

ALTER TABLE 하나가 서비스를 멈추는 순간

MySQL에서 수억 건짜리 테이블에 ALTER TABLE로 컬럼 하나를 추가하려는데, 이 명령이 몇 시간 동안 테이블을 잠그고 서비스 전체를 멈춰 세운 적이 있다면 이미 이 문제를 몸으로 겪은 것입니다. InnoDB의 온라인 DDL이 많이 개선되긴 했지만, 여전히 특정 변경 유형이나 버전에 따라 부족한 경우가 많습니다.

이 틈을 메우는 것이 gh-ost(GitHub)와 pt-online-schema-change(Percona Toolkit)입니다. 둘 다 "원본 테이블을 잠그지 않고 스키마를 바꾼다"는 목표는 같지만, 내부 메커니즘이 근본적으로 다릅니다.

 

핵심 개념 1 — 공통 전략, 그림자 테이블 복사 후 스왑

두 도구 모두 기본 전략은 같습니다. 원본과 동일한 구조에 변경 사항을 적용한 그림자 테이블을 새로 만들고, 원본 데이터를 조금씩 복사합니다. 복사가 끝나면 이름을 원자적으로 바꿔치기해서 전환을 완료합니다. 복사가 진행되는 동안 원본에 계속 들어오는 변경을 그림자 테이블에도 반영해야 하는데, 이 부분에서 두 도구의 접근이 갈립니다.

 

핵심 개념 2 — 트리거 방식 vs binlog 스트리밍

pt-online-schema-change는 원본 테이블에 트리거를 걸어, 변경이 생길 때마다 그림자 테이블에도 즉시 반영합니다. 구현이 단순하지만 모든 쓰기 트랜잭션이 트리거 실행 비용을 추가로 부담합니다. gh-ost는 트리거를 전혀 쓰지 않습니다. 대신 자신을 복제 레플리카처럼 등록해서 binlog 스트림을 직접 읽고 변경 이벤트를 파싱해 그림자 테이블에 비동기로 반영합니다. 원본 테이블 쓰기 경로에 추가 부하가 없고 정교한 스로틀링이 가능한 대신, ROW 포맷 binlog와 복제 권한이 필요해 운영 복잡도는 더 높습니다.

구분 pt-online-schema-change gh-ost
변경 반영 방식 트리거 binlog 스트림 파싱
원본 쓰기 부하 추가 발생 거의 없음
필요 조건 트리거 생성 권한 ROW binlog, 복제 권한

 

핵심 개념 3 — 컷오버, 가장 위험한 순간

복사가 끝난 뒤 원본과 그림자 테이블을 바꿔치기하는 컷오버 순간이 가장 조심스러운 구간입니다. rename 자체는 원자적이지만, 그 직전까지 밀려 있던 변경분을 마저 반영하고 나서 rename해야 데이터 누락이 없습니다. 두 방식 모두 이 구간은 수백 밀리초 수준으로 짧지만, 트래픽이 매우 많은 서비스라면 이 순간에도 타임아웃이 발생할 수 있어 트래픽이 낮은 시간대로 잡는 것이 안전합니다.

 

예제 — gh-ost 실행 명령
gh-ost \
  --host=db-primary.internal \
  --user=migration_user \
  --database=shop \
  --table=orders \
  --alter="ADD COLUMN shipped_at DATETIME NULL" \
  --max-load=Threads_running=25 \
  --critical-load=Threads_running=50 \
  --chunk-size=1000 \
  --switch-to-rbr \
  --execute
# --execute 없이 실행하면 dry-run으로 예상 동작만 검증

 

실무 도입 시 이것만은 챙기세요
1. 외래 키가 걸린 테이블은 별도 검토가 필요합니다 — 두 도구 모두 FK 처리 방식을 옵션으로 제공하니 사전에 관계를 파악하세요.
2. 복사 도중 부하 모니터링은 필수입니다 — 스로틀링 기본값이 트래픽 패턴에 안 맞을 수 있습니다.
3. 롤백 계획을 미리 세우세요 — 원본 테이블은 즉시 삭제되지 않고 남겨지니, 언제 정리할지도 계획해야 합니다.

 

마무리 — 3줄 요약

① gh-ost와 pt-osc 모두 그림자 테이블 복사 후 원자적 rename 전략은 같지만, 변경 반영 방식이 트리거냐 binlog 스트리밍이냐로 갈립니다.
② gh-ost는 트리거 부하가 없고 정교한 스로틀링이 가능한 대신 운영 복잡도가 더 높습니다.
③ 컷오버 순간이 가장 위험하므로 트래픽이 낮은 시간대로 잡고 dry-run 검증과 부하 모니터링을 병행해야 합니다.
