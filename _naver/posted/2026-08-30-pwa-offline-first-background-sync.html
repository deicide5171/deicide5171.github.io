네트워크가 끊겨도 작업은 이어진다 — 오프라인 퍼스트 PWA와 백그라운드 동기화

프론트엔드

한 줄 요약 — 오프라인 퍼스트 PWA는 서비스 워커 캐싱으로 읽기를 보장하고, 오프라인 쓰기는 IndexedDB 큐에 저장했다가 Background Sync API로 연결 복구 시 자동 반영합니다.

 

네트워크가 항상 있다는 전제가 깨지는 순간

대부분의 웹 앱은 네트워크가 항상 연결돼 있다는 암묵적 전제 위에 짜입니다. 이 전제가 깨지는 순간 — 지하철 터널, 엘리베이터, 약한 와이파이 — 사용자는 로딩 스피너가 멈추지 않거나 네트워크 오류만 보게 됩니다. 오프라인 퍼스트 설계는 이 전제를 뒤집습니다. 네트워크를 있으면 좋은 것으로 취급하고, 앱의 핵심 기능이 네트워크 없이도 최소한 읽기는 되고 쓰기는 나중에 반영되도록 만드는 접근입니다.

 

핵심 개념 1 — 서비스 워커 캐싱 전략

오프라인에서도 앱 셸이 뜨려면 서비스 워커가 정적 자원을 캐시해 둬야 합니다. 캐싱 전략은 리소스 성격에 따라 다르게 골라야 합니다.

전략 동작 적합한 리소스
Cache First 캐시 우선, 없으면 네트워크 JS/CSS/폰트/아이콘
Network First 네트워크 우선, 실패 시 캐시 자주 바뀌는 목록·피드 API
Stale-While-Revalidate 캐시 즉시 반환 + 백그라운드 갱신 약간의 지연 허용 데이터

 

핵심 개념 2 — 오프라인 쓰기: IndexedDB에 낙관적으로 쌓아둡니다

읽기는 캐싱으로 해결되지만, 오프라인 중 저장 버튼을 누르는 쓰기 작업은 다른 문제입니다. 그 쓰기 요청을 IndexedDB에 큐 형태로 저장해두고, 화면에는 낙관적으로 저장됨 상태를 즉시 보여줍니다.

이 단계에서 중요한 설계 결정은 각 작업에 멱등성 키를 부여하는 것입니다. 연결 복구 후 큐에 쌓인 작업을 재생할 때 같은 요청이 중복 전송될 가능성이 있는데, 서버가 같은 멱등성 키로 온 요청을 한 번만 처리하도록 설계해야 오프라인 동안 한 번 누른 좋아요가 여러 번 반영되는 사고를 막을 수 있습니다.

 

핵심 개념 3 — Background Sync API: 연결 복구를 브라우저가 알려줍니다

Background Sync API를 쓰면 브라우저가 네트워크 연결 복구 시점을 감지해 서비스 워커를 깨워줍니다. 페이지가 닫혀 있어도 서비스 워커가 백그라운드에서 동작해 큐에 쌓인 요청을 전송할 수 있다는 점이 핵심 가치입니다. 다만 이 API는 브라우저 지원이 제한적이므로(Safari 미지원), 지원하지 않는 브라우저에서는 online 이벤트나 페이지 복귀 시점에 큐를 수동으로 재생하는 폴백을 함께 구현해야 합니다.

 

 

예제 — 서비스 워커 등록과 Background Sync
// service-worker.js
self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-pending-writes') {
    event.waitUntil(replayQueuedWrites());
  }
});

async function replayQueuedWrites() {
  const db = await openDB('offline-queue', 1);
  const pending = await db.getAll('writes');

  for (const item of pending) {
    try {
      const res = await fetch(item.url, {
        method: item.method,
        headers: {
          'Content-Type': 'application/json',
          'Idempotency-Key': item.idempotencyKey,
        },
        body: JSON.stringify(item.payload),
      });
      if (res.ok) await db.delete('writes', item.id);
    } catch {
      // 여전히 오프라인이면 큐에 남아 다음 sync를 기다린다
    }
  }
}

 

실무 포인트

캐시 버전 관리를 소홀히 하면 오래된 앱 셸이 영구히 고정됩니다. 캐시 이름에 빌드 해시나 버전을 포함시키고, 새 서비스 워커 활성화 시 이전 버전 캐시를 정리하는 로직이 필요합니다.

낙관적 UI와 실패 알림 사이의 균형을 설계하세요. 온라인 복귀 후 서버 검증 실패 시 사용자에게 뒤늦게라도 명확히 알려야 신뢰가 유지됩니다.

주의 — 모든 기능을 오프라인 대응할 필요는 없습니다. 결제, 실시간 경매처럼 최신 서버 상태를 반드시 확인해야 하는 기능은 오프라인에서 비활성화하고 안내 메시지를 보여주는 것이 낙관적 처리보다 안전합니다.
