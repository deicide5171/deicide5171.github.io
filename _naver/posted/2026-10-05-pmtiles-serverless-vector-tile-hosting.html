타일 서버를 걷어낸다는 것 — PMTiles로 지도를 서버리스로 서빙하는 설계

GIS

한 줄 요약 — "지도에 마커 몇 개 찍어서 보여주면 돼요"라는 요구가 Tileserver-GL이나 Martin 같은 상시 가동 타일 서버 운영으로 이어지는 건 당연한 선택이 아닙니다. PMTiles로 타일 피라미드 전체를 단일 파일에 담아 S3·R2에서 HTTP Range Request만으로 서빙하는 구조와, 이 접근이 통하지 않는 경계선까지 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"지도에 우리 매장 위치랑 배달 권역을 올려서 보여주면 돼요. 사용자가 직접 데이터를 바꾸는 건 아니에요." 이 요구를 들으면 거의 반사적으로 타일 서버부터 떠올리게 됩니다. Tileserver-GL이나 Martin을 띄우고, 벡터 타일을 동적으로 생성하거나 캐싱하고, 트래픽이 튈 때를 대비해 오토스케일링까지 설계합니다. 그런데 이 요구를 다시 읽어보면 "사용자가 데이터를 바꾸지 않는다"는 말이 핵심입니다. 바뀌지 않는 데이터를 매 요청마다 서버가 다시 계산해서 내려줄 이유가 없다면, 애초에 서버가 필요한지부터 의심해야 합니다.

PMTiles는 이 질문에 "타일 피라미드 전체를 미리 만들어 파일 하나에 담고, HTTP Range Request로 필요한 바이트만 떼어 읽으면 서버가 필요 없다"고 답합니다. ZIP 아카이브처럼 수많은 타일을 하나의 파일 안에 넣되, 고정 길이 헤더와 계층형 디렉터리 구조를 둬서 클라이언트가 전체 파일을 내려받지 않고도 특정 줌 레벨·좌표의 타일 위치를 바로 찾아갈 수 있게 설계했습니다. 실제로 전 세계 OpenStreetMap 데이터를 9시간마다 갱신하면서 월 1.61달러로 운영한 사례가 보고될 만큼, 상시 가동 서버 없이도 글로벌 스케일 지도 서빙이 가능하다는 것이 증명됐습니다. 여기에 더해 Overture Maps 같은 공개 데이터셋이 아예 PMTiles 형식으로 AWS·Azure에 직접 배포되기 시작하면서, "타일 서버를 먼저 띄운다"는 전제 자체를 재검토할 타이밍이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"지도 데이터를 서빙해주세요"는 실제로 세 가지 다른 요구를 가리킬 수 있습니다. 첫째, 전 세계 또는 특정 지역의 정적 베이스맵이나 참조 데이터를 불특정 다수에게 빠르게 보여주는 경우 — 읽기 전용이고 갱신 주기가 하루~며칠 단위입니다. 둘째, 사용자별로 필터링되거나 권한에 따라 달라지는 지도 데이터를 보여주는 경우 — 요청마다 결과가 달라지므로 어떤 형태로든 동적 계산이 필요합니다. 셋째, 대용량 공간 데이터를 집계·분석해서 통계나 히트맵을 뽑아내는 경우 — 이건 타일 서빙이 아니라 쿼리 엔진의 영역입니다. PMTiles는 정확히 첫 번째 경우에 최적화된 해법이고, 나머지 두 경우에는 보조적으로만 쓰이거나 아예 맞지 않습니다.

 

전체 시스템에서의 위치

 

데이터 파이프라인은 원본 공간 데이터를 tippecanoe로 벡터 타일 피라미드로 구운 뒤, pmtiles convert로 단일 .pmtiles 파일로 묶는 것에서 시작합니다. 이 파일을 S3나 Cloudflare R2 같은 오브젝트 스토리지에 올리고 CDN을 앞단에 붙이면, 브라우저의 pmtiles.js가 MapLibre GL JS와 연동해 현재 보이는 영역의 타일만 Range Request로 가져옵니다. 서버 프로세스는 어디에도 없습니다 — CDN 캐시 히트가 늘어날수록 오히려 원본 스토리지 부하는 줄어듭니다. 반면 사용자별 권한 필터링이나 실시간 위치 업데이트처럼 동적인 레이어가 필요하다면, 그 레이어만 별도의 경량 API로 분리해서 PMTiles 베이스맵 위에 겹쳐 그리는 하이브리드 구조로 가야 합니다. "전부 정적이거나 전부 동적이거나"로 이분화할 필요는 없습니다.

 

선택의 트레이드오프
기준 PMTiles(서버리스) 전통 타일 서버 클라이언트 직접 GeoJSON
운영 비용 매우 낮음 중간~높음 낮음
데이터 갱신 주기 배치 재생성(분~일) 실시간 반영 가능 즉시 반영
사용자별 동적 필터링 불가능 가능 가능(전송량 부담)
데이터 규모 전 세계 단위도 가능 가능하지만 서버 자원 소요 소규모에만 적합
가장 흔한 함정 캐시 무효화 설계 누락 트래픽 급증 시 서버 병목 초기 로딩 지연

 

표에서 결정적인 줄은 "사용자별 동적 필터링"입니다. PMTiles 파일은 모든 사용자에게 동일한 내용을 서빙하므로, "로그인한 사용자에게만 보이는 매장"처럼 요청마다 결과가 달라져야 하는 레이어는 애초에 이 방식으로 풀 수 없습니다. 이 요구를 무시하고 PMTiles로 밀어붙이면 결국 클라이언트에서 전체 데이터를 받아 직접 필터링하는 식으로 돌아가며, PMTiles가 주려던 효율을 스스로 포기하는 셈이 됩니다.

 

실제 프로젝트 진행 순서

1단계: 레이어별로 갱신 주기와 개인화 여부를 먼저 분류합니다. 모두에게 동일하고 갱신이 느린 레이어만 PMTiles 후보로 남깁니다.

2단계: tippecanoe 빌드 파이프라인을 CI에 통합하고, 파일명에 버전·해시를 붙여 캐시 무효화 문제를 구조적으로 피합니다.

3단계: Range Request를 제대로 지원하는 스토리지·CDN인지 도입 전에 검증합니다.

4단계: 동적 레이어는 처음부터 별도 API로 분리 설계해 MapLibre 위에서 합성합니다.

5단계: 서버가 없다는 것은 서버 로그로 장애를 감지하는 방식이 통하지 않는다는 뜻이므로, 빌드 파이프라인 실패와 CDN 캐시 적중률을 별도로 모니터링합니다.

주의 — "서버가 필요 없다"를 "인프라 설계가 필요 없다"로 오해하지 마세요. PMTiles는 상시 프로세스를 없애는 것이지, 빌드 파이프라인·캐시 무효화·버전 관리 설계를 없애주지 않습니다.

 

정리

"지도 데이터를 보여주세요"라는 요구는 정적 베이스맵, 사용자별 동적 필터링, 분석 집계라는 서로 다른 세 가지 기술 문제로 번역되며, PMTiles는 그중 정적 베이스맵 서빙에만 최적화돼 있습니다. 실제 프로젝트에서는 정적 레이어를 PMTiles로, 동적 레이어를 별도 API로 분리하는 하이브리드 구조로 설계하는 것이 가장 현실적입니다.
