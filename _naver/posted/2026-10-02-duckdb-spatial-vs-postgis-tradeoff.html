분석 한 번에 PostGIS 서버를 또 띄워야 할까 — DuckDB Spatial로 끝내는 판단 기준

GIS

한 줄 요약 — "GeoParquet 파일 하나만 분석해주세요"라는 1회성 요청에 매번 PostGIS 서버를 새로 띄우는 건 과합니다. 서버 없이 프로세스 안에서 분석을 끝내는 DuckDB Spatial과, 언제 PostGIS로 승격해야 하는지 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"이번 분기 상권 확장 검토용으로, Overture에서 받은 이 지역 GeoParquet 파일 하나만 빠르게 분석해주세요." 이런 요청을 받으면 그동안 빌더가 쥔 카드는 PostGIS 서버를 새로 띄우고 데이터를 임포트하거나, GeoPandas로 파일 전체를 메모리에 올리는 것뿐이었습니다. 둘 다 파일 하나 들여다보는 일치고는 과했습니다.

이 전제가 흔들린 이유는 DuckDB의 spatial 확장이 빠르게 성숙했기 때문입니다. GEOS 기반 공간 함수와 PROJ 좌표계 변환을 바이너리 하나에 담아, 서버 프로세스 없이 공간 쿼리를 실행할 수 있습니다. S3의 GeoParquet·COG 파일을 내려받지 않고 원격에서 바로 읽는 기능까지 갖추면서, "서버 기반 공간 DB가 항상 정답"이라는 전제 자체를 다시 물어야 하게 됐습니다.

 

요구사항을 기술 문제로 번역하기

"공간 데이터를 분석해달라"는 말은 전혀 다른 두 요구를 뭉뚱그린 표현입니다. 하나는 앱이 실시간으로 반복해서 던지는 공간 질의(반경 안 매장 보여주기, 지오펜싱)로 동시 접속과 낮은 지연을 보장해야 하는 서빙 문제입니다. 다른 하나는 분석가가 한 번 돌리는 리포트성 질의로 읽기 위주이고 동시성 요구가 거의 없습니다. 요청을 받으면 가장 먼저 이 둘을 구분해야 합니다.

 

전체 시스템에서의 위치

 

서빙 경로는 상시 가동 중인 PostGIS가 GiST 인덱스로 요청을 빠르게 처리한 뒤 다음 요청을 또 받습니다. 분석 경로는 정반대로, DuckDB 프로세스가 S3의 원본 파일을 ETL 없이 그 자리에서 읽고 질의가 끝나면 사라집니다. 결과만 저장소에 남습니다. 분석 경로에는 애초에 "상주"라는 개념이 없어도 됩니다.

 

선택의 트레이드오프
기준 PostGIS (상시 서버) DuckDB Spatial (임베디드)
운영 모델 서버 프로세스 상시 가동 프로세스 내 라이브러리, 서버 불필요
데이터 소스 로컬 테이블로 임포트 필요 S3 원격 파일 직접 쿼리
적합한 경우 앱의 실시간 반복 질의 1회성·배치 분석

 

가장 흔한 함정은 "DuckDB가 빠르니 운영 DB도 교체하자"는 성급한 결론입니다. DuckDB spatial은 매 쿼리마다 범위를 스캔하는 구조라 초당 수백 번 반복되는 서빙 워크로드에는 맞지 않습니다. 반대로 분석가가 매번 새 테이블을 만들고 지우는 작업을 운영 PostGIS에서 반복하는 것도 그 자체로 사고 위험입니다.

 

실제 프로젝트 진행 순서

1단계: 요청이 앱 기능인지 분석 작업인지부터 구분합니다.

2단계: 분석이라면 DuckDB부터 시도합니다. 설치 없이 INSTALL spatial; LOAD spatial;만으로 바로 쿼리할 수 있습니다.

3단계: 원본이 S3의 GeoParquet·COG라면 ETL 없이 원격 경로를 그대로 쿼리에 바인딩합니다.

4단계: 같은 질의가 반복·동시·저지연 요구로 바뀌면 그때 PostGIS 승격을 검토합니다.

5단계: 승격 시 DuckDB에서 검증한 쿼리를 거의 그대로 포팅합니다. 두 시스템 모두 GEOS 기반이라 함수명이 대부분 겹칩니다.

INSTALL spatial;
LOAD spatial;

SELECT name, ST_AsText(geometry) AS geom
FROM read_parquet('s3://overture-maps/release/places/*.parquet')
WHERE ST_Within(
  geometry,
  ST_GeomFromText('POLYGON((127.0 37.5, 127.1 37.5, 127.1 37.6, 127.0 37.6, 127.0 37.5))')
)
LIMIT 100;
주의 — DuckDB의 공간 인덱스는 세션이 끝나면 함께 사라지는 비영속 구조입니다. 동시 쓰기 트랜잭션 보장도 약해 운영 DB의 대체재로 쓰면 안 됩니다.

 

정리

"공간 데이터를 분석해달라"는 요청은 먼저 앱 서빙 문제인지 1회성 분석 문제인지부터 구분해야 합니다. 분석이라면 서버를 새로 띄우기 전에 DuckDB Spatial로 S3의 원본 파일을 직접 쿼리하는 쪽이 더 빠르고 가볍습니다. 반복·동시·저지연 요구로 바뀌는 순간이 PostGIS 승격 시점입니다.
