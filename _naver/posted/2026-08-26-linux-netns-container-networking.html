컨테이너는 어떻게 자기만의 네트워크를 갖는가 — 리눅스 네트워크 네임스페이스 내부구조

2026. 8. 26. · 인프라

한 줄 요약 — 같은 이름·같은 IP 대역의 컨테이너 수백 개가 충돌 없이 공존하는 이유는 리눅스 커널의 네트워크 네임스페이스 기능 때문입니다. veth 페어, 브리지, iptables NAT까지 손으로 직접 재현하며 내부 구조를 뜯어봤습니다.

 

모든 컨테이너가 eth0을 가질 수 있는 이유

같은 호스트에서 컨테이너 A와 컨테이너 B를 띄우면 둘 다 eth0이라는 이름의 인터페이스를 갖고, 둘 다 172.17.0.x 대역의 IP를 받습니다. 호스트 입장에서 물리 네트워크 인터페이스는 하나뿐인데, 어떻게 같은 이름·같은 대역의 인터페이스가 컨테이너마다 독립적으로 존재할 수 있을까요? 답은 Docker나 Kubernetes가 특별한 마법을 부리는 게 아니라, 리눅스 커널이 제공하는 네트워크 네임스페이스(netns)라는 격리 기능을 그대로 활용한다는 데 있습니다.

네임스페이스는 프로세스가 보는 커널 리소스의 뷰를 격리하는 리눅스 커널 기능입니다. 네트워크 네임스페이스는 라우팅 테이블, 인터페이스 목록, 방화벽 규칙, 포트 공간을 통째로 격리합니다. 컨테이너 런타임의 "네트워크 격리" 기능은 사실 이 커널 기능을 얇게 감싼 것에 불과합니다.

 

핵심 개념 1 — 네임스페이스 격리와 veth 페어

새 네트워크 네임스페이스를 만들면 그 안에는 루프백만 존재하는 완전히 빈 네트워크 스택이 생깁니다. 외부와 연결하려면 veth(virtual ethernet) 페어를 씁니다. veth는 항상 쌍으로 생성되는 가상 인터페이스로, 한쪽에 들어간 패킷이 다른 쪽으로 그대로 나오는 파이프처럼 동작합니다. 한쪽 끝을 컨테이너 네임스페이스에, 다른 쪽 끝을 호스트 브리지에 연결하면 격리된 네임스페이스와 호스트 네트워크가 이어집니다.

Docker가 컨테이너를 띄울 때 정확히 이 작업을 합니다. 새 netns를 만들고, veth 페어를 생성해 한쪽을 컨테이너 netns의 eth0으로 넣고, 다른 쪽을 호스트의 docker0 브리지에 연결합니다. 컨테이너가 수백 개라도 각자 다른 netns에 있으므로 모두 eth0을 써도 충돌하지 않습니다.

 

핵심 개념 2 — 외부 통신은 결국 NAT를 거칩니다

컨테이너의 IP는 호스트 밖에서는 라우팅되지 않는 사설 대역입니다. 컨테이너가 외부와 통신하려면 호스트가 출발지 주소를 자신의 것으로 바꿔주는 SNAT(마스커레이딩)이 필요하고, 외부에서 컨테이너로 들어오는 포트 포워딩은 DNAT로 이뤄집니다. 이 규칙은 Docker가 iptables 규칙으로 자동 생성합니다.

방향 처리 실행 위치
컨테이너 → 외부 출발지 IP를 호스트 IP로 SNAT iptables nat POSTROUTING
외부 → 컨테이너 목적지를 컨테이너 IP:포트로 DNAT iptables nat PREROUTING
같은 브리지 내 통신 netns만 거쳐 L2 통신, NAT 없음 docker0 브리지

 

 

예제 — ip netns로 컨테이너 네트워킹 재현하기

아래 여섯 단계가 곧 컨테이너 런타임이 매번 자동으로 수행하는 작업입니다. Docker, containerd, CRI-O 모두 결국 이 커널 프리미티브 위에 구현돼 있습니다.

# 1. 새 네트워크 네임스페이스 생성
sudo ip netns add ns1

# 2. veth 페어 생성
sudo ip link add veth-host type veth peer name veth-ns1

# 3. veth-ns1을 ns1 네임스페이스로 이동
sudo ip link set veth-ns1 netns ns1

# 4. ns1 안에서 IP 부여 및 활성화
sudo ip netns exec ns1 ip addr add 172.18.0.2/24 dev veth-ns1
sudo ip netns exec ns1 ip link set veth-ns1 up
sudo ip netns exec ns1 ip link set lo up

# 5. 호스트 쪽 브리지에 연결
sudo ip link add br-demo type bridge
sudo ip addr add 172.18.0.1/24 dev br-demo
sudo ip link set br-demo up
sudo ip link set veth-host master br-demo
sudo ip link set veth-host up

# 6. SNAT 규칙 (마스커레이딩)
sudo iptables -t nat -A POSTROUTING -s 172.18.0.0/24 ! -o br-demo -j MASQUERADE

# 검증
sudo ip netns exec ns1 ping -c 3 8.8.8.8

 

실무 도입 시 이것만은 챙기세요
1. docker0은 단일 호스트 안에서만 유효합니다 — 여러 노드에 걸친 컨테이너 통신은 VXLAN 오버레이나 BGP 라우팅으로 노드 간 네트워크를 이어야 합니다. Flannel, Calico 같은 CNI 플러그인이 이 부분을 담당합니다.
2. 트러블슈팅은 ip netns exec로 확인하세요 — 컨테이너 안에서 curl이 안 될 때 nsenter나 ip netns exec로 그 네임스페이스에 직접 들어가 라우팅 테이블과 iptables 카운터를 확인하는 것이 가장 빠릅니다.
3. 극한 성능이 필요하면 hostNetwork를 고려하세요 — veth·브리지·NAT 경로는 약간의 오버헤드가 있습니다. 다만 격리를 포기하는 트레이드오프이므로 신중히 적용해야 합니다.

 

마무리 — 3줄 요약

① 컨테이너의 네트워크 격리는 리눅스 커널의 네트워크 네임스페이스 기능을 그대로 활용한 것이며, ip netns로 직접 재현 가능한 표준 기능입니다.
② veth 페어가 격리된 네임스페이스와 호스트를 연결하고, 브리지가 여러 veth를 하나의 L2 대역으로 묶으며, iptables NAT이 외부 통신을 중계합니다.
③ 노드 간 컨테이너 통신은 단일 호스트 브리지로 해결되지 않으며 CNI 플러그인의 오버레이 네트워크가 필요합니다.
