프롬프트 엔지니어링을 넘어, 컨텍스트 엔지니어링

2026. 8. 15. · AI

한 줄 요약 — AI 에이전트 시대에는 "무엇을 말할까"보다 "모델에게 무엇을 보여줄까"를 설계하는 컨텍스트 엔지니어링이 더 중요해지고 있습니다.

 

프롬프트만 잘 쓰면 되던 시절은 지나갔습니다

한동안 AI를 잘 쓰는 기술은 곧 "프롬프트를 잘 쓰는 기술"이었습니다. 어떤 문구를 넣어야 답이 잘 나오는지, 예시를 몇 개 넣어야 하는지가 관심사였죠. 그런데 AI가 여러 단계에 걸쳐 스스로 도구를 쓰고 파일을 읽는 에이전트 형태로 발전하면서, 단일 질문 하나 잘 쓰는 것만으로는 부족한 상황이 늘어났습니다.

여러 단계를 거치다 보면 AI가 몇 단계 전에 준 지시를 잊어버리거나, 필요 없는 정보가 쌓여 정작 중요한 내용이 묻히는 문제가 생깁니다. 이런 이유로 최근에는 컨텍스트 엔지니어링이라는 표현이 자주 쓰이고 있습니다.

 

두 개념, 어떻게 다를까요
구분 프롬프트 엔지니어링 컨텍스트 엔지니어링
초점 문구, 지시사항 표현 전체 정보 구성과 흐름
범위 한 번의 요청 여러 턴에 걸친 대화 전체
대표 문제 지시를 잘못 이해함 정보 과다, 핵심 누락

 

둘이 완전히 다른 개념은 아닙니다. 컨텍스트 엔지니어링이 프롬프트 엔지니어링을 포함하는 더 큰 개념이라고 보시면 이해가 쉽습니다.

 

컨텍스트 윈도우, 어떻게 관리할까요

AI가 참고할 수 있는 정보의 양(컨텍스트 윈도우)은 정해져 있습니다. 그래서 실무에서는 세 가지를 함께 신경 씁니다. 첫째는 관련성 필터링으로, 검색 결과나 파일 내용을 전부 넣지 않고 필요한 부분만 추립니다. 둘째는 압축으로, 오래된 대화 내용을 요약본으로 바꿔 공간을 확보합니다. 셋째는 단기기억과 장기기억의 구분으로, 지금 이 순간만 필요한 정보와 계속 기억해야 할 정보(사용자 선호, 프로젝트 규칙 등)를 나눠서 관리하는 것입니다.

 

코드로 보는 개념

아래는 컨텍스트를 조립하는 과정을 단순화한 예시입니다. 실제 구현은 더 복잡하지만 핵심 흐름은 비슷합니다.

def build_context(session, current_task):
    long_term = load_persistent_memory(session.user_id)
    recent_turns = summarize_if_needed(session.history, max_tokens=4000)
    relevant_snippets = filter_by_relevance(
        session.tool_results, current_task, top_k=5
    )
    return {
        "system": long_term,
        "history": recent_turns,
        "context": relevant_snippets,
    }

 

실무 도입 시 이것만은 챙기세요
1. 정보량 ≠ 성능 — 컨텍스트가 길다고 항상 답변이 좋아지는 것은 아닙니다. 오히려 관련 없는 내용이 섞이면 방해가 됩니다.
2. 압축 규칙을 미리 정하세요 — 요약 과정에서 어떤 정보는 반드시 원문 그대로 보존할지 정해두면 나중에 문제 원인을 찾기 쉽습니다.
3. 도구 설명도 공간을 차지합니다 — 자주 안 쓰는 도구는 필요할 때만 불러오는 방식을 고려하세요.
4. 감이 아니라 지표로 판단하세요 — 구성 방식을 바꿨다면 실제 작업 성공률 같은 지표로 비교해보는 것이 안전합니다.

 

마무리 — 3줄 요약

① 컨텍스트 엔지니어링은 프롬프트 엔지니어링보다 넓은, "무엇을 보여줄까"를 설계하는 개념입니다.
② 관련성 필터링, 압축, 장단기 기억 구분이 핵심 관리 전략입니다.
③ 도구 설명과 시스템 프롬프트도 컨텍스트의 일부이니 토큰 예산을 함께 고려해야 합니다.

읽어주셔서 감사합니다. AI 에이전트를 다루신다면 프롬프트 문구 하나보다 전체 정보 흐름을 먼저 점검해 보시길 권해 드립니다.
