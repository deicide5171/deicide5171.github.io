차원이 크다고 항상 좋은 건 아니다 — 임베딩 모델 선택 기준 정리

2026. 8. 25. · AI

한 줄 요약 — 임베딩 모델 선택은 벤치마크 리더보드 점수가 아니라 도메인 적응, 다국어 성능, 차원 수를 자체 데이터로 검증해서 결정해야 합니다.

 

리더보드 1위가 우리 데이터에도 1위일까요

RAG 파이프라인을 구축할 때 임베딩 모델 선택은 종종 "MTEB 리더보드에서 점수가 제일 높은 걸로 하자"로 끝납니다. 문제는 공개 벤치마크가 일반 도메인, 주로 영어 위주 데이터셋으로 구성돼 있어서, 실제 서비스가 다루는 한국어 고객 상담 로그나 사내 용어가 잔뜩 섞인 기술 문서에서는 리더보드 순위와 실제 검색 품질이 따로 노는 경우가 드물지 않다는 점입니다.

임베딩 모델 선택은 "가장 성능 좋은 모델"이 아니라 "우리 데이터와 쿼리 분포에 가장 잘 맞는 모델"을 찾는 문제에 가깝습니다.

 

핵심 개념 1 — 도메인 적응, 벤치마크와 실제 데이터의 간극

임베딩 모델은 사전학습 데이터 분포에 강하게 영향을 받습니다. 범용 모델은 법률·의료·금융처럼 전문 용어 밀도가 높은 도메인에서 표면적으로 비슷한 단어를 가진 문장들을 실제 의미와 무관하게 가깝다고 판단하는 실수를 저지르기 쉽습니다. 이를 완화하는 방법은 도메인 데이터로 파인튜닝하거나, 임베딩은 범용 모델을 쓰고 검색 결과를 도메인 특화 리랭커(reranker)로 재정렬하는 것입니다.

 

핵심 개념 2 — 다국어 처리, 언어별 성능 편차

"multilingual" 표기가 붙은 모델이라고 모든 언어를 균등하게 잘 처리하는 것은 아닙니다. 대부분 학습 데이터에서 영어·중국어 비중이 압도적으로 높아, 한국어 검색 품질 편차가 큽니다. 교차 언어 검색(한국어 쿼리로 영어 문서 검색)을 지원해야 한다면 단일 언어 성능뿐 아니라 언어 간 임베딩 공간이 실제로 잘 정렬돼 있는지도 별도로 검증해야 합니다.

 

핵심 개념 3 — 차원 수, 크다고 항상 좋은 건 아닙니다

차원이 커지면 벡터 DB 저장 공간과 검색 연산량이 그대로 늘어나고, 학습 데이터 규모 대비 차원이 지나치게 크면 오히려 노이즈에 과적합되는 경우도 있습니다. 최근에는 Matryoshka Representation Learning(MRL) 기법으로 하나의 모델이 여러 차원으로 잘라 써도 성능이 크게 떨어지지 않도록 학습된 모델들도 있어, 저장 비용과 품질의 트레이드오프를 배포 후에도 유연하게 조정할 수 있습니다.

실무 도입 시 이것만은 챙기세요
1. 리더보드 순위보다 자체 골든셋을 먼저 만드세요 — 수십~수백 개 규모라도 실제 쿼리-정답 문서 쌍을 만들어 두는 것이 장기적으로 훨씬 저렴합니다.
2. 임베딩 모델 교체는 재인덱싱 비용을 동반합니다 — 잦은 모델 교체는 성능 개선보다 리스크가 더 커질 수 있습니다.
3. 쿼리와 문서의 길이 분포 차이를 확인하세요 — 일부 모델은 query:, passage: 같은 프리픽스를 요구합니다.

 

마무리 — 3줄 요약

② 다국어 모델은 언어별 성능 편차가 크므로 한국어 성능과 교차 언어 정렬을 별도로 검증해야 합니다.
③ 차원 수는 무조건 클수록 좋은 것이 아니며, Matryoshka 학습 모델처럼 유연하게 조정 가능한 선택지도 고려할 수 있습니다.
