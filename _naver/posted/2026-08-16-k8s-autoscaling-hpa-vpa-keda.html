쿠버네티스 오토스케일링 완전정복 — HPA·VPA·KEDA, 언제 무엇을 조합할까

2026. 8. 16. · 인프라

한 줄 요약 — HPA는 Pod 개수(수평), VPA는 Pod당 자원량(수직), KEDA는 외부 이벤트 기반 확장을 담당합니다. 세 도구는 경쟁이 아니라 보완 관계이며, 워크로드 특성에 맞게 조합하는 것이 핵심입니다.

 

왜 지금 오토스케일링을 다시 봐야 할까요

많은 팀이 kubectl autoscale로 HPA 하나만 걸어두고 "오토스케일링은 끝났다"고 생각합니다. 하지만 트래픽이 몰릴 때 Pod 개수는 늘어나는데 개별 Pod의 자원 배분(requests/limits)은 그대로라 여전히 스로틀링이 걸리거나, 메시지 큐에 작업이 쌓여도 CPU 사용률이 낮아 HPA가 전혀 반응하지 않는 경우를 겪어보셨을 겁니다.

이는 오토스케일링이 사실 서로 다른 축의 문제라는 것을 보여줍니다. 얼마나 많은 Pod를 띄울 것인가는 HPA(Horizontal Pod Autoscaler)가, Pod 하나가 얼마만큼의 자원을 쓸 것인가는 VPA(Vertical Pod Autoscaler)가, CPU·메모리가 아닌 다른 신호로 스케일할 것인가는 KEDA(Kubernetes Event-Driven Autoscaling)가 담당합니다.

세 도구의 차이를 모르면 "오토스케일링을 붙였는데 왜 장애가 그대로냐"는 질문에 답하기 어렵습니다. 오늘은 세 도구의 동작 원리 차이와 실전 조합 전략을 정리해보겠습니다.

 

핵심 개념 1·2: HPA와 VPA

HPA는 지정한 메트릭(기본은 CPU 사용률)이 목표치를 넘으면 Deployment의 replica 수를 늘리고, 낮아지면 줄입니다. Kubernetes 표준 컨트롤러로 metrics-server만 있으면 바로 쓸 수 있고, Custom Metrics API를 붙이면 요청 수·큐 대기시간 같은 지표로도 확장할 수 있습니다. 핵심 제약은 상태를 갖지 않는(stateless) 워크로드에 적합하다는 점입니다.

VPA는 Pod의 실제 CPU·메모리 사용 이력을 관찰해 requests/limits 값을 자동으로 조정(또는 추천)합니다. 다만 값을 바꾸려면 대부분 Pod 재시작이 필요합니다(In-place resize 지원 범위는 클러스터 버전에 따라 다르므로 반드시 확인이 필요합니다). 그래서 실시간 반응보다는 배치 잡이나 정기적인 리소스 사이징 최적화에 더 잘 맞습니다. HPA와 VPA를 같은 메트릭(CPU) 기준으로 동시에 적용하면 서로 충돌할 수 있어 주의가 필요합니다.

 

핵심 개념 3: KEDA와 Scale-to-Zero

KEDA는 CPU·메모리가 아닌 외부 이벤트 소스(메시지 큐 길이, Kafka consumer lag, 예약 큐 대기 작업 수 등)를 기준으로 스케일링을 트리거합니다. 내부적으로는 HPA를 생성해 위임하는 구조이며, 다양한 시스템을 위한 Scaler를 제공합니다. 가장 큰 차별점은 Scale-to-Zero입니다 — 유휴 상태일 때 Pod를 0개까지 줄였다가 이벤트가 들어오면 다시 띄우는 것으로, CPU 기반 HPA는 할 수 없는 동작입니다.

도구 확장 축 트리거 Scale-to-Zero 대표 적합 대상
HPA 수평(Pod 개수) CPU/메모리, 커스텀 메트릭 불가 상태 없는 웹/API 서버
VPA 수직(자원 요청량) 사용량 이력 분석 해당 없음 배치, 단일 인스턴스
KEDA 수평(Pod 개수) 외부 이벤트(큐, lag 등) 가능 비동기 워커, 큐 컨슈머

 

 

예제: HPA와 KEDA 설정 (YAML)

먼저 CPU 사용률 70%를 기준으로 하는 기본 HPA 설정입니다. stabilizationWindowSeconds는 트래픽이 일시적으로 빠졌다가 다시 늘어나는 패턴에서 Pod를 줄였다 늘렸다 반복하는 플래핑을 막는 데 유용합니다.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300

다음은 RabbitMQ 큐 길이를 기준으로 워커를 확장하는 KEDA ScaledObject입니다. minReplicaCount: 0이 핵심 기능으로, 큐가 비어 있으면 워커 Pod를 0개까지 줄여 유휴 비용을 없애고 메시지가 쌓이면 다시 Pod를 띄웁니다.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-worker-scaler
spec:
  scaleTargetRef:
    name: order-worker
  minReplicaCount: 0
  maxReplicaCount: 20
  cooldownPeriod: 60
  triggers:
    - type: rabbitmq
      metadata:
        queueName: order-queue
        mode: QueueLength
        value: "5"

 

실무 도입 시 이것만은 챙기세요
1. HPA와 VPA를 같은 메트릭으로 동시에 걸지 않기 — CPU 기준 HPA + CPU 기준 VPA는 서로 충돌 가능, VPA는 메모리 위주 또는 추천 모드로 운용
2. KEDA는 결국 HPA 위에서 동작 — ScaledObject 생성 시 내부적으로 HPA 리소스를 만들므로 기존 HPA 운영 노하우를 그대로 활용 가능
3. Scale-to-Zero는 콜드 스타트 비용과 함께 검토 — Pod가 0개에서 다시 뜨는 시간이 서비스 지연 요구사항과 맞는지 확인
4. 버전별 기능 차이는 반드시 클러스터에서 재확인 — VPA의 In-place resize 등은 배포판·버전에 따라 지원 범위가 다름

 

마무리 — 3줄 요약

① HPA는 Pod 개수(수평), VPA는 Pod당 자원량(수직), KEDA는 외부 이벤트 기반 확장(+ Scale-to-Zero)을 담당하는 서로 다른 도구입니다.
② KEDA는 내부적으로 HPA를 생성해 위임하는 구조이므로 기존 HPA 지식을 그대로 활용할 수 있습니다.
③ HPA와 VPA를 같은 메트릭으로 동시에 적용하지 말고, 워크로드 특성(상태 없음/배치/이벤트 기반)에 맞게 조합하는 것이 핵심입니다.
