"이 작업은 몇 분 걸려요"라는 요구 — MCP Tasks로 장시간 작업 설계하기

AI

한 줄 요약 — "코드베이스 전체를 분석하는 데 10분 걸리는데 그동안 세션이 멈춰 있지 않게 해주세요"라는 요구는 MCP의 동기 도구 호출 모델로는 풀리지 않습니다. 2025-11-25 리비전에서 실험적 확장으로 들어온 '지금 부르고 나중에 받기(call-now, fetch-later)' 패턴, MCP Tasks의 구조와 아직 확정되지 않은 표준에 지금 올라타야 하는지 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"리포트 생성 에이전트를 MCP 도구로 연결했는데, 분석 대상 저장소가 크면 도구 호출 하나가 몇 분씩 걸려요. 그동안 클라이언트가 멈춘 것처럼 보이고, 연결이 끊기면 처음부터 다시 해야 해요." MCP 서버로 실제 업무 도구를 열어본 팀이라면 금방 부딪히는 문제입니다. MCP의 도구 호출(tools/call)은 원래 "요청 하나에 응답 하나"를 가정한 동기 모델입니다. 응답이 수 초 안에 오는 검색·조회 도구에는 문제가 없지만, 대규모 코드 분석·영상 인코딩·복잡한 멀티스텝 추론처럼 몇 분에서 몇 시간이 걸리는 작업을 그 틀에 욱여넣으면 HTTP 연결 유지, 클라이언트 타임아웃, 네트워크 단절 시 재시작이라는 세 가지 문제가 동시에 터집니다.

이 문제를 정면으로 다루기 위해 MCP 스펙은 2025-11-25 리비전에서 Tasks를 실험적 프리미티브로 추가했습니다(SEP-1686). 핵심은 "지금 부르고 나중에 받기(call-now, fetch-later)" 패턴입니다. 다만 이 기능은 아직 코어 스펙이 아니라 별도 확장 저장소로 옮겨간 상태라, 지금 당장 표준으로 못 박고 설계할지, 당분간 직접 만든 패턴으로 버틸지 판단이 필요한 시점입니다.

 

요구사항을 기술 문제로 번역하기

"오래 걸리는 작업도 끊기지 않게 해주세요"는 사실 두 가지 서로 다른 요구가 섞여 있습니다. 하나는 "작업이 끝날 때까지 클라이언트가 블로킹되지 않게 해주세요"이고, 다른 하나는 "클라이언트가 재시작되거나 연결이 끊겨도 진행 중이던 작업 결과를 잃지 않게 해주세요"입니다. 전자는 비동기 호출 패턴 아무거나로도 어느 정도 해결되지만, 후자는 작업의 생존 주기가 클라이언트의 연결 생존 주기와 분리되어야 한다는 조건을 요구합니다. 그래서 실제 작업은 "콜백 하나 추가해주세요"가 아니라, 도구 호출이 결과 대신 내구성 있는 핸들(task id)을 즉시 반환하고, 그 핸들을 통해 상태를 조회하거나 결과를 나중에 가져올 수 있는 상태 저장 계층을 서버 쪽에 두는 문제로 번역됩니다.

 

전체 시스템에서의 위치

 

이 구조에서 Task 핸들은 LLM 추론 루프와 실제 작업을 수행하는 백엔드 워커 사이의 상태 저장소 역할을 합니다. 앞단에는 사용자 요청을 받아 도구 호출을 발행하는 에이전트 런타임이 있고, 뒷단에는 실제로 코드를 분석하거나 영상을 인코딩하는 워커가 있습니다. 기존 동기 모델에서는 이 둘이 하나의 연결로 직접 묶여 있어서, 연결이 끊기면 작업의 존재 자체가 사라졌습니다. Task 핸들을 중간에 두면 작업은 서버가 보장하는 TTL(결과를 보존하겠다고 약속하는 기간) 동안 독립적으로 살아 있고, 클라이언트는 같은 task id로 언제든 다시 찾아와 상태를 물을 수 있습니다. 이 레이어가 없으면 모든 장시간 작업은 클라이언트의 네트워크 안정성에 그대로 종속됩니다.

 

선택의 트레이드오프
접근 구현 비용 재연결 복원력 적합한 상황
동기 도구 호출 그대로 사용 거의 없음 없음(끊기면 유실) 응답이 수 초 내로 끝나는 도구
자체 잡 큐 + 웹훅/폴링 패턴 높음 설계하기 나름 지금 당장 안정적으로 돌려야 하는 프로덕션
MCP Tasks 확장 채택 중간 핸들 기반으로 내장 여러 MCP 서버의 패턴을 통일하고 싶은 경우

 

동기 호출을 그대로 쓰면 구현은 가장 쉽지만 작업이 조금만 길어져도 타임아웃과 재시작 비용을 사용자가 고스란히 떠안습니다. 자체 잡 큐는 지금 당장 프로덕션 요구를 만족시킬 수 있지만, MCP 서버를 여러 개 운영할수록 서버마다 폴링 엔드포인트 이름과 상태 값이 제각각이라 클라이언트 쪽 통합 비용이 누적됩니다. MCP Tasks는 이 반복을 프로토콜 레벨에서 표준화하려는 시도지만, 아직 코어 스펙이 아니라 별도 확장 저장소로 옮겨간 실험적 기능이라 클라이언트별 지원 수준이 들쭉날쭉하고, 푸시 알림보다 폴링이 여전히 주된 패턴입니다. 지금 바로 안정성이 필요하다면 자체 패턴으로 가되, 핸들 기반 설계로 구조를 맞춰두면 나중에 Tasks가 안정화됐을 때 전환 비용을 줄일 수 있습니다.

 

실제 프로젝트 진행 순서

1단계: 먼저 실제 소요 시간을 측정합니다. 도구 호출이 몇 초 안에 끝나는지, 몇 분 넘게 걸리는지부터 로그로 확인합니다. 대부분의 도구는 생각보다 짧고, 문제는 소수의 무거운 도구에 집중됩니다.

2단계: 클라이언트(에이전트 런타임)가 Tasks 확장을 지원하는지 확인합니다. 지원하지 않는 클라이언트에 작업을 반환하면 핸들을 받아줄 쪽이 없어 무의미합니다.

3단계: 지원하지 않는다면 자체 핸들 패턴부터 만듭니다. 도구 호출이 즉시 task_id를 반환하고, 별도 조회 도구로 폴링하게 하는 최소 구조를 먼저 구현합니다. 이 구조가 Tasks 확장의 모양과 비슷해야 나중에 갈아타기 쉽습니다.

4단계: TTL과 재시작 시나리오를 명시적으로 테스트합니다. 워커가 죽었을 때 상태가 어떻게 남는지, TTL이 지난 뒤 조회하면 무엇을 반환하는지를 먼저 정의해야 합니다.

5단계: 진행률 알림이 꼭 필요한 도구만 선별합니다. 모든 도구에 진행률 스트리밍을 넣으려 하지 말고, 실제로 체감 대기 시간이 긴 소수의 도구부터 적용합니다.

{
  "task": {
    "taskId": "task_8f21",
    "status": "working",
    "ttl": 3600,
    "pollInterval": 2000
  }
}

{
  "taskId": "task_8f21",
  "status": "completed",
  "result": {
    "content": [{ "type": "text", "text": "분석 리포트 요약..." }]
  }
}

 

주의 — 지금 당장 Tasks를 "표준"이라 부르며 설계를 확정하지 마세요. 실험적 확장 단계라 필드명과 상태 값이 바뀔 수 있습니다. 폴링 간격은 서버가 제안하게 해, 클라이언트마다 제각각 간격으로 요청해 불필요한 트래픽이 쌓이는 상황을 줄이세요. 또한 모든 도구를 비동기로 바꾸려 하지 마세요. 응답이 빠른 도구까지 핸들 구조로 바꾸면 왕복 횟수만 늘어납니다. 실제로 몇 분 이상 걸리는 소수의 도구에만 적용하는 편이 안전합니다.

 

정리

"오래 걸리는 작업도 끊기지 않게 해주세요"는 작업의 생존 주기를 클라이언트 연결 주기에서 분리하는, 내구성 있는 핸들 설계 문제로 번역됩니다. MCP Tasks는 이 패턴을 "지금 부르고 나중에 받기"로 표준화하려는 시도지만 아직 코어가 아닌 실험적 확장이라 클라이언트 지원이 고르지 않습니다. 지금은 자체 핸들 패턴으로 먼저 안정성을 확보하되, Tasks의 모양에 맞춰 설계해두면 표준이 안정화될 때 전환 비용을 줄일 수 있습니다.
