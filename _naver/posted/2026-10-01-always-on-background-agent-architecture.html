시키고 잊어도 되는 에이전트 — 상시 가동(Always-on) 백그라운드 에이전트 아키텍처

AI

한 줄 요약 — 메신저로 요청만 하면 밤새 알아서 조사·개발까지 끝내는 상시 가동 에이전트는 작업 큐·가상 컴퓨터 샌드박스·승인 게이트·선호 메모리로 이뤄진 작은 분산 시스템입니다. 무엇부터 만들어야 하는지 순서대로 정리합니다.

 

왜 지금 이 구조가 중요해졌는가

"챗봇 켜놓고 대화하는 건 이제 지겹다. 메신저로 한 줄만 요청하면 알아서 조사하고, 코드도 짜고, 끝나면 결과만 보여주는 비서가 필요하다." 이런 요구사항은 얼마 전까지 "일단 스트리밍 챗 UI부터 만들고 나중에 생각하자"로 넘어갈 수 있었습니다. 그런데 OpenAI가 공개한 상시 가동 에이전트 '닷츠(Dots)'는 정확히 이 모델을 상품화했습니다. 가상 컴퓨터 위에서 조사·문서 작업·개발을 스스로 수행하고, 사용자가 미리 정한 규칙과 명시적 승인으로만 민감한 작업을 통제하며, 대화가 쌓일수록 과거 선호를 학습해 다음 작업에 반영합니다.

이건 "더 똑똑한 챗봇"이 아니라 완전히 다른 실행 모델입니다. 지금까지 대부분의 에이전트 서비스는 요청과 응답이 수 초 안에 끝나는 동기식 구조를 전제로 설계됐습니다. 상시 가동 에이전트는 이 전제를 깹니다. 요청과 응답 사이에 몇 시간이 걸릴 수 있고, 그 사이 에이전트는 사람 없이 혼자 수십 번의 판단을 이어갑니다. 이 차이가 서버 아키텍처, 실패 복구, 권한 설계를 전부 다시 쓰게 만듭니다.

 

요구사항을 기술 문제로 번역하기

"요청만 하면 알아서 처리해주는 비서"라는 한 줄은 풀어보면 네 가지 문제로 나뉩니다. 요청을 즉시 처리 못 하니 작업을 큐에 넣고 비동기로 실행해야 하고, 그 실행은 격리된 가상 컴퓨터 안에서 벌어져야 사용자 환경에 영향을 주지 않습니다. 작업이 몇 시간씩 걸리니 중간에 끊겨도 체크포인트에서 이어서 재개할 수 있어야 하고, 되돌리기 어려운 행동 앞에서는 그 자리에서 멈추고 승인을 기다리는 게이트가 있어야 합니다.

이 네 가지를 묶으면 상시 가동 에이전트는 'LLM 호출 하나'가 아니라 하나의 작은 분산 시스템이 됩니다.

 

전체 시스템에서의 위치

요청이 들어와 결과가 돌아가기까지, 데이터는 다음 경로를 지납니다.

 

요청은 바로 LLM을 호출하지 않고 작업 큐에 적재됩니다. 워커가 큐에서 작업을 꺼내 가상 컴퓨터를 띄우고, 그 안에서 에이전트가 웹 검색·코드 실행·파일 조작 같은 도구를 반복 호출합니다. 결제·외부 전송·삭제처럼 사전에 정의된 민감 행동이 나오면 실행을 멈추고 승인 게이트로 넘어가 사람의 확인을 기다립니다. 완료되면 같은 채널로 알림을 보내고, 이 과정에서 드러난 사용자의 선택은 선호 메모리에 쌓여 다음 작업에 자동 반영됩니다.

 

선택의 트레이드오프 — 동기식 챗 에이전트와 무엇이 다른가
기준 동기식 챗 에이전트 상시 가동 백그라운드 에이전트
응답 모델 요청-응답, 수 초~수십 초 큐잉-실행-알림, 수 분~수 시간
실패 복구 재요청하면 그만 체크포인트에서 재개 필요
신뢰 설계 매 응답을 사람이 바로 확인 사람이 안 보는 사이 행동에 선승인 규칙 필요
적합한 작업 즉답이 필요한 질의, 짧은 코드 수정 리서치 보고서, 다단계 리팩터링, 반복 모니터링

 

핵심 함정은 "일단 에이전트 루프를 비동기로만 바꾸면 된다"는 착각입니다. 승인 게이트 없이 비동기 큐만 얹으면 밤새 결제 API를 반복 호출하는 사고로 이어질 수 있습니다. 반대로 사용자가 화면 앞에서 즉답을 기다리는 서비스라면 샌드박스·큐·승인 게이트는 지연과 복잡도만 늘리는 과잉 설계입니다.

 

실제 프로젝트 진행 순서

1단계: 위임 가능한 작업과 승인이 필요한 행동부터 분류합니다. 되돌릴 수 있는 작업과 되돌릴 수 없는 행동을 먼저 나눠야 승인 게이트 위치가 정해집니다.

2단계: 격리 실행 환경을 먼저 검증합니다. 컨테이너로 할지 마이크로 VM으로 할지, 네트워크 아웃바운드를 어디까지 열지부터 결정합니다.

3단계: 체크포인트 가능한 작업 상태 모델을 설계합니다. 워커가 죽어도 같은 지점에서 이어 실행할 수 있어야 합니다.

4단계: 승인 게이트와 알림 채널을 하나로 연결해, 사용자가 한 창에서 승인과 확인을 모두 처리하게 만듭니다.

5단계: 선호 메모리는 가장 마지막에 넣습니다. 실행이 안정화되기 전에 메모리부터 쌓으면 잘못된 선호 학습이 누적됩니다.

주의 — 모든 서비스가 상시 가동 모델을 필요로 하지 않습니다. 즉답이 핵심인 서비스에 이 구조를 통째로 가져오면 지연과 인프라 비용만 늘어납니다.

 

정리

상시 가동 에이전트는 'LLM 응답을 비동기로 바꾼 것'이 아니라 작업 큐·샌드박스·체크포인트·승인 게이트로 이뤄진 작은 분산 시스템입니다. 요구사항이 즉답인지 위임인지부터 구분해야 하고, 승인 게이트와 체크포인트를 먼저 안정화한 뒤에야 선호 메모리 같은 개인화 기능을 얹어야 신뢰할 수 있는 기반 위에 쌓입니다.
