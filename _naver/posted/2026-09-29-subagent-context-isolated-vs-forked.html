서브에이전트에게 무엇을 물려줄 것인가 — Isolated vs Forked 컨텍스트 설계

AI

한 줄 요약 — 서브에이전트에게 부모의 대화 이력을 물려줄지 말지는 정확도만이 아니라 프롬프트 캐시 재사용 여부를 결정하는 비용 문제입니다. LangChain deepagents의 isolated·fork 두 모드를 기준으로 언제 무엇을 쓸지 정리합니다.

 

"리서치는 서브에이전트한테 시키고, 결과만 받아오세요"

에이전트 오케스트레이터를 짜다 보면 자연스럽게 이런 요구가 생깁니다. 메인 에이전트가 사용자와 긴 대화를 이어가는 도중, 무거운 조사나 코드 수정 같은 하위 작업을 별도 에이전트에 위임하고 싶어집니다. 조사 과정에서 나오는 수십 번의 시행착오를 메인 에이전트의 컨텍스트 창에 그대로 쌓으면, 정작 사용자와의 대화 맥락이 뒤로 밀려나거나 비용이 감당 안 되게 불어나기 때문입니다.

그런데 "위임한다"는 말은 구체적으로 무엇을 의미할까요? 서브에이전트가 부모의 대화 이력을 전부 알아야 할까요, 아니면 작업 지시 한 줄만 알면 될까요? 이 질문의 답이 서브에이전트의 정확도, 토큰 비용, 응답 지연을 동시에 결정합니다. 2026년 9월 LangChain이 deepagents에 정식으로 넣은 컨텍스트 모드(isolated / fork)는 이 질문을 프레임워크 차원의 명시적 선택지로 만들었습니다.

 

두 가지 모드, 완전히 다른 실패 양상

Isolated(기본값)는 서브에이전트가 부모로부터 작업 설명 하나만 받고, 부모 대화가 어떻게 흘러왔는지는 전혀 모르는 상태로 시작합니다. 깨끗한 상태에서 시작하니 부모의 잡음에 오염되지 않지만, 프롬프트 캐시가 처음부터 다시 쌓이므로(cold start) 매번 시스템 프롬프트 전체를 새로 계산해야 합니다.

Fork는 서브에이전트가 부모의 전체 대화 이력과 정확히 동일한 시스템 프롬프트 접두사를 그대로 물려받습니다. 부모가 이미 진단을 끝낸 작업을 이어받아 실행만 하는 워커에 적합합니다. 접두사가 완전히 같기 때문에 부모의 프롬프트 캐시를 그대로 재사용할 수 있어, fork는 정확도 문제일 뿐 아니라 순수하게 비용 문제이기도 합니다.

 

기준 Isolated Fork
물려받는 것 task 설명 한 줄 전체 대화 이력 + 시스템 프롬프트
프롬프트 캐시 새로 시작(cold) 부모 것 재사용(warm)
적합한 작업 독립적 조사, 병렬 리서치 부모가 진단한 작업을 이어받아 실행

 

진행 순서 — 기본값에서 시작해 필요한 곳만 fork로

1단계: 모든 서브에이전트를 isolated로 두고 시작합니다. 대부분의 "이 조사 좀 해줘" 류 위임은 격리로 충분합니다.

2단계: 프롬프트 캐시 히트율과 토큰 비용을 관찰합니다. 같은 시스템 프롬프트를 매번 콜드로 다시 계산하는 게 비용 로그에서 보이기 시작하면 그 서브에이전트가 진짜 부모 맥락을 이어받아야 하는지 재판단합니다.

3단계: "부모가 이미 결정을 내렸고, 서브에이전트는 그 결정을 그대로 실행만 한다"는 조건을 만족하는 작업만 fork로 바꿉니다.

fix_worker = SubAgent(
    name="apply-fix",
    description="부모가 진단한 버그를 실제로 수정한다",
    mode="fork",  # 부모의 진단 맥락을 그대로 물려받음
)

researcher = SubAgent(
    name="background-research",
    description="독립적인 배경 조사를 수행한다",
    mode="isolated",  # 기본값
)

4단계: 여러 fork를 병렬로 띄울 때는 각 fork가 부모의 로컬 상태 일부를 결과에 담아 동시에 덮어쓰지 않는지 반드시 검증합니다. LangChain도 이 문제를 겪은 뒤 준비·응답 관련 필드를 결과에서 제외하도록 고쳤습니다.

 

실무 포인트

fork를 남용하면 격리의 장점이 사라집니다. 부모 대화에 다른 요청이나 실패한 시도가 섞여 있다면 fork된 서브에이전트도 그 잡음을 그대로 물려받아 엉뚱한 판단을 내릴 수 있습니다.

캐시 재사용은 접두사가 바이트 단위로 같을 때만 성립합니다. 부모와 자식이 같은 프롬프트 생성 경로를 공유하도록 구성해야 fork의 이점이 유지됩니다.

주의 — isolated 모드는 컨텍스트 엔지니어링 관점의 격리일 뿐, 권한이나 도구 접근 범위를 제한하는 보안 경계는 아닙니다. 서브에이전트가 쓸 도구 범위는 별도로 설계해야 합니다.

 

정리

서브에이전트 위임은 "누가 무엇을 기억하는가"를 정하는 컨텍스트 설계 문제이며, 기본값은 격리로 두는 것이 안전합니다. fork는 부모의 결정을 그대로 이어받아 실행하는 작업에만, 프롬프트 캐시 재사용을 노리고 씁니다. 병렬 fork를 쓸 때는 부모 상태 덮어쓰기 위험을 꼭 점검하세요.
