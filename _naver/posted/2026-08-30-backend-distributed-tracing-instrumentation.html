스팬 하나가 끊기면 추적도 끊긴다 — 백엔드 분산 트레이싱 계측 실무

백엔드

한 줄 요약 — 분산 트레이싱 계측의 실제 작업량은 라이브러리 도입보다, 스레드 풀·리액티브 체인·메시지 큐 같은 비동기 경계마다 컨텍스트 전파를 빠짐없이 이어주는 것에 있습니다. Micrometer Tracing과 OpenTelemetry 기준으로 실무를 정리했습니다.

 

라이브러리를 붙였는데 트레이스가 끊깁니다

분산 트레이싱을 그냥 라이브러리 붙이면 되는 것으로 여기다가 실제로 붙여보면 예상 밖의 지점에서 트레이스가 끊깁니다. @Async 메서드로 넘어가는 순간, CompletableFuture의 콜백 스레드로 넘어가는 순간, 메시지 큐에 이벤트를 발행하고 다른 프로세스가 소비하는 순간 — 이런 경계마다 지금 이 작업이 어느 트레이스에 속하는지를 나타내는 컨텍스트가 스레드 로컬을 벗어나며 유실되기 쉽습니다.

계측 라이브러리를 넣는 것 자체는 몇 줄이지만, 이 컨텍스트 전파(context propagation)를 코드베이스 전체의 비동기 경계마다 빠짐없이 이어주는 것이 실제 작업의 8할입니다.

 

핵심 개념 1 — 트레이스, 스팬, 컨텍스트 전파의 관계

하나의 요청이 여러 서비스를 거치는 흐름 전체가 트레이스이고, 그 안에서 개별 작업 단위가 스팬입니다. 각 스팬은 부모 스팬 ID를 가져 트리 구조를 이루고, 이 부모-자식 관계를 다음 작업에 전달하는 것이 컨텍스트 전파입니다. HTTP 경계를 넘을 때는 W3C Trace Context 표준의 traceparent 헤더로 전파되고, 같은 프로세스 안에서는 스레드 로컬에 담겨 전파됩니다.

문제는 스레드 로컬이 스레드 경계를 자동으로 넘지 못한다는 점입니다. ExecutorService에 작업을 제출하면 별도 처리 없이는 원래 스레드의 트레이스 컨텍스트가 새 스레드로 전달되지 않습니다.

 

 

핵심 개념 2 — Spring Boot에서 실제로 끊기는 지점들
경계 유형 기본 동작 필요 조치
@Async 메서드 스레드 풀 전환 시 유실 ContextExecutorService로 래핑
리액티브 체인(WebFlux) 스레드가 계속 바뀜 Reactor Context에 전파 설정
Kafka/RabbitMQ 발행-구독 프로세스 경계라 전파 불가능 메시지 헤더에 traceparent 수동 주입/추출

가장 자주 놓치는 것이 Kafka 같은 메시지 큐 경계입니다. 발행자와 소비자 프로세스는 완전히 분리돼 있으므로, 발행 시점에 현재 트레이스 컨텍스트를 메시지 헤더에 직접 써넣고 소비 시점에 그 헤더를 읽어 새 스팬의 부모로 지정해야 합니다.

 

핵심 개념 3 — 로그와 트레이스를 잇는 MDC 연동

트레이스 ID만으로는 부족합니다 — 실제 장애 조사는 트레이스 뷰어와 로그를 오가며 진행되는데, 로그 라인에 traceId가 찍혀 있어야 이 둘을 연결할 수 있습니다. Micrometer Tracing은 SLF4J MDC에 자동으로 traceId, spanId를 심어주는 브리지를 제공하므로, 로그 포맷에 관련 패턴을 넣는 것만으로 상관관계가 생깁니다. 단, 이 역시 비동기 경계를 넘으면 함께 끊길 수 있습니다.

 

예제 — Spring Boot 계측 설정
// AsyncConfig.java — @Async 실행기에 컨텍스트 전파 래핑
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Override
    public Executor getAsyncExecutor() {
        ThreadPoolTaskExecutor delegate = new ThreadPoolTaskExecutor();
        delegate.setCorePoolSize(8);
        delegate.initialize();
        return ContextExecutorService.wrap(delegate.getThreadPoolExecutor(),
                () -> ContextSnapshot.captureAll());
    }
}

// 발행 시 traceparent를 메시지 헤더에 주입
public void publish(OrderEvent event) {
    ProducerRecord<String, OrderEvent> record =
            new ProducerRecord<>("order-events", event.orderId(), event);

    propagator.inject(tracer.currentTraceContext().context(),
            record.headers(),
            (carrier, key, value) ->
                    carrier.add(key, value.getBytes(StandardCharsets.UTF_8)));

    kafkaTemplate.send(record);
}

 

실무 포인트

계측 도입 초기엔 끊긴 트레이스부터 찾으세요. 새로 계측을 붙이면 처음엔 트레이스 그래프가 여러 조각으로 나뉘어 보이는 게 정상입니다. 각 조각의 시작 스팬이 어느 경계 직후에 생기는지 찾아 하나씩 전파를 붙여나가야 합니다.

커스텀 스팬은 비즈니스 의미 단위로 만드세요. 프레임워크가 자동으로 만들어주는 HTTP·DB 스팬만으로는 재고 확인 로직이 왜 느린지 구분하기 어렵습니다.

주의 — 컨텍스트 전파 누락은 조용히 실패합니다. 전파가 끊겨도 애플리케이션은 정상 동작하고 에러도 나지 않습니다 — 트레이스가 새 루트로 시작될 뿐입니다. 새로운 비동기 경계가 추가될 때마다 컨텍스트 전파 처리 여부를 코드 리뷰 체크리스트에 명시해야 재발을 막을 수 있습니다.
