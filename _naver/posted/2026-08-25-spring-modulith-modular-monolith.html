빌드 모듈을 나눠도 경계는 안 지켜진다 — Spring Modulith로 모듈러 모놀리스 구축하기

2026. 8. 25. · 백엔드

한 줄 요약 — 빌드 모듈 분리로는 강제되지 않는 도메인 경계를, Spring Modulith가 테스트 시점에 검증하고 이벤트 기반 통신으로 결합도를 낮추는 방법을 정리했습니다.

 

빌드 설정으로는 경계를 강제할 수 없습니다

Gradle이나 Maven 멀티모듈로 프로젝트를 domain, infra, api 모듈로 나눠본 분이라면 한 번쯤 겪는 배신감이 있습니다. 빌드 설정에서 모듈 간 의존 방향을 아무리 깔끔하게 그려도, 결국 같은 JVM 프로세스 안에서 실행되는 이상 클래스패스에 올라간 어떤 클래스든 import 한 줄이면 자유롭게 참조할 수 있습니다. 빌드 모듈 분리는 경계에 대한 합의는 만들어주지만, 실제로 그 경계를 넘는 참조를 강제로 막지는 못합니다.

Spring Modulith는 이 틈을 메우는 프레임워크입니다. 애플리케이션 패키지 구조를 기준으로 "모듈"을 정의하고, 그 경계를 테스트 시점에 검증하며, 모듈 간 통신을 이벤트 기반으로 유도합니다.

 

핵심 개념 1 — 패키지 구조가 곧 모듈 경계입니다

Spring Modulith는 별도 설정 파일 없이, 최상위 패키지 바로 아래 패키지 구조를 모듈 경계로 인식합니다. 각 모듈의 최상위 패키지 클래스만 공개 API로 취급되고, 하위 패키지(internal 등)의 클래스는 모듈 밖에서 참조하면 위반으로 감지됩니다. 격리 단위가 레이어가 아니라 비즈니스 도메인 단위라는 점이 특징입니다.

 

핵심 개념 2 — ApplicationModules, 경계 위반을 테스트로 검증

Spring Modulith의 핵심 가치는 이 경계가 문서상의 약속이 아니라 테스트 실패로 강제된다는 점입니다. ApplicationModules.of(Application.class).verify() 한 줄이면 모듈 내부 패키지를 다른 모듈이 직접 참조하는 위반이나 순환 의존을 테스트 실행 시점에 검사해 실패시킵니다.

구분 Gradle 멀티모듈 Spring Modulith
격리 단위 빌드 아티팩트(jar) 최상위 도메인 패키지
위반 감지 컴파일 타임(모듈 간만) 테스트 실행 시점
도입 난이도 빌드 구조 재편 필요 기존 구조에 점진 적용

 

핵심 개념 3 — 이벤트 기반 모듈 간 통신

Spring Modulith는 한 모듈이 다른 모듈의 서비스를 직접 호출하는 대신, ApplicationEventPublisher로 도메인 이벤트를 발행하고 다른 모듈이 @ApplicationModuleListener로 이를 구독하는 방식을 제시합니다. 이벤트 발행과 리스너 실행이 트랜잭션 커밋 이후로 처리되어, 향후 마이크로서비스로 분리할 때 이벤트를 메시지 브로커로 옮기는 이행 경로도 자연스럽게 마련됩니다.

 

예제 — 모듈 경계 검증과 이벤트 기반 통신
class ModularityTests {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);

    @Test
    void verifiesModularStructure() {
        modules.verify();
    }
}

// order 모듈: 인벤토리 모듈을 직접 호출하지 않고 이벤트만 발행
@Service
class OrderService {
    void placeOrder(Order order) {
        orderRepository.save(order);
        events.publishEvent(new OrderPlaced(order.getId(), order.getItems()));
    }
}

// inventory 모듈: 이벤트를 구독
@Component
class InventoryEventListener {
    @ApplicationModuleListener
    void on(OrderPlaced event) {
        inventoryService.reserve(event.items());
    }
}

 

실무 도입 시 이것만은 챙기세요
1. 기존 레거시 모놀리스에 점진적으로 도입하세요 — verify() 테스트를 우선 추가해 현재 위반 목록을 파악한 뒤 우선순위 높은 도메인부터 정리하세요.
2. 이벤트 리스너의 실패 처리를 명시적으로 설계하세요 — 재시도나 보상 처리를 별도로 준비해야 합니다.
3. 마이크로서비스 전환의 리허설로 활용하세요 — 자동 생성되는 모듈 의존 다이어그램이 분리 우선순위 판단에 도움이 됩니다.

 

마무리 — 3줄 요약

① Gradle 멀티모듈은 빌드 아티팩트 수준의 분리이고, Spring Modulith는 도메인 패키지 수준의 경계를 테스트 시점에 강제합니다.
② ApplicationModules.verify()로 모듈 경계 위반과 순환 의존을 테스트 실패로 검출할 수 있습니다.
③ 이벤트 기반 통신은 결합도를 낮추고, 향후 마이크로서비스 분리 시 이행 경로도 자연스럽게 마련해줍니다.
