별도 오케스트레이터 없이, Postgres로 워크플로우를 관리하는 법

2026. 8. 15. · 시스템 설계

한 줄 요약 — Airflow 같은 별도 오케스트레이션 미들웨어 없이, PostgreSQL 트랜잭션만으로 워크플로우의 상태·재시도·복구를 관리하는 접근을 정리했습니다. 2026년 QCon SF에서 DBOS 등이 소개하며 다시 주목받고 있는 흐름입니다.

 

왜 이 이야기가 지금 나오는 걸까요

Airflow, Temporal, Step Functions 같은 워크플로우 오케스트레이터는 여러 서비스를 넘나드는 긴 작업을 안정적으로 관리하려고 만들어졌습니다. 그런데 이런 도구들도 결국 하나의 분산 시스템이어서, 오케스트레이터의 상태 저장소와 스케줄러 자체가 또 다른 장애 지점이 되곤 합니다.

2026년 QCon San Francisco를 비롯한 여러 발표에서 DBOS 같은 팀이 제시한 아이디어는 이미 신뢰하고 있는 PostgreSQL 트랜잭션 위에 워크플로우 상태를 얹자는 것입니다. 새로운 미들웨어를 배포하는 대신, 애플리케이션이 이미 쓰고 있는 DB의 신뢰성을 그대로 재사용하자는 발상입니다.

다만 이 방식이 모든 워크플로우에 맞는 만능 해법은 아닙니다. 어떤 상황에서 유효하고, 어떤 상황에서는 여전히 전용 오케스트레이터가 나은지 구분하는 것이 실무에서 훨씬 중요합니다.

 

기존 오케스트레이터와 무엇이 다른가

전통적인 오케스트레이터는 실행 상태와 재시도 로직을 별도 컨트롤 플레인이 관리합니다. 반면 Postgres 기반 접근은 각 워크플로우 단계를 하나의 트랜잭션으로 표현하고, 실행 결과와 다음 단계 전이를 같은 테이블에 원자적으로 기록합니다. 프로세스가 죽어도 마지막 커밋 상태를 그대로 읽어와 재개할 수 있다는 것이 핵심입니다.

구분 별도 오케스트레이터 Postgres 기반 접근
상태 저장 위치 오케스트레이터 전용 메타 DB 애플리케이션이 쓰던 Postgres
추가 장애 지점 오케스트레이터 클러스터 기존 DB 신뢰성에 편승
가시성(모니터링) 전용 대시보드 제공 SQL 조회, 직접 구축 필요
적합한 규모 수백~수천 개 태스크 DAG 서비스 내부 국소적 장기 작업

 

기존 오케스트레이터에 대한 대표적인 불만은 두 가지입니다. 첫째는 실패 처리의 복잡성입니다. 재시도 정책과 보상 트랜잭션을 오케스트레이터 전용 DSL로 표현하다 보니 실제 비즈니스 로직과 괴리가 생기기 쉽습니다. 둘째는 가시성 부족입니다. 지금 워크플로우가 어느 단계에서 멈췄는지 알기 위해 오케스트레이터 UI와 애플리케이션 로그를 번갈아 확인해야 하는 경우가 많습니다.

 

예제로 보는 트랜잭션 기반 워크플로우

개념을 단순화한 예시입니다. 실제 DBOS류 라이브러리는 더 정교한 멱등성 키와 버전 관리를 제공하지만, 핵심 원리는 아래와 크게 다르지 않습니다.

-- 워크플로우 단계 상태 테이블
CREATE TABLE workflow_step (
    workflow_id   UUID NOT NULL,
    step_name     TEXT NOT NULL,
    status        TEXT NOT NULL DEFAULT 'pending',
    attempt       INT NOT NULL DEFAULT 0,
    result        JSONB,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (workflow_id, step_name)
);
def run_step(conn, workflow_id, step_name, fn):
    with conn.transaction():
        row = conn.execute(
            "SELECT status, attempt FROM workflow_step "
            "WHERE workflow_id=%s AND step_name=%s FOR UPDATE",
            (workflow_id, step_name),
        ).fetchone()

        if row and row["status"] == "done":
            return row  # 이미 완료된 단계는 재실행하지 않음

        conn.execute(
            "UPDATE workflow_step SET status='running', attempt=attempt+1 "
            "WHERE workflow_id=%s AND step_name=%s",
            (workflow_id, step_name),
        )

        result = fn()  # 실제 비즈니스 로직 실행

        conn.execute(
            "UPDATE workflow_step SET status='done', result=%s "
            "WHERE workflow_id=%s AND step_name=%s",
            (result, workflow_id, step_name),
        )

핵심은 단계 실행과 상태 갱신이 같은 트랜잭션 경계 안에 있다는 점입니다. 프로세스가 중간에 죽어도 status는 running으로 남아 있고, 재기동할 때 이 값을 보고 재시도 여부를 판단할 수 있습니다.

 

도입 전 이것만은 챙기세요
1. 규모를 먼저 확인하세요 — 국소적이고 단계 수가 적은 워크플로우에는 적합하지만, 수백 개 태스크의 복잡한 DAG에는 부적합할 수 있습니다
2. 장기 대기·승인 단계는 별도 검토 — 사람이 며칠씩 승인을 기다리는 단계가 있다면 전용 오케스트레이터가 여전히 유리합니다
3. 트랜잭션 락 범위에 유의 — 트랜잭션이 오래 걸리면 DB 전체 처리량을 떨어뜨릴 수 있어 격리 수준 설계가 중요합니다
4. 모니터링은 직접 구축해야 함 — 오케스트레이터의 대시보드 대신 SQL 기반 조회 도구를 별도로 준비해야 합니다
5. 확정 수치는 문서로 재확인 — 발표마다 언급되는 벤치마크나 로드맵이 다를 수 있어 도입 전 공식 문서를 직접 확인하는 것이 안전합니다

 

마무리 — 3줄 요약

① 워크플로우 상태·재시도·복구를 별도 오케스트레이터가 아니라 PostgreSQL 트랜잭션 위에서 관리하는 접근이 주목받고 있습니다.
② 기존 DB의 신뢰성을 재사용해 운영 부담과 장애 지점을 줄일 수 있지만, 가시성은 직접 구축해야 하는 트레이드오프가 있습니다.
③ 규모가 크지 않은 국소적 워크플로우에는 적합하지만, 대규모 DAG나 장기 승인 단계가 있다면 여전히 전용 오케스트레이터가 낫습니다.
