시계열 데이터베이스 선택 가이드 — TimescaleDB vs InfluxDB, 언제 무엇을 써야 할까

2026. 8. 18. · DB·데이터모델링

한 줄 요약 — IoT 센서, 서버 메트릭처럼 시간이 축이 되는 데이터를 다룰 때 PostgreSQL 확장인 TimescaleDB와 전용 엔진인 InfluxDB 중 무엇을 골라야 하는지, 데이터 모델과 쿼리·운영 관점에서 비교해봤습니다.

 

왜 지금 시계열 데이터베이스인가

서버 메트릭, IoT 센서값, 주가 틱처럼 "시간 + 값" 형태로 끊임없이 쌓이는 데이터가 계속 늘고 있습니다. 이런 데이터는 쓰기가 압도적으로 많고, 조회는 대부분 최근 구간이나 특정 시간 범위에 집중되며, 오래된 데이터는 요약하거나 삭제하는 보존 정책이 꼭 필요하다는 공통점이 있습니다.

일반 RDB에 그대로 쌓다 보면 테이블과 인덱스가 비대해지고, 오래된 데이터를 지우는 작업이 락 경합을 일으키는 문제가 반복됩니다. 이 문제를 겨냥한 시계열 데이터베이스 중 실무에서 가장 자주 비교되는 두 축이 TimescaleDB(PostgreSQL 확장)와 InfluxDB(전용 시계열 엔진)입니다. 접근 방식이 근본적으로 다르기 때문에 "무엇이 더 빠른가"보다 "우리 팀의 기존 스택과 쿼리 패턴에 어느 쪽이 맞는가"가 더 중요한 질문입니다.

 

핵심 개념: 저장 구조가 근본적으로 다릅니다

TimescaleDB는 PostgreSQL 테이블을 시간 구간별 청크(chunk)로 쪼개 하나의 논리적 테이블(하이퍼테이블)처럼 보이게 만듭니다. InfluxDB는 처음부터 시계열 전용으로 설계된 TSM(Time-Structured Merge Tree) 엔진에 쓰기를 순차 기록한 뒤 백그라운드로 압축·병합합니다.

 

핵심 개념: 데이터 모델과 쿼리 언어 비교
항목 TimescaleDB InfluxDB
데이터 모델 일반 테이블(컬럼 스키마) + 시간 컬럼 측정값 + 태그 + 필드
쿼리 언어 표준 SQL 그대로 InfluxQL 또는 Flux(버전별 상이)
JOIN PostgreSQL JOIN 그대로 사용 제한적, 별도 처리 필요한 경우 많음
카디널리티 민감도 상대적으로 낮음 태그 종류가 많아지면 성능 저하 위험

TimescaleDB는 결국 PostgreSQL이므로 기존에 쓰던 ORM, 트랜잭션, 외래 키, 다른 테이블과의 JOIN을 그대로 쓸 수 있다는 점이 가장 큰 실무 장점입니다. InfluxDB는 태그 기반 조회에 최적화돼 있어 특정 조건의 최근 데이터 조회는 빠르지만, 태그 조합이 지나치게 다양해지면(예: 사용자 ID를 태그로 사용) 카디널리티 폭발로 메모리 사용량이 급증할 수 있습니다.

 

예제: 시간대별 집계 쿼리

TimescaleDB는 하이퍼테이블을 만든 뒤 연속 집계 뷰로 시간대별 평균을 자동 갱신할 수 있습니다.

-- 센서 데이터용 하이퍼테이블 생성
CREATE TABLE sensor_data (
  time        TIMESTAMPTZ NOT NULL,
  sensor_id   INT NOT NULL,
  temperature DOUBLE PRECISION
);
SELECT create_hypertable('sensor_data', 'time');

-- 1시간 단위 평균 온도 집계(연속 집계 뷰)
CREATE MATERIALIZED VIEW hourly_avg_temp
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 hour', time) AS bucket,
       sensor_id,
       avg(temperature) AS avg_temp
FROM sensor_data
GROUP BY bucket, sensor_id;

InfluxDB에서 같은 목적(최근 24시간 평균)을 Flux로 표현하면 다음과 같습니다.

from(bucket: "sensors")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "temperature")
  |> aggregateWindow(every: 1h, fn: mean, createEmpty: false)

 

실무 도입 시 이것만은 챙기세요
1. 기존 스택이 PostgreSQL이면 TimescaleDB가 유리 — 새 쿼리 언어 없이 기존 운영 도구를 그대로 재사용
2. 태그로 쓸 값의 카디널리티를 미리 가늠 — 사용자 ID, 요청 ID처럼 무한히 늘어나는 값은 태그 대신 필드로
3. 보존 정책은 처음부터 설계에 포함 — 원본을 무한히 쌓아두는 전제로 시작하면 소급 적용이 번거로움
4. 버전별 쿼리 언어 변화 확인 필수 — InfluxDB는 버전에 따라 지원 범위가 달라 공식 문서로 반드시 확인
5. 벤치마크보다 스택 적합도로 판단 — 성능 수치는 워크로드마다 달라지므로 팀 상황에 맞춰 검증

 

마무리 — 3줄 요약

① 시계열 데이터는 쓰기 위주·시간 범위 조회·보존 정책이라는 공통 요구사항 때문에 일반 RDB만으로는 한계가 생깁니다.
② TimescaleDB는 PostgreSQL 확장으로 SQL·JOIN·기존 운영 도구를 그대로 쓸 수 있고, InfluxDB는 태그 기반 조회에 최적화된 전용 엔진이지만 카디널리티 관리가 필요합니다.
③ 선택 기준은 성능 벤치마크보다 팀의 기존 스택, 쿼리 패턴, 태그(라벨) 다양성에 두는 것이 현실적입니다.
