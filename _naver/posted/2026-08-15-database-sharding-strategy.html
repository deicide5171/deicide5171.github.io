DB 샤딩 전략, 키를 어떻게 나눌까

2026. 8. 15. · 시스템 설계

한 줄 요약 — 샤딩 키 선택은 되돌리기 어려운 결정이라, 쓰기 분산과 쿼리 지역성을 함께 고려해 신중히 골라야 합니다.

 

단일 DB의 한계와 샤딩의 필요성

단일 데이터베이스로 감당할 수 있는 트래픽과 데이터 규모에는 한계가 있습니다. 서버를 더 크게 키우는 수직 확장도 언젠가 물리적, 비용적 한계에 부딪히기 마련입니다. 이 지점에서 많은 팀이 샤딩을 고려하지만, 샤딩 키를 잘못 고르면 특정 샤드에만 트래픽이 몰리는 핫스팟이 생기고 나중에 되돌리기 매우 어려운 문제가 됩니다.

 

샤딩 방식 세 가지 비교

샤딩 방식은 크게 해시 기반, 레인지 기반, 디렉토리 기반으로 나눌 수 있습니다. 실무에서는 여러 방식을 조합해서 쓰는 경우가 많습니다. 예를 들어 해시로 1차 분산을 시키되, 특정 대형 테넌트만 별도 샤드로 매핑해두는 식입니다.

방식 장점 단점
해시 기반 균등 분산 범위 쿼리 비효율
레인지 기반 범위 쿼리 효율적 특정 범위 쏠림 가능
디렉토리 기반 유연한 재배치 매핑 테이블이 병목 가능

 

좋은 샤딩 키의 조건

좋은 샤딩 키는 쓰기 분산, 쿼리 지역성, 카디널리티를 동시에 만족해야 합니다. 예를 들어 멀티테넌트 서비스라면 tenant_id를 샤딩 키로 쓰면 대부분의 쿼리가 한 샤드 안에서 끝나 효율적입니다. 반면 시간순으로 증가하는 ID를 그대로 쓰면 최신 데이터에 쓰기가 몰리는 문제가 생길 수 있습니다.

import hashlib

def get_shard(key: str, shard_count: int) -> int:
    digest = hashlib.md5(key.encode()).hexdigest()
    return int(digest, 16) % shard_count

shard_id = get_shard("tenant_8823", shard_count=16)

 

리샤딩과 핫스팟, 실무에서 반복되는 문제

샤딩 키를 처음부터 완벽하게 고르기는 사실상 불가능합니다. 서비스가 성장하면 결국 샤드를 늘리거나 재배치해야 하는데, 이 과정은 이중 쓰기와 백필, 컷오버 단계를 거쳐야 하는 큰 작업입니다. 또한 인기 테넌트 쏠림처럼 핫스팟은 샤딩 이후에도 반복적으로 나타나므로 상시 모니터링이 필요합니다.

 

실무 도입 시 이것만은 챙기세요
1. 파티셔닝 먼저 검토 — 샤딩 전에 단일 DB 내 테이블 분할로 버틸 수 있는지 확인해야 합니다.
2. 크로스 샤드 트랜잭션 최소화 — 필요하면 사가 패턴 같은 보상 로직을 별도로 설계해야 합니다.
3. 가상 샤드로 여유 확보 — 물리 노드는 유연하게, 논리 샤드는 넉넉히 잡아야 리샤딩 부담이 줄어듭니다.
4. 샤드별 트래픽 모니터링 — 불균형을 상시 추적해야 핫스팟을 조기에 발견할 수 있습니다.

 

마무리 — 3줄 요약

① 샤딩 키는 쓰기 분산, 쿼리 지역성, 카디널리티를 모두 만족해야 합니다.
② 리샤딩은 이중 쓰기와 백필, 컷오버가 필요한 큰 작업입니다.
③ 핫스팟은 ID 설계나 테넌트 분리로 완화하되 상시 모니터링이 필요합니다.

읽어주셔서 감사합니다. 샤딩을 앞두고 계시다면 되돌리기 어려운 결정인 만큼 키 선택부터 신중히 검토해보시길 권해드립니다.
