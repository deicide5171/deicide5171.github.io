Next.js App Router 데이터 페칭 패턴 총정리 — fetch 위치, 병렬 처리, 스트리밍

2026. 8. 17. · 프론트엔드

한 줄 요약 — Next.js App Router에서는 어떤 컴포넌트에서든 직접 fetch할 수 있게 되면서, 캐싱과는 별개로 fetch 위치·병렬 처리·스트리밍 설계가 중요해졌습니다. 이 글은 캐시 무효화가 아니라 그 세 가지에 집중해서 정리했습니다.

 

왜 지금 데이터 페칭 방식을 다시 봐야 할까요

Pages Router 시절에는 getServerSideProps 하나에 데이터 로딩을 몰아넣고, 그 결과를 props로 하위 컴포넌트에 뿌리는 구조가 사실상 유일한 선택지였습니다. App Router로 넘어오면서 트리 안 어떤 Server Component에서든 직접 fetch를 호출할 수 있게 됐고, "데이터를 어디서 가져올 것인가"가 그 자체로 설계 결정이 됐습니다.

캐시 전략(revalidate, revalidateTag 등)과 페칭 위치·순서 문제는 자주 뒤섞여 다뤄집니다. 캐시를 아무리 잘 설계해도 fetch 호출이 컴포넌트 트리에 순차적으로 쌓여 워터폴을 만들면 체감 성능은 그대로 나쁩니다. 이번 글은 캐시 무효화 대신 fetch를 어디에 두고, 병렬로 묶고, 스트리밍으로 내보낼지에 집중합니다.

 

핵심 개념 1 — fetch는 어디서 호출해야 할까요

App Router의 기본 원칙은 "데이터가 필요한 컴포넌트에서 직접 fetch한다"입니다. 최상위 페이지에서 한 번에 가져와 props로 내려주던 관성은 버리는 편이 좋습니다. 아래 표로 방식별 차이를 정리했습니다.

방식 위치 특징
Pages Router getServerSideProps 페이지 하나당 한 번, props로 하향 전달
App Router 권장 필요한 Server Component 각각 컴포넌트별 독립 fetch, 트리 어디서든 호출
클라이언트 상태 필요 시 Client Component + SWR 등 인터랙션 후 재요청, 폴링

 

Server Component는 async function으로 선언하고 그 안에서 바로 await fetch(...)를 호출하면 됩니다. React가 동일 렌더 패스 안의 중복 요청을 자동으로 메모이제이션해주기 때문에, 여러 컴포넌트가 같은 데이터를 필요로 해도 각자 fetch하는 편이 오히려 단순합니다. 클릭·입력에 반응해 다시 가져와야 하는 경우만 Client Component에서 직접 요청하도록 남겨두면 됩니다.

 

핵심 개념 2 — Server/Client 경계와 병렬 vs 순차 페칭

Server Component는 서버에서만 실행되므로 DB 접근이나 비밀 키를 쓰는 fetch를 안전하게 둘 수 있지만 onClick이나 useState는 쓸 수 없습니다. 실무에서 자주 쓰는 패턴은 Server Component가 fetch한 결과를 props로 Client Component에 넘기는 것입니다. 좋아요 버튼처럼 상태가 필요한 부분만 Client Component로 분리하고 나머지는 Server Component에 남기면, 클라이언트로 내려가는 JS 번들과 하이드레이션 비용을 최소화할 수 있습니다.

한편 컴포넌트 A에서 사용자 정보를 fetch한 뒤 그 결과를 컴포넌트 B에 넘겨 B가 다시 게시글을 fetch한다면, 두 데이터에 의존 관계가 없는데도 순차 실행되는 워터폴이 생깁니다. 의존성이 없는 요청은 같은 컴포넌트 안에서 Promise.all로 동시에 시작해야 합니다. 반면 형제 컴포넌트 각각의 독립 fetch는 트리 렌더링 과정에서 사실상 동시에 시작되므로 별도 처리가 필요하지 않습니다.

 

핵심 개념 3 — Suspense로 스트리밍하기

App Router는 loading.tsx와 <Suspense> 경계 단위로 HTML을 점진적으로 스트리밍합니다. 느린 데이터를 가진 컴포넌트를 <Suspense fallback=...>로 감싸두면, 나머지 페이지는 먼저 렌더링해 브라우저로 보내고 느린 부분은 준비되는 대로 나중에 채워 넣습니다. 사용자는 빈 화면 대신 뼈대와 로딩 상태를 먼저 보고, 콘텐츠가 하나씩 채워지는 경험을 하게 됩니다.

 

예제: 병렬 페칭 + 스트리밍 적용 (TSX)

아래는 의존 관계 없는 두 요청을 Promise.all로 병렬 실행하고, 느린 컴포넌트는 별도 Suspense로 감싸 스트리밍하는 예시입니다.

// app/dashboard/page.tsx
import { Suspense } from "react";

async function getUser() {
  return fetch("https://api.example.com/user").then((r) => r.json());
}
async function getStats() {
  return fetch("https://api.example.com/stats").then((r) => r.json());
}

// 의존 관계 없는 두 요청을 명시적으로 병렬 실행
export default async function DashboardPage() {
  const [user, stats] = await Promise.all([getUser(), getStats()]);
  return (
    <div>
      <h1>{user.name}님의 대시보드</h1>
      <StatsPanel stats={stats} />
      {/* 느린 컴포넌트는 별도 Suspense 경계로 분리해 스트리밍 */}
      <Suspense fallback={<p>최근 활동을 불러오는 중...</p>}>
        <RecentActivity userId={user.id} />
      </Suspense>
    </div>
  );
}

async function RecentActivity({ userId }: { userId: string }) {
  const res = await fetch(`https://api.example.com/activity/${'{userId}'}`, { cache: "no-store" });
  const activity = await res.json();
  return <ul>{activity.map((a: any) => <li key={a.id}>{a.text}</li>)}</ul>;
}

RecentActivity가 느리게 응답하더라도 user, stats가 준비되는 즉시 페이지 뼈대는 먼저 렌더링되고, 활동 목록은 준비되는 대로 스트리밍되어 교체됩니다.

 

실무 도입 시 이것만은 챙기세요
1. fetch 위치를 억지로 최상위로 몰지 않기 — 같은 데이터를 여러 형제가 쓴다면 각자 fetch해도 요청 메모이제이션이 중복을 처리
2. 연속된 await는 병렬화 가능 여부부터 점검 — 진짜 의존 관계가 아니라면 Promise.all로 묶기
3. Suspense 경계는 콘텐츠 블록 단위로 적당히 묶기 — 과도하게 잘게 쪼개면 화면이 계속 흔들리는 부작용
4. 서버·클라이언트 fetch 경계를 설계 초기에 정하기 — 최초 렌더링 데이터는 서버에서, 사용자 액션에 따른 갱신은 클라이언트에서
5. 캐시 무효화(revalidateTag 등)는 이 글의 범위 밖 — 캐시 레이어·재검증 전략은 별도 글에서 다룸

 

마무리 — 3줄 요약

① App Router에서는 데이터가 필요한 Server Component 각각에서 직접 fetch하는 것이 기본이며, 인터랙션에 따라 변하는 데이터만 Client Component로 내립니다.
② 의존 관계 없는 요청은 Promise.all로 명시적으로 병렬화해야 워터폴을 피할 수 있고, 형제 컴포넌트의 개별 fetch는 렌더링 과정에서 자연히 동시에 시작됩니다.
③ 느린 데이터는 Suspense 경계로 분리해 스트리밍하면 가장 느린 요청 하나가 전체 페이지를 막지 않습니다.
