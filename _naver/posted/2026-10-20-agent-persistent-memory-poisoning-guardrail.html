"매번 같은 설명을 또 해야 해요" — 에이전트 지속 메모리를 포이즈닝 없이 설계하기

AI

한 줄 요약 — 세션이 끝나도 사용자 선호와 프로젝트 맥락을 기억해 달라는 요구는 저장소 하나를 추가하는 문제가 아니라, 신뢰할 수 없는 과거 대화 내용을 미래의 지시로 다시 주입하는 통로를 여는 문제입니다. 수집-검증-저장-회수 4단계 게이트로 설계 순서를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"매번 같은 설명을 또 해야 하는 게 너무 피곤해요. 지난번에 말한 코딩 스타일, 이번 프로젝트 배경, 자주 틀리는 부분 좀 기억해 두세요." 에이전트를 몇 주 굴려본 팀이면 반드시 받는 요구입니다. 단일 세션 안에서는 컨텍스트 윈도우에 다 욱여넣으면 그만이지만, 세션이 끝나고 다음 날 다시 켰을 때도 기억하려면 별도의 영속 저장소와, 그 저장소를 다음 세션의 프롬프트에 다시 꽂아 넣는 회수(retrieval) 경로가 필요합니다.

문제는 이 회수 경로가 공격 표면이기도 하다는 점입니다. 메모리에 쓰인 문장은 과거의 어느 시점에 — 사용자의 입력일 수도, 에이전트가 처리한 외부 문서나 이메일 내용일 수도 — 만들어진 것입니다. 그 문장이 검증 없이 "신뢰할 수 있는 과거 맥락"으로 미래 세션에 다시 주입되면, 공격자는 지금 이 순간 프롬프트 인젝션을 성공시킬 필요가 없습니다. 한 번만 메모리에 악성 지시를 심어 두면 이후 모든 세션에서 조용히 반복 실행됩니다. 2026년 초 보안 리서치에서 이런 연쇄가 실제로 데모됐고, 벤더들은 에이전트가 자기 메모리를 참조하기 전에 먼저 검증하는 계층을 별도로 두기 시작했습니다.

 

전체 시스템에서의 위치

지속 메모리는 "대화 로그를 DB에 저장"하는 일이 아닙니다. 아래 네 단계로 나눠 보면 위치가 분명해집니다.

① 수집 — 세션 종료 시점에 "기억할 만한 사실"을 모델이 스스로 요약해 후보로 뽑습니다. ② 위험도 평가 게이트 — 후보 문장의 출처, 민감 정보 포함 여부, 기존 메모리와의 충돌을 점수화합니다. ③ 저장소 — 통과한 것만 출처 메타데이터와 함께 저장합니다. ④ 회수·주입 — 다음 세션 시작 시 관련 메모리를 꺼내 프롬프트 앞단에 삽입합니다. 이 ②번 게이트가 없는 구현이 가장 흔한 실수입니다.

 

선택의 트레이드오프
설계 장점 단점
메모리 없음(세션 스코프만) 공격 표면 없음, 구현 단순 매 세션 재설명 필요
무검증 자동 저장 구현 빠름 포이즈닝·개인정보 위험 그대로 노출
사용자 확인 후 저장 명시적 동의, 투명성 확인 누적 시 피로
위험도 점수 게이트 + 출처 메타데이터 자동화 유지하면서 위험 격리, 사후 감사 가능 게이트 구현·튜닝 비용

 

핵심 판단 기준은 "이 에이전트가 신뢰 경계 밖의 텍스트를 처리하는가"입니다. 순수 개인 비서형이면 사용자 확인 방식으로 충분하지만, 외부 입력을 일상적으로 다루는 업무 에이전트라면 점수 게이트 없이는 메모리 기능을 켜지 않는 것이 안전합니다.

 

실제 프로젝트 진행 순서

1. 저장 대상부터 선호 / 프로젝트 사실 / 민감 정보로 분류하고, 민감 정보는 후보에서 자동 제외합니다.
2. 모든 메모리 레코드에 출처(source_type), 사용자 확인 여부, 생성 세션 ID를 필수 필드로 넣습니다.
3. "외부 문서에서 추출 + 민감 키워드 포함이면 자동 격리" 같은 간단한 규칙으로 위험도 게이트를 먼저 돌립니다.
4. 회수해서 프롬프트에 삽입하기 직전, 명령형 문장인지 한 번 더 점검하는 2차 방어선을 둡니다.
5. 어떤 메모리가 언제 생성·회수되어 어떤 응답에 영향을 줬는지 감사 로그를 남깁니다.

 

예제(의사코드, 저장 전 위험도 게이트):

def evaluate_memory_candidate(candidate):
    score = 0
    if candidate.source_type == "external_document":
        score += 40
    if contains_imperative_pattern(candidate.text):
        score += 30
    if contains_sensitive_pattern(candidate.text):
        return "reject"
    if score >= 50:
        return "quarantine"
    return "approve"

 

주의 — 메모리 삭제·수정 UI를 반드시 사용자에게 노출하세요. 팀 공유 메모리 저장소라면 개인 선호와 조직 공통 사실을 같은 네임스페이스에 섞지 말고, 벡터 유사도 검색으로 회수한다면 상위 N개를 무조건 주입하지 말고 출처 신뢰도로 재정렬하세요.

 

정리

지속 메모리는 저장소 추가가 아니라 과거 텍스트가 미래 지시가 되는 새로운 입력 경로를 여는 설계 문제입니다. 수집과 저장 사이에 출처 기반 위험도 게이트를 두지 않으면 포이즈닝된 메모리가 세션마다 조용히 반복 실행될 수 있습니다. 분류 → 출처 메타데이터 → 게이트 프로토타입 → 회수 시점 2차 방어 → 감사 로그 순으로 쌓아가는 것이 가장 안전한 도입 경로입니다.
