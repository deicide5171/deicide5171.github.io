컨테이너 쿼리로 완성하는 진짜 컴포넌트 반응형 레이아웃

2026. 8. 16. · 프론트엔드

한 줄 요약 — 미디어 쿼리로는 풀리지 않던 '같은 컴포넌트, 다른 위치' 문제를 CSS 컨테이너 쿼리와 컨테이너 쿼리 유닛으로 카드 컴포넌트 하나에 직접 적용해봅니다.

 

왜 지금 컨테이너 쿼리를 제대로 파야 할까요

디자인 시스템 기반 개발이 보편화되면서 카드 컴포넌트 하나를 사이드바에도, 본문 그리드에도, 모달 안에도 그대로 재사용하는 일이 당연해졌습니다. 그런데 미디어 쿼리는 오직 화면(뷰포트) 폭만 보기 때문에, 같은 카드가 좁은 사이드바에 들어갔는지 넓은 본문 컬럼에 들어갔는지는 알 방법이 없었습니다. 그래서 오랫동안 ResizeObserver로 컴포넌트 크기를 감시하고 JS로 클래스를 토글하는 우회 방식이 표준처럼 쓰였습니다.

컨테이너 쿼리(Container Queries)는 이 문제를 CSS 레벨에서 해결합니다. 최근에는 여러 컴포넌트 라이브러리와 디자인 시스템이 컨테이너 쿼리를 실제 반응형 전략으로 채택하는 사례가 늘고 있습니다. 다만 확정 사양이 계속 논의 중인 후속 기능(스타일 쿼리 등)도 있으니, 도입 전에는 최신 브라우저 지원 현황을 직접 확인하는 것이 안전합니다. 이번 글은 개념만 나열하지 않고, 카드 컴포넌트 하나를 처음부터 끝까지 컨테이너 쿼리로 구현하는 데 집중합니다.

 

container-type, 컨테이너를 선언하는 세 가지 방법

컨테이너 쿼리를 쓰려면 먼저 부모 요소를 컨테이너로 선언해야 합니다. 이때 container-type 값에 따라 어떤 축을 쿼리할 수 있는지, 어떤 부작용이 생기는지가 달라집니다.

값 쿼리 가능 축 대표 부작용
inline-size 인라인 방향(보통 너비)만 containment 발생, 자식 margin이 밖으로 collapse 안 됨
size 너비·높이 모두 높이가 콘텐츠에 의존하면 순환 참조로 무시됨
normal 쿼리 불가(기본값) 없음 — 컨테이너로 동작하지 않음

실무에서는 대부분 inline-size만으로 충분합니다. size는 높이까지 반응시켜야 하는 특수한 경우(정사각형 그리드 셀 등)에만 쓰고, 컨테이너 자체에 고정 높이나 aspect-ratio를 지정해 순환 참조를 피해야 합니다.

 

컨테이너 쿼리 유닛 — 폭이 아니라 '내부 비율'로 스케일링

컨테이너 쿼리와 함께 등장한 cqw, cqh, cqi, cqb, cqmin, cqmax 유닛은 뷰포트 단위(vw, vh)의 컨테이너 버전입니다. 미디어 쿼리 breakpoint마다 값을 다시 지정하는 대신, 컨테이너 크기에 비례해 폰트나 패딩이 자동으로 스케일됩니다. cqi/cqw는 컨테이너의 인라인(보통 너비) 크기 1%, cqb/cqh는 블록(보통 높이) 크기 1%를 기준으로 하고, cqmin과 cqmax는 두 값 중 작은 쪽과 큰 쪽을 각각 사용합니다.

 

예제: 카드 컴포넌트를 컨테이너 쿼리로 완성하기

하나의 카드 컴포넌트를 정의해서 좁은 컨테이너에서는 세로 스택, 넓은 컨테이너에서는 가로 배치로 전환하고, 내부 요소 크기까지 컨테이너 비율로 스케일링하는 전체 예제입니다.

/* 1) 카드를 감쌀 요소를 컨테이너로 선언 */
.card-slot {
  container-type: inline-size;
  container-name: card;
}

/* 2) 기본(좁은 컨테이너) 레이아웃: 세로 스택 */
.card {
  display: flex;
  flex-direction: column;
  gap: 8px;
  padding: 12px;
  border-radius: 8px;
  border: 1px solid #e2e5e9;
}

.card__title {
  font-size: clamp(14px, 5cqi, 20px);
}

/* 3) 컨테이너 폭이 일정 크기를 넘으면 가로 배치로 전환 */
@container card (min-width: 420px) {
  .card {
    flex-direction: row;
    align-items: center;
  }
}

/* 4) 컨테이너가 아주 넓을 때는 여백까지 비례 확장 */
@container card (min-width: 640px) {
  .card {
    padding: 3cqw;
    gap: 3cqw;
  }
}

.card 자체가 아니라 .card-slot이라는 감싸는 요소에 container-type을 건다는 점이 핵심입니다. 요소는 자기 자신의 크기를 스스로 쿼리할 수 없고, 반드시 조상 컨테이너의 크기를 기준으로 쿼리합니다. container-name으로 이름을 지정해두면 중첩된 컨테이너 사이에서도 어떤 컨테이너를 기준으로 삼는지 명시할 수 있어, 여러 겹의 컨테이너가 있는 실제 페이지에서 의도치 않은 컨테이너에 걸리는 실수를 막을 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. containment 부작용 확인 — container-type: inline-size는 contain: layout style을 함께 유발해 자식 margin collapse가 달라질 수 있습니다.
2. 자기 자신에는 쿼리 불가 — .card에 container-type과 @container를 동시에 걸면 동작하지 않습니다. 감싸는 부모에 선언하세요.
3. 이름 없는 컨테이너는 자동 매칭 — 중첩 컴포넌트가 많다면 container-name을 명시해 의도한 컨테이너에만 걸리게 하세요.
4. 점진적 도입 — @supports (container-type: inline-size)로 감싸 구형 환경에서는 미디어 쿼리 기반 기본 레이아웃을 유지하세요.

 

마무리 — 3줄 요약

① 컨테이너 쿼리는 컴포넌트를 감싼 조상 요소를 container-type으로 선언하고, 그 조상의 크기를 기준으로 자식 스타일을 바꾸는 방식입니다.
② cqw, cqi, cqb 같은 컨테이너 쿼리 유닛을 쓰면 breakpoint별로 값을 다시 쓰지 않고도 컨테이너 크기에 비례해 폰트·여백이 자동으로 스케일됩니다.
③ container-type: inline-size가 만드는 containment 부작용과 이름 없는 컨테이너의 자동 매칭 문제를 미리 알고 container-name으로 명시하는 것이 실전 도입의 핵심입니다.
