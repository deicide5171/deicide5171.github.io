AI

한 줄 요약 — 여러 요청이 공유하는 접두사의 KV 캐시를 라딕스 트리로 자동 재사용해, 시스템 프롬프트를 매번 다시 계산하지 않도록 만드는 SGLang의 원리를 정리했습니다.

 

왜 지금 프리픽스 캐싱을 다시 봐야 하는가

에이전트 서비스가 늘면서 하나의 요청 안에 긴 시스템 프롬프트, 도구 설명, few-shot 예제가 함께 딸려 들어가는 패턴이 표준이 됐습니다. 실제로 다른 부분은 마지막 몇 줄뿐인데, 서빙 엔진이 요청마다 전체 시퀀스의 KV 캐시를 처음부터 다시 계산한다면 GPU 연산의 대부분이 완전히 똑같은 값을 반복해서 만드는 데 쓰입니다.

 

라딕스 트리로 KV 캐시를 색인하기

RadixAttention의 핵심은 지금까지 처리한 모든 시퀀스의 KV 캐시를 하나의 라딕스 트리(압축 트라이)에 저장해둔다는 것입니다. 새 요청이 들어오면 엔진은 토큰 시퀀스를 트리 루트부터 따라 내려가며 이미 캐시된 최장 공통 접두사를 찾고, 그 구간의 연산을 건너뛴 채 실제로 새로운 부분에 대해서만 prefill을 수행합니다. 같은 시스템 프롬프트를 공유하는 멀티테넌트 API 서버나 tree-of-thought처럼 하나의 프리픽스에서 여러 분기가 뻗어나가는 워크로드에서 특히 효과가 큽니다.

방식 캐시 경계 지정 적중 판단
API 프롬프트 캐싱 사용자가 명시 표시 요청 수신 즉시
단순 KV 캐시 재사용 완전 동일 요청만 문자열 완전 일치
RadixAttention 자동 탐지 트리 탐색으로 최장 일치

 

캐시 축출과 스케줄링

GPU 메모리는 유한하므로 트리는 무한정 커질 수 없습니다. RadixAttention은 각 노드에 참조 카운트를 유지해 현재 활성 요청이 물고 있는 노드는 축출하지 않고, 가장 오래전에 접근한 리프 노드부터 LRU 방식으로 제거합니다. 여기에 캐시 인지 스케줄러가 더해져 공유 접두사가 많은 요청끼리 묶어 배치하도록 큐 순서 자체를 조정합니다.

SGLang 서버 활용 예제
import sglang as sgl

@sgl.function
def multi_turn_qa(s, system_prompt, question):
    s += sgl.system(system_prompt)
    s += sgl.user(question)
    s += sgl.assistant(sgl.gen("answer", max_tokens=256))

states = multi_turn_qa.run_batch(
    [{"system_prompt": SHARED_PROMPT, "question": q} for q in questions],
)

명시적인 캐시 API를 호출하지 않아도, 배치 안에서 동일한 접두사를 가진 요청들은 엔진 내부에서 자동으로 트리 노드를 공유합니다.

 

실무 포인트

접두사가 정확히 일치해야 캐시가 재사용됩니다. 시스템 프롬프트에 요청마다 타임스탬프나 요청 ID를 끼워 넣으면 캐시 이득이 사라지므로, 가변 정보는 프롬프트 뒷부분에 배치해야 합니다.

캐시 적중률은 트래픽 패턴에 크게 좌우됩니다. 공통 템플릿을 쓰는 멀티테넌트·에이전트 워크로드일수록 이 최적화의 이득이 커집니다.

주의 — 캐시를 위해 확보하는 GPU 메모리가 커질수록 동시 처리 배치 크기가 줄어들 수 있으므로, 캐시 풀 크기와 배치 크기를 함께 튜닝해야 합니다.
