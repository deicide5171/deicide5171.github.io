PostgreSQL 선언적 파티셔닝 — Range/List/Hash 전략과 파티션 프루닝의 조건

DB·데이터 모델링

한 줄 요약 — 파티셔닝의 성능 이점은 파티션 프루닝이 실제로 동작할 때만 살아나며, 파티션 키가 조건절에 직접 노출돼야 프루닝이 확실히 작동합니다.

 

왜 필요해지는가

테이블이 수억 행을 넘어가면 VACUUM 시간이 길어지고, 인덱스 B-tree 탐색 깊이가 늘어나며, 대량 삭제가 WAL을 폭발적으로 생성합니다. 선언적 파티셔닝은 논리적으로 하나의 테이블처럼 보이지만 물리적으로 여러 작은 테이블로 나눠 이 문제를 해결합니다.

 

Range, List, Hash 전략 선택

Range는 날짜 등 연속 범위로 나누며 오래된 파티션을 DETACH로 빠르게 아카이빙할 수 있습니다. List는 테넌트 ID처럼 이산 값으로 나눠 물리적 격리를 줍니다. Hash는 자연스러운 기준이 없을 때 균등 분산으로 관리 부담만 줄이고 싶을 때 선택합니다.

전략 예시 장점
Range 생성일자 빠른 아카이빙
List 테넌트 ID 물리 격리
Hash 임의 키 균등 분산

 

파티션 프루닝이 동작하는 조건

쿼리 플래너가 필요 없는 파티션을 스캔 계획에서 제외하는 것이 프루닝입니다. 파티션 키가 리터럴 값이면 계획 시점에 프루닝을 결정할 수 있지만, 키를 함수로 감싸거나 다른 컬럼과 조합한 조건에서는 프루닝이 무력화되어 모든 파티션을 스캔하게 됩니다.

Range 파티션 생성과 프루닝 확인 예제
CREATE TABLE orders (
    id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    amount NUMERIC NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_08 PARTITION OF orders
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE orders_2026_09 PARTITION OF orders
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE created_at >= '2026-09-01' AND created_at < '2026-09-15';

계획에 orders_2026_08이 아예 등장하지 않아야 프루닝이 성공한 것입니다.

 

실무 포인트

파티션 키는 조건절에 직접 등장해야 합니다. 함수로 감싼 조건으로만 필터링하면 프루닝이 무력화되므로 쿼리 패턴을 먼저 분석하세요.

파티션 수가 너무 많아지면 계획 수립 비용이 커집니다. 시계열이라면 월 단위로 관리하고 오래된 파티션은 정기적으로 통합·아카이빙하세요.

주의 — PostgreSQL 파티션 테이블에서 기본키나 유니크 제약을 걸려면 그 제약이 파티션 키를 포함해야 하는 제한이 있으므로 스키마 설계 초기에 감안해야 합니다.
