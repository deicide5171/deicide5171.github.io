MySQL에서 이모지 저장하면 깨지는 이유 — utf8과 utf8mb4 문자셋 제대로 잡기

데이터베이스

한 줄 요약 — MySQL의 utf8은 최대 3바이트까지만 저장하는 축소판이라 4바이트인 이모지를 담을 수 없습니다. 진짜 전체 UTF-8은 utf8mb4이며, 서버·DB·테이블·컬럼·연결 다섯 곳 모두 일치해야 합니다.

 

왜 분명 UTF-8인데 이모지가 깨질까

사용자 닉네임이나 채팅 메시지에 이모지를 입력했더니 저장이 안 되거나, 저장은 됐는데 조회하면 물음표나 깨진 문자로 보이는 문제를 겪게 됩니다. 테이블 인코딩을 utf8로 이미 설정해뒀는데도 이런 일이 생기면 당황스럽습니다. 하지만 여기 함정이 있습니다 — MySQL의 utf8은 이름과 달리 진짜 UTF-8이 아닙니다.

MySQL의 utf8 문자셋은 실제로는 최대 3바이트까지만 표현하는 축소판입니다. 그런데 이모지 대부분은 UTF-8 인코딩에서 4바이트를 차지합니다. 3바이트 한도에 4바이트 문자를 넣으려 하면 MySQL은 문자를 자르거나 조용히 물음표로 치환해버립니다.

 

 

핵심 개념 1 — utf8과 utf8mb4는 다른 문자셋이다
항목 utf8 (레거시) utf8mb4
최대 바이트 3바이트 4바이트
이모지 저장 불가능 가능

MySQL 8.0부터는 기본 문자셋이 utf8mb4로 바뀌었지만, 오래된 DB를 이어받았다면 여전히 utf8로 남아 있는 경우가 흔합니다. mb4는 "multi-byte 4"의 줄임말로 진짜 완전한 UTF-8이라고 기억하면 헷갈리지 않습니다.

 

핵심 개념 2 — 다섯 곳 모두 확인해야 한다

가장 흔한 실수는 테이블 문자셋만 바꾸고 끝냈다고 생각하는 것입니다. MySQL 연결 문자셋이 여전히 utf8이면 애플리케이션에서 아무리 4바이트 문자를 보내도 연결 계층에서 깨집니다. JDBC 커넥션 URL의 characterEncoding도 함께 확인해야 합니다.

 

예제 — 기존 테이블을 안전하게 전환하기
-- 1. 현재 문자셋 확인
SHOW CREATE TABLE users;
SHOW VARIABLES LIKE 'character_set%';

-- 2. 데이터베이스 기본 문자셋 변경
ALTER DATABASE mydb CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 3. 테이블과 모든 컬럼을 함께 변환
ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

JDBC URL의 characterEncoding=utf8은 자바 진영의 이름 표기일 뿐 MySQL의 3바이트 utf8을 의미하지 않습니다. 최신 커넥터를 쓴다면 connectionCollation 옵션으로 명시하는 편이 안전합니다.

 

전환 시 흔한 함정
함정 결과
CONVERT TO 없이 컬럼 정의만 변경 기존 데이터가 옛 인코딩 그대로 남아 재해석 시 깨짐
인덱스 걸린 VARCHAR 그대로 전환 인덱스 최대 길이(767바이트) 초과 에러 가능
unicode_ci와 general_ci 혼용 "Illegal mix of collations" 에러

 

실무 포인트

VARCHAR(255)에 utf8mb4를 적용하면 문자당 최대 4바이트라 인덱스가 1020바이트를 요구하게 되는데, InnoDB 기본 키 길이 제한(767바이트)을 넘어설 수 있습니다. 컬럼 길이를 줄이거나 innodb_large_prefix 설정을 확인하세요.

주의 — 문자셋은 서버, DB, 테이블, 컬럼, 연결 다섯 곳이 모두 일치해야 하며 하나라도 utf8로 남아 있으면 이모지가 깨집니다.
