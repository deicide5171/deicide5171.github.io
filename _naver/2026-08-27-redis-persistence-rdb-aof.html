레디스도 디스크에 씁니다 — RDB vs AOF 영속성 트레이드오프

2026. 8. 27. · 데이터베이스

한 줄 요약 — Redis를 순수 캐시로만 쓰지 않고 세션 저장소나 큐로 쓴다면 재시작 시 데이터가 얼마나 살아남는지가 중요해집니다. RDB와 AOF의 동작 방식과 선택 기준을 정리했습니다.

 

Redis 영속성이 왜 필요할까요

Redis를 순수 캐시로만 쓴다면 재시작 시 데이터가 날아가도 큰 문제가 안 될 수 있습니다. 하지만 세션 저장소, 레이트 리밋 카운터, 간단한 큐로 쓴다면 이야기가 달라집니다. Redis는 이를 위해 두 가지 영속성 메커니즘을 제공합니다. RDB(스냅샷)와 AOF(추가 전용 로그)입니다. 둘은 서로 다른 트레이드오프를 가지며, 함께 쓸 수도 있습니다.

 

핵심 개념 1 — RDB, 특정 시점의 스냅샷

RDB(Redis Database)는 특정 시점의 전체 데이터셋을 이진 파일로 디스크에 저장하는 방식입니다. 저장 시 Redis는 fork()로 자식 프로세스를 만들고, 이 자식 프로세스가 부모의 메모리를 COW(Copy-on-Write)로 공유하며 스냅샷을 디스크에 씁니다. 부모 프로세스는 계속 요청을 처리하므로 스냅샷 저장 중에도 서비스 중단이 없습니다.

장점은 파일이 작고 복구가 빠르다는 것입니다. 단점은 마지막 스냅샷 이후의 변경사항은 장애 시 전부 유실된다는 점입니다.

 

핵심 개념 2 — AOF, 모든 쓰기 명령의 로그

AOF(Append Only File)는 Redis에 들어온 쓰기 명령을 순서대로 파일에 이어 붙이는 방식입니다. 재시작 시 이 로그를 처음부터 재생해 데이터를 복원합니다.

appendfsync 값 동작 데이터 손실 위험
always 매 쓰기마다 즉시 fsync 사실상 없음(가장 느림)
everysec (기본값) 1초마다 배치로 fsync 최대 1초치 손실
no OS에 맡김 수 초~수십 초 손실 가능

 

 

예제 — redis.conf 영속성 설정(하이브리드 모드)
# RDB: 900초 내 1개, 300초 내 10개, 60초 내 10000개 키 변경 시 스냅샷
save 900 1
save 300 10
save 60 10000
dbfilename dump.rdb

# AOF 활성화 및 동기화 정책
appendonly yes
appendfsync everysec
appendfilename "appendonly.aof"

# Redis 4.0+ 하이브리드 방식: AOF 재작성 시 RDB 형식 프리앰블 사용
aof-use-rdb-preamble yes

auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

aof-use-rdb-preamble yes는 AOF 재작성 시 파일 앞부분을 RDB 형식으로 압축해 넣고 그 뒤에 재작성 이후의 증분 명령만 AOF 형식으로 붙이는 하이브리드 방식입니다. 순수 AOF 재생보다 복구가 훨씬 빠르면서도 손실 없는 로그는 유지합니다.

 

실무 도입 시 이것만은 챙기세요
1. fork() 시 메모리 스파이크를 고려하세요 — 쓰기가 많은 인스턴스에서는 COW로 인해 순간적으로 메모리 사용량이 최대 2배 가까이 튈 수 있습니다.
2. RDB만으로는 부족한 워크로드를 먼저 식별하세요 — 세션·큐처럼 데이터 손실이 곧 사용자 경험 문제로 이어지는 워크로드는 AOF를 켜야 합니다.
3. 복제는 영속성을 대체하지 않습니다 — 영속성과 복제는 서로 다른 문제를 해결하는 별개의 메커니즘이므로 함께 설계해야 합니다.

 

마무리 — 3줄 요약

① RDB는 특정 시점 전체 스냅샷이라 파일이 작고 복구가 빠르지만 마지막 스냅샷 이후 변경은 유실될 수 있습니다.
② AOF는 모든 쓰기 명령을 로그로 남겨 손실 창을 appendfsync 설정으로 좁힐 수 있지만 파일 크기와 쓰기 오버헤드가 더 큽니다.
③ Redis 4.0+ 하이브리드 모드로 두 방식의 장점을 조합하는 것이 실무 기본값에 가깝습니다.
