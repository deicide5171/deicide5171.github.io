2026. 8. 23. · 프론트엔드

한 줄 요약 — 조건부 타입, infer, 템플릿 리터럴 타입을 조합하면 "/users/:userId" 같은 API 경로 문자열에서 파라미터 타입을 컴파일 타임에 자동 추출할 수 있습니다. 이 글에서는 그 원리와 실전 구현, 그리고 "어디까지 써야 하는가"의 기준까지 정리했습니다.

 

왜 타입 레벨 프로그래밍인가요

API를 호출할 때 경로 파라미터 하나를 빼먹거나 이름에 오타를 내면, 컴파일러는 아무 말도 하지 않고 런타임에 404가 돌아옵니다. 경로와 파라미터의 짝이 맞는지는 오랫동안 "사람이 잘 확인해야 하는 영역"이었는데요, TypeScript의 타입 시스템은 이제 이 검증을 컴파일 타임으로 끌어올 수 있을 만큼 표현력이 좋아졌습니다.

이 조합의 대표적인 수혜자가 우리가 매일 쓰는 라이브러리들입니다. tRPC는 서버 라우터 정의에서 클라이언트 타입을 통째로 추론하고, Hono 같은 프레임워크는 경로 문자열에서 params의 형태를 뽑아냅니다. 오늘은 그 밑바닥에서 돌아가는 세 가지 도구 — 조건부 타입, infer, 템플릿 리터럴 타입 — 를 하나씩 살펴보고, 이를 조합해 타입 안전한 API 클라이언트를 직접 만들어보겠습니다.

 

핵심 개념 1 — 조건부 타입, 타입 세계의 if문

조건부 타입은 T extends U ? X : Y 형태로, 타입 T가 U에 할당 가능하면 X, 아니면 Y가 되는 타입입니다. 타입 레벨 프로그래밍에서 분기문 역할을 합니다. 여기서 꼭 알아두셔야 할 동작이 분배 법칙(distributive conditional types)인데요, 검사 대상이 "벌거벗은(naked)" 타입 파라미터이면 유니온 타입이 들어왔을 때 각 멤버에 조건이 하나씩 분배되어 적용됩니다.

type ToArray<T> = T extends unknown ? T[] : never;

// string[] | number[] — (string | number)[] 가 아닙니다!
type A = ToArray<string | number>;

// 분배를 막고 싶으면 양쪽을 튜플로 감쌉니다
type ToArrayNonDist<T> = [T] extends [unknown] ? T[] : never;
type B = ToArrayNonDist<string | number>; // (string | number)[]

이 분배 동작은 Exclude, Extract 같은 내장 유틸리티 타입의 원리이기도 하지만, 모르고 당하면 대표적인 함정이 됩니다. 아래 주의사항에서 다시 짚어보겠습니다.

 

핵심 개념 2 — infer, 타입에서 정보를 꺼내는 유일한 방법

infer는 조건부 타입의 extends 절 안에서만 쓸 수 있는 키워드로, 매칭에 성공한 위치의 타입을 변수처럼 캡처합니다. 내장 유틸리티인 ReturnType이 정확히 이 방식으로 구현되어 있습니다. 함수의 반환 타입, 배열의 요소 타입, Promise의 내부 타입처럼 다른 타입 안에 갇혀 있는 타입을 꺼내려면 infer 외에 다른 수단이 없습니다.

type MyReturnType<T> = T extends (...args: never[]) => infer R ? R : never;

// Promise를 재귀적으로 벗겨내기 (내장 Awaited의 단순화 버전)
type UnwrapPromise<T> = T extends Promise<infer U> ? UnwrapPromise<U> : T;

type C = UnwrapPromise<Promise<Promise<number>>>; // number

 

핵심 개념 3 — 템플릿 리터럴 타입으로 경로 문자열 파싱하기

템플릿 리터럴 타입은 문자열 리터럴 타입을 조합하고 분해할 수 있게 해줍니다. infer와 결합하면 문자열 패턴 매칭이 가능해지는데요, 세 가지 도구를 모두 조합해 API 경로에서 파라미터를 추출하는 타입 안전 클라이언트를 만들어보겠습니다.

// 1) 경로 문자열에서 ":param" 이름들을 유니온으로 추출 (재귀)
type ExtractParams<Path extends string> =
  Path extends `${string}:${infer Param}/${infer Rest}`
    ? Param | ExtractParams<`/${Rest}`>
    : Path extends `${string}:${infer Param}`
      ? Param
      : never;

// 2) 유니온을 매핑 타입으로 객체 형태로 변환
type PathParams<Path extends string> = {
  [K in ExtractParams<Path>]: string | number;
};

// 3) 파라미터가 없으면 인자를 아예 받지 않는 시그니처
type RequestArgs<Path extends string> =
  ExtractParams<Path> extends never
    ? [path: Path]
    : [path: Path, params: PathParams<Path>];

export async function apiGet<Path extends string>(
  ...[path, params]: RequestArgs<Path>
): Promise<unknown> {
  const url = params
    ? path.replace(/:([A-Za-z0-9_]+)/g, (_, k) =>
        encodeURIComponent(String((params as Record<string, unknown>)[k])),
      )
    : path;
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${url}`);
  return res.json();
}

// 사용 예 — 전부 컴파일 타임에 검증됩니다
await apiGet("/users/:userId/posts/:postId", { userId: 1, postId: 42 }); // OK
await apiGet("/health"); // OK — 파라미터 없는 경로는 두 번째 인자 금지
// await apiGet("/users/:userId/posts/:postId", { userId: 1 });
//   ^ 컴파일 오류: 'postId' 속성이 없습니다

ExtractParams에 "/users/:userId/posts/:postId"를 넣으면 "userId" | "postId"로 평가되고, 매핑 타입이 이를 파라미터 객체 타입으로 바꿉니다. 경로 문자열이 곧 스키마가 되는 셈입니다.

 

 

언제 쓰고, 언제 쓰지 말아야 할까요

타입 레벨 프로그래밍은 강력하지만 공짜가 아닙니다. 상황별 판단 기준을 표로 정리해봤습니다.

상황 권장 접근 이유
사내 공용 라이브러리·SDK의 공개 API 타입 레벨 추론 적극 활용 한 번의 복잡도 투자로 수십 개 호출부가 안전해짐
백엔드에 OpenAPI/GraphQL 스키마가 있음 openapi-typescript 등 코드 생성 직접 파싱 타입을 만들 이유가 없음. 생성기가 유지보수까지 대신함
런타임 검증도 필요한 외부 입력 Zod 등 스키마 라이브러리 + z.infer 타입만으로는 런타임 데이터를 막을 수 없음
앱 내부 비즈니스 로직의 일회성 타입 그냥 손으로 타입 작성 읽는 사람의 비용이 얻는 안전성보다 큼

 

핵심 기준은 "이 타입을 읽고 고칠 사람이 몇 명이고, 이 타입이 지켜주는 호출부가 몇 곳인가"입니다. 호출부가 많은 경계(라이브러리, 공용 클라이언트)에서는 복잡한 타입이 값을 하고, 호출부가 한두 곳인 내부 코드에서는 오히려 부채가 됩니다.

 

실무에서 이것만은 주의하세요
1. boolean은 조건부 타입에서 두 번 분배됩니다 — TypeScript에서 boolean은 내부적으로 true | false 유니온이라, 벌거벗은 타입 파라미터에 넣으면 조건이 두 번 분배되어 의도치 않은 유니온 결과가 나옵니다. [T] extends [boolean]처럼 튜플로 감싸 분배를 차단하는 것이 올바른 대안입니다.
2. 재귀 깊이와 컴파일 성능을 살피세요 — 템플릿 리터럴 재귀는 컴파일러의 인스턴스화 깊이 제한에 걸릴 수 있고, 수백 개 경로 조합 같은 거대한 유니온을 만들면 IDE 자동완성이 눈에 띄게 느려집니다.
3. 오류 메시지를 팀원이 읽을 수 있어야 합니다 — 타입이 복잡해질수록 오류 메시지도 난해해집니다. 팀원이 오류를 보고 스스로 고칠 수 없다면 그 타입은 이미 과했다는 신호입니다. 복잡한 타입에는 tsd나 Vitest의 expectTypeOf 같은 타입 테스트를 붙여 리팩터링 시 회귀를 잡는 것을 권장합니다.

 

마무리 — 3줄 요약

① 조건부 타입은 타입의 분기, infer는 타입 속 정보의 추출, 템플릿 리터럴 타입은 문자열의 타입 레벨 파싱을 담당하며, 셋을 조합하면 API 경로 문자열에서 파라미터 타입을 자동 추론할 수 있습니다.
② 호출부가 많은 경계(공용 클라이언트·SDK)에는 투자 가치가 충분하지만, OpenAPI 스키마가 있다면 코드 생성이 우선이고, 일회성 내부 타입은 손으로 쓰는 편이 낫습니다.
③ 벌거벗은 타입 파라미터의 분배 법칙(특히 boolean)과 재귀 깊이·컴파일 성능은 대표적인 함정이므로, 튜플 감싸기와 타입 테스트로 방어하시길 권합니다.
