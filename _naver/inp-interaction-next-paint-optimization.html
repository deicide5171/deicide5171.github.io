INP(Interaction to Next Paint) — 새로운 Core Web Vitals 지표 최적화하기

프론트엔드

한 줄 요약 — INP는 입력 지연·처리 시간·표시 지연 세 구간의 합입니다. 메인 스레드 점유가 세 구간 모두에 영향을 주는 이유와 최적화법을 정리했습니다.

 

왜 지금 INP를 다시 봐야 하는가

FID(First Input Delay)는 사용자의 "첫 번째" 입력에 대한 지연시간만 측정했고, 실제로 화면이 갱신되는 시점까지는 포함하지 않았습니다. 페이지 초반 반응만 빨랐다면 이후 상호작용이 버벅여도 점수에 잡히지 않는 맹점이 있었습니다. INP는 페이지 생애주기 전체의 상호작용 응답성을 측정해 이 맹점을 해소합니다.

 

INP가 측정하는 세 구간

INP는 입력 지연, 처리 시간, 표시 지연 세 구간의 합으로 측정됩니다. 어느 구간이 병목인지에 따라 최적화 방향이 완전히 달라지므로, "INP가 나쁘다"는 결과만 보고 대응하면 엉뚱한 곳을 고치게 됩니다.

 

메인 스레드 점유가 세 구간 모두에 영향을 준다

실무에서 INP를 악화시키는 가장 흔한 원인은 메인 스레드가 장시간 다른 작업(Long Task)으로 점유돼 있는 것입니다. 상호작용과 무관한 곳에서 메인 스레드를 오래 점유하는 코드(대량 리스트 렌더링, 무거운 계산, 서드파티 스크립트)를 찾아 분산시키는 것이 핵심입니다.

구간 주요 원인 대응
입력 지연 메인 스레드가 Long Task로 점유 작업을 작은 단위로 쪼개기
처리 시간 핸들러 자체의 무거운 로직 불필요한 리렌더링 제거
표시 지연 큰 DOM 변경, 레이아웃 스래싱 DOM 변경 최소화

 

예제 — 긴 작업을 yield로 쪼개기
function processLargeList(items) {
  let i = 0;
  function chunk(deadline) {
    while (i < items.length && (deadline.timeRemaining() > 0 || i % 50 === 0)) {
      renderItem(items[i]);
      i++;
    }
    if (i < items.length) {
      if ('scheduler' in window && 'yield' in window.scheduler) {
        window.scheduler.yield().then(() => chunk({ timeRemaining: () => 5 }));
      } else {
        requestIdleCallback(chunk);
      }
    }
  }
  requestIdleCallback(chunk);
}

scheduler.yield()는 실행 중인 작업을 명시적으로 양보해 브라우저가 대기 중인 사용자 입력을 먼저 처리할 기회를 줍니다.

 

실무 포인트

Chrome DevTools의 Performance 패널에서 Interactions 트랙을 직접 확인하세요. INP 값만 보지 말고 어느 구간이 늘어났는지 트레이스로 확인해야 정확한 원인을 찾을 수 있습니다.

서드파티 스크립트의 실행 시점을 상호작용이 몰리는 구간과 분리하세요. 광고나 분석 스크립트가 초기 로드 직후 한꺼번에 실행되면 메인 스레드 점유로 INP가 크게 튈 수 있습니다.

주의 — React나 Vue 같은 프레임워크에서는 상태 업데이트 배치와 렌더링 범위를 좁히세요. 하나의 클릭으로 큰 트리 전체가 리렌더링되도록 설계하면 처리 시간 구간이 불필요하게 길어집니다.
