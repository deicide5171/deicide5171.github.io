커버링 인덱스와 Index-Only Scan으로 쿼리 성능 극대화하기

DB·데이터 모델링

한 줄 요약 — 조건절 인덱스가 있어도 SELECT 컬럼 때문에 테이블을 재접근하는 heap fetch가 병목이 됩니다. 커버링 인덱스와 Index-Only Scan의 동작 원리를 정리했습니다.

 

왜 지금 커버링 인덱스를 다시 봐야 하는가

조건절에 맞는 인덱스를 추가해도 기대만큼 빨라지지 않는 경우가 있습니다. 인덱스로 조건에 맞는 행 위치는 빠르게 찾았지만, SELECT 절 나머지 컬럼을 가져오기 위해 테이블 본체(heap)에 다시 접근하는 추가 I/O가 발생하고 있는 경우가 많습니다. 커버링 인덱스는 필요한 컬럼을 아예 인덱스에 포함시켜 이 재접근 자체를 없앱니다.

 

일반 인덱스와 커버링 인덱스의 차이

일반 B-tree 인덱스는 인덱스 컬럼과 행 위치 포인터만 담습니다. 커버링 인덱스는 조건절 컬럼뿐 아니라 SELECT 절에 필요한 컬럼까지 인덱스 안에 함께 저장해(PostgreSQL의 INCLUDE 절 등) 쿼리가 인덱스만 읽고도 완결되게 만듭니다.

 

Index-Only Scan이 성립하기 위한 추가 조건

PostgreSQL은 MVCC 구조상 인덱스만으로는 행의 가시성을 판단할 수 없어 원칙적으로 heap 확인이 필요합니다. Visibility Map이 해당 페이지가 모든 트랜잭션에 보인다는 것을 보장할 때만 heap 접근 없이 완결됩니다. VACUUM이 자주 안 돌면 커버링 인덱스를 만들어도 여전히 heap fetch가 섞일 수 있습니다.

항목 일반 인덱스 커버링 인덱스
SELECT 컬럼 조회 테이블 본체 재접근 인덱스에서 바로 획득
PostgreSQL 요건 해당 없음 Visibility Map 최신 필요

 

예제 — PostgreSQL INCLUDE 절로 커버링 인덱스 만들기
CREATE INDEX idx_orders_status_covering
ON orders (status)
INCLUDE (order_id, total, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, total, created_at
FROM orders
WHERE status = 'SHIPPED';

-- Index Only Scan using idx_orders_status_covering on orders
--   Index Cond: (status = 'SHIPPED')
--   Heap Fetches: 0   <- 이 값이 0이면 완전한 Index-Only Scan

INCLUDE 절 컬럼은 정렬 순서에 관여하지 않고 함께 저장만 되므로, 정렬 비용을 늘리지 않고 효율적으로 커버링을 구현할 수 있습니다.

 

실무 포인트

Heap Fetches 값을 반드시 확인하세요. Index Only Scan이라고 나와도 이 값이 0이 아니면 여전히 heap 접근이 발생하고 있다는 뜻이므로 autovacuum 설정을 점검해야 합니다.

모든 조회 컬럼을 무작정 인덱스에 포함시키지 마세요. 쓰기 시 유지보수해야 할 인덱스 크기가 늘어나므로 빈번하고 중요한 쿼리에만 선택적으로 적용해야 합니다.

주의 — 넓은 테이블(컬럼이 많거나 TEXT/JSON이 큰 경우) 커버링 인덱스 자체가 비대해질 수 있습니다. 인덱스 크기와 개선 효과를 함께 저울질해야 합니다.
