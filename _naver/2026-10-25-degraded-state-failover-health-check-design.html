헬스체크는 살아있는지만 본다 — Degraded 상태를 놓치는 페일오버 설계의 구멍

시스템 설계

한 줄 요약 — DB가 완전히 죽지는 않고 응답만 느려질 때 자동 페일오버가 트리거되지 않는 사고가 2026년에도 반복됐습니다. 살아있는지만 보는 liveness 헬스체크가 '응답은 하지만 너무 느린' degraded 상태를 구조적으로 못 잡는 이유와, 지연시간 기반 헬스체크·회로차단기로 이 구멍을 메우는 설계를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"DB가 응답은 하는데 너무 느려요. 근데 페일오버는 왜 안 일어나죠?" 장애 대응 중에 이 질문을 받아본 적이 있다면, 이미 흔한 함정을 밟은 것입니다. 2026년에도 여러 서비스의 공개 포스트모템에 같은 패턴이 반복됐습니다. 어느 인증 플랫폼은 세션 DB가 완전히 다운되지 않고 그저 느려졌을 뿐인데, 헬스체크가 "살아있음"으로 판정해 자동 장애조치가 끝내 트리거되지 않았다고 밝혔습니다. 문제는 설정 실수가 아니라, 가장 널리 쓰이는 liveness/readiness 헬스체크 모델 자체가 이런 상태를 구분하지 못하도록 설계돼 있다는 점입니다.

"서버가 죽으면 대기 서버로 넘겨주세요"라는 요구를 받으면 대부분 TCP 연결이나 HTTP 200 응답 여부로 "살아있다/죽었다"를 판정하는 헬스체크부터 만듭니다. 이 모델은 완전한 다운은 잘 잡아내지만, 실무에서 더 흔하고 더 위험한 것은 프로세스는 응답하지만 지연시간이 수십 배로 늘어난 degraded 상태입니다.

 

전체 시스템에서의 위치

로드밸런서나 오케스트레이터는 보통 헬스체크 신호 하나만 보고 라우팅 결정을 내립니다. 이 신호가 "응답했는가/안 했는가"라는 이진값이면, 그 뒤에 있는 DB·캐시·업스트림 서비스가 "응답은 하지만 5초씩 걸린다"는 상태에 있어도 트래픽은 계속 그쪽으로 흘러갑니다. 커넥션 풀은 느린 응답을 기다리는 연결로 가득 차고, 대기 중인 요청이 쌓이면서 연쇄적으로 전체 서비스가 느려집니다.

지연시간 기반 체크가 빠져 있으면, "응답은 하지만 느리다"는 상태가 liveness와 readiness 사이 사각지대에 그대로 남습니다.

 

선택의 트레이드오프
방식 잡아내는 장애 놓치는 장애
TCP/HTTP 200 liveness 완전 다운, 프로세스 크래시 degraded(느린 응답)
readiness(의존성 ping) 의존 서비스 완전 단절 의존 서비스가 느리기만 한 경우
지연시간 임계값 체크 degraded 상태 포함 순간 지연 스파이크 오탐 가능
회로차단기 느린 응답의 연쇄 전파 체크 주기 길면 반응 지연

 

판단 기준은 "이 시스템에서 degraded 상태가 발생할 수 있는가, 그리고 발생했을 때 비용이 얼마나 큰가"입니다. 세션·인증·결제처럼 느린 응답이 연쇄 장애로 번질 수 있는 핵심 경로라면, 지연시간 기반 체크와 회로차단기를 반드시 함께 둬야 합니다. 지연시간 체크는 상태를 "감지"하고, 회로차단기는 감지된 상태에서 트래픽을 실제로 "차단"합니다.

 

실제 프로젝트 진행 순서

1. 현재 헬스체크가 실제로 무엇을 보는지 코드로 직접 확인합니다.
2. 정상 응답 시간의 p50·p95·p99 기준선을 먼저 측정합니다.
3. 지연시간 임계값 체크를 readiness에 추가하고, 연속 N회 초과 시에만 전환하도록 완충을 둡니다.
4. 커넥션 풀에 상한과 획득 타임아웃을 명시적으로 설정합니다.
5. 완전 단절이 아니라 "응답은 하되 느리게" 만드는 장애 주입 테스트로 검증합니다.

 

예제 설정:

# readiness probe에 지연시간 기반 판정을 추가하는 예시
readinessProbe:
  httpGet:
    path: /health/ready
  periodSeconds: 5
  failureThreshold: 3   # 연속 3회 실패해야 unready로 전환

# /health/ready 핸들러 내부 로직
# - DB ping 응답 시간이 p99 기준선의 5배를 넘으면 실패 반환
# - 단순 연결 성공 여부가 아니라 "느림"도 실패로 간주

 

주의 — DB 자동 유지보수 작업이 쿼리 플랜을 갑자기 바꿔 응답 시간을 늘리는 경우, 이는 "다운"이 아니라 "degraded"로 나타나므로 지연시간 기반 체크가 아니면 아예 안 잡힙니다. 긴 실행 쿼리에 문장 타임아웃을 걸지 않으면 degraded 상태에서 요청이 계속 쌓이며 상황을 더 악화시킵니다. 오탐을 줄이려고 임계값을 너무 느슨하게 잡으면 degraded 상태를 또 놓치니, 반드시 기준선 측정 후 임계값을 정하세요.

 

정리

liveness/readiness 중심의 헬스체크는 완전 다운은 잘 잡지만, "응답은 하되 느린" degraded 상태는 구조적으로 놓칩니다. 핵심 경로에는 지연시간 기반 체크로 감지하고 회로차단기로 차단하는 두 단계가 함께 필요하며, 설계는 현재 체크 확인 → 기준선 측정 → 임계값 추가 → 커넥션 풀 상한 설정 → 장애 주입 검증 순서로 진행합니다.
