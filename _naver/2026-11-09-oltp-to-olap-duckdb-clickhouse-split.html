대시보드에 실시간 집계 지표를 보여주세요 — Postgres 하나로 버틸지, DuckDB·ClickHouse로 쪼갤지 판단하기

시스템 설계

한 줄 요약 — '대시보드에 실시간 집계 지표를 보여주세요'라는 요구는 서비스 DB에 집계 쿼리를 그대로 얹을지, 분석 전용 엔진을 따로 둘지 가르는 아키텍처 분기점입니다. 2026년 업계가 정리한 DuckDB(임베디드)와 ClickHouse(분산 서빙)의 역할 차이를 기준으로, 언제 분리하고 무엇부터 도입할지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"운영 대시보드에 실시간으로 집계된 지표를 보여주세요. 매출 추이, 사용자별 활동량, 최근 한 시간 에러율 같은 거요." 서비스 초기에는 이 요구가 그냥 서비스 DB에 GROUP BY 쿼리 하나 더 얹는 일처럼 보입니다. 실제로도 데이터가 적을 때는 그렇습니다. 문제는 이 요구가 계속 늘어난다는 데 있습니다. 지표 종류가 늘고, 조회 기간이 길어지고, 동시에 보는 사람이 많아지면 같은 Postgres 인스턴스에서 OLTP 트랜잭션과 OLAP 집계 쿼리가 CPU·I/O를 다투기 시작합니다. 결제 트랜잭션이 느려지는 원인을 추적해 보면 대시보드의 무거운 집계 쿼리가 범인인 경우가 드물지 않습니다.

2026년 들어 이 문제에 대한 업계의 답은 "ClickHouse든 DuckDB든 빨리 도입하라"가 아니라 "이 둘은 경쟁 관계가 아니라 역할이 다른 도구"라는 쪽으로 정리됐습니다. 빌더가 답해야 할 질문은 "둘 중 뭐가 더 빠른가"가 아니라 "우리 워크로드가 임베디드로 충분한가, 아니면 다수 사용자가 동시에 쓰는 서빙 계층이 필요한가"입니다.

 

OLTP가 집계에 약한 이유는 저장 구조 때문이다

Postgres 같은 행 지향 OLTP DB는 한 행의 모든 컬럼을 디스크에 나란히 저장합니다. "주문 하나의 전체 정보를 가져오라"는 쿼리에는 이 구조가 유리합니다. 하지만 "최근 한 달간 결제 금액의 평균을 구하라"처럼 컬럼 하나만 필요한 집계 쿼리에서는, 필요 없는 컬럼까지 모두 읽어 와야 합니다. 행 수가 수백만을 넘어가는 순간부터 이 비효율이 체감되는 지연으로 나타납니다. 컬럼 지향 저장 방식을 쓰는 OLAP 엔진은 필요한 컬럼만 읽고 압축률도 높아 같은 집계 쿼리를 훨씬 적은 I/O로 끝냅니다.

 

DuckDB와 ClickHouse는 "같은 문제의 다른 규모판"이 아니다

흔히 생기는 오해가 "DuckDB는 작은 ClickHouse"라는 생각입니다. 실제로는 배포 모델 자체가 다릅니다. DuckDB는 별도 서버 없이 애플리케이션 프로세스 안에 임베디드로 실행되는 분석 엔진입니다. 데이터 과학 노트북, 로컬 분석 스크립트, 서버리스 함수 안에서 그때그때 분석 쿼리를 돌리는 용도에 맞습니다. 네트워크 왕복이 없어 중소 규모 데이터에서는 콜드 쿼리 성능이 ClickHouse와 대등하거나 더 나을 수 있습니다. 반면 ClickHouse는 여러 클라이언트가 동시에 접속해 서브초 단위 응답을 받아야 하는 서빙 워크로드, 즉 수십 명이 동시에 보는 실시간 대시보드나 로그·관측성 플랫폼에 맞춰 설계됐습니다. 수십억 행 규모의 분산 환경에서 강점이 있는 대신 클러스터 운영이라는 대가가 따릅니다.

 

전체 시스템에서의 위치

핵심은 대시보드가 서비스 DB를 직접 조회하지 않는다는 경계선입니다. 서비스 DB는 CDC나 주기적 배치로 분석 계층에 데이터를 밀어 넣는 역할만 하고, 대시보드·리포트가 던지는 무거운 집계 쿼리는 전부 분석 계층이 받습니다. 이 경계가 없으면 분석 쿼리 하나가 서비스 트랜잭션 성능을 갉아먹는 구조가 영구히 반복됩니다.

 

선택 기준
기준Postgres에서 버팀DuckDB 도입ClickHouse 도입
동시 조회자 수적음적음~중간많음
데이터 규모수백만 행 이하수천만~수억 행수십억 행 이상
운영 부담가장 낮음낮음높음

표에서 가장 중요한 축은 "동시 조회자 수"입니다. 데이터 규모만 보고 ClickHouse부터 도입하는 팀이 많은데, 실제로 병목이 되는 건 대개 분석 쿼리가 몰리는 시점의 동시성이지 데이터 총량이 아닙니다. 내부 임원 몇 명만 보는 주간 리포트라면 데이터가 수억 행이어도 DuckDB로 배치 처리하는 편이 운영 부담 면에서 훨씬 이득입니다.

 

실제 진행 순서

가장 먼저 할 일은 분리를 결정하기 전에 지금 느려지는 게 트랜잭션인지 집계 쿼리인지를 분리해서 측정하는 것입니다. EXPLAIN ANALYZE로 대시보드 쿼리의 실행 계획과 소요 시간을 확인하고, 같은 시간대 핵심 트랜잭션의 지연 분포가 실제로 영향을 받는지 먼저 봅니다. 분리하기로 했다면 두 번째로 막히는 지점은 거의 항상 동기화 지연 허용 범위입니다. "실시간"이라는 말을 그대로 받아들이지 말고, 몇 초·몇 분까지의 지연이 허용되는지 먼저 합의해야 합니다.

-- DuckDB: Postgres에서 뽑은 Parquet 스냅샷을 그 자리에서 바로 집계
SELECT
  date_trunc('hour', ordered_at) AS hour,
  sum(amount) AS revenue
FROM read_parquet('s3://exports/orders/*.parquet')
WHERE ordered_at >= now() - interval '7 days'
GROUP BY 1
ORDER BY 1;

위 쿼리처럼 서버 구축 없이 object storage의 Parquet 파일을 그대로 읽어 집계하는 것이 DuckDB 도입의 전형적인 첫걸음입니다. 이 수준에서 성능과 운영 부담이 이미 만족스럽다면, 굳이 ClickHouse 클러스터를 세울 이유가 없습니다. 동시 조회자가 늘어나고 서브초 응답이 요구되는 시점이 와서야 비로소 ClickHouse 같은 서빙 전용 클러스터 투자가 정당화됩니다.

 

주의 — "실시간"의 허용 지연 범위를 합의하지 않은 채 CDC 파이프라인부터 구축하면, 나중에 "왜 대시보드 숫자가 방금 들어온 주문을 반영 못 하냐"는 문의에 매번 설명하게 됩니다.

 

정리

OLTP가 집계에 약한 건 행 지향 저장 구조 때문이고, 컬럼 지향 OLAP 엔진이 이 문제를 구조적으로 해결합니다. DuckDB는 서버 없는 임베디드 분석 도구이고 ClickHouse는 다수 동시 사용자를 위한 서빙 클러스터입니다. 선택 기준은 데이터량보다 동시 조회자 수이고, 분리 전에 트랜잭션과 집계 쿼리 지연을 분리 측정하는 것이 첫걸음입니다.
