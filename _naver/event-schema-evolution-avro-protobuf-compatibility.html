이벤트 스키마 진화 — Avro/Protobuf로 프로듀서·컨슈머를 깨지 않고 구조 바꾸기

아키텍처·시스템 설계

한 줄 요약 — 이벤트 스트림은 배포 시점을 맞출 수 없으므로, 하위·상위 호환성 규칙과 스키마 레지스트리 검증으로 파싱 실패를 사전에 막아야 합니다.

 

왜 위험한가

이벤트 기반 아키텍처는 프로듀서와 컨슈머가 서로를 몰라도 되는 느슨한 결합이 매력이지만, 이 느슨함은 스키마가 바뀌는 순간 위험해집니다. 프로듀서가 배포한 변경을 여러 컨슈머가 각자 다른 시점에 마주치므로, 배포 순서를 완벽히 맞추는 것은 현실적으로 불가능합니다.

 

하위 호환성과 상위 호환성

하위 호환성은 새 스키마 데이터를 옛 컨슈머가 읽을 수 있는 것("프로듀서 먼저 배포" 가능), 상위 호환성은 옛 데이터를 새 컨슈머가 읽을 수 있는 것("컨슈머 먼저 배포" 가능)입니다. 둘 다 만족하면 배포 순서 제약이 아예 없습니다.

안전한 변경과 위험한 변경

Avro에서 하위 호환을 지키려면 새 필드에 반드시 기본값을 지정해야 합니다. Protobuf는 필드를 추가하는 것은 항상 안전하지만, 기존 필드 번호를 재사용하면 완전히 다른 의미의 데이터가 같은 번호로 해석되어 조용한 데이터 손상으로 이어집니다.

변경 유형 Avro Protobuf
필드 추가(기본값 있음) 안전 안전
필드 번호/이름 재사용 이름 재사용 위험 번호 재사용 치명적

 

스키마 레지스트리 호환성 검증 예제
{
  "compatibility": "BACKWARD"
}

{
  "type": "record",
  "name": "OrderEvent",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "currency", "type": "string", "default": "KRW"}
  ]
}

스키마 레지스트리는 새 스키마 등록 시 지정된 호환성 모드를 기준으로 자동 비교해, 규칙을 위반하면 등록 자체를 거부합니다.

 

실무 포인트

호환성 모드를 팀 차원에서 명시적으로 결정하세요. 배포 순서를 아예 통제할 수 없다면 FULL 모드가 필요합니다.

Enum 값 추가도 생각보다 위험합니다. 옛 컨슈머가 새 enum 값을 만나면 예외를 던질 수 있으므로 "알 수 없는 값" 케이스를 명시적으로 처리해야 합니다.

주의 — 스키마 파일을 애플리케이션 코드와 별도로 관리하면 리뷰 프로세스에서 누락되기 쉬우므로, 스키마 저장소를 CI 파이프라인에 통합해 PR 단계에서 검증하는 것이 안전합니다.
