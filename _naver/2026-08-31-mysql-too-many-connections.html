MySQL Too many connections 에러 원인과 해결

2026. 8. 31. · 데이터베이스

한 줄 요약 — max_connections를 올리기 전에 PROCESSLIST의 Sleep 연결 비율부터 확인해야 커넥션 누수를 진짜로 해결할 수 있습니다.

 

왜 한도를 올리는 것만으로는 안 되는가

Too many connections 에러를 처음 만나면 대부분 max_connections 값을 늘려서 대응합니다. 하지만 이는 임시방편입니다. 실제 동시 접속자가 늘어서가 아니라 애플리케이션이 커넥션을 제대로 반납하지 않아서 발생하는 경우가 훨씬 많기 때문입니다.

 

원인을 좁히는 순서
확인 항목 명령 의미
현재 연결 수 SHOW STATUS LIKE 'Threads_connected' 실제로 한도에 근접했는지
연결 출처 SHOW PROCESSLIST 특정 서버가 몰아 연결하는지
Sleep 비율 PROCESSLIST의 Command 컬럼 커넥션 반납 누락 의심

SHOW PROCESSLIST에서 Command: Sleep인 연결이 대다수라면, 쿼리 실행 중이 아니라 커넥션 풀에 반납되지 않고 방치된 연결일 가능성이 높습니다.

 

커넥션 풀 크기 계산 공식
max_connections(DB) >= 인스턴스 수 × 풀 최대 크기 + 여유분

예: 인스턴스 5대 × 풀 크기 20 = 100
    관리 작업 여유분 20을 더해 최소 120 이상으로 설정

오토스케일링 환경이라면 최대 스케일 시점의 인스턴스 수를 기준으로 계산해야 스케일 아웃 도중 커넥션 고갈을 막을 수 있습니다.

 

실무 포인트

애플리케이션 커넥션 풀에 타임아웃을 반드시 설정하세요. 커넥션을 반납하지 않는 코드가 있으면 결국 풀이 고갈됩니다.

다수의 애플리케이션 인스턴스가 DB에 직접 연결하는 대신 ProxySQL을 거치면 DB 쪽 연결 수를 훨씬 적게 유지할 수 있습니다.

주의 — 배치 작업이나 관리 스크립트가 커넥션을 안 닫고 종료되는 경우도 흔한 원인입니다. cron 스크립트는 커넥션 정리를 명시적으로 확인하세요.
