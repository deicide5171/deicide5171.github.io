다단계 캐싱 아키텍처 — Write-Through와 Write-Behind 전략 비교

아키텍처·시스템 설계

한 줄 요약 — 로컬 캐시-분산 캐시-DB로 이어지는 다단계 캐싱에서 Write-Through와 Write-Behind의 일관성·지연시간 트레이드오프를 정리했습니다.

 

왜 지금 다단계 캐싱을 다시 봐야 하는가

읽기 트래픽이 늘어나면 Redis 같은 분산 캐시를 도입합니다. 하지만 트래픽이 임계치를 넘으면 분산 캐시 자체에 대한 네트워크 왕복이 병목이 됩니다. 이때 애플리케이션 프로세스 안의 로컬 캐시를 앞단에 추가하는 다단계 캐싱을 도입하면 대부분의 요청이 로컬 캐시에서 끝나 지연시간이 극적으로 줄어듭니다.

문제는 계층이 늘어날수록 쓰기가 발생했을 때 각 계층을 언제 갱신할 것인가라는 일관성 문제가 복잡해진다는 점입니다.

 

Write-Through: 캐시와 DB를 동기적으로 함께 쓴다

Write-Through는 쓰기 요청 시 캐시와 DB를 동기적으로 갱신하고 두 곳 모두 성공한 뒤 응답합니다. 캐시와 DB가 항상 일치한다는 강한 보장을 주지만, 쓰기 경로에 캐시 쓰기 지연이 그대로 더해집니다.

 

Write-Behind: 캐시만 먼저 쓰고 DB는 비동기로 반영한다

Write-Behind는 캐시만 즉시 갱신하고 DB 반영은 백그라운드로 나중에 처리합니다. 쓰기 지연시간이 캐시 쓰기 수준으로 짧아지지만, 캐시에는 반영됐지만 DB에는 아직 반영되지 않은 구간에 캐시 노드가 죽으면 데이터가 유실될 수 있습니다.

전략 쓰기 지연시간 유실 위험
Write-Through 캐시+DB 쓰기 시간 합산 낮음
Write-Behind 캐시 쓰기 시간만 있음 (캐시 장애 시)
Write-Around DB만 쓰고 캐시 무효화 낮음

 

예제 — Write-Behind 큐 기반 구현
@Service
public class ProductCacheService {

    private final BlockingQueue<WriteTask> writeQueue = new LinkedBlockingQueue<>();

    public void updateProduct(Long id, Product product) {
        redisTemplate.opsForValue().set("product:" + id, product);
        writeQueue.offer(new WriteTask(id, product));
    }

    @Scheduled(fixedDelay = 500)
    public void flushToDatabase() {
        List<WriteTask> batch = new ArrayList<>();
        writeQueue.drainTo(batch, 100);
        if (!batch.isEmpty()) {
            productRepository.batchUpdate(batch);
        }
    }
}

 

실무 포인트

금융·결제처럼 데이터 유실이 허용되지 않는 도메인에는 Write-Behind를 쓰지 마세요. 이런 경우 Write-Through가 유일한 선택지에 가깝습니다.

Write-Behind를 쓴다면 큐 자체의 내구성을 확보하세요. 인메모리 큐만 쓰면 프로세스가 죽는 순간 쓰기가 통째로 사라지므로 Kafka 같은 내구성 있는 큐를 두는 것이 안전합니다.

주의 — 다단계 캐싱에서는 각 계층의 TTL을 다르게 가져가세요. 로컬 캐시 TTL을 분산 캐시보다 짧게 두면 분산 캐시 갱신 반영 지연을 최소화할 수 있습니다.
