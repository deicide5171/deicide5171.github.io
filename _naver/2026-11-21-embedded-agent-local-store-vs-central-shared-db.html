"에이전트마다 자기 메모리를 들고 다니게 해주세요, 근데 가끔은 여러 에이전트가 같은 걸 알아야 해요" — Neo4j Relate로 보는 임베디드 로컬 저장소 vs 중앙 공유 DB

시스템 설계

한 줄 요약 — 에이전트 상태를 어디에 둘지는 서버를 하나 더 둘지 말지의 문제가 아니라, 무엇이 에이전트 고유의 사실이고 무엇이 여러 에이전트가 합의해야 하는 공유 진실인지 먼저 나누는 문제입니다. Neo4j Relate(인프로세스 임베디드 그래프 DB)를 기준으로 로컬 저장소와 중앙 공유 DB를 가르는 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"에이전트를 여러 개 띄워서 각자 맡은 영역을 처리하게 해주세요, 근데 매번 중앙 DB에 왕복하느라 느려지면 안 돼요"라는 요구를 받으면, 먼저 떠오르는 해법은 "상태를 에이전트 프로세스 안에 들고 있게 하자"입니다. 네트워크 왕복이 없으니 빠르고, 서버 운영 부담도 없습니다. 그런데 곧바로 다음 요구가 따라붙습니다 — "근데 에이전트 A가 알아낸 걸 에이전트 B도 알아야 하는 경우가 있어요." 이 순간 로컬 상태만으로는 풀리지 않는 문제가 생깁니다. 상태를 어디에 둘지는 무엇이 에이전트 고유의 사실이고 무엇이 여러 에이전트가 합의해야 하는 공유 진실(shared truth)인지를 먼저 나누는 설계 문제입니다.

2026년 11월 11일 Neo4j가 공개한 Relate는 이 구조를 제품으로 구체화한 사례입니다. Rust로 작성된 오픈소스 인프로세스 임베디드 그래프 DB로, 서버를 따로 띄울 필요 없이 Python·JavaScript·Rust·Java 등에서 라이브러리처럼 바로 붙여 씁니다. 인메모리 엔진에 내구성이 필요하면 WAL을 옵션으로 켤 수 있고, MCP 서버로 에이전트 하네스가 바로 붙을 수 있게 했습니다. 동시에 Bolt·HTTP Query API를 노출해 서브그래프를 Neo4j Aura 같은 중앙 서비스와 주고받을 수 있다는 점이 핵심입니다 — 로컬 임베디드와 중앙 공유를 완전히 분리된 세계가 아니라, 필요할 때 연결할 수 있는 두 계층으로 설계했습니다.

 

전체 시스템에서의 위치

에이전트 로컬 저장소는 에이전트 프로세스 안, 즉 "이 에이전트가 이번 작업에서만 필요한 상태"가 사는 자리입니다. 작업 중 쌓이는 중간 추론, 이번 세션에서만 유효한 캐시가 여기 머뭅니다. 반대로 중앙 공유 DB는 "여러 에이전트, 또는 여러 세션에 걸쳐 같은 값을 봐야 하는 사실"이 사는 자리입니다. 두 계층 사이에는 반드시 동기화 지점이 있어야 합니다. 이 지점이 없으면 로컬 저장소는 그냥 서로 다른 세상을 사는 여러 개의 섬이 되고, 에이전트 B는 에이전트 A가 이미 알아낸 사실을 다시 처음부터 알아내야 합니다.

 

선택의 트레이드오프
방식지연·비용일관성 보장적합한 상황
임베디드 로컬 저장소만매우 낮음없음 — 각자 진실에이전트가 독립 영역을 맡고 결과만 나중에 합치는 경우
중앙 공유 DB만네트워크 왕복만큼 높음강함 — 단일 진실 소스여러 에이전트가 실시간 협업·경쟁해야 하는 경우
로컬 우선 + 주기적 동기화평상시 낮음최종 일관성공유가 결과 단계에만 필요한 경우
로컬 캐시 + 중앙 쓰기 강제읽기 빠름, 쓰기 느림쓰기 기준 강함쓰기 충돌 비용이 크고 읽기는 약간 오래돼도 되는 경우

 

네 가지 중 무엇을 고르든 진짜 어려운 부분은 기술 선택이 아니라 "병합 정책"입니다. 로컬에서 각자 돌던 에이전트 A와 B가 같은 대상에 대해 서로 다른 결론을 들고 중앙으로 올라오면, 누구 결론이 이기는지를 미리 정해 두지 않으면 병합 시점에 조용히 데이터가 덮어써집니다. 타임스탬프 기준 최신 우선, 명시적 우선순위, 충돌 시 사람에게 넘기는 방식 중 하나를 데이터 종류별로 미리 정해야 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 코드를 짜는 것이 아니라, 에이전트가 다루는 데이터를 "이 에이전트만 알면 되는 것"과 "다른 에이전트도 알아야 하는 것" 두 칸으로 분류하는 것입니다. 이 분류 없이 로컬이든 중앙이든 먼저 정하면, 나중에 공유가 필요해진 데이터를 옮기는 마이그레이션 비용을 떠안습니다.

local_only:
  - 현재 작업의 중간 추론 체인
  - 이번 세션에서만 쓰는 캐시된 조회 결과
shared_truth:
  - 작업 배정 상태 (어느 에이전트가 무엇을 맡았는가)
  - 이미 사람이 승인한 결론
sync_policy:
  shared_truth: "쓰기는 항상 중앙 DB에, 로컬은 읽기 캐시로만"
  local_only: "세션 종료 시 폐기, 영속 불필요"

둘째로, 공유가 필요한 데이터부터 먼저 중앙 DB에 쓰기를 강제하고, 로컬에는 그 값의 캐시만 두는 가장 보수적인 구조로 시작해야 합니다. 셋째로, 로컬 저장소의 내구성 여부를 데이터 종류별로 명시하고, 프로세스가 죽는 시나리오를 실제로 재현해 검증해야 합니다. 마지막으로, 병합 정책을 실제 충돌 시나리오로 미리 테스트한 뒤에야 로컬 우선 구조로 확장해야 합니다.

 

주의 — 내구성(WAL)을 꺼두면 더 빠르지만 프로세스가 죽는 순간 로컬 상태가 통째로 사라집니다. 그 상태가 다시 만들어도 되는 캐시인지, 잃으면 곤란한 진행 상황인지 먼저 구분해야 합니다.
