헥사고날 아키텍처(포트와 어댑터)로 도메인 로직을 프레임워크에서 분리하기

아키텍처·시스템 설계

한 줄 요약 — 도메인이 정의한 포트(인터페이스)를 어댑터가 구현하게 해 의존성 방향을 뒤집는 헥사고날 아키텍처를 정리했습니다.

 

왜 지금 헥사고날 아키텍처를 다시 봐야 하는가

레이어드 아키텍처로 시작한 프로젝트는 시간이 지날수록 서비스 클래스에 프레임워크 관심사(어노테이션, ORM 엔티티, 벤더 SDK 타입)가 스며드는 경향이 있습니다. 이렇게 되면 단위 테스트가 어려워지고, PG사나 DB 교체가 도메인 코드 전체를 건드리는 사태로 번집니다. 헥사고날 아키텍처는 의존성 방향을 강제로 뒤집어 이 문제를 해결합니다.

 

포트: 도메인이 원하는 인터페이스를 도메인이 직접 정의한다

도메인은 외부와 소통하는 방식을 포트(인터페이스)로 정의하고 직접 소유합니다. 인터페이스는 인프라의 편의가 아니라 도메인의 필요로 설계됩니다. 그 결과 의존성 방향이 "도메인 → 기술"이 아니라 "기술(어댑터) → 도메인이 정의한 포트"로 뒤집힙니다.

 

어댑터: 포트를 실제 기술로 구현하는 교체 가능한 껍데기

인바운드 어댑터(REST 컨트롤러 등)는 외부 요청을 도메인 호출로 변환하고, 아웃바운드 어댑터(DB 리포지토리, PG API 클라이언트)는 도메인 요청을 실제 기술로 실행합니다. 도메인 코드는 어댑터의 존재 자체를 모릅니다. PG사나 DB 교체는 새 어댑터 구현체 하나만 추가하면 됩니다.

구성 요소 역할
도메인 순수 비즈니스 규칙
포트 도메인이 정의한 계약
아웃바운드 어댑터 실제 기술 호출 구현

 

예제 — 포트 정의와 두 개의 아웃바운드 어댑터
public interface PaymentGateway {
    PaymentResult charge(OrderId orderId, Money amount);
}

public class OrderService {
    private final PaymentGateway paymentGateway;

    public void completeOrder(Order order) {
        PaymentResult result = paymentGateway.charge(order.getId(), order.getTotal());
    }
}

public class TossPaymentAdapter implements PaymentGateway {
    public PaymentResult charge(OrderId orderId, Money amount) {
        var tossResponse = tossClient.requestPayment(orderId.value(), amount.toWon());
        return PaymentResult.from(tossResponse);
    }
}

public class StubPaymentAdapter implements PaymentGateway {
    public PaymentResult charge(OrderId orderId, Money amount) {
        return PaymentResult.success();
    }
}

OrderService는 어떤 어댑터를 쓰든 코드 변경 없이 동작해, 실제 PG사 연동 없이도 도메인 로직만 빠르게 단위 테스트할 수 있습니다.

 

실무 포인트

모든 계층에 헥사고날을 도그마처럼 적용하지 마세요. 단순 CRUD 화면까지 나누면 오히려 과잉 설계가 됩니다. 핵심 도메인에 우선 적용하세요.

포트 인터페이스의 이름은 인프라 용어가 아니라 도메인 용어로 지으세요. JpaOrderRepository 같은 이름이 포트에 등장하면 이미 의존 방향이 뒤집힌 것입니다.

주의 — 아웃바운드 어댑터의 예외를 도메인 예외로 반드시 변환하세요. DB나 PG사 SDK의 구체적 예외가 도메인까지 그대로 전파되면 도메인이 다시 특정 기술에 종속됩니다.
