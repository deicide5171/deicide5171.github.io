@WebMvcTest vs @DataJpaTest vs @SpringBootTest — 스프링 테스트 슬라이스 제대로 고르기

백엔드

한 줄 요약 — 모든 테스트에 @SpringBootTest를 습관적으로 붙이면 테스트 스위트가 느려집니다. 목적에 맞는 테스트 슬라이스로 로딩 범위를 줄이세요.

 

왜 테스트가 갈수록 느려지나

컨트롤러 하나의 URL 매핑만 확인하고 싶은 테스트에서까지 DB 커넥션, 시큐리티 필터, 메시지 브로커 연결 같은 애플리케이션 전체 빈을 매번 로딩하면 명백한 낭비입니다. 스프링은 목적별로 필요한 빈만 로딩하는 테스트 슬라이스 애노테이션을 제공합니다.

 

 

@WebMvcTest — 컨트롤러 레이어만

MVC 관련 빈만 로딩하고 Service, Repository 빈은 로딩하지 않습니다. 컨트롤러가 요청을 올바르게 매핑하고 상태 코드와 응답 형식을 올바르게 반환하는지만 검증할 때 적합합니다.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mockMvc;
    @MockBean OrderService orderService;

    @Test
    void 주문_조회_성공() throws Exception {
        given(orderService.findById(1L))
            .willReturn(new OrderResponse(1L, "PAID"));
        mockMvc.perform(get("/orders/1"))
            .andExpect(status().isOk());
    }
}
@DataJpaTest — 리포지토리 레이어만

JPA 관련 빈만 로딩하고 기본적으로 인메모리 DB(H2 등)를 자동 구성합니다. 각 테스트는 트랜잭션으로 감싸져 종료 시 롤백되어 테스트 간 데이터 오염이 없습니다.

주의 — 인메모리 DB(H2)와 실제 운영 DB(MySQL, PostgreSQL) 사이에 SQL 문법이나 제약조건 동작 차이가 있을 수 있습니다. 이 차이가 우려된다면 Testcontainers로 실제 DB를 띄워 검증하는 편이 안전합니다.

 

실무 포인트

단위 테스트를 가장 많이, 슬라이스 테스트를 중간 정도, @SpringBootTest 통합 테스트는 핵심 시나리오 몇 개로 최소화하는 구성이 빠르고 안정적인 테스트 스위트를 만듭니다. 시큐리티가 적용된 프로젝트라면 @WebMvcTest에도 필터가 함께 로딩되므로 @WithMockUser로 인증 컨텍스트를 채워줘야 합니다.
