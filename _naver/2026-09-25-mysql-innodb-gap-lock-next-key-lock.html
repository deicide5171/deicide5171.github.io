MySQL InnoDB Gap Lock과 Next-Key Lock — Phantom Read를 막는 락 범위 확장의 내부 동작

DB·데이터 모델링

한 줄 요약 — InnoDB가 REPEATABLE READ에서 존재하지 않는 값의 범위까지 잠그는 Gap Lock과 Next-Key Lock의 내부 동작을 정리했습니다.

 

왜 지금 Gap Lock을 다시 봐야 하는가

REPEATABLE READ로 운영하다 보면, 존재하지 않는 값 범위를 조회했을 뿐인데 다른 트랜잭션의 INSERT가 락 대기에 걸려버리는 현상을 마주칠 수 있습니다. InnoDB가 표준 REPEATABLE READ보다 한 단계 더 나아가, 실제 존재하는 행뿐 아니라 행과 행 사이의 간격까지 잠그기 때문입니다.

 

Record Lock, Gap Lock, Next-Key Lock의 세 층위

Record Lock은 실제 존재하는 행에 거는 전통적인 락입니다. Gap Lock은 인덱스 레코드 사이의 간격에 걸어 그 간격으로의 새 INSERT를 막습니다. Next-Key Lock은 Record Lock과 그 앞쪽 Gap을 합친 것으로, 범위 조건 쿼리는 실제 행에 Next-Key Lock을, 범위의 시작과 끝에 Gap Lock을 추가로 걸어 범위 전체를 봉쇄합니다.

 

왜 REPEATABLE READ에서만 문제가 되는가

MVCC 스냅샷만으로는 SELECT FOR UPDATE 같은 쓰기 의도 쿼리에서 Phantom Read를 막을 수 없습니다. InnoDB는 REPEATABLE READ에서 이를 Gap Lock으로 해결합니다. READ COMMITTED로 낮추면 Gap Lock이 사실상 비활성화되어 동시성은 높아지지만, Phantom Read를 허용하게 되는 트레이드오프가 생깁니다.

락 종류 잠그는 대상 READ COMMITTED에서
Record Lock 실제 존재하는 행 그대로 동작
Gap Lock 행 사이의 간격 사실상 비활성화
Next-Key Lock Record Lock + 앞쪽 Gap Record Lock만 남음

 

Gap Lock으로 인한 INSERT 대기 재현
-- 세션 A (REPEATABLE READ)
BEGIN;
SELECT * FROM orders WHERE amount BETWEEN 100 AND 200 FOR UPDATE;

-- 세션 B (동시 실행)
BEGIN;
INSERT INTO orders (amount) VALUES (150); -- 대기 걸림!
-- 세션 A가 COMMIT/ROLLBACK 할 때까지 블로킹

-- 잠금 대기 현황 확인 (MySQL 8.0+)
SELECT * FROM performance_schema.data_lock_waits;

 

실무 포인트

인덱스가 없는 컬럼에 조건을 걸면 Gap Lock 범위가 예상보다 넓어질 수 있습니다. 인덱스가 없으면 풀스캔에 가까운 범위 전체에 락이 걸려 동시성이 급격히 나빠지므로, 락 경합이 심한 쿼리는 인덱스부터 확인해야 합니다.

AUTO-INCREMENT 컬럼에 대량 INSERT가 몰리는 테이블은 데드락 위험이 커집니다. 배치 크기를 줄이거나 INSERT 순서를 통일하면 도움이 됩니다.

주의 — READ COMMITTED로 낮추는 것이 만능 해법은 아닙니다. Gap Lock 경합은 사라지지만 Phantom Read를 허용하게 되므로, 애플리케이션 로직이 반복 조회 일관성에 의존하고 있지 않은지 먼저 점검해야 합니다.
