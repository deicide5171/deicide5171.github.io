Karpenter 노드 프로비저닝 내부 동작 — Cluster Autoscaler와 다른 즉시 빈패킹 방식

인프라

한 줄 요약 — 노드 그룹 없이 파드의 실제 요구사항을 보고 그때그때 최적의 인스턴스를 계산·프로비저닝하는 Karpenter의 내부 동작을 정리했습니다.

 

왜 지금 노드 오토스케일러를 다시 봐야 하는가

Cluster Autoscaler는 사전에 정의된 노드 그룹의 최소·최대 대수 범위 안에서만 스케일을 조절합니다. 파드가 실제로 필요한 CPU·메모리 조합이 노드 그룹의 고정 인스턴스 타입과 맞지 않으면 자원 낭비가 발생합니다. Karpenter는 "노드 그룹" 개념 자체를 없애고, 스케줄링 안 된 파드의 요구사항을 보고 그때그때 최적의 인스턴스를 직접 만듭니다.

 

노드 그룹 없이 즉시 프로비저닝

Karpenter는 Pending 파드가 쌓이면 CPU·메모리 요청량, nodeSelector, 어피니티 조건을 종합해 "이 조건을 만족하는 가장 저렴하고 적합한 인스턴스 조합"을 클라우드 API에서 실시간으로 계산합니다. NodePool에는 넓은 제약만 선언해두면, Karpenter가 스팟 가격과 가용 용량까지 고려해 구체적인 인스턴스 타입을 선택합니다. "미리 정해둔 메뉴 중 고르기"가 아니라 "필요한 사양을 그때그때 맞춤 주문"하는 것에 가깝습니다.

항목 Cluster Autoscaler Karpenter
노드 선택 단위 사전 정의된 노드 그룹 실시간 계산된 인스턴스
자원 최적화 범위 노드 그룹 경계 내 클러스터 전체

 

빈패킹 최적화와 노드 통합(Consolidation)

Karpenter는 이미 떠 있는 노드들의 활용률이 떨어지면 재배치를 시도하는 Consolidation 기능도 핵심입니다. 파드들을 더 적은 수의 노드로 옮겨 담을 수 있는지 계산하고, 가능하면 재스케줄링한 뒤 남는 노드를 종료합니다. Cluster Autoscaler에도 비슷한 로직이 있지만, Karpenter는 노드 그룹 경계에 얽매이지 않고 클러스터 전체를 대상으로 재배치를 고려할 수 있습니다.

스팟·온디맨드 혼합 NodePool 예제
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s

capacity-type 조건에 spot과 on-demand를 함께 허용하면, Karpenter가 스팟 가용성과 톨러레이션 설정을 보고 그때그때 어느 쪽을 쓸지 판단합니다.

 

실무 포인트

consolidateAfter 값이 너무 짧으면 잦은 파드 재배치로 불필요한 재시작이 늘어납니다. 워크로드의 시작 시간과 트래픽 패턴에 맞춰 여유를 두는 것이 안전합니다.

PodDisruptionBudget을 반드시 함께 설정해야 합니다. Consolidation은 파드를 옮기기 위해 축출을 수행하므로, PDB 없이는 가용성이 중요한 서비스가 순간적으로 다운될 수 있습니다.

주의 — 인스턴스 타입 제약을 지나치게 좁히면 Karpenter의 장점이 사라집니다. 최소한의 제약(아키텍처, 세대 등)만 걸고 나머지는 Karpenter의 선택에 맡기는 것이 비용 효율적입니다.
