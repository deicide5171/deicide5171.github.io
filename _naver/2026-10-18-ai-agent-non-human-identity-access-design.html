에이전트는 사람도 서비스 계정도 아니다 — Non-Human Identity로 접근 권한 설계하기

AI

한 줄 요약 — "에이전트가 사용자 대신 메일도 보내고 PR도 올리고 문서도 정리하게 해주세요"라는 요구를 사용자 OAuth 토큰을 그대로 쥐여주는 식으로 풀면, 프롬프트 인젝션 한 번에 그 사용자의 모든 연동 서비스 권한이 함께 털립니다. 에이전트를 사람도 전통적 서비스 계정도 아닌 별도의 Non-Human Identity로 다루는 설계 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"에이전트가 사용자 대신 메일도 보내고, GitHub PR도 올리고, Notion 문서도 정리하게 해주세요." 연동 서비스를 하나씩 늘려가는 팀이라면 피하기 어려운 요구입니다. 가장 빠른 구현은 사용자가 로그인하며 받은 OAuth 토큰을 그대로 에이전트 실행 컨텍스트에 넘기는 것입니다. 사람이 쓰던 토큰이니 권한 범위도 맞고, 추가 인증 플로우를 설계할 필요도 없어 보입니다.

문제는 에이전트가 그 토큰을 사람처럼 쓰지 않는다는 데 있습니다. 에이전트는 작업 하나를 처리하면서 같은 토큰으로 수십 번씩 API를 호출하고, 중간에 외부 문서나 PR 본문처럼 신뢰할 수 없는 텍스트를 읽습니다. 그 텍스트 안에 숨은 지시문 하나(프롬프트 인젝션)가 에이전트의 다음 행동을 바꿔버리면, 공격자는 에이전트가 쥔 토큰의 전체 권한 범위에 접근하는 통로를 얻습니다. 2026년 들어 Microsoft가 Entra Agent ID를 프리뷰로 내놓는 등, 업계가 에이전트를 별도의 principal 유형으로 다루기 시작한 이유가 여기에 있습니다.

 

사람 토큰을 재사용하면 왜 깨지는가

OAuth의 기본 전제는 사람이 동의한 범위 안에서 앱이 짧고 예측 가능한 패턴으로 대신 행동한다는 것입니다. 에이전트는 이 전제를 세 지점에서 깹니다. 호출 빈도와 패턴이 사람과 다르고, 자율적으로 다음 행동을 판단하는 구간이 존재하며, 사용자 토큰을 그대로 쓰면 로그에는 "사용자 A가 했다"고만 남아 에이전트의 자율 행동인지 사람의 직접 행동인지 구분이 안 됩니다.

 

두 가지 토큰 모델과 선택 기준

클라이언트 자격증명(client credentials) 모델은 에이전트 자체를 독립된 서비스 주체로 등록하고 관리자가 사전 승인한 고정 스코프 토큰을 발급합니다. 반복적이고 저위험인 백그라운드 작업에 적합합니다. 위임(OBO) 모델은 사용자의 동의 체인을 토큰 안에 유지한 채 에이전트가 대신 행동한다는 사실을 토큰 자체에 남깁니다. 메일 발송·결제·파일 삭제처럼 책임 소재가 중요한 민감 작업에 맞습니다.

어느 모델을 쓰든 공통 원칙은 같습니다. 토큰 수명은 짧게, 스코프는 필요한 최소 범위로, 가능하면 특정 클라이언트에 묶는 sender-constrained 방식을 씁니다. 처음부터 넓게 주고 나중에 줄이겠다는 계획은 실제로 거의 지켜지지 않습니다.

 

전체 시스템에서의 위치

 

사용자의 요청이 에이전트 오케스트레이터로 들어오면, 외부 콘텐츠를 읽는 지점이 반드시 생기고 이곳이 프롬프트 인젝션이 유입되는 경계입니다. 오케스트레이터가 실제 외부 API를 호출하기 전에 토큰 브로커 레이어를 두면, 이 레이어가 작업 위험도를 판단해 저위험 반복 작업에는 client credentials 토큰을, 민감한 위임 작업에는 OBO 토큰을 최소 스코프로만 발급합니다. 외부 API는 이 브로커를 거치지 않은 직접 호출을 받아들이지 않도록 구성합니다.

 

선택의 트레이드오프
모델 강점 약점
사용자 토큰 재사용 구현 가장 빠름 탈취 시 전체 권한 노출
전용 client credentials 스코프를 처음부터 좁게 고정 위임 맥락이 토큰에 없음
OBO 위임 체인 위임 맥락 유지, 책임 추적 명확 구현 복잡도 높음

 

대부분의 실무 설계는 작업 위험도에 따라 client credentials와 OBO를 함께 쓰고, 사용자 토큰 재사용은 프로토타입 이후 반드시 걷어냅니다.

 

실제 프로젝트 진행 순서

1단계: 연동 서비스별 액션을 위험도로 분류합니다. 삭제·발송·결제와 조회·요약을 먼저 나눕니다.

2단계: 민감 액션에는 OBO + 사람 승인 게이트를, 반복 저위험 액션에는 client credentials를 배정합니다.

3단계: 토큰 TTL과 스코프를 서비스별로 최소화해 설정합니다.

4단계: 감사 로그에 "에이전트가 자율적으로 호출했는가"를 1급 필드로 남기고, 에이전트 전용 이상 탐지 기준을 따로 만듭니다.

 

토큰 구조 예제
{
  "subject_type": "agent",
  "agent_id": "support-agent-07",
  "acting_for": "user_8841",
  "scope": ["gmail.send"],
  "token_binding": "mtls",
  "expires_in": 900
}

 

주의 — 넓은 스코프를 먼저 주고 나중에 줄이겠다는 계획은 실무에서 거의 실행되지 않습니다. 설계 초기부터 최소 스코프로 시작하세요.

 

정리

사용자 OAuth 토큰을 에이전트에 그대로 재사용하면 프롬프트 인젝션 한 번으로 해당 사용자의 모든 연동 서비스 권한이 함께 노출됩니다. client credentials와 OBO는 서로 다른 문제를 풀며, 작업의 위험도와 책임 추적 필요성에 따라 나눠 적용해야 합니다. 토큰 수명과 스코프는 처음부터 최소로 설계해야 하며, 나중에 좁히는 일은 거의 일어나지 않습니다.
