PostgreSQL BRIN 인덱스로 대용량 시계열 테이블 인덱스 크기 줄이기

DB·데이터 모델링

한 줄 요약 — 물리적 저장 순서를 활용해 B-tree보다 수백 배 작은 인덱스를 만드는 BRIN의 동작 원리와 전제 조건을 정리했습니다.

 

왜 지금 BRIN 인덱스를 다시 봐야 하는가

시간 순서로 계속 쌓이는 로그 테이블이 수억 건 규모로 커지면 B-tree 인덱스 크기가 테이블 크기의 상당 부분을 차지합니다. 인덱스가 메모리에 다 올라가지 못해 인덱스 스캔조차 디스크 I/O를 유발합니다. BRIN은 물리적 저장 순서와 값의 순서가 일치한다는 특성을 이용해 훨씬 작은 크기로 비슷한 효과를 냅니다.

 

B-tree와 근본적으로 다른 저장 단위

B-tree는 개별 행마다 엔트리를 만듭니다. BRIN은 블록 범위(기본 128페이지) 단위로 최솟값·최댓값 요약만 저장합니다. 범위 안에 수천 행이 있어도 인덱스 엔트리는 하나뿐이라 크기가 B-tree의 몇백 분의 1 수준입니다.

 

"물리적 순서와 값의 상관관계"가 성립해야 효과가 있다

BRIN은 쿼리 시점에 조건을 만족할 수 없는 블록 범위를 통째로 건너뜁니다. 이게 성립하려면 값이 물리적 저장 순서와 상관관계를 가져야 합니다. created_at처럼 계속 증가하며 append되는 컬럼은 이상적이지만, user_id처럼 뒤섞여 삽입되는 컬럼은 사실상 풀스캔과 다를 바 없어집니다.

항목 B-tree BRIN
인덱스 단위 개별 행 블록 범위 요약값
인덱스 크기 테이블 비례 큼 매우 작음
전제 조건 없음 저장 순서-값 상관관계 필요

 

예제 — BRIN 인덱스 생성과 크기 비교
CREATE INDEX idx_events_created_at_btree ON events (created_at);
SELECT pg_size_pretty(pg_relation_size('idx_events_created_at_btree'));
-- 2.1 GB (1억 건 기준)

DROP INDEX idx_events_created_at_btree;
CREATE INDEX idx_events_created_at_brin ON events USING BRIN (created_at)
    WITH (pages_per_range = 32);

SELECT pg_size_pretty(pg_relation_size('idx_events_created_at_brin'));
-- 4.8 MB — B-tree 대비 수백 분의 1

EXPLAIN ANALYZE
SELECT * FROM events WHERE created_at BETWEEN '2026-03-01' AND '2026-03-02';

 

실무 포인트

도입 전 실제 물리적 상관관계를 확인하세요. pg_stats의 correlation 값이 1에 가까울수록 BRIN이 효과적이고, 0에 가까우면 효과가 거의 없습니다.

대량 UPDATE나 VACUUM FULL 이후에는 상관관계가 깨질 수 있습니다. 재배치 작업 이후 성능을 재검증하세요.

주의 — BRIN과 B-tree를 함께 쓰는 것도 선택지입니다. 최근 데이터에는 B-tree를, 오래된 대용량 이력에는 BRIN을 파티셔닝과 결합해 쓰는 경우도 흔합니다.
