SSR을 서울 데이터센터가 아니라 사용자 옆에서 — 엣지 렌더링과 CDN 기반 SSR

2026. 8. 28. · 프론트엔드

한 줄 요약 — SSR을 단일 리전 서버가 아니라 사용자와 물리적으로 가장 가까운 CDN 엣지에서 실행하는 엣지 렌더링의 원리와, Node.js 런타임을 그대로 못 쓰는 이유·제약을 정리했습니다.

 

서버를 빠르게가 아니라 사용자 옆으로 옮긴다는 발상

전통적인 SSR은 도쿄나 버지니아 같은 단일 리전에 있는 서버가 전 세계 요청을 받아 HTML을 렌더링해 내려보냅니다. 서버 자체의 렌더링 속도가 아무리 빨라도, 먼 지역 사용자에게는 요청이 그 리전까지 왕복하는 네트워크 지연이 렌더링 시간 위에 그대로 얹힙니다.

엣지 렌더링은 이 문제를 "서버를 더 빠르게"가 아니라 "서버를 사용자 옆으로" 옮겨서 풉니다. Vercel Edge Functions, Cloudflare Workers, Deno Deploy 같은 플랫폼은 전 세계 수백 개 PoP(Point of Presence)에 동일한 코드를 배포해두고, 요청이 들어오면 지리적으로 가장 가까운 PoP에서 즉시 실행합니다.

 

핵심 개념 1 — 리전 서버 SSR vs 엣지 렌더링
구분 리전 서버 SSR 엣지 렌더링
실행 위치 고정된 1~2개 리전 가장 가까운 PoP
런타임 완전한 Node.js V8 isolate 경량 런타임
콜드 스타트 수백ms 가능 수ms 목표
파일 시스템 접근 가능 대부분 불가능

 

핵심 개념 2 — 왜 완전한 Node.js를 못 쓸까요

엣지 플랫폼 대부분은 컨테이너나 VM 대신 V8 isolate를 실행 단위로 씁니다. isolate는 격리된 하나의 JS 실행 컨텍스트로, 프로세스나 컨테이너를 새로 띄우는 것보다 시작 비용이 훨씬 낮습니다. 대신 Node.js의 네이티브 애드온, 파일 시스템 API(fs), 일부 저수준 네트워킹 API를 지원하지 않고, fetch·Request·Response 같은 웹 표준 API만 제공하는 경우가 많습니다.

핵심 개념 3 — 데이터 접근 지연이라는 새로운 병목

렌더링 자체는 사용자 옆에서 실행돼 빨라졌지만, 그 렌더링에 필요한 데이터는 여전히 특정 리전에만 있는 경우가 대부분입니다. 이 경우 렌더링은 빨라졌는데 전체 응답은 그대로인 상황이 생길 수 있습니다. 엣지 렌더링을 제대로 활용하려면 읽기 전용 데이터도 엣지 KV 스토어나 리전 복제본으로 함께 분산시켜야 합니다.

 

예제 — Next.js에서 엣지 런타임 선택
// app/product/[id]/page.tsx
export const runtime = "edge"; // 이 라우트만 엣지 런타임에서 렌더링

export default async function ProductPage({ params }) {
  const res = await fetch(`https://api.example.com/products/${params.id}`, {
    next: { revalidate: 60 },
  });
  const product = await res.json();
  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.price}원</p>
    </main>
  );
}
// Cloudflare Workers: KV로 지연 없는 읽기 전용 데이터 접근
export default {
  async fetch(request, env) {
    const cached = await env.PRODUCT_KV.get("featured-products", "json");
    if (cached) {
      return new Response(renderHTML(cached));
    }
    const fresh = await fetch("https://origin.example.com/api/featured");
    return new Response(await fresh.text());
  },
};

Next.js처럼 라우트 단위로 runtime을 선택할 수 있는 프레임워크에서는, 전체 앱을 엣지로 옮기기보다 지연에 민감하고 무거운 Node 의존성이 없는 라우트만 선별적으로 배치하는 것이 현실적입니다.

 

실무 도입 시 이것만은 챙기세요
1. Node 전용 패키지 의존성을 먼저 감사하세요 — 이미지 처리(sharp), 네이티브 드라이버 등은 엣지 런타임에서 그대로 동작하지 않습니다.
2. DB 커넥션 전략을 다시 짜세요 — 전통적인 커넥션 풀 대신 HTTP 기반 DB 드라이버나 커넥션 풀러를 앞단에 두는 것이 일반적입니다.
3. 엣지가 항상 정답은 아닙니다 — 무거운 연산, 긴 실행 시간, Node 전용 라이브러리에 의존하는 로직은 여전히 리전 서버가 적합합니다.

 

마무리 — 3줄 요약

① 엣지 렌더링은 SSR 코드를 전 세계 PoP에 미리 배포해 사용자와 가장 가까운 곳에서 즉시 실행합니다.
② 콜드 스타트를 줄이기 위해 V8 isolate 기반 경량 런타임을 쓰는 대가로 완전한 Node.js API 대신 웹 표준 API만 지원합니다.
③ 렌더링만 옮겨서는 부족하고, 데이터도 엣지 KV·리전 복제본으로 함께 분산시켜야 실제 응답 지연이 줄어듭니다.
