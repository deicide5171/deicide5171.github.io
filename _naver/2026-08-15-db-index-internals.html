한 줄 요약 — Flutter, 지도 API, PostGIS, 분산 SQL까지 다뤄온 흐름을 보면 다음으로 채워야 할 빈틈은 DB 인덱스 내부 구조입니다. 왜 그런지, 무엇부터 보면 되는지 정리했습니다.

 

왜 지금 인덱스 내부 구조인가

이 블로그의 글들을 쭉 훑어보면 흐름이 보입니다. Flutter로 앱을 만들고, 네이버 클라우드 지도 API를 붙이고, 최근에는 PostGIS 기반 공간 DB와 분산 SQL, AI 에이전트까지 다루기 시작했죠. "기능을 붙이는 단계"에서 "데이터를 저장하고 조회하는 방식 자체를 설계하는 단계"로 관심사가 옮겨가고 있다는 뜻입니다.

그런데 지금까지의 글에는 공통된 빈틈이 하나 있습니다. 인덱스를 "쓰는" 이야기는 많은데(공간 인덱스 GiST, 분산 SQL의 range 등), 인덱스가 내부적으로 왜 그렇게 동작하는지는 아직 다루지 않았다는 점입니다. WHERE 절에 인덱스를 걸었는데도 느린 경우, EXPLAIN 결과를 봐도 왜 인덱스를 안 타는지 판단이 안 서는 경우는 결국 내부 구조를 모르면 답이 안 나오는 문제들입니다.

 

다른 후보와 비교해봤습니다
후보 주제 지금 필요한 이유 시급도
DB 인덱스 내부 구조 지도·분산 DB 글에서 반복 등장한 개념의 뿌리 높음
테스팅 전략 Flutter 앱 글은 많은데 테스트 글이 없음 중간
Docker/CI 배포 자동화 경험이 블로그에 없음 중간

 

테스팅과 CI도 분명 필요하지만, 지금 막 분산 SQL·공간 인덱스를 다룬 직후이니 "그 인덱스가 왜 그렇게 동작하는가"를 먼저 메우는 게 학습 곡선상 자연스럽습니다.

 

핵심 개념: B-Tree vs LSM-Tree vs GiST

B-Tree는 PostgreSQL, MySQL의 기본 인덱스입니다. 정렬된 키를 균형 트리로 유지해 =, <, >, BETWEEN 조회에 강하고 읽기 위주 워크로드에 적합합니다.

LSM-Tree는 RocksDB, Cassandra 등이 채택합니다. 쓰기를 메모리에 먼저 모았다가 순차적으로 디스크에 병합(compaction)해서, 쓰기가 매우 많은 워크로드에 유리합니다.

GiST는 PostGIS의 공간 인덱스가 기반으로 삼는 구조입니다. 값이 아니라 겹치는 범위(bounding box)를 기준으로 트리를 구성해, 좌표·범위 데이터를 인덱싱할 수 있게 일반화했습니다.

셋 다 "탐색 범위를 좁혀서 전체 스캔을 피한다"는 목적은 같지만, 무엇을 빠르게 하고 무엇을 희생하는지가 다릅니다.

 

예제: EXPLAIN으로 직접 확인하기

이론만으로는 감이 안 오니, 실제 쿼리 플랜으로 확인하는 습관을 들이는 게 중요합니다.

-- 인덱스가 있는지, 실제로 타는지 확인
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 42
  AND created_at > now() - interval '7 days';

-- 결과 예시
Index Scan using idx_orders_customer_created on orders
  Index Cond: (customer_id = 42 AND created_at > ...)
  Buffers: shared hit=12

Index Scan이 아니라 Seq Scan이 나온다면, 인덱스가 없거나 옵티마이저가 "인덱스보다 전체 스캔이 더 싸다"고 판단한 것입니다. 이 판단 기준(선택도, 통계 정보)을 이해하는 것 자체가 인덱스 내부 구조 학습의 핵심 목표입니다.

 

학습 순서 제안

① B-Tree 기본기 — 노드 분할, 균형 유지 원리부터
② 복합 인덱스와 컬럼 순서 — (customer_id, created_at)과 (created_at, customer_id)가 왜 다른지 직접 실험
③ EXPLAIN 읽는 습관 — 쿼리마다 플랜을 확인하는 루틴
④ LSM-Tree, GiST로 확장 — 분산 SQL·PostGIS 글과 연결 지어 복습

 

실무에 적용할 때 이것만은 챙기세요
1. "걸어두면 무조건 빠르다"는 착각 금지 — 쓰기 비용이 늘고, 잘못된 컬럼 순서는 옵티마이저에게 무시당함
2. 낮은 카디널리티 컬럼 주의 — 값의 다양성이 낮으면 단독 인덱스를 걸어도 옵티마이저가 잘 안 씀
3. 오늘 쓴 글과 연결해서 복습 — 분산 SQL·GIS 글의 인덱스가 왜 그런 트레이드오프를 갖는지 스스로 설명해보기

 

마무리 — 3줄 요약

① 이 블로그는 지도·분산 DB 글에서 인덱스를 반복적으로 언급해왔지만, 정작 인덱스 내부 구조는 다룬 적이 없습니다.
