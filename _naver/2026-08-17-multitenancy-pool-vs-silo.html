한 DB에 모두 담을까, 테넌트마다 나눌까 — 멀티테넌시 Pool vs Silo 아키텍처

2026. 8. 17. · 아키텍처·시스템설계

한 줄 요약 — 여러 고객사(테넌트)를 하나의 서비스로 운영하는 SaaS에서, 데이터를 한 DB에 모아 둘지(Pool 모델) 테넌트마다 완전히 분리할지(Silo 모델) 결정하는 기준과, 그 사이의 하이브리드 전략인 테넌트 티어링을 정리했습니다.

 

왜 지금 멀티테넌시 아키텍처인가

SaaS 제품 하나로 수십, 수백 개의 고객사를 동시에 서비스하는 구조는 이제 특이한 선택이 아니라 기본값에 가깝습니다. 문제는 "테넌트가 늘어날수록 인프라도 그만큼 늘려야 하는가"입니다. 테넌트마다 서버와 DB를 통째로 복제하면 비용이 테넌트 수에 비례해 커지고, 반대로 모든 테넌트를 하나의 DB에 몰아넣으면 한 테넌트의 트래픽 폭주가 다른 테넌트에게 그대로 전이되는 노이즈 이웃(Noisy Neighbor) 문제와, 데이터가 물리적으로 같은 테이블에 있어도 되는가라는 보안·규제 질문이 남습니다.

이 딜레마를 정리하는 표준 어휘가 Pool(공유) 모델과 Silo(격리) 모델입니다. 초기 스타트업은 대개 비용 효율을 위해 Pool로 시작하지만, 금융·의료 고객사나 엔터프라이즈 계약이 들어오는 순간 데이터 상주(residency)·감사(audit) 요구 때문에 Silo 격리를 고려하게 됩니다. 두 모델의 차이와 그 사이의 스펙트럼, 실무의 하이브리드 전략을 정리해보겠습니다.

 

핵심 개념: Pool 모델 vs Silo 모델

Pool 모델은 모든 테넌트가 같은 애플리케이션과 같은 데이터베이스를 공유하고, 각 데이터 행에 tenant_id 같은 식별 컬럼을 두어 논리적으로만 구분합니다. Silo 모델은 반대로 테넌트마다 별도의 DB(또는 애플리케이션 스택 전체)를 두어 물리적으로 격리합니다.

항목 Pool 모델(공유) Silo 모델(격리)
인프라 비용 낮음(자원을 나눠 씀) 높음(테넌트 수만큼 복제)
데이터 격리 논리적(쿼리 조건 의존) 물리적(접근 경로 자체 분리)
노이즈 이웃 위험 있음 없음
운영 복잡도 낮음 높음(테넌트 수만큼 반복)
규제 대응 어려움 쉬움(리전·인프라 지정 가능)

 

격리 스펙트럼 — Row-Level부터 Silo까지

실제로는 "Pool 아니면 Silo"라는 이분법이 아니라, 그 사이에 여러 단계가 있습니다. DB를 얼마나 잘게 나누느냐에 따라 격리 강도와 운영 비용이 함께 올라갑니다.

단계 방식 대표 구현
Row-Level(완전 Pool) 한 테이블, tenant_id 컬럼으로 구분 PostgreSQL RLS
Schema-per-Tenant(Bridge) 같은 DB, 테넌트마다 스키마 분리 Hibernate SCHEMA 전략
Database-per-Tenant 같은 서버, 테넌트마다 별도 DB 테넌트별 커넥션 라우팅
Silo(Infra-per-Tenant) 앱+DB 스택 전체 분리 테넌트별 독립 배포

전체 테넌트를 하나의 모델로 통일해야 할 이유는 없습니다. 실무에서는 요금제 등급에 따라 격리 모델을 다르게 적용하는 티어링이 흔합니다. 무료·스타터 테넌트는 Pool로 저렴하게 수용하고, 엔터프라이즈나 규제 산업 고객사는 Database-per-Tenant 또는 완전 Silo로 격리해 SLA와 데이터 상주 요구를 만족시키는 식입니다.

 

예제 1: PostgreSQL Row-Level Security로 Pool 모델 격리하기

RLS를 쓰면 애플리케이션 코드가 조건절을 빠뜨리는 실수를 하더라도 DB 엔진이 강제로 필터링해줍니다.

-- tenant_id 컬럼을 가진 공유 테이블
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 세션에 설정된 tenant_id와 일치하는 행만 보이도록 정책 생성
CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- 애플리케이션은 요청마다 현재 테넌트를 세션 변수로 설정
SET app.current_tenant = '11111111-1111-1111-1111-111111111111';
SELECT * FROM orders; -- 위 tenant_id 를 가진 행만 반환됨

다만 세션 변수 설정을 커넥션 풀 반환 시점에 반드시 초기화해야, 커넥션이 재사용될 때 이전 테넌트 컨텍스트가 새 요청에 새어 들어가는 사고를 막을 수 있습니다.

 

예제 2: 테넌트별 DB 라우팅(Spring AbstractRoutingDataSource)
public class TenantRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return TenantContext.getCurrentTenant(); // 요청 스레드에 저장된 테넌트 ID
    }
}

@Bean
public DataSource routingDataSource() {
    TenantRoutingDataSource routingDataSource = new TenantRoutingDataSource();
    Map<Object, Object> targetDataSources = new HashMap<>();
    targetDataSources.put("tenant_a", tenantADataSource());
    targetDataSources.put("tenant_b", tenantBDataSource());
    routingDataSource.setTargetDataSources(targetDataSources);
    routingDataSource.setDefaultTargetDataSource(poolDataSource()); // 신규/소형 테넌트는 공유 풀로 폴백
    return routingDataSource;
}

setDefaultTargetDataSource로 공유 Pool을 기본값으로 지정해 두면, 별도 DB가 배정되지 않은 신규 테넌트는 자동으로 Pool 모델로 수용되고 이후 필요할 때만 전용 DataSource를 등록하는 점진적 티어링이 가능해집니다.

 

실무 도입 시 이것만은 챙기세요
1. 테넌트 컨텍스트 누락은 곧 데이터 유출 — 통합 테스트에 "테넌트 A로 로그인해 테넌트 B의 리소스 직접 요청" 같은 교차 접근 시나리오 포함
2. 마이그레이션 전략은 모델별로 다르게 — Schema/DB-per-Tenant는 테넌트 수만큼 반복 적용되므로 자동화 필수
3. 노이즈 이웃은 먼저 모니터링으로 확인 — Silo 전환 전에 테넌트별 자원 사용량 지표로 실제 영향 검증
4. 격리 모델 전환은 무중단으로 설계 — 데이터 마이그레이션과 트래픽 전환 시점을 분리해 이중 쓰기·읽기 불일치 방지

 

마무리 — 3줄 요약

① Pool 모델은 비용 효율적이지만 논리적 격리에 그치고, Silo 모델은 물리적으로 완전히 격리되지만 테넌트 수만큼 운영 비용이 커집니다.
② 실제로는 Row-Level → Schema-per-Tenant → Database-per-Tenant → Silo로 이어지는 격리 스펙트럼이 있으며, 요금제 등급별로 다른 모델을 적용하는 테넌트 티어링이 흔한 실무 전략입니다.
③ 어떤 모델을 쓰든 테넌트 컨텍스트 누락은 곧 데이터 유출로 이어지므로, 교차 테넌트 접근을 막는 테스트와 무중단 이관 절차를 함께 설계해야 합니다.
