Node.js Streams와 백프레셔 — 대용량 파일 처리에서 메모리를 지키는 파이프라인 설계

백엔드

한 줄 요약 — 생산 속도가 소비 속도를 앞지를 때 자동으로 속도를 늦추는 백프레셔 메커니즘과 pipeline() 활용법을 정리했습니다.

 

왜 지금 Node.js 백프레셔를 다시 봐야 하는가

fs.readFile로 수 GB짜리 파일을 읽으면 파일 전체가 그대로 메모리 사용량이 되어 OOM으로 죽을 수 있습니다. Streams는 청크 단위로 흘려보내 이를 해결하지만, 생산 쪽이 소비 쪽보다 빠르면 처리 못 한 청크가 버퍼에 쌓여 똑같이 메모리를 다 써버립니다. 백프레셔가 이 흐름을 자동으로 조절합니다.

 

write()의 반환값이 신호를 보낸다

Writable의 write()는 boolean을 반환합니다. false면 버퍼가 highWaterMark를 넘어섰으니 그만 보내라는 신호입니다. 이를 무시하면 데이터가 버퍼에 계속 쌓여 메모리가 무한정 늘어납니다. drain 이벤트가 발생할 때까지 기다렸다가 재개하는 것이 올바른 처리입니다.

 

pipe()와 pipeline()이 이 규약을 대신 지켜준다

pipe()는 백프레셔 처리를 자동화하지만 에러 발생 시 나머지 스트림을 자동 정리해주지 않아 리소스 누수 위험이 있습니다. stream.pipeline()은 백프레셔 처리는 동일하게 하면서 에러 시 관련된 모든 스트림을 자동 정리해줍니다.

방식 에러 시 정리 권장 여부
pipe() 자동으로 안 됨 레거시만 유지
pipeline() 자동 정리 신규 코드 기본

 

pipeline로 대용량 CSV 처리 예제
const { pipeline } = require('node:stream/promises');
const fs = require('node:fs');

async function processLargeFile() {
  await pipeline(
    fs.createReadStream('huge-input.csv'),
    upperCaseTransform,
    fs.createWriteStream('output.csv')
  );
}

processLargeFile().catch(console.error);

 

실무 포인트

highWaterMark를 무작정 키우는 것은 해결책이 아닙니다. 버퍼가 커지면 메모리 사용량 상한선도 함께 올라갑니다. 프로파일링을 근거로만 조정해야 합니다.

비동기 Transform에서 콜백을 빠뜨리면 파이프라인 전체가 멈춥니다. 에러 처리 경로에서 callback() 호출을 누락하면 다음 청크를 영원히 기다리며 조용히 멈춰버립니다.

주의 — Express나 Fastify에서도 같은 원리가 적용됩니다. 요청·응답 객체 자체가 스트림이므로 버퍼에 전부 담지 말고 pipeline()에 그대로 연결하면 대용량 파일도 일정한 메모리로 처리할 수 있습니다.
