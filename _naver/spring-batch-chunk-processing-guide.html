Spring Batch로 대용량 배치 작업 처리하기 — Chunk 기반 처리 입문

백엔드

한 줄 요약 — Spring Batch의 Chunk 기반 처리는 일정 단위로 트랜잭션을 나누고 재시도·건너뛰기 정책을 선언적으로 설정할 수 있게 해, 대량 데이터 배치 작업의 메모리·복구 문제를 해결합니다.

 

왜 @Scheduled와 for문만으론 한계가 오는가

데이터가 수천 건일 땐 @Scheduled와 반복문으로 충분하지만, 수백만 건으로 늘면 전체를 메모리에 올리다 OutOfMemoryError가 나고, 처리 도중 서버가 재시작되면 어디까지 처리했는지 알 방법이 없어 처음부터 다시 돌려야 합니다.

 

잘못된 접근 vs 올바른 접근

재시도 로직을 직접 짜 넣어도, 서버가 배치 도중 완전히 죽으면 여전히 어디서 다시 시작해야 하는지 알 수 없습니다. Spring Batch는 이 문제를 프레임워크 레벨에서 해결합니다.

.<Transaction, Settlement>chunk(1000, transactionManager)
    .reader(transactionReader())
    .processor(settlementProcessor())
    .writer(settlementWriter())
    .faultTolerant()
    .retryLimit(3)
    .skipLimit(10)

chunk(1000, ...)은 1000건씩 묶어 하나의 트랜잭션으로 처리합니다. 하나에서 예외가 나면 그 청크만 롤백되고, 이미 커밋된 이전 청크는 영향받지 않습니다. retryLimit·skipLimit으로 일시적 오류는 재시도하고, 특정 데이터 문제는 건너뛰도록 세밀하게 제어할 수 있습니다.

주의 — Spring Batch는 JobRepository에 실행 이력과 마지막 커밋 지점을 자동 기록합니다. 배치 도중 서버가 죽어도 같은 Job을 다시 실행하면 실패한 지점부터 재시작할 수 있습니다.

 

실무 포인트

Reader·Processor·Writer 책임을 명확히 분리하면 각 단계를 독립적으로 테스트하기 쉬워집니다. 페이징 기반 Reader는 정렬 기준을 명시해야 페이지 경계에서 데이터 중복·누락이 없습니다. 재시작 가능성을 전제로 Writer를 멱등하게 설계하고, Chunk 크기는 데이터 특성에 맞춰 수백~수천 단위로 실측하며 조정하세요.
