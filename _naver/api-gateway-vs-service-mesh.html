API 게이트웨이 vs 서비스 메시, 언제 어떤 것을 선택할까

시스템설계

한 줄 요약 — API 게이트웨이는 외부 → 내부 트래픽의 단일 진입점, 서비스 메시는 내부 서비스 간 트래픽 제어라는 서로 다른 문제를 해결합니다.

 

왜 자주 헷갈리는가

마이크로서비스로 전환한 팀은 인증, 재시도, 서킷 브레이커, 로드밸런싱을 어디에 둘지 고민하다 API 게이트웨이와 서비스 메시를 동시에 떠올립니다. 둘 다 트래픽을 가로채 정책을 적용한다는 점이 비슷해 보이지만, 실제로는 다루는 트래픽 방향이 근본적으로 다릅니다.

 

책임 범위 비교
항목 API 게이트웨이 서비스 메시
트래픽 방향 외부 → 내부 내부 서비스 간
배치 위치 클러스터 경계 각 서비스 옆 사이드카
주요 기능 인증, 라우팅, 속도 제한 mTLS, 재시도, 서킷 브레이커

 

잘못된 접근 vs 올바른 접근

서비스가 5~10개일 때는 게이트웨이에 서비스 간 호출 로직까지 몰아넣어도 괜찮아 보이지만, 수십 개로 늘면 게이트웨이가 모든 서비스의 위치와 상태를 알아야 하는 중앙 집중 지점이 되어버립니다. 반대로 "메시가 있으니 게이트웨이는 필요 없다"는 접근도, API 키 발급이나 요금제별 속도 제한 같은 외부 계약 역할을 대신하기엔 적합하지 않습니다.

올바른 방식은 두 계층을 분리해 함께 쓰는 것입니다. 외부 클라이언트 → API 게이트웨이(인증, 속도 제한) → 서비스 메시 사이드카(mTLS, 재시도) → 내부 서비스 간 호출 순서로 역할을 나눕니다.

주의 — 서비스 메시 도입 비용을 과소평가하지 마세요. 사이드카 프록시가 모든 Pod에 붙으면서 리소스 사용량과 지연시간이 늘어납니다. 성능이 민감한 소수 서비스는 메시에서 제외하는 선택지도 검토하세요.

 

실무 포인트

서비스 규모가 작다면 게이트웨이만으로 충분한 경우가 많습니다. 서비스 간 통신 정책이 언어·팀별로 중복 구현되기 시작하는 시점이 메시 도입을 검토할 신호입니다. 인증은 외부 사용자 인증(게이트웨이)과 서비스 간 신원 검증(메시)으로 역할을 겹치지 않게 나누고, OpenTelemetry로 트레이스 ID를 양쪽에서 일관되게 전파하세요.
