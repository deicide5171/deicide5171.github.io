Java FFM API — JNI를 대체하는 Foreign Function & Memory 연동

백엔드

한 줄 요약 — C 헤더 생성과 별도 빌드 체인 없이 순수 자바 코드만으로 네이티브 함수를 호출하는 JDK 22 FFM API의 원리를 정리했습니다.

 

왜 지금 네이티브 연동 방식을 다시 봐야 하는가

C/C++로 작성된 고성능 라이브러리를 자바에서 호출해야 할 때, JNI는 상당한 복잡도를 요구했습니다. javah로 헤더 생성, C 스텁 작성, 별도 네이티브 빌드 체인까지 준비해야 함수 하나를 호출할 수 있었고, 포인터를 잘못 다루면 JVM이 세그멘테이션 폴트로 통째로 죽는 문제도 있었습니다. FFM API는 JDK 22에서 정식 기능으로 자리 잡으며 이 문제를 해결합니다.

 

링커와 심볼 조회로 네이티브 함수 호출하기

FFM API의 핵심 축은 Linker입니다. SymbolLookup으로 공유 라이브러리에서 함수 심볼을 찾은 뒤, FunctionDescriptor로 C 시그니처를 선언하면 downcallHandle()이 그 함수를 호출 가능한 MethodHandle로 만들어줍니다. 컴파일 타임에 별도 C 스텁을 생성할 필요가 없고, 실행 중에 동적으로 어떤 네이티브 함수든 연결할 수 있다는 점이 JNI와 근본적으로 다릅니다.

항목 JNI FFM API
빌드 요구사항 네이티브 컴파일러 필요 순수 자바만으로 충분
메모리 오류 시 JVM 크래시 위험 자바 예외로 처리

 

MemorySegment와 Arena로 오프힙 메모리 안전하게 다루기

FFM API는 오프힙 메모리를 MemorySegment라는 타입 안전한 핸들로 감싸고, 그 수명을 Arena가 명시적으로 관리하게 합니다. Arena.ofConfined()로 만든 아레나는 close() 시점에 관련된 모든 세그먼트가 한꺼번에 해제되며, 이미 닫힌 아레나의 세그먼트에 접근하면 JVM 크래시가 아니라 자바 예외가 발생합니다. try-with-resources와 자연스럽게 맞물립니다.

libc strlen 호출 예제
Linker linker = Linker.nativeLinker();
SymbolLookup stdlib = linker.defaultLookup();

MethodHandle strlen = linker.downcallHandle(
    stdlib.find("strlen").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS)
);

try (Arena arena = Arena.ofConfined()) {
    MemorySegment cString = arena.allocateUtf8String("Hello, FFM!");
    long length = (long) strlen.invoke(cString);
    System.out.println("길이: " + length); // 11
}

 

실무 포인트

Arena.ofConfined()와 Arena.ofShared()를 상황에 맞게 골라야 합니다. 단일 스레드에서만 쓰는 리소스는 confined로, 여러 스레드가 공유해야 하는 장기 리소스는 shared로 선언해야 합니다.

기존 JNI 코드를 당장 걷어낼 필요는 없습니다. FFM API는 신규 네이티브 연동부터 우선 적용하고, 안정성이 검증된 기존 JNI 모듈은 점진적으로 이관하는 편이 리스크가 적습니다.

주의 — JNI에서 마이그레이션할 때는 성능 프로파일링을 반드시 다시 해야 합니다. Linker.Option.critical() 같은 옵션은 안전 검사를 줄여 성능을 높이지만 그만큼 안전성과 맞바꾸는 것입니다.
