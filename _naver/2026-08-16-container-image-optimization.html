컨테이너 이미지 최적화 실전 — 멀티스테이지 빌드로 레이어 다이어트하기

2026. 8. 16. · 인프라

한 줄 요약 — 빌드 도구와 소스코드가 그대로 남아 무거워진 컨테이너 이미지를, 멀티스테이지 빌드와 베이스 이미지 선택만으로 가볍고 안전하게 줄이는 실전 방법을 정리했습니다.

 

왜 지금 이미지 크기를 신경 써야 할까

컨테이너 이미지를 처음 만들 때는 대부분 "일단 동작하게" 만드는 데 집중합니다. 익숙한 베이스 이미지 위에 소스를 통째로 복사하고 빌드 도구까지 그대로 남겨둔 채 배포하는 경우가 많습니다. 문제는 이렇게 만들어진 이미지가 실행에 필요 없는 컴파일러, 패키지 캐시, 소스코드, 테스트 파일까지 껴안고 다닌다는 점입니다.

이미지가 무거워지면 레지스트리 푸시·풀 시간이 늘어나고, 오토스케일링이나 롤링 배포 시 새 인스턴스가 뜨는 시간도 함께 늘어납니다. 더 중요한 문제는 보안입니다. 이미지 안에 셸, 패키지 매니저, 불필요한 라이브러리가 많을수록 취약점 스캐너가 잡아내는 항목도, 컨테이너가 뚫렸을 때 공격자가 활용할 수 있는 도구도 늘어납니다.

이번 글은 Dockerfile 기초나 CI/CD 개괄이 아니라, 멀티스테이지 빌드를 이용해 실제로 이미지 크기와 공격 표면을 줄이는 구체적인 기법에 집중합니다.

 

핵심 개념 1: 레이어 캐시는 순서가 전부

Docker 이미지는 Dockerfile의 각 명령이 만드는 레이어를 쌓아 만듭니다. 레이어는 위에서부터 순서대로 캐시되며, 한 레이어의 내용이 바뀌면 그 아래 모든 레이어의 캐시가 무효화됩니다. 그래서 자주 바뀌는 것(소스코드)은 나중에, 잘 안 바뀌는 것(의존성 목록)은 먼저 복사하는 순서가 빌드 속도를 좌우합니다.

순서 안 좋은 예 좋은 예
1 COPY . . (전체 복사) package*.json만 먼저 복사
2 npm install npm ci (캐시 재사용 가능)
3 npm run build 소스는 마지막에 복사
결과 소스 한 줄만 바뀌어도 재설치 소스만 바뀌면 설치 단계 캐시 재사용

 

BuildKit을 사용하면 캐시 마운트로 의존성 다운로드 캐시를 레이어 밖에 별도로 보관할 수도 있습니다. 레이어 자체에 캐시 파일이 남지 않으면서도 반복 빌드는 빨라집니다.

 

핵심 개념 2: 베이스 이미지 선택이 최종 크기를 결정

멀티스테이지 빌드를 아무리 잘 써도 마지막 런타임 스테이지의 베이스 이미지가 무거우면 절반의 효과만 얻습니다. 상황에 맞는 베이스를 고르는 것이 중요합니다.

베이스 유형 특징 주로 쓰는 상황
풀(full) 이미지
(debian, ubuntu)		 셸·패키지 매니저 포함, 용량 큼 로컬 개발, 디버깅이 잦은 초기 단계
slim / alpine 계열 최소 유틸리티만 포함 대부분의 운영 배포
distroless OS 유틸리티·셸 자체가 없음 보안 표면을 최소화해야 하는 운영
scratch 완전히 빈 이미지 Go 등 정적 바이너리 단일 실행 파일

 

alpine은 musl libc를 쓰기 때문에 glibc 기반으로 컴파일된 바이너리나 일부 네이티브 애드온과 호환성 문제가 생길 수 있다는 점은 감안해야 합니다. 무조건 가장 작은 베이스를 고르기보다, 팀의 디버깅 요구 수준과 런타임 호환성을 먼저 따진 뒤 선택하는 편이 안전합니다.

 

예제: 캐시 마운트 + distroless 멀티스테이지 Dockerfile

아래는 의존성 설치 단계와 빌드 단계를 분리하고, 최종 실행 이미지는 distroless 베이스에 산출물만 올리는 예시입니다.

# syntax=docker/dockerfile:1

# 1단계: 의존성 설치 (레이어 캐시 극대화)
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

# 2단계: 빌드 (풀 의존성 + 소스)
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
RUN npm run build

# 3단계: 실행 (distroless, 최소 산출물만)
FROM gcr.io/distroless/nodejs20-debian12 AS runtime
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER nonroot
EXPOSE 3000
CMD ["dist/main.js"]

deps와 build 스테이지를 분리한 이유는, 운영에 필요한 node_modules(devDependencies 제외)와 빌드에만 필요한 전체 의존성을 구분하기 위해서입니다. 최종 runtime 스테이지는 distroless 이미지를 베이스로 써서 셸조차 없앴고, 비루트 사용자로 실행해 컨테이너가 침해당하더라도 루트 권한으로 확장되지 않도록 했습니다.

 

실무 도입 시 이것만은 챙기세요
1. .dockerignore를 반드시 관리 — node_modules, .git, 테스트 픽스처 등 빌드 컨텍스트 전송 자체를 가볍게 유지
2. 이미지 레이어를 직접 눈으로 확인 — dive 같은 도구나 docker history로 어느 레이어가 용량을 많이 차지하는지 점검
3. RUN 명령을 논리적으로 묶기 — 설치와 캐시 삭제를 같은 RUN 안에서 끝내야 실제로 용량이 줄어듦
4. 버전을 태그로 고정 — latest 대신 구체적인 버전을 명시해 빌드 재현성 확보
5. distroless·scratch 전환 전 디버깅 경로 확보 — 셸이 없는 이미지는 문제 발생 시 접속 확인이 불가능하므로 구조화 로깅과 디버그용 이미지 태그를 함께 준비

 

마무리 — 3줄 요약

① 레이어는 위에서부터 캐시되므로, 의존성 설치를 먼저·소스 복사를 나중에 배치하는 순서만으로도 빌드 속도가 달라집니다.
② 멀티스테이지 빌드로 빌드 도구·소스·캐시를 최종 이미지에서 걷어내고, distroless나 scratch처럼 좁은 런타임 베이스를 선택하면 이미지 크기와 공격 표면을 함께 줄일 수 있습니다.
③ 셸 없는 최소 이미지로 전환하기 전에는 레이어를 직접 점검하고, 디버깅 경로(로깅, 디버그 태그)를 먼저 마련해두는 것이 안전합니다.
