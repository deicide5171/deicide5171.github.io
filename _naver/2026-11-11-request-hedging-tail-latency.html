Request Hedging — 꼬리 지연시간을 줄이기 위해 일부러 중복 요청을 보내는 전략

아키텍처·시스템 설계

한 줄 요약 — 응답이 늦어지는 요청에 한해 다른 서버로 같은 요청을 하나 더 보내 먼저 온 응답을 채택하는 Request Hedging 전략을 정리했습니다.

 

왜 지금 Request Hedging을 다시 봐야 하는가

평균 응답시간(p50)은 빠른데 p99·p999 꼬리 구간만 유독 길게 튀는 현상은 GC 일시정지나 디스크 I/O 경합처럼 예측하기 어려운 원인에서 비롯됩니다. 병렬 하위 요청이 많을수록 그중 하나만 느려도 전체 응답이 그것을 기다려야 합니다. Hedging은 실패를 기다리지 않고 선제적으로 대응합니다.

 

재시도(Retry)와 헤징(Hedging)의 근본적 차이

재시도는 요청 실패를 확인한 뒤에야 다시 시도합니다. 헤징은 임계값을 넘으면 원래 요청을 취소하지 않은 채 다른 인스턴스로 하나 더 보내고, 먼저 도착한 응답을 씁니다. 다만 헤징된 요청만큼 백엔드에 추가 부하가 걸리므로 무분별하게 적용하면 상황을 악화시킬 수 있습니다.

 

언제 얼마나 헤징할지 결정하는 임계값 설계

가장 흔한 기준은 최근 응답시간 분포의 특정 백분위수(예: p95)를 임계값으로 삼는 것입니다. 이렇게 하면 전체 요청의 5%만 헤징 대상이 되어 추가 부하를 예측 가능한 범위로 통제합니다. 헤징은 반드시 멱등성이 보장된 읽기 요청에만 적용해야 합니다.

항목 Retry Hedging
발동 시점 실패 확정 후 임계값보다 늦어질 때
목적 실패 복구 꼬리 지연시간 단축

 

gRPC 클라이언트 헤징 설정 예제
{
  "methodConfig": [{
    "name": [{ "service": "search.SearchService" }],
    "hedgingPolicy": {
      "maxAttempts": 3,
      "hedgingDelay": "0.1s",
      "nonFatalStatusCodes": ["UNAVAILABLE"]
    }
  }]
}

 

실무 포인트

헤징 비율을 반드시 모니터링하세요. 헤징 비율이 설정 백분위수보다 훨씬 높다면 백엔드 전체가 느려지고 있다는 신호이지 헤징으로 해결할 문제가 아닙니다. 헤징 비율이 너무 높아지면 헤징 자체를 잠시 끄는 상한을 두는 것이 안전합니다.

캐시가 있는 계층에서는 헤징 효과가 배가됩니다. 첫 요청이 캐시 미스로 느린 동안 두 번째 헤징 요청이 다른 노드의 캐시 히트로 빠르게 응답하는 경우가 흔합니다.

주의 — 모든 요청에 헤징을 걸지 마세요. 실제로 꼬리 지연시간이 사용자 경험에 크게 영향을 주는 핵심 경로에만 선택적으로 적용해야 관리 복잡도가 늘어나지 않습니다.
