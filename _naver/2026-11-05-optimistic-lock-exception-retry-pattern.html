OptimisticLockException이 뜰 때 — 낙관적 락 충돌 재시도 처리 실전 패턴

데이터베이스

한 줄 요약 — OptimisticLockException은 데이터 손상이 아니라 낡은 버전으로 수정을 시도했다는 신호입니다. 새 트랜잭션에서 최신 데이터를 다시 읽어 재시도하면 대부분 해결됩니다.

 

왜 가끔씩 500 에러가 뜰까

재고 차감이나 포인트 적립처럼 동시 수정이 잦은 로직에 @Version 필드로 낙관적 락을 걸어뒀는데, 트래픽이 몰리는 시간대에만 간헐적으로 500 에러가 쌓입니다. 로그를 열어보면 ObjectOptimisticLockingFailureException이 원인입니다. 낙관적 락을 건 것 자체는 올바른데, 이 예외를 만났을 때 그대로 사용자에게 에러 화면을 보여주는 것이 문제입니다.

 

 

핵심 개념 1 — 충돌은 재시도 신호다

검증에 실패했다는 것은 데이터가 손상됐다는 뜻이 아니라, 단지 내가 읽은 시점의 데이터가 이미 낡았다는 뜻입니다. 최신 데이터를 다시 읽어 같은 로직을 다시 시도하면 대부분 성공합니다. 이 예외는 로그만 남기고 끝낼 것이 아니라 정해진 횟수만큼 재시도하는 로직으로 감싸는 것이 정석입니다.

 

핵심 개념 2 — 새 트랜잭션에서 다시 시작해야 한다

실패한 트랜잭션 안에서 그냥 다시 저장을 시도하면 안 됩니다. 이미 실패한 트랜잭션의 영속성 컨텍스트는 낡은 버전 정보를 들고 있으므로, 완전히 새로운 트랜잭션을 열어 엔티티를 다시 조회하는 것부터 재시도해야 합니다.

 

예제 — Spring Retry로 감싸기
@Service
public class InventoryService {

    @Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2)
    )
    @Transactional
    public void decreaseStock(Long itemId, int quantity) {
        Item item = itemRepository.findById(itemId)
                .orElseThrow(() -> new ItemNotFoundException(itemId));
        if (item.getStock() < quantity) {
            throw new InsufficientStockException(itemId);
        }
        item.decreaseStock(quantity);
    }

    @Recover
    public void recover(ObjectOptimisticLockingFailureException e, Long itemId, int quantity) {
        throw new StockUpdateFailedException(itemId);
    }
}

@Retryable이 재시도를 관리하고 매 시도가 새 트랜잭션이 되도록 합니다. @Recover는 재시도를 다 소진했을 때 호출되는 최종 처리 지점입니다.

 

흔한 실수와 함정
실수 결과
같은 트랜잭션 안에서 재시도 낡은 영속성 컨텍스트로 계속 실패
백오프 없이 즉시 재시도 같은 타이밍에 다시 충돌 확률 높음

충돌이 극심한 선착순 이벤트 재고 차감 같은 지점이라면, 낙관적 락 재시도보다 SELECT ... FOR UPDATE 같은 비관적 락이나 Redis 원자적 연산으로 설계를 바꾸는 것이 더 적절할 수 있습니다.

 

실무 포인트

재시도 대상 예외를 정확히 지정하세요. 모든 예외를 재시도 대상으로 잡으면 재고 부족처럼 절대 성공할 수 없는 비즈니스 예외까지 불필요하게 반복 실행됩니다.

백오프 간격에 지터(jitter)를 섞는 것도 고려하세요. 여러 요청이 동시에 충돌했다면 같은 간격으로 재시도할 때 다시 충돌할 확률이 높아집니다.

주의 — 재시도 소진 시 사용자 메시지를 "잠시 후 다시 시도해주세요"처럼 일시적 상황임을 알려주는 것이, 그냥 "오류가 발생했습니다"보다 사용자 경험 면에서 훨씬 낫습니다.
