"주문 이벤트, 지금 바로 SQL로 조회하게 해주세요" — Kafka 위에 쿼리 레이어를 직접 얹을 것인가, 관리형 테이블로 뗄 것인가

시스템 설계

한 줄 요약 — 주문 이벤트가 Kafka에 쌓이는데 대시보드와 에이전트가 그걸 SQL·MCP로 바로 조회하게 해달라는 요구가 들어옵니다. Confluent Lightning Tables의 GA를 계기로, 직접 스트림 프로세서를 얹을지 관리형 쿼리 레이어로 뗄지 판단하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"주문 상태가 바뀌는 순간 운영팀 대시보드에서, 고객 응대 에이전트도 바로 확인할 수 있게 해주세요"라는 요구는 이벤트 기반 아키텍처를 쓰는 팀이라면 한 번쯤 받습니다. 문제는 Kafka 토픽이 원래 "조회용"이 아니라 "전달용"으로 설계됐다는 점입니다.

2026년 11월 8일, Confluent는 Lightning Tables를 AWS 리전에 GA로 내놓았습니다. Kafka 토픽 위에 올리는 읽기 전용 레이어로, SQL·REST API·MCP로 토픽의 현재 상태를 바로 조회할 수 있게 해줍니다. 반대쪽에는 기존 정석인 ksqlDB·Flink로 토픽을 머티리얼라이즈드 뷰로 집계해 자체 서빙 저장소에 꽂는 방식이 있습니다. 둘 다 목표는 같지만 신선도·운영 부담·확장성에서 결과가 갈립니다.

 

전체 시스템에서의 위치

주문 이벤트가 Kafka 토픽에 들어온 뒤 조회 가능한 형태로 바뀌기까지 세 경로가 있습니다. ①직접 구축(Flink/ksqlDB 집계 후 자체 저장소), ②관리형 쿼리 레이어(Lightning Tables류, 서빙 저장소 없이 바로 SQL/MCP), ③CDC+웨어하우스(신선도보다 분석 표현력 우선)입니다. 세 경로는 공존 가능하며, 요구의 성격에 따라 경로를 나눠야 합니다.

 

선택의 트레이드오프
기준① 직접 구축② 관리형 레이어③ CDC+웨어하우스
신선도초 단위초 단위분~시간
운영 부담직접 다벤더가 흡수ETL 운영
쿼리 표현력자유로운 설계벤더 범위 제한풍부한 분석 SQL

 

세 경로 모두 "정답"이 아니라 "다른 걸 포기하는 선택"입니다. 요구의 성격을 먼저 분류하지 않고 하나의 레이어로 전부 받으려 하면 어느 쪽도 제대로 못 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 "얼마나 신선해야 하는가"를 숫자로 못박습니다. "실시간"이라는 말은 각자 다르게 해석하므로 합의가 먼저입니다. 그다음 토픽 스키마를 레지스트리에 명시적으로 등록해 둡니다.

-- Flink SQL로 직접 구축할 때의 머티리얼라이즈드 뷰 예시
CREATE TABLE order_status_view AS
SELECT order_id,
       LAST_VALUE(status) AS current_status,
       MAX(event_time) AS updated_at
FROM order_events
GROUP BY order_id;

작은 범위(주문 상태 하나)로 먼저 PoC를 돌려 신선도·쿼리 지연·비용을 양쪽 경로에서 실측합니다. 조회 패턴이 늘어나면, 단순 상태 조회는 관리형 레이어에 남기고 복잡한 집계만 별도 파이프라인으로 분리하는 하이브리드 구성으로 넘어갑니다. 어떤 경로를 택하든 조회 레이어는 토픽의 파생물이지 원본이 아니라는 원칙을 지켜, 장애 시 토픽을 재생해 통째로 다시 만들 수 있는 재구성 경로를 처음부터 설계해 둡니다.

 

주의 — 관리형 레이어가 지원하는 조인·집계 범위를 우리 쿼리 패턴이 벗어나는지 PoC 단계에서 반드시 확인하세요. 벗어난다면 처음부터 직접 구축으로 가는 게 나중에 마이그레이션하는 것보다 쌉니다.
