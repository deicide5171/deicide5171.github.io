누가 대장을 할 것인가 — 분산 시스템 리더 선출 패턴 정리

2026. 8. 24. · 아키텍처/시스템 설계

한 줄 요약 — 분산 환경에서 "이 작업은 하나의 노드만 해야 한다"는 요구를 리스(lease)와 펜싱 토큰으로 안전하게 보장하는 방법을, ZooKeeper와 etcd 구현 비교로 정리했습니다.

 

왜 리더 선출이 필요할까요

배치 스케줄러, 파티션 리밸런서, 단일 쓰기 노드를 요구하는 복제 시스템 — 분산 환경에서도 "이 작업은 딱 하나의 인스턴스만 해야 한다"는 요구는 끊임없이 등장합니다. 인스턴스를 여러 대 띄워 가용성을 확보하면서도 동시에 정확히 하나만 활성 상태이길 바라는 이 모순적인 요구를 푸는 것이 리더 선출(leader election)입니다.

문제는 "리더가 죽었는지"를 분산 환경에서 확실히 아는 방법이 없다는 데 있습니다. 네트워크 지연과 진짜 장애를 구분할 수 없기 때문에, 순진하게 하트비트만으로 리더를 교체하면 옛 리더가 살아있는데 새 리더도 선출되는 split-brain이 발생합니다.

 

핵심 개념 1 — 순수 하트비트의 한계와 리스 모델

가장 단순한 접근은 일정 시간 하트비트가 없으면 죽은 것으로 간주하고 다음 노드가 리더가 되는 것입니다. 그러나 네트워크가 일시적으로 끊긴 것뿐이라면, 원래 리더는 여전히 리더라고 믿은 채 계속 쓰기 작업을 수행하고, 동시에 새로 선출된 리더도 쓰기 작업을 수행하는 상황이 생깁니다.

이를 막는 표준 해법이 리스(lease)입니다. 리더는 "이 시각까지 내가 리더"라는 시간 제한이 있는 임대권을 조정 서비스로부터 발급받고, 만료 전에 갱신하지 못하면 자동으로 리더 자격을 잃습니다. TTL이 너무 짧으면 정상 노드도 일시적 지연으로 리더를 잃고, 너무 길면 실제 장애 감지가 늦어집니다.

 

핵심 개념 2 — 펜싱 토큰, 리스만으로는 부족합니다

리스가 만료됐다고 옛 리더가 즉시 활동을 멈추는 것은 아닙니다. GC 정지나 스케줄링 지연으로 "리스가 만료된 줄 모르는 좀비 리더"가 뒤늦게 쓰기 요청을 보낼 수 있습니다. 이를 막는 장치가 펜싱 토큰(fencing token)입니다. 조정 서비스는 리더가 바뀔 때마다 단조 증가하는 토큰을 발급하고, 실제 자원은 더 작은 토큰의 쓰기 요청을 거부하는 규칙을 강제합니다.

 

 

핵심 개념 3 — ZooKeeper vs etcd 구현 비교
구분 ZooKeeper etcd
합의 알고리즘 ZAB Raft
선출 메커니즘 임시 순차 znode 중 최소 번호 Lease + campaign API
펜싱 토큰 znode 버전(zxid) revision 번호
대표 라이브러리 Curator LeaderLatch clientv3 concurrency.Election

 

Kubernetes 자체도 컨트롤러 매니저·스케줄러의 다중 인스턴스 중 하나만 활성화하기 위해 client-go의 leaderelection 패키지로 이 패턴을 그대로 씁니다. Lease 오브젝트에 리더 정보와 갱신 시각을 기록하는 방식입니다.

 

예제 — etcd concurrency 패키지로 리더 선출
session, _ := concurrency.NewSession(cli, concurrency.WithTTL(10))
defer session.Close()

election := concurrency.NewElection(session, "/services/order-scheduler/")

if err := election.Campaign(ctx, "node-a"); err != nil {
    log.Fatal(err)
}
log.Println("리더로 선출됨:", session.Lease())
// 리더인 동안에만 수행할 작업
// session이 만료되거나 Resign()이 호출되면 리더십 상실

 

실무 도입 시 이것만은 챙기세요
1. 리스 TTL은 네트워크 지연 분포를 보고 정하세요 — p99 왕복 지연과 GC 정지 시간을 감안하지 않고 짧게 잡으면 재선출이 반복되는 진동 현상이 생깁니다.
2. 애플리케이션 계층에서 펜싱을 강제해야 합니다 — 조정 서비스가 토큰을 발급해도 실제 자원이 토큰을 검증하지 않으면 무용지물입니다.
3. Redis 기반 락을 리더 선출 대용으로 쓸 때는 신중하세요 — 강한 일관성이 필요하다면 합의 프로토콜 기반 조정 서비스가 안전한 기본값입니다.

 

마무리 — 3줄 요약

① 분산 리더 선출의 핵심 난제는 네트워크 지연과 진짜 장애를 구분할 수 없다는 것이며, 이를 리스의 TTL로 관리합니다.
② 리스 만료만으로는 좀비 리더의 지연된 쓰기를 막을 수 없어, 단조 증가하는 펜싱 토큰으로 실제 자원 쪽에서 오래된 리더의 요청을 거부해야 합니다.
③ ZooKeeper는 ZAB, etcd는 Raft 기반으로 같은 문제를 풀며, Kubernetes 컨트롤러도 동일한 패턴을 사용합니다.
