PodDisruptionBudget과 노드 드레인 — 클러스터 유지보수 중에도 가용성 지키기

네트워크·OS·분산처리·DevOps

한 줄 요약 — 노드 드레인 중 동시에 종료 가능한 파드 수를 제한해 서비스 가용성을 지키는 PodDisruptionBudget의 동작 원리를 정리했습니다.

 

왜 지금 PodDisruptionBudget을 다시 봐야 하는가

노드 커널 패치나 오토스케일러의 노드 축소 작업은 정기적으로 발생합니다. 문제는 replicas 3인 서비스의 파드가 우연히 같은 노드 몇 곳에 몰려 있다면, 드레인 한 번으로 서비스 전체가 동시에 종료될 수 있다는 점입니다. PDB는 이런 자발적 중단 상황에서 동시에 죽어도 되는 파드 수의 상한선을 명시적으로 강제합니다.

 

minAvailable과 maxUnavailable의 차이

PDB는 minAvailable(항상 유지할 최소치) 또는 maxUnavailable(허용할 최대 중단치) 중 하나로 예산을 정의합니다. HPA로 replicas가 계속 변하는 워크로드라면 maxUnavailable을 퍼센트로 지정하는 편이 스케일 변화에 자동으로 대응해 더 안전합니다. PDB 자체는 파드를 종료·재생성하지 않으며, 자발적 종료 요청이 예산을 넘기면 그 요청을 거부하는 가드레일 역할만 합니다.

 

Eviction API와 드레인 절차가 PDB를 만나는 지점

kubectl drain은 파드를 직접 삭제하지 않고 Eviction API를 통해 축출 가능 여부를 API 서버에 묻습니다. 예산이 소진된 상태라면 API 서버는 오류를 반환하고, drain은 해당 파드를 건너뛰었다가 예산이 회복되면 재시도합니다. 다만 이 메커니즘은 노드가 갑자기 죽는 비자발적 중단에는 적용되지 않는다는 한계가 있습니다.

항목 minAvailable maxUnavailable
의미 항상 유지될 최소 가용 파드 수 동시 허용 최대 중단 파드 수
HPA와 함께 절대값이면 과도하게 제약적일 수 있음 퍼센트 지정 시 스케일에 자동 비례

 

PDB 정의와 드레인 확인 예제
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
spec:
  maxUnavailable: 25%
  selector:
    matchLabels:
      app: payment-api

# 드레인 시도
kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data

# 현재 예산 여유분 확인
kubectl get pdb payment-api-pdb -o jsonpath='{.status.disruptionsAllowed}'

 

실무 포인트

replicas가 1~2개인 워크로드에 maxUnavailable: 0을 걸면 드레인이 영원히 멈출 수 있습니다. 최소 replicas 수를 늘리거나 예산을 현실적인 값으로 조정해야 합니다.

PDB만으로는 부족합니다 — Topology Spread Constraints와 함께 써야 실효성이 있습니다. PDB는 몇 개까지 죽어도 되는지만 정할 뿐, 애초에 같은 노드에 몰리는 것은 막지 못합니다.

주의 — 클라우드 관리형 노드 자동 업그레이드도 내부적으로 Eviction API를 쓰므로 PDB의 보호를 그대로 받습니다. 관리형 서비스라고 PDB 설정을 소홀히 하면 자동 업그레이드 중 예기치 않은 중단을 겪을 수 있습니다.
