위성사진에 자연어로 질문한다는 것 — 지리공간 멀티 파운데이션 모델 오케스트레이션

GIS

한 줄 요약 — "전국 매장 중 옥상에 냉방 설비가 없는 곳을 찾아주세요"라는 요구는 더 이상 객체탐지 모델 하나를 새로 학습시키는 문제가 아닙니다. Google의 Geospatial Reasoning처럼 여러 전문 파운데이션 모델을 LLM이 조율해 자연어 질의에 답하는 멀티모델 오케스트레이션 구조와, 기존 임베딩 재사용 전략과 어떻게 다른 판단인지 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"전국 매장 중 옥상에 냉방 설비가 없는 지점을 찾아서 보고서로 만들어주세요." 시설관리팀에서 이런 요구가 내려오면, 과거의 답은 늘 비슷했습니다. 위성·항공 이미지를 구매하고, 라벨링 팀을 꾸려 "냉방 설비"가 찍힌 수천 장의 샘플에 바운딩 박스를 그리고, 객체탐지 모델을 파인튜닝한 뒤, 그 모델을 전국 타일에 돌려 좌표를 뽑아냅니다. 몇 주에서 몇 달이 걸리는 파이프라인입니다.

Google Research가 2026년 하반기 공개 범위를 넓힌 Geospatial Reasoning은 이 흐름 자체를 바꿉니다. 분석가가 "대형 HVAC 냉방탑이 있는 건물을 찾아줘" 같은 평범한 문장을 입력하면, 시스템이 그 문장을 지리공간 작업으로 분해하고, 객체 인식·변화 탐지·토지 피복 분류 등 이미 학습된 여러 전문 파운데이션 모델 중 적합한 것을 골라 호출한 뒤, 결과를 지도 위에 합성해 돌려줍니다. 모델을 새로 학습시키는 대신 이미 존재하는 전문 모델들을 오케스트레이션하는 에이전트 레이어를 추가하는 접근입니다.

 

요구사항을 기술 문제로 번역하기

자연어로 들어오는 지리공간 질의는 실제로는 서로 다른 성격의 하위 작업으로 쪼개집니다. "냉방 설비가 없는 건물을 찾아줘"는 ①대상 지역의 건물 풋프린트를 특정하고(공간 필터링), ②각 건물 옥상 이미지에서 특정 객체의 유무를 판별하고(객체 탐지), ③결과를 신뢰도 순으로 정렬해 사람이 검토할 수 있는 형태로 묶는(결과 합성) 세 단계로 번역됩니다. 여기에 "작년과 비교해 새로 생긴 걸 찾아줘"가 섞이면 변화 탐지 모델이, "숲인지 농경지인지 구분해줘"가 섞이면 토지 피복 분류 모델이 추가로 필요해집니다.

 

전체 시스템에서의 위치

 

질의가 들어오는 입구에는 오케스트레이터 역할을 하는 LLM이 있습니다. 이 모델 자체는 픽셀을 직접 보지 않습니다. 대신 함수 호출(tool-calling) 형태로 전문 모델에 작업을 위임합니다. 전문 모델들은 뒷단의 위성·항공 이미지 타일 인덱스(STAC 카탈로그나 클라우드 네이티브 래스터 저장소)를 조회해 실제 추론을 수행하고, 그 결과를 오케스트레이터에게 돌려줍니다. 오케스트레이터는 여러 모델의 결과를 하나의 지도 레이어로 합성합니다. 이 구조에서 앞단은 자연어 인터페이스, 뒷단은 기존 GIS 파이프라인과 그대로 맞닿아 있습니다 — 오케스트레이션 레이어가 그 사이에 새로 끼어든 셈입니다.

 

선택의 트레이드오프
기준 단일 end-to-end 모델 전문 모델 오케스트레이션 기존 수작업 GIS 분석
정확도(좁은 태스크) 중간 높음 높음
신규 질의 대응 속도 빠름 중간 느림
결과 설명가능성 낮음 중간~높음 높음
전국 단위 스케일 가능하나 검증 어려움 가능 사실상 불가능

 

결정적인 줄은 "설명가능성"입니다. 단일 거대 모델이 "이 건물에 냉방 설비가 있다"고 답하면 왜 그렇게 판단했는지 추적하기 어렵습니다. 반면 오케스트레이션 구조에서는 "객체 탐지 모델이 이 바운딩 박스에서 0.87 신뢰도로 탐지했다"는 식으로 책임 소재가 모델 단위로 분리됩니다. 오탐이 실제 비용(인력 파견, 오판)으로 이어지는 도메인에서는 이 추적 가능성이 정확도 수치보다 더 중요한 선택 기준이 됩니다.

 

기존 임베딩 재사용 전략과의 차이

위성 이미지 파운데이션 모델을 처음부터 학습할지, 사전계산된 임베딩(AlphaEarth·Clay류)에 분류기만 얹을지를 고르는 문제는 "표현을 누가 만들 것인가"에 대한 질문이었습니다. 이번 오케스트레이션은 다른 층위입니다 — 표현 학습이 이미 끝난 여러 전문 모델이 존재한다고 가정하고, 그 모델들을 자연어 질의 하나에 어떻게 조합해 호출할지를 다룹니다. 실제 프로젝트에서는 임베딩으로 저비용 1차 필터링을 하고, 그 결과를 오케스트레이터가 정교한 전문 모델로 재확인하는 2단계 구조로 결합되는 경우가 많습니다.

 

실제 프로젝트 진행 순서

1단계: 어떤 종류의 자연어 질문이 들어올지부터 목록화합니다. 객체 탐지만으로 끝나는 질의와 변화 탐지·시계열 분석까지 필요한 질의는 다른 전문 모델 조합을 요구합니다.

2단계: 전문 모델은 자체 학습보다 기존 상용·오픈 모델을 먼저 검토하고, 도메인 특화가 정말 필요한 지점에서만 파인튜닝을 고려합니다.

3단계: 오케스트레이터의 함수 호출 스키마를 먼저 설계합니다. 각 모델이 어떤 입력을 받고 어떤 형태로 결과를 반환하는지 명확히 정의해야 LLM이 올바르게 위임할 수 있습니다.

4단계: 신뢰도 임계값과 사람 검수 루프를 처음부터 넣습니다. 일정 신뢰도 이하 결과는 자동 승인하지 않고 사람에게 넘기는 게이트를 설계 단계에서 박아둡니다.

5단계: 비용과 지연시간을 질의 단위로 계측합니다. 여러 모델을 순차 호출하는 구조는 지연시간이 누적되기 쉬우므로 어떤 호출이 병목인지 초기부터 추적합니다.

주의 — LLM이 질의를 잘못 해석해 변화 탐지가 필요한데 객체 탐지만 호출하는 경우가 실제로 발생합니다. 함수 호출 로그를 남겨 어떤 모델이 왜 선택됐는지 사후 추적이 가능해야 하고, 범위가 고정된 좁은 문제에는 오케스트레이션을 과하게 적용하지 않는 편이 낫습니다.

 

정리

자연어 지리공간 질의는 공간 필터링·객체 탐지·변화 탐지·결과 합성 같은 서로 다른 하위 작업으로 번역되며, 이를 전문 모델 하나로 전부 처리하려 하기보다 LLM 오케스트레이터가 적절한 전문 모델에 위임하는 구조가 현재 더 실용적입니다. 다만 모델 간 호출이 누적되며 지연시간과 비용이 쌓이는 트레이드오프가 있으니, 범위가 고정된 문제라면 오케스트레이션 없이 전문 모델을 직접 쓰는 편이 나을 수 있습니다.
