지도 하나 더 열 때마다 좌표계 맞추는 코드를 또 짜고 있다 — Giro3D·iTowns와 수동 합성 중 고르는 기준

GIS

한 줄 요약 — OpenLayers 지도 위에 three.js로 3D 건물을 올리는 PoC가 성공할 때마다 좌표계 동기화 코드를 또 손으로 짜고 있다면, 그건 이미 프레임워크가 풀어야 할 문제입니다. Giro3D·iTowns 같은 전용 3D 지리공간 프레임워크로 넘어갈 시점을 판단하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"2D 지도 위에 3D 건물을 올려주세요"라는 요구를 OpenLayers와 three.js를 직접 붙여 풀어낸 팀은, 얼마 지나지 않아 비슷한 요구를 또 받습니다. "이번엔 포인트클라우드도 같이 보여주세요", "건물 돌출(extrusion)도 되나요", "다른 좌표계로 들어온 데이터도 섞어주세요". 그때마다 답은 같습니다 — 좌표계 재투영 코드를 또 짜고, 두 렌더 루프를 맞추는 동기화 코드를 또 손봅니다. 이 반복 자체가 신호입니다. 문제는 "3D를 어떻게 띄울까"가 아니라 "이 글루 코드를 언제까지 직접 들고 갈 것인가"로 이미 옮겨가 있습니다.

이 글이 다루는 건 OpenLayers+three.js를 이미 붙이기로 정한 다음의 성능·피킹 문제가 아니라, 그보다 한 단계 앞선 질문입니다. 같은 문제를 반복해서 겪고 있다면, 애초에 직접 합성 대신 전용 3D 지리공간 프레임워크를 채택하는 선택지를 지금 검토해야 하는가입니다.

Oslandia가 2025년 12월 1.0을 낸 Giro3D는 OpenLayers를 2D 지도 엔진으로, three.js를 3D 렌더러로 쓰면서 그 사이의 좌표계 재투영, 래스터 변환, 3D 건물 돌출 표현을 프레임워크 레벨에서 끝내놓은 라이브러리입니다. 프랑스 국토지리원(IGN)이 지원하는 iTowns도 같은 계열입니다 — three.js 기반으로 2D·3D 지리공간 데이터를 함께 다루며, 3D Tiles와 포인트클라우드(COPC·EPT·Potree) 로딩을 표준 지원합니다.

 

전체 시스템에서의 위치

직접 합성 구조에서는 OpenLayers와 three.js가 각자 독립된 렌더 루프와 좌표계를 갖고, 그 사이를 잇는 동기화 레이어를 팀이 직접 작성해 유지합니다. 신규 데이터 포맷이나 좌표계가 들어올 때마다 이 동기화 레이어에 변환 로직이 하나씩 쌓입니다. 처음엔 코드 몇 줄이지만, 데이터 소스가 늘어날수록 이 레이어 자체가 하나의 미니 프레임워크로 자라납니다 — 다만 테스트도, 문서도, 유지보수 담당자도 없는 프레임워크입니다.

Giro3D·iTowns를 채택하면 이 동기화 책임이 프레임워크 내부로 들어갑니다. 애플리케이션 코드는 "이 레이어를 이 좌표계로 추가해달라"는 선언만 하면 되고, 재투영·타일링·3D 오브젝트 배치는 프레임워크가 맡습니다. 대신 팀이 작성한 변환 로직 전체를 프레임워크 API로 다시 써야 하는 마이그레이션 비용이 한 번 발생합니다.

 

선택의 트레이드오프
선택지강점약점언제 쓰면 안 되는가
수동 합성완전한 제어글루 코드가 비공식 프레임워크로 자람포맷·좌표계가 계속 늘어날 로드맵인 경우
Giro3DCRS 재투영·건물 돌출 내장1.0 출시가 최근이라 레퍼런스 얇음포인트클라우드가 당장 핵심인 경우
iTownsIGN 검증, 포인트클라우드 성숙API가 지구본형 중심2D 지도가 주력인 경우
Cesium 전면 전환진짜 3D 지구본·지형전면 재구축 필요기존 2D UX 자산을 유지해야 하는 경우

 

Giro3D·iTowns는 "OpenLayers 중심 2D 지도에 3D를 자연스럽게 얹는" 선택지이고, Cesium 전환은 "애초에 3D 지구본이 주인공이고 2D는 그 위의 투영일 뿐"이라는 완전히 다른 출발점입니다. 지금 서비스가 2D 지도 UX를 이미 OpenLayers 생태계로 다 갖춰 놓은 상태라면, Cesium 전면 전환보다 Giro3D·iTowns 쪽을 먼저 검토하는 것이 합리적입니다.

 

실제 진행 순서

1) 지금 유지보수 중인 좌표계·렌더 루프 동기화 코드의 규모를 먼저 측정합니다. 파일 하나, 함수 몇 개 수준이라면 아직 전환할 때가 아닙니다. 2) 대표 레이어 몇 개만 골라 Giro3D 또는 iTowns로 PoC를 만들어 기존과 렌더링 품질을 비교합니다. 3) 포인트클라우드가 급하면 iTowns, 래스터 재투영·건물 돌출이 급하면 Giro3D를 고릅니다. 4) 기존 OpenLayers 스타일·데이터 연결 코드를 레이어 단위로 쪼개 단계적으로 옮깁니다. 5) 프레임워크의 피킹 API가 기존 커스텀 레이캐스트 로직과 다른 좌표 기준을 쓸 수 있으니 먼저 검증합니다.

 

주의 — 전체 레이어를 한 번에 옮기면 회귀 테스트 범위가 감당이 안 됩니다. 반드시 레이어 단위로 PoC → 검증 → 단계적 마이그레이션 순서를 지켜야 합니다.
