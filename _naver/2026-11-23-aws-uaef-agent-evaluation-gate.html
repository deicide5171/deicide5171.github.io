"에이전트 프레임워크 바꾸는 중인데, 진짜 좋아진 거 맞나요?" — AWS UAEF로 설계하는 프레임워크 중립 평가 게이트

AI

한 줄 요약 — AWS가 2026년 11월 공개한 오픈소스 UAEF는 LangGraph·LangChain·Strands·AgentCore 트레이스를 하나의 형식으로 모아 36개 지표로 채점합니다. 프레임워크를 갈아타도 버전 간 품질을 같은 기준으로 비교하는 회귀 게이트를 어떻게 설계하는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"에이전트 프레임워크를 LangGraph에서 Strands Agents로 옮기려고 하는데, 바꾸고 나서 품질이 떨어지지 않는지 확인 좀 해주세요." 이런 요청을 받으면 대부분의 팀은 수동으로 질문 몇 개를 던져보고 감으로 승인합니다. 프레임워크마다 트레이스 포맷이 다르고 평가 도구도 특정 생태계에 묶여 있어서, "버전 A와 버전 B를 같은 기준으로 비교"하는 일 자체가 어렵기 때문입니다.

AWS는 2026년 11월 11일 이 공백을 겨냥한 오픈소스 도구 UAEF(Universal Agent Evaluation Framework)를 Apache-2.0 라이선스로 공개했습니다. 여러 프레임워크의 트레이스를 하나의 canonical 형식으로 변환한 뒤, 7개 차원에 걸친 36개 내장 지표로 동일하게 채점합니다. 텔레콤·헬스케어·금융 12개 조직이 사전에 이 도구로 릴리스 전 버전 비교를 했다는 점도 "프레임워크 중립 평가"가 이제 실무 요구라는 신호입니다.

 

전체 시스템에서의 위치

에이전트 평가는 모델 평가와 다른 자리에 있습니다. 모델 벤치마크는 모델 하나의 출력을 채점하지만, 에이전트 평가는 오케스트레이터·도구 호출·서브에이전트까지 얽힌 실행 트리 전체를 봐야 합니다. UAEF의 어댑터는 프레임워크마다 제각각인 스팬 구조를 하나의 canonical 트레이스 레코드로 눌러, 뒤따르는 메트릭 엔진이 어떤 프레임워크에서 왔는지 신경 쓰지 않게 만듭니다. 36개 지표 중 24개는 Bedrock의 LLM 판정을 호출하는데, 이는 평가 엔진 자체가 외부 서비스 가용성과 비용에 묶인다는 뜻입니다. 점수가 5% 넘게 떨어지면 경미·보통·심각 세 등급으로 분류돼 CI 배포 게이트의 입력이 됩니다.

 

선택의 트레이드오프
방식프레임워크 커버리지비용·의존성보안 판단 용도
UAEFLangGraph·LangChain·Strands·AgentCore 등 + 커스텀 어댑터24개 지표가 Bedrock 판정 의존AWS가 명시적으로 비권장
벤더 전용 평가 도구자사 생태계에만 강함벤더 요금제 종속도구마다 다름
자체 LLM-as-judge 스크립트자유 설계직접 운영 비용 전부 부담설계 나름, 책임도 내부
순수 사람 수동 평가제약 없음인건비·시간 가장 큼민감한 판단에 가장 신뢰 가능

 

이 표에서 가장 중요한 줄은 "보안 판단 용도"입니다. UAEF는 품질·회귀 비교에는 강하지만, AWS 스스로 보안 결정에는 쓰지 말라고 명시했습니다. "프레임워크를 갈아타도 품질이 유지되는가"는 UAEF 같은 canonical 평가 도구로 답하고, "보안 취약점이 없는가"는 별도의 보안 리뷰 절차로 분리해야 합니다. 하나의 게이트에 두 질문을 섞으면 둘 다 어설프게 답하게 됩니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 도구를 설치하는 게 아니라, 7개 평가 차원 중 우리 서비스에서 실제로 중요한 차원을 선정하는 것입니다. 모든 지표를 다 켜면 24개의 Bedrock 판정 호출이 매 릴리스마다 비용으로 쌓이기 때문입니다.

baseline = LangGraphAdapter().load("traces/v1/")
candidate = StrandsAdapter().load("traces/v2/")

evaluator = Evaluator(dimensions=["task_completion", "tool_call_accuracy"])
report = evaluator.compare(
    evaluator.score(baseline), evaluator.score(candidate),
    regression_threshold=0.05
)
# report.severity: "minor" | "moderate" | "severe"

검증이 끝나면 현재 프로덕션 버전의 점수를 베이스라인으로 고정하고, 이후 모든 변경은 이 베이스라인과 비교해 회귀 등급을 받도록 CI에 넣습니다. "심각" 등급은 배포를 자동 차단하고, "경미"는 로그만 남기는 식으로 등급별 대응을 미리 정해둡니다. 보안 관련 판단은 이 게이트에서 완전히 분리해 기존 보안 리뷰 프로세스를 그대로 유지해야 합니다.

 

주의 — 평가 도구 하나가 품질 회귀와 보안 판단을 동시에 떠맡는 순간, 그 도구의 한계가 곧 조직의 맹점이 됩니다. UAEF 같은 도구는 "품질 비교"에만 쓰고 보안 판단은 분리하세요.
