GraalVM 네이티브 이미지로 Spring Boot 콜드스타트 없애기

2026. 8. 20. · 백엔드

한 줄 요약 — 서버리스·오토스케일링 환경에서 JVM의 JIT 워밍업 지연이 발목을 잡는 상황이 늘고 있어, GraalVM 네이티브 이미지로 Spring Boot 애플리케이션을 미리 컴파일해 콜드스타트를 없애는 방법과 그 한계를 정리해 봤습니다.

 

왜 지금 이 이야기를 해야 할까요

전통적인 JVM 애플리케이션은 처음엔 인터프리터로 코드를 실행하다가, 자주 호출되는 부분을 JIT(Just-In-Time) 컴파일러가 뒤늦게 네이티브 코드로 최적화하는 방식으로 동작합니다. 오래 떠 있는 서버라면 이 워밍업 구간이 전체 수명에서 차지하는 비중이 작아 크게 신경 쓸 일이 없었습니다. 하지만 서버리스 함수나 오토스케일링으로 인스턴스가 수시로 뜨고 내려가는 환경에서는 이야기가 달라집니다. 새 인스턴스가 뜰 때마다 클래스 로딩과 JIT 웜업을 처음부터 다시 거쳐야 하고, 그 구간 동안 응답 지연이 눈에 띄게 늘어나기 때문입니다.

이 문제의 근본 원인은 JVM이 "실행하면서 최적화 대상을 찾는" 런타임 중심 설계라는 데 있습니다. GraalVM 네이티브 이미지는 이 구조 자체를 바꿔, 애플리케이션을 배포 전에 미리 네이티브 실행 파일로 컴파일해 두는 방식을 택합니다. 오늘은 Spring Boot 애플리케이션을 네이티브 이미지로 빌드하는 과정과, 그 대가로 감수해야 하는 제약사항을 정리해 보겠습니다.

 

핵심 개념 1 — AOT 컴파일과 JIT은 무엇이 다를까요

JIT은 애플리케이션이 실행되는 동안 실제 호출 빈도와 타입 정보를 관찰해 최적화 대상을 동적으로 판단합니다. 반면 AOT(Ahead-Of-Time) 컴파일은 빌드 시점에 도달 가능한 코드 전체를 정적으로 분석해 미리 네이티브 기계어로 컴파일해 버립니다. GraalVM 네이티브 이미지는 애플리케이션이 실제로 쓸 가능성이 있는 클래스·메서드만 빌드 시점에 그래프로 추적하는 "닫힌 세계(closed-world)" 가정을 전제로 하는데, 이 때문에 런타임에 새 클래스를 동적으로 로드하거나 처음 보는 코드 경로가 나타나는 상황은 원칙적으로 허용하지 않습니다.

구분 JIT (기존 JVM) AOT (네이티브 이미지)
최적화 시점 실행 도중 동적으로 판단 빌드 시점에 미리 완료
클래스 로딩 런타임에 자유롭게 동적 로딩 닫힌 세계 가정, 사전에 전부 확정
기동 속도 JVM 부트스트랩 + 웜업 필요 네이티브 코드로 즉시 시작
리플렉션 제약 없이 자유롭게 사용 힌트 설정 없이는 누락 위험

 

핵심 개념 2 — Spring Boot는 AOT 처리를 어떻게 끼워 넣나요

Spring 프레임워크는 원래 컴포넌트 스캔, 조건부 빈 등록, 프록시 생성처럼 런타임 리플렉션에 의존하는 작업이 많았습니다. 이는 닫힌 세계 가정과 정면으로 충돌하기 때문에, Spring Framework 6과 Spring Boot 3부터는 별도의 Spring AOT 처리 단계를 빌드 과정에 넣었습니다. 이 단계에서 스프링은 애플리케이션 컨텍스트를 미리 한 번 구동해 보면서 빈 정의와 프록시 대상을 분석하고, 그 결과를 네이티브 이미지 빌드에 필요한 힌트 메타데이터와 초기화 코드로 미리 생성해 둡니다.

이후 GraalVM의 native-image 도구가 이 산출물과 애플리케이션 클래스 전체를 정적으로 분석해 하나의 독립 실행 파일로 컴파일합니다. 개발자 입장에서는 평소처럼 Gradle이나 Maven의 네이티브 빌드 플러그인을 통해 이 과정 전체를 한 번의 빌드 명령으로 실행하게 됩니다.

 

핵심 개념 3 — 네이티브 이미지가 감수하는 제약사항

닫힌 세계 가정은 성능의 원천이자 동시에 제약의 원천입니다. 리플렉션으로 클래스를 동적으로 조회하거나, JDK 동적 프록시로 인터페이스를 즉석에서 구현하거나, 클래스패스에서 리소스를 런타임에 스캔하는 코드는 정적 분석기가 그 대상을 미리 알 수 없어 기본적으로 누락되기 쉽습니다. 이런 경우 reflect-config.json 등 GraalVM Reachability Metadata로 "이 클래스와 메서드는 리플렉션 대상이니 포함하라"고 명시적으로 알려주어야 합니다. Spring Boot와 주요 스타터는 이미 상당수의 힌트를 라이브러리 차원에서 제공하지만, 팀에서 직접 작성한 리플렉션 기반 코드나 서드파티 라이브러리는 이 힌트가 없을 수 있어 개별 검증이 필요합니다.

 

예제: 빌드 명령어와 설정 파일
# Gradle 네이티브 이미지 빌드 (GraalVM 네이티브 빌드 도구 플러그인 적용 시)
./gradlew nativeCompile

# 빌드된 실행 파일 직접 구동
./build/native/nativeCompile/myapp

 

// build.gradle
plugins {
    id 'org.springframework.boot' version '3.x.x'
    id 'org.graalvm.buildtools.native' version '0.1x.x'
}

graalvmNative {
    binaries {
        main {
            buildArgs.add('--enable-preview')
        }
    }
}

 

<!-- pom.xml: Spring Boot 3 프로젝트에 기본 포함되는 native 프로파일 예시 -->
<profiles>
  <profile>
    <id>native</id>
    <build>
      <plugins>
        <plugin>
          <groupId>org.graalvm.buildtools</groupId>
          <artifactId>native-maven-plugin</artifactId>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>

 

실무 도입 시 이것만은 챙기세요
1. 빌드 시간이 상당히 늘어납니다 — 정적 분석과 네이티브 컴파일 단계가 추가되므로, 로컬 반복 개발보다는 CI 파이프라인의 배포 단계에 배치하는 편이 실용적입니다.
2. 리플렉션 힌트 설정은 선택이 아니라 필수 검증 항목입니다 — 자체 코드나 힌트가 없는 라이브러리를 쓴다면 네이티브 빌드 이후 반드시 통합 테스트로 런타임 실패를 걸러내야 합니다.
3. 모든 라이브러리가 네이티브 이미지와 호환되는 것은 아닙니다 — 도입 전에 주요 의존성이 GraalVM Reachability Metadata Repository에 등록되어 있는지 먼저 확인하는 편이 시행착오를 줄여 줍니다.

 

마무리 — 3줄 요약

① JVM은 런타임에 최적화 대상을 찾는 JIT 구조라서 서버리스·오토스케일링 환경에서는 매 기동마다 워밍업 지연이 반복됩니다.
② GraalVM 네이티브 이미지는 애플리케이션을 빌드 시점에 정적으로 분석해 하나의 실행 파일로 AOT 컴파일하며, Spring Boot는 별도의 Spring AOT 처리 단계로 런타임 리플렉션 의존을 최소화해 이를 지원합니다.
③ 다만 닫힌 세계 가정 때문에 리플렉션·동적 프록시 등은 별도 힌트 설정이 필요하고, 빌드 시간 증가와 라이브러리 호환성 문제를 실무 도입 전에 검증해야 합니다.
