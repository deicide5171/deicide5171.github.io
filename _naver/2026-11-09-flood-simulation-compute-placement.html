주민들이 침수 위험을 지도에서 바로 확인하게 해주세요 — 침수 시뮬레이션, 연산을 어디서 돌릴 것인가

GIS

한 줄 요약 — '장마철에 우리 동네가 얼마나 잠기는지 지도에서 바로 보여주세요'라는 요구는 침수 시뮬레이션을 서버에서 미리 다 돌려둘지, 예보값만 서버가 주고 클라이언트가 그 자리에서 지오프로세싱할지, 아예 물리 모델 전체를 브라우저에서 돌릴지를 가르는 연산 배치 문제입니다. 세 방식의 실제 사례와 선택 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"장마철마다 민원이 쏟아지는데, 주민들이 자기 동네가 얼마나 잠기는지 지도 켜서 바로 확인하게 해주세요." 지자체나 보험사, 부동산 플랫폼에서 이런 요구를 받으면 팀은 보통 침수 시뮬레이션 엔진을 어떤 걸 쓸까부터 고민합니다. 하지만 실제로 먼저 정해야 하는 건 엔진 선택이 아니라 그 연산을 어디서, 언제 돌릴 것인가입니다. 침수는 가시권처럼 한 번 계산하면 끝나는 정적 값이 아니라, 강우량·상류 유량·제방 상태 같은 변수가 바뀔 때마다 다시 흘러야 하는 시간축 시뮬레이션이기 때문에, 연산 위치를 잘못 정하면 "비가 더 오면 어떻게 되나요"라는 가장 흔한 질문 하나에 답하는 데도 몇 분씩 걸리는 서비스가 나옵니다.

이 질문에 대한 업계의 접근은 뚜렷하게 세 갈래로 갈립니다. 2026년 2월 Esri가 ArcGIS Pro에 공개한 Flood Simulation 도구처럼 무거운 계산을 전부 서버·데스크톱에서 끝내고 결과만 타일로 배포하는 방식, 2026년 8월 연구 사례처럼 서버는 예보 데이터만 제공하고 그걸 지도·구조물 데이터와 합치는 가벼운 지오프로세싱을 브라우저에서 돌리는 방식, 그리고 fastflood.org 같은 사례처럼 물리 기반 시뮬레이션 자체를 브라우저 안에서 완결시키는 방식입니다. 셋 다 결과물은 비슷해 보여도 요구사항의 성격에 따라 맞는 답이 완전히 다릅니다.

 

세 가지 연산 배치와 각각이 실제로 하는 일

서버 사전계산 + 타일 발행형은 ArcGIS Pro의 Flood Simulation 도구가 대표적입니다. 지정한 영역 안에서 얕은 물 방정식을 돌려 강우 강도·장애물·침투율별 시나리오를 미리 계산하고, 결과를 호스팅된 타일형 이미지 레이어로 발행합니다. 클라이언트는 이 타일을 FlowRenderer로 입혀 유속·흐름 방향을 애니메이션으로 보여줄 뿐 실시간 계산은 하지 않습니다. 정확도는 가장 높지만 시나리오가 바뀔 때마다 서버에서 전체를 다시 돌려야 합니다.

서버 예보 + 클라이언트 경량 지오프로세싱형은 국가 단위 수문 예보 모델이 내놓는 하천 유량 예보치만 서버에서 받아오고, 그걸 지역 구조물 데이터와 교차 처리하는 마지막 단계를 WebAssembly·Web Worker·IndexedDB로 브라우저 안에서 처리합니다. 무거운 수문 모델은 서버가 맡고, "이 집이 몇 cm나 잠기나"를 계산하는 단계는 클라이언트가 즉시 처리해 캐시합니다. 서버 왕복 없이 여러 조건을 빠르게 조회할 수 있는 게 핵심입니다.

완전 클라이언트 물리모델형은 fastflood.org나 HAND 모델의 WebAssembly 빌드처럼 수리·수문 계산 전체를 브라우저에서 끝냅니다. 서버 부담이 가장 적고 사용자가 파라미터를 자유롭게 바꿔가며 즉시 결과를 볼 수 있지만, 브라우저 메모리와 연산력의 한계로 다룰 수 있는 영역 크기와 모델 정교함에 뚜렷한 천장이 있습니다.

 

전체 시스템에서의 위치

세 방식은 "어디까지가 서버의 일이고 어디부터가 클라이언트의 일인가"라는 경계선만 다를 뿐, 입력(강우량·하천 수위·지형)에서 출력(지도 위 침수 표시)까지 흐르는 파이프라인의 모양은 같습니다. 경계선을 앞쪽(서버)에 당기면 구현은 쉽지만 시나리오 유연성을 잃고, 뒤쪽(클라이언트)까지 밀면 유연성은 얻지만 브라우저가 감당할 수 있는 계산 범위라는 물리적 제약에 바로 부딪힙니다.

 

세 방식의 트레이드오프
기준서버 사전계산+타일서버 예보+클라이언트 경량완전 클라이언트 물리모델
정확도가장 높음예보 모델에 의존다소 낮음
시나리오 변경 응답느림빠름즉시
인프라 비용높음중간낮음
적합한 요구공식 재난 대응·보험 심사시민 대상 즉시 조회교육용·소규모 도구

 

실제 진행 순서

엔진부터 고르지 말고 요구사항이 "하나의 정확한 답"을 원하는지 "빠르게 여러 번 바꿔보는 경험"을 원하는지부터 정해야 합니다. 재난 대응 상황실처럼 틀린 숫자가 치명적이면 서버 사전계산형으로, 시민에게 즉시 답해줘야 하는 서비스라면 예보+클라이언트 경량처리형이 체감 속도와 비용의 균형점입니다. 그다음 검증할 것은 수문·수리 모델의 출력 포맷입니다. 이미 완성된 침수 심도 그리드라면 타일 발행형이 자연스럽고, 시계열 유량 예보치처럼 가공 전 데이터라면 클라이언트 측 지오프로세싱을 끼워 넣을 여지가 생깁니다.

// Web Worker: 침수 예보 그리드와 구조물 좌표를 교차 처리
self.onmessage = async ({ data }) => {
  const { depthGrid, structures } = data;
  const cache = await openIndexedDbCache('flood-depth-v1');

  const results = structures.map((s) => {
    const cached = cache.get(s.id);
    if (cached) return cached;

    const depth = sampleDepthAtPoint(depthGrid, s.lon, s.lat);
    const result = { id: s.id, depthCm: depth, risk: depth > 30 ? 'high' : 'low' };
    cache.set(s.id, result);
    return result;
  });

  self.postMessage({ results });
};

메인 스레드를 막지 않고 교차 처리 결과를 IndexedDB에 캐시해 두면, 같은 영역을 다시 조회하거나 필터만 바꿀 때 서버 왕복 없이 즉시 응답할 수 있습니다. 다만 이 캐시는 예보가 갱신될 때마다 무효화해야 하므로, 예보 버전을 키에 함께 넣어 두는 것을 처음부터 설계에 넣는 게 나중에 캐시 무효화 버그를 막는 가장 싼 방법입니다.

 

주의 — 클라이언트 처리를 택했다면 Web Worker로 메인 스레드를 반드시 보호하고, 예보 버전을 캐시 키에 포함시켜 무효화 버그를 처음부터 막아야 합니다.

 

정리

침수 시뮬레이션은 가시권과 달리 시간축을 가진 연산이라, 어디까지 서버가 하고 어디부터 클라이언트가 하는가의 경계가 곧 아키텍처 결정입니다. 공식 재난 대응용이면 서버 사전계산+타일 발행, 시민 대상 즉시 조회형이면 서버 예보+클라이언트 경량 지오프로세싱, 교육·소규모 도구면 완전 클라이언트 물리모델이 균형점입니다.
