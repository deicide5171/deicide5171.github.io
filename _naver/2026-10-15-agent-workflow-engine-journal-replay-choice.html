LLM 호출을 다시 재생해도 되는가 — 에이전트 워크플로 엔진(Temporal·Restate·Inngest) 선택 설계

시스템 설계

한 줄 요약 — "에이전트가 중간에 죽어도 이미 호출한 LLM을 또 부르지 말아주세요"라는 요구는 전통적인 저널-리플레이 워크플로 엔진의 전제와 부딪힙니다. Temporal의 대형 투자와 Restate의 신규 투자가 겹친 지금, 비결정적 LLM 호출을 다루는 에이전트 오케스트레이션에 어떤 엔진을, 또는 엔진 없이 직접 짤지를 판단하는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"에이전트가 열 단계짜리 조사 작업을 하다가 배포 때문에 프로세스가 재시작되면, 이미 끝낸 LLM 호출은 다시 부르지 말고 그다음부터 이어서 해주세요." 이 요구는 평범한 재시도 로직으로는 풀리지 않습니다. LLM 호출은 비싸고 느리고 결과가 매번 달라질 수 있어서 "이미 성공한 호출을 또 하는 것" 자체가 비용이자 버그입니다. 전통적인 워크플로 엔진이 쓰는 저널-리플레이 모델은 원래 이 문제를 풀려고 나온 것이지만, 그 모델의 전제 자체가 "워크플로 코드는 결정적이다"라는 가정 위에 서 있습니다. LLM 호출은 이 가정을 정면으로 깹니다.

이 판단이 지금 특히 중요해진 이유는 생태계가 막 요동치고 있어서입니다. 2026년 9월 Temporal이 125억 달러 기업가치로 5억5천만 달러 시리즈E를 유치했고, 3주도 안 돼 베를린의 Restate가 2천만 달러 시리즈A를 발표했습니다. 업계가 "에이전트 워크로드에 durable execution이 필요하다"는 데는 합의했지만 "어떤 엔진으로"는 아직 안 정해졌다는 뜻입니다.

 

핵심 개념 — 저널-리플레이와 비결정성의 충돌

Temporal과 Restate는 둘 다 저널-리플레이 모델을 씁니다. 워크플로가 진행하면서 발생하는 이벤트를 저널에 기록해두고, 프로세스가 재시작되면 저널을 재생해 이미 완료된 단계는 건너뛰고 미완료 지점부터 이어갑니다. 이게 성립하려면 워크플로 코드가 결정적이어야 합니다. LLM 호출은 같은 프롬프트를 넣어도 매번 다른 응답이 나올 수 있으므로, 반드시 "활동(activity)"으로 명시적으로 분리해 그 결과를 저널에 한 번 기록하고 재생 시에는 그 기록을 그대로 재사용하도록 설계해야 합니다.

 

엔진 모델 에이전트 워크로드 특징
Temporal 저널-리플레이, 전체 히스토리 보관 성숙하지만 큰 페이로드는 오프로드 전략 필요
Restate 저널-리플레이, 가벼운 런타임 앱 레벨 멱등키 없이 exactly-once 쓰기 주장
Inngest 스텝별 체크포인트 구현은 단순하지만 재시도 많으면 과금이 커질 수 있음

 

전체 시스템에서의 위치

 

에이전트 오케스트레이터 입장에서 워크플로 엔진은 "이 작업을 끝까지 책임지고 이어가 줄게"라고 약속하는 신뢰 경계입니다. 오케스트레이터가 직접 상태를 테이블에 적고 폴링하는 대신, 워크플로 코드를 평범한 함수로 짜고 엔진이 저널·재생·재시도를 대신 맡습니다.

 

선택의 트레이드오프 — 언제 엔진 없이 가도 되는가

요청-응답이 수 초 안에 끝나고 중간 장애 복구가 문제되지 않는다면, 워크플로 엔진은 과잉 설계입니다. 큐 하나와 멱등성 키만으로 충분합니다. 작업이 분 단위 이상 걸리고 재시작 복구가 실제로 자주 발생한다면 세 엔진 중 하나를 검토할 시점입니다. 큰 페이로드를 자주 다룬다면 Temporal은 오프로드 전략을 처음부터 설계에 넣어야 하고, 멱등성 키를 직접 관리하고 싶지 않다면 Restate가 유리하지만 생태계 성숙도를 따져야 합니다.

 

실무 설정 예제
# 워크플로 코드(개념 예시) — LLM 호출을 활동으로 명시적으로 분리
async def research_workflow(query: str):
    plan = await call_activity(llm_plan_activity, query)

    results = []
    for step in plan.steps:
        r = await call_activity(llm_execute_step_activity, step)
        results.append(r)

    summary = await call_activity(llm_summarize_activity, results)
    return summary

 

실제 프로젝트 진행 순서

1단계: 크래시 복구가 실제로 문제인지부터 확인합니다. 장애 로그에 "중간에 죽어서 처음부터 다시 돌린" 사례가 실제로 있는지 셉니다.

2단계: LLM 호출과 부수효과 호출의 경계를 먼저 긋습니다. 엔진을 고르기 전에 이 경계부터 확정해야 합니다.

3단계: 페이로드 크기를 측정합니다. Temporal을 고려 중이라면 오프로드가 필요한지 미리 판단합니다.

4단계: PoC로 하나를 붙여보고 장애를 인위적으로 주입해 저널 재생이 의도대로 동작하는지 확인합니다.

 

주의 — "제일 유명한 엔진"으로 고르지 마세요. 자신의 페이로드 크기와 재시도 빈도를 먼저 재고, 특히 스텝 단위 과금 엔진은 재시도가 잦은 워크로드에서 비용이 비선형으로 늘 수 있으니 미리 시뮬레이션하세요.

 

정리

LLM 호출은 비결정적이므로 저널-리플레이 엔진에서는 반드시 별도 활동으로 분리해 한 번만 기록·재사용해야 합니다. 세 엔진은 저널 모델, 페이로드 처리, 과금 구조에서 실질적으로 다르며, 크래시 복구가 실제로 드문 워크로드라면 엔진 자체가 과잉 설계일 수 있습니다.
