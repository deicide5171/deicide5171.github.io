API 버저닝 전략 비교 — URI, 헤더, 콘텐츠 협상, 언제 무엇을 써야 하나

2026. 8. 18. · 아키텍처·시스템설계

한 줄 요약 — API 버저닝에서 가장 많이 쓰이는 URI 경로, 커스텀 헤더, Accept 헤더 콘텐츠 협상 세 가지 전략을 비교하고, 서비스 성격에 따라 어떤 전략을 선택하면 좋은지 정리했습니다.

 

왜 지금 API 버저닝인가

API는 한 번 공개되면 그 순간부터 계약이 됩니다. 프론트엔드, 모바일 앱, 외부 파트너가 이미 그 응답 구조를 가정하고 코드를 짜놓았기 때문에, 필드 이름 하나만 바꿔도 어딘가는 깨집니다. 그런데 서비스는 계속 진화해야 하고, 응답 구조 자체가 바뀌어야 하는 순간이 반드시 옵니다. 이 둘 사이의 긴장을 관리하는 것이 바로 API 버저닝입니다.

문제는 버전을 어디에 표시할 것인가부터 의견이 갈린다는 점입니다. URL에 박아 넣을지, 헤더로 뺄지, HTTP의 콘텐츠 협상 메커니즘을 그대로 활용할지에 따라 클라이언트 개발 경험, 캐싱 동작, 라우팅 구현 난이도가 전부 달라집니다. 정답은 하나가 아니고, 서비스의 소비자 구성과 운영 방식에 따라 유리한 전략이 다릅니다. 이번 글에서는 실무에서 가장 많이 쓰이는 세 가지 전략을 비교하고, 각각 언제 선택하면 좋은지 정리했습니다.

 

핵심 개념: 버전을 바꿔야 하는 변경과 아닌 변경

버저닝 전략을 논의하기 전에 먼저 구분해야 할 것은 이 변경이 정말 새 버전을 필요로 하는가입니다. 불필요하게 버전을 올리면 유지보수 부담만 늘어납니다. 기준은 명확합니다. 하위 호환이 깨지는가(breaking change) 여부입니다.

변경 유형 예시 새 버전 필요 여부
필드 추가(선택적) 응답에 createdAt 필드 추가 불필요
필드 이름 변경 user_name → userName 필요
응답 구조 변경 배열 응답 → 페이지네이션 객체로 감싸기 필요
필수 파라미터 추가 요청에 필수 헤더·바디 필드 신설 필요

 

핵심 개념: 세 가지 버저닝 전략 비교

세 전략 모두 결국 서버 쪽에서는 요청 어딘가에 담긴 버전 신호를 읽어서 적절한 핸들러로 분기하는 동작이 동일합니다. 차이는 그 신호를 어디에 담느냐, 그리고 그로 인해 캐싱·문서화·클라이언트 구현이 얼마나 쉬워지거나 어려워지느냐에 있습니다.

전략 표기 방식 장점 단점
URI 경로 버저닝 /v2/users/42 눈으로 바로 보임, 캐싱·라우팅 단순 리소스 식별자 순수성이 흐려짐
커스텀 헤더 버저닝 X-API-Version: 2 URI는 고정, 리소스와 버전 분리 문서를 봐야 알 수 있음
콘텐츠 협상(Accept) Accept: vnd.api.v2+json HTTP 표준 메커니즘 활용 구현 복잡, 브라우저 테스트 불가

 

예제: 헤더 기반 버저닝 라우팅(Spring Boot)

아래는 스프링 MVC의 headers 속성으로 라우팅 단계에서부터 버전을 분기시키는 패턴입니다. 컨트롤러 메서드 안에서 if (version == 2) 식으로 분기하지 않아도 되므로, 버전별 응답 DTO와 서비스 로직을 명확히 분리할 수 있습니다.

@RestController
@RequestMapping("/users")
public class UserController {

    // 헤더 값이 1이면 v1 핸들러
    @GetMapping(value = "/{id}", headers = "X-API-Version=1")
    public UserV1Response getUserV1(@PathVariable Long id) {
        return userService.getUserAsV1(id);
    }

    // 헤더 값이 2이면 v2 핸들러 - 응답 구조가 변경된 버전
    @GetMapping(value = "/{id}", headers = "X-API-Version=2")
    public UserV2Response getUserV2(@PathVariable Long id) {
        return userService.getUserAsV2(id);
    }

    // 헤더가 없으면 기본 버전(v1)으로 폴백
    @GetMapping("/{id}")
    public UserV1Response getUserDefault(@PathVariable Long id) {
        return userService.getUserAsV1(id);
    }
}

헤더가 없는 클라이언트를 위한 기본 버전 폴백도 반드시 함께 정의해야 합니다. 그래야 기존 클라이언트가 신규 배포 이후에도 그대로 동작합니다.

 

실무 도입 시 이것만은 챙기세요
1. 외부 공개 API는 URI 버저닝이 유리 — 서드파티 개발자가 문서를 안 읽어도 URL에 버전이 보여 실수를 줄임
2. 내부 서비스 간 API는 헤더 방식도 고려 — 리소스 식별자를 버전과 분리하고 싶고 클라이언트가 통제된 소수라면 부담이 크지 않음
3. 버전은 최소한으로 유지 — 동시 운영 버전이 늘어날수록 테스트·문서·인프라 비용이 배로 증가
4. 버전은 메이저(breaking) 변경에만 사용 — 하위 호환 변경까지 버전을 올리면 클라이언트 마이그레이션 피로만 누적
5. 캐싱 계층의 Vary 헤더 설정 필수 — 헤더·콘텐츠 협상 방식을 쓴다면 CDN·프록시가 버전 헤더를 캐시 키에 포함해야 함

 

마무리 — 3줄 요약

① API 버저닝은 하위 호환이 깨지는 변경(breaking change)에만 필요하며, 비파괴적 변경은 같은 버전 안에서 처리합니다.
② URI 경로 버저닝은 외부 공개 API에, 헤더·콘텐츠 협상 방식은 내부 서비스 간 API에 적합합니다.
③ 어떤 전략을 쓰든 버전 수는 최소로 유지하고, 캐싱 계층의 Vary 설정과 구버전 종료 일정 공지를 함께 챙겨야 합니다.
