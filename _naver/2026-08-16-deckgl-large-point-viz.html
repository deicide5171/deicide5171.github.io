지도 위 수백만 포인트, deck.gl은 어떻게 끊김 없이 그릴까

2026. 8. 16. · GIS

한 줄 요약 — 위치 로그, IoT 센서, AIS 선박 데이터처럼 포인트 개수가 크게 늘어나는 데이터를 웹 지도에서 끊김 없이 보여주고 싶을 때, deck.gl의 GPU 기반 레이어 렌더링이 어떻게 이 문제를 풀어주는지 정리했습니다.

 

왜 지금 대량 포인트 시각화인가

위치 기반 데이터의 크기는 계속 커지고 있습니다. IoT 센서 로그, 차량·선박 위치 이력, 앱 사용자 행동 로그처럼 포인트 수가 수만~수십만 단위로 쌓이는 데이터를 지도 위에 그대로 뿌리면, 흔히 쓰는 지도 라이브러리의 기본 마커 방식은 포인트가 늘어날수록 화면이 눈에 띄게 버벅이기 시작합니다.

이유는 단순합니다. 기본 마커는 포인트 하나마다 DOM 엘리먼트를 만드는 방식이라, 브라우저의 레이아웃·페인트 비용이 포인트 수에 거의 비례해서 늘어나기 때문입니다. 이 한계를 정면으로 다루는 대표적인 오픈소스가 바로 deck.gl입니다.

deck.gl은 우버가 만들고 현재 vis.gl 프로젝트로 관리되는 시각화 프레임워크로, 지도 자체를 그리는 대신 Mapbox GL·MapLibre 같은 기존 베이스맵 위에 별도의 WebGL 캔버스를 겹쳐서 대량 포인트만 GPU로 빠르게 렌더링하는 역할에 집중합니다. React 생태계와도 잘 맞물려서 대시보드·분석 도구에 자주 쓰입니다.

 

핵심 개념: 레이어 구조와 GPU 인스턴싱

deck.gl의 기본 단위는 Layer입니다. 점을 그리는 ScatterplotLayer, 선을 그리는 LineLayer, 밀도를 표현하는 HeatmapLayer, 공간을 격자로 집계하는 HexagonLayer 등 목적별 레이어가 준비되어 있습니다. 각 레이어는 데이터 배열과 accessor 함수(getPosition, getFillColor, getRadius 등)를 받아 "각 데이터 항목을 화면에서 어떻게 표현할지"를 선언적으로 정의합니다.

핵심은 이 accessor로 정의된 값들이 매 프레임 CPU에서 다시 계산되는 게 아니라, 한 번 GPU 버퍼로 업로드된 뒤 GPU 인스턴싱으로 그려진다는 점입니다. 위경도를 화면 좌표로 바꾸는 투영 변환(Web Mercator)조차 정점 셰이더 안에서 처리되기 때문에, 포인트 개수가 늘어나도 CPU가 반복해서 해야 할 일은 크게 늘지 않고 GPU가 병렬로 나눠 처리합니다.

구분 DOM 마커 / Canvas 2D deck.gl (GPU 레이어)
렌더링 단위 포인트마다 개별 DOM/draw 호출 동일 지오메트리를 GPU 인스턴싱으로 일괄 처리
좌표 변환 위치 CPU (JS) GPU (셰이더)
데이터 갱신 비용 포인트 수에 비례해 증가 버퍼 재업로드 범위에 따라 결정
적합한 규모 수백~수천 개 대규모(기기·데이터에 따라 상이)

 

아래는 deck.gl 렌더링 파이프라인을 정리한 그림입니다. 원본 데이터가 Layer 정의를 거쳐 GPU 버퍼로 업로드되고, GPU 인스턴싱으로 렌더링된 뒤 베이스맵과 합성되는 흐름을 보여줍니다.

 

예제: React에서 deck.gl로 포인트 레이어 그리기

React + MapLibre 조합에서 ScatterplotLayer로 대용량 포인트 배열을 그리는 기본 예제입니다. 실제 GPU 버퍼 생성과 업로드는 deck.gl 내부에서 처리되므로, 개발자는 데이터와 accessor 함수만 선언하면 됩니다.

import { DeckGL } from '@deck.gl/react';
import { ScatterplotLayer } from '@deck.gl/layers';
import Map from 'react-map-gl/maplibre';

const INITIAL_VIEW_STATE = {
  longitude: 127.0, latitude: 37.5, zoom: 10,
};

function PointMap({ points }) {
  // points: [{ position: [lng, lat], value: number }, ...] 대용량 배열
  const layer = new ScatterplotLayer({
    id: 'points',
    data: points,
    getPosition: d => d.position,
    getFillColor: d => (d.value > 50 ? [220, 60, 60] : [40, 130, 220]),
    getRadius: 30,
    radiusMinPixels: 1,
    pickable: true,
  });

  return (
    <DeckGL
      initialViewState={INITIAL_VIEW_STATE}
      controller
      layers={[layer]}
    >
      <Map mapStyle="https://demotiles.maplibre.org/style.json" />
    </DeckGL>
  );
}

radiusMinPixels는 줌아웃 시 점이 너무 작아져 안 보이는 문제를 막아주는 옵션입니다. accessor 함수만 바꿔도 색상·크기 조건을 데이터 기반으로 자유롭게 표현할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. updateTriggers로 불필요한 재계산 방지 — accessor가 참조하는 값이 바뀔 때만 GPU 버퍼를 다시 만들도록 지정하지 않으면 성능이 떨어질 수 있음
2. 데이터가 매우 크다면 바이너리 포맷 고려 — 일반 객체 배열 대신 Typed Array 기반 속성으로 넘기면 내부 변환 비용 절감
3. 극단적으로 많은 포인트는 집계 레이어 검토 — HexagonLayer·GridLayer로 밀도를 표현하면 시각적으로도, 성능면에서도 유리한 경우가 많음
4. 실제 처리 가능 규모는 환경마다 다름 — GPU 성능, 브라우저, 동시 레이어 수에 따라 달라지므로 목표 환경에서 직접 확인 필요

 

마무리 — 3줄 요약

① deck.gl은 베이스맵 위에 별도 WebGL 캔버스를 겹쳐, 대량 포인트 렌더링을 GPU 인스턴싱으로 처리하는 시각화 프레임워크입니다.
② 좌표 변환까지 GPU 셰이더에서 수행되기 때문에 DOM 마커 방식과 달리 포인트 수가 늘어도 CPU 부담이 비례해서 커지지 않습니다.
③ 실무에서는 updateTriggers, 바이너리 데이터 포맷, 집계 레이어 활용 여부를 데이터 규모에 맞춰 판단해야 합니다.
