이벤트 소싱과 CQRS 심화 — 스냅샷과 프로젝션 재구축 전략

아키텍처·시스템 설계

한 줄 요약 — 이벤트가 쌓일수록 매번 처음부터 재생하는 방식은 한계에 부딪힙니다. 스냅샷과 프로젝션 재구축 파이프라인 설계 전략을 정리했습니다.

 

왜 지금 이 문제가 불거지는가

이벤트 소싱은 상태의 현재 값 대신 상태를 변화시킨 모든 이벤트를 순서대로 저장해 감사 추적·시점 복원을 쉽게 만듭니다. 초기에는 이벤트 재생이 문제없지만, 애그리게이트의 이벤트가 수만~수십만 건으로 쌓이면 매번 처음부터 재생하는 방식은 응답 시간을 감당할 수 없게 됩니다.

CQRS와 함께 쓰는 경우, 새 조회 뷰가 필요하거나 프로젝션 로직에 버그가 있을 때마다 전체 이벤트 스트림을 처음부터 재생해 프로젝션을 재구축해야 합니다. 이벤트가 많아질수록 이 작업은 몇 시간짜리 배치가 되어 장애 복구와 배포의 발목을 잡습니다.

 

스냅샷으로 재생 시간 줄이기

스냅샷은 특정 시점까지 이벤트를 재생한 결과를 별도로 저장해두는 것입니다. 이후에는 최근 스냅샷을 불러온 뒤 그 이후 이벤트만 추가로 재생하면 됩니다. 스냅샷은 신뢰의 원천이 아니라 캐시이므로, 손상되더라도 이벤트 스트림에서 다시 정합성 있는 상태를 복원할 수 있어야 합니다.

 

프로젝션 재구축 파이프라인

프로젝션 재구축은 새 읽기 모델 추가, 버그 수정, 데이터 손상 복구 시 발생합니다. 서비스 운영 중 재구축을 어떻게 진행하느냐가 실무의 핵심 난이도입니다.

방식 설명 트레이드오프
오프라인 재구축 서비스 중단 후 처음부터 재생 단순하지만 다운타임 발생
블루-그린 재구축 새 테이블을 채운 뒤 스위칭 다운타임 없음, 이중 저장 공간 필요
체크포인트 병렬 재생 여러 파티션 병렬 재생 후 병합 속도 향상, 파티셔닝 설계 필요

 

예제 — 스냅샷 기반 상태 복원
async function loadAggregate(aggregateId) {
  const snapshot = await snapshotStore.getLatest(aggregateId);
  const fromVersion = snapshot ? snapshot.version + 1 : 0;

  const events = await eventStore.readStream(aggregateId, fromVersion);
  let state = snapshot ? snapshot.state : initialState();

  for (const event of events) {
    state = applyEvent(state, event);
  }
  if (events.length >= SNAPSHOT_THRESHOLD) {
    await snapshotStore.save(aggregateId, state, fromVersion + events.length - 1);
  }
  return state;
}

 

실무 포인트

스냅샷 주기를 애그리게이트별 이벤트 발생 빈도에 맞춰 다르게 가져가세요. 핫 애그리게이트와 거의 변하지 않는 것을 동일 주기로 스냅샷하면 자원 낭비이거나 재생 지연이 반복됩니다.

프로젝션 재구축은 블루-그린 방식으로 설계하세요. 재구축 중인 테이블에 실시간 조회가 붙지 않도록 스위칭 시점을 명확히 관리해야 합니다.

주의 — 이벤트 스키마 버전 관리를 프로젝션 재구축과 함께 고려해야 합니다. 오래된 이벤트 포맷을 최신 스키마로 변환하는 업캐스터 계층이 없으면 재구축 자체가 실패합니다.
