프롬프트에 한 줄씩 덧붙이다 지친 사람에게 — ACE, 스스로 진화하는 컨텍스트 플레이북

AI

한 줄 요약 — "같은 실수를 반복하지 말라"는 요구는 프롬프트 수정이 아니라 에이전트가 실행 경험에서 스스로 배우는 메모리 구조의 문제입니다. 요약할수록 지식이 증발하는 context collapse를, 삭제 없이 구조화된 델타로 누적하는 ACE 프레임워크로 풀 수 있는지 정리했습니다.

 

왜 지금 이 문제가 불거지는가

"우리 고객지원 에이전트가 환불 정책 관련 티켓에서 계속 같은 실수를 해요. 그때마다 '이런 경우엔 이렇게 처리하세요'를 시스템 프롬프트에 한 줄씩 추가하는데, 몇 주 지나니 프롬프트가 거대해지고 오히려 엉뚱한 상황에서도 그 규칙을 끌어다 씁니다." 이 요구는 표면적으로는 프롬프트를 더 잘 쓰는 문제처럼 보이지만, 실제로는 에이전트가 실행 피드백에서 무엇을 배우고 어떻게 저장할 것인가라는 메모리 아키텍처 문제입니다.

에이전트가 프로덕션에서 장기간 반복 실행되기 시작하면서 "지난 실행에서 배운 것을 다음 실행에 어떻게 반영할까"가 실질적인 설계 질문이 됐습니다. 2026년 공개된 ACE(Agentic Context Engineering) 프레임워크는 컨텍스트를 매번 새로 쓰는 프롬프트가 아니라, 실행할수록 누적·정제되는 플레이북으로 다룹니다.

 

요구사항을 기술 문제로 번역하기

"같은 실수를 반복하지 않게 해달라"는 말은 세 가지 선택지로 갈립니다. 사람이 직접 프롬프트에 규칙을 추가하면 비대해지다 규칙끼리 충돌하고, 실패 사례로 파인튜닝하면 효과는 있지만 반영 주기가 느리고, LLM 스스로 컨텍스트를 요약해 메모리로 쓰면 brevity bias(간결함을 선호해 디테일을 깎아내는 현상)와 context collapse(반복해서 다시 쓸 때마다 정보가 누적 손실되는 현상)에 취약합니다.

ACE는 컨텍스트를 하나의 문단이 아니라 구조화된 전략 단위(불릿)의 집합으로 유지하고, 전체를 다시 쓰는 대신 추가·수정·폐기의 증분 델타만 적용합니다. 요약이 아니라 축적이라는 점이 핵심입니다.

 

전체 시스템에서의 위치

 

ACE는 Generator-Reflector-Curator 세 모듈이 순환합니다. Generator는 현재 플레이북을 컨텍스트로 받아 실제 작업을 수행하고, 실행이 끝나면 성공·실패·재시도 횟수 같은 자연 실행 피드백이 남습니다. Reflector는 이 피드백에서 "왜 실패했는지, 다음엔 뭘 다르게 해야 하는지"를 전략 단위로 추출합니다. Curator는 그 전략을 기존 플레이북과 대조해 중복이면 보강하고, 모순이면 조건을 분리하고, 쓸모없어졌으면 제거하는 식으로 구조를 유지한 채 병합합니다. 다음 실행은 이 갱신된 플레이북을 그대로 이어받습니다.

 

선택의 트레이드오프
기준 수동 프롬프트 수정 파인튜닝 ACE 플레이북
반영 속도 빠름(즉시) 느림(재학습 필요) 빠름
지식 보존 사람이 관리하는 동안만 가중치에 영구 반영 델타 누적으로 보존
적합 규모 규칙 수십 개 이하 패턴이 안정적일 때 반복 실행되는 상시 에이전트

 

파인튜닝은 모델 자체의 능력을 바꾸고 싶을 때, ACE류 플레이북은 모델은 그대로 두고 도메인 지식과 절차만 빠르게 진화시키고 싶을 때 적합합니다. 둘은 배타적이지 않고, 플레이북으로 먼저 패턴을 검증한 뒤 안정화된 규칙만 파인튜닝 데이터로 승격하는 조합도 가능합니다.

 

실제 프로젝트 진행 순서

1단계: 라벨 없는 실행 피드백 신호부터 정의합니다. 테스트 통과·API 에러 코드·후속 재작업 여부처럼 시스템이 자동 관찰 가능한 신호가 출발점입니다.

2단계: Reflector가 뽑을 전략 단위의 포맷을 고정합니다. "상황 조건 + 권장 행동 + 근거 사례" 구조가 있어야 Curator가 중복·모순을 기계적으로 판별할 수 있습니다.

3단계: Curator의 병합 규칙을 보수적으로 설계합니다. 초기에는 완전히 동일한 조건만 교체하고 나머지는 추가하는 식의 단순 규칙으로 시작합니다.

4단계: 플레이북 크기 상한과 정리 주기를 둡니다. 구조화돼 있어도 무한히 쌓이면 컨텍스트 비용이 늘어납니다.

5단계: 오프라인 최적화와 온라인 갱신 범위를 분리합니다. 안정적인 규칙은 배치로 정제하고, 세션 중 실시간 맥락만 온라인 갱신 대상으로 좁힙니다.

주의 — 플레이북은 감사 가능해야 합니다. 왜 특정 행동을 하게 됐는지 추적이 안 되면 디버깅이 불가능하므로, 각 델타에 추가된 시점과 근거 사례를 남겨야 합니다.

 

정리

같은 실수를 반복하지 말라는 요구는 프롬프트 땜질이 아니라 실행 피드백 → 전략 추출 → 구조화 병합이라는 메모리 파이프라인 설계 문제입니다. ACE는 Generator-Reflector-Curator 순환과 증분 델타로 brevity bias와 context collapse를 피하면서 컨텍스트를 플레이북처럼 누적시킵니다. 성패는 라벨 없는 실행 피드백 신호 설계와 Curator의 병합 규칙 보수성에 달려 있습니다.
