패킷 하나가 전체를 멈추던 시대의 끝 — HTTP/3와 QUIC 실전 도입 가이드

2026. 8. 23. · 인프라

한 줄 요약 — HTTP/3가 TCP를 버리고 QUIC(UDP 기반)을 채택하면서 무엇이 달라졌는지(HOL 블로킹 격리, 1-RTT/0-RTT 핸드셰이크, 커넥션 마이그레이션)를 정리하고, 0-RTT 리플레이 위험과 UDP 차단 대비 등 실전 도입 시 확인할 점을 담았습니다.

 

왜 지금 HTTP/3인가요

HTTP/2가 멀티플렉싱으로 요청 대기 문제를 해결한 지 오래되었지만, 모바일 사용자 비중이 높은 서비스의 지연시간을 분석해 보면 여전히 꼬리 지연(p95, p99)이 유독 긴 구간이 발견됩니다. 원인을 추적해 보면 상당수가 애플리케이션이 아니라 전송 계층, 즉 TCP 자체에서 오는 경우가 많습니다. 패킷 하나가 유실되면 뒤에 도착한 멀쩡한 데이터까지 모두 기다리게 만드는 TCP의 순서 보장이, 손실이 잦은 무선망에서는 족쇄가 되기 때문입니다.

HTTP/3는 이 문제를 프로토콜 튜닝이 아니라 전송 계층 교체로 풀었습니다. TCP 대신 UDP 위에 구현된 QUIC을 채택한 것인데요. 현 시점 기준 주요 브라우저와 대형 CDN이 모두 HTTP/3를 지원하고 nginx도 안정 버전에서 HTTP/3 모듈을 제공하면서, 도입을 검토하는 팀이 많아졌습니다. 이번 글에서는 QUIC이 실제로 바꾸는 것들과 도입 전 확인 사항을 정리해 보겠습니다.

 

핵심 개념 1 — HOL 블로킹, HTTP/2는 절반만 해결했습니다

HTTP/1.1의 HOL(Head-of-Line) 블로킹은 애플리케이션 계층의 문제였고, HTTP/2는 하나의 TCP 커넥션 안에 여러 스트림을 멀티플렉싱하는 방식으로 이를 해결했습니다. 문제는 그 아래 계층입니다. HTTP/2의 스트림이 논리적으로는 독립적이어도 실제로는 하나의 TCP 바이트 스트림에 직렬화되어 흐르는데, TCP는 스트림이라는 개념을 모르기 때문에 패킷 하나가 유실되면 재전송이 도착할 때까지 커넥션 전체의 데이터 전달을 멈춥니다. 스트림 A의 손실이 이미 도착해 있는 스트림 B, C의 데이터까지 붙잡아 두는 셈입니다.

QUIC은 스트림을 전송 계층의 일급 개념으로 끌어올렸습니다. 손실 감지와 재전송이 스트림 단위로 이루어지므로, 한 스트림의 패킷이 유실되어도 다른 스트림의 데이터는 즉시 애플리케이션에 전달됩니다. HOL 블로킹의 영향 범위가 손실이 발생한 스트림 하나로 격리되는 것입니다.

 

 

핵심 개념 2 — 핸드셰이크 단축과 커넥션 마이그레이션

TCP + TLS 1.3 조합은 첫 요청까지 TCP 핸드셰이크 1왕복, TLS 핸드셰이크 1왕복을 합쳐 최소 2-RTT가 필요합니다. QUIC은 TLS 1.3을 전송 프로토콜 내부에 통합해 전송 수립과 키 교환을 같은 왕복에서 처리하므로 첫 연결이 1-RTT로 끝나고, 한 번 연결했던 서버라면 핸드셰이크 완료 전에 데이터를 실어 보내는 0-RTT도 가능합니다. RTT가 긴 국제 구간이나 모바일 환경에서는 체감할 수 있는 차이가 됩니다.

또 하나 유용한 것이 커넥션 마이그레이션입니다. TCP 커넥션은 IP와 포트 조합으로 식별되므로 Wi-Fi에서 LTE로 넘어가는 순간 연결이 끊기지만, QUIC은 커넥션 ID로 연결을 식별하기 때문에 클라이언트 IP가 바뀌어도 세션이 유지됩니다. 이동 중 사용이 많은 모바일 앱 API라면 이 특성만으로도 도입 가치가 있습니다.

구분 HTTP/1.1 HTTP/2 HTTP/3
전송 계층 TCP TCP QUIC (UDP 기반)
HOL 블로킹 앱 + 전송 계층 모두 전송 계층에 잔존 스트림 단위로 격리
첫 연결 핸드셰이크 2-RTT 2-RTT 1-RTT (0-RTT 재개 가능)
IP 변경 시 커넥션 끊김 커넥션 끊김 커넥션 ID로 유지

 

예제 — nginx에서 HTTP/3 켜기

nginx 안정 버전 기준으로 HTTP/3 활성화는 아래처럼 구성합니다. 핵심은 UDP 443을 여는 것과, TCP로 접속한 클라이언트에게 Alt-Svc 헤더로 HTTP/3 지원을 광고하는 것입니다. 브라우저는 첫 방문에서는 TCP(HTTP/2)로 붙고, 이 헤더를 본 뒤부터 HTTP/3로 전환합니다.

server {
    # HTTP/3 (QUIC) — UDP 443
    listen 443 quic reuseport;
    # HTTP/2 폴백 — TCP 443 (반드시 함께 유지)
    listen 443 ssl;
    http2 on;

    server_name example.com;

    ssl_certificate     /etc/ssl/certs/example.com.pem;
    ssl_certificate_key /etc/ssl/private/example.com.key;
    ssl_protocols       TLSv1.3;

    # TCP로 온 클라이언트에게 HTTP/3 지원을 광고
    add_header Alt-Svc 'h3=":443"; ma=86400' always;

    location / {
        root /var/www/html;
    }
}

적용 후에는 커널의 UDP 버퍼 크기(net.core.rmem_max 등)를 함께 점검하시고, HTTP/3를 지원하는 curl 빌드에서 curl -sI --http3 https://example.com 명령으로 응답이 "HTTP/3 200"으로 오는지 확인하시면 됩니다.

 

함정 — 0-RTT를 아무 요청에나 허용하면 안 됩니다
0-RTT 조기 데이터는 리플레이 공격에 취약합니다. 핸드셰이크가 완료되기 전에 보내는 데이터이므로, 공격자가 이 패킷을 캡처해 그대로 다시 보내면 서버가 같은 요청을 두 번 처리할 수 있습니다. 주문 생성 같은 POST 요청이 0-RTT로 들어와 재생되면 주문이 중복 생성되는 것입니다. 올바른 접근은 ① 0-RTT를 GET처럼 멱등한 요청에만 허용하고, ② 리버스 프록시가 조기 데이터 요청에 Early-Data: 1 헤더를 붙여 백엔드로 넘기게 하며, ③ 백엔드는 상태를 바꾸는 요청이라면 425 Too Early로 거부해 핸드셰이크 완료 후 재시도하게 만드는 것입니다. 확신이 없다면 0-RTT는 끄고 1-RTT만으로 시작해도 이득의 대부분을 챙길 수 있습니다.

 

언제 켜고, 언제 미뤄야 할까요

켜야 할 때 — 모바일·무선 사용자 비중이 높고 꼬리 지연이 문제가 되는 대외 서비스, RTT가 긴 국제 구간 트래픽이 많은 경우입니다. CDN 뒤에 있다면 CDN의 HTTP/3 옵션을 켜는 것만으로 엣지 구간의 이득을 얻을 수 있어 시작 비용도 낮습니다.

미뤄도 될 때 — 데이터센터 내부의 서비스 간 통신입니다. 내부망은 손실률이 사실상 0이고 RTT가 밀리초 미만이라 QUIC의 장점이 발휘될 무대가 없습니다. 오히려 QUIC은 암호화와 패킷 처리가 사용자 공간에서 이루어져 같은 처리량에서 TCP보다 CPU를 더 쓰는 경향이 있고, TCP가 누려온 커널·NIC 오프로드 최적화의 혜택도 아직 온전히 받지 못합니다. 내부 gRPC 통신을 서둘러 바꿀 이유는 없습니다.

도입 시 체크리스트도 짚어두겠습니다. 첫째, 방화벽이나 보안장비에서 UDP 443이 막힌 기업망이 존재하므로 TCP 폴백 경로는 절대 제거하면 안 됩니다. 둘째, L4 로드밸런서가 IP·포트 조합 해싱만 지원하면 커넥션 마이그레이션 시 다른 백엔드로 패킷이 흘러갈 수 있어 커넥션 ID 기반 라우팅 지원 여부를 확인해야 합니다. 셋째, QUIC은 헤더까지 암호화되므로 기존 패킷 기반 모니터링 장비가 내용을 보지 못하며, 관측은 서버·클라이언트 측 로그와 qlog 같은 엔드포인트 계측으로 옮겨야 합니다.

 

마무리 — 3줄 요약

① HTTP/2는 애플리케이션 계층의 HOL 블로킹만 해결했고, QUIC은 스트림을 전송 계층으로 내려 손실의 영향 범위를 스트림 하나로 격리합니다.
② QUIC은 TLS 1.3 통합으로 첫 연결 1-RTT, 재연결 0-RTT를 제공하지만, 0-RTT는 리플레이 위험 때문에 멱등 요청으로 제한하고 425 Too Early 처리를 갖춰야 합니다.
③ 대외 모바일 트래픽에는 이득이 크지만 내부 통신에는 CPU 비용 대비 실익이 적으며, UDP 차단 대비 TCP 폴백과 로드밸런서의 커넥션 ID 라우팅 확인이 필수입니다.
