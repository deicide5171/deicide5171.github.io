큰 모델의 답을 작은 모델이 먼저 쓴다 — 스페큘레이티브 디코딩의 원리

2026. 8. 23. · AI

한 줄 요약 — 작은 드래프트 모델이 다음 토큰들의 초안을 빠르게 써두면 큰 타깃 모델이 순전파 한 번으로 병렬 검증하는 스페큘레이티브 디코딩의 동작 원리, 성패를 가르는 수락률, 그리고 언제 켜야 이득인지를 정리했습니다.

 

품질을 건드리지 않고 LLM을 빠르게 만들 수 있을까요

LLM 추론 비용을 줄이는 기법은 크게 두 갈래로 나뉩니다. 양자화처럼 모델 자체를 가볍게 만드는 쪽과, 같은 모델을 두고 하드웨어를 더 알뜰하게 쓰는 쪽입니다. 전자는 정도의 차이는 있어도 출력 품질에 영향을 주는데, 후자 중에는 출력의 확률 분포를 수학적으로 전혀 바꾸지 않으면서 응답 속도만 끌어올리는 기법이 있습니다. 바로 스페큘레이티브 디코딩(speculative decoding)입니다.

아이디어는 직관적입니다. 큰 모델이 다음 토큰을 한 개씩 뽑는 대신, 작은 모델이 먼저 여러 토큰의 초안을 빠르게 써두고, 큰 모델은 그 초안이 맞는지 한 번의 순전파로 병렬 검증만 하는 것입니다. 초안이 맞으면 여러 토큰이 한꺼번에 확정되고, 틀리면 틀린 지점부터 큰 모델이 바로잡습니다. 결과물은 큰 모델이 혼자 생성한 것과 통계적으로 동일한데 속도만 빨라지는 구조입니다.

 

핵심 개념 1 — 디코딩의 병목은 연산이 아니라 메모리입니다

이런 구조가 가능한 이유를 이해하려면 먼저 디코딩이 왜 느린지 봐야 합니다. 트랜스포머의 자기회귀 생성에서는 토큰을 하나 뽑을 때마다 모델의 전체 가중치를 GPU 메모리(HBM)에서 연산 유닛으로 읽어와야 합니다. 70B급 모델이라면 토큰 하나당 수십 GB를 옮기는 셈인데, 이때 실제 연산은 GPU가 낼 수 있는 성능의 극히 일부만 사용합니다. 즉 디코딩 중의 GPU는 대부분 계산이 아니라 가중치 나르기를 하며 놀고 있는 것입니다.

여기서 중요한 비대칭이 생깁니다. 가중치를 한 번 읽어온 김에 토큰 1개 위치를 계산하든 5개 위치를 계산하든 걸리는 시간이 거의 같다는 점입니다. 문제는 자기회귀 특성상 다음 토큰을 알아야 그다음 토큰을 만들 수 있어서, 검증할 미래 토큰 후보가 애초에 없다는 것인데요. 스페큘레이티브 디코딩은 이 후보를 작은 모델에게 만들게 해서 큰 모델의 남는 연산 능력을 채웁니다.

 

 

핵심 개념 2 — 검증 규칙이 무손실을 보장합니다

한 사이클은 세 단계로 진행됩니다. 드래프트 모델(예: 1B급)이 토큰 k개(보통 3~8개)를 자기회귀로 빠르게 생성하고, 타깃 모델(예: 70B급)이 그 k개 위치를 단 한 번의 순전파로 훑으며 각 위치에서 자신이라면 어떤 확률 분포를 냈을지 계산합니다. 마지막으로 앞에서부터 위치별로 수락과 거절을 결정합니다.

핵심은 검증 규칙입니다. 각 위치에서 드래프트 모델이 그 토큰을 뽑은 확률 q와 타깃 모델이 계산한 확률 p를 비교해, p가 q 이상이면 무조건 수락하고 p가 q보다 작으면 p/q의 확률로만 수락합니다. 거절이 발생하면 그 위치에서 두 분포의 차이로부터 토큰을 다시 샘플링하고 사이클을 마칩니다. 이 수정 기각 샘플링 덕분에 최종 출력의 확률 분포가 타깃 모델 단독 생성과 정확히 일치한다는 것이 원 논문의 증명입니다. 근사가 아니라 무손실입니다. 게다가 검증 순전파에서 타깃 모델의 분포를 이미 얻었기 때문에, 최악의 경우에도 사이클당 토큰 1개는 반드시 확정됩니다.

 

핵심 개념 3 — 성패는 수락률이 결정합니다

이 기법의 성능은 수락률(acceptance rate) 하나로 요약됩니다. 수락률이 높으면 사이클당 서너 개의 토큰이 한꺼번에 확정되어 타깃 모델의 순전파 횟수가 크게 줄지만, 수락률이 낮으면 드래프트 비용만 얹은 꼴이 됩니다. 원 논문들과 이후 구현들에서는 도메인이 잘 맞을 때 2~3배 수준의 지연 시간 단축이 보고돼 왔습니다. 수락률은 두 모델의 분포 정렬(같은 계열의 축소판일수록 유리), 텍스트의 예측 가능성(코드처럼 다음 토큰이 뻔한 구간이 많을수록 유리), 샘플링 온도(높을수록 불리)에 좌우됩니다.

드래프트를 만드는 방식도 여러 갈래로 발전했습니다.

방식 장점 한계
독립 드래프트 모델
(별도 소형 모델)		 구현이 단순하고 기존 모델을 재활용할 수 있음 토크나이저 일치 필요, 별도 메모리 점유
셀프 드래프팅
(Medusa, EAGLE 계열)		 타깃 모델에 얹은 추가 헤드라 정렬이 좋고 수락률이 높음 헤드 학습 비용, 모델별 준비 필요
n-gram / 프롬프트 룩업 학습도 추가 모델도 필요 없음 요약·RAG처럼 입력이 출력에 되풀이되는 작업에만 효과

 

예제 — vLLM에서 켜보기

vLLM에서는 설정 한 덩어리로 스페큘레이티브 디코딩을 켤 수 있습니다. 같은 패밀리의 소형 모델을 드래프트로 붙이는 예시입니다. 인자 이름은 버전에 따라 다를 수 있으니 사용 중인 버전의 공식 문서를 함께 확인해 주세요.

from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=4,
    speculative_config={
        "model": "meta-llama/Llama-3.2-1B-Instruct",  # 같은 패밀리, 같은 토크나이저
        "num_speculative_tokens": 5,                   # 사이클당 초안 토큰 수 k
    },
)

params = SamplingParams(temperature=0.2, max_tokens=512)
outputs = llm.generate(["PostgreSQL의 MVCC를 세 문단으로 설명해줘."], params)
print(outputs[0].outputs[0].text)

별도 모델 없이 입력 컨텍스트에서 초안을 찾는 n-gram 방식도 있습니다. 요약이나 문서 QA처럼 입력 문장이 출력에 다시 등장하는 워크로드에서 공짜에 가까운 이득을 줍니다.

llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    speculative_config={
        "method": "ngram",
        "num_speculative_tokens": 5,
        "prompt_lookup_max": 4,   # 매칭에 쓸 최대 n-gram 길이
    },
)

 

실무 도입 시 이것만은 챙기세요
1. 지연 시간 최적화 기법이지 처리량 최적화 기법이 아닙니다 — 배치 크기가 작은 대화형 서비스에서는 GPU가 메모리 대역폭에 묶여 놀고 있어 검증 계산이 공짜에 가깝지만, 배치가 큰 오프라인 대량 처리에서는 디코딩이 이미 연산 병목으로 넘어가 있어 거절된 초안의 계산이 고스란히 낭비가 됩니다. 이 경우 전체 처리량이 오히려 떨어질 수 있으니 끄는 편이 낫습니다.
2. 토크나이저가 다른 모델을 드래프트로 붙이지 마세요 — 검증은 토큰 ID 단위로 확률을 비교하므로 두 모델의 어휘가 일치해야 합니다. 작고 빠르다는 이유로 다른 패밀리의 모델을 골랐다가 아예 동작하지 않거나 수락률이 바닥을 치는 경우가 많습니다. 같은 패밀리의 최소 사이즈나 EAGLE 계열처럼 타깃 모델에서 파생된 드래프터를 쓰는 것이 올바른 선택입니다.
3. 초안 길이 k를 무작정 키우지 마세요 — 수락률이 받쳐주지 않으면 뒤쪽 초안은 대부분 버려져 드래프트 비용만 늘어납니다. 사이클당 평균 수락 토큰 수를 지표로 두고 k를 3~8 범위에서 조정하는 편이 안전합니다.

 

마무리 — 3줄 요약

① 디코딩의 병목은 메모리 대역폭이라 큰 모델은 토큰 여러 개를 한 개 비용으로 검증할 수 있고, 스페큘레이티브 디코딩은 이 여유를 작은 모델의 초안으로 채웁니다.
② 수정 기각 샘플링 덕분에 출력 분포는 타깃 모델 단독 생성과 동일한 무손실 가속이며, 성능은 전적으로 수락률(모델 정렬·텍스트 예측 가능성·온도)에 달려 있습니다.
③ 저지연 대화형·소규모 배치에서 켜고, 대규모 배치 처리량 워크로드에서는 오히려 손해일 수 있습니다. 드래프트는 반드시 같은 토크나이저를 쓰는 모델로 고르세요.
