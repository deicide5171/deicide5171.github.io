Bounded-Load 일관 해싱 — 균등 분배를 수학적으로 보장하는 확장판

시스템 설계

한 줄 요약 — 각 서버가 받는 부하에 수학적 상한을 강제해 핫키로 인한 핫스팟을 원천 차단하는 Consistent Hashing with Bounded Loads의 원리를 정리했습니다.

 

왜 지금 일관된 해싱을 다시 봐야 하는가

일관된 해싱은 "서버 수가 바뀌어도 재배치되는 키가 최소화된다"는 문제를 잘 풀지만, "부하가 균등하게 분배되는가"는 별도의 보장이 없습니다. 실제 트래픽에서는 인기 상품이나 바이럴 콘텐츠 같은 핫키에 요청이 몰리고, 이 핫키가 해시 링 위에서 같은 구간에 몰리면 그 서버 하나가 나머지보다 훨씬 많은 부하를 받습니다.

 

평균 부하에 여유 계수를 곱한 상한선

전체 요청 수를 서버 수로 나눈 평균 부하에 여유 계수 c(보통 1.25)를 곱해 각 서버의 용량 상한으로 삼습니다. 키를 해시 링에서 찾을 때 원래 가장 가까운 서버가 이미 상한에 도달했다면 건너뛰고, 링을 계속 돌며 여유가 있는 다음 서버를 찾습니다. 이 과정으로 어떤 서버도 평균 부하의 c배를 초과해 받지 않음이 수학적으로 보장됩니다.

방식 부하 상한 보장 캐시 지역성
기본 일관된 해싱 없음 최상
Bounded Loads 수학적으로 c배 이내 상한 도달 시 저하

 

여유 계수가 만드는 트레이드오프

여유 계수 c를 1에 가깝게 잡을수록 부하는 더 균등해지지만, 원래 서버가 아닌 우회 서버로 가는 요청이 늘어나 캐시 지역성이 깨집니다. 반대로 c를 크게 잡으면 캐시 지역성은 잘 유지되지만 핫스팟 완화 효과가 줄어듭니다. 실무에서는 c=1.25 전후에서 시작해 트래픽 패턴을 보며 조정합니다.

Bounded Load 조회 로직
def get_server_bounded(key, ring, load_tracker, c=1.25):
    total_load = sum(load_tracker.values())
    num_servers = len(load_tracker)
    capacity = int(c * total_load / num_servers)

    candidate = ring.find_first_clockwise(hash(key))
    while load_tracker[candidate] >= capacity:
        candidate = ring.next_clockwise(candidate)

    load_tracker[candidate] += 1
    return candidate

 

실무 포인트

여유 계수 c는 서비스 특성에 맞춰 실험적으로 결정해야 합니다. 캐시 적중률이 결정적인 서비스는 c를 크게, 부하 균등이 더 중요한 서비스는 c를 작게 잡는 편이 유리합니다.

부하 카운터의 감소 시점 설계가 실질적인 효과를 좌우합니다. 일정 시간 윈도우로 누적하면 순간적인 버스트에 더 안정적으로 대응할 수 있습니다.

주의 — 모든 서버가 동시에 상한에 도달하는 극단적 상황에서는 우회 탐색이 링을 한 바퀴 돌 수 있으므로, 임계 상황에서는 상한을 무시하고 라운드로빈으로 폴백하는 안전장치가 필요합니다.
