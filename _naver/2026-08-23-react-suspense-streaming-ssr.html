첫 바이트는 먼저, 느린 데이터는 나중에 — React Suspense 스트리밍 SSR의 동작 원리

2026. 8. 23. · 프론트엔드

한 줄 요약 — 기존 SSR은 가장 느린 데이터가 준비될 때까지 HTML을 한 바이트도 못 보내는 구조였습니다. React의 renderToPipeableStream과 Suspense가 셸을 먼저 보내고 느린 조각을 나중에 흘려보내는 스트리밍 SSR의 내부 동작 원리와 실무 주의점을 정리했습니다.

 

기존 SSR은 왜 느린 데이터에 인질로 잡힐까요

전통적인 React 서버 렌더링의 병목은 함수 이름에 이미 드러나 있습니다. renderToString은 완성된 문자열 하나를 반환해야 하므로, 페이지에서 가장 느린 데이터(예: 외부 API에서 가져오는 추천 목록)가 준비될 때까지 서버는 브라우저에 아무것도 보내지 못합니다. 페이지의 대부분이 이미 렌더링 가능한 상태여도, 남은 한 조각 때문에 전체 응답이 붙들려 있는 셈입니다.

문제는 서버에서 끝나지 않습니다. HTML이 도착한 뒤에도 브라우저는 자바스크립트 번들을 로드하고 페이지 전체를 하이드레이션해야 비로소 클릭에 반응합니다. 즉 기존 SSR은 "데이터 전부 → 렌더 전부 → 하이드레이션 전부"라는 세 단계가 직렬로 이어진 폭포수 구조였습니다.

React 18에서 도입된 renderToPipeableStream과 Suspense 조합은 이 세 단계를 각각 조각냅니다. Next.js App Router의 스트리밍도 결국 이 기반 위에 서 있으므로, 프레임워크를 쓰시더라도 밑에서 무슨 일이 일어나는지 알아두시면 디버깅과 성능 튜닝의 관점이 달라집니다.

 

핵심 개념 1 — 셸(shell)을 먼저 보내고, fallback을 나중에 교체합니다

스트리밍 SSR에서 서버는 페이지를 두 부류로 나눕니다. Suspense 경계 바깥의 모든 것이 셸이고, 경계 안쪽은 나중에 채워도 되는 조각입니다. 서버는 셸 렌더링이 끝나는 즉시 HTML 전송을 시작하는데, 아직 준비되지 않은 Suspense 영역 자리에는 fallback으로 지정한 스피너나 스켈레톤의 HTML이 대신 실려 나갑니다.

이후 느린 데이터가 준비되면 서버는 같은 HTTP 응답 위에 추가 청크를 흘려보냅니다. 각 청크에는 완성된 콘텐츠가 hidden 상태의 태그로 들어 있고, 그 뒤에 붙는 작은 인라인 스크립트가 DOM에서 fallback을 찾아 실제 콘텐츠로 교체합니다. 자바스크립트 번들이 로드되기 전이라도 스트리밍만으로 화면이 점진적으로 완성되는 것입니다.

 

 

핵심 개념 2 — 하이드레이션도 조각 단위로, 클릭한 곳부터

스트리밍이 "HTML을 조각으로 보내기"라면, 선택적 하이드레이션(Selective Hydration)은 "자바스크립트를 조각으로 붙이기"입니다. React 18부터 하이드레이션은 페이지 전체가 아니라 Suspense 경계 단위로 진행됩니다. 아직 HTML이 도착하지 않은 영역이 있어도 나머지 부분은 먼저 인터랙티브해집니다.

더 흥미로운 것은 우선순위 조정입니다. 사용자가 아직 하이드레이션되지 않은 영역을 클릭하면 React는 그 이벤트를 기록해 두고, 해당 경계의 하이드레이션을 앞당긴 뒤 이벤트를 재생합니다. 결국 Suspense 경계는 로딩 UI의 단위이자, 스트리밍 청크의 단위이자, 하이드레이션 스케줄링의 단위라는 세 가지 역할을 겸하게 됩니다.

구분 renderToString renderToPipeableStream
첫 바이트 시점 전체 렌더 완료 후 셸 완료 즉시
느린 데이터 처리 전체 응답이 대기 fallback 먼저, 청크로 교체
하이드레이션 사실상 전체 단위 경계 단위 + 우선순위 조정
적합한 환경 간단한 페이지, 레거시 호환 느린 데이터 소스가 섞인 동적 페이지

 

예제 — Express에서 스트리밍 SSR 구성하기

아래는 Node.js Express 서버에서 renderToPipeableStream으로 스트리밍 응답을 구성하는 예시입니다. 핵심은 onShellReady 콜백에서 pipe를 호출해, 느린 데이터를 기다리지 않고 전송을 시작하는 부분입니다.

// App.jsx — 느린 데이터 영역만 Suspense로 감쌉니다
import { Suspense } from 'react';
import Recommendations from './Recommendations';

export default function App() {
  return (
    <div>
      <main>빠르게 렌더링되는 본문(셸)</main>
      <Suspense fallback={<p>추천 목록 불러오는 중…</p>}>
        <Recommendations />
      </Suspense>
    </div>
  );
}

// server.js — Node.js + Express
import express from 'express';
import { renderToPipeableStream } from 'react-dom/server';
import App from './App';

const app = express();

app.get('/', (req, res) => {
  let didError = false;
  const { pipe } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/main.js'],
    onShellReady() {
      // 셸이 준비된 순간 전송 시작
      res.statusCode = didError ? 500 : 200;
      res.setHeader('Content-Type', 'text/html; charset=utf-8');
      pipe(res);
    },
    onShellError(err) {
      // 셸 실패 시엔 아직 아무것도 안 보냈으므로 온전한 에러 응답 가능
      res.statusCode = 500;
      res.send('<h1>일시적인 오류가 발생했습니다</h1>');
    },
    onError(err) {
      didError = true; // 셸 이후 에러는 상태코드를 못 바꿉니다
      console.error(err);
    },
  });
});

app.listen(3000);

검색엔진 크롤러처럼 완성된 HTML이 필요한 요청에는 onShellReady 대신 onAllReady에서 pipe하도록 분기하면, 같은 코드로 스트리밍과 완전 렌더링을 모두 제공할 수 있습니다.

 

실무에서 자주 빠지는 함정
1. 중간 버퍼가 스트리밍을 삼킵니다 — 코드를 다 맞춰놓고도 스트리밍이 동작하지 않는 가장 흔한 원인은 React가 아니라 인프라의 버퍼링입니다. Nginx의 proxy_buffering, 일부 CDN, Node의 압축 미들웨어는 기본 설정에서 응답을 모아뒀다가 한 번에 내보내는 경우가 있습니다. 이러면 브라우저에는 응답이 통째로 도착해 기존 SSR과 다를 게 없어지므로, 프록시 버퍼링을 끄거나(X-Accel-Buffering: no) 압축 미들웨어의 flush 동작을 확인하셔야 합니다.
2. 셸 전송 후에는 상태코드를 바꿀 수 없습니다 — onShellReady에서 이미 200을 보낸 뒤 발생한 에러는 HTTP 상태코드로 표현할 방법이 없습니다. 셸에는 반드시 성공해야 하는 최소한만 남기고, 실패 가능성이 있는 영역은 Suspense 경계 안으로 밀어 넣어 에러 바운더리와 함께 격리하는 것이 올바른 설계입니다.
3. 경계가 하나뿐이면 의미가 없습니다 — 페이지 전체를 하나의 거대한 Suspense로 감싸면 스트리밍의 이점이 사라집니다. 경계는 "독립적으로 늦어도 되는 단위"마다 쪼개시는 것이 좋습니다.

 

언제 쓰고, 언제 쓰지 말아야 할까요

스트리밍 SSR이 빛나는 경우는 응답 시간이 제각각인 데이터 소스가 한 페이지에 섞여 있을 때입니다. 커머스 상품 페이지에서 상품 정보는 빠르지만 리뷰·추천은 느릴 때, 셸을 먼저 보내고 느린 부분을 흘려보내면 첫 바이트 시간과 첫 화면 표시 시점이 동시에 좋아집니다.

반면 페이지 전체가 정적이라면 정적 생성(SSG)과 CDN 캐시가 언제나 더 빠르고 저렴합니다. 스트리밍 응답은 전체 HTML이 완성되기 전에 전송이 시작되므로 응답 단위 CDN 캐싱과 궁합이 나쁘고, 개인화가 없는 페이지에 굳이 적용하면 서버 비용만 늘어난다는 점도 함께 계산에 넣으시길 권합니다.

 

마무리 — 3줄 요약

① 스트리밍 SSR은 Suspense 경계 바깥(셸)을 즉시 보내고, 느린 조각은 fallback → hidden 콘텐츠 → 인라인 스크립트 교체 순서로 같은 응답에 흘려보냅니다.
② 하이드레이션도 경계 단위로 쪼개지며, 사용자가 클릭한 영역이 먼저 하이드레이션되는 우선순위 조정까지 이뤄집니다.
③ 프록시·압축의 버퍼링이 스트리밍을 무효화하는 함정과, 셸 전송 후 상태코드를 바꿀 수 없다는 제약을 설계 단계에서 고려해야 합니다.
