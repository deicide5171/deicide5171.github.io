"이 업무 프로세스를 에이전트로 자동화해주세요" — 결정론적 워크플로우와 자유형 위임, 경계를 어디에 그을 것인가

dev-strategy

한 줄 요약 — 업무 자동화 요청을 받으면 가장 먼저 답해야 할 질문은 모델 선택이 아니라, 작업을 실행 전에 단계로 적어둘 수 있는가입니다. 결정론적 워크플로우와 자유형 에이전트 위임의 실행 모델 차이, 프로덕션 실패율 데이터, 하이브리드 설계로 가는 판단 기준을 정리했습니다.

 

어떤 요구에서 출발하는가

"견적서 검토 프로세스를 에이전트로 자동화해주세요 — 서류를 받으면 항목을 확인하고, 이상하면 담당자에게 확인 요청을 보내고, 문제없으면 승인 처리까지 해주세요." 이런 요청이 들어오면 설계자가 가장 먼저 답해야 할 질문은 어떤 에이전트 프레임워크를 쓸까가 아닙니다. 이 작업의 다음 단계를 실행 전에 코드로 적어둘 수 있는가, 아니면 서류 내용을 보기 전까지는 다음에 뭘 할지 알 수 없는가입니다. 이 질문에 잘못 답하면 두 방향으로 실패합니다. 모든 경우의 수를 미리 그래프로 그리려다 기능 하나 추가할 때마다 그래프 전체를 다시 그려야 하는 유지보수 지옥에 빠지거나, 반대로 반복적이고 예측 가능한 작업에까지 완전한 자율성을 줘서 실행할 때마다 다른 경로를 타고 실패를 재현할 수 없는 상태에 빠집니다.

업무 자동화를 에이전트로 넘기는 일이 일상이 된 지금, 이 경계를 어디에 그을지는 매 프로젝트 초반에 반드시 내려야 하는 아키텍처 결정이 됐습니다.

 

전체 시스템에서의 위치 — 오케스트레이션 레이어는 어디에 앉는가

오케스트레이션 레이어는 요청을 받는 API 서버와 실제 LLM 호출 사이에 놓입니다. 결정론적 워크플로우를 선택하면 이 레이어는 상태를 가진 그래프나 스크립트가 되어, 어떤 단계 다음에 어떤 단계가 오는지를 코드가 통제하고 LLM은 각 노드 내부의 국소적 판단만 맡습니다. 자유형 에이전트를 선택하면 이 레이어 자체가 LLM이 되어, 다음에 어떤 도구를 부를지와 언제 작업을 끝낼지까지 스스로 판단합니다.

 

두 구조 모두 체크포인트 저장소(실패 시 재개 지점)와 도구 호출 계층을 공유하지만, 다음에 무엇을 할지 누가 결정하는가가 완전히 다릅니다.

 

선택의 트레이드오프
기준 결정론적 워크플로우 자유형 에이전트 위임
재현성·감사 같은 입력이면 같은 경로 실행마다 경로가 달라질 수 있음
실패 복구 단계 단위 체크포인트로 부분 재개 전체 트랜스크립트를 되짚어야 함
변화 대응 새 분기마다 그래프 수정 필요 프롬프트 수정만으로 대응 가능
적합한 작업 분기·순서가 이미 명확한 반복 업무 다음 단계가 불분명한 탐색 작업

 

이 선택이 추상적인 취향 문제가 아니라는 근거가 있습니다. 프로덕션에 올라간 1,600건 이상의 멀티에이전트 실행 트레이스를 분석한 조사에서 실패율이 41%~86.7%에 달했고, 그 원인의 대부분이 모델의 추론 능력 부족이 아니라 시스템 설계와 에이전트 간 정합성 문제였습니다. 자유도를 주면 더 똑똑하게 풀 것이라는 직관과 달리, 분할선이 이미 명확한 작업일수록 그 분할을 코드로 고정하는 편이 실패를 줄입니다.

업계 전반의 수렴 지점은 결국 하이브리드입니다. 뼈대는 결정론적 코드로 짜고, 판단이 꼭 필요한 지점에서만 LLM을 부릅니다. 2026년 들어 LangGraph의 PostgresSaver 체크포인터처럼 주요 오케스트레이션 프레임워크들이 공통적으로 "내구성 있는 실행(durable execution)"을 핵심 기능으로 끌어올린 것도 같은 흐름입니다.

 

코드로 보는 하이브리드 경계
def review_quote(document):
    state = checkpoint.load_or_init(document.id)

    if state.stage == "extract":
        fields = extract_fields(document)          # 결정론적 파싱
        state.stage = "classify"
        checkpoint.save(state)

    if state.stage == "classify":
        # 판단이 꼭 필요한 지점에서만 LLM 호출
        verdict = llm_classify(fields, schema=ANOMALY_SCHEMA)
        state.stage = "approve" if not verdict.anomaly else "escalate"
        checkpoint.save(state)

    if state.stage == "escalate":
        notify_reviewer(fields, verdict.reason)
        return "pending_human"

    if state.stage == "approve":
        approve_quote(document.id)
        return "approved"

전체 흐름은 코드가 결정하지만, "이 항목이 이상한가"라는 판단 하나만 스키마가 강제된 LLM 호출로 좁혀 넣었습니다. 이 범위를 넘어 LLM이 다음 단계 자체를 고르게 하면 하이브리드가 아니라 자유형으로 되돌아갑니다.

 

실무에서 걸리는 두 가지 안티패턴

첫 번째는 탐색적 작업을 억지로 결정론적 그래프에 끼워맞추는 경우입니다. 신규 요청 유형이 생길 때마다 그래프에 분기를 추가해야 하고, 결국 그래프가 if문 트리와 다를 바 없어지며 유지보수 비용이 자유형 에이전트보다 커집니다. 두 번째는 반대로 반복적이고 예측 가능한 업무에 완전한 자율성을 준 경우입니다. 판단 체크리스트는 세 가지로 좁힐 수 있습니다. 다음 단계를 실행 전에 적을 수 있는가, 틀렸을 때 되돌리는 비용이 큰가, 분기 자체가 자주 바뀌는가.

 

실제 프로젝트 진행 순서

1단계: 작업을 단계 다이어그램으로 먼저 그려봅니다. 막히는 지점이 나오면 그 지점만 자유형 위임 후보로 표시합니다.

2단계: 각 단계의 입출력 스키마를 정의해 단계 간 경계를 명확히 합니다.

3단계: 실패 복구 비용이 큰 단계부터 체크포인트 저장을 붙입니다.

4단계: 자유도가 꼭 필요한 지점만 식별해 그 노드에 한해 LLM 판단을 넣는 하이브리드로 전환하고, 실패 트레이스를 재현 가능한 리그레션 테스트 셋으로 전환합니다.

 

주의 — "에이전트가 알아서 판단하게 두면 더 유연하다"는 직관만으로 자유형을 고르면, 반복 업무에서도 실행 경로가 매번 달라져 디버깅이 불가능해집니다.

 

정리

자동화 설계의 첫 질문은 모델 선택이 아니라 다음 단계를 실행 전에 적을 수 있는가입니다. 실제 실패율 데이터는 자유도를 늘릴수록 좋아진다는 직관과 반대로, 분할선이 명확한 작업은 코드로 고정하는 편이 안전하다는 것을 보여줍니다. 뼈대는 결정론적 코드, 판단은 범위가 좁혀진 LLM 호출이라는 하이브리드가 2026년 주요 프레임워크들이 수렴한 지점입니다.
