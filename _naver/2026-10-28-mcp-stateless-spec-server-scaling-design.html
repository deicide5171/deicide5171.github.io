"MCP 서버를 여러 대 띄웠더니 대화가 끊겨요" — 2026-07-28 스펙, 세션을 버리고 stateless로 가는 이유

AI

한 줄 요약 — MCP 2026-07-28 스펙이 세션 ID와 initialize 핸드셰이크를 없애고 완전한 stateless 아키텍처로 전환했습니다. 세션 스토어 없이 수평 확장하는 서버 설계, MRTR로 바뀌는 확인 흐름, 인증 강화까지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"MCP 서버 트래픽이 늘어서 인스턴스를 세 대로 늘렸는데, 같은 대화 중간에 요청이 다른 서버로 튀면 맥락이 끊깁니다." MCP 서버를 직접 운영해본 팀이라면 한 번쯤 마주쳤을 불만입니다. 원인은 단순합니다. 기존 MCP는 initialize 핸드셰이크에서 세션 ID를 발급하고, 이후 모든 요청이 Mcp-Session-Id 헤더를 달고 같은 서버 인스턴스로 돌아와야 했습니다. 로드밸런서는 이 세션을 기억해 항상 같은 뒷단으로 꽂아주는 sticky routing을 해야 했고, 서버는 세션 상태를 메모리나 Redis 같은 별도 스토어에 들고 있어야 했습니다.

2026년 7월 28일 발표된 MCP 스펙은 이 구조를 통째로 걷어냈습니다. initialize/initialized 핸드셰이크와 Mcp-Session-Id 헤더 자체가 사라졌고, 클라이언트의 신원·버전·역량 정보는 매 요청의 _meta 필드에 실려 함께 옵니다. 서버가 상태를 들고 있지 않아도 되는 쪽으로 설계가 바뀐 것입니다.

 

전체 시스템에서의 위치

세션 기반 구조에서는 서버를 여러 대로 늘리면 sticky routing 또는 공유 세션 스토어 중 하나를 선택해야 했습니다. 전자는 트래픽 분산이 안 되고, 후자는 매 요청마다 외부 스토어를 왕복해야 해서 지연이 늘어납니다.

stateless 전환 이후에는 클라이언트가 _meta에 신원 정보를 싣고, 게이트웨이는 Mcp-Method·Mcp-Name 같은 표준 헤더만 보고 아무 서버 인스턴스에나 요청을 보냅니다. 중간 확인이 필요한 흐름도 달라졌습니다. 기존에는 SSE 스트림을 계속 열어둔 채 기다려야 했지만, 이제는 MRTR(Multi Round-Trip Requests)로 짧은 요청-응답을 반복합니다.

 

선택의 트레이드오프
기준 기존(stateful) 신규(stateless)
수평 확장 sticky routing·공유 세션 스토어 필요 아무 인스턴스나 처리 가능
인스턴스 재시작 세션 유실 → 재연결 필요 영향 없음
중간 확인 흐름 SSE 장기 연결 유지 MRTR로 짧은 요청-응답 반복
마이그레이션 비용 해당 없음 세션 의존 코드 전면 재작성 필요

 

사내 전용으로 인스턴스가 한 대뿐이고 확장 계획이 없다면 당장 전환할 유인은 적습니다. 하지만 외부에 노출하거나 트래픽이 늘어날 가능성이 있는 서버라면, 세션 의존 코드가 쌓이기 전에 지금 전환하는 쪽이 나중의 재작성 비용보다 쌉니다.

 

실제 프로젝트 진행 순서

1. 세션 의존 코드부터 전수 식별합니다(세션 스토어 읽기/쓰기 지점).
2. 클라이언트 정보를 _meta에서 읽도록 요청 처리 로직을 재작성합니다.
3. 구버전 클라이언트를 위한 호환 레이어를 둡니다(Mcp-Session-Id 유무로 분기).
4. 게이트웨이가 Mcp-Method·Mcp-Name 헤더로 라우팅하도록 설정을 바꿉니다.
5. 확인이 필요한 플로우를 MRTR 기반으로 재구현합니다.
6. Dynamic Client Registration에 의존하던 인증 로직을 Client ID Metadata Document 방식으로 전환합니다.

 

예제 코드:

// 기존: 세션 ID로 서버 쪽 상태를 조회
app.post('/mcp', (req, res) => {
  const sessionId = req.headers['mcp-session-id'];
  const session = sessionStore.get(sessionId);
  res.json(handleRequest(session, req.body));
});

// 신규: 요청에 실린 _meta로 처리, 서버는 상태를 들고 있지 않음
app.post('/mcp', (req, res) => {
  const { _meta, ...rpc } = req.body;
  res.json(handleStatelessRequest(_meta, rpc));
});

 

주의 — sampling·roots 폐기는 서버가 클라이언트의 LLM 호출 능력을 빌려 쓰던 패턴을 막습니다. 이에 의존한 서버는 직접 모델을 호출하는 구조로 바꿔야 하며, 세션 제거와는 별개의 작업으로 다뤄야 합니다. 이번 변화는 블로그·뉴스레터 재구성 보도가 먼저 퍼졌으니, 구현 전 반드시 공식 스펙 문서와 SDK 체인지로그를 직접 확인하세요.

 

정리

MCP 2026-07-28 스펙은 세션 ID와 initialize 핸드셰이크를 없애고, 클라이언트 정보를 매 요청의 _meta에 싣는 완전한 stateless 구조로 전환했습니다. 서버를 여러 대로 늘릴 때 sticky routing이나 공유 세션 스토어가 필요 없어지고, 게이트웨이는 표준 헤더만으로 라우팅할 수 있습니다. 마이그레이션은 세션 의존 코드 제거, 구버전 호환 레이어, 인증 흐름 재검증, MRTR 기반 확인 플로우 재구현 순으로 접근하는 것이 안전합니다.
