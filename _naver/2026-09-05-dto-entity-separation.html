DTO와 엔티티를 왜 분리하나요 — 계층 간 데이터 전달 기초

백엔드

한 줄 요약 — 엔티티를 그대로 노출하면 민감정보 유출·강한 결합 문제가 생기며, DTO는 필요한 필드만 담아 이를 차단합니다.

 

엔티티를 그대로 응답으로 주면 안 되나

엔티티를 그대로 응답해도 처음엔 잘 동작하는 것 같지만, 프로젝트가 커지면 문제가 생깁니다. DTO는 계층 사이 데이터 전달용 전용 객체로, 엔티티를 직접 노출하지 않기 위해 씁니다.

 

엔티티를 그대로 노출할 때의 문제
문제 설명
민감정보 노출 비밀번호 해시까지 딸려 나감
강한 결합 DB 구조 변경이 API에 직결
순환 참조 연관 엔티티 직렬화 무한 루프

 

DTO로 분리하기
public record UserResponse(Long id, String email) {
    public static UserResponse from(User user) {
        return new UserResponse(user.getId(), user.getEmail());
        // passwordHash는 담지 않음 -> 노출 원천 차단
    }
}

응답용 DTO는 보여줄 필드만 담아, 비밀번호 해시 같은 필드를 애초에 넣지 않으므로 노출 사고를 원천 차단합니다.

 

실무 포인트

엔티티를 요청 본문으로 그대로 받는 것도 위험합니다. 클라이언트가 id나 권한 필드를 임의로 넣어 보낼 수 있기 때문입니다. 요청도 DTO로 받으세요.

주의 — 변환 코드가 번거로우면 MapStruct 같은 도구로 자동화할 수 있습니다. 학습용 토이 프로젝트가 아니면 DTO 분리가 사실상 표준입니다.
