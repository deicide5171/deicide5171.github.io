API 버저닝 입문 — API를 바꿔도 기존 앱이 안 깨지게

2026. 9. 8. · 백엔드

한 줄 요약 — API 버저닝은 옛 버전을 함께 제공해 기존 사용자를 안 깨뜨리는 방법이며, URI 경로(/v1/) 방식이 가장 직관적입니다.

 

API를 함부로 바꾸면 안 되는 이유

응답 형식을 바꾸면 이미 설치된 앱들이 오작동합니다. 앱은 사용자가 업데이트해야 새 버전이 되므로 옛 버전도 계속 쓰입니다. API 버저닝은 옛·새 버전을 함께 제공해 이를 해결합니다.

 

버저닝 방법 3가지
방법 예시
URI 경로 /v1/users, /v2/users
쿼리 파라미터 /users?version=2
헤더 Accept: ...v2+json

 

언제 새 버전이 필요한가
버전 올림(호환 깨짐): 필드 이름·타입 변경, 필드 삭제, 필수 파라미터 추가
버전 안 올림(하위 호환): 선택 필드 추가, 새 엔드포인트 추가
-> "기존 클라이언트가 계속 동작하는가?"가 기준

 

실무 포인트

버전을 함부로 올리지 말고 하위 호환을 최대한 유지하세요. 버전이 여러 개면 유지보수 부담이 커집니다.

주의 — v2를 냈다고 v1을 갑자기 없애면 v1 사용자가 깨집니다. 지원 종료(deprecation) 계획을 미리 공지해 마이그레이션 시간을 주세요.
