서킷 브레이커 패턴, 장애 전파를 막는 방법

2026. 8. 15. · 시스템 설계

한 줄 요약 — 서킷 브레이커는 계속 실패하는 서비스 호출을 잠시 차단해서, 작은 장애가 시스템 전체로 번지는 것을 막아주는 패턴입니다.

 

작은 장애가 왜 시스템 전체를 멈추게 할까요

여러 서비스가 서로 호출하며 동작하는 구조에서는, 서비스 하나가 잠깐 느려지기만 해도 그걸 기다리는 다른 서비스들의 자원(스레드, 커넥션)까지 함께 고갈되는 일이 벌어질 수 있습니다. 이렇게 장애가 도미노처럼 퍼지는 현상을 연쇄 장애라고 부릅니다. 이를 막기 위해 나온 대표적인 방법이 바로 서킷 브레이커입니다.

 

전기 차단기에서 이름을 따온 이유

전기 회로에 과부하가 걸리면 차단기가 전류를 끊어 화재를 막듯이, 소프트웨어에서도 특정 서비스 호출이 계속 실패하면 호출 자체를 아예 막아버립니다. 서킷 브레이커는 아래 표처럼 세 가지 상태를 오가며 동작합니다.

상태 동작 다음 단계로 넘어가는 조건
Closed(닫힘) 평소처럼 요청을 통과시킴 실패가 많아지면 Open으로
Open(열림) 요청을 즉시 차단 일정 시간 뒤 Half-Open으로
Half-Open(반열림) 시험 삼아 일부만 통과시킴 성공하면 Closed, 실패하면 다시 Open

 

재시도와 함께 써야 하는 이유

서킷 브레이커만 있어서는 부족합니다. 실무에서는 타임아웃(무한 대기 방지), 재시도(잠깐의 장애는 시간 간격을 두고 다시 시도), 서킷 브레이커(계속 실패하면 아예 차단), 벌크헤드(문제 영역 격리)를 함께 사용합니다. 재시도만 하고 서킷 브레이커가 없으면 이미 힘든 서비스에 재시도 요청이 몰려 오히려 상황이 나빠질 수 있다는 점이 자주 지적됩니다.

if state == "OPEN":
    if 시간_경과 > 재시도_대기시간:
        state = "HALF_OPEN"
    else:
        return 대체_응답()  # fallback

result = 실제_서비스_호출()
if result == 실패:
    실패횟수 += 1
    if 실패횟수 >= 임계치:
        state = "OPEN"
else:
    state = "CLOSED"

 

실무 도입 시 이것만은 챙기세요
1. 임계치는 서비스마다 다르게 — 트래픽 패턴이 다르니 일괄 적용은 피하세요.
2. 폴백 응답을 미리 설계 — 차단됐을 때 무엇을 보여줄지 미리 정해두세요.
3. 상태 전이를 꼭 모니터링 — Open으로 바뀌는 순간을 놓치지 마세요.
4. 재시도와의 상호작용 검증 — 재시도가 서킷을 너무 빨리 열게 만들지 않는지 확인하세요.

 

마무리 — 3줄 요약

① 서킷 브레이커는 계속 실패하는 호출을 차단해 연쇄 장애를 막습니다.
② 타임아웃, 재시도, 벌크헤드와 함께 계층적으로 써야 효과가 큽니다.
③ 임계치, 폴백 전략, 모니터링을 서비스 특성에 맞게 설계해야 합니다.

읽어주셔서 감사합니다. 다음에는 벌크헤드 패턴처럼 함께 쓰이는 다른 회복력 패턴도 다뤄보겠습니다.
