분산 환경에서 Rate Limiting이 새는 이유

아키텍처·시스템 설계

한 줄 요약 — 인스턴스별 독립 카운팅은 트래픽 분산이 불균등할 때 한도를 초과시키므로, Redis Lua 스크립트로 원자성을 확보한 슬라이딩 윈도우 카운터가 필요합니다.

 

왜 분산 환경에서 어려운가

싱글 인스턴스에서 메모리 변수 하나로 요청 수를 세는 rate limiter는 완벽하게 동작합니다. 문제는 서비스를 스케일 아웃하는 순간 시작됩니다. 특정 클라이언트의 요청이 라우팅 정책 때문에 한두 인스턴스에 몰리면, 그 인스턴스만 한도를 초과해서 통과시키거나 다른 클라이언트를 부당하게 차단하게 됩니다.

 

알고리즘 선택: 고정 윈도우 vs 슬라이딩 윈도우 vs 토큰 버킷

가장 단순한 고정 윈도우는 윈도우 경계에서 버스트가 두 배로 통과하는 결함이 있습니다. 슬라이딩 윈도우 로그는 정확하지만 메모리 비용이 큽니다. 실무에서 가장 널리 쓰이는 절충안은 슬라이딩 윈도우 카운터로, 현재와 이전 윈도우의 카운트를 가중 평균해 근사치를 계산합니다.

알고리즘 정확도 메모리 비용
고정 윈도우 낮음(경계 결함) 최소
슬라이딩 윈도우 카운터 근사치(충분) 낮음
토큰 버킷 높음 낮음

 

진짜 문제: 원자성

여러 인스턴스가 Redis 같은 공유 저장소에 카운트를 두더라도, "읽고 → 비교하고 → 증가"를 별도 명령으로 실행하면 두 요청이 동시에 같은 값을 읽어 둘 다 통과시키는 경쟁 조건이 생깁니다. Redis Lua 스크립트는 싱글 스레드로 실행되므로 이 세 단계를 하나의 원자적 연산으로 묶을 수 있습니다.

Redis Lua 원자적 토큰 버킷 예제
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call("HMGET", key, "tokens", "last_refill")
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

local elapsed = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call("HMSET", key, "tokens", tokens, "last_refill", now)
    return 1
else
    return 0
end

이 스크립트를 EVALSHA로 호출하면 읽기·계산·쓰기가 하나의 원자적 단위로 실행되어, 인스턴스가 몇 대든 정확한 한도를 보장합니다.

 

실무 포인트

로컬 캐시로 Redis 왕복을 줄이되 트레이드오프를 고려하세요. 로컬 한도를 전체의 80%로 설정하고 정밀 판단만 Redis에 위임하는 2단계 구조가 흔히 쓰입니다.

시계 드리프트에 주의하세요. 인스턴스 시각이 미세하게 다르면 토큰 버킷 리필 계산이 왜곡될 수 있으므로, Redis의 TIME 명령으로 기준 시각을 통일하는 것이 안전합니다.

주의 — 한도 초과 응답에 Retry-After 헤더를 포함하지 않으면 클라이언트가 즉시 재시도를 폭주시켜 오히려 부하를 키울 수 있습니다.
