분산 레이트 리미팅 알고리즘 비교 — Token Bucket vs Sliding Window Log

아키텍처·시스템 설계

한 줄 요약 — 여러 인스턴스에서 로컬 카운터로 레이트 리미팅하면 실제 제한이 무력화됩니다. Token Bucket, Sliding Window 알고리즘의 경계 처리 차이를 정리했습니다.

 

왜 지금 레이트 리미팅 알고리즘을 다시 봐야 하는가

서비스가 여러 인스턴스로 스케일아웃되면 인메모리 카운터로는 초당 100건 제한이 인스턴스 10대에서 각각 100건씩 통과해 실제로 1000건이 통과하는 상황이 벌어집니다. 모든 인스턴스가 공유하는 중앙 저장소에서 카운팅해야 하며, 알고리즘에 따라 정확도와 메모리 사용량이 크게 달라집니다.

 

Fixed Window의 경계 버스트 문제

고정 시간 창마다 카운터를 리셋하는 방식은 0.9초에 99건, 리셋 직후 다시 100건이 몰리면 0.2초 사이 199건이 통과하는 결함이 있습니다. 실제 감당해야 하는 순간 부하를 과소평가하게 만듭니다.

 

Token Bucket과 Sliding Window Log의 접근 차이

Token Bucket은 일정 속도로 토큰이 채워지는 버킷에서 요청마다 토큰을 꺼내 쓰며, 버킷 용량만큼 버스트를 허용합니다. Sliding Window Log는 모든 요청 타임스탬프를 기록해 정확하게 판단하지만 메모리 사용량이 크다는 단점이 있습니다. Sliding Window Counter가 그 사이를 근사적으로 절충합니다.

알고리즘 경계 정확도 메모리 사용량
Fixed Window 낮음 (최대 2배 통과) 매우 낮음
Token Bucket 중간 (의도된 버스트) 낮음
Sliding Window Log 높음 (정확) 높음

 

예제 — Redis로 구현하는 Token Bucket (Lua)
local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or tonumber(ARGV[1])
local last_refill = tonumber(bucket[2]) or tonumber(ARGV[3])

local elapsed = tonumber(ARGV[3]) - last_refill
local refill = elapsed * tonumber(ARGV[2])
tokens = math.min(tonumber(ARGV[1]), tokens + refill)

if tokens < 1 then
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_refill', ARGV[3])
    return 0
else
    tokens = tokens - 1
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_refill', ARGV[3])
    return 1
end

Lua 스크립트로 Redis에서 원자적으로 실행하면 여러 인스턴스가 동시에 접근해도 경쟁 조건 없이 정확하게 토큰을 소비할 수 있습니다.

 

실무 포인트

API 특성에 따라 알고리즘을 다르게 고르세요. 결제·로그인은 Sliding Window 계열, 검색·조회는 Token Bucket이 더 적합한 경우가 많습니다.

레이트 리미팅 로직은 반드시 원자적 연산으로 구현하세요. GET 후 SET을 별도 명령으로 나누면 경쟁 조건이 생겨 제한이 새어나갈 수 있습니다.

주의 — 클라이언트에게 제한 상태를 명시적으로 알려주세요. X-RateLimit-Remaining, Retry-After 헤더로 클라이언트가 자체 백오프하도록 유도하면 불필요한 재시도 폭주를 줄일 수 있습니다.
