대량 데이터 벌크 INSERT가 느릴 때 — 흔한 실수와 튜닝 방법

데이터베이스

한 줄 요약 — 반복문으로 INSERT를 하나씩 실행하면 네트워크 왕복이 누적되어 급격히 느려지므로, JDBC 배치나 DB 전용 벌크 로드 도구로 묶어서 처리해야 합니다.

 

왜 반복문 INSERT가 느린가

수십만 건을 반복문으로 하나씩 INSERT하면, 쿼리 자체는 수 밀리초여도 애플리케이션과 DB 사이의 네트워크 왕복이 그 횟수만큼 누적됩니다. 여기에 매 건마다 커밋까지 하면 DB가 매번 디스크에 로그를 플러시해야 해서 오버헤드가 더 쌓입니다.

 

잘못된 접근 vs 올바른 접근

흔한 실수는 커넥션 풀 크기를 늘리는 것인데, 커넥션 풀은 동시 요청을 위한 것이지 순차 반복문 자체를 빠르게 만들지 않습니다. 올바른 접근은 JDBC 배치로 여러 INSERT를 한 번에 전송하는 것입니다.

jdbcTemplate.batchUpdate(
    "INSERT INTO orders (id, amount) VALUES (?, ?)",
    orders, 500,
    (ps, order) -> {
        ps.setLong(1, order.getId());
        ps.setBigDecimal(2, order.getAmount());
    }
);

MySQL은 URL에 rewriteBatchedStatements=true를 명시하지 않으면 batchUpdate를 써도 내부적으로 하나씩 보내는 경우가 있으니, 실제 배치가 적용됐는지 반드시 확인해야 합니다. 초대량 이관이라면 PostgreSQL의 COPY, MySQL의 LOAD DATA INFILE 같은 DB 전용 벌크 도구가 훨씬 빠릅니다.

방식 특징
반복 INSERT 건별 네트워크 왕복, 매우 느림
JDBC 배치 수백 건씩 묶어 전송, 실용적
COPY / LOAD DATA 파싱·플래닝 생략, 가장 빠름

 

주의 — 인덱스가 많은 테이블은 행마다 모든 인덱스가 함께 갱신되어 느려집니다. 초기 대량 적재라면 인덱스를 일시 제거하고 데이터를 넣은 뒤 다시 생성하는 것이 더 빠를 수 있습니다.

 

실무 포인트

오토커밋을 반드시 끄고 명시적 트랜잭션으로 묶으세요. 전체를 하나의 트랜잭션으로 묶으면 롤백 비용이 커지므로 수천~수만 건 단위로 커밋 지점을 나누는 것이 안전합니다. 적재 후에는 옵티마이저 통계(ANALYZE)를 갱신해야 이후 쿼리 실행 계획이 정확해집니다. 배치 크기도 너무 크게 잡으면 DB의 최대 패킷 크기를 초과할 수 있으니 실측하며 조정하세요.
