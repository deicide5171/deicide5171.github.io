레이트 리밋이 왜 필요할까요

외부에 API를 열어두면 누군가 과도하게 호출해서 시스템 전체가 흔들리는 상황을 피하기 어렵습니다. 최근에는 요청 단가가 비싼 LLM API가 늘면서 레이트 리밋이 단순한 방어 장치를 넘어 비용 관리 수단으로도 쓰이고 있습니다. 문제는 서버를 한 대에서 여러 대로 늘리는 순간, 예전에 잘 동작하던 카운팅 로직이 어긋나기 시작한다는 점입니다.

단일 서버와 분산 환경, 무엇이 다를까요

서버가 한 대라면 메모리 안에서 카운터를 관리해도 충분합니다. 하지만 여러 대로 늘어나면 각 서버가 따로따로 카운트를 세기 때문에 실제로는 훨씬 많은 요청이 통과해버릴 수 있습니다. 이를 막기 위해 Redis 같은 중앙 저장소에서 원자적 연산으로 카운터를 관리하는 방식이 널리 쓰입니다.

 

간단한 코드 예시
def is_allowed(client_id, limit=100, window_sec=60):
    key = f"rl:{client_id}:{int(time.time() // window_sec)}"
    count = r.incr(key)
    if count == 1:
        r.expire(key, window_sec)
    return count <= limit

 

실무 도입 시 이것만은 챙기세요
1. 429 응답과 Retry-After — 언제 재시도하면 되는지 클라이언트에 명확히 알려주세요.
2. 등급별·엔드포인트별 정책 — 쓰기 API는 읽기 API보다 낮은 한도를 두는 식으로 세분화하세요.
3. 게이트웨이와 애플리케이션 이중 구조 — 1차 방어는 게이트웨이, 세밀한 정책은 애플리케이션에서 처리하세요.
4. Redis 장애 대응 전략 — 장애 시 허용할지 차단할지 미리 정해두어야 합니다.

 

마무리 — 3줄 요약

① 토큰 버킷은 버스트 허용, 리키 버킷은 평탄화라는 차이를 이해하고 상황에 맞게 선택해야 합니다.
② 서버가 여러 대라면 Redis 등 중앙 저장소의 원자적 연산으로 정확한 카운팅을 보장해야 합니다.
③ 429 응답, Retry-After, 등급별 정책까지 함께 설계해야 실무에서 안정적으로 동작합니다.
