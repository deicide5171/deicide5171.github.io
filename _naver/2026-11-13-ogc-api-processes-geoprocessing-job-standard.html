'지도 위에서 시뮬레이션 버튼 눌러주세요'가 왔을 때 — 지오프로세싱 작업을 표준 API로 만들 것인가

GIS

한 줄 요약 — 침수·확산 시뮬레이션처럼 오래 걸리는 연산을 지도 위 버튼 하나로 돌리게 하려면 비동기 작업 큐가 필요합니다. 이걸 사내 REST+Celery로 직접 짤지, OGC API - Processes 표준을 따를지 — 표준화의 득과 실을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"지도에서 지역을 그리고 '침수 시뮬레이션 돌리기'를 누르면 결과가 지도 위에 뜨게 해주세요." 기획자의 이 한 문장은 생각보다 복잡한 기술 문제로 번역됩니다. 시뮬레이션 연산은 몇 초가 아니라 몇 분, 심하면 몇십 분이 걸릴 수 있어서 HTTP 요청-응답으로 바로 받을 수 없습니다. 그러면 작업을 큐에 넣고, 작업 ID를 돌려주고, 클라이언트가 그 ID로 상태를 폴링하다가 끝나면 결과를 받아오는 비동기 작업 패턴이 필요해집니다. 문제는 이 작업이 "지오프로세싱"이라는 점입니다 — 입력은 폴리곤과 좌표계가 섞인 공간 데이터이고, 결과도 지도에 바로 얹을 수 있는 형태여야 합니다. 이걸 사내 REST API로 직접 설계할지, 아니면 OGC가 정한 표준인 OGC API - Processes를 따를지가 바로 이 자리의 선택입니다.

이 표준은 2022년에 Part 1(Core)이 정식 승인됐지만, 실무에서 체감되는 변화는 최근입니다. pygeoapi 같은 오픈소스 구현체가 비동기 실행을 지원하기 시작했고, GeoServer 쪽에서도 커뮤니티 모듈 형태로 Processes API를 노출하는 시도가 올라오고 있습니다. 동시에 Part 3(워크플로)는 여러 프로세스를 체이닝하고 다른 OGC API의 자원을 프로세스 입력으로 직접 참조하는 쪽으로 확장 중입니다. 중요한 건 "표준이 있다"는 사실이 아니라, 우리가 지금 짜려는 비동기 작업 큐를 표준 스펙에 맞춰 짜는 게 실제로 이득인지 판단하는 기준입니다.

 

전체 시스템에서의 위치

클라이언트는 연산 엔진을 직접 보지 않습니다. 항상 작업 API를 거쳐 "제출 → 폴링 → 결과 수신"의 3단계를 지납니다. OGC API - Processes가 표준화하는 건 바로 이 3단계의 엔드포인트 형태와 상태 모델(accepted → running → successful/failed)입니다. 연산 엔진 자체는 표준이 전혀 관여하지 않습니다 — 표준은 어디까지나 그 엔진을 감싸는 API 계약입니다.

 

선택의 트레이드오프
기준자체 REST+작업 큐OGC API - Processes
개발 속도빠름느림(스펙 학습 필요)
클라이언트 재사용성낮음높음(QGIS 등 호환 도구)
다른 OGC 데이터 연계직접 구현Part 3에서 바로 참조 가능
생태계 성숙도해당 없음pygeoapi는 성숙, GeoServer 모듈은 Draft

 

핵심 판단 기준은 "이 지오프로세싱 기능을 외부에 공개하거나, 다른 GIS 도구와 연동할 계획이 있는가"입니다. 사내 전용으로 끝나는 단발성 기능이라면 표준을 따르는 학습 비용이 아깝습니다. 반대로 여러 시뮬레이션 모델을 동일한 패턴으로 계속 추가하거나 외부 기관이 같은 API를 호출해야 한다면 표준의 일관성이 빠르게 이득으로 돌아옵니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 표준을 공부하는 게 아니라, 우리 시뮬레이션이 실제로 얼마나 걸리는지 측정하는 것입니다. 몇 초 안에 끝난다면 비동기 작업 자체가 필요 없습니다. 몇 분 이상 걸린다면, 프로세스 입력·출력 스키마를 OGC의 프로세스 디스크립션 형식으로 먼저 적어봅니다 — 이 단계에서 적합성이 거의 결정됩니다.

{
  "id": "flood-simulation",
  "inputs": {
    "area": { "schema": { "type": "object", "format": "geojson-polygon" } },
    "rainfallMm": { "schema": { "type": "number", "minimum": 0 } }
  },
  "outputs": {
    "floodExtent": { "schema": { "type": "object", "format": "geojson-featurecollection" } }
  }
}

스키마가 자연스럽게 나오면 pygeoapi 같은 참조 구현 위에 우리 연산 엔진을 플러그인으로 얹어 프로토타입을 돌려봅니다. 여기서 막히는 지점은 대개 두 곳입니다 — 작업 상태를 어디에 저장할지(Redis나 DB 필요), 결과 지오메트리가 커질 때 응답에 직접 담을지 별도 파일로 분리할지입니다.

 

주의 — GeoServer의 Processes 모듈은 아직 Draft 단계입니다. 프로덕션에 바로 올리기보다는 pygeoapi를 프록시 삼아 먼저 검증하는 편이 안전합니다.
