수천만 건을 안전하게 — Spring Batch로 설계하는 대용량 배치 처리

2026. 8. 24. · 백엔드

한 줄 요약 — for문 기반 배치 스크립트가 무너지는 지점을 짚고, Spring Batch의 청크 모델·파티셔닝·재시작 설계로 대용량 배치를 안전하게 구성하는 법을 정리했습니다.

 

단순 for문 배치가 무너지는 지점

"매일 새벽 3시, 전체 주문 테이블을 읽어 정산 파일을 생성한다"는 요구사항을 단순 for문과 JPA로 구현하면 처음 몇 달은 문제없이 돌아갑니다. 그러다 데이터가 수백만 건을 넘기면 영속성 컨텍스트에 엔티티가 쌓여 메모리가 터지고, 중간에 실패하면 처음부터 다시 돌려야 하고, 어디까지 처리됐는지 추적할 방법도 없습니다.

Spring Batch는 이 문제를 위해 처음부터 설계된 프레임워크입니다. 청크 단위 처리로 메모리를 제한하고, 실패 지점부터 재시작할 수 있는 메타데이터를 자동 관리하며, 파티셔닝으로 멀티스레드·분산 처리까지 확장할 수 있습니다.

 

핵심 개념 1 — Job-Step-Chunk 모델

Spring Batch의 계층 구조는 Job → Step → Chunk입니다. Tasklet 방식은 단순 작업을 한 번에 실행하고, Chunk-oriented 방식은 ItemReader가 하나씩 읽고 ItemProcessor가 변환하고 지정한 개수(청크 크기)만큼 모이면 ItemWriter가 한 번에 씁니다. 이 단위로 트랜잭션이 커밋됩니다.

청크 방식이 대용량 처리의 핵심인 이유는 메모리 사용량이 청크 크기에 비례해 고정되기 때문입니다. 1000만 건을 처리하든 100건을 처리하든, 청크 크기를 100으로 두면 메모리에는 항상 최대 100건만 존재합니다.

 

핵심 개념 2 — 확장 전략: 멀티스레드, 파티셔닝, 원격 청킹
전략 동작 방식 적합한 상황
Multi-threaded Step 청크 처리를 여러 스레드로 병렬화 Reader/Writer 스레드 안전 확보 시
Partitioning 범위별로 나눠 워커가 각각 처리 ID/날짜 범위로 자연 분할 가능할 때
Remote Chunking 메시징으로 원격 워커에서 처리 처리 로직이 무겁고 별도 스케일 아웃 필요 시

 

파티셔닝이 실무에서 가장 널리 쓰이는데, PartitionHandler가 각 파티션의 범위를 워커 Step에 나눠주고, 각 워커가 독립적인 트랜잭션과 재시작 상태를 갖습니다.

 

예제 — 파티셔닝 기반 대용량 정산 배치
@Bean
public Step partitionStep(JobRepository jobRepository,
                           Step workerStep,
                           Partitioner rangePartitioner) {
    return new StepBuilder("partitionStep", jobRepository)
            .partitioner("workerStep", rangePartitioner)
            .step(workerStep)
            .gridSize(8) // 8개 파티션으로 분할
            .taskExecutor(new SimpleAsyncTaskExecutor("partition-"))
            .build();
}

@Bean
public Step workerStep(JobRepository jobRepository,
                        PlatformTransactionManager txManager,
                        ItemReader<Order> reader,
                        ItemProcessor<Order, Settlement> processor,
                        ItemWriter<Settlement> writer) {
    return new StepBuilder("workerStep", jobRepository)
            .<Order, Settlement>chunk(500, txManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .skip(DataIntegrityViolationException.class)
            .skipLimit(100)
            .build();
}

 

실무 도입 시 이것만은 챙기세요
1. 재시작 가능성을 처음부터 설계에 넣으세요 — ItemWriter가 멱등하지 않으면 재시작 시 중복 처리가 발생하므로 UPSERT나 처리 여부 플래그로 멱등성을 확보해야 합니다.
2. Reader는 커서보다 페이징 방식을 기본으로 고려하세요 — 커서 방식은 연결을 오래 점유하고 파티셔닝과의 조합에서 스레드 안전성 문제가 생기기 쉽습니다.
3. skip과 retry 정책을 명확히 분리하세요 — 일시적 오류는 retry, 데이터 결함은 skip으로 처리해야 진짜 문제가 재시도 루프에 묻히지 않습니다.

 

마무리 — 3줄 요약

① 대용량 배치는 청크 단위 처리로 메모리 사용량을 고정 크기로 제한하는 것이 출발점이며, Spring Batch의 Job-Step-Chunk 모델이 이를 기본 제공합니다.
② 처리량 확장은 멀티스레드 Step, 파티셔닝, 원격 청킹 중 데이터 분할 가능성에 맞춰 선택하며, 파티셔닝이 가장 널리 쓰입니다.
③ 재시작 시 멱등성 확보, 페이징 기반 Reader, skip/retry 정책 분리가 배치 안정성을 좌우하는 핵심입니다.
