캐시는 채우기보다 지우기가 어렵다 — 쿼리 결과 캐싱과 무효화 전략

2026. 8. 30. · 데이터베이스

한 줄 요약 — 쿼리 결과 캐싱의 진짜 난제는 저장이 아니라 무효화입니다. 키 설계, TTL과 쓰기 시 무효화의 구분, 태그 기반 무효화로 정확도를 올리는 방법을 정리했습니다.

 

캐싱보다 어려운 건 지우는 타이밍입니다

읽기 비중이 압도적으로 높은 서비스에서 쿼리 결과를 캐싱하는 건 당연한 선택입니다. 문제는 캐싱 자체가 아니라 원본 데이터가 바뀌었을 때 캐시를 어떻게 정확히, 늦지 않게 지우느냐입니다. 무효화 로직은 데이터 변경 경로마다 빠짐없이 걸려 있어야 하고, 하나라도 놓치면 사용자는 오래된 데이터를 계속 보게 되는데 이 버그는 재현하기도, 알아차리기도 어렵습니다.

이 글에서는 애플리케이션 코드 캐시가 아니라 쿼리 결과 캐싱을 DB 접근 계층에서 어떻게 설계하는가에 초점을 맞춥니다. 키 설계, TTL만으로 버틸 수 있는 경우와 버틸 수 없는 경우, 태그 기반 무효화까지 순서대로 살펴보겠습니다.

 

핵심 개념 1 — 캐시 키 설계: 무엇이 결과를 결정하는가

쿼리 결과 캐시의 키는 그 쿼리 결과를 유일하게 결정하는 모든 입력을 반영해야 합니다. 단순히 엔티티 ID만 키로 쓰면, 같은 데이터를 서로 다른 필터·정렬·페이지네이션으로 조회하는 여러 쿼리가 한 키에 뒤섞여 잘못된 결과를 반환할 수 있습니다. 실무에서는 쿼리 파라미터 전체를 정규화해 키의 일부로 씁니다.

cache:orders:user_id=123:status=shipped:sort=created_desc:page=2:v=3

여기서 v=3 같은 스키마 버전 접미사는 응답 필드가 바뀌는 배포를 할 때 이전 캐시를 자동으로 무효화하는 값싼 방법입니다. 버전을 올리면 새 버전 키만 채워지기 시작하고 옛 키는 TTL에 따라 자연히 사라집니다.

 

핵심 개념 2 — TTL만으로 버틸 수 있는 경계

가장 단순한 무효화 전략은 TTL뿐입니다. 원본이 바뀌어도 캐시를 굳이 찾아 지우지 않고 시간이 지나면 자연히 만료되게 둡니다. 이 방식이 통하려면 데이터가 바뀐 뒤 TTL이 끝날 때까지 오래된 값을 보여줘도 되는지가 "그렇다"여야 합니다. 반대로 재고, 결제 상태처럼 즉시 반영돼야 하는 데이터는 쓰기 시점에 능동적으로 무효화해야 합니다.

이때 흔한 실수가 쓰기 후 캐시부터 지우고 DB를 갱신하는 순서입니다 — 그 사이 다른 요청이 옛 DB 값으로 캐시를 다시 채워버리는 경쟁 조건이 생깁니다. 올바른 순서는 DB를 먼저 갱신하고 그 다음 캐시를 지우는 것이며, 남는 짧은 경쟁 조건 창은 짧은 TTL을 안전망으로 함께 둬서 완화합니다.

전략 적합한 데이터 최신성
TTL만 상품 설명, 통계성 집계 TTL만큼 지연 허용
쓰기 시 무효화 재고, 주문 상태 거의 즉시
태그 기반 무효화 다대다 참조 관계 데이터 관련 키 전체 즉시

 

핵심 개념 3 — 태그 기반 무효화: 관계형 캐시의 실전 해법

쿼리 결과가 여러 테이블을 조인한 결과라면, 이 캐시 키가 어떤 원본 로우들에 의존하는지를 추적해야 정확한 무효화가 가능합니다. 캐시 값을 저장할 때 그 값이 의존하는 엔티티들의 태그를 함께 등록하고, 해당 엔티티가 변경되면 그 태그에 연결된 모든 캐시 키를 한 번에 무효화하는 방식입니다. Redis에서는 흔히 Set 자료구조로 구현합니다.

 

예제 — cache-aside + 태그 무효화
// cache-aside 패턴 + 태그 기반 무효화
async function getOrderWithItems(orderId) {
  const key = `cache:order:${orderId}:v=2`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const order = await db.query(
    `SELECT o.*, oi.* FROM orders o
     JOIN order_items oi ON oi.order_id = o.id
     WHERE o.id = $1`, [orderId]
  );

  await redis.set(key, JSON.stringify(order), 'EX', 300);
  await redis.sadd(`tag:order:${orderId}`, key);
  for (const item of order.items) {
    await redis.sadd(`tag:product:${item.productId}`, key);
  }
  return order;
}

async function invalidateByTag(tagKey) {
  const keys = await redis.smembers(tagKey);
  if (keys.length > 0) {
    await redis.del(...keys);
  }
  await redis.del(tagKey);
}

 

실무 포인트

음성 캐싱(negative caching)을 잊지 마세요. 존재하지 않는 리소스 조회가 반복되면 매번 DB까지 내려가 부하를 만듭니다. 다만 나중에 생성되는 리소스라면 이 캐시가 최근 데이터를 숨기는 함정이 될 수 있으므로 TTL을 짧게 유지해야 합니다.

캐시 스탬피드는 별개 문제로 다뤄야 합니다. 인기 키가 만료되는 순간 동시에 수백 요청이 DB로 몰리는 현상은 TTL을 잘 설계해도 발생합니다. 락이나 확률적 조기 만료 같은 별도 장치가 필요합니다.

주의 — 캐시 무효화 호출 자체가 실패해도 애플리케이션은 조용히 넘어가는 경우가 많습니다. 무효화 실패율을 메트릭으로 노출하고, 실패 시 해당 키를 짧은 TTL로 강제 만료시키는 폴백 경로를 반드시 둬야 영원히 오래된 캐시가 남는 사고를 막을 수 있습니다.
