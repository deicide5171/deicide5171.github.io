가상 스레드 실전 도입 — Spring Boot에서 Virtual Threads 써도 될까

2026. 8. 15. · 웹 개발

한 줄 요약 — JDK Virtual Threads가 실무 적용 사례를 넓혀가는 가운데, 플랫폼 스레드와의 차이, Spring Boot 활성화 방법, pinning 같은 실전 함정을 정리했습니다.

 

왜 지금 Virtual Threads인가

Project Loom을 통해 JDK에 정식으로 들어온 Virtual Threads는 "스레드 하나당 요청 하나"라는 익숙한 프로그래밍 모델을 유지하면서도, 수만 개의 동시 요청을 감당할 수 있게 해줍니다. 그동안 대규모 동시성을 다루려면 리액티브 스택으로 전환해 콜백·연산자 체인을 배워야 했는데, Virtual Threads는 "블로킹 코드를 그대로 써도 확장이 된다"는 다른 접근을 제시합니다.

Spring Boot가 Virtual Threads를 정식 지원하면서, "리액티브로 재작성할 것인가, 기존 블로킹 코드에 Virtual Threads만 얹을 것인가"는 백엔드 설계에서 실질적인 선택지가 됐습니다.

 

플랫폼 스레드 vs 가상 스레드
항목 플랫폼 스레드 가상 스레드
생성 비용 OS 스레드 1:1, 무거움 JVM 관리, 매우 가벼움
동시 개수 수백~수천 개 한계 수십만 개까지 실용적
블로킹 I/O 스레드풀 고갈 위험 블로킹 시 캐리어 스레드 반납
프로그래밍 모델 동기 코드 동기 코드(변경 거의 없음)

 

핵심은 코드를 리액티브 스타일로 바꾸지 않고도 동시성 확장을 얻을 수 있다는 점입니다. 다만 모든 시나리오에서 리액티브를 완전히 대체하는 것은 아닙니다.

 

핵심 개념: Carrier Thread와 Pinning

가상 스레드는 실제로는 소수의 캐리어 스레드 위에서 스케줄링됩니다. 가상 스레드가 블로킹 I/O를 만나면 캐리어 스레드에서 내려가고, 캐리어 스레드는 다른 가상 스레드를 실행하러 갑니다.

문제는 pinning입니다. synchronized 블록 안에서 블로킹 I/O를 수행하면 가상 스레드가 캐리어 스레드를 내려놓지 못하고 그대로 점유해버려, 가상 스레드의 장점이 사라집니다. 레거시 코드에 synchronized가 많다면 ReentrantLock 등으로 교체하는 작업이 선행되어야 합니다.

 

예제: Spring Boot에서 활성화하기
# application.yml
spring:
  threads:
    virtual:
      enabled: true

// Controller 코드는 그대로
@GetMapping("/orders/{id}")
public Order getOrder(@PathVariable String id) {
    return orderRepository.findById(id);
}

설정 한 줄만 추가하면 서블릿 컨테이너의 요청 처리 스레드가 가상 스레드로 바뀌며, 컨트롤러 코드는 전혀 수정할 필요가 없습니다.

 

실무 도입 시 이것만은 챙기세요
1. synchronized 사용처 점검 — pinning 발생 지점을 찾아 ReentrantLock으로 교체 검토
2. 커넥션 풀 크기 재검토 — 동시 요청 수가 늘면 DB 커넥션 풀 같은 유한 자원이 먼저 병목이 될 수 있음
3. CPU 바운드 작업엔 큰 이득 없음 — I/O 대기 구간만 효율화, 연산 자체는 빨라지지 않음
4. 점진적 전환 — I/O 대기 비중이 높은 엔드포인트부터 적용해 효과 확인 후 확대

 

마무리 — 3줄 요약

① Virtual Threads는 기존 블로킹 코드를 그대로 두고도 대규모 동시 요청을 처리할 수 있게 해줍니다.
② 캐리어 스레드 위에서 스케줄링되며, synchronized 블록 안 블로킹은 pinning을 유발할 수 있습니다.
③ Spring Boot는 설정 한 줄로 도입 가능하지만, 커넥션 풀 등 다른 병목은 별도로 재검토해야 합니다.
