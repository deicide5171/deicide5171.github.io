분산 SQL, 왜 지금 RDBMS와 NoSQL 사이의 답이 됐나

2026. 8. 15. · 시스템 설계

한 줄 요약 — 분산 SQL은 관계형 DB의 익숙함과 NoSQL의 수평 확장성을 동시에 노리는 아키텍처입니다. 내부 구조와 도입 전 체크포인트를 정리했습니다.

 

왜 지금 분산 SQL인가

서비스가 커지면 늘 같은 갈림길에 섭니다. 관계형 DB는 트랜잭션과 스키마가 익숙하지만 단일 노드의 한계에 부딪히고, NoSQL은 수평 확장은 쉽지만 조인·트랜잭션을 포기해야 하는 경우가 많죠. 그동안 많은 팀이 직접 샤딩을 구현하거나 일부 데이터만 NoSQL로 빼는 식으로 이 갈림길을 우회해왔습니다.

최근 CockroachDB, Google AlloyDB, YugabyteDB 같은 분산 SQL(Distributed SQL) 데이터베이스가 성숙해지면서, 관계형 스키마와 트랜잭션 보장을 유지한 채로 NoSQL 수준의 수평 확장을 노리는 선택지가 실용적인 수준에 올라왔습니다. PostgreSQL 호환 계층을 앞세운 제품이 늘어, 애플리케이션 코드를 크게 바꾸지 않고도 분산 아키텍처로 넘어갈 수 있다는 점이 특히 매력적입니다.

 

세 갈래 아키텍처 비교
항목 단일 노드 RDBMS NoSQL 분산 SQL
스키마/조인 강한 스키마, 조인 지원 유연, 조인 미지원 강한 스키마, 조인 지원
트랜잭션 강한 ACID 대체로 약함 분산 환경에서도 ACID 목표
확장 방식 수직 확장 위주 수평 확장 기본 수평 확장 + 관계형 유지
대표 비용 확장 한계, 단일장애점 트랜잭션·조인 제약 지연 시간(합의 라운드트립)

 

분산 SQL이 공짜로 확장성을 주는 건 아닙니다. 여러 노드가 하나의 값에 합의해야 하니, 그 합의 과정 자체가 새로운 지연 요소가 됩니다.

 

핵심 개념: Raft 합의와 리전 간 쓰기

분산 SQL 대부분은 데이터를 작은 범위(range)로 쪼개고, 각 range를 3개 이상의 노드에 복제한 뒤 Raft 같은 합의 알고리즘으로 리더를 뽑아 쓰기를 처리합니다.

리더는 해당 range의 쓰기를 받아 로그를 복제하고, 과반수 노드가 승인하면 커밋을 확정합니다. 팔로워는 리더의 로그를 복제해두고 리더 장애 시 새 리더 선출에 참여합니다. 노드 5개 중 3개(쿼럼)만 응답하면 커밋이 확정되므로, 과반수만 살아있으면 서비스가 계속됩니다.

멀티 리전 배포에서는 이 쿼럼 노드들이 지리적으로 떨어져 있을 수 있어, 쓰기 하나가 여러 리전을 오가는 라운드트립을 거치게 됩니다. 이것이 분산 SQL에서 가장 자주 나오는 지연 이슈의 원인입니다.

 

예제: 리전 인지 테이블 설계

CockroachDB 스타일의 지역 지정 예시입니다.

CREATE TABLE orders (
    order_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    region     STRING NOT NULL,
    customer   STRING NOT NULL,
    amount     DECIMAL NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
) LOCALITY REGIONAL BY ROW AS region;

REGIONAL BY ROW는 각 행의 리더 복제본을 region 컬럼 값에 해당하는 리전에 고정시킵니다. 한국 사용자의 주문은 한국 리전 노드가 리더가 되어, 매 요청마다 해외 리전까지 왕복하지 않고 로컬에서 쓰기를 처리할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. 핫스팟 방지 — range 하나에 쓰기가 몰리면 해당 리더 노드가 병목이 되니, 파티션 키 설계 단계에서 쓰기 분산을 검토
2. 읽기 일관성 수준을 명시적으로 선택 — 강한 일관성이 필요 없는 조회는 팔로워 읽기로 지연을 줄일 수 있음
3. 점진적 마이그레이션 — 전체 DB를 한 번에 옮기기보다, 확장이 필요한 도메인부터 이전하며 운영 노하우를 쌓기
4. 새로운 모니터링 지표 정의 — 단일 노드 시절의 응답 시간만으로는 부족, 리더 선출 빈도·쿼럼 지연·리밸런싱 이벤트도 함께 관찰

 

마무리 — 3줄 요약

① 분산 SQL은 관계형 스키마·트랜잭션을 유지하면서 NoSQL 수준의 수평 확장을 노리는 아키텍처입니다.
② 내부적으로는 range를 Raft로 복제하고 쿼럼 합의로 쓰기를 커밋하며, 이 합의 과정이 지연의 핵심 원인이 됩니다.
③ 리전 인지 테이블 설계와 파티션 키 선정이 실제 성능을 좌우하므로, 도입 전 워크로드 패턴 분석이 필수입니다.
