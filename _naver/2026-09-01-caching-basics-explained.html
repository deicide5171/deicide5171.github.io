캐시란 무엇인가 — 캐싱 기본 개념과 언제 써야 할까

시스템설계

한 줄 요약 — 캐시는 자주 쓰는 데이터를 빠른 저장소에 미리 복사해두는 기법으로, Cache-Aside 패턴이 가장 기본이 되는 조회 방식입니다.

 

왜 캐시 하나로 그렇게 큰 차이가 나는가

같은 데이터를 반복 요청하는데 매번 DB까지 가서 조회하면 DB 부하가 계속 쌓이고 응답도 느려집니다. 캐시는 자주 쓰이는 데이터를 원본보다 훨씬 빠른 위치(메모리)에 미리 복사해두는 기법입니다. 메모리 접근은 디스크보다 수백~수천 배 빠릅니다.

 

캐시가 있는 곳과 없는 곳의 차이
상황 캐시 없음 캐시 있음
인기 상품 조회 1000번 DB 쿼리 1000번 첫 요청만 DB, 나머지는 캐시
응답 속도 수십~수백ms 수ms 이하

 

캐시를 쓸 때 반드시 마주치는 질문
1. 얼마나 오래 캐시에 둘 것인가? (TTL)
2. 원본이 바뀌면 캐시는? (무효화)
3. 캐시에 없으면? (캐시 미스 -> cache aside 패턴)

 

예제 — 기본적인 캐시 조회 패턴
def get_user(user_id, cache, db):
    cached = cache.get(f"user:{user_id}")
    if cached is not None:
        return cached

    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    cache.set(f"user:{user_id}", user, ttl=300)
    return user

이 패턴을 Cache-Aside라고 부릅니다. 애플리케이션이 직접 캐시를 확인하고, 없으면 원본을 조회해 캐시를 채우는 가장 널리 쓰이는 방식입니다.

 

실무 포인트

자주 조회되면서 자주 바뀌지 않는 데이터가 캐싱 효과가 가장 큽니다. 매번 바뀌는 데이터는 무효화 비용이 이득보다 클 수 있습니다.

주의 — Redis 같은 별도 캐시 서버 없이 애플리케이션 프로세스 내부 메모리만 캐시로 쓰면, 서버가 여러 대일 때 각자 다른 캐시를 갖게 됩니다.
