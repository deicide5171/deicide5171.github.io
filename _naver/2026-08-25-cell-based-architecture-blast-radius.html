한 줄 요약 — 리전 이중화로도 막지 못하는 소프트웨어 결함 전파를, 사용자 집합을 셀 단위로 격리해 장애 반경을 사전에 정한 크기로 제한하는 셀 기반 아키텍처를 정리했습니다.

 

리전 이중화만으로는 막을 수 없는 장애

멀티 리전 액티브-액티브 구성을 잘 갖춰놓은 서비스도 특정 배포 이후 전체 사용자가 동시에 영향을 받는 장애를 겪는 경우가 있습니다. 리전 이중화는 하드웨어 장애나 데이터센터 단위 재해에는 강하지만, 잘못된 설정 값이나 소프트웨어 버그처럼 모든 리전에 동일하게 배포된 결함에는 무력합니다.

셀 기반 아키텍처(cell-based architecture)는 전체 사용자 기반을 여러 개의 독립적인 "셀"로 쪼개고, 각 셀은 다른 셀과 거의 완전히 격리된 인프라 스택을 갖습니다. 배포도 셀 단위로 순차 진행해서, 특정 셀에서 문제가 생겨도 그 셀에 속한 사용자만 영향을 받고 나머지 셀은 정상 동작합니다.

 

핵심 개념 1 — 리전 이중화와 셀 분리는 서로 다른 축입니다

리전 이중화는 "물리적 장소" 축의 장애를 방어합니다. 반면 셀 분리는 "논리적 결함 전파" 축의 장애를 방어합니다 — 배포 실수, 특정 사용자의 비정상 트래픽, 포이즌 메시지처럼 물리적 위치와 무관한 문제가 전체로 번지는 것을 막습니다. 두 축은 직교하므로 함께 적용할 수 있으며, 각 리전 안에 여러 셀을 두는 구성이 일반적입니다.

 

핵심 개념 2 — 폭발 반경(blast radius)이라는 설계 목표
항목 셀 없는 단일 스택 셀 기반(N=10)
배포 버그 최대 영향 전체 사용자 최대 10%
디버깅 대상 규모 전체 트래픽 로그 해당 셀 로그로 축소
운영 복잡도 낮음 높음(셀 수만큼 중복)

 

핵심 개념 3 — 셀 경계를 어디에 그을까요

사용자/테넌트 ID 해시, 지리적 그룹, 테넌트 등급 등이 흔한 기준입니다. 중요한 것은 라우팅 계층(요청을 올바른 셀로 보내는 게이트웨이)이 셀 경계 밖에 있어야 한다는 점입니다. 이 계층 자체가 단일 장애점이 되지 않도록 단순하고 상태가 없어야 합니다 — 라우팅 계층이 죽으면 셀 분리의 의미가 없어지기 때문입니다.

 

예제 — 셀 라우팅 게이트웨이의 기본 구조
def route_to_cell(tenant_id):
    cell_id = consistent_hash(tenant_id) % TOTAL_CELLS
    return f"cell-{cell_id}"

def handle_request(request):
    cell = route_to_cell(request.tenant_id)
    cell_endpoint = CELL_ENDPOINTS[cell]
    return forward_request(cell_endpoint, request)

# 셀 단위 순차 배포: 첫 셀에서 이상 감지 시 즉시 중단
def deploy_release(version):
    for cell in ALL_CELLS:
        deploy_to_cell(cell, version)
        if not health_check_passes(cell, wait_minutes=15):
            halt_remaining_deployment()
            raise DeploymentAborted(f"{cell} 배포 후 이상 감지")

 

실무 도입 시 이것만은 챙기세요
1. 셀 단위 순차 배포가 핵심입니다 — 배포를 전체 셀에 동시에 밀어 넣으면 폭발 반경 제한 효과가 사라집니다.
2. 셀 간 데이터 공유는 최소화하고 명시적으로 설계하세요 — 전역 검색·통계 같은 기능은 별도 집계 파이프라인으로 비동기 처리하세요.
3. 운영 복잡도 증가를 감안하세요 — 대규모 멀티테넌트 SaaS처럼 이득이 큰 서비스에 우선 적용하는 것이 현실적입니다.

 

마무리 — 3줄 요약

① 리전 이중화는 물리적 장애를, 셀 분리는 소프트웨어 결함의 전파 범위를 방어하는 서로 다른 축의 대응입니다.
② 셀 기반 아키텍처는 사용자 기반을 N개 셀로 나눠 최악의 경우에도 영향 범위를 1/N 이하로 상한을 두는 것이 목표입니다.
③ 셀 단위 순차 배포와 셀 경계를 넘지 않는 요청 경로 설계가 없다면 인프라만 나눠도 효과를 얻을 수 없습니다.
