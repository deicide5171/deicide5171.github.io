벡터 타일(MVT) 포맷 뜯어보기 — Protobuf 인코딩과 좌표 압축 원리

GIS

한 줄 요약 — MapLibre·Mapbox가 받는 .pbf 타일 안에서 딕셔너리 인코딩과 정수 델타 좌표로 타일 크기를 줄이는 MVT의 내부 구조를 정리했습니다.

 

왜 지금 MVT 포맷을 다시 봐야 하는가

MapLibre GL JS로 지도를 만들 때 표현식으로 스타일을 입히는 방법은 잘 알아도, 서버가 내려주는 .pbf 파일 안에 무엇이 들어있는지는 블랙박스로 취급하는 경우가 많습니다. 타일 서버를 직접 운영하거나 PostGIS 데이터를 벡터 타일로 인코딩해야 한다면, MVT 스펙의 내부 구조를 모르고는 타일 크기와 필터링 동작을 이해할 수 없습니다.

 

계층 구조: Tile → Layer → Feature

MVT 파일은 Protocol Buffers로 직렬화된 Tile 메시지이며, 그 안에 여러 Layer가 들어갑니다. 각 Layer는 extent 값을 갖는데, 이는 좌표가 표현되는 로컬 좌표계 크기(보통 4096)를 의미합니다. 즉 MVT 좌표는 위경도 절대값이 아니라 타일 로컬 그리드 안의 정수 좌표입니다.

 

딕셔너리 인코딩과 지오메트리 명령어

GeoJSON은 각 feature마다 "highway": "primary" 같은 키·값 문자열을 매번 반복합니다. MVT는 Layer 단위로 keys[]와 values[] 딕셔너리를 한 번만 만들고 feature의 tags에는 인덱스 정수 쌍만 저장합니다. 지오메트리도 절대 좌표 대신 MoveTo·LineTo 명령어와 이전 점 대비 델타값을 zigzag+varint로 인코딩해 훨씬 적은 바이트를 차지합니다.

항목 GeoJSON MVT
좌표 표현 절대 위경도(float) 타일 로컬 정수+델타
속성 저장 feature마다 반복 저장 딕셔너리+인덱스 참조

 

MVT 디코딩 결과 확인하기
// vector-tile-js로 런타임 파싱
import { VectorTile } from '@mapbox/vector-tile';
import Protobuf from 'pbf';

const tile = new VectorTile(new Protobuf(pbfBuffer));
const roadsLayer = tile.layers['roads'];
for (let i = 0; i < roadsLayer.length; i++) {
  const feature = roadsLayer.feature(i);
  console.log(feature.properties, feature.loadGeometry());
}

 

 

실무 포인트

줌 레벨이 낮을수록 좌표 정밀도가 거칠어집니다. 저줌 레벨에서 폴리곤 경계가 계단처럼 보이는 것은 버그가 아니라 생성 시점에 좌표를 단순화해 넣었기 때문인 경우가 많습니다.

필터링이 딕셔너리 구조 위에서 동작한다는 것을 이해하면 스타일 디버깅이 쉬워집니다. 대소문자나 공백이 다르면 다른 딕셔너리 엔트리로 취급돼 필터가 안 먹는 실수가 여기서 비롯됩니다.

주의 — 직접 타일 서버를 운영한다면 tippecanoe의 옵션들이 결국 딕셔너리·델타 인코딩 효율에 영향을 줍니다. 속성 종류가 적고 지오메트리가 단순할수록 타일이 작아진다는 원리를 알면 옵션 튜닝 방향을 잡기 쉽습니다.
