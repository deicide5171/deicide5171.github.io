"하천 수위 센서 값을 지도에서 실시간으로 보여주세요" — OGC SensorThings API 도입 판단

GIS

한 줄 요약 — 수백 개 수위·수질 센서 값을 지도에서 실시간으로 보여달라는 요구는 WFS·WMS가 풀도록 설계된 문제가 아닙니다. OGC SensorThings API가 기존 공간 데이터 스택과 어떻게 공존하는지, 도입 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"하천 수위·수질 센서 수백 개 값을 지도에서 실시간으로 보여주고, 임계값을 넘으면 바로 경보를 띄워주세요." 재난 대응이나 시설 관제 부서에서 흔히 나오는 요구입니다. 얼핏 보면 기존 지도 서비스에 레이어 하나 더 얹는 일 같지만, 실제로는 전혀 다른 성격의 데이터를 다루게 됩니다. WFS로 서빙하던 필지·건물 같은 피처는 지금 이 순간의 스냅샷을 조회하는 데 맞춰져 있고 변경 빈도도 낮습니다. 반면 센서 값은 같은 위치에서 끊임없이 발생하는 시계열이고, 값이 바뀌는 순간 알림을 받고 싶어 합니다.

이 둘을 같은 WFS 엔드포인트에 욱여넣으면 금방 한계가 드러납니다. 관측값마다 피처를 새로 만들면 테이블이 기하급수적으로 불어나고, 폴링 주기를 짧게 잡으면 서버 부하가 늘어납니다. OGC SensorThings API(STA)는 바로 이 간극을 메우기 위해 설계된 표준입니다.

 

전체 시스템에서의 위치

센서 데이터는 디바이스에서 출발해 지도 화면에 닿기까지 기존 WFS 파이프라인과는 다른 경로를 탑니다. 디바이스는 MQTT로 값을 발행하고, STA 서버(대표적으로 FROST-Server)가 Thing·Sensor·Datastream·Observation 모델로 적재합니다.

지도 클라이언트는 과거 이력은 REST 조회로, 실시간 갱신은 MQTT 구독으로 받습니다. 필지·건물처럼 변경이 드문 레이어는 계속 WFS로 서빙하고, STA는 동적 관측 레이어만 전담하는 것이 핵심입니다. 경보 임계값 판정도 STA 서버 안에 넣지 않고 별도 구독자 서비스로 분리합니다.

 

선택의 트레이드오프
기준 OGC SensorThings API 자체 시계열DB + 커스텀 API WFS에 관측값 적재
표준 호환성 OGC 표준, 기존 클라이언트 호환 직접 문서화·유지보수 모델이 맞지 않음
실시간 전달 MQTT 구독이 스펙에 포함 Kafka/WebSocket 별도 구축 폴링 외 방법 없음
공간 질의 위치 기반 Thing 조회 지원 시계열은 강하나 공간 질의 약함 공간은 강하나 시계열에 비효율

 

센서 수가 수십 개 수준이고 하루 한 번 집계만 보면 된다면 STA 도입은 과한 투자입니다. 반대로 센서가 수백~수천 개로 늘어나거나 실시간 경보가 핵심 기능이라면, 표준을 따르는 쪽이 기존 STA 호환 뷰어·분석 도구를 그대로 가져다 쓸 수 있어 장기적으로 쌉니다.

 

실제 프로젝트 진행 순서

1. Thing/Datastream 설계를 먼저 끝냅니다(센서 하나가 여러 관측 항목을 가질 수 있음).
2. FROST-Server 등 레퍼런스 구현으로 PoC를 돌립니다.
3. MQTT 구독으로 프런트 실시간 갱신을 검증합니다.
4. 기존 GeoServer/WFS와 병행 운영 구조를 확정합니다(정적은 WFS, 동적은 STA).
5. 경보 임계값 로직을 별도 서비스로 분리합니다.
6. 센서 수 증가를 가정한 부하테스트를 수행합니다.

 

예제 코드:

// STA REST API로 새 관측값 등록
POST /v1.1/Datastreams(12)/Observations
{
  "phenomenonTime": "2026-10-28T03:15:00Z",
  "result": 2.47,
  "resultQuality": "good"
}

// 클라이언트에서 MQTT로 실시간 구독
const client = mqtt.connect('mqtt://sta-broker.example.com');
client.subscribe('v1.1/Datastreams(12)/Observations');
client.on('message', (topic, payload) => {
  const obs = JSON.parse(payload.toString());
  updateMapMarker(datastreamId, obs.result);
});

 

주의 — 경보 임계값 로직은 STA 서버 밖에 둬야 합니다. 표준 구현체에 커스텀 로직을 끼워 넣으면 업그레이드 때마다 포크 유지보수 부담이 생깁니다. MQTT 브로커가 단일 장애점이 되지 않도록 클러스터링이나 관리형 브로커 사용을 먼저 검토하세요. 기존 WFS 레이어를 STA로 옮기려 하지 마세요 — 두 표준은 애초에 다른 문제를 풀도록 설계됐습니다.

 

정리

실시간 센서 데이터는 위치가 있는 시계열이라 WFS·WMS가 가정하는 정적 피처 모델과 근본적으로 다릅니다. OGC SensorThings API는 Thing–Sensor–Datastream–Observation 모델과 MQTT 구독으로 저장·전달 문제를 표준화하며, 기존 GeoServer 스택은 정적 레이어 전담으로 남겨 공존시키는 것이 현실적입니다. 센서 수가 적고 실시간성이 중요하지 않다면 도입은 과투자이고, 수백 개 이상·실시간 경보가 핵심일 때 도입 가치가 커집니다.
