로그만으로는 부족하다 — Spring Boot Micrometer/Actuator 옵저버빌리티 실무

2026. 8. 27. · 백엔드

한 줄 요약 — 장애가 나면 로그를 grep하는 것으로는 한계가 있습니다. Micrometer와 Actuator로 메트릭·트레이스를 표준화하고 카디널리티 함정을 피하는 법을 정리했습니다.

 

로그와 메트릭은 다른 질문에 답합니다

장애가 발생했을 때 로그를 grep으로 뒤지는 것은 "무슨 일이 일어났는지"는 알려주지만 "얼마나 자주, 어느 정도 심각하게 일어나는지"는 알려주지 않습니다. 이 간극을 메우는 것이 메트릭이고, Spring 생태계에서는 Micrometer가 사실상 표준 계측 라이브러리 역할을 합니다. Micrometer는 여러 모니터링 시스템에 대한 벤더 중립적 파사드로, 애플리케이션 코드는 Micrometer API로만 계측하고 실제 백엔드는 설정으로 바꿀 수 있습니다.

Spring Boot Actuator는 이 위에 /actuator/health, /actuator/metrics, /actuator/prometheus 같은 관리용 HTTP 엔드포인트를 얹어줍니다. 최근에는 분산 트레이싱도 Micrometer Tracing이 담당하게 되면서, 메트릭과 트레이스를 같은 계측 축으로 다룰 수 있게 됐습니다.

 

핵심 개념 1 — Micrometer의 세 가지 계측 프리미티브

Counter는 누적 증가만 하는 값으로 요청 수, 에러 수를 셉니다. Timer는 이벤트의 지속시간과 발생 빈도를 함께 기록합니다. Gauge는 특정 시점의 순간값으로 커넥션 풀 사용량 같은 오르내리는 값을 표현합니다. Spring MVC는 HTTP 요청 처리량, 응답 시간을 자동 계측해 주므로, 커스텀 계측은 비즈니스 로직에서 의미 있는 값에 집중하는 것이 효율적입니다.

 

핵심 개념 2 — 카디널리티, 조용히 시스템을 무너뜨리는 함정

메트릭에 태그를 붙이면 그룹별로 값을 나눠 볼 수 있어 유용합니다. 문제는 태그 값의 종류(카디널리티)가 커지면 시계열 개수가 태그 값의 곱만큼 폭발한다는 것입니다. user_id나 request_id처럼 사실상 무한한 값을 갖는 필드를 태그로 붙이면, 메트릭 백엔드의 메모리와 쿼리 성능이 감당 불가능해집니다.

태그 예시 카디널리티 적합성
http.status 낮음 안전
endpoint (경로 패턴) 중간 대체로 안전
user_id, order_id 매우 높음 위험 — 로그/트레이스로

 

 

예제 — 커스텀 메트릭과 트레이스 상관관계 설정
@Service
public class OrderService {
    private final Counter orderFailureCounter;
    private final Timer orderProcessingTimer;

    public OrderService(MeterRegistry registry) {
        this.orderFailureCounter = Counter.builder("orders.failed")
            .tag("reason", "unspecified")
            .register(registry);
        this.orderProcessingTimer = Timer.builder("orders.processing.time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
    }

    public void processOrder(Order order) {
        orderProcessingTimer.record(() -> {
            try {
                doProcess(order);
            } catch (OrderException e) {
                orderFailureCounter.increment();
                log.error("order processing failed order_id={}", order.getId(), e);
                throw e;
            }
        });
    }
}
# application.yml — Micrometer Tracing으로 trace id를 로그에 자동 삽입
management:
  tracing:
    sampling:
      probability: 0.1
logging:
  pattern:
    level: "%5p [%X{traceId:-},%X{spanId:-}]"

logging.pattern.level에 MDC 값을 넣으면, 로그 한 줄만으로 해당 요청의 분산 트레이스를 역추적할 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. /actuator 엔드포인트는 반드시 접근 제어를 거세요 — 민감 정보나 메모리 덤프를 노출할 수 있는 엔드포인트가 있습니다.
2. 히스토그램 버킷은 실제 SLO 경계에 맞추세요 — 정확한 임계값이 있다면 serviceLevelObjectives()로 해당 버킷을 명시적으로 추가해야 합니다.
3. 샘플링 비율은 트래픽 규모에 맞춰 조정하세요 — 초기값은 낮게 잡고 에러 트레이스는 별도 정책으로 100% 포착하는 구조를 검토하세요.

 

마무리 — 3줄 요약

① Micrometer는 Counter·Timer·Gauge라는 벤더 중립 계측 API로 여러 모니터링 백엔드에 동일한 코드로 값을 보낼 수 있게 합니다.
② user_id처럼 카디널리티가 높은 값을 메트릭 태그로 쓰면 모니터링 백엔드가 감당 못 하므로, 그런 값은 로그·트레이스에만 남깁니다.
③ Micrometer Tracing으로 trace id를 로그 MDC에 심으면 메트릭에서 이상 신호를 포착한 뒤 로그·트레이스로 바로 이어서 조사할 수 있습니다.
