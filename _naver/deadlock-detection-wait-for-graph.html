데드락 탐지와 Wait-For Graph — PostgreSQL이 교착 상태를 찾아내는 방법

DB·데이터 모델링

한 줄 요약 — DB는 타임아웃이 아니라 Wait-For Graph의 순환(cycle)을 실시간으로 탐지해 데드락을 판정합니다. 탐지 원리와 희생자 선정 기준을 정리했습니다.

 

왜 지금 데드락 탐지 원리를 다시 봐야 하는가

deadlock 에러를 만나면 대부분 재시도 로직만 추가하고 넘어갑니다. 하지만 DB가 두 트랜잭션이 영원히 기다리고 있다는 것을 어떻게 알아냈는지 이해하지 못하면, 락 획득 순서 불일치라는 근본 원인을 못 찾고 재시도로만 덮게 됩니다.

 

Wait-For Graph: 트랜잭션 간 대기 관계를 그래프로 표현하기

트랜잭션을 노드로, "A가 B가 쥔 락을 기다린다"를 A→B 방향 엣지로 표현합니다. 데드락은 이 그래프에 순환이 생기는 순간과 정확히 일치합니다. 락 매니저는 새 대기 관계가 추가될 때마다 순환 여부를 확인해 실시간에 가깝게 탐지합니다.

 

사이클이 발견되면 누구를 희생시킬 것인가

사이클을 찾은 뒤 그 안의 트랜잭션 중 하나를 강제 롤백해야 나머지가 진행됩니다. 희생자 선정 기준은 DB마다 다릅니다. PostgreSQL은 데드락을 탐지한 트랜잭션 자체를 롤백시키는 경향이 있고, 다른 시스템은 비용 기반으로 더 정교하게 고릅니다.

항목 설명
Wait-For Graph 노드 트랜잭션(세션)
데드락 판정 조건 그래프 순환(cycle) 존재
해소 방법 사이클 내 하나 강제 롤백

 

예제 — 락 획득 순서 불일치로 데드락 재현
-- 트랜잭션 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- 트랜잭션 2 (반대 순서로 락)
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
COMMIT;

-- ERROR: deadlock detected
-- DETAIL: Process 1234 waits for ShareLock on transaction 5678; ...

두 트랜잭션이 같은 두 행을 다른 순서로 잠그려 할 때 데드락이 발생하는 패턴이 실무에서 가장 흔한 원인입니다.

 

실무 포인트

여러 행을 갱신하는 트랜잭션은 항상 동일한 순서로 락을 획득하세요. 예를 들어 항상 더 작은 ID부터 잠그도록 강제하면 순환 대기 자체가 구조적으로 발생하지 않습니다.

데드락 에러는 애플리케이션 레벨에서 재시도하도록 처리하세요. 데이터 정합성 문제가 아니라 타이밍 문제이므로 짧은 backoff 후 재시도가 안전합니다.

주의 — 데드락 로그를 주기적으로 모니터링하세요. log_lock_waits나 상세 로그를 분석하면 반복되는 트랜잭션 조합을 찾아 락 순서 문제를 근본적으로 고칠 수 있습니다.
