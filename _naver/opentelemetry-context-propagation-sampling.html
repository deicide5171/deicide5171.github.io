OpenTelemetry 분산 트레이싱 심화 — Context Propagation과 샘플링 전략

네트워크·OS·분산처리·DevOps

한 줄 요약 — 메시지 큐를 넘을 때 끊기는 트레이스와, 잘못된 샘플링으로 놓치는 에러 트레이스 문제를 Context Propagation과 샘플링 전략으로 정리했습니다.

 

왜 지금 트레이스 전파와 샘플링을 다시 봐야 하는가

서비스 수가 늘어나면 두 문제가 나타납니다. 서비스 A에서 시작된 요청이 큐를 거쳐 B로 넘어가는 순간 트레이스가 끊겨 별개의 트레이스로 보이는 문제, 그리고 100% 수집은 비용이 커서 샘플링을 낮추면 정작 필요한 에러 트레이스가 누락되는 문제입니다.

 

Context Propagation이 트레이스 연속성을 만드는 방식

OpenTelemetry는 W3C Trace Context 표준에 따라 traceparent 헤더로 trace ID와 span ID를 서비스 간에 전달합니다. HTTP는 자동 계측이 잘 되지만, 메시지 큐나 비동기 배치처럼 헤더가 없는 경로는 개발자가 직접 컨텍스트를 실어 보내고 추출해야 합니다. 이 지점을 놓치는 것이 트레이스가 끊기는 가장 흔한 원인입니다.

 

샘플링 전략: 비율 기반에서 우선순위 기반으로

Head-based 샘플링은 요청 시작 시점에 확률로 결정하지만 에러가 날지 미리 알 수 없다는 한계가 있습니다. Tail-based 샘플링은 요청이 끝난 뒤 실제 결과를 보고 결정해 에러·느린 요청을 우선 보존하지만, 버퍼링 인프라가 추가로 필요합니다.

샘플링 방식 장점 단점
Head-based 구현 단순 에러·이상 요청 놓칠 수 있음
Tail-based 에러·느린 요청 우선 보존 버퍼링 인프라 필요

 

예제 — 메시지 큐를 통한 수동 컨텍스트 전파
// 발행 측
Map<String, String> headers = new HashMap<>();
propagator.inject(Context.current(), headers,
    (carrier, key, value) -> carrier.put(key, value));
producer.send(new ProducerRecord<>(topic, key, value, toKafkaHeaders(headers)));

// 소비 측
Context extractedContext = propagator.extract(Context.current(), kafkaHeaders,
    (carrier, key) -> carrier.get(key));

try (Scope scope = extractedContext.makeCurrent()) {
    Span span = tracer.spanBuilder("process-order-message").startSpan();
    span.end();
}

 

실무 포인트

비동기 경계마다 전파 여부를 명시적으로 점검하세요. HTTP는 자동 계측이 대신해주지만 메시지 큐·스케줄러 경계는 직접 확인해야 합니다.

초기에는 head-based로 시작하되 에러 트레이스는 강제 수집 규칙을 추가하세요. 5xx 응답이나 고지연 요청은 샘플링 확률과 무관하게 100% 수집하면 상당한 이득을 얻습니다.

주의 — 샘플링 비율을 서비스별로 다르게 가져가세요. 트래픽 많은 게이트웨이와 호출 빈도 낮은 배치 서비스에 동일 비율을 적용하면 한쪽은 과도한 비용, 다른 쪽은 데이터 부족에 시달립니다.
