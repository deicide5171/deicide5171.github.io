FlashAttention — GPU 메모리 계층을 이해해야 보이는 어텐션 가속의 진짜 원리

AI

한 줄 요약 — FlashAttention이 빠른 이유는 연산량 감소가 아니라, GPU의 SRAM과 HBM 사이 데이터 이동을 줄이는 IO-aware 설계 덕분입니다.

 

왜 지금 다시 봐야 하는가

긴 컨텍스트 윈도우가 표준이 되면서 어텐션 연산의 비용이 다시 병목으로 떠올랐습니다. 많은 분들이 이를 "행렬곱이 느려서"라고 오해하지만, 실제로는 표준 어텐션 구현이 느린 진짜 이유가 연산(FLOPs) 자체가 아니라 GPU의 고대역폭 메모리(HBM)와 온칩 SRAM 사이를 오가는 데이터 이동량이라는 사실을 FlashAttention 논문이 처음 보여주었습니다.

 

병목은 연산이 아니라 메모리 이동

표준 어텐션은 Q·K로 어텐션 스코어 행렬을 만들고, softmax를 적용한 뒤, V와 곱해 출력을 만듭니다. 문제는 시퀀스 길이 N에 대해 N×N 크기의 중간 행렬을 매 단계마다 HBM에 썼다가 다시 읽어온다는 점입니다. GPU 내부에는 HBM보다 수십 배 빠르지만 용량이 훨씬 작은 SRAM이 있는데, 표준 구현은 이를 거의 활용하지 못합니다.

타일링과 online softmax

FlashAttention의 해법은 두 가지입니다. 첫째는 타일링(tiling)으로, Q·K·V를 SRAM에 들어갈 만큼 작은 블록으로 쪼개 한 번에 하나의 블록 쌍만 처리합니다. 둘째는 online softmax로, 블록 단위로 처리하면서도 정규화 상수를 점진적으로 갱신하는 수치적으로 안정적인 알고리즘을 씁니다. 이렇게 하면 전체를 다시 훑지 않고도 정확한 softmax 결과를 얻습니다.

구현 HBM 왕복 중간 행렬 저장
표준 어텐션 O(N²) 규모 N×N 전체 저장
FlashAttention O(N) 규모로 축소 블록 단위만 SRAM 유지

 

흥미로운 점은 FlashAttention이 연산량(FLOPs)을 줄이지 않는다는 것입니다. 역전파 시 중간 값을 재계산하기 때문에 연산량은 오히려 미세하게 늘어나지만, 병목이 연산이 아니라 메모리 대역폭이었기 때문에 전체 실행 시간은 크게 줄어듭니다.

PyTorch 활용 예제
import torch
import torch.nn.functional as F

q = torch.randn(1, 8, 4096, 64, device="cuda", dtype=torch.float16)
k = torch.randn(1, 8, 4096, 64, device="cuda", dtype=torch.float16)
v = torch.randn(1, 8, 4096, 64, device="cuda", dtype=torch.float16)

with torch.backends.cuda.sdp_kernel(
    enable_flash=True, enable_math=False, enable_mem_efficient=False
):
    out = F.scaled_dot_product_attention(q, k, v, is_causal=True)

시퀀스가 길고 헤드 차원이 크지 않을수록(보통 128 이하) FlashAttention 커널의 이득이 두드러집니다.

 

실무 포인트

헤드 차원이 클수록 이득이 줄어듭니다. SRAM 용량이 고정돼 있으므로 헤드 차원이 커지면 블록 크기를 줄여야 하고, 타일링 효율이 떨어집니다.

causal mask 처리 방식이 실제 속도에 영향을 줍니다. 디코더의 인과적 어텐션에서는 상삼각 블록을 건너뛰는 최적화가 들어가, 순수 self-attention보다 오히려 더 빠른 경우가 많습니다.

주의 — GQA/MQA를 쓰는 모델은 K·V 헤드 수가 Q보다 적은데, 커널 구현이 이를 제대로 지원하지 않으면 K·V를 불필요하게 복제해 메모리 이득을 깎아먹을 수 있습니다.
