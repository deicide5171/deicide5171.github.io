무한 스크롤 구현하기 — Intersection Observer vs scroll 이벤트 성능 비교

프론트엔드

한 줄 요약 — scroll 이벤트로 만든 무한 스크롤은 매번 레이아웃을 재계산해 버벅이지만, Intersection Observer는 감지를 브라우저에 위임해 메인 스레드 부담을 크게 줄입니다.

 

왜 scroll 이벤트 방식이 버벅이나

scroll 이벤트는 초당 수십~수백 번씩 발생하는 매우 빈번한 이벤트입니다. 콜백 안에서 scrollTop, offsetHeight 같은 값을 읽으면 브라우저가 그 값을 계산하려고 레이아웃을 강제로 다시 계산(reflow)하게 되고, 이 작업이 메인 스레드를 붙잡으면서 스크롤 렌더링이 밀리는 버벅임(jank)이 생깁니다.

 

 

올바른 접근: Intersection Observer

쓰로틀링·디바운싱은 콜백 실행 빈도만 줄여줄 뿐 근본 구조는 그대로입니다. Intersection Observer API는 특정 요소가 뷰포트에 들어오는지를 브라우저가 직접 비동기로 감지하게 위임하는 방식입니다.

const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach((entry) => {
      if (entry.isIntersecting) loadNextPage();
    });
  },
  { root: null, rootMargin: '300px', threshold: 0 }
);
observer.observe(sentinel);

목록 맨 아래에 눈에 보이지 않는 sentinel 요소를 두고, 이 요소가 뷰포트에 들어오는 순간 콜백이 호출되도록 등록합니다. rootMargin으로 미리 여유를 주면 사용자가 스크롤 끝에 닿기 전에 다음 페이지를 미리 불러올 수 있습니다.

주의 — rootMargin으로 미리 트리거되는 특성상 네트워크 응답이 오기 전에 콜백이 다시 호출될 수 있습니다. 로딩 플래그로 중복 요청을 반드시 막고, 마지막 페이지에 도달하면 observer.disconnect()로 감시를 해제하세요.
