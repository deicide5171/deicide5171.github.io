커스텀 어노테이션 만들기 — @interface와 AOP로 검증 로직 재사용하기

백엔드

한 줄 요약 — 반복되는 권한 검사·로깅 코드를 커스텀 애노테이션 + AOP로 분리하면 비즈니스 로직 코드가 훨씬 단순해집니다.

 

왜 매번 같은 코드를 복붙하게 되나

여러 API 메서드에 "관리자만 호출 가능" 같은 공통 요구사항이 반복되면, 검증 코드를 그대로 복사해 넣다가 유지보수 부담이 커집니다. @Transactional, @PreAuthorize 같은 스프링 애노테이션도 사실 같은 패턴입니다. 메서드에 애노테이션만 붙이면 별도의 공통 처리기(Aspect)가 대신 실행해주는 구조입니다.

 

 

1단계: 애노테이션 정의, 2단계: AOP 구현
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireAdmin {
    String message() default "관리자 권한이 필요합니다.";
}

@Retention(RetentionPolicy.RUNTIME)은 실행 시점까지 애노테이션 정보가 유지되어야 한다는 뜻입니다. 이걸 CLASS나 SOURCE로 잘못 설정하면 AOP가 실행 시점에 애노테이션을 인식하지 못합니다.

@Around("@annotation(requireAdmin)")
public Object checkAdmin(ProceedingJoinPoint jp, RequireAdmin requireAdmin) throws Throwable {
    if (!isAdmin()) throw new AccessDeniedException(requireAdmin.message());
    return jp.proceed();
}
주의 — 애노테이션 자체는 메타데이터일 뿐 아무 동작도 하지 않습니다. 반드시 이를 읽어 실제로 무언가를 하는 별도의 처리기(AOP Aspect 등)가 함께 있어야 합니다.

 

실무 포인트

AOP는 스프링 빈으로 등록된 객체에만 적용됩니다. new로 직접 생성한 객체나 같은 클래스 내부에서 this.method()로 호출하는 경우 프록시를 거치지 않아 AOP가 동작하지 않는다는 점을 기억하세요. 여러 애노테이션이 겹칠 때는 @Order로 Aspect 실행 순서를 명시할 수 있습니다.
