쿠버네티스 Secret에 그대로 넣지 마라 — Vault와 External Secrets Operator로 보는 시크릿 관리

2026. 8. 29. · 인프라

한 줄 요약 — 쿠버네티스 기본 Secret은 base64 인코딩일 뿐 암호화가 아니어서, HashiCorp Vault로 시크릿을 중앙에서 암호화·회전시키고 External Secrets Operator로 쿠버네티스 Secret에 자동 동기화하는 구조가 실무 표준입니다.

 

쿠버네티스 Secret, 안전할 것 같지만 아닙니다

쿠버네티스 Secret 오브젝트는 이름부터 안전할 것 같은 인상을 주지만, 실제로는 값을 base64로 인코딩해 etcd에 저장할 뿐입니다. base64는 암호화가 아니라 인코딩이므로, etcd 접근 권한이 있거나 kubectl get secret 권한이 있는 사람은 누구나 원문 값을 즉시 복원할 수 있습니다.

이 문제를 푸는 실무 표준은 시크릿을 실제로 저장·암호화·회전시키는 HashiCorp Vault와, 그 값을 쿠버네티스 네이티브 Secret으로 동기화해주는 External Secrets Operator(ESO)입니다.

 

핵심 개념 1 — Vault, 시크릿의 단일 진실 공급원

Vault는 시크릿을 암호화된 상태로 저장하고, 접근할 때마다 정책 기반으로 권한을 검증합니다. Vault의 핵심 차별점은 동적 시크릿입니다. DB 자격 증명을 요청하면 Vault가 그 순간 실제 DB에 접속해 짧은 TTL을 가진 임시 사용자 계정을 즉시 생성해 발급하고, TTL이 지나면 자동 폐기됩니다. 자격 증명이 유출돼도 피해 창구가 짧게 제한됩니다.

 

핵심 개념 2 — ESO, Vault와 쿠버네티스를 잇는 다리

External Secrets Operator는 SecretStore로 Vault 연결 정보를 정의하고, ExternalSecret 리소스로 "이 경로의 시크릿을 가져와서 이런 이름의 쿠버네티스 Secret으로 만들어라"라고 선언하면 컨트롤러가 주기적으로 Vault를 폴링해 동기화합니다. 애플리케이션은 여전히 표준 쿠버네티스 Secret만 참조하므로, 시크릿이 Vault에서 왔는지 몰라도 됩니다.

 

 

핵심 개념 3 — 회전과 폴링 주기의 트레이드오프

ESO는 이벤트 기반이 아니라 설정된 refreshInterval마다 Vault를 폴링하므로, 시크릿이 갱신된 시점과 쿠버네티스 Secret에 반영되는 시점 사이에 지연이 생깁니다. 게다가 Secret이 갱신돼도 이미 실행 중인 파드가 즉시 인지하는 것은 아니어서, 환경 변수는 파드 재시작이, 볼륨 마운트는 애플리케이션의 파일 변경 감지 로직이 필요합니다.

구분 기본 K8s Secret Vault + ESO
저장 방식 base64 인코딩 Vault가 암호화 저장
동적 시크릿 미지원 TTL 기반 임시 자격 증명
회전 자동화 수동 Vault 회전 + ESO 동기화

 

실무 도입 시 이것만은 챙기세요
1. 회전 리스크가 큰 것부터 동적 시크릿으로 옮기세요 — DB 자격 증명부터 시작하고 나머지는 정적 저장만으로도 base64 노출 문제는 해결됩니다.
2. 회전 후 애플리케이션 재로드 경로를 반드시 검증하세요 — 이전 값을 캐시하고 있다면 회전이 무의미해집니다.
3. 폴링 주기를 시크릿 성격에 맞게 차등화하세요 — 모두 같은 주기를 쓰면 불필요한 Vault API 부하가 늘어납니다.

 

마무리 — 3줄 요약

① 쿠버네티스 기본 Secret은 base64 인코딩일 뿐 암호화가 아니라는 근본적 한계가 있습니다.
② Vault는 암호화 저장과 TTL 기반 동적 시크릿을 제공하고, ESO는 이를 쿠버네티스 Secret으로 동기화하는 다리 역할을 합니다.
③ 폴링 주기와 파드 재로드 방식 때문에 회전이 실제 반영되기까지 지연이 생길 수 있어 재로드 경로 검증이 중요합니다.
