실시간 집계를 어디서 미리 계산할 것인가 — 구체화 뷰 vs 캐시 설계 트레이드오프

2026. 8. 28. · 시스템 설계

한 줄 요약 — 무거운 집계 쿼리를 DB의 구체화 뷰(materialized view)로 미리 계산할지 애플리케이션 캐시로 저장할지는, 신선도 관리 책임을 어디에 둘 것인가의 문제입니다. 선택 기준을 정리했습니다.

 

매번 다시 계산하기 부담스러운 집계, 어디에 미리 저장할까요

주문 건수, 매출 합계, 인기 상품 랭킹처럼 여러 행을 집계해야 나오는 값은 원본 테이블이 커질수록 매 요청마다 다시 계산하기 부담스러워집니다. 이 문제를 푸는 방법은 크게 두 갈래로 갈립니다. 하나는 DB 안에서 미리 계산해두는 구체화 뷰이고, 다른 하나는 계산 결과를 Redis 같은 애플리케이션 캐시에 저장하는 방식입니다.

둘 다 "미리 계산해서 저장해둔다"는 발상은 같지만, 신선도를 관리하는 위치와 일관성 보장 수준이 근본적으로 다릅니다. 이 선택을 잘못하면 무효화 로직이 모든 변경 경로를 놓치지 않아야 하는 부담을 애플리케이션이 떠안거나, 반대로 갱신 주기가 요구되는 신선도보다 느려서 사용자가 오래된 숫자를 보게 됩니다.

 

핵심 개념 1 — 구체화 뷰는 DB가 신선도를 책임집니다

구체화 뷰는 쿼리 결과를 실제 디스크 테이블처럼 저장해두는 DB 객체입니다. PostgreSQL의 CREATE MATERIALIZED VIEW, 증분 갱신용 pg_ivm 확장, ClickHouse의 Materialized View가 대표적입니다. 애플리케이션은 그냥 뷰를 조회할 뿐이고, 언제 갱신할지는 배치 REFRESH나 증분 스트리밍 방식으로 DB 쪽에서 처리합니다.

장점은 애플리케이션 코드가 캐시 무효화라는 어려운 문제에서 완전히 자유로워진다는 것입니다. 단점은 배치형의 경우 갱신 주기 동안은 필연적으로 오래된 데이터를 보여준다는 것입니다.

핵심 개념 2 — 애플리케이션 캐시는 유연하지만 무효화가 어렵습니다

캐시 방식은 집계 쿼리 결과를 Redis 같은 별도 저장소에 TTL과 함께 저장합니다. 원본 데이터가 바뀌면 관련 캐시 키를 지우거나 새 값으로 다시 채웁니다. 장점은 DB 부하와 무관하게 초저지연 조회가 가능하다는 것이고, 문제는 무효화 책임이 애플리케이션 코드로 넘어온다는 점입니다. 변경 경로 하나라도 무효화를 빠뜨리면 캐시가 영원히 오래된 값을 보여주는 버그가 생깁니다.

기준 구체화 뷰 애플리케이션 캐시
신선도 관리 주체 DB 애플리케이션 코드
일관성 실패 시 증상 오래된 스냅샷임이 명확 무효화 누락 시 조용히 틀린 값
신선도 커스터마이징 뷰 단위 일괄 쿼리·키별 세밀 조정
인프라 추가 불필요 Redis 등 필요

 

핵심 개념 3 — 선택 기준은 변경 경로의 개수입니다

실무에서는 집계에 영향을 주는 원본 데이터의 변경 경로가 몇 개인지를 먼저 셉니다. 변경 경로가 한두 개로 명확하면 캐시 무효화가 쉬우므로 애플리케이션 캐시가 유리하고, 변경 경로가 많고 계속 늘어날 것 같으면 구체화 뷰가 안전합니다. 두 방식을 함께 쓰는 하이브리드도 흔한 패턴입니다 — 무거운 히스토리는 야간 배치 구체화 뷰로, 최근 실시간 카운터는 Redis로 따로 유지하는 식입니다.

예제 — 증분 구체화 뷰 vs write-through 캐시
-- 배치형: 야간 스케줄러가 주기적으로 REFRESH
CREATE MATERIALIZED VIEW daily_sales_summary AS
SELECT date_trunc('day', ordered_at) AS sale_date,
       product_id, count(*) AS order_count, sum(amount) AS total_amount
FROM orders WHERE status = 'completed'
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON daily_sales_summary (sale_date, product_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales_summary;
# 애플리케이션 캐시: write-through로 즉시 최신화
def create_order(order):
    db.insert_order(order)
    key = f"sales_summary:{order.product_id}:{order.date}"
    cache.hincrby(key, "order_count", 1)
    cache.hincrbyfloat(key, "total_amount", order.amount)
    cache.expire(key, ttl=3600)  # 안전망: 무효화 누락돼도 자연 소멸

캐시 방식에서는 무효화 누락에 대비한 안전망으로 TTL을 반드시 둡니다. TTL이 없으면 영원히 틀릴 수 있는 값이 되지만, TTL이 있으면 최악의 경우에도 만료 후 자연 복구됩니다.

 

실무 도입 시 이것만은 챙기세요
1. REFRESH는 CONCURRENTLY 옵션을 검토하세요 — 기본 REFRESH는 뷰 전체에 락을 걸어 갱신 중 조회가 막힙니다. CONCURRENTLY는 락 없이 갱신하지만 UNIQUE 인덱스가 필요합니다.
2. 캐시 무효화는 지우기보다 다시 채우기가 안전할 때가 많습니다 — 단순 삭제는 다음 조회가 몰릴 때 캐시 스탬피드를 유발할 수 있습니다.
3. 신선도 SLA를 문서화해두세요 — "최대 5분 지연될 수 있다"는 명시가 없으면 나중에 실시간이 아니라는 이유로 버그 리포트가 올라옵니다.

 

마무리 — 3줄 요약

① 구체화 뷰는 신선도 관리 책임을 DB가 지고, 애플리케이션 캐시는 그 책임이 애플리케이션 코드로 넘어갑니다.
② 변경 경로가 많고 계속 늘어난다면 무효화 누락 위험이 큰 캐시보다 구체화 뷰가 안전하고, 경로가 단순하면 캐시가 유리합니다.
③ 두 방식은 배타적이지 않으며, 히스토리는 구체화 뷰로 최근 실시간 카운터는 캐시로 병행하는 하이브리드가 흔한 실무 패턴입니다.
