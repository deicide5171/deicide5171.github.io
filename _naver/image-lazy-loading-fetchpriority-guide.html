이미지 lazy loading만으로 충분할까 — fetchpriority 함께 쓰기

프론트엔드

한 줄 요약 — 모든 이미지에 loading="lazy"를 일괄 적용하면 히어로 이미지까지 우선순위가 낮아져 LCP가 오히려 늦어질 수 있습니다.

 

왜 lazy를 다 붙였는데 점수가 떨어지나

스크롤 하단 이미지에 loading="lazy"를 붙이면 초기 로딩 시간이 확실히 줄어듭니다. 하지만 스크롤 없이 바로 보이는 히어로 이미지에까지 붙이면, 브라우저가 이 이미지를 즉시 로딩은 하되 우선순위를 높게 매기지 않습니다. LCP는 대개 이 이미지가 그려지는 시점을 기준으로 측정되므로, 다른 리소스와 경쟁하느라 오히려 늦어집니다.

 

잘못된 접근 vs 올바른 접근

"이미지는 다 늦게 불러오는 게 좋다"는 단순화로 모든 이미지에 lazy를 붙이는 것이 흔한 실수입니다. 올바른 원칙은 처음부터 보이는 이미지는 최대한 빨리, 스크롤해야 보이는 이미지는 늦게 불러오게 구분하는 것입니다.

<!-- 히어로 이미지 -->
<img src="hero-banner.jpg" fetchpriority="high" loading="eager" alt="...">

<!-- 스크롤 하단 이미지 -->
<img src="product-1.jpg" loading="lazy" alt="...">

fetchpriority="high"는 브라우저의 리소스 우선순위 큐에서 이 이미지를 앞자리로 올려, 같은 시점에 요청되는 다른 리소스보다 먼저 다운로드되게 합니다.

속성 역할 히어로 이미지
loading 로딩 시점 eager
fetchpriority 동시 요청 중 우선순위 high

두 속성은 다른 축을 조정합니다. loading은 "언제 요청을 시작할지", fetchpriority는 "동시에 여러 요청이 있을 때 뭘 먼저 처리할지"를 결정하므로, 히어로 이미지에 lazy가 실수로 남아있으면 high를 줘도 소용없습니다.

주의 — fetchpriority를 모든 이미지에 붙이면 우선순위 큐 자체가 무의미해집니다. 진짜 LCP 후보 이미지 1~2개에만 적용하세요. CSS background-image로 넣은 이미지는 이 속성들의 혜택을 받지 못합니다.

 

실무 포인트

LCP 후보 이미지는 link rel="preload"로 HTML 파싱 초기 단계에 미리 알려주는 방법도 함께 검토하세요. 실제 개선 여부는 반드시 Lighthouse나 CrUX 데이터로 검증해야 합니다.
