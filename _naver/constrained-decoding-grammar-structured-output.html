제약 디코딩 — LLM이 JSON 스키마를 100% 지키게 만드는 원리

AI

한 줄 요약 — 프롬프트 지시는 확률적 준수일 뿐이며, 제약 디코딩은 토큰 생성 단계에서 문법 위반 토큰의 확률을 0으로 마스킹해 구조를 강제합니다.

 

왜 프롬프트만으로 부족한가

에이전트 파이프라인에서 LLM 출력을 다음 단계 코드가 그대로 파싱해야 할 때, JSON 스키마 위반 하나가 전체 파이프라인을 멈춥니다. "반드시 JSON만 출력하라"는 지시는 모델에게 부탁하는 것일 뿐 강제하는 것이 아니므로, 드물게 스키마를 깨는 토큰이 선택될 여지가 항상 남습니다.

 

유한 오토마타로 스키마 표현하기

Outlines, xgrammar 같은 라이브러리는 JSON 스키마를 유한 상태 오토마타(FSM)로 컴파일합니다. 디코딩이 진행되는 매 스텝마다, 현재 오토마타 상태에서 허용되는 다음 토큰이 무엇인지 계산할 수 있습니다.

로짓 마스킹으로 샘플링 강제하기

모델이 다음 토큰의 로짓을 계산하면, 엔진은 현재 상태에서 문법적으로 불가능한 토큰들의 로짓을 -∞로 마스킹합니다. 이렇게 하면 온도나 top-p와 무관하게 그 토큰은 절대 선택되지 않습니다. xgrammar 같은 최신 구현은 이 전처리를 GPU 디코딩과 겹쳐 실행해 오버헤드를 거의 없앱니다.

방식 강제력 오버헤드
프롬프트 지시 없음 없음
출력 후 검증·재시도 사후적 재시도 비용
제약 디코딩 100% 낮음

 

Outlines로 Pydantic 스키마 강제 예제
import outlines
from pydantic import BaseModel

class Extraction(BaseModel):
    name: str
    age: int
    is_active: bool

model = outlines.models.transformers("meta-llama/Llama-3.1-8B-Instruct")
generator = outlines.generate.json(model, Extraction)

result = generator("이름은 김민준, 32세, 활성 사용자입니다.")
print(result.name, result.age, result.is_active)

생성된 문자열은 파싱 실패 가능성 없이 항상 스키마를 만족합니다.

 

실무 포인트

문법이 복잡할수록 사전 컴파일 비용이 커집니다. 자주 쓰는 스키마는 컴파일 결과를 캐싱해 재사용하는 것이 좋습니다.

문법적으로 유효해도 의미적으로 틀릴 수 있습니다. 형식은 보장되지만 존재하지 않는 값을 채워 넣는 환각은 별도 검증이 필요합니다.

주의 — vLLM, SGLang, TGI 등 서빙 엔진마다 지원하는 문법 표현력(정규식만/전체 JSON Schema/CFG)이 다르므로, 사용할 스키마 복잡도에 맞는 엔진을 선택해야 합니다.
