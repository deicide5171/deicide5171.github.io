리눅스 cgroups와 네임스페이스 — 도커 컨테이너는 실제로 어떻게 격리될까요

2026. 8. 20. · 인프라

한 줄 요약 — 컨테이너는 별도의 커널을 가진 가상머신이 아니라, 네임스페이스로 보이는 범위가 나뉘고 cgroups로 쓸 수 있는 자원이 제한된 리눅스 프로세스일 뿐이라는 점을 하나씩 뜯어봤습니다.

 

컨테이너는 왜 VM처럼 보이지만 VM이 아닐까요

docker run 한 번으로 컨테이너를 띄우면 마치 독립된 작은 컴퓨터가 하나 생긴 것처럼 느껴집니다. 자기만의 프로세스 목록, 자기만의 IP, 자기만의 파일시스템 루트를 가진 것처럼 보이니까요. 하지만 실제로는 호스트와 완전히 같은 커널 위에서 돌아가는 평범한 프로세스일 뿐입니다. 하이퍼바이저가 하드웨어를 가상화하고 별도의 커널을 부팅하는 VM과는 근본적으로 다른 구조입니다.

이 "격리된 것처럼 보이는 프로세스"를 만드는 실체는 도커가 새로 발명한 기술이 아니라, 리눅스 커널에 오래전부터 있던 두 가지 기능입니다. 하나는 네임스페이스(namespace)로 프로세스가 커널 자원을 바라보는 뷰 자체를 분리하고, 다른 하나는 cgroups(control groups)로 프로세스 그룹이 실제로 쓸 수 있는 자원의 양에 상한을 겁니다. 도커·containerd 같은 도구는 이 두 커널 기능을 편리하게 호출해주는 계층에 가깝고, 격리와 제한의 실질적인 작업은 커널이 담당합니다.

 

핵심 개념 1 — 네임스페이스는 "무엇이 보이는지"를 나눕니다

네임스페이스는 프로세스마다 특정 커널 자료구조에 대해 서로 다른 뷰를 부여하는 기능입니다. 자원을 실제로 나누는 게 아니라, 같은 커널 안의 자원 중 어디까지를 보여줄지를 프로세스 단위로 다르게 설정한다는 점이 핵심입니다. 대표적으로 PID, 네트워크, 마운트, UTS, IPC, 유저 네임스페이스가 있습니다.

네임스페이스 분리 대상 체감 효과
PID 프로세스 ID 공간 컨테이너 안 첫 프로세스가 PID 1로 보임
Net 네트워크 인터페이스·라우팅 여러 컨테이너가 각자 80번 포트 사용 가능
Mount 마운트 지점 이미지 루트 파일시스템이 별도로 보임
UTS 호스트명·도메인명 컨테이너마다 다른 hostname 설정 가능
IPC 공유메모리·세마포어·메시지큐 프로세스 간 통신 자원이 컨테이너별로 분리
User UID/GID 매핑 컨테이너 안 root가 호스트에서는 일반 사용자로 매핑 가능

 

이 여섯 가지는 각각 독립적으로 켜고 끌 수 있습니다. 컨테이너 런타임은 보통 이 여러 네임스페이스를 한꺼번에 새로 만들어 프로세스를 그 안에 넣는 방식으로 동작합니다. 참고로 cgroup 자체의 뷰를 분리하는 cgroup 네임스페이스, 시간 값을 분리하는 time 네임스페이스도 존재합니다.

 

핵심 개념 2 — cgroups는 "얼마나 쓸 수 있는지"를 제한합니다

네임스페이스가 "무엇이 보이는가"를 다룬다면, cgroups는 "얼마나 쓸 수 있는가"를 다룹니다. 프로세스를 하나의 그룹으로 묶고, 그 그룹 전체에 CPU 시간·메모리·블록 I/O 같은 자원의 사용량 상한을 커널이 강제하도록 설정하는 기능입니다. cpu 컨트롤러는 CPU 시간 할당 비율을, memory 컨트롤러는 메모리 사용량 상한과 초과 시 OOM 동작을, io 컨트롤러는 디스크 I/O 대역폭을 제어합니다.

각 컨트롤러는 /sys/fs/cgroup 하위에 마운트된 가상 파일시스템의 파일을 읽고 쓰는 방식으로 설정값을 조회·변경합니다. 별도의 API 호출이 아니라 일반 파일 읽기·쓰기 인터페이스라는 점이 리눅스답습니다. 네임스페이스가 "이 프로세스는 다른 프로세스를 못 보게 하자"는 격리라면, cgroups는 "이 프로세스 그룹이 호스트 CPU를 다 잡아먹지 못하게 하자"는 자원 통제입니다.

 

핵심 개념 3 — 두 메커니즘의 결합이 "컨테이너"입니다

정리하면 "컨테이너를 만든다"는 것은 커널 관점에서 두 단계로 요약됩니다. 첫째, 새 프로세스를 여러 네임스페이스(PID, net, mnt, UTS, IPC, user 등) 안에 격리해서 실행합니다. 둘째, 그 프로세스가 속한 cgroup에 CPU·메모리·I/O 사용량 상한을 겁니다. 도커 같은 런타임은 이 두 커널 기능을 이미지 레이어·네트워크 설정·볼륨 마운트 같은 개념과 엮어 편리한 CLI로 제공하는 역할을 합니다.

실제 격리와 제한이 일어나는 지점은 어디까지나 커널의 네임스페이스·cgroups 서브시스템입니다. 이 관점을 이해하면 "컨테이너 보안"이 곧 "네임스페이스가 얼마나 촘촘히 분리되어 있는가"와 "cgroups가 자원 남용을 얼마나 잘 막는가"의 문제로 좁혀진다는 것도 자연스럽게 이해됩니다.

 

예제 — unshare와 cgroup 파일시스템 직접 다뤄보기
# 새 PID·마운트·UTS 네임스페이스에서 셸을 실행
sudo unshare --pid --mount --uts --fork --mount-proc /bin/bash

# 이 셸 안에서 hostname을 바꿔도 호스트에는 영향을 주지 않는다
hostname sandbox-test
hostname

# ps를 보면 자신이 PID 1(또는 그에 가까운 낮은 번호)로 보인다
ps aux

 

# 새 cgroup 생성 (디렉터리를 만드는 것만으로 cgroup이 생성된다)
sudo mkdir /sys/fs/cgroup/demo

# CPU 사용량을 100ms 주기 중 20ms로 제한 (약 20%)
echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max

# 메모리 사용량 상한을 200MB로 설정
echo "200M" | sudo tee /sys/fs/cgroup/demo/memory.max

# 현재 셸 프로세스를 이 cgroup에 등록
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs

unshare 예제는 네임스페이스가 프로세스의 "뷰"를 실제로 바꾼다는 점을, cgroup 파일시스템 예제는 자원 제한이 별도 API가 아니라 파일 읽기·쓰기로 이뤄진다는 점을 직접 확인해볼 수 있는 최소 실습입니다.

 

실무에서 이것만은 챙기세요
1. cgroup v1과 v2의 계층 구조가 다릅니다 — v1은 컨트롤러마다 독립된 트리를, v2는 단일 통합 계층을 씁니다. 최근 배포판·런타임은 v2가 기본 추세지만 호스트별로 mount 명령 등으로 직접 확인해야 합니다
2. 메모리 제한과 OOM 동작을 함께 이해해야 합니다 — memory.max를 넘기면 해당 cgroup 안 프로세스가 OOM killer에 의해 종료될 수 있습니다. 애플리케이션 힙 크기를 호스트 전체 메모리 기준으로 잡으면 컨테이너 안에서만 예기치 않게 죽는 문제가 반복될 수 있습니다
3. 네임스페이스 격리와 커널 취약점은 별개 문제입니다 — 네임스페이스는 논리적 격리일 뿐 하드웨어 수준 격리가 아니라서, 커널 취약점이 발견되면 경계를 우회해 호스트나 다른 컨테이너에 영향을 줄 수 있습니다
4. 자원 제한 없이 띄우면 "하나가 다 죽인다"가 재현됩니다 — 오케스트레이션 도구의 리소스 request/limit 설정은 결국 cgroups 상한을 대신 관리해주는 것입니다

 

마무리 — 3줄 요약

① 컨테이너는 별도 커널을 가진 VM이 아니라, 같은 리눅스 커널 위에서 네임스페이스로 뷰가 분리되고 cgroups로 자원이 제한된 프로세스일 뿐입니다.
② 네임스페이스(PID·네트워크·마운트·UTS·IPC·유저 등)는 "무엇이 보이는가"를, cgroups(CPU·메모리·I/O 컨트롤러)는 "얼마나 쓸 수 있는가"를 각각 담당합니다.
③ 컨테이너 런타임은 이 두 커널 기능을 편리하게 조합해주는 계층일 뿐이며, cgroup v1/v2 차이와 메모리 상한 초과 시 OOM 동작을 실무에서 미리 점검해야 합니다.
