이 프롬프트, 모델에 가기 전에 누가 막을 것인가 — Inference Hooks로 보는 추론 정책 집행 계층 설계

system-design

한 줄 요약 — Claude Enterprise의 Inference Hooks처럼 공급자가 내장한 집행 지점을 쓸지, 직접 게이트웨이를 만들어 모든 추론 호출을 가로챌지의 선택 문제를 정리했습니다. 전자는 구축이 공짜지만 커버하지 못하는 경로가 있고, 실무에서는 결국 둘을 함께 둬야 완전해집니다.

 

왜 지금 이 판단이 중요해졌는가

"업무 시간 외에는 특정 모델 호출을 막고, 프로젝트마다 쓸 수 있는 모델을 제한해주세요." AI 거버넌스를 챙겨야 하는 조직이라면 늦든 빠르든 마주치는 요구입니다. 예전에는 이런 통제를 애플리케이션 코드 안에 조건문으로 박아 넣거나, 사후에 로그를 뒤져서 위반 사례를 찾는 수밖에 없었습니다.

Anthropic이 Claude Enterprise에 공개한 Inference Hooks는 이 문제를 추론이 시작되기 전에 조직의 보안 서버에 "이 요청, 보내도 됩니까"를 묻는 동기 호출로 풀었습니다. 그런데 이 기능이 Claude Platform API, Amazon Bedrock, Google Cloud를 통한 직접 호출은 커버하지 않는다는 점이 진짜 질문을 던집니다 — 공급자가 내장한 집행 지점에 기댈 것인가, 아니면 우리가 직접 모든 경로를 가로채는 게이트웨이를 세울 것인가.

 

전체 시스템에서의 위치

정책 집행 지점은 "사용자 프롬프트"와 "모델 추론 실행" 사이, 딱 한 곳에 들어가야 합니다. 이 지점이 여러 군데로 흩어지면 규칙이 어디서 적용됐는지 추적하기 어려워집니다. Inference Hooks는 이 지점을 공급자 플랫폼 안에 내장해 구축 없이 바로 켜는 이점을 주지만, 자체 게이트웨이는 모델·공급자가 몇 개든 같은 규칙을 적용할 수 있는 대신 가용성과 지연시간을 전부 우리가 책임져야 합니다. 중요한 건 이 둘이 상호 배타적이지 않다는 점입니다 — 커버 경로가 겹치지 않게 설계하면 전체 호출 표면을 빈틈없이 덮을 수 있습니다.

표에서 드러나는 핵심은 Inference Hooks가 "빠르게 켤 수 있는 안전망"이지 "완전한 집행 계층"은 아니라는 점입니다. 조직이 API를 직접 호출하는 내부 서비스를 하나라도 운영한다면, Inference Hooks만으로는 그 경로가 통제 밖에 남습니다.

 

실제 프로젝트 진행 순서

1) 모델 호출 경로를 전수 조사합니다. 제품형 접점뿐 아니라 API 직접 호출, Bedrock·GCP 경로까지 목록화합니다.
2) 섀도 모드부터 켭니다. 판정 로그만 쌓아 오탐으로 인한 업무 중단 없이 규칙을 검증합니다.
3) 커버되지 않는 경로를 명시적으로 찾아 별도 조치합니다. 자체 게이트웨이나 최소한 사후 감사를 둡니다.
4) 역할 제외와 롤아웃 비율을 점진적으로 넓힙니다.
5) 인라인 집행과 사후 감사를 한 쌍으로 설계합니다. 서로 다른 시점의 안전망이므로 하나만 두면 구멍이 남습니다.

 

주의 — "Inference Hooks를 켰으니 끝"이라고 생각하지 마세요. 이 기능은 claude.ai·Cowork·Claude Code 세 표면만 덮습니다. 또한 매 요청 동기 호출이므로 보안 서버가 느리면 모든 추론 요청이 그 지연을 떠안습니다. 보안 서버 자체의 가용성 설계가 도입의 전제 조건입니다.

 

정리

공급자 내장 집행 지점은 빠르게 켤 수 있지만 그 공급자의 제품 표면만 덮고, API·타 클라우드 직접 호출 같은 경로는 사각지대로 남습니다. 전 경로를 통제해야 하는 조직은 자체 게이트웨이를 함께 두어야 하며, 사전 차단과 사후 감사를 한 쌍으로 두지 않으면 항상 구멍이 남습니다.
