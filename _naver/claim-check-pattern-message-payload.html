Claim Check 패턴 — 메시지 브로커에 큰 페이로드를 직접 넣지 않는 법

아키텍처·시스템 설계

한 줄 요약 — 큰 데이터는 객체 스토리지에 두고 메시지에는 참조만 실어 브로커 부하를 없애는 Claim Check 패턴을 정리했습니다.

 

왜 지금 Claim Check 패턴을 다시 봐야 하는가

이벤트에 필요한 데이터를 전부 담아 보내면 편해 보이지만, 이미지 분석 결과나 대용량 리포트처럼 큰 데이터가 늘면 문제가 생깁니다. Kafka는 메시지 크기 제한이 있고, 이를 억지로 늘리면 페이지 캐시 효율과 복제 지연이 나빠집니다. Claim Check은 큰 데이터를 별도 저장소에 두고 참조만 메시지로 주고받는 방식으로 이를 해결합니다.

 

메시지는 가볍게, 무거운 데이터는 별도 스토리지로

생산자는 큰 데이터를 객체 스토리지에 먼저 업로드하고, 그 키와 최소 메타데이터만 담은 작은 메시지를 발행합니다. 컨슈머는 메시지의 키로 필요할 때 스토리지에서 실제 데이터를 가져옵니다. 브로커는 항상 작고 예측 가능한 크기의 메시지만 다룹니다.

 

모든 이벤트를 이렇게 처리할 필요는 없다는 트레이드오프

Claim Check은 컨슈머가 항상 스토리지에 추가로 접근해야 하므로 지연시간이 늘어납니다. 작은 페이로드까지 적용하면 과잉 설계가 되므로, 크기 임계값을 두고 넘는 경우에만 전환하는 하이브리드 설계가 실무적입니다. 스토리지 만료 정책도 반드시 함께 설계해야 합니다.

항목 페이로드 직접 포함 Claim Check
메시지 크기 데이터 크기 비례 항상 작고 일정
브로커 부하 데이터 클수록 증가 데이터 크기 무관
적합한 크기 수 KB 이하 수백 KB 이상

 

예제 — Claim Check 발행과 소비 (Kafka + S3)
def publish_large_event(topic, payload_bytes, metadata):
    if len(payload_bytes) > CLAIM_CHECK_THRESHOLD:
        object_key = f"events/{uuid4()}.bin"
        s3_client.put_object(
            Bucket="event-payloads", Key=object_key,
            Body=payload_bytes, Tagging="ttl=7days",
        )
        message = {"type": "claim_check", "storage_key": object_key, "metadata": metadata}
    else:
        message = {"type": "inline", "payload": payload_bytes, "metadata": metadata}

    kafka_producer.send(topic, json.dumps(message).encode())


def consume_event(message):
    data = json.loads(message.value)
    if data["type"] == "claim_check":
        payload = s3_client.get_object(Bucket="event-payloads", Key=data["storage_key"])["Body"].read()
    else:
        payload = data["payload"]
    process(payload, data["metadata"])

 

실무 포인트

스토리지 객체의 생명주기 정책을 메시지 발행 로직과 함께 설계하세요. Lifecycle Rule 없이 두면 원본 데이터만 계속 쌓이는 누수가 생깁니다.

컨슈머의 스토리지 접근 실패를 재시도 정책에 포함하세요. 메시지가 소비돼도 스토리지 조회가 실패할 수 있습니다.

주의 — 여러 컨슈머가 같은 참조를 반복 조회한다면 캐시를 고려하세요. 매번 원본 스토리지에서 받는 대신 로컬 캐시나 CDN을 앞단에 두면 비용과 지연시간을 함께 줄입니다.
