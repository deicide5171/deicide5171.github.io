"에이전트들이 서로 의견을 주고받으면서 같이 일하게 해주세요" — Agent Teams가 다시 그리는 멀티 에이전트 협업 경계

AI

한 줄 요약 — 서브에이전트의 위계형 호출-응답 구조로는 "서로 반박하며 토론하는" 멀티 에이전트를 만들 수 없습니다. Claude Code 2.1.326이 공식화한 Agent Teams의 메일박스 통신 구조를 기준으로, 서브에이전트·에이전트 팀·세션 간 메시징 중 무엇을 고를지와 헤드리스 자동화에서는 왜 이 선택지가 아예 사라지는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"조사는 에이전트 여러 개를 띄워서 서로 다른 가설을 검증하게 하고, 틀린 가설은 서로 반박하면서 걸러내게 해주세요." 장애 원인 분석이나 아키텍처 리뷰를 자동화해달라는 요구를 받다 보면 이런 문장이 점점 자주 나옵니다. 지금까지 이런 요구는 메인 에이전트가 서브에이전트 몇 개를 띄우고, 서브에이전트는 각자 조사한 결과를 메인에게 "보고"하면 메인이 종합하는 위계형 구조로 번역해 왔습니다. 문제는 "서로 반박한다"는 요구 자체가 이 구조와 맞지 않는다는 데 있습니다. 서브에이전트는 서로의 존재를 모르고, 메인을 거치지 않고는 대화할 수 없기 때문에 "토론"이 아니라 "순차 보고의 합산"만 가능합니다.

2026년 11월 16일 공개된 Claude Code 2.1.326은 Code Mode(에이전트가 도구 호출을 직접 코드로 조율하는 모드)를 Agent Teams와 함께 켤 수 있게 하면서, 실험적으로 다듬어지던 Agent Teams 기능의 공식 문서를 정비했습니다. 이 기능은 여전히 기본값으로 꺼져 있고 환경변수로 켜야 하는 실험 단계지만, 서브에이전트와는 통신 구조 자체가 다르다는 점에서 멀티 에이전트 설계의 선택지를 하나 더 늘려놓았습니다.

 

전체 시스템에서의 위치

기존 서브에이전트 구조에서는 메인 세션이 유일한 조율자입니다. 서브에이전트를 부르고, 결과가 돌아오면 요약해서 자기 컨텍스트에 흡수하고, 다음 서브에이전트를 부릅니다. 통신은 항상 "호출 → 결과 반환"의 1:1 왕복이고, 서브에이전트끼리는 서로를 호출할 수 없습니다. Agent Teams는 이 전제를 바꿉니다. 팀 리드가 팀원을 이름 붙여 띄우는 건 같지만, 띄워진 팀원은 메일박스(mailbox)라는 파일 기반 채널로 다른 팀원에게 직접 메시지를 보낼 수 있고, 공유 작업 목록에서 대기 중인 작업을 스스로 집어갈 수 있습니다. 조율의 중심이 리드 한 곳에서, 리드가 뼈대만 짜고 나머지는 팀원들의 메시지 교환으로 분산되는 구조로 옮겨가는 것입니다.

 

선택의 트레이드오프
구조통신 방식토큰 비용가장 맞는 상황
서브에이전트호출자에게 결과만 반환낮음빠른 조사·검증처럼 결과만 필요한 작업
Agent Teams메일박스 + 공유 작업 목록높음 — 선형 증가경쟁 가설 검증, 다관점 리뷰 등 토론이 결과물인 작업
세션 간 메시징사람이 띄운 세션끼리 전달세션 수만큼사람이 각 세션을 직접 들여다봐야 하는 느슨한 병렬 작업
단일 세션통신 없음 — 순차 처리가장 낮음같은 파일을 반복 수정하는 의존성 많은 작업

 

여기서 가장 많이 놓치는 지점은 비용이 아니라 실행 환경 제약입니다. Agent Teams는 비대화형(-p 플래그) 모드, 즉 Agent SDK를 통한 자동화 세션에서는 팀원을 띄우지 않습니다. 리드가 이름을 붙여 부르려 해도 그 호출은 평범한 서브에이전트로 그대로 떨어집니다. 하루 세 번 글을 자동으로 만들어 올리는 이런 파이프라인도 -p 기반 헤드리스 세션으로 동작하기 때문에, 애초에 Agent Teams를 선택지로 쓸 수 없고 서브에이전트 구조로만 멀티 에이전트 작업을 설계해야 합니다. "토론형 멀티 에이전트가 필요한가"를 묻기 전에 "이게 사람이 터미널로 들여다보는 대화형 세션인가, 자동화 세션인가"부터 물어야 합니다.

 

실제 프로젝트 진행 순서

먼저 지금 만들려는 워크플로우가 대화형 세션에서 도는지, 자동화 파이프라인에서 도는지부터 확정합니다. 자동화라면 서브에이전트 설계로 바로 갑니다. 대화형이라면 작업을 "결과만 필요한가, 토론이 필요한가"로 나눠 봅니다. 코드 리뷰를 보안·성능·테스트 커버리지 세 관점으로 쪼개 동시에 보게 하거나, 장애 원인을 두고 여러 가설을 경쟁시키는 작업은 팀 쪽이고, 모듈 하나를 구현하는 작업은 서브에이전트 쪽입니다.

// Agent Teams를 쓰기로 했다면 설정 예시
{
  "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" },
  "teammateMode": "auto",
  "subagentPromptCacheTtl": "1h"
}

플래그를 켠 뒤에는 바로 실무 작업에 투입하지 말고, 경계가 분명한 리서치·리뷰 작업으로 먼저 검증해야 합니다. 그다음 파일을 나눠 쓰는 구현 작업으로 넘어가되, 팀원 간 파일 소유권을 반드시 분리해야 합니다. 같은 파일을 두 팀원이 동시에 고치면 덮어쓰기가 납니다. 마지막으로 작업 완료 시점에 훅을 걸어 품질 게이트를 강제해야 합니다 — 팀원이 작업을 완료로 표시하는 타이밍이 지연되는 경우가 보고되고 있어, 훅 없이는 의존 작업이 조용히 막혀 있는 상태를 놓치기 쉽습니다.

 

주의 — Agent Teams는 토큰 비용이 세션 수만큼 선형으로 늘어나는 데다, 세션 재개(/resume) 시 팀원이 복원되지 않는 등 실험 단계의 한계가 뚜렷합니다. 프로덕션 자동화 경로에는 아직 올리지 말고, 사람이 지켜보는 탐색·리뷰 작업에 한정해 검증하는 것이 안전합니다.
