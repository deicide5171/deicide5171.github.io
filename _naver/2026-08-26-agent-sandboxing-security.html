AI 에이전트에게 셸을 내주기 전에 — 코드 실행 샌드박스 격리 설계

2026. 8. 26. · AI

한 줄 요약 — LLM 에이전트가 생성한 코드를 실행하는 순간 방어 단위는 애플리케이션이 아니라 OS·하이퍼바이저 계층이 됩니다. 컨테이너, gVisor, Firecracker microVM의 격리 경계 차이와 실무 체크리스트를 정리했습니다.

 

에이전트가 코드를 직접 실행한다는 것의 의미

에이전트에게 "코드를 짜고 직접 실행해서 결과를 확인하라"는 능력을 주는 순간, 그 에이전트는 임의 코드 실행기가 됩니다. 문제는 이 코드가 사람이 아니라 LLM이 생성한다는 점입니다. 프롬프트 인젝션에 당한 에이전트가 rm -rf를 실행하거나, 내부 네트워크로 요청을 보내거나, 크리덴셜이 담긴 환경변수를 읽어 외부로 전송하는 시나리오는 이미 여러 사고 리포트에 등장했습니다.

전통적인 웹 애플리케이션 보안은 "입력값을 검증한다"는 전제 위에 서 있지만, 에이전트가 생성하는 코드는 입력값 검증으로 막을 수 있는 범주가 아닙니다. 임의의 함수 호출, 임의의 시스템 콜을 막아야 하므로 방어의 단위가 애플리케이션 계층에서 OS·하이퍼바이저 계층으로 내려갑니다.

 

핵심 개념 1 — 격리 수준은 하나가 아닙니다

"샌드박스"라는 말이 가리키는 격리 수준은 실제로 스펙트럼입니다. 컨테이너는 커널을 공유하므로 커널 취약점 하나로 탈옥(container escape)이 가능하고, gVisor 같은 유저스페이스 커널은 시스템 콜을 가로채 재구현하지만 오버헤드가 있습니다. Firecracker나 Kata Containers 같은 microVM은 하드웨어 가상화로 커널까지 완전히 분리하지만 부팅 비용이 붙습니다.

방식 격리 경계 콜드스타트 대표 사고 유형
일반 컨테이너(runc) 커널 공유 수십ms 커널 CVE, 잘못된 마운트
gVisor 유저스페이스 커널 수십~수백ms 미구현 syscall 우회
Firecracker microVM 하드웨어 가상화(KVM) 100ms대 하이퍼바이저 취약점 필요
WASM 런타임 바이트코드 캡슐화 수ms 호스트 바인딩 함수 과다 노출

 

핵심 개념 2 — 코드 실행 격리만으로는 끝나지 않습니다

컨테이너나 microVM으로 프로세스를 가둬도, 네트워크와 파일시스템 경계를 따로 그리지 않으면 격리는 무의미해집니다. 실무에서 자주 놓치는 세 가지가 있습니다. 첫째, 아웃바운드 네트워크 기본 차단입니다. 실행 환경은 egress를 전부 막고 필요한 도메인만 화이트리스트로 열어야 내부 메타데이터 서버나 사내 서비스로의 요청을 막을 수 있습니다.

둘째, 파일시스템 읽기 전용 마운트입니다. 실행 디렉터리 외에는 전부 읽기 전용으로 마운트하고, 실행이 끝나면 파일시스템 전체를 폐기해야 세션 간 비밀값 노출을 막을 수 있습니다. 셋째, 리소스 쿼터입니다. CPU·메모리·프로세스 수·실행 시간에 하드 리밋을 걸어 무한 루프나 포크 폭탄이 호스트 자원을 고갈시키지 못하게 해야 합니다.

 

예제 — Firecracker 리소스 제한 설정

아래는 Firecracker microVM 구성 예시입니다. 루트 파일시스템을 읽기 전용으로 고정하고 네트워크 인터페이스 자체를 만들지 않아, 네트워크가 필요한 도구 호출은 별도의 브로커 프로세스가 대신 수행하는 프록시 패턴을 사용합니다.

{
  "boot-source": {
    "kernel_image_path": "vmlinux",
    "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
  },
  "drives": [
    { "drive_id": "rootfs", "path_on_host": "rootfs.ext4", "is_root_device": true, "is_read_only": true }
  ],
  "machine-config": {
    "vcpu_count": 1,
    "mem_size_mib": 256,
    "smt": false
  },
  "network-interfaces": []
}

 

실무 도입 시 이것만은 챙기세요
1. 격리 계층을 코드 실행 기능과 분리해서 설계하세요 — "일단 컨테이너에 넣었으니 안전하다"는 가정은 위험합니다. API 경로, 실행 환경, 결과 반환 경로를 각각 별도 신뢰 경계로 그리세요.
2. 감사 로그는 실행 환경 밖에서 수집하세요 — 실행 환경 내부에 로깅 에이전트를 심으면 탈옥 시 로그도 조작될 수 있습니다. 호스트 레벨 syscall 트레이싱이 필요합니다.
3. 콜드스타트 비용을 과소평가하지 마세요 — 매 요청마다 새로 띄우면 동시성 높은 서비스에서 병목이 됩니다. 워커 풀을 미리 띄워두는 방식이 일반적입니다.

 

마무리 — 3줄 요약

① 에이전트가 실행하는 코드는 입력값 검증으로 막을 수 없으므로 방어 단위를 OS·하이퍼바이저 계층으로 내려야 합니다.
② 컨테이너·gVisor·Firecracker microVM·WASM은 격리 경계와 콜드스타트 비용이 다른 스펙트럼이며, 워크로드 특성에 맞춰 선택해야 합니다.
③ 코드 실행 격리만큼 아웃바운드 네트워크 차단, 읽기 전용 파일시스템, 리소스 쿼터가 함께 갖춰져야 실질적인 보안 경계가 완성됩니다.
