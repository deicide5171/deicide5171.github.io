cgroup v2 통합 계층 구조로 CPU·IO 리소스 실전 제어하기

2026. 8. 25. · 인프라

한 줄 요약 — cgroup v1의 컨트롤러별 분리 계층이 v2에서 단일 통합 계층으로 바뀌면서, cpu.max와 io.max 파일 하나로 CPU·IO 리소스를 훨씬 일관되게 제어할 수 있게 됐습니다.

 

옆 컨테이너가 갑자기 느려지는 이유

같은 노드에 컨테이너를 여러 개 올려두면 언젠가 반드시 겪는 문제가 있습니다. 로그를 몰아서 쓰는 배치 작업 하나가 디스크 IO를 독점해서 옆 컨테이너의 DB 쿼리가 갑자기 느려지거나, CPU를 많이 쓰는 워커 하나가 같은 노드의 API 서버 레이턴시를 끌어올리는 경우입니다. resources.limits를 설정했다고 안심하기 쉽지만, 그 뒤에서 실제로 커널이 자원을 나누는 것은 cgroup(control group)이라는 리눅스 커널 기능입니다.

최근 배포판 대부분은 이제 cgroup v1이 아니라 cgroup v2를 기본으로 씁니다. v2는 단순히 버전만 올라간 게 아니라 계층 구조 자체가 근본적으로 바뀌었고, 이 차이를 모르면 리소스 제한 설정이 기대와 다르게 동작하는 이유를 진단하기 어렵습니다.

 

핵심 개념 1 — 분리 계층에서 통합 계층으로

cgroup v1에서는 컨트롤러(cpu, memory, blkio 등)마다 독립된 계층 구조를 가질 수 있었습니다. 유연해 보이지만 "이 프로세스가 CPU 관점에서는 그룹 A인데 메모리 관점에서는 그룹 B"라는 앞뒤가 안 맞는 구성이 흔했고, 컨트롤러 간 협조도 구현하기 어려웠습니다.

cgroup v2는 이를 단일 통합 계층 하나로 합쳤습니다. 프로세스는 하나의 트리에서 정확히 하나의 cgroup에만 속하고, 그 cgroup에 cpu·memory·io·pids 컨트롤러를 동시에 붙여 함께 관리합니다. 이 구조 덕분에 컨테이너 런타임과 systemd도 리소스 관리 로직을 단순화할 수 있었습니다.

 

핵심 개념 2 — v1과 v2 핵심 차이
구분 cgroup v1 cgroup v2
계층 구조 컨트롤러별 독립 트리 단일 통합 트리
CPU 제한 cfs_quota_us / cfs_period_us cpu.max (한 줄)
IO 제한 blkio.throttle.* io.max (단일 인터페이스)
위임 모델 제한적 delegation으로 안전하게 지원

 

핵심 개념 3 — cpu.max와 io.max로 실제 제어하기

CPU 제한은 cpu.max 파일 하나로 표현합니다. 형식은 "quota period"이며, 예를 들어 "200000 100000"은 100ms 주기마다 최대 200ms(2코어 분량)까지 쓸 수 있다는 뜻이고, 넘기면 커널이 해당 그룹을 쓰로틀링합니다. IO 제한은 io.max로 디바이스별 rbps·wbps·riops·wiops 상한을 걸 수 있습니다.

 

예제 — cgroup v2로 CPU·IO 제한 걸기
# 배치 작업용 cgroup 생성
mkdir /sys/fs/cgroup/batch-job
echo "+cpu +io" > /sys/fs/cgroup/cgroup.subtree_control

# CPU: 100ms 주기 중 최대 50ms(0.5코어)만 허용
echo "50000 100000" > /sys/fs/cgroup/batch-job/cpu.max

# IO: 특정 디스크(8:0)에 대해 쓰기 대역폭 50MB/s로 제한
echo "8:0 wbps=52428800" > /sys/fs/cgroup/batch-job/io.max

# 프로세스 소속시키기
echo $BATCH_PID > /sys/fs/cgroup/batch-job/cgroup.procs

# 쓰로틀링 발생 여부 확인
cat /sys/fs/cgroup/batch-job/cpu.stat

쿠버네티스 환경에서는 이 파일을 직접 만지는 대신 파드의 resources.limits를 설정하면 kubelet과 컨테이너 런타임이 대신 써줍니다.

 

실무 도입 시 이것만은 챙기세요
1. cpu.stat의 nr_throttled를 반드시 모니터링하세요 — 평균 CPU 사용률만 보면 쓰로틀링이 잦아도 착시가 생깁니다. 버스트 워크로드는 쓰로틀링 빈도로 판단해야 합니다.
2. quota/period 비율이 코어 수와 안 맞으면 지터가 생깁니다 — 짧은 period 안에 스레드가 몰려 조기에 quota를 소진하고 나머지 시간을 쉬는 현상이 있으니 period를 늘려 완충 여유를 주세요.
3. memory.high와 io.max를 함께 보세요 — 메모리 압박이 심해지면 페이지 캐시 회수로 IO가 급증합니다. PSI(cpu.pressure, io.pressure, memory.pressure)를 함께 보면 병목이 명확해집니다.

 

마무리 — 3줄 요약

① cgroup v2는 v1의 컨트롤러별 분리 계층을 단일 통합 트리로 합쳐 컨트롤러 간 협조와 안전한 위임을 가능하게 했습니다.
② CPU는 cpu.max, IO는 io.max로 상한을 걸며, 쿠버네티스에서는 리소스 필드를 통해 간접적으로 설정됩니다.
③ 쓰로틀링 여부는 평균 사용률이 아니라 nr_throttled와 PSI 지표로 판단해야 실제 자원 경합을 놓치지 않습니다.
