MCP Sampling이 폐기된다 — 서버가 직접 LLM을 호출하는 설계로 전환하기

AI

한 줄 요약 — '도구가 가져온 데이터를 요약까지 해서 돌려주세요'라는 요구를 MCP 서버는 그동안 sampling으로 클라이언트의 모델에 떠넘겨 풀었습니다. MCP 스펙 개정(SEP-2577)이 이 sampling을 폐기 경로에 올리면서, 서버가 직접 LLM 제공자 API를 호출하는 쪽으로 설계를 옮겨야 하는 이유와 전환 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"검색 도구가 찾아온 문서 10개를 그냥 다 돌려주지 말고, 핵심만 요약해서 보여주세요." MCP 서버를 만들어본 사람이라면 한 번쯤 받아봤을 요구사항입니다. 요약은 LLM이 해야 하는 일인데, 서버 안에 또 다른 모델 호출 로직을 넣는 건 과한 책임처럼 느껴집니다. 그래서 MCP는 처음부터 sampling/createMessage라는 기능을 뒀습니다. 서버가 "이 텍스트를 요약해줘"라는 요청을 클라이언트로 역으로 보내면, 클라이언트가 자신이 이미 쓰고 있는 모델로 추론해 결과만 서버에 돌려주는 구조입니다. 서버는 API 키도, 모델 선택권도 가질 필요가 없었습니다.

이 전제가 2026-07-28 스펙 개정으로 흔들렸습니다. SEP-2577이 Roots·Sampling·Logging 세 기능을 나란히 폐기 경로에 올렸습니다. 와이어 레벨 동작은 이 리비전에서 아직 바뀌지 않고, 폐기 선언 이후 최소 12개월간은 기존 버전들이 그대로 지원됩니다. 내일 당장 깨지는 건 아니지만, 공식 스펙 문서가 "새 구현체는 이 기능을 채택하지 말라"고 명시한 이상 지금 서버를 새로 짜는 팀이라면 설계 전제를 다시 세워야 합니다.

 

전체 시스템에서의 위치

sampling이 있을 때와 없을 때, 추론이 일어나는 위치 자체가 달라집니다.

기존 sampling 구조는 MCP 서버가 createMessage 요청을 클라이언트로 보내고, 클라이언트가 자신이 연결한 모델로 추론해 결과만 돌려주는 방식입니다. 서버는 어떤 모델이 응답했는지조차 알 필요가 없습니다. 전환 후 구조는 서버가 자체적으로 Anthropic·OpenAI 같은 제공자 API를 직접 호출합니다. API 키, 비용, 모델 버전 관리는 전부 서버 쪽 책임이 됩니다. 서버 주도 다중 왕복이 필요한 다른 경우는 같은 개정에서 논의 중인 MRTR(SEP-2322) 패턴이 참고가 됩니다. 서버가 input_required 결과 타입을 돌려주면 클라이언트가 같은 호출을 inputResponses와 함께 재시도하는 구조입니다.

 

선택의 트레이드오프
접근 장점 단점
sampling 계속 사용 지금 당장 변경 없음 신규 구현 금지 권고
서버 직접 LLM 호출 모델 선택권 확보, 응답 일관성 API 키·비용 책임 전가
MRTR 패턴 전환 표준 메커니즘 위에서 왕복 유지 아직 확정 전 단계
하이브리드(직접 호출+sampling 폴백) 전환 리스크 분산 두 경로 동시 유지보수

 

판단 기준은 "이 도구가 모델 호출 결과의 품질에 얼마나 민감한가"입니다. 요약·추출처럼 결과 품질이 곧 도구의 가치인 기능이라면, 클라이언트가 어떤 모델을 쓰는지 모르는 sampling 위임 자체가 리스크였습니다. 반대로 단순 텍스트 변환 수준이라면 유예기간 동안은 서두를 필요가 없습니다.

 

실제 프로젝트 진행 순서

1. sampling 의존 지점부터 전수 조사합니다. createMessage 호출을 모두 찾아 목록화합니다.
2. 도구별로 전환 우선순위를 정합니다. 결과 품질이 핵심 가치인 도구를 먼저 옮깁니다.
3. 키·시크릿 관리 설계를 먼저 끝냅니다. 비밀 관리, 레이트 리밋, 비용 모니터링이 서버 운영 범위로 들어옵니다.
4. 제공자 락인을 피할 추상화 계층을 둡니다.
5. 서버 주도 되묻기가 필요한 도구는 MRTR을 검토하되, 급하지 않으면 기존 구조로 버텨도 됩니다.
6. 12개월 유예기간을 역산해 일정을 잡습니다.

 

예제 코드:

// 전환 전: 클라이언트에게 추론을 위임
async function summarizeDocs(docs, ctx) {
  const result = await ctx.sample({
    messages: [{ role: "user", content: `요약: ${docs.join("\n")}` }],
    maxTokens: 500,
  });
  return result.content;
}

// 전환 후: 서버가 직접 제공자 API를 호출
async function summarizeDocs(docs) {
  const response = await anthropic.messages.create({
    model: "claude-sonnet-5-5",
    max_tokens: 500,
    messages: [{ role: "user", content: `요약: ${docs.join("\n")}` }],
  });
  return response.content;
}

 

주의 — Sampling만 바뀌는 게 아니라 Roots·Logging도 같은 폐기 경로에 올랐습니다. 와이어 프로토콜은 아직 바뀌지 않았으니 "폐기 예고"와 "제거"를 혼동해 성급하게 전체 코드를 갈아엎지 마세요. 사용 중인 SDK의 마이그레이션 노트를 직접 확인하세요.

 

정리

MCP 스펙(SEP-2577)이 Sampling·Roots·Logging을 폐기 경로에 올리며, 서버가 클라이언트 모델에 추론을 위임하던 전제가 바뀌고 있습니다. 와이어 레벨은 아직 그대로지만 12개월 유예 안에, 결과 품질이 도구 가치를 좌우하는 기능부터 서버 직접 LLM 호출로 옮기는 게 안전합니다. 전환의 실제 비용은 모델 호출 코드가 아니라 API 키·비용·레이트 리밋을 서버 책임으로 끌어오는 운영 설계에 있습니다.
