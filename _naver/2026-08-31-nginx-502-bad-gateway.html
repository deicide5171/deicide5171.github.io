Nginx 502 Bad Gateway, 원인과 해결법

인프라

한 줄 요약 — 502는 대부분 Nginx가 아니라 업스트림 애플리케이션 서버 문제이며, error.log의 메시지로 원인을 구분해야 합니다.

 

502는 Nginx가 아니라 뒷단 문제일 때가 많다

502 Bad Gateway는 Nginx가 뒤에 있는 애플리케이션 서버(업스트림)로부터 유효한 응답을 받지 못했다는 뜻입니다. Nginx 자체는 정상이고 원인은 대부분 업스트림 쪽에 있으므로, Nginx 로그만 보지 말고 애플리케이션 서버 상태까지 함께 봐야 합니다.

 

원인 후보와 확인 방법
원인 확인 방법 대응
업스트림 서버 다운 curl localhost:앱포트 프로세스 재시작·로그 확인
응답 지연(타임아웃) error.log의 upstream timed out proxy_read_timeout 조정
Nginx 설정 오류 nginx -t proxy_pass 주소 확인

 

로그 확인이 최우선
tail -f /var/log/nginx/error.log

# "connect() failed (111: Connection refused)..."
# "upstream timed out (110: Connection timed out)..."

Connection refused면 애플리케이션이 죽어 있는 것이고, timed out이면 앱은 살아 있지만 응답이 늦는 것입니다. 원인도 대응도 완전히 다릅니다.

 

설정 예제 — 타임아웃과 재시도
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081 backup;
}

location /api/ {
    proxy_pass http://backend;
    proxy_read_timeout 30s;
    proxy_next_upstream error timeout http_502;
}

 

실무 포인트

배포 직후에만 502가 발생한다면 무중단 배포(롤링 업데이트)로 전환하면 사라집니다.

주의 — proxy_read_timeout을 무작정 늘리는 것은 임시방편입니다. 근본적으로는 왜 응답이 느려졌는지(느린 쿼리, 외부 API 대기 등)를 찾아야 합니다.
