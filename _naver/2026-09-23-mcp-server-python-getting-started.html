한 줄 요약 — 사내 시스템을 AI 에이전트에 연결하려고 MCP 서버를 직접 만들 때, stdout 오염과 상대 경로 설정이 초기 실패의 가장 흔한 두 원인입니다. Python SDK 기준으로 정리했습니다.

 

왜 지금 MCP 서버를 직접 만들어야 하나

AI 에이전트가 파일을 읽고 웹을 검색하는 범용 도구는 이미 공개된 MCP 서버가 많지만, 사내 티켓 시스템이나 자체 DB처럼 회사 고유 시스템은 직접 서버를 만들어 연결하는 수밖에 없습니다. 그런데 문서를 따라 몇 줄 붙여넣었는데 클라이언트가 서버를 인식하지 못하거나 도구 목록이 비어 보이는 경우가 흔합니다.

MCP(Model Context Protocol)는 AI 모델이 외부 도구·데이터 소스와 통신하는 방식을 표준화한 프로토콜입니다. 서버를 만든다는 건 결국 "이 함수를 도구로 노출하겠다"고 선언하는 작업입니다.

 

 

핵심 개념 1 — 서버는 stdio로 통신한다

로컬에서 실행하는 MCP 서버 대부분은 HTTP가 아니라 표준 입출력(stdio)으로 클라이언트와 통신합니다. 클라이언트가 서버 프로세스를 직접 실행시키고 stdin/stdout으로 JSON-RPC 메시지를 주고받는 구조입니다. 이걸 모르고 서버 코드 안에서 print()로 디버그 로그를 찍으면, 그 출력이 stdout으로 나가면서 프로토콜 메시지와 뒤섞여 클라이언트가 서버를 인식조차 못 하는 사고가 납니다.

디버그 출력은 반드시 sys.stderr나 로깅 모듈로 보내야 합니다.

 

핵심 개념 2 — 타입 힌트가 곧 스키마다

Python SDK는 함수에 데코레이터를 붙이는 것만으로 도구를 등록하게 해주지만, 그 함수의 타입 힌트와 docstring이 그대로 클라이언트에 노출되는 스키마가 됩니다. 타입 힌트를 생략하면 클라이언트가 파라미터 타입을 모른 채 호출하려다 실패하거나, 도구 목록에서 흐릿하게 표시되는 경우가 많습니다.

 

예제 — FastMCP로 최소 서버 만들기
# server.py
from mcp.server.fastmcp import FastMCP
import sys

mcp = FastMCP("internal-ticket-server")

@mcp.tool()
def get_ticket_status(ticket_id: str) -> str:
    """티켓 ID로 사내 이슈 트래커의 현재 상태를 조회한다."""
    print(f"조회 요청: {ticket_id}", file=sys.stderr)  # stdout이 아니라 stderr!
    return f"티켓 {ticket_id}: 진행중"

if __name__ == "__main__":
    mcp.run(transport="stdio")

클라이언트 설정 파일에는 이 스크립트를 실행할 절대 경로와 인터프리터를 명시해야 합니다. 상대 경로나 PATH 의존 명령을 그대로 쓰면, 클라이언트가 다른 작업 디렉터리에서 프로세스를 띄우면서 모듈을 못 찾는 에러가 자주 발생합니다.

 

흔한 실수와 원인
증상 원인 해결
도구 목록이 비어 보임 print()가 stdout 오염 stderr나 logging 사용
클라이언트가 인식 못 함 설정 파일 경로가 상대 경로 절대 경로로 지정
파라미터 타입 에러 타입 힌트 누락 모든 파라미터에 타입 힌트
서버가 조용히 죽음 미처리 예외로 프로세스 종료 try/except로 에러 메시지 반환

 

실무 포인트

도구 설명(docstring)을 모델이 읽는다고 생각하고 쓰세요. 모델은 이 docstring을 보고 언제 이 도구를 호출할지 판단합니다. 구체적으로 쓸수록 잘못된 시점에 호출되는 일이 줄어듭니다.

입력 검증은 서버 쪽에서 반드시 다시 하세요. 클라이언트가 스키마를 지킨다는 보장이 없으므로, 경로 탈출이나 SQL 인젝션 가능성을 서버 코드 자체에서 막아야 합니다.

주의 — 여러 사람이 공유하는 사내 서버라면 stdio 대신 인증이 가능한 HTTP/SSE 기반 transport로 전환하는 것을 검토해야 합니다. 로컬 개발용 stdio를 그대로 공유 환경에 쓰면 접근 통제가 되지 않습니다.
