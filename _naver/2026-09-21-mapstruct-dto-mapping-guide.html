MapStruct로 DTO 변환 자동화하기 — 수동 매핑과 비교

백엔드

한 줄 요약 — MapStruct는 컴파일 시점에 실제 매핑 코드를 생성해, 수동 매핑과 동일한 성능을 유지하면서 필드 누락을 빌드 단계에서 잡아줍니다.

 

왜 이 문제가 반복되는가

엔티티를 그대로 API 응답으로 내보내지 않고 DTO로 변환하는 것은 이제 상식입니다. 문제는 프로젝트가 커질수록 엔티티-DTO 변환 코드가 기하급수적으로 늘어난다는 점입니다. 필드 하나가 추가될 때마다 변환 메서드를 빠뜨리지 않고 고쳐야 하고, 코드 리뷰에서도 "필드 하나 빠뜨렸다"는 지적이 반복됩니다.

 

잘못된 대안: 리플렉션 기반 매핑

ModelMapper 같은 런타임 리플렉션 기반 라이브러리는 코드량은 줄지만, 런타임에야 매핑 오류를 발견하고 리플렉션 오버헤드가 있으며 디버깅이 어렵다는 대가가 있습니다.

올바른 접근: MapStruct
@Mapper(componentModel = "spring")
public interface OrderMapper {
    @Mapping(source = "customer.name", target = "customerName")
    OrderDto toDto(Order order);
}

이 인터페이스만 작성하면 빌드 시점에 MapStruct가 실제 필드 대입 코드가 담긴 구현체를 자동으로 만들어줍니다. 리플렉션이 아니라 일반 getter/setter 호출로 컴파일되므로 런타임 성능이 수동 매핑과 동일하고, 필드명이 틀리면 컴파일 시점에 에러로 바로 드러납니다.

방식 오류 발견 런타임 성능
수동 매핑 컴파일 타임 좋음
ModelMapper 런타임 상대적으로 느림
MapStruct 컴파일 타임 수동과 동일

 

주의 — MapStruct는 이름이 다른 필드는 조용히 매핑하지 않고 넘어갈 수 있습니다. 빌드 설정에서 unmappedTargetPolicy = ERROR로 엄격하게 잡아두는 것이 안전합니다.

 

실무 포인트

양방향 매핑이 필요하면 각각 메서드를 명시적으로 선언해야 합니다. 중첩 객체는 uses = {CustomerMapper.class}처럼 다른 매퍼를 참조하게 구성할 수 있습니다. 코드 생성이라 안전해 보이지만 Mapping 설정 자체가 잘못되면 논리적 버그가 날 수 있으므로, 매퍼도 단위 테스트 대상으로 다루세요.
