"이 작업, 에이전트 여러 개로 나눠서 처리해주세요" — 오케스트레이션 토폴로지가 바꾸는 장애 처리 설계

시스템 설계

한 줄 요약 — '에이전트 여러 개로 나눠서 처리해달라'는 요구는 토폴로지를 먼저 정하지 않으면 장애가 어디까지 번질지도 정해지지 않습니다. 순차·병렬·계층형 구조별로 실패가 전파되는 범위와 복구 전략이 어떻게 달라지는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"이 보고서, 리서치·분석·작성 에이전트로 나눠서 처리해주세요." 또는 "이 PR, 버그·성능·보안 관점으로 에이전트 세 개한테 각각 맡겨주세요." 업무를 여러 에이전트에 나누는 요구는 이제 흔합니다. 그런데 이 한 문장 뒤에는 보이지 않는 질문이 숨어 있습니다. 에이전트들이 어떤 순서와 구조로 연결되는가, 그리고 그중 하나가 실패했을 때 나머지는 어떻게 되는가입니다.

멀티 에이전트 오케스트레이션 토폴로지는 크게 세 가지입니다. 순차(앞 단계 결과가 다음 단계 입력이 되는 파이프라인), 병렬(독립 작업을 동시에 실행하고 모으는 fan-out/fan-in), 계층형(감독 에이전트가 작업을 쪼개 위임하는 supervisor-worker). 세 구조는 평상시엔 비슷해 보여도 하나가 실패했을 때의 모습이 완전히 다릅니다.

 

전체 시스템에서의 위치

순차 구조에서 장애는 선형으로 전파됩니다. 실패 지점을 기준으로 이전 결과는 보존되지만 이후는 전부 멈춥니다. 병렬 구조에서 장애는 국소적으로 머물지만, fan-in 지점에서 부분 성공을 어떻게 처리할지 별도 정책이 필요합니다. 계층형 구조에서 장애는 깊이에 비례해 번집니다 — 감독 노드가 실패하면 그 서브트리 전체가 영향을 받습니다.

 

선택의 트레이드오프
기준 순차 병렬 계층형
장애 전파 범위 실패 지점 이후 전체 실패한 분기만 실패 노드의 서브트리 전체
복구 전략 실패 단계부터 재실행 실패한 분기만 재시도 감독이 재시도·재위임으로 흡수
구현 복잡도 낮음 중간 (fan-in 정책 필요) 높음 (감독 장애도 설계)
적합한 상황 단계가 이전 결과에 의존 독립적으로 쪼갤 수 있는 작업 작업 분해를 동적으로 판단

 

세 구조를 섞어 쓰는 경우도 흔합니다. "리서치(병렬 다섯 갈래) → 종합(순차 한 단계) → 검증(병렬 두 갈래)"처럼 구성하면, 전체를 하나의 토폴로지로 억지로 맞추는 것보다 실제 의존 관계를 더 정확히 반영할 수 있습니다.

 

실제 프로젝트 진행 순서

1. 작업 간 의존 관계부터 그래프로 그립니다. 이 그래프가 사실상 토폴로지를 결정합니다.
2. 각 노드의 실패 정책(재시도/건너뛰기/전체실패)을 토폴로지 선택과 동시에 정의합니다.
3. fan-in 지점의 부분 성공 기준을 숫자(quorum)로 못 박습니다.
4. 계층형이라면 감독 노드 자체의 장애 대응을 별도로 설계합니다.
5. 관측성을 토폴로지 구조에 맞춰 설계해 어느 노드에서 실패했는지 추적합니다.
6. 단일 토폴로지로 억지로 통일하지 않고, 구간별로 혼합 구조를 고려합니다.

 

예제 코드:

# fan-in 지점에서 부분 성공 기준을 명시적으로 정의
results = run_parallel([review_bugs, review_perf, review_security])
succeeded = [r for r in results if r.ok]

if len(succeeded) < 2:  # quorum: 3개 중 최소 2개
    raise AggregationFailure("리뷰 결과 부족, 합의된 결론을 낼 수 없음")

merged = merge_reviews(succeeded)

 

주의 — 순차 구조는 단계가 많아질수록 지연이 선형으로 늘어난다는 점을 놓치기 쉽습니다. 실제로는 병렬화할 수 있는 단계를 습관적으로 순차로 묶어 설계하는 경우가 많으니, 의존 그래프를 그릴 때 불필요한 순서 강제를 먼저 걷어내세요. 계층형 구조에서 감독 노드를 단순 전달 역할로만 설계하면, 감독 자체의 장애 복구는 공짜로 따라오지 않습니다.

 

정리

순차·병렬·계층형 토폴로지는 평상시 동작은 비슷해 보여도 장애가 전파되는 범위와 복구 전략이 근본적으로 다릅니다. 토폴로지 선택은 "에이전트를 몇 개 쓸까"가 아니라 작업 간 실제 의존 관계를 그래프로 그리는 데서 시작해야 합니다. fan-in의 부분 성공 기준과 계층형 감독 노드의 장애 대응은 구현 이후가 아니라 설계 단계에서 정량적으로 정해둬야 합니다.
