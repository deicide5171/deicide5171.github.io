테넌트 컬럼 하나로 될 일이 아니다 — 멀티테넌트 DB 스키마 설계 실무

2026. 8. 29. · 데이터베이스

한 줄 요약 — 공유 스키마, 스키마 분리, DB 분리라는 세 가지 멀티테넌트 스키마 모델을 마이그레이션·인덱싱·격리 강도 관점에서 비교하고 실제 구현 디테일을 정리했습니다.

 

인프라 결정과 스키마 구현은 다른 층위입니다

멀티테넌트 SaaS를 어느 인프라 형태로 배포할지는 아키텍처 레벨의 결정이지만, 그 결정을 실제 DB 스키마로 어떻게 구현할지는 또 다른 문제입니다. 테넌트마다 완전히 분리된 DB를 쓴다고 정해도 그 안에서 스키마 마이그레이션을 어떻게 굴릴지, 인덱스를 어떻게 설계할지는 별도로 풀어야 합니다.

 

핵심 개념 1 — 세 가지 모델의 스키마 구현

공유 스키마는 모든 테넌트 데이터가 같은 테이블에 섞여 있고 tenant_id 컬럼으로 구분합니다. 스키마 분리는 같은 DB 인스턴스 안에 테넌트마다 별도 스키마를 두고 같은 테이블 구조를 복제합니다. DB 분리는 테넌트마다 완전히 별도의 DB를 둬 가장 강한 격리를 제공하지만 운영 오버헤드가 가장 큽니다.

 

 

핵심 개념 2 — 공유 스키마의 RLS와 인덱스 설계

공유 스키마를 선택했다면 애플리케이션이 매 쿼리마다 tenant_id 조건을 빼먹지 않는가에 데이터 격리 전체가 달립니다. PostgreSQL의 행 수준 보안(RLS)을 걸어두면 애플리케이션이 실수로 조건을 빠뜨려도 DB가 자동으로 다른 테넌트 행을 걸러냅니다. 인덱스는 복합 인덱스의 첫 컬럼을 항상 tenant_id로 두는 것이 기본 원칙입니다.

SET app.current_tenant = 'tenant_123';

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.current_tenant')::uuid);
-- 애플리케이션이 WHERE tenant_id를 빼먹어도 DB가 자동으로 다른 테넌트 행 숨김

 

핵심 개념 3 — 마이그레이션이 테넌트 수만큼 곱해집니다

스키마 분리와 DB 분리의 공통된 난제는 마이그레이션이 테넌트 수만큼 곱해진다는 것입니다. 컬럼 하나를 추가해도 스키마가 100개면 100번 실행해야 하고, 일부가 실패하면 스키마 드리프트가 생길 수 있습니다. DB 분리는 여기에 테넌트-DB 라우팅과 커넥션 풀 관리 부담까지 추가됩니다.

구분 공유 스키마 스키마 분리 DB 분리
격리 강도 약함 중간 강함
마이그레이션 1회 실행 스키마 수만큼 DB 수만큼

 

실무 도입 시 이것만은 챙기세요
1. RLS는 애플리케이션 필터링의 안전망으로 쓰세요 — RLS가 있어도 애플리케이션 필터링을 생략하면 안 됩니다.
2. 테넌트 규모 편차가 크다면 하이브리드를 고려하세요 — 대형 고객만 별도 스키마·DB로 빼는 혼합 전략이 현실적입니다.
3. 마이그레이션 실패 테넌트 추적을 자동화하세요 — 사람이 수작업으로 확인하는 방식은 곧 감당할 수 없어집니다.

 

마무리 — 3줄 요약

① 멀티테넌트 스키마는 공유 스키마·스키마 분리·DB 분리로 나뉘며 격리가 강해질수록 운영 복잡도도 늘어납니다.
② 공유 스키마는 RLS로 필터링 누락을 방어하고 복합 인덱스 첫 컬럼에 tenant_id를 두는 것이 기본입니다.
③ 스키마·DB 분리는 마이그레이션이 테넌트 수만큼 곱해지므로 실패 추적 자동화와 하이브리드 전략이 유리합니다.
