"필지 데이터 수십만 건을 한 번에 내려주세요" — GeoServer WFS 대용량 요청 타임아웃을 막는 설계

GIS

한 줄 요약 — '외부 파트너가 우리 WFS로 지역 전체 필지 데이터를 한 번에 가져가게 해주세요'라는 요구는 GeoServer 설정값 하나로 풀리지 않습니다. maxFeatures·startIndex 페이징의 실제 동작과 CSV·Shapefile처럼 공간 인덱스가 없는 스토어가 왜 같은 요청에서만 타임아웃을 내는지, 그리고 OGC API Features로 넘어가야 할 시점을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"외부 파트너사가 우리 WFS로 특정 시·군 전체 필지 데이터를 한 번에 내려받게 해주세요." GIS 데이터 제공 업무를 맡아본 사람이라면 한 번쯤 받아봤을 요구입니다. 처음 몇 달은 문제없이 돌아가다가, 어느 날 수십만 건짜리 레이어 하나가 WFS 요청마다 타임아웃을 냅니다. 2026년에도 GeoServer 포럼에는 "2.28.1에서 대용량 레이어만 WFS로 타임아웃 난다"는 글이 꾸준히 올라옵니다. 흥미로운 건 원인이 GeoServer 버전이나 설정이 아니라, 그 레이어가 공간 인덱스 없는 CSV 파일로 올라가 있었다는 데 있었다는 점입니다. 즉 "WFS가 느리다"는 증상 뒤에는 보통 서비스 계층이 아니라 데이터 스토어 선택 문제가 숨어 있습니다.

이 문제는 GeoServer 3.0(2026년 6월, 17년 만의 메이저 개편)이 나오고, OGC API Features가 WFS 1.0/1.1/2.0 옆에 정식 벡터 서비스로 나란히 올라오는 지금 시점에 다시 짚을 필요가 있습니다. 대용량 요청을 "어떻게 페이징할 것인가"와 "어느 프로토콜로 내보낼 것인가"는 서로 다른 질문이고, 둘 다 설계 판단이 필요합니다.

 

왜 같은 설정에서 어떤 레이어만 타임아웃이 나는가

GeoServer의 WFS maxFeatures는 안전장치가 아니라 응답 상한일 뿐입니다. 실제 대용량 제어는 startIndex와 count(WFS 2.0 기준)로 페이지를 나누는 것으로 합니다. 여기서 핵심은 스토어가 네이티브 정렬을 지원하는가입니다.

PostGIS·GeoPackage처럼 DB 기반 스토어는 sortBy 조건을 그대로 쿼리 플랜에 넘겨 인덱스로 OFFSET을 처리합니다. 페이지가 깊어져도 비용이 완만히 증가합니다. 반면 Shapefile·CSV처럼 네이티브 정렬이 없는 스토어는 GeoServer가 직접 병합정렬을 수행하는데, 이때 메모리에는 최대 1,000건만 유지하고 나머지는 디스크로 스필합니다. 깊은 페이지로 갈수록, 전체 건수가 늘수록 이 디스크 스필 비용이 기하급수적으로 불어납니다.

결론은 단순합니다: WFS 설정을 아무리 튜닝해도 스토어가 비인덱스 파일이면 한계가 명확합니다. 대용량 다운로드를 열어줘야 하는 레이어는 먼저 PostGIS나 GeoPackage로 옮기는 것이 선결 조건입니다.

 

OGC API Features로 넘어가야 하는가

OGC API Features는 WFS와 같은 데이터를 내보내지만 설계 철학이 다릅니다. WFS가 클라이언트가 startIndex·count를 직접 계산해 요청하는 "오프셋 기반" 방식이라면, OGC API Features는 응답에 next 링크를 포함해 클라이언트가 그 링크만 따라가게 하는 "커서에 가까운" 방식입니다. JSON(GeoJSON) 우선 설계라 범용 HTTP 클라이언트·에이전트 도구가 다루기도 더 쉽습니다.

다만 2026년 기준으로도 아직 완전히 성숙하진 않았습니다. GeoServer 2.28.2 릴리스 노트에는 OGC API Features 플러그인에서 CloseableIterator가 닫히지 않는 버그, 지원하지 않는 outputFormat을 WFS가 잘못 광고하던 버그 같은 수정 사항이 포함돼 있습니다. 핵심 조회 경로는 안정적이지만, 엣지 케이스에서 여전히 패치가 나오고 있는 단계입니다. "지금 당장 WFS를 완전히 걷어내도 되는가"에는 "아니오"에 가깝고, "신규 통합(특히 에이전트·범용 HTTP 클라이언트 대상)은 OGC API Features부터 검토해도 된다"가 현실적인 답입니다.

 

전체 시스템에서의 위치

눈여겨볼 지점은 GWC(GeoWebCache)가 이 경로에는 전혀 관여하지 않는다는 것입니다. GWC는 렌더링된 타일(WMS 출력)을 캐시하지, GetFeature가 뱉는 원시 벡터 피처 응답은 캐시 대상이 아닙니다. 그래서 "타일은 빠른데 데이터 다운로드만 느리다"는 증상이 흔히 나옵니다 — 두 경로가 완전히 분리돼 있기 때문입니다.

 

선택의 트레이드오프
방식 장점 단점
WFS 1.0/1.1 가장 널리 호환 깊은 오프셋에서 비인덱스 스토어는 비용 급증
WFS 2.0 sortBy로 순서 결정론 보장 여전히 오프셋 기반, 페이지 직접 관리
OGC API Features JSON 우선, next 링크, 에이전트 친화적 일부 엣지케이스 버그, 구형 클라이언트 미지원
전체 익스포트(ogr2ogr 등) 페이징 로직 불필요, 서버 부하 최소 실시간성 없음, 별도 배치 필요

 

실제 프로젝트 진행 순서

1. 대용량 다운로드를 열어줄 레이어의 백엔드부터 확인합니다. Shapefile·CSV라면 PostGIS나 GeoPackage로 먼저 이관합니다.
2. 정렬 키를 정합니다. sortBy에 쓸 안정적인 유니크 키가 없으면 페이지 순서가 흔들릴 수 있습니다.
3. 페이지 크기를 보수적으로 잡고 측정합니다. 500~2,000건 단위로 늘려가며 응답 시간을 봅니다.
4. 기존 WFS 경로는 유지한 채 OGC API Features를 병행 노출합니다.
5. 타임아웃·메모리 모니터링을 걸어 디스크 스필이 발생하는 레이어를 조기에 잡아냅니다.

 

예제 코드:

# WFS 2.0 페이징 요청 (PostGIS 기반 레이어, id로 정렬)
curl "https://geoserver.example.com/wfs?service=WFS&version=2.0.0&request=GetFeature&typeNames=parcels&count=1000&startIndex=2000&sortBy=id"

# OGC API Features 요청 (next 링크를 따라가는 방식)
curl "https://geoserver.example.com/ogc/features/collections/parcels/items?limit=1000"

 

주의 — maxFeatures 기본값을 믿지 말고 레이어별로 실제 운영 가능한 상한을 명시적으로 설정하세요. CSV·Shapefile 레이어에 대용량 WFS 요청이 들어올 가능성이 있다면, 서비스 노출 전에 반드시 PostGIS로 옮기는 것이 먼저입니다. OGC API Features 도입은 "WFS 대체"가 아니라 "신규 소비자용 추가 경로"로 접근하는 편이 2026년 기준 안전합니다.

 

정리

WFS 대용량 요청이 느려지는 진짜 원인은 대부분 서비스 설정이 아니라 데이터 스토어의 공간 인덱스 유무입니다. OGC API Features는 커서형 페이징과 JSON 우선 설계로 에이전트·범용 클라이언트에 유리하지만, 2026년에도 일부 버그 수정이 진행 중인 단계입니다. 대용량 다운로드를 설계할 때는 백엔드 이관 → 정렬 키 확정 → 페이지 크기 측정 → 신규 경로 병행 노출 순서로 접근하면 됩니다.
