재시도 버튼 두 번 누르면 결제도 두 번 — Spring에서 멱등성 키 실제 구현

2026. 8. 26. · 백엔드

한 줄 요약 — 네트워크 타임아웃 후 클라이언트가 재시도하면 서버에는 이미 처리된 요청이 다시 도착합니다. Spring에서 어노테이션 기반 인터셉터와 Redis로 멱등성 키를 실제로 구현하는 법을 정리했습니다.

 

타임아웃 후 재시도가 만드는 중복 처리

클라이언트가 결제 요청을 보냈는데 응답이 타임아웃됐다고 합시다. 실제로는 서버가 결제를 정상 처리했지만 응답 패킷이 유실됐을 뿐이라면, 클라이언트는 실패로 판단하고 같은 요청을 재시도합니다. 이 재시도가 서버에 다시 도달하면 결제가 두 번 일어납니다. 네트워크는 본질적으로 신뢰할 수 없고, 클라이언트의 재시도 로직은 이 사실을 전제로 짜여 있으므로 중복 요청을 걸러내는 책임은 결국 서버 API가 져야 합니다.

멱등성 키(Idempotency Key)는 클라이언트가 요청마다 고유한 키를 헤더에 실어 보내고, 서버는 같은 키로 온 요청을 두 번째부터는 처리하지 않고 첫 번째 결과를 그대로 돌려주는 방식으로 해결합니다.

 

핵심 개념 1 — 멱등성 키의 상태 전이

멱등성 키 하나는 "처리된 적 없음 → 처리 중 → 완료" 세 상태를 가집니다. 이 상태 전이를 원자적으로 관리하지 못하면, 같은 키로 온 두 요청이 동시에 처리를 시작하는 경쟁 조건이 생깁니다. Redis의 SETNX가 이 원자적 상태 전이에 적합합니다.

상태 의미 두 번째 요청의 동작
키 없음 처음 보는 요청 처리 시작, 키를 선점
처리 중 아직 처리되고 있음 409 Conflict
완료 응답이 저장됨 저장된 응답 반환

 

핵심 개념 2 — 키의 스코프와 만료 정책

멱등성 키는 "무엇을 기준으로 같은 요청인가"를 정확히 정의해야 실효성이 있습니다. 클라이언트가 보낸 키 값만으로 판단하면 다른 사용자가 우연히 같은 키를 보내는 경우까지 같은 요청으로 취급될 위험이 있어, 실무에서는 사용자ID + 엔드포인트 + 클라이언트 제공 키의 조합으로 네임스페이스를 나눠 저장합니다.

 

예제 — Spring AOP 인터셉터로 멱등성 처리
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface IdempotentRequest {
    long ttlSeconds() default 86400;
}

@Aspect
@Component
@RequiredArgsConstructor
public class IdempotencyAspect {

    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    @Around("@annotation(idempotentRequest)")
    public Object handle(ProceedingJoinPoint joinPoint,
                          IdempotentRequest idempotentRequest) throws Throwable {
        String idempotencyKey = extractHeaderKey();
        Long userId = getCurrentUserId();

        String redisKey = "idem:%d:%s:%s".formatted(
                userId, joinPoint.getSignature().getName(), idempotencyKey);

        Boolean acquired = redisTemplate.opsForValue().setIfAbsent(
                redisKey + ":lock", "1",
                Duration.ofSeconds(idempotentRequest.ttlSeconds()));

        if (Boolean.FALSE.equals(acquired)) {
            String cached = redisTemplate.opsForValue().get(redisKey + ":result");
            if (cached != null) {
                return objectMapper.readValue(cached, Object.class);
            }
            throw new ResponseStatusException(HttpStatus.CONFLICT, "처리 중입니다");
        }

        try {
            Object result = joinPoint.proceed();
            redisTemplate.opsForValue().set(redisKey + ":result",
                    objectMapper.writeValueAsString(result),
                    Duration.ofSeconds(idempotentRequest.ttlSeconds()));
            return result;
        } catch (Exception e) {
            redisTemplate.delete(redisKey + ":lock"); // 실패 시 락 해제
            throw e;
        }
    }
}

컨트롤러 메서드에는 @IdempotentRequest만 붙이면 됩니다. 처리 실패 시 락을 명시적으로 해제하는 부분이 중요합니다. 이걸 빼먹으면 일시적 오류로 실패한 요청도 TTL이 끝날 때까지 재시도가 막혀버립니다.

 

실무 도입 시 이것만은 챙기세요
1. 멱등성 키는 비멱등 메서드에만 적용하세요 — GET·PUT·DELETE는 프로토콜상 이미 멱등해야 하므로, 결제·주문 생성 같은 POST 요청에만 필요합니다.
2. 실패 응답 캐싱 여부를 정하세요 — 검증 오류(400)는 캐싱해도 되지만, 일시적 인프라 오류(503)까지 캐싱하면 진짜 재시도가 필요한 상황에서 문제가 됩니다.
3. 클라이언트에 키 생성 책임을 명확히 안내하세요 — 재시도 시마다 새 키를 생성하면 멱등성이 무의미해집니다. 같은 논리적 요청에는 같은 키를 재사용해야 합니다.

 

마무리 — 3줄 요약

① 네트워크는 신뢰할 수 없고 클라이언트 재시도는 필연적이므로, 중복 요청을 걸러내는 책임은 서버 API가 져야 합니다.
② Redis SETNX로 처리 중 상태를 원자적으로 선점하고, 실패 시 락을 명시적으로 해제해야 정상적인 재시도까지 막지 않습니다.
③ 멱등성 키는 사용자ID+엔드포인트+클라이언트 키로 스코프를 나누고, TTL과 실패 응답 캐싱 여부를 도메인에 맞게 정해야 합니다.
