"우리 서비스는 Deno로 돌아가고 있는데요" — 런타임 개발 중단 공지 앞에서 마이그레이션 여부를 판단하는 법

실무 스택

한 줄 요약 — Deno 팀이 Cloudflare에 합류하며 독자 런타임 개발을 1년 뒤 종료하기로 한 공지 앞에서, Deno 기반 서비스가 지금 당장 뭘 해야 하는지와 런타임 마이그레이션 여부를 가르는 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"우리 백엔드, Deno로 짰는데 괜찮나요?" 이 질문에 최근까지는 "Node 대비 기본 보안 샌드박스, TypeScript 네이티브 지원이 강점"이라고 답하면 충분했습니다. 그런데 Deno 팀이 Cloudflare에 합류하면서, 독자적인 Deno 런타임 개발을 1년간의 유지보수 기간 이후 종료하고 Deno Deploy도 그로부터 6개월 뒤 서비스를 종료한다는 공지가 나왔습니다. 복수의 소식통이 같은 내용을 전하고 있어 신뢰도가 낮은 루머는 아닙니다.

이건 단순히 "한 런타임이 사라진다"는 뉴스가 아니라, 빌더에게 실제 실행 과제를 던지는 사건입니다. 이미 Deno로 서비스를 운영 중이라면 당장 마이그레이션 로드맵을 짜야 하는지 판단해야 하고, 지금 새 프로젝트의 런타임을 고르는 입장이라면 이 사건 자체가 선택 기준에 새 변수를 추가합니다. 중요한 건 패닉이 아니라, 우리 서비스의 Deno 의존도와 남은 유지보수 기간을 놓고 실제로 지금 움직여야 하는지를 계산하는 것입니다.

 

전체 시스템에서의 위치

이 판단은 런타임 하나를 바꾸는 일처럼 보이지만, 실제로는 서비스 스택 전체를 관통합니다. 런타임은 애플리케이션 코드와 OS·클라우드 인프라 사이에 있는 실행 계층입니다. 여기가 바뀌면 패키지 생태계 호환성(npm 호환 레이어 차이), 배포 파이프라인(Deno Deploy 전용 설정), 내장 API 사용 범위(Deno 고유 API), 모니터링·로깅 연동까지 전부 영향을 받습니다.

즉 "런타임만 바꾸면 된다"는 생각은 틀렸습니다. 런타임 교체는 배포 인프라 교체, 의존성 호환성 재검증, 플랫폼 고유 API를 범용 API로 재작성하는 작업을 동시에 요구하는 시스템 전반의 변경입니다.

핵심은 "Deno 런타임 개발이 1년 뒤 끝난다"가 "내일 당장 서비스가 멈춘다"를 의미하지 않는다는 점입니다. 유지보수 기간과 Deploy 유예 기간이 남아 있으므로, 당장 올인 마이그레이션을 할 필요는 없습니다. 다만 신규 기능을 Deno 고유 API에 계속 묶어두는 선택은 이제 명백히 기술부채를 늘리는 결정이 됐습니다.

 

실제 프로젝트 진행 순서

1) Deno 고유 API 직접 호출, Deploy 전용 설정이 코드베이스에 얼마나 퍼져 있는지 정량화합니다.
2) Deno Deploy에 직접 묶인 부분부터 분리합니다 — 컨테이너 기반 배포로 먼저 바꿔두면 런타임 교체는 나중으로 미뤄도 급하지 않습니다.
3) 신규 코드는 Deno 고유 API 대신 Web 표준 API(fetch, Request/Response 등)로 작성하도록 가이드를 바꿉니다.
4) 팀의 TypeScript 의존도와 npm 패키지 사용 범위를 보고 Bun 또는 Node LTS 중 전환 대상을 고릅니다.
5) 1년의 유지보수 기간을 마감일이 아니라 단계적 전환의 여유로 활용합니다.

 

주의 — "아직 1년 남았으니 괜찮다"와 "1년 동안 아무것도 안 해도 된다"는 다른 말입니다. 유지보수 기간은 보안 패치만 들어오는 기간이지, 새 기능이 계속 추가되는 기간이 아닙니다. 단일 벤더 런타임을 고를 때는 항상 "이 벤더의 전략이 바뀌면 어떻게 되는가"를 설계에 넣어야 합니다.

 

정리

Deno 팀의 Cloudflare 합류와 독자 런타임 개발 종료 공지는 Deno 기반 서비스에 즉각적인 위기가 아니라 계획된 전환 유예 기간을 줍니다. 런타임 교체는 배포 인프라·패키지 호환성·플랫폼 고유 API까지 함께 바뀌는 시스템 전반의 변경이므로, 전면 마이그레이션보다 Deploy 의존 분리와 Web 표준 API로의 신규 코드 전환을 먼저 시작하는 것이 현실적입니다.
