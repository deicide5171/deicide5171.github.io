새 프로젝트에 Redux부터 까는 습관, 이제는 버려야 할까 — 상태관리 선택 기준

2026. 8. 26. · 프론트엔드

한 줄 요약 — 지금 중요한 질문은 "Zustand냐 Redux냐"가 아니라 "이 상태는 애초에 어떤 종류의 상태인가"입니다. 상태 분류부터 Zustand·Jotai·Redux Toolkit 선택 기준까지 정리했습니다.

 

모든 상태를 한 스토어에 넣던 시절

새 React 프로젝트를 시작할 때 "상태관리 라이브러리는 뭘 쓰죠?"라는 질문에 예전에는 관성적으로 Redux가 답이었습니다. 지금은 선택지가 늘었을 뿐 아니라, 애초에 "전역 상태관리 라이브러리 하나로 모든 상태를 관리한다"는 전제 자체가 낡은 접근이 됐습니다. 서버에서 가져온 데이터, UI 로컬 상태, 진짜 전역 클라이언트 상태는 성격이 완전히 다른데도 예전에는 이걸 다 Redux 스토어 하나에 욱여넣었습니다.

 

핵심 개념 1 — 상태를 먼저 종류별로 나눕니다
상태 종류 특징 적합한 도구
서버 상태 서버가 원본, 캐시·재검증 필요 TanStack Query, SWR
UI 로컬 상태 컴포넌트 하나에만 필요 useState, useReducer
클라이언트 전역 상태 여러 트리에서 공유 Zustand, Jotai, Redux Toolkit

서버 상태를 전역 스토어에 직접 넣고 로딩·에러·캐시 무효화를 손으로 관리하던 시절의 패턴은, TanStack Query 같은 서버 상태 전용 라이브러리가 대신해주면서 대부분 사라졌습니다. 그 결과 진짜로 클라이언트에서만 존재하는 상태(로그인 여부, 테마, 사이드바 열림 상태 등)만 남았습니다.

 

핵심 개념 2 — 남은 전역 상태를 무엇으로 관리할까
구분 Zustand Jotai Redux Toolkit
모델 단일 스토어 원자(atom) 조합 스토어+액션/리듀서
보일러플레이트 매우 적음 적음 여전히 구조 필요
적합한 규모 중소~중대형, 빠른 도입 세분화 리렌더 중요한 대시보드 액션 이력·감사 중요한 대형 앱

 

예제 — 같은 요구사항을 Zustand와 Redux Toolkit으로
// Zustand — 스토어 생성과 사용이 한 파일에서 끝난다
import { create } from 'zustand';

const useCartStore = create((set) => ({
  items: [],
  addItem: (item) => set((state) => ({ items: [...state.items, item] })),
  clear: () => set({ items: [] }),
}));

function CartBadge() {
  const itemCount = useCartStore((state) => state.items.length);
  return <span>{itemCount}</span>;
}
// Redux Toolkit — 슬라이스 정의, 스토어 등록, Provider 연결이 각각 필요
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    addItem: (state, action) => { state.items.push(action.payload); },
    clear: (state) => { state.items = []; },
  },
});

export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

같은 기능이라도 Redux Toolkit 쪽이 세 단계를 거쳐야 합니다. 이 차이가 작은 프로젝트에서는 부담이지만, 팀 규모가 커지고 액션 흐름을 명시적으로 추적해야 하는 조직에서는 오히려 이 명시성이 유지보수 이점으로 작용합니다.

 

실무 도입 시 이것만은 챙기세요
1. 서버 상태를 전역 스토어에 넣지 마세요 — API 응답을 스토어에 그대로 저장하고 캐시 무효화를 손으로 짜는 패턴은 대부분 TanStack Query로 대체하는 게 낫습니다.
2. 라이브러리 교체보다 상태 분류가 먼저입니다 — "상태관리가 복잡하다"는 불만은 대개 서버·전역·로컬 상태가 뒤섞여 있다는 신호입니다.
3. 팀 관례와 디버깅 요구를 무시하지 마세요 — Redux DevTools 기반 프로세스가 자리 잡은 조직이라면 전환 비용이 기술적 이득보다 클 수 있습니다.

 

마무리 — 3줄 요약

① 상태관리 도구를 고르기 전에 서버 상태·UI 로컬 상태·클라이언트 전역 상태를 먼저 구분해야 합니다.
② Zustand는 빠른 도입, Jotai는 세분화된 리렌더 최적화, Redux Toolkit은 성숙한 디버깅·감사 생태계가 강점입니다.
③ "상태관리가 복잡하다"는 불만은 대부분 도구 문제가 아니라 상태 분류가 안 된 신호이며, 도구 교체보다 분류가 우선입니다.
