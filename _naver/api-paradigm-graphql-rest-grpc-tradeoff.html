2026. 8. 28. · 시스템 설계

한 줄 요약 — 새 서비스의 API 패러다임을 정할 때 REST·GraphQL·gRPC 중 무엇을 고를지, 클라이언트 다양성과 성능·스키마 강제력이라는 세 가지 축으로 선택 기준을 정리했습니다.

 

되돌리기 비용이 큰 초반 결정

새 서비스를 설계할 때 API 패러다임 선택은 초반에 결정되고 나면 되돌리기 비용이 큰 결정 중 하나입니다. REST로 시작한 API를 나중에 GraphQL로 바꾸려면 클라이언트 코드 전체를 다시 짜야 하고, gRPC로 만든 내부 서비스를 외부 공개 API로 노출하려면 처음부터 다시 설계해야 하는 경우가 많습니다.

REST는 단순함과 생태계 성숙도를, GraphQL은 클라이언트가 필요한 필드만 요청할 수 있는 유연성을, gRPC는 강타입 스키마와 HTTP/2 기반 성능을 각각 우선합니다.

 

핵심 개념 1 — 클라이언트가 다양한가, 단일한가

모바일, 웹, 여러 서드파티가 저마다 다른 필드 조합을 필요로 하는 공개 API라면 GraphQL이 정확히 맞습니다. 반대로 클라이언트가 소수이고 예측 가능하다면(내부 마이크로서비스 간 통신 등) GraphQL의 유연성은 실익보다 복잡도 비용이 큽니다.

핵심 개념 2 — 오버/언더페칭 vs N+1 vs 강타입 계약
기준 REST GraphQL gRPC
데이터 유연성 낮음 높음 낮음
대표 약점 오버/언더페칭 N+1 쿼리 강결합, 브라우저 비친화적
적합한 상황 공개 API, 단순 CRUD 다양한 클라이언트 내부 고성능 통신

 

 

핵심 개념 3 — 캐싱 전략의 차이

REST는 URL이 캐시 키 역할을 해 HTTP 캐싱을 그대로 활용할 수 있습니다. GraphQL은 같은 엔드포인트로 서로 다른 쿼리가 들어와 URL 기반 캐싱이 통하지 않으므로 클라이언트 쪽 정규화 캐시가 필요합니다. gRPC는 스트리밍까지 포함한 다양한 통신 패턴을 지원해 애플리케이션 레벨 캐싱이 기본 전제입니다.

예제 — 같은 요구사항을 세 패러다임으로
# REST: 게시글과 작성자를 함께 보려면 두 번 호출
GET /posts/42          -> { id, title, body, authorId }
GET /users/7           -> { id, name, email }
# GraphQL: 필요한 필드만 한 번의 쿼리로
query {
  post(id: 42) {
    title
    author { name }
  }
}

GraphQL 예제의 N+1 문제는 DataLoader 같은 배치·캐싱 유틸리티로 리졸버 호출을 모아 한 번의 배치 쿼리로 묶어 해결하는 것이 표준적인 접근입니다.

 

실무 도입 시 이것만은 챙기세요
1. 하나의 패러다임만 고집할 필요는 없습니다 — 외부 공개 API는 GraphQL, 내부 통신은 gRPC, 단순 웹훅은 REST처럼 혼용이 흔합니다.
2. GraphQL 도입 시 N+1과 쿼리 복잡도 제한은 필수입니다 — DataLoader 없이 프로덕션에 올리면 성능 문제를 겪습니다.
3. gRPC는 브라우저 직접 호출을 전제하지 마세요 — grpc-web 프록시나 별도 게이트웨이가 필요합니다.

 

마무리 — 3줄 요약

① REST는 단순함, GraphQL은 필드 선택 유연성, gRPC는 강타입 성능이 각각의 최우선 가치입니다.
② 세 패러다임은 각기 다른 구조적 약점을 가지므로 선택은 트레이드오프 인식 위에서 이뤄져야 합니다.
③ 내부 서비스는 gRPC, 다양한 외부 클라이언트는 GraphQL, 단순 CRUD는 REST처럼 계층별 혼용이 현실적입니다.
