API 인증 전략 완전 비교 — OAuth2 vs JWT vs 세션, 언제 무엇을 써야 할까

2026. 8. 17. · 백엔드

한 줄 요약 — OAuth2, JWT, 세션은 같은 층위의 대안이 아닙니다. 세 방식의 실제 동작 원리와 상황별 선택 기준을 정리했습니다.

 

왜 이 세 개념이 자꾸 섞일까요

API 인증을 설계할 때 "JWT 쓸까 세션 쓸까", "OAuth2 도입해야 하나" 같은 질문이 팀 안에서 자주 반복됩니다. 그런데 이 셋은 같은 층위의 대안이 아닙니다. 세션과 JWT는 "사용자가 누구인지를 요청마다 어떻게 증명할 것인가"에 대한 답이고, OAuth2는 애초에 "제3자 애플리케이션에게 내 리소스에 대한 제한된 권한을 어떻게 위임할 것인가"를 다루는 인가(authorization) 프레임워크입니다. 인증(authentication) 용도로 OAuth2를 쓰려면 그 위에 OpenID Connect(OIDC) 계층을 얹어야 합니다.

이 구분이 흐려지면 "소셜 로그인 붙였으니 인증은 끝났다"거나 "JWT는 무조건 최신 방식이라 세션보다 낫다" 같은 오해로 이어집니다. 실제로는 셋 다 지금도 각자의 자리에서 널리 쓰이고 있고, 선택 기준은 유행이 아니라 서버 아키텍처, 클라이언트 형태, 토큰 폐기·감사 요구사항입니다.

 

개념도: 인증 방식별 흐름 비교

 

핵심 개념: 세션 · JWT · OAuth2

세션은 로그인 성공 시 서버가 세션을 생성해 서버 측 저장소(메모리, Redis 등)에 사용자 상태를 보관하고, 클라이언트에는 세션ID만 쿠키로 내려주는 방식입니다. 요청마다 서버가 저장소를 조회해야 하는 stateful 구조입니다.

JWT는 사용자 정보와 만료 시각 등을 담은 클레임을 서버가 서명해 발급하는 토큰입니다. 클라이언트가 매 요청의 Authorization 헤더에 토큰을 실어 보내면 서버는 서명만 검증하면 되므로 별도 저장소 조회가 필요 없는 stateless 구조입니다.

OAuth2는 로그인 자체가 아니라 제3자 서비스에게 제한된 권한을 위임하는 표준입니다. 흔히 말하는 "OAuth2로 로그인"은 대부분 OAuth2 위에 신원 증명 계층을 얹은 OIDC를 쓰는 것으로, 접근 권한을 나타내는 access token과 별도로 신원 정보를 담은 ID 토큰이 함께 발급됩니다.

 

비교표: 언제 무엇을 쓸까요
기준 세션 JWT OAuth2(+OIDC)
해결하는 문제 자체 서비스 로그인 상태 유지 자체 서비스 로그인 상태 유지(무상태) 제3자 위임·소셜 로그인
서버 상태 필요(세션 스토어) 불필요 인가 서버가 상태 보유
즉시 무효화 쉬움(세션 삭제) 어려움(블랙리스트 필요) 인가 서버의 토큰 폐기에 의존
수평 확장 세션 공유 인프라 필요 공유 상태 없이 확장 용이 별도 인가 서버 인프라 필요
적합한 상황 단일 서비스, 전통적 웹 앱 MSA, 모바일 API, 서버 간 인증 소셜 로그인, 제3자 API 연동, SSO

 

예제: JWT 검증 필터 구조 (Java, Spring Security)

JWT 방식에서는 요청이 들어올 때마다 토큰의 서명만 검증하면 됩니다. 세션 저장소를 조회하지 않기 때문에 서버를 여러 대로 늘려도 별도의 상태 공유가 필요 없습니다.

public class JwtAuthFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                     FilterChain chain) throws ServletException, IOException {
        String token = extractBearerToken(req);
        if (token != null && jwtValidator.isValid(token)) {
            Claims claims = jwtValidator.parseClaims(token);
            var auth = new UsernamePasswordAuthenticationToken(
                claims.getSubject(), null, mapAuthorities(claims));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res); // DB·세션 저장소 조회 없이 서명 검증만으로 통과
    }
}

 

실무 도입 시 이것만은 챙기세요
1. JWT 만료 시간은 짧게, 갱신은 refresh token으로 — access token은 짧게 만료시키고 refresh token으로 재발급하는 구조가 유출 피해를 줄입니다.
2. 즉시 로그아웃이 중요하면 순수 JWT만으로는 부족 — 세션처럼 즉시 무효화하려면 블랙리스트를 함께 두거나 세션 기반이 더 단순할 수 있습니다.
3. OAuth2/OIDC는 직접 구현하지 말 것 — authorization code, PKCE, 리다이렉트 URI 검증 등 세부 사양이 많아 직접 구현 시 취약점이 생기기 쉽습니다.
4. 혼합 전략이 흔합니다 — 브라우저는 세션, 서버 간·모바일 API는 JWT, 소셜 로그인 진입점만 OAuth2/OIDC로 처리하는 조합이 실제로 많이 쓰입니다.

 

마무리 — 3줄 요약

① 세션과 JWT는 같은 문제(자체 로그인 상태 유지)에 대한 stateful·stateless 두 해법이고, OAuth2는 애초에 제3자 위임 인가를 위한 별개의 표준입니다.
② 즉시 로그아웃·감사가 중요하면 세션이, 수평 확장·서버 간 인증이 중요하면 JWT가 유리하며 정답은 상황에 따라 갈립니다.
③ OAuth2로 "로그인"을 구현하려면 OIDC 계층이 필요하고, 세부 구현은 직접 만들기보다 검증된 라이브러리를 쓰는 것이 안전합니다.
