왜 지금 이 주제인가

이 블로그는 Flutter 앱 개발에서 시작해 네이버 클라우드 지도 API, PostGIS 공간 데이터, AI 에이전트 프로토콜, 분산 시스템, Docker와 CI/CD 파이프라인, DB 인덱스 내부 구조, 테스트 피라미드, 네트워크 심화, 웹 애플리케이션 보안까지 폭넓은 주제를 추천 지식 시리즈로 다뤄왔습니다. 돌이켜보면 "무언가를 만든다 → 데이터를 저장하고 조회한다 → 안전하게 배포한다 → 신뢰할 수 있게 검증한다 → 네트워크로 연결하고 지킨다"는 흐름을 순서대로 밟아온 셈입니다.

그런데 이 모든 글에서 은근히 당연하게 취급하고 넘어간 질문이 하나 있습니다. 바로 "그 데이터를 메모리 안에서 어떤 구조로 들고 있을 것인가"입니다. DB 인덱스 글에서 B-Tree를 다뤘지만, 자동완성 기능에서 문자열 접두사를 빠르게 찾는 구조나, 대량의 캐시를 메모리 안에서 효율적으로 유지하는 구조, 수십억 건의 존재 여부를 아주 적은 메모리로 확인하는 구조는 아직 다루지 않았습니다.

그래서 이번 글에서는 이 시리즈의 마지막 추천 지식으로 트라이(Trie), 스킵리스트(Skip List), LRU 캐시 구현, Bloom Filter 같은 "실무에서 실제로 쓰이는 자료구조 심화"를 다룹니다. 이론으로만 배우고 지나가기 쉬운 주제들이지만, 지금까지 쌓아온 백엔드·인프라·네트워크·보안 지식 위에 얹으면 왜 특정 시스템이 그렇게 설계되었는지가 훨씬 선명하게 보입니다.

핵심 개념: 트라이와 Bloom Filter

트라이는 문자열 집합을 트리 형태로 저장해, 각 노드가 문자 하나에 대응하는 자식을 갖는 구조입니다. 검색할 때 문자를 한 글자씩 따라 내려가기만 하면 되므로, 검색 대상 문자열 개수와 무관하게 입력한 접두사 길이에 비례하는 시간만 걸립니다. 검색창 자동완성, IP 라우팅 테이블의 최장 접두사 매칭, 사전 기반 맞춤법 검사기가 대표적인 활용 사례입니다.

Bloom Filter는 "이 값이 집합에 있을 수도 있다" 또는 "확실히 없다"만 답하는 확률적 자료구조입니다. 비트 배열과 여러 개의 해시 함수로 구성되며, 원소를 넣을 때마다 여러 해시 값 위치의 비트를 1로 세팅합니다. 조회 시 비트가 하나라도 0이면 확실히 없는 것이고, 모두 1이면 있을 가능성이 있다고 판단합니다. 오탐은 있지만 미탐은 없다는 특성 덕분에 캐시 미스 판별이나 악성 URL 사전 필터링에 널리 쓰입니다.

 

예제: Python으로 구현한 간단한 LRU 캐시
class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = {}
        self.order = []

    def get(self, key):
        if key not in self.cache:
            return -1
        self.order.remove(key)
        self.order.append(key)
        return self.cache[key]

    def put(self, key, value):
        if key in self.cache:
            self.order.remove(key)
        elif len(self.cache) >= self.capacity:
            oldest = self.order.pop(0)
            del self.cache[oldest]
        self.cache[key] = value
        self.order.append(key)

이 구현은 이해를 돕기 위해 리스트로 순서를 관리했지만, list.remove는 O(n)이라 실무 성능이 나오지 않습니다. 실제로는 OrderedDict나, 해시맵과 이중 연결 리스트를 직접 조합해 조회와 삽입 모두 상수 시간으로 만드는 것이 표준적인 접근입니다.

 

실무 도입 시 이것만은 챙기세요
1. 트라이는 메모리를 많이 먹습니다 — 자식 노드를 해시맵으로 구현하거나 압축 트라이(radix tree)를 쓰면 메모리 사용량을 줄일 수 있습니다
2. LRU만이 정답은 아닙니다 — 접근 빈도가 중요하면 LFU, 스캔 패턴이 섞이면 LRU-K나 ARC 같은 변형 정책이 더 적합할 수 있습니다
3. Bloom Filter 크기 설계가 핵심입니다 — 비트 배열 크기와 해시 함수 개수를 예상 원소 수·허용 오탐률에 맞춰 계산해야 합니다
4. 기존 라이브러리를 먼저 확인하세요 — Redis의 BF.ADD, Guava의 BloomFilter, Java의 LinkedHashMap 기반 LRU 등 검증된 구현이 이미 있는 경우가 많습니다
