블로킹 코드 한 줄이 스레드 풀을 멈춘다 — Spring WebFlux 함정과 디버깅

2026. 8. 29. · 백엔드

한 줄 요약 — WebFlux의 소수 이벤트 루프 스레드에서 블로킹 호출 하나가 발생하면 그 스레드가 담당하던 모든 요청이 함께 멈추므로, 블로킹 코드는 반드시 별도 스케줄러로 격리해야 합니다.

 

"리액티브니까 빠를 것"이라는 착각

Spring MVC에서 WebFlux로 넘어가는 팀이 흔히 겪는 착각이 있습니다. 리액티브니까 당연히 빠를 것이라는 기대입니다. 실제로는 WebFlux를 도입한 뒤 처리량이 오히려 떨어지거나 알 수 없는 지연이 간헐적으로 발생하는 사례가 드물지 않습니다. 원인은 대부분 "이벤트 루프 스레드에서는 절대 블로킹해서는 안 된다"는 규칙을 어딘가에서 어겼기 때문입니다.

 

핵심 개념 1 — 스레드 모델의 근본적 차이

Spring MVC(Tomcat)는 요청마다 스레드 하나를 할당합니다. WebFlux(Netty)는 정반대로, CPU 코어 수에 맞춘 소수의 이벤트 루프 스레드가 매우 많은 요청을 논블로킹 I/O로 동시에 처리합니다. I/O 작업을 시작해두고 결과가 오면 콜백으로 이어받는 식이라 스레드가 기다리며 노는 시간이 없습니다.

 

핵심 개념 2 — 블로킹 호출 하나가 전체를 멈춥니다

적은 수의 이벤트 루프 스레드 중 하나가 블로킹 호출(동기 JDBC, Thread.sleep() 등)을 만나 멈추면, 그 스레드가 처리하던 다른 모든 요청까지 함께 멈춥니다. 개발 환경에서는 문제없어 보이다가, 운영에서 동시 요청이 몰리면 응답 시간이 갑자기 치솟는 형태로 나타나 원인 파악이 늦어지기 쉽습니다.

// 잘못된 예 - 이벤트 루프 스레드에서 블로킹 JDBC 실행
public Mono<Report> getReport(String id) {
    return Mono.fromCallable(() -> legacyJdbcRepository.findById(id))
               .map(this::toReport);
}

// 수정 - 블로킹 전용 스레드 풀로 옮김
public Mono<Report> getReportFixed(String id) {
    return Mono.fromCallable(() -> legacyJdbcRepository.findById(id))
               .subscribeOn(Schedulers.boundedElastic())
               .map(this::toReport);
}

 

핵심 개념 3 — 끊긴 스택 트레이스와 디버깅

리액티브 체인에서는 연산자마다 실행 스레드가 바뀌고 콜백이 비동기로 실행되기 때문에, 스택 트레이스가 예외가 조립된 체인의 원래 위치를 보여주지 못하는 경우가 흔합니다. Project Reactor는 Hooks.onOperatorDebug()나 ReactorDebugAgent로 조립 위치를 스택 트레이스에 덧붙일 수 있지만, 성능 오버헤드가 있어 문제 재현 시 임시로 활성화하는 것이 일반적입니다.

구분 Spring MVC Spring WebFlux
스레드 모델 요청당 스레드 할당 소수 이벤트 루프 + 논블로킹
블로킹 호출 영향 해당 요청만 지연 이벤트 루프 전체 지연 가능
블로킹 코드 처리 기본 동작과 호환 boundedElastic로 명시적 격리

 

실무 도입 시 이것만은 챙기세요
1. 레거시 블로킹 라이브러리 경계를 명확히 표시하세요 — 코드 리뷰 단계에서 이 호출은 블로킹인가를 체크리스트화하세요.
2. BlockHound 같은 도구로 블로킹 호출을 자동 탐지하세요 — 테스트 환경에 통합해두면 배포 전에 실수를 잡아낼 수 있습니다.
3. WebFlux 전면 도입 전 I/O 스택 전체를 점검하세요 — R2DBC, WebClient로 전체 스택을 일관되게 맞추는 것이 전제조건입니다.

 

마무리 — 3줄 요약

① WebFlux는 소수 이벤트 루프 스레드가 논블로킹 I/O로 많은 요청을 처리하는 모델이라 블로킹 하나가 전체를 지연시킵니다.
② 블로킹 호출은 반드시 Schedulers.boundedElastic()으로 명시적으로 옮겨야 합니다.
③ 리액티브 체인은 스택 트레이스가 끊기기 쉬워 Hooks.onOperatorDebug()나 BlockHound 같은 도구가 중요해집니다.
