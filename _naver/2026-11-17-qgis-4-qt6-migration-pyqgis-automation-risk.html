"QGIS로 돌리던 사내 공간 데이터 야간 배치, 최신 버전으로 그냥 올리면 되나요" — QGIS 4.0 Qt6 전환이 PyQGIS 자동화를 깨뜨리는 지점

GIS

한 줄 요약 — QGIS 4.0은 Qt5에서 Qt6로의 전면 전환이며, 영향은 QGIS 자체보다 그 위의 PyQGIS 플러그인·Processing 스크립트에서 먼저 드러납니다. 사람이 지켜보는 대화형 플러그인보다 아무도 보지 않는 야간 배치부터 먼저 검증해야 하는 이유를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"공장 부지 분석에 쓰던 QGIS 사내 자동화, 야간에 Processing 스크립트로 돌아가는데 최신 버전으로 그냥 올려도 되나요"라는 요구는 QGIS 4.0이 2026년 3월 정식 출시되면서 실제로 자주 들어오기 시작했습니다. 겉보기엔 버전 번호가 하나 올라가는 일처럼 보이지만, 핵심은 GUI 프레임워크 자체를 Qt5에서 Qt6로 통째로 옮긴 것입니다. QGIS 개발팀 스스로 "Qt6 전환과 직접 관련된 범위에서만" 호환성 깨짐을 허용했다고 밝힐 만큼 구조적인 변화입니다.

문제는 이 전환이 PyQGIS 플러그인·스크립트 쪽에서 먼저 드러난다는 점입니다. Qt를 직접 import하는 플러그인은 API 차이로 깨질 수 있고, 사람이 화면을 보는 대화형 플러그인은 깨지면 바로 눈에 띄지만 새벽에 도는 배치 스크립트는 몇 주 뒤에야 뒤늦게 발견됩니다.

 

전체 시스템에서의 위치

QGIS는 원천 공간 데이터와 사내 자동화 사이에 놓인 오케스트레이션 레이어입니다. 데이터 흐름 자체는 바뀌지 않지만, QGIS와 PyQGIS 스크립트·플러그인 사이의 Qt 경계가 바뀝니다. QGIS 공식 API만 쓰는 배치 스크립트는 상대적으로 안전하지만, Qt 위젯을 직접 그리는 코드는 거의 예외 없이 손봐야 합니다.

 

선택의 트레이드오프
선택지받는 것치러야 하는 것
3.44 LTR 유지(Qt5)안정성신기능 못 씀, 지원 종료 다가옴
4.0 즉시 전환(Qt6)신기능, LTR 라인 선점플러그인 전수 수정 필요
두 버전 병행리스크 점진 분산운영 복잡도 2배

 

가장 흔한 실수는 "데스크톱에서 플러그인 몇 개 열어보고 잘 뜨길래 넘어갔다"고 안심하는 것입니다. 대화형 플러그인이 잘 뜨는 것과 headless 배치가 끝까지 정상 종료되는 것은 전혀 다른 검증입니다.

 

실제 프로젝트 진행 순서

가장 먼저 플러그인·스크립트 인벤토리를 만들고, Qt를 직접 import하는지 QGIS 공식 API만 쓰는지 분류합니다.

grep -rl "from PyQt5" plugins/ scripts/
grep -rl "from qgis.PyQt" plugins/ scripts/

분류가 끝나면 대화형 플러그인보다 야간 배치·headless 스크립트부터 먼저 4.0 환경에서 돌려봅니다. 산출물 레이어가 기대한 형태로 나오는지 결과물 기준으로 확인하고, Qt 직접 import 플러그인은 import 구문을 1차로 정리한 뒤 동작까지 반드시 수동으로 재확인합니다.

 

주의 — Processing 2.x GUI API에 의존하는 코드는 지금 당장 깨지지 않더라도 이번 전환 범위에 포함시키세요. QGIS 개발팀이 향후 4.x 라인에서 걷어내겠다고 이미 예고했으므로, 지금 미뤄봐야 다음에 같은 마이그레이션을 반복하게 됩니다.
