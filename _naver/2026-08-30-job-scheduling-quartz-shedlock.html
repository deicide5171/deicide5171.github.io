@Scheduled를 인스턴스 3대에 붙이면 3번 실행된다 — Quartz vs ShedLock 분산 스케줄링

백엔드

한 줄 요약 — Spring @Scheduled는 인스턴스마다 독립적으로 도는 로컬 스케줄러라, 여러 인스턴스로 스케일아웃하면 배치가 중복 실행됩니다. Quartz 클러스터 모드와 ShedLock의 접근 차이와 선택 기준을 정리했습니다.

 

스케일아웃하는 순간 배치가 세 번 실행됩니다

Spring Boot 애플리케이션에 @Scheduled(cron = "0 0 3 * * *")로 새벽 3시 정산 배치를 붙여두고 인스턴스를 1대에서 3대로 스케일아웃하면, 그 배치는 하루아침에 세 번 실행되는 잡이 됩니다. @Scheduled는 애플리케이션 컨텍스트 안의 로컬 스레드 스케줄러일 뿐이라 인스턴스 간에 아무런 조율이 없기 때문입니다. 정산·알림 발송·리포트 메일처럼 부작용이 있는 배치는 중복 실행 자체가 장애입니다.

이 문제를 푸는 접근은 크게 두 갈래입니다. 스케줄링 자체를 클러스터 인식 구조로 다시 설계하는 Quartz 클러스터 모드, 그리고 기존 코드는 그대로 두고 실행 앞뒤에 분산 락만 얇게 씌우는 ShedLock입니다.

 

핵심 개념 1 — Quartz 클러스터 모드: 스케줄러 자체가 분산을 압니다

Quartz는 원래부터 클러스터 환경을 염두에 두고 설계된 엔터프라이즈 스케줄링 프레임워크입니다. 클러스터 모드에서는 모든 인스턴스가 같은 데이터베이스를 바라보고, 트리거가 발화할 시점이 되면 각 인스턴스가 그 잡을 획득하려고 DB 락 경쟁을 벌입니다. 락을 획득한 인스턴스만 실제로 잡을 실행하고 나머지는 자동으로 건너뜁니다.

대신 Quartz는 잡, 트리거, 실행 이력을 저장하는 전용 테이블 세트를 DB에 만들어야 하고, 잡 정의를 등록하는 방식이 애노테이션 하나 붙이는 것보다 번거롭습니다. 미스파이어 처리 정책, 잡 우선순위, 잡 체이닝처럼 정교한 스케줄링 요구가 있는 조직에는 이 투자가 값어치를 하지만, 단순히 중복 실행만 막고 싶다는 요구에는 과할 수 있습니다.

 

핵심 개념 2 — ShedLock: 기존 스케줄러에 분산 락만 얹습니다

ShedLock은 스케줄러를 대체하지 않고, 이미 쓰고 있는 @Scheduled 메서드 위에 @SchedulerLock 애노테이션 하나를 추가하는 방식으로 동작합니다. 각 인스턴스가 여전히 독립적으로 메서드를 호출하려 시도하지만, 실행 직전에 공유 저장소에서 락을 획득하려 시도하고 락을 얻은 인스턴스만 실제 로직을 실행합니다.

구분 Quartz 클러스터 모드 ShedLock
접근 방식 스케줄러 자체를 클러스터 인식으로 교체 기존 스케줄러 위에 락만 추가
기존 코드 변경 Quartz Job 형태로 재작성 애노테이션 한 줄 추가
적합한 상황 복잡한 잡 체이닝·우선순위 단순 중복 실행 방지

 

핵심 개념 3 — 락 획득 실패는 대기가 아니라 스킵입니다

두 방식 모두에서 반드시 이해해야 할 공통점이 있습니다. 락을 획득하지 못한 인스턴스는 락이 풀릴 때까지 기다렸다가 실행하는 게 아니라 그 회차 실행 자체를 건너뜁니다. ShedLock에서는 lockAtLeastFor(실행이 너무 빨리 끝나 다른 인스턴스가 곧바로 재획득하는 것을 방지)와 lockAtMostFor(락을 쥔 인스턴스가 죽었을 때 영원히 안 풀리는 것을 막는 안전장치)라는 두 파라미터로 이 시간 창을 명시적으로 설정해야 합니다.

 

 

예제 — ShedLock 설정
@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "10m")
public class SchedulerConfig {
    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
                JdbcTemplateLockProvider.Configuration.builder()
                        .withJdbcTemplate(new JdbcTemplate(dataSource))
                        .usingDbTime()
                        .build());
    }
}

@Component
public class SettlementJob {
    @Scheduled(cron = "0 0 3 * * *")
    @SchedulerLock(
        name = "dailySettlement",
        lockAtLeastFor = "5m",
        lockAtMostFor = "30m"
    )
    public void runDailySettlement() {
        settlementService.processDailySettlement();
    }
}

 

실무 포인트

lockAtMostFor는 실제 작업 소요 시간보다 넉넉히 잡아야 합니다. 이 값을 실제 시간보다 짧게 설정하면, 작업이 끝나지 않았는데 락이 만료돼 다른 인스턴스가 동시에 시작하는 최악의 상황이 생깁니다.

usingDbTime()으로 인스턴스 간 시계 오차를 제거하세요. 로컬 시계 기준이면 인스턴스 간 시계가 어긋날 때 락 판정이 꼬일 수 있습니다.

주의 — 락 저장소 자체가 단일 장애점이 되지 않게 하세요. ShedLock의 락 테이블이 있는 DB가 다운되면 모든 스케줄 작업이 락 획득 실패로 전부 스킵될 수 있습니다. 이미 고가용성이 확보된 인프라를 재사용하는 것이 안전합니다.
