선착순 쿠폰 발급 시스템 설계 — Redis로 동시성 제어하고 재고 정합성 지키기

시스템 설계

한 줄 요약 — DB UPDATE로 재고를 차감하면 커넥션 고갈과 락 경합이 생기므로, Redis의 원자적 연산으로 요청을 앞단에서 걸러내야 합니다.

 

왜 선착순 이벤트만 만들면 장애가 나는가

선착순 쿠폰 이벤트는 짧은 시간에 같은 재고 값 하나를 두고 수많은 요청이 경쟁하는 가장 가혹한 트래픽 패턴입니다. 단순한 카운터 증가 로직을 그대로 쓰면 재고가 마이너스로 내려가는 초과 발급이나, 재고가 남았는데도 이벤트가 조기 종료되는 사고가 동시에 날 수 있습니다.

 

잘못된 접근 vs 올바른 접근

조건부 UPDATE 쿼리는 이론적으로는 원자적이지만, 순간적으로 요청이 몰리면 DB 커넥션 풀이 고갈되고 같은 행을 두고 벌어지는 락 경합으로 응답 시간이 기하급수적으로 늘어납니다.

def try_issue_coupon(coupon_id, user_id):
    remaining = r.decr(f"coupon:stock:{coupon_id}")
    if remaining < 0:
        r.incr(f"coupon:stock:{coupon_id}")
        return False
    r.sadd(f"coupon:issued:{coupon_id}", user_id)
    return True

Redis의 DECR은 단일 스레드로 동작하는 특성 덕분에 별도 락 없이도 원자적으로 값을 감소시킵니다. 결과가 음수가 되면 즉시 INCR로 되돌리고, SADD의 반환값으로 중복 참여를 함께 차단합니다.

 

 

DB 반영은 비동기로 분리하기

재고 확보에 성공한 요청만 메시지 큐에 적재하고, 별도 워커가 순차적으로 소비해 DB에 기록하면 DB 부하를 완전히 분리할 수 있습니다. 사용자는 Redis 결과만으로 즉시 당첨·실패 응답을 받고, DB는 큐가 흘려보내는 만큼만 처리하면 됩니다.

주의 — Redis 자체도 단일 장애 지점이 될 수 있습니다. 이벤트 규모가 크다면 Redis Cluster나 Sentinel로 가용성을 확보하고, 반드시 사전 부하 테스트로 처리량 한계를 확인하세요. 이벤트 종료 후 키에 TTL을 걸어 메모리도 정리해야 합니다.
