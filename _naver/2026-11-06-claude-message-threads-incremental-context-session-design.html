AI

한 줄 요약 — Anthropic이 Messages API에 공개한 Message Threads는 매 턴 전체 대화를 다시 보내지 않고 새 메시지만 전송하게 해줍니다. TTFT는 줄지만 토큰 비용은 그대로이고 5분 TTL이라는 제약이 있어, 어디까지 설계에 믿고 넣을지 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"이 작업은 몇 시간짜리인데, 매번 모델을 부를 때마다 지금까지 주고받은 메시지를 전부 다시 올려야 하나요?" 장시간 실행되는 코딩 에이전트나 조사 에이전트를 만들어본 팀이라면 한 번쯤 마주치는 질문입니다. 지금까지는 모델이 상태를 기억하지 않으므로, 클라이언트가 전체 대화 이력을 세션 스토어에 들고 있다가 매 요청마다 처음부터 끝까지 다시 실어 보내야 했습니다.

그런데 Anthropic이 Messages API에 Message Threads를 퍼블릭 베타로 열면서 이 전제가 흔들렸습니다. 첫 요청에서 thread 파라미터로 스레드를 열면, 이후 요청은 새로 생긴 메시지와 직전 응답 ID만 보내면 됩니다 — 서버가 나머지를 기억합니다. Claude Code에서 기본으로 켠 결과 대형 대화에서 TTFT 중앙값이 약 35% 줄었다고 합니다. 다만 이게 "세션 관리를 안 해도 된다"는 뜻은 아닙니다. 토큰 비용은 그대로이고, 스레드는 5분 TTL을 가진 메모리 캐시일 뿐입니다.

 

전체 시스템에서의 위치

Message Threads는 클라이언트의 세션 스토어와 모델 호출 사이, "요청 바디 조립" 단계에만 끼어듭니다. 이 기능이 대체하는 것은 전송 방식이지 세션 상태 관리 책임 자체가 아닙니다. 클라이언트는 여전히 전체 대화를 자신의 스토어에 가지고 있어야 합니다 — 스레드가 5분 안에 만료되면, 다음 요청은 전체 이력을 다시 실어 새 스레드를 여는 수밖에 없기 때문입니다. 이 폴백 경로를 설계에서 빼먹으면, 사용자가 자리를 비운 사이 요청이 조용히 실패하거나 컨텍스트가 끊긴 채로 이어집니다.

표가 말해주는 핵심은 Message Threads가 네트워크 전송 최적화이지 비용 최적화나 상태 관리 대체재가 아니라는 점입니다. 토큰 비용을 줄이려면 여전히 압축(compaction)이나 오래된 턴 요약 같은 별도 설계가 필요하고, 멱등성이 중요한 배치·감사 추적이 필요한 조직이라면 Inference Hooks와 동시에 못 쓴다는 제약부터 확인해야 합니다.

 

실제 프로젝트 진행 순서

1) 먼저 TTFT가 실제 병목인지 측정합니다. 대화 길이별 TTFT를 재보지 않고 무조건 켜면, 병목이 모델 추론 시간이나 도구 호출 왕복이었던 경우 효과를 체감하지 못합니다.
2) 기존 세션 스토어는 그대로 유지한 채 베타 헤더를 켭니다. 세션 스토어를 먼저 걷어내면 TTL 만료 시 되돌아갈 데이터가 없습니다.
3) 5분 무응답 시 전체 재전송으로 넘어가는 폴백 경로를 먼저 구현하고 테스트합니다.
4) Inference Hooks·Batches·토큰 카운팅 같은 기존 기능과의 충돌 여부를 체크리스트로 확인합니다.
5) 실제 트래픽 일부에만 적용해 TTFT 개선폭과 스레드 만료율을 함께 관찰한 뒤 전체 롤아웃을 결정합니다.

 

주의 — "상태를 서버가 들고 있다"는 말에 안심하지 마세요. 스레드는 영속 저장소가 아니라 TTL이 있는 캐시입니다. 또한 토큰 비용 절감을 기대하고 도입하면 실망합니다. 모델은 매 턴 전체 대화를 다시 읽으므로 과금되는 토큰 수는 변하지 않습니다.

 

정리

Message Threads는 장시간 에이전트 대화의 전송 효율을 높이지만, 세션 상태 관리 책임을 대체하지 않습니다. TTFT는 줄어도 토큰 비용은 그대로이므로 레이턴시 개선과 비용 절감을 같은 기능으로 기대하면 안 되고, 5분 TTL 만료와 일부 기능 비호환은 설계 초기부터 반드시 반영해야 하는 제약입니다.
