"이 Skill, 다른 에이전트에서도 그대로 쓰게 해주세요" — SKILL.md가 벤더를 넘어 수렴하는 지금의 설계 판단

AI

한 줄 요약 — 구글이 2026년 9월 30일 제미나이 앱의 Gems를 SKILL.md 기반 Skills로 전환한다고 발표하면서, Claude Code·Codex CLI·Cursor·Gemini가 같은 확장 파일 포맷으로 수렴하고 있습니다. 사내 Skill을 벤더 중립으로 설계할지, 특정 벤더에 최적화할지를 가르는 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"우리 팀이 만든 PR 리뷰 Skill, Claude Code뿐 아니라 ChatGPT나 Cursor에서도 똑같이 쓰고 싶어요." 사내에 에이전트 확장 기능을 만들어본 팀이라면 자연스럽게 나오는 요구입니다. 불과 1년 전만 해도 이건 거의 불가능한 요구였습니다. Claude의 도구 정의, OpenAI의 커스텀 GPT 액션, Cursor의 규칙 파일이 서로 다른 스키마를 썼고, 한 벤더용으로 만든 확장은 다른 벤더에서 처음부터 다시 작성해야 했습니다.

그런데 이 전제가 최근 몇 달 사이 빠르게 무너지고 있습니다. OpenAI가 Codex CLI와 ChatGPT에 Anthropic이 공개한 SKILL.md 포맷을 그대로 채택했고, Cursor도 .cursor/skills/ 폴더로 같은 구조를 받아들였습니다. 2026년 9월 30일에는 구글이 제미나이 앱의 Gems를 같은 SKILL.md 기반 Skills로 전환한다고 발표했습니다. 빌더에게 질문이 바뀌었습니다 — "어떤 벤더 전용 포맷으로 만들 것인가"가 아니라 "벤더 중립적으로 설계해서 여러 런타임에서 재사용할 것인가"로.

 

전체 시스템에서의 위치

사내 Skill 하나가 여러 에이전트 런타임에 걸쳐 동작하려면 "포맷은 공통, 실행 환경은 벤더별"이라는 구조로 설계해야 합니다. SKILL.md + 참조 파일을 버전 관리하는 공통 저장소를 두고, 각 런타임이 자기만의 discovery 방식으로 같은 파일을 읽습니다.

포맷이 같아도 벤더마다 다른 것이 있습니다. Progressive Disclosure가 "언제 본문을 로드할지" 판단하는 방식과, 각 런타임이 표준 필드 외에 추가로 지원하는 벤더 고유 확장 필드입니다.

 

선택의 트레이드오프
기준 벤더 중립 SKILL.md 벤더 전용 최적화 포맷
이식성 여러 런타임에서 재사용 가능 해당 벤더에서만 동작
벤더 고유 기능 공통 분모만 활용 가능 특화 기능 최대 활용
유지보수 파일 하나만 관리 벤더 수만큼 관리
적합한 상황 여러 도구를 넘나드는 범용 작업 한 벤더에 강하게 락인된 조직

 

단일 벤더에 이미 깊게 결합돼 있고 그 벤더만의 고유 기능이 핵심이라면, 벤더 중립 포맷으로 공통분모만 쓰는 것이 오히려 손해일 수 있습니다. 하지만 여러 팀이 서로 다른 에이전트 도구를 쓰고 있다면 지금이 벤더 중립 설계로 전환할 적기입니다.

# PR 리뷰 체크리스트

1. 변경된 파일 중 테스트 커버리지가 없는 로직 확인
2. 사내 네이밍 컨벤션 준수 여부 확인
3. 벤더별 확장 필드는 런타임별 설정 파일에서 보강

 

주의 — 외부 마켓플레이스에서 가져온 Skill은 포맷이 공통이라고 해서 안전이 보장되는 것은 아닙니다. 설치 전 프롬프트 인젝션·과도한 권한 요구 여부를 점검하는 절차를 그대로 유지하세요. 표준이 아직 1년이 안 된 만큼, 세부 필드나 동작이 앞으로도 바뀔 수 있으니 버전과 변경 이력을 추적할 장치를 함께 두세요.

 

정리

Claude·OpenAI·Cursor에 이어 구글까지 제미나이 앱의 Gems를 SKILL.md 기반 Skills로 전환하면서, 이 포맷이 사실상 벤더를 넘나드는 공통 표준으로 자리 잡고 있습니다. 포맷은 공통이어도 런타임별 discovery 메커니즘과 벤더 고유 확장 기능은 다르므로, "포맷은 공통, 실행 환경은 벤더별"이라는 구조로 설계해야 합니다. 여러 도구를 넘나드는 범용 작업은 벤더 중립 설계가, 특정 벤더 고유 기능이 핵심인 작업은 벤더 전용 최적화가 더 맞습니다.
