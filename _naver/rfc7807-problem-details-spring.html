API 에러 응답을 표준화하기 — RFC 7807 Problem Details와 Spring ProblemDetail 활용

백엔드

한 줄 요약 — RFC 7807은 type, title, status, detail, instance 다섯 필드로 API 에러 형식을 표준화합니다. Spring Boot 3의 ProblemDetail로 별도 라이브러리 없이 적용할 수 있습니다.

 

왜 에러 응답 형식이 API마다 제각각일까

여러 사람이 오랫동안 기능을 추가해온 API 서버를 보면 에러 응답 형식이 엔드포인트마다 미묘하게 다른 경우가 흔합니다. 프론트엔드 개발자는 API를 호출할 때마다 이 엔드포인트는 에러가 어떤 모양으로 올까를 문서에서 다시 확인해야 하고, 공통 에러 처리 로직을 만들기도 어려워집니다.

 

 

핵심 개념 1 — RFC 7807은 공식 표준이다
필드 의미
type 문제 유형을 식별하는 URI
title / status 짧은 요약 / HTTP 상태 코드
detail / instance 구체적 설명 / 요청 식별 URI

이 구조는 필드가 고정돼 있지만 확장도 허용합니다 — 검증 실패 시 어떤 필드가 문제인지 알려주는 errors 배열 같은 커스텀 필드를 추가할 수 있습니다. 중요한 것은 다섯 개 기본 필드만큼은 모든 API에서 동일한 이름과 의미로 나온다는 점입니다.

 

핵심 개념 2 — Spring Boot 3는 ProblemDetail을 내장한다

Spring Framework 6부터는 ProblemDetail 클래스가 내장돼 있어 별도 라이브러리 없이도 RFC 7807 형식의 응답을 만들 수 있습니다. 전역 예외 처리기에서 이 클래스를 반환하면 자동으로 application/problem+json 콘텐츠 타입과 표준 필드 구조로 응답이 나갑니다.

 

예제 — 전역 예외 처리기 적용
@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("리소스를 찾을 수 없음");
        problem.setType(URI.create("https://api.example.com/errors/not-found"));
        problem.setProperty("resourceId", ex.getResourceId());
        return problem;
    }
}
{
  "type": "https://api.example.com/errors/not-found",
  "title": "리소스를 찾을 수 없음",
  "status": 404,
  "detail": "ID 42인 주문을 찾을 수 없습니다",
  "instance": "/api/orders/42",
  "resourceId": 42
}

 

도입 시 흔한 실수
실수 결과
type을 about:blank로 방치 클라이언트가 에러 유형 구분 못 함
detail에 스택 트레이스 노출 보안 정보 유출 위험

 

실무 포인트

type URI는 실제로 접근 가능한 문서로 연결하는 것이 이상적입니다. 당장 문서 페이지를 만들 여력이 없다면 최소한 에러 코드처럼 고유하고 일관된 값으로 유지해야 합니다.

레거시 엔드포인트는 한 번에 다 바꾸려 하지 말고 점진적으로 전환하세요. 새 엔드포인트부터 표준을 적용하고 트래픽이 큰 기존 엔드포인트를 우선순위로 옮기는 것이 현실적입니다.

주의 — detail 필드에 데이터베이스 제약조건 이름이나 내부 클래스 경로가 그대로 노출되지 않도록, 사용자에게 보여줄 메시지와 서버 로그에만 남길 상세 정보를 분리해야 합니다.
