"브라우저에서 이 작업까지 자동으로 해주세요" — 전용 브라우저 에이전트가 접힌 자리에서 Computer Use 범위를 정하는 법

AI

한 줄 요약 — 독립 브라우저 에이전트 제품이 접히고 더 큰 에이전트의 한 기능으로 흡수되는 흐름을 보며, 컴퓨터 제어 권한을 어디까지 열어줄지와 전용 API 도구로 대체할지를 가르는 설계 기준을 정리했습니다.

 

왜 지금 이 판단이 다시 중요해졌는가

"관리자 페이지에 로그인해서 이 설정값들을 매일 체크해주세요", "경쟁사 사이트 가격을 매일 확인해서 알려주세요" 같은 요구가 들어오면, 요즘은 API를 찾기 전에 "그냥 에이전트가 브라우저를 직접 조작하게 하면 안 되나?"라는 질문이 먼저 떠오릅니다. 화면을 보고, 클릭하고, 입력하고, 결과를 읽는 범용 컴퓨터 제어 능력이 실제로 쓸 만해졌기 때문입니다. 그런데 최근 시장에서 재미있는 신호가 나왔습니다. 독립 제품으로 나왔던 브라우저 전용 에이전트들이 하나둘 접히거나 더 큰 에이전트 플랫폼의 한 기능으로 흡수되고 있다는 점입니다.

이 흐름은 단순한 제품 통폐합 뉴스가 아니라, 빌더에게 실제 설계 판단 기준을 줍니다. "브라우저 자동화"를 별도의 독립 제품·엔드포인트로 만들 가치가 있는지, 아니면 더 넓은 컴퓨터 제어 능력 안의 한 모드로 흡수시켜야 하는지의 문제입니다. 이 판단은 곧바로 "이 작업에 컴퓨터 전체를 내줄 것인가, 전용 API 도구 하나만 내줄 것인가"라는, 모든 에이전트 설계에서 반복되는 더 근본적인 질문으로 이어집니다.

 

전체 시스템에서의 위치

이 요구는 셋 중 하나의 자리로 번역됩니다. 첫째는 전용 API 도구 — 대상 서비스가 API를 제공하면 그 엔드포인트를 직접 호출하는 함수 하나를 에이전트에 붙입니다. 둘째는 스코프가 좁은 브라우저 자동화 — 특정 사이트의 로그인·클릭·추출 흐름만 스크립트로 고정하고 에이전트는 그 스크립트를 트리거만 합니다. 셋째는 범용 컴퓨터 제어(Computer Use) — 에이전트가 화면 스크린샷을 보고 마우스·키보드를 직접 움직여 어떤 사이트든, 어떤 앱이든 다룹니다.

세 경로 모두 "요청 → 실행 계층 → 결과 해석 → 응답"이라는 같은 위치에 있지만, 실행 계층의 통제 가능성이 반대 방향으로 좁아집니다. API 도구는 입력·출력 스키마가 고정돼 있어 무엇이 일어날지 사전에 완전히 예측할 수 있습니다. 컴퓨터 제어는 화면에 뭐가 떠 있는지에 따라 에이전트가 매번 다른 경로로 클릭할 수 있어, 실행 전에는 정확히 무엇을 할지 알 수 없습니다. 이 예측 불가능성이 바로 설계에서 다뤄야 할 핵심 리스크입니다.

 

선택의 트레이드오프
기준전용 API 도구좁은 브라우저 스크립트범용 Computer Use
적용 범위API 있는 서비스만미리 정한 흐름만화면이 있는 모든 것
실행 예측 가능성높음중간낮음
실패 시 블라스트 반경작음중간큼
적합한 상황API가 있거나 만들 수 있을 때반복적인 고정 작업API 없는 레거시·일회성 작업

 

독립 브라우저 에이전트 제품은 둘째와 셋째 사이 애매한 위치에 있었습니다. 결국 시장은 "브라우저만 따로 떼어 제품화"하기보다, 범용 컴퓨터 제어 능력 하나에 브라우저·터미널·파일·데스크톱 앱을 전부 포함시키는 방향으로 수렴하고 있습니다. 빌더 입장에서 얻는 교훈은, 브라우저 자동화를 위해 별도 아키텍처를 구축하는 대신 "범용 컴퓨터 제어 vs 전용 도구"라는 더 큰 이분법으로 판단을 단순화하라는 것입니다.

 

실제 프로젝트 진행 순서

1) 대상 서비스에 API가 있는지부터 확인합니다. 있다면 무조건 전용 도구가 우선입니다.
2) API가 없다면 작업의 반복성을 따집니다. 매번 같은 흐름이면 셀렉터 기반 스크립트가 더 저렴하고 안정적입니다.
3) 작업이 비정형적이거나 일회성이라면 그때 Computer Use를 꺼냅니다.
4) Computer Use를 쓰기로 했다면 샌드박스 경계부터 긋습니다 — 권한 제한 계정, 격리된 VM, 쓰기·결제·삭제는 사람 승인 게이트.
5) 실행 로그(스크린샷·클릭 좌표·입력값)를 전부 남겨 사후 재구성이 가능하게 합니다.

 

주의 — "컴퓨터 전체를 내준다"는 결정은 기능 하나가 아니라 권한 모델 전체를 다시 설계하는 일입니다. 민감한 동작(결제, 계정 설정 변경, 삭제)은 Computer Use 경로에서 아예 차단하거나 별도 승인 게이트를 거치게 해야 합니다. 같은 작업을 API로 할 수 있는데 Computer Use로 돌리고 있다면, 거의 항상 성능·비용 면에서 손해입니다.

 

정리

독립 브라우저 에이전트 제품들이 접히고 범용 컴퓨터 제어 능력의 한 모드로 흡수되는 흐름은, "브라우저 자동화를 따로 설계하지 말고 전용 API 도구 vs 범용 컴퓨터 제어"라는 더 단순한 이분법으로 판단하라는 신호입니다. API가 있으면 전용 도구, 반복 작업이면 고정 스크립트, 비정형·일회성 작업에서만 Computer Use를 꺼내는 순서로 판단하고, Computer Use를 쓰기로 했다면 권한 모델 재설계부터 시작하세요.
