"지도가 느려졌는데 뭐부터 봐야 하나요" — Cesium 성능 프로파일링, 증상에서 병목까지 좁혀가는 순서

GIS

한 줄 요약 — "지도가 느려요"라는 증상 하나에는 CPU·GPU·네트워크·LOD 전환 비용 등 여러 원인 후보가 있습니다. requestRenderMode로 유휴 렌더링을 분리하고, Chrome DevTools로 CPU/GPU를 나누고, 3D Tiles Inspector로 타일·드로우콜을 확인하는 순서로 병목을 좁혀가야 땜질식 튜닝을 피할 수 있습니다.

 

왜 지금 이 판단이 필요한가

"지도가 느려졌어요. 왜 그런지는 모르겠고 그냥 빠르게 해주세요"는 Cesium을 운영해본 사람이라면 한 번쯤 듣는 요구입니다. 3D Tiles 1.1의 메타데이터·시맨틱스 확장, Gaussian Splatting의 3D Tiles 통합, Photorealistic 3D Tiles 같은 무거운 콘텐츠가 기본 선택지가 되면서, 예전이라면 "건물 몇 개 띄워보고 괜찮네"로 끝났을 검증 단계가 더 이상 실제 운영 환경을 대변하지 못하게 됐습니다.

문제는 "느리다"는 증상 하나에 원인 후보가 최소 네 가지나 있다는 점입니다. 체계 없이 접근하면 가장 먼저 눈에 띄는 처방부터 땜질식으로 적용하게 되고, 병목이 다른 곳에 있으면 체감 개선이 없습니다. 빌더에게 필요한 것은 암기가 아니라, 증상을 보고 병목 단계를 좁혀가는 재사용 가능한 진단 순서입니다.

 

전체 시스템에서의 위치

Cesium 렌더링 파이프라인은 크게 세 단계입니다. 타일·엔티티 데이터가 네트워크로 들어오고, CPU(메인스레드)가 컬링·애니메이션·엔티티 갱신을 수행하고, GPU가 드로우콜과 셰이더로 화면에 그립니다. 패닝·줌 중에만 느려진다면 CPU나 네트워크를, 카메라가 멈춰 있는데도 GPU 사용률이 높다면 fill-rate 쪽을 먼저 의심하는 식으로, 증상 자체가 이미 어느 단계를 먼저 볼지에 대한 힌트를 담고 있습니다.

 

선택의 트레이드오프
증상유력한 병목대표 처방
가만히 있어도 GPU 사용률 높음불필요한 상시 렌더링requestRenderMode로 on-demand 렌더링
패닝·줌 중에만 끊김CPU 메인스레드Entity → Primitive 전환
줌 전환 시 순간 멈춤타일 로드·언로드 비용maximumScreenSpaceError 조정
초기 진입이 유독 느림네트워크 타일 요청타일 우선순위·프리로드 조정

 

이 처방들은 서로 대체재가 아니라 보완재입니다. maximumScreenSpaceError를 높이면 타일 로드 비용은 줄지만 화질이 떨어지므로, 체감 화질 저하와 측정된 성능 개선 폭을 같이 보며 어디까지 낮출지 정해야 합니다. 엔티티를 Primitive로 바꾸는 것도 개발 비용과 성능을 맞바꾸는 결정이라, 실제로 엔티티 수가 수천 개를 넘는 시점에만 적용하는 것이 합리적입니다.

 

실제 프로젝트 진행 순서

가장 먼저 할 일은 재현 가능한 시나리오를 고정하는 것입니다. 매번 다른 카메라 경로로 "느리다, 안 느리다"를 판단하면 어떤 변경이 실제로 효과가 있었는지 알 수 없습니다.

viewer.scene.requestRenderMode = true;
viewer.scene.maximumRenderTimeChange = Infinity;
// 카메라가 멈춘 상태에서도 GPU 사용률이 높다면
// fill-rate·셰이더 쪽이 유력

이 1차 분리로 "유휴 상태에서도 느린가"를 걸러낸 뒤, 카메라를 움직이는 구간에서 Chrome DevTools Performance 탭을 켜서 메인스레드와 GPU 중 어느 쪽 막대가 긴지 확인합니다. 마지막으로 3D Tiles Inspector를 띄워 타일 개수·메모리·드로우콜 통계를 보면서 maximumScreenSpaceError를 단계적으로 조정해, 품질 저하 대비 성능 개선 폭이 어디서 꺾이는지 직접 측정합니다.

 

주의 — 측정 없이 설정값부터 바꾸면 체감 개선 없이 화질이나 유지보수성만 잃을 수 있습니다. 같은 시나리오로 변경 전후를 반드시 비교하세요.
