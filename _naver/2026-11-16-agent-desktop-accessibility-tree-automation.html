"사내 전자결재 프로그램도 에이전트가 처리하게 해주세요" — 접근성 트리로 데스크톱을 조작하는 에이전트 설계

AI

한 줄 요약 — API가 없는 사내 레거시 데스크톱 프로그램까지 에이전트가 다루게 해달라는 요구에, 2026년 10월 말 Vercel Labs가 공개한 agent-desktop은 스크린샷 좌표 추측 대신 OS 접근성 트리를 직접 읽는 방식으로 답합니다. 무엇이 다르고 어디까지 믿어도 되는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"사내 전자결재 프로그램, API가 없어서 그런데 에이전트가 대신 눌러서 처리하게 해주세요"라는 요구는 생각보다 자주 들어옵니다. 은행 창구 단말기, 10년 넘은 ERP 클라이언트, 특정 장비 제조사가 깔아준 설정 프로그램처럼 API 문서 한 줄 없는 네이티브 데스크톱 앱이 업무 한가운데 버티고 있는 경우가 많기 때문입니다.

지금까지 답은 사실상 하나였습니다 — 화면을 스크린샷으로 찍어 모델에게 보여주고, 모델이 "여기를 클릭하라"고 좌표를 돌려주면 그 좌표를 클릭하는 픽셀 기반 컴퓨터 사용 루프입니다. 느리고, 해상도나 테마가 바뀌면 좌표가 어긋나고, 매 턴 이미지 토큰 비용이 쌓입니다. Vercel Labs의 agent-desktop은 macOS·Windows·Linux가 스크린 리더를 위해 이미 제공하는 OS 접근성 트리를 직접 읽어, 화면의 버튼·입력창 하나하나에 안정적인 JSON 참조를 부여하는 오픈소스 CLI입니다. 도구 안에 모델은 없고, 추론은 전적으로 에이전트 몫입니다.

 

전체 시스템에서의 위치

이 기술은 에이전트 파이프라인에서 "조작 실행 계층" 한 자리를 차지합니다. 에이전트의 추론은 하나의 모델이 맡지만, 그 결정을 실행으로 옮기는 계층은 대상에 따라 갈립니다. 같은 제작자가 만든 agent-browser가 웹 페이지를 다룬다면, agent-desktop은 네이티브 데스크톱 앱을 다룹니다. 두 도구는 대체재가 아니라 역할이 분리된 보완재이므로, 데스크톱 앱에서 뽑은 데이터를 웹 대시보드에 입력하는 식의 작업은 둘을 체인으로 엮어야 합니다.

 

선택의 트레이드오프
조작 방식속도·비용안정성커버리지
픽셀 비전(좌표)느림, 이미지 토큰해상도·테마에 취약화면만 있으면 가능
접근성 트리빠름, 텍스트만참조 기반이라 안정적트리 노출 앱만 가능
네이티브 API 연동가장 빠름매우 안정벤더 제공 범위로 제한

 

접근성 트리 기반이 픽셀 기반보다 거의 모든 면에서 낫다고 만능은 아닙니다. 트리 자체를 노출하지 않는 앱(자체 렌더링 UI 등)에서는 이 방식 자체가 통하지 않습니다. 이런 경우 픽셀 비전으로 돌아가거나 벤더 공식 연동을 다시 찾아야 합니다.

 

실제 프로젝트 진행 순서

가장 먼저 대상 프로그램이 접근성 트리를 실제로 노출하는지 확인합니다. macOS라면 손쉬운 사용 권한을 내주고 Accessibility Inspector로, Windows라면 Inspect.exe로 UI 트리가 제대로 잡히는지 눈으로 먼저 확인합니다.

agent-desktop snapshot --app "전자결재" --format json > snapshot.json
agent-desktop click --ref "button:로그인"
agent-desktop type --ref "input:사번" --text "2026-1234"

트리가 확인되면 가장 위험도가 낮은 흐름부터 자동화하고, 결재·승인처럼 되돌리기 어려운 동작은 사람 승인 게이트를 겁니다. 동시에 스냅샷과 클립보드 로그에 계좌번호·주민등록번호 같은 민감정보가 그대로 찍히는지 꼭 점검해야 합니다. 마지막으로 접근성 트리가 없는 화면을 만났을 때의 폴백 경로를 미리 설계해 둬야 합니다.

 

주의 — 접근성 정보는 "읽을 수 있는 그대로" 반환되므로, 로그 보관 정책과 전송 구간 암호화를 자동화 도입과 동시에 정리하지 않으면 자동화 자체보다 로그 유출이 더 큰 사고가 될 수 있습니다.
