"이 코드 리뷰 자동화, CI에서 밤새 돌려주세요" — Claude Code 헤드리스 실행에서 exit code를 믿으면 안 되는 이유

AI

한 줄 요약 — claude -p의 exit code 0은 "프로세스가 끝까지 실행됐다"는 뜻이지 "작업이 의도한 대로 끝났다"는 뜻이 아닙니다. 권한 거부·rate limit도 exit 0으로 보고된 사례가 있어, CI 파이프라인은 exit code와 JSON 응답의 is_error·subtype을 함께 봐야 합니다.

 

왜 지금 이 판단이 필요한가

"이 리포지토리, 매일 밤 PR 올라오는 대로 Claude Code한테 자동 리뷰시키고 문제 없으면 그대로 머지 파이프라인 태워주세요"라는 요구는 헤드리스(claude -p) 실행이 CI에 자리 잡으면서 흔해졌습니다. 이때 거의 모든 엔지니어가 본능적으로 짜는 코드는 셸 스크립트의 오랜 관습 그대로입니다 — exit code가 0이면 성공, 0이 아니면 실패로 분기합니다. 문제는 이 가정이 claude -p에서는 그대로 통하지 않는다는 점입니다.

커뮤니티에 보고된 사례들을 보면, 권한이 거부돼 Claude가 파일을 전혀 건드리지 못한 실행도 exit code 0에 "subtype": "success"로 끝나는 경우가 있습니다. API rate limit 에러도 마찬가지로 subtype: "success" + exit code 0으로 돌아오고, 에러 메시지는 결과 텍스트 안에 섞여 들어간다는 보고도 있습니다.

 

전체 시스템에서의 위치

CI 러너가 claude -p를 호출하면 두 가지 신호가 동시에 나옵니다. 하나는 OS가 관리하는 exit code, 다른 하나는 stdout으로 찍히는 JSON 바디(result, is_error, subtype 등)입니다. "무슨 일이 있었는지"에 대한 더 정확한 정보는 JSON 바디 안에 있습니다. 성공/실패 판정 로직은 OS 프로세스 계층이 아니라 애플리케이션 계층에 있어야 합니다.

 

선택의 트레이드오프
검증 방식잡아내는 것못 잡는 것
exit code만 체크프로세스 크래시권한 거부·rate limit
is_error·subtype 체크애플리케이션 레벨 실패미분류 신규 실패 유형
--allowedTools 범위 제한위험 액션 자체 차단허용 범위 안의 실패

 

가장 흔한 실수는 "exit code가 0이니 리뷰가 정상적으로 끝났다"고 로그 한 줄 없이 다음 단계로 넘어가는 것입니다. 반대로 exit code를 아예 무시하는 것도 답이 아닙니다 — exit code는 여전히 "프로세스가 끝까지 실행됐는가"를 확인하는 1차 게이트로서 의미가 있습니다.

 

실제 프로젝트 진행 순서

가장 먼저 호출 자체를 구조화된 JSON 출력으로 바꿉니다.

output=$(claude -p "PR 리뷰해줘" --output-format json --allowedTools "Read,Grep")
process_exit=$?

if [ $process_exit -ne 0 ]; then
  echo "프로세스 자체가 비정상 종료됨"; exit 1
fi

is_error=$(echo "$output" | jq -r '.is_error')
subtype=$(echo "$output" | jq -r '.subtype')

if [ "$is_error" = "true" ] || [ "$subtype" != "success" ]; then
  echo "애플리케이션 레벨 실패: subtype=$subtype"; exit 1
fi

이 두 게이트가 자리 잡으면, --allowedTools로 Claude가 건드릴 수 있는 범위를 좁혀 권한 거부 자체가 발생할 여지를 줄입니다. 마지막으로 재시도하면 해결될 실패 유형과 그렇지 않은 유형을 분리해 분기합니다.

 

주의 — rate limit처럼 재시도로 해결될 수 있는 실패와, 코드 자체 문제로 재시도해도 똑같이 실패할 유형을 분리하세요. 이 분리가 없으면 재시도 루프가 영구 실패하는 작업에 비용만 쌓이게 됩니다.
