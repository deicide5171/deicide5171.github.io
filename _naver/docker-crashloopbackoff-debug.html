Docker 컨테이너가 계속 재시작될 때 — CrashLoopBackOff 원인 찾는 법

2026. 8. 31. · 인프라

한 줄 요약 — kubectl logs --previous로 죽기 직전 로그를 확인하고, Exit Code 137이면 로그 대신 메모리 제한을 먼저 의심하세요.

 

왜 이 에러가 골치 아픈가

CrashLoopBackOff는 쿠버네티스가 "이 컨테이너를 계속 재시작했지만 계속 죽는다"고 알려주는 상태일 뿐, 왜 죽었는지는 말해주지 않습니다. Docker Compose에서도 Restarting이 반복되는 동일한 증상이 나타납니다. 이 글은 원인을 좁혀가는 순서를 정리했습니다.

 

원인 카테고리 4가지
카테고리 대표 증상 확인 명령
애플리케이션 크래시 시작 직후 에러 로그 후 종료 kubectl logs --previous
리소스 부족(OOM) Exit Code 137 kubectl describe pod의 Last State
헬스체크 실패 Liveness 실패로 재시작 kubectl describe pod의 Events
설정·의존성 오류 DB 연결 실패로 즉시 종료 로그의 스택트레이스 첫 줄

 

진단 순서
# 1. 현재 상태와 재시작 횟수, 마지막 종료 사유 확인
kubectl describe pod <pod-name>

# 2. 방금 죽은 컨테이너의 로그 확인 (--previous가 핵심)
kubectl logs <pod-name> --previous

# 3. Exit Code 확인
#    0   : 정상 종료
#    1   : 애플리케이션 자체 에러
#    137 : OOM Killer에 의해 강제 종료
#    139 : 세그멘테이션 폴트
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'

Docker Compose 환경이라면 docker logs --tail 100과 docker inspect의 State.ExitCode로 같은 정보를 얻을 수 있습니다.

 

실무 포인트

Exit Code 137이 보이면 로그를 아무리 봐도 답이 없습니다. 메모리 제한을 올리거나 애플리케이션의 메모리 사용량 자체를 줄여야 합니다.

Liveness Probe 설정이 너무 빡빡하면 정상 앱도 재시작 루프에 빠집니다. initialDelaySeconds를 부팅 시간보다 넉넉하게 주는 것이 첫 점검 포인트입니다.

주의 — 로컬에서는 멀쩡한데 클러스터에서만 죽는다면 환경변수·시크릿 마운트 차이나 네트워크 정책으로 인한 DB 연결 실패를 의심하세요. kubectl exec로 직접 들어가 연결을 테스트하면 빠르게 확인됩니다.
