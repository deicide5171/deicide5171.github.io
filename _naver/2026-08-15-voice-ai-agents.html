음성 AI 에이전트 전쟁 — Siri 재편과 음성 인터페이스의 부상

2026. 8. 15. · AI

한 줄 요약 — 구글 에이전트가 매장에 전화를 걸고 애플이 Siri를 재구성하는 등, AI 에이전트 경쟁의 무대가 텍스트에서 음성 인터페이스로 넓어지고 있는 흐름과 그 기술적 난제를 정리했습니다.

 

왜 지금 음성인가

최근 구글의 에이전트가 실제 매장에 전화를 걸어 예약이나 재고 확인을 대신 처리해주는 시연이 화제가 되었습니다. 애플도 Siri를 대규모로 재구성하고 있다는 소식이 이어지고 있고, 음성 AI 스타트업에 대한 투자 규모도 눈에 띄게 커지는 분위기입니다. 지금까지 AI 에이전트 이야기는 대부분 텍스트 챗봇 중심이었지만, 이제 무대가 조금씩 음성으로 옮겨가고 있습니다.

사람이 가장 자연스럽게 쓰는 인터페이스는 사실 여전히 말입니다. 전화로 예약하거나, 운전 중에 질문하거나, 손이 자유롭지 않은 상황에서는 텍스트보다 음성이 훨씬 편합니다. 실시간 음성 인식(STT)과 저지연 음성 합성(TTS) 기술이 실용적인 수준에 이르면서, 이런 음성 에이전트를 만드는 진입 장벽이 눈에 띄게 낮아지고 있습니다.

 

텍스트 에이전트와 무엇이 다른가

같은 언어모델을 쓰더라도 음성 인터페이스는 텍스트 인터페이스와 요구 조건이 크게 다릅니다. 텍스트는 사용자가 엔터를 눌러야 다음 턴이 시작되지만, 음성은 침묵이나 억양만으로 상대가 말을 끝냈는지 판단해야 합니다. 또한 텍스트는 답이 이상하면 스크롤해서 다시 확인할 수 있지만, 음성은 한번 지나가면 되돌릴 수 없어 즉시 자연스럽게 정정해야 합니다.

구분 텍스트 에이전트 음성 에이전트
지연시간 수 초도 무방 수백 ms 이내여야 자연스러움
턴테이킹 명시적(전송 버튼) 암묵적(침묵·억양 판단 필요)
오류 복구 다시 읽고 확인 가능 즉시 자연스럽게 정정 필요
입력 형태 완결된 문장 단위 끊긴 발화, 잡음 포함 스트리밍

 

핵심 난제: 지연시간·턴테이킹·스트리밍

지연시간이 가장 큰 벽입니다. 사람 사이의 자연스러운 대화는 응답까지 대략 200~300ms 안팎이라고 알려져 있는데, 음성 인식→언어모델 추론→음성 합성으로 이어지는 파이프라인 전체를 그 안에 넣기는 쉽지 않습니다. 그래서 최근에는 이 세 단계를 순서대로 잇는 대신, 오디오를 직접 다루는 음성-음성 모델이나 중간 결과를 먼저 흘려보내는 스트리밍 구조가 함께 시도되고 있습니다.

턴테이킹도 까다롭습니다. 사용자가 말을 끝냈는지, 잠시 생각 중인지, 끼어들려는 것인지를 침묵 길이만으로 판단하면 오작동이 잦습니다. 그래서 실제 서비스들은 억양과 발화 리듬까지 함께 보는 턴 감지 로직을 두고, 사용자가 에이전트 발화 도중에 끼어드는 상황을 처리하는 로직을 별도로 구현합니다. 실시간 스트리밍 STT/TTS 역시 오디오를 청크 단위로 계속 흘려보내며 중간 결과를 갱신하고, 네트워크가 불안정해도 대화가 끊기지 않도록 버퍼링·재연결 전략을 신경 써야 합니다.

 

예제: 실시간 음성 세션 의사코드
import asyncio
import websockets
import json

async def voice_agent_session(ws_url, api_key):
    async with websockets.connect(
        ws_url,
        extra_headers={"Authorization": f"Bearer {api_key}"}
    ) as ws:
        # 세션 초기화: 턴 감지 방식, 오디오 포맷 설정
        await ws.send(json.dumps({
            "type": "session.update",
            "session": {
                "turn_detection": {"type": "server_vad", "threshold": 0.5},
                "input_audio_format": "pcm16",
                "output_audio_format": "pcm16",
            }
        }))

        async def receive_events():
            async for message in ws:
                event = json.loads(message)
                if event["type"] == "response.audio.delta":
                    play_audio_chunk(event["delta"])  # 부분 오디오 즉시 재생
                elif event["type"] == "input_audio_buffer.speech_started":
                    stop_playback()  # 사용자가 끼어들면 즉시 중단(barge-in)

        await receive_events()

서버 측 음성 활동 감지(VAD)에 턴 판단을 맡기고, 사용자가 말을 시작하는 이벤트가 오면 재생 중이던 에이전트 음성을 즉시 멈추는 바지인(barge-in) 처리가 실무에서 자주 놓치는 부분입니다.

 

실무 도입 시 이것만은 챙기세요
1. 엔드투엔드 지연 측정 — 마이크 입력부터 스피커 출력까지 전체 왕복 시간을 로깅해야 병목 구간을 찾을 수 있음
2. 부분 실패 대비 설계 — 네트워크 끊김이나 인식 오류 시 자연스러운 재확인 발화를 준비해두는 것이 무음보다 나음
3. 음성 데이터 정책 사전 정의 — 통화·음성 녹음은 텍스트보다 민감하게 다뤄지므로 저장 여부·보존 기간을 미리 정할 것
4. 비용 구조 재검토 — 음성 스트리밍은 세션 유지 시간·오디오 처리량 기준 과금이 많아 텍스트 토큰 기준과 다르게 접근 필요
