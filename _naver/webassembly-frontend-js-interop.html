WebAssembly로 프론트엔드 성능 끌어올리기 — WASM과 JS 상호운용 내부 동작

프론트엔드

한 줄 요약 — WASM이 JS보다 빠른 이유와, JS-WASM 경계를 넘을 때 실제로 발생하는 비용을 이해해야 언제 도입할 가치가 있는지 판단할 수 있습니다.

 

왜 지금 프론트엔드에서 WebAssembly를 다시 봐야 하는가

이미지·비디오 편집, PDF 렌더링, 대용량 CSV 파싱처럼 CPU 집약적인 작업을 브라우저에서 직접 처리해야 하는 애플리케이션이 늘고 있습니다. WASM은 미리 컴파일된 바이트코드를 브라우저에 전달해 JS 엔진의 인터프리트·최적화 과정을 건너뛰고 거의 네이티브에 가까운 속도로 실행할 수 있게 합니다. 다만 "WASM이 항상 JS보다 빠르다"는 단순화는 오해이며, 경계 비용을 이해해야 합니다.

 

WASM이 빠른 이유: 정적 타입과 선형 메모리

WASM은 정적 타입 스택 기반 명령어 집합으로 설계되어 런타임 타입 추측·재컴파일 과정이 필요 없습니다. 또한 선형 메모리(연속된 바이트 배열) 위에서 동작해 CPU 캐시 지역성이 뛰어나고 GC 개입 없이 결정적으로 동작합니다. 이 덕분에 반복적인 수치 연산에서 JS 대비 몇 배의 성능 이득을 보입니다.

 

JS-WASM 경계를 넘는 비용: 직렬화와 데이터 복사

WASM의 선형 메모리는 JS 객체·문자열과 직접 호환되지 않습니다. 경계를 넘을 때마다 데이터를 바이트 형태로 인코딩해 복사해야 하므로, 호출이 잦고 데이터가 클수록 비용이 누적됩니다. 핵심 원칙은 "경계를 최대한 적게, 한 번에 큰 덩어리로 넘어라"입니다. 픽셀마다 매번 오가는 대신 버퍼 전체를 한 번에 복사해 넣고 결과 하나만 꺼내오는 방식이 효율적입니다.

항목 순수 JS WebAssembly
메모리 모델 객체 그래프, GC 관리 선형 메모리(연속 바이트)
DOM 접근 직접 접근 가능 불가능(JS 경유 필수)
데이터 전달 비용 없음(같은 힙) 경계마다 복사 필요

 

큰 덩어리로 경계를 넘기는 패턴
// 나쁜 예: 픽셀마다 호출 - 경계 비용 누적
for (let i = 0; i < pixels.length; i++) {
  result[i] = wasmModule.processPixel(pixels[i]);
}

// 좋은 예: 버퍼 전체를 한 번에 복사
const { memory, process_buffer } = wasmModule.instance.exports;
const inputPtr = wasmModule.instance.exports.alloc(pixels.length);
new Uint8Array(memory.buffer, inputPtr, pixels.length).set(pixels);
process_buffer(inputPtr, pixels.length); // 단 한 번의 경계 호출

 

실무 포인트

DOM 조작이 필요한 로직은 WASM으로 옮기지 마세요. WASM은 DOM에 직접 접근할 수 없어 결국 JS를 경유해야 하므로, 오히려 경계 비용만 늘어납니다. WASM은 순수 연산 로직에만 국한하는 것이 원칙입니다.

번들 크기와 초기 로딩 비용을 반드시 측정하세요. 작은 연산 하나를 위해 수백 KB짜리 모듈을 로드하면 오히려 손해입니다. 반복 실행되는 무거운 연산에만 투입 가치가 있습니다.

주의 — wasm-bindgen 같은 도구가 직렬화 보일러플레이트를 자동 생성해주지만, 내부적으로 여전히 복사가 일어난다는 사실은 변하지 않습니다. 경계를 넘는 횟수와 데이터 크기는 개발자가 직접 통제해야 합니다.
