에이전트가 다른 에이전트를 직접 부르면 안 되는 이유 — 큐 기반 비동기 핸드오프와 백프레셔 설계

SYSTEM DESIGN

한 줄 요약 — '에이전트 A가 끝나면 바로 B가 이어받게 해주세요'라는 요구를 함수 호출 한 줄로 풀면, 뒤의 에이전트가 느려지거나 재시도를 시작하는 순간 앞의 에이전트까지 통째로 묶입니다. AWS Well-Architected 에이전틱 AI 렌즈가 권고하는 비동기 메시징 기본값과, 직접 호출에서 큐 기반 핸드오프로 옮겨가야 하는 판단 기준을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"조사 에이전트가 자료를 모으면, 바로 작성 에이전트가 이어받아서 보고서를 써주세요." 멀티에이전트 파이프라인을 처음 짤 때 가장 직관적인 구현은 A의 코드 안에서 B를 함수처럼 호출하는 것입니다. 코드도 짧고 디버깅도 한 호출 스택 안에서 끝납니다. 문제는 이 직관이 두 에이전트를 완전히 결합시킨다는 데 있습니다. B가 느려지면 A는 블로킹되고, B가 실패하면 A가 이미 한 작업까지 함께 유실됩니다.

더 나쁜 경우는 재시도입니다. LLM 호출 하나가 레이트 리밋에 걸려 재시도를 시작하면, 그 호출을 직접 물고 있던 상위 에이전트의 재시도 로직까지 함께 발동해 요청량이 기하급수적으로 불어납니다. 7개 오픈소스 멀티에이전트 프레임워크의 1,600여 개 실행 트레이스를 분석한 MAST 연구(2025)는 실패 원인 대부분이 모델 한계가 아니라 시스템 설계 문제와 에이전트 간 정합성 붕괴에서 비롯된다고 지적합니다. AWS가 2025년 말 공개한 Well-Architected 에이전틱 AI 렌즈 역시 "즉각적인 응답이 꼭 필요한 경우를 제외하면 비동기 메시징을 기본값으로 하라"고 명시하며, 에이전트 간 직접 호출을 안티패턴으로 지목합니다.

 

전체 시스템에서의 위치

직접 호출 구조는 A가 B를 동기 호출해 B의 지연·실패·재시도가 호출 스택을 타고 그대로 A에 전달됩니다. 큐 기반 구조는 A가 작업 완료를 큐에 메시지로 적재하고 끝납니다. B는 자신의 속도로 큐를 소비하며, B가 느려지거나 멈춰도 메시지는 큐에 쌓일 뿐 A는 영향받지 않습니다. 메시지는 전체 데이터가 아니라 참조만 담아 가볍게 유지합니다. 에이전트는 무상태 워커로 두고, 진행 단계는 별도 DB에 기록해 중복 전달에도 중복 실행되지 않게 합니다.

 

선택의 트레이드오프
접근 장점 단점
직접 함수 호출 구현 단순, 지연 최소 장애·재시도 전파, 백프레셔 없음
큐 기반 핸드오프 장애 격리, 자연스러운 백프레셔 지연 증가, 운영 복잡도 추가
하이브리드(동기+비동기) 체감 응답성과 안정성 동시 확보 경계 설계·상태 동기화 복잡
공유 블랙보드 에이전트 간 결합도 최소화 상태 관리 자체가 새 난제

 

판단 기준은 "B의 실패가 A의 실패여도 괜찮은가"입니다. 괜찮다면 직접 호출로 충분합니다. 반대로 B가 외부 LLM API처럼 지연이 들쭉날쭉하거나 레이트 리밋에 걸리기 쉬운 자원을 쓴다면, 그 변동성을 A까지 전달하지 않도록 큐 한 겹을 끼워 넣어야 합니다.

 

실제 프로젝트 진행 순서

1. 먼저 직접 호출로 파이프라인을 완성해 핸드오프 지점과 각 단계의 소요 시간을 파악합니다.
2. 지연·실패가 전파되는 지점을 찾습니다. 특히 외부 LLM API 호출 단계를 표시해둡니다.
3. 그 지점부터만 큐를 끼워 넣습니다. 전체를 한 번에 바꾸지 않습니다.
4. 소비자를 멱등하게 만들어 재전달된 메시지가 중복 실행되지 않게 합니다.
5. 데드레터 큐와 재처리 경로를 마련해 계속 실패하는 메시지를 격리합니다.
6. 큐 길이·소비 지연·재시도율을 계측해 백프레셔를 눈에 보이게 만듭니다.

 

예제 코드:

# 직접 호출 — A가 B의 실패·지연을 그대로 떠안는다
def run_pipeline(task):
    research = research_agent.run(task)
    report = writer_agent.run(research)  # writer가 느려지면 블로킹
    return report

# 큐 기반 핸드오프 — A는 적재만 하고 끝난다
def run_research_stage(task):
    research = research_agent.run(task)
    save_result(task.id, "research", research)
    queue.publish("writer-stage", {"task_id": task.id})

def writer_worker(message):
    task_id = message["task_id"]
    if get_stage(task_id) != "research_done":
        return  # 중복 전달 방어
    research = load_result(task_id, "research")
    report = writer_agent.run(research)
    save_result(task_id, "writer", report)

 

주의 — 큐를 끼운다고 메시지 순서가 자동으로 보장되지는 않습니다. 순서가 중요한 흐름이라면 파티션 키나 로그 기반 큐로 순서 보장 범위를 명확히 정의하세요. 직접 호출을 쓰더라도 동시 실행 가능한 하위 에이전트 수를 제한하는 세마포어만 추가해도 재시도 폭주를 어느 정도 억제할 수 있습니다.

 

정리

에이전트 간 직접 호출은 구현은 쉽지만 지연·실패·재시도를 그대로 전파시켜 연쇄 장애의 원인이 됩니다. AWS Well-Architected 에이전틱 AI 렌즈는 즉각 응답이 필요한 경우를 제외하면 비동기 메시징을 기본값으로 권고하며 직접 호출을 안티패턴으로 분류합니다. 전환은 한 번에 전체를 바꾸는 게 아니라, 지연이 들쭉날쭉한 경계부터 큐를 끼우고 소비자를 멱등하게 만드는 순서로 진행합니다.
