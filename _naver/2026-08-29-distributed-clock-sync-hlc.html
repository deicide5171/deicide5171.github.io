분산 DB는 '지금'을 어떻게 아는가 — HLC와 TrueTime으로 보는 시간 동기화

데이터베이스

한 줄 요약 — 물리 시계 오차만으로는 분산 트랜잭션 순서를 보장할 수 없어, HLC(Hybrid Logical Clock)는 논리 카운터로 소프트웨어적으로 보정하고, 구글 TrueTime은 하드웨어로 오차를 줄이고 커밋 대기로 순서를 보장합니다.

 

여러 대륙에 흩어진 노드는 '지금'을 어떻게 맞출까요

단일 서버 DB에서는 트랜잭션 순서를 시스템 시계 하나로 자연스럽게 판정할 수 있습니다. 하지만 여러 대륙에 흩어진 노드가 각자 커밋을 수행하는 분산 DB에서는 각 서버의 물리 시계가 수 밀리초에서 수십 밀리초까지 어긋날 수 있고, 이 오차가 순서 판정에 섞이면 미래에 커밋된 트랜잭션이 과거보다 먼저 보이는 인과관계 위반이 생길 수 있습니다.

이 문제를 푸는 접근은 크게 두 갈래로 갈렸습니다. CockroachDB, MongoDB 등이 채택한 HLC와, 구글 Spanner가 쓰는 TrueTime입니다.

 

핵심 개념 1 — HLC, 물리 시각에 논리 카운터를 얹습니다

HLC 타임스탬프는 (물리 시각, 논리 카운터) 쌍으로 구성됩니다. 로컬 이벤트가 발생하면 물리 시각을 로컬 시계값과 이전 HLC 중 큰 쪽으로 갱신하고, 다른 노드의 메시지를 받으면 세 값(로컬 시계, 자신의 이전 HLC, 수신한 HLC) 중 가장 큰 물리 시각으로 맞추고 물리 시각이 같으면 논리 카운터를 증가시킵니다.

이 규칙 덕분에 인과관계가 있는 두 이벤트 사이의 순서는 항상 보장되면서도, 물리 시각과 거의 같은 값을 유지해 사람이 봐도 대략 언제 일어난 일인지 알 수 있습니다.

 

핵심 개념 2 — TrueTime, 불확실성을 API로 노출합니다

구글 Spanner의 TrueTime은 GPS 수신기와 원자시계를 데이터센터에 배치해 물리 시계 오차를 극히 작게 줄이고, 잔여 불확실성을 숨기지 않고 TT.now() API로 [earliest, latest] 구간을 그대로 노출합니다. Spanner는 커밋 시 이 구간의 폭만큼 실제로 대기(commit wait)한 뒤 커밋을 확정해, 커밋 타임스탬프가 실제로 지나간 시각임을 보장합니다.

 

 

구분 HLC TrueTime
핵심 아이디어 물리 시각 + 논리 카운터 하드웨어로 불확실성 축소
필요 인프라 일반 NTP 동기화 GPS·원자시계 전용 배치
대표 사례 CockroachDB, MongoDB Google Spanner

 

예제 — HLC 갱신 로직(의사코드)
def receive_event(self, remote_physical, remote_logical):
    now = wall_clock_ms()
    new_physical = max(now, self.physical, remote_physical)
    if new_physical == self.physical == remote_physical:
        new_logical = max(self.logical, remote_logical) + 1
    elif new_physical == self.physical:
        new_logical = self.logical + 1
    elif new_physical == remote_physical:
        new_logical = remote_logical + 1
    else:
        new_logical = 0
    self.physical, self.logical = new_physical, new_logical
    return (self.physical, self.logical)

원격 메시지를 받을 때마다 가장 앞선 물리 시각으로 자신을 맞추고, 물리 시각이 겹치는 경우에만 논리 카운터로 순서를 세분화하는 것이 핵심입니다.

 

실무 도입 시 이것만은 챙기세요
1. NTP 오차 모니터링을 소홀히 하지 마세요 — HLC 값이 벽시계 시각과 크게 벌어지면 로그 상관관계 분석에 혼란을 줍니다.
2. TrueTime류 도입은 하드웨어 투자가 전제입니다 — 온프레미스라면 HLC 기반 오픈소스 분산 DB가 현실적인 선택지입니다.
3. 커밋 대기 비용을 이해하세요 — TrueTime 방식은 불확실성 구간만큼 커밋을 지연시키므로 시계 동기화 품질이 처리량에 직결됩니다.

 

마무리 — 3줄 요약

① 분산 DB에서 노드별 물리 시계 오차는 트랜잭션 순서에 인과관계 위반을 일으킬 수 있습니다.
② HLC는 물리 시각에 논리 카운터를 얹어 소프트웨어만으로 보정하고, TrueTime은 하드웨어로 오차를 줄이고 커밋 대기로 순서를 보장합니다.
③ 전용 하드웨어 없이 인과관계를 지키고 싶다면 HLC 기반 접근이 실무에서 더 접근하기 쉬운 선택지입니다.
