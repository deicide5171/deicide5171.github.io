방금 쓴 데이터가 안 보이는 이유 — 읽기 전용 복제본과 Read-Your-Writes

2026. 8. 19. · 아키텍처·시스템 설계

한 줄 요약 — 읽기 전용 복제본(Read Replica)을 도입한 뒤 방금 저장한 값이 화면에 안 보이는 문제를, DB 복제 메커니즘이 아니라 애플리케이션의 라우팅·세션 설계 관점에서 어떻게 해결하는지 정리했습니다.

 

왜 지금 이 문제인가

트래픽이 늘면 가장 먼저 손대는 것이 읽기 트래픽 분산입니다. 쓰기는 Primary DB 하나로 보내고, 조회는 Read Replica 여러 대로 나누면 DB 부하가 눈에 띄게 줄어듭니다. 문제는 이 구조를 넣은 다음날부터 시작됩니다. 사용자가 프로필을 수정하고 저장 버튼을 눌렀는데, 곧바로 이어지는 화면에는 수정 전 값이 그대로 보입니다. DB 장애도 코드 버그도 아닙니다. 쓰기는 Primary에 성공적으로 반영됐지만, 그 직후의 조회가 아직 값을 따라잡지 못한 Replica로 라우팅됐을 뿐입니다.

이 현상은 DB 복제가 느려서라기보다, 애플리케이션이 "누가 방금 무엇을 썼는지"를 전혀 모른 채 읽기와 쓰기를 완전히 독립된 요청으로 취급하기 때문에 생깁니다. 복제 지연 자체를 줄이는 것은 인프라·DB 엔진 영역의 과제이고, 이 글에서 다루는 것은 그 지연이 0이 아니라는 전제 위에서 애플리케이션이 사용자 경험을 어떻게 지킬 것인가라는 시스템 설계 문제입니다. 복제 지연을 없애는 이야기가 아니라, 복제 지연이 있어도 "내 화면"만큼은 일관되게 만드는 이야기입니다.

 

핵심 개념: Read-Your-Writes 일관성

분산 시스템의 일관성 모델 중 실무에서 가장 자주 요구되는 것이 read-your-writes(RYW)입니다. "시스템 전체가 항상 최신 상태를 보여줘야 한다"는 강한 일관성이 아니라, "내가 쓴 값은 적어도 내가 다시 읽을 때는 보여야 한다"는 훨씬 실용적인 보장입니다. 다른 사용자가 그 값을 아직 못 보는 것은 대체로 문제가 되지 않지만, 정작 값을 쓴 본인이 자신의 변경을 못 보면 "저장이 안 됐다"는 오해와 중복 제출로 이어집니다.

RYW는 시스템 전체의 강한 일관성보다 비용이 훨씬 낮습니다. 모든 조회를 Primary로 보낼 필요 없이, 이 사용자가 방금 쓴 그 데이터에 한해서만 최신성을 보장하면 되기 때문입니다. 이 범위를 어떻게 좁혀서 구현하느냐가 핵심입니다.

 

세 가지 구현 전략 비교

아래 세 전략은 서로 배타적이지 않으며, 실무에서는 대부분 조합해서 사용합니다.

전략 핵심 아이디어 트레이드오프
Sticky Routing
(세션 고정)		 쓰기 후 일정 TTL 동안 해당 세션의 조회를 Primary로 고정 구현은 단순하나 TTL이 짧으면 여전히 stale read, Primary 부하 증가
버전 토큰 추적 쓰기 응답에 커밋 시점 버전(LSN 등)을 담아 다음 조회에 함께 전달 정확도는 높으나 DB·프로토콜 변경 비용 필요
쓰기 경로
캐시 우회		 쓰기 API 응답 자체에 갱신된 값을 담아 해당 화면만 즉시 반영 보장 범위가 "그 화면"으로 한정, 새로고침·다른 화면은 별도 처리 필요

 

실무에서는 쓰기 API 응답에 갱신된 값을 그대로 담아 화면을 즉시 채우고(전략 3), 이어지는 후속 조회 몇 건에 한해서는 세션을 짧게 Primary에 고정하는(전략 1) 조합이 흔합니다. 버전 토큰 추적(전략 2)은 정확도가 가장 높지만 비용이 있어, RYW 위반이 곧바로 사고로 이어지는 결제·잔액 같은 도메인에 우선 적용하는 경우가 많습니다.

 

예제: 세션 고정 라우팅 미들웨어 (TypeScript/Express)

아래는 쓰기 요청 이후 일정 시간 동안 같은 세션의 조회를 Primary로 고정하는 미들웨어 예시입니다. TTL 값은 임의로 정하지 않고 실제 복제 지연 모니터링 지표를 근거로 설정해야 합니다.

// 쓰기 요청 이후 일정 시간 동안 이 세션의 조회를 Primary로 고정한다
const STICKY_WINDOW_MS = 5000; // 복제 지연 관측치보다 여유 있게 설정

function stickyRoutingMiddleware(req, res, next) {
  const session = req.session;

  // 이번 요청이 쓰기(POST/PUT/PATCH/DELETE)라면 타임스탬프 기록
  if (["POST", "PUT", "PATCH", "DELETE"].includes(req.method)) {
    res.on("finish", () => {
      if (res.statusCode < 400) {
        session.lastWriteAt = Date.now();
      }
    });
  }

  // 최근 쓰기 이력이 있으면 이번 요청은 Primary로 라우팅
  const withinWindow =
    session.lastWriteAt && Date.now() - session.lastWriteAt < STICKY_WINDOW_MS;

  req.dbTarget = withinWindow ? "primary" : "replica";
  next();
}

서버가 여러 대라면 세션 상태를 Redis 같은 공유 저장소에 두어야 인스턴스마다 라우팅 결정이 달라지지 않습니다.

 

실무 도입 시 이것만은 챙기세요
1. 모든 읽기에 같은 보장을 적용하지 않는다 — RYW가 필요한 건 "방금 이 사용자가 쓴 데이터"뿐, 무관한 목록·통계 조회까지 Primary로 몰지 않기
2. TTL·윈도우 값은 실측 지연 지표에 근거해 정한다 — 확인 안 된 값을 하드코딩하면 트래픽 패턴이 바뀔 때 재발 가능
3. 세션 고정은 상태 저장소를 공유해야 한다 — 서버가 여러 대면 Redis 등 공유 세션 저장소 필요
4. 모바일 앱처럼 세션 개념이 약한 클라이언트는 버전 토큰 방식이 더 잘 맞는 경우가 많음
5. 결제·재고처럼 오류 비용이 큰 도메인은 애플리케이션 레벨에서 명시적으로 제어, 무해한 도메인은 프록시 레벨 일괄 규칙에 위임

 

마무리 — 3줄 요약

① Read-Your-Writes는 시스템 전체의 강한 일관성이 아니라 "내가 쓴 값은 내가 본다"는 좁고 실용적인 보장입니다.
② Sticky Routing, 버전 토큰 추적, 쓰기 경로 캐시 우회는 서로 배타적이지 않으며 도메인 민감도에 따라 조합해서 적용합니다.
③ TTL·라우팅 규칙은 실측 복제 지연 지표에 근거해 설정하고, 정기적으로 재검토해야 재발을 막을 수 있습니다.
