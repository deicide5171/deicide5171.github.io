"해외 모델은 쓰면 안 된다는데요" — 코딩 에이전트를 벤더에 종속되지 않게 설계하는 법

AI

한 줄 요약 — DeepSeek의 새 코딩 에이전트 출시로 '해외 모델 금지' 요구가 실제 설계 문제가 됐습니다. 모델 교체 가능성을 API 키 교체가 아니라 어댑터 레이어·데이터 분류·평가 게이트 수준에서 설계하는 법을 정리했습니다.

 

왜 지금 이 판단이 필요한가

"저희 보안팀이, 코드가 해외 리전에 저장될 수 있는 모델은 에이전트 백엔드로 못 쓰게 막아달라고 해요. 근데 다음 분기엔 또 다른 리전 요구가 올 수도 있다는데, 그때마다 에이전트를 새로 짜야 하나요?" — 이런 요청은 더 이상 가정이 아닙니다. 중국 DeepSeek이 미국 벤더가 장악한 개발자 도구 시장을 겨냥한 강화된 코딩 에이전트를 웹과 API로 공개했고, 곧이어 보안 업계에서는 이 모델이 사용자 데이터를 중국 내에 저장하며 현지 법에 따른 정부 접근 가능성이 있다는 점, 또 학습 데이터가 공개되지 않아 생성된 코드에 알려지지 않은 보안 취약 패턴이 섞여 들어갈 수 있다는 점을 경고했습니다. 동시에 GitHub Copilot과 Cursor 같은 상용 도구가 이미 DeepSeek을 모델 백엔드 선택지 중 하나로 문서화해 제공한다는 점도 함께 알려졌습니다.

이 둘을 겹쳐 보면 결론은 하나입니다 — "모델을 바꿀 수 있어야 한다"는 요구는 이제 특정 기업의 특수 사정이 아니라, 코딩 에이전트를 조직에 들이는 모든 빌더가 마주치는 기본 요구사항이 됐습니다. 문제는 이 요구를 "API 키만 바꾸면 되는 일"로 받아들이는 순간 생깁니다. 실제로는 프롬프트 포맷, 도구 호출 스키마, 품질 평가 기준, 로그가 쌓이는 리전까지 여러 층이 얽힌 문제이고, 이 층들을 미리 분리해 두지 않으면 벤더를 바꾸는 날 에이전트 전체를 다시 설계해야 합니다.

 

전체 시스템에서의 위치

"모델을 바꿀 수 있게 해달라"는 말은 대개 오케스트레이션 코드 안에 벤더 SDK를 직접 호출하는 구조에서 나옵니다. 이 구조에서는 프롬프트 문자열, 도구(tool) 정의 JSON, 응답 파싱 로직이 전부 특정 벤더의 API 형태에 맞춰져 있습니다. 벤더를 바꾸면 이 세 가지를 전부 다시 쓰고, 그 과정에서 생긴 회귀를 사람이 수작업으로 찾아야 합니다. 어느 코드가 어느 리전으로 나갔는지도 사후에 로그를 뒤져야 알 수 있습니다.

해결 구조는 오케스트레이션과 벤더 API 사이에 모델 어댑터 레이어를 끼워 넣는 것입니다. 어댑터는 세 가지 일을 합니다. 첫째, 프롬프트와 도구 스키마를 벤더 중립 포맷으로 받아 각 벤더 형식으로 번역합니다. 둘째, 응답을 다시 공통 포맷으로 되돌립니다. 셋째, 어떤 데이터(코드 스니펫, 레포 경로, 사용자 식별자)가 그 벤더로 나가는지를 분류해 차단·마스킹 여부를 결정합니다. 이 어댑터가 데이터 분류 정책과 맞물려야 "이 모델은 국내 리전만", "이 모델은 사용 금지" 같은 규칙을 코드 변경 없이 설정값으로 적용할 수 있습니다. 모델 포터빌리티는 코딩 스타일의 문제가 아니라 오케스트레이션과 벤더 사이에 경계 하나를 추가로 긋는 아키텍처 결정입니다.

 

선택의 트레이드오프
방식전환 비용데이터 통제언제 쓰면 안 되는가
벤더 SDK 직접 호출초기엔 낮음없음(사후 로그 추적만)벤더가 둘 이상이 될 가능성이 조금이라도 있을 때
LLM 게이트웨이·어댑터 레이어중간설정 가능(정책 레벨)벤더 특화 기능에 핵심 경로가 깊이 의존할 때
완전 자체 호스팅높음가장 높음(물리적 경계)품질 격차를 감수할 수 없는 핵심 제품 경로

 

트레이드오프의 핵심은 "어느 모델이 더 똑똑한가"가 아니라 "코드와 로그가 어디로, 누구의 법 아래로 나가는지를 누가 언제 결정하느냐"입니다. 어댑터 레이어를 두면 이 결정을 배포 시점 설정으로 미룰 수 있지만 공짜는 아닙니다. 벤더마다 다른 도구 호출 방식(병렬 호출 지원 여부, 스트리밍 포맷, 긴 컨텍스트 캐싱 방식)을 하나의 공통 스키마로 수렴시키는 과정에서 일부 벤더 고유 최적화는 포기해야 합니다.

 

실제 진행 순서
interface ModelAdapter {
  translateRequest(req: CommonAgentRequest): ProviderRequest;
  translateResponse(res: ProviderResponse): CommonAgentResponse;
  dataPolicy: { allowedRegions: string[]; maskFields: string[] };
}

1) 데이터 분류부터 합니다 — 코드 스니펫 / 레포 경로·커밋 메타데이터 / 사용자 식별자·로그로 나누고 각각에 "국내 리전만", "마스킹 후 전송", "전송 금지" 라벨을 붙입니다. 2) 공통 스키마를 먼저 고정합니다 — 이미 쓰는 벤더 스키마를 기준 삼되, 다른 벤더가 지원하지 않는 필드는 옵셔널로 둡니다. 3) 두 번째 벤더는 섀도 모드로 먼저 붙여, 품질 회귀를 평가 게이트로 수치화합니다. 4) 로깅·텔레메트리 목적지를 벤더·리전별로 분리합니다. 5) 전환 완료 기준을 수치로 정해 둡니다 — 기준 없이 가면 전환은 영원히 보류됩니다.

 

주의 — 데이터 분류표 없이 어댑터부터 만들면 나중에 정책을 코드에 다시 박아 넣어야 합니다. 분류가 항상 먼저입니다.
