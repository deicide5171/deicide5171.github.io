쿠버네티스 Pod가 자꾸 재시작될 때 — OOMKilled 진단하기

인프라

한 줄 요약 — CPU limit 초과는 느려질 뿐이지만, 메모리 limit 초과는 즉시 프로세스가 강제 종료(OOMKilled)됩니다. 이 차이를 모르면 아무리 값을 조정해도 문제가 반복됩니다.

 

증상: 이유 없이 재시작하는 Pod

운영 중인 Pod가 계속 재시작을 반복합니다. kubectl describe pod로 확인하면 Last State: Terminated, Reason: OOMKilled가 찍혀 있는데, 애플리케이션 로그에는 특별한 에러가 없습니다. 이는 애플리케이션 버그가 아니라 대부분 리소스 설정과 리눅스 cgroup 메모리 제한이 부딪히는 문제입니다.

 

requests vs limits, 서로 다른 일을 한다
항목 작동 시점 동작
requests 스케줄링 시점 이 자원이 확보된 노드에만 배치
limits(CPU) 실행 중 상시 초과 시 스로틀링(느려짐)만 발생
limits(메모리) 실행 중 상시 초과 시 즉시 강제 종료

 

잘못된 설정 vs 올바른 설정

가장 흔한 실수는 limits를 아예 설정하지 않는 것입니다. 한 Pod가 메모리를 무한정 늘려 같은 노드의 다른 Pod까지 함께 죽이는 이웃 사고가 발생합니다. 반대로 QoS를 Guaranteed로 만들려고 requests와 limits를 완전히 똑같이 맞추면, JVM처럼 GC 시점에 메모리 사용량이 출렁이는 애플리케이션은 스파이크 순간 바로 OOMKilled가 납니다.

올바른 접근은 requests보다 limits를 1.5~2배 여유 있게 잡아 버스트를 흡수하는 것입니다. 자바라면 -XX:MaxRAMPercentage 옵션으로 힙을 컨테이너 limit의 비율로 자동 계산하게 하면 유지보수가 쉬워집니다.

주의 — 값을 추측하지 말고, kubectl top pod나 Prometheus의 container_memory_working_set_bytes 지표로 최소 1~2주간 실제 사용 패턴을 관찰한 뒤 정하세요.

 

실무 포인트

OOMKilled와 CrashLoopBackOff는 다릅니다. OOMKilled는 원인, CrashLoopBackOff는 그 결과로 반복 재시작하는 상태 표시일 뿐입니다. 또한 사이드카 컨테이너(로그 수집기, 서비스 메시 프록시)도 별도 limit을 가진다는 점을 잊으면 전체 Pod 메모리 예산 계산이 틀어집니다.

VPA 추천값도 특정 시점 스냅샷 기반이라 트래픽이 주기적으로 변하는 서비스에서는 피크 상황을 놓칠 수 있으니 참고만 하는 것이 안전합니다.
