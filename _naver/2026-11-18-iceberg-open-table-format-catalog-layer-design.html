"여러 엔진이 같은 데이터를 봐야 해요" — Iceberg 오픈 테이블 포맷과 카탈로그 계층 설계

시스템 설계

한 줄 요약 — 오픈 테이블 포맷 경쟁은 Iceberg로 정리됐고, 남은 결정은 카탈로그 계층입니다. 여러 엔진이 실제로 같은 데이터를 동시에 읽고 쓸 때만 이 계층을 도입하고, 벤더 종속 여부에 따라 관리형 카탈로그와 오픈 카탈로그 중 고르면 됩니다.

 

왜 지금 이 판단이 필요한가

"Spark 배치로 적재한 데이터를, 분석가는 DuckDB로 가볍게 보고 싶어 하고 BI 툴은 Snowflake에서 조회하고 싶어 해요. 같은 데이터인데 왜 복사본을 세 개나 만들어야 하나요?"라는 요구는 단일 엔진 분석 구조가 한계에 닿는 지점을 정확히 짚습니다. 분석 엔진을 서비스 DB에서 분리하는 단계까지는 많은 팀이 이미 지났지만, 그다음 단계인 "여러 엔진이 같은 물리 데이터를 동시에 읽고 쓴다"는 요구는 엔진 선택이 아니라 데이터가 저장되는 포맷 자체의 설계를 요구합니다.

이 영역은 최근 들어 구도가 명확해졌습니다. 테이블 포맷 경쟁은 사실상 Apache Iceberg 쪽으로 정리됐다는 평가가 업계에 자리 잡았고, Apache Polaris가 2026년 2월 Apache 최상위 프로젝트로 졸업했으며, Snowflake는 2026년 11월 1일 Horizon Catalog의 워크로드 아이덴티티 연합 기반 교차 계정 읽기·쓰기를 정식 출시해 비밀키 공유 없이 다른 계정의 Iceberg 테이블에 접근할 수 있게 했습니다. 포맷 전쟁이 끝나고 "어떤 카탈로그를 쓸 것인가"가 경쟁의 축이 됐다는 뜻입니다.

 

전체 시스템에서의 위치

레이크하우스 구조에서 데이터는 원천에서 출발해 Iceberg 같은 오픈 테이블 포맷으로 오브젝트 스토리지에 쌓입니다. 물리 파일 자체는 어떤 엔진도 직접 읽을 수 있지만, "지금 이 테이블의 최신 스냅샷이 어떤 파일들로 구성되는지"를 중재하는 계층이 바로 카탈로그입니다. 카탈로그 없이 여러 엔진이 같은 테이블을 건드리면 서로 다른 시점의 메타데이터를 참조해 정합성 문제가 생깁니다.

 

선택의 트레이드오프
방식락인운영 부담교차 엔진 호환성
카탈로그 없이 엔진별 메타스토어낮음낮음(초기)매우 낮음 — 동시 쓰기 시 정합성 깨짐
벤더 관리형 카탈로그높음낮음벤더 생태계 안에서는 높음
오픈 카탈로그 자체 호스팅(Polaris)낮음높음표준 REST API 기준 높음

 

이미 특정 벤더에 데이터 웨어하우스가 묶여 있다면 그 벤더의 관리형 카탈로그로 시작하는 쪽이 이득이 큽니다. 여러 클라우드·벤더 엔진을 혼용해야 한다면 Polaris 같은 오픈 카탈로그를 직접 운영하는 비용을 감수할 가치가 있습니다. 엔진이 하나뿐이고 당분간 늘어날 계획이 없다면 이 계층 자체가 과한 설계라는 점이 중요합니다.

 

실제 프로젝트 진행 순서

가장 먼저 확인할 것은 "정말로 여러 엔진이 같은 테이블을 동시에 읽고 쓰는가"입니다. 이 요구가 실제로 확인되면 테이블 포맷은 Iceberg로 고정합니다.

1. 적재 파이프라인의 출력 포맷을 Iceberg 테이블로 변경
2. 카탈로그 선택: 벤더 종속 있으면 관리형, 벤더 중립 필요하면 Polaris self-host
3. 교차 계정 인증을 비밀키 공유 대신 WIF 방식으로 설계
4. 스키마 진화·컴팩션 책임 주체를 하나로 명확히 지정
5. 두 번째 엔진을 연결해 동시 쓰기 충돌 시나리오를 직접 재현

마지막 단계를 건너뛰고 바로 운영에 들어가면, 두 엔진이 동시에 컴팩션을 트리거하거나 스키마를 서로 다르게 변경하는 충돌이 실제 트래픽에서야 발견되는 경우가 많습니다. 카탈로그 계층의 가치는 설계 문서가 아니라 이 충돌 시나리오를 실제로 막아내는지로 검증해야 합니다.

 

주의 — 엔진이 하나뿐인데 "나중에 확장할 수도 있으니까"라는 이유로 카탈로그 계층부터 도입하지 마세요. 실제 다중 엔진 요구가 생긴 뒤에 도입해도 늦지 않습니다.
