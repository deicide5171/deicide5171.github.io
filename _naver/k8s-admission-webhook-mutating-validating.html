Kubernetes Admission Webhook 내부 동작 — Mutating과 Validating으로 클러스터 정책 강제하기

인프라

한 줄 요약 — API 서버가 오브젝트를 저장하기 직전 Mutating·Validating 두 단계로 요청을 검사·수정하는 Admission Webhook의 처리 파이프라인과 실패 모드를 정리했습니다.

 

왜 지금 승인 단계를 다시 봐야 하는가

RBAC은 "누가 어떤 리소스에 어떤 동작을 할 수 있는가"를 결정하지만, "그 요청의 내용이 규칙에 맞는가"는 전혀 검사하지 않습니다. 개발자에게 파드 생성 권한이 있어도, latest 태그 이미지를 쓰거나 리소스 requests/limits를 아예 설정하지 않은 매니페스트를 RBAC은 막지 못합니다. Kubernetes API 서버는 이 틈을 메우기 위해 요청이 etcd에 저장되기 직전 마지막 관문으로 Admission Webhook을 제공합니다.

 

요청이 etcd에 도달하기까지의 파이프라인

kubectl apply로 보낸 요청은 인증 → 인가(RBAC) → 어드미션 컨트롤 순으로 통과해야 합니다. 먼저 Mutating Admission Webhook들이 순서대로 실행되며 오브젝트를 수정하고(사이드카 자동 주입 등), 스키마 검증을 거친 뒤 Validating Admission Webhook들이 병렬로 실행되며 검사만 하고 거부하거나 통과시킵니다. Validating 단계는 수정 후 최종 오브젝트를 기준으로 검사한다는 점이 중요합니다.

웹훅은 결국 외부 HTTP 서버다

Admission Webhook의 실체는 API 서버가 HTTPS로 호출하는 외부 서버입니다. API 서버는 AdmissionReview 오브젝트를 보내고, 웹훅 서버는 허용 여부(및 JSON Patch)를 담아 응답합니다. 이 구조 때문에 웹훅 서버의 가용성이 곧 클러스터의 파드 생성 가용성과 직결됩니다. failurePolicy를 Fail로 두면 웹훅이 응답하지 않을 때 요청 전체가 막히고, Ignore로 두면 검증 없이 통과됩니다.

설정 웹훅 다운 시 적합한 용도
failurePolicy: Fail 요청 전체 거부 보안·컴플라이언스
failurePolicy: Ignore 검증 생략 통과 부가 기능

 

리소스 제한 강제 웹훅 설정 예제
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: require-resource-limits
webhooks:
  - name: resource-limits.example.com
    clientConfig:
      service:
        name: policy-webhook-svc
        namespace: policy-system
        path: "/validate-pods"
    rules:
      - apiGroups: [""]
        operations: ["CREATE"]
        resources: ["pods"]
    failurePolicy: Fail
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: ["kube-system"]

namespaceSelector로 시스템 네임스페이스를 제외하지 않으면, 웹훅 배포 자체가 자기 자신 때문에 막히는 교착 상태에 빠질 수 있습니다.

 

실무 포인트

웹훅 서버는 반드시 고가용성으로 배포해야 합니다. failurePolicy: Fail을 쓴다면 레플리카가 한 대뿐일 때 재시작되는 짧은 순간 클러스터 전체의 파드 생성이 멈출 수 있습니다.

타임아웃을 짧게 설정해야 합니다. 기본 10초 동안 웹훅이 응답하지 않으면 요청 전체가 지연되므로, 1~2초 이내 응답하도록 로직을 가볍게 유지해야 합니다.

주의 — 대부분의 정책 강제 요구사항은 이미 성숙한 OPA Gatekeeper·Kyverno 같은 정책 엔진으로 선언적으로 표현 가능하니, 직접 웹훅 서버를 만들기 전에 먼저 검토해야 합니다.
