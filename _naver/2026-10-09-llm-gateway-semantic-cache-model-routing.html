여러 모델에 걸쳐 호출할 때 — LLM 게이트웨이의 캐시·라우팅·장애 격리 레이어 설계

시스템 설계

한 줄 요약 — Claude도 쓰고 GPT도 쓰는데 특정 제공자가 느려지거나 장애 나면 자동으로 넘어가고 비용도 줄여달라는 요구는, 호출 지점에 게이트웨이 한 층을 끼워 넣는 설계 문제로 번역됩니다. 시맨틱 캐시를 라우터 앞에 두는 표준 레이어 구성과, 어디까지 직접 구축하고 어디서부터 기존 제품에 맡길지의 트레이드오프를 정리했습니다.

 

왜 지금 이 판단이 불거지는가

"우리 서비스가 지금은 Claude만 쓰는데, GPT나 Gemini도 섞어 쓰고 싶고, 한쪽이 느려지거나 장애 나면 자동으로 다른 쪽으로 넘어가게 해주세요. 그리고 비용도 좀 줄여주세요." 프로덕션에 LLM을 올린 지 몇 달만 지나면 반드시 듣게 되는 요구입니다. 처음엔 각 제공자 SDK를 if-else로 분기하는 코드 한 줄로 시작하지만, 제공자가 둘 셋으로 늘고 재시도·레이트리밋·비용 추적까지 겹치면 이 분기 로직은 금세 감당 못 할 크기로 불어납니다.

이 문제를 애플리케이션 코드가 아니라 별도의 LLM 게이트웨이 계층으로 분리하는 패턴이 자리 잡았습니다. 애플리케이션과 여러 모델 제공자 사이에 인증, 요청 라우팅, 응답 캐싱, 레이트리밋, 장애 복구를 한 곳에서 처리하는 추상화 층을 두는 구조입니다. Redis가 공개한 아키텍처 가이드는 이 게이트웨이 안에서도 시맨틱 캐시를 라우터보다 앞에 두라고 권고합니다. 캐시 히트가 나면 모델 선택도, 실제 LLM 호출도 건너뛰기 때문에 캐시가 가장 먼저 거치는, 가장 저렴한 체크포인트가 되어야 한다는 논리입니다. LiteLLM, Portkey, OpenRouter 같은 제품이 이미 이 구조를 제품화해 놓은 지금, 직접 짤지 기존 제품에 올라탈지를 판단해야 하는 시점이 됐습니다.

 

요구사항을 기술 문제로 번역하기

"여러 모델 호출을 관리해주세요"는 사실 하나의 문제가 아니라 서로 독립적으로 결정해야 하는 네 가지 관심사가 섞여 있습니다. 첫째는 인증·비용 추적, 둘째는 캐싱(의미적으로 같은 질문에 모델을 다시 호출하지 않기), 셋째는 라우팅(이 요청에 어떤 제공자·모델이 비용 대비 품질이 가장 좋은가), 넷째는 장애 격리(한 제공자가 느려지거나 죽었을 때 트래픽을 다른 쪽으로 넘기기)입니다. 이 네 가지를 하나의 래퍼 함수에 욱여넣으면 캐시 정책을 바꿀 때마다 라우팅 로직까지 건드리게 되는 결합이 생깁니다. 그래서 실제 작업은 "게이트웨이 하나 만들어주세요"가 아니라, 이 네 관심사를 순서가 있는 파이프라인의 독립된 단계로 분리해 설계하는 문제로 번역됩니다.

 

전체 시스템에서의 위치

 

이 구조에서 게이트웨이는 애플리케이션 코드와 여러 모델 제공자 API 사이의 통제 계층에 위치합니다. 앞단에서 들어온 요청은 먼저 인증·쿼터 체크를 통과하고, 그다음 시맨틱 캐시에서 의미적으로 동일한 과거 질의가 있었는지 확인합니다. 캐시 미스일 때만 라우터로 넘어가 어떤 제공자·모델을 쓸지 결정하고, 실제 호출 직전에 서킷 브레이커가 해당 제공자의 최근 에러율을 확인해 임계치를 넘겼으면 다른 제공자로 폴백합니다. 뒷단에는 Claude, GPT, Gemini 같은 외부 제공자와 필요하다면 자체 호스팅 모델이 있습니다. 게이트웨이를 빼면 이 네 가지 결정이 애플리케이션 코드 곳곳에 흩어져, 제공자를 하나 추가할 때마다 호출부 전체를 다시 손봐야 하는 상태로 남습니다.

 

선택의 트레이드오프
접근 셀프호스팅 시맨틱 캐시 적합한 상황
직접 구축(사내 게이트웨이) 완전 자체 운영 직접 구현 필요 요구사항이 특수하거나 규제가 엄격한 경우
LiteLLM(오픈소스) 자체 운영 Redis 연동 기본 수준 초기 비용을 낮추고 직접 제어하고 싶은 경우
OpenRouter(SaaS) 불필요 미지원 여러 모델을 빠르게 실험해보려는 경우
Portkey(관리형/셀프호스팅) 선택 가능 전용 구현 캐싱·라우팅을 제품 수준으로 바로 쓰고 싶은 경우

 

직접 구축하면 네 관심사를 서비스 특성에 맞게 세밀히 조정할 수 있지만, 서킷 브레이커 임계치나 캐시 유사도 threshold 같은 세부 튜닝을 처음부터 다 맞혀야 하는 부담이 큽니다. 반대로 SaaS형 게이트웨이는 빠르게 시작할 수 있지만 캐싱 같은 핵심 기능이 아예 없거나 벤더의 라우팅 로직에 트래픽 흐름을 맡기게 됩니다. 트래픽이 적을 때는 캐싱·라우팅 없이 인증과 로깅만 하는 얇은 프록시로 시작하고, 호출량과 비용이 실제로 문제가 될 때 레이어를 하나씩 추가하는 편이 과도한 선행 투자를 피하는 길입니다.

 

실제 프로젝트 진행 순서

1단계: 인증·로깅·비용 집계만 하는 가장 단순한 프록시부터 시작합니다.

2단계: 실패율을 관찰하며 서킷 브레이커와 폴백을 캐싱보다 먼저 추가합니다.

3단계: 중복 질의 패턴이 실제로 관찰될 때만 보수적인 threshold로 캐시를 도입합니다.

4단계: 비용·품질 트레이드오프가 분명해지면 캐스케이딩부터, 이후 시맨틱 라우팅을 추가합니다.

5단계: 라우팅 정확도를 프로덕션 전에 평가 하네스로 검증합니다.

6단계: 캐시 히트 여부, 선택된 라우팅 전략, 실제 호출 제공자를 요청 단위로 전부 로그에 남깁니다.

model_list:
  - model_name: primary-chat
    litellm_params:
      model: anthropic/claude-sonnet
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: fallback-chat
    litellm_params:
      model: openai/gpt-5
      api_key: os.environ/OPENAI_API_KEY

router_settings:
  routing_strategy: "latency-based"
  fallbacks:
    - primary-chat: ["fallback-chat"]
  cooldown_time: 60
  allowed_fails: 3

 

주의 — 시맨틱 캐시는 의미적으로 같은 질문에 몇 달 전 답을 그대로 돌려줄 수 있습니다. 대화 맥락이 섞이는 멀티턴 요청이나 최신 정보가 중요한 질의는 캐시 대상에서 제외하세요. 유사도 threshold는 실제 트래픽에서 오탐·누락 사례를 수집하며 점진적으로 조정해야 하고, 벤더가 제시하는 비용 절감 수치는 대부분 자체 측정이므로 자사 트래픽으로 직접 검증한 뒤 도입 여부를 판단하세요.

 

정리

"여러 모델 호출을 관리해주세요"는 인증·캐싱·라우팅·장애 격리라는 네 개의 독립된 관심사로 분해해, 순서가 있는 게이트웨이 파이프라인으로 설계하는 문제로 번역됩니다. 게이트웨이는 애플리케이션과 여러 모델 제공자 사이의 통제 계층에 위치하며, 시맨틱 캐시를 라우터보다 앞에 두는 구성이 비용 절감 관점에서 효율적입니다. 도입은 단순 프록시 → 서킷 브레이커 → 캐시 → 라우팅 순으로, 트래픽이 실제로 문제를 드러낼 때마다 한 층씩 추가하는 것이 안전합니다.
