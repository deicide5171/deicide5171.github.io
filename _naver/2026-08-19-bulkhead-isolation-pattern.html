벌크헤드 패턴 — 한 서비스 장애가 전체를 침몰시키지 않는 격리 설계

2026. 8. 19. · 아키텍처·시스템 설계

한 줄 요약 — 의존성 하나가 느려질 때 스레드풀·커넥션풀이 통째로 고갈되어 서비스 전체가 멈추는 문제를, 배의 격벽처럼 리소스를 나눠서 막는 벌크헤드(Bulkhead) 패턴을 정리했습니다.

 

왜 지금 이 패턴인가

MSA 환경에서 서비스 하나는 보통 여러 다운스트림 의존성(다른 API, DB, 외부 서비스)을 호출합니다. 문제는 이 호출들이 같은 스레드풀, 같은 커넥션풀을 공유하는 경우가 많다는 점입니다. 의존성 중 하나가 느려지면 그 요청을 처리하던 스레드와 커넥션이 반환되지 못하고 계속 쌓이고, 결국 풀 전체가 고갈되어 그 의존성과 아무 상관없는 요청까지 처리하지 못하는 상황이 벌어집니다.

벌크헤드는 배의 격벽(隔壁)에서 이름을 따온 패턴입니다. 배 밑바닥에 구멍이 나도 격벽으로 나뉜 구획 하나만 침수되고 배는 가라앉지 않습니다. 소프트웨어에서도 의존성별로 스레드풀·커넥션풀을 물리적으로 분리해두면, 한 의존성의 장애가 그 구획 안에서만 소진되고 다른 요청 처리 능력은 그대로 남습니다. 서킷 브레이커가 "장애 난 대상으로의 호출을 끊는" 역할이라면, 벌크헤드는 그보다 앞서 "장애의 영향 범위를 물리적으로 제한"하는 역할이라는 점이 다릅니다.

 

 

격리 전략: 스레드풀 격리 vs 세마포어 격리

벌크헤드를 구현하는 방식은 크게 두 가지입니다. 스레드풀 격리는 의존성 호출마다 별도 스레드풀에서 실행해 큐까지 분리하는 방식이고, 세마포어 격리는 호출 스레드를 그대로 쓰되 동시 실행 수만 카운터로 제한하는 방식입니다.

구분 스레드풀 격리 세마포어 격리
타임아웃 처리 호출 스레드와 분리되어 즉시 반환 가능 실행 중인 호출을 강제로 끊기 어려움
오버헤드 스레드 전환 비용 발생 상대적으로 가벼움
적합한 상황 신뢰하기 어려운 외부 호출 지연이 짧고 예측 가능한 내부 호출

 

어느 레벨에서 격리할 것인가

"격리"는 여러 층위에 적용할 수 있습니다. 스레드풀 레벨부터 시작해 커넥션풀, 프로세스·컨테이너, 나아가 서비스(MSA 경계) 단위까지 조합해서 쓰는 경우가 많습니다. 작게는 스레드풀 하나를 나누는 것부터 시작해서, 조직이 감당할 수 있는 만큼 상위 레벨로 확장하는 것이 현실적인 접근입니다.

 

예제: Resilience4j로 스레드풀 벌크헤드 적용하기 (Java)

아래는 특정 의존성(serviceY) 호출만 전용 스레드풀에서 실행하도록 격리하는 기본 패턴입니다.

@Bean
public ThreadPoolBulkheadRegistry threadPoolBulkheadRegistry() {
    ThreadPoolBulkheadConfig configForServiceY = ThreadPoolBulkheadConfig.custom()
            .maxThreadPoolSize(10)
            .coreThreadPoolSize(5)
            .queueCapacity(20)
            .build();

    return ThreadPoolBulkheadRegistry.of(Map.of("serviceY", configForServiceY));
}

// 호출부: serviceY 전용 풀에서만 실행
public CompletableFuture<Response> call(Request request) {
    return bulkhead.executeSupplier(() -> restClient.post(request));
}

serviceY 전용 풀을 별도로 정의해두면, 이 의존성이 응답을 지연시켜도 대기·거부가 이 풀 안에서만 발생하고 다른 의존성 호출은 영향을 받지 않습니다. 커넥션풀도 마찬가지로, 주문 처리 DB와 리포트 집계 DB를 같은 풀로 묶지 않고 HikariCP 풀을 용도별로 분리하면 무거운 리포트 쿼리가 주문 처리 커넥션까지 잡아먹는 상황을 막을 수 있습니다.

 

실무 도입 시 이것만은 챙기세요
1. 풀 크기는 추정치에서 시작 — 코드의 수치는 예시일 뿐, 실제 값은 부하 테스트로 맞춰야 합니다
2. 풀 사용률·큐 대기·거부 횟수를 모니터링 — 조용히 거부되기 시작하면 원인 파악이 늦어집니다
3. 가장 흔한 안티패턴은 "편의상 풀 공유" — 새 의존성을 기존 공용 풀에 얹는 순간 격리 효과가 사라집니다
4. 타임아웃 → 벌크헤드 → 서킷 브레이커 → 재시도 순으로 계층화 — 벌크헤드로 반경을 제한하고, 서킷 브레이커로 무의미한 호출을 끊고, 재시도는 그 뒤에서 짧게만 수행합니다

 

마무리 — 3줄 요약

① 벌크헤드 패턴은 의존성별로 스레드풀·커넥션풀 같은 리소스를 물리적으로 분리해 한 곳의 장애가 다른 요청 처리 능력까지 갉아먹지 않게 만드는 격리 전략입니다.
② 구현은 스레드풀 격리와 세마포어 격리 두 방식이 있으며, 신뢰도가 낮은 외부 호출일수록 스레드풀 격리가 유리합니다.
③ 타임아웃·벌크헤드·서킷 브레이커·재시도를 계층적으로 조합해야 연쇄 장애를 실질적으로 예방할 수 있습니다.
