React Server Components 내부 동작 원리 — 서버와 클라이언트 경계는 어떻게 나뉘나

프론트엔드

한 줄 요약 — RSC는 HTML이 아니라 독자적인 직렬화 포맷(RSC Payload)으로 서버 트리를 전달합니다. use client 경계의 실제 동작 원리를 정리했습니다.

 

왜 지금 RSC 내부 동작을 알아야 하는가

Next.js App Router를 쓰다 보면 use client를 어디에 붙여야 하는지, 왜 서버 컴포넌트에서 useState를 쓰면 에러가 나는지 같은 표면적 규칙은 금방 외울 수 있습니다. 하지만 RSC가 실제로 무엇을 서버에서 클라이언트로 전달하는지를 이해하지 못하면 번들 최적화나 데이터 페칭 구조 설계에서 잘못된 판단을 내리기 쉽습니다.

 

RSC가 실제로 전달하는 것은 HTML이 아니다

전통적인 SSR은 완성된 HTML 문자열을 클라이언트에 보냅니다. RSC는 다릅니다. 서버 컴포넌트는 렌더링 결과를 React 고유의 직렬화 포맷("RSC Payload" 또는 "Flight" 포맷)으로 직렬화해 전송합니다. 클라이언트 컴포넌트가 등장하는 지점에는 실제 렌더 결과 대신 "이 모듈을 로드해 끼워 넣어라"는 참조만 담깁니다.

이 방식 덕분에 클라이언트는 서버 컴포넌트가 사용한 라이브러리 코드를 전혀 다운로드하지 않아도 됩니다. RSC의 핵심 이점은 서버 전용 코드가 클라이언트 번들에 전혀 포함되지 않는다는 점입니다.

 

use client는 경계선이지 컴포넌트 속성이 아니다

use client를 붙이면 그 파일이 export하는 컴포넌트와 import하는 모든 하위 모듈이 클라이언트 번들에 포함되는 경계가 그어집니다. 그 지점부터 트리 아래쪽 전체가 클라이언트 모듈 그래프에 편입됩니다. 반대로 클라이언트 컴포넌트는 서버 컴포넌트를 직접 import할 수 없습니다.

상황 가능 여부 이유
서버 컴포넌트가 클라이언트 컴포넌트를 렌더 가능 참조만 Payload에 담김
클라이언트가 서버 컴포넌트를 import 불가능 이미 클라이언트 번들 그래프에 편입됨
서버 컴포넌트를 children으로 전달 가능 이미 렌더된 결과로 전달됨

 

예제 — children 패턴으로 서버 컴포넌트 끼워 넣기
// ClientWrapper.jsx ('use client')
'use client';
export default function ClientWrapper({ children }) {
  const [open, setOpen] = useState(false);
  return (
    <div onClick={() => setOpen(!open)}>
      {open && children}
    </div>
  );
}

// page.jsx (서버 컴포넌트)
import ClientWrapper from './ClientWrapper';
import ServerHeavyContent from './ServerHeavyContent';

export default function Page() {
  return (
    <ClientWrapper>
      <ServerHeavyContent />
    </ClientWrapper>
  );
}

ClientWrapper가 ServerHeavyContent를 직접 import하지 않고 children으로 받는 이 패턴이, 클라이언트 상호작용 UI 안에 서버 전용 데이터 페칭을 끼워 넣는 표준적인 방법입니다.

 

실무 포인트

use client 경계는 가능한 한 트리의 리프에 가깝게 배치하세요. 최상단 레이아웃에 습관적으로 붙이면 그 아래 전체가 클라이언트 번들에 편입돼 RSC의 이점이 사라집니다.

서버 컴포넌트에 넘기는 props는 직렬화 가능한 값으로 한정됩니다. 함수나 커스텀 클래스 인스턴스를 넘기면 런타임 에러가 납니다.

주의 — RSC Payload 크기도 최적화 대상입니다. 서버 컴포넌트가 반환하는 트리가 크면 초기 로드 시 Payload 자체가 커지므로, Suspense 경계로 스트리밍을 나누는 것이 좋습니다.
