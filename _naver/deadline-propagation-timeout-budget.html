Deadline Propagation — 타임아웃을 서비스마다 따로 정하면 왜 위험한가

아키텍처·시스템 설계

한 줄 요약 — 남은 시간을 절대 시각으로 호출 체인 전체에 전파해, 이미 포기된 요청에 하위 서비스가 계속 리소스를 낭비하는 것을 막습니다.

 

왜 독립적인 타임아웃이 위험한가

서비스 A가 B를, B가 다시 C와 D를 호출하는 구조에서 각 서비스가 타임아웃을 독립적으로 정하면, 클라이언트가 이미 포기한 요청을 하위 서비스들이 전혀 모른 채 계속 작업합니다. 트래픽이 몰리면 이런 좀비 요청이 누적되어 유효한 요청의 리소스까지 잠식하는 연쇄 장애로 이어집니다.

 

남은 시간 예산을 호출 체인에 전파하기

Deadline propagation은 타임아웃을 절대 시각으로 표현하고 호출 체인 전체에 전파합니다. B가 이미 4초를 썼다면 C에게는 1초짜리 예산만 남아있음을 알려주고, 예산이 0 이하면 하위 호출 없이 즉시 실패를 반환할 수 있습니다.

절대 시각을 전달해야 하는 이유

남은 시간을 상대값으로 전달하면 전송 지연이 누적돼 오차가 생깁니다. 절대 시각을 전달하면 각 서비스가 로컬 시계로 정확한 남은 예산을 계산할 수 있습니다. gRPC는 grpc-timeout 헤더로 이를 프로토콜 레벨에서 자동 지원합니다.

방식 문제점
서비스별 독립 타임아웃 상위 포기해도 하위 계속 작업
절대 시각 전파 시계 동기화만 전제하면 해결

 

gRPC 컨텍스트로 데드라인 전파 예제
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
resp, err := client.GetOrder(ctx, &pb.OrderRequest{Id: orderId})

func (s *Server) GetOrder(ctx context.Context, req *pb.OrderRequest) (*pb.OrderResponse, error) {
    if deadline, ok := ctx.Deadline(); ok && time.Until(deadline) < 200*time.Millisecond {
        return nil, status.Error(codes.DeadlineExceeded, "insufficient time budget")
    }
    return s.inventoryClient.CheckStock(ctx, &pb.StockRequest{Id: req.Id})
}

 

실무 포인트

최소 예산 임계값을 두고 조기 실패시키세요. 남은 시간이 네트워크 왕복 시간보다 적으면 호출 자체가 낭비이므로 즉시 실패를 반환해야 합니다.

비동기 팬아웃에서는 데드라인을 기준으로 취소하세요. 개별 응답 타임아웃이 아니라 전체 요청 데드라인을 기준으로 취소 신호를 보내야 합니다.

주의 — REST API에는 gRPC 같은 표준 헤더가 없지만, 커스텀 헤더로 절대 시각을 전달하고 각 서비스가 이를 해석하도록 구현할 수 있습니다.
