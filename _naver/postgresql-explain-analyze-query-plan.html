PostgreSQL EXPLAIN ANALYZE 실행계획 제대로 읽는 법

DB·데이터 모델링

한 줄 요약 — cost와 actual time의 차이, rows 추정치와 실제값의 괴리를 읽으면 진짜 병목과 통계 왜곡을 구분할 수 있습니다.

 

왜 지금 실행계획 읽는 법을 제대로 배워야 하는가

느린 쿼리를 만나면 EXPLAIN ANALYZE를 실행해보긴 하지만 "Seq Scan이 있으니 인덱스가 없나 보다" 정도로만 판단하고 끝내는 경우가 많습니다. PostgreSQL 플래너는 통계 정보를 기반으로 계획을 세우기 때문에, 통계가 실제 데이터 분포와 어긋나면 계획 자체가 잘못된 방향으로 왜곡될 수 있습니다.

 

cost와 실제 실행시간(actual time)은 다른 것을 말한다

EXPLAIN만 실행하면 예측 비용(cost)만 보이고, EXPLAIN ANALYZE는 실제 실행시간(actual time)까지 보여줍니다. cost는 통계 기반 추정 상대값이지 실제 밀리초 시간이 아닙니다. 중요한 것은 여러 노드의 actual time을 비교해 병목 단계를 찾는 것입니다.

 

rows 추정치와 actual rows의 괴리는 통계 왜곡의 신호다

예측 행 수(rows)와 실제 행 수(actual rows)의 차이가 크다면 통계 정보가 오래됐거나 선택도를 잘못 추정하고 있다는 뜻입니다. 이 괴리는 이후 조인 순서나 조인 알고리즘 선택까지 연쇄적으로 왜곡시킵니다.

신호 의미 대응
rows vs actual rows 괴리 통계 오래됨/선택도 오추정 ANALYZE 재실행
Seq Scan + 큰 필터링 인덱스 부재 조건절 인덱스 검토
Nested Loop 반복 과다 내부 테이블 접근 반복 조인 순서 재검토

 

예제 — 실행계획에서 병목 찾기
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE o.created_at > '2026-01-01'
ORDER BY o.total DESC
LIMIT 20;

Limit (actual time=812.3..812.4 rows=20 loops=1)
  ->  Sort (actual time=812.2..812.3 rows=20 loops=1)
        ->  Hash Join (actual time=5.1..790.4 rows=198512 loops=1)
              ->  Seq Scan on orders o
                    (actual time=0.02..410.5 rows=198512 loops=1)
                    Filter: (created_at > '2026-01-01')
                    Rows Removed by Filter: 1801488

Seq Scan on orders가 필터 조건으로 180만 행을 걸러내고 있다는 점(Rows Removed by Filter)이 핵심 단서입니다. created_at에 인덱스가 없어 전체 스캔 후 필터링하고 있으므로, 인덱스를 추가하면 이 단계 시간을 크게 줄일 수 있습니다.

 

실무 포인트

BUFFERS 옵션을 항상 함께 사용하세요. EXPLAIN (ANALYZE, BUFFERS)로 실행하면 캐시 히트 여부까지 알 수 있어, 콜드 캐시 문제인지 근본적인 계획 문제인지 구분할 수 있습니다.

운영 DB에서 EXPLAIN ANALYZE는 실제로 쿼리를 실행한다는 점을 잊지 마세요. INSERT/UPDATE/DELETE에 붙이면 실제 데이터가 변경되므로 트랜잭션으로 감싸고 롤백해야 합니다.

주의 — 통계 오래됨이 의심되면 ANALYZE 테이블명을 먼저 실행해 보세요. autovacuum이 자동 갱신하지만, 대량 데이터 변경 직후에는 수동으로 실행해 통계를 즉시 최신화하는 것이 진단 정확도를 높입니다.
