한 팀의 배포가 다른 팀의 화면을 깨뜨릴 때 — 마이크로 프런트엔드와 Module Federation

2026. 8. 26. · 프론트엔드

한 줄 요약 — 여러 팀이 하나의 프런트엔드 코드베이스를 공유하다 배포가 서로를 막는 상황을, Module Federation으로 런타임에 독립 배포되는 마이크로 프런트엔드로 분리하는 실전 구성을 정리했습니다.

 

프런트엔드에서 재현되는 모놀리스 문제

백엔드를 마이크로서비스로 쪼갠 조직에서도 프런트엔드는 여전히 하나의 거대한 SPA로 남아있는 경우가 흔합니다. 팀은 여러 개인데 배포할 프런트엔드 저장소는 하나이므로, A팀이 배포를 준비하는 동안 B팀의 변경사항이 같은 빌드에 섞여 들어가고, 한 팀의 버그가 전체 애플리케이션의 배포를 막습니다.

마이크로 프런트엔드는 이 문제를 프런트엔드 애플리케이션을 여러 개의 독립 배포 단위로 쪼개는 방식으로 접근합니다. Webpack 5가 제공하는 Module Federation은 런타임에 서로 다른 출처에서 빌드된 JS 번들을 동적으로 로드해 하나의 애플리케이션처럼 조합하는 방식으로 가장 널리 쓰입니다.

 

핵심 개념 1 — 호스트와 리모트, 공유 의존성

Module Federation은 애플리케이션을 호스트(host)와 리모트(remote)로 나눕니다. 호스트는 사용자가 처음 접속하는 셸 애플리케이션이고, 리모트는 호스트가 런타임에 동적으로 불러오는 독립 배포된 모듈입니다.

개념 역할
호스트(host) 셸 애플리케이션, 여러 리모트를 조합
리모트(remote) 독립적으로 빌드·배포되는 기능 단위
shared React 등 공통 의존성 중복 로드 방지

shared 설정이 실무에서 가장 까다로운 부분입니다. 호스트와 모든 리모트가 React를 각자 번들에 포함하면 사용자는 같은 라이브러리를 여러 번 다운로드하게 되고, 버전이 다르면 하나의 페이지에 React 인스턴스가 두 개 존재해 훅 관련 오류가 발생합니다.

 

예제 — 호스트와 리모트의 Webpack 설정
// remote(상품-상세 팀)의 webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'productDetail',
      filename: 'remoteEntry.js',
      exposes: {
        './ProductDetail': './src/ProductDetail.jsx',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
      },
    }),
  ],
};
// host 코드에서 리모트 모듈을 동적으로 불러와 사용
import { lazy, Suspense } from 'react';

const ProductDetail = lazy(() => import('productDetail/ProductDetail'));

function ProductPage() {
  return (
    <Suspense fallback={<Spinner />}>
      <ProductDetail />
    </Suspense>
  );
}

productDetail 팀이 자신의 저장소에서 독립적으로 빌드·배포해 remoteEntry.js를 CDN에 올리면, 호스트는 재배포 없이 다음 페이지 요청부터 최신 버전을 자동으로 불러옵니다. 이것이 마이크로 프런트엔드가 해결하려는 핵심 문제 — 팀 간 배포 독립성 — 입니다.

 

실무 도입 시 이것만은 챙기세요
1. 공유 의존성 버전 정책을 조직 차원에서 정하세요 — 메이저 버전 업그레이드는 모든 리모트 팀이 조율된 일정으로 진행해야 합니다.
2. 런타임 통합은 성능 비용을 수반합니다 — 리모트 로딩을 라우트 단위로 지연시키고, 핵심 경로는 프리페치하세요.
3. 팀 경계와 화면 경계를 일치시키세요 — 팀 소유 경계가 명확한 기능 단위부터 분리하는 것이 안전합니다.

 

마무리 — 3줄 요약

① 여러 팀이 하나의 프런트엔드 저장소를 공유하면 배포가 서로를 막는 병목이 생기며, 마이크로 프런트엔드는 이를 독립 배포 단위로 쪼개 해결합니다.
② Module Federation은 호스트가 런타임에 리모트의 번들을 동적으로 불러오는 방식이며, shared 설정으로 공통 의존성 중복과 버전 충돌을 관리해야 합니다.
③ 공유 의존성 버전 조율, 런타임 로딩 성능, 팀-화면 경계 일치라는 트레이드오프를 감안하지 않으면 도입 효과보다 복잡도 증가가 더 클 수 있습니다.
