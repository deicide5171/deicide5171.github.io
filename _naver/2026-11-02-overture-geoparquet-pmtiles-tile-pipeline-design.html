"전세계 지도를 우리 베이스맵으로 쓰고 싶어요" — Overture의 GeoParquet와 '프로덕션에 쓰지 말라'는 PMTiles 사이에서 파이프라인 설계하기

GIS

한 줄 요약 — 오픈 글로벌 지도 데이터를 우리 서비스 베이스맵으로 쓰려 할 때, Overture가 GeoParquet로 배포하는 원본 데이터와 '그대로 쓰지 말라'고 경고하는 공식 PMTiles 사이의 책임 경계와 직접 타일을 만드는 파이프라인을 정리했습니다.

 

왜 지금 이 판단이 중요해졌는가

"전세계 건물·도로·POI를 우리 지도에 베이스맵으로 깔아주세요"라는 요구는 예전이라면 거의 자동으로 OpenStreetMap 추출본이나 상용 베이스맵 공급사로 번역됐습니다. 그런데 Overture Maps Foundation이 전세계 지도 데이터를 정기적으로 GeoParquet 포맷으로 공개하면서, "우리가 직접 클라우드에서 필요한 지역만 긁어다 베이스맵을 만든다"는 선택지가 현실적인 옵션이 됐습니다. 문제는 Overture가 참고용으로 함께 공개하는 PMTiles 벡터 타일에 대해 공식 문서가 명시적으로 "이 타일을 프로덕션에 쓰지 말라"고 경고한다는 점입니다.

이 경고를 가볍게 넘기면 설계가 꼬입니다. 데모용 타일을 그대로 서비스에 박아 넣었다가, 트래픽이 늘면서 성능·가용성 문제로 되돌아오는 경우가 실제로 있습니다. 빌더 입장에서는 Overture가 그어놓은 "데이터 배포(GeoParquet)"와 "서빙(타일)" 사이의 책임 경계를 먼저 이해해야, 어디까지가 공짜로 받는 부분이고 어디서부터 직접 구축해야 하는지가 머릿속에서 바로 그려집니다.

 

전체 시스템에서의 위치

Overture가 직접 책임지는 영역은 왼쪽 끝 하나뿐입니다 — 테마(건물, 도로, 장소, 행정경계 등)별로 분리된 GeoParquet 파일을 클라우드 스토리지에 정기적으로 올려두는 것입니다. Overture가 함께 공개하는 PMTiles는 데이터가 어떻게 생겼는지 빠르게 확인하는 점검용이며, 공식 문서 자체가 안정된 베이스맵이 필요한 애플리케이션은 Overture 데이터로 직접 타일을 만들라고 안내합니다.

즉 실제 서비스가 되려면 GeoParquet(원본) → 지역 추출 → Tippecanoe 같은 도구로 MVT 타일 생성 → PMTiles로 패키징 → CDN 서빙이라는 중간 파이프라인을 직접 세워야 합니다. 이 파이프라인이 곧 GeoServer 같은 전통적 타일 서버를 쓸지, 아니면 서버 프로세스 없이 정적 파일 하나를 HTTP Range 요청으로 서빙할지를 가르는 분기점이기도 합니다.

 

선택의 트레이드오프
기준GeoServer WMS/WFS직접 생성 PMTiles
서버 프로세스상시 구동 필요없음 — 정적 파일 + CDN
데이터 갱신레이어 교체·캐시 무효화새 파일 생성 후 원자적 교체
동적 필터·질의가능불가능에 가까움(생성 시점 고정)
운영 부담서버 패치·스케일링빌드 파이프라인·CDN 설정

 

사용자별로 다른 필터를 걸거나 실시간으로 바뀌는 자체 데이터를 보여줘야 한다면 GeoServer 쪽이 맞습니다. 반대로 전세계 건물·도로처럼 갱신 주기가 느리고 조건 없이 그대로 보여주면 되는 베이스맵이라면, 서버 프로세스 자체를 없애고 정적 타일을 CDN에서 서빙하는 쪽이 운영 부담과 비용 모두에서 유리합니다.

 

실제 프로젝트 진행 순서

1) 필요한 지역·테마를 먼저 좁혀 bbox와 테마 단위로 GeoParquet를 추출합니다.
2) Tippecanoe로 줌 레벨별 단순화 수준을 조정하며 MVT 타일을 생성하고 PMTiles로 패키징합니다.
3) 특정 국가·도시 단위만 필요하면 pmtiles CLI의 extract로 지역을 분할합니다.
4) 생성된 PMTiles를 CDN 뒤에 두고 MapLibre 등에서 Range 요청으로 직접 읽게 합니다.
5) Overture의 월간 릴리스에 맞춰 파이프라인을 재실행하고 새 파일로 원자적 교체하는 배치로 운영합니다.

 

주의 — "공식에서 타일을 준다"와 "서비스에 쓸 수 있는 타일이다"는 다른 말입니다. Overture 데모 PMTiles는 데이터 점검용으로만 쓰고, 실제 트래픽을 받는 경로에는 절대 직결하지 마세요. 동적 질의가 필요한 레이어와 정적 베이스맵 레이어를 같은 파이프라인에 억지로 합치지 말고, 레이어 성격별로 서빙 방식을 나누는 것이 장기적으로 유지보수가 쉽습니다.

 

정리

Overture는 전세계 지도 데이터를 GeoParquet로 배포하는 역할까지만 책임지며, 함께 제공하는 PMTiles는 공식적으로 프로덕션 사용이 권장되지 않는 점검용입니다. 실서비스 베이스맵은 GeoParquet 추출 → Tippecanoe 타일 생성 → PMTiles 패키징 → CDN 서빙이라는 파이프라인을 직접 구축해야 하며, 동적 필터가 필요한 레이어는 기존 GeoServer WMS/WFS와 병행하는 것이 실무에서 더 안정적입니다.
