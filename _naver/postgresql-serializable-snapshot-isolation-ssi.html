PostgreSQL Serializable Snapshot Isolation — Predicate Lock으로 진짜 직렬성 잡아내기

데이터베이스

한 줄 요약 — REPEATABLE READ로도 잡히지 않는 write skew 이상현상을, PostgreSQL이 SIREAD 예측 락으로 커밋 시점에 사후 검사하는 SERIALIZABLE(SSI)의 원리를 정리했습니다.

 

왜 지금 SERIALIZABLE을 다시 봐야 하는가

REPEATABLE READ(스냅샷 격리)는 대부분의 이상현상을 막아주지만, write skew라는 패턴은 여전히 통과시킵니다. "최소 1명은 당직을 서야 한다"는 규칙에서 당직 의사 두 명이 동시에 "다른 한 명이 남아있다"고 각자 판단해 둘 다 취소하면, 각 트랜잭션은 자기 스냅샷 안에서는 정합적이었지만 결과적으로 당직자가 0명이 됩니다. 서로 다른 행을 쓰기 때문에 단순 락 충돌 감지로는 잡히지 않습니다.

 

SIREAD 락은 잠그지 않는다

PostgreSQL의 SSI가 사용하는 SIREAD 락(predicate lock)은 실제로 아무것도 차단하지 않습니다. "이 트랜잭션이 이 조건으로 이 데이터를 읽었다"는 기록일 뿐입니다. 커밋을 시도할 때 PostgreSQL은 이 읽기 기록들을 모아 위험한 구조가 형성됐는지 검사하고, 상호 의존 사이클이 발견되면 나중에 커밋하는 트랜잭션을 직렬화 실패 오류로 롤백시킵니다.

격리수준/기법 write skew 방지 실무 부담
REPEATABLE READ 방지 못함 이상현상 잔존
Strict 2PL 방지함 대기·데드락 관리
SERIALIZABLE(SSI) 방지함 재시도 로직 필수

 

2단계 락(2PL)과 무엇이 다른가

전통적인 Strict 2PL은 읽기·쓰기 시점에 실제로 락을 걸어 충돌하는 트랜잭션을 대기시킵니다. 반대로 SSI는 스냅샷 격리처럼 낙관적으로 모두 진행시킨 뒤, 커밋 시점에만 사후적으로 위험 패턴을 검사합니다. 순수 읽기 트랜잭션 사이에는 어떤 대기도 없지만, SERIALIZABLE 격리수준에서는 애플리케이션이 40001 오류를 받으면 반드시 트랜잭션을 처음부터 재시도해야 합니다.

write skew 재현 예제
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call WHERE shift = 'night';  -- 결과: 2
DELETE FROM on_call WHERE doctor_id = 101 AND shift = 'night';
COMMIT;  -- SSI가 위험 구조 감지 시 40001 오류 발생

 

실무 포인트

SERIALIZABLE은 무료가 아닙니다. SIREAD 락 기록과 사이클 검사에 오버헤드가 있으므로, write skew 위험이 실제로 있는 트랜잭션에만 선택적으로 적용하고 나머지는 READ COMMITTED를 유지하는 것이 일반적입니다.

재시도 로직 없이 SERIALIZABLE을 쓰면 안 됩니다. 40001 오류는 버그가 아니라 정상 동작이므로, 애플리케이션 레벨에서 지수 백오프 재시도를 반드시 구현해야 합니다.

주의 — 읽기 전용 트랜잭션은 READ ONLY DEFERRABLE로 선언하면 스냅샷을 안전한 시점까지 지연시켜 직렬화 실패 없이 일관된 읽기를 보장받을 수 있습니다.
