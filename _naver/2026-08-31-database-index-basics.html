인덱스는 왜 아무 데나 걸면 안 될까 — 초보자를 위한 인덱스 기초

데이터베이스

한 줄 요약 — 인덱스는 읽기를 빠르게 하는 대신 쓰기 성능과 저장 공간을 대가로 치르므로, 카디널리티 높은 컬럼 위주로 신중히 걸어야 합니다.

 

왜 인덱스를 다 걸면 안 된다고 하는가

"쿼리가 느리면 인덱스를 걸어라"는 절반만 맞습니다. 인덱스는 SELECT를 빠르게 해주는 대신, INSERT/UPDATE/DELETE마다 인덱스도 함께 갱신해야 하므로 쓰기 성능을 떨어뜨리고 저장 공간도 추가로 씁니다.

 

인덱스가 하는 일 — 책의 찾아보기

인덱스가 없으면 DB는 원하는 행을 찾기 위해 테이블 전체를 훑습니다(Full Table Scan). 인덱스는 정렬된 자료구조(대부분 B-Tree)에 값과 위치를 저장해 찾아보기 페이지처럼 빠르게 접근하게 해줍니다.

상황 인덱스 없음 인덱스 있음
100만 건 중 1건 조회 최악의 경우 전체 스캔 B-Tree 탐색, log(N) 수준
INSERT 1건 테이블에만 추가 테이블 + 인덱스 모두 갱신

 

예제 — 인덱스 유무의 차이 확인
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- type: ALL (Full Table Scan)

CREATE INDEX idx_users_email ON users(email);

EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- type: ref/const -> 인덱스로 바로 접근

EXPLAIN의 type이 ALL이면 전체 스캔 중이라는 뜻이므로 이 컬럼이 인덱스 후보인지 검토해야 합니다.

 

어떤 컬럼에 걸어야 하나

WHERE 절에 자주 등장하는 컬럼, JOIN 연결 키, 그리고 카디널리티(값의 다양성)가 높은 컬럼이 우선순위입니다. 성별처럼 값이 두세 가지뿐이면 인덱스 효과가 거의 없습니다.

 

실무 포인트

자주 갱신되는 테이블에 인덱스를 과도하게 걸면 쓰기 성능이 크게 저하됩니다. 로그성 테이블은 인덱스를 최소화하세요.

주의 — 복합 인덱스 (a, b)는 a만으로 조회할 때는 쓰이지만 b만으로 조회할 때는 쓰이지 않습니다. 컬럼 순서가 매우 중요합니다.
