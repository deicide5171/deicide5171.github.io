DNS 해부하기 — 재귀 리졸버부터 캐싱, 그리고 장애까지

2026. 8. 20. · 인프라

한 줄 요약 — 도메인을 주소창에 치는 순간부터 IP가 돌아오기까지, 스텁 리졸버 → 재귀 리졸버 → 루트/TLD/권한 네임서버로 이어지는 해석 과정과 캐싱·TTL이 만드는 흔한 장애 패턴을 정리했습니다.

 

왜 지금 DNS를 다시 들여다봐야 할까요

DNS는 인프라 중에서도 유독 존재감이 없는 편입니다. 평소에는 도메인을 치면 곧바로 페이지가 뜨니 그 뒤에서 무슨 일이 일어나는지 신경 쓸 이유가 없습니다. 그러다 배포 직후 새 서버로 트래픽이 안 옮겨가거나, 오타 하나로 존재하지 않는 서브도메인을 찾다가 애플리케이션 전체가 응답 불가에 빠지는 순간, DNS는 갑자기 인프라 전체를 좌우하는 변수로 떠오릅니다.

문제는 DNS 장애가 보통 애매하게 나타난다는 점입니다. 서버는 멀쩡히 떠 있고 방화벽도 열려 있는데 클라이언트 쪽에서는 연결 자체가 안 되거나, 어떤 사용자는 새 IP로 붙고 어떤 사용자는 여전히 옛 IP로 붙는 식의 비일관적인 증상이 흔합니다. 대부분의 원인은 이름을 IP로 바꾸는 해석(resolution) 단계 어딘가—스텁 리졸버의 로컬 캐시일 수도, 중간 재귀 리졸버일 수도, TTL이 걸어둔 시간일 수도 있습니다—에 있습니다.

 

핵심 개념 1 — 스텁 리졸버에서 권한 네임서버까지

이름 해석에 참여하는 주체는 역할이 뚜렷이 나뉩니다. 애플리케이션이 이름 해석 함수를 호출하면 가장 먼저 만나는 것이 OS에 내장된 스텁 리졸버입니다. 스텁 리졸버는 스스로 답을 찾지 않고, 설정된 재귀 리졸버(가정에서는 ISP가, 사내망에서는 내부 DNS 서버가, 혹은 공용 리졸버가 이 역할을 맡습니다)에게 질의를 넘깁니다.

재귀 리졸버가 캐시에 답을 갖고 있지 않다면, 이때부터 실제 재귀 탐색이 시작됩니다. 순서는 항상 위에서 아래로 내려갑니다. 먼저 루트 네임서버에 질의해 최상위 도메인(TLD)을 담당하는 네임서버 주소를 받고, 다시 TLD 네임서버에 질의해 해당 도메인을 관리하는 권한(authoritative) 네임서버 주소를 받은 뒤, 마지막으로 권한 네임서버에 최종 질의를 보내 실제 레코드 값을 받습니다. 재귀 리졸버는 이 과정을 대신 수행한 뒤 최종 답만 스텁 리졸버에 돌려주므로, 클라이언트 입장에서는 복잡한 과정이 단 한 번의 요청·응답으로 보입니다.

 

 

핵심 개념 2 — 캐싱과 TTL

매 질의마다 루트부터 다시 훑는다면 인터넷 전체가 감당할 수 없는 트래픽이 루트·TLD 네임서버로 몰릴 것입니다. 이를 막는 장치가 캐싱입니다. 각 DNS 레코드에는 TTL(Time To Live)이 초 단위로 붙어 있고, 재귀 리졸버는 응답을 이 TTL만큼 캐시에 보관한 뒤 재사용합니다. TTL이 만료되기 전까지는 같은 질의가 들어와도 권한 네임서버까지 다시 갈 필요가 없습니다.

캐싱은 여러 계층에서 동시에 일어난다는 점이 중요합니다. OS 자체가 캐시를 두는 경우도 있고(운영체제·버전에 따라 동작이 다르므로 단정하기보다 확인이 필요합니다), 재귀 리졸버가 캐시를 두며, 브라우저도 자체적으로 짧은 시간 동안 DNS 결과를 캐시하는 경우가 있습니다. 즉 레코드를 바꿔도 누구의 어느 캐시가 언제 만료되는가에 따라 반영 시점이 제각각일 수 있다는 뜻입니다.

 

핵심 개념 3 — 흔한 장애 패턴
패턴 원인 대응 방향
DNS 전파 지연 각 캐시가 TTL 만료 전까지 옛 값을 계속 반환 변경 전 TTL을 미리 낮춰두기
NXDOMAIN 오타·삭제된 서브도메인·미전파 신규 레코드 이름 자체와 negative caching TTL 함께 확인
TTL을 너무 길게 잡음 마이그레이션·장애 대응 시 전환이 늦게 반영됨 계획된 변경 전 TTL 단축, 완료 후 복원

 

예제 — dig로 캐시된 TTL 확인하기

dig 명령으로 재귀 리졸버가 실제로 어떤 답을 캐시하고 있는지, 남은 TTL이 얼마인지 확인할 수 있습니다.

$ dig example.com A

;; QUESTION SECTION:
;example.com.                  IN      A

;; ANSWER SECTION:
example.com.            287    IN      A       93.184.216.34

;; Query time: 12 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)

ANSWER SECTION의 두 번째 컬럼(287)이 남은 TTL(초)입니다. 이 값이 원래 설정한 TTL과 비슷하게 줄어드는 중이라면 캐시가 정상 동작 중인 것이고, 값을 바꾼 지 한참 지났는데도 옛 IP가 계속 나온다면 어느 경로의 캐시가 아직 만료되지 않았는지 의심해봐야 합니다.

 

$ dig +trace example.com

;; global options: +cmd
.                       518400  IN      NS      a.root-servers.net.
com.                    172800  IN      NS      a.gtld-servers.net.
example.com.            172800  IN      NS      ns1.example-dns.com.
example.com.            300     IN      A       93.184.216.34

+trace 옵션을 붙이면 루트 → .com TLD → 해당 도메인의 권한 네임서버로 위임이 내려가는 과정을 단계별로 그대로 볼 수 있습니다.

 

실무에서 이것만은 챙기세요
1. 마이그레이션·장애 대응 전에는 대상 레코드의 TTL을 미리 낮춰두기 — 전환 시점에 옛 캐시가 오래 남지 않도록 준비
2. 변경 직후 확인할 때는 로컬 캐시를 우회하는 방법 활용 — 지금 보는 결과가 갱신된 값인지 옛 캐시인지부터 구분
3. NXDOMAIN이 예상 밖으로 나오면 오타·존재 여부 먼저 확인 — 다만 negative caching TTL 때문에 방금 고친 레코드가 아직 옛 상태로 남아있을 가능성도 함께 고려
4. 증상이 사용자마다 다르게 나타난다고 곧바로 서버 문제로 단정하지 않기 — OS·사내 DNS·공용 리졸버·브라우저마다 캐시 갱신 시점이 다를 수 있음

 

마무리 — 3줄 요약

① 이름 해석은 스텁 리졸버 → 재귀 리졸버 → 루트 → TLD → 권한 네임서버 순으로 내려가며, 재귀 리졸버가 이 과정을 대신 수행해 최종 답만 돌려줍니다.
② 각 레코드에 붙은 TTL만큼 여러 계층(재귀 리졸버, OS, 브라우저)이 각자 캐시를 유지하기 때문에, 레코드를 바꿔도 반영 시점이 캐시마다 다르게 나타날 수 있습니다.
③ DNS 전파 지연, NXDOMAIN의 negative caching, TTL을 너무 길게 잡아 생기는 지연은 모두 "캐시가 언제 어디서 만료되는가"라는 같은 원인에서 갈라져 나오는 증상입니다.
