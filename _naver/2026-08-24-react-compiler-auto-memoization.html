useMemo를 그만 써도 될까 — React Compiler 자동 메모이제이션 실전

2026. 8. 24. · 프론트엔드

한 줄 요약 — useMemo/useCallback을 수동으로 흩뿌려야 했던 문제를, 빌드 타임에 메모이제이션을 자동 삽입하는 React Compiler가 어떻게 대체하는지 정리했습니다.

 

왜 수동 메모이제이션이 문제였을까요

React에서 불필요한 리렌더링을 막으려면 useMemo, useCallback, React.memo를 적재적소에 손으로 붙여야 했습니다. 문제는 이 작업이 반복적이고 실수하기 쉽다는 것입니다. 의존성 배열을 하나 빠뜨리면 stale closure 버그가 생기고, 반대로 최적화가 필요 없는 곳까지 습관적으로 감싸면 코드만 지저분해집니다.

React Compiler(구 React Forget)는 이 문제를 컴파일 타임으로 옮깁니다. 컴포넌트와 훅의 코드를 정적으로 분석해, 어디에 메모이제이션이 필요한지 판단하고 빌드 시점에 자동으로 삽입합니다.

 

핵심 개념 1 — 무엇이 자동화될까요

React Compiler는 컴포넌트 함수와 커스텀 훅의 코드를 분석해, 각 값이 이전 렌더링과 비교해 실제로 바뀌었는지 추적하는 코드를 자동 생성합니다.

// 개발자가 작성하는 코드 — 메모이제이션 훅이 전혀 없다
function ProductList({ items, category }) {
  const filtered = items.filter(item => item.category === category);
  const handleClick = (id) => console.log('clicked', id);

  return filtered.map(item => (
    <ProductCard key={item.id} item={item} onClick={handleClick} />
  ));
}

핵심은 개발자가 의존성 배열을 신경 쓸 필요가 없어진다는 것입니다. 컴파일러가 데이터 흐름을 분석해 무엇이 실제로 바뀌었는지 정확히 추적하므로, 의존성 배열을 빠뜨려서 생기는 버그 자체가 사라집니다.

 

핵심 개념 2 — 전제 조건: Rules of Hooks 준수

React Compiler는 마법이 아니라 정적 분석입니다. 코드가 React의 규칙(훅은 최상위에서만 호출, 조건문 안에서 호출 금지)을 지킨다는 전제 위에서 안전하게 최적화를 적용합니다. 규칙을 위반하는 코드가 있으면 컴파일러는 해당 컴포넌트에 대한 최적화를 건너뛰고 원래 동작대로 둡니다. eslint-plugin-react-compiler로 이 규칙 위반을 빌드 전에 먼저 잡는 것이 마이그레이션의 첫 단계입니다.

 

핵심 개념 3 — 수동 메모이제이션 vs 컴파일러 기반
구분 수동 useMemo/useCallback React Compiler
적용 주체 개발자가 직접 삽입 컴파일러가 자동 삽입
실수 가능성 의존성 배열 누락 등 규칙 준수 시 일관되게 적용
점진적 도입 필요 없음 디렉터리/컴포넌트 단위 opt-in

 

실무 도입 시 이것만은 챙기세요
1. 전면 전환보다 점진적 도입이 안전합니다 — 특정 디렉터리만 대상으로 지정하거나 "use no memo" 지시어로 개별 컴포넌트를 제외할 수 있습니다.
2. 컴파일러가 만능은 아닙니다 — 알고리즘적으로 비효율적인 렌더 로직까지 고쳐주지는 않으므로 프로파일링은 여전히 필요합니다.
3. 렌더링 횟수를 검증하던 테스트는 재점검이 필요합니다 — 최종 결과와 부수효과 검증에 집중하는 테스트 스타일로 옮겨가는 것이 안전합니다.

 

마무리 — 3줄 요약

① React Compiler는 컴포넌트 코드를 정적 분석해 메모이제이션을 빌드 타임에 자동 삽입해 의존성 배열 실수를 구조적으로 없앱니다.
② 이 최적화는 Rules of Hooks를 지키는 코드에만 안전하게 적용되므로 린트로 규칙 위반을 먼저 걸러내는 것이 중요합니다.
③ 컴파일러 도입은 점진적으로 진행하고, 렌더링 횟수보다 실제 성능 프로파일링에 집중하는 것이 안전합니다.
