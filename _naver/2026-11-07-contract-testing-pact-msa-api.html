계약 테스트(Contract Testing)로 MSA 간 API 깨짐 막기 — Pact 실전

백엔드

한 줄 요약 — 전체 서비스를 함께 띄우지 않고도 소비자가 정의한 계약을 공급자가 지키는지 독립적으로 검증하는 Pact 계약 테스트 구조를 정리했습니다.

 

왜 지금 계약 테스트를 다시 봐야 하는가

MSA에서 API 응답 필드 하나를 바꿨을 뿐인데 다른 서비스가 배포 후에야 깨지는 사고를 겪곤 합니다. 이를 막으려 E2E 테스트를 늘리면 서비스 수가 늘어날수록 환경 구축이 무거워지고 테스트가 느려집니다. 계약 테스트는 소비자가 기대하는 계약을 공급자가 지키는지 각자 독립적으로 검증하는 방식으로 이 문제에 접근합니다.

 

소비자 주도 계약(Consumer-Driven Contract)

Pact는 소비자 서비스가 먼저 "이런 요청으로 호출하고 이런 응답을 기대한다"는 계약을 테스트 코드로 작성합니다. 이 계약은 Mock 서버로 검증돼 JSON 파일로 산출됩니다. 공급자 서비스는 이 파일을 가져와 실제 구현이 계약을 만족하는지 별도로 검증합니다. 두 서비스는 서로를 직접 띄우지 않고도 호환성을 확인할 수 있습니다.

 

Pact Broker가 배포 안전성까지 보장하는 방식

Pact Broker는 계약 파일을 중앙에서 관리하고 어떤 버전끼리 호환되는지 매트릭스로 추적합니다. can-i-deploy 검사로, 공급자를 배포하기 전에 현재 운영 중인 모든 소비자 버전의 계약을 새 버전이 여전히 만족하는지 CI에서 자동 확인한 뒤에만 배포하도록 게이트를 걸 수 있습니다.

접근 방식 실행 속도 실패 원인 파악
E2E 테스트 느림 어려움
계약 테스트 빠름 쉬움
계약 + can-i-deploy 빠름 배포 전 사전 차단

 

예제 — 소비자 측 Pact 테스트
const provider = new PactV3({
  consumer: 'OrderService',
  provider: 'CustomerService',
});

describe('CustomerService와의 계약', () => {
  it('고객 정보를 정상적으로 반환해야 한다', () => {
    provider
      .given('customer with id 42 exists')
      .uponReceiving('a request for customer 42')
      .withRequest({ method: 'GET', path: '/customers/42' })
      .willRespondWith({
        status: 200,
        body: { id: like(42), name: like('홍길동'), tier: like('gold') },
      });

    return provider.executeTest(async (mockServer) => {
      const client = new CustomerClient(mockServer.url);
      const customer = await client.getCustomer(42);
      expect(customer.name).toBeDefined();
    });
  });
});

이 테스트를 실행하면 계약 파일이 생성되고, CustomerService 팀은 이 파일로 실제 구현이 계약을 만족하는지 확인합니다.

 

실무 포인트

계약 테스트는 E2E 테스트를 완전히 대체하지 않습니다. 여러 서비스가 얽힌 비즈니스 흐름 전체는 여전히 소수의 스모크성 E2E로 검증해야 합니다.

팀 간 계약 변경 프로세스를 먼저 합의하세요. 공급자와 소통 없이 계약을 임의로 바꾸면 협업 마찰이 커집니다.

주의 — can-i-deploy를 CI/CD 파이프라인의 필수 게이트로 넣으세요. 로컬에서만 통과시키고 배포 게이트에 연결하지 않으면 계약 테스트 도입의 실질적 효과를 얻지 못합니다.
