타일 서버를 지워버리기 — tippecanoe와 PMTiles로 만드는 정적 벡터 타일 파이프라인

2026. 8. 23. · GIS

한 줄 요약 — 요청이 올 때마다 타일을 만들어주는 서버를 운영하는 대신, 빌드 시점에 tippecanoe로 벡터 타일을 미리 굽고 PMTiles 단일 파일로 정적 스토리지에 올려, 브라우저가 HTTP Range 요청으로 필요한 부분만 읽어가게 하는 서버리스 벡터 타일 파이프라인을 정리했습니다.

 

왜 타일 서버 없이 배포할 생각을 하게 됐을까요

웹 지도에 벡터 타일을 올리는 방법을 찾아보면 대부분 서버를 세우는 이야기부터 나옵니다. PostGIS에 데이터를 넣고 pg_tileserv나 martin 같은 타일 서버를 붙이거나, 상용 지도 서비스의 타일 API를 구독하는 방식이 일반적입니다. 그런데 실제 서비스에서 지도에 올리는 데이터의 상당수는 행정경계, 도로망, 건물 폴리곤처럼 한번 만들면 한동안 그대로인 데이터입니다. 이런 데이터를 위해 24시간 돌아가는 서버와 DB를 유지하는 것은 낭비에 가깝습니다.

대안은 발상을 뒤집는 것입니다. 타일을 요청 시점에 만들지 말고, 빌드 시점에 전 줌 레벨을 미리 구워 정적 파일로 배포하는 방식입니다. 사실 미리 굽기 자체는 오래된 기법인데, 결과물이 문제였습니다. z/x/y 디렉터리 구조로 풀면 수십만 개의 작은 파일이 생겨 업로드가 고통스럽고, MBTiles로 묶으면 SQLite 파일을 읽어줄 서버가 다시 필요해집니다.

이 마지막 퍼즐을 푼 것이 PMTiles입니다. 타일 전체를 단일 파일에 담되, 클라이언트가 HTTP Range 요청으로 필요한 타일 바이트만 읽어갈 수 있게 설계된 포맷입니다. 굽는 쪽은 현재 Felt가 관리하는 tippecanoe가 사실상 표준 도구이고, 두 도구를 이으면 서버 프로세스가 하나도 없는 벡터 타일 파이프라인이 완성됩니다.

 

 

핵심 개념 1 — tippecanoe는 변환기가 아니라 지도 제작 도구입니다

tippecanoe를 GeoJSON을 타일로 바꾸는 단순 변환기로 생각하면 절반만 이해한 것입니다. 벡터 타일의 진짜 어려움은 변환이 아니라 줌 레벨마다 무엇을 버릴지 결정하는 일이기 때문입니다. 전국 건물 수백만 채를 낮은 줌 타일에 전부 담으면 타일 하나가 수 MB로 부풀어 렌더링이 불가능해집니다. tippecanoe는 낮은 줌에서 지오메트리를 단순화하고, 밀집 지역의 피처를 규칙적으로 솎아내고, 작은 폴리곤을 병합해 각 타일을 렌더링 가능한 크기로 유지해 줍니다.

실무에서 자주 쓰는 옵션을 보면, -zg는 데이터 밀도를 보고 적절한 최대 줌을 자동으로 결정하고, --drop-densest-as-needed는 타일이 크기 상한을 넘을 때 가장 밀집된 곳부터 피처를 떨어뜨리며, --extend-zooms-if-still-dropping은 최대 줌에서도 피처가 버려지고 있으면 줌을 한 단계 더 늘려 줍니다. 어떤 조합이 정답인지는 데이터 성격에 따라 달라서, 한 번 굽고 끝내기보다 결과를 지도에 올려보며 옵션을 조정하는 반복 작업이 필요합니다.

 

핵심 개념 2 — PMTiles, 단일 파일을 Range 요청으로 읽습니다

PMTiles 파일 내부는 헤더, 디렉터리, 타일 데이터 세 부분으로 구성됩니다. 디렉터리는 타일 좌표를 파일 안의 오프셋과 길이로 매핑하는 색인이고, 타일들은 힐베르트 곡선 순서로 정렬되어 지리적으로 인접한 타일이 파일 안에서도 가까이 배치됩니다. 클라이언트는 먼저 파일 앞부분을 Range 요청으로 읽어 색인을 확보하고, 이후 화면에 필요한 타일의 바이트 구간만 골라 요청합니다. 서버가 하는 일은 정적 파일의 일부를 잘라 보내는 것뿐이라, S3·Cloudflare R2·일반 웹 서버 등 Range를 지원하는 곳이면 어디든 호스팅이 가능합니다.

구분 z/x/y 디렉터리 MBTiles PMTiles
파일 개수 수십만~수백만 개 1개 (SQLite) 1개
정적 호스팅 직접 서빙 가능하나 동기화 부담 큼 불가 (서버 필요) 가능 (Range 요청)
배포/갱신 파일 단위 동기화 파일 교체 + 서버 재시작 파일 1개 교체
서버 프로세스 불필요 필요 불필요

 

핵심 개념 3 — MapLibre에서 pmtiles 프로토콜로 소비합니다

MapLibre GL JS는 기본적으로 z/x/y URL 템플릿으로 타일을 요청합니다. PMTiles를 쓰려면 protomaps가 제공하는 pmtiles 자바스크립트 라이브러리로 커스텀 프로토콜을 한 번 등록해서, pmtiles:// 스킴의 소스 URL이 내부적으로 Range 요청으로 변환되게 하면 됩니다. 색인은 클라이언트가 캐싱하므로 지도를 움직일 때마다 다시 읽지 않고, 앞에 CDN을 두면 자주 요청되는 바이트 구간이 엣지에 캐싱되어 전용 타일 서버와 구분하기 어려운 응답 속도가 나옵니다.

이 구조의 진짜 매력은 운영 비용의 형태가 바뀐다는 점입니다. 동적 타일 서버는 트래픽이 없어도 인스턴스와 DB가 상시 비용을 발생시키고, 트래픽이 몰리면 스케일링을 고민해야 합니다. 반면 PMTiles는 남는 비용이 스토리지 요금과 전송량뿐이고, 부하 대응은 CDN이 대신해 줍니다. 장애 지점도 정적 파일 하나로 줄어들어 소규모 팀이 지도 서비스를 유지하는 부담이 크게 낮아지고, 원본 데이터가 바뀔 때 CI에서 tippecanoe를 돌려 파일 하나를 교체하는 배치 작업으로 갱신을 자동화할 수 있습니다.

 

예제 — 굽기부터 지도 표시까지

건물 폴리곤 GeoJSON을 PMTiles로 굽는 명령입니다. 최근 버전의 tippecanoe는 출력 확장자를 .pmtiles로 주면 PMTiles를 직접 만들어 줍니다.

tippecanoe -o buildings.pmtiles \
  -l buildings \
  -n "서울 건물 폴리곤" \
  -zg \
  --drop-densest-as-needed \
  --extend-zooms-if-still-dropping \
  --force \
  buildings.geojson

# 결과 확인 후 정적 스토리지에 업로드 (예: S3)
aws s3 cp buildings.pmtiles s3://my-tiles-bucket/buildings.pmtiles

브라우저 쪽에서는 프로토콜 등록 한 번이면 일반 벡터 소스처럼 쓸 수 있습니다.

import maplibregl from "maplibre-gl";
import { Protocol } from "pmtiles";

const protocol = new Protocol();
maplibregl.addProtocol("pmtiles", protocol.tile);

const map = new maplibregl.Map({
  container: "map",
  center: [126.978, 37.566],
  zoom: 11,
  style: {
    version: 8,
    sources: {
      buildings: {
        type: "vector",
        url: "pmtiles://https://tiles.example.com/buildings.pmtiles",
      },
    },
    layers: [
      {
        id: "buildings-fill",
        type: "fill",
        source: "buildings",
        "source-layer": "buildings",
        paint: { "fill-color": "#4a78a8", "fill-opacity": 0.6 },
      },
    ],
  },
});

 

실무에서 이것만은 조심하세요
1. maxzoom을 무작정 올리지 마세요 — 줌이 한 단계 오를 때마다 타일 수는 4배가 되어 파일 크기와 빌드 시간이 폭증합니다. 벡터 타일은 래스터와 달리 오버줌(overzoom)이 가능해서, 최대 줌 타일의 좌표 데이터를 렌더러가 그대로 확대해 그려 줍니다. 대부분의 데이터는 줌 14~15까지만 굽고 그 이상은 렌더러에 맡기시는 것이 좋습니다.
2. 중간 프록시의 자동 압축을 끄세요 — 타일 데이터는 이미 내부적으로 gzip 압축되어 있는데, CDN이나 웹 서버가 파일 전체에 압축을 다시 걸면 Range 요청의 바이트 오프셋이 원본과 어긋나 타일이 깨집니다. PMTiles는 반드시 압축 변환 없이 서빙해야 하고, 브라우저에서 직접 읽는다면 CORS 설정에서 Range 헤더 허용도 필요합니다.
3. 실시간 데이터에는 쓰지 마세요 — 갱신이 파일 전체 재빌드·교체 방식이라, 분 단위로 바뀌는 실시간 위치 데이터나 사용자 권한별로 다른 피처를 보여줘야 하는 요구사항에는 맞지 않습니다. 그런 경우에는 PostGIS 기반 동적 타일 서버가 여전히 정답입니다.

 

마무리 — 3줄 요약

① tippecanoe는 줌별 단순화와 피처 드로핑을 자동화해, 원본 공간 데이터를 렌더링 가능한 벡터 타일로 구워주는 빌드 도구입니다.
② PMTiles는 전체 타일을 단일 파일에 담고 HTTP Range 요청으로 필요한 부분만 읽게 해서, 타일 서버 없이 정적 스토리지와 CDN만으로 서빙을 완성합니다.
③ 주기적 배치 갱신 데이터에는 최적이지만, 실시간 갱신이나 사용자별 필터링이 필요하다면 동적 타일 서버를 선택하셔야 합니다.
