"PR을 버그·성능·보안 세 관점에서 각각 보고 검증까지 해주세요" — Claude Code Workflow로 짜는 결정론적 멀티에이전트 파이프라인

AI

한 줄 요약 — 여러 서브에이전트가 각각 맡고 그 결과를 또 다른 에이전트가 검증하게 하는 작업은 자유형 위임이 아니라 오케스트레이션 설계 문제입니다. Claude Code의 Workflow 도구가 agent·pipeline·parallel이라는 원시 함수로 "뼈대는 결정론, 판단은 모델"이라는 패턴을 코드로 어떻게 구현하는지 정리했습니다.

 

왜 지금 이 판단이 매일 벌어지는가

"PR이 올라오면 버그·성능·보안 세 관점에서 각각 리뷰하고, 발견된 문제는 다른 에이전트가 실제로 재현되는지 검증까지 해서 확정된 것만 알려주세요." 이런 요청을 받으면 설계자가 답해야 할 질문은 "어떤 모델을 쓸까"가 아니라 "이 세 갈래 리뷰와 뒤이은 검증을 몇 개의 독립 실행 단위로 나누고 어떤 순서·의존관계로 묶을 것인가"입니다. 코딩 에이전트가 서브에이전트를 몇 개 띄울지, 어떤 순서로 부를지까지 스스로 판단하게 맡기는 자유형 위임은 유연하지만 매번 다른 경로로 실행되고 실패 지점을 재현하기도 어렵습니다. 반대로 외부 오케스트레이션 프레임워크를 레포에 통째로 들여오는 것은 또 하나의 인프라를 운영하는 부담을 낳습니다.

Claude Code에 최근 추가된 Workflow 도구는 이 중간 지점을 메웁니다. 에이전트가 직접 짠 스크립트 하나가 전체 흐름을 결정론적으로 통제하고, 그 안의 각 호출 지점에서만 서브에이전트가 자율적으로 판단하게 하는 구조입니다.

 

핵심 구조 — 뼈대는 코드, 판단은 모델

Workflow 스크립트는 몇 가지 원시 함수로 구성됩니다. agent(prompt, opts)는 서브에이전트 하나를 호출하며 label·phase·schema를 지정할 수 있고, schema를 지정하면 다음 단계가 파싱 가능한 구조화된 출력을 강제할 수 있습니다. parallel(fns)은 여러 에이전트를 동시에 실행하고, pipeline(items, stepA, stepB)은 1단계 결과가 나오는 즉시 그 항목만 2단계로 흘려보냅니다. 전체 항목이 1단계를 다 마칠 때까지 기다리지 않는다는 점이 핵심입니다 — 버그 리뷰가 먼저 끝나면 그 항목은 검증 단계로 바로 넘어가고, 보안 리뷰가 느리게 끝나도 전체 파이프라인은 그만큼만 늦어집니다.

 

이 구조에서 "결정론적"인 부분은 호출 순서·의존관계·재시도 로직 같은 제어 흐름이고, "자율적 판단"은 각 agent() 호출 내부에서 LLM이 맡습니다. 오케스트레이션 레이어는 몇 번을 실행해도 같은 경로를 타는 재현 가능한 코드이고, 그 안의 각 판단 지점만 모델의 자유도에 맡기는 셈입니다.

 

자유형 위임과의 선택 기준
기준 자유형 서브에이전트 위임 Workflow 스크립트
작업 분할 에이전트가 그때그때 판단 작성자가 사전에 단계·의존관계 설계
재현성 실행마다 경로가 달라질 수 있음 같은 스크립트는 같은 경로로 실행
중단 후 재개 처음부터 다시 수행 체크포인트 기반 부분 재실행
적합한 상황 탐색적 조사, 범위가 불분명한 작업 분할선이 이미 명확한 반복 작업

 

업계의 멀티에이전트 운영 사례를 보면, 프로덕션에 올라간 1,600건 이상의 실행 트레이스를 분석한 조사에서 실패율이 41%~86.7%에 달했고 대부분의 원인이 모델의 추론 실패가 아니라 시스템 설계와 에이전트 간 정합성 문제였다는 결과가 있습니다. 분할선이 이미 명확한 작업일수록 그 분할을 코드로 고정하는 편이 실패를 줄인다는 뜻입니다. 반대로 범위가 실행 중에 드러나는 탐색적 조사라면 스크립트로 미리 단계를 못박는 순간 오히려 유연성을 잃습니다.

 

코드로 보는 뼈대
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, { label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA }),
  review => parallel(review.findings.map(f => () =>
    agent(`발견이 실제로 재현되는지 검증: ${f.title}`,
      { label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA })
      .then(v => ({ ...f, verdict: v }))
  ))
)
const confirmed = results.flat().filter(f => f?.verdict?.isReal)

 

실무에서 걸리는 지점

스크립트 상단의 meta 블록은 반드시 순수 리터럴이어야 하고 변수나 함수 호출로 계산된 값을 넣을 수 없습니다. 실행 전에 진행 단계를 고정해 진행률 UI와 재개 로직이 어떤 단계가 몇 개 있는지 미리 알아야 하기 때문입니다. 또한 중단된 실행은 같은 (prompt, opts) 조합의 호출 결과를 캐시에서 그대로 재사용하고 수정되거나 새로 추가된 호출만 다시 실행하는데, 이걸 믿고 스크립트를 짜려면 각 호출의 프롬프트와 옵션이 실행마다 달라지지 않도록 설계해야 합니다. 서브에이전트를 수십 개까지 띄울 수 있어 토큰 소비가 크므로, 사용자가 명시적으로 멀티에이전트 오케스트레이션을 요청했을 때만 호출하도록 하는 opt-in 설계가 비용 거버넌스 관점에서 필수입니다.

 

실제 프로젝트 진행 순서

1단계: 작업을 실행 전에 단계·의존관계로 쪼갤 수 있는지부터 판단합니다. 다음 단계가 실행 중에야 드러난다면 자유형 위임이 맞습니다.

2단계: 각 단계의 산출물 스키마를 먼저 정의해 다음 단계가 파싱 가능하게 만듭니다.

3단계: pipeline으로 1차 구현해 느린 항목이 전체를 묶어두지 않는지 확인합니다.

4단계: 중단 시나리오를 강제로 만들어 재개가 캐시를 제대로 재사용하는지 검증하고, 서브에이전트 수를 작업 범위에 맞게 통제합니다.

 

주의 — 날짜나 난수를 프롬프트에 직접 섞으면 재개 시 캐시가 매번 무효화됩니다. 또한 사용자 동의 없이 수십 개 에이전트를 fan-out하는 것은 비용 폭증으로 이어지므로 opt-in 설계가 필요합니다.

 

정리

멀티에이전트 오케스트레이션의 핵심 판단은 "모델이 똑똑한가"가 아니라 "분할선을 코드로 고정할지, 모델에게 맡길지"입니다. 분할선이 이미 명확한 반복 작업은 결정론적 스크립트로, 범위가 실행 중에 드러나는 탐색적 작업은 자유형 위임으로 가르고, 체크포인트 기반 재개와 opt-in 실행 설계로 장시간 파이프라인의 비용과 신뢰성을 함께 지키는 것이 요점입니다.
