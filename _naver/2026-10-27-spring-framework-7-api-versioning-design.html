"이 앱, 구버전 쓰는 유저 안 끊기게 하면서 새 API 내보내주세요" — Spring Framework 7 네이티브 버저닝으로 설계하기

Stack

한 줄 요약 — 모바일 앱 강제 업데이트 없이 API를 바꿔야 한다는 요구는 결국 버전 공존 문제입니다. Spring Framework 7이 @RequestMapping에 추가한 네이티브 버저닝과 ApiVersionConfigurer를 기준으로, 헤더·경로·파라미터 전략의 트레이드오프와 도입 순서를 정리했습니다.

 

왜 지금 이 판단이 필요한가

"이번에 API를 바꿀 건데, 아직 구버전 앱 쓰는 유저가 30%나 돼요. 그 사람들 끊기면 안 돼요." 모바일 앱을 가진 백엔드라면 분기마다 듣는 요구입니다. 그동안 Spring에는 이걸 위한 표준 장치가 없어서, 팀마다 /v1/, /v2/ 같은 URL 접두어로 컨트롤러를 통째로 분리하거나 커스텀 인터셉터로 분기하는 자체 구현을 쌓아왔습니다.

Spring Boot 4의 기반인 Spring Framework 7은 이 문제에 네이티브 지원을 추가했습니다. @RequestMapping에 version 속성이 생겼고, ApiVersionConfigurer로 버전을 어디서 읽을지(헤더, 경로, 쿼리 파라미터, 미디어 타입) 선택할 수 있습니다. 다만 이 기능은 7.1 기준 공식 문서에서 아직 안정화되지 않았다고 명시하므로, 프로덕션 적용은 7.0.x 안정 버전 기준으로 검증해야 합니다.

 

전체 시스템에서의 위치

클라이언트 요청이 들어오면 API Version Resolver가 설정된 전략에 따라 버전 값을 추출하고, SemanticApiVersionParser가 이를 major.minor.patch 형태로 해석합니다. 이 값으로 같은 경로에 매핑된 여러 핸들러 중 하나를 고르고, 지원하지 않는 버전이면 예외를 던집니다.

ApiVersionDeprecationHandler를 등록하면 지원 종료 예정 버전에 자동으로 Deprecation 헤더(RFC 9745)를 붙여 클라이언트에게 전환을 유도할 수 있습니다.

 

선택의 트레이드오프
전략 특징 적합한 상황
요청 헤더 URI가 버전과 무관하게 유지 내부 서비스 간 세밀한 제어
경로 세그먼트(/v1/) 가장 직관적, 캐싱 쉬움 외부 공개 API
쿼리 파라미터 기존 호출에 추가만 하면 됨 점진적 전환, 레거시 호환
미디어 타입(Accept) HTTP 콘텐츠 협상과 부합 엄격한 REST 설계

 

이미 API 게이트웨이 레벨에서 버저닝을 처리하고 있다면, 애플리케이션 레벨에서 또 버저닝 로직을 두는 것은 중복 설계입니다. 게이트웨이가 없다면 기존 클라이언트와의 호환성을 가장 덜 해치는 전략부터 시작하는 것이 안전합니다.

 

실제 프로젝트 진행 순서

1. 기존 버저닝 방식을 전수 감사합니다.
2. ApiVersionConfigurer로 전략을 선택합니다(기존 클라이언트 호환성 우선).
3. 버전 포맷이 표준과 다르면 커스텀 Resolver를 작성합니다.
4. DeprecationHandler로 점진적으로 전환을 유도합니다.
5. 7.0.x 안정 버전 기준으로 검증합니다.
6. API 게이트웨이와의 역할 분담을 문서화합니다.

 

예제 코드:

@RestController
@RequestMapping("/orders")
class OrderController {

    @GetMapping(path = "/{id}", version = "1.0.0")
    OrderV1Response getOrderV1(@PathVariable String id) { return null; }

    @GetMapping(path = "/{id}", version = "2.0.0")
    OrderV2Response getOrderV2(@PathVariable String id) { return null; }
}

@Configuration
class WebConfig implements WebMvcConfigurer {
    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer.useRequestHeader("API-Version").setVersionRequired(true);
    }
}

 

주의 — 네이티브 버저닝이 생겼다고 기존 URL 접두어 방식을 당장 걷어낼 필요는 없습니다. setVersionRequired(true)로 버전 명시를 강제하면 기존 클라이언트 요청이 전부 실패할 수 있으니, 전환 초기에는 기본 버전을 지정해 하위 호환을 유지하는 설정부터 시작하세요.

 

정리

API 버전 공존 요구는 Spring Framework 7의 version 속성과 ApiVersionConfigurer로 네이티브하게 풀 수 있게 됐습니다. 전략 선택은 캐싱·REST 원칙·클라이언트 구현 난이도의 트레이드오프이며, 이미 게이트웨이가 버저닝을 처리 중이라면 중복 설계를 피해야 합니다. 적용 순서는 기존 방식 감사 → 전략 선택 → 커스텀 파서 확인 → 점진적 전환 → 안정 버전 검증입니다.
