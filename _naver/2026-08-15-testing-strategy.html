왜 지금 이 주제인가

이 블로그는 Flutter 앱 개발과 네이버 클라우드 지도 API 연동에서 시작해, PostGIS 기반 공간 데이터, DB 인덱스 내부 구조, 분산 SQL과 캐시 스탬피드 같은 백엔드 심화 주제, 그리고 최근에는 MCP·A2A 같은 AI 에이전트 프로토콜과 Docker/CI-CD 파이프라인까지 폭넓게 다뤄왔습니다. 그런데 이 모든 글의 밑바탕에 있어야 할 질문 하나가 아직 정면으로 다뤄지지 않았습니다. "이 코드가 실제로 의도한 대로 동작하는지 어떻게 확신할 것인가" 입니다.

지난 글에서 CI/CD 파이프라인을 다루며 "테스트 실패 시 배포를 반드시 막는다"는 원칙을 언급했지만, 정작 그 파이프라인 안에서 무엇을 어떤 비율로 테스트해야 하는지는 다루지 않았습니다. 그래서 다음 학습 주제로 테스트 피라미드와 실전 테스팅 전략을 추천합니다.

 

학습 로드맵
단계 주제 왜 필요한가
1 단위 테스트와 테스트 더블(Mock/Stub/Fake) 외부 의존성 없이 로직 정확성을 빠르게 검증
2 통합 테스트(DB, API, 메시지 큐 연동) 컴포넌트 경계에서 발생하는 실제 버그 발견
3 E2E 테스트와 계약 테스트(Contract Test) 사용자 시나리오와 서비스 간 API 계약 준수
4 테스트 커버리지·플레이키 테스트 관리 숫자에 매몰되지 않고 신뢰할 수 있는 테스트만 유지
5 CI 파이프라인에 테스트 단계 통합 앞서 다룬 CI/CD 파이프라인과 자연스럽게 연결

 

핵심 개념: 테스트 피라미드가 말하는 것

테스트 피라미드는 단위 테스트를 가장 넓은 기반에, 통합 테스트를 중간에, E2E 테스트를 가장 좁은 꼭대기에 배치하는 모델입니다. 단위 테스트는 실행이 빠르고 실패 원인을 즉시 특정할 수 있지만, 네트워크 지연이나 DB 락 경합 같은 실제 환경의 문제는 잡지 못합니다. 반대로 E2E 테스트는 실제 사용자 흐름을 검증하지만 느리고, 환경 변화에 취약해 자주 실패하는 플레이키 테스트가 되기 쉽습니다.

이 블로그에서 다룬 캐시 스탬피드나 분산 SQL의 장애 시나리오처럼, 동시성·타이밍 이슈는 단위 테스트만으로는 재현되지 않습니다. 이런 경우엔 통합 테스트 계층에서 실제 캐시·DB를 띄우고 부하를 재현하는 것이 훨씬 효과적입니다. 즉 계층마다 검증할 책임을 명확히 나누는 것이 테스트 전략의 핵심입니다.

 

예제: 단위 테스트와 통합 테스트의 역할 분리
// 단위 테스트: 순수 로직만 빠르게 검증 (외부 의존성 없음)
test('할인율 계산은 최대 30%를 넘지 않는다', () => {
  expect(calculateDiscount(1000, 0.5)).toBe(300); // 30% 상한 적용
});

// 통합 테스트: 실제 DB 연결로 쿼리 정합성까지 검증
test('주문 생성 시 재고가 정확히 차감된다', async () => {
  await db.seed({ stock: 10 });
  await createOrder({ productId: 1, qty: 3 });
  const stock = await db.query('SELECT stock FROM products WHERE id = 1');
  expect(stock).toBe(7);
});

 

실무 도입 시 이것만은 챙기세요
1. 테스트 더블은 최소한으로 사용 — 모든 것을 Mock으로 대체하면 실제 통합 지점의 버그를 놓칠 수 있습니다
2. 플레이키 테스트는 즉시 격리 — 간헐적으로 실패하는 테스트를 방치하면 CI 실패를 무시하는 습관이 생깁니다
3. 커버리지 숫자보다 경계 조건 — 널 값, 동시성, 예외 경로처럼 실제 버그가 숨는 지점을 우선 검증합니다
4. E2E는 핵심 시나리오에만 집중 — 회원가입, 결제처럼 실패하면 치명적인 흐름만 남기고 나머지는 하위 계층에 맡깁니다
