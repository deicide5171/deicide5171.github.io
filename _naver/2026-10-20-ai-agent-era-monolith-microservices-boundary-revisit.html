"에이전트한테 맡겼더니 엉뚱한 서비스를 고쳐요" — AI 에이전트 시대에 다시 묻는 모놀리스 vs 마이크로서비스

dev-strategy

한 줄 요약 — 서비스를 12개로 쪼개 놓았더니 AI 에이전트가 계약도 모르는 다른 서비스를 건드려 버리는 사고가 반복된다는 요구는, 서비스 경계를 "사람 팀 조직"이 아니라 "에이전트가 한 번에 읽을 수 있는 범위"로도 다시 그어야 하는지 묻는 아키텍처 문제입니다.

 

어떤 요구에서 출발하는가

"코딩 에이전트한테 기능 하나 추가를 맡겼는데, 자기가 건드려야 할 서비스의 계약(API 스펙)을 몰라서 다른 서비스 코드까지 엉뚱하게 고쳐 버렸어요. 서비스가 12개로 쪼개져 있다 보니 에이전트가 전체 그림을 못 보는 것 같아요." 에이전트에게 실제 작업을 맡기기 시작한 팀에서 요즘 자주 나오는 호소입니다. 이전에는 서비스 경계를 팀 조직, 배포 주기, 장애 격리 범위 기준으로 그었습니다. 그런데 이제 작업을 수행하는 주체에 한 번에 읽을 수 있는 컨텍스트 양이 제한된 에이전트가 추가되면서, 그 제한이 아키텍처 경계 판단에 새로운 변수로 들어옵니다.

 

전체 시스템에서의 위치

서비스 경계 문제는 코드가 어디서 끊기는가의 문제입니다. 끊기는 지점마다 계약(스펙 문서, 타입 정의, API 계약)이 코드 밖에 따로 존재해야 하고, 에이전트든 사람이든 그 계약을 신뢰할 수 없으면 경계를 넘어가는 작업에서 사고가 납니다.

모놀리스(또는 모듈러 모놀리스)에서는 에이전트가 레포 하나를 통째로 열어 함수 호출 관계를 코드에서 직접 추적할 수 있습니다. 마이크로서비스에서는 서비스 A를 고치다가 서비스 B의 동작에 의존하면, 에이전트는 B의 실제 코드를 볼 수 없고 B의 API 문서 같은 "코드 밖 계약"을 신뢰해야 합니다. 이 계약이 코드와 어긋나 있으면 에이전트는 그 어긋남을 알아챌 방법이 없습니다.

 

선택의 트레이드오프
구조 장점 단점
모놀리스 교차 참조를 코드로 직접 확인, 계약 불일치 위험 없음 레포가 커지면 컨텍스트 윈도우 초과
모듈러 모놀리스 경계를 지키면서도 필요시 다른 모듈 코드 직접 확인 경계 강제가 코드 리뷰·린트에 의존
마이크로서비스 배포·장애 격리 독립적, 팀별 소유권 명확 계약-코드 불일치 시 에이전트가 틀린 가정으로 작업

 

2025년 CNCF 설문에서 마이크로서비스를 도입했던 조직의 42%가 일부 서비스를 다시 큰 배포 단위로 통합했고, 가장 흔한 착지점이 모듈러 모놀리스였다는 보고가 있습니다. 동시에 반대 흐름도 있습니다 — 에이전트 자체를 작은 역할 단위로 쪼개 오케스트레이션하는 설계도 확산 중인데, 여기서 지적되는 실패 모드가 "분산 모놀리스"입니다. 에이전트들이 서로 너무 강하게 결합돼 하나를 못 고치면 전체 체인이 멈추는 경우입니다. 문제의 본질은 쪼개느냐 마느냐가 아니라 경계가 실제로 지켜지고 계약이 신뢰할 수 있는가입니다.

 

실제 프로젝트 진행 순서

1. 지금 에이전트가 실패하는 지점을 먼저 구체적으로 기록합니다.
2. 재구조화 전에 OpenAPI 스펙이나 타입 정의가 실제 코드와 얼마나 어긋나 있는지 점검합니다. 어긋남이 원인이라면 계약 자동 생성으로 해결됩니다.
3. 그래도 부족하면 배포 독립성이 꼭 필요하지 않은 서비스 쌍부터 모듈러 모놀리스로 중간 통합합니다.
4. 합칠 수 없는 경계는 기계가 파싱 가능한 스펙을 소스 오브 트루스로 못 박습니다.
5. 마이크로에이전트로 쪼개는 쪽을 택했다면 에이전트 간 결합도를 먼저 측정합니다.

 

주의 — "AI가 다루기 쉬우니까 무조건 합친다"는 결론으로 가지 마세요. 장애 격리나 독립 배포가 중요한 경계는 에이전트 편의보다 우선합니다. 조직 구조(콘웨이의 법칙)와 에이전트 작업 단위가 충돌하면 조직 경계가 더 무겁게 우선해야 합니다.

 

정리

에이전트가 한 번에 읽을 수 있는 범위가 작아질수록, 서비스 경계를 넘는 작업에서 틀린 가정에 기반한 변경이 늘어납니다. 문제의 본질은 쪼개진 서비스 개수가 아니라 경계마다 존재하는 계약이 코드와 얼마나 일치하는가입니다. 실패 지점 기록 → 계약 점검 → 필요시 모듈러 모놀리스 검토 → 못 합치는 경계는 계약 강화 → 결합도 측정 순으로 판단하면 과도한 재구조화를 피할 수 있습니다.
