정확도와 속도, 어느 쪽을 먼저 포기할까 — pgvector HNSW/IVFFlat 인덱스 튜닝

2026. 8. 30. · 데이터베이스

한 줄 요약 — pgvector의 HNSW와 IVFFlat은 순차 스캔을 근사 최근접 이웃 탐색으로 바꿔 검색 속도를 높이지만 탐색 원리가 근본적으로 다릅니다. 재현율·지연·구축 비용을 맞바꾸는 파라미터를 정리했습니다.

 

순차 스캔은 데이터가 늘수록 느려집니다

임베딩 벡터를 PostgreSQL에 컬럼으로 넣고 코사인 유사도로 정렬하면 정확한 결과가 나옵니다. 문제는 이 방식이 전체 로우를 순회하는 순차 스캔이라는 점입니다. 데이터가 수만 건일 때는 문제없지만 수백만 건으로 늘면 쿼리 하나에 수 초가 걸립니다. pgvector가 제공하는 HNSW와 IVFFlat 인덱스는 정확한 최근접 이웃 대신 근사 최근접 이웃(ANN)으로 바꿔서 이 문제를 해결합니다 — 100% 정확한 답 대신 대부분 정확한 답을 훨씬 빠르게 얻는 트레이드오프입니다.

 

핵심 개념 1 — IVFFlat: 공간을 클러스터로 나눠 탐색 범위를 좁힙니다

IVFFlat은 전체 벡터 공간을 k-means 클러스터링으로 lists개의 클러스터로 미리 나눕니다. 검색 시에는 쿼리 벡터가 어느 클러스터 중심에 가까운지 확인한 뒤, 가장 가까운 probes개의 클러스터 안에 있는 벡터들만 정확하게 비교합니다. 빨라지지만, 쿼리 벡터가 클러스터 경계 근처에 있으면 진짜 최근접 이웃이 탐색하지 않은 클러스터에 있을 수 있어 재현율 손실이 생깁니다.

pgvector 공식 가이드는 lists = rows / 1000(백만 건 미만) 또는 sqrt(rows)(그 이상)를 출발점으로 권장합니다.

 

핵심 개념 2 — HNSW: 계층적 그래프를 타고 내려가며 탐색합니다

HNSW는 벡터들을 그래프의 노드로 보고, 각 노드가 가까운 다른 노드들과 연결된 다층 그래프를 만듭니다. 검색은 가장 위 레이어에서 시작해 쿼리와 가까운 노드로 그리디하게 이동하다가, 더 가까운 노드를 못 찾으면 한 층 아래로 내려가는 과정을 반복합니다.

이 구조 덕분에 HNSW는 IVFFlat보다 일반적으로 더 높은 재현율과 빠른 쿼리 속도를 동시에 낸다는 평가를 받습니다. 대신 그래프 구축 비용과 메모리 사용량이 훨씬 큽니다.

구분 IVFFlat HNSW
인덱스 구축 속도 빠름 느림(메모리·CPU 많이 씀)
쿼리 속도·재현율 준수하나 경계에서 손실 대체로 더 우수
적합한 상황 구축 시간·메모리가 빠듯한 대용량 쿼리 성능·재현율이 최우선

 

 

핵심 개념 3 — 재현율-지연-구축 비용의 삼각형

탐색 범위를 넓히면(probes나 ef_search를 늘리면) 재현율은 올라가지만 쿼리 지연도 함께 늘어납니다. 인덱스 구축 시 더 정교한 구조를 만들면(m, ef_construction을 늘리면) 쿼리 시점의 재현율·속도는 좋아지지만 구축 시간과 저장 공간이 커집니다. 어느 것도 공짜로 얻을 수 없다는 것이 ANN 인덱스 튜닝의 근본 제약입니다.

 

예제 — 인덱스 생성과 검색 파라미터 조정
-- HNSW 인덱스 생성
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 검색 시 재현율-지연 트레이드오프 조정
SET hnsw.ef_search = 100;

SELECT id, content FROM items
ORDER BY embedding <=> '[0.12, 0.87, ...]'::vector
LIMIT 10;

-- IVFFlat 인덱스 생성
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 1000);

SET ivfflat.probes = 20;

 

실무 포인트

재현율을 실측 없이 추정하지 마세요. 순차 스캔 결과를 기준 삼아, 인덱스를 쓴 근사 검색 결과와 얼마나 겹치는지(recall@k)를 실제 데이터셋으로 측정해야 합니다.

HNSW의 m, ef_construction은 인덱스 생성 후 바꿀 수 없습니다. 반면 ef_search와 IVFFlat의 probes는 쿼리 시점(세션 단위) 파라미터라 재생성 없이 즉시 조정 가능합니다.

주의 — 대량 삽입 후에는 IVFFlat 인덱스를 재검토해야 합니다. 클러스터 중심은 인덱스 생성 시점 데이터 분포로 고정되므로, 이후 데이터 분포가 크게 바뀌면 재현율이 서서히 떨어질 수 있습니다.
