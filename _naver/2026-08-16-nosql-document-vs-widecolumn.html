도큐먼트 vs 와이드컬럼 — NoSQL 데이터 모델링, 언제 무엇을 써야 할까

2026. 8. 16. · 데이터베이스

한 줄 요약 — 같은 NoSQL이라도 MongoDB 같은 도큐먼트 모델과 Cassandra 같은 와이드컬럼 모델은 데이터 구조와 설계 철학이 정반대라, 워크로드에 맞춰 골라야 합니다.

 

왜 지금 이 구분이 중요한가

"관계형은 무거우니 NoSQL로 가자"는 결정을 내리는 팀은 많은데, 정작 어떤 NoSQL이냐는 대충 넘어가는 경우가 흔합니다. 문제는 NoSQL이 하나의 모델이 아니라는 점입니다. MongoDB 같은 도큐먼트 모델과 Cassandra 같은 와이드컬럼 모델은 스키마리스, 조인 없음이라는 인상 때문에 비슷해 보이지만 실제 데이터 저장·조회 방식은 완전히 다릅니다.

이 차이를 모르고 고르면, 카산드라 테이블을 문서 DB처럼 설계했다가 조회 한 번에 전체 테이블을 스캔하거나, 몽고DB 컬렉션을 관계형처럼 정규화했다가 조인을 애플리케이션에서 다시 구현하는 상황이 벌어집니다. 오늘은 두 모델의 데이터 구조 차이와 각각 유리한 워크로드를 정리해봤습니다.

 

도큐먼트 모델(MongoDB)의 사고방식

도큐먼트 DB는 JSON과 비슷한 구조(BSON)로 하나의 엔티티를 문서 하나에 담습니다. 관계형이라면 여러 테이블에 나뉘어 있을 사용자와 최근 주문 목록을 문서 하나 안에 배열로 임베딩할 수 있고, 반대로 독립적으로 자주 조회되는 데이터는 별도 컬렉션으로 분리해 참조합니다. 스키마가 컬렉션 단위로 강제되지 않아 문서마다 필드가 달라도 되고, 이 유연성 덕분에 요구사항이 자주 바뀌는 서비스나 카테고리별 속성이 제각각인 상품 카탈로그에 잘 맞습니다.

 

와이드컬럼 모델(Cassandra)의 사고방식

와이드컬럼 스토어는 반대로 접근합니다. 먼저 "이 데이터를 어떤 쿼리로 조회할 것인가"를 정하고, 그 쿼리가 한 노드에서 빠르게 끝나도록 파티션 키와 클러스터링 키를 설계합니다. 같은 파티션 키를 가진 행들은 물리적으로 같은 노드에 모여 저장되고, 그 안에서 클러스터링 키 순서로 정렬됩니다. 정해진 접근 패턴은 매우 빠르지만 설계 시 고려하지 않은 조건으로 검색하는 쿼리는 비효율적이거나 아예 지원되지 않습니다. 조인이 없고 마스터 없는 구조라 노드를 늘리면 쓰기 처리량이 거의 선형으로 늘어나, 로그·시계열·이벤트처럼 쓰기가 많고 조회 패턴이 고정된 워크로드에 강합니다.

 

두 모델 비교
기준 도큐먼트(MongoDB) 와이드컬럼(Cassandra)
데이터 구조 중첩 가능한 JSON 유사 문서 파티션 키 + 클러스터링 키 기반 넓은 행
쿼리 유연성 임의 필드 조건·집계 지원 파티션 키 기반 조회가 기본
확장 방식 샤딩(레인지·해시 기반) 컨시스턴트 해싱, 쓰기 확장성 강점
대표 워크로드 카탈로그, 사용자 프로필, CMS 시계열, 센서 로그, 대규모 쓰기 이벤트

 

 

예제: 같은 데이터, 다른 설계

MongoDB에서는 사용자 문서 안에 최근 주문을 그대로 임베딩해서 조회 한 번으로 관련 데이터를 다 가져올 수 있습니다.

db.users.insertOne({
  _id: "user_123",
  name: "김민준",
  orders: [
    { orderId: "o1", amount: 32000 },
    { orderId: "o2", amount: 15000 }
  ]
});

// 조회 한 번으로 사용자와 최근 주문을 함께 가져온다(조인 없음)
db.users.findOne({ _id: "user_123" });

Cassandra에서는 같은 데이터를 조회 패턴에 맞춰 미리 테이블로 설계합니다. user_id로 파티셔닝하고 order_date로 정렬해두면, 사용자별 최신 주문 조회가 매우 빠릅니다.

CREATE TABLE orders_by_user (
  user_id text,
  order_date timestamp,
  order_id text,
  amount decimal,
  PRIMARY KEY (user_id, order_date)
) WITH CLUSTERING ORDER BY (order_date DESC);

SELECT order_id, amount FROM orders_by_user
WHERE user_id = 'user_123' LIMIT 10;

 

실무 도입 시 이것만은 챙기세요
1. 도큐먼트 임베딩은 무한 성장을 조심 — 계속 커지는 배열은 별도 컬렉션으로 분리하는 편이 안전합니다.
2. Cassandra는 테이블을 쿼리 단위로 여러 개 만드는 게 정상 — 관계형처럼 테이블 하나로 모든 쿼리를 처리하려 하지 않습니다.
3. 세컨더리 인덱스·ALLOW FILTERING은 예외적으로만 — 대규모 데이터에서는 전체 스캔에 가까워질 수 있습니다.
4. 강한 트랜잭션이 필요하면 두 모델 모두 한계가 있음 — 정산처럼 강한 정합성이 필수라면 관계형 DB 병행을 검토합니다.

 

마무리 — 3줄 요약

① 도큐먼트 모델(MongoDB)은 관련 데이터를 문서 하나에 임베딩해 유연한 스키마와 풍부한 쿼리를 지원합니다.
② 와이드컬럼 모델(Cassandra)은 쿼리 패턴을 먼저 정하고 파티션 키·클러스터링 키로 저장 위치를 설계하는 것이 핵심입니다.
③ 조회 패턴이 다양하면 도큐먼트, 쓰기량이 압도적이고 접근 패턴이 고정돼 있으면 와이드컬럼이 유리합니다.

읽어주셔서 감사합니다. NoSQL 도입을 검토하신다면 "우리 서비스의 조회 패턴이 얼마나 고정적인가"부터 먼저 점검해보시길 권해드립니다 🙂
