"에이전트 덕분에 더 빨리 나가겠죠?" — PR 리뷰가 새 병목이 됐을 때 다시 설계할 것

개발전략

한 줄 요약 — AI 코딩 에이전트가 짜는 코드 양이 늘면서 PR 볼륨과 크기가 함께 치솟았고, 리뷰 시간이 작성 시간보다 더 길어지는 조직이 늘고 있습니다. 2026년 업계 데이터를 근거로 리뷰 프로세스를 어디서부터 다시 설계해야 하는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"에이전트 다 붙였으니 이제 기능 출시 속도가 훨씬 빨라지겠죠?" — 경영진이나 PM이 흔히 하는 기대입니다. 실제로 코드 작성 속도는 분명히 빨라졌습니다. 문제는 그 다음 단계입니다. Faros AI가 1만 명 이상의 개발자를 분석한 결과, PR 볼륨은 98% 늘었는데 PR 리뷰에 걸리는 시간은 91% 더 늘었습니다. 코드를 짜는 속도가 빨라진 만큼 병목이 작성 단계에서 리뷰 단계로 그대로 옮겨갔을 뿐이라는 뜻입니다.

병목이 옮겨간 자리의 품질도 간단치 않습니다. LeadDev 분석에 따르면 AI가 작성한 PR은 평균 10.83건의 이슈를 안고 들어오는 반면 사람이 작성한 PR은 6.45건에 그쳤고, Kodus의 리서치에서도 AI 작성 코드는 PR당 리뷰 지적 사항이 1.6배 많았습니다. 여기에 DX의 조사는 PR 중앙값 크기가 44줄에서 72줄로 거의 두 배가 됐다고 보고합니다. "에이전트를 도입하면 더 빨리 나간다"는 기대가 "리뷰 체계를 그대로 두면 오히려 전체 출시 속도가 느려질 수 있다"는 실제 설계 문제로 번역되는 지점이 바로 여기입니다.

 

전체 시스템에서의 위치

에이전트를 도입하기 전 파이프라인은 코드 생성 → PR 생성 → 사람 리뷰어 한 명(또는 소수)의 단일 게이트 → 머지로 이어집니다. 이 구조에서 "리뷰어가 처리할 수 있는 PR 수"는 사람의 처리량에 묶여 있는 상수에 가깝습니다. 에이전트가 코드 생성 단계의 처리량만 올려버리면, 뒤에 있는 상수 처리량 게이트 앞에 PR이 쌓입니다.

재설계의 핵심은 게이트를 하나 더 늘리고 PR 단위를 쪼개는 것입니다. 에이전트가 생성한 변경을 리뷰 가능한 크기로 스택형(stacked) PR로 나누고, 그 앞에 자동화된 1차 게이트(린트, 보안 스캐너, 정책 체크, 또 다른 에이전트의 1차 리뷰)를 세웁니다. 사람 리뷰어는 이 1차 게이트를 통과한 PR만, 그것도 코드 한 줄 한 줄이 아니라 아키텍처와 의도가 맞는지 중심으로 봅니다.

 

선택의 트레이드오프
방식리뷰어 부담머지 지연언제 쓰면 안 되는가
기존 그대로(사람 전체 리뷰)계속 증가계속 증가PR 볼륨이 이미 용량을 넘어선 팀
PR 크기 상한 + 스택형 분할감소감소본질적으로 쪼개기 어려운 핵심 로직일 때
1차 자동 게이트 + 2차 사람 승인가장 적음가장 적음자동 게이트 구축·튜닝 여유가 없는 조직

 

세 번째 방식이 가장 매력적으로 보이지만 공짜는 아닙니다. 1차 게이트가 설익은 상태로 들어가면 "기계가 이미 걸러줬으니 괜찮겠지"라는 방심이 더해져 오히려 결함이 새어나갈 위험이 커집니다. Anthropic의 2026년 보고서도 사람 리뷰만으로는 늘어난 코드 생산량을 더 이상 흡수할 수 없다고 진단하면서, 동시에 에이전틱 품질관리가 사람 리뷰를 대체하는 게 아니라 역할을 나누는 장치여야 한다는 점을 강조합니다.

 

실제 진행 순서
CHANGED=$(git diff --shortstat origin/main | awk '{print $4+$6}')
if [ "$CHANGED" -gt 400 ]; then
  echo "PR이 400줄을 넘습니다 - 스택형 분할을 검토하세요"
fi

1) 현재 기준선부터 잽니다 — 평균 PR 크기, 첫 리뷰까지 걸리는 시간, 리뷰당 지적 사항 수를 2~4주 측정합니다. 2) PR 크기 상한 정책과 스택형 PR 템플릿부터 도입합니다. 3) 1차 자동 게이트를 사람 리뷰 앞에 배치하되, 처음엔 경고 모드로 오탐률을 먼저 확인합니다. 4) 사람 리뷰어의 역할을 "아키텍처·의도·엣지케이스 판단"으로 공식 재정의합니다. 5) 측정 지표를 처리량에서 리뷰 시작까지 걸린 시간, 머지 후 결함률 같은 결과 지표로 바꿉니다.

 

주의 — 처리량(머지된 PR 수)만 지표로 삼으면 다시 "빨리 밀어내는" 쪽으로 역주행합니다. 결과 지표를 반드시 함께 보세요.
