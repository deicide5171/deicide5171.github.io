PostgreSQL 파티셔닝 전략 — Range/List/Hash 파티션과 파티션 프루닝

DB·데이터 모델링

한 줄 요약 — 파티셔닝의 이득은 파티션 프루닝에서 나옵니다. Range/List/Hash 전략과 프루닝이 실제로 성립하는 조건을 정리했습니다.

 

왜 지금 파티셔닝을 다시 봐야 하는가

테이블이 수억 건으로 커지면 인덱스 크기 자체가 메모리에 다 올라가지 않고, VACUUM·백업 소요 시간도 늘어납니다. 파티셔닝은 논리적 테이블을 여러 물리적 파티션으로 나눠 필요한 파티션만 건드리도록 만듭니다. 다만 파티션 키 선택과 쿼리 조건이 맞지 않으면 모든 파티션을 스캔하는 최악의 상황에 빠질 수 있습니다.

 

Range, List, Hash 파티션의 적합한 상황

Range는 날짜·숫자 범위로 나눠 시계열 데이터에 적합하고 오래된 파티션 드롭이 쉽습니다. List는 값 종류가 제한적일 때, Hash는 자연스러운 범위가 없지만 쓰기 부하를 고르게 분산하고 싶을 때 씁니다.

 

파티션 프루닝이 실제로 동작하는 조건

쿼리 플래너가 WHERE 절만으로 "이 조건은 특정 파티션에만 있다"고 판단하면 나머지를 제외합니다. 하지만 파티션 키에 함수를 씌우거나 다른 컬럼으로만 필터링하면 플래너가 판단하지 못해 모든 파티션을 스캔할 수 있습니다.

파티션 방식 적합한 데이터 프루닝 조건
Range 시계열(로그, 주문) 날짜/숫자 범위 조건
List 값 종류 제한적 등치/IN 조건
Hash 균등 분산 필요 등치 조건만

 

예제 — Range 파티션 생성과 프루닝 확인
CREATE TABLE orders (
    id BIGSERIAL,
    created_at TIMESTAMPTZ NOT NULL,
    customer_id BIGINT,
    total NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- 프루닝 됨
EXPLAIN SELECT * FROM orders WHERE created_at >= '2026-02-10';

-- 프루닝 안 됨 (함수로 감쌈)
EXPLAIN SELECT * FROM orders WHERE DATE_TRUNC('month', created_at) = '2026-02-01';

 

실무 포인트

애플리케이션의 실제 쿼리가 파티션 키를 직접 조건절에 쓰는지 먼저 확인하세요. 함수를 씌우거나 다른 컬럼으로만 필터링하면 프루닝 이득을 얻지 못합니다.

파티션 키는 유니크 제약·프라이머리 키에도 포함돼야 하는 PostgreSQL 제약을 미리 파악하세요. 기존 스키마에 나중에 도입할 때 PK 구조 변경이 필요한 경우가 많습니다.

주의 — 파티션 개수가 지나치게 많아지지 않도록 관리하세요. 수백~수천 개로 늘어나면 쿼리 플래너의 계획 수립 시간 자체가 늘어나는 역효과가 날 수 있습니다.
