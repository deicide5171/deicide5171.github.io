삭제 대신 숨기기 — Soft Delete 패턴 설계와 그 대가

데이터베이스

한 줄 요약 — 행을 실제로 지우지 않고 deleted_at 같은 플래그로 숨기는 Soft Delete는 복구성과 무결성을 지켜주지만, 조회 로직과 유니크 제약을 함께 재설계해야 합니다.

 

왜 진짜로 지우지 않는가

사용자가 계정 삭제를 요청했을 때 실제로 DELETE 문을 실행하면, 그 사용자가 남긴 게시글·결제 내역의 참조 관계가 깨지거나 "탈퇴한 사용자" 표시조차 할 수 없게 됩니다. 그래서 많은 서비스가 deleted_at 컬럼에 값을 채우는 것으로 삭제를 표현합니다.

 

Soft Delete vs Hard Delete
항목 Soft Delete Hard Delete
복구 가능 불가능
조회 쿼리 조건 추가 필요 조건 불필요
개인정보 완전 삭제 별도 조치 필요 기본 충족

 

잘못된 접근: 모든 테이블에 일괄 적용

첫째, 모든 조회 쿼리에 WHERE deleted_at IS NULL 조건을 빠뜨리면 삭제된 데이터가 그대로 노출됩니다. 둘째, 유니크 제약이 깨집니다. 이메일에 유니크 제약이 걸려 있으면 소프트 삭제된 사용자와 같은 이메일로 재가입할 때 제약 위반 에러가 납니다. 셋째, 개인정보를 소프트 삭제만 해두면 법적 삭제 요구를 충족하지 못합니다.

올바른 접근
-- 부분 인덱스로 삭제되지 않은 행에서만 유니크 보장 (PostgreSQL)
CREATE UNIQUE INDEX users_email_active_uidx
  ON users (email)
  WHERE deleted_at IS NULL;

부분 인덱스를 쓰면 삭제된 이메일로 재가입하는 시나리오가 정상 동작합니다. 조회 로직은 ORM의 글로벌 스코프나 뷰(View)로 감싸서 개발자가 조건을 매번 기억하지 않아도 안전하게 동작하도록 만드는 것이 좋습니다.

주의 — 개인정보는 소프트 삭제와 별개로 익명화·파기 프로세스를 둬야 합니다. "논리적으로 삭제됨"과 "실제 개인정보가 남아있음"은 법적으로 다른 문제입니다.

 

실무 포인트

모든 테이블에 일괄 적용하지 말고 테이블 성격에 따라 판단하세요. 감사·복구가 중요한 주문·결제 테이블은 Soft Delete, 세션 같은 임시성 데이터는 Hard Delete가 더 적합합니다. 또한 오래된 소프트 삭제 데이터는 배치로 완전 삭제하거나 파티셔닝해 테이블이 무한정 커지지 않게 관리해야 합니다.
