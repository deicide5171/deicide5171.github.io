GitHub Actions 빌드가 느릴 때 — 캐시 전략으로 CI 시간 줄이기

인프라

한 줄 요약 — CI 시간 낭비의 대부분은 컴파일이 아니라 의존성 재설치에서 발생하며, hashFiles 기반 캐시 키 설계로 대부분 해결됩니다.

 

왜 CI가 점점 느려지는가

레포지토리 초반엔 CI가 1~2분이면 끝나지만, 의존성이 늘면서 PR 하나 올릴 때마다 오래 기다리게 됩니다. 확인해보면 대부분의 시간이 npm install, gradlew build 같은 의존성 설치 단계에서 소모됩니다. 캐시 설정을 아예 안 했거나, 캐시 키를 잘못 잡아 매번 미스가 나는 경우가 흔합니다.

 

잘못된 설정 vs 올바른 설정
<!-- 잘못된 예: 커밋마다 키가 달라져 캐시가 매번 새로 생성됨 -->
key: npm-cache-${{ github.sha }}

이렇게 하면 다음 실행에서 정확히 같은 SHA가 나올 일이 없어 항상 캐시 미스가 납니다. 핵심은 의존성 정의 파일 내용이 바뀔 때만 캐시 키가 바뀌게 하는 것입니다.

key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
restore-keys: |
  npm-${{ runner.os }}-

hashFiles()는 락파일이 바뀌지 않는 한 항상 같은 값을 반환하므로 캐시를 재사용합니다. restore-keys는 정확한 키가 없을 때 접두사가 일치하는 가장 최근 캐시를 대신 가져오는 폴백 역할을 합니다.

언어 캐시 경로 키 기준 파일
Node.js ~/.npm package-lock.json
Java(Gradle) ~/.gradle/caches *.gradle*
Python ~/.cache/pip requirements.txt

setup-node, setup-java 같은 공식 액션은 cache: 'npm'처럼 옵션 하나만 켜면 위 설정을 대신 처리해주므로, 직접 캐시를 조합하기 전에 사용 중인 setup 액션의 내장 캐시부터 확인하세요.

주의 — GitHub Actions 캐시는 저장소당 총량 제한이 있어 오래된 캐시가 자동으로 밀려납니다. 캐시 히트율이 갑자기 떨어졌다면 이 제한에 걸린 건 아닌지 확인하세요.

 

실무 포인트

Docker 이미지를 빌드하는 워크플로우라면 build-push-action의 cache-from/cache-to(type=gha)도 함께 설정하세요. 모노레포는 락파일 하나로 전체 캐시 키를 잡으면 한 패키지만 바뀌어도 전체가 무효화되므로, 워크스페이스별로 캐시 키를 나누는 편이 유리합니다.
