Spring Boot 3.4/3.5 신규 기능 총정리 — 지금 업그레이드해야 하는 이유

2026. 8. 20. · 백엔드

한 줄 요약 — Spring Boot 3.4/3.5대에서는 구조화 로깅, 프로파일별 설정 병합, ProblemDetail·Jackson 직렬화, Actuator 헬스체크 쪽에 실무 영향이 큰 변화가 있었습니다. 업그레이드 전에 확인해야 할 포인트를 정리했습니다.

 

마이너 업그레이드, 왜 자꾸 미루게 될까요

메이저 버전 업그레이드는 마이그레이션 가이드를 정독하고 준비하지만, 마이너 버전은 "패치 정도만 올리면 되겠지"라는 생각으로 방치되는 경우가 많습니다. 문제는 릴리스 주기가 촘촘한 만큼 변경 사항이 누적되고, 나중에 한꺼번에 여러 버전을 건너뛰려 하면 오히려 더 큰 부담이 된다는 점입니다.

Spring Boot 3.4/3.5대는 이렇게 미뤄두기 어려운 릴리스에 가깝습니다. 로깅, 설정 구성, 예외 응답 포맷, Actuator 등 애플리케이션의 기본 골격에 해당하는 부분에서 실무 영향이 큰 변화가 여럿 포함되어 있기 때문입니다. 오늘은 이 두 버전대에서 실제로 다뤄진 대표적인 변화와, 업그레이드 전에 점검해야 할 항목을 정리해보겠습니다.

 

핵심 개념 1 — 구조화 로깅(Structured Logging) 지원

Spring Boot 3.4대부터는 별도의 커스텀 인코더나 외부 라이브러리 설정 없이, 애플리케이션 설정만으로 로그를 JSON 형식의 구조화된 포맷으로 출력할 수 있게 되었습니다. 기존에는 Logback이나 Log4j2 설정 파일에 JSON 인코더를 직접 구성하거나 logstash-logback-encoder 같은 외부 의존성을 추가해야 했지만, 이제는 프로퍼티 몇 줄만 지정하면 표준 포맷(ECS, GELF 등) 중 하나로 즉시 출력할 수 있습니다.

컨테이너 환경에서 로그를 수집기(Fluentd, Filebeat 등)로 넘길 때 파싱 규칙을 별도로 관리하지 않아도 된다는 점에서, 클라우드 네이티브 운영 환경에 특히 유용한 변화입니다. 사용자 정의 포맷을 직접 구현해 등록할 수 있는 확장 지점도 함께 제공되므로, 사내 표준 로그 스키마가 이미 있다면 그쪽으로 확장하는 방향도 검토해볼 만합니다.

 

핵심 개념 2 — 프로파일별 설정 구성 개선

프로파일 특화 설정 파일의 로딩 순서와 우선순위 관련 개선이 3.4/3.5대에 걸쳐 이어졌습니다. 특히 YAML 다중 문서 구조가 프로파일 그룹과 조합될 때 발생하던 일부 모호한 우선순위 케이스가 정리되었고, 설정 값의 출처를 추적하기 위한 진단 정보도 개선되었습니다.

정확한 세부 동작은 버전별로 조금씩 다르기 때문에, 여러 프로파일 설정 파일을 조합해서 사용하는 프로젝트라면 업그레이드 후 실제 병합 결과를 반드시 재확인하는 것이 안전합니다. 로그나 Actuator의 환경 엔드포인트로 최종 설정 값을 확인해보는 습관을 들이면 좋습니다.

영역 주요 변화 실무 영향
구조화 로깅 프로퍼티만으로 JSON 로그 출력 로그 수집 파이프라인 단순화
프로파일 구성 우선순위·병합 로직 정리 병합 결과 재검증 필요
ProblemDetail/Jackson 직렬화 동작 예측 가능성 개선 에러 응답 스펙 재확인
Actuator 헬스체크 그룹별 상세도·상태 조합 개선 프로브 임계값 재점검

 

핵심 개념 3 — ProblemDetail·Jackson, 그리고 Actuator 헬스체크

Spring Framework 6.x 계열과 맞물려, 예외를 RFC 9457 ProblemDetail 형식으로 응답할 때의 직렬화 동작이 다듬어졌습니다. 커스텀 필드를 properties에 추가하는 방식과 Jackson 모듈 등록 방식이 이전보다 예측 가능해졌고, 전역 예외 처리기를 사용하는 REST API에서 에러 응답 포맷을 통일하기가 한결 수월해졌습니다.

Actuator의 헬스 인디케이터 쪽에서도 그룹별 상세도 노출 제어와 개별 컴포넌트 상태를 조합하는 방식에 다듬기가 이어졌습니다. 쿠버네티스 liveness/readiness 프로브와 연동해 헬스 엔드포인트를 쓰는 구성이 일반화된 만큼, 업그레이드 후 /actuator/health 응답 구조를 스테이징 환경에서 한 번 비교해보는 것을 권합니다.

 

예제 — 구조화 로깅 및 프로파일 설정
# application.properties
logging.structured.format.console=ecs
logging.structured.format.file=ecs

ecs 대신 조직에서 이미 쓰고 있는 로그 수집 표준에 맞는 포맷을 지정하거나, 커스텀 포맷터 빈을 등록해 대체할 수 있습니다.

# application.yml — 프로파일별 병합 예시
spring:
  profiles:
    group:
      production: "prod-db,prod-logging"
---
spring:
  config:
    activate:
      on-profile: prod-logging
logging:
  structured:
    format:
      console: ecs

 

실무 도입 시 이것만은 챙기세요
1. 로그 파이프라인 담당자와 먼저 논의하기 — 구조화 로깅을 켜기 전 수집기 파싱 규칙이 텍스트 로그 기준인지 확인
2. 프로파일 병합 결과 직접 검증하기 — 여러 프로파일 파일·그룹을 조합해 쓴다면 업그레이드 후 최종 병합 값 재확인
3. 에러 응답 포맷 계약 재점검하기 — ProblemDetail 기반 API의 클라이언트 공유 스키마가 그대로인지 통합 테스트로 확인
4. 헬스체크 프로브 설정 스테이징에서 먼저 검증하기 — 응답 구조 변화가 liveness/readiness 실패로 이어지지 않는지 확인
5. 연관 의존성 버전 함께 확인하기 — Spring Framework, Jackson 등이 함께 올라가므로 사내 공용 라이브러리 고정 버전 점검

 

마무리 — 3줄 요약

① Spring Boot 3.4/3.5대는 구조화 로깅, 프로파일 설정 병합, ProblemDetail·Jackson 직렬화, Actuator 헬스체크 등 애플리케이션 기본 골격에 영향을 주는 변화를 다수 포함하고 있습니다.
② 구조화 로깅은 별도 인코더 설정 없이 프로퍼티만으로 JSON 로그를 출력할 수 있게 해주지만, 기존 로그 수집 파이프라인과의 호환 여부를 먼저 확인해야 합니다.
③ 업그레이드 전에는 프로파일 병합 결과, 에러 응답 포맷, 헬스체크 응답 구조를 스테이징 환경에서 직접 검증하는 체크리스트를 거치는 것이 안전합니다.
