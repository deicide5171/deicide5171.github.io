React Compiler 파헤치기 — useMemo/useCallback 없는 세상이 올까

2026. 8. 20. · 프론트엔드

한 줄 요약 — 수동 메모이제이션 없이도 리렌더링을 자동 최적화하겠다는 React Compiler가 실제로 어떤 원리로 동작하고, 어떤 코드에서는 여전히 수동 개입이 필요한지 정리했습니다.

 

왜 지금 React Compiler일까요

리스트 아이템 하나에 콜백을 내려주려다 useCallback을 붙이고, 그 콜백이 의존하는 값에 useMemo를 붙이고, 다시 그 값을 계산하는 함수에 useCallback을 붙이는 흐름은 React 컴포넌트를 짜본 분이라면 낯설지 않으실 겁니다. 문제는 이 패턴이 반복될수록 정작 컴포넌트가 하는 일보다 "무엇을 언제 다시 계산할지"를 설명하는 코드가 더 길어진다는 점입니다. 의존성 배열 하나를 빠뜨리면 오래된 값을 참조하는 버그가 생기고, 반대로 과도하게 메모이제이션을 걸면 비교 비용만 늘어 성능에 도움이 안 되는 경우도 흔했습니다.

React 팀은 이 부담을 개발자의 손이 아니라 빌드 타임 컴파일러로 옮기는 방향을 택했습니다. React Compiler는 컴포넌트와 훅의 소스 코드를 정적으로 분석해서, 개발자가 손으로 붙이던 useMemo·useCallback·React.memo를 컴파일 결과물에 자동으로 삽입해 줍니다. 코드는 최적화 이전의 단순한 형태로 남겨두고, 실제 최적화는 빌드 단계에서 기계적으로 처리하겠다는 접근입니다.

 

핵심 개념 1 — 정적 분석으로 메모이제이션을 자동 삽입하는 원리

React Compiler는 컴포넌트 함수와 커스텀 훅의 본문을 분석해서, 어떤 값이 어떤 입력(prop, state, 다른 변수)에 의존하는지 의존성 그래프를 구성합니다. 이 그래프를 바탕으로 렌더링마다 다시 계산할 필요가 없는 값과 함수를 찾아내고, 입력이 바뀌지 않았으면 캐시해 둔 값을 그대로 재사용하도록 코드를 변환합니다. 결과물은 사람이 useMemo를 촘촘히 박아 넣은 코드와 개념적으로 비슷하지만, 실제로는 컴파일러 전용의 저수준 캐싱 메커니즘을 사용합니다.

중요한 점은, 컴파일러가 판단을 잘못하더라도 최악의 경우 "메모이제이션을 덜 적용하는" 방향으로만 안전하게 실패하도록 설계돼 있다는 것입니다. 즉 성능 이득을 놓칠 수는 있어도, 이 판단 실수 때문에 화면이 아예 잘못 그려지는 상황은 피하도록 만들어져 있습니다.

 

핵심 개념 2 — Rules of React 준수가 왜 전제조건일까요

이 자동화가 성립하려면 컴포넌트와 훅이 순수 함수처럼 동작해야 합니다. 같은 입력에는 항상 같은 출력을 내고, 렌더링 도중에 외부 상태를 직접 바꾸지 않으며, 훅 호출 순서가 조건문에 따라 바뀌지 않아야 합니다. React 팀이 오래전부터 문서화해 온 이른바 Rules of React — 컴포넌트를 순수하게 유지하기, 훅을 최상위에서만 호출하기 같은 규칙 — 를 어기면 컴파일러가 의존성을 잘못 추론해서 화면이 갱신되지 않거나 오래된 값을 그대로 보여주는 문제가 생길 수 있습니다.

다시 말해 React Compiler는 새로운 규칙을 추가하는 것이 아니라, 원래부터 지켜야 했던 규칙을 지켰을 때만 안전하게 작동하는 도구입니다. 이 때문에 팀 차원에서는 eslint-plugin-react-hooks 규칙을 엄격하게 적용해 두는 것이 컴파일러 도입의 실질적인 선행 조건이 됩니다.

 

핵심 개념 3 — 수동 메모이제이션과 비교하면
구분 수동 메모이제이션 React Compiler
적용 방식 개발자가 직접 useMemo/useCallback/memo 삽입 빌드 타임에 컴파일러가 자동 삽입
실수 가능성 의존성 배열 누락·과다 적용 등 사람 실수 정적 분석 기준으로 일관되게 처리
가독성 최적화 코드가 비즈니스 로직과 뒤섞임 소스 코드는 최적화 이전 형태 유지
전제 조건 별도 규칙 없음(단, 잘못 쓰면 버그) 컴포넌트·훅이 Rules of React를 준수해야 함
세밀한 제어 특정 값만 골라 수동으로 최적화 가능 컴파일러 판단에 맡기되, 필요시 옵트아웃 가능

 

표에서 보듯 두 방식이 완전히 대체 관계는 아닙니다. 컴파일러가 처리하기 어려운 경계 상황이나, 특정 최적화를 명시적으로 강제하고 싶은 구간에서는 여전히 수동 메모이제이션이나 옵트아웃 지시어를 함께 쓰는 편이 현실적입니다.

 

예제: 컴파일 전과 후 코드 비교

컴파일 이전 소스 코드는 다음과 같이 최적화를 신경 쓰지 않은 단순한 형태로 작성합니다.

// 컴파일 전 — 개발자가 작성하는 원본 코드
function ProductList({ items, onSelect }) {
  const sorted = items.slice().sort((a, b) => a.price - b.price);
  const handleClick = (id) => onSelect(id);

  return (
    <ul>
      {sorted.map((item) => (
        <li key={item.id} onClick={() => handleClick(item.id)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}

 

React Compiler를 거치면 개념적으로 아래와 같이 값과 콜백이 자동으로 캐시됩니다(실제 산출물은 컴파일러 내부 표현을 쓰며, 아래는 그 의도를 사람이 읽을 수 있게 옮긴 것입니다).

// 컴파일 후 — 컴파일러가 자동으로 메모이제이션을 적용한 형태(개념적 표현)
function ProductList({ items, onSelect }) {
  const sorted = useMemo(
    () => items.slice().sort((a, b) => a.price - b.price),
    [items]
  );
  const handleClick = useCallback((id) => onSelect(id), [onSelect]);

  return (
    <ul>
      {sorted.map((item) => (
        <li key={item.id} onClick={() => handleClick(item.id)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
}

개발자는 첫 번째 형태만 작성하고 유지보수하면 되고, 두 번째 형태에 해당하는 최적화는 빌드 파이프라인이 대신 책임져 줍니다.

 

실무 도입 시 이것만은 챙기세요
1. 점진적 도입을 전제로 설계돼 있습니다 — 파일·디렉터리 단위로 켜고 끌 수 있어 레거시 코드 전체를 한 번에 손보지 않아도 됩니다
2. ESLint 규칙을 먼저 정비하세요 — eslint-plugin-react-hooks 위반 사항을 해소하는 작업이 컴파일러 도입보다 선행돼야 실제 이득을 볼 수 있습니다
3. 서드파티 훅을 감싸는 코드는 별도로 점검하세요 — 규칙을 어기는 외부 훅이 있으면 잘못된 최적화가 적용될 여지가 있어, 초기에는 해당 구간을 옵트아웃하는 편이 안전합니다
4. 기존 수동 메모이제이션을 무조건 걷어내지 마세요 — 참조 안정성을 명시적으로 보장해야 하는 구간은 남겨두는 편이 나을 수 있습니다
5. 성능 수치는 프로젝트마다 직접 검증하세요 — 리렌더링 감소 폭은 컴포넌트 구조에 따라 달라지므로 도입 전후를 프로파일링으로 비교해야 합니다

 

마무리 — 3줄 요약

① React Compiler는 컴포넌트·훅을 정적 분석해서 useMemo/useCallback을 빌드 타임에 자동으로 삽입해 주는 도구입니다.
② 이 자동화는 컴포넌트가 Rules of React(순수성, 훅 호출 규칙)를 지킬 때만 안전하게 동작하므로, 도입 전 ESLint 규칙 정비가 사실상 선행 조건입니다.
③ 기존 수동 메모이제이션을 전면 대체하기보다, 컴파일러가 커버하기 어려운 구간에서는 여전히 수동 개입이나 옵트아웃이 필요합니다.
