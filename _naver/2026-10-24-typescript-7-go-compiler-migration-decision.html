TypeScript 7, tsc가 Go로 다시 태어났다 — 10배 빨라진 대신 무엇이 조용히 깨지는가

STACK

한 줄 요약 — "CI 타입체크가 너무 오래 걸려요"라는 요구에 TypeScript 7.0의 네이티브 Go 컴파일러는 8~12배 빠른 답을 내놓지만, 그 대가로 커스텀 트랜스포머·ts-patch·ts-morph 같은 프로그래매틱 API 위에 쌓인 툴체인을 조용히 무너뜨릴 수 있습니다. 무엇이 깨지고, 무엇부터 점검하고, 어떻게 단계적으로 올려야 하는지 정리했습니다.

 

왜 지금 이 판단이 필요한가

"레포가 커지니까 tsc --noEmit CI 단계가 3분, 5분씩 걸려요. 좀 빠르게 해주세요." 모노레포를 운영하는 팀이라면 한 번쯤 받아봤을 요구사항입니다. 그동안 답은 늘 비슷했습니다. 프로젝트 레퍼런스로 쪼개거나, 증분 빌드 캐시를 쓰거나, 타입체크를 별도 잡으로 분리하는 식이었죠. 어느 쪽도 "타입체커 자체가 JavaScript로 짜여 있어서 느리다"는 근본 문제는 건드리지 못했습니다.

Microsoft는 2026년 7월 8일 TypeScript 7.0을 정식 출시하며 이 전제를 뒤집었습니다. 코드명 Corsa, tsc의 핵심 로직을 Go로 완전히 재작성한 네이티브 컴파일러입니다. 공식 발표에 따르면 전체 빌드 기준 8~12배 속도 향상이 보고됐습니다. 문제는 이 재작성이 단순 포팅이 아니라는 점입니다. 기존 TypeScript(코드명 Strada)의 JavaScript 기반 프로그래매틱 컴파일러 API 위에 지어진 생태계 — ts-patch, 커스텀 AST 트랜스포머, ts-morph 같은 도구들 — 가 7.0의 Go 바이너리에서는 동작할 API 표면 자체가 없습니다. 빌더 입장에서 중요한 질문은 "더 빨라지는가"가 아니라 "우리 툴체인 중 무엇이 그 API에 의존하고 있고, 지금 올려도 되는가"입니다.

 

가장 조용히, 가장 흔하게 깨지는 지점

TypeScript 7.0은 두 개의 컴파일러가 공존하는 과도기 산물입니다. 일반적인 "컴파일하고 타입 에러 보여주기" 용도로는 6.x와 거의 동일하게 동작합니다. 문제는 프로그래매틱 컴파일러 API 자체가 7.1로 연기됐다는 점입니다.

ts-patch·커스텀 트랜스포머를 tsconfig.json에 등록해 쓰던 프로젝트는 Corsa가 해당 훅을 조용히 건너뛸 수 있습니다. "컴파일은 되는데 런타임에 뭔가 빠져 있다"는 형태로 나타나기 쉽습니다. ts-morph 기반 코드 생성 스크립트는 Strada의 프로그램 API에 의존하므로, 7.1 API가 나오기 전까지는 구버전을 별도로 고정해야 합니다. ts-jest 등 테스트 러너 통합도 내부 Strada API를 직접 호출한다면 깨진다는 보고가 있습니다. 다행히 7.0은 개발 도구가 구버전 API로 폴백하고 실제 컴파일만 Go 러너가 맡는 듀얼 설치 구성을 지원합니다.

 

전체 시스템에서의 위치

TypeScript 컴파일러는 혼자 동작하지 않습니다. 에디터 LSP, CI 타입체크, 번들러의 트랜스파일, 플러그인 생태계가 같은 typescript 패키지를 서로 다른 방식으로 호출합니다. 번들러의 실제 트랜스파일은 이미 대부분 esbuild·SWC·oxc 같은 네이티브 도구가 맡고 있었기 때문에 Corsa 전환의 직접 영향권 밖입니다. Corsa가 실제로 바꾸는 것은 타입 체크 자체가 일어나는 경로 — 에디터의 실시간 타입 힌트와 CI의 tsc --noEmit — 그리고 그 결과에 프로그래매틱으로 접근하던 플러그인·스크립트 계층입니다.

 

선택의 트레이드오프
선택지 장점 단점
즉시 전면 전환 8~12배 빌드 속도, CI 비용 즉시 절감 커스텀 트랜스포머·스크립트 전수 재검증 필요
듀얼 설치(타입체크만 전환) 속도 개선 + 기존 툴체인 유지 두 버전 당분간 함께 관리
당분간 6.x 유지 리스크 제로 속도 이점 전혀 없음

 

모노레포에 데코레이터 메타데이터를 가공하는 커스텀 트랜스포머가 하나라도 박혀 있다면, 즉시 전면 전환은 사실상 배제해야 합니다. 듀얼 설치로 타입체크 레이어만 먼저 옮기고, 플러그인 의존 스크립트는 7.1 공개 이후로 미루는 쪽이 현실적입니다.

 

실제 프로젝트 진행 순서

1. tsconfig.json의 plugins·transform 설정과 ts-patch, ttypescript 레지스트리 의존을 전수 조사합니다.
2. ts-morph·커스텀 코드 생성 스크립트를 분리하고, 그 스크립트만 TypeScript 6.x에 고정합니다.
3. CI의 타입체크 단계만 먼저 Corsa(7.0)로 교체해 속도를 측정합니다. 번들러 트랜스파일은 손대지 않습니다.
4. ts-jest 등 테스트 통합이 내부 API를 직접 호출하는지 확인하고, 깨지면 테스트 전용으로 구버전을 고정합니다.
5. 에디터 플러그인은 Language Service Plugin API만 쓰는지 확인 후 적용합니다.
6. 7.1 프로그래매틱 API 공개 공지를 구독해 두고, 공개 즉시 2차 전환을 계획합니다.

 

예제 코드:

// package.json — 듀얼 설치 구성 예시
{
  "devDependencies": {
    "typescript": "^7.0.0",
    "typescript-strada": "npm:typescript@^6.9.0"
  },
  "scripts": {
    "typecheck": "tsc --noEmit",
    "generate:types": "typescript-strada-node scripts/generate-types.ts"
  }
}

 

주의 — "프로젝트가 6.0에서 깨끗이 컴파일되면 7.0에서도 변경 없이 동일하게 컴파일된다"는 말은 평범한 프로젝트에만 해당합니다. 프로그래매틱 API나 커스텀 트랜스포머를 하나라도 쓰고 있다면 반드시 별도로 검증하세요.

 

정리

TypeScript 7.0(Corsa)은 tsc 자체를 Go로 재작성해 8~12배 빠른 타입체크를 제공하지만, 프로그래매틱 컴파일러 API는 7.1로 연기돼 ts-patch·ts-morph·일부 테스트 통합이 조용히 깨질 수 있습니다. 번들러의 트랜스파일 경로는 이미 esbuild·SWC가 맡고 있어 영향이 적고, 실제 영향은 에디터 LSP와 CI 타입체크, 플러그인 계층에 집중됩니다. 플러그인·코드 생성 의존이 있는 프로젝트는 타입체크 레이어만 먼저 Corsa로 옮기는 듀얼 설치 전략이 안전합니다.
