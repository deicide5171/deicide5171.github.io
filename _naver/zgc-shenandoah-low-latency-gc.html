ZGC와 Shenandoah — 저지연 GC 알고리즘 내부 동작과 언제 써야 하는가

백엔드

한 줄 요약 — ZGC와 Shenandoah는 힙 크기와 무관하게 정지 시간을 일정하게 유지합니다. 컬러 포인터와 로드 배리어로 이를 구현하는 원리를 정리했습니다.

 

왜 지금 저지연 GC를 다시 봐야 하는가

G1GC도 영역 단위로 점진 수거하지만, 특정 단계에서는 여전히 Stop-The-World 정지가 발생하며 힙이 커질수록 정지 시간도 늘어나는 경향이 있습니다. ZGC와 Shenandoah는 힙 크기와 무관하게 정지 시간을 한 자릿수 밀리초 이내로 유지하는 것을 목표로 설계됐습니다.

 

대부분의 GC 작업을 애플리케이션 스레드와 동시에 수행한다

ZGC와 Shenandoah는 객체 이동과 참조 갱신 대부분을 애플리케이션 스레드가 계속 실행되는 동안 동시에 수행합니다. 정지가 필요한 구간은 GC 사이클 시작·종료의 짧은 동기화 지점 정도로 최소화됩니다.

 

컬러 포인터와 로드 배리어로 "이동 중인 객체" 문제를 푼다

ZGC는 64비트 포인터의 상위 비트에 GC 상태를 메타데이터로 인코딩하는 컬러 포인터 기법을 씁니다. 참조를 읽을 때(로드 배리어)마다 메타데이터를 확인해 이동된 객체면 즉시 새 주소로 고쳐 씁니다. Shenandoah는 각 객체 헤더에 forwarding pointer를 두는 Brooks Pointer 방식을 씁니다.

항목 G1GC ZGC / Shenandoah
목표 처리량-지연 균형 힙 크기 무관 초저지연
이동 중 참조 처리 STW 구간에서만 컬러 포인터/Brooks Pointer
힙 확장성 수십 GB에서 정지 증가 테라바이트급까지 안정

 

예제 — ZGC 활성화와 기본 로그 확인
java -XX:+UseZGC -Xmx32g \
     -Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=50m \
     -jar application.jar

# GC(N) Pause Mark Start, Pause Mark End, Pause Relocate Start 등
# 각 Pause 시간이 힙 크기와 무관하게 일정한지 확인

 

실무 포인트

애플리케이션의 실제 지연시간 요구사항을 먼저 계량화하세요. p99 지연이 이미 네트워크·DB 요인에 좌우된다면 저지연 GC 도입 효과가 기대만큼 크지 않을 수 있습니다.

처리량 저하 가능성을 감안하세요. 로드 배리어 오버헤드로 일부 워크로드에서는 G1 대비 처리량이 낮게 나올 수 있습니다.

주의 — JDK 버전과 배포판별 지원 상태를 확인하세요. ZGC, Shenandoah 모두 여러 버전에 걸쳐 개선돼 왔으므로 사용 중인 배포판에서의 성숙도를 확인해야 합니다.
