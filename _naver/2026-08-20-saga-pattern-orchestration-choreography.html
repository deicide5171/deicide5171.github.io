사가(Saga) 패턴 — 마이크로서비스 분산 트랜잭션을 조율하는 두 가지 방법

2026. 8. 20. · 시스템 설계

한 줄 요약 — 마이크로서비스로 쪼개진 서비스 사이에서 하나의 비즈니스 트랜잭션을 완성해야 할 때, 2PC 대신 널리 쓰이는 Saga 패턴을 오케스트레이션 방식과 코레오그래피 방식으로 나눠 정리했습니다.

 

왜 2PC 대신 Saga일까요

모놀리스 시절에는 주문 생성, 재고 차감, 결제 처리를 하나의 DB 트랜잭션으로 묶어 커밋하거나 롤백하면 그만이었습니다. 하지만 이 세 기능이 서로 다른 마이크로서비스로 나뉘고 각자 독립된 데이터베이스를 갖는 순간, 단일 트랜잭션이라는 전제 자체가 사라집니다. 교과서적으로는 2PC(2단계 커밋)를 떠올릴 수 있지만, 2PC는 커밋 준비가 끝난 참여자가 코디네이터의 최종 지시를 기다리는 동안 관련 리소스에 락을 걸어 둔 채 블로킹된다는 근본적인 한계가 있습니다.

이 락은 서비스 하나가 응답하지 않거나 네트워크가 잠깐 끊기기만 해도 전체 트랜잭션을 오래 붙잡아 둘 수 있고, 서비스마다 배포 주기와 가용성 목표가 다른 마이크로서비스 환경에서는 이 결합이 곧 장애 전파 경로가 됩니다. 그래서 실무에서는 강한 일관성을 일부 희생하는 대신 가용성과 서비스 간 느슨한 결합을 지키는 쪽으로 타협하는 경우가 많은데, 이 타협을 구조화한 패턴이 바로 Saga입니다.

 

핵심 개념 1 — 로컬 트랜잭션 연쇄와 보상 트랜잭션

Saga의 기본 골격은 단순합니다. 전체 비즈니스 트랜잭션을 T1, T2, ..., Tn이라는 로컬 트랜잭션의 순차 실행으로 쪼개는데, 각 단계는 자신이 속한 서비스의 로컬 DB에서만 커밋되는 일반적인 트랜잭션입니다. 문제는 중간 단계가 실패했을 때인데, 이미 커밋된 앞 단계들은 물리적으로 롤백할 수 없으므로 대신 보상 트랜잭션(compensating transaction)을 실행해 그 효과를 의미적으로 상쇄합니다.

즉 "커밋을 취소한다"가 아니라 "커밋된 결과를 지우는 새로운 트랜잭션을 실행한다"는 접근입니다. 재고를 차감했다면 보상은 재고를 다시 늘리는 트랜잭션이고, 결제를 승인했다면 보상은 환불 트랜잭션입니다. 이 때문에 Saga는 원자성을 전통적 의미가 아니라 "결국에는 모든 단계가 성공하거나, 실패한 단계까지의 효과가 모두 보상된다"는 완화된 의미로 보장합니다.

 

핵심 개념 2 — 오케스트레이션 vs 코레오그래피

오케스트레이션(Orchestration) 방식은 중앙의 오케스트레이터가 각 서비스에게 다음에 무엇을 할지 명령을 내리고, 결과를 받아 다음 단계를 결정하는 구조입니다. 오케스트레이터가 Saga 전체의 상태 기계를 소유하며, 어느 단계까지 진행했는지, 실패 시 어떤 보상을 어떤 순서로 호출해야 하는지를 스스로 알고 있습니다.

코레오그래피(Choreography) 방식은 중앙 조정자 없이, 각 서비스가 이벤트 브로커를 통해 이벤트를 발행하고 구독하며 다음 행동을 스스로 결정합니다. 주문 서비스가 "주문 생성됨" 이벤트를 발행하면 결제 서비스가 이를 구독해 결제를 처리한 뒤 새 이벤트를 발행하고, 재고 서비스가 다시 이를 구독하는 식으로 트랜잭션이 서비스 사이를 이어 달리듯 전파됩니다.

 

두 방식 비교
구분 오케스트레이션 코레오그래피
흐름 제어 중앙 오케스트레이터가 전체 순서를 명령 각 서비스가 이벤트를 보고 자율적으로 판단
서비스 간 결합도 오케스트레이터-서비스 간 결합은 있으나 서비스끼리는 분리 이벤트 스키마를 통한 암묵적 결합
전체 흐름 파악 오케스트레이터 코드 하나만 보면 됨 여러 서비스의 이벤트 핸들러를 추적해야 함
단일 장애점 우려 오케스트레이터 자체가 병목·장애점이 될 수 있음 집중된 장애점은 없으나 이벤트 유실 시 추적이 어려움
적합한 규모 단계가 많고 분기 로직이 복잡한 트랜잭션 단계가 적고 결합 최소화가 우선인 경우

 

실무에서는 참여 서비스 수가 늘고 실패 시 분기 로직이 복잡해질수록 오케스트레이션 쪽이 전체 흐름을 추적하기 쉬워 선호되는 경향이 있고, 반대로 단계가 단순하고 서비스 간 결합을 최소화하는 것이 우선이라면 코레오그래피가 자연스럽다는 것이 일반적으로 언급되는 경험칙입니다. 다만 이는 팀 구조와 관측 가능성 인프라 성숙도에 따라 달라질 수 있어 절대적인 기준은 아닙니다.

 

예제 — 주문·결제·재고 시나리오의 보상 트랜잭션

아래는 "주문 생성 → 결제 승인 → 재고 차감" 순서로 진행되다가 재고 차감 단계에서 실패했을 때, 오케스트레이터가 보상 트랜잭션을 역순으로 호출하는 흐름을 의사코드로 표현한 것입니다.

# 오케스트레이션 방식 Saga 의사코드
def order_saga(order):
    completed_steps = []
    try:
        order_id = order_service.create_order(order)
        completed_steps.append(("order", order_id))

        payment_id = payment_service.charge(order.customer, order.amount)
        completed_steps.append(("payment", payment_id))

        inventory_service.reserve_stock(order.items)  # 재고 부족으로 실패했다고 가정
        completed_steps.append(("inventory", order.items))

    except SagaStepFailed as e:
        # 성공했던 단계를 역순으로 보상
        for step_name, step_data in reversed(completed_steps):
            if step_name == "payment":
                payment_service.refund(step_data)       # 보상: 결제 취소(환불)
            elif step_name == "order":
                order_service.cancel_order(step_data)   # 보상: 주문 취소 상태로 전환
        raise

 

같은 시나리오를 코레오그래피 방식으로 표현하면 아래와 같이 이벤트 발행·구독의 연쇄로 흐름이 흩어져 나타납니다.

# 코레오그래피 방식 이벤트 흐름 (동일 시나리오)
1. OrderService  --publish--> "OrderCreated"
2. PaymentService --subscribe "OrderCreated"--> 결제 승인 --publish--> "PaymentCompleted"
3. InventoryService --subscribe "PaymentCompleted"--> 재고 확인 --재고 부족-->
   --publish--> "InventoryReservationFailed"
4. PaymentService --subscribe "InventoryReservationFailed"--> 환불 처리
   --publish--> "PaymentRefunded"
5. OrderService   --subscribe "PaymentRefunded"--> 주문 상태를 '취소'로 전환

두 방식 모두 결과(재고 부족 시 결제 환불, 주문 취소)는 같지만, 오케스트레이션은 실패 처리 순서가 한 함수 안에 명시적으로 드러나는 반면 코레오그래피는 그 순서가 여러 서비스의 이벤트 구독 관계에 흩어져 있다는 차이가 코드 형태로도 그대로 드러납니다.

 

실무 도입 시 이것만은 챙기세요
1. 멱등성(idempotency)은 선택이 아니라 전제 조건입니다 — 메시지 브로커는 대부분 최소 한 번 전달을 보장하므로, 같은 명령·이벤트가 중복 도착해도 결과가 달라지지 않도록 설계해야 합니다
2. 보상 트랜잭션이 항상 완벽하게 되돌릴 수 있는 것은 아닙니다 — 이미 출고된 배송처럼 물리적으로 되돌릴 수 없는 부작용은 "취소"가 아니라 "사후 조치"에 가까워집니다
3. Saga 진행 중에는 중간 상태가 다른 요청에 노출될 수 있습니다 — 격리성이 전통적 트랜잭션만큼 보장되지 않으므로, 조회 API에 "처리 중" 상태를 노출하는 등 보완이 필요합니다
4. 오케스트레이터 자체의 상태도 영속화해야 합니다 — 오케스트레이터 프로세스가 중간에 죽어도 진행 상태를 복구할 수 있도록 DB 등에 기록해 두어야 합니다

 

마무리 — 3줄 요약

① Saga는 2PC의 블로킹 문제를 피하기 위해 하나의 비즈니스 트랜잭션을 로컬 트랜잭션들로 쪼개고, 실패 시 보상 트랜잭션으로 앞선 단계의 효과를 상쇄하는 패턴입니다.
② 오케스트레이션은 중앙 오케스트레이터가 전체 흐름을 명령·추적해 복잡한 분기 처리에 유리하고, 코레오그래피는 이벤트 기반으로 서비스가 자율적으로 반응해 결합도를 낮추지만 전체 흐름 파악이 어려워집니다.
③ 실무 적용 시에는 멱등성 보장과 보상 트랜잭션 설계(특히 되돌릴 수 없는 부작용 처리)가 패턴 자체보다 더 까다로운 문제인 경우가 많습니다.
